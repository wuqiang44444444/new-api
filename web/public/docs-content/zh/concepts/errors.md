# 错误与重试

先根据 HTTP 状态决定是否重试，再读取公开错误信封中的 `error.type`、`error.code` 和 `error.message`。不要依赖上游原始错误文本。

## HTTP 状态

| 状态  | 含义                       | 默认策略                   |
| ----- | -------------------------- | -------------------------- |
| `400` | 请求字段、格式或状态不合法 | 修正请求，不重试           |
| `401` | 鉴权失败                   | 修复 Key，不重试           |
| `403` | 权限或模型访问被拒绝       | 修复权限，不重试           |
| `404` | 资源或任务不存在           | 检查 ID 与所属用户         |
| `409` | 幂等冲突或资源状态冲突     | 读取错误码后决定           |
| `429` | 频率、并发或额度限制       | 按指数退避并加入抖动       |
| `5xx` | 服务暂时不可用             | 对可安全重放的请求有限重试 |

## 错误信封

```json
{
  "error": {
    "message": "request cannot be completed",
    "type": "invalid_request_error",
    "param": null,
    "code": "invalid_request"
  }
}
```

不同原生协议可能使用自己的公开错误信封。客户端应先按所调用的协议解析，不能只判断错误文本。

## 安全重试

使用指数退避，例如 1 秒、2 秒、4 秒，并加入随机抖动。限制总次数和总等待时间。

- 查询请求通常可以重试。
- 流式请求只在尚未收到业务数据时重试。
- 创建媒体或素材的请求应使用该接口支持的幂等机制。
- 客户端超时不代表服务端一定没有接收请求；先查询任务或使用原幂等键确认。

## 限流与计费

限流、并发和额度是不同约束。降低请求频率不能修复余额不足；切换模型可能改变计费和权限。始终保存自己的请求 ID、时间、模型与任务 ID，排障时不要记录完整敏感输入。
