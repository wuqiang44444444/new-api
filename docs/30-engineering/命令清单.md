# 命令清单

## Backend

- `go test ./...`
- `go run main.go`

涉及 Seedance Channel、Task、无状态素材代理或 Provider relay 时，至少执行：

```bash
go test ./model ./middleware ./controller ./service ./relay/...
go vet ./model ./middleware ./controller ./service ./relay/...
```

涉及 `relaykit/` 或其公开 API 时，根模块测试不能替代独立构建：

```bash
cd relaykit && GOWORK=off go build ./...
```

## Seedance 价格迁移与盘点工具

只读盘点（脱敏矩阵：模式、表达式当前合同、预扣数值边界、依赖、未完成资金）：

```bash
go run ./cmd/seedance-p0-inventory -dsn <sqlite 快照>
```

盘点同时统计 Task 与创建 attempt 的状态/持款状态；没有 Task 或当前渠道已删除的冻结 ModelArk V3
attempt 仍纳入。Task 全部 settled 不代表 unknown/held 已清零。无效配置 JSON 会终止盘点，
不得将不完整读取当作通过结果。

价格表达式迁移预览与批次生成（工具从不写数据库；`-emit` 只输出变更批次 JSON，
维护窗口内经现有模型价格事务应用；输入须为切换前的旧计价快照；纯常量没有可证明的来源单位，工具拒绝自动缩放，须明确配置美元价）：

```bash
go run ./cmd/seedance-price-migrate -dsn <sqlite 快照>
go run ./cmd/seedance-price-migrate -dsn <sqlite 快照> -emit changes.json -models m1,m2
```

Channel 保存、Task/attempt、素材代理和计费结构必须同时验证 SQLite、MySQL 与 PostgreSQL。CI 在
`.github/workflows/ci.yml` 提供 disposable MySQL/PostgreSQL 服务；本地只跑 SQLite 不能作为三数据库
通过结论。

## 历史任务日志补修

`repair-task-billing-logs` 只处理主库/日志同库的本地 SQLite，默认预览，写入要求新备份路径；
实际补修前须先在一致性副本上验证，确认非日志表与既有日志金额不变后再应用到目标本地数据库。
目标库必须已经完成账单版本表迁移；工具不自动迁移，也不以“版本表为空”跳过保护。
正式写入前通过独立维护操作持久关闭确认，取得 generation；`-apply` 必须同时传入当前
`-maintenance-generation` 和新备份路径。补修事务锁定并复核维护代际，失败或中断不退出维护。
维护控制与审计是该流程允许修改的辅助事实；用户余额、累计用量、Key 余额与 Task 结算事实不改。
必须指定客户、API Key、模型和不超过 31 天的完整生命周期范围。默认修正有冻结证据的元数据；
`-link-initial-logs` 仅按 Task、attempt 与日志中完全一致的冻结 Provider 请求 ID、客户/Key/应用/渠道/模型
以及唯一已转移 hold 关联旧初始日志；不按时间接近或金额相等猜测归属。
`-repair-create-task-id` 显式补一条由唯一已转移 hold 证明的初始日志，
`-repair-final-task-id` 显式补一条由已结清 Task 与唯一初始日志证明的完成日志，包含零差额。
冻结参数表达式可用于重算验证金额；无法确认 Token 计量时保留未知分类，不制造 Token 用量。
带明确失败/欠费状态且金额、用量均为零的诊断日志保留原样；不能重写为调整日志而重复计入最终用量。
存在在线日志交付记录、合同限制、冲突行或证据缺失时拒绝。补修不会触发资金或重建历史看板。

```bash
go run ./cmd/repair-task-billing-logs -dsn <SQLite副本> -user-id <客户ID> -token-id <KeyID> -model <客户模型> -start <Unix秒> -end <Unix秒>
```

报告同时给出净额差异、归属缺失、最终日志缺失及用量不一致；不能仅凭净额相等视为通过。

```bash
go run ./cmd/repair-task-billing-logs -dsn <目标SQLite库> -maintenance begin -operator-id <启用的Root用户ID> -evidence <批准清单索引>
go run ./cmd/repair-task-billing-logs -dsn <目标SQLite库> -apply -backup <新备份路径> -maintenance-generation <返回的代际> -user-id <客户ID> -token-id <KeyID> -model <客户模型> -start <Unix秒> -end <Unix秒>
go run ./cmd/repair-task-billing-logs -dsn <目标SQLite库> -maintenance end -maintenance-generation <同一代际> -operator-id <Root用户ID> -evidence <逐笔核验结果索引>
```

结束维护不会自动开启确认。MySQL/PostgreSQL 不得套用 SQLite 补修命令；维护与版本模型使用跨库
实现，历史补修入口仍需针对目标数据库验收。滚动升级前关闭确认，所有写入及后台实例升级后再开放；
旧实例不具备新解析版本校验，不能靠新实例的检查约束旧实例。
已确认月份不重写原版本及产物；补修来源后通过更正草稿发布客户可见原因和差额。旧草稿因维护代际
变化被拒绝；解析规则变化的待确认草稿被标记失效并释放占位，重新生成后才可确认。

### 零金额持款投影补正

仍使用同一个 SQLite 专用工具，先只读生成完整清单。仅审核并批准清单中的可证明项，排除项不得被
当成追加收费或累计校准依据。清单包含行标识与证据摘要，不包含私有 Task 内容。

```bash
go run ./cmd/repair-task-billing-logs -dsn <一致性副本> -hold-plan <新清单路径>
go run ./cmd/repair-task-billing-logs -dsn <目标SQLite库> -maintenance begin -operator-id <Root用户ID> -evidence <批准与客户告知依据>
go run ./cmd/repair-task-billing-logs -dsn <目标SQLite库> -hold-apply <审核后清单路径> -approved-plan-sha256 <审核文件摘要> -apply -backup <新备份路径> -maintenance-generation <当前代际> -operator-id <Root用户ID> -evidence <逐笔批准与客户更正通知依据>
go run ./cmd/repair-task-billing-logs -dsn <目标SQLite库> -maintenance end -maintenance-generation <同一代际> -operator-id <Root用户ID> -evidence <补正差额与资金不变核验依据>
```

清单文件 SHA-256 可用 `shasum -a 256 <审核后清单路径>` 核对。审核后删减候选必须重新核对摘要。
执行重读 Task、attempt、完整关联日志与人工退款引用，证据变化整批回滚；同一清单重跑为 0 行。
这一路径只补正缺少的已转移持款投影，不增加 Token、不改资金；原零值诊断字段保留并增加管理员
补正审计。它不能与旧 user/key/model/time scope 参数混用。

外部维护命令写入的开关通过各节点 `SyncOptions` 周期同步（默认 60 秒）。确认节点已观察关闭即可，
无需机械重启；最终确认以数据库开关和代际为准。维护窗口须考虑 SQLite 写锁影响，结束后仍需人工
恢复确认，已有确认月份按更正版本发布，不覆盖旧版。完整准入与验收见
[历史解析与持款补正记录](../80-dev/2026-09-18-账单历史解析与持款投影补正.md)。

## Synlink 历史失败任务单笔恢复

```bash
go test ./cmd/recover-synlink-failure ./common -run 'TestSynlink' -count=1
go run ./cmd/recover-synlink-failure -database <SQLite文件> -task-id <公开TaskID> -user-id <客户ID> -app-id <应用ID> -channel-id <渠道ID> -operator-id <Root用户ID> -expected-quota <占用quota> -evidence-ref <证据索引>
```

默认只读预览；只适用于冻结 Synlink 1.3.3 的已核实失败任务。写入要求主库与日志／审计同库、
全部节点停机、部署未使用 Redis、新备份路径及显式失败确认。作用为记录单笔人工终态并复用既有
幂等退款和日志交付，不进行 Provider 查询或重发，不迁移冻结插件版本。
完整核实、执行和中断恢复步骤见[Synlink 失败任务处置手册](../40-operations/Synlink失败任务处置手册.md)。

## Docs

- `task docs:check`
- `task ai:check`
- `task docs:new-adr -- title=决策标题`

文档收敛或归档前必须同时执行 `task docs:check` 与 `task ai:check`。归档只允许新增目标不存在的
历史文件；执行前后用 `git status --short -- docs/99-archive` 确认没有任何既有归档文件被修改、删除
或重命名。
