# 人工智能编码指南

## Before Any Task
1. 读 AGENTS.md 与 docs/README.md。
2. 读 docs/00-context/硬约束.md。
3. 改架构前读 docs/20-architecture/架构概览.md。
4. 涉及 tiered/dynamic billing 前读 `pkg/billingexpr/expr.md`。
5. 新建文档前先读目标目录的 README.md，确认放对位置。
6. 涉及从最上游接取、同步或升级代码时，必须先读 `docs/30-engineering/上游代码合并指南.md`，并先确定本地非业务定制白名单。

## Verification
- 后端改动：优先跑相关包测试；范围不清时跑 `go test ./...`。
- 前端改动：在 `web/` 下使用 Bun 跑对应检查或构建。
- 文档改动：跑 `task docs:check` 与 `task ai:check`。
- 上游同步：验证非白名单业务文件与上游目标提交完全一致，并给出数据库是否需要更新的明确结论；涉及数据库变化时必须验证 SQLite、MySQL、PostgreSQL。

## Boundaries
- 只改与任务相关的代码，不顺手重构。
- 不删除、替换或弱化受保护项目身份、组织/作者身份、授权、署名和元数据。
- 数据库、认证、计费、限流、Provider relay 行为改动必须保留可验证的回归路径。
- 重大架构决策必须新增 ADR。
- 上游同步时，业务逻辑必须按文件整体以上游覆盖，禁止选择性摘取代码块或保留未批准的本地业务分叉。
- 编码过程临时问题分析/方案放 `docs/80-dev/`，文件名必须以 `YYYY-MM-DD-` 开头。

## 编码质量守则

- 默认只审查本次改动及直接影响链；未经明确要求，不扩大为全库审计或顺手重构。
- 实现前先搜索现有入口、类型和工具，避免新增语义重复或并行实现。
- 仅当存在多个真实调用方、语义稳定且归属明确时抽取公共逻辑；不得仅为消除局部重复创建通用 utils、策略或钩子。“最小入侵”优先。
- 判定死代码前必须核对调用、路由/注册、接口实现、反射、配置、脚本和测试入口；证据不足标记为“疑似”，不得直接删除。
- 审查优先级：正确性、安全、数据、计费与接口契约 > 死代码、重复实现与类型问题 > 命名和格式。
- 修改后执行与风险匹配的测试和检查；前端使用 Bun 的 typecheck、lint、format:check、build，死代码专项可使用 knip。
- 用户明确要求全面审计时，按“严重/建议/疑似”输出；每项包含置信度、文件与行号、证据、影响、最小修改方向和验证方式，最后给出健康度评分及前三项优先改进点。
