# 上游代码合并指南

## 一、目的与适用范围

本指南适用于从项目最上游仓库、上游主分支或指定上游发布版本接取代码的所有场景，包括定期同步、版本升级、安全修复和紧急补丁同步。

本项目采用“上游业务逻辑优先、本地非业务定制白名单保留”的合并策略。核心目标是避免本地业务分叉、选择性合并和长期维护隐性补丁。

## 二、硬性原则

### 2.1 业务逻辑以上游为唯一事实源

- Router、Controller、Service、Model、Relay、Middleware、Setting、DTO、Types、OAuth、`pkg/` 等业务与运行逻辑，必须完整以上游版本为准。
- 上游修改过的业务文件必须按文件整体直接覆盖本地版本，包括上游的新增、删除、重命名和目录调整。
- 禁止按代码块挑选上游改动，禁止在同一业务文件中混合保留本地旧实现，禁止为了减少冲突而只摘取“看起来需要”的部分。
- 若本地业务逻辑与上游冲突，先完整采用上游实现。本地业务诉求必须作为独立需求重新评估，并优先提交到上游解决，不得在同步过程中暗中保留本地分叉。

### 2.2 本地保留项必须使用白名单

默认允许评估保留的仅限非业务定制：

- 首页展示、首页专属交互与首页内容编排。
- 纯视觉样式、主题、品牌展示资源和静态素材。
- 与具体部署环境绑定、且不改变业务语义的本地配置。

每次同步前必须列出本次保留白名单。未进入白名单的文件一律按业务文件处理并以上游覆盖。“首页、样式等”中的“等”不得被自行扩大解释；新增例外必须获得明确批准并写入本次合并记录。

### 2.3 数据库检查是合并完成的前置条件

任何上游同步都必须检查数据库结构、迁移与数据语义是否需要更新。没有完成数据库检查和兼容性验证，不得宣布合并完成。

## 三、标准合并流程

### 3.1 建立可追溯基线

1. 确认本地目标分支、上游远端和上游目标提交。
2. 记录同步前本地提交、上游提交及两者共同祖先。
3. 确认工作区现有修改的归属；不得覆盖、清理或提交与本次同步无关的用户修改。
4. 建立可恢复的备份分支或等价保护点，再开始覆盖操作。

建议记录：

```text
本地基线：<local-commit>
上游目标：<upstream-commit>
共同祖先：<merge-base>
本地保留白名单：<paths>
```

### 3.2 先分类，再覆盖

先查看上游从共同祖先到目标提交的完整文件变更：

```bash
git fetch upstream
git diff --name-status <merge-base>..<upstream-commit>
```

将文件分为两类：

1. **本地非业务定制白名单**：首页、样式、品牌资源等明确批准的路径，允许人工审查并适配合并。
2. **业务逻辑与其他非白名单文件**：必须直接采用上游完整文件状态，不做逐块融合。

覆盖时必须同时处理：

- 上游新增文件：完整加入。
- 上游修改文件：以目标上游提交中的完整文件覆盖。
- 上游删除文件：本地同步删除，不得因本地仍有引用而私自保留；应继续修正本地非业务定制中的引用。
- 上游重命名或移动文件：遵循上游新路径，不保留旧路径副本。

### 3.3 冲突处理规则

- 业务文件发生冲突时，直接选择上游文件版本，不允许手工拼接双方代码。
- 白名单文件发生冲突时，先保留上游新增契约、组件 API 和运行边界，再重新适配本地展示。
- 如果首页或样式依赖了已经被上游删除或修改的业务接口，只能修改本地首页或样式适配新接口，不能回退上游业务代码迁就旧页面。
- 任何无法按上述规则解决的冲突都必须停止合并并记录阻塞原因，不得用临时兼容分支绕过。

## 四、数据库更新与匹配检查

### 4.1 必查内容

逐项检查上游是否改变了：

- GORM Model 字段、类型、默认值、索引、唯一约束、外键和表名。
- `AutoMigrate`、显式迁移逻辑、初始化逻辑及数据库启动顺序。
- 枚举值、状态值、配置键、计费字段、额度字段及其数据语义。
- 查询条件、排序规则、锁行为、事务边界和原始 SQL。
- 需要回填、重算、清洗、重命名或删除的历史数据。
- 新旧版本并行运行时的向前兼容与向后兼容要求。

### 4.2 三数据库兼容性

数据库变更必须同时检查并匹配：

- SQLite
- MySQL >= 5.7.8
- PostgreSQL >= 9.6

不得只在当前开发数据库验证。涉及原始 SQL、列类型、布尔默认值、索引、锁或 `ALTER TABLE` 时，必须逐一确认三种数据库的行为与回退路径符合项目硬约束。

### 4.3 数据库结论必须明确

合并记录必须给出下列结论之一：

- **无需更新**：说明已检查的 Model、迁移和数据语义范围，以及为何无需变更。
- **需要更新**：列出迁移内容、执行顺序、数据备份、回填方案、回滚方案和验证结果。
- **暂时阻塞**：说明未确认的数据库风险；在风险关闭前不得发布或宣布合并完成。

仅写“未发现问题”不构成有效数据库检查结论。

## 五、验证门禁

### 5.1 上游一致性检查

合并后必须确认：

- 所有非白名单业务文件与上游目标提交完全一致。
- 最终差异只存在于本次批准的本地非业务定制白名单中。
- 上游删除、重命名和新增文件均已完整同步。
- 仓库中不存在被遗忘的旧实现、兼容副本或同名替代文件。

建议对业务路径执行目录级差异检查：

```bash
git diff --exit-code <upstream-commit> -- \
  router controller service model relay middleware setting dto types oauth pkg
```

如果某个业务路径被列入差异结果，必须先消除差异或取得明确例外批准，不能直接进入测试阶段。

### 5.2 工程验证

至少执行：

```bash
go test ./...
cd web
bun run typecheck
bun run lint
bun run build
```

根据上游改动范围追加 Provider、计费、认证、额度、限流、任务结算和 API 契约测试。测试通过不能替代上游文件一致性检查，也不能替代数据库检查。

### 5.3 数据库验证

涉及数据库变化时，至少完成：

1. 空数据库初始化。
2. 现有版本数据库升级。
3. 关键数据读取与写入回归。
4. 索引、约束和默认值核对。
5. SQLite、MySQL、PostgreSQL 三种数据库验证。
6. 备份恢复或回滚方案演练，或给出明确的不可逆变更说明与发布批准。

每次上游同步必须保留以下记录：

- 本地保留白名单：

## 七、禁止事项

- 禁止把业务冲突解释为“本地定制”并继续保留。
- 禁止只同步能够编译的部分而遗漏上游删除、迁移或数据语义变化。
- 禁止仅凭应用启动成功判断数据库已经匹配。
- 禁止在没有三数据库兼容结论时合并数据库相关上游变化。
- 禁止在业务文件仍与上游存在未批准差异时宣布同步完成。
- 禁止用后续修复承诺替代当前合并门禁。
