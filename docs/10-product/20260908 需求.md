场景：gpt-5.6-sol模型，给用户suxuehua配置prc-gpt-ap路由组和prc-gpt-azure路由组，prc-gpt-ap路由组的合同折扣为0.25，prc-gpt-azure路由组的合同折扣为0.55折，目前添加prc-gpt-ap的gpt-5.6-sol模型进合同之后，再选择prc-gpt-azure路由组就无法看到gpt-5.6-sol。

# 需求分析（2026-09-08，基于当前代码核实）

结论：需求 2、3 边界清晰可直接排期；需求 1 存在两个必须先拍板的产品决策，否则无法开工。

## 需求 1：厂商特殊服务档位（Batch / Fast / Flex / Priority）

### 现状

| 环节 | 现状 |
| --- | --- |
| 请求侧 | `service_tier` 字段在 OpenAI/Claude/Responses DTO 中已存在，但被默认过滤（`relay/common/relay_info.go:1112`），仅渠道开启 `allow_service_tier`（`relaykit/dto/channel_settings.go:74`）才透传 |
| 计费侧 | 完全没有"档位"维度。即使透传了 `service_tier: priority`，仍按标准价计费——2x/1.8x 档位存在漏费路径，0.5x 档位平台白赚差价 |
| Batch | 未接入任何厂商 Batch API（无 `/v1/batches`、`/v1/messages/batches` 路由）。厂商 Batch 是异步文件作业（上传文件→建 batch→轮询），与本站同步 relay 是两种形态 |
| 计费扩展点 | `types/price_data.go` 的 `OtherRatios` + `relay/helper/price.go:124-133` 的 `model_ratio × group_ratio × 合同折扣` 链路是现成的倍率挂载点 |

### 必须先确认的两个决策

1. 档位的北向表达：客户端怎么选档位？
   - 原生 `service_tier` 参数（OpenAI/Claude 天然有；Gemini 没有对应字段）；
   - 模型名变体（如 `gpt-x-batch`，走 `model_mapping` 映射）；
   - 自定义 header。
2. Batch 的履约语义：真·上游 Batch API（异步作业，需要新建 relay format + Task 生命周期 + 文件代理，工作量大一档），还是仅作为"价格档位"同步调用按 5 折计费？需求原文按字面读更像后者，但需确认。

### 其他待确认

- Gemini 的 Flex/Priority 在官方 API 无同名档位，需与实际上游（可能是聚合渠道）确认真实参数映射——属于线下模型兼容性审核范畴。
- 档位倍率与路由组倍率、合同折扣的叠加顺序（预期：标准价 × 路由组 × 合同折扣 × 档位倍率）。
- 档位支持度的配置粒度（模型级/渠道级），以及不支持组合必须 fail-closed 明确拒绝，不能静默降级标准价。
- 定价页需展示档位价（与需求 3 的展示修复同域）。

## 需求 2：合同明细唯一约束改为【模型 + 路由组】

### 唯一性目前散布在四层，需同步改

| 层 | 位置 | 现状 |
| --- | --- | --- |
| DB 约束 | `model/customer_contract.go:25-26` | `uniqueIndex` 仅 (user_id, public_model)；已有专门迁移 `model/customer_model_contract_uniqueness_migration.go`（Option marker 幂等模式，可仿照新增三列版本迁移） |
| 保存校验 | `model/customer_contract.go:327-331` | `normalizeCustomerContractRules` 按 lower(model) 去重，需改 (model, route_group) |
| 请求时解析（核心） | `service/customer_contract.go:101-109` | `ResolveCustomerContractRule` 按 model 首个匹配，然后把 `fact.RouteGroup` 写成 UsingGroup/TokenGroup（`middleware/customer_contract.go:42-45`）。同模型多条规则时选哪条直接决定南向渠道和计费折扣，选错=按错误折扣计费 |
| 前端 | `web/src/features/users/components/user-contract-add-rule.tsx:43-46` | 过滤"任何组已有"的模型（就是需求里说的"看不到 gpt-5.6-sol"的直接原因）；文案 "Each public model can bind to exactly one route group" 需改；`user-contract-rule-list.tsx:67` 和 `user-contract-drawer.tsx:158-193` 的 `key={rule.model}` / 重复校验需改为组合键 |

### 关键设计问题（需产品拍板）

同模型多条规则在请求时如何选取？最自然的依据是 token 分组（`middleware/auth.go:463` 在合同模式下恰好跳过了 token 分组判断，有现成钩子）：

- token 分组 = prc-gpt-ap → 用 prc-gpt-ap 那条折扣；
- token 分组为空 / `auto` / 与任何规则的 route_group 都不匹配时的行为（拒绝？回退？）必须定义。

另外三个连带点：

- 用户侧视图 `CustomerContractUserRuleView` 目前没有 route_group 字段，必须补，否则用户看到同模型多行无法区分；`customer-contract-pricing.tsx:88` 的 `key={rule.model}` 会重复。
- 日志目前只记 `contract_version/contract_discount`（`service/customer_contract_billing.go`），建议补记 route_group 便于对账。
- `BuildCustomerContractPricing`（`service/customer_contract_pricing.go:17`）会为同模型输出多条 Pricing 条目（model_name 重复），定价页前端索引需兼容。

## 需求 3：合同用户阶梯价格详情空白

根因已定位，高置信，是前后端配合缺失，不是数据坏了：

1. 后端 `service/customer_contract_view.go:110-114`：`tiered_expr`（阶梯计费）模型在 `buildCustomerContractPricePreview` 中提前返回，只给 `price_type: "tiered_multiplier"`，不带任何价格数据和 billing_expr。
2. 前端 `web/src/components/contract-price-details.tsx:172-232`：展开详情只有 `model_price` / `model_ratio` 两个分支，`tiered_multiplier` 分支什么都不渲染 → 点开就是一个空白盒子。这正是需求描述的现象。

修复方向：后端在合同价格视图带上阶梯数据（`billing_expr` + `billing_usage_schema`，前端已有现成的 `DynamicPricingBreakdown` 解析渲染），并按该行有效倍率折算展示。该组件被 admin drawer 和用户 keys 页共用，一次修复两处生效。

## 需求间的耦合与排期建议

- 需求 2 ↔ 需求 3 强耦合：需求 2 的"点开阶梯价格详情，展示当前选中这一行折扣对应的阶梯价格"就是需求 3 组件的扩展（每行不同倍率）。建议需求 3 先修（独立可交付），需求 2 在其上叠加多行区分。
- 需求 1 独立，但依赖两个产品决策；其计费挂载点与合同折扣同链路，实现时需一并验证叠加后的 pre-consume/结算（遵循 `common/quota_math.go` 饱和约束）。
