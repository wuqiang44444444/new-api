# 客户与上游对账单产品说明

## 1. 文档定位

本文定义客户账单和上游对账的目标产品行为。它是待实现、待验收的产品要求，不表示相关能力已经
生产发布。

当前平台已经具有 Request ID、用量日志、结算日志和账单明细入口。本产品不建立第二套 Request ID
或在账单主页复制请求明细，而是在现有事实之上提供月度汇总、模型聚合和带筛选条件的明细链接。

普通用户从“我的账单”入口查看自己的账单；平台管理员从独立的“账单对账”入口进入，并通过
“客户账单”和“上游对账”两个一级 Tab 切换。管理员也可以从“我的账单”查看自己的用户账单。
两个管理 Tab 使用两套独立口径：客户账单回答“客户用了多少、应付多少”；上游对账只回答“平台
数据库记录了各渠道和 Provider 模型多少用量”。平台没有供应商账单接口时，不录入、模拟或比较
供应商侧 Token、次数和金额。

## 2. 产品目标

1. 用户打开账单后先看到金额汇总，不需要先浏览请求明细。平台管理员进入“客户账单”时，先看到整个账期的全客户汇总和客户账单列表，再选择客户下钻。
2. 平台管理员从客户账单列表下钻某个用户后，可以在“渠道”和“API Key”两个维度间切换；每个维度下展示模型
   汇总，不能展示一条条请求记录。
3. 模型汇总同时支持按 Token 收费和按次收费，并明确展示计费方式、用量、原价、折扣和实付金额。
4. 上游对账只展示平台数据库已有用量：按 Token 收费的模型展示各类 Token，按次收费的模型展示
   平台记录的计费次数；不创建未知的供应商侧数值。
5. 每个渠道的每个 Provider 模型可以按月设置上游折扣；新月份复制上一个自然月的值，上月没有值
   时使用 `1`。
6. 历史账单使用请求发生时的价格和折扣快照，不因当前价格、用户折扣或上游折扣变化而改变。
7. 页面上的汇总、筛选、折扣、平台侧上游用量、余额和审计结果全部以数据库持久化事实为准。

## 3. 角色与权限

系统只有两个账单角色：

| 角色 | 可见范围 | 允许操作 |
| --- | --- | --- |
| 用户 | 自己的金额汇总、API Key → 客户模型汇总、余额流水和明细链接 | 查询、筛选、下钻和导出自己的账单 |
| 平台管理员 | “客户账单”Tab 中全客户账期列表及任一用户的两种客户汇总；“上游对账”Tab 中平台记录的全部渠道用量 | 查询、录入上游折扣和发起余额调整 |

“我的账单”和“账单对账”必须使用独立路由和独立侧栏入口。`/billing` 对所有已登录用户开放，且始终
只查询当前登录用户；`/admin/billing` 仅平台管理员可进入，非管理员必须被前端路由和后端接口同时
拒绝。普通用户页面不得渲染客户数量、客户搜索、客户列表或上游对账控件。

渠道维度和上游对账只对平台管理员开放。用户不看到 Provider 账号、真实 Provider 模型、Provider
成本、内部实现或其他管理员审计字段。API Key 只显示名称和稳定 ID，不显示密钥值。

## 4. 数据权威与展示边界

- 主数据库保存用户、API Key、渠道、余额流水、上游折扣和人工审计事实。
- 日志数据库保存现有 Request ID、请求用量、计费结果、渠道和模型等请求级事实。
- 客户汇总和平台侧上游用量只能由后端查询数据库产生；前端不得把已加载的部分明细自行汇总为
  正式账单，也不得用浏览器状态补齐缺失数据。
- 平台侧上游 Token 和计费次数只从日志数据库读取；上游折扣必须先成功保存到主数据库。不得增加
  供应商账单录入表单、供应商用量字段、双方差异字段或对账处理状态来补充平台并不知道的事实。
- Redis、进程缓存、React Query 缓存和页面状态只用于性能或交互，均可重建，不能成为账单权威。
- 缓存与数据库不一致时，以数据库为准；账单接口必须返回数据生成时间和数据库事实版本或账期版本。
- 数据库缺少某项历史用量、价格或折扣时必须显示“未知”或“不可用”，不得从当前配置、页面合计、
  Provider 金额或缓存值反向推断。
- 页面导出必须由后端按相同数据库查询口径生成，或使用后端返回的完整汇总结果；不能导出仅存在于
  前端的未持久化数据。

## 5. 统一计费口径

### 5.1 两种计费方式

每个模型汇总必须明确标记一种计费方式，不能只展示金额而隐藏计费单位。

| 计费方式 | 主要用量 | 金额计算 |
| --- | --- | --- |
| 按 Token 收费 | 输入 Token、缓存读取 Token、缓存写入 Token、输出 Token | 各类 Token × 各自成交单价后求和 |
| 按次收费 | 总请求次数、计费次数、免费或退款次数 | 计费次数 × 单次成交价 |

同一模型在同一账期存在多种计费方式时，必须拆成独立汇总行，不得把 Token 和次数相加成一个“总量”。
不同模型的 Token 单价、按次价格或计费语义不同，父级渠道和 API Key 只汇总金额与请求数；具体用量
在展开后的模型行查看。

### 5.2 金额精度

- Token、请求次数和计费次数保存原始整数。
- 单次请求金额至少保留 8 位小数，不逐请求四舍五入到分。
- 账期汇总后才按照人民币分展示或结算。
- 页面必须说明币种、金额精度和舍入方式；不得因页面格式化改变账务事实。

### 5.3 价格与折扣快照

- 所有客户价格均属于带生效时间的 PriceBook 版本；调价创建新版本，不覆盖旧版本。
- 请求结算时冻结适用的原价、用户折扣和成交价。
- 按 Token 收费时，输入、缓存读取、缓存写入和输出分别保存单价快照。
- 按次收费时，保存单次原价、用户折扣和单次成交价快照。
- 月度账单直接汇总已经结算的历史金额，不使用当前价格或当前用户折扣重新计算。

用户折扣统一使用系数表达：`1` 表示无折扣，`0.8` 表示按原价的 80% 成交。

## 6. 客户账单 Tab

### 6.1 页面结构

平台管理员在独立“账单对账”页的“客户账单”Tab 按管理员的实际核对顺序分为三层：

1. 当月全客户账单总览和客户账单列表；
2. 点击客户后的单客户账期金额总览，以及按渠道或 API Key 分组的汇总；
3. 展开渠道或 API Key 后的模型用量和金额汇总。

普通用户不经过全客户列表，直接进入自己的账期金额总览与 API Key 汇总。

请求明细不出现在该 Tab。页面只提供“查看明细”链接，跳转到平台现有用量日志或独立明细页，并
自动携带当前用户、账期、渠道、API Key、模型和计费方式等筛选条件。

该 Tab 不提供 Request ID 列表，也不重新设计请求详情。用户发生争议时，通过现有 Request ID 在明细
入口定位原始请求和结算记录。

### 6.2 全客户账单列表

平台管理员进入“客户账单”Tab 时，默认展示当前自然月全部已有账务事实的客户，不要求先选择一个客户。首屏总览至少包含客户数、请求数、原价金额、折扣优惠和净结算金额。

每个客户行至少展示：

- 客户名称、用户名和稳定用户 ID；
- 请求数、原价金额、折扣优惠、实付消费、退款和净额；
- 数据质量与最近账务活动时间；
- “查看账单”下钻入口。

列表支持按客户名称、用户名或 ID 搜索，按数据质量过滤，按金额、请求数或客户排序，并做服务端分页。总览始终是当前全部筛选结果的数据库汇总，不得由当前页行相加。

### 6.3 单客户账期金额总览

页面顶部优先展示：

- 期初余额；
- 本期充值；
- 本期原价金额；
- 本期折扣优惠；
- 本期实付消费；
- 本期退款；
- 本期人工调整；
- 期末余额；
- 账期、币种、结算时区和数据更新时间。

总览必须满足：

```text
期末余额 = 期初余额 + 本期充值 - 本期实付消费 + 本期退款 + 本期调整
```

“客户账单”Tab 不展示 Provider 成本或毛利。历史流水不完整或无法勾稽时，必须显示“不可勾稽”及差额，
不能用估算值填平。

### 6.4 平台管理员的两种汇总维度

平台管理员从账单列表点击某个客户下钻后，可以切换：

```text
渠道 → 客户模型汇总
API Key → 客户模型汇总
```

渠道或 API Key 父级行只展示：请求数、原价金额、折扣优惠、实付消费、退款和净额。展开父级后，
每一行代表一个模型在该账期内的聚合结果，不代表单个请求。

用户自己的账单只提供：

```text
API Key → 客户模型汇总
```

用户不能通过账单推断内部渠道或 Provider 信息。

### 6.5 模型汇总字段

所有模型行共同展示：

- 客户模型；
- 计费方式；
- 请求数和成功/失败数；
- 原价金额；
- 用户折扣；
- 折扣优惠；
- 实付消费、退款和净额；
- “查看明细”链接。

按 Token 收费的模型额外展示：

- 输入 Token 总量；
- 缓存读取 Token 总量；
- 缓存写入 Token 总量；
- 输出 Token 总量；
- 对应的单位价格或“账期内多价格版本”标记。

按次收费的模型额外展示：

- 总请求次数；
- 计费次数；
- 未计费或已退款次数；
- 单次价格或“账期内多价格版本”标记。

同一账期只有一个折扣版本时展示该折扣系数；存在多个价格或折扣版本时显示“多版本”，并展示：

```text
账期有效折扣 = 实付消费 / 原价金额
折扣优惠 = 原价金额 - 实付消费
```

原价金额为零时不计算有效折扣，显示“不适用”。

### 6.6 查询与筛选

- 用户账单：账期、API Key、客户模型、计费方式；
- 管理员客户账单列表：账期、客户搜索、数据质量、排序和分页；
- 管理员单客户下钻：账期、渠道/API Key 汇总维度、客户模型和计费方式；
- 默认进入当前自然月，并支持选择历史自然月；
- 切换渠道/API Key 维度或筛选条件时，顶部金额必须与当前可见汇总一致。

## 7. 余额流水

余额只能由流水累计得到，禁止后台直接覆盖余额。流水至少包含：

| 类型 | 方向 | 关联事实 |
| --- | --- | --- |
| 充值 | 增加余额 | 充值单号 |
| 消费 | 减少余额 | 现有 Request ID 或结算记录 |
| 退款 | 增加余额 | 原 Request ID 和退款原因 |
| 人工调整 | 增加或减少余额 | 唯一调整单号、原因、平台管理员和操作时间 |

已入账流水不可编辑或删除。纠错必须追加冲正或调整流水，并关联原流水。用户可以查看自己的流水；
只有平台管理员可以发起人工调整，且缺少调整单号或原因时不能提交。

## 8. 上游对账 Tab

### 8.1 页面结构

平台管理员账单管理页的“上游对账”Tab，主结构固定为：

```text
上游渠道 → Provider 模型汇总
```

该 Tab 不展示逐请求记录。每个渠道和模型行提供“查看明细”链接，跳转到现有日志或独立对账明细页，
并携带账期、渠道、Provider 模型和计费方式筛选条件。

### 8.2 平台用量口径

按 Token 收费的 Provider 模型展示平台日志已保存的输入、缓存读取、缓存写入和输出 Token；按次收费
的模型展示平台记录的请求数和计费次数。缺失字段显示未知，Token 与次数不能互相换算，也不能跨
计费方式相加。

客户退款日志表示平台对客户的资金调整，不表示供应商已经退款，因此不得从客户退款日志生成上游
退款次数或冲减平台记录的 Provider 用量。

### 8.3 金额展示边界

当前上游对账不展示供应商金额、参考金额或双方金额差异。只有未来平台在请求发生时已经持久化了
独立、可信的 Provider 成本事实，产品重新评审后才可以展示该平台事实；不得通过手工填写供应商账单、
当前价格回算或客户金额反推来补齐。

### 8.4 上游模型月度折扣

上游折扣的业务键为：

```text
账期 + 上游渠道 + Provider 模型 + 计费方式
```

- 折扣由平台管理员手动输入；`1` 表示无折扣，`0.85` 表示内部月度折扣系数为 85%。
- 新账期首次生成时，复制上一个自然月相同渠道、Provider 模型和计费方式的折扣。
- 上月没有记录时使用 `1`；不得继续向更早月份查找并静默继承旧值。
- 复制后形成当前月份自己的版本，修改当前月不会影响上月。
- 空值、非数字、非正数或大于 `1` 的值不能提交。
- 每次修改记录修改前后值、平台管理员、原因和时间。

该折扣是平台内部月度配置，不修改客户成交价，也不得据此生成供应商账单金额。

### 8.5 明确不做的能力

- 不提供供应商账单录入、导入或编辑接口；
- 不保存供应商 Token、次数、退款或实际金额；
- 不计算平台与供应商的差异和差异率；
- 不提供基于未知供应商事实的处理状态或关闭流程。

## 9. 客户收费规则

| 场景 | 按 Token 收费 | 按次收费 |
| --- | --- | --- |
| 成功交付 | 按实际可计费 Token 结算 | 计一次 |
| 平台或上游异常且未交付 | 不收费或全额退款 | 不计次或全额退款 |
| 流式输出被用户中断 | 仅按可信且可计量的已交付 Token 结算；无法确认时不收费 | 按产品合同明确是否已形成一次有效交付 |
| 系统自动重试 | 一个逻辑 Request ID 只结算一次客户 Token | 一个逻辑 Request ID 最多计一次 |
| 余额不足 | 发送 Provider 前拒绝，不允许透支 | 发送 Provider 前拒绝，不允许透支 |

系统重试产生的多次 Provider 用量或计费次数必须分别进入上游对账，但不能导致客户重复收费。

## 10. 账期、数据质量与审计

- 默认结算时区为北京时间 `Asia/Shanghai`（UTC+8），页面、导出和明细链接使用同一账期边界。
- 月账期按该时区自然月计算；跨期退款进入实际退款发生的账期并关联原请求。
- 价格、用户折扣和上游折扣均按生效时间版本化。
- 用户只能读取自己的账单；平台管理员的用户选择、折扣修改和余额调整必须经过权限校验。
- 平台或上游用量缺失时显示“未知”或“上游未提供”，不按当前配置补算，不用金额反推用量。
- 页面查询、筛选或明细链接失败不能修改消费、余额、折扣或对账状态。
- 所有人工调整和上游折扣修改均记录平台管理员、时间、原因和业务单号。

## 11. 交付约束

- 复用 NEWAPI 现有鉴权、用户、API Key、渠道、Request ID、消费日志、退款日志和计费结果，不建立
  平行请求体系或重写原生计费语义。
- 新增账单能力优先放入独立的后端查询、对账服务、数据模型和前端功能模块。
- 原生 Router 和数据库迁移入口只保留必要的注册调用；原生请求、Relay、Provider adapter 和计费
  热路径只允许必要的单行快照调用或极窄分支。
- 不为消除新增模块内的少量局部重复而重构、移动或格式化 NEWAPI 原生文件。
- 每个原生文件修改都必须说明必要性、最小接线点和未来接取上游时的冲突影响；无法说明时不得修改。

## 12. 产品验收标准

### 12.1 客户账单 Tab

- 首屏先展示金额总览，页面上没有逐请求记录表。
- 管理员可以在“渠道 → 模型”和“API Key → 模型”之间切换；两种维度的账期总金额一致。
- 父级展开后每行都是模型聚合结果，模型金额之和等于父级金额。
- 按 Token 模型展示输入、缓存读取/写入和输出 Token 总量；按次模型展示计费次数。
- 每个模型行只有明细链接，链接能正确带入当前筛选条件并使用平台现有 Request ID 定位请求。
- 修改当前价格或用户折扣后，历史账期的原价、折扣和实付金额不变化。
- 刷新页面、切换设备或清空缓存后，账单结果不变化；数据库缺失的数据不会由前端补算。

### 12.2 上游对账 Tab

- 页面按渠道展开到 Provider 模型，不显示逐请求列表。
- 按 Token 模型展示平台记录的各类 Token；按次模型展示平台记录的计费次数。
- 页面不出现供应商侧 Token、次数、金额、差异或录入操作。
- 新月份折扣只复制上一个自然月；上月没有值时为 `1`，修改后不影响上月。
- 系统重试只有在平台留下独立 Provider 用量事实时才进入汇总；客户仍只发生一次有效结算。
- 上游折扣保存成功后重新加载结果一致，且不会生成供应商账单事实。

### 12.3 余额、权限和一致性

- 余额可以由充值、消费、退款和调整流水逐笔复算，平台管理员不能直接覆盖余额。
- 用户只能访问自己的账单和明细链接；渠道、Provider 模型和平台记录的上游用量只对平台管理员开放。
- 按次、按 Token 两种模型不会被合并为同一用量总数。
- 月初边界请求按 `Asia/Shanghai` 唯一归属一个账期。
- 未完成真实数据库用量、权限、金额精度和账期边界验证前，该能力不得标记为生产可用。
- 平台管理员页面固定提供“客户账单”和“上游对账”两个一级 Tab，两个 Tab 的金额和用量口径互不
  覆盖。

## 13. 产品成功指标

- 客户账单主页逐请求记录数为 `0`，所有明细访问均通过带筛选条件的链接完成；
- 两种管理员汇总维度的客户账期金额一致率为 `100%`；
- 数据库已记录上游用量的模型中，Token 或计费次数可完整汇总的比例达到 `100%`；
- 历史账单因当前价格或折扣变化而改变的次数为 `0`；
- 因重试、回调或退款导致的重复客户收费次数为 `0`。
