# 视频创建未知结果长期占款问题分析与退款闭环方案

> 本方案已完成开发与本地验证，最新实施状态以第 9 节为准。前文问题分析和方案阶段记录保留其当时语境；
> 真实 Provider、目标部署灰度及存量资金处置仍需按验收清单完成，不表示已生产发布。

## 1. 问题与目标

用户反馈：视频创建接口已经报错，没有取得可使用的任务或结果，但预扣额度长期不退；客户重新提交
成功后，旧请求仍占用余额。这是重大资金体验与服务履约问题，不能以“上游结果未知”为由无限期
转嫁给客户，也不能仅修正日志文案后认为问题解决。

本次分析的核心结论：**当前实现把“不能确认上游有没有创建任务”与“客户资金必须一直冻结”绑定，
同时缺少有期限、可重试、可审计的客户资金收尾机制。** DNS 等确定未发送的错误被误归为 unknown，
进一步扩大了占款规模。退款不是完全没有实现，而是大量记录既进不了自动退款路径，也没有进入
持续有人处理的人工流程。

目标是让每笔已预扣请求最终有明确资金结果：正常交付并结算，或者释放客户预扣。技术核实可以
继续，客户资金不得无限等待。本文区分两个层次：

1. 当前合同内可以修复的代码缺陷：确定未发送误判、已删除 Key 阻断退款、错误事件诊断缺失。
2. 为落实用户资金保障要求必须调整的产品合同：视频创建异常从预扣成功起满24小时，仍 held 且
   未原子转移到正式 Task 时自动退款；覆盖 unknown、滞留 sending，以及上游成功但本地建 Task
   持续失败。由平台承担潜在 Provider 成本，不能因内部状态不同而无限占用客户额度。24小时期限
   已由用户明确指定，本次按综合评审建议补齐创建异常范围，不再采用此前讨论的5分钟建议。

本文最初为只读问题分析；本轮实现与隔离开发环境实测记录见第 9 节。尚未部署生产、处理生产存量或修改线上客户资金。
第2—8节保留排查时的基线、设计目标和前次阶段记录；本轮已实现范围及验证结果以第9节为准，
不代表生产已发布。

范围按用户最新要求限定为**视频请求**：占款日志覆盖视频创建 attempt、正式视频 Task，以及这些
请求的退款历史和交付异常；不做文本、图片、音频、素材或 Batch 的占款管理。24小时自动退款政策
针对尚未完成 Task 原子转移的视频创建占款，具体条件见第4.1节；正式 Task 不因存在满24小时就
一律退款。Task 已建立但客户未收到任务 ID 或最终结果的异常进入日志处置与人工退款范围，不能
把“已建 Task”当成交付完成。

视频识别必须使用已登记入口、任务类型和冻结协议事实，不按模型名包含 video/seedance 等文字猜测。
日志应纳入系统已有视频路径；Seedance Link 与原生视频分别沿其权威资金入口读取和处置，不能为了
统一页面给原生请求套 Link 状态机。没有可靠资金事实的历史视频记录明确列为待核对，不捏造占款额，
不静默排除；原生视频各路径的覆盖清单与资金入口核查是实施验收项。

## 2. 当前实际情况

### 2.1 证据来源与可信边界

| 证据 | 内容 | 本次验证程度 |
| --- | --- | --- |
| 用户提供的线上只读分析 | 199 条 unknown + held，合计 178,714,738 quota；198 条已超过旧 task_deadline_at；没有人工恢复记录 | 外部排查结果，本次未重新访问生产数据库 |
| 用户提供的单次事件 | DNS 解析失败；该 attempt 占用 476,518 quota；后续新请求成功，旧 hold 仍在 | 外部日志摘要，本次未读取完整线上日志 |
| 当前本地代码 | HTTP 调用、attempt 状态、退款事务、恢复路由、错误事件记录 | 已沿调用链检查；工作区存在其他任务的未提交改动 |
| 本地定向回归 | 已登记明确拒绝退款、unknown 保留 hold、人工拒绝幂等、稳定 unknown 响应 | 已通过，不等同于真实 Provider 或生产验收 |

不在本文复制凭据、私有任务内容、完整签名 URL 或原始 Provider 响应。线上记录数量、金额与日期
均是所提供材料的快照，不声明为当前实时统计。

### 2.2 为什么这么多 unknown 没有完成退款

当前链路如下：

```text
预扣成功，attempt = sending / held
  → HTTP 传输错误，或响应不足以证明创建结果
  → attempt = unknown / held，next_attempt_at = 当前时间 + 30 秒
  → 后台扫描到 unknown
  → next_attempt_at = 0，打印一次“需要技术核实”
  → 后续到期扫描不再选中该记录
  → 只能等待人工 recover 或 reject
  → 人工未执行：资金长期 held
```

关键证据：

- [标记 unknown](../../model/task_create_attempt_release.go)：`MarkTaskCreateAttemptUnknown` 设置状态、
  30 秒后的调度时间，并递增 `reconcile_attempts`。
- [后台处理](../../service/task_create_attempt_reconcile.go)：`unknown` 分支仅停止调度并打印警告，
  没有查询 Provider，也没有退款动作。`upstream_succeeded` 才尝试恢复 Task，并在失败时退避重试。
- [到期筛选](../../model/task_create_attempt.go)：`GetTaskCreateAttemptsDue` 和
  `HasTaskCreateAttemptWork` 都要求 `next_attempt_at > 0`；停止调度后记录不会再次进入这条扫描。
- [现行合同](../20-architecture/Seedance专用渠道与Link架构.md) 第 7.3 节规定 unknown 不自动退款；
  [ADR-0016](../20-architecture/decisions/0016-Seedance专用渠道与确定性素材代理.md) 明确取消自动释放期限。

因此，`reconcile_attempts = 1` **不是“已向 Provider 核实过一次”的证据**，它在写入 unknown 时已经
递增。当前实现也不是“没有 task ID 只查一次，有 ID 就继续查”；分流依据是持久状态与恢复快照。

`task_deadline_at` 即使过期，也没有驱动 unknown 客户资金释放。反复重启服务或等待更久不能解决。
历史上已恢复的少量记录不能证明现版本对所有 unknown 都有自动补查能力。

### 2.3 为什么客户会觉得“出错就把钱扣住”

从客户视角，同一次请求返回错误、没有可查询的任务，余额却减少，且没有明确退款时点。这是实际
不可用资金；内部将它称为“预扣”而非“最终消费”，并不能减轻客户影响。

从代码看，并非所有错误都会挂款：预扣前校验失败不会产生 hold；已登记的明确拒绝会释放；正常
Task 的终态退款也有独立逻辑。问题集中在已经预扣、尚未形成正式 Task 的创建异常：

- 被误分类的未发送错误，进入不应进入的 unknown；
- 真正 unknown 被无期限挂起，没有客户资金兜底；
- 即使人工核实后允许退，原 Key 删除等实现缺陷仍可能使退款失败。

普通 Task 失败退款扫描无法兜住这批数据，因为没有可信上游任务 ID 时根本不创建 Task。不能伪造
失败 Task 来触发退款，必须在 attempt 的资金路径上完成收尾。

客户随后成功提交的新请求是另一个创建意图，不能自动关联成旧请求的恢复。新请求正常结算与旧
请求继续占款会叠加影响；“重试成功”不代表事故的资金影响已经消除。

### 2.4 对线上分析的修正

1. 当前 Go 宿主在 HTTP 调用阶段就写 unknown，早于公共错误文案包装；仅修改插件 500 文案不能解决。
2. 当前[明确拒绝分类](../../relay/task_create_disposition.go)已覆盖火山
   `401 + AuthenticationError`，并有[端到端退款回归](../../controller/seedance_create_rejection_integration_test.go)。
   历史 401 挂账需核对当时部署版本、冻结协议和响应证据，不应宣布现版本统一漏掉了 401。
3. 没有 upstream_request_id / upstream_task_id / Task 行，不能单独证明上游未执行；发送成功后
   响应丢失也可能形成这种记录。160 条无 request ID 的记录不能直接当作160条可安全退款记录。
4. 渠道被删除不必然导致无法恢复。attempt 和恢复模板冻结了连接、协议及执行事实，仍需检查
   快照完整性、冻结插件可用性和凭据有效性，不能改用当前渠道配置重解释历史。
5. Docker 实际是否转发到公共 DNS 是待现场验证的环境推断；修复 DNS 通路有必要，但不能替代
   网关在网络故障下的资金保障。

## 3. 已确认的代码问题

### 3.1 P1：确定未发送的错误被当作 unknown

置信度：高。位置：[HTTP 请求执行](../../relay/channel/api_request.go) `doRequest`、
[任务提交](../../relay/relay_task.go)、[attempt 服务](../../service/task_create_attempt.go)。

`MarkTaskCreateAttemptUpstreamStarted` 在 `client.Do` 前执行，表示进入调用，不证明网络请求已
发送。所有传输错误随后都被标记 unknown；任务提交层还会再次调用同一未知标记。只要写入该标记，
`SkipRequestRefund = true`，请求结束时就不退 hold。DNS 解析失败因此被放大为无限期人工挂账。

修复：在 Link 创建边界建立唯一的传输结果分类。确定整个调用从未发送业务请求时，进入既有拒绝
释放路径；可能已发送或无法证明时才进入 unknown。分类必须先于两处未知标记，并保持上下层一致。
持久 `sending` 仍须先于发送提交，不能为了区分 DNS 而把发送许可延后到网络写入后。

不能只匹配 `dial`、`timeout` 等字符串，也不能把“最后一次连接失败”当作“整个调用没有发送”。
需覆盖连接复用、代理、底层透明重试和部分写入；诊断正文的 not_recorded 也不是资金判定依据。
不增加自动重发、换渠道或基于模型名的推断。

### 3.2 P1：删除原 Key 后，已核实退款也会回滚

置信度：高；尚未核实线上199条是否命中。位置：
[attempt 退款事务](../../model/task_create_attempt_release.go) `releaseTaskCreateAttemptHold`。

当 `TokenQuotaHeld` 为真，退款在同一事务内普通查询原 Token。Token 支持软删除，普通查询会过滤
已删除记录；读取失败直接回滚，包括此前的钱包或订阅退款。客户在等待期间删除 Key 后，即使管理员
已经核实未创建，仍不能完成退款。

[attempt 转移计费](../../model/task_create_attempt_transfer_billing.go) 与
[Task 原子计费](../../model/task_billing_atomic.go) 已采用另一种正确语义：识别已删除 Token，
不调整失效 Token 的可用额度，但继续处理客户资金；数据库异常仍须失败。

修复：让 attempt 退款对齐既有 Token 生命周期规则，保留原子资金入口与幂等门闩，不恢复被删除
Key，不新增另一套退款服务，不无条件忽略数据库错误。钱包、订阅、Token 与 attempt 的资金事实
必须仍保持一致。

### 3.3 P2：错误事件丢失渠道、模型、阶段和原因

置信度：高。位置：[合同错误响应](../../controller/task_create_contract.go)、
[任务错误出口](../../controller/relay.go)、[错误事件记录器](../../clienterrlog/recorder.go)。

unknown 错误出口生成稳定503后没有附加统一诊断。错误事件字段依赖 `clienterrlog.Attach`，
没有附加时渠道为0，阶段和原因为 unclassified。旧文本日志中的渠道信息不会自动补入新错误事件，
导致运营必须翻完整后台日志才能定位一条占款。

修复：在 Link 的实际失败点附加客户模型、渠道、协议、阶段及稳定原因；合同响应出口补齐缺失信息。
复用现有错误事件与请求证据关联，不增加第二套诊断表，不把原始错误或 Provider 私有信息返回客户。

### 3.4 运营配套缺口：停止扫描后缺少持续处理入口

已有 [Root 管理路由](../../router/task-contract-router.go)：attempt 列表、recover 和 reject。
写操作有安全验证与审计说明要求；人工退款不是没有后端实现。

当前前端未找到这些接口的调用；unknown 后台分支只打印一次警告。人工流程未被使用是线上材料
报告的现象，不能证明接口不可用，但说明“停下来等人处理”没有形成实际运营闭环。

修复方向：在既有管理面提供待核实与待退款列表、金额、年龄、明确负责人及超时提醒，使用已有
受控操作入口。告警只促进处置，不能替代有期限的资金保障。

### 3.5 只查 unknown 或错误事件，会漏掉客户没有拿到结果的视频

置信度：高。创建链路在 [任务控制器](../../controller/relay.go) 中先持久化 Task 并转移 hold，
随后才返回客户响应。因此“Task 已存在”不能证明客户收到 task ID，更不能证明最终视频已经交付。
[创建响应中间件](../../middleware/task_create_response.go) 的缓冲与最终写出也不是客户确认。

[交付证据](../../service/task_request_evidence_delivery.go) 能补充写出字节、错误及中断信息，但只在
证据采集开启时存在。服务端写出完成不等于客户端收到；证据正文因采集上限截断也不等于网络交付
失败。不能将这两种情况混淆后自动退钱，或因没有证据就认为已经交付。

错误事件不是资金账本：[错误事件模型](../../model/error_event.go) 与资金事实可能位于不同数据库，
有占款也未必有匹配错误事件。专项页面必须从视频资金事实出发，附带错误信息；不能先筛错误日志，
再把没有错误日志的占款排除。

### 3.6 手动退款需要补齐政策退款和结算后退款

现有 [人工控制器](../../controller/task_contract_operations.go) 的 reject 要求
`provider_verified=true` 与审计说明，其语义是核实未创建后拒绝并释放。给这个接口加前端按钮，
仍不能支持“上游未知、平台决定承担风险先退客户”；不能替管理员伪造核实标记。

[Task 原子计费](../../model/task_billing_atomic.go) 的 `ApplyTaskBillingTarget` 对 settled 直接返回，
这是正常结算幂等保护。已经收费但客户没有取得结果时，不能直接调用它并把无动作当作退款成功，
也不能把 settled 重置成 pending 来绕过保护。需要明确、耐久、幂等的结算后退款处置。

现有 [attempt 释放条件](../../model/task_create_attempt_release.go) 只接受 `sending/unknown`，
不接受 `upstream_succeeded + held`；人工 reject 又要求 unknown。因此上游成功但本地建 Task
持续失败，目前只能恢复，不能直接走现有释放入口。第4.7节提出的退款需要扩展资金处置条件，
不能只给 reject 接按钮。后台对此状态会退避重试，但没有对应的客户资金释放期限。

[Task 计费目标校验](../../model/task_seedance_billing_facts.go) 还会拒绝非终态、成功但必要用量缺失、
目标与冻结 TargetQuota 冲突等情况。正常结算的这些保护不能全局删除；政策退款必须有明确受控
动作，按第4.7节区分客户退款与原业务结算，不能机械调用普通结算目标为零。

[异步计费补偿筛选](../../model/task_async_billing.go) 对非 debt 状态存在尝试次数上限；实现视频退款
兜底时须核对所有视频退款分支，防止一次人工提交最终又因达到上限而永久退出处理。新的持续退款
保障只改变明确纳入的视频退款工作，不顺带改变其他类型任务或所有结算重试策略。

### 3.7 订阅跨周期退款缺少原扣款周期约束

置信度：高，指代码条件下的风险；未证明线上199条记录中存在订阅或跨周期案例。
[订阅重置](../../model/subscription.go) 会清空当前 `AmountUsed`，而 attempt 退款直接从当前
`AmountUsed` 减原 HeldQuota，且要求当前用量足够；Task 退款也直接调整当前周期用量。

例如旧周期预扣100，重置后新周期正常消费150，再退旧请求100，会误把新周期消费减到50；若当前
用量只有20，attempt 释放条件不满足，又会退款失败。预扣时的订阅记录有订阅身份与金额，但这些
视频资金路径没有按原扣款周期判定退款。24小时退款容易跨日，因此必须补充第4.8节的处理规则，
不能仅以“回退原订阅”认为已安全覆盖。

## 4. 优化方案

### 4.1 客户资金合同：错误必须有资金处理结果

用户本次明确提出长期占款不可接受。方案据此将“客户资金是否应继续占用”与“Provider 是否实际
创建或计费”分开。后者未知，并不意味着前者可以永久没有结果。

用户已明确要求 unknown 在24小时后自动退款，并要求按综合评审建议更新方案。以下将相同期限
补齐到未完成本地 Task 受理的创建异常；均为实施目标，业务代码尚未实现：

| 场景 | 客户资金目标 | Provider 事实与后续处理 |
| --- | --- | --- |
| 预扣前拒绝 | 不扣款 | 不发送 |
| 已预扣，确定未发送或明确未创建 | 立即发起幂等释放；数据库失败继续补偿直到完成 | 保存确定性分类；不重发 |
| 创建结果真正未知 | 从预扣成功起24小时后，仍为 unknown 且 hold 未转移/释放时自动退款，不以供应商回复或人工审核为前提 | 保持未知，潜在成本由平台记录和承担 |
| 滞留 sending，或上游成功但本地 Task 持续未建成 | 同一预扣期限满24小时，仍 held 且未完成 Task 原子转移时自动退款；不因结果已知就延长占款 | 保留已知成功或未确认事实，不伪造 rejected，不再转入收费 Task |
| 已取得可信 task ID、任务正常受理 | 原子转移到 Task，按其交付与计费合同处理 | 使用冻结事实继续生命周期 |
| 已释放客户资金后才发现上游成功 | 不再次扣款、不重新 hold、不自动恢复收费执行 | 记录迟到结果与平台成本，按专项核实流程处置 |

自动到期处理的可执行边界为：已登记视频创建 attempt、预扣成功且 `billing_hold_state=held`、
冻结到期时间已到、状态为 `sending/unknown/upstream_succeeded`，且未完成与 Task 的原子转移。
在资金事务内重读并校验；`prepared/unheld` 不属于占款，已释放或已转移不得再次释放。
明确未发送/拒绝的已确认退款仍立即处理，不等到期。到期后的创建恢复入口也须检查同一期限：
未转移的超期记录转入保障退款，不能抢先补建收费 Task 来绕开期限；期限前已提交转移的走 Task
合同。字段矛盾时保留异常待办并告警，不伪造状态或重复退钱。

没有 attempt 的原生视频路径按其已有持久资金事实单独核对，不能凭页面分类套用上述数据库条件，
更不能据此建立第二套 Link 状态机。其覆盖与资金入口验收未完成前不宣称已支持相同自动保障。

这里的“立即退款”表示立即进入可重试的退款动作；只有资金事务提交后才向客户显示已退。数据库
故障期间显示退款处理中，并由补偿和告警推动完成，不能把一次失败静默变成永久 held。

仅修复 DNS 分类只能减少新增误挂款，无法解决真实 unknown 的长期占款；只增加人工按钮同样不能
保证资金有期限收尾。要解决用户提出的重大问题，必须同时落实本节客户资金合同。

#### 为什么旧设计不设期限，以及24小时退款承担什么风险

旧设计试图防止“上游已经创建并收费，只是平台未收到结果”的情况下退还客户资金。持续保留 hold
可以保留后续结算的资金，但把 Provider 响应丢失、核实困难的后果无限转嫁给客户。缺少有效人工
闭环时，其实际风险是余额长期不可用、客户重复提交后多笔资金同时占用，以及投诉与对账成本增长。

24小时自动退款是服务保障政策，并不声称“超过24小时就证明上游没执行”。风险与处理如下：

| 风险 | 处理原则 |
| --- | --- |
| 上游已执行或最终收费，客户资金已退 | 由平台承担并记录 Provider exposure；未知金额不填成零，也不用客户 quota 冒充上游金额 |
| 退款后收到成功结果 | 保留迟到结果用于核实，不重新预扣、不静默补扣、不恢复收费执行 |
| 自动退款与成功恢复或人工退款并发 | 使用同一 attempt 行锁/CAS及资金事务，只允许一次退款或一次成功转移 |
| 退款执行时数据库故障 | 保留退款目标并持续重试和告警，不能因到期扫描执行过一次就结束 |
| 大量响应丢失使平台承担重复上游成本 | 用既有渠道监控和运营处置控制故障扩散；不通过延长客户占款或自动重发转嫁成本 |

这些风险可以通过幂等资金事务、审计、上游核实和渠道运营管理控制，不要求无限期保留客户资金。
明确未发送或明确未创建的请求仍立即退款，无需等24小时。

### 4.2 现行规则的调整边界

当前[硬约束第4节](../00-context/硬约束.md)、Seedance 架构及 ADR-0016 禁止 unknown 自动退款。
上述有期限客户资金释放是明确的目标合同调整，不能偷偷在扫描器里加一条“时间到了就 rejected”。

实施时应同步记录新的架构决策与产品规则：允许客户资金按服务保障期限释放，但继续禁止重发和
换渠道；未知 Provider 结果仍保持未知。若新 ADR 取代旧决策，只标记其被取代关系并保留原编号；
不修改既有归档。本文不是新的权威合同源，也不提前把拟议状态写进当前事实文档。

客户占款期限已确定为24小时；用户本次指示是调整旧“不自动释放”规则的依据，不能继续用旧规则
否定本目标。实施时同步修改当前权威合同，避免代码和文档相互矛盾；本轮只更新方案，不代表已上线。
不得直接复用 Task 超时参数；Task 执行期限与创建失败的客户占款期限是不同语义。

调度实现目标：资金到期检查间隔不超过30秒，已受理但执行失败的退款安排30秒后重试，沿用现有
后台执行框架；两者是不同参数。24小时到期后的下一轮开始执行，不是再等一个24小时周期。
数据库不可用或调度积压时不承诺精确到账秒数，但必须保留可恢复工作并告警。

当前 [异步任务调度入口](../../controller/system_task_handlers.go) 的配置周期为15秒，并受
`constant.UpdateTask` 与 [待办判断](../../model/task_refund_reconciliation.go) 控制。这是当前事实，
不能把上述30秒目标写成现行周期，也不能为了本方案修改整个共享轮询频率。

资金待办必须能独立唤醒现有调度框架，不能依赖 Provider 轮询开关、是否有未完成 Task 或旧
`next_attempt_at > 0`。可以在现有 SystemTask 框架内登记视频资金处理任务，复用统一资金方法；
不建供应商专属进程，不保留两个会独立判定同一退款政策的扫描实现。原自动/人工入口都使用同一
持久处置条件；上游轮询停用后，已有客户资金仍需收尾。

按资金到期/下次执行时间加稳定 ID 排序分页；每批有数量和执行时长上限，失败项推进下次时间，
不能让前几条永久失败阻塞后续到期记录。实现时确定批次预算并验证多实例领取/幂等、重启恢复、
积压最老年龄和退款失败告警；“30秒”不替代吞吐与积压验收。

### 4.3 在现有 attempt 与资金事务上实现闭环

1. **保留唯一事实源。** 扩展现有 `TaskCreateAttempt` 的必要资金处置事实：冻结的期限、处置原因、
   资金重试时间和审计关联等；最终字段按模型评审落地。主库权威，缓存与管理页只做投影。
2. **明确待退款意图。** 确定未发送、明确拒绝或达到客户保障期限后，形成耐久的资金目标；资金事务
   失败可恢复，不能丢失已确认分类后再被旧 sending 扫描误改成无期限 unknown。无法落库期间不得
   宣称已退款，恢复后仍由期限保障最终收尾。
3. **区分业务结论与资金结果。** 明确未创建才能记 `rejected`。期限退款只说明客户 hold 已释放，
   不能伪造 Provider 拒绝、成功或失败。复用状态/资金两个维度表达；不要重新引入旧合同兼容解码。
4. **原子释放。** 客户资金回退、hold 状态、退款成功与防重复标记必须同一主库事务提交；最小处置
   审计、必要 Provider exposure 或其耐久交付任务也在该事务建立。日志库投影可用既有幂等交付
   机制补齐，不能异步补写决定是否已经退钱的标记。复用现有 `ProviderCostExposure`；未知金额保持未知，
   不以客户 quota 冒充上游成本，不向 Provider 发起新的创建请求。
5. **独立安排核实与资金工作。** 没有 Provider 查询能力时可以停止无意义补查，但不能将客户资金
   期限和待退款补偿一并设为不再调度。第4.1节内所有创建占款必须保留资金到期安排；到期后的
   退款失败继续按30秒周期补偿，不因尝试次数达到上限而静默停止。扩展既有任务扫描器，不另建
   供应商专属后台进程，并按第4.2节覆盖资金独立触发条件。
6. **收敛竞争。** 自动期限退款、人工 reject/recover、成功响应落库使用同一 attempt 行锁/CAS。
   Task 转移成功后退款不能再执行；退款先成功后禁止 hold 转移、建收费 Task或静默补扣。
7. **释放后保留最小核实事实。** 检查现有释放会清理恢复快照的行为：保留脱敏关联、处置依据及必要
   受保护核实信息，制定保留期；不能为方便核实永久保留原始正文或秘密，也不能因一次退款丢失
   平台成本核对所必需的事实。

退款期限为预扣成功时间加24小时，应在预扣时冻结，不从首次后台扫描、告警或服务升级时间重新
计时，也不随重启、配置修改或失败重试延长。实际执行时限需包含调度延迟与
资金存储故障的告警升级；不得只写一个 deadline 字段却没有实际扫描和补偿。

### 4.4 客户与管理员可见行为

- 客户通过受自身身份范围保护的请求记录看到：本次预扣、待核实/退款处理中/已退款、保障到期时间
  与平台 request_id。没有正式 Task 时仍可查询资金进度；该视图只投影 attempt，不创建伪 Task。
- unknown 响应明确不要自动重试；客户主动创建的新请求是独立意图。公开接口字段改动需同步协议
  与文档校验，不暴露内部渠道、Provider ID、冻结连接或凭据。
- 已退款与最终消费分开展示，不能把 hold 永久当作已完成消费；账单投影不得触发二次资金变更。
- 管理面持续展示待核实及待退款数量、额度、最老年龄、失败原因；达到阈值通知负责人。已停止
  Provider 补查的记录仍保留在资金待办中，避免一次 WARN 后从运行视野消失。
- 所有客户展示与通知仅需中文、英文，后续实现必须按现有 i18n 规范处理。

### 4.6 视频【占款日志】：入口、数据与处置视图

在现有错误日志页面新增专项按钮 **【占款日志】**，进入视频占款列表，明确显示“仅视频”。复用
[错误日志页面](../../web/src/features/usage-logs/error/index.tsx) 的页面组织及已有表格组件，新增
视频业务查询与详情；不把资金规则塞入通用表格组件，也不另建客户余额账本。

页面按以下口径提供视图，默认优先展示异常占款；“当前占款”同时包含正常执行中的视频：

| 视图 | 纳入记录 | 管理目的 |
| --- | --- | --- |
| 当前占款 | 创建 sending/unknown/upstream_succeeded 且实际 held；正式视频 Task 尚持有客户资金 | 看全部占用，区分正常执行与异常 |
| 异常待处理 | 创建异常、超过保障期限、退款失败、Task 异常、任务 ID 或视频结果交付异常 | 推动恢复交付或资金处理；已收费项单列“已收费待处理” |
| 已退款 | 明确拒绝即时退款、24小时保障退款、人工退款、Task 失败退款、结算后退款 | 核对真实资金回退与原因 |
| 全部记录 | 有预扣事实的视频请求及其后续转移、结算、退款 | 追踪同一请求完整生命周期 |

成功结算退回的预估差额要标明“结算差额退回”，不能标成业务失败或全额退款。已收费待处理记录
必须可查可退，但不计入当前占款总额。预扣前拒绝仍在普通错误日志，不虚构成占款请求。

**同一视频请求一条主记录。** attempt 转 Task 时沿持久关联合并；转移不是新扣款，也不是退款。
一条请求的多次错误、补偿尝试和退款事件放在详情时间线，不生成重复占款行。请求 ID 仅作关联条件，
不能代替唯一生命周期身份；历史关联不足时明确标注并核对，不按相近时间、模型或额度猜测合并。

列表至少展示：用户/应用、客户模型、渠道标识、request ID、attempt/Task ID、请求时间、预扣额、
当前占款额、累计实际退回额、当前净收费额、资金来源、业务状态、资金状态、交付状态、占款时长、
保障退款到期时间（仅适用记录）、最近失败原因与下一次退款处理时间。内部额度转换沿用现有单位
规则，不把 quota 直接标成货币。钱包退款与 Key 额度恢复属于同一次操作的不同维度，不相加。

顶部汇总当前占款、异常占款、超期创建占款、退款失败数量/额度，以及所选期间实际退款。
后端负责分页、筛选和汇总，统计必须覆盖完整筛选集；期间退款按实际退款发生时间计算。未完成
占款默认不限创建日期，避免旧挂款被“最近七天”隐藏。退款历史可设置日期范围。支持用户、应用、
模型、渠道、请求/任务 ID、状态、原因及时间筛选，保留已删除 Key/渠道对应的历史记录。

详情按事实展示预扣、发送、创建结果、Task 转移、结果可用、已观察到的响应写出、结算、退款申请、
每次退款执行及最终到账。关联错误日志、现有证据和操作审计；证据缺失或失效明确标注，不能阻断
退款查询。客户未下载不自动等于交付失败，HTTP 200 也不自动等于交付完成；客户反馈未拿到结果
必须进入平台排查，可由管理员记录核查依据并退款，不能以“上游成功”直接结案。

主库提供资金、关联与必要处置事实，错误库及可选证据只补充诊断，不要求跨库直接 JOIN。
[TaskBillingDelivery](../../model/task_billing_delivery.go) 是计费日志交付机制，其中 `DeliveredAt`
表示日志投影已交付，**不表示视频已交付客户**。[TaskCreateAttempt](../../model/task_create_attempt.go)
中的 `HeldQuota` 是历史预扣值，释放后仍可能保留，不能不看资金状态就求和作为当前占款。

按现有模型补齐必要的预扣/退款时间、退款原因、请求关联、操作者和资金操作身份；只保存最小事实。
历史缺失的准确交付/退款时间不可伪造。列表不返回私有快照、密钥、原始正文或完整签名 URL。

### 4.7 管理员在日志中手动退款

**目标：有退款权限的管理员可以在视频占款日志详情中直接发起退款，无需改数据库；unknown 未满
24小时也允许人工提前退款。** 自动保障不能取代人工兜底，人工操作也不能替代到期自动退款。

普通错误日志中能可靠关联视频资金记录的行，提供“查看占款/退款”进入同一详情；只有错误事件而
没有资金依据的行不直接产生资金变更。所有按钮最终调用同一权威退款入口，不按日志 ID 直接加余额。

拟采用以下操作语义：

| 资金与业务情况 | 可执行操作 | 约束 |
| --- | --- | --- |
| attempt held，确定未发送/未创建 | 退款，明确拒绝原因 | 可复用核实拒绝语义；已有可信事实不重新伪造 |
| unknown held，平台决定先退 | 人工保障退款，可早于24小时 | 无需假称 Provider 已核实；保留 unknown，记录平台承担风险 |
| sending 或 upstream_succeeded held，客户创建异常 | 核查后人工保障退款 | 不等待未知结果无限占款；与仍在执行的响应落库/恢复竞争并加锁 |
| 已转正式视频 Task、资金仍持有或退款失败 | 人工退款/重试已确认退款 | 从 Task 资金入口处理；原 attempt 不再退款 |
| 已结算收费，但客户未取得可用结果等服务问题 | 人工售后退款 | 记录原因与核查说明，退剩余净收费，不篡改原成功和结算事实 |
| 已全额退款或无可退资金 | 查看退款结果 | 不再产生新退款；有待清理债务时单独显示处置结果 |

一期采用**退清该请求剩余可退金额**，不提供任意金额输入，不做批量一键退款。金额由服务端根据
该视频请求已经实际预扣/扣收与已实际退回的权威事实计算；扣减已发生差额退回和既有退款，不能
直接再退最初 `HeldQuota`。尚未扣到客户的欠费不是现金，不可退成余额；人工决定全额免收时，应
同步持久化免收剩余债务，停止后续自动补扣，并单列豁免额度。资金来源按第4.8节限定为钱包，
不直接变成钱包充值；来源缺失或无法证明金额时明确阻塞原因，保留待处理，不猜金额或资金账户。

权限方案沿用现有边界：Admin 可以查看脱敏日志，具有 Root 权限的管理员执行退款，复用安全证明、
关键操作限流与审计。该方案不新增一套角色系统；如后续需要普通 Admin 退款，必须显式调整后台
授权，不能只显示按钮而绕过 Root。安全证明应绑定相应退款操作及目标，不复用其他用途的证明。

交互：详情点击【退款】→ 服务端预览客户/应用、请求、资金来源、可退额度、当前状态和潜在上游
成本 → 选择原因并填写必要说明 → 完成安全验证与确认 → 返回持久化操作编号和实际处理状态。
确认时重新校验资金版本与金额；若预览后已结算、转移或被其他管理员处理，先刷新结果，不按旧
金额退款。显示“退款处理中”“退款失败待重试”“已退款”时必须对应真实持久状态，HTTP 请求
超时不等于退款失败，再次打开页面应能查询原操作。

**资金实现约束：**

1. 自动退款、人工退款、退款重试共用各自资金对象的唯一事务入口。服务端持久化操作身份，重复
   点击、网络重试、两位管理员并发或自动扫描并发都不能多退；仅前端禁用按钮不构成幂等。
2. attempt 与 Task 的归属切换使用已有原子转移约束和一致锁序。退款先提交时，后来到达的创建
   成功不得转入收费 Task；转移先提交时，旧 attempt 退款失败关闭，页面刷新后从 Task 处理。
3. 正式 Task 退款与正常结算、欠费补扣、轮询更新共用资金锁和处置门闩；退款意图一旦被耐久接受，
   后台不能覆盖它重新收费。旧内存快照也不能覆写已提交的退款。退款不代表 Provider 已取消，
   不伪造失败/取消终态，不自动调用重新生成；必要的后续核实只记录结果与平台 exposure。
4. 已 settled 的售后退款需要在现有 Task 资金体系内新增受控退款动作与耐久幂等记录，保留原始
   结算事实，生成关联的退款记录和账单冲正投影。不得重置 settled、改写旧消费日志、直接加余额，
   也不得建立另一套余额账本。复用事务与日志交付机制前必须证明它支持追加退款事件及统计冲正，
   不能把现有方法的无动作返回当成功。
5. 资金变更、退款成功状态、防重复标记、最小处置审计及必要 exposure/日志交付任务同主库事务提交。
   主库资金已提交而日志库暂不可用时，继续补交日志，不再次退资金。后续账单同时保留原消费与
   退款，正确投影净收费；Provider 潜在成本不冲成零。
6. 已接受退款意图的执行失败按30秒周期持续补偿并告警，不因普通任务重试次数上限而丢弃。
   持久意图提交前数据库就不可用时，诚实返回“未受理/状态待确认”，不能承诺后台已排队；重试
   使用原操作身份查证。已完成的操作重复请求返回原结果。

本节是拟实施方案。现有 reject/recover 仅覆盖部分场景，当前尚无上述完整的日志操作、政策退款、
结算后退款和退款后禁止补扣机制，不能在编码时只接一个按钮就视为完成。

#### 人工退款状态处理表与耐久处置约束

退款是受控的客户资金处置，不通过改写 Provider 业务终态实现。以下表格定义所需行为，不表示现有
`ApplyTaskBillingTarget` 已支持；普通结算的终态、用量和冻结目标校验继续保留。

| 接受退款时的状态 | 受控退款行为 | 原事实保留与后续限制 |
| --- | --- | --- |
| attempt sending/unknown 且 held | 按已知拒绝或平台保障原因受理，释放尚持有额度 | 已知拒绝才写 rejected；unknown 保持未知，sending 不伪造 Provider 结论；受理后禁止转移收费 Task |
| attempt upstream_succeeded 且 held | 扩展现有释放条件，受理保障退款 | 保留上游成功事实；恢复入口看到退款意图后不再建收费 Task |
| 正式 Task 执行中 | 按售后原因受理，退已实际占用资金 | 不等待 Provider 终态，不伪造取消；后续观察不能重新扣费 |
| Task 成功、等待必要用量 | 允许保障退款，不以用量补齐作为客户退款前提 | 原用量缺失事实保留；后来补齐只服务成本核实，不恢复客户结算 |
| Task 已冻结结算目标，failed/debt | 退实际已收且未退部分；同时明确豁免剩余未收债务 | 保留原目标及豁免依据，不把 TargetQuota 改零；原补扣工作停止 |
| Task settled | 追加售后退款处置，退剩余实收 | 保留原结算和消费，账单追加关联退款；不重开普通结算 |
| 同一请求已有退款处理中或已退款 | 返回既有操作与实时结果；失败重试仍用同一操作 | 不新建第二次全额退款，不再次增加余额 |

在 attempt/Task 现有资金体系中增加最小耐久退款处置事实，至少能够表达：业务对象、操作唯一身份、
受理原因与操作者、受理时间、资金版本、可退额度/资金来源、豁免债务、执行状态、实际
退回额度、成功时间、失败原因及下次执行时间。最终字段与表归属在模型设计中确定；这不是第二套
余额账本，也不是只写一条普通错误日志。人工和自动处置沿同一资金对象的唯一入口落库。

处置过程只需表达“已受理待执行 → 执行成功”，执行失败保留待执行并带失败信息和重试时间。
后台领取使用现有租约/并发机制，进程崩溃不能留下无法恢复的“执行中”。在事务内锁定资金对象、
重新验证预览版本、确认没有其他有效全额退款，再持久化意图；**意图提交就是停止后续客户收费的
生效点**。意图已存在时，普通结算、欠费补扣、attempt 恢复和旧快照写入均须尊重该处置。

可以在同一事务完成受理与资金释放；需要后续执行时，只在意图提交后告知已受理。资金释放与成功
标记必须原子，重试不重新计算并扩大已受理金额；并发资金变化由锁和版本检查在受理前解决。
未知提交结果时，按原操作身份和资金对象查询再重试；两位管理员使用不同请求编号也不能绕过
业务对象的全额退款唯一约束。退款执行失败不撤销免收决定，不恢复后台补扣。

### 4.8 资金来源范围（按业务方最终确认）

业务方于本轮实施明确：**本站不支持订阅**。本次保障与人工退款只处理钱包扣款，并同步恢复仍存在的
API Key 额度；两个维度不相加。订阅跨周期核销、补发权益、延期与钱包换算均不属于实施范围，
不再作为待决策或验收阻塞项。此前关于周期序号的扩展已撤去，保留 NEWAPI 原生订阅实现。

异常历史记录若标记非钱包资金来源，占款日志保留可见并标注 `unsupported_funding_source`，禁止
将其猜测为钱包余额进行退款。该保护不代表本站发布了订阅产品。

## 5. 199 条存量的处置方案

### 5.1 先核对，不按缺失字段猜结论

对一致性只读快照生成逐笔清单，至少核对客户/应用、attempt、原 Key、冻结渠道/协议、hold 金额、
当前状态、是否已有退款或 Task 转移、请求证据关联、待核实年龄。检查软删除 Key 和缺失快照等阻塞项。
渠道不存在的记录仍须纳入，不按当前渠道列表过滤。

| 类别 | 依据 | 处理 |
| --- | --- | --- |
| 确定未发送/未创建 | 可关联到同一请求的传输证据，或已验证的 Provider 明确拒绝 | 现行受控 reject 幂等释放 |
| 确定创建成功 | 可信 Provider task ID及匹配的冻结事实 | 当前只能 recover；目标实现中未到期可恢复，已到期仍 held 且未转移则保障退款，不能用恢复绕开期限 |
| 仍无法确认 | 丢响应、无日志、无可查询身份等 | 满24小时且仍 unknown + held 的自动纳入保障退款；无需先取得“上游未创建”的证明；资金释放与未知成本分开记账 |
| 已退款或已转移 | 现有资金事实 | 排除重复释放，仅修正必要展示或审计缺失 |

本表围绕材料中的199条 unknown 展开，不声称已清点其他状态。实施时补查滞留 sending 和
upstream_succeeded + held，按第4.1节相同条件纳入；同时按钱包/订阅、原周期可核实性和实际可退
额度拆分清单，不能把所有记录统一减余额或订阅用量。

单次 DNS 案例若同请求证据足以证明整个调用未发送，可按明确未创建处理。其余记录不能因为相同
渠道、相近时间、空 ID 或后来新请求成功而套用该结论。

存量同样适用24小时保障，不从部署新版本时再等24小时。时间基准优先使用可验证的预扣时间；没有
精确预扣时刻的历史记录，方案采用 `attempt.created_at + 24小时` 作为明确的存量迁移口径并记录
依据，不使用会被调度更新的 `updated_at`。原 `task_deadline_at` 受其他配置影响，不直接当作新期限。
上线前清单核对是避免重复扣退的资金一致性检查，不是要求每笔超期 unknown 都先人工证明未创建。

### 5.2 执行与核销

存量执行前修复会阻塞合法退款的代码，形成明确批次与适用范围。使用统一资金事务、小批次、逐笔
记录操作者、依据、处置原因及结果；失败项保持待处理，不能仅写日志后退出。不得直接批量改 status
或单独给用户余额加钱，也不能跳过现有人工入口的安全证明。

未知结果的存量保障退款应通过新的专用原因进入同一资金入口，不能把
`provider_verified=true` 当作绕过核实要求的开关。批量入口如有必要，应复用现有权限、事务和审计，
而不是额外维护一套离线资金修改逻辑。

验收需要核对初始 held、转移到 Task、释放成功及仍待处理的数量与金额。释放额度与用户资金变化
一致；Token/订阅按冻结来源核对，不能把钱包和 Key 两个额度维度相加当成两次退款。批次重复执行
不得再次改变余额。政策退款后的迟到成功不能重新向客户扣费。

## 6. 分阶段实施与验收

| 阶段 | 交付 | 完成标准 |
| --- | --- | --- |
| 一：止住可避免挂款 | 未发送分类、删除 Key 退款、诊断字段 | DNS/连接拒绝无新 unknown hold；合法退款不受 Key 删除阻断 |
| 二：建立资金保障 | 正式合同、创建异常24小时期限、独立资金调度与退款补偿、exposure、竞争控制 | 第4.1节范围内的超期创建占款自动处理，失败继续补偿；按资金来源明确验收边界 |
| 三：视频占款日志与人工兜底 | 全部视频覆盖清单、占款/退款历史、错误关联、受控人工退款及结算后退款 | 无错误事件也能查占款；同请求不重复统计；日志中可退且后续不重复扣退 |
| 四：处理存量与客户进度 | 分级清单、受控处置、客户进度及管理员待办 | 批次资金可核销，未完成项都有原因与下一次处理安排 |
| 五：生产验收 | 数据库兼容、故障注入、灰度及真实账单核对 | 服务异常、重启、退款失败及迟到成功均不造成重复扣退或永久静默占款 |

上述阶段是能力拆分，不是把全部验证推迟到最后。每批上线前完成对应资金来源和状态的必要验证；
资金保障与最小占款查询/人工入口优先，完整汇总、筛选和时间线不应阻塞已验证退款能力上线。
本站不支持订阅；对应产品政策不属于本次范围，异常来源仍须显式可见。

必须验证的行为：

1. DNS、连接拒绝、代理失败等确定未发送路径；部分写入、发送后超时、响应中断仍保持正确未知语义。
2. HTTP 状态与 Provider 业务码的精确组合；HTML、截断数据、冲突 task ID 不误判明确拒绝。
3. 钱包/订阅、有限/无限额度 Key、已软删除 Key；重复释放、数据库回滚及后续恢复。
4. 已确认应退款但第一次事务失败；进程重启后继续退款，不丢失处置依据，不延长冻结期限。
5. 到期释放与成功转移并发、人工恢复并发、重复扫描；只产生一个资金终态。
6. 客户已退款后收到迟到成功，不再扣客户；Provider 金额未知时 exposure 金额仍未知。
7. 渠道删除、插件不可用、Provider 无查询能力，不阻断客户保障期限；系统不自动重发。
8. 客户隔离、Root权限与安全证明、审计脱敏，以及错误日志和账单投影一致性。
9. SQLite、MySQL、PostgreSQL均通过事务与迁移验证；本地 SQLite 通过不能代替三库验收。
10. 验证24小时边界：到期前不做期限退款，到期后下一轮释放；重启不重置期限；已超期存量直接进入
    退款队列。已转移或已释放记录不重复处理，退款失败经过后续扫描可恢复。
11. 占款日志仅纳入视频，逐一验证已登记的 Link 与原生视频路径；无错误事件、渠道/Key 已删除、
    很早之前创建的未完成占款仍可查。attempt 转 Task 后只统计一次，汇总不受当前分页影响。
12. 交付异常覆盖创建成功但 task ID 响应写出失败、正式 Task 结果不可用、已结算但客户反馈未收到。
    不把 HTTP 200、证据截断、未下载、计费日志 DeliveredAt 当作可靠交付结论。
13. unknown 在24小时前可以人工保障退款，不需要伪造 Provider 核实；已 settled 的视频能按售后
    退款退清剩余净收费。已经部分退回差额的不多退；没有实际收取的债务不产生现金退款。
14. 双管理员、重复点击、响应丢失重试、自动退款与人工退款并发；金额预览过期、attempt 转移、
    Task 结算和人工退款竞争时不多退不漏退。API 后端验证视频范围、权限、资金归属和安全证明。
15. 人工退款后迟到成功、旧轮询快照、结算补偿与欠费补扣不能再次向客户收费；正式退款没有伪造
    Provider 取消、失败或成本为零。处置原因、操作者、金额及关联消费在审计与账单中可核对。
16. 退款失败超过普通补偿重试上限仍可恢复；资金已退而日志投影失败只重试投影。主库在接收意图前
    不可用时不展示“已受理”；重启和管理员重新打开页面后可查询同一操作的真实结果。
17. upstream_succeeded 本地恢复持续失败，以及滞留 sending 超过24小时，均按冻结期限处理；
    到期后恢复不能绕过保障规则建立收费 Task。明确拒绝仍即时退款，不等24小时。
18. 按第4.7节覆盖执行中、等待必要用量、冻结目标 failed/debt、settled 四类 Task；政策退款可受理，
    普通结算保护未被全局删除，受理后旧快照与补扣均不能覆盖处置事实。
19. 订阅同周期、跨日/月、自动和人工重置、过期/取消及历史周期缺失；旧退款不冲减新周期消费，
    不伪造钱包到账。周期重置与退款并发、旧义务解除及实际权益补偿各自核销，后者按明确政策验收。
20. 系统只有已停调度 unknown、只有售后退款待办或 Provider 轮询关闭时，资金工作仍能触发；

## 9. 完整实施与隔离开发验收（2026-09-22）

### 9.1 本轮修复与交付

- 资金范围限定视频钱包：Batch 不获得保障期限、不进入退款扫描。存量期限回填同时处理 NULL 和 0。

  这是到期后开始处理的保障，数据库故障、停机和积压会影响实际到账时刻，不能承诺精确第 86400 秒到账。
- 普通创建转移、后台恢复与人工恢复共用持锁资金检查；到期不再补建收费 Task。确定拒绝的退款意图
  先保存，资金事务失败后仍可恢复，不会只剩 sending/unknown 技术状态。

- 错误日志新增【占款日志】：从主库按请求展示视频 attempt 与正式 Task，原子转移后只展示 Task；
  无错误事件也可见。支持任务 ID、用户、渠道、资金状态筛选、分页和详情，金额采用 quota，历史未知
  退款额明确标注，不返回私有快照、凭据、原始响应或媒体 URL。

- 支持占款 Task、欠款 Task、已结算 Task 的全额售后退款。按锁内当前净扣款退款，欠款仅免收未扣部分；
