# 账单页面证据核验闭环方案

## 问题与目标

现有弹窗只登记自由文本和 intact，管理员无法在页面识别核验对象，也不能证明已处置金额差异。
本次先更新方案，再实现按客户、自然月的证据核验界面及后端约束。不得通过勾选消除未知事实，
不得扣费、退款、修改日志金额、Task 或已经确认的账单。

## 当前实际情况

- 现有 Root 接口只接受人工来源保留结论，不扫描差异；前端缺少证据清单。
- 本地八月用户 91 有 5 条计费解释未知，另有 5 笔消费投影补记候选 3,667,520 quota。
  二者不是同一组记录，生产必须自行扫描，不能复用本地编号、数量或结论。
- 原生资金路径、离线补正工具与版本固化已经有各自权威入口。本次不建立第二套资金账本或网页补扣入口。

## 优化方案

1. 在账单版本区提供“核验与差异”，普通管理员可读，Root 可登记。复用现有弹窗、分页和基础控件。
2. 后端按目标客户完整历史读取消费、退款与任务关联，账期内展示解释缺项及涉及该月的任务金额差异。
   分类复用正式解析器；退款使用现有补证。任务差额只是一项待调查信号，不等于应向客户追收的金额。
   只采信显式 Task/原消费关系，不按模型、邻近时间或金额猜测关联；跨月关联参与核验。
3. 展示日志号、模型、时间、消费/退款、精确 quota、已有关联及缺失原因。分页只影响展示，不能限制检查范围。
   扫描超时、失败、分库均明确报错，不返回“零问题”。检查覆盖范围必须写明，不能宣称能发现已删除且无残留证据的记录。
4. 解释缺项允许逐项记录“已审阅，接受解释缺项”，保留未知状态。金额差异只能登记调查说明，
   不能点击通过；必须经既有受控补正或外部证据处置后重新扫描。逐项记录附操作者、时间、说明及来源指纹，复用追加审计。
5. 来源登记拆分备份/覆盖依据和日志保留/恢复依据；所有解释缺项已审阅、金额差异为零、来源依据完整，
   才能登记。后端重新扫描并核对指纹，不能依赖前端按钮或用户提供的异常计数。旧自由文本请求不得绕过新检查。
6. 读取前后验证来源修订及维护代际；登记时按维护控制行、客户证据修订的既有锁序验证。
   原始 SQL/备份恢复仍遵守维护协议。核验绑定解析版本、客户、月份和来源；相关变化使旧核验失效。
   生成与确认复验新核验的绑定，已确认版本继续幂等读取；历史人工登记不得冒充新的逐项核验。
7. 所有新增逻辑放账单扩展文件，现有接口/版本路径只作窄接线；不侵入原生 Relay 或资金路径。
   中英文同步；同库 SQLite/MySQL/PostgreSQL 使用项目 GORM 和锁封装，不引入方言专有 JSON 查询。

## 验证与部署

- 回归：精确消费退款、跨月退款、身份冲突、未知计费、正常零额、人工说明不能消除差额、旧请求拒绝、
  未授权拒绝、来源变化拒绝、扫描失败关闭、已确认版本不变。
- 前端：逐项证据和分页、保存/失败/刷新、普通管理员只读、阻断原因、来源字段与后台冲突处理。
- 本地实际备份只读运行真实解析器和核验器；改动前后金额及原库保持不变。
- 部署全部后端、工作实例和前端后，在生产自身数据上核验；滚动期间关闭正式确认。
  旧版服务不能与新版核验合同混用；真实外部数据库和生产灰度未验证前不得写为生产验收完成。


## 实施结果与验证

实现已完成：原自由文本弹窗替换为核验面板，提供完整范围概览、分页、逐项审阅、关联日志证据展开、
调查说明和两类来源依据。普通管理员可读；写入保留 Root 校验。金额项保存说明后仍阻断。
后台 GET 只读；两个 POST 均重新核验来源，旧请求不能旁路。记录复用审计和来源保留表，不修改资金。

一个必要调整：来源登记只递增本客户月份修订，不再递增全局维护代际，以免核验一个客户影响其他客户。
登记锁仍与确认/维护共用；来源证据按实际依赖记录，新增跨月显式关联消费、退款、补写任务都会使对应旧核验失效。
无关月份普通消费不撤销该月依据。来源详细字段复用 BillingStatementJSON，MySQL 迁移到 LONGTEXT，
SQLite/PostgreSQL 保持 TEXT；保留旧记录，旧自由文本证据需重新核验。

所有主体代码位于账单本地扩展，原生 Relay/资金文件零修改。已有扩展版本入口增加核验接线；
来源跟踪扩展增加 Task 创建时间、quota 和日志 task_id 关系的精确修订，是封闭跨月证据变更所必需。
不新增后台资金修复，不把通用任务比较重写成持款补正算法；真正执行金额补正仍由既有受控工具负责。

| --- | ---: | ---: | ---: | ---: |
| 91 | 5424 | 264047487 | 5 | 224 |
| 80 | 521 | 108714138 | 12 | 12 |

消费/退款记录数包含退款，因此不等于页面请求次数。任务项数量表示“当前显式关联不足以与最终 Task 金额吻合”，
不表示已经证明同等数量的漏扣，更不能把差额相加作为追收目标。此前严格证明的 5 笔补记候选只是其中一部分；
未显式关联的初始消费可能已在账单中，需恢复可靠证据后重新核验。源库及快照均未执行登记、补正或财务写入。

- 单独覆盖：旧请求拒绝、Root 权限、未审阅阻断、金额不能接受、说明不改金额、跨月结算、
  来源变化拒绝、无关月份不失效、未来关联补写失效、渠道测试排除及 playground 正常计费、取消和缺表失败关闭。

  不以这两项现代版本测试替代最低版本或目标生产验收。
- 前后端和所有工作实例必须一起升级，滚动期间关闭账单确认；在目标环境执行迁移并重新核验，不复制本地报告与确认状态。

  临时数据库测试容器已停止并清理。

- 管理员在正式生成开关关闭时仍可进入核验面板；生成与发布继续受开关约束，便于上线前先核验后开放确认。


## 管理员处理决定与资金影响（2026-09-19 修订，优先于前述交互）

### 业务合同

原“审阅依据与结论 / 接受解释缺项”要求管理员证明页面无法提供的事实，替换为明确处理决定、
业务原因、补充备注、影响预览及不可覆盖的处理历史。普通接受缺项可不填写备注；系统记录完整上下文。

| 选择 | 保存后的状态 | 账单 / 客户余额 |
| --- | --- | --- |
| 保留现有记录，不新增退款 | 解释缺项已接受；仅限非金额阻断项 | 均不变，历史退款也不撤销 |
| 金额有疑问，待复核 | 待复核 | 均不变，不能完成核验 |
| 申请减免费用 | 待核实并处理减免 | 均不变，不等于批准或退款完成 |
| 申请排除重复记录 | 待核实重复记录及重复扣款 | 均不变，不隐藏原记录 |
| 申请更正账期 | 待核实所属账期 | 均不变，不直接移走费用 |

本次修复的是管理决定登记入口。现有入口没有通用减免、账期迁移及退款执行合同，不新增旁路资金
写入。三个调整选项必须明确为“申请”，而不是“确认不计入账单”。不能宣称申请已执行、已退款，
也不能用保存说明清除真实金额差异。实际资金或历史投影更正继续由已核准的权威流程执行；不具备
执行流程的业务申请明确保留待处理，不自动派单、不假装已通知其他人员。

系统在提交前后均显示本次账单调整为零、客户余额变化为零、无新增退款。消费与退款分别标识；
Task 对比金额只作待核实信号，不作为当前应付或可退金额。未知退款关系不显示为“零退款”。
管理员不需要填写 quota、备份摘要、日志编号。内部诊断放在折叠详情；来源完整性的技术登记单独
折叠标明技术人员负责，不能被业务接受替代，也不能因隐藏技术表单而绕过原安全闸。

### 审计、并发与版本

- 复用现有追加审计，持久记录客户、月份、对象、模型、当时记录金额/类型、来源指纹、处理决定、
  原因、备注、操作者、时间、前一决定和实际影响（均为零）；返回可读处理历史，旧决定不覆盖。
- 更正决定是新增记录；旧来源历史仍展示但标明失效，不作为当前金额正确证明。旧自由文本接受不
  冒充新业务决定；历史审计保留可读。来源登记合同升版，已确认账单不受影响。
- 请求标识防止双击或重试重复登记；前一决定编号防止两位管理员覆盖彼此的决定；服务端自行冻结
  影响，拒绝不存在的决定、未知原因、旧请求、伪造接受及金额阻断项放行。
- 保存新决定必须使该客户该月原来源登记及未确认版本失效；不能先登记完整再撤回接受却仍可确认。
- 不修改原始日志、Task、余额、原生资金路径或已确认账单；不新增独立资金表。

覆盖无需编写技术证据的保留操作、待复核/三种调整申请仍阻断、退款原记录不撤销、金额影响零、
历史追溯/来源失效提示、重复提交、并发冲突、更正后旧来源登记失效、旧接口拒绝、Root 权限、
中文/英文、键盘操作及技术核验折叠。生产用实际数据重新核验，不携带本地人员决定上线。

## 2026-09-19 复审修订：申请结案与审计可用性

### 问题与目标

技术异常消失不能自动结束管理员的业务申请；保存一条记录不应清空其他记录的未提交内容。
损坏审计行应允许管理员查看问题，但不能忽略该行后恢复更早的接受决定。

### 优化方案与边界

- 以追加审计中每个对象的最新有效决定投影待处理申请，独立于当前异常列表、来源指纹及分页。
  来源变化或异常消失后仍展示原申请、原金额、操作者及原因，并持续阻止来源完整登记。
- 超级管理员可以填写依据后“撤回申请”或“驳回申请，保持原账务”。二者都明确表示不执行调整，
  记录前一决定、当前来源指纹和零资金影响；不得把未执行的调整登记为“已完成”。
  有待处理申请时不能直接用“保留记录”覆盖，必须明确结案；结案也不能清除仍存在的金额差异或自动接受缺项。
- 结案复用现有决定入口、锁序、幂等请求及前一决定校验；不创建资金账本，不修改日志、Task 或客户余额。
- 损坏、异形或不支持的审计内容只返回编号、操作人和时间等诊断信息，不返回原始损坏文本。
  整月业务写入和来源登记保持阻断，不能静默降级后沿用旧接受决定。原记录不得删除，实际恢复须走
  经核实的维护与审计恢复流程；本轮不提供凭备注绕过损坏记录的按钮。
- 刷新期间保持表单实例，仅禁用提交；同一记录来源或决定发生变化时保留输入，要求重新审阅后再提交。
  页面切换需保护未提交输入；保存成功只清除当前表单。退款类别复用既有日志枚举。
- 决定接口与来源完整性收据升级到版本 3。已确认版本保留；旧来源登记须重新核验，旧未确认草稿
  不能利用旧收据继续确认。生产需先关闭确认、更新全部实例及前端，再重验来源并生成新草稿，禁止混用新旧服务。

### 验收要求

覆盖异常消失/来源变化后的持续待处理、显式撤回/驳回、旧前驱冲突、重复提交、退款与金额阻断不被
结案绕过、审计损坏可读但不可写、旧收据失效、零资金变动，以及多行填写、刷新失败、分页和证据变化后的输入保留。
本节先记录方案；实际测试结果另行补充，不等同生产验收。

### 复审修订实现与验证结果

## 2026-09-19 终审补正：动态列表中的未提交草稿

### 问题与目标

现有表单只在子组件保留输入。禁止主动翻页不能防止刷新改变分页位置；申请被其他管理员结案后，
列表移除也会卸载表单。两者都可能丢失未提交说明。

### 优化方案

- 将问题处理和申请结案的草稿值、已审阅来源标识及原记录上下文保留在本账期弹窗内，按记录 ID
  分别管理；不写入浏览器持久存储或数据库，不作为账务事实。
- 分页仅切分服务器返回的记录。当前有草稿但不在当前页的记录继续留在页面供处理；记录已从服务器
  列表消失时只保留草稿供查阅/放弃，禁止提交。卸载组件不等同用户放弃草稿。
- 草稿仅在该条保存成功、明确放弃或内容恢复为空白默认值时清除；另一条保存、刷新失败、来源变化
  或他人处理不能清除。来源或前驱变化后继续要求重新核对；金额与后端核验规则不变。
- 优先复用现有表单、分页和提示，不增加资金接口、后端迁移或第三方依赖。

### 验收

先复现再修复：申请被他人结案、普通问题跨页移动、申请跨页移动。验证保留决定/原因/说明、来源
变化继续禁提交、消失记录只能放弃、清除当前草稿不影响其他草稿，以及成功保存后恢复正常分页。
