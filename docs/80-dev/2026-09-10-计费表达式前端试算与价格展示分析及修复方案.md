# 计费表达式前端试算与价格展示分析及修复方案

## 1. 问题与目标

用户在线上分别为 DeepSeek Pro、Flash 配置人民币价格、北京时间工作日高峰倍率和 `/ 6.71` 换算。
配置页出现 `Unsupported identifier in browser preview: weekday`；公开价格页仅显示 `base`，
将人民币系数显示成美元，并缺少分时条件。

**结论：三个前端缺陷已经复现——价格系数提取忽略算术、条件识别依赖表达式排版、试算与后端语义分叉。
当前工作区的实际后端结算函数能够正确执行用户提供的两条表达式；这不等于已经完成线上账单验收。**

本方案目标：

1. 管理端对完整表达式试算，能说明所用时间、用量语义、条件命中和费用单位。
2. 模型卡片、列表、详情、分组价格、合同价格、管理摘要、用量日志统一消费可信的价格解释。
3. 保留管理员可直接修改的 `/ 6.71`，不要求提前算成小数，不要求为展示改写表达式。
4. 无法完整解释的合法表达式明确显示“无法展开单价”，不得展示猜测的数值。
5. 修复不改变现有表达式、模型计费模式、实际计价时刻、预扣/结算/退款、组倍率或合同折扣。

第 1–10 节保留问题分析与验收方案；第 11 节记录初版实施，第 12 节记录复审后的修复与当前验证边界。当前仅完成本地验证，未完成线上部署与真实账单验收。

### 2.2 固定复现输入

以下是用户实际提供的配置，用于回归夹具，不是自动更新的 Provider 价格表。两条必须分别保存到对应模型，
不得把两个表达式合并为一个模型的表达式。`6.71` 的业务含义来自用户说明；通用解释器不得仅凭除法猜测币种。

Pro：

```text
tier("base", p * 4.5 + cr * 0.15 + c * 13.5) * (
  weekday("Asia/Shanghai") >= 1 &&
  weekday("Asia/Shanghai") <= 5 &&
  (
    (hour("Asia/Shanghai") >= 9 && hour("Asia/Shanghai") < 12) ||
    (hour("Asia/Shanghai") >= 14 && hour("Asia/Shanghai") < 18)
  )
  ? 2 : 1
) / 6.71
```

Flash：

```text
tier("base", p * 1.5 + cr * 0.05 + c * 4.5) * (
  weekday("Asia/Shanghai") >= 1 &&
  weekday("Asia/Shanghai") <= 5 &&
  (
    (hour("Asia/Shanghai") >= 9 && hour("Asia/Shanghai") < 12) ||
    (hour("Asia/Shanghai") >= 14 && hour("Asia/Shanghai") < 18)
  )
  ? 2 : 1
) / 6.71
```

未计组倍率、合同折扣和显示币种转换时，正确的 USD / 百万 tokens 如下。表内仅为展示而保留九位小数，
实际计算不能先把单价截为这些小数。

| 模型 | 时段 | 普通输入 `p` | 缓存读取 `cr` | 输出 `c` |
| --- | --- | ---: | ---: | ---: |
| Flash | 空闲 | 0.223546945 | 0.007451565 | 0.670640835 |
| Flash | 高峰 | 0.447093890 | 0.014903130 | 1.341281669 |
| Pro | 空闲 | 0.670640835 | 0.022354694 | 2.011922504 |
| Pro | 高峰 | 1.341281669 | 0.044709389 | 4.023845007 |

高峰条件是北京时间周一至周五 `[09:00,12:00)` 或 `[14:00,18:00)`；其余为空闲。
本次语法不含节假日调休规则，不应自行添加。

### 2.3 当前调用链及权威边界

```text
配置编辑
  rawExpr -> 前端字符串拆分 -> billingExpr + requestRuleExpr
  -> 保存时 combineBillingExpr -> 后端编译/向量校验 -> 原配置存储

浏览器试算
  effectiveExpr（拆分后的基础部分）+ 本地草稿
  -> 标识符白名单 -> new Function -> 浏览器 USD/配额换算

价格展示
  billing_expr -> 字符串拆分 -> 正则提取 tier 中的系数
  -> 单价/条件列表 -> 组倍率、合同倍率、显示币种格式化

实际计费
  保存的完整表达式 -> 预扣时冻结表达式
  -> 可信用量归一 -> Go 引擎执行完整表达式
  -> quota 换算及组倍率/合同事实 -> 结算与消费日志
```

实际结算不读取前端解析的单价。代码依据：

- `relay/helper/price.go:289`：读取完整表达式并建立预扣快照。
- `service/text_quota.go:424`：以实际用量进入表达式结算，并将结果交给正式结算链。
- `service/tiered_settle.go:172`：读取创建时表达式快照；求值失败时保留预扣结果，不改走前端显示价格。
- `pkg/billingexpr/settle.go:24`：重新执行完整表达式，再换算 quota 并应用组倍率。
- `service/log_info_generate.go:319`：日志保留 `expr_b64`、命中档位及规则执行痕迹。

这只能证明正常表达式结算路径及已测试场景。上游缺失用量、结算异常、配置尚未同步、不同线上代码版本等，
仍需按实际请求排查，不能用价格截图替代账单验收。

## 3. 严重问题

### S1：局部系数被当作完整单价，汇率及外层算术丢失

- 类型：逻辑分叉、静默错误；置信度：高；优先级：P1。
- 位置：`web/src/features/pricing/lib/billing-expr.ts:165`（系数正则）、
  `web/src/features/pricing/lib/billing-expr.ts:276`（档位正文）、
  `web/src/features/pricing/lib/billing-expr.ts:290`（档位提取）。
- 证据：`BILLING_VAR_REGEX` 仅提取“变量乘数字”；`parseTierBody` 取每个变量第一次匹配的数字；
  `parseTiersFromExpr` 用正则寻找 `tier` 局部片段，不验证整个表达式是否被解释。
- 复现：原始 Flash 表达式被解释为输入 `1.5`、缓存 `0.05`、输出 `4.5`；末尾 `/ 6.71` 不参与展示。
  即使将除法移入 `tier`，结果仍然错误。与用户截图一致。
- 影响：模型卡片/列表/详情、组价格和管理摘要可能展示错误美元单价；日志详情的单价解释也可能错误。
  这不是日志持久化扣费额被改写。
- 活跃消费者：`web/src/features/pricing/lib/dynamic-price.ts:219`、
  `web/src/features/pricing/components/dynamic-pricing-breakdown.tsx:274`、
  `web/src/features/system-settings/models/model-pricing-snapshots.ts:100`、
  `web/src/features/usage-logs/lib/format.ts:332`；合同详情复用同一个 breakdown 组件。
- 最小修复方向：停止在这些消费者中用正则片段推断金额；由同一后端表达式语法解析产生严格、只读的价格投影。
  不可完整展开时返回明确的“不可展开”，不能保留部分错误数字。
- 验证：外层/内层除法、括号、重复变量项、常量项、负号、非线性表达式、显示币种及组倍率回归。

### S2：时间规则拆分依赖排版及固定形状，合法条件被静默隐藏

- 类型：多套语法解释、需求偏离；置信度：高；优先级：P1。
- 位置：`web/src/features/pricing/lib/billing-expr.ts:610`（顶层乘法拆分）、
  `web/src/features/pricing/lib/billing-expr.ts:839`（条件因子识别）、
  `web/src/features/pricing/lib/billing-expr.ts:901`（表达式拆分）；
  `web/src/features/pricing/components/dynamic-pricing-breakdown.tsx:274`、
  `web/src/features/pricing/components/dynamic-pricing-breakdown.tsx:298`（展示消费）。
- 证据：顶层乘法仅按字面量 ` * ` 拆分；条件因子匹配固定的 `(条件 ? 数字 : 1)`；条件解析又限制
  运算符和组合形状。用户表达式的外层除法、嵌套 OR、`<= 5` 等不能作为一个整体被识别。
- 复现：原式得到 `rules=[]`，页面仍显示基础档位，而不说明未解析的时间条件。
  改写成两个单行、独立时间因子后可得到两组规则，但 S1 仍存在。
- 影响：管理员误以为分时规则没有保存，客户误以为所有时段同价；格式变化就改变展示。
- 最小修复方向：展示条件来自语法树，保留 AND/OR/NOT 的层级、时区、比较运算符和边界。
  展示不能依赖编辑器为了可视化而采用的序列化格式。
- 验证：原始多行表达式、单行等价式、不同空白、外层括号、独立因子和跨午夜条件应正确解释；
  不认识的条件仍显示完整条件文本及“未展开”，不得变成“没有条件”。

### S3：浏览器试算不是完整表达式的后端等价执行

- 类型：多套实现、输入合同不清；置信度：高；优先级：P1。
- 位置：`web/src/features/pricing/lib/tier-expr-estimator-safety.ts:23`、
  `web/src/features/pricing/lib/tier-expr.ts:315`、
  `web/src/features/system-settings/models/tiered-pricing-editor.tsx:1436`、
  `web/src/features/system-settings/models/tiered-pricing-editor.tsx:1887`、
  `web/src/features/system-settings/models/tiered-pricing-editor.tsx:2114`。
- 证据一：白名单和运行环境都没有 `hour/minute/weekday/month/day`，不是只遗漏 `weekday` 名称。
- 证据二：`effectiveExpr` 会去掉可识别的请求倍率；`CostEstimator` 只接收这部分，因而可视化生成的
  时间倍率可能不报错却完全不参与试算。
- 证据三：本地 `p=promptTokens`，`len=promptTokens+缓存量`；后端根据实际 API 用量语义和表达式
  UsedVars 归一。页面仅标“输入 tokens”，没有明确区分原始 API 总输入与归一后的普通输入。
  将 OpenAI 的总输入直接抄入草稿不能保证得到同样结果。这是输入口径风险，不能笼统认定每次都重复计费。
- 证据四：`web/src/features/system-settings/models/tiered-pricing-estimator-state.ts:166`
  直接返回浮点 quota；后端使用统一 quota 取整。
  缺请求探针还会使用 nil/空串继续计算；必须区分“明确模拟缺失”与“管理员尚未填写”。
- 影响：合法表达式被提示错误，或得到未含倍率、口径不同的试算金额；补五个函数只能解决其中一部分。
- 最小修复方向：管理试算调用现有 Go 引擎的只读入口，输入完整表达式、明确的用量语义和模拟时刻；
  删除此通用 token 试算路径中的 JavaScript 求值与重复配额换算。
- 验证：相同输入下与后端结算函数一致；时段切换、缓存归一、取整、缺上下文与失败状态可区分。

## 4. 建议与非缺陷边界

### A1：把试算、保存、单价展开三个状态分开表达

- 类型：交互状态不清；置信度：高；优先级：P2。
- 位置：`web/src/features/system-settings/models/tiered-pricing-editor.tsx:1635`（错误展示）、
  `web/src/features/system-settings/models/tiered-pricing-editor.tsx:1377`（试算组件输入）、
  `web/src/features/system-settings/models/model-pricing-sheet.tsx:548`（保存草稿校验）。
- 证据：编辑器将本地试算错误展示为“表达式错误”；试算组件只接收表达式和模型名，没有向保存层
  回传错误的接口。`commitDraft` 检查表单及 `validatePricingValues` 后构造提交数据，不读取试算结果。
  展示位置与保存调用链共同证明两者未绑定；这不意味着后端保存接口省略了表达式校验。
- 影响：用户将浏览器能力限制误认为后端拒绝配置。
- 最小修改：分别显示“表达式有效性”“单价能否展开”“试算是否成功”“保存是否成功”。
  单价不可展开不应阻止合法表达式保存；后端保存错误必须阻止成功提示。
- 验证：无效语法、不可展开但可执行、上下文未填写、网络失败、保存成功分别覆盖。

以下行为必须保留并说明，不作为此次修复对象：

1. 普通实时请求在实际结算时读取时间；跨边界的预扣价与结算价可以不同。
   `pkg/billingexpr/run.go:143` 在未传 PricingTime 时使用当前时间。
2. `tier("base", ...)` 的命中名称仍可能是 `base`；高峰由 `request_rules` 记录，不能仅以名称判断是否翻倍。
3. 历史请求以其冻结表达式、实际日志金额和已有规则痕迹为准；不能用当前模型配置或当前时间重算历史。
4. 组倍率和合同折扣位于表达式之外；截图中的 `0.87` 不是表达式失效，也不能被展示修复移除。
5. 当执行失败或可信用量缺失时，现有资金处理有独立语义；展示项目不得顺手修改它们。

## 5. 多套实现归一化

| 能力 | 当前实现 | 保留的权威 | 迁移调用方 | 删除/限制项 | 必须保留的真实用途 |
| --- | --- | --- | --- | --- | --- |
| 完整表达式求值 | Go expr 引擎、浏览器 new Function | `pkg/billingexpr` | 通用 token/旧 `_task` 试算器 | 删除这些调用方的 JS 求值及白名单 | 原生插件 `u()` 的类型化任务编辑器另有单位合同，不借此改写 |
| 单价解释 | 多个页面共享但不完整的正则提取 | Go 同源语法树的只读严格投影 | 定价、摘要、合同、日志 | 删除通用 token 金额展示对 `parseTiersFromExpr` 的依赖 | 可视化编辑器的受限反向识别可以保留，必须有无损往返保护 |
| 条件解释 | 正则拆分、运行时规则痕迹 | 静态完整条件树；历史命中用运行痕迹 | 价格详情、日志详情 | 不再从正则是否成功推断有无条件 | 编辑器构造函数保留为作者工具，不再是显示/试算权威 |
| 用量归一与配额 | 浏览器赋值/换算、后端归一/取整 | `BuildTieredTokenParams`、统一 quota helpers | 管理员试算 | 删除同路径的重复金额及整数配额算法 | 本地草稿仍可保存非敏感 token 数，不能保存请求头/正文 |

迁移完成后以真实 import/callsite 搜索决定可删除导出；不能直接删除仍被类型化任务编辑器使用的解析函数。
不新增“统一 wrapper”后继续让旧数字解析成为隐式备用路径。

## 6. 优化方案

### 6.1 选定方向及约束

**推荐：前端改为消费后端的只读表达式解释与试算结果。复用同一个 Go 语法解析器和计费执行引擎，
不在浏览器再实现完整 expr 语言。**

这需要少量后端只读接线，但不改变真实计费。单纯补浏览器时间函数不能修复外层算术、完整倍率、
缓存归一及历史解释；单纯扩展正则不能可靠表达嵌套语法。部署前后原配置内容必须保持一致。

本期范围：通用 token 表达式及现有通用编辑器中的已登记 `_task` 试算；共享页面的通用 token
价格解释。原生插件 `u()` 的 schema 驱动编辑器、任务单位换算、矩阵展示保留既有分支并做回归；
不将任务输出 USD 与 token 输出的百万单位混为一谈，不借本次改成一套万能任务解释框架。

明确禁止：

- 根据模型名识别 DeepSeek 或增加专属时段配置表。
- 将 `/ 6.71` 折成配置中的固定小数、自动改写存量表达式、追加隐藏倍率。
- 修改实际请求的时间冻结策略、Channel、Provider 请求、资金或退款逻辑。
- 为展示新建持久化价格表、独立规则注册表、迁移历史日志或建立后台定时刷新任务。
- 从 Provider 配置读取真实 Key、Header、URL 作为试算上下文，或由试算触发 Provider 调用。

### 6.2 只读表达式投影

拟在 `pkg/billingexpr/` 新增独立的展示投影文件，输入原始表达式，输出严格的展示模型。
这是一份可重建的读模型，不是新的计费合同或执行器。

处理顺序：

1. 复用 `ParseExprVersion`、现有编译校验及 expr-lang 语法解析器。
2. 展示遍历未经执行痕迹 patch 改写的语法树。`compile.go` 会把部分三元表达式改成 `_trace` 调用，
   不能假设 `prog.Node()` 仍是原始树；允许校验后用同库 parser 解析原始 body，不另造语法。
3. 只对可证明的线性 token 单价、常量算术、档位条件和条件倍率展开。
   标量乘除应传递到其覆盖的整个价格子树，位置在 `tier` 内外都不能丢失。
4. 常数折叠遵循 Go expr 的数值语义，并与实际引擎逐项对照；不是用 JavaScript 算出另一个结果。
5. 保留完整布尔层级与分支优先级，支持比较、AND/OR/NOT、嵌套条件及函数时区参数。
6. 不可证明的局部不能产生“精确价格”。非线性、变量分母、复杂动态调用等整体标记不可展开；
   原式仍可通过引擎执行和保存。

首期展示模型至少包含：

| 字段 | 含义 |
| --- | --- |
| `expression_hash`、表达式版本 | 对应精确源字符串，用于防止新表达式配旧结果；不是新的持久化身份 |
| `status` | `exact` / `opaque`；语法无效另作为请求错误返回，不混为合法的不可展开 |
| `unit` | 本期通用 token 固定 `usd_per_million_tokens`；不根据数值或模型名猜测 |
| `tiers` | 完整分支条件、label、已吸收固定乘除的价格、可独立解释的常量项 |
| `rules` | 完整条件树、规范化原文、倍率、适用范围；不能丢掉非 1 的另一个分支 |
| `reason` | 无法展开的稳定原因；前端翻译，不暴露内部栈或秘密值 |

规则说明不能只复用 `request_rules` 作为全部静态条件，因为运行时痕迹只记录特定的
`condition ? literal : 1` 形状；其他合法三元表达式也必须保留或明确不可展开。

展开必须有边界：沿用现有编译缓存容量约束；新增投影复杂度限制只影响展示，例如最多 32 个价格分支，
超出后显示不可展开，不限制原生合法配置或实际计费。无需为任意条件实现 SAT 求解器，不宣称不能证明的
分支一定可达/互斥，不穷举每分钟或生成全年日历。

`exact` 仅在整个金额结构都被解释时成立。同一个 `p` 出现多次必须正确合并，固定请求费用必须单独
标注，不能忽略它之后只列 token 单价。返回的是数值含义；输出精度由 formatter 控制，内部不能先截断。

### 6.3 管理员只读试算接口

当前路由没有可复用的通用表达式试算接口。拟新增独立路由注册文件和 controller/service，
在原生路由处仅增加一行注册；权限沿用模型价格编辑所需的管理员权限。

拟定入口：`POST /api/option/billing-expression/preview`。一个入口支持限量 `items`，每项必含
客户端关联标识、完整表达式及明确的模型/计费上下文；仅需展示时不带 sample，需要试算时带 sample。
管理列表可批量获取当前页投影，编辑器单项获取；不为列表另建第二个价格解释端点。

| 输入/输出 | 内容与边界 |
| --- | --- |
| 输入 expression | 保存时的完整表达式，包含所有倍率和除法；不使用 `effectiveExpr` 的基础片段 |
| 输入模型上下文 | 用于读取代码登记的协议/schema；不允许客户端自创 `_task` 字段含义或 usage schema |
| 输入 sample | 明确的用量语义、各 token 字段、可选模拟时刻、人工填写的最小探针；不读真实凭据 |
| 输出 projection | 与公开价格页相同的展示模型 |
| 输出 evaluation | 实际采样时刻、归一后的用量、rawCost、USD、整数 quota、命中 tier 和规则、是否饱和 |
| 输出 scope | 明确为模型费用试算，不含组/合同/工具附加费用；不把它命名为最终用户扣费 |

试算 service 复用 `BuildTieredTokenParams`、`RunExprWithRequest` 与统一 quota 换算路径。
使用显式 `GroupRatio=1` 的只读快照，不构造真实资金会话，不调用 `PostTextConsumeQuota`、
`PreConsumeBilling` 或任何落账接口。QuotaPerUnit 从服务器读取，客户端不得传入伪造配置。

为避免自创原始用量合同，sample 明确区分 OpenAI 总输入语义和 Claude 文本输入语义；
标签清楚说明缓存是否已经包含在输入中。OpenAI 场景的总输入不能再次加缓存，`len` 与 `p` 仍由后端
UsedVars 规则决定。未使用 `cr` 时缓存必须留在 `p` 中，不能由前端永久扣除。

五个时间函数均按同一次模拟时刻执行。默认采用服务器收到试算请求的时刻并返回该时刻；
用户也可指定含时区偏移的模拟时间，时区换算仍由表达式参数决定。无须每秒自动请求。
当前工作区已有 `RequestInput.PricingTime`，但属于其他未提交工作；实施前必须确认目标提交具备该能力。
如需单独提交该可选上下文支持，必须保持未传值的原生实时请求语义不变，不私自修改实际结算时刻。

缺 `param/header` 上下文时不能伪装已模拟真实请求：展示缺失项，让用户显式选择模拟缺失或填写合成值。
真实 Key、Cookie、完整业务正文不得写入本地草稿、接口访问日志或错误日志。沿用已有鉴权、请求大小及
访问频率限制；新增 preview 专属批量/复杂度限制不反向收紧原生保存及计费。

### 6.4 只读投影如何交付给各页面

1. **公开价格与合同价格**：在现有鉴权、可见模型和合同过滤之后，为响应中的表达式附加
   `billing_display`。可用新增响应包装结构嵌入原有 DTO，避免修改数据库模型；若现有合同 DTO
   必须增加字段，仅增加这个字段。每个入口调用同一投影函数，不复制解析实现。
2. **模型管理列表与编辑器**：使用管理员 preview 接口；当前页批量 describe，编辑器按钮执行 sample。
   query key 包含完整表达式内容或准确 hash，不仅按模型名缓存。切换模型/表达式后不得继续显示旧试算。
3. **用量日志**：在现有日志查询完成权限过滤/脱敏之后，以该条日志的 `expr_b64` 生成响应级投影。
   保留原有日志金额、UsedTokens、`request_rules`；不更新数据库日志，不按当前模型价格生成历史投影。
   普通用户、管理员和现有按 Key 日志响应都应进入同一装配逻辑。
4. **共享组件**：`DynamicPricingBreakdown` 消费显式投影；合同和日志页面传递自己的投影来源。
   不再让组件对原始 token 表达式重新提取系数。

投影必须与同一响应中的表达式匹配。若接口没有投影、投影版本不支持或 hash 不一致，页面显示
“表达式定价，暂无法展开”，不能恢复使用旧正则猜价。这是展示能力状态，不是计费 fallback。
日志金额不依赖投影，因此即使投影不可用也必须继续正常显示。

#### 6.4.1 分页去重、缓存与上下文隔离

在权限过滤及脱敏后，对本次响应实际可见的表达式先去重，再生成静态投影，避免大分页逐行重复解析。
缓存键由服务端从完整原式计算的 hash、表达式版本、投影版本组成；影响静态解释的变量 schema、
单位合同等上下文也必须进入键。不信任客户端传入的 hash，不按模型名或删空白后的文本替代原式身份。

请求内去重是必需项；跨请求复用可使用有容量上限的进程缓存，容量不超过现有编译缓存的 256 项，
淘汰后按需重建。复用现有有界缓存设施，不增加持久化表或通用缓存框架；投影语义或 schema 改动必须
更新对应版本。只缓存静态、不可变的投影，不能把暂时性解析服务失败当作永久的不可展开结果缓存。

同一表达式的模拟时刻、条件实际命中、用户/组/合同倍率、历史扣费额均不能仅凭表达式 hash 复用。
每条日志的 `request_rules`、用量、冻结倍率和已发生金额在静态投影之外独立装配；不得修改共享缓存对象。
sample 结果须关联完整模拟输入和当前草稿状态，不进入此静态缓存。缓存命中也必须经过原有权限过滤，
不得携带其他用户的日志或合同事实。

### 6.5 展示与交互合同

**配置编辑器：**

- 原始字符串是待保存内容；原始模式保存不能先经过有损拆分/再生成。
- 可视化模式仅接收可无损往返的子集；不支持时保留原始模式，不用空模板覆盖现有表达式。
- 试算按钮提交完整草稿，显示选定的模拟时刻、时区、归一用量、费用范围和条件命中。
- 状态区分为未试算、进行中、成功、语法错误、上下文未完成、接口不可用；失败不显示金额 0。
- 改动表达式/用量/时间后旧结果立即标为过期；异步旧响应不能覆盖当前模型或新草稿。
- 预览失败不直接判保存失败；最终有效性仍由原保存接口校验。保持预览不修改配置的边界。

**公开定价：**

- 用户原式应显示正确换算后的基础单价，以及北京时间周一至周五两个高峰窗口和 `×2`。
- 对该可精确解释的单一两分支条件，展示空闲/高峰两行有效单价；条件作为可读文本明确标出。
  这些标签是本例的说明，通用程序不能从模型名推断“高峰”的业务名称。
- 对多个独立条件保留各倍率及适用范围；仅在可证明时合并为有效分档，否则不生成虚假的全局最小/最大价。
- 基础价与条件生效价分开，不能将高峰价又乘一次 `×2`。时区、闭开边界、周末说明不省略。
- 不默认按当前时钟给价格表某行加“本请求已命中”；未来请求可能跨边界结算。
- `opaque` 时隐藏不可信单价及范围，保留动态定价说明和原表达式的已有可见内容。
  对没有分时条件的旧静态/阶梯表达式保持紧凑展示。

**分组、合同与币种：**

- 表达式输出单位始终遵守引擎合同，先得到 USD 价格，再应用明确的组/合同展示倍率，最后格式化币种。
- 表达式内部 `/ 6.71` 已参与单价，不能在外部再除一次。它不是网站显示汇率设置的替代品。
- 充值展示折算、显示币种汇率和表达式里的常量是三件不同的事；沿用已存在的正确 formatter，
  UI 清晰标识当前显示口径，不通过改表达式让几个口径强行相等。
- 合同页读取其现有合同展示倍率；实际消费日志读取当次冻结事实，不能套当前合同。

**用量日志：**

- 已发生的费用始终展示持久化日志金额。解释区可展示本次冻结表达式的正确基础单价及已记录倍率。
- 是否命中高峰只相信当次 `request_rules`；不能用 `matched_tier=base` 判定未翻倍。
- 缺命中痕迹时说明“历史记录未提供该条件的执行结果”，不使用当前时间或日志展示时间猜测。
- 同一个 UI 不把基础单价列和最终有效单价列混名；若字段不足以证明有效单价，只显示基础价与已知倍率。

新增文案实施时必须先读取项目 `i18n-translate` 技能，按 en/zh/zh-TW/fr/ja/ru/vi 七语言补齐；
预览结果区提供可访问的状态提示，不能只靠颜色区分错误/过期/命中。模拟时间输入须显示明确时区。

## 10. 方案取舍与剩余风险

| 备选 | 判断 |
| --- | --- |
| 只补浏览器五个时间函数 | 能消除第一条错误，但倍率、完整语法、用量与 quota 分叉仍在，不作为完整修复 |

| 在浏览器实现完整 expr 引擎 | 增加长期语义维护面；本项目已有权威 Go 引擎，不采用 |
| 同源语法的严格只读投影 + Go 试算 | 需要窄后端接线，但可以验证完整表达式并保留原配置，推荐 |

线上版本差异与真实 Provider 计价时刻差异。分别通过新增文件隔离、opaque 状态、既有 task 回归、
版本核对和独立账单验收控制；不得用隐藏规则、猜测价格或改写实际计费来掩盖。
