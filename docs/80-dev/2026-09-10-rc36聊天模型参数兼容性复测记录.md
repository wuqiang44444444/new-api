# rc36 聊天模型参数兼容性复测记录

## 问题与目标

在[rc.36 同步](./2026-09-10-上游rc36同步实施与验证记录.md)后的实际工作区，验证渠道测试的
`max_tokens` 不兼容问题是否解决，并复核截图中 Chat→Responses 策略的效果。

**结论：部分解决，不能宣布原渠道故障已经消失。** 已登记的标准模型及正确映射到它们的客户别名能转换
旧字段；裸名 `chat-latest` 仍保留旧字段。截图中的策略在正式 Chat 请求生效，但渠道测试入口没有调用
该策略，开启策略不能保证测试按钮通过。

## 当前实际情况

后续用户已明确授权将精确名称 `gpt-chat-latest` 按 GPT-5.6 处理，该修复与新增验证见
[固定名称兼容修复](./2026-09-10-GPT聊天滚动模型固定名称兼容修复.md)。下文表格保留修复前 rc36 的诊断结果，
其中 `gpt-chat-latest` 一项的当前状态以该修复记录为准。

### 环境与验证边界

- 环境：本机合并后的源代码，Go 1.26.5；临时 SQLite 仅存合成测试用户，不读取业务渠道或凭据。
- 使用 Go overlay 注入临时探针，不修改生产代码。HTTP transport 拦截全部探针上游请求，捕获实际
  序列化请求的模型、路径及 token 字段，不发送到真实 Provider。
- 渠道测试调用真实 `testChannel`，涵盖模型映射、请求构造、adapter、参数覆盖、发送与响应解析。
  模拟上游遇到 `max_tokens` 即返回与截图一致的参数拒绝；合法形状返回固定 Chat JSON/SSE 或 Responses JSON。
  因而验证的是网关字段转换与该拒绝条件，不证明任意供应商支持这些模型或其它参数。
- 正式路径调用真实 `relay.TextHelper`，捕获发送请求后由模拟上游返回专用终止信号，避免进入计费。
  这 7 项验证发送行为，不是正式请求成功生成或结算验收。
- 61 个渠道用例中，37 个完整模拟调用成功，24 个成功复现参数 400；另有 7 个正式发送路径用例。
  全部 68 个探针断言通过，包含对已知失败的确认，不能解读为 68 次业务请求都成功。

### 渠道测试结果

除明确指定 Responses 的一项外，每行均覆盖流式/非流式、自动端点/显式 OpenAI Chat 端点四种组合。

| 客户名称或配置 | 最终发送 | 模拟结果 |
| --- | --- | --- |
| `gpt-5.5`、`gpt-5.6` | Chat，只有 `max_completion_tokens: 16` | 通过；同步前 GPT-5 前缀也已能识别，不能据此认为原反馈必由旧版本引起 |
| `gpt-6-astra`、日期快照 `gpt-6-astra-2026-09-01` | Chat，只有新字段 16 | 通过；快照是命名匹配样本，不证明真实模型存在 |
| `chat-latest` 分别映射到上述三个标准基础模型；`customer-chat` 映射到 Astra | Chat，发送映射后的模型，只有新字段 16 | 通过，客户别名不影响能力转换 |
| 裸名 `chat-latest`、`gpt-chat-latest`、`gpt-6` | Chat，仍带 `max_tokens: 16` | 复现 400；这些名字未命中本次能力表 |
| `chat-latest` 映射到不透明 `deployment-a` | Chat，仍带旧字段 16 | 复现 400；网关不能仅凭部署字符串识别模型 |
| 裸名 `chat-latest`，开启截图中的完整策略 | 仍为 Chat，仍带旧字段 16 | 复现 400；策略未进入渠道测试链 |
| `chat-latest` 映射到 Astra，同时开启截图策略 | 仍为 Chat，只有新字段 16 | 通过；原因是 adapter 能力转换，不是策略将端点改成 Responses |
| Astra 参数覆盖重新写入 `max_tokens: 16` | Chat，同时出现新旧字段 | 复现 400；参数覆盖执行于转换之后 |
| 裸名 `chat-latest`，显式选择 OpenAI Responses，非流式 | `/v1/responses`，不含两个 Chat token 字段 | 模拟通过；真实供应商是否支持该端点待验收 |

### 正式请求发送结果

| 情况 | 实际发送结果 |
| --- | --- |
| 客户 `chat-latest` 映射到 Astra，关闭策略与透传 | 新字段 16，模型改为 Astra |
| Astra 同时传旧字段 16、新字段 32 | 两个字段均保留，该边界仍存在 |
| Astra 仅传新字段 32 | 原样保留新字段，无旧字段 |
| 裸名 `chat-latest` 命中策略，关闭透传 | 转向 `/v1/responses`，`max_output_tokens: 16`，无两个 Chat 字段 |
| `customer-chat` 映射到 Astra，但只有 Astra 名称命中策略 | 仍走 Chat；能力表正确转换为新字段。策略匹配客户名称，能力表匹配映射后名称，两者依据不同 |
| 开启渠道透传或全局透传，同时配置策略与映射 | 原始正文仍带客户名称和旧字段；转换策略及 adapter 参数转换均被绕过 |

## 优化方案与剩余验收

1. 如果供应商要求的真实上游 ID 是 `gpt-5.5`、`gpt-5.6` 或 `gpt-6-astra`，将客户别名准确映射到该 ID，
   清除会重新添加旧字段的覆盖，再使用已部署的 rc.36 复测。不要为命中能力表虚构模型或改写供应商部署 ID。
2. 如果供应商要求裸名 `chat-latest` 或不透明部署名，升级没有解决识别缺口。供应商明确支持 Responses 时，
   可先显式选择 Responses 测试；正式请求可使用现有策略并关闭其不需要的透传。策略命中以客户名称为准。
3. 若产品要求“测试按钮遵循正式 Chat→Responses 策略”，应单独评估复用现有转换路径的最小接线，并对照
   上游演进；本次只测试，未增加第二套参数规则或改变原生透传语义。
4. 双非零字段与转换后覆盖的边界仍需独立处理；该结论不能替代对原截图渠道配置的取证。
5. 尚未读取实际渠道映射、部署版本或执行真实 Provider 请求。生产故障是否消失仍待真实渠道复测；本次也
   不覆盖推理预算 16 是否足以产生可见输出、采样参数支持和实际计费。
