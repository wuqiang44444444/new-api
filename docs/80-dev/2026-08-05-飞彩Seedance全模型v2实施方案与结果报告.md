# 飞彩 Seedance 全模型 v2 实施方案与结果报告

## 1. 目标与结论

本次实施按 `docs/20-architecture/seedance 模型接入设计/飞彩/` 的单轨方案接入飞彩资料中的 10 个
Seedance 模型。飞彩只保留 `feicai.seedance-videos@v2`；不保留飞彩 v1 capability、implementation、adapter
或 size fallback。其他 Provider 的 v1 合同不受影响。

截至 2026-08-05，本地代码、两条飞彩渠道的 10 模型映射、计费草案、确定性回归和正式 Provider
黑盒均已完成。Provider 直连黑盒确认 6 个精确模型能生成同源 HTTPS MP4；随后又从其中选择 Mini 720p、
Standard 720p 和 Standard 1080p，经本系统 `:8100` 的 ModelArk v3 客户入口完成了创建、持久化、轮询、
客户计费、鉴权内容下载和 Range 端到端验证。三个精确 `16:9` 组合已进入 v2 size registry 和 capability；
其余 7 个 SKU 仍无 size 白名单。由于生产 `/v1/tasks` 返回 404、逐任务 Provider 成本和客户价格审批仍未闭合，
渠道 51、52 与 10 条 Ability 已恢复禁用，三个模型不对客户暴露。

### 2.2 代码结果

- 新增飞彩 v2 implementation，登记 10 个 execution binding、三类媒体和 v2 adapter 快照。
- 飞彩 v1 implementation 不再注册；解析 `feicai.seedance-videos@v1` 会失败。
- capability 新增 `min_images`、billing mode、显式 duration/resolution/ratio 要求和 Pro PI video role。
- SD2 在 Provider POST 前强制 1–9 张 reference image，禁止 audio/video。
- media-arrays converter 发送整数 `duration`，支持 `images[]`、`audios[]`、`videos[]`；video 仅 Pro PI 的
  `reference_video` 角色可通过 capability。
- audio/video 直传 URL 强制 HTTPS；未解析 `asset://` 不能进入 Provider dispatch。
- size resolver 已从全局 `{resolution}:{ratio}` 替换为：

```text
(implementation ID/version, provider_model, resolution, ratio)
  -> provider size + billing class + evidence version
```

- converter 与 billing probe 共用同一 resolver；registry 未命中时在预扣前拒绝。当前只登记
  Mini 720p、Standard 720p 和 Standard 1080p 的 `16:9` 精确组合，证据版本为
  `feicai-prod-2026-08-05-r1`。
- media-arrays adapter 当前版本提升为 `54:third_party_json_video_media_arrays:v2`，v1 快照不再接受。
- 飞彩 v1 的 `403 + feicai_account_required` 确定拒绝规则已移除。v2 在取得精确合同证据前一律进入
  `TaskCreateOutcomeUnknown`，不会错误退款。
- Provider create/query 仍以顶层 `id` 为唯一任务身份，不使用会漂移的 `task_id`。
- 生产黑盒发现主轮询还会返回小写 `in_progress`；v2 现将其精确归一为 running，并保留未知状态失败关闭。
- `/v1/tasks` 大写状态没有自动接入恢复链；目标生产 HTTPS Base URL 实测返回 404，在接口可用性及稳定关联
  证明闭合前，不用研究环境列表接口猜测归属。

## 3. 本地渠道与计费配置

### 3.1 渠道配置

本地 `one-api.db` 已更新：

- 渠道 51：5 个 VIP/standard 模型；精确 model mapping；Link implementation 为 v2。
- 渠道 52：SD2、4 个 933/value/Pro PI 模型；精确 model mapping；Link implementation 为 v2。
- 两条渠道 `status=2`（手工禁用）。
- 两条渠道共 10 条 Ability，全部 `enabled=0`。
- 受控 E2E 期间为三个 SKU 建立的 publication 作为不可变审计事实保留；因渠道和 Ability
  均已禁用，当前没有合格候选实现，`/v1/models` 不暴露这三个模型。
- Base URL、密钥、创建/查询路径和素材 TTL 未改动。
- 数据库变更前快照：`one-api-pre-seedance-v2-20260805.db`；临时目录另保留一份一致快照。

### 3.2 计费草案

10 个 Link SKU 均配置为 `tiered_expr`，预扣 token 均为 1。表达式语法已经使用
`billingexpr.CompileFromCache` 逐条编译通过。

按秒模型的草案形式为：

```text
v1:tier("base", duration_seconds × CNY研究单价÷7×1,000,000 × size_multiplier)
```

Pro PI 的草案不乘 duration：

```text
v1:tier("base", 1578571.428571 × size_multiplier)
```

这里的 `v1:` 是 billing expression 语言版本，不是飞彩 implementation v1。汇率 7、研究报价和
`size_multiplier=1` 都只是禁用渠道中的候选配置。正式黑盒已观察到 Fast 的单次成功窗口 usage 增量为
180 分，而研究估算为 240 分；因输出时长与任务级 quota 未在同一证据源闭合，不能据此反推生产单价，
更不能发布当前草案。

## 4. v1 处置与审计

切换前检查结果：

- 飞彩 Task：0。
- Task create attempt：2，均为历史 rejected/released 记录，且无 upstream task ID。
- binding、provider cost exposure、incident、asset/source：0。
- 两条旧渠道只有两个 v1 720p 模型。

- 删除运行时的飞彩 v1 capability、implementation、adapter 接受规则和确定拒绝分支。

- 两条历史 attempt 是不可变审计记录，不删除、不改写，也不作为 v2 恢复依据。

## 6. 正式 Provider 黑盒结果

### 6.1 范围、预算与安全边界

经明确授权，使用渠道 51、52 的现有真实凭据对正式 HTTPS Base URL 执行 10 模型黑盒，费用上限 ¥100。
验证器只把凭据放入请求头，不输出 Key、Provider task ID、完整结果 URL 或原始响应；临时下载的视频在
`ffprobe` 完成后删除。

测试分三段执行：

1. 10 模型首次矩阵：2026-08-05 08:11–08:19（Asia/Shanghai）；
2. 仅重试已明确终态失败的 Fast、value-1080p、value-4k：08:23–08:26；
3. 修正 `in_progress` 解析后单独复测 Pro PI：08:28–08:32。

账户 `total_usage` 从 5508 分变为 11196 分，受控窗口观察增量为 5688 分，即 ¥56.88，未超过授权上限。
渠道 51、52 当前使用同一账户凭据，因此不能把两份 usage 响应重复相加；该增量也不能在缺少逐任务 quota
时拆分为各模型实际成本。

### 6.2 本系统 `:8100` 端到端结果

本节与 Provider 直连黑盒分开：三次创建都请求本系统
`POST /api/v3/contents/generations/tasks`，客户端只使用 Link SKU，没有接触 Provider 模型名、凭据、
任务 ID 或结果 URL。每个任务都经过本地 publication/ability 选渠道、durable create attempt、客户预扣/
结算、后台 Provider 轮询和本系统内容代理。

| Link SKU | 创建与状态 | 平台内容代理 | MP4 证据 | 客户 quota |

| `seedance-2.0-standard-720p` | 200；`queued -> running -> succeeded` | 200；Range 206/1024 B | 4,556,997 B；1280×720；4.086712 s | 211429 |

### 6.4 生产合同偏差

- 主轮询除研究资料中的 `queued/processing/completed/failed` 外，实测还返回小写 `in_progress`。代码已将
  `processing` 与 `in_progress` 都精确归一为 running，并新增回归。
- 目标生产 HTTPS Base URL 的 `/v1/tasks`、带 `task_id` 过滤的 `/v1/tasks` 均返回 404，无法取得研究资料
  描述的大写状态和逐任务 quota。该接口不再被描述为当前生产可用事实。
- Fast 的隔离复测窗口 usage 从 11016 分增至 11196 分，增量 180 分；研究报价按 4 秒计算为 240 分。
  因当次产物时长尚未与任务 quota 同源冻结，当前只能判定“口径不一致”，不能反推新价格。
- value-720p 在请求 `size=1280x720` 时产物为 1256×720，证明 Provider 请求 size 与最终编码像素不能被
  当成同一字段，也不能把同族 720p 结果横向复用。

## 7. 验证器与最终发布决定

`cmd/verify-feicai-v2` 现在具备：

- 完整 10 模型矩阵及精确子集选择；
- 显式付费确认和所选模型费用上界检查；
- `/v1/models` 精确可见性与 usage 前后读数；
- 单次 create、无自动 create 重试、顶层 `id` 权威轮询；
- `queued/processing/in_progress/completed/failed` 主轮询状态；
- `/v1/tasks` HTTP 状态和任务级 quota 独立记录；
- 同源 HTTPS 内容完整下载、MP4 元数据、像素与时长探测；
- API Key、任务身份和完整内容 URL 脱敏输出。

最终决定是 10 个模型继续“已配置、当前禁用”：

1. 六个成功模型已有 16:9 创建、身份和内容证据，但缺少可信逐任务 Provider 成本与批准后的客户价格；
2. SD2 的 503 属 create unknown，在没有唯一对账源时禁止通过自动重发“测到成功”；
3. value-1080p、value-4k 与 Pro PI 尚无成功内容证据；
4. `/v1/tasks` 404 使研究资料中的任务级 quota 与 create-unknown 恢复路径不可用；
5. Mini 720p、Standard 720p 和 Standard 1080p 的 `16:9` 已用本系统 E2E 证据登记；
   这不授权横向推导其它画幅或其它 SKU。

因此 production size registry 当前只有上述三个精确条目，对应 capability ratio 只有 `16:9`；渠道
51、52 保持 `status=2`，10 条 Ability 保持 `enabled=0`。三条 publication 作为受控 E2E 中已经发生的持久化事实
保留，但当前无合格候选实现。后续必须在任务账单或等价供应商账单、usage 口径和客户价格审批闭合后，
才能对三个已验证模型重新启用；其它模型仍须分别取得自身证据，不得为了“全部可用”放宽 fail-closed 门禁。
