# 近三天错误专家分析复核

## 问题与目标

对另一份专家分析逐项复核，判断哪些结论有数据库和代码支持、哪些只是假设，以及哪些修复建议可能改变协议或计费语义。
本记录补充 [原分析](2026-09-22-近三天数据库错误分析与代码改进建议.md)，不实施业务代码、配置、渠道状态或资金变更。
用户已确认 429 属上游并发容量问题，本轮继续排除，不改变其处理策略。

本复核结论已按用户要求整合进[主分析文档](2026-09-22-近三天数据库错误分析与代码改进建议.md)。
本文保留专家观点的逐项评审与证据；综合结论、最新优先级和实施跟踪以主文档为入口，避免维护两份独立待办。

## 当前实际情况

### 1. 证据范围与总判断

- 数据库：当前工作区 `one-api.db`，以 SQLite `mode=ro` / `query_only` 读取。
- 主窗口沿用原报告：北京时间 2026-09-19 23:13:14—09-22 23:13:14，Unix 秒 `1789830794`—`1790089994`，包含两端。
- 延伸窗口单独统计至北京时间 2026-09-23 14:15:45，Unix 秒 `1790144145`。之后数据库继续新增的记录不并入此快照。
- 核对 `error_events`、消费及错误日志、合同审计、渠道当前状态、系统任务检查结果；另读取本机电源日志验证休眠线索。
- 当前代码说明当前实现机制；未独立核验每次历史请求对应的进程构建版本，不能把当前代码当成历史执行追踪。
- 未读取 Provider 账单或客户侧日志；不输出客户正文、凭据、完整 URL、私有任务数据或原始上游响应。

总体判断：专家补充的渠道自动禁用时间线和零扣费关联有价值，但“全部闭环”“全部正确拒绝”“真实收入损失已经成立”表述过强。
Gemini 的错误类别已明显收窄，但其默认补类型方案不可直接采用。合同历史、403 分类、计费现有能力和素材回源责任存在具体事实错误。

### 2. 合同 503：主要因果链可信，但要更正触发机制和证据强度

数据库时间线复核如下，时间均为 09-22 北京时间：

| 时间 | 已核实事实 |
| --- | --- |
| 19:01:59 | 渠道 56、用户 154 的传统错误日志记录上游 HTTP 503 |
| 19:05:19 | 错误事件 1526：渠道 56 自动测试 `response_time_exceeded`；上游 HTTP 200，实际耗时 263,643 ms |
| 18:58:43—19:06:31 | 系统任务 155477：测试 68 个目标，失败 7，`disabled=1`；渠道 56 的检查结果是响应超阈值 |
| 19:05:23—19:12:35 | 100 次合同 503，用户 106 为 83 次、用户 154 为 17 次 |
| 19:36:38—19:38:37 | 系统任务 155682：失败 0，`enabled=1`；渠道 56 于 19:37:27 完成真实生成探测并通过 |
| 19:37:27 | 渠道 56 当前 `other_info.status_time` 与该测试时间一致 |

两个合同在事发前的历史审计快照中，相关 GPT 模型确实仅指向渠道 56。
`model/customer_contract_availability.go:95` 排除非启用渠道；`service/customer_contract_routes.go:103` 过滤不可用规则，候选为空时返回范围错误；
`middleware/distributor.go:51` 的选渠出口返回 503。这与上述时间线一致。

但专家有三个地方需要修正：

1. `setting/operation_setting/status_code_ranges.go:17` 的默认自动禁用范围是 **401**；500—503 出现在自动重试范围。
   当前数据库也不存在 `AutomaticDisableStatusCodes` 覆盖项。不能据此说 19:01 的 503 按状态码触发禁用。
   当前自动禁用总开关、渠道 auto_ban 和 90 秒阈值符合超时禁用路径；真正有力的触发证据是 19:05 的 **263.643 秒探测**。
2. `controller/channel-test.go:1015` 对超过阈值的实际探测独立设置禁用判定，即使上游是 HTTP 200。
   因此应描述为“探测总响应耗时超阈值触发保护，合同单渠道依赖导致不可用”。这并不能进一步证明一定是 Azure 慢首 token。
3. `model/channel.go:798` 的 `status_time` 只是最近一次状态更新时间，会被覆盖；它单独不能证明自动恢复。
   本次是系统任务 `enabled=1`、渠道 56 成功探测、当前状态时间三者相互印证。任务汇总计数仍不是逐渠道状态提交回执，100 条请求又缺模型，故不宣称逐笔不可反驳闭环。

“其他流量完全正常”也应收窄：同一轮测试还包含其他 6 个渠道的拒绝。部分测试成功不能证明全部客户流量健康。

**代码侧含义：** 首先修复诊断与状态变更审计，不应直接删除自动禁用或绕过合同授权。
合同只授权一个渠道时，不得自动使用合同外渠道。是否增加已授权渠道是配置/产品决策。

### 3. 合同 403：数量与历史解释存在明确错误

主窗口内可确认的合同拒绝是 **101 次**：用户 106 为 100 次、用户 154 为 1 次。
其中 09-20 用户 106 为 81 次，09-22 用户 106 为 19 次、用户 154 为 1 次。
专家提及的用户 170 有另 **6 次原生令牌模型权限拒绝**，响应不是合同不可用。101 + 6 = 107，不能统称为合同 403。
此外还有素材令牌模型权限和余额不足等独立 403 类别，HTTP 状态不能代替业务归因。

合同 16 的历史审计直接否定“当前规则创建时间证明当时尚未授权”的推理：

| 时间 | 合同 16 的历史事实 |
| --- | --- |
| 09-14 09:52:45 | 创建时已含 gpt-5.5、gpt-5.6-luna/sol/terra、gpt-6-astra → 渠道 56 |
| 09-14 10:01:55 | 合同启用 |
| 09-18 15:36:22 | 已有 gpt-image-2、gpt-image-2-n → 渠道 57 |
| 09-20 10:47:10 | 版本更新，模型/渠道集合未变化 |
| 09-20 14:52:45 | 为已有两个图片公开模型增加 110—119 渠道；没有新增公开模型名称 |

`model/customer_contract_entity.go:330` 保存规则时先删除该合同全部规则，再重建。
所以当前规则行的 `created_at=09-20 14:52:45` 是最近重建时间，**不是 GPT 模型第一次被授权的时间**。
应使用 `customer_contract_entity_audits.before_state/after_state` 判断历史。

这也不意味着 101 次拒绝就是代码误拒。`service/customer_contract_routes.go:86` 的合同门同时检查令牌模型限制与合同列出的模型。
缺少请求模型、拒绝分支和当时令牌限制，无法证明“全部正确”，也无法证明“全部误拒”。
同秒有成功和 403，只能说明两类请求同时存在，不能证明必然是 Codex 主模型与辅助模型差异。

**不赞成直接统一 403/503：** 当前合同门检查模型授权，选渠阶段检查可用性；模型未授权适用 403，已授权但没有健康候选适用 503，有合理区别。
两处复用 `ErrCustomerContractScope` 和相同公开文案，造成诊断混淆；应先拆分内部原因，再维持与业务语义匹配的状态码。
不能仅因为复用了一个 Go 错误变量就认定是“同一真实原因返回两个状态码”。

### 4. 断连与零扣费：关联成立，但确定收入损失和计费缺陷尚未成立

同一主窗口、按非空 `request_id` 对齐：

| 统计 | 数量 |
| --- | ---: |
| 所有客户端断连事件 | 517 |
| 用户 106 的断连事件 | 502 |
| 用户 106 的零扣费且带缺计费信息说明的消费日志 | 495 |
| 上述 495 笔与该用户断连的交集 | 495 |
| 该用户其他已扣费的断连请求 | 7 |
| 全用户零扣费且带缺计费信息说明的消费日志 | 505 |
| 全用户上述零扣费与断连交集 | 499 |

495 笔按日期为 09-20：124、09-21：5、09-22：366，全部在 `/v1/responses`，记录为 Responses 原生协议处理。
所以“495 笔都关联断连”成立；“断连必然零扣费”不成立，也不能把这一用户子集外推给全部流式请求。

专家遗漏了已有代码能力：

- `relay/helper/stream_scanner.go:298` 观察到请求上下文取消后关闭上游响应体，目的是停止继续读取和尽量停止上游生成。
- `relay/channel/openai/relay_responses.go:92` 从完成事件提取 usage；`:131` 积累文本 delta；
  **`:153` 在缺少输出 token 时对已收到文本估算 token，`:163` 再补估算输入 token。**
- `service/text_quota.go:454` 在没有可计费用量时写入缺计费信息说明，并以算出的 quota 结算；该说明并不是 Provider 账单证明。

因此“最终 usage 未到 → 必定无法扣费”不符合当前实现。需要查的是：请求终止前实际收到哪些流事件、是否收到文本、是否只有推理或工具参数、估算路径有无有效输入。

现有日志进一步表明：495 笔中 **307 笔 `frt=-1000`**，188 笔 `frt>=0`。
`relay/common/relay_info.go:574` 将首响应时间初始化为开始时间减一秒，`service/log_info_generate.go:107` 直接写入差值，故 -1000 表示首响应时间尚未设置，不是负延迟。
188 笔有首事件也不代表有文本 delta：可能只是创建、排队、推理或工具相关事件。

这 502 次断连大量集中在 09-20 11 时、09-22 09/11/16 时，并非集中在 09-22 19:05 的渠道故障窗口。
不能用一次夜间自动禁用事件，证明前面数百次取消都由同一慢首包故障造成。
`client_gone` 也无法区分用户主动停止、客户端超时或中间代理取消。

**建议命名为“取消流的用量证据缺口及潜在成本暴露”。** 实际 Provider 成本、应收客户费用、已经少收金额是三个不同量。
需要将 Provider usage/账单与请求关联后量化；成功长请求的 3,000—27,000 quota 不能直接乘以 495 估算短时取消请求损失。
不应直接追加最低消费、按请求数补扣，或无上限继续读取已取消流。

### 5. Gemini 400：可确定失败点，不足以批准默认类型修复

27 次均为同一用户、渠道 103、同一模型；错误均指向工具定义中 `video` 节点缺少 schema type。
这一点确实比原报告更进一步，可将“泛化 Gemini 400”收窄为“工具 schema 在目标协议校验失败”。

但 27 次的 **北向 request 与南向 upstream_request 均为 `too_large`**，没有保存正文。
因此还不知道原节点是显式空 schema、只有 description、通过 `$ref` 引用类型、使用组合 schema，还是转换中丢掉类型信息。
上游报错证明发送后的形状不被接受，不能独自证明客户端原定义或网关转换哪一步有错。

专家对代码的描述也不准确：`relaykit/relayconvert/internal/shared/gemini/schema.go:36` 不只是删空 properties；
它有字段白名单、类型规范化、nullable 处理、properties/items/anyOf 递归及深度限制。
当前白名单不保留 `$ref`、`$defs`、`allOf`，这是应核对的可能信息损失点，**尚不能认定本次请求使用了它们**。
同一 helper 被 Chat、Responses、toolconv 三个入口使用，不能只在其中一条转换路径补另一套规则。

“有 properties 就 OBJECT、有 items 就 ARRAY、其他都 STRING”有明确语义风险：

- `{}` 在 JSON Schema 中允许任意合法 JSON；补 STRING 会改变允许的值。
- 数字枚举或数字/布尔联合类型不能默认解释成字符串。
- `$ref` 若已被删除，正确动作首先是确定引用合同和目标支持能力，而不是凭空指定字符串。
- 即便有 properties/items，也需要确认源 schema 的类型约束意图；不能把常见写法等同于普遍等价转换。

空 schema 与类型约束的区别可由 [JSON Schema 官方说明](https://json-schema.org/understanding-json-schema/basics) 核对。
上述例子是方案语义反例，不是对这 27 笔客户正文的推测性还原。

**最小下一步：** 获取不含业务正文的 schema 结构特征或最小脱敏复现；比较转换前后节点。
修复在共享转换层完成，覆盖 Chat 和 Responses。能保持语义的转换应保持语义；无法表达时明确返回受控的不支持原因，不能静默造类型。
新增诊断只保存缺失 type、引用/组合结构、节点类别等受控事实，不为排障扩大持久化客户完整请求。

### 7. 延伸窗口与部署环境

截至本次固定延伸截止点，渠道测试事件 **78 次、26 个渠道**，互斥 reason 分类为：

| reason | 数量 |
| --- | ---: |
| test_upstream_rejected | 42 |
| response_time_exceeded | 21 |
| test_upstream_unreachable | 10 |
| test_config_error | 3 |
| asset_probe_failed | 2 |
| 合计 | 78 |

21 次超阈值中，detail 的 upstream_status 为 200 的有 **12 次**、504 的有 8 次、666 的有 1 次。
不能将这些子集再与 reason 汇总相加。`error_events.status` 与受控 detail 中的 `upstream_status` 也不能混为同一字段。
专家的“62 次失败 + 15 次 200 超时”与本次可复核口径不一致，其列出的分类数字本身也无法支撑这个拆分。

相对原窗口，新增的是 7 次不可达、1 次超阈值、1 次素材探测失败；未观察到新增已入库 API 错误或 Task 失败。
这只能证明采集范围内没有新记录，不是完整请求成功率证明。

夜间 `task lease expired` 实际为 **9 个系统任务：6 个 channel_test、3 个 error_report**，最后一批于 08:55:37 标记失败。
不是 9 个客户生成 Task，也不等于 9 次客户订单失败。

本次额外核对 `pmset -g log`：本机夜间多次 Sleep / DarkWake。
例如 02:45:05 创建的测试任务，随后机器进入休眠；03:00:16 唤醒，03:00:29 被标记租约过期。
05:13 和 05:47 的任务创建/失效也与短时唤醒及再次休眠时段对应。
结合 `model/system_task.go:371`—`:397` 的过期锁回收机制，**休眠中无法正常续租、唤醒后发现过期**是有较强直接证据的解释。

应优先处理承载在线服务的主机持续运行与网络可用性，不应通过取消租约、无限延长锁来掩盖。
数据库中有客户业务记录不能单独证明部署的正式 SLA；若此实例承载需要持续可用的客户流量，该运行形态确实存在风险。

“SQLite 写负载导致只读查询 unable to open database file”仍未证实：本次只读查询成功，也未获得专家那两次查询的连接路径、环境、权限和扩展错误码。
不能把查询工具连接失败直接归因数据库锁竞争，或据此推断客户数据库写入故障。

## 优化方案

### 1. 建议优先级与最小修复边界

以下为本次复核提出的建议摘要；已合入主文档“优化方案”，后续状态只在主文档“最小侵入、实施顺序和剩余事项”更新。

| 优先级 | 工作项 | 应做的最小动作 | 验收重点 |
| --- | --- | --- | --- |
| P1 | 合同拒绝诊断 | 在现有合同门与候选筛选权威路径保存模型、合同版本、拒绝原因和候选数量；拆分令牌限制、合同未列出、渠道禁用、能力缺失、读取失败 | 相同公开错误可在后台精确区分；403/503 对应真实语义；不泄露上游身份，不放宽权限 |
| P1 | 渠道状态变更证据 | 记录自动/手工来源、状态前后、受控触发原因和关联测试；记录持久化成功事实，不只保留汇总计数或覆盖式 status_time | 能把某次无候选与真实禁用相连；并发失败不能被误报为已提交状态变化 |
| P1 | 素材诊断入事件库 | 保留已有安全诊断中的 HTTP 状态、网络/解码类别与 source/upstream 阶段 | 502 可区分拒绝、网络和解析；源站失败不再归给素材 Provider；不保存源 URL |
| P1 调查 | Gemini schema | 先取得最小脱敏复现或结构诊断，再修改共享转换 helper | Chat/Responses 行为一致；空 schema、引用、枚举和组合不会被错误改成 STRING；无需增加第二套转换实现 |
| P1 运维 | 夜间休眠 | 对持续提供服务的实例落实持续运行、网络和调度健康检查 | 跨夜系统任务能正常续租；异常退出仍能由租约恢复 |
| P2 | 取消流用量证据 | 区分未收到首事件、收到首事件无文本、已收到文本、拿到 usage；记录估算是否实际使用 | 与已有文本估算共用权威路径；不重复扣费；不把未知供应商成本记成零或客户 quota |
| 暂缓 | 取消流收费政策 | 先做 Provider 用量/账单核对，再决定是否调整收费合同 | 不按完整成功请求均价推算损失，不直接补扣 |
| 不纳入修复 | 明确的输出长度输入错误、版权/音频拒绝 | 保持明确错误反馈；图片尺寸优先调用方处理 | 不静默扩大输出、不自动改尺寸、不绕过审核 |
| 继续排除 | 429 | 按用户要求暂不处理 | 不改并发、重试或相关资金状态 |

上述 P1 调查不表示已批准业务实现；诊断修复也必须保持 NEWAPI 原生最小侵入，以现有权威路径为准。
“所有渠道不可用”应与“已确认自动禁用”分开存储；没有状态变更证据时不能把“疑似自动禁用”写成事实原因。

### 3. 可复核统计口径

主窗口统计均使用 `created_at BETWEEN 1789830794 AND 1790089994`。
零扣费候选为 `logs.type=2 AND quota=0 AND content LIKE '%上游没有返回计费信息%'`；
与 `error_events.reason='client_disconnected'` 按 request_id 对齐，并分别统计用户 106 和全部用户，避免子集外推。
渠道测试延伸统计使用 `created_at BETWEEN 1789830794 AND 1790144145`，按 reason 互斥分组；上游 HTTP 状态从 detail 的 upstream_status 读取。
合同历史采用审计 before/after 中模型和渠道集合的差异，不能以可重建规则行的 created_at 代替首次授权时间。
