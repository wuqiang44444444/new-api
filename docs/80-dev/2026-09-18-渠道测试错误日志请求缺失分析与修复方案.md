# 渠道测试错误日志请求缺失分析与修复方案

## 问题与目标

自动渠道测试错误详情显示上游 400，但顶部显示“无 HTTP 响应”，四段正文均为“此事件未记录正文”，
方法、路径和协议也为空。本次补齐诊断信息并明确状态所属方向，遵守 NEWAPI 原生代码最小入侵原则。

## 当前实际情况

### 已验证事实

- 环境：本地 SQLite 与本地开发进程；未重新调用真实 Provider。
- 截图对应 `error_events.id=130`，2026-09-18 09:30:08（Asia/Shanghai），渠道 87。
  该行 `event_type=channel_test`、`status=0`，详情只有 `test_mode=auto`、`upstream_status=400`，
  不存在 `http_exchange`。当时库中全部 130 条错误事件均无正文快照；不是前端把已存正文解析丢失。
- 生成该事件的后端于 00:57:52 启动、09:30:54 退出。正文采集相关文件最后修改时间为 01:03—01:13，
  晚于该进程启动；启动入口为 `go run .`，没有后端热更新。证据指向旧进程未加载新增正文采集实现。
- 随后后端于 09:31:03 启动、09:31:24 退出，未生成新的渠道测试错误事件，不能将其当作修复后的验收。
- 同时刻运行日志显示 OpenAI、`/v1/chat/completions`、非流式，上游错误的脱敏摘要为“参数解析失败”。
  未保存该次请求正文，无法确定具体错误字段；不将渠道名称推断为实际使用 Gemini 协议。
- 自动事件的 `status=0` 表示没有客户 HTTP 状态；前端将它泛化为“无 HTTP 响应”，与上游 400 形成误导。
- 当前后台事件结构未承载 method、route、protocol；重启只能启用已有正文采集，不能补齐这三个字段。
- 自动测试不归属客户身份，用户名、令牌为空是正确语义。上游 400 分支未写客户响应，网关返回正文可为空。

### 未确认项与边界

- 文件时间与运行日志支持上述版本判断，未保留旧二进制逐符号对照。
- 不修改历史错误行，不伪造历史正文、协议或路径，不自动重放渠道测试。
- 本次不修上游“参数解析失败”的业务请求，不修改模型映射、路由选择、计费和测试调度。

## 优化方案

### 后端

1. 沿用 `clienterrlog` 现有 HTTP 正文采集与 `error_events` 入库实现，不增加表、迁移或第二套采集器。
2. 在本地 `BackendEvent` 扩展 method、route、protocol，净化后写入现有同名字段。
3. 在渠道测试事件构建处读取合成测试请求的方法和纯路径（不含 query、host、headers）；协议直接取
   已选定的 `relayFormat`，不根据模型或路径重新推断。
4. 通过已有 `ObserveChannelTestRequest` 调用传递协议；手工与自动事件复用本地提交入口。
5. 新增独立测试，覆盖自动与手工测试的状态语义、请求元数据、上游拒绝正文、脱敏和提前失败。

### 前端

1. 错误列表和详情共享小型状态展示组件，继续复用 `StatusBadge`，避免两处状态解释分叉。
2. 渠道测试以已记录的 `detail.upstream_status` 显示“上游 HTTP 400”；缺失时显示“未记录上游 HTTP 状态”，
   不从错误码推断响应状态。详情单独保留手工测试管理接口的 HTTP 状态。
3. 其他事件继续使用实际客户状态；状态 0 显示“无客户 HTTP 状态”。数据库状态字段保留原事实；筛选含义按下文补充修正，与列表展示一致。
4. 无正文的历史事件保持缺失提示；只更新中英文文案，不扩展其他语言。

### 最小入侵与上游同步影响

| 位置 | 必要性与改动边界 | 上游同步影响 |
| --- | --- | --- |
| `controller/channel-test.go` | 已有观测调用增加已选协议参数，单行接线 | 仅该调用可能冲突；不改测试控制流和原生 adapter |
| `service/channel_test_error_event.go`、`clienterrlog/backend.go` | 本地日志扩展负责组装、净化和传递 | 不扩写原生业务实现 |
| 错误日志前端目录 | 本地错误日志列表与详情共用状态语义 | 不改通用 StatusBadge 和原生使用记录 |
| 独立后端测试文件 | 模拟上游拒绝并通过真实测试路径检查日志证据 | 不把测试塞入原生测试文件 |

- 后端验证：渠道测试集成路径、事件净化与正文采集/保存的现有回归；只使用内存数据库、模拟上游。
- 前端验证：受影响测试、类型检查、文件级 lint 和格式检查。

## 状态搜索补充修复（2026-09-18）

### 问题与目标

用户选择 HTTP 200 后，页面仍返回“上游 HTTP 500”。这是查询合同与展示合同不一致，不能仅通过
解释 200 的含义解决。目标是筛选、列表、详情和分页总数一致，同时保留客户/管理接口的真实状态事实。

### 当前实际情况

- 已在真实 Chrome 页面复现：选择 200 返回一条 10:07:39 的渠道测试，上游 HTTP 500。
- `model.GetErrorEvents` 原先固定按 `status` 列筛选；`ErrorLogStatus` 对渠道测试改为读取
  `detail.upstream_status`。前一次修复只调整了显示，漏掉后端查询。此前前端 mock 测试不能证明真实查询。
- 该条 `status=200` 是管理接口已成功返回测试结果，返回内容中的 `success=false` 才是测试失败。
  上游实际返回 500，两者不是同一次 HTTP 交换。错误事件还包括 HTTP 200 后的流式中途失败或解析失败，
  因此不能简单删除 200 选项，也不能将所有日志的 200 强制改成 500。

### 优化方案与最小入侵

- 只在本地错误日志查询中增加一个独立状态过滤函数：渠道测试读取已记录的上游状态；其他事件读取
  客户状态；未记录对应状态时按 0 筛选。管理接口原始 `status` 及历史数据保持不变。
- 提取 `detail` 顶层 JSON 字段，支持已有仅含 `upstream_status` 的历史事件。按日志库类型使用
  SQLite、MySQL、PostgreSQL、ClickHouse 的 JSON 表达式，不使用字符串模糊匹配。
- 过滤在数据库中执行，先过滤再计数/分页；不加载全表到内存过滤，不增加新列、回填任务或第二份状态事实。
- `model/error_event.go` 仅替换状态查询调用并更新注释；新增逻辑位于 `model/error_event_status.go`。
  均为本地错误日志扩展；本轮不增加 NEWAPI 原生文件修改、不改变渠道测试或 Provider 行为。
- `detail` 沿用现有写入合同：空值或由 `common.Marshal(map[string]string)` 生成的 JSON，
  `upstream_status` 是规范化的三位 HTTP 状态字符串；缺失、空值、无效状态按未记录处理。
- JSON 字段筛选需要读取候选行的诊断文本；可组合时间/事件类型等现有过滤缩小范围。本次优先避免表结构
  迁移和历史数据改写，未将本地功能验证宣称为大规模日志性能验收。
