# 用户历史用量虚高分析与修复方案

## 问题与目标

用户要求部署后自动修复历史累计消费，后续查询显示最新结果。2026-09-24 补充确认：
**单实例、线上 SQLite，并支持 PostgreSQL；旧备份不在，错误退款也按退款处理。**
按仓库约束同时保持 MySQL 兼容。主库与日志同库时，新版本在开放业务前自动执行，
不要求正常升级逐用户填写核验文件、生成清单或运行 repair 命令。

代码已实现并通过本地业务库副本验收：84 个用户中校正 5 个、保持 79 个、阻塞 0 个；
randy 从 5,545,156,555 修正为 2,829,317,796 quota，余额和请求数不变。副本再次运行校正 0 个、
保持 84 个。**原业务库与生产库未执行本次校正，生产验收仍待实际部署。**

本方案的用量为客户累计净消费金额，包含已入账预扣并减去已记录退款；不是 Token 数、供应商成本
或“所有任务均已最终结清的费用”。仍以 `users.used_quota` 为唯一累计投影，不重放资金、不新增账本。
后续消费和退款沿用既有有符号统计更新，查询不临时全表汇总日志。

依据：[硬约束](../00-context/硬约束.md)、
[异步任务与计费事实架构](../20-architecture/账单计费-异步任务与计费事实架构.md)、
[API Key 用量账单架构](../20-architecture/账单计费-APIKEY用量账单架构.md)、
[客户与上游对账架构](../20-architecture/账单计费-客户与上游对账架构.md)。

## 当前实际情况

### 1. 本地证据与精确对账

2026-09-23 通过 SQLite 只读连接检查仓库本地 `one-api.db`。本地没有用户名 `rany`，与反馈金额
对应的是 `randy`，用户 ID 为 91。其最新留存日志时间为北京时间 2026-09-22 18:50:19；本轮结果
不等于线上实时查询结果。美元换算为 `quota / 500000`，以下计算均先使用整数 quota。

| 项目 | 条数 | quota | 美元（保留六位） |
| --- | ---: | ---: | ---: |
| 用户累计 `used_quota` | 1 | 5,545,156,555 | 11,090.313110 |
| 消费日志 `type=2` | 34,043 | 6,361,019,369 | 12,722.038738 |
| 退款日志 `type=6` | 2,578 | 3,531,701,573 | 7,063.403146 |
| 消费减退款 | — | 2,829,317,796 | 5,658.635592 |
| 可匹配 TaskBillingDelivery 的退款日志 | 789 | 815,862,814 | 1,631.725628 |
| 未匹配交付记录的退款日志 | 1,789 | 2,715,838,759 | 5,431.677518 |

核对等式：

```text
6,361,019,369 - 815,862,814 = 5,545,156,555（等于当前 used_quota）
6,361,019,369 - 3,531,701,573 = 2,829,317,796（留存日志净额）
5,545,156,555 - 2,829,317,796 = 2,715,838,759（等于未匹配退款合计；本轮按已确认的记录退款政策校正）
残差 = 0 quota
```

匹配使用日志稳定 `request_id = task-billing:<Task 行 ID>:<event>`，不是按时间或金额猜测。
1,789 条包含 1,778 条无新版事件标记的任务退款、7 条带人工退款元数据的记录，以及
2026-09-14 00:00—00:01 的 4 条 `adjustment` 退款。最后 4 条合计 4,194,445 quota，
解释了只统计无新版事件标记退款时剩余的 8.388890 美元差异。

评审复核进一步按是否具有 `task-billing:` 前缀拆分退款，得到以下互斥分类：

| 分类 | 条数 | quota |
| --- | ---: | ---: |
| 精确匹配交付记录 | 789 | 815,862,814 |
| 有 `task-billing:` 前缀但没有对应交付记录 | 7 | 9,385,336 |
| 其他未匹配交付记录的退款 | 1,782 | 2,706,453,423 |

宽松前缀匹配共 796 条、825,248,150 quota，比精确匹配多出的就是上述 7 条。只读复核确认这
7 条全部带 `admin_info.manual_refund` 标记及 `original_preauth_log_id` 原预扣引用，不再仅是
“可能为人工退款”的推测。它们仍单列为“人工退款日志，未关联交付记录”；标记与引用的存在不单独证明历史统计处理方式。
2026-09-24 用户确认历史备份不在、错误退款也按退款处理，因此这 7 条按已记录退款纳入净额，
不再要求找回脚本或伪造逐笔人工核验。
日志前缀不证明已交付，缺少交付行也不证明应再次回减。

另外已验证：

- 用户 91 没有尚未交付的 `task_billing_deliveries`；消费、退款非空 Request ID 未发现重复。
- `quota_data` 合计为 5,536,704,637 quota，同样不是日志净额，不能用它替代首页累计字段。
- 当前钱包余额为 186,392,868 quota，请求数为 33,799；这些值不属于本次累计金额校正目标。
- 本地仍有未结清的图片任务；因此 5,658.635592 美元只能称留存日志净额，不能称全部最终费用。

上述对平能证明本账号累计值与退款投影之间的精确差异，但“没有交付记录”不是通用的漏减判定：
原生退款、旧版已正确处理的退款和人工校正均可能没有这类记录。其他用户仍须满足下述精确总额边界，不能仅凭
无交付记录自动扣减统计，也不能从日志留存最早日期推断账户全生命周期记录完整。

### 2. 代码根因与当前链路

| 环节 | 已核实行为 | 代码位置 |
| --- | --- | --- |
| 首页 | 从 auth store 读取 `user.used_quota` 后调用 `formatQuota` | `web/src/features/dashboard/components/overview/summary-cards.tsx` |
| 用户资料 | `/api/user/self` 读取主库用户行并返回 `used_quota` | `controller/user.go`、`model/user.go` |
| 旧版异步结算 | 退还钱包/Key 并记录退款，但负差额没有回减用户与渠道累计统计 | 提交 `3ed0f5c57` 的父版本 `service/task_billing_state.go` |
| 旧版正差额 | 仅 `quotaDelta > 0` 时调用 `UpdateUserUsedQuotaAndRequestCount` | 同上，`recalculateTaskQuotaWithReconcile` |
| 当前异步交付 | 用有符号金额更新用户、渠道、QuotaData，与交付确认同一主库事务 | `model/task_billing_delivery.go`、`model/task_log_quota_data.go` |
| 当前旧任务退款 | 资金退款后单独回减用户和渠道用量 | `service/task_billing.go` |
| 图片 | 部分累计统计在图片完成事务中提交，交付明确跳过重复更新 | `model/task_image_lifecycle.go`、`model/task_billing_delivery.go` |
| 售后退款 | 原 Task 追加 `customer_refund` 事件，再交付统计 | `model/video_fund_refund.go`、`service/video_fund_refund.go` |

现有 `service/task_billing_delivery_test.go` 已覆盖退款差额、分库日志写成功但主库确认失败的恢复，
并验证余额不重放、用户累计值只更新一次。当前代码已有新事件修复机制；不能再在结算 service
无条件减一次用量，否则会与交付事务重复回减。代码存在不证明所有运行实例均已升级。

首页进入/聚焦的资料刷新已接线，并补齐用户 ID、会话 SID 与旧响应隔离。刷新只重新读取主库，
不会自动修复旧 `used_quota`；截图中的管理列表也不是首页刷新 hook 所覆盖的入口。
`auth-store.ts:setUser` 本身无条件替换用户，竞态保护由刷新流程承担，不能把 setter 当成通用守卫。
本轮已补启动校正与统一查询投影；首页刷新负责获取数据库最新值，历史修正由启动事务完成。

### 3. 不能直接按全部留存日志覆盖累计值

`common.LogConsumeEnabled` 允许关闭消费日志，`model/log.go:DeleteOldLogBatch` 允许清理日志；
日志库还可能与主库分离。`quota_data` 受数据导出开关、缓存批量刷写和旧错误影响。
因此，每次打开首页执行全量 `SUM(logs)` 会同时引入缺失历史、全量扫描和日志库故障依赖。

`model/utils.go` 还维护进程内累计统计批量缓冲。仅停止 HTTP 流量或仅打开账单维护开关，不会
自动排空全部节点的缓冲，也不能停止后台结算。校正前必须控制全部写入者。

### 4. 累计字段容量是落地前置条件

`User.UsedQuota` 的 GORM 声明已改为 bigint，Go 字段仍为 `int`；AGENTS.md 已区分累计容量
与单次收费 int32 上限。SQLite 使用 64 位 INTEGER，隔离 MySQL/PostgreSQL 已验证 bigint 存取，
但不能据此认定生产存量列已完成迁移。本例候选值 2,829,317,796 已超过有符号 int32 上限。

现已补齐累计字段扩容的启动接线：在现有 `ensureUserQuotaColumns` 中先验证其他钱包字段，
仅 `used_quota` 为旧整数类型时调用独立迁移；SQLite 保持原列，MySQL/PostgreSQL 扩为 bigint
并复查结果。其他钱包字段不符合原要求时仍拒绝启动，不先做部分扩容。执行平台仍须支持 64 位
整数；扩容只改变存储容量，不代表历史金额已校正，也不能标记历史统计版本完成。金额汇总和差额使用带溢出检查的 int64 运算，
不得调用单次收费的 int32 饱和转换。`Channel.UsedQuota` 已为 int64/bigint；本轮不扩大钱包、
单次扣费上限或全部额度字段。生产实际容量核验仍未完成。

## 优化方案与当前实现

### 1. 记录退款政策与自动判断

新增 `model/user_usage_repair_startup.go`，政策版本为 `recorded-refunds-v1`。复用现有
`CollectUserUsageRepairEvidence`、精确退款分桶、证据指纹和校正事务，不生成假的人工核验资料。
设当前累计为 U、留存消费合计为 C、退款合计为 R、精确匹配已交付事件的退款为 D：

| 情形 | 自动行为 |
| --- | --- |
| 已存在有效的本版本成功审计且没有回退 | 跳过历史校正，直接保留当前累计；不要求仍等于历史 after |
| 无留存退款且没有异常证据 | 保持累计，不用缺失的消费历史将累计清零 |
| U = C − R 且净额非负 | 已为净额，金额不变并记录版本审计 |
| U = C − D、U 不等于 C − R、没有既有维护操作且净额非负 | 将累计修正为 C − R，包含 7 条人工退款 |
| 残差、负金额、重复 Request ID、待交付事件、退款分桶缺项或矛盾 | 不改金额，查询显示“用量待核对” |
| 本版本已经回退、审计无效 | 不再次自动回减，显示待核对 |

这是一项经用户确认的**统计基线政策**：记录中的退款被接受为退款。精确等式用于限定自动校正范围，
不代表证明每条历史退款都曾漏减，也不代表证明日志全生命周期完整。取消旧版逐笔人工证明前置，
不取消剩余矛盾的阻断，更不把所有无交付记录的退款直接减一次。金额全用带范围检查的整数。

### 2. 单实例启动接线与事务

1. 旧实例退出后启动新版本，禁止新旧实例重叠运行。复用 `InitResources` 原有初始化顺序。
2. 主库初始化验证容量；仅旧 `used_quota` 列扩容，SQLite 保持 64 位整数列。日志库与审计表初始化后，
   在 HTTP、系统任务 runner 和批量更新器启动前调用 `InitUserUsageRepair`。
3. 用户按 ID 每批 100 个扫描。按执行时刻采集证据，动态生成 before/delta/after；不硬编码用户 91、
   日期或上述历史金额。证据读取失败、数据库写入或审计失败返回启动错误，不带着部分未知结果开放业务。
4. 复用 `applyUserUsageRepair`：清单自校验 → 用户行锁 → 操作 ID 查重 → before 校验 → 事务内重新采集
   并比较证据 → 重新推导目标 → 带 before 条件的更新 → 同事务审计。审计失败回滚该用户累计。
5. 操作 ID 固定为 `usage-recorded-refunds-v1:<user_id>`；成功审计保存政策、用户、before/delta/after、
   证据与回退摘要。操作者为 `system` / `startup_migration`，不虚构 Root 或人工审核。
6. 逐用户提交；崩溃后重新启动跳过已完成用户，继续其余用户。成功后的正常新增消费、退款或日志清理，
   不会触发再次扣减。无金额变化的用户也留下版本确认审计。

主库与日志分库、ClickHouse 日志拓扑不执行校正，返回不可用累计投影。不能把这种部署标为金额修复完成。
本实现复用现有同库事务边界；没有新增分布式锁、后台修复 worker、修复数据库或统计版本字段。

自动修复只写累计统计与审计，不重放钱包、Token、Task、退款日志，不修改请求数、渠道用量或 QuotaData。
审计留存是防止重复修复的必要条件，不能作为普通历史消费日志一起清理。

现有进程内批量缓冲不因本修复获得新的关机排空能力；单实例升级仍使用正常停止/启动流程。
若异常关机造成日志与累计残差，系统会阻断对应累计展示，不能宣称可恢复已丢失的内存事实。

### 3. 统一查询与页面刷新

`controller/user_usage_projection.go` 提供窄 DTO 投影，用户列表、搜索、详情和 `/api/user/self` 共用
`UserUsedQuotaForDisplay`；登录/刷新会话沿既有 `buildSelfUserData` 获取同一投影。成功用户保持原来
数值型 `used_quota`，金额来自每次查询的主库用户行。四个查询接口复用 `setAuthNoStore`，避免 HTTP 缓存旧值。

内存仅保存启动时的不可用用户集合/拓扑结果，可重建且不保存金额。不能证明正确的用户返回
`used_quota: null`，首页、管理列表、用户资料、钱包和日志用户信息统一显示中英文“用量待核对”，
不显示 0、不继续把旧虚高金额作为已核实值。余额等正常功能保持可用；异常原因由启动日志记录。
异常被修复后需重新启动以重新评估；当前实现没有运行期间自动重试后台队列。

首页复用 `/api/user/self`、auth store 和既有刷新 hook；进入/聚焦时拉取，有节流和失败提示。
用户 ID 与会话 SID 守卫均在刷新 hook，拒绝旧会话迟到结果。`setUser` 不是自带竞态保护的 setter。
新消费后的再次查询读取新值，不使用迁移时冻结的 after 作为展示值。

日志用户信息弹窗原有嵌套组件及嵌套三元表达式未通过当前文件 lint；按必要验证边界将原子展示组件
移到文件级、将加载/内容/空态条件平铺，保持原页面结构与行为，并补 null/正常金额回归。

### 5. 备份与保守回退

旧备份缺失不再阻塞正常自动升级。自动入口不生成数据库全量备份；在更新累计的同一事务保存
before/delta/after 和源证据摘要，支持只逆转本次统计变更。审计不是数据库备份，也不能恢复历史删除的日志。
部署方已有整库备份流程继续有效，不属于按用户手工修复的前置操作。

异常情况下，现有离线 CLI 增加 `-rollback-recorded`，从当前库成功启动审计构造反向清单，
复用原来的 Root 校验、停写确认、SQLite 一致性备份/外部引擎备份确认、事务检查及反向审计。
无需查找启动时并不存在的人工清单文件。该命令用于回退，不是部署后修正金额的日常步骤。

```bash
go run ./cmd/repair-user-usage -dsn /path/to/source.db -user-id 91 \
  -operator-id 1 -confirm-stop-write -backup /path/to/new-backup.db -rollback-recorded
```

只允许逆转负差额。当前累计、用户日志、Task、attempt、交付、QuotaData、渠道统计以及原审计基线
必须仍满足原约束；新增消费或无关维护审计都会拒绝旧回退。仅同一政策对其他用户追加的有效自动迁移
