# randy 账单质量告警只读核验

## 问题与目标

核对截图中的输入 Token 总量未知 4,350 条、计费方式未知 5 条、原价及优惠不能估算 5 条，
判断计数是否正确，并区分历史证据缺失、读取实现限制和金额异常。本轮只分析，不修复资金或改写日志。

## 当前实际情况

### 核验范围与结果

以 `mode=ro` 打开工作区 `one-api.db`，使用当前 `GetBillingCustomerStatement` 和共享退款解析器
读取客户 randy（ID 91），范围为上海时间 2026 年 9 月，包含 27,139 条消费/退款日志。
三项计数精确复现为 **4350 / 5 / 5**，净额为 **2,172,634,879 quota**。
后两项命中同 5 条退款，不是 10 条异常。此结果证明本地同范围数据与截图一致，不证明目标服务构建版本。

### 输入 Token 总量不可确认：4,350 条

| 客户模型 | 条数 |
| --- | ---: |
| deepseek-v4-flash-0731 | 2,766 |
| deepseek-v4-pro-0813 | 1,584 |

时间范围为 2026-09-07 17:28:51 至 2026-09-15 23:44:01（上海时间）。这些行均没有
`input_tokens_total` 和 `usage_semantic`，计费路径标记为 `upstream`，但保存了缓存用量。
由于历史输入字段可能包含缓存，也可能只保存非缓存部分，不能直接相加或统一当作总输入。
`upstream` 只证明未走带语义的规范化路径，并不证明缓存是否已包含。

当前读取器因此排除这些行的未知输入合计，保留已记录金额和其它可确认用量。此告警作为保守
的统计口径提示成立，不表示调用失败或金额错误，也不表示所有 Token 都丢失。当前证据不足以
直接清零；仍需历史部署和用量处理分支证据。不能仅凭当前模型名称或渠道配置恢复。

本地 9 月 16 日起的 426 条带缓存消费记录均已有 `usage_semantic=openai`。这说明本地样本中新
写入已携带口径，不能据此声称所有部署、所有入口已完成验证；新字段不会自动回填旧记录。

解析入口：[输入总量解释](../../model/billing_statement_breakdown.go:299)、
[未知标记](../../model/billing_reconciliation.go:599)。

### 计费方式未知与估算失败：同 5 条人工退款

五条均发生于 9 月 15 日，属于 API Key ID 40：`seedance-2-0-s` 四条、
`seedance-2-0-fast-s` 一条。退款行自身缺少计费方式与分组倍率，但具有明确的原预扣日志引用。

只读核验确认：

- 五个原预扣均存在，用户、API Key、渠道、模型和全额退款金额匹配；各引用在该用户/Key 的
  全部历史退款中均只出现一次。
- 原预扣均保留计费表达式和分组倍率 **0.87**；独立调用现有事实校验/应用函数，五条均可恢复
  为 `token`，估算阻断原因均为空。此步骤只验证证据可用，不修改正式读取器或日志。
- 当前读取器为了核验原预扣引用唯一性，先取该用户/Key 的全部历史退款，最多读取 1,001 行。
  一旦超过 1,000 行，就不解析引用并删除整个范围的候选。
- Key 40 有 **2,034 条历史退款**，触发上述限制。作为对照，另外两条人工退款属于 Key 50，
  其历史退款只有 348 条，可以正常恢复，因此剩下的是 5 条而非 7 条。

根因是[退款关联核验上限](../../model/billing_statement_refund_facts.go:295)，不是原预扣数据丢失。
未继承分组倍率后，解析器返回 `missing_group`，并增加不能估算计数。这也不是“没有合同”导致：
当前合同未记录时按分组倍率计算的用户口径已经生效。

因此两项“5 条”准确描述当前程序结果，但若向客户解释成历史事实不可恢复就不正确。更具体的
原因是“退款关联信息未完成核验”。已入账退款仍计入净额；此检查不证明资金全链路正确或错误。

## 优化方案

1. 优先修复人工退款的引用核验方式：围绕明确原预扣引用验证全历史唯一性和身份，采用可索引、
   有界的查询方案，不让同一个 Key 无关的其它退款数量阻断已有证据。不要简单取消预算、扩大
   常量、按金额猜关联或默认补写倍率。
2. 保持用户、Key、渠道、模型、全额退款、唯一引用与冲突证据检查；月汇总、明细、导出共用
   同一读取逻辑，修复不得改变消费、退款、净额或原始日志。
3. 输入 Token 4,350 条继续保留未知，直到历史写入分支得到证明；将提示具体化为“历史输入
   Token 是否包含缓存尚未确认”，与退款核验未完成区分，避免统称计费信息不能展示。
4. 旧方案中的 27,063 条原价未知是严格合同三态时的历史结果，已被后续用户口径修正取代。
   本轮同库实测为 5 条；不能继续沿用旧数字或“匹配原预扣后仍一定无法估算”的旧结论。
