# 客户账单折前金额留证与历史回补方案

## 1. 问题与目标

客户账单需要同时解释原价、优惠和净结算金额。旧消费日志能证明实际扣款，但部分记录没有独立保存折前金额。当前日报接受已记录的折前金额，或在分组与合同倍率均可核验为中性时采用入账金额。存在非中性倍率的旧记录即使保留了充分的计算证据，也缺少进入日报的复算路径。任一资金事件缺原价，相关汇总的原价和优惠就会留空。

本方案把问题收敛为一条完整的账单证据链。新请求在资金事件入账时保存折前金额及必要依据。旧请求按当时的规则逐笔复算，校验通过后进入新报表版本。线上回补覆盖生产仍可核查的所有受影响账期、客户和计费入口。对已知有账单但来源不足的账期，登记缺口及可用的现有版本。

验收以客户能从总览追溯到明细、导出和资金事件为准。钱包、订阅、API Key 额度、消费和退款的入账语义沿用现有规则。账单金额回补只增加可核验的展示证据。正式月账单继续采用既有冻结和更正规则。

## 3. 优化方案

### 3.1 统一折前金额的来源和使用边界

资金事件提供实际扣减或退回，冻结计价证据提供该事件对应的原价，账单版本提供可复核的展示。
在客户账单层统一原价判定，日报汇总、逐笔明细、账单导出和正式账单草稿消费同一判定结果。
原价、优惠和净额按同一批逐笔资金事实汇总。消费和退款分别核对，再计算净额。优惠按已核验原价减净额计算。
已确认的零保留为零，证据缺失保留为空并给出原因。

优先读取原始资金事件已保存的折前金额。现有中性倍率规则可以复用。其余事件只有在冻结证据足够且
正向复算通过时，才可使用复算金额。解析版本由发布制品声明，报表代际记录解析版本，逐笔投影标识原价来源。
盘点与重建使用同一版本。复算算法、历史兼容解释或金额口径发生变化时，按版本重新核对受影响的范围。
通过原资金事件标识复核来源，沿用现有下钻权限。页面和导出只呈现授权的金额与原因摘要。
上游参考金额沿用其独立口径，已有估算只在上游证据范围内解释。

### 3.2 补齐新资金事件的留证

- 对照同步文本、图片、音频、Realtime、异步图片与视频、Batch、Midjourney 原生普通任务和换脸消费及退款、
  独立违规费和其他退款入口，确认已用的计价器、
  实际入账事件、折前金额是否已得出以及证据是否随事件保存。共用能表达相同业务语义的留证逻辑，
  将新增逻辑放在可独立验证的位置，现有计费入口保留最小接线。
- 成功入账时优先保存本次实际结算已经算出的折前金额。需要追溯时保留最小的历史计价依据，
  例如公式版本、实际采用的计量、档位、有效倍率、所需汇率或计价时刻。附加费用按现有原价合同处理，
  先明确组成及入账口径，再决定该事件能否提供原价。
- 预扣、结算调整、全额或部分退款按各自资金事件留证。结算差额失败、公式回退到预扣、发生饱和或
  关联不足时，沿用真实入账额并记录原价不可用原因。异步事件继续以原 Task 和交付身份为依据。
- 单独核查 ADR-0021 的未转移视频创建 attempt 到期自动释放及同源人工释放。以 attempt 的原占款、
  实际退款和释放状态为依据，核对现有视频资金流水与客户账单的覆盖边界。已转移到正式 Task 的退款
  继续走 Task 交付。核对未转移 attempt 时禁止套用 Task 的 `BeforeQuota` / `AfterQuota` 写入条件，
  也不凭空补一笔客户消费或退款。若产品需要将现有独立资金流水纳入客户账单，先明确归集合同和去重边界。

### 3.3 实现可核验的历史复算

| 环节 | 判定 |
| --- | --- |
| 锁定范围与身份 | 使用现有日志扫描、来源边界和事件身份。退款按已验证的原扣款或 Task 关联，区分任务差额与客户退款。遇到冲突或多个候选时进入待核对 |
| 验证历史输入 | 使用当时持久化的表达式、固定价或倍率规则以及实际计量。依据表达式实际依赖核对缓存、图像和音频分项、请求条件、定价时间、汇率及换算因子。字段缺省是否等于零取决于该版本的日志语义和独立计量证据。当前配置和反除实扣都不能作为历史精确原价依据 |
| 正向执行与对账 | 复用现有定价、用量归一化及该历史路径的转换顺序。分组、合同倍率和附加费用按原顺序应用，再核对入账金额、计价单位、可得的档位和资金事件符号。预扣与差额分别核验。相同实扣无法消除输入歧义 |
| 写入报表版本 | 在候选日报中保存原价、来源、解析版本及失败分类。缺证与对账不符分别计数。通过原有来源与覆盖校验后发布，候选版本需要包含新的解析结果，旧工作进程或旧候选结果不得覆盖它 |

复算走日汇总后台任务，页面查询仍按已发布版本读取。批量盘点使用同一判定逻辑，可先只读输出汇总。
对可修复日期用现有重建队列分批排程，复用任务租约、资源门控、日期重试、导出引用及原子发布。
若需提供批量运维入口，入口只负责盘点或提交日期，日报任务继续负责构建、校验和发布。

逐笔转换统一走 [`common/quota_math.go`](../../common/quota_math.go)。`QuotaRound*` 与
`QuotaFromDecimal*` 按半值远离零取整。原结算路径明确使用 `QuotaFromFloat*` 时保留其向零截断语义。
使用对应的 Strict 变体，或显式检查 Checked 变体返回的 clamp，拒绝把饱和值确认为精确原价。
现存部分计算轨迹把调用 `QuotaFromDecimalChecked` 的步骤标成 `truncate`，复算以对应版本的实际函数行为为准。
禁止另建本地转换函数、直接整数转换或提前取整。逐笔额度边界和账期 int64 汇总边界分别处理。

### 3.4 线上盘点、灰度和全量回补

1. **部署前建立基线。** 确认目标数据库、日志保留范围、已发布日报和确认月账单的覆盖情况。用本次发布制品
   的只读盘点模式，按北京时间日期、入口和原因统计已知原价、可复算、缺证和对账失败。对已清理的日期，
   优先核查仍保留的可信冻结证据和既有报表。记录受影响日期清单、来源读取边界、旧版本和分批顺序。
2. **部署并验证新写入。** 在目标拓扑验证已接入的结算入口。切换前确认旧 worker 已退出发布路径，
   并在候选复用和提交发布时校验解析版本。按原有控制面观察批次用时、查询延迟、主库负载、失败和重试。
3. **灰度首批。** 优先选择 2026-11-11。若线上原始证据仍完整，核对 314 笔全部通过，抽样日志
   `673715` 的原价为 119,774 quota、实扣为 89,831 quota。对照同一来源边界下的旧日报，验证总览、
   明细、逐笔和导出的原价覆盖提升。记录单日复算耗时、处理笔数、查询延迟和数据库负载，
   结合既有资源门控确定后续批量和提交节奏。若源范围已变化，先解释变化，再按实际来源边界重设基线。
4. **推进余下日期。** 按日期和业务负载分批入队，记录可恢复、未恢复、已发布、待重试及原因。
   除现有来源覆盖校验外，对比同一来源边界下旧版本已核验的逐笔原价与新版本，避免源记录数相同却丢失
   已有原价。若金额确需更正，保留差异及依据。对覆盖降低、证据变化、校验失败或资源门控未通过的日期
   保留当前发布结果。首批发布前演练使用上一代际或等价可恢复制品的回退，核验其保留期和导出引用。
   发布异常时停止提交下一批，按已验证的恢复入口处理。
5. **核查正式版本。** 已确认月账单及其下载产物按版本冻结。需补正的客户和月份列出影响，
   通过现有更正、审核和确认流程发布新版本。待确认草稿按现有解析版本校验，必要时重新生成。
   日报切换与正式账单更正分别验收。

### 3.5 验收标准和剩余事项

- **计费正确。** 覆盖非中性倍率的取整边界、合同显式未适用与未记录、缓存分项缺省、条件公式和汇率、
  固定价、零原价、违规费、Midjourney 消费及退款、Task 差额及退款、创建 attempt 到期释放及去重边界。
  覆盖证据冲突、实际入账不符及重复重算。
- **报表一致。** 同一版本的逐笔原价加总与汇总、详情和导出一致。按相同来源边界比对逐笔入账金额及符号、
  请求数、扣款、退款和净额。验证来源变化、任务重启、发布失败、导出版本引用和正式账单冻结。
- **全量可核对。** 生产清单中的日期都有处理结果。所有证据充分且对账通过的资金事件均恢复原价与优惠。
  剩余事件按缺项与失败原因计数，能追溯到账期和计费入口。上线后持续观察新日志的原价覆盖，
  确认剩余缺项来自已登记的证据边界。
- **目标环境可运行。** 计费和报表回归覆盖 SQLite、MySQL、PostgreSQL 的相关路径。生产灰度另外核对
  实际拓扑、历史负载、迟到事实覆盖和关键 API 延迟，沿用[路线图](../50-planning/路线图.md)第 39 项的报表验收条件。
- **架构合同与交付同步。** 实施时更新[客户与上游对账架构 §7.1](../20-architecture/账单计费-客户与上游对账架构.md#71-客户账单)
  和[报表日汇总架构 §7](../20-architecture/账单计费-报表日汇总架构.md#7-账单发布版本)，写明核验复算这一原价来源、
  适用条件、算法版本、失败与发布规则、正式账单边界。随实现提交并执行 `task docs:check` 和 `task ai:check`。
  页面、导出及运维可见的新增原因使用稳定原因码并提供简体中文和英文文案。

当前完成问题分析和方案设计。业务代码、线上盘点、批量重建和正式账单更正均待实施与验收。
