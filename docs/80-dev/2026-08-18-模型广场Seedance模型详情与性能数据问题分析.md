# 模型广场 Seedance 模型详情与性能数据问题分析

## 问题与目标

本记录针对模型广场中 Seedance 模型详情页的截图和反馈，分析以下问题：

1. 概览中的 TPS、延迟、成功率没有数据；
2. 性能页没有数据；
3. Seedance 模型的 API 示例和参数说明不正确；
4. API 页右上角缺少 API 文档链接；
5. 模型卡片左下角直接显示内部端点名 `modelark-video`，普通用户难以理解，也没有文档链接。

截图只作为页面现象证据，不作为新的业务或架构指令。当前目标是明确真实数据来源、公开 API 合同来源和最小修复边界，暂不把推测数据写入页面。

## 当前实际情况

### 1. 性能数据链路

模型详情概览通过 `/api/perf-metrics?model=...` 查询最近 24 小时数据，并从分组结果计算平均 TPS、平均延迟和成功率。没有分组结果时，格式化函数会显示 `—` 或未知状态。

- 概览查询和汇总逻辑位于 `web/src/features/pricing/components/model-details.tsx`；
- 性能页在 `web/src/features/pricing/components/model-details-performance.tsx` 中，当 `groups` 为空时显示“Performance data is not yet available for this model.”；
- 卡片页通过 `/api/perf-metrics/summary` 获取性能徽章数据；
- 后端性能采集由 `pkg/perf_metrics` 负责，数据写入 `perf_metrics` 表并结合进程内热桶读取。

当前 `RecordRelaySample` 的调用点主要位于同步 Relay 成功/失败和文本结算路径，依赖 `RelayInfo`、流式首响应时间、完成 Token 数和生成耗时。Seedance 使用 ModelArk V3 异步 Task 创建与轮询流程，当前未发现其 Task 完成/结算路径调用同一采集入口。

因此需要区分两种情况：

- 如果所有模型都没有数据，应先检查运行环境的 `perf_metrics_setting.enabled`、`perf_metrics` 表和热桶是否为空；该设置代码默认值为启用，但部署配置可能覆盖默认值。
- 如果同步文本模型有数据而 Seedance 没有数据，则主要原因是异步视频链路尚未接入性能采集。

Seedance 的 TPS 还不能直接套用文本模型语义。视频任务的 Provider 等待时间、任务完成时间和 Token usage 不是同步文本的 TTFT/TPS 等价物。不能为了填充 UI 而生成随机 TPS，或把视频任务耗时直接伪装成文本 TPS。

### 2. Seedance 的公开 API 合同已经存在于后端

后端在 Seedance 公共模型目录中已经生成了客户可见的 API 元数据：

- 协议：`modelark_v3`；
- 文档路径：`/docs/api-reference/videos/modelark`；
- 创建路径：`/api/v3/contents/generations/tasks`；
- 创建必填字段：`model`、`content`；
- 任务查询、列表、删除和视频内容下载操作均有明确描述。

对应事实来源：

- `model/channel_seedance_public_catalog.go` 的 `seedancePublicModelAPI`；
- `web/public/docs-content/zh/api-reference/videos/modelark.md`；
- `docs/10-product/验收标准.md` 中关于 `api.video`、`supported_endpoint_types` 和 ModelArk V3 的目录合同。

### 2.1 ModelArk V3 是共同北向协议，不是统一的逐模型参数合同

这里需要特别纠正一个容易导致错误实现的假设：Seedance 客户模型虽然都使用 ModelArk V3 作为北向协议，
但不代表所有模型都支持同一组字段、枚举和数量范围。实际能力由
`video_upstream_protocol + 精确 Provider 模型` 的代码化校验事实决定；客户模型名可以自定义，不能由前端
根据 `seedance`、`2-0`、价格、分辨率或 Provider 名称猜测参数。

架构文档中的差异证据包括：

本节依据 [Seedance 模型接入设计索引](../20-architecture/Seedance模型接入设计/README.md)、[公开模型调用与素材能力元数据设计](../20-architecture/Seedance模型接入设计/公开模型调用与素材能力元数据设计.md) 以及墨行、FunCloud、飞彩、火山官方和 BytePlus 官方各自的“模型与素材能力元数据”文档；这些文档是能力边界的设计证据，不能被截图中的端点名替代。

| 模型/线路事实（内部证据） | 可观察差异 | 对模型广场的影响 |
| --- | --- | --- |
| 墨行 2.0、Fast/Mini、2.5 | 时长分别为 4–15 秒、4–15 秒、4–30 秒或智能时长 `-1`；2.5 支持 `seed`，Fast/Mini 不支持；图片/视频/音频上限也不同 | 不能为所有模型统一展示 `seed`、时长范围或素材数量 |
| FunCloud Standard/Fast/Mini、2.5 | 2.0 可到 1080p，Fast/Mini 只有 480/720p；2.5 为 4–30 秒或 `-1` 且不支持素材 CRUD | 分辨率、素材入口和时长字段必须按客户模型投影 |
| 飞彩 SD2、Pro PI、720p/1080p/4K 系列 | SD2 只允许 `16:9`/`9:16` 且必须有图片；Pro PI 固定 15 秒并允许参考视频；其它模型的分辨率和比例集合不同 | 不能只显示一套通用比例、必填字段或固定时长 |
| 火山官方/BytePlus 官方 Standard、Fast/Mini、2.5 | Standard 可到 1080p/4K，Fast/Mini 通常只有 480/720p；2.5 的时长、媒体和字段限制不同 | 公开参数不能从端点名或客户模型名推导 |

因此，当前 `api.video.creation` 只说明共同的创建入口和 `model`、`content` 等基础字段，尚不足以支撑准确的
“支持参数”表。前端直接复用 `mock-stats.ts` 或按模型名正则生成参数，会把某个模型的能力误显示给其它模型，
并可能让用户提交随后会被 adapter 正确拒绝的合同外字段。

最小正确的长期方向是扩展现有 `api.video` 的公开、脱敏、只读投影（示意）：

```text
api.video.parameters
  model: 客户模型名
  content: text/image_url/video_url/audio_url 的支持状态与数量上限
  duration: min/max/是否允许智能时长
  resolution: 可用枚举
  ratio: 可用枚举
  generate_audio / watermark / seed / camera_fixed: supported 与默认值（若已验证）
  output_format: 可用枚举（若已验证）
```

该投影只公开客户可以提交的 ModelArk 字段和已验证限制，不返回 Provider 模型名、Provider、Channel、协议私有
路径或凭据。它是目录/文档的只读投影，不是新的运行时 capability、路由选择或第二套 Link 状态；真实请求仍由
现有 adapter 和精确模型 spec 校验，不支持字段必须明确拒绝或保持未发布。不能把
`provider_model_specs.go` 或飞彩内部 spec 结构直接序列化给前端，因为各协议结构不统一且会泄露内部身份，
应在新增 DTO/投影适配文件中转换为稳定的公共形状。

### 3. 前端 API 示例使用了错误的推断链路

前端 `PricingModel` 类型没有声明后端返回的 `api` 字段，API 详情组件也没有读取 `model.api.video`，而是仅根据 `supported_endpoint_types` 和一个全局 `endpointMap` 生成示例。

`model-details-api.tsx` 的 `buildSample` 只为 Anthropic、Gemini、Embedding、图片生成提供专门分支；`modelark-video` 没有专门分支，会落入通用 Chat 示例。因此 Seedance 会出现 `messages`、`temperature`、`max_tokens` 等文本请求字段，而不是 ModelArk V3 的 `content`、`duration`、`ratio` 等合同字段。

参数表同样不是后端合同投影，而是 `web/src/features/pricing/lib/mock-stats.ts` 中的模拟/启发式列表。`apiCategoryOf` 通过模型名称正则判断类别，`seedance-2-0` 不匹配视频名称规则，最终被识别为 `chat`，所以截图出现通用聊天参数表。

这不仅影响示例代码，也意味着当前 API Tab 中的部分参数和限流数据不能视为真实 Provider 或平台合同。对于 Seedance，
示例必须使用共同的 ModelArk V3 外壳，但字段取值和可选字段要以当前客户模型的公开参数投影为准：例如不能因为
某个 2.5 模型支持 `seed`，就把 `seed` 放进所有 Seedance 示例。第一阶段在没有参数投影时，只展示最小已确认的
`model`、`content` 示例，并明确提示“可用参数、枚举和限制以该模型文档为准”；不能生成一张看似完整的通用参数表。

### 4. API Tab 当前没有文档操作区

`ModelDetailsApi` 当前只按顺序渲染代码示例、鉴权、支持参数和限流区块，没有统一的标题栏或右上角操作入口。

Seedance 的文档链接已有后端事实来源，应使用 `model.api.video.documentation_path`，目标为 `/docs/api-reference/videos/modelark`，而不是根据模型名称、Provider 或端点字符串拼接 URL。

### 5. 模型卡片直接暴露内部端点枚举

`ModelCard` 将 `supported_endpoint_types` 原始值直接输出到左下角元数据区域，所以用户看到的是 `modelark-video`。这是内部类型化端点标识，不是面向普通用户的产品名称。

Seedance 应展示可理解的名称，例如“ModelArk V3 Seedance 视频”，并将其链接到 `model.api.video.documentation_path`。该链接只表达北向公开合同，不应暴露 Provider 模型、Channel ID、南向协议或凭据等内部事实。

## 优化方案

### A. 先完成性能数据事实核查

1. 在运行环境确认 `perf_metrics_setting.enabled` 是否开启；
2. 检查 `/api/perf-metrics/summary` 和具体模型查询是否返回空数组；
3. 检查 `perf_metrics` 表和进程热桶是否有近期记录；
4. 对同步文本模型和 Seedance 异步模型分别验证采集范围。

如果同步模型也没有数据，应先修复或恢复通用性能采集配置；不能只修改模型广场前端空状态。

### B. 为异步视频定义独立且可解释的性能合同

如果产品确实需要在 Seedance 性能页展示数据，应新增明确的视频 Task 指标，例如：

- 请求受理到任务完成的总耗时；
- 任务成功率；
- 可选的排队耗时和 Provider 处理耗时；
- Provider 明确提供且已验证的 usage 证据。

不要把视频任务耗时转换成文本 TPS。若暂时没有稳定的视频指标合同，Seedance 的 TPS/TTFT 应显示“不适用”，性能页显示“暂无已采集的视频任务指标”，而不是显示伪造数值。

### C. 以后端公开 API 元数据为唯一前端来源

前端应补充 `PricingModel.api` 的类型，并优先读取：

- `api.video.documentation_path`；
- `api.video.creation`；
- `api.video.operations`；
- `api.assets` 的支持状态和操作矩阵。

Seedance API 示例应使用 ModelArk V3 请求结构。对于后端尚未提供完整字段矩阵的部分，应链接到公开文档，而不是由前端按模型名猜测。

### D. 统一文档链接和端点展示

建议抽取一个前端只读映射/展示逻辑：

- 端点标签使用产品名称；
- 链接使用公开 API 元数据中的文档路径；
- API Tab 右上角显示“查看 API 文档”；
- 模型卡片左下角端点显示为带链接的“ModelArk V3 Seedance 视频”；
- 所有新增文案补齐前端 i18n。

### E. 验证范围

实现后至少验证：

1. Seedance 模型 API Tab 的 cURL/SDK 示例不再使用 Chat Completions 字段；
2. API 文档链接打开 `/docs/api-reference/videos/modelark`；
3. 模型卡片不再裸露 `modelark-video`，且端点链接可访问；
4. 无性能数据时显示明确的“暂无数据/不适用”，不显示 0 或随机值；
5. 有真实性能记录的同步模型仍保持原有展示；
6. 前端类型检查、相关组件测试和文档检查通过。

本分析未修改业务代码，也未把“代码存在”或“测试通过”表述为真实 Provider 或生产灰度验收完成。

## 最小入侵实施路径分析

### 总原则

最小入侵的关键是把“已有后端事实投影到前端”与“性能指标合同是否需要扩展”分开处理：

- API 示例、文档链接和端点名称问题，后端已经有公开 `api` 元数据，优先只改前端；
- 性能数据问题不能靠前端补数，先核查配置和数据，再决定是否新增异步 Task 指标；
- 不修改 NEWAPI 原生路由、DTO、Relay 或 Provider adapter，不建立第二套 Seedance API 合同。

### 第一阶段：只改前端即可完成的目标

这一阶段不需要修改 Go 代码，也不需要改数据库：

1. 在 `web/src/features/pricing/types.ts` 为 `PricingModel` 增加 `api` 的前端类型，类型只覆盖当前后端已经返回的 `video`、`assets`、`creation` 和 `operations` 字段；
2. 新增一个局部的前端只读合同辅助文件，例如 `web/src/features/pricing/lib/model-api.ts`，集中处理：
   - `documentation_path` 的读取；
   - `modelark-video` 的用户可读标签；
   - API 合同是否存在的判断；
3. 在 `model-details-api.tsx` 保留现有通用模型分支，只增加 `modelark-video` 的窄分支，并从独立文件引入 ModelArk V3 示例生成逻辑；
4. 对 Seedance 不再调用基于模型名的 `apiCategoryOf` 来生成聊天参数。最小安全行为是展示 `model`、`content` 等基础请求示例，并明确提示参数以该模型文档为准；不要在前端复制一整套未经结构化后端支持的参数合同；
5. 在 API Tab 顶部增加一个窄的标题/操作行，使用 `model.api.video.documentation_path` 渲染“查看 API 文档”；
6. 在 `model-card.tsx` 只替换端点元数据的渲染方式：`modelark-video` 显示为可读标签并链接到相同的文档路径。其它端点保持现有展示，避免借机重构整个模型卡片。

预计最小接线点只有 `PricingModel` 类型、API Tab、模型卡片三个现有前端文件，以及一个新增合同辅助文件。后端 `model/channel_seedance_public_catalog.go`、`model/pricing.go` 和原生路由无需修改，因为它们已经提供正确数据。

### 第二阶段：补齐模型级公开参数投影（需要后端窄接线）

如果产品要求模型广场显示准确的参数表，必须增加后端公共投影，而不是继续扩大前端启发式：

1. 在 `relaykit/dto/public_model_api.go` 增加稳定的公共 `VideoParameters` DTO，字段只表达 ModelArk 北向可见
   的支持状态、枚举、默认值和数量/范围限制；不要复用某个 Provider 的内部 spec 类型。
2. 在新增的 Seedance 目录投影文件中，按现有 `video_upstream_protocol + model_mapping` 解析精确模型，调用
   已有各协议 model spec/validator 的事实，转换为脱敏 `api.video.parameters`。客户模型名仍来自目录，Provider
   模型身份只在后端内部使用。
3. 对 Moxing/FunCloud/飞彩以及火山/BytePlus 已有代码化规则分别补 projection adapter；不能用一张“Seedance
   通用参数表”覆盖所有线路。未完成真实 Provider 验证的能力不得写进公开投影。
4. 前端 `PricingModel.api.video.parameters` 只作为展示和示例生成输入，不能替代后端校验；未返回的字段不显示，
   不根据名字补齐。

这一阶段仍可保持最小入侵：新增 DTO/投影和单行目录接线，复用现有 adapter/model spec；不修改 NEWAPI 原生视频
入口、通用 Relay 或路由，不建立 capability/routing registry。

### 第三阶段：性能问题先做零侵入核查

在新增代码前，先用运行环境确认：

1. `perf_metrics_setting.enabled` 是否为 `true`；
2. `/api/perf-metrics/summary` 是否对同步模型也返回空数组；
3. `perf_metrics` 表是否有最近 24 小时记录；
4. Seedance 任务是否已有可公开使用的创建时间、完成时间和成功终态事实。

如果同步模型也为空，最小修复可能只是恢复性能监控配置或排查采集进程，不应修改模型广场组件。

### 第四阶段：只有产品确认后才扩展异步性能采集

如果确认 Seedance 必须显示性能数据，建议先确定产品字段，而不是直接复用文本 TPS：

- 若只需要视频任务成功率和端到端耗时，可在新增的 `pkg/perf_metrics` 扩展文件中定义 Task 样本，并在 Seedance Task 完成的现有生命周期接线点增加单行记录调用；
- 若必须展示 TPS、TTFT 等文本指标，则需要单独的视频指标合同、存储字段/API 响应和前端展示语义，这已经不是小范围 UI 修复，不应伪装成复用现有 `PerfMetric`；
- 对没有真实指标的字段，前端显示“不适用”或“暂无数据”，不写入模拟值。

这样可以把新增后端改动限制在新增的性能采集文件和一个异步 Task 完成接线点，避免修改通用 Relay 热路径、原生视频入口或 Provider adapter。

### 不建议的方案

- 不在前端根据 `seedance`、`video`、价格或 Provider 名称继续推断 API 类型；
- 不把 `modelark-video` 直接改名成普通字符串而不带公开文档来源；
- 不为 Seedance 复制一套独立 API DTO、路由或模型目录；
- 不使用 `mock-stats.ts` 生成 TPS、延迟、限流或视频参数来填补空白；
- 不为了让所有卡片“看起来有数据”而修改同步性能采集逻辑或污染 `perf_metrics` 的文本语义。

### 推荐实施顺序

1. 先完成运行环境性能数据核查；
2. 先做前端 `api` 元数据接入、正确 ModelArk 基础示例、API 文档链接和端点链接；
3. 若需要准确参数表，再增加模型级 `api.video.parameters` 公共投影，并为每类协议补投影测试；
4. 用前端测试验证 Seedance 示例不会出现 Chat 字段，且两个文档链接可访问；
5. 根据真实核查结果决定是否新增异步 Task 指标；
6. 若新增指标，再单独补充后端采集测试和性能页的“不适用/暂无数据”状态测试。

该顺序能以最小改动先解决截图中确定的 API 和可理解性问题，同时避免在性能指标定义尚未确认前扩大后端和数据库变更范围。
