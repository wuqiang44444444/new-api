后续启动观察确认总闸门中的用量补查查询仍有索引选择问题，详见
[启动异常与证据密钥持久化问题分析及修复方案](2026-09-17-启动异常与证据密钥持久化问题分析及修复方案.md)。

## 问题与目标

`HasUnfinishedSyncTasks()` 是原生 Suno/视频共用轮询调度的存在性闸门，只回答是否至少存在
一条符合现有轮询条件的任务。调度调用链为：

`asyncTaskPollHandler.Enabled()` → `HasTaskPollingWork()` → `HasUnfinishedSyncTasks()`。

调度周期为 15 秒。总闸门还检查用量补查、create attempt、失败欠退款、终态待结算与日志交付；
不能把“没有未完成任务”解释为“没有补偿工作”。

后端日志出现以下慢查询：

```sql
SELECT id FROM tasks
WHERE progress != '100%'
  AND status NOT IN ('SUCCESS', 'FAILURE', 'PROVIDER_CONTRACT_FAILURE', 'CANCELLED', 'EXPIRED')
  AND (client_protocol IS NULL OR client_protocol <> 'image_openai_v1')
  AND platform <> 'azure_batch'
LIMIT 1;
```

本地 SQLite 的执行计划为 `SCAN tasks`。一次只需回答存在性的问题，在无匹配行时仍扫描历史
任务。日志中的 257ms 不足以独立证明冷缓存、写锁或磁盘竞争各自的贡献，不能把这些推断写成根因事实。

- 保留原生任务、空状态、`UNKNOWN`、`RECONCILIATION_REQUIRED` 和未来新增状态的现有资格。
- 保留图片协议与 Azure Batch 的排除条件，包括各列现有 NULL 行为。
- 保留单条 SQL、`LIMIT 1`、错误处理与返回方式；不拆为两次独立读取。
- 不改变 15 秒调度、真实轮询、超时、取消、创建恢复、计费、退款及日志交付逻辑。
- 主库仍是唯一事实源；不增加缓存、工作标记、回填、迁移或新索引。

## 优化方案：等价范围查询

唯一生产代码改动位于 [model/task.go](../../model/task.go) 的 `HasUnfinishedSyncTasks()`：

```go
// 原查询
Where("progress != ?", "100%").
// 等价改写
Where("(progress < ? OR progress > ?)", "100%", "100%").
```

其余条件全部保留，括号保证 OR 只作用于进度条件。这里仍然按数据库对原字符串列的比较规则
比较，不解析百分比、不转数字、不裁剪或标准化字段。

对于同一列、同一参数和排序规则，不等于等价于小于或大于；NULL 在两种写法中都不满足 WHERE。
例如 `100.0%` 是否等于 `100%` 仍由原数据库比较规则决定，不人为改成“已完成”。

现有 `idx_tasks_progress` 可以用于两个范围；SQLite 本地执行计划为：

```text
MULTI-INDEX OR
  SEARCH tasks USING INDEX idx_tasks_progress (progress<?)
  SEARCH tasks USING INDEX idx_tasks_progress (progress>?)
```

这样可跳过大量 `progress = '100%'` 的历史记录，对其余候选继续应用原条件。具体执行计划由
数据库版本、排序规则、统计信息与数据分布决定，不强制索引，不保证所有数据库均选择相同计划。
SQLite 的 OR 分支索引机制参见[官方查询优化说明](https://www.sqlite.org/optoverview.html#or_optimizations)。

## NEWAPI 原生业务影响与最小入侵

- 原生 Suno/视频使用这个闸门，必须验证新旧查询结果一致，不能将其描述成只影响 Link。
- 原生文件修改是为优化该查询本身，必要接线点仅一行谓词；新增回归测试放独立文件。
- 不增加本地状态清单，未来上游新增状态不会因遗漏本地正向枚举而失去唤醒资格。
- 上游修改同一函数时仍可能发生一行合并冲突，应重验查询等价性；不重排、格式化或重构其他代码。
- Midjourney 使用独立闸门；本次不修改其调度。图片与 Batch 继续由原专属 worker 推进。
- 不修改 `GetAllUnFinishSyncTasks()`、`GetTimedOutUnfinishedTasks()` 或总闸门中的其他工作探测。

## 当前实际情况：已验证的方案证据及限制

评审阶段对本地 `one-api.db` 只读查询，并将查询所需的非私有字段复制到内存实验库：

- 共 3538 条任务，其中 3519 条进度为 `100%`、19 条为其他进度。
- 新旧查询在该数据下均返回无匹配任务；范围查询在原数据库使用现有进度索引。
- SQLite 3500 组确定性边界组合的命中集合一致，覆盖 NULL、空字符串、非标准进度、未来状态、
  图片与 Batch。该实验是语义核对，不替代 Go/GORM 行为回归。
- 固定 19 条应排除的活跃图片任务，内存库的历史已完成任务从 1000 增至 100000 时，原查询
  SQLite 指令量从约 3373 增至 300369，范围查询为约 156—168；这不是生产延迟承诺。

收益来自跳过已完成进度的历史记录；如果非 `100%` 候选本身很多，仍需扫描和过滤这些候选，
不能宣称恒定成本或与所有数据增长完全脱钩。MySQL/PostgreSQL 的隔离验证见文末；目标部署环境
的实际结果与性能仍须单独验证。

## 不采用的方案

- `status IN` 正向枚举：收紧原有字符串状态域；空状态、未来状态可能被漏掉。硬编码全集测试
  也不能自动发现新增常量，因此不满足保持业务语义的要求。
- 缓存空闲结论、降低扫描频率或按创建时间截断：可能延迟新任务或遗漏历史未完成任务。
- 删除闸门：改变空闲时的调度和写入行为。
- 新增复合索引：可以在某些查询中减少回表，不能笼统说“不等式无法使用索引”；但本次现有
  进度索引已有可验证收益，无需增加写入负担与迁移范围。
- 部分索引：不作为 SQLite/MySQL/PostgreSQL 的统一实现。
