# 客户与上游对账实施方案

## 1. 目标与依据

本文是[客户与上游对账单产品说明](../10-product/客户与上游对账单产品说明.md)的阶段性实施与验收记录。
客户/上游数据库汇总、管理员双 Tab、上游月度折扣持久化与审计，以及历史计费快照已落地；
余额不可变流水、上游折扣前端编辑和真实三数据库及 ClickHouse 用量验证仍是后续门禁。
平台没有供应商账单接口，因此上游 Tab 只展示我方数据库已记录的用量；供应商数值录入、差异比较和处理状态不在范围内。
因此本文不是生产发布声明。

本次实施必须同时满足：

1. 所有正式展示数据均来自数据库；
2. 平台管理员页面拆为“客户账单”和“上游对账”两个一级 Tab；
3. 复用 NEWAPI 现有请求、日志、鉴权、渠道和计费事实，尽量不修改原生源码；
4. 客户汇总与上游汇总在后端完成，前端只展示后端返回的完整聚合结果；
5. 按 Token 和按次计费分别聚合，不混合用量单位。

## 2. 已核对的当前实现

### 2.1 本次已落地范围

| 能力 | 状态 | 实现位置或边界 |
| --- | --- | --- |
| 用户 API Key → 客户模型月度汇总 | 已实现 | `GET /api/billing/statement/self` |
| 管理员客户账单，渠道/API Key 两维切换 | 已实现 | `GET /api/billing/admin/customer-summary` |
| 管理员全客户月度账单列表与客户下钻 | 已实现 | `GET /api/billing/admin/customer-statements`；服务端搜索、质量过滤、排序和分页 |
| 普通用户“我的账单”独立入口 | 已实现 | `/billing`；固定调用当前用户接口，不包含客户搜索或客户数量 |
| 管理员客户/上游两个一级 Tab | 已实现 | `/admin/billing?section=customer\|upstream`；路由和接口均要求管理员权限 |
| 渠道 → Provider 模型的 Token/按次平台用量汇总 | 已实现 | `GET /api/billing/admin/upstream-summary`；只读取我方日志数据库 |
| 月度折扣、上月复制和缺省 `1` | 部分实现 | 后端已持久化当前月版本并支持 expected-version 写入；前端编辑待补 |
| 请求发生时的计费方式、Provider 模型和计价因子快照 | 部分实现 | 已冻结现有计价因子；标准化人民币单价和 PriceBook 版本尚未建立 |
| 主页不展示请求行，仅提供明细链接 | 已实现 | API Key 使用稳定 `token_id`；合并多个客户模型的上游行只下钻到渠道账期，不伪造单模型条件 |
| 余额不可变流水与期初/期末勾稽 | 未实现 | 保留为独立阶段 E，当前只直读主数据库当前余额 |
| 上游平台用量 CSV 导出 | 已实现 | 仅导出后端返回的完整汇总；不导入供应商账单 |

### 2.2 实施前核对事实

| 当前事实 | 代码入口 | 对本方案的影响 |
| --- | --- | --- |
| 已有用户账单页 `/billing` | `web/src/routes/_authenticated/billing/index.tsx` | 保留用户入口，不另建请求明细页；页面只承载当前用户账单 |

| 自助账单当前按 API Key × 模型聚合 | `model.GetUserBillingStatement` | 可复用数据口径，但管理员需要新增渠道维度和指定用户权限 |
| 原前端曾在浏览器内筛选并重新汇总 | 旧 `web/src/features/billing/` | 已由服务端筛选与汇总替代，旧模块确认无路由引用后整体移除 |
| Request ID 已写入日志数据库 | `model.Log.RequestId`、`model.ensureLogRequestId` | 不新增 Request ID；明细跳转复用现有用量日志 |
| 日志已有用户、API Key、客户模型、渠道、输入/输出 Token 和结算 quota | `model/log.go` | 作为客户用量及平台侧上游用量的数据库来源 |
| 缓存 Token、价格、倍率和动态计费信息主要位于日志 `other` | `service/log_info_generate.go`、`model/billing_statement_breakdown.go` | 服务端解析历史快照；不能从当前价格设置回算 |

| 管理员客户/上游账单使用独立入口 | `web/src/routes/_authenticated/admin/billing/index.tsx` | 与普通用户页面分离，并在路由前置校验管理员角色 |

当前日志关闭、日志清理、历史 `other` 信息不足或同步重试未留下独立 Provider 尝试事实时，无法仅靠
页面补齐。此类数据必须标记为未知或不可用，不得使用当前配置、Redis、前端缓存或客户金额推断。

## 3. 数据权威设计

### 3.1 唯一权威来源

| 数据 | 权威数据库事实 | 禁止替代来源 |
| --- | --- | --- |
| 用户、API Key、渠道及当前余额 | 主数据库 | Redis、页面状态 |
| 客户请求用量、结算金额、退款、Request ID | 日志数据库中的消费与退款日志 | 当前价格设置、前端重算 |
| 平台统计的上游用量 | 日志数据库中按渠道、Provider 模型聚合的已持久化用量 | 进程计数器、监控指标 |
| 上游月度折扣 | 主数据库中的折扣版本 | 前端默认值、配置缓存 |
| 上游折扣操作审计 | 主数据库中的追加式审计记录 | 浏览器 localStorage、日志文本 |
| 余额流水 | 主数据库中的不可变流水 | `User.quota` 的后台直接覆盖记录 |

主数据库与日志数据库可以独立部署。查询服务可以分别读取两者后在服务端组合响应，但不得把组合结果
只保存在内存或前端并宣称为账单事实。任何需要跨请求保留的折扣和审计事实都必须先写入
主数据库。

### 3.2 缓存规则

- Redis、进程缓存和 React Query 只允许缩短读取时间；缓存项必须能从数据库完全重建。
- 正式账单默认直接查询数据库。后续如增加服务端缓存，缓存键必须包含用户、账期、维度、筛选条件
  和数据库事实版本，且响应继续返回 `generated_at` 与 `data_version`。
- 数据写入成功后可以失效缓存，但不能先更新缓存再异步补写数据库。
- 数据库与缓存不一致时，以数据库结果为准；禁止使用缓存回填数据库。

### 3.3 前端边界

- 前端不接收请求级数据后再生成正式月度汇总。
- 每次切换 Tab、用户、账期、渠道、API Key、模型或计费方式，都调用对应聚合接口。
- 前端只负责格式化、展开模型行和导航；金额、Token、计费次数和数据质量均由后端返回。
- 导出由后端按相同查询条件生成；若第一阶段继续导出后端返回的汇总数据，必须确认响应已包含当前
  筛选条件下的完整结果，而不是当前页或虚拟列表片段。

## 4. 页面与路由方案

### 4.1 用户入口

保留 `/billing` 作为普通用户自助账单入口，只展示自己的：

```text
API Key → 客户模型汇总
```

现有用量日志继续作为明细入口。账单页不显示请求表，模型行只生成带账期、API Key、模型和计费方式
筛选条件的“查看明细”链接。

### 4.2 平台管理员入口

管理员使用独立的 `/admin/billing` 页面入口，并通过 URL 查询参数深链到两个 Tab：

```text
/admin/billing?section=customer
/admin/billing?section=upstream
```

页面顶部固定两个一级 Tab：

| Tab | 默认结构 | 权限 |
| --- | --- | --- |
| 客户账单 | 全客户账期总览和分页列表；点击客户后切换渠道/API Key 维度，再展开到客户模型 | `AdminAuth` |
| 上游对账 | 上游渠道 → Provider 模型汇总 | `AdminAuth` |

两个 Tab 共用数据库状态提示，但请求不同接口、使用不同响应类型；禁止在前端把客户金额与上游金额
合并成同一个汇总对象。管理员侧栏单独展示“账单对账”，个人侧栏继续展示“我的账单”。管理员访问
`/billing` 时看到的仍然只是自己的账单，不自动跳转到全客户列表。

新增前端功能已隔离在独立目录：

```text
web/src/features/billing-reconciliation/
  api.ts
  types.ts
  index.tsx
  my-billing.tsx
  admin-billing-reconciliation.tsx
  lib.ts
  components/customer-statement.tsx
  components/customer-statements-list.tsx
  components/upstream-statement.tsx
```

旧的 `web/src/features/billing/index.tsx` 页面实现已在自助账单迁移后删除，避免同一路由存在第二套页面
口径。新模块原先反向引用的 CSV 转义工具已迁入 `billing-reconciliation`，旧目录确认无其他生产引用后整体移除。

## 5. 后端接口方案

### 5.1 路由隔离

在新增 `router/billing-reconciliation.go` 中注册全部新接口，现有 `router/api-router.go` 只增加一行：

```text
registerBillingReconciliationRoutes(apiRouter)
```

建议接口：

| 方法与路径 | 权限 | 数据库行为 |
| --- | --- | --- |
| `GET /api/billing/statement/self` | `UserAuth` | 从数据库返回当前用户的 API Key → 模型汇总 |
| `GET /api/billing/admin/customer-summary` | `AdminAuth` | 按指定用户、账期和维度聚合日志数据库 |
| `GET /api/billing/admin/customer-statements` | `AdminAuth` | 按账期从数据库生成全客户汇总，并做客户搜索、质量过滤、排序和分页 |
| `GET /api/billing/admin/upstream-summary` | `AdminAuth` | 聚合日志数据库的平台用量，并读取主数据库中的月度折扣 |
| `PUT /api/billing/admin/upstream-discounts` | `AdminAuth` | 使用版本校验保存折扣及审计 |

保留现有 `GET /api/billing/self` 和 breakdown 接口作为兼容入口，直到新用户账单完成迁移和验证；不在
本需求中改变其响应合同。

当前没有、也不计划增加供应商账单导入、供应商数值维护或双方差异确认接口。

### 5.2 请求约束

- 账期必须大于零且不超过产品允许范围；自然月边界由后端按 `Asia/Shanghai` 生成。
- 管理员客户查询必须显式提供合法 `user_id`，普通用户接口始终从认证上下文读取用户 ID。
- `dimension` 只接受 `channel` 或 `api_key`；普通用户固定为 `api_key`。
- `billing_mode` 只接受 `token` 或 `per_call`。
- 全客户列表只在客户维度分页；顶部总计必须是当前全部筛选结果的服务端全量聚合，不能由当前页相加。
- 所有写接口经过 `AdminAuth`、CSRF 保护、参数校验和操作审计。

### 5.3 响应约束

每个聚合接口使用统一信封，实际合同为：

```text
data.period
data.filters
data.result
data.generated_at
data.data_version
data.data_source
```

单客户接口的 `data.result` 包含 `summary`、`groups` 和 `data_quality`；全客户列表接口的 `data.result` 包含筛选后全量 `summary`、当页 `items`、`page`、`page_size` 和 `total`；上游接口的 `data.result` 包含
`channels` 和 `data_quality`。聚合行不包含 Request ID 列表，每个模型子行返回 `detail_filter`，前端
据此构造现有用量日志链接。`data_quality.status=partial` 时页面必须提示部分事实不可用；不能把部分
原价合计展示成完整金额。

## 6. 数据模型方案

### 6.1 客户账单不复制请求事实

客户账单继续以日志数据库的 `logs` 为请求级权威，不新增第二张“客户请求账单表”。新增查询按以下
维度在后端聚合：

```text
用户汇总：user_id + token_id + customer_model + billing_mode
管理员 API Key 维度：user_id + token_id + customer_model + billing_mode
管理员渠道维度：user_id + channel_id + customer_model + billing_mode
```

全客户首页列表不新增账单表，而是在给定自然月内从日志数据库扫描消费和退款事实，按 `user_id` 聚合后与主数据库的用户身份合并。已删除客户的历史账务事实仍然可查，但显式标记删除状态。搜索、质量过滤、排序、全量总计和分页全部在后端完成。

基础请求数、输入/输出 Token、quota、退款和渠道直接使用结构化日志列。缓存 Token、历史价格、用户
折扣和计费方式从已持久化的 `other` 快照解析。解析发生在服务端，沿用 `common.Unmarshal*`，不在
三种数据库上引入不同的 JSON SQL。

历史日志缺少足够快照时：

- 不从当前 `ratio_setting`、当前用户分组或当前模型价格回算；
- 能确认的 Token 和结算 quota 继续展示；
- 原价、折扣或计费方式标记为未知；
- 不把未知行计入需要该字段的折扣汇总。

若实现阶段确认现有 `other` 无法稳定区分按次和按 Token，新请求可在现有日志 `other` 内追加
`admin_info.statement_snapshot.billing_mode` 和必要计费分项。构建逻辑放入新增文件，原有日志生成函数只增加
单行调用；不得为此重写 Relay、价格计算或 Provider adapter。历史行仍按上述未知规则处理。

当前 `other.admin_info.statement_snapshot` 已冻结版本、计费方式、Provider 模型以及结算时存在的
`model_price`、`model_ratio`、`completion_ratio`、`cache_ratio`、`group_ratio`、`user_group_ratio` 和
表达式标识。它足以避免读取当前配置，但还不是统一的“人民币/百万 Token”PriceBook 快照；在统一
单价模型落地前，历史原价只能在所有相关结算行都存在冻结折扣因子时展示，任一行缺失则整层返回未知。

### 6.2 上游折扣与审计

在主数据库已新增以下独立模型：

```text
ProviderBillingDiscount
ProviderBillingAudit
```

`ProviderBillingDiscount` 的唯一键为：

```text
period_start + channel_id + provider_model + billing_mode
```

同时保存折扣、来源月份、版本、修改人、原因和时间。新月份只复制上一个自然月；无记录时创建值为
`1` 的当前月记录。复制或缺省发生在该账期首次生成时并立即写入数据库、追加审计，不是每次读取时
动态引用上月。普通保存使用 expected version，避免并发覆盖。

`ProviderBillingAudit` 以追加方式保存折扣每次写入的 before/after、原因和操作人。
不创建供应商账单行、双方差异或 review 模型；这些数据在供应商未提供可信事实时没有业务依据。
`BillingBalanceLedgerEntry` 尚未创建，属于阶段 E。

### 6.3 余额流水的独立门禁

`BillingBalanceLedgerEntry` 保存充值、消费、退款和人工调整，使用不可变业务单号及 Request ID 关联。
但当前 NEWAPI 有多条用户额度增减路径，且部分路径先更新 `User.quota` 再同步缓存。不能仅在账单页面
新增一张流水表就宣称“余额由流水累计”。

余额流水必须作为独立阶段实施：

1. 先枚举充值、同步消费、异步预扣/结算/退款、订阅、签到、邀请和管理员调整等全部额度写路径；
2. 为数据库事务增加统一的 `WithTx` 记账入口，使余额变化和流水追加同一事务提交；
3. 每种业务使用唯一幂等键，重复回调或补偿只命中已有流水；
4. 完成历史余额基线迁移后，才允许页面展示期初/期末勾稽结果；
5. 在此之前保留当前数据库余额为权威，余额流水功能标记为未完成，不用日志估算代替。

该阶段涉及计费热路径，必须单独评审，不能为了赶 UI 与前两阶段混合修改。

## 7. 聚合逻辑

### 7.1 客户账单

后端按请求参数选择 `token_id` 或 `channel_id` 作为父级键，再按客户模型和计费方式聚合。响应同时
返回数据库全量总计和父级行，前端不二次计算正式金额。

管理员首屏先按 `user_id` 聚合账期内的消费和退款日志，在一次数据库查询结果上完成客户账单汇总；再批量查询主数据库的用户名称、显示名称和删除状态。首屏不加载请求行，也不为生成列表对每个用户重复调用单客户接口。

按 Token 行：

```text
input_tokens
cache_read_tokens
cache_write_tokens
output_tokens
gross_quota
refund_quota
net_quota
```

按次行：

```text
requests
billable_calls
refunded_calls
gross_quota
refund_quota
net_quota
```

异步任务调整行影响 Token 和费用但不重复增加逻辑请求数，沿用现有账单口径。净费用保持非负；跨期
退款按退款日志发生时间进入查询账期。

### 7.2 上游平台用量

平台侧用量从日志数据库按以下维度聚合：

```text
period + channel_id + provider_model + billing_mode
```

Provider 模型优先读取请求发生时已持久化的上游模型快照；缺失时标记无法映射，不从当前
`model_mapping` 反推历史 Provider 模型。

服务端只组合同一业务键下的平台用量、`ProviderBillingDiscount` 和数据质量。
按 Token 行返回平台记录的输入、缓存读写和输出 Token；按次行返回平台记录的请求数和计费次数。
客户退款日志只代表平台对客户的资金调整，不冲减平台记录的 Provider 用量，也不生成上游退款次数。

响应不包含供应商 Token、次数、金额、退款、差异率或处理状态。平台没有这些权威事实，不通过手工录入、客户金额或当前价格推断。

如果现有日志只保留最终成功渠道而没有每次同步重试的 Provider 用量，就只能对账已持久化的最终用量。
不得假设失败重试成本为零。是否新增“Provider 尝试用量事实”必须在真实 Provider 账单验证后单独
评审；若需要，优先在统一上游尝试边界增加一行独立记录调用，不分散修改各 Provider adapter。

## 8. 最小入侵实施边界

### 8.1 实际新增文件


### 8.2 实际修改的原生文件

| 原生文件 | 最小接线 | 必要性 | 上游冲突影响 |
| --- | --- | --- | --- |
| `router/api-router.go` | 一行注册新增 billing route | Gin 当前无外部自动注册入口 | 极低，单行相邻路由冲突 |
| `model/main.go` | 普通与 fast migration 各调用新增迁移函数 | 新表必须在三数据库创建 | 低，不扩写现有 AutoMigrate 列表主体 |
| `web/src/routes/_authenticated/billing/index.tsx` | 替换为新自助账单组件并扩展查询参数 schema | `/billing` 需连接新聚合合同并保留旧深链参数兼容 | 中，是前端最大原生接线点，未重构其他路由 |
| `web/src/routeTree.gen.ts` | 由 TanStack Router 生成器机械更新 | 新文件路由要求 | 可再生成，不手工维护 |
| `service/log_info_generate.go` | 两处日志路径各增加一行 snapshot builder 调用 | 区分计费方式并冻结历史信息 | 中，属于计费热路径，但未改动原有结算逻辑 |
| `controller/log.go`、`model/log.go` | 四个 handler 透传 `token_id`；三个导出查询函数增加 `tokenId int` 位置参数及筛选 | API Key 名称可重复或修改，名称筛选不能复现账单聚合 | 中，签名变更是未来合并冲突点，但调用面仅限四个现有 handler |
| 用量日志前端路由与查询参数 | 透传可选 `tokenId` | 让账单下钻使用稳定 API Key 身份 | 低，旧链接保持兼容 |

除上述接线外，不修改 NEWAPI 原生 Router 行为、请求 DTO、Relay、Provider adapter、选渠、计费公式、
预扣、结算和退款语义。若实现时发现必须扩大修改面，应暂停该阶段，记录无法由新增模块完成的证据并
重新评审，不得顺手重构。

### 8.3 不采用的方案

- 不复制或包装 NEWAPI 原生计费主链路；
- 不新增第二套 Request ID；
- 不把当前价格表作为历史账单来源；
- 不使用 Redis、前端缓存或内存定时聚合作为唯一权威；
- 不为了统一类型而移动现有 `BillingStatement*` 类型；
- 不直接把管理员逻辑塞入现有用户账单 controller、model 和大型 React 组件；
- 不在第一阶段重构所有余额增减路径。

## 9. 实施阶段

### 阶段 A：数据库模型与合同

- 新增上游月度折扣和追加式审计模型；
- 完成 SQLite、MySQL、PostgreSQL 的迁移与唯一键测试；
- 定义两个管理员 Tab 的聚合响应合同和数据质量语义；
- 验证历史日志能否可靠区分按 Token/按次及取得 Provider 模型快照。

退出条件：三数据库迁移通过，未知字段不会被转换为零，API 合同测试通过。不引入供应商账单数据模型。

### 阶段 B：数据库聚合接口

- 新增用户服务端汇总接口；
- 新增管理员客户汇总接口；
- 新增上游平台用量汇总和折扣读取/保存接口；
- 所有过滤和汇总在后端完成；
- 明细只返回跳转过滤器，不返回请求列表。

退出条件：清空 Redis 后结果不变；分页、筛选和导出总计一致；权限越界失败。

### 阶段 C：管理员双 Tab 前端

- 新增独立 `billing-admin` 模块和路由；
- 实现“客户账单”“上游对账”一级 Tab；
- 客户 Tab 先展示全客户月度汇总列表，支持服务端搜索、质量过滤、排序和分页；
- 点击客户后实现渠道/API Key 维度切换和模型展开；
- 上游 Tab 只展示平台记录的 Token/次数，并提供月度折扣编辑；
- 移除账单主页逐请求视图，只保留明细链接；
- 按 i18n 规范补齐全部语言。

退出条件：两个 Tab 可独立刷新和深链；页面不含请求表；浏览器不计算正式汇总。

### 阶段 D：历史快照补强

- 仅在阶段 A 证明现有日志字段不足时实施；
- 在 `other.admin_info.statement_snapshot` 增加版本、计费方式、Provider 模型和已结算计价因子；
- 通过新增 builder 隔离逻辑，原生日志生成路径只做必要单行接线；
- 历史数据不伪回填，继续显示未知。

退出条件：同步、异步、按次、按 Token、退款和重试样例均能稳定分类，原计费结果完全不变。

### 阶段 E：余额流水

- 完成全部额度写路径清单和事务边界设计；
- 新增不可变流水及历史基线迁移；
- 将余额变化与流水追加原子提交；
- 完成幂等、冲正、并发和三数据库测试后再启用期初/期末勾稽。

退出条件：数据库余额可由基线加流水复算，所有已知额度写路径均不能绕过流水。

上述全量测试阻断来自执行环境的本地监听权限，不是本功能断言失败；仍不得因此略过真实数据库、
完整 CI 和月末验证门禁。

### 11.2 未解除风险

- `LogConsumeEnabled` 关闭或日志被清理时，数据库事实不完整；必须在页面标记并禁止月度确认。
- 历史日志可能无法可靠区分按次/按 Token 或还原原价与折扣；不得使用当前配置回填。
- 日志数据库与主数据库不能做跨库原子事务；上游汇总读取平台日志，月度折扣独立写入主数据库并使用版本校验。
- ClickHouse 日志表字段和 SQL 能力与三种主数据库不同，不能用主数据库测试替代。
- 同步请求的每次 Provider 重试未必都有独立用量事实；上游 Tab 只能声称展示数据库已记录的用量，不能声称包含未持久化的失败尝试。
- 余额流水改造涉及多条原生资金路径，必须单独上线，不能以“页面已显示流水”代替原子记账验收。
- 未完成真实数据库用量汇总、三数据库、权限、月末边界和脱敏验证前，不得
  把管理员对账标记为生产可用。

## 12. 完成定义

本方案只有在以下条件全部满足后才能从 `80-dev` 收敛为当前架构事实：

1. 管理员两个 Tab 均从数据库接口读取完整聚合结果；
2. 客户与上游数据模型、权限和口径保持独立；
3. 按 Token 和按次均通过真实数据验证；
4. 上游折扣持久化并可审计，上游页面只展示我方数据库用量；
5. NEWAPI 原生文件修改保持在已列出的最小接线范围；
6. 三数据库、ClickHouse 合同、前端构建和文档校验通过；
7. 未完成项仍明确标记为未发布，没有写成生产事实。
