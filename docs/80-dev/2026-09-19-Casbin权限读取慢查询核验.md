# Casbin权限读取慢查询核验

## 问题与目标

用户报告 `service/authz/adapter.go:23` 读取 7 条权限规则耗时 281.595 ms，要求优化不能破坏
现有业务逻辑。本次核验查询计划、实际驱动读取及权限加载调用链，不将一次慢日志直接解释为缺索引。
用户进一步确认是偶尔出现，尚未确认仅发生在启动阶段。

## 当前实际情况

- 查询为 `SELECT * FROM casbin_rule ORDER BY id asc`。本地表共 7 行，`id` 是 SQLite 整数主键。
  只读执行计划为 `SCAN casbin_rule`，没有 `USE TEMP B-TREE FOR ORDER BY`；全量加载需要读取
  全部策略，扫描此小表本身不构成索引缺陷。
- 使用项目 `model.CasbinRule`、SQLite 驱动、GORM Find 和预处理语句，业务库以
  `mode=ro` 与 `query_only` 打开。五次读取均返回 7 行，首轮约 0.337 ms，随后约
  0.015—0.027 ms；本次独立连接池等待次数和等待时间均为零。没有输出权限行内容或写入业务库。
- 用户原始 281.595 ms 未重现；本机当前 stdout 日志还存在一次 231.877 ms、7 行的同形查询。
  独立复测不能代表原进程的连接池、调度或磁盘负载，无法据此分解当时耗时。
- `Init` 构造 Casbin enforcer 时加载完整策略；`ReloadPolicy` 用于提交后的本机刷新及
  `StartPolicySync` 的多节点周期同步，默认周期配置为 60 秒。授权判定使用 enforcer 的内存策略，
  不能因表行数少而移除加载，也不能依据行数未变跳过读取：同数量的 allow/deny 改动仍必须生效。
- GORM 慢查询计时涵盖模型处理、连接/执行与结果扫描，不包含随后逐条调用
  `persist.LoadPolicyLine` 的时间。现有日志不足以证明是排序、连接等待、锁、磁盘或调度中的哪一项。

## 优化方案与边界

本次没有发现可证明有效的 SQL 或索引修改，保留生产查询及权限加载逻辑。与 Task 退款取证的
联合索引缺口分别处理，不能给这条无筛选的全量策略读取照搬联合索引。

必须保持完整规则、ID 顺序、用户拒绝覆盖、默认角色、提交后刷新、多节点撤权同步与加载错误语义。
不新增权限缓存、减少同步频率、限制行数、取消拒绝规则、吞掉加载错误或提高慢查询阈值。

后续在原运行进程复现时，先核对启动/同步阶段，采集同一时间窗口的连接池等待、查询及扫描耗时、
锁等待和进程负载，再选择针对已证实瓶颈的修复；未定位前不能宣称已消除这条慢日志。

- `go test ./service/authz ./middleware ./router ./controller -count=1`：权限包与 middleware 通过。
  首轮 router/controller 被工作区其它正在修改的合同文件未使用导入阻断；该无关改动由其它工作
  修正后，单独重跑 `go test ./router ./controller -count=1`，两包均通过。本次没有改动该合同文件。
- 权限现有回归覆盖默认角色、从节点只读加载、用户 allow/deny 覆盖、事务提交后刷新、回滚与策略幂等。
- `task docs:check` 与 `task ai:check` 通过。
- 本轮未改权限代码、数据库或运行实例；此次只读复测不等同于生产性能验收。
