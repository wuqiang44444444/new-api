# Nano 渠道与详细日志真实验收记录

## 问题与目标

补测数据库中的其他 nano 生图渠道，并用真实请求核验消费与错误日志、请求关联、计费明细、
角色隔离及敏感信息。承接[首轮真实验收](2026-09-06-图片与对象存储真实功能验收记录.md)。

## 当前实际情况

### 环境与范围

- 当前代码独立构建，使用端口 3507、隔离 SQLite、随机测试凭据；原服务与原数据库只读。
- 发现 nano 渠道 88、93、99，以及官方 Google 渠道 89 的图片模型。每次请求 n=1，
  固定对应渠道，关闭失败重试，不修改 Provider 账号或在线渠道配置。
- 当前原库 nano 标准版与 Lite 已使用 `tiered_expr`，分别为
  `v1:tier("base", p * 0.5 + img_o * 60)`、`v1:tier("base", p * 0.25 + img_o * 30)`。
  本轮结论以当前配置为准，不能直接沿用首轮的旧定价描述。
- 初始隔离夹具遗漏迁移标记、表达式配置和正确的响应请求 ID 头，已纠正；这部分本地失败
  不计为渠道实现失败。完整配置之前额外完成一次 Lite 生图，扣款 1 quota，仅计入测试总账。
- 为核验错误日志，隔离实例显式开启 `ERROR_LOG_ENABLED=true`，`DEBUG=false`。
  代码默认关闭错误日志落库，不能据此声称未开启该开关的原部署也有相同错误详情。

### 详细日志实测通过项

通过实际 `/api/log/`、`/api/log/self` 查询及隔离数据库读取核验，而非仅运行单元测试：

- 请求 ID 使用响应头 `X-Oneapi-Request-Id`，可精确查询对应日志；成功请求只有一条消费日志，
  失败请求记录错误日志，包含请求路径、状态码、错误码和渠道归属。
- 99 渠道日志有上游请求 ID；记录输入 15、输出 1,427 Token，11 秒、生成数量 1、
  表达式、命中档位和扣款 33,604。FunCloud 未提供可用的上游请求 ID，未伪造填充。
- Root/Admin 管理日志可查看 `admin_info`；调用者自己的 `/self` 投影移除该字段；
  另一个用户查询同一请求 ID 返回空列表。错误日志也验证了相同角色边界。
- 数据库日志与测试进程日志经内存扫描，未发现本次使用的凭据、图片 Data URL 或签名 URL。
  结论限定于本轮请求和 DEBUG=false，不替代其它路径的敏感信息审计。
- 全部请求完成后，消费日志总额、用户余额差额、用户累计消费、Token 余额差额与累计消费
  均为 33,605 quota；其中 1 quota 来自配置补齐前的夹具 Lite 请求。不存在悬挂预扣。

### 未通过项与证据

1. **FunCloud 标准版与 Lite 成功生图但表达式扣款为 0。** 两条消费日志都是
   `prompt_tokens=1`、`completion_tokens=0`。`relay/channel/asyncimage/adaptor.go`
   的 `writeImageResponse` 返回空 Usage；图片入口补入的 1 不是 Provider 可信用量。
   因而当前按 `img_o` 收费的模型定价与该渠道实际可提供的计量不匹配。不能凭图片数量猜造
   输出 Token，也不能从 Gemini 渠道的用量推算 FunCloud 成本。
2. **图片表达式日志不足以独立复算。** 99 渠道表达式引用 `img_o`，实际日志只保留输入/输出
   总数，缺少图片输出 Token 分项；`other` 中没有 `img_o`、`image_output` 或对应独立用量。
   仅靠输出总数 1,427 与表达式无法还原本次图片分项费用。
3. **账单快照与实际计费模式不一致。** 三条当前配置成功日志顶层都为
   `billing_mode=tiered_expr`，有 `expr_b64`；但 `admin_info.statement_snapshot`
   为 `billing_mode=token` 且缺少表达式。`service/billing_statement_snapshot.go` 在表达式
   信息注入前形成快照，且模式只区分 token/per_call，需修正快照构建时机和模式来源。
4. **两个渠道配置尚不可用。** JD 被 Provider 拒绝；官方 Lite 图片名称虽在渠道模型清单中，
   但不在当前标准图片支持登记中。官方 Pro 另受额度限制。分别属于协议/映射、支持清单、
   账号额度问题，不应全部归为网络故障。

本轮未做浏览器页面视觉/交互验收；“详细日志通过”仅指上面明确列出的接口及数据库事实，
不包含图片分项复算和快照一致性。图片请求没有被错误扩展成音视频原始正文证据存储。

## 优化方案

- 当前任务以真实测试及记录为范围，没有擅改原库价格、禁用渠道或重写原生 Provider 语义。
- FunCloud 需按已核实的 Provider 计量配置可履约价格；若同名模型还要与 Gemini 共用图片
  Token 表达式，应先解决权威用量来源，不能用假 Token 或静默按次降级。
- 图片用量日志需保存实际结算所用的图片输出分项；账单快照应使用结算时冻结的模式与表达式，
  按新增文件/最小接线原则修复，并通过日志实际复算验证。
- JD 由配置负责人核对仍启用的渠道及映射；官方 Lite 在核实支持合同前不应作为可用图片入口。
- 文档完成后运行 `task docs:check` 与 `task ai:check`。测试结束停止独立实例，删除临时凭据、
  数据库与日志，仅保留生成图片和脱敏结果。生产发布与 Provider 财务对账仍未完成。
