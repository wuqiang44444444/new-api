# 渠道上游信息配置与对账按渠道聚合方案

## 1. 问题与目标

当前管理员在“账单对账 → 上游对账”中编辑上游名称和月度折扣，而渠道连接配置在渠道管理中维护。
名称按基础 URL 分组共享，折扣按月份和渠道保存，两者的编辑位置与数据归属不一致。

本方案将上游名称、上游折扣的编辑入口统一放到渠道管理，上游对账直接按渠道聚合，保留现有月度
折扣机制及历史更正能力。线上尚未使用对账是用户提供的信息；本次选择从现有日志重新聚合，
不将旧 URL 分组名称复制到渠道，不搬迁或改写历史业务日志。

本文是已确认方向的待实施方案，不代表代码已实现、线上数据库已核对或生产已发布。
本次仅形成方案文档，未执行数据库变更。

### 1.1 用户已确认的业务决策

| 项目 | 已确认规则 |
| --- | --- |
| 编辑位置 | 上游名称和上游折扣移到渠道页面；上游对账保留只读展示 |
| 对账主结构 | 月份 → 渠道 → 上游模型 × 计费方式，取消 URL 分组 |
| 名称归属 | 上游名称由各渠道独立保存；相同 URL 或相同名称均不合并渠道 |
| 折扣归属 | 保留“月份＋渠道”的综合折扣，不改为一个覆盖所有月份的静态字段 |
| 历史更正 | 渠道页面默认当月，允许选择历史月份更正该月折扣 |
| 更正影响 | 查询与新导出使用更正后的折扣；已生成文件保持当次内容；客户扣款和原始用量保持原值 |
| 存量处理 | 从历史日志按渠道重新聚合，不执行旧 URL 名称到渠道名称的数据迁移 |
| 已删除渠道 | 历史用量独立展示并纳入汇总及导出，不因渠道删除而漏计 |
| 已删除渠道编辑 | 渠道管理提供其对账配置入口，继续允许历史折扣更正；不恢复渠道调用能力 |

### 1.2 分析建议与待核对证据

以下为实现建议，不作为已完成事实：

- 上游名称采用独立的渠道对账配置保存，以减少 NEWAPI 原生 Channel 文件改动。
- 名称未填写时展示当前渠道名称；已删除渠道没有可用名称时展示“已删除渠道 #ID”。
- 名称作为跨月显示配置，修改后之后的查询与新导出显示新名称；已生成导出保留原名称。
- 上线前只读核对旧 URL 名称、月度折扣、旧模型级折扣及相关导出任务是否存在。用户说明线上未使用
  对账，不等于已验证所有配置表为空；若发现需要延续的业务记录，先核对实际来源与处理范围。

### 2.2 聚合与配置的区别

历史日志中的渠道 ID 是重新聚合的身份依据，历史用量及有冻结证据的金额可以沿用现有核算逻辑。
上游名称和商务折扣无法从日志推导，仍须由管理员配置并持久化。

本次“重新聚合”表示替换只读查询投影，不表示重放调用、重新结算客户、修改价格、补造缺失成本，
也不表示将渠道当前价格用于重算历史原价。原价缺失、估算、已知小计及数据质量标记继续遵循既有口径。
核算金额仍是本地原价乘渠道当月系数的参考金额，不是独立采集的供应商账单或实际应付金额。

当前事实入口为[客户与上游对账单产品说明](../10-product/客户与上游对账单产品说明.md)及
[客户与上游对账架构](../20-architecture/账单计费-客户与上游对账架构.md)。实现完成并验证后再更新
对应当前事实，本文不提前将目标行为写成现状。

## 3. 优化方案

### 3.1 渠道对账配置

渠道管理展示“上游名称”“上游折扣”，并为折扣明确展示账期、来源及版本信息。

- 上游名称按 `channel_id` 独立保存，不使用 Base URL、渠道名称或上游名称作为关联键。
  建议采用独立配置模型，保存名称、修改人和时间，并复用追加式对账审计。
- 名称复用现有普通文本规则：裁剪首尾空白，最多 255 个 Unicode 码点，清空后恢复默认展示；
  CSV 继续执行公式注入防护。该字段仅用于管理员对账展示、检索和导出。
- 上游折扣复用 `ProviderChannelBillingDiscount`，不在 Channel 中额外保存“当前折扣”作为另一权威。
  页面中的折扣值对应明确选中的月份；名称不随月份变化。
- 月份默认上海时区当前自然月，历史月份必须经显式选择；提交携带账期、渠道、系数及 expected-version。
  保存所选月份不能连带覆盖其他月份。
- 输入继续使用百分比，例如 80 表示系数 0.8；沿用 `0 < 系数 <= 1`、最多八位系数小数、版本冲突
  重新读取、服务端系统说明及修改前后审计规则。仅编辑普通渠道配置不应顺带产生月度折扣写入。
- 保留仅继承上一个自然月、无有效来源默认 1、当前待确认记录不自动默认、初始化幂等且不覆盖人工值
  的既有月度机制。对账汇总查询保持只读；需要物化月份配置时继续使用明确的初始化写入。
- 新建渠道获得正式渠道 ID 后保存对账配置；渠道一般保存、复制、删除路径与对账配置的接线范围在
  实施时核对，避免将月度历史复制到另一渠道 ID。

### 3.2 按渠道重新聚合

上游对账统一采用以下结构：

```text
账期月份
  → 渠道 ID / 上游名称 / 渠道名称 / 月度折扣 / 用量与核算金额
    → Provider 模型 × 计费方式
```

- 保留底层日志扫描、冻结计价证据解析、退款用量分类及金额完整性判断，移除外层 URL 归组。
- 渠道 ID 决定唯一归属；同 URL、同显示名称或同 Provider 模型的不同渠道分别汇总。
  同一渠道内继续区分 Provider 模型、fallback 身份与计费方式。
- 渠道选项、搜索、分页、质量说明、逐笔明细和导出范围统一按渠道表达；名称修改不改变归属。
- 移除 URLKey 必填条件、URL 分组选项及名称编辑入口，调整响应 DTO 与前端查询状态。
  旧 URL 名称链路直接退出本功能，不新增双读、URL 推断渠道或历史 URL 分组兼容层。
- 缓存元数据纳入渠道上游名称与账期折扣版本；更正后下一次查询必须读取新配置或使用新缓存键。
  Base URL 变化不再重分组历史账单。
- 渠道范围从所选账期日志确定，不能只查询当前 Channel 表；无调用量的渠道仍可在渠道管理中编辑
  自身对账配置。

### 3.3 已删除渠道的历史对账

- 日志中已删除渠道的 ID 保持独立身份，其用量、原价、折后核算金额及数据质量继续参与账期合计。
- 独立名称配置、月度折扣与审计在渠道删除后保留，避免依赖当前 Channel 记录或级联删除。
  已经缺失的历史名称不自动猜测或从旧 URL 名称回填。
- 渠道管理提供已删除渠道的历史对账配置入口，仅操作对账配置，不重新创建 Channel、不恢复凭据、
  模型路由或调用资格。
- 管理员可在该入口更正历史月份折扣，继续使用同样的范围校验、expected-version 和事务审计。
- 接口须通过可核对的历史日志或已有对账配置确认该渠道身份，不能仅凭任意正整数创建“已删除渠道”。
  当 Channel 记录不存在时，保存及初始化的并发控制须依靠持久化对账记录，不能假定仍能锁定原 Channel。
  具体锁定方式在实施时按 SQLite、MySQL、PostgreSQL 共同支持的路径验证。

### 3.4 明细与导出

- 单渠道明细及汇总导出按账期和渠道 ID 固定范围，不再通过当前 URL 找到渠道集合。
- 后台任务提交时冻结渠道 ID、渠道名称、上游名称及该月折扣值、版本和来源。
  执行及同任务重新生成沿用提交时事实，不在执行时读取改名或更正后的配置。
- 更正折扣或改名后新建的导出任务采用新配置；已生成文件保持原内容。
- CSV 保留可核对的渠道 ID、名称、模型、计费方式和折扣版本。叶行单次计入，不能与父级合计重复相加。
- 保留现有管理员权限、Root 私有字段限制、下载时再鉴权、后台队列和完整范围导出机制。
  普通客户账单及客户资金主链路不使用这两个管理配置字段。

### 3.5 数据库与上线策略

采用“结构接入＋日志重新聚合＋管理员配置”，不执行旧 URL 名称到渠道名称的数据迁移。

1. 上线前只读核对相关旧配置和导出任务，记录脱敏数量与分类，确认线上未使用对账的具体范围。
2. 按需增加独立渠道名称配置存储；新增结构兼容 SQLite、MySQL >= 5.7.8、PostgreSQL >= 9.6。
   建表或加字段属于结构变更，与批量搬迁历史业务数据分开验收。
3. 月度折扣直接沿用原业务键和保存记录；已有有效值不批量覆盖。名称由管理员填写，不从旧 URL 表复制。
4. 新查询从日志重建渠道汇总，不回写历史日志、Task、客户资金或既有导出产物。
5. 移除旧 URL 名称读写接线；停止业务使用旧配置不等于部署时清表或删表，本方案不包含生产破坏性清理。
6. 现有启动阶段还有旧模型级折扣到渠道级折扣的迁移入口。实施时核对其来源、调用及保留必要性；
   本方案不新增迁移或批量回填，也不将旧迁移当成重新聚合的前置条件。

### 3.6 改动边界与最小入侵

| 层次 | 拟调整范围 |
| --- | --- |
| Model | 新增渠道名称配置与审计接线，复用渠道月度折扣，改写上游查询投影和历史渠道保存边界 |
| Controller / Router | 调整渠道范围查询和名称读写入口，删除旧 URL 名称路由，保持管理员鉴权 |
| Service | 调整导出提交快照、执行范围与 CSV 字段，沿用现有核算及队列 |
| Frontend | 渠道管理增加名称、月份及折扣编辑，补充已删除渠道对账入口；上游对账按渠道只读展示 |
| Docs | 完成后更新产品说明和对账架构的当前事实，保留未完成真实数据库、账单和灰度验收事项 |

主体逻辑放到本地独立文件与现有本地对账模块，优先避免扩写 NEWAPI 原生 Channel 模型和保存热路径。
确需原生接线时逐处记录必要性、最小修改点与上游同步冲突影响。前端新增或修改文案仅维护 `zh` / `en`。

## 4. 实施顺序与验收

### 4.1 最小实施顺序

1. 核对线上配置与导出任务的只读证据，确定名称存储和已删除渠道管理范围。
2. 增加独立渠道名称配置读写，复用月度折扣读写及审计，打通已删除渠道的历史更正。
3. 将汇总、选项、缓存、明细及导出范围统一为渠道 ID，移除 URL 分组依赖。
4. 接入渠道页面编辑，调整上游对账为渠道只读展示，删除旧折扣和名称编辑动作。
5. 执行下面的合同验收，再更新产品及架构事实；真实部署和账单验收单独记录。

### 4.2 可观察验收清单

- [ ] 同 URL 的两个渠道分别汇总；同上游名称的渠道仍保持独立；名称修改不改变渠道归属。
- [ ] Base URL 修改前后，同一账期、同一渠道的历史用量及金额归属一致。
- [ ] 默认显示当月；更正历史月份只影响该月查询和新导出，不影响其他月或客户资金。
- [ ] 上月继承、无来源系数 1、待确认状态、幂等初始化及不覆盖人工值均保持既有行为。
- [ ] 两位管理员同时修改同月折扣时，过期版本保存失败，成功保存与审计原子提交。
- [ ] 已删除渠道仍参与汇总、明细及导出；可在渠道管理更正历史折扣，任意无证据渠道 ID 被拒绝。
- [ ] 删除后名称配置与月度折扣仍存在，历史入口不会恢复渠道调用能力。
- [ ] 缺失或估算原价、未知 Provider 模型及退款用量仍按现有规则表现，不制造供应商成本。
- [ ] 更正或改名后页面缓存刷新；已提交导出及其重新生成保持冻结值，新建导出使用新值。
- [ ] 渠道、模型展开、筛选、分页与全范围导出一致；父级合计与叶行不重复计数。
- [ ] 管理员名称持久化、清空、长度边界、CSV 公式防护和 `zh` / `en` 文案通过验证。
- [ ] SQLite、MySQL、PostgreSQL 的新结构、历史渠道保存和并发修改均有实际验证记录。

后端测试放在对应 Model、Controller、Service 边界，以确定性的输入和输出保护上述合同。
前端按实际改动执行 Bun 的类型、lint、格式、相关测试及构建检查。
文档改动执行 `task docs:check`、`task ai:check`；若实施涉及公开 API 文档，再执行
`cd web && bun run docs:validate`。本管理面方案本身不修改客户公开 API 文档。

## 5. 风险、依赖与当前状态

| 项目 | 影响与处置 |
| --- | --- |
| 线上数据是否为空 | 尚未实际核对；需要只读证据。发现业务记录时核对其范围，不自动清理或默默搬迁 |
