# 账单历史事实完整恢复方案

## 问题与目标

承接 randy 账单只读核验，完整修复 4,350 条历史输入口径未知与五条退款计费事实恢复被技术预算
阻挡的问题。让可证明的事实进入账单，不删除告警来掩盖缺失，不改历史扣款、退款和用户余额。

## 当前实际情况

本地固定截面为客户 91、上海时间 2026 年 9 月，27,139 条消费/退款，质量计数 4350/5/5，
净额 2,172,634,879 quota。五条退款已有唯一原预扣引用，却因 Key 的 2,034 条历史退款超过
1,000 条限制而被丢弃。原预扣保留 Token 计价事实和 0.87 分组倍率。

进一步检查历史提交 `2b231ae6e`、`4d46ebb79` 的文本结算与日志写入：OpenRouter-Claude
扣除缓存的分支走 `GenerateClaudeOtherInfo`，写入 `claude`、缓存创建字段与 anthropic 语义；
其它 Claude 转换分支由最终格式标记或缓存创建分项表达。之前仅检查 `upstream` 而未组合
这些证据，过于保守。4,350 条实际记录全部具有 `/v1/chat/completions`、单项
`["OpenAI Compatible"]` 转换链及 `upstream` 计费路径，且无 Claude/缓存创建标记。
因此可根据历史写入合同恢复总输入为已存 prompt_tokens，不额外累加缓存。

## 优化方案

1. 退款唯一引用核验按用户、Key 和类型索引，使用 ID 游标分批扫描完整历史，仅累计当前目标引用
   的出现次数。每批内存有界、尊重请求取消与导出超时；移除“超过 1,000 条就保持未知”的业务降级。
   扫描失败返回错误，不输出部分核验结果。跨月重复引用、身份冲突和非全额退款仍保持未知。
2. 增加用户/类型/Key/ID 联合索引，复用现有本地账单索引迁移入口，不增加原生日志字段、资金
   写入或第二套引用事实。使用 GORM 实现 SQLite/MySQL/PostgreSQL 共用读取与索引定义。
3. 输入恢复只接受上述完整冻结证据，排除 Claude、缓存创建标记、转换链不符、非法字段、缓存
   大于输入等情况；直接记录的总输入与语义继续优先。保留已有 Gemini 规则。不得按客户、模型名、
   当前渠道或当前价格推断；不重新执行计费表达式。
4. 月汇总、列表、明细、导出、新固化版本共用解析器，升级导出字段版本避免复用旧投影。实时账单直接查询数据库，无独立聚合缓存需要升级。已固化文件和原始日志不改写。当前修复均位于本地账单扩展，无原生计费热路径改动。

## 验证与风险

先增加大 Key 完整关联与历史输入恢复回归，复现旧逻辑失败，再实现修复。覆盖跨批次/跨月重复、
身份/倍率冲突、请求取消、单连接 SQLite、直接语义优先和不重复累加缓存。
本地数据库只读复核同一范围，目标三项质量计数归零且消费、退款、净额不变；同时核对明细和导出。
运行 model 全量、service/controller 相关回归、文档检查和差异检查。外部数据库与线上部署未验证
时如实记录，不把本地测试写成已上线。索引构建的生产执行成本需部署时按实际数据规模评估。

- 新增完整历史引用核验函数，每批 500 行，固定扫描上界，仅保存目标引用的 0/1/重复计数。
  取消每 Key 1,000 行业务降级，保留取消/查询错误返回及跨月唯一性校验。

  SQLite 执行计划验证分页读取使用该索引；既有迁移重入和拓扑测试通过。

  这补足前一轮只读核验未完成的写入分支证明，不依赖模型、客户或当前渠道配置。
