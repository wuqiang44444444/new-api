# 索引读写平衡优化与验证

## 问题与目标

账单与 Task 查询增加索引后，需要同时控制日志写入和任务更新成本。优化只改变物理索引，保留
租户隔离、权限唯一约束、排序分页、历史计费事实、任务状态推进和事务语义；不以调整慢查询阈值
或省略业务写入掩盖问题。

## 当前实际情况

本轮开始时只读检查本地 SQLite：logs 有 16 个二级索引，tasks 有 19 个（退款取证索引尚未部署），
error_events 有 14 个，casbin_rule 有 2 个。Task create attempts 的 21 个索引不在本轮删除范围。

已验证的结构问题：

- `idx_created_at_id` 代码声明为 `(created_at,id)`，实际库为 `(id,created_at)`；当前日志时间排序
  仍需要临时排序。不能仅凭索引名称认定迁移完成。
- logs 的 `user_id`、`model_name` 单列索引分别由已有 `(user_id,id)`、`(model_name,username)`
  的前缀覆盖。业务查询未绑定旧索引名。
- error_events 的 `created_at` 单列索引由 `(created_at,id)` 覆盖。
- Casbin 普通索引和唯一索引具有相同的七列，唯一索引必须保留。
- Task 全字段更新路径有既有业务含义，不为节省索引维护成本改为省略字段。Task/attempt 状态、
  资金、恢复调度索引不能因为当前数据取值少就删除。

## 优化方案与实现

### 索引和迁移

1. 保留两个账单日志联合索引和任务用量轮询索引。Task 退款取证改为非唯一
   `idx_tasks_task_user_app(task_id,user_id,app_id)`，替换原 `task_id` 单列索引；全部查询条件和
   业务代码保持不变。同一联合索引同时支持原生 Task ID 查询和带用户/应用的退款取证。
2. 修正日志排序索引。先建相同目标列顺序的临时索引，再替换错误的旧索引；最终移除临时索引。
   中断后按实际索引结构继续，不持久化迁移状态或修改业务行。MySQL DDL 隐式提交不影响恢复设计。
3. 删除四个已审查的普通索引：`idx_logs_user_id`、`idx_logs_model_name`、
   `idx_error_events_created_at`、`idx_casbin_rule`。同时移除旧 GORM 声明，避免每次启动重建再删除。
   迁移后 logs 14、error_events 13、casbin_rule 1；Task 替换索引后仍为 19，不增加索引数量。
   已部署首轮 `idx_tasks_user_app_task` 的数据库也在新索引可用后删除旧方案索引。
4. 新文件 `model/read_write_index_migration.go` 只处理明确列出的索引。删除前检查原索引为普通
   完整索引，替代索引存在且列顺序、唯一性等符合预期；遇到自定义唯一、条件、表达式、前缀或
   不符合预期的索引，返回迁移错误，不擅自删除约束。
5. 元数据查询分别适配 SQLite、MySQL 5.7、PostgreSQL 9.6。PostgreSQL 按 `indkey` 顺序读取列，
   不使用当前 GORM `GetIndexes` 未保证顺序的结果作删除依据。ClickHouse 保持原分支，不执行这些迁移。

### 最小入侵说明

- 原生 `model/log.go` 只移除两个重复索引标签；必须修改声明，否则 AutoMigrate 会重复创建已退役索引。
- 原生 `model/task.go` 只移除 TaskID 的单列索引标签；Task 字段、状态和资金写入方法不变。
- 原生 `model/main.go` 只增加 Casbin 迁移调用及错误返回，接在 AutoMigrate 之后。
- 主体逻辑、回归与基准放在独立文件。其它接线位于本地账单迁移和错误事件迁移；不改 Task 生命周期、
  Relay 或权限 adapter。上游合并只需核对日志/Task 索引标签与主库迁移接线，保留独立文件。

### 验证

- 升级回归比较迁移前后原始日志、权限规则和错误事件，验证日志/事件过滤分页、同时间 ID 排序、
  权限唯一约束和普通日志重复写入。重复 AutoMigrate/迁移不得产生索引 DDL。
- 中断回归覆盖旧索引与临时索引共存、仅临时索引、正确索引与临时索引共存；未知约束和缺少有效
  替代索引时拒绝删除。Task 替换回归额外验证不带用户的历史首行查找、用户内查找、应用隔离、
  capability 查询拒绝重复 ID、同 ID 继续可写，以及重复启动不重建旧索引。
- 既有 Task/日志账单回归覆盖租户隔离、退款分类、完整账单/明细/导出一致性、重复任务证据保持未知、
  回滚、取消和并发提交；CI 的服务器索引回归包含本轮迁移测试。
- 新增 `BenchmarkReadWriteIndexes`，使用纯合成数据和隔离数据库：10,000 条日志、500 条任务，
  4 个并发工作者；每操作插入日志并更新 Task，每十次创建 Task；混合场景每八次额外读取时间排序
  日志页和作用域内的任务证据。前后比较使用完整索引集合，包括 Task 新索引的写入成本。
  三轮交替执行优化前后顺序，输出每操作耗时、写阶段 P95/P99 和连接池等待次数，不设脆弱的耗时断言。

基准命令：

```sh
go test ./model -run '^$' -bench '^BenchmarkReadWriteIndexes$' -benchtime=2000x -cpu=4 -count=1
```

服务器测试使用既有 `TEST_BILLING_STATEMENT_DIALECT` / `TEST_BILLING_STATEMENT_DSN` 隔离夹具，
仅允许回环服务器，每次新建随机测试库，结束删除；不向配置 DSN 指向的数据库迁移业务表。

### 存储成本复测

项目 SQLite 3.50.4 驱动，WAL/FULL；临时库保留本地数据的规模、索引字段分布和正文长度，字符串
脱敏、正文替换为合成数据，不复制原始私有快照。四轮交替前后顺序，逐行提交；每轮 400 次计时插入，
另用 100 次插入测 WAL，以下为各轮指标的中位数。仅在其它本任务基准结束后串行运行。

| 范围 | 优化前 | 最终方案 | 解释 |
| --- | --- | --- | --- |
| 日志插入 P50 / P95 | 0.1202 / 0.2518 ms | 0.1082 / 0.2063 ms | 移除重复索引，修正排序索引 |
| 日志 WAL / 插入 | 84,007 B | 75,396 B | 本样本减少约 10.3%，不是跨工作负载的常数 |
| 空账期退款读取 P50 | 0.0106 ms | 0.0106 ms | 仍使用账单联合索引，不丢失已有优化 |
| Task 插入 P50 / P95 | 0.1328 / 0.2296 ms | 0.1332 / 0.2275 ms | 总索引数保持不变，耗时基本一致 |
| Task WAL / 插入 | 109,922 B | 109,263 B | 本样本未增加；不宣称所有数据分布都减少 |
| 19 个 Task 取证 P50 | 1.7011 ms | 0.0784 ms | 查询计划同时使用三个条件，约快 22 倍 |
| 包含身份列的 Task 更新 P50 | 0.0604 ms | 0.0600 ms | 无需改变业务更新字段来降低成本 |

最初额外增加 Task 联合索引的方案在纯写基准有约一成开销，因此最终改成替换 Task ID 索引。
早期并行运行测试所得的耗时波动较大，不作为最终性能结论。WAL 字节数、索引数和查询计划提供
可重复的结构证据，耗时和尾延迟仍需结合实际部署负载判断。

### 最终三库并发基准

最终基准在本任务各数据库之间串行执行，各场景三轮、每轮 2,000 次操作，交替前后顺序。下表每项
均取三轮中位数；平均耗时是 benchmark 的墙钟时间/操作数，P95/P99 为单次操作写阶段的延迟，
两者不能直接换算。MySQL 5.7.44 使用本地 Docker amd64 模拟，PostgreSQL 9.6 与 SQLite 为 arm64；
只比较同一数据库内的前后值，不比较不同数据库的绝对快慢。

| 数据库 / 场景 | 平均 ms/操作，前→后 | 写阶段 P95 ms，前→后 | 写阶段 P99 ms，前→后 |
| --- | --- | --- | --- |
| SQLite / 纯写 | 0.366 → 0.348 | 0.683 → 0.610 | 8.839 → 8.777 |
| SQLite / 混合 | 0.414 → 0.364 | 0.619 → 0.551 | 4.496 → 5.153 |
| MySQL 5.7 / 纯写 | 1.394 → 1.377 | 8.435 → 8.171 | 10.508 → 9.665 |
| MySQL 5.7 / 混合 | 1.642 → 1.299 | 8.437 → 7.714 | 10.261 → 9.817 |
| PostgreSQL 9.6 / 纯写 | 0.697 → 0.636 | 4.380 → 3.778 | 5.941 → 4.875 |
| PostgreSQL 9.6 / 混合 | 0.832 → 0.801 | 4.547 → 4.557 | 5.881 → 5.318 |

各场景连接池等待计数均为 0（8 个连接、4 个工作者），不代表数据库内部没有锁或磁盘等待。
最终平均耗时未出现退化，但 SQLite 混合场景 P99 增加约 0.66 ms，PostgreSQL 混合 P95 基本持平；
如实保留波动，不声称所有尾延迟都改善，也不把本机样本当作生产 SLA。

### 回归结果

- SQLite、MySQL 5.7.44、PostgreSQL 9.6：最终 Task 替换、日志排序修复、冗余清理、账单/明细/导出、
  错误事件状态筛选与并发提交回归通过。
- `go test ./model ./service/authz ./middleware ./controller ./service -count=1` 通过，包含既有权限、
  Task/attempt 与资金事务回归。
- 相关包 `go vet` 和根模块 `go build ./...` 通过。
- SQLite、MySQL 5.7.44、PostgreSQL 9.6 的 DDL 故障注入均通过：目标索引创建失败后临时索引仍可用，
  原始记录不变，下一次迁移可恢复并移除临时索引。
- `task docs:check` / `task ai:check` 通过。

### 部署与边界

本轮不重启正在使用的服务，不直接给业务库执行 DDL。由部署后的主节点启动迁移；首次建索引需
备份与受控升级窗口，避免多节点同时迁移，预留临时索引空间。索引 DDL 可能等待锁或阻塞写入，
这与迁移完成后的稳态写入成本分开评估。

基准只衡量数据库/GORM 层，不包含完整资金事务、Provider 调用和真实生产流量。最低版本隔离测试
和本机基准不能视为生产峰值验收，也不保证所有 SQL 均低于 200 ms。部署后仍需观察写入尾延迟、
连接池等待和账单读取；不能把尚未重现的 743 ms/281 ms 日志宣称为已精确定位。
