# 统一图片生成、编辑与异步查询方案

## 1. 问题与目标

为图片能力提供统一的生成、编辑及可选异步查询合同，支持文生图、参考图生成、图片编辑和多图融合。
原则是 **北向统一，南向适配**：客户不因 Provider 的认证、路径或字段差异改写图片请求。

- 本期原生渠道范围仅为 Gemini / Vertex：保留类型、认证和既有能力，仅增加对统一图片接口的支持。
- 本期异步图片渠道（管理面“图片中转”）完整改造：承接 NEWAPI 未原生支持的中转站图片业务，
  由显式登记的南向协议履约；包含 93 所在渠道类型，不是只修改 93 这一条记录。
- 对上述范围统一提供默认同步、显式异步；上游同步或异步均使用同一平台任务查询与结果合同。

本文件保留首次建立的文件名以维持引用；正文同时覆盖 Gemini/Vertex 接口补齐与图片中转渠道完整改造。
此前“所有原生图片渠道逐一补齐”的泛化表述由本轮明确范围取代，不构成修改其他原生渠道的授权。

用户于 2026-09-05 总体确认本次讨论的全部建议。本文记录已接受的设计、待取得的证据和后续实施边界，
不是已发布 API 合同，也不替代当前架构事实文档。

本次仅维护方案文档；不实施代码、不调用真实生成接口、不修改数据库、渠道、模型映射或价格。
此前的管理员映射授权与本次文档确认不构成自动执行授权；仍遵守用户“先讨论，不实施”的边界。

### 1.1 成功标准

- 正式入口为 `POST /v1/images/generations` 和 `POST /v1/images/edits`，不是单数或缩写路径。
- 全部标准参数进入合同核对与履约范围；按标准自身的操作、模型适用条件处理，而非拼接所有模型字段。
- 不能以“接收参数但不生效”“转换成一句提示词”代替业务语义实现。
- 明确登记、可发现的模型能力限制可以保留；已确认 Google 图片 `n` 只能为 `1`。
- 统一结果用 `data[]` 承载多图；异步任务支持部分成功，不自动补生成。
- 异步受理持久化，客户端断开不取消；查询复用 `GET /v1/tasks/{task_id}`。
- OSS 为本期异步能力依赖，结果优先 URL，下载链接有效期 5 分钟；清理由 OSS 管理。
- Gemini/Vertex 与纳入的图片中转协议分别验证；代码测试通过不能代替 Provider、账单及灰度验收。

### 1.3 本期实施边界

| 对象 | 要做什么 | 不做什么 |
| --- | --- | --- |
| Gemini / Vertex | 增加对既有北向 generations、edits 的南向转换和结果转换，按统一合同接入共享图片同步/异步能力；复用现有认证、项目、区域、连接和代理。 | 不重建渠道类型或认证，不把 Google 渠道迁到图片中转类型，不改聊天等既有能力，不进行整个原生 adapter 的顺带重构。 |
| 异步图片渠道 | 完整改造图片北向参数、生成/编辑、同步/异步执行、任务查询、幂等、OSS、多图/部分成功、计费接线、公开参数与管理测试；各南向协议吸收 Provider 差异。 | 不只改路由或解除几个校验就称完成；不保留旧 url-only、只生成、固定单图等限制作为全渠道公共合同，不要求客户发送 Provider 私有结构。 |
| 共享底座 | 为本期两个范围复用并最小扩展现有图片入口、Task、计费与存储底座，唯一的图片任务事实与公共查询。 | 不新建平行任务系统或账本，不改变视频/其他任务语义，不借共享接线扩展其他原生渠道功能。 |
| 其他 NEWAPI 原生渠道 | 验证共享改动没有回归，保留原有功能和默认行为。 | 本期不逐一新增接口支持、不迁移渠道、不改参数合同。 |

“仅新增接口支持”指让 Gemini/Vertex 能履约已有的北向图片接口，不是新增一套北向路径，
也不是要求 Google 上游提供 /v1/images/generations 或 /v1/images/edits。
异步执行由共享图片底座提供；不为 Gemini 与 Vertex 各做一套后台任务。
“异步图片渠道”是现有类型名称，不代表其客户只能异步、也不代表其上游必须是异步 API。

### 1.4 中转站业务目标与验收

平台向客户交付的是统一图片服务，中转站是南向供应来源，不是第二套客户产品。
总体接入原则是“原生已有渠道优先复用；原生没有的中转站使用图片中转渠道”；
本期该原则的原生实施范围仅限 Gemini/Vertex，不能据业务原则扩大代码改造范围。

| 编号 | 业务目标 | 可观察的验收结果 |
| --- | --- | --- |
| B1 一次接入 | 客户使用平台客户模型及统一生成/编辑合同，无需理解供应商。 | 在已发布能力范围内切换客户模型，不需要更换接口路径、参考图结构、尺寸含义或查询方式；明确模型限制可发现且不静默改义。 |
| B2 完整图片工作流 | 交付文生图、参考图生成、编辑、多图融合，不停留在单一文生图代理。 | generations、edits、三种图片输入和标准适用参数都有真实履约验证；不以接收后忽略参数冒充支持。 |
| B3 南向差异内收 | 技术人员维护代码协议，管理员选择协议与渠道配置。 | Provider 私有路径、字段、认证、任务状态和 usage 由 adapter 转换；客户不填写协议 JSON、Provider task ID 或私有参数。 |
| B4 同步与异步统一 | 既照顾标准同步客户端，也支持长耗时任务提交后查询。 | 相同创建路径和图片参数，通过 Prefer: respond-async 返回 202 与平台任务 ID；原生同步上游和异步中转上游均可统一查询。 |
| B5 稳定且低流量的结果交付 | 任务可追踪，图片由 OSS 按需下载。 | 异步结果优先 URL，5 分钟过期后授权查询可取得新链接；显式 Base64 仍履约；OSS 删除只改变结果可用性，不改写历史生成事实。 |
| B6 多图真实交付 | 一个请求可返回多张图片，并如实表达部分成功。 | data[] 返回可用图片；已明确结束时才判最终部分成功，未知仍待核实；不自动补图，不截成全局单图。 |
| B7 管理员掌握商业配置 | 客户模型名、映射、渠道连接和价格由管理员配置。 | 不在代码中定价、自动添加映射或继承价格；固定价/token/表达式按冻结配置履约，真实 usage、预扣、结算、退款可审计。 |
| B8 控制重复调用与成本风险 | 客户重提、进程重启及网络异常不能无依据重复生成或收费。 | 可选幂等只产生一个受理结果；恢复根据持久事实进行，Provider 可能受理后的未知结果不自动重发/换渠道/退款。 |
| B9 客户与基础设施隔离 | 客户只接触自己的任务和图片，不获知供应商内部配置。 | 查询按 user_id + app_id 授权；无渠道凭据、原始响应或签名 URL 日志泄漏；平台不擅自改变 OSS 删除策略。 |
| B10 可持续接入中转协议 | 完整改造现有图片中转公共链路，使协议新增不反向形成新的客户合同。 | 现有 FunCloud、Moxing 协议分别验证并接入统一链路；未来新增协议复用同一合同与底座，但不承诺未知供应商无需 adapter 即可接入。 |

客户流程保持为：使用公开客户模型与参数提交 → 同步取结果或异步取平台任务 ID → 同一查询入口获取
状态和结果 → URL 过期后重新查询。客户无需跟随 Provider 创建/轮询路径，也无需处理上游身份。

管理员负责渠道、映射与商业配置；技术适配负责协议转换和能力证据；平台负责受理、执行、任务、资金和
交付；OSS 生命周期由部署方管理。不默认增加回调、取消接口、通用工作流引擎或客户可编辑协议脚本。
Provider 限制导致目标无法实现时，应记录证据并报告范围冲突，不以“中转站不支持”为由静默削减已承诺合同。

## 3. 优化方案

以下编号保留总体确认清单的标识，便于实施与验收追溯。

### 3.1 合同原则（C1—C5）

| 编号 | 已接受的设计 |
| --- | --- |
| C1 | 全部标准字段纳入统一合同核对，依据标准的操作和模型适用条件履约。禁止只接收、丢弃并宣称功能完成。 |
| C2 | 字段、路径、认证、结构差异由 adapter 吸收；实现未完成不等于模型不支持。只有明确的能力限制或无法履约的业务要求才可报错。 |
| C3 | 仅标准或已发布合同明确规定的条件生效字段可在条件不满足时不生效；不能任意忽略 mask、透明背景等结果要求。 |
| C4 | 本期创建操作为 generations、edits，并复用任务查询提供显式异步扩展；不自动发布 variations、Responses 图片工具或完整 Files 管理 API。file_id 的必要解析与授权依赖仍须解决。 |
| C5 | 复用原生路由、Task 与计费底座，不建立第二套公共任务系统或账本。仅扩展明确的图片执行类型；主体转换隔离到新增文件，现有热路径最小接线，不改变无关原生和视频行为。 |

具体字段必须生成按操作区分的合同清单；字段类型、必填性、默认值、枚举、上下限及条件生效规则要
有唯一实现来源，并用于校验、公开元数据和合同测试。不得另建管理员可编写的协议 JSON 或逐模型平行能力系统。

### 3.2 标准参数（P1—P14）

| 编号 | 参数 | 已接受的处理方向与完成条件 |
| --- | --- | --- |
| P1 | model | 使用客户模型，按原生管理员映射解析最终 Provider 模型；不按名称片段猜测能力。 |
| P2 | prompt | 保留客户原意，不自动改写业务请求；内部履约说明不得替代参数实现。长度和计数方式在合同冻结时明确，不把某个 Provider 的限制无差别施加给原生入口。 |
| P3 | n | 标准合同范围为整数 1—10，未传为 1；Google 图片仅允许 1，其他值在 Provider 调用前报错。不循环调用、钳制或把显式 0 当默认值。共享 MaxImageN 安全上限不因此全局改为 10。 |
| P4 | size | 以标准 auto、宽x高语义为准，南向转换到 Google 分辨率档位与宽高比；之前直接用 512/1K/2K/4K 充当标准 size 的方案被取代。 |
| P5 | 尺寸后处理 | 允许必要的等比例缩放；不得擅自裁切、拉伸、补边或返回另一尺寸。可发布的像素尺寸、auto 行为及转换表须验证；无法保持要求的规格不得虚假发布。 |
| P6 | aspect_ratio 扩展 | 不作为标准请求必填字段。优先由 size 表达尺寸；如需额外暴露原生比例，应另行明确可选扩展与冲突规则，不能出现两个尺寸权威。本次不默认新增扩展。 |
| P7 | quality | 对标准适用值建立可靠规则，不直接把 high 当 4K 或更多 thinking。缺少等价映射时保留为实施/验证阻断，不静默降级或将未实现写成支持。 |
| P8 | output_format / output_compression | 支持标准适用格式及压缩语义；上游无法直出时允许网关转换。明确 PNG/JPEG/WebP、格式对应 MIME、透明度与压缩适用条件；保留合法压缩值 0，验证范围及无效组合。 |
| P9 | background | transparent 必须有真实透明通道；opaque 验证或处理透明度。允许必要图像处理，但不得仅依赖提示词冒充透明背景支持；需完成实际结果验证。 |
| P10 | moderation | 不假定两家审核档位等价，不绕过 Provider 安全策略；建立可验证映射或明确能力限制。实现缺口不能靠忽略字段掩盖。 |
| P11 | style | 按标准模型适用条件处理，不强行把 DALL·E 专用字段变成 Google 风格提示词。 |
| P12 | user | 仅作调用方辅助标识，不替代 user_id、app_id 或真实授权，不凭空映射为 Google 账号。 |
| P13 | response_format | 异步未指定时默认 url，显式 b64_json 按数组返回；同步遵守已发布默认行为，显式格式按统一合同履约，不强行全局更改原生默认值。Data URL 不得冒充托管 URL。 |
| P14 | stream / partial_images | 显式 false、0 正常解析；同步流式按标准适用语义履约，不拿 thought 图片冒充中间成品。Prefer: respond-async 与 stream=true 互斥，在受理、预扣、调用上游前报参数冲突；异步允许 stream 未传或 false。partial_images 的条件生效按标准冻结，不能将其当 n 或异步任务开关。 |

“总体确认”确认上述完成要求，不代表 quality、透明背景或流式的技术映射已被证明。
若最终证据证明某个适用标准语义无法可靠履约，应携证据重新报告范围冲突；不能自行排除后宣布本期完成。
仅明确确认的模型例外（例如 Google n=1）可直接作为本期限制；OSS URL 已不再是延后项。

### 3.4 URL 与大小履约（U1—U5）

| 编号 | 已接受的设计 |

| U4 | 南向要求 MIME 时必须有可靠获取方式，不能依赖 URL 后缀或猜成 JPEG。若必要探测，应限于类型履约，落实 SSRF、重定向、超时和取消，不能演变为大小检查。具体无探测/探测路径需技术验证。 |

额度相容的内存、读取和取消边界；不得引入一个更小、未公开的整体 body 限额使合法 Base64 请求失败。

| 编号 | 已接受的设计 |

### 3.7 异步提交、幂等与查询

| 项目 | 已确认合同 |
| --- | --- |
| 创建入口 | POST /v1/images/generations、POST /v1/images/edits 不变，图片请求参数不因同步/异步分成两套。 |
| 选择方式 | 默认同步；请求头 Prefer: respond-async 显式选择异步。这是平台新增扩展，不是 OpenAI Images 原生参数，也不是 stream=true。 |
| 流式冲突 | 异步与 stream=true 在受理、预扣、调用上游前报参数冲突；不静默忽略任一选项。 |
| 受理响应 | 完成持久化受理后返回 HTTP 202、平台任务 ID、查询地址，不等待生成完成；不承诺在必要文件上传完成前返回。 |
| 查询入口 | 复用 GET /v1/tasks/{task_id}，一次查询获得状态与可用结果；图片专属投影不改变其他任务合同。按 user_id + app_id 授权，不泄漏 Provider/渠道身份。 |
| 可选幂等 | Idempotency-Key 在同一用户、应用、操作内定位请求；同 key 相同请求返回原任务，不重复生成/预扣；同 key 不同请求明确报冲突；未传则每次为新意图。 |
| 未知任务重提 | 原任务待核实时，同 key 重提仍返回原任务，不创建新的发送机会。幂等防客户重复提交，不等于上游支持幂等。 |

请求等价判定、幂等保留期、任务记录保留期、202/查询 JSON 字段名及错误码在技术合同冻结时补齐，
不擅自采用 5 分钟作为幂等期限；下载链接的期限与任务/幂等生命周期无关。
并发相同 key 必须只有一个受理结果；202 丢失后可用同 key 恢复任务 ID。生成业务、幂等绑定及资金写入
必须有原子约束，不能先多次扣款再靠事后退款抵消。

### 3.8 持久化受理与恢复

采用数据库驱动的后台执行，不新增外部消息队列。沿用现有 Task 和计费底座，增加显式的图片执行类型，
不另建第二套公共任务系统；任务 ID 是平台 ID，真实 Provider task ID 有则独立保存，没有则不伪造。

受理顺序：

1. 校验图片合同、权限、容量与幂等；选择渠道，冻结模型映射、连接、adapter 与管理员计费事实。
2. 保存必要执行输入：上传文件/Base64 放私有 OSS；数据库保存对象引用。直传 URL 不自动搬运媒体，
   但恢复所需 URL 与必要参数必须有受保护的持久保存方式，不能只留在请求内存。
3. 在同一数据库事务中保存可执行任务、预扣资金与幂等绑定；只有输入可用且事务成功才返回 202。
4. 后台通过条件更新取得唯一发送许可；发送前核实预扣状态，不重复扣费。客户连接不再控制已受理任务。
5. 上游同步接口由后台等待结果；上游异步接口持久化真实 task ID 后持续查询，两者均归一成同一客户结果。
6. 校验图片、写入 OSS 并可靠登记结果引用后才宣布可交付完成；结算状态单独幂等推进，数据库结算失败
   不抹去已取得的生成事实。

| 重启/异常时的可靠事实 | 恢复动作 |
| --- | --- |
| 尚未取得发送许可 | 在输入仍可用、未超过明确排队期限时恢复执行。 |
| 已保存真实上游 task ID | 恢复查询，不能重新创建。 |
| 请求可能已发送，但无可恢复结果 | 待核实，不自动重发、换渠道或退款；未发出字节与已发出之间的崩溃窗口按保守原则处理。 |
| 图片已保存 OSS，但数据库结果登记未完成 | 按可验证的对象关联补登记，不重新生成；需设计确定的关联，不能把“能恢复”仅当假设。 |
| 上游成功，OSS 暂时失败，仍有可恢复的结果 | 仅重试读取/保存已有结果，不重试生成；只在内存的图片随崩溃丢失时记录交付异常，不承诺恢复。 |

执行权/租约失效不赋予新节点再次发送生成 POST 的权限。未知结果需要可靠证据或技术人员核实，不通过
单次查询失败判业务失败。明确失败按既有政策释放预扣，成功按冻结规则结算；未知保留待核实。

现有“真实 Provider task ID 后创建 Task”、prepared 清理及超时退款不能原样套用。
实施前必须针对新图片类型明确调整上述合同及扫描范围，并保持视频和其他既有任务不变。
异步必要输入保存也是对旧图片“请求正文/源 URL 不持久化”范围的局部变更，需落实私有存储、授权、
脱敏及部署方生命周期规则；不能把全文媒体或签名 URL 填入普通任务数据/日志。
OSS 生命周期可能提前删除待执行输入，客户 URL 也可能在排队后过期；这些失败必须如实表达，不能自动换图、
换 URL 或重新生成。具体时间上限与受保护保存机制仍是实施门槛。

### 3.9 多图与部分成功

- 一个平台任务对应一次生成/编辑请求，`data[]` 可有多张结果，不拆成多次 Provider 创建来凑 n。
- 每张有效结果独立保存、签发 URL 并表达到期时间；显式 Base64 时逐张返回。
- 全部成功：返回全部有效结果；全部明确失败：返回失败。
- 上游已明确结束且部分结果成功：返回成功图片，任务明确标记“部分成功”，不自动补生成。
- 尚有生成结果无法确认：仍待核实，可以表达已知可用结果，但不能提前宣布最终部分成功。
- 上游生成成功而部分 OSS 上传失败属于交付问题，不直接等同 Provider 部分生成失败；先按已有结果恢复保存。
- 计费使用可信完整用量与管理员规则，不擅自按成功张数折算、添加价格倍率或把图片数量冒充 token。
- 同步图片结果也使用数组；异步“部分成功”等状态属于任务封装，不向原生同步响应擅自加入同名状态字段。

实际状态枚举、逐图错误/可用性字段及异常数量规则在技术合同中冻结，不能将未知事实压成成功/失败二选一。

## 5. OSS 本期范围与结果访问

对象存储实现已从后续 TODO 提升为本期异步图片必要依赖；普通同步调用不因此被全局强制依赖 OSS。
同步显式要求托管结果时，按相应存储能力履约，不把缺少 OSS 变成所有原生同步请求的禁止条件。

| 项目 | 已确认规则 |
| --- | --- |
| 保存内容 | 本期异步必要文件输入和最终图片进入私有对象存储；任务/归属/计费仍以数据库为权威，不把 OSS 当队列或账本。 |
| 输出优先级 | 异步默认 URL，显式 b64_json 仍支持；内部存储格式不决定客户返回格式。 |
| 链接期限 | 每张下载 URL 有效期固定为 5 分钟；授权重新查询时签发新的 5 分钟链接，并返回到期时间。 |
| 持久引用 | 保存对象标识与必要 MIME 等元数据，不把临时签名下载 URL 当持久结果；不将存储桶设为公开访问，也不额外返回内部存储配置。 |
| 对象清理 | 由部署方的 OSS 生命周期/管理负责；平台不建立图片自动删除、保留期清理任务，也不擅自设置 OSS 删除策略。此规则不意味着承诺永久保留。 |
| 对象已删除 | 确认对象不存在后，保留生成成功/部分成功历史，表达对应图片结果不可用，不自动重新生成或退款。多图分别表达可用性，不因一张被删除抹去其他图片。 |
| 对象暂不可访问 | OSS 超时、权限错误等不能当成已删除；报告暂时访问问题，不签发明知无法履约的结果并伪装可用。 |
| 失败恢复 | 只重试保存/读取已有可恢复结果，不重新调用生成；OSS 与数据库不能跨系统原子提交，必须验证对象保存后补登记的恢复路径。 |
| 费用与安全 | 价格由管理员政策决定，不写固定存储价格；日志不记录完整签名 URL、媒体正文或凭据。 |

URL 下载通常绕过网关图片正文传输，可减少 Base64 膨胀与重复轮询正文，但上游接收和上传 OSS 的流量仍存在。
5 分钟仅是链接期限，不是 OSS 对象、平台任务、输入资料或幂等记录的保留期限。
异步队列与执行要求部署方确保输入对象在必要执行期间可用，具体保障方式需技术合同明确；不由平台偷偷下载
客户直传 URL 或自动更改 OSS 清理规则来补偿。
