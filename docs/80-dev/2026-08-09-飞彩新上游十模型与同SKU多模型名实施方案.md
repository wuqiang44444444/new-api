# 飞彩新上游十模型与同 SKU 多模型名实施方案

## 1. 目标与边界

本文记录 `http://43.161.200.208` 当前对已配置渠道凭证可见的十个 Seedance
Provider 模型 ID，并给出“新旧 Provider 模型名称履行同一客户 SKU”的实施建议。

截至 2026-08-10，本轮已完成 V3 代码注册、失败关闭门禁与首轮十模型真实验证：

- 未修改任何生产 Channel、Ability、publication 或价格；
- 已新增 `feicai.seedance-videos/v3`，其十个 execution binding 只包含无后缀模型；
- V3 已为 Mini、Fast、Standard 720p 登记独立 `16:9 -> 1280x720` size evidence；其它七个模型
  继续在 publication readiness 门禁失败关闭；
- `/v1/models` 可见只证明当前 Key 能发现该 ID，不证明创建、轮询、内容、账单或
  新旧名称之间的履约等价性；
- 本文不记录 Key、上游请求 ID、Provider Task ID 或原始私有响应。

### 2.2 已确认的当前故障

渠道 56 当前五条 `model_mapping` 的目标值均带 `-feicai` 后缀，而新上游的十条
ID 均不带该后缀。五条当前 mapping 目标在新上游 `/v1/models` 中的精确匹配数
均为 0。

因此本次 Mini 720p 创建失败的已证明配置原因是：

```text
客户模型 seedance-2.0-mini-720p
  -> 当前 mapping seedance-2.0-vip-720p-mini-azhw-feicai
  -> 新上游不存在该精确模型 ID
```

新上游未提供可信的确定拒绝证据，本系统仍必须将已发送创建保持为
`create_outcome_unknown`。配置修复不会自动恢复或重发该历史 attempt。

## 3. 合同分层结论

若真实黑盒证据证明新旧模型名只是同一产品的 Provider 别名，则应保持：

- 客户接入合同 `modelark.contents.generations.v3` 不变；
- 客户模型和 Link SKU 不变；
- `VideoSKUCapability` 和 publication 不因 Provider 别名变化而升版；
- 新旧 Provider 模型名分别作为精确 execution binding，可以指向同一 Link SKU；
- Provider 模型集合进入 implementation `ContentHash`，不得就地修改已冻结的
  `feicai.seedance-videos/v2`。

该变化不是“新增客户合同”，而是“同一客户合同新增一组 Provider 履约身份”。

## 4. 建议实施方案

### 4.1 已实现方案：v2 与 v3 并行可选

新增不可变 implementation `feicai.seedance-videos/v3`，v3 只登记新上游可见的十个
无 `-feicai` 后缀 Provider 模型；现有 `feicai.seedance-videos/v2` 继续只登记旧上游的
十个带后缀 Provider 模型。两个 implementation 各自使用唯一精确 Provider 模型履行
同一客户 Link SKU，不在任一 implementation 内建立新旧别名二选一。

```text
v2 / 旧 URL:
seedance-2.0-vip-720p-mini-azhw-feicai -> seedance-2.0-mini-720p

v3 / 新 URL:
seedance-2.0-vip-720p-mini-azhw        -> seedance-2.0-mini-720p
```

v2 不标记 deprecated，继续服务旧 URL 的新任务与历史任务；v3 服务新 URL。
两者都是管理员可选方案。由于 registry 禁止两个未 deprecated implementation 使用完全
相同的 Provider/PlanName，当前代码使用以下可区分且不泄露凭证或内部地址的展示名：

```text
飞彩 · Seedance 2.0 Video（后缀模型）
飞彩 · Seedance 2.0 Video（无后缀模型）
```

### 4.2 尺寸与计费证据

Provider size evidence 使用以下精确键：

```text
(implementation ID/version, Provider model, resolution, ratio)
```

因此只增加 v3 binding 不足以使新名称通过发送前门禁。实施时必须：

1. v2 的旧名 binding 和 v2 evidence 保持原样，不迁移、复制或重解释到 v3；
2. v3 只为无后缀新名建立独立 evidence 键，并且只能在精确的真实创建、轮询、
   内容和账单证据通过后登记；
3. Mini、Fast、Standard 720p、Standard 1080p、Standard 4K 和 Value 720p 的 v2 成功
   证据不能直接当作新名在新 IP 上的生产验收；
4. SD2、Value 1080p、Value 4K 和 Pro PI 仍保持不可发布，不得因 `/v1/models`
   可见或名称去后缀而继承相邻 SKU 的 evidence。

为避免在正式代码中增加无证据绕过路径，新名首次黑盒验证应使用独立验证器直连上游；
获得证据后再登记 evidence，然后执行本站 E2E。

### 4.3 exposure policy 与在途事实

- 代码默认 `provider_exposure_setting.monitored_implementations` 已精确包含
  `feicai.seedance-videos/v2` 和 `feicai.seedance-videos/v3`；已有部署若保存过自定义值，仍须在
  启用 V3 渠道前显式加入 V3，不能依赖新默认值覆盖持久化配置；
- v3 未受 exposure policy 保护前不允许启用 Channel；
- v2 和 v3 各自使用精确 exposure policy 身份，一侧事故不直接改写另一侧的风险事实；
- 旧 v2 Task、Asset、Binding 和 create attempt 继续使用冻结的 v2/hash 与旧 URL，不随 v3
  重解释；v3 任务同样冻结 v3/hash 与新 URL；
- 现有 Mini 720p unknown attempt 保持单独对账，不因 v3 上线自动重发、恢复或退款。

### 4.4 管理员选模型与 mapping 交互

后端在 v3 登记无后缀 binding 后，能够接受以下渠道事实：

```text
Models: seedance-2.0-mini-720p
model_mapping:
  seedance-2.0-mini-720p -> seedance-2.0-vip-720p-mini-azhw
```

Provider 模型作为 mapping 目标，不应因选择 Link 方案而直接写入客户可见 `Models`。当前表单已
取消 Link 方案的 Provider 模型自动填充：选择 v2/v3 时，`models` 与 `model_mapping` 保持不变；
当前 implementation 的精确 create bindings 只作为只读清单和 mapping 右侧候选。

Link 模式的表单职责为：

| 表单事实 | 来源 | 作用 |
| --- | --- | --- |
| 客户模型 | `models` / publication alias | 客户可见、Ability、价格、日志和 publication key |
| 已登记 Provider 模型 | 选中 implementation 的 execution bindings | 限制允许履约的精确模型集合 |
| mapping | 管理员选择 | 客户模型到精确 Provider 模型的唯一转换 |
| Link SKU | execution binding | 对 mapping 结果做唯一精确复检 |

当前管理员交互：

1. 选择 Link 访问方案 v3；
2. 从客户模型/SKU 列表选择 `seedance-2.0-mini-720p`；
3. mapping 右侧只展示当前 implementation 已登记的精确 Provider 模型；
4. 选择 `seedance-2.0-vip-720p-mini-azhw` 后生成 mapping；
5. Link 方案区域只读展示当前 implementation 的 Provider 模型清单；
6. 提交时后端仍以精确唯一 execution binding 为权威，前端候选不能绕过门禁。

`/v1/models` 仍是 NEWAPI 原生的显式模型发现动作，本轮不把它改造成 Link 合同来源或持久化第二套
候选状态。管理员若显式把上游发现结果加入 `Models`，现有 guardrail 会识别 mapping 目标泄露并提供
移除入口；选择 Link 方案本身不会触发该写入。

未来如需把实时发现结果收窄为候选交集，应在不改变上述权威边界的前提下另行实现：

```text
已登记 Provider 模型 ∩ 当前连接实时发现结果 -> mapping 右侧候选
```

该增强不能替代后端 execution binding 复检，也不能自动写入客户 `Models`。

原建议中的只读预览可以继续演进为：

```text
seedance-2.0-mini-720p -> seedance-2.0-vip-720p-mini-azhw -> seedance-2.0-mini-720p SKU
```

该交互需与同日
[Link 渠道真实模型展示与映射职责收敛方案](2026-08-09-Link渠道真实模型展示与映射职责收敛方案.md)
已完成职责收敛：“Link 方案区展示当前 implementation 的真实 Provider 模型”保留，
“将 Provider 模型自动填入客户 `models`”已移除。

### 4.5 渠道迁移

1. 先登记 v3 和 exposure policy，但不增加任何启用 Ability；
2. 通过独立真实验证取得新名精确 evidence；
3. 将渠道 56 的 implementation ref 切换为 v3，只配置已通过 evidence 的客户模型和
   无后缀 Provider mapping；
4. 渠道 56 先留在隔离测试分组，不直接承接生产流量；
5. 闭合创建、轮询、内容、Range、客户计费、Provider 账单与 unknown 故障注入后，再按
   精确 SKU 逐个放开 Ability；
6. 旧 URL 渠道继续选择 v2 和带后缀 mapping，不迁移到 v3；新 URL 渠道只选择 v3
   和无后缀 mapping。

publication 不因该迁移改绑：客户模型仍指向原 Link SKU，只是下一次请求的候选
implementation 和精确 Provider 模型变化。

客户不能在单次请求中选择 v2 或 v3。若两类渠道同时进入同一分组，分发器可以在两个等价
候选之间选渠。若运营上需要严格只走旧 URL 或新 URL，必须通过渠道启用状态、分组、Ability、
优先级和权重显式控制。

## 5. 实施顺序

### 阶段 A：合同和后端门禁（已完成）

- 已新建飞彩 v3 implementation 文件，原 v2 execution binding 与不可变 hash 未改写；
- 已新增无后缀 Provider 模型常量，v3 只登记这十个新 binding；
- v2 保留十个带后缀 binding 并继续可选，不标记 deprecated；
- v2/v3 已配置可区分的 PlanName，避免管理员误选；
- exposure policy 默认值已增加 v3 精确身份；
- registry 已冻结 V3 hash
  `sha256:a5aaab34a88874b93ca6edc6a7aad59bd1ed665c5cba6992a7afb21aaa10c613`；
- 已增加 v2/v3 分离解析、交叉 mapping 拒绝和无 evidence fail-closed 回归测试。

### 阶段 B：管理员表单（本轮收口完成）

- 已取消 Link 方案选择时向客户 `models` 自动写入 Provider 模型；
- mapping 源候选只来自客户模型，选中 Link 方案时目标候选只来自当前 implementation 的精确 binding；
- 先选择 v2 或 v3，再由对应 binding 候选建立 mapping；
- 不按后缀、Base URL 文本或列表顺序自动推断 implementation；
- 保留 JSON 编辑器与 NEWAPI 原生显式模型发现，不创建第二套 Link mapping 状态；
- 本轮未新增用户文案，因此无需修改 locale 文件。

### 阶段 C：证据和分组灰度

- 已按授权对十个模型执行首轮最小规格 Provider 黑盒，完整过程见
  [飞彩 V3 逐模型真实验证记录](2026-08-10-飞彩V3逐模型真实验证记录.md)；
- Mini、Fast、Standard 720p 取得真实 `1280x720` 内容及一致 task quota/usage，已回填精确 evidence；
- Standard 1080p、Standard 4K、Value 720p、Value 1080p、Value 4K 和 Pro PI 明确失败，继续关闭；
- SD2 create HTTP 503 没有可信顶层 ID，保持 unknown 且不自动重发；
- 客户入口幂等、Range、素材组合、边界拒绝和灰度稳定性仍未闭合，三个 size 条目不等于生产发布完成。

## 6. 验证矩阵

### 6.1 后端自动化

- `ValidateLinkImplementationRegistry`：v2 和 v3 均为可选飞彩方案，各自有稳定 hash 和可区分展示名；
- `DeriveChannelLinkExecutions`：v2 Mini 只接受带后缀 Provider 名，v3 Mini 只接受无后缀 Provider 名，
  两者都精确解析到同一 SKU；
- v2 mapping 不得在 v3 解析，v3 mapping 不得在 v2 解析；
- 无后缀模型没有精确 size evidence 时在预扣和 Provider POST 前失败关闭；
- 渠道 mapping 与 v3 binding 冲突时禁止保存或启用；
- publication 仍为原 SKU，不因 Provider 名改变；
- 历史 v2 Task/create attempt 继续按 v2/hash 恢复和对账。

### 6.2 前端行为

- 选择 Link 方案后，客户 `models` 与 `model_mapping` 不被 Provider 候选覆盖；
- mapping 右侧只出现当前 implementation 已登记的 Provider 模型；
- 无 binding 、未发现、重复或不等价模型均显示稳定错误；
- 管理员选择 v2 时只看到带后缀 mapping 目标，选择 v3 时只看到无后缀目标；
- 预览同时展示客户模型、Provider 模型和 Link SKU；
- 敏感凭证不进入前端状态、toast、测试快照或日志。

### 6.3 真实上游

- `/v1/models` 仍精确返回目标新名；
- create 返回可信顶层 `id`；
- poll 仅使用冻结的 Base URL、Key、Provider 模型和 adapter；
- `queued/processing/completed/failed` 归一化正确；
- 成功结果提供与冻结 Base URL 同源的可用 `video_url`；
- 内容完整下载和 Range 部分请求通过；
- 客户 quota 与 Provider 账单分别核对，不以客户 quota 冒充 Provider 成本；
- 任何未取得可信 Task ID 的异常继续进入 unknown，不自动重发。

## 7. 验收标准

1. 十个新上游模型 ID 有精确、不重复的收集表，不将可见性写成生产可用。
2. v2 不被就地改写且继续可选；v3 只有十个无后缀 binding 和新的不可变 hash。
3. 客户合同、SKU capability 和 publication 不因 Provider 别名重新定义。
4. 管理员可以从新上游发现结果选择 Provider 模型并建立映射，但 Provider 模型不直接变成
   客户可见模型。
5. 无精确 binding、evidence 或 exposure policy 的候选无法保存为启用渠道，也无法通过预扣与
   Provider POST 门禁。
6. 只有通过真实 Provider 创建、轮询、内容和账单闭环的精确 SKU/模型/参数组合才能
   进入灰度分组。

## 8. 回滚与未完成事项

- v3 发布前后都不修改或删除 v2 binding，v2 继续作为旧 URL 的可选 implementation；
- 任何验证失败只禁用精确渠道/Ability，不回退历史 Task 快照；
- 已创建的 unknown attempt 按原 SLA 对账，不因方案修改执行破坏性清理；
- 本文尚未授权付费视频验证，不得把后续验证矩阵解释为已执行；
- 新名等价验证完成后，将稳定架构事实收敛到
  [Seedance 统一北向合同架构](../20-architecture/Seedance统一北向合同架构.md)，将未完成生产验收继续留在
  `50-planning/` 路线图或真实验证矩阵中。
