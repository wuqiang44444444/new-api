# 渠道 52 真实验证与收窄发布记录

## 1. 任务目标与边界

渠道 52 原配置包含 SD2、Value 720p、Value 1080p、Value 4K 和 Pro PI 五个独立 Link SKU。启用时因
这些 capability 没有精确 Provider ratio/size evidence 而失败关闭。本次目标不是绕过门禁，而是执行
一次最小真实 Provider 矩阵，只发布能够以创建、轮询、同源内容和媒体探测证明履约的精确组合。

测试未输出或保存 Provider task ID、完整内容 URL、Key 或原始私有响应。`/v1/tasks` 仍返回 404，
账户 `total_usage` 只作为隔离窗口观察，不解释为任务级 Provider 账单。

`size=1280x720` 和 `16:9`；SD2 使用 11 秒和一张公共中性 PNG，其余按各自最小时长执行。验证器中的
¥40.37 只是阻止误操作超过授权范围的费用护栏，不是计划消费、实际消费或要求重复验证的目标。隔离
value 账户窗口 `total_usage` 从 14,556 增至 14,700，变化 144 分。

### 2.1 其余四个模型的失败阶段分析

以下分析只陈述现有响应能够证明的失败阶段，不用猜测代替 Provider 错误码。五个精确 Provider 模型
均通过同一 value Key 的 `/v1/models` 可见性预检，因此“模型未出现在模型列表”不是本轮失败原因；
可见性也不等于生成能力可用。

| 模型 | 已排除的本地原因 | 可证明的失败阶段 | 仍不能断言的根因 |
| --- | --- | --- | --- |
| SD2 | 请求使用允许的 11 秒、`1280x720`、非空 prompt 和一张可公网访问的 HTTPS PNG，满足已登记的图片必填边界 | Provider 创建端返回无可信顶层 ID 的 HTTP 503；按异步合同只能归类为 create outcome unknown | Provider 未提供结构化错误码且 `/v1/tasks` 为 404，不能断言是图片、权限、容量、线路或“确定未创建” |
| Value 1080p | 创建 HTTP 200、返回稳定顶层 ID 并进入 queued，说明本站校验、Key 鉴权、精确模型名和创建请求已被 Provider 接受 | Provider 创建后的生成阶段终态 failed；没有内容 URL | 终态没有可用错误码，不能把失败归因于 prompt、请求 size、分辨率实现、账号配额或内容策略；只能确认当前 Provider 执行不稳定 |
| Value 4K | 与 Value 1080p 相同，创建已被 Provider 接受并形成可信任务 | Provider 创建后的生成阶段终态 failed；没有内容 URL | 不能借用 Standard 4K 的成功解释 Value 4K，也不能在无错误码时断言是 4K 容量或 size 参数问题 |
| Pro PI | 15 秒符合固定时长；资料把图片/音频/视频列为可选上限，没有证据证明文本请求必须附带媒体 | 已观察两种 Provider 失败：早期任务进入 in_progress 后 failed；本轮创建 HTTP 503 unknown | 不能据此把媒体改为必填，也不能判断是按次线路、账号权限、容量或内容生成故障 |

Value 1080p 和 Value 4K 在多轮独立观察中重复出现“create 200 后 failed”，属于 Provider 模型执行阶段
不稳定，不是本站 publication/ratio 门禁造成的拒绝。SD2 和 Pro PI 的 503 没有可信任务 ID，不能自动
重发或用相邻模型补测。四者都缺少成功内容，因此从渠道 52 候选移除是证据驱动的发布收窄，不是对
Provider 根因的过度推断。

## 3. 实施结论

为保持 fail closed，渠道 52 从五模型候选收窄为唯一通过验证的 `seedance-2.0-value-720p`：

- 新增四元 size evidence：`feicai.seedance-videos@v2`、精确 Provider 模型、`720p`、`16:9`；
- Provider 请求 size 为 `1280x720`，billing class 为 `value-720p-16-9`，倍率为 1；
- evidence version 为 `feicai-prod-2026-08-06-r3`；
- capability version 为 `feicai-media-arrays-v2-r3`，implementation hash 固定为
  `530ad1bf49b065bc4c2b10af817ca763d024b9e32c2e5b12883a603ef6f65ee0`；
- 渠道 52 的 Models 与 model mapping 只保留 Value 720p；旧四条 Ability 被删除，没有仅靠状态切换
  留下启用的陈旧候选；
- 原四个未通过门禁的模型被移入新建渠道 55 `SD-08 飞彩待验证四模型（隔离）`；该渠道状态为
  manually disabled，保留四条禁用 Ability，enabled Ability 为 0，publication 为 0；
- 主库创建 1 条 publication version 1、启用 1 条 Ability，渠道状态为 enabled；
- `/v1/models` 可见 Value 720p，SD2、Value 1080p、Value 4K 和 Pro PI 均不可见。

客户计费表达式未因 144 分账户窗口变化而修改。未登记 ratio 仍在预扣和 Provider POST 前拒绝。

发布后的第一次客户入口 E2E 已取得可信 Provider Task，但 Provider 最终返回无错误码的 failed。本站
attempt 为 `complete/transferred`，Task 为 `FAILURE/settled/quota=0`，177,143 quota 预扣已完整退款；
这证明失败账务路径正确，不推翻同规格 Value 720p 已完成的真实 Provider 成功内容证据。准备停止追加
验证时，第二个客户 E2E 已在命令中断前完成创建，因此只轮询该既有任务，没有再创建新视频。它最终
`SUCCESS/settled`，内容 URL 存在，attempt 为 `complete/transferred`，最终客户 quota 为 177,143。
该成功确认了 publication、选渠、r3 capability、Provider 执行和客户结算链；publication 仍以最初的
真实成功内容为充分证据，不把重复成功次数设为门禁。

  必要媒体证据；在此之前不得启用渠道 55 或其中任一 Ability；

- 当前“渠道 52 已闭合”只表示其收窄后的 Value 720p 候选可发布，不表示原五模型集合全部可用。

  publication，也不能作为绕过证据门禁的发布依据。
