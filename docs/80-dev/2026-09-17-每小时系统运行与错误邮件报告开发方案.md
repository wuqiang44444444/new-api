# 每小时系统运行与错误邮件报告开发方案

> 后续修复（2026-09-19）：新生成邮件的固定标题、摘要、表头、数据说明及补发标识采用中英双语；语言内容在分卷前生成，随既有正文冻结，不增加语言配置和第二条投递流程。旧邮件仍读取原冻结正文。无活动证据时继续显示“数据不足”，不推断零调用。当前事实见[系统错误报告架构](../20-architecture/运维-系统错误报告架构.md)，验证见[修复记录](2026-09-19-账单启动与邮件评审修复记录.md)；真实 SMTP 与生产验收状态没有因此改变。

> 状态：需求已确认并完成本地实现与合并评审修复。最新行为及验证边界以文末“评审修复与验收跟踪”及其链接记录为准，

## 问题与目标

管理员目前需要主动打开错误页面排查，无法定期收到系统状态及完整错误明细。业务目标是在
复用当前错误记录、模型统计、SMTP 配置和系统任务框架的基础上，每小时发送一份运行与错误报告：

1. 回答“过去一小时有哪些错误”，正文逐条展示全部已纳入报告的错误。
2. 回答“已观测范围内系统是否出现服务故障”，区分客户侧问题与平台／上游问题。
3. 数据不足时明确说明，不把缺少错误、缺少统计或未观测到流量当成系统正常。
4. 邮件发送故障恢复后可以按小时补齐；重复可识别，不能默默丢弃积压报告。

### 用户已确认的业务决策

| 项目 | 已确认要求 |
| --- | --- |
| 报告内容 | 系统运行摘要与错误明细均需要 |
| 错误来源 | 复用错误页面背后的记录，不另建采集流程和错误事实库 |
| 统计来源 | 优先复用已有数据；成功率仅展示可核实范围，不推算全站成功率 |
| 数据缺失 | 显示“数据不足，无法判断”，不能用 0 补齐未知数量 |
| 故障判断 | 区分客户侧与平台／上游问题；客户参数错误不直接判为系统故障，明细仍展示 |
| 周期 | 北京时间每个整点，报告上一自然小时 |
| 无错误 | 仍发送运行摘要 |
| 无调用 | 确认无流量时写“无调用，无法据此判断稳定性”；不能将没有记录等同于没有流量 |
| 明细方式 | 全部逐条放入邮件正文，不以代表性样本或附件替代 |
| 过长邮件 | 允许拆成多封，使用固定报告时段和“第 i/N 封”编号，不删减错误记录 |
| 收件人 | 在现有系统配置的邮件配置区域指定一个或多个邮箱；不自动收集管理员账户邮箱 |
| 发送失败 | 按原小时窗口逐份补发，标题标注“补发”，不合并多个小时 |
| 发送结果不明 | 重试，允许偶尔重复；固定报告标识和分卷编号便于识别 |
| 首次开启 | 例如 10:20 开启，11:00 发 10:00–11:00；更早历史不主动补发 |
| 开启后漏发 | 按原小时窗口逐小时补齐 |

### 非本轮目标

- 不重新采集 API、渠道测试、流式或异步错误，不改变错误页面已定义的采集边界。
- 不补齐全量请求统计，不建立另一套健康评分、Provider 根因分类或业务状态机。
- 不改变渠道启停、重试、退款、任务生命周期及原生使用日志。
- 不创建 Codex 自动化、操作系统 cron 或独立调度服务；这是产品内的系统任务能力。
- 不承诺邮件到达收件箱、不承诺无重复，也不把 SMTP 成功当作送达回执。

## 当前实际情况

### 已核对的本地代码事实

| 系统任务 | `service/system_task.go`、`model/system_task.go` | 已有注册、持久任务、按类型租约和进度；定时任务按距离上次运行的间隔创建，不等于自然整点 |
| 配置注册 | `setting/config/`、`setting/operation_setting/notification_setting.go` | 已有配置注册到 options 的方式，可新增独立设置结构 |
| 邮件设置页面 | `web/src/features/system-settings/integrations/email-settings-section.tsx` | 新增报告设置放在此区域，沿用页面框架和配置保存入口 |
| 设置权限 | `router/api-router.go` 的 `/option` | 当前由 RootAuth 保护，不因邮件收件人被称作管理员就放宽权限 |

第二轮错误采集扩展在关联文档中已有实施记录，本次也核对到相关类型和字段存在；本文不重新
宣称其全部 Provider 路径已验收。Batch 部分行失败、部分回调／批量写入路径、WSS/realtime、
采集队列丢失等限制继续有效。错误邮件不会使原本未入库的错误自动可见。

### 对“直接复用”的准确解释

复用的是数据事实、邮件通道和执行框架。小时汇总、正文渲染、整点窗口、持久发送进度及补发
是新增能力，不能仅把错误列表 HTML 定时调用一次 `SendEmail` 就视为满足全部要求。

既有用户生命周期通知使用无补发异步发送，并可能受每用户通知限频影响；本功能收件人是
显式邮箱列表，应复用 SMTP 能力，不直接套用 `NotifyUser` 的地址覆盖和静默限频行为。

## 优化方案

以下工程细节是根据已确认要求推导的建议，不冒充用户逐项指定的数据库结构或参数。

### 1. 配置与启停

建议新增 `error_report_setting` 配置组：默认关闭、收件人默认为空，复用现有 SMTP 设置。
第一版用户可见项保持为报告开关、收件人列表和规则说明；频率固定每小时，时区固定
`Asia/Shanghai`，不扩成通用计划任务编辑器。

- 邮箱须做服务端格式校验、去空白及去重，拒绝 CR/LF；规范化规则不能随意改变邮箱本地部分。
- 保存多个收件人时按独立地址处理，发送时逐地址跟踪，不把多个地址拼成一次不可区分结果的发送。
- 启用必须有合法收件人并满足 SMTP 必要配置；运行中配置变坏应显示任务故障，而非“本小时无错误”。
- 首次启用的时间基准必须持久化，不在进程重启时重新计算。
- 建议将报告设置作为整体校验，避免逐字段保存暂时出现“已启用但无收件人”。实际接入须核对
  options 保存合同，必要时增加极窄的分组校验／保存入口，不重构通用配置系统。

建议的后续变更语义：关闭停止新生成和新发送，保留已有待发记录；再次开启继续已有待发补发，
关闭期间不主动生成报告。收件人新增默认只影响新报告；移除收件人后停止对该地址的后续尝试，
保留“配置移除而停止”的事实，不把旧报告转投给新地址。这些是待实现评审确认的默认语义，
不改变“服务故障期间开启状态未变，应补发”的已确认要求。

### 2. 时间窗口与调度

报告窗口统一使用北京时间自然小时，在数据库保存绝对时间戳：`[window_start, window_end)`。
恰好 11:00:00 的事件属于 11:00–12:00，不属于前一小时。标题同时写日期、时区和起止时间。

首次开启在 10:20 时，首个窗口起点为 10:00；11:00 成为首个到期窗口。报告覆盖的是这一完整
自然小时，不伪装成 10:20 才开始有数据。重启后从已持久化窗口进度继续，不从“现在减一小时”
重新起算而跳过积压。

新增一个注册到现有系统任务框架的报告处理器。建议短周期检查到期窗口和重试，例如一分钟
一次；内部按绝对时间计算窗口，不以“上次发送结束加一小时”定义统计范围。整点是到期时间，
实际发送受框架轮询、生成及 SMTP 耗时影响，不承诺整点零秒即收到。

各轮处理采用有限工作量，避免大量积压或单个故障邮箱长期占用租约；未完成进度必须可续跑。
按小时生成报告，各收件人的待发分卷按窗口和卷序递进；一个地址失败不阻止其他地址，也不
阻止新窗口生成。源数据库故障不能推进该窗口为已完成。

### 3. 数据口径与状态表述

| 内容 | 来源与计算 | 展示限制 |
| --- | --- | --- |
| 错误事件数 | 同一窗口内 `error_events` 的记录行数 | 称“错误事件数”，不能泛称失败请求总数 |
| 分类汇总 | 按事件类型、渠道、原因码汇总 | 同一事实可能同时关联任务与请求，不能跨类型相加计算成功率 |
| 模型统计 | 经校验覆盖范围、窗口和新鲜度后的已有性能统计 | 标注模型／采样口径；不得称全站或渠道成功率 |
| 用量信息 | 可选复用既有 Token、费用等可核实数据 | 不以消费记录数代替真实请求数，不与性能桶混算分母 |
| 渠道状态 | 报告中的错误事实，必要时展示读取时的渠道当前状态 | 当前状态不代表整小时状态，不能补造测试成功次数 |
| 采集状况 | 已有可取得的故障计数和任务状态 | 进程累计值、单节点值须明确标识；不得宣称是历史小时或全节点统计 |

同一指标的分子、分母必须来自同一已验证集合。不得使用“错误事件数 ÷ 消费记录数”、
“消费记录数 + 错误数”，也不得用当前性能成功数扣除流式错误数来猜测真实成功率。
现有性能查询的闭区间、滚动最近 N 小时等行为不能原样套用到自然小时报告。

整点时默认不等待统计刷新而推迟整个报告。已持久统计尚未完整、模型统计禁用、保留期已过、
跨节点数据不齐或成功定义不符合目标时，对应成功率显示“数据不足，无法判断”。历史补发
使用该小时可核实的数据，不能混入发送时刻的最近一小时或当前节点内存桶。

状态用语建议采用以下可解释规则，不另建任意阈值健康分数：

| 证据 | 状态说明 |
| --- | --- |
| 明确的平台／上游服务错误 | “已发现平台／上游相关异常”，列出影响范围和次数 |
| 只有明确客户侧错误 | “已记录客户侧错误；未在本次数据中发现明确的平台／上游故障” |
| 存在原因不明错误 | “存在待分类错误，需排查”，不默认归责客户或 Provider |
| 无错误且有可靠活动证据 | “本次已入库记录中未发现错误”，同时标注统计覆盖范围 |
| 有可靠完整范围且确认为零调用 | “无调用，无法据此判断稳定性” |
| 缺少可靠活动／采集证据 | “数据不足，无法判断”，不能显示绿色“系统正常” |

错误责任优先复用已有结构化分类。不得只按 HTTP 400/401/403 判断客户责任；上游账号失效、
模型权限或渠道额度不足也可能返回 4xx。客户断开、正常取消、可恢复流处理错误分别说明，
测试失败不等于实际客户调用失败。资料不足时保留未知，不通过原始错误文本关键词猜测根因。

### 4. 完整明细、快照与迟到数据

邮件明细复用错误页面可展示的安全字段：时间、类型、模块、HTTP 状态、用户／令牌名称、
模型、渠道、阶段、原因码、安全说明、请求 ID、上游请求 ID、任务 ID、耗时和受控详情。
没有字段时显示“—”，不能生成不存在的请求 ID 或从原始日志重新拼装敏感错误正文。

“完整”指该报告生成快照中所有符合窗口条件的已入库记录，不做抽样、Top N 截断或省略。
邮件可以保留回到错误页面的链接，但链接不能替代正文。报告同时写生成时间、数据截止说明、
事件总数与分卷总数，避免用户把快照误认为持续更新的实时列表。

生成时需要固定读取集合与稳定顺序。不得边发送边按偏移分页读取不断变化的事件表，否则
可能漏行、重复或使补发内容变化。建议采用日志库一致性读取，将有界批次渲染结果持久化为
暂存分卷；所有分卷完成、行数对账成功后才发布为可发送。中途失败的生成批次不能发送半份
报告；恢复时重新生成未发布批次或从有证据的进度续建。

SQL 日志库的可用主键与读取隔离需要实测；ClickHouse 当前事件行 `id` 不具备唯一业务身份，
`created_at + request_id` 也可能重复，不能直接当作唯一翻页或去重键。实现前须完成完整读取
测试，必要时采用单次服务端流式查询取得一致数据集合，不假定跨库事务或主键语义相同。

**迟到数据是尚需收敛的范围边界。** 现有事件没有通用可靠的入库水位，发生时间也不等于
入库时间。初版技术建议明确展示“截至生成时已入库”，固定报告在补发时不悄悄变化。若要求
生成之后才入库的同小时错误仍全部送达，必须增加“原小时补充报告”及可靠增量识别设计，
不能用有限回看窗口宣称绝不漏记。此项在编码前完成评审，不能把用户的“全部明细”静默
缩减为“随意延迟几分钟后认为数据完整”。邮件机制也不能恢复错误采集层本来就丢失的事件。

### 5. 正文与分卷

标题示例（示意，不代表实际已生成）：

```text
[系统运行与错误报告] 2026-09-17 10:00–11:00 北京时间｜发现服务异常｜第 1/3 封
[补发][系统运行与错误报告] 2026-09-17 10:00–11:00 北京时间｜发现服务异常｜第 2/3 封
```

正文顺序为报告标识与数据说明、运行摘要、错误分类汇总、逐条明细。无错误时也生成一封。
后续分卷保留简要报告信息、分卷编号和对应明细，不重复整小时明细造成重复计数。摘要自身
过大时也分段，不能因为渠道很多而截断统计。

分卷按实际 UTF-8 HTML／邮件编码后的大小预算，不按固定行数假定容量。建议初始将正文预算
控制在约 48 KiB，给邮件头和编码留余量；这是待 SMTP／客户端验证的工程初值，不是平台容量
事实。分卷生成后冻结，重试不因当前参数、渠道改名、页面模板升级而重新分页。

每条错误在报告中只计一次。单条内容超过预算时可按带关联编号的续段展示，不能删掉该记录。
如果仍无法履约，报告应保持明确失败状态并显示原因，不把部分内容发送后宣称完成。
任何预算都不能保证所有邮件客户端不折叠或截断，真实验收需覆盖管理员使用的客户端。

使用 HTML 模板转义全部动态字段，防止错误内容、模型名和渠道名形成 HTML 注入或外部资源。
只保留已公开安全字段，不保存／发送密钥、Token 值、Cookie、原始响应、Task 私有数据和
完整签名 URL。收件地址与正文快照仅通过受控管理权限访问，不写入普通系统任务公开结果。

### 6. 持久化发送模型

报告是已有事实的投递快照，不是新的错误事实源。建议新增以下主数据库模型，具体名字可在
实现时按项目风格调整；主库使用 SQLite/MySQL/PostgreSQL，不把投递状态存入 ClickHouse。

| 模型 | 最小职责与关键字段 |
| --- | --- |
| 报告调度状态 | 单实例配置作用域、启用起点／启用区间、下一待生成窗口；重启可恢复 |
| 小时报告 | 稳定报告 ID、窗口、生成时间、数据截止说明、生成状态、总事件数、总卷数、冻结收件人集合；唯一窗口约束 |
| 报告分卷 | 报告 ID、卷序、冻结主题与安全 HTML 正文、明细行数；唯一 `(report_id, part_no)` |
| 收件人投递 | 分卷 ID、收件人、状态、尝试次数、下次重试、租约／尝试标识、最后安全错误、SMTP 接受时间；唯一 `(part_id, recipient)` |

不把同一正文按每个收件人重复存储；不把多小时正文塞进单个 SystemTask 的 State 字段。
SystemTask 只执行工作并展示报告 ID、处理数量和安全状态，持久报告记录负责跨次任务续跑。

报告状态建议 `building → ready`；创建完整分卷和投递行后原子发布 ready。窗口调度进度只能
在已有持久报告可恢复后推进。发送进度由投递行聚合，不维护多套独立可冲突的成功标记。
投递状态建议 `pending → sending → smtp_accepted`；失败／结果不明进入 `retry_wait`，租约
过期的 sending 视为结果不明重试，配置移除单独标注停止原因。

按既有框架租约运行，并对报告唯一窗口和投递领取做数据库条件更新。数据库事务仅用于
领取、冻结和结果提交，不能包住 SMTP 网络调用。投递成功写回必须匹配本次领取标识，
防止旧执行者覆盖新结果。并发去重靠唯一约束和条件更新，不靠“先查有没有再插入”。

数据库字段使用跨库可迁移类型；正文分卷保持有界，验证 MySQL TEXT 字节限制。需要锁的
查询复用 `lockForUpdate(tx)`；JSON 编解码复用 `common.*`。不因新增文档把表名或具体
状态枚举视为已发布协议。

### 7. SMTP 发送、重试和恢复

每次只向一个已配置地址发送一个冻结分卷，成功与失败分别持久化。一个地址失败时，不重发
其他已经成功地址的分卷。接受状态统一称“SMTP 已接受”，不写“已送达收件箱”。

失败和结果不明均自动重试。建议采用有上限的指数退避，初值可为 1、5、15、60 分钟，之后
按小时重试；这些为工程建议值。不得达到次数后悄悄丢弃，需保留积压数量和下一次尝试时间。
明显配置错误先标注可操作原因并低频重试，避免对无效 SMTP 高频轰炸。发送过程中网络断开、
SMTP 成功后本地状态写入失败均按结果不明处理，允许重复。

补发使用原窗口、原正文和原分卷编号，仅增加补发标识；当前小时的统计不能替换积压报告。
固定报告 ID + 分卷编号 + 收件人作为应用关联，不依赖 `common.SendEmail` 每次新生成的
Message-ID 来保证去重。已接受但未写回的重复是用户明确接受的取舍，不承诺 exactly-once。

当前 SMTP 函数没有上下文取消与明确总超时合同。实施须证明 DNS／连接／TLS／认证／DATA
全过程有界，失去任务租约后停止后续分卷。不能通过启动 goroutine 后超时返回却留下后台
发送来伪装取消。若无法零修改现有函数完成，允许新增共用的带 context／deadline 发送入口，
原 `SendEmail` 只保留兼容调用接线，复用认证和安全配置；记录必要性及上游同步冲突范围，
不复制另一套 SMTP 协议实现。

积压处理不得阻塞新窗口生成。建议生成与投递在一次工作内分别有预算，并按收件人公平推进。
吞吐不足时显示最早积压窗口、未发卷数及失败地址数；不通过抽样明细或丢弃历史解决积压。

### 8. 可观察性和失败隔离

复用系统任务页面显示最近运行、待生成窗口、生成失败、待发小时数、待发分卷数、最早积压、
最后 SMTP 接受时间及安全错误原因；邮件设置区给出当前开启状态和下一报告窗口。
这些是报告投递运行状态，不称为网关业务健康状态。

报告生成／投递故障写入自己的系统任务和发送状态，不能再次生成业务错误事件并触发递归
报告。源数据查询失败应明确记录生成失败，不能降级成空列表邮件。若数据源缺失但仍能
生成一份真实的数据不足摘要，必须明确区分该摘要与“完整错误明细报告”，不能标为全量完成。

邮件配置、报告控制状态和投递进度以主库为权威，不使用内存定时器或 Redis 作为唯一进度。
当前站点完全停机时不会产生实时邮件，恢复后才能补发；本功能不替代站外可用性监控。

### 启停和升级语义

- 开启时间以配置事务保存时刻为准，报告始终使用北京时间自然小时。10:59 开启、11:00 后
  执行，仍从 10:00–11:00 开始。
- 关闭后不生成或开始发送新报告。关闭前已完成、但因故障尚未处理的小时保留；关闭时尚未
  完成的小时不加入该段积压。再次开启从开启所在小时恢复，保留已冻结待发邮件。
- `ErrorReportSchedule.periods` 是同一调度行中的 TEXT JSON 启用区间，不新增业务错误源或
  调度框架。已处理的关闭区间在读取下一个窗口时移除。
- 原预发布实现没有启停时间事实。一次性 `migrateErrorReportPeriods` 将当前开启状态的旧
  cursor 转为启用区间，并保留冻结报告；当前已关闭的旧状态不猜测历史关闭时段，后续新生成
  从下次明确开启开始。旧版本未生成的关闭前小时无法完整恢复，不能伪称有完整启停历史。
  迁移后运行时只有一种区间表示，不建立双读路径。
- 配置和调度许可在主库读取，不能用另一节点尚未刷新的内存开关继续发送。已开始的 SMTP
  发送可能在管理员修改配置时完成；修改生效后下一次发送会重新检查。无法撤回已接受邮件。
