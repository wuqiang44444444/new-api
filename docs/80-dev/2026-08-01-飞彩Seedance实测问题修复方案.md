# 飞彩 Seedance 实测问题修复方案

> 实施状态（2026-08-01）：代码、自动化测试、稳定架构文档和本地运行配置均已更新；5 个 SKU
> 已完成严格串行纯文本复测。3 个生成成功并通过平台内容代理下载，2 个由 Provider 明确返回生成失败；
> 图片和参考音频组合仍待真实链路验收。
> 详见[修复后串行实测报告](./2026-08-01-飞彩Seedance修复后串行实测报告.md)。

## 1. 结论

2026-07-31 的首次串行实测证明飞彩渠道能够完成鉴权、模型映射、任务创建、轮询和视频生成，
同时暴露出 `third_party_json_video_omni_reference` 渠道 profile 与飞彩真实响应的差异。本文所列
代码修复已于 2026-08-01 实施；修复后 3 个成功任务已完成创建、轮询和平台内容下载闭环。

首次实测的五个公开 SKU 中：

- `seedance-2.0-standard-720p` 上游生成成功，客户端最终投影为 `succeeded`，但平台内容代理未能
  下载视频；
- 其余四个 SKU 在创建阶段收到飞彩 `502 upstream_service_unavailable`，网关按安全策略记录
  为 `create_outcome_unknown`，没有重发上游 POST；
- 上游生成成功率为 1/5，客户端端到端闭环成功率为 0/5。

问题性质不是同一种：

| 问题 | 定性 | 是否应改变既有安全原则 |
| --- | --- | --- |
| 飞彩返回 `processing`，profile 只接受 `in_progress` | Provider 状态归一化缺陷 | 否，只增加经过验证的精确别名 |
| 完成响应使用顶层 `video_url`，固定 `/content` 不可用 | 原 Provider 内容源假设被实测推翻 | 需要修订显式内容源合同，不能增加静默 fallback |
| 本地把域名解析为 `198.18.1.1` 并被 SSRF 拒绝 | 本地代理/DNS 环境问题 | 否，必须保留 SSRF fail-closed |
| 成功恢复后残留 `fail_reason=upstream_contract_violation` | 共享 Task 状态迁移缺陷 | 否，只在可信恢复迁移中清理临时原因 |
| 四个创建保持 `unknown` | 创建三态的预期安全行为，但对账能力不足 | 否，不得自动重发或凭错误文案推断未创建 |

按接入成熟度区分，本轮可以确认“飞彩渠道适配协议与网关主链路已经接通”，但不能据此宣布“5 个
SKU 已达到正式生产开放标准”：

| 层级 | 当前结论 | 证据或阻塞 |
| --- | --- | --- |
| 协议接入 | 已通过 | 5/5 创建成功；状态、v2 结果 URL、平台代理、Range、幂等和计费主链路均有真实证据 |
| 成功交付 | 部分通过 | 3/5 生成并下载成功；2 个高规格 value SKU 由 Provider 明确返回生成失败 |
| 产品合同 | 未完全闭合 | `generate_audio:false` 仍有 AAC，待 Provider 书面确认 |
| 正式开放 | 未通过 | 继续限制在 `randy` 分组，待高规格 SKU 可用性与 Provider 合同完成灰度验收 |

修复必须继续遵守以下整体设计：

1. 客户端仍是 ModelArk v3，客户端不接触飞彩私有字段或上游任务 ID；
2. 客户端成功响应中的视频地址仍是平台 `/v1/videos/{public_task_id}/content`；
3. 渠道适配协议由显式 profile 和冻结的 adapter version 决定，不按模型名、Base URL 或 Key 猜测；
4. 渠道配置只影响新任务，在途任务继续使用创建时冻结的 profile、adapter version、连接和凭证；
5. 上游结果 URL 不直接暴露给普通用户，完整 URL 和 Bearer Token 不进入普通日志；
6. 创建结果不明确时不换渠道、不重新 POST、不立即退款；
7. 价格键始终是公开 SKU，不使用上游模型名决定售价。

运行中网关的 `/api/pricing` 验证全部返回 `model_price=3`、`quota_type=1`：

- `seedance-2.0-standard-720p`；
- `seedance-2.0-standard-1080p`；
- `seedance-2.0-value-720p`；
- `seedance-2.0-value-1080p`；
- `seedance-2.0-value-4k`。

价格修改只影响之后创建的任务。四个既有 unknown attempt 的计费快照仍为
`held_quota=0`，不能按新价格追溯修改；这符合创建时冻结计费合同的设计。原串行实测报告中的

两个渠道当前只属于 `randy` 分组。代码修复和 5 个 SKU 复测已经完成，但

因此仍保持受控分组灰度，不扩大到正式用户分组。

## 3. 状态 `processing` 的修复

### 3.1 修复前问题

修复前，`relay/channel/task/doubao/thirdparty/jsonvideo/json_video_response.go` 只接受：

```text
queued / in_progress / completed / failed
```

飞彩真实运行中响应使用：

```json
{"status":"processing"}
```

因此正常运行中的任务被 normalizer 返回为 `upstream_contract_violation`，共享轮询服务把 Task
推进到 `RECONCILIATION_REQUIRED`。后续出现 `completed` 时虽然能够恢复成功，但产生了错误的
对账状态和告警。

### 3.2 已实施方案

只在 `third_party_json_video_omni_reference` profile 的 Provider normalizer 中增加经过实测确认的
精确别名：

| 飞彩状态 | Provider 归一化状态 |
| --- | --- |
| `queued` | `queued` |
| `in_progress` | `running` |
| `processing` | `running` |
| `completed` | `succeeded` |
| `failed` | `failed` |

其他空值、未知值、大小写变体继续返回 `UpstreamContractViolation`，不得通过模糊匹配或默认
分支解释为运行中。

这项修改属于 Provider 归一化，不修改 ModelArk Link 公开状态，也不扩散到 official、relay 或
reverse-proxy profile。

`processing` 是对实测状态别名的精确补充，适用于唯一的 v2 合同，不单独触发 adapter version
升级。

## 4. 内容源合同的修复

### 4.1 被实测推翻的假设

原方案把以下地址定义为飞彩 profile 的唯一权威回源地址：

```text
join(<frozen_base_url>, /v1/videos/{escaped_upstream_task_id}/content)
```

实测结果是：

- 完成响应在顶层 `video_url` 返回可下载地址；
- 响应没有原方案预期的 `metadata.url`；
- 固定 `/v1/videos/{id}/content` 返回 HTTP 502，上游内部状态为 400；
- 使用顶层 `video_url` 无 Bearer 直接下载成功；
- 实测 URL 与冻结 Base URL 同源，形式为 `https://feicai123.top/v1/a/...`。

因此不能继续把固定 `/content` 描述为已验证合同。也不能简单实现“固定路径失败后尝试
`video_url`”，因为这会形成两套内容地址权威、两套凭据策略，并使在途行为受网络偶然结果影响。

### 4.2 以 adapter version 作为唯一内容合同键

本次不在 `ChannelOtherSettings`、`relaykit` 或前端渠道表单增加通用
`video_content_source` 字段，也不重构 OpenAI、Sora、Gemini、Vertex 的既有内容代理分支。
稳定架构已经规定 profile/渠道 adapter 是渠道执行唯一合同键。用 adapter version 表达经过验证
的合同，比增加一个可任意组合的渠道维度更小、更明确。

`third_party_json_video_omni_reference` 的唯一内容合同为：

| Adapter version | 地址来源 | Bearer |
| --- | --- | --- |
| `54:third_party_json_video_omni_reference:v2` | `completed` 响应顶层、经校验的 `video_url` | 不发送 |

这里的 v2 不是飞彩模型版本、公开 SKU 版本或客户端 API 版本，而是 new-api 冻结到每个 Task
上的渠道执行合同版本。开发期首次实施时按文档推定定义了“固定 `/content` + Bearer”的本地 v1；
它不是 Provider 或上游 new-api 的版本定义。真实实测随后证明固定端点不可用，飞彩实际使用“顶层
`video_url` + 无 Bearer”。本地数据无需兼容，因此已删除 omni v1 decoder、固定内容地址和
Bearer 回源分支：空版本按唯一 v2 解释，显式 v1 fail closed。

同一 profile 只能存在一个权威内容地址和一套凭据规则；v2 不得在响应 URL 失败后回退固定路径。
如果未来同一请求/查询形状出现第三种经过实测确认的结果或鉴权合同，应新增明确 adapter version
或 profile，不能增加模糊开关或从渠道地址猜测行为。

把 omni 新任务的当前版本切换为 v2 前，必须再次盘点所有使用该 profile 的启用渠道。当前本地
数据库只有两个飞彩渠道使用它；如果上线环境存在不符合 v2 结果合同的其他渠道，就不能全局切换
该 profile，应为不同合同新增明确 profile，避免按供应商名称或渠道 ID 写特例。

### 4.3 版本校验是 v2 上线的阻断性前置（已完成）

修复前，`SouthboundAdapterVersion` 只有写入，没有参与轮询 decoder 或 VideoProxy 的执行分发。
本次已完成版本感知执行路径并把 omni 收敛为唯一 v2 内容合同。

最小实现要求：

1. 在独立文件中提供 adapter version 的权威解析、校验和“新任务当前版本”选择；omni 明确只
   接受 v2，其他 profile 不因本次修复改变版本；
2. 正常创建的 Task、发送前 `TaskCreateAttempt` 和人工恢复模板调用同一版本选择逻辑，禁止分别
   硬编码 `v1`/`v2`；
3. 轮询从 Task 或 recovery snapshot 读取冻结版本，并把它传给 normalizer 和内容代理；
4. v2 始终执行响应 URL 和无 Bearer 合同，不保留固定路径 fallback；
5. omni Task 缺少版本时按唯一 v2 解释；所有新快照必须写入非空版本；
6. 未登记、畸形或 profile 不匹配的版本 fail closed，进入既有合同违例对账，不能默认使用最新
   decoder。

内容源变化同时修改了结果 URL 来源、鉴权和下载规则，符合原适配方案规定的强制升级条件，
因此 v2 是必须项，不保留“把内容源变化视为 v1 纠错”的替代路径。管理员之后修改渠道也不能
改变在途任务冻结的版本、地址或凭据规则。

### 4.4 完成响应校验

v2 合同下，`completed` 只有满足以下条件才能归一化为成功：

- `id` 与预期上游任务 ID 精确一致；
- `video_url` 是非空绝对 HTTPS URL；
- URL 不含 userinfo；
- URL 的规范化 scheme、host 和 port 与冻结 Base URL 同源；
- URL 长度在受控上限内；
- 不把完整 URL 写入普通日志。

缺失、畸形或跨域 URL 返回 `UpstreamContractViolation` 并进入既有
`RECONCILIATION_REQUIRED`，不能静默退回固定 `/content`。如果未来飞彩改用跨域 CDN，应新增
经过安全评审的 adapter version、profile 或受控 origin 配置，不能放宽 v2 的同源含义。

### 4.5 私有保存与平台代理

通过校验的实际 URL 保存到 `Task.private_data.result_url`。普通 ModelArk 查询仍只投影：

```text
/v1/videos/{public_task_id}/content
```

VideoProxy 按唯一 v2 合同使用私有 `result_url`，不附加 Authorization。

内容代理必须保留任务所有权、真人授权回查、Range、安全响应头、60 秒超时和 SSRF
保护。v2 响应 URL 的所有重定向也必须逐跳执行 SSRF 校验。

当前 `redactTaskResponseForLog` 已递归清理 `url` 和 `*_url` 字段，新增实现必须保留该边界；
不得把完整结果 URL 放入 `FailReason`、消费日志或普通告警。

## 5. Fake-IP 与 SSRF

### 5.1 当前问题

本地网络把 `feicai123.top` 解析为 `198.18.1.1`。`198.18.0.0/15` 常被代理软件用作 Fake-IP
地址，网关的 SSRF 防护将其识别为非公网地址并返回 `content_url_not_allowed`。这是正确的
fail-closed 行为，不是 SSRF 校验器缺陷。

### 5.2 处理方式与实施结果

在本地 Clash、sing-box 或等价代理的 Fake-IP 排除/真实 DNS 规则中加入：

```text
feicai123.top
*.feicai123.top
```

验收时应从运行 Go 进程的同一网络环境确认该域名解析为真实公网地址，并再次通过平台内容代理
下载视频。

本机实际提供 Fake-IP 的是 Shadowrocket 网络扩展。已为 `feicai123.top` 增加
`always-real-ip`，重启网络扩展后解析从 `198.18.1.1` 变为 `43.161.227.198`；3 个成功视频
随后均通过平台内容代理返回 HTTP 200，第 1 个视频的 Range 请求返回 HTTP 206。网关 SSRF
策略没有改动。

禁止采用以下办法：

- 关闭全局 SSRF 防护；
- 打开全局私网地址访问；
- 把 `198.18.1.1` 加入允许列表；
- 因为域名属于已知 Provider 就跳过 DNS rebinding 或重定向校验。

## 6. 成功恢复后清理临时失败原因

### 6.1 修复前问题

轮询合同违例会把 Task 写为：

```text
status      = RECONCILIATION_REQUIRED
fail_reason = upstream_contract_violation
```

后续可信 `completed` 响应会把状态更新为 `SUCCESS` 并完成结算，但修复前成功分支没有清除
`FailReason`，最终产生“业务成功但仍带失败原因”的矛盾记录。

### 6.2 已实施方案

只在以下可信恢复迁移中清空临时失败原因：

```text
RECONCILIATION_REQUIRED
  -> QUEUED / IN_PROGRESS / SUCCESS
```

清理必须与状态推进放在同一个 `UpdateWithStatus` CAS 更新中。`FAILURE`、`CANCELLED`、
`EXPIRED`、`PROVIDER_CONTRACT_FAILURE` 等真实终态继续保存各自失败原因。

最小实现可以在共享视频轮询状态迁移处判断旧快照状态和新规范状态；不需要新增数据库列，也不
应在飞彩 adapter 内直接修改 Task。

## 7. 创建结果 unknown 的处理

### 7.1 当前行为是安全边界

飞彩 502 发生在请求已经向 Provider 发送之后。即使错误消息声称“任务未获得有效提交回执”，
仍不能证明 Provider 内部从未创建任务。因此当前行为应保持：

- attempt 转为 `unknown`；
- 保留计费 hold 与幂等 claim；
- 不换渠道；
- 不重新 POST；
- 同幂等键重放返回 `idempotency_in_progress`；
- 截止时间前持续对账，超过期限后释放客户 hold 并记录 exposure。

不能通过匹配中文错误消息把 502 改成确定拒绝。只有飞彩正式、可测试的机器合同明确保证某个
`status + error.code` 表示“请求未被接受且绝不会异步创建任务”时，才可把该精确组合登记为
`terminal_rejection`。

当前没有登记任何飞彩确定拒绝组合。请求字节已经发送后收到的 400、401、403、429、其他 4xx、
5xx、意外 2xx/3xx 或无法解析响应均按 `create_outcome_unknown` 处理；不能仅凭 HTTP 状态释放
hold。以后如取得正式合同，只允许新增精确的 `status + error.code` 分类及回归测试。

### 7.2 已补齐上游 request ID

本次日志已经取得上游 request ID，但四条 unknown attempt 的 `upstream_request_id` 均为空。
修复前 `MarkTaskCreateAttemptOutcomeUnknown` 只推进状态，没有把请求上下文中的上游 request ID
持久化。这会削弱人工查账和未来自动对账。

修复时应在 `sending -> unknown` 的同一次状态转换中写入经过长度和控制字符校验的
`upstream_request_id`。不得只依赖普通日志，也不能把该 ID 暴露给普通用户。

### 7.3 自动对账

如果飞彩提供按 request ID 查询、任务列表或账单查询接口，应在现有共享
`ReconcileTaskCreateAttempts` 调度器中增加 profile 对账能力，不新增供应商专用 worker：

| 对账结果 | 动作 |
| --- | --- |
| 找到可信上游任务 ID | 原子推进 `upstream_succeeded`，使用 recovery snapshot 恢复共享 Task |
| Provider 明确证明未创建 | 原子推进 `rejected`，释放一次 hold，关闭授权 reservation 和幂等 claim |
| 仍不确定或查询暂时失败 | 保持 `unknown`，按退避计划下一次 GET |
| 超过 hold deadline | `released_with_exposure`，释放客户资金并记录 Provider 暴露 |

自动对账只能执行只读查询，绝不能重新发送创建 POST。

当前飞彩尚未提供或确认上述查询合同，因此 Provider 主动查询没有实现。共享调度器目前只负责把
陈旧 `sending` 保守转为 `unknown`、恢复已经取得可信上游任务 ID 的 attempt，以及到期释放 hold
并记录 exposure；“按 request ID 自动找到任务”仍是条件性待办，不能列为已完成能力。

### 7.4 人工处置（已实施）

现有 Root 接口已经支持 Provider 核实成功后补录上游任务 ID 并恢复 Task：

```text
POST /api/task-contract/attempts/{attempt_id}/recover
```

修复前缺少对称的“Provider 已确认未创建”处置入口。本次已新增：

```text
POST /api/task-contract/attempts/{attempt_id}/reject
```

该入口必须：

- 仅 Root；
- 要求 2FA 或 Passkey security proof；
- 要求 `provider_verified=true` 和非空审计备注；
- 只能处理 `unknown + held`；
- 幂等调用 `ReleaseTaskCreateAttemptHold(...Rejected)`；
- 记录操作人、时间、Provider 证据摘要和管理审计；
- 不接受“根据错误文案猜测未创建”。

本次四个 unknown attempt 的 `held_quota=0`，当前没有客户资金风险。若无法从 Provider 获得
可信结论，应让它们按既有 24 小时 deadline 自动进入 `released_with_exposure`，不要直接修改
数据库状态。

| `service/task_polling.go` | 把冻结 adapter version 传入 adapter；可信恢复时清除临时 `FailReason` |
| `relay/channel/task/doubao/video_upstream.go` | 按冻结版本分发 JSON video normalizer，未知版本 fail closed |
| `relay/channel/task/doubao/video_contract.go`、`thirdparty/jsonvideo/` | omni 创建只保留类型化 capability builder；删除不可达的 body 重解析备用路径 |
| `relay/channel/task/doubao/thirdparty/jsonvideo/json_video_response.go` | 支持 `processing`；唯一 v2 decoder 校验顶层 `video_url` |
| `controller/video_json_content.go` | 只接受 v2 并使用私有结果地址 |
| `controller/video_proxy.go` | v2 不附加 Bearer，继续使用 SSRF protected client |
| `service/task_create_attempt.go`、`model/task_create_attempt_release.go` | unknown 转换时持久化 upstream request ID |
| `relay/task_create_disposition.go` | 未取得精确 Provider 机器合同时，所有发送后异常 HTTP 响应 fail closed 为 unknown |
| `router/task-contract-router.go`、`controller/task_contract_operations.go` | 增加经过安全证明的人工确认未创建入口 |

本方案不需要修改 `relaykit`、渠道配置结构或前端渠道表单。如果实施中发现必须改动
`relaykit/`，应先重新论证为何 adapter version 不能表达该合同；确认改动后仍必须执行
`cd relaykit && GOWORK=off go build ./...`。

## 9. 验证要求与结果

以下自动化要求已经落地并通过根模块全量 Go 测试；真实 Provider 验证结果记录在
[修复后串行实测报告](./2026-08-01-飞彩Seedance修复后串行实测报告.md)。

### 9.1 Normalizer

- `processing` 精确归一化为 `running`；
- `in_progress` 继续为 `running`；
- 未知状态和大小写变体继续产生 `UpstreamContractViolation`；
- v2 下合法同源 HTTPS `video_url` 成功；
- 缺失、空白、HTTP、userinfo、跨域、超长 URL 进入对账；
- v2 不得回退固定 `/content`；
- 未登记、畸形或 profile 不匹配的 adapter version fail closed。

### 9.2 冻结与内容代理

- 正常创建、create attempt 和 recovery snapshot 写入同一个权威 adapter version；
- v2 使用 `private_data.result_url` 且不发送 Authorization；
- omni Task 缺少版本时按 v2 解释，显式 v1 fail closed，新任务不得写入空版本；
- public Task 响应始终只返回平台 content URL；
- Range、Content-Type、重定向逐跳 SSRF 和真人授权回查不退化；
- 完整结果 URL、签名参数和 Key 不进入日志。

### 9.3 状态与计费

- `RECONCILIATION_REQUIRED -> QUEUED/IN_PROGRESS/SUCCESS` 原子清空临时 `FailReason`；
- 真实失败、取消和过期仍保存原因；
- 成功只结算一次，重复终态轮询不重复扣费；
- 价格 3 冻结在新 attempt/Task，后续修改价格不改变在途任务。

### 9.4 创建 unknown

- 400、401、403、429、其他未登记 4xx、5xx、网络超时和无效 2xx 创建响应均不重发；
- unknown 原子保存上游 request ID；
- 同幂等键不再次调用 Provider；
- 已取得可信上游任务 ID 后只恢复一次；Provider 主动查询尚未实现；
- 人工 recover/reject 都要求安全证明、Provider 确认和审计备注；
- deadline 到期只释放一次并只记录一条 exposure。

### 9.5 Provider 合同待确认项

- 固化 `processing` 与 `completed + video_url` 的脱敏真实响应样例；
- 确认内容 URL 无 Bearer 下载是稳定合同；
- 确认 `generate_audio:false` 仍产出 AAC 音轨是否为预期行为，并据结论冻结“无音频”产品合同；
- 确认 502 是否存在可机器判定且保证“绝不创建任务”的精确错误合同。
- 确认是否提供按 request ID、任务列表或账单查询的只读接口；确认前不实现 Provider 主动对账。
