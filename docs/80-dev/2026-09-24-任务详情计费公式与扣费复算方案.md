# 任务详情计费公式与扣费复算方案

## 1. 问题与目标

客户在“任务日志 → 查看详情”中需要知道本次费用如何由 Token 或其他计量方式计算得到，能够
按照展示的步骤自行复算，并与实际扣费核对。仅展示金额、用量或原始表达式不能满足该目标。

本文保留 2026-09-24 确认的需求与方案，记录 2026-09-25 的实现与本地验证。任务预扣、终态、
日志读取、详情页面与 Batch 逐行说明已接入；具体接线及验证见第 6 节。真实 Provider 账单和
生产验收尚未完成，不能将本地实现等同于生产已发布。

### 1.1 已确认要求

| 要求 | 验收含义 |
| --- | --- |
| 面向客户自行复算 | 从本次计费依据展示到实际入账金额，不限于管理员诊断 |
| 覆盖全部任务类型 | 视频、异步图片、Batch 及任务日志中的其他类型均纳入 |
| 复杂动态计费也能复算 | 展示真实计算步骤与代入值，不以“动态计费”或“无法展开”代替 |
| 无需复算按钮 | 页面直接呈现已有计算过程，不因查看详情重新结算 |
| 公式及代码可能变化 | 历史说明保留当次过程，不被当前配置或新版计算代码改写 |
| 历史依据不足如实说明 | 保留已扣金额，提示“计费依据未完整记录，无法还原计算过程” |
| 简洁有效 | 复用现有计费入口、快照、事务和恢复机制，不为假设性极端情况增加独立系统 |

### 1.2 范围与依据

本方案调整的是计费说明的记录与读取逻辑，**不迁移、不批量回填、不重算或改写历史任务、日志及
金额**。后文“调整调用入口”只表示修改代码并验证相关调用方，不表示搬迁数据或执行历史补修。
新增记录需要的存储字段在实施时确定；如需增加数据库结构，应单独说明变更并验证三库兼容，不能
把结构变更当作修改历史账务数据的授权。尚未结算的任务仍按原有生命周期和冻结合同正常完成。

展示的是客户费用，不是 Provider 成本。各任务类型继续由原有计费入口负责，解释只是已有事实的
投影，不建立第二套账本、求值器或结算状态机。前端文案只要求简体中文和英文。

权威依据为[硬约束](../00-context/硬约束.md)、
[异步任务与计费事实架构](../20-architecture/账单计费-异步任务与计费事实架构.md)、
[API Key 用量账单架构](../20-architecture/账单计费-APIKEY用量账单架构.md)及
[表达式计费说明](../../pkg/billingexpr/expr.md)。本文不复制为第二套通用合同。

### 2.2 主要计费路径

| 路径 | 现有入口 | 接入时保留的语义 |
| --- | --- | --- |
| 类型化视频 | `service/task_tiered_calculation.go`、`task_tiered_settle.go` | 使用冻结探针和已接受用量；上报 Token 不等于一定按 Token 收费 |
| 原生插件任务 | `service/task_polling.go` | 保留既有用量合并、adapter 调整和结算语义，不套用本地视频状态机 |

部分路径终态不再求值：`task_polling.go` 的按次成功任务保持预扣，`task_billing_state.go` 可以
按冻结预扣完成计费，`image_task_billing.go` 的部分路径直接使用 `HeldQuota`。因此仅在终态

Token 表达式结果需要按百万换算；任务 `u()` 表达式已返回美元金额。展示继续使用各路径冻结的
单位语义，不能根据变量名猜测或重复除以一百万。

### 2.3 需要调整的说明读取逻辑

实施前存在以下调用链（现已移除投影中的重新求值）：

```text
taskBillingOther
→ appendTaskSettlementExpressionFacts
→ ComputeTaskTieredBilling
```

它在生成日志元数据时重新求值，写入档位、条件倍率和用量事实。风险是日志延迟交付或恢复跨越
代码升级后，说明可能偏离原过程；这不是重新扣款，也不表示每次打开详情都会重算。

调整该公共入口可以集中解决这条投影链的问题，但不能代替视频、图片、Batch 和原生插件各自的
过程采集。相关调用方应按实际职责验证：

| 入口 | 回归关注点 |
| --- | --- |
| `service/task_billing_delivery.go` | 已记录过程的正常交付、延迟交付和重复交付 |
| `service/task_billing_state.go` 的 `persistTaskBillingFailure` | 失败诊断日志不伪装为已完成结算 |
| `service/batch_progress.go` 的 `applyBatchSettlement` | Batch 结算汇总与逐行事实一致 |
| `cmd/repair-task-billing-logs/main.go`、`final_log.go` | 核对公共函数调整的调用影响；不运行补修、不追补或回写历史数据 |

## 3. 优化方案

### 3.1 客户看到的计算说明

按实际计费路径展示以下内容，不适用的步骤省略：

1. 结算状态与金额：预扣、待结算、已结算、退款等状态分清，执行成功不等于资金已结算。
2. 计费方式与数量：Token、秒、次、张或其他单位；注明数量来自实测、请求、估算或规则默认值。
3. 条件与价格：本次参数、判断结果、命中档位、单价和附加倍率。
4. 公式代入：展示运算、函数及分支的实际结果，得到各项费用。
5. 最终扣费：按真实顺序展示组倍率、合同折扣、换算和取整，与已入账金额核对。
6. 资金调整：存在预扣、补扣或退款时，解释最终净扣费。

保留足够的计算精度，不用已格式化或截短的金额作为下一步输入。当前显示币种换算与历史定价依据
须区分，不能用当前汇率冒充原结算汇率。

以下仅为虚构价格示例，具体顺序以真实结算为准：

```text
输出用量：120,000 Token；单价：$10 / 百万 Token
加速条件命中：2 倍；组倍率：0.8；合同折扣：0.9

基础费用 = 120,000 ÷ 1,000,000 × $10 = $1.20
加速费用 = $1.20 × 2 = $2.40
分组调整 = $2.40 × 0.8 = $1.92
合同折扣 = $1.92 × 0.9 = $1.728
随后展示实际 quota 换算、取整与入账金额。
```

### 3.2 在实际计算时记录步骤

**预扣和终态计算都要接入。** 初次预扣计算时保存公式、代入值及步骤，并与预扣事实一起持久化。
终态重新计算时记录该次实际过程；终态直接沿用预扣金额时，关联原预扣过程并说明采用原因，不再
求值或复制一份假定的终态公式。沿用估算收费的记录不能被展示成 Provider 实测。

优先验证推广现有 `expr.Patch`：在实际执行的节点插入记录回调，由原引擎完成计算。它是适合
当前代码的候选，不预先声称已覆盖全部合法语法，也不新增前端或离线求值器。

采集内容包括实际变量及单位、条件结果、运算或函数结果、必要中间值和最终值。表达式外的用量
归一化、组倍率、折扣、换算与取整，由原执行位置补齐。代码内公式也记录实际算术过程。

验证重点保持集中：

- 数值类型、运算顺序、短路和异常语义不变，不重复求值；不能把所有运算都包装成浮点回调。
- 未执行分支不强行执行。静态结构可辅助展示，但不能代替实际执行记录。
- trace 状态属于每次运行的 `env`，共享编译缓存不保存客户输入或可变结果。
- 复杂公式仍须完整说明；已有价格展示器返回 `opaque` 不构成新任务豁免理由。

### 3.3 与已有金额事实一致保存

复用各路径已有快照和事务，补充足以展示过程的必要记录；不先建立通用 trace 平台。

- 初次预扣金额与其过程一致提交。先持久化 `TargetQuota` 再扣款的路径，把目标与过程放在同一
  事务接受；直接在资金事务内提交目标的路径，在该事务内保存对应过程。
- Batch 保持先保存逐行事实、再资金汇总的顺序，每行金额与过程一起保存，不合并各路径的结算职责。
- 并发和重试复用已接受的金额与过程，不能将两次计算的结果拼接；采用预扣的终态可引用已有过程。
- 必要过程保存失败时，不能留下可被恢复逻辑独立执行但缺少过程的新目标。沿既有失败与恢复机制
  处理，不触发 Provider 重发或额外扣退；具体接线在各路径实施时验证。
- 已提交资金事实不因页面渲染或日志交付失败而回滚；这些读取与投影操作可按既有机制重试。

### 3.4 调整计费说明读取逻辑，并验证相关调用入口

`appendTaskSettlementExpressionFacts`、`BuildTaskBillingDeliveryLog` 及详情展示，对新增
记录读取当次保存的过程，不再为生成说明调用当前计费代码重新求值。检查第 2.3 节调用方即可，
不为每个调用方新增一层处理框架。

新旧记录判定作为普通持久化细节处理：优先利用既有快照中的版本信息，必要时补一个最小记录标识，
说明对应计费事件应具备过程。不能单凭 trace 缺失就把新记录异常归为历史缺失。默认不新增发布
开关、灰度体系或独立状态机。

上线前已存在的任务可能有旧预扣、但随后产生新结算事件，应分别说明其依据；不补造旧预扣步骤。
既有任务正常完成时可保存实际新产生的过程，这与批量补修历史数据无关。

历史已有的可证明记录继续只读展示；不足时保留实际金额并说明无法完整还原。不为展示重新运行新版
计费代码追补历史，不倒推单价或倍率凑等式，不执行历史任务、日志或账务回填。

### 3.5 公式变化、权限与异常展示

新产生的记录保留当次实际公式及已有表达式版本、变量和单位、分支结果、必要中间值、倍率、换算、
取整与入账结果。只有公式字符串或版本号不够，因为归一化和取整等代码逻辑也会变化。

后续修改配置、公式或计算代码不改变已有过程。新公式在现有合法语法内变化时，步骤随实际执行产生，
不手写前端公式模板；新增计费能力时同步接入说明。不建立第二套计价版本系统或历史代码回放器。

客户只读取自身有权限的任务。采集时处理 `header()`、`param()`、条件文本、异常中的敏感内容，
不把凭据、原始正文、完整签名 URL 或 Provider 私有响应写入 trace。受保护条件展示安全的判断
结果与生效倍率，不能先持久化秘密再靠前端隐藏。

| 情况 | 展示方式 |
| --- | --- |
| 已结算、依据完整 | 展示计算步骤与入账金额，核对一致 |
| 按次计费或保留预扣 | 展示原计算过程及采用原因，不伪造新的实测或终态求值 |
| 预扣中、待用量或待结算 | 明确当前状态，估算不称为最终实际费用 |
| 历史依据不足 | 保留已扣金额和缺失说明，不补算历史 |
| 新记录缺少必要过程或金额不符 | 明确记录异常，沿已有诊断方式核查，不自动凑数或改账 |
| 退款、部分退款或失败收费 | 按具体路径解释净额，不假设全部失败任务都全额退款 |
| 零用量、免费或缺失值 | 分别表达，不把缺失填成零 |

### 3.6 记录体量与保留

先采用紧凑的结构化记录、逐行数值、详情按需加载和分页，不重复保存整段中英文展示文案。
按当前 10,000 行 Batch 上限测量记录大小、写入量、运行内存及读取大小；使用有业务含义的固定
样例。**只有实测表明确有需要时，再增加任务内结构共享、压缩或分块优化。**

若采用结构共享，只共享实际相同的不变公式、常量和步骤结构；每行的变量、分支、中间结果与最终
金额仍独立保留。表达式版本、事实形状和命中分支相同，并不足以证明价格常量和过程相同。
优化必须无损，不能截断或抽样后将新任务降级为无法复算，也不能依赖未来重新执行公式补回步骤。
不引入跨客户全局去重、内容 hash 等价合同或专用存储平台。

计算步骤随所属计费事实管理。上线前确认具体保留期限及与现有日志清理的关系；不默认永久保留，
也不能跟随临时图片输入或缓存清理而丢失仍承诺可查询的账单依据。这是普通存储和运维配置项，
不阻塞编码，不为此新增生命周期系统。

### 6.2 存储与容量

Task/attempt 复用现有私有 JSON 快照，无新增 trace 表。Batch 行新增 `calculation`、
`calculation_version`；`frozen_snapshot` 和行计算记录使用跨库 `BillingText`：MySQL 为 LONGTEXT，

固定 10,000 行合法样例覆盖分档、缓存扣除和合同折扣，每行最终 918 quota：

仅增加实测需要的无损压缩和 MySQL 容量调整，未引入结构共享、全局去重、独立存储或截断降级。

  字符串/对象继续保护其数值派生结果，包括容器提取、局部变量和嵌套迭代。成功与异常返回都在交出
