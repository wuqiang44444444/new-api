# 任务详情计费公式与扣费复算方案

## 1. 问题与目标

客户在“任务日志 → 查看详情”中需要知道本次金额如何由 Token 或其他计量方式计算得到，能够
按照展示的步骤独立复算，并与实际扣费核对。仅展示金额、用量或原始表达式不能满足该目标。

本文记录 2026-09-24 会话确认的需求与只读代码分析结果。方案尚未实施，未完成页面、真实账单
或生产验收；本文不是已发布产品或架构事实。

### 1.1 用户已确认的决定

| 决定 | 验收含义与理由 |
| --- | --- |
| 主要面向客户自行复算实际扣费 | 解释必须从本次计费输入一直到已入账金额，不能只提供管理员诊断字段 |
| 覆盖全部任务类型 | 以最后一次范围确认“全部”为准，包含视频、异步图片、Batch 及任务日志中其他类型，不能只完成视频 |
| 复杂动态计费必须能够复现 | 不能因为表达式复杂而只显示“动态计费”、原始表达式或“无法展开” |
| 展示完整步骤与代入数值即可 | 不需要新增客户点击“复算”的交互入口 |
| 历史记录不足时明确说明 | 保留实际扣费，显示“计费依据未完整记录，无法还原计算过程”，不得使用当前价格补算 |

以上为用户明确确认项。后文的计算解释结构、接线方式与实施顺序为基于代码分析的建议，具体类型、
存储字段和追踪机制需在实施时验证，不代表已取得对应实现或历史数据完整性的证据。

### 1.2 范围与依据

- 展示客户侧模型费用与实际扣费，不把客户金额解释为 Provider 成本。
- 覆盖按 Token、秒、次数、张数、插件声明计量单位及动态表达式等实际存在的计费路径。
- 基于已有任务、快照和资金记录解释费用，不创建第二套账本或修改原有计费语义。
- 只展示该客户有权限访问的任务；不将 Task 私有快照整体返回浏览器。
- 前端及其他新增文案只要求简体中文、英文。

权威约束继续以[硬约束](../00-context/硬约束.md)、
[异步任务与计费事实架构](../20-architecture/账单计费-异步任务与计费事实架构.md)、
[API Key 用量账单架构](../20-architecture/账单计费-APIKEY用量账单架构.md)和
[表达式计费说明](../../pkg/billingexpr/expr.md)为准。本文不另建通用计费合同。

## 2. 当前实际情况

| `web/src/features/usage-logs/components/batch-billing-details.tsx`、`controller/batch_billing.go` | 展示逐行输入、输出、缓存 Token 和 quota | 缺少每条请求的公式与计算步骤 |

| `model/task.go`、`model/task_async_billing.go` | 保存价格、组倍率、表达式、合同及部分实际用量事实 | 各任务路径事实结构不同，不能假设所有历史任务都完整 |
| `pkg/billingexpr/display.go`、`pkg/billingexpr/display_task.go` | 支持已识别表达式形状的价格投影 | 合法但不能证明的结构会成为 `opaque`，不满足复杂公式也须复算的要求 |
| `pkg/billingexpr/types.go`、`pkg/billingexpr/run.go` | 现有引擎求值并记录命中档位、部分请求倍率规则 | 尚无通用的完整逐步求值记录 |

### 2.2 不同任务路径的接入基础

| 路径 | 可复用的权威入口或事实 | 实施时必须保留的区别 |
| --- | --- | --- |
| 本地类型化视频 | `service/task_tiered_calculation.go`、冻结计费探针、已接受实际用量 | 使用当次冻结事实；上报 Token 不等于一定按 Token 收费 |
| 原生插件任务 | `service/task_polling.go`、`BillingSnapshot.UsageFacts`、`UsageUnits` | 原有用量合并、计价与结算语义保持不变，不能套用本地视频状态机 |
| 异步图片 | `service/image_task_billing.go`、图片用量与冻结价格、受保护计费输入 | 图片有独立的输入恢复、用量归一化与结算路径，不能直接调用视频计算函数 |
| Azure Batch | `model/batch_job.go`、`service/batch_pricing.go`、逐行用量事实 | 按行判断档位、应用倍率及取整后汇总，不能合并 Token 后套一次总公式 |

表达式的单位换算也不同：Token 表达式结果按百万换算，任务 `u()` 表达式已经返回美元金额。
解释必须使用创建时冻结的单位合同，不能根据变量名称猜测或重复除以一百万。

### 2.3 尚未验证的事项

- 各任务类型和计费分支的完整覆盖清单，包括非表达式 adapter 调整、失败收费及资金来源差异。
- 历史任务中可可靠恢复单价、用量、请求条件、汇率、换算比例与资金过程的实际占比。
- 复杂表达式逐步追踪在现有编译优化、短路执行和数值类型下的等价实现方式。
- 受保护图片计费输入的可用期限及缺失时的历史可复算范围。
- 线上页面、真实账单、外部数据库和生产行为；本轮未访问生产数据或调用 Provider。

## 3. 优化方案

### 3.1 详情展示顺序

建议在任务详情增加客户可见的“计费明细”，按以下顺序解释；不适用的步骤按真实路径省略。

1. **结算状态与实际金额**：明确已结算、预扣中、待结算或退款状态；执行成功不等于资金已结算。
2. **计费方式与用量**：列出计量单位、数量、来源，以及数量属于实测、请求参数、估算或规则默认值。
3. **计费条件与单价**：列出当次采用的条件值、判断结果、命中档位与相应价格。
4. **代入与中间结果**：将参与本次计算的变量代入，逐步展示算式、函数计算和各项小计。
5. **倍率与折扣**：展示真实适用的附加倍率、组倍率、合同折扣，避免重复计入表达式内部倍率。
6. **换算与入账**：解释实际采用的货币、quota 换算比例、取整位置和结果，最终与已入账记录核对。
7. **预扣与调整**：存在预扣、补扣、退款时，按可证明的资金事实解释最终净扣费。

金额展示保留足够的计算精度，不用已截短的 UI 金额作为下一步输入。若显示币种还需要展示换算，
应区分结算时使用的换算事实与当前展示换算，不能把当前显示设置冒充历史定价依据。

### 3.2 简单公式示例

以下仅为验收说明的虚构数据，不是现行模型价格：

```text
本次输出用量：120,000 Token
命中单价：$10 / 百万 Token
加速条件：命中，倍率为 2
分组倍率：0.8
合同折扣：0.9

基础费用 = 120,000 ÷ 1,000,000 × $10 = $1.20
加速费用 = $1.20 × 2 = $2.40
分组调整 = $2.40 × 0.8 = $1.92
合同折扣 = $1.92 × 0.9 = $1.728
后续逐步展示本次实际 quota 换算、取整和最终入账金额。
```

具体展示顺序必须服从真实结算顺序；该例不规定所有路径都先算美元再取整。

### 3.3 复杂表达式解释

现有价格投影用于识别单价结构，不能承担全部动态表达式的求值过程解释。建议在现有表达式引擎
边界增加可选的计算过程记录，优先由实际结算求值产生；不新增前端求值器或第二套独立计价引擎。

拟记录或投影的最小内容包括：

- 本次使用的表达式版本和参与计费的变量值、单位；缓存等子类剔除后的变量值与原始数量须区分。
- 实际执行的条件判断、命中分支、采用单价和倍率；未执行的短路分支标记未执行，不为了说明强行求值。
- 四则运算、多项费用、`min/max`、`ceil/floor` 等实际调用的输入与结果，以及最终表达式结果。
- 表达式以外的组倍率、合同折扣、quota 换算、取整、最小收费或其他真实生效规则。
- 与已经入账金额的核对结果。

记录必须与既有引擎数值类型、运算顺序和异常语义一致；开启解释前后计算结果及资金行为必须一致。
追踪扩展放在新增文件中，原有热路径仅保留必要接线，不借此重写或收紧原生表达式支持范围。

新任务不能因公式复杂而降级为“无法展开”。所有当前允许用于任务结算的表达式结构都需要进入
覆盖清单；未完成复杂结构的等价解释时，功能不得被宣称为满足本方案。只有历史依据确实缺失时
才适用第 3.5 节的历史说明，而不能把展示器不支持包装为历史数据缺失。

### 3.4 事实来源、持久化与权限

- 首先复用各路径已有冻结快照、实际用量和结算记录，统一的只是客户可见解释结构，不统一或替换
  视频、图片、原生插件与 Batch 各自的结算 owner。
- 新结算需要补充的计算事实应附着于既有结算事实边界，保持幂等；具体存储位置在事实清单完成后
  确定，不预设新通用表。解释是派生证据，不是资金指令或第二权威账本。
- 详情读取不得触发 Provider 查询、任务重发、重新结算或资金调整。允许基于完整历史冻结事实
  使用既有引擎只读还原，但必须先证明输入完整且不依赖当前配置、当前时间或当前汇率。
- 新增 trace 若持久化，必须与对应结算版本和金额一致；并发、重试及恢复不能覆盖成另一轮计算。
  不得因渲染或展示失败改变本应发生的资金处理；必要的计费依据完整性由结算路径本身保障。
- 不回传私有快照、凭据、原始请求正文、完整签名 URL、Provider 原始响应或内部渠道身份。
  条件涉及受保护输入时，只投影计费所需的安全事实或判断结果，并保留金额计算所需的数值。
- 客户只能读取自身有权限访问的任务；沿用现有用户、应用与控制台访问边界，不能由前端隐藏代替
  后端鉴权或脱敏。
- Batch 展示逐行计算与最终汇总；大任务按现有分页思路加载，汇总必须来自完整权威事实，不能把
  当前页合计伪装为整个任务金额。

### 3.5 历史缺失、异常与资金状态

| 情况 | 展示要求 |
| --- | --- |
| 已结算且事实完整 | 展示完整步骤、精确取整结果及已入账金额，核对一致 |
| 历史依据不足 | 展示已扣金额与具体缺失项，明确无法完整复算；不读取当前配置补齐 |
| 解释金额与入账金额不一致 | 保留两者与差异说明，交由既有诊断流程核查；不能反推倍率凑等式或改账 |
| 仅预扣或尚未结算 | 明确预扣或待结算，已有估算步骤标为估算；不能称为最终实际费用 |
| 合同允许保留估算作为最终收费依据 | 明确实际入账金额使用了哪项估算，不能把估算称为 Provider 实测 |
| 退款、部分退款或额外收费 | 根据具体路径解释费用及净额，不能假设所有失败任务都全额退款 |
| 实际零用量、免费与缺失用量 | 分别展示，不能把缺失用量填零或由零值推断免费 |

| 验收维度 | 必须验证的可观察结果 |

## 6. 风险、依赖与剩余证据

- 最大实现风险是追踪对表达式执行语义的影响，尤其编译优化、短路、浮点与整数类型。需要同一表达式
  在追踪启用/关闭时精确一致的回归证据，不能新建另一求值器来规避。
- 历史事实不完整是已接受的展示边界；实际可还原比例仍需抽样，不承诺补齐所有历史记录。
- 权限与计费条件可能冲突：受保护字段不能直接展示，需要设计安全的计费判断投影并验证可复算性。
- 现有不同结算路径的取整、默认用量和失败收费差异必须保留；统一 UI 不构成统一修改账务的授权。
- 本方案落地依赖第 4.1 节的覆盖清单与第 5 节证据；代码存在、自动化通过、真实账单验收和生产发布
  必须分别记录。当前下一步为事实清单与引擎追踪验证，尚未进入业务代码实施。
