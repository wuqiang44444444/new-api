### 历史 writer 证明与解析规则

核对历史提交 `4d46ebb79` 与当前代码的以下分支：

  `input_tokens` 写入 `PromptTokens`，缓存读取、创建另存为输入子项，不能再次加到输入总量。
- `service/text_quota.go` 的普通 OpenAI 分支从输入扣除单独计价的缓存子项；通用
  `cache_creation_tokens` 的存在不证明 Anthropic 语义。
- 同文件 `isLegacyClaudeDerivedOpenAIUsage` 以非 Claude 最终格式、缺少 UsageSource/UsageSemantic、
  非零 5m/1h 创建量辨认旧 Claude 派生分支。历史日志不总能证明全部条件，因此非零 TTL 创建量
  继续未知，不仅凭转换链末端强判 OpenAI。
- `service/log_info_generate.go` 写入完整 request_conversion；首段必须与已知北向路径匹配，所有
  段须为已知格式；末端 writer 决定语义，不仅支持单/双段。最终 Claude 且 claude 标记为真时，
  输入总量累加缓存读写；最终 OpenAI/Responses 且无冲突标记、无歧义 TTL 字段时，输入已含缓存。
- `billing-usage-gemini` 表示明确的 Gemini 规范化证据，三段
  Claude Messages → OpenAI Compatible → Google Gemini 使用该语义。不能仅凭末段 Gemini 猜测。
- 显式总量/语义继续优先；显式字段损坏、输入缓存矛盾、未知格式、本地估算或缺少 writer 证据
  均不通过历史恢复。恢复只改变只读用量解释，不改变已记录费用。

### 附加费验收裁决

历史 writer 的工具价格单位可证明为 USD/1,000 calls；公式包含 count、历史 group ratio、
当时 QuotaPerUnit，并在总费用阶段舍入。日志的 tool_surcharges 仅保存 name/count/price，
不能据此证明完整历史换算与模型/工具分摊。禁止读取今天 QuotaPerUnit 或按整笔费用统一除折扣。
因此继续保留 `auxiliary_charge`，中英文 UI/CSV 明确为“附加费历史换算依据未核实”，不再把它
统一描述为缺少价格或缺少明细。回归锁定有 name/count/price 仍不得制造原价。

### 持款补正清单与其他差异裁决

新 `-hold-plan` 只读扫描已结算且 Task 目标金额一致的任务，按显式 Task 关系和人工退款原日志引用
建立关联。只有唯一钱包 attempt 已完成且持款已转移、唯一零金额初始投影、唯一结算同时证明
pre_consumed_quota/actual_quota、Task 减日志净额等于持款，且身份及元数据无冲突，才列候选。

本快照候选为 **66 笔 / 51,874,820 quota**，均属于用户 91；8 月 5 笔 / 3,667,520 quota，
9 月 61 笔 / 48,207,300 quota。这里只确认可证明的日志投影差额，不把它计作新的钱包消费。

## 优化方案

### 已落地实现与最小入侵

- 历史恢复隔离在 `model/billing_statement_historical_semantic.go`，沿用唯一账单解析入口。
  正式解析版本升至 3，导出字段版本升至 10；旧草稿重新生成，已确认版本保持冻结事实。
- 补正复用 `cmd/repair-task-billing-logs`，新逻辑独立文件；不改原生 Relay、资金或 Provider 路径。
  主库/日志同库 SQLite 专用，不据此声称支持 MySQL/PostgreSQL 离线补正。
- `-hold-plan` 生成新文件（0600），只含行标识、批准金额、摘要及排除项，不输出凭据/Task 私有数据。
  `-hold-apply` 必须使用明确审核文件及其 SHA-256、启用的 Root、核验/客户告知依据、新备份与维护代际。
  禁止混用旧 scope 参数，避免用户以为只改某个 Key 实际应用整个清单。
- 执行在同一个 SQLite 写事务内验证维护屏障、重读全历史证据、比对每笔摘要，只更新批准日志的
  quota 和 admin_info 审计。任意一笔失配全部回滚。审核后修改 Task、attempt、关联日志或添加退款
  将导致证据失配；同一清单再次执行为 0 行。JSON 数值原样保留，不经 float64 重写大整数。
- 原零值诊断状态、用量和其它事实保留，补正不伪装为最终 adjustment，不重复累计最终 Token。
  补正前 quota、补正后 quota、审核依据、操作者、时间及证据摘要写入日志管理员审计区。
- 用户/Key 余额、累计字段、Task、attempt、正式版本和文件保持不变。已确认月必须生成更正版本，
  披露原因与差额，按客户对账约定告知/重新确认；工具不会代替客户确认或自动发布更正版本。
- 前端复用同一个质量说明组件，分别呈现用量可用性、原价优惠估算可用性及具体缺项条数；明确金额
  来自现存扣退款记录，用量完整不表示钱包对账完成。没有新建另一套财务核对状态。
- 维护命令提供脱敏分类错误，区分代际/维护状态、参数/开关、缺控制记录及数据库结构/可用性问题。
  外部 begin 的开关通过既有 SyncOptions 周期传播，默认 60 秒；确认最终权威仍为数据库。
  运维确认各节点已同步即可，不把重启当成必需条件。缓存满时保留完整扫描，不增加额外缓存状态。

### 生产执行边界

代码和副本演练不代表生产已执行。目标库必须先生成自己的清单，在一致性副本复演，确认批准清单、
客户通知/更正流程、备份与恢复方法，再按命令清单进入维护。不能把本地 66 条 ID 或金额直接套到生产。
维护关闭确认不等于停止 Relay；SQLite 补正会持有写锁，须安排低峰维护窗口并确认容量。
最低数据库版本与真实对象存储、目标部署的验证仍按上述边界验收，不声称已经生产可用。
