# 客户账单汇总与调用明细导出区分方案

## 问题与目标

客户需要汇总回答“哪个 API Key、哪个模型花了多少钱、优惠多少”，需要明细回答“每次调用何时发生、
用了多少、如何折扣及入账”。两种导出应在粒度、列顺序、命名与选择说明上直接区分。

## 当前实际情况

已核对本地实现：汇总混合 total、api_key、model、discount_combination 四层行，金额重复出现，
且大量任务、quota 等内部列遮挡客户金额。明细沿用通用使用日志导出，机器字段占主导。
运行中的真实文件未读取，已有固化制品保持不可变。

## 优化方案

- 汇总只输出 API Key × 模型 × 计费方式叶子行，可直接按金额列求和，不混入重复的小计和折扣组合。
  前置 API Key、模型、请求数、币种、净额、估算原价、估算优惠、扣款及退款金额；保留用量、账期和估算原因。
- 明细每行一个入账事件，前置记录时间、请求 ID、API Key、模型、扣款/退款、净额、原价和优惠。
  同一调用的调整或退款通过请求 ID 关联；不将退款当新调用，不伪造缺失关联。随后列出用量、
  历史分组倍率、合同状态/倍率及最终倍率，供客户核验。不导出请求正文或上游私有事实。
- 金额使用冻结币种和换算参数；未知数值为空并附原因，已知零为零，退款为负净额。
  继续使用现有扫描、估算、权限、流式分片与预算边界；仅客户账单明细采用客户列，管理员使用日志保持原格式。
- 表头及主要枚举提供中英文，文件名明确 summary/details；导出选择器补充两种用途说明。
  新格式提升字段版本避免复用旧任务；新固化账单制品共用此格式，已有文件不重写。
- 修改仅限本地账单扩展和现有账单 UI，无原生资金、Relay 热路径或数据库改动。

## 验证与剩余事项

先验证旧实现无法满足单层汇总及选择说明，再检查：汇总金额不重复；明细请求身份、用量、
扣款和退款符号、无合同分组估算、未知与零、中英文、CSV 注入保护、分片及固化制品完整性。
执行定向 Go/Bun 回归、前端类型和 lint、i18n 同步、docs:check 与 ai:check。
未部署、未核验生产账单及外部数据库，不把本地结果表述为线上已更新。


## 实施与验证结果

- 已将汇总改为单层 API Key × 模型 × 计费方式行，移除重复总计、小计及折扣组合。
  金额、请求数优先展示；明细改为客户中英文表头和枚举，保留逐事件请求 ID、用量、历史倍率。
  明细的多分项 JSON 转为可读文字，仍保持每个事件一行与原始 USD 单价基数。
- 两类文件分别命名 `statement-summary.csv`、`statement-details.csv`；后者分片沿用
  `.partN.csv`。线上任务与新固化制品共用格式；版本号升为 8；旧固化文件不改写。
- 下载确认沿用已有 ConfirmDialog、Select，通过现有 children 插槽补充用途说明与状态朗读，
  没有新增通用交互组件。中英文通过 i18n 脚本更新并同步。导出记录将汇总明确标为“账单汇总”。
- 账单 CSV 的账期结束统一显示上海自然月最后一秒，与实际半开区间查询及固化文件一致。
  未改变扫描范围、用户隔离、历史估算、金额换算、资金或数据库结构。
- 修复前回归已复现：单模型汇总生成 4 行重复金额；选择器缺少汇总/明细解释。
  修复后 Go 定向测试通过：`go test ./service -run
  'Test(CustomerStatement|CustomerExport|BillingStatement|ComputeBillingStatement)' -count=1`。
  覆盖真实任务生成及复用、汇总单层金额、逐笔身份、退款负号、无合同倍率、未知与零、中英文、
  CSV 注入保护、分片表头、冻结事实完整性与跨批次导出。
- 前端账单模块 16 个文件、91 个用例通过；`bun run typecheck`、项目配置的改动文件 lint、
  i18n 同步、`task docs:check`、`task ai:check`、`git diff --check` 通过。
  额外尝试的 type-aware lint 因仓库未安装 tsgolint 未运行，随后按项目规定的 oxlint 配置检查通过。

  [账单架构](../20-architecture/账单计费-客户与上游对账架构.md)。本地测试使用 SQLite 与对象存储替身，
  未部署、未读取或修改生产账单，真实对象存储和外部数据库验收仍未完成。
