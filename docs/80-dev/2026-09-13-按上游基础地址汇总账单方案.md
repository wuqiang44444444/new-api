# 按上游基础地址汇总账单方案

## 问题与目标

同一上游供应商可能对应多个渠道，管理员需要通过上游基础 URL 查看这些渠道合并后的计费数据。
已在账单对账页面新增第三个 Tab「按上游 URL 汇总」，保留现有「客户账单」与「上游对账」。

本方案暂将“计费统一”解释为计费数据统一汇总。相同基础 URL 可以作为管理统计的归组依据，但不能
直接证明账号、合同、价格和折扣相同。统一定价、统一折扣及供应商应付金额计算不纳入本次建议范围。

## 实施状态（2026-09-14）

- 第 2 节三个业务口径按本文建议值落地：仅统一汇总、按渠道当前基础 URL 归组并在页面与 CSV 标注、
  协议/非默认端口/基础路径分别归组。
- 代码已实现：`model/billing_reconciliation_url.go`（只读扫描 + URL 归一化 + 三层归组，不物化折扣）、
  `controller/billing_reconciliation_url.go`、`GET /api/billing/admin/upstream-url-summary`、
  前端 `upstream_url` Tab、CSV 导出与七语言文案；Go 与前端测试覆盖归组、隔离、筛选、导出与质量标记。
- 未完成：真实 MySQL/PostgreSQL 与供应商账单的外部验收；正式结算所需的请求时 URL 快照仍是独立的
  后续需求，未实施。

- 管理员账单页面包含客户账单、上游对账与按上游 URL 汇总三个 Tab，Tab 与账期通过页面查询参数表达。

### 当前实施口径

本次按用户授权采用仅统一汇总、按渠道当前基础 URL 归组、协议/非默认端口/基础路径分别归组的口径。

## 优化方案

### 1. 页面与层级

新增管理员 Tab「按上游 URL 汇总」，建议层级如下：

```text
上游基础 URL
  └─ 上游模型 × 计费方式
       └─ 各渠道明细
```

| 层级 | 展示内容 |
| --- | --- |
| URL 汇总 | 基础 URL、渠道数、模型数、请求数、Token 用量、计费次数、数据质量 |
| 模型汇总 | 同一上游模型跨渠道的合计；Token、按次和未知计费方式分行 |
| 渠道明细 | 渠道名称、客户模型与上游模型对应关系、各渠道用量及明细入口 |

支持自然月账期选择、URL 筛选、展开明细和 CSV 导出。沿用现有管理员权限与页面组件；Tab 切换保留
账期，并能通过页面 URL 直接打开新视图。普通用户自助账单不增加供应商信息。

### 2. URL 归组规则

以完整基础 URL 为归组依据，只规范化可明确认为等价的部分：

- 统一域名大小写、默认端口与末尾斜线。
- 保留协议、非默认端口及基础路径；不只按域名合并。编码路径保持编码语义，`%2F` 不作为路径分隔符；
  IPv6 主机保留方括号。
- 不根据渠道名称、模型名称或价格推测供应商。
- 已删除渠道、地址缺失或无法安全识别的地址按渠道单独保留，不能全部并入一个未知供应商。
- URL 中的凭据、查询参数等敏感内容不展示；不能在删掉可能影响身份的部分后直接合并。

| 示例 | 建议处理 |
| --- | --- |
| `https://api.example.com/` 与 `https://API.EXAMPLE.COM:443` | 归为同组 |
| `https://api.example.com/v1` 与 `https://api.example.com/v1/` | 归为同组 |
| `https://api.example.com/v1` 与 `https://api.example.com/v2` | 分别归组 |
| `http://api.example.com` 与 `https://api.example.com` | 分别归组 |
| 两个缺失基础地址的渠道 | 各自保留独立分组 |

URL 分组只服务账单展示，不建立新的供应商身份、路由或履约合同。

### 3. 历史数据口径

第一版建议使用渠道当前配置的基础 URL，并在页面及导出中注明「按渠道当前基础 URL 归组」。
这表示当前渠道归组下的历史用量，不表示请求发生时已经确认的供应商归属。渠道 URL 改动后，历史
账期在此视图中的归组也可能变化，日志中的历史用量和金额本身不因此改变。

如果后续需要用于正式供应商月度结算，应另行增加请求发生时的基础 URL 快照，并贯穿异步任务的
创建与结算。已有历史数据只能根据可靠历史证据恢复；没有证据时保持未知，不用当前配置回写历史。

### 4. 汇总、金额与折扣

- 复用现有平台用量规则，后端完成 URL、模型和渠道各层汇总，前端只负责展示。
- 请求数与按次计费次数分别统计；异步结算调整不重复增加请求数。
- 同 URL 下相同上游模型仍按计费方式分行；模型数只按模型身份计数，不随计费方式增加；
  上游模型身份未知的记录不与已确认模型混并。
- 缺失用量和数据质量标记逐层保留，不能将未知显示为零或将部分数据标成完整；
  总体质量仅累计筛选后分组，空结果的质量计数为零。
- 客户退款不作为供应商用量冲减；客户扣款金额不作为供应商成本。
- 渠道原有折扣事实保留，不自动统一、不取平均、不用当前价格重算历史。
- 模型下合并了多个渠道时，不构造指向单个渠道的伪明细入口；通过真实渠道明细继续下钻。

供应商应付金额计算需要额外明确上游模型价格、币种、折扣和生效时间，不在本次汇总 Tab 中补造。

### 5. 技术实施范围

| 层次 | 拟实施内容 |
| --- | --- |
| 后端聚合 | 在独立的本地对账文件中增加 URL 汇总投影，复用现有用量聚合结果，批量读取必要渠道字段 |
| 管理接口 | 在现有管理员对账路由组下增加 URL 汇总接口，沿用账期校验、响应信封及管理员鉴权 |
| 前端页面 | 新增 Tab、查询参数值、查询及响应类型；复用筛选、表格、展开、加载、错误和空状态组件 |
| 导出 | 导出当前筛选范围的后端汇总数据，包含基础 URL 和归组口径，避免重复加总父行与子行 |
| 国际化 | 新增文案同步覆盖 en、zh、zh-TW、fr、ja、ru、vi |

仅为当前配置归组时不需要新增供应商主表或资金表，也不需要改写历史日志。沿用跨数据库 GORM
查询，不引入数据库专属 JSON 聚合。原生计费、预扣、结算和退款入口不因展示归组发生变化。

### 6. 实施步骤

1. 确认上述业务口径，确定页面列和归组说明。
2. 实现 URL 规范化及后端聚合，覆盖跨渠道归组、模型合并和未知数据场景。
3. 接入管理员接口与第三个 Tab，完成明细展开、筛选、CSV 和七语言文案。
4. 使用脱敏数据比对新视图与原上游渠道汇总，核对总量及质量标记。
5. 完成相关测试、前端检查和文档检查，记录环境与未完成的外部验收。

### 7. 验收标准

- 同基础 URL 的多渠道只形成一个已识别 URL 分组，跨渠道用量不重不漏。
- URL 组总量等于所属渠道总量，模型汇总等于对应渠道模型行之和。
- 域名大小写、默认端口与末尾斜线等价规则通过；不同协议、端口或路径保持隔离。
- 已删除、缺失及敏感地址不误并、不泄漏；缺失用量继续显示未知或未记录。
- 模型身份和计费方式不同的记录不混算，客户退款不误冲减上游用量。
- 账期切换、URL 筛选、加载、错误、空状态、展开与收起均有用户行为测试。
- 页面与 CSV 范围、指标和归组说明一致；无法取得当前范围数据时不能导出旧范围数据。
- 管理员可以查看新 Tab，普通用户不能通过页面或接口读取上游基础 URL。
- 相关 Go 测试、前端测试、类型检查、涉及文件的 lint 和国际化检查通过。
- 文档变更通过 `task docs:check` 与 `task ai:check`；未完成真实外部数据库及供应商账单验证时，
  不宣称已完成生产结算验收。

### 8. 风险与后续事项

相同 URL 仍可能对应不同账号或商业合同，第一版只提供管理归组，不自动赋予统一供应商身份。
当前配置归组不具备历史不可变性；正式供应商结算需要另行评审历史 URL 快照与成本价格事实。
人工供应商映射、多域名合并、统一折扣维护和应付账款管理保留为后续需求，不在本次隐式扩展。
