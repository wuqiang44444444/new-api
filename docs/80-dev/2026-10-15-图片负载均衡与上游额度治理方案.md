# 图片负载均衡与上游额度治理方案

## 问题与目标

用户当前有二十多个 Azure 图片渠道，不同部署的请求限额可能为 8 RPM 或 2 RPM。用户提供的
生产只读分析显示，同一图片编辑请求连续调用两个渠道，均收到 Azure 429，随后重试预算耗尽。
该生产现场由用户提供，本次未访问生产数据库或真实 Provider 复核。

本方案规划图片请求的上游容量调度与本地 CPU 开销治理。前者在既有授权、分组、合同、渠道与
协议约束内，减少容量分配不均、瞬时突发和无效重试造成的上游 429；后者减少图片响应与证据
处理中的重复计算，缓解本地 CPU 自保 503。两类问题分别归因和验收，不能互相替代。
超过真实容量的需求应获得明确拒绝或受控等待，不能承诺消除所有 Provider 429 或本地 503。

本文件为待实施方案。本次只编写文档，不实施负载均衡、不修改生产配置、不部署、不调用付费
Provider。此前的[原生错误事件修复](2026-10-15-原生错误事件渠道与分类修复方案.md)只补诊断，
不表示本文调度能力已经实现。

### 范围

- 首批接入原生同步 `/v1/images/generations` 与 `/v1/images/edits`，同时覆盖 JSON、multipart
  和既有流式响应；首批真实 Provider 验收以 Azure 为目标，底座不按 Azure 名称写死。
- 只为显式配置的图片额度启用保护；文字、Embedding、音频、Realtime 与 Responses 不参与本批
  调度，不依模型名称或计费价格推断图片身份。
- 同一真实配额单元存在平台异步图片、渠道测试等其他调用源时，必须清点并共享调用额度，或在
  上线前明确隔离和预留容量。异步接入另设阶段，不把同步接入写成全路径覆盖。
- Seedance、MiniMax、Azure Batch 等类型化入口及既有 Task 的渠道、协议、连接和资金事实保持
  原合同；图片调度不能赋予它们随机分发、跨渠道重试或 fallback。

### 外部证据与未确认项

Azure 官方说明：RPM 可能按较短窗口评估；429 可携带 `retry-after-ms`；失败请求也可能计入
限额；文字 Token 限流估算与账单实际 Token 并不相同。因此“按次收费”不能直接等价为
“上游只按请求次数限流”。见 [Azure 配额与限流说明](https://learn.microsoft.com/en-us/azure/foundry/openai/how-to/quota#understanding-rate-limits)。

实施前需要确认每个目标部署的真实限额单位、窗口、共享范围、响应头及是否还有 Token 限制。
图片请求若还受 TPM 限制，本批请求数控制只能提供部分保护，不能标记为完整额度治理。
本次未进行真实 Provider 限额、账单或并发上限验证。

| sar 窗口用户态为主，报告估计增量约 350 CPU 秒 | 支持整机用户态计算显著；增量依赖基线与窗口口径 | 全部增量属于网关、AES 或图片重编码 |
| 仅有 cgroup 九小时平均约 0.47 核，无进程级历史或 profile | 长窗口累计使用可作背景 | 据此证明压测几分钟内网关是主要消耗方 |

当前 [CPU 自保判断](../../middleware/performance.go) 是 `int(status.CPUUsage) > threshold`，
阈值 95 时须到 96% 才满足表达式，不能写成严格的“≥95%”。
[系统监控](../../common/system_monitor.go)约每五秒更新缓存，读取两次采样之间的使用率；
实际调度间隔不保证恰好五秒，也没有固定二十秒拒绝冷却期。生产是否同实现以 `v47` 为准。

已有 sar、访问日志、任务执行记录、证据事件及对象大小应按同一时区对齐，保留原始分辨率。
十分钟 sar 不能插值为十秒 CPU 峰值。若存在本次自动生成的 `pprof/cpu-*.pprof`，可离线分析；
若当时未采集，事后开启不能恢复本次热点。无需等待未来 profile 才能识别源码中的重复工作，
但不能据此填写其生产 CPU 百分比。

#### 代码确认：每份证据包含重复解析和脱敏

通用采集路径使用 `allRequests=true`，上游响应和客户交付分别捕获正文。每个事件的主要链路
如下；任务专属证据路径可能不同，不把通用路径全部步骤套用到每个媒体任务：

```text
ImageErrorEvidence.Finish
  -> persistAPIRequestEvidence
     -> 复制正文
     -> evidenceRedactBody：校验并完整脱敏，结果被丢弃
     -> persistTaskEvidenceBodyUsing
        -> 事件预留、关闭状态检查
        -> redactObservedBody
           -> evidenceRedactBody：再次校验、递归脱敏与 JSON 重组
           -> 整包 URL 扫描
           -> JSON 字符串逐项解码、URL/凭据扫描与重新编码
        -> AES-GCM -> 文件写入/同步 -> 事务保护下发布 -> 父目录同步
        -> SHA256、事件完成更新
```

1. [persistAPIRequestEvidence](../../service/api_request_evidence.go) 为设置 `formatInvalid`
   调用完整脱敏，丢弃结果；持久化时 [redactObservedBody](../../service/api_request_evidence_redaction.go)
   又调用一次。重复工作可直接确认；优化须保留原始格式错误标记、非法/截断正文脱敏与失败语义。
2. [evidenceRedactJSON](../../service/task_request_evidence_redaction.go) 对对象和数组逐层
   Unmarshal/Marshal。根对象、`data` 数组、图片对象均携带大段 Base64，`RawMessage` 不代表
   全流程零复制。扫描、分配和复制量高于最终落盘量，精确倍数未测量。
3. [通用字符串处理](../../service/api_request_evidence_redaction.go)对全部 JSON 字符串执行
   正则匹配、解码、URL/凭据扫描、重新编码，`b64_json` 也进入该流程。应减少重复遍历和相同
   凭据的重复检查，不能仅因字段很大而跳过脱敏、转义和截断保护。

优先嫌疑是大 JSON 的重复扫描、重组、字符串处理及分配，不应仅凭“AES×2、SHA”认定加密是
主要热点。常驻内存低不能排除短命大对象的 GC 成本；本次没有函数占比或累计分配量实测。

#### 代码确认：同步持久化与收尾工作重叠

[事件持久化](../../service/task_request_evidence_persist.go)及
[证据存储](../../service/task_request_evidence_store.go)除 AES/SHA 外，还包含数据库事件
预留、关闭检查、文件 `fsync`、对象发布事务、逐层父目录同步和事件更新。AES 在取得文件写入
槽位之前执行，写入并发限制不等于前置脱敏、复制和加密并发限制。

0.3–2 秒 wall time 包含执行、等待调度、数据库和存储等待。不能用“2 秒/张 × 1.9 张/秒 =
3.8 核”证明 CPU 成本；整机用户态占比高也不等于每个请求都不存在等待。

当前 [main.go](../../main.go)先注册通用证据中间件，后注册
[GIN 日志](../../middleware/logger.go)。通用证据在 `c.Next()` 返回后直接同步持久化，
不使用旧图片错误证据路径的后台队列。其时序为：

```text
外层证据中间件进入
  -> GIN 日志计时
     -> 图片处理与响应写出
  -> GIN 记录耗时
  -> 外层证据解析、脱敏、加密与持久化
```

图片可能已经写出、GIN 已记录耗时，而原请求 goroutine 仍在消耗资源，客户端 worker 也可能
已发出下一请求。该重叠机制与本次集中完成后自保的现象相容，但尚非历史 CPU 贡献拆分。
不能用 GIN 耗时减上游耗时当作全部本地成本；文件修改或事件创建时间也不天然等于计算起止。

当前通用观察器位于 CPU 自保之前，开启时也观察图片本地拒绝；线上“503 无证据目录”不能
直接由当前默认调用链解释。应离线核对 `v47` 接线、采集条件和分支，核清前不宣称上述全部
步骤已在生产执行。二进制内含函数符号只证明代码编入，不证明本次请求调用过。

#### 图片交付、像素处理及 Blob 边界

- [OpenaiImageHandler](../../relay/channel/openai/relay_image.go) 普通同步路径读取响应、
  解析错误/usage、统计图片数并写出，没有 PNG/JPEG 解码重编码或 C2PA 处理。
  [GPT Image 元数据投影](../../pkg/publicmodel/image_native_gpt.go)不处理像素；异步 adapter
  和 worker 仅在实际请求进入其模式时计入成本。PNG/JPEG 符号不能指认 Azure 路径。
- [Gemini 尺寸转换](../../relay/channel/gemini/image_pixels.go)只在适用路径、请求精确尺寸
  且上游像素不匹配时解码、等比例缩放与重编码，不是普通 Azure 的共同步骤。
- [图片交付层](../../relay/image_delivery.go)由非流式请求显式非空 `response_format` 触发。
  即使上下游均为 `b64_json`，[prepare](../../relay/image_delivery_convert.go)仍扫描 JSON，
  构造 `data` 临时文件及完整输出文件；[区间解析](../../relay/image_delivery_json.go)逐字节
  扫描，[临时写入](../../relay/image_delivery_spool.go)还包含全局锁和磁盘余量检查。这不是
  像素重编码。本次请求未设置该字段或未经过该实现时，不计入本次归因。
- [task_request_evidence_delivery.go](../../service/task_request_evidence_delivery.go)记录
  客户响应，不代表证据上传 Azure Blob。通用图片对象存储与证据存储是不同链路；未确认生产
  接线和执行记录前，不把“delivery”符号或 Blob SDK 编入解释为存在上传任务。

#### 业务必要性

| 能力 | 业务价值与必要边界 | 可优化方向 |
| --- | --- | --- |
| 错误、usage、实际图片数及资金结算 | 履约和计费必需 | 保留合同，减少大响应重复处理 |
| 上游响应事件与客户交付事件 | 分别证明供应商返回内容、平台实际写出内容及完整性 | 保留两个阶段，正文共享须实际证明相同 |
| 已显式开启的完整证据正文 | 客诉与排障依据，现合同要求保存登记内容 | 先减少计算；采样、仅失败或少存正文属于策略变更 |
| 异步必要输入、结果与资金状态 | 已受理任务恢复和交付所需 | 与可选证据分开，不能作为冗余证据删除 |
| URL/Base64 转换 | 客户明确请求且已发布时必须履约 | 格式一致优先直接交付，实际不匹配才转换 |
| 渠道测试完整响应 dump | 可用性判断一般不需要整包图片 | 改为状态、耗时、usage、字节数及脱敏错误摘要 |

本次结论为：图片集中完成触发 CPU 自保；用户报告确认大响应证据双份持久化；当前代码又确认
重复解析、脱敏及同步存储成本，应优先治理。尚不能给出函数 CPU 百分比、单图 CPU 秒、优化
降幅或扩容后的容量保证，也没有证据证明 Azure 路径发生像素重编码。

## 优化方案

### 1. 用真实配额单元描述容量

新增图片额度配置，以主数据库保存配置事实，进程缓存只做投影。建议独立模型和附加配置接口，
不扩写原生 Channel 的大量字段；配置及迁移同时支持 SQLite、MySQL、PostgreSQL。

| 配置 | 含义 |
| --- | --- |
| 配额单元 ID | 内部稳定、不含凭据的标识，描述 Provider 真正共享额度的边界 |
| 渠道绑定 | 指定渠道、明确映射后的部署/上游模型及必要操作范围；不同客户模型别名可共享同一单元 |
| Key 作用域 | 只有证据证明按 Key 独立限流时才区分；同一部署的多个 Key 默认不推导多份容量 |
| 限额单位 | `requests` 或经验证的 `images`；按图片数时以最终发送数量计量 |
| 窗口与额度 | 如每 60 秒 2 次、8 次；允许配置更短窗口约束 |
| 突发容忍 | 显式配置瞬时突发上限；低额度 Azure 首批建议保守平滑，真实验收后调整 |
| 最大并发 | 可选，描述允许同时占用的生成调用，与 RPM 独立 |
| 启用状态 | 未配置、关闭、观察或执行；观察模式不阻止发送，也不能宣称已保护 |

绑定来自明确配置与现有模型映射，不按客户模型名称、地区字符串、价格、Key 个数或 URL 相似度
猜测。生成与编辑只有在证实额度独立时才拆分计数；需要同时满足账号共享额度与部署额度时，
一次发送必须同时获取所有适用额度，不能复制出两份独立容量。

配置涉及多 Key 且 Key 额度独立时，首批必须完成精确绑定和可用 Key 选择；若尚不能覆盖，保存
时明确拒绝该配置形状，不静默使用通道级限额代替。Key 轮换不得产生新的配额单元重置额度。

### 2. 发送前原子获取额度与并发占用

```text
既有授权、合同、分组、固定渠道与会话规则
  -> 既有规则内的图片候选与权重选择
  -> 检查冷却、额度和并发可用性
  -> 完成南向构造与最终数量校验
  -> 原子取得实际发送许可
  -> 调用 Provider
  -> 读取原始响应与限流反馈
  -> 响应读取结束后释放本地并发占用
```

候选检查仅为提示，最终发送许可必须原子取得，防止多个实例同时认为还剩一个名额。候选检查
不扣额度；并发竞争失败后只在合法候选内有界重选，不发送“试试看”的请求。

建议使用 Redis 原子脚本实现跨实例调用额度与同步并发占用。滚动窗口请求计数配合可配置的
最小间隔/突发约束，避免固定整分钟窗口边界出现双倍突发。2 RPM 平均间隔 30 秒、8 RPM 平均
间隔 7.5 秒只是本地平滑参考，不等价于对 Azure 实际算法的保证。

- 一个许可唯一对应一次实际调用；同时涉及多个计数和并发时，原子完成全部获取或全部不获取。
  Redis Cluster 部署需验证相关键可在同一脚本原子操作，不用串行多次扣减冒充整体原子。
- 获取点放在请求构造、参数校验等可确定本地失败之后，发送之前；不能在客户端上传开始就消耗
  Provider 调用额度，也不能在原生多条路径各扣一次。
- 在能够证明尚未发送时取消许可；已发出或无法证明未发出时，不因 429、超时、退款而回补请求
  额度。并发释放与请求额度过期是两件独立的事。
- 并发占用保持到上游响应读取结束或本地连接结束，覆盖流式图片；HTTP 响应头到达不算完成。
  并发约束首先描述平台正在执行的调用，断线后 Provider 是否仍执行必须保持未知。
- 使用可续期、带唯一持有者的同步并发租约，保证正常释放幂等；超时和实例崩溃后租约的回收策略
  必须结合 Provider 执行上界验收，不把租约到期当作 Provider 已停止的证据。
- 单实例无 Redis 可以显式使用进程内实现；多实例执行模式依赖共享存储，不能静默降为各自计数。
  已启用保护但共享存储不可用时，拒绝新受保护调用并返回服务不可用，不能伪造上游 429。
- Redis 数据丢失/重建不能立即恢复全部额度。按所配置窗口进入保守恢复期；并发事实无法恢复时
  按运维恢复策略处理。此状态不是 Task、资金或资源的耐久事实源。

### 3. 保留既有选择规则，增加容量可用性

首批保留层内权重随机作为偏好，只在当前原生策略允许的优先级、分组和候选范围内跳过临时
不可用配额单元。容量层不能扩展合同授权、改变模型映射、越过固定渠道或严格会话绑定。

单候选、固定渠道和会话命中也必须经过发送准入；受约束渠道不可用时明确拒绝，不能偷偷换渠。
本地额度不足与真实调用失败分别记账：候选扫描不消耗实际调用预算，但扫描次数必须有界。

同一请求维护已扫描候选与已真实调用配额单元，避免重复抽中同一不可用目标造成循环。新增单调
递增的实际调用计数与总截止时间，不能仅依赖 auto 分组可能重置的重试索引限制放大量。

8 RPM 与 2 RPM 的独立同层部署可按容量比例设置权重，但权重不是硬限额。实现前需明确处理
内存/数据库权重差异并分别验证；不得将权重 0 当作跨模式一致的停用开关。

“同层全部用尽再降到下一优先级”属于后续显式策略评审项，首批不借容量过滤暗改优先级含义。
后续如按并发比例或耗时做动态分配，仍以同一个原生资格与优先级实现为权威。

### 4. 429 反馈与重试

- 在状态映射前读取原始上游状态、Provider 已登记错误码和有效限流头；客户响应映射保持原行为。
- 按 Provider 代码解释 `retry-after-ms`、标准 `Retry-After` 秒数/日期及已验证重置字段，不把
  所有 Provider 的同名字段单位当成相同。不按错误正文正则猜测额度和等待秒数。
- 明确的临时频率限制更新其实际配额单元冷却截止时间；并发更新保留较晚截止时间，避免旧响应
  提前解禁。缺少可信等待信息时，使用有上限的退避与随机抖动。
- 有效 Provider 等待期限不得被本地退避上限缩短；期限超出客户请求剩余时间时结束本次请求，
  而不是提前重试。乱序响应中的剩余额度只能按对应窗口保守校准，不能覆盖本地已占用名额。
- 额度耗尽、临时容量压力、凭据/账户额度问题按已验证协议分类；未知 429 采取保守临时冷却和
  诊断，不自动增加永久禁用或跨渠道重发资格。
- 明确限流拒绝且原生规则允许安全重试时，排除本次已失败配额单元，再从允许的候选中取得许可。
  不能只排除 Channel ID，让同一部署的另一条渠道或 Key 继续撞限流。
- 网络错误、5xx、上传后断线、输出读取失败及异步 `unknown`，不能统一推断为“未生成”；本批
  不扩大原有自动重发范围。已开始向客户交付图片流时不切换渠道或拼接另一条响应。
- 临时冷却与管理员停用分离，冷却到期按额度重新准入，不无界放行积压请求。

### 5. 容量耗尽与资金时序

首批不增加同步长队列。合法候选均因额度、冷却或并发暂不可用时，返回可解释的本地 429，带
可估计的 `Retry-After`；无资格候选、Provider 拒绝及共享存储不可用保持各自不同错误原因。
若仅因并发满且无法可靠估计释放时间，不伪造精确等待时间。

当前原生初始预扣发生在重试循环前，首批本地拒绝必须通过既有最终失败退款路径结束，不重复
预扣或漏退；重试成功只结算一次。不能宣称所有容量检查天然都在预扣前。

短暂、有界等待作为后续可选阶段：明确队列长度、请求截止时间、公平性、取消与预扣时序后再
实施；等待 RPM 时不得先长期占住并发槽位。不能自动将同步请求改为 202 或另建图片 Task 体系。

### 6. 同步以外的额度消费者

| 来源 | 接入要求 |
| --- | --- |
| 图片渠道测试 | 每个真实生成调用也占 Provider 额度；管理操作不默认绕过 |
| 平台显式异步图片 | 复用同一请求额度与冷却；继续使用现有 Task 执行槽位，不新增平行 Task 状态 |
| 异步任务查询/轮询 | 仅在 Provider 证实与生成共享限额时绑定，不能每次轮询都按生成额度计数 |
| 同部署的外部程序 | 清点、隔离或保留额度余量；网关无法原子约束外部调用 |

异步 worker 获取调用额度必须在既有 durable 发送许可提交之前完成；未取得额度时继续遵循
原有队列、租约和期限机制，不得提前标记已发送。两类存储无法同事务时，允许保守损失短期请求
额度，不允许在没有 durable 许可时发送。发送许可与平台任务行为的改动必须独立验证。

异步任务按冻结渠道和连接执行，不参加新的随机选渠、换渠道重试或结果未知重发。接入共享
配额所需的稳定引用及历史任务处理要在该阶段确定，不能根据当前 Channel 新配置重解释旧任务。

若首批只覆盖同步调用，上线仅允许使用已隔离或已明确预留预算的配额单元；与未接入的异步/
测试调用共享全部额度的部署不能标记为完整保护，也不能纳入“严格不超过配置额度”的验收。

### 7. 可观测性

复用 `request_policy` 决策链与既有错误事件，不建立第二份请求状态。新增决策字段需标明本地
容量拒绝、冷却跳过、实际调用和 Provider 拒绝，保留客户模型与最后一次真实尝试归属。

管理员诊断记录配额单元内部 ID、限制维度、等待估计、真实调用序号和重选原因，不记录凭据、
原始输入、完整签名 URL 或 Provider 原始正文；客户响应不暴露内部部署及渠道信息。

最少观察：每单元实际调用率、上游 429 比例、本地拒绝数、冷却命中数、并发占用、最终成功率、
请求耗时，以及“实际调用数 / 客户请求数”的重试放大。最终错误事件与逐次失败日志不能混用
为同一个失败率。健康惩罚不使用客户参数错误、审核拒绝或客户主动断连替代 Provider 容量故障。

### 8. 本地 CPU 与大响应证据治理

本项与上游额度治理独立，可先处理已确认的重复工作，不等待再次生产压测或先实施 Redis 容量
调度。先以 `v47` 对应代码与本次历史脱敏元数据核定适用路径，再按单一根因分步实施。

| 顺序 | 拟采取动作 | 验收与限制 |
| --- | --- | --- |
| 1 | 合并证据格式检查与脱敏并复用结果；减少重复 JSON 重组、复制及字符串扫描 | 保留凭据、转义、截断、原始格式错误标记和失败语义，不跳过安全处理 |
| 2 | 格式一致时避免重建整个图片响应，保留实际需要的 URL/Base64 转换 | 保留未知字段、结果顺序、usage、图片数及生成后交付失败的结算/不重发边界 |
| 3 | 删除渠道测试完整响应 dump，采用有界脱敏摘要；复核同步存储次数 | 本次测试任务未重合，不把此日志修改宣传成本次 503 根因修复；不任意取消 fsync 或发布事务 |
| 后续评审 | 同请求两个阶段的脱敏正文确实相同时，共享一个受保护对象 | 两个事件分别保留时间、状态、实际字节数、EOF/截断与错误；整体设计对象授权、完整性、过期和清理 |
| 后续业务决策 | 成功采样、仅失败全文或调整正文保留政策 | 明确排障证据损失并同步合同与界面，不隐式少存正文 |

当前对象键按事件 ID 派生，清理按事件和文件归属回收；共享正文不是简单删除第二个文件。
只在同一请求的受保护范围内评审，不引入跨用户/应用的全局去重、第二套资源事实或历史双读。
发生转换、客户断连或无法证明正文相同时，分别记录实际观测，不能用一次成功冒充两阶段成功。
正文共享是否减少 CPU 取决于是否避免重复处理，不能从落盘减半推导计算减半。

压缩不作为 CPU 优化首选：它增加计算，主要节省存储；后续若有存储收益依据，应在加密前执行
并验收读取生命周期，不压缩密文，也不重编码图片、删除 C2PA 或改变交付质量。单纯把证据移到
后台主要改变延迟和峰值，不等于减少总 CPU；新增队列还涉及有界容量、退出丢失及持久性，
首批不借性能优化改变证据可靠性合同。

进程 CPU 用于归因，自保策略另行评审；只看网关进程会遗漏宿主机或数据库饱和。提高阈值、
短队列或客户端限速改变准入/节奏，不减少单图处理成本；不承诺 ≤1 张/秒零 503，不自动把同步
请求改为异步或重发已生成图片。

优先修改本地新增的证据与交付文件，不重构原生 OpenAI handler、计费及通用分发。确需修改
`controller/channel-test.go` 的正文日志，只替换必要日志点并记录原生文件修改必要性与上游
同步冲突面；不为本项更换全局 JSON 引擎或增加无依据 fallback。

- `relay/image_handler.go` 提供图片身份、最终数量及响应结束生命周期的窄接线，不重写 DTO、

- `relay/channel/api_request.go` 在实际发送与原始响应位置作受图片标记约束的窄接线，必须证明
  文字、音频、Realtime 不进入新策略；JSON 与 multipart 只获取一次许可。
- `controller/relay.go` / `service/relay_error.go` 如需接线，仅承载图片本地容量结果、请求预算和
  安全重试决策，主体放新增文件，不顺带改通用重试策略。
- 异步阶段在 `relay/image_native_executor.go`、`service/image_task_worker.go` 的真实发送许可

每处原生文件修改必须记录必要性、最小接线点与上游同步影响。若无法保留窄接线，应先调整实现
方案，不能用“通用化”扩大原生冲突面。配置发布、禁用与滚动升级期间保留已在执行调用的占用，
调低额度不重置计数；关闭保护也不能触发重发、退款或 Task 状态变更。

## 验证与验收

### 确定性回归与本地实际 HTTP

使用可控时钟、隔离数据库、共享 Redis 与本地模拟 Provider 验证；不使用真实付费 Provider
制造超限，也不以随机压测、长时间 sleep 或实现细节断言替代业务验收。

| 场景 | 必须观察到的结果 |
| --- | --- |
| 8 RPM 与 2 RPM 混合候选 | 固定输入序列中每个单元符合窗口/突发约束；不会因等权随机把 2 RPM 单元打穿 |
| 窗口边界、短时突发 | 不因整分钟切换绕过窗口约束；平滑策略有明确最早发送时间 |
| 两个网关实例竞争一个名额 | 只有一个取得发送许可；模拟 Provider 记录与共享计数一致 |
| 多渠道/多 Key 指向相同部署 | 共享额度与冷却；轮换凭据不恢复名额 |
| JSON 生成、JSON 编辑与 multipart 编辑 | 同等保护，每次实际调用恰好一次计数 |
| 最终 `n` 与客户原值不同 | 计数使用校验后的南向数量；不拆请求、不改数量、不绕过 `dto.MaxImageN` |
| RPM 有余但并发已满；流式图片 | 不继续生成；HTTP 头或流首帧到达不提前释放占用 |
| 429 带等待头、缺失头或状态映射 | 读取真实状态，按对应协议冷却；映射不影响冷却，不伪造永久停用 |
| 本地构造失败、候选竞争失败 | 不产生 Provider 调用；未发出的许可按约定取消，无失控扫描 |
| 重试、auto 分组和预算 | 已失败配额单元被排除；实际调用总预算单调，不被重试索引重置绕过 |
| 单候选、固定渠道、严格会话、合同 | 不绕过容量保护，也不越权换渠；无候选与暂时没容量错误可区分 |
| 全部冷却/无额度、Redis 故障或重建 | 明确本地拒绝/服务不可用，合理等待提示；无静默多实例放行 |
| 断线、5xx、响应丢失及已输出图片流 | 不新增未知结果自动重发，不混接另一条输出 |
| 失败、重试成功与取消 | 既有预扣/退款/结算幂等，无重复扣费、漏退或失败事件归属污染 |
| 文字、Embedding、音频和 Link 请求 | 不进入本批图片策略，既有路由与状态合同不变 |
| 异步阶段与共享调用源 | 先额度后 durable 发送许可；固定渠道不变；unknown 不重发；原有任务槽位可重建 |
| 证据去重复处理；JSON、multipart、SSE、非法与截断正文 | 凭据不保存，转义不绕过脱敏，原始格式错误与完整性保留；错误归属及清理关闭语义不变 |
| 同格式交付及必要的 URL/Base64 转换 | 图片字节、未知字段、顺序、usage 与数量保持；存储/交付失败不重新生成、重复扣费或错误退款 |
| 后续正文共享与客户断连 | 两阶段观测独立，不同正文不合并；授权、完整性、过期与并发清理不产生悬空引用 |

对涉及配置/数据库的实现执行 SQLite、MySQL、PostgreSQL 实际验收；Redis 单节点及实际生产所用
部署形态分别验证。不把模拟 Provider 通过写为真实 Azure 验收。

本地 CPU 优化使用固定结构和大小的非敏感响应做离线成本测量，结合既有证据边界回归记录
CPU 时间、累计分配和持久化耗时。性能测量不作为有波动的测试通过阈值，不新增随机压力、
睡眠或仅证明代码运行的测试。离线结果只解释相应代码成本，不冒充本次历史函数 profile。
