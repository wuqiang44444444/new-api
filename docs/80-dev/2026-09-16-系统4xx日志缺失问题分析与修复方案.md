# API 鉴权后 4xx 日志缺失问题分析与修复方案

## 问题与目标

用户反馈创建素材返回 `400 invalid_request` 或 `422 unsupported_asset_type` 时，系统日志和数据库
缺少能够解释原因的记录。本方案最终范围明确为：**所有 API 请求在正式鉴权入口成功放行之后，
实际返回给调用方的全部 4xx 错误**。素材接口保留为已确认的诊断缺失案例，不能把覆盖范围缩为 asset。

这里的“已鉴权”以该 API 的现有鉴权规则执行成功并放行后续处理为准，不等同于携带 API Key、
Token 可查到、上下文已有用户 ID，也不要求参数验证、模型权限、业务执行已经成功。
“全部 4xx”使用 `400 <= status < 500` 判断，不限于参数验证产生的 400/422。

目标：每个满足“API 已鉴权 + 最终为 4xx”的请求恰好产生一条可按 `request_id` 查询的统一诊断，
保留已知业务阶段和安全原因。鉴权成功之后的参数错误、模型权限拒绝、资源不存在、业务冲突和限流
均应记录。匿名请求、鉴权失败、鉴权前限流、未经过 API 鉴权的路由扫描和静态资源错误不进入此类日志。

**最高实施原则：最小入侵，新增日志仅观察，不阻挡任何现有逻辑。** 日志初始化、分类、排队、写入或
采集失败不得改变请求是否被接受、HTTP 状态、响应正文、鉴权与参数校验结果、上游调用、重试、Task
状态或资金结果。原有成功与失败路径均按原逻辑执行，不把“日志写入成功”作为业务继续的前提。

原有访问日志、认证安全日志和审计记录继续承担各自职责，不因本次范围调整而删除或停用。
代理层在请求到达应用前产生的错误不属于已通过应用 API 鉴权的请求，不纳入本轮新增记录与验收。
Go `net/http` 在调用 Gin 之前直接返回的 malformed request 400、请求头过大 431 等同样不纳入：
这些请求尚未进入应用 middleware，更不可能已通过正式 API 鉴权。不能要求全局 middleware
记录它从未接收到的请求，也不能把这类错误纳入本方案的日志完整性对账。

**当前状态：统一鉴权成功快照、非阻塞有界记录出口、动态插件跨 Gin 记录与素材上下文已实现；可选认证的已匹配凭据和素材下载 capability 成功入口已接线。Dashboard/Relay/插件的具体原因分类、受控环境部署验收尚未完成。**

## 当前实际情况

| 当前工作区代码 | 多个业务 4xx 分支未记录诊断，部分错误原因在返回过程中丢失 | 解释当前实现，不能替代线上版本核对 |

### 2. 对“先鉴权，再验证参数”的核对

这个理解适合作为业务排障日志的范围：先通过 API 鉴权，才能可靠地把后续错误关联到实际调用方。
但执行顺序不能一概表述为“所有验证都在鉴权之后”，也不能说鉴权前的日志没有价值。

已确认的调用顺序：

- asset：`TokenAuth → TokenModelAccess → CreateAsset → 参数与素材检查`，主要业务校验在鉴权之后。
- 原生 Relay：`TokenAuth → ModelRequestRateLimit → Distribute → handler`；部分后续权限和限流
  即使尚未进入 handler，也属于已鉴权后的失败。
- 部分接口存在鉴权前的全局限流、解压或请求体限制；这些请求可能在鉴权之前就结束。
- `TokenAuth` 内同时包含令牌、IP、用户状态、分组和 Token 上下文检查；本方案以该入口全部成功并
  放行后续 middleware 为边界。入口内部拒绝不计为“鉴权通过后的错误”，不移动既有检查顺序来扩大范围。

依据为 [API 鉴权](../../middleware/auth.go)、[素材路由](../../router/asset-router.go)、
[Relay 路由](../../router/relay-router.go) 和 [管理 API 路由](../../router/api-router.go)。

特别注意：`TokenAuth` 在检查 `ValidateUserToken` 返回的 `err` 之前，就可能把 `token.UserId` 写入
`c["id"]`。因此 **`user_id > 0` 不能作为鉴权成功判据**。日志需要正式成功放行点写入的明确标记。

鉴权前的 401、限流和扫描记录仍有认证安全与运维价值；本次只把它们从“已鉴权 API 业务错误日志”
中分离，并非判定这些记录无意义。资源权限、模型权限等在正式鉴权放行后仍可拒绝，也不能误认为
鉴权通过就已经通过全部权限或业务验证。

### 3. 请求处理与日志路径

```text
TokenAuth → TokenModelAccess → CreateAsset
  → 请求结构与 URL 校验
  → 选择素材 adapter、检查素材类型与素材组
  → 下载源素材、检查响应类型与大小
  → adapter 创建；托管路径继续检查实际图片与解码
  → writeAssetServiceError → assetAPIError → HTTP 响应
```

依据为 [素材路由](../../router/asset-router.go)、[素材控制器](../../controller/asset.go) 和
[素材服务](../../service/asset_service.go)。`TokenModelAccess` 只检查模型访问权限；其放行不能证明
后续请求结构、URL、媒体类型或图片解码已经通过。

### 4. 根因一：业务错误出口只写响应

`controller/asset.go` 的 `writeAssetServiceError` 按错误类型选择 HTTP 状态和公开错误码，
`assetAPIError` 只调用 `c.JSON`，两者都不写系统诊断日志或数据库错误日志。
创建请求的 JSON 解析失败和 URL TTL 不足还有各自直接返回的路径，不能只修复通用 service 错误出口。

| HTTP | 代表性触发条件 | 当前诊断缺口 |
| --- | --- | --- |
| 400 | 请求字段、URL 或 TTL 不合法；源素材下载失败；媒体声明不匹配；图片无法解码 | 多种原因合并成通用响应，缺少阶段和原因码 |
| 404 | 客户模型不存在；所选素材服务返回资源不存在；托管素材或组不可见 | 缺少模型查找与资源查找的区分 |
| 409 | 默认素材组未配置 | 已选渠道上下文没有进入失败日志 |
| 422 | `asset_kind + media_type` 不支持；整个素材操作不支持 | 缺少实际请求类型与拒绝原因的关联记录 |

前述 422 的类型检查在 `CreateRemoteAsset` 调用 `adapter.Supports` 时发生，早于下载源素材和调用
`adapter.CreateAsset`。所以它不能证明供应商审核拒绝，也不能证明 WebP 格式不支持。

### 5. 根因二：现有 adapter 日志入口提前跳过部分 4xx

`service/asset_service.go` 的 `normalizeAssetAdapterError` 只有走到末尾才调用 `logger.LogWarn`。
以下分支在日志之前直接返回：

- `ErrInvalidAssetRequest`：转换为 400，且用通用错误替换原错误，丢失包装中的具体描述；
- `ErrAssetOperationUnsupported`：转换为 422；
- `IsUpstreamNotFound`：转换为 404。

请求结构、类型、默认素材组与源素材下载失败通常发生在调用 adapter 之前，根本不会进入这个函数。
托管图片解码失败虽进入这个函数，但命中上述 400 提前返回分支。

必须区分两种状态：供应商返回 HTTP 4xx 不一定意味着平台对客户返回 4xx。
部分供应商拒绝会归一为平台 502，并经过现有 WARN 日志；本方案不能把它们误改成客户 4xx。

### 6. 根因三：底层错误在记录前已经失去分类

在 [源素材下载](../../service/asset_funcloud_stream.go) 中，`client.Do` 失败统一返回
`source fetch failed`，没有保留超时、DNS、TLS、连接失败或重定向拒绝的分类。
源站非 2xx、文件过大、MIME 不匹配虽生成不同错误描述，最终也只返回通用公开文案，未写诊断。

在 [托管图片创建](../../service/asset_hosted_funcloud.go) 中，实际格式、声明 MIME、尺寸和解码
检查失败返回 `ErrInvalidAssetRequest` 的包装错误；其中多个原因本已合并，随后包装又被移除。
只在控制器打印最终错误，无法恢复这些已丢失的原因。

### 7. 根因四：通用访问日志与数据库没有兜底

- [访问日志](../../middleware/logger.go) 记录时间、请求 ID、状态、耗时和路径等，不记录业务错误码、
  阶段或失败原因。
- asset 走独立路由，没有经过 [原生 Relay 错误处理](../../controller/relay.go) 中的
  `RecordErrorLog` 调用；原生错误日志开关不会自动覆盖此入口。
- 素材路由没有挂载视频请求证据采集或通用的素材失败审计，因此数据库没有相应明细。
- 当前相关测试验证错误类型和公共响应，没有验证失败时必须记录可关联、脱敏且不重复的诊断。

这是记录入口与诊断信息传递的缺口。当前 `LogWarn` 本身不依赖 Debug 开关，开启 Debug 不能让
未调用日志函数的分支自动产生记录。

## 优化方案

### 0. 编码前交付两类覆盖清单

先形成可独立检查的清单，再按清单接线；不把“覆盖完整”留到编码结束后凭印象判断。
清单以本节表格为起点，在本文件维护，避免另建一套范围定义。每项都应补齐实际调用方、拟改文件、
测试用例及核验状态；未完成实现或测试不能标记为通过。

两类覆盖分别验收：

- **记录覆盖**：所有正式鉴权成功分支是否设置标记，并由统一出口记录其后全部 4xx。
- **诊断覆盖**：各失败出口是否保留具体原因，哪些仍为 `unclassified`，尚缺哪些回归。

共用鉴权入口和全局出口负责基础记录，业务错误出口负责补充原因；不按“鉴权入口 × 所有路由”
逐项重复埋日志。Provider 数量不等于独立鉴权入口数量，工作量以实际调用链和共用错误出口为准。

#### 记录覆盖清单初稿

| 入口或分支 | 当前代码核对 | 标记与覆盖决策 | 实施验证状态 |
| --- | --- | --- | --- |

| `TokenAuthReadOnly` | Token 日志、用量与余额等读取入口使用 | 沿用自身检查，成功放行前标记 | 已实现；回归：同文件（过期令牌放行即记录、禁用令牌拒绝不记录） |
| `authHelper` | `UserAuth` / `AdminAuth` / `RootAuth` 共用，覆盖管理 API 和 Playground | 正式成功放行点统一标记，入口内角色拒绝不标记 | 已实现（Session/PAT 共用放行点）；回归：同文件（PAT 400 记录为 `personal_access_token`） |

| 动态插件及静态协议路由 | 动态插件在独立 Gin 引擎运行 TokenAuth；静态协议路由复用外层 TokenAuth | 成功事实、身份、实际路由模板保存到共享请求载体；只由外层 Recorder 写一次 | 已接线；真实插件 dispatcher + TokenAuth 回归覆盖 400/403/404/429、鉴权拒绝、200/502 与路由脱敏 |
| `TokenOrTaskArtifactAccessAuth` | API Key 分支委托 TokenAuth；下载 capability 分支独立验证路由绑定凭据并通过既有限流 | 后者只在放行前标记 `task_artifact_access`；无用户身份时记录缺失，不读取数据库补造身份 | 已接线；有效 capability 后的 404 有事件，非法凭据无事件，日志不含 capability 或资源 ID |

证明线上有该路由。实施前再次核对调用方，不扩展未使用接口，不顺手删除或重构它。

每项后续记录“已分类”或“暂为 `unclassified`”及对应代码/测试位置。基础记录全覆盖和具体原因
全覆盖分开汇报，不能以基础事件存在替代原因完整，也不能因原因尚未分类而不记录请求。

### 1. 明确成功标记与统一记录条件

新增最小的请求级鉴权成功标记，例如 `api_auth_passed`；由 API 正式鉴权入口在完成全部现有检查、
放行下游之前设置。标记只表示本请求已经通过该入口，不参与权限判定，不持久化、不缓存，也不成为
另一套认证事实源。

统一记录条件为：

```text
API 正式鉴权成功标记为 true
且最终 HTTP 状态满足 400 <= status < 500
```

不能根据请求头存在、用户 ID 非零、路由前缀、状态码本身或响应正文推断成功。
不能等参数验证成功或创建 Task 后才设置标记，否则会漏掉本次最需要定位的请求。

建议在请求 ID 已建立后的全局 middleware 中注册统一记录出口，在请求结束时检查上述两个条件。
全局注册用于覆盖所有 API 路由，但未标记成功的请求不产生此类事件；不需要为了日志重新执行鉴权，
也不需要改变现有请求处理顺序。

鉴权入口接线按实际合同执行：

- `TokenAuth`：`SetupContextForToken` 成功后、`c.Next()` 前标记；令牌、IP、账号、分组或指定渠道
  检查未通过均不标记。不能在拿到 Token 或写入用户 ID 时提前标记。
- `TokenAuthReadOnly`：其自身实际检查全部通过后、放行前标记；沿用该入口允许的只读凭据语义，
  不为日志收紧认证规则，实施时以代码而非可能过时的注释为准。
- Session/PAT 的正式 API 鉴权：在 `UserAuth` / `AdminAuth` / `RootAuth` 的共用正式成功放行点标记，
  包括管理 API 与使用 Session 的 Playground；入口内角色检查失败不标记。
- `TokenOrUserAuth`：单独登记 API Key 委托分支和独立 Session 分支，按记录覆盖清单的调用方状态
  决定实际接线；后者不能误认为已由 `authHelper` 覆盖，前者不能重复标记。
- 可选认证、插件和其他鉴权入口：逐项确认实际成功点及是否属于受鉴权 API。匿名放行不能标记，
  仅填充身份上下文的通用函数不能替代正式成功点；相同凭据解析逻辑的复用不等于鉴权已经完成。

`TokenModelAccess` 位于 `TokenAuth` 成功之后，故它返回的模型权限 403 必须记录。
同理，后续 API 业务返回任何 4xx 都纳入；即使下游实际返回 401，也根据成功标记与最终状态记录，
不能再写“忽略所有 401”之类的状态码排除规则。

### 2. 统一出口写一次，业务路径补充原因

为当前请求附加最小诊断结构，业务失败发生处提供安全阶段、原因码和已知上下文，统一 middleware
在请求结束时非阻塞提交一条 `authenticated_api_client_error`，由独立日志写入端输出。
业务 controller/service 不再分别写同一种
统一请求结果事件；保留原有访问日志、上游尝试日志和安全审计，按事件类型区分用途。

不依赖 `c.Error` 或特定 JSON 形状，`Abort`、`c.JSON`、`c.Status` 等只要发生在鉴权成功后，都应
被记录。尚未细分诊断的分支仍写基础事件并标为 `reason=unclassified`，不能因此漏记；分类缺失仍是
待办，不能直接宣称根因诊断已完成。

不读取完整请求体或捕获完整响应体来猜错误。已有业务错误出口将公共错误码与白名单诊断附加到
上下文，公共状态和正文仍由现有处理逻辑决定。

#### 非阻断与失败隔离约束

[现有日志实现](../../logger/logger.go) 的 `LogWarn` 经 `logHelper` 加锁并同步写入输出端，直接在
请求 goroutine 调用可能等待文件、管道或锁。即使调用放在 `c.Next()` 之后，也不能把同步写入称为
“不会阻塞”。本轮仅为新增事件隔离写入，不重构现有全局 logger 或改变其他日志的行为。

- 请求路径只设置标记、提取有界白名单字段和尝试非阻塞提交；不等待文件、网络、数据库或队列腾空，
  不执行同步重试、强制刷盘、后台任务排空或诊断性 Provider 调用。
- 优先复用满足上述条件的现有异步设施；如没有，只在新增文件中使用有界队列及固定数量写入任务，
  不为每个请求启动 goroutine，不用无限队列，也不建立新的通用日志平台。
- 后台只接收独立、不可变的脱敏字段快照，不持有或异步访问 `gin.Context`、请求/响应对象、请求体、
  凭据或可继续变化的业务 map。请求结束或取消不使快照失效，也不等待后台完成。
- 新增记录函数不能调用 `Abort`、写响应、修改业务 header、改变路由/上下文中的业务字段、返回
  需要调用方处理的新错误，或触发退款、渠道禁用和业务重试。标记与诊断仅使用独立日志字段。
- 日志自身的格式化、提交与后台写入异常只在新增日志代码内部隔离；不能用包住 `c.Next()` 的宽泛
  recover 吞掉原有业务 panic，也不能替代既有 Recovery 或重新执行 handler。
- 日志组件不可用、队列满、输出失败或输出端阻塞时，业务继续按原结果完成；不回退到请求内同步写入，
  不让日志初始化或关闭排空成为服务启动、请求结束或停机的无限等待条件。

**全量与故障的优先级必须明确：正常健康容量内逐请求记录、不采样；日志设施故障或容量耗尽时，
业务不阻断优先。** 有限资源、绝不等待与故障时绝不丢失不能同时保证，方案不以阻塞业务或无限增长
内存来兑现全量。失败提交/写入通过有界的进程级计数及独立健康观察暴露，不能静默当成记录成功，
也不能递归调用同一个故障日志出口报告失败。该故障处置不允许变成日常采样或按模块跳过记录。

基础性能开销无法严格为零；验收要求是业务无新增日志 I/O 等待、资源有界、公共行为不变。

| 失败位置 | 是否进入新增日志 | 判断依据 |
| --- | --- | --- |
| 缺少、无效或被拒绝的 API 凭据 | 否 | 正式鉴权未放行，保留既有认证/访问日志 |
| 正式鉴权入口内部拒绝 IP、分组、角色等 | 否 | 沿用现有鉴权完成边界 |
| Token 校验通过，但 `SetupContextForToken` 拒绝非法指定渠道 ID，返回 400 | 有意不记录 | 正式鉴权入口尚未完成；不能为了这条 400 前移标记点 |
| 正式鉴权后模型权限拒绝、参数不合法 | 是 | 已成功放行，不要求后续验证通过 |
| 正式鉴权后资源不存在、配置冲突、素材不支持 | 是 | 已鉴权 API 业务 4xx |
| 限流或大小检查 | 取决于执行阶段 | 鉴权后记录，鉴权前不记入此类日志 |
| 未匹配路由、方法拒绝 | 取决于是否实际经过鉴权 | 仅携带有效 Key 但未执行鉴权仍不计入 |
| 静态资源、匿名公共 API、入口代理拒绝 | 否 | 没有正式 API 鉴权成功事实 |
| `net/http` 在 Gin 之前直接返回 400/431 | 否 | 未进入应用 middleware，也未通过 API 鉴权 |
| 上游 4xx 被平台转换成 502 | 否 | 最终响应不是平台 4xx，继续既有上游诊断 |
| SSE 已发送 200 后的业务错误 | 否 | 不伪造 HTTP 4xx，继续既有流式错误机制 |

不为纳入某种错误而新增路由、把鉴权移动到限流之前，或让未匹配路由重新消耗一次鉴权。

### 3. 修复 asset 已确认的原因丢失

素材路径仍需补充底层诊断，否则统一日志只能保证“记到鉴权后的 4xx”，无法解释它为什么发生。

- JSON 解析失败、TTL 专用返回、`writeAssetServiceError` 等出口都写入诊断上下文。
- 请求类型不支持时保留标准 `asset_kind`、`media_type` 和已选择的客户模型上下文。
- `normalizeAssetAdapterError` 通过独立诊断通道保留安全原因，原有业务错误匹配和公共映射不变；
  不为日志新增会改变调用方分支的错误类型或替换业务返回结果。
- 下载失败按受控错误类型区分超时、DNS、TLS、连接或重定向拒绝；不能直接打印可能带签名 URL 的
  `http.Client` 原始错误，也不能仅凭字符串猜测业务结果。
- 图片格式、MIME、尺寸、完整解码失败分别保留原因码，仍保持现有公共错误映射。

拟议的内部诊断示例：

| 阶段 | 原因码示例 | 白名单补充信息 |
| --- | --- | --- |
| `request_validation` | `malformed_json`、`missing_model`、`invalid_media_type` | 字段名，不保存请求体 |
| `source_validation` | `unsafe_url`、`url_ttl_insufficient` | 安全分类、必要 TTL 阈值 |
| `model_resolution` | `model_not_found` | 已解析客户模型 |
| `capability_check` | `unsupported_asset_type`、`unsupported_asset_operation` | 标准素材种类、媒体类型、操作 |
| `group_resolution` | `default_asset_group_not_configured`、`asset_group_not_found` | 已选渠道，不输出 Provider 组 ID |
| `source_fetch` | `timeout`、`dns_error`、`tls_error`、`redirect_rejected`、`source_http_error` | 源站状态、耗时 |
| `content_validation` | `content_type_mismatch`、`source_too_large`、`invalid_image`、`image_dimensions_exceeded` | 归一化 MIME、大小或尺寸 |
| `upstream_operation` | `resource_not_found`、`operation_unsupported` | 既有上游脱敏诊断 |

### 4. 字段、记录落点与范围内全量要求

每条统一事件至少包含：

- `event=authenticated_api_client_error`、时间、`request_id`、HTTP 方法、最终 HTTP 状态、耗时；
- 已成功鉴权的身份来源及 `user_id`，明确区别于从请求中提交的用户字段；
- 路由模板、模块标签、失败阶段、原因码、可用时的公共错误码；
- 已知的客户模型、Channel ID、协议和业务白名单诊断，未解析时省略，不重新查库或推断。

身份字段异常时以正式成功标记为记录依据，保留日志并明确标注身份上下文缺失，不能以数据不全为由
丢弃已鉴权请求，也不能伪造用户关联。

路由、客户模型等字段处理控制字符和长度；非法枚举只记录字段及无效分类，不原样保存任意输入。
不保存查询参数、Cookie、凭据、源 URL、签名参数、用户提示词、素材名称、Provider opaque ID、
原始请求体或响应体。无可用路由模板时保留受控分类，不直接输出任意 URL 路径。

初期由隔离的写入端复用现有系统日志输出和采集链路，使用独立事件类型与 WARN 级别。不受 Debug
开关、原生 Relay `ErrorLogEnabled` 或 `IsRecordErrorLog` 筛选影响。**健康容量内符合条件的每个请求均记录**，不对
重复 400/403/404/429 采样、合并或抑制；日志容量通过保留期、轮转和采集能力管理。

Dashboard Session API 纳入上述范围，是有意保留的业务诊断；纯前端表单校验未发起请求，不会产生
后端 400。后端校验或鉴权后限流可能增加日志体积，但当前没有证据量化噪音占比，不能据此缩减范围。

统一使用 `module` 字段表达受控模块分类，登记其与现有路由标签的映射，不从 URL 或模型名猜测
Provider。查询视图和采集索引按 `module`、`reason`、状态码筛选或分流，保持统一事件类型及 WARN
级别；不按模块降低级别，避免采集阈值漏收。可聚合告警通知，不能因此合并、删除或采样原始请求事件。
灰度时检查模块标签映射、日志体积和采集吞吐；分流后的所有落点共同满足完整性验收。

数据库与后台页面接入单独验收：本方案先保证所有已鉴权 API 4xx 的系统诊断日志，不把现有
数据库调用点缺失描述成开启开关即可解决。若同时实施数据库展示，应复用日志底座，遵守用户隔离、
管理员诊断可见性和零费用语义，不新建按业务拆分的错误表；未接入时明确说明后台还不能查询。

### 5. 实施顺序与最小入侵

1. 编码前先交付并核对本节的记录覆盖、诊断覆盖两张清单，补齐调用方、成功点、有意排除项及验证
   方式；可选认证和动态路由的范围待确认项必须落实，不能只凭函数名假定覆盖。
2. 新增请求级成功标记和统一记录 middleware，在正式鉴权成功点及 `main.go` 做必要接线。
3. 清点已鉴权 API 的所有 4xx 出口，补充诊断；优先修复素材下载与内容验证丢失原因的问题。
4. 核对原有日志/审计的事件用途，保证每次符合条件的请求只有一条新增统一结果事件。
5. 完成真实路由顺序测试、脱敏验证，核对部署版本与各节点采集后进行受控环境验收。

非阻断交付与故障隔离在日志接线前确定，在业务诊断扩展前验证。不能先把同步日志散落到热路径，
再以功能已完成为由推迟阻塞和资源上限问题。

主体逻辑放在新增文件。`main.go` 只增加必要单行注册；各鉴权入口仅在现有成功放行点增加最小
标记调用，不修改原有检查或执行顺序。

本轮实施落点：新增 `clienterrlog` 包（标记 `MarkAuthPassed`、请求级白名单诊断 `Attach`、
统一出口 `Recorder`）；`main.go` 在 `RequestId()` 后单行注册；`middleware/auth.go` 正式
成功放行点与可选认证匹配分支标记；asset 诊断分布于 `controller/asset.go`、`service/asset_service.go`、
`service/asset_funcloud_stream.go`、`service/asset_hosted_funcloud.go` 与新增
`service/asset_client_diag.go`，全部为在既有错误出口上追加受控诊断，公共响应语义不变。
日志新组件不可用时也不得拒绝启动 API 服务；暴露自身不可用状态并继续原服务逻辑。

鉴权成功标记的接线不可用 `user_id > 0` 替代，因为代码已证明失败请求也可能有用户 ID；单独挂
素材路由无法覆盖其他 API。触及上游原生鉴权、Relay 文件时，逐处说明必要性、最小调用点与未来
合并冲突；不重构认证系统，不为 Link 在原生协议中新增模型识别或兼容分支。

### 6. 验证与验收

新增或重写 Go 测试使用 `require` / `assert`，检查最终响应和捕获日志。使用固定输入、受控路由
和实际鉴权 fixture 验证，不通过手工塞入 `user_id` 冒充鉴权通过。

| 场景 | 验收要求 |
| --- | --- |
| 实际鉴权通过后返回 400、401、403、404、405、408、409、413、415、422、429 与区间边界 | 完整 4xx 区间判断，每请求恰好一条；非 4xx 不误计 |
| 缺少/无效凭据、Token 可查到但鉴权失败 | 不产生新增事件；即使上下文已有用户 ID 也不能误记 |
| TokenAuth 内 IP、分组、指定渠道检查失败；AdminAuth 角色拒绝 | 正式入口未成功，不标记；原有响应不变 |
| 有效 Token 搭配非法指定渠道 ID，`SetupContextForToken` 返回 400 | 明确验证有意排除，成功标记未设置，不能误认作日志遗漏 |
| TokenAuth 后 TokenModelAccess 返回 403 | 必须记录，controller 未执行也不漏记 |
| 同类限流、大小或格式拒绝分别位于鉴权前后 | 前者无新增事件，后者有完整事件，不移动既有检查顺序 |
| API Key、只读 Token、Session、PAT 与插件的正式成功入口 | 覆盖各自实际认证合同；可选认证匿名分支不被误标记 |
| `TokenOrUserAuth` 的调用图核对 | 当前无调用方不新增无用途接线；若实施时有活跃调用，分别测试独立 Session 成功点和 API Key 委托分支 |
| 无效路由仅携带有效 Key | 未实际执行鉴权，不计入；不得额外鉴权以制造成功标记 |
| 合法字段后源站拒绝、超时、MIME 不匹配或图片损坏 | 仍记录 4xx，保留真实阶段与安全原因；不误称参数均已通过就不应失败 |
| 素材不支持、模型/资源不存在、默认组缺失 | 公共响应不变，具体 422/404/409 原因可关联 |
| Abort、直接返回、多次上游尝试后最终 4xx | 每请求一条新增统一结果，既有尝试日志可区分 |
| 上游 4xx 转平台 502、SSE 200 后错误 | 不计入新增 4xx 日志，不破坏流式与连接行为 |
| 连续重复的已鉴权 400/403/404/429 | 每个请求均记录，不采样、不去重吞记录 |
| 敏感字段与异常文本 | 日志无凭据、原始正文或签名 URL，字段长度和字符受控 |
| Dashboard 与 Relay 按模块分流、重复业务拒绝 | 统一 WARN 与事件类型，模块映射准确，各落点合计不漏记；告警聚合不影响原始记录 |
| HTTP 解析层在 Gin 前拒绝 malformed request 或超大请求头 | 不进入本类业务日志对账，不要求应用 middleware 为未接收请求生成记录 |
| 日志输出端阻塞、队列已满、写入返回错误或组件不可用 | 请求无需等日志恢复即完成，最终状态/正文/业务调用次数不变；资源有界，失败计数可观察 |
| 日志分类/提交/写入自身异常 | 日志故障不改变业务结果；原有业务 panic 仍交由原 Recovery，不被新增代码吞掉 |
| 请求取消、结束或 Context 被复用 | 后台仅处理独立快照，无数据竞争、不访问失效请求对象，不延长请求等待 |
| 正常路径与日志故障路径对照 | 鉴权、校验、上游调用及适用的 Task/资金事实一致，无额外重试、退款或渠道操作 |

阻塞与队列故障测试使用可控制的输出端、同步信号和固定容量构造，证明在未释放日志输出端时业务
仍能完成；超时仅用于防止测试挂死，不用睡眠、随机压力或耗时差比较冒充非阻断证明。

先运行新增回归对应的窄测试，再按实际涉及包执行项目要求的测试与静态检查。
只有实际触及 `relaykit/` 或其公开 API 时，额外执行独立模块构建。

部署验收记录版本、环境、时间窗口、路由类别、最终状态与脱敏请求 ID，区分鉴权成功和失败的
受控请求集合。以**已进入 Gin middleware 链、实际通过正式 API 鉴权且最终为 4xx 的请求集合**
在日志组件健康、容量充足的受控窗口对账新增日志，按请求 ID、节点和状态核对缺失与重复均为零；
鉴权前失败不得混入。不能拿所有访问日志的 4xx 总数直接对账，
也不能只靠用户 ID 或 Authorization 头反推哪些历史请求已成功鉴权。
仅进入 Gin 尚不足以纳入对账，仍须证明正式鉴权成功。代理、`net/http` 提前拒绝和匿名扫描不属于
该集合，不能为追求总数一致而伪造业务身份、请求 ID 或鉴权成功事件。
故障注入窗口单独验收：业务不等待、不改结果，日志提交/写入失败可观察；不得把该窗口与健康窗口
混算后宣称全量零丢失。真实运行出现持续丢失需恢复采集和容量，不能通过阻塞业务强行补齐计数。

### 7. 风险、未完成事项与本次交付

- 日志不改变认证、参数验证、请求处理顺序或返回语义；范围内全量记录，不以采样减负。

### 8. 本次评审修复与运行观察

- `clienterrlog` 每进程固定一个后台写入任务和 1024 条队列，请求通过非阻塞提交交付独立的
  `Event`（时间、脱敏请求 ID、有限长度消息）。队列不采样；队列满、组件不可用时计数丢弃，
  写入返回错误/短写/panic 时计数失败，不重试、不回退同步日志。进程结束不等待排空，队列不持久化。
- WARN 输出沿用系统日志目的地；专用写入函数返回错误，输出 I/O 不持有全局 logger 锁。
  输出快照与文件轮转竞争可能导致一次可观察写入失败，不因此阻塞请求或重发。
  新事件成功写入计入已有日志计数，轮转仍由原有 logger 驱动，不在新组件调用可能致命退出的初始化流程。
- 唯一鉴权成功事实保存于共享 request context 的诊断载体；身份、模块及路由模板在正式放行点冻结。
  动态插件无需复制鉴权、用户字段或再挂一个 Recorder。源载体只在请求内使用，后台不保留 Gin 或 HTTP 对象。
- 素材 service 在已有模型解析/渠道选择位置附加客户模型、Channel ID、代码协议；后续下载、解码、
  上游归一错误保留这些字段。详情使用固定键白名单并限制长度，不保留任意业务 map。
- Root 可查询 `GET /api/system-info/client-error-log`：`available`、`capacity`、`queued`、
  `accepted`、`written`、`failed`、`dropped`、`diagnostic_failures`、`write_started_at`、
  `last_success_at` 均为当前进程观察值。时间为 Unix 秒，0 表示未发生/当前无写入；采集需按节点查询。
  查询不调用日志输出。持续增长的 dropped/failed 或长期未归零的 write_started_at 表示需要排查输出与容量，
  不能把 accepted 当作已写入。并发读数不是事务快照，稳定后 accepted = written + failed + queued + 正在写入数。
- 原生文件最小接线：`main.go` 的单行 Recorder 注册负责所有请求；`middleware/auth.go` 只在既有
  成功点调用日志标记；`router/api-router.go` 只在既有 Root system-info 组登记一条健康查询路由。
  主体在新增文件；这些调用位置是后续上游同步需复核的冲突面，不改变原生认证、路由选择和错误映射。
- 新增回归使用真实 TokenAuth/插件 dispatcher、可选认证、HeaderNav 条件和 capability 凭据，
  故障测试用同步信号证明输出未释放时请求仍结束，并覆盖队列满、输出失败/panic、不可用组件、
  请求取消、身份变更、公共响应不变和业务 panic 仍交给既有 Recovery。
