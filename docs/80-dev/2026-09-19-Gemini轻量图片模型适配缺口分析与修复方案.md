# Gemini 轻量图片模型适配缺口分析与修复方案

## 1. 问题与目标

本地渠道 103（Google 官方，Vertex AI 类型）调用 `gemini-3.1-flash-lite-image` 时，
标准图片入口返回 HTTP 500、`convert_request_failed`，整体耗时 0.894 秒。
用户要求查明是否为模型名错误、默认支持被删除或上游更新未同步，并形成修复方案。

2026-09-19 已完成初版实现、正式价格配置及六次真实 URL 调用（§7）。后续账号风控阻断了补充验收。
本轮根据用户确认改为原生 1K 字节交付，并修复用量证据与冻结执行问题；最新结果见 §8。
初版方案中任意 1～1699 像素换算方案已被取代，不能作为当前接口合同。
目标是在既有标准图片入口中正确支持该模型，并以显式 URL 返回完成真实验证；
不引入新的渠道类型、模型别名、路由或任务系统。

本方案专门针对 Google Gemini 模型及 Gemini/Vertex adapter，计费核验也以 Gemini 的实际 Token 用量
和官方价格为依据，不套用其他供应商的按张定价或中转协议。

标准 Images 接口是本次必须交付的客户入口：

| 操作 | 方法与路径 | 客户请求与返回 |
| --- | --- | --- |
| 图片生成 | `POST /v1/images/generations` | JSON；显式 `response_format=url`，成功返回 `data[].url` |
| 图片编辑 | `POST /v1/images/edits` | 沿用已有 multipart 文件和 JSON 图片引用合同；显式 `response_format=url`，成功返回 `data[].url` |

路径使用复数 `generations`，不新增 `/v1/images/generation` 别名。两个入口内部均转换为 Google
`generateContent`，客户无需切换 Google 原生接口或提交 `imageConfig` 等 Provider 私有字段。
标准入口兼容不等于支持所有模型的全部可选字段；Lite 的尺寸、编辑输入和未发布字段仍须明确描述并验收。

## 2. 当前实际情况

### 2.1 本地测试证据

环境：本地开发服务 `http://127.0.0.1:3501`，渠道 103，类型 41（Vertex AI）。
测试固定渠道，使用 `POST /v1/images/generations`、`n=1`、`size=1024x1024`、
`response_format=url`，普通产品摄影提示词；未选择显式异步模式。

| 同渠道模型 | HTTP | 整体耗时（秒） | URL 数 | Base64 结果数 | 结论 |
| --- | --- | ---: | ---: | ---: | --- |
| `gemini-3.1-flash-lite-image` | 500 | 0.894 | 0 | 0 | 本地转换失败 |
| `gemini-3.1-flash-image` | 200 | 136.478 | 1 | 0 | 成功交付 URL |
| `gemini-3-pro-image` | 200 | 292.838 | 1 | 0 | 成功交付 URL |

耗时从客户端开始发送到读完响应正文，包含网关处理、适用的上游等待与图片交付转换，
不包含之后下载图片。失败行的 0.894 秒不能解释为模型生成速度。
同渠道其他模型成功，证明该环境存在可用的 URL 交付链路，但不能证明 Lite 的权限或履约已经通过。

本机原始测试索引为 `.local-tests/image-url-all-20260919/cases.json`、`results.json`、
`汇总结果.md`，属于未纳入版本管理的本地证据；本表保留可公开的必要摘要，不依赖它们作为长期链接。
文档不保存密钥、完整签名 URL、媒体正文或原始 Provider 响应。

### 2.2 Google 官方模型身份

截至本次核对，Google 官方页面明确列出：

- API 模型 ID：`gemini-3.1-flash-lite-image`；名称 Gemini 3.1 Flash-Lite Image，别名 Nano Banana 2 Lite。
- 支持图片生成和编辑；Google Cloud 页面列出的正式版发布日期为 2026-06-23。
- 输出分辨率为 1K；Gemini API 页面明确不支持 2K、4K。

证据：[Google AI 模型页](https://ai.google.dev/gemini-api/docs/models/gemini-3.1-flash-lite-image)、
[Google Cloud 模型页](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/gemini/3-1-flash-lite-image?hl=zh-cn)。
这是官方模型，当前失败不是拼错模型名的证据。官方支持仍不能替代本渠道的权限、参数及实际生成验证。

### 2.3 本地拒绝链路

1. 排查时渠道 103 已启用并列出该模型，`model_mapping` 为空，最终上游模型名保持不变。
2. [Vertex 图片转换](../../relay/channel/vertex/adaptor.go)委托 Gemini adapter。
3. [Gemini 图片转换](../../relay/channel/gemini/adaptor.go)首先调用 `SupportsGenerateContentImage`。
   它通过 [Gemini 配置](../../setting/model_setting/gemini.go)中的
   `IsGeminiModelSupportImagine` 对 `SupportedImagineModels` 做精确成员匹配。
4. 默认列表没有 Lite；排查时本地数据库也没有持久化的 `gemini.supported_imagine_models` 覆盖项。
   该名称既未登记，也不以 `imagen` 开头，因此本地返回不支持图片模型的转换错误。
5. [图片 handler](../../relay/image_handler.go)将转换错误包装为 `convert_request_failed`；
   [通用错误构造](../../relaykit/types/error.go)默认赋予 HTTP 500。
   转换已经返回，后续 `adaptor.DoRequest` 不会执行。

因此，这次 500 来自网关本地，未向 Google 发起图片生成请求。`response_format=url` 的交付逻辑尚未执行，
改成 Base64 不能解决这次拦截。错误也不是“未配置模型价格”；失败发生在另一个检查位置。
本结论不推断最终客户账务或 Google 账单，资金核验需独立证据。

### 2.4 默认支持是否被移除

检查了非浅克隆仓库中所有本地可见分支的该配置文件历史、逐行来源和当前工作区差异：

| 证据 | 核对结果 |
| --- | --- |
| 对配置文件检索 Lite 名称的增删历史 | 未发现曾加入或删除该名称的提交 |
| `c4a3127b1`（2026-07-25） | 默认列表增加 Pro Image、Flash Image 正式型号，没有增加 Lite |
| `0a6a7d867`（2026-09-06，本地扩展） | 增加 Gemini/Vertex 标准图片适配，沿用已有登记列表 |
| `4d46ebb79`（2026-09-11）对该文件的改动 | 将循环判断换为等价的 `slices.Contains`，没有删模型 |
| 排查时配置文件未提交差异 | 无 |

可证实的历史原因是：继承的默认表不包含该型号，本地扩展图片入口时没有补齐。
未发现“我们删除了已有 Lite 支持”的证据；历史检索不覆盖已丢失提交或未记录的旧部署配置。
无法仅凭代码推断上游维护者为何没有加入该型号。

### 2.5 最新上游适配现状

直接查询官方 GitHub 仓库后，将本次结论固定到 `main` 提交
[`ea336ed6654a97c0c27e004581578231e0d92824`](https://github.com/QuantumNous/new-api/commit/ea336ed6654a97c0c27e004581578231e0d92824)，
提交时间北京时间 2026-09-19 00:39:38。没有以本地停留在 9 月 4 日的 `upstream/main` 代替最新结论。

| 检查层面 | 固定提交中的事实 | 判断 |

| [Vertex 图片转换](https://github.com/QuantumNous/new-api/blob/ea336ed6654a97c0c27e004581578231e0d92824/relay/channel/vertex/adaptor.go#L115-L118) | 委托 Gemini 图片转换 | 同样受限 |

### 2.6 仅增加名称仍有的缺口

- [通用图片转换](../../relay/channel/gemini/image_generate_content.go)目前按长边选 1K/2K/4K，
  不区分 Lite；例如 `1920x1080` 会发送 2K，`3840x2160` 会发送 4K。
  仅放开登记会使官方不支持的规格进入 Provider 调用。
- `size` 的北向形式是 `auto` 或 `WxH`。文档中的“1K 验证”指分辨率档，不能直接照抄为
  Gemini 北向 `size="1K"`；实际最小请求应使用 `1024x1024`。
- [公开模型投影](../../model/public_image_model_api.go)与[管理端测试](../../controller/channel_test_image_profile.go)
  也依赖这份登记。[Gemini 公开合同](../../pkg/publicmodel/image_gemini.go)会同时发布生成和编辑，
  目前没有 Lite 专属尺寸表达；登记的影响超过一次生成请求。
- 官方列出的部分极端宽高比不在现有十种比例集合内。本次不应顺手放开全部比例；
  新规格需要逐项确认北向像素语义、南向档位和实际输出。
- [配置装载](../../setting/config/config.go)会用持久化数组覆盖默认值。
  只改编译默认不能保证所有已保存自定义列表的部署同时生效。

### 2.7 实施前 Gemini 价格配置快照（实施结果见 §7.3）

2026-09-19 实施前只读查询本地数据库中该准确模型名的配置，结果为：

| 配置项 | 当前持久化值 | 可以得出的结论 |
| --- | --- | --- |
| `ModelRatio` | `0.125` | 已存在输入 Token 倍率配置 |
| `CompletionRatio` | `120` | 已存在输出相对倍率配置 |
| `ModelPrice` | 无准确条目 | 未配置该名称的按次价格，不等于没有计费配置 |
| `billing_setting.billing_mode` / `billing_setting.billing_expr` | 无准确条目 | 未配置该名称的表达式计费覆盖 |

这是数据库配置快照，尚未证明进程实际生效值、最终计费模式或官方价格一致性。
不能据此断言缺价，也不能据此自动切换按张收费。实施前需核验输入文本、输入图片、输出文本、
输出图片的 usage 归类及适用单价，确认既有倍率能否正确表达；当前值的正确性仍待官方价格和真实用量核对。
如核验发现差异，应单独列明拟修改值、价格来源、单位和影响范围，经正式配置入口处理。
人民币换算采用用户指定的 `1 USD = 6.76 CNY`；网关倍率不是人民币单价，不能直接乘汇率写回。

## 3. 优化方案

### 3.1 推荐实施顺序

1. **先补规格边界，再启用登记。** 为映射后的准确上游型号增加 1K 限制，复用现有解析、转换和交付流程。
   `auto` 保留既有 Provider 默认语义；`1024x1024` 作为首个明确验收规格。
   对当前换算会落入 2K/4K 的请求在发送前明确报参数错误，不静默降档或放大输出冒充高分辨率生成。
   不修改其他 Gemini 模型现有尺寸行为；不靠客户别名、价格或模糊前缀判断能力。
2. **对齐公开合同。** 按 §3.4 的确定设计，由一处共享尺寸规则驱动请求校验、南向换算和公开尺寸约束，
   不增加另一套支持模型登记表，不把推荐尺寸当作完整允许范围。
   检查模型列表、单模型详情、价格目录和管理端测试，保证客户别名映射后得到相同参数语义。
3. **补齐唯一登记源。** 在既有 `SupportedImagineModels` 默认列表增加准确型号。
   不另建 Router、ChannelType、Link 模型推断或运行时 fallback。
   对已有持久化自定义列表的部署，经正式管理入口读取现值、备份并仅追加缺失项，保留其他模型和管理员删除意图；
   不做启动强制合并或批量覆盖数据库。当前本地无覆盖项，部署含新默认的版本后核实实际生效值。
4. **核验计费和所有随登记开放的能力。** 付费实测前先完成 §2.7 的实际生效价格、模式和用量归类核对；
   存在未解释的缺项或口径差异时不进入发布验收，不擅自改成固定按张价格。
   最小真实验收先做同步生成 URL；因登记同时发布编辑，
   还应核验编辑请求与输入限制，不能以生成成功宣称编辑已完成。
   检查已有异步入口是否可受理该模型，若可受理则复用同一尺寸约束并补齐冻结/执行一致性验证，
   不仅修同步路径。真实异步履约未验证时保持待验收标记。
5. **验证后再发布。** 先验证一次明确规格，再拓展到现有 1K 比例子集。
   如真实 Provider 返回权限、区域、参数或配额错误，单独记录；不得自动改用另一型号证明“成功”。

默认列表属于上游原生文件。该处修改的必要性是补齐已有唯一注册源，最小改动为一个模型条目；
另造本地覆盖列表会产生第二权威源。未来上游同步时需处理相邻列表冲突并去重。
其他规格逻辑优先隔离到新增文件和现有本地图片扩展中，不改原生聊天、Imagen 或通用 Relay 行为。
公开参数 DTO 所需的另一处最小接线及其上游冲突影响见 §3.4，不能将整个方案概括为只修改一个原生文件。

### 3.2 URL 返回合同

以下生成与编辑示例均用于修复后验证，不表示当前已经成功。
生成请求发送至 `POST /v1/images/generations`：

```json
{
  "model": "gemini-3.1-flash-lite-image",
  "prompt": "一只蓝色陶瓷杯的产品摄影",
  "n": 1,
  "size": "1024x1024",
  "response_format": "url"
}
```

标准 multipart 编辑请求发送至 `POST /v1/images/edits`，表单字段为：

| 字段 | 示例值 |
| --- | --- |
| `model` | `gemini-3.1-flash-lite-image` |
| `prompt` | `把杯子改成绿色，保留其余画面` |
| `image` | 一张调用方有权使用的图片文件 |
| `n` | `1` |
| `size` | `1024x1024` |
| `response_format` | `url` |

JSON 编辑沿用现有 Gemini 图片合同的 `image` 字符串或 `images` 字符串数组，两者互斥，
引用形式按现有合同选择 HTTPS URL 或 Data URL。输入图引用与输出格式是两个独立概念；
客户传入图片文件或 Data URL，不改变成功输出必须为 URL 的要求。

客户端使用标准 Images 的 `data[].url` 获取结果；用户所说的 image_url 返回方式在此指图片 URL，
并不是新增 `response_format="image_url"` 值或要求响应改为 `image_url` 字段。
成功验收必须是 HTTP 200、有效 HTTP(S) URL，不能用 Data URL 或非空 `b64_json` 冒充。
Google 南向返回内嵌图片字节、网关再存储签发 URL 属于现有适配流程，不违背客户侧 URL 返回要求。
对象存储预检失败和生成成功后交付失败沿用现有语义，不因本次适配改变结算或自动重新生成。

### 3.3 不采用的替代方案

| 方案 | 不采用原因 |
| --- | --- |
| 只同步最新上游 | 固定提交仍不包含所需标准图片适配 |
| 只追加模型名便宣布完成 | 仍有 2K/4K、编辑、公开元数据及真实验收缺口 |
| 把 Lite 映射到 Flash Image | 改变实际模型、费用和性能，不是修复 Lite |
| 改成 Base64 请求或更换客户端接口 | 绕不开当前登记问题，也不满足用户的 URL 返回目标 |
| 全局按 `gemini-*image*` 放行 | 模糊名称不能证明履约兼容性，扩大未经验证的支持范围 |

HTTP 500 的错误分类是另一个可改进点。本次先修已明确支持型号的登记与规格，不扩大修改通用错误构造。
未知型号的更友好提示可在已有图片边界另行处理，不能把所有 `convert_request_failed` 全局改成 400。

### 3.4 共享尺寸规则与公开表达的确定设计

采用“唯一模型登记 + 无状态共享尺寸规则 + 只读公开投影”的结构，不增加另一套模型资格登记。
以下文件与接口已按本设计新增或调整；验证和剩余事项见 §7：

1. 在根模块新增 `pkg/geminiimage/size.go`，集中定义 Gemini 图片的现有比例集合、尺寸解析、
   长边到档位换算及逐模型允许档位。按准确的、映射后的 Provider 模型名选择 Lite 的 1K 规则；
   其他已登记模型保持现有行为。此包不依赖数据库、渠道、价格、Gin 或 `publicmodel`，
   不自行决定模型是否可以进入图片入口，也不让独立 `relaykit` 反向依赖根模块。
2. `image_generate_content.go` 的现有尺寸函数保留必要调用入口，内部委托该规则；同步解析、
   编辑解析、异步受理和 worker 转换使用同一结果。不得在 adapter 和 metadata 中分别硬编码 Lite 尺寸表。
3. `GeminiImageAPI` 接收客户模型名与映射后的 Provider 模型名；由 `public_image_model_api.go`
   传入已经解析的结果，不在公开层再次猜测或重做模型映射。公开响应仍只展示客户模型名。
4. 现有 `PublicAPIParameter.Enum` 适用于完整有限集合，`SuggestedValues` 只表示推荐项；
   两者均不能把当前连续的合法 `WxH` 范围准确表示为少数示例。因此不以 `auto/1024x1024` 枚举
   偷换整个允许范围，也不为数千个合法像素组合生成庞大枚举。
5. 为 `size` 增加可选、可机读的 `size_constraints`，类型定义隔离在新增的
   `relaykit/dto/public_image_size_constraints.go`；原 `PublicAPIParameter` 只增加一个带 `omitempty`
   的指针字段。字段描述像素尺寸格式、每边最小/最大值及精确宽高比集合；`auto` 默认与省略语义
   继续使用原有 `DefaultValue` 和参数可选性表达。生成、编辑的 `size` 都发布同一规则投影。
6. Lite 首期继续沿用既有十种比例和档位换算：当前长边从 1700 起进入 2K，因此允许 1K 的
   `WxH` 每边必须为正整数且不超过 1699，同时满足精确比例。该 1699 是现有网关换算规则推导的
   请求像素边界，不是 Google 官方对 1K 的尺寸定义；Provider 的实际输出与已有等比例归一仍需验证。
   范围上限从共享档位规则推导，不在公开层另写常量；保持其他型号的现有尺寸行为。

此设计保留标准 Images 请求字段，新增的 `size_constraints` 仅属于模型发现的说明数据，
不是生成或编辑请求的新参数。相关展示与调用示例读取新约束；旧消费者忽略可选说明字段时，
服务端仍执行同一校验。公开 DTO 的修改是准确表达运行时尺寸范围所需的最小接线，新增类型单独放置；
未来上游同步的冲突面限于 `PublicAPIParameter` 一个字段及可能的同名元数据字段，需核对语义再合并。

`auto` 的确定语义：不发送 `imageConfig`，不由网关替换成固定像素；
Provider 默认生成属于 1K 是真实验收预期，不能用“请求中没有 imageConfig”的单元测试代替输出证据。

### 8.1 问题与目标

遵循北向统一、南向适配。Gemini 原生渠道是类型 24，Vertex 是类型 41；二者客户均使用标准

### 8.2 当前实际情况与已完成修复

- `pkg/geminiimage` 同时驱动尺寸 enum 和输入限制；Lite 成品保留原始字节与随图元数据。
  Gemini 24 保持公共输入预算，Vertex 41 的 Lite 内联图片按官方每张 7 MB（7,000,000 字节）限制。
- Gemini 24 模拟 HTTP 回归覆盖标准生成、JSON 编辑、multipart 编辑的南向路径、认证头、JSON
  转换及 URL-only 返回；没有要求客户按 Provider 改请求字段。
- 同步转换标记固定本次响应族；异步受理后直接复用 generateContent 转换核心，不因当前登记被删除
  而拒绝旧任务。新请求仍须通过现行管理员登记，规格规则不授予路由资格。
- 新增 Lite usage 校验，必须有图片输出分类，所有计费总数非负且有界，图片/文本/思考之和等于
  输出量，输入 + 输出等于总量，缓存不能超过输入。缺证据不推算固定图片 Token。
- 同步标准请求没有可复用的持久化待结算 Task：证据不足时在输出响应前返回
  `502 image_usage_incomplete` 并禁止重试，由既有失败路径退款；不另建账务系统或遗留无人管理的 hold。
  异步则保留成功图片、持久化用量与 pending 计费，不按预扣金额或廉价文本费率伪造最终结算。
- 正式价格仍为标准 Token 表达式：`tier("base", p * 0.25 + cr * 0.025 + c * 1.5 + img_o * 30)`。
  对输入 1200、缓存 40、图片输出 1120、文本 20、思考 10 的可信用量，结果是
  $0.033936 / 16968 quota；人民币按 6.76 为 ¥0.22940736。缓存从普通输入中剔除，思考按文本输出。
