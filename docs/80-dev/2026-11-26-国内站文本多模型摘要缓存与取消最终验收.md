# 国内站文本多模型摘要、缓存与取消最终验收

## 问题与目标

核对国内站 private.linkmetax.com 的 gpt-6.2-sol、gemini-3.5-flash 和 claude-sonnet-4-6，覆盖 Chat、Responses、Claude 与 Gemini 原生协议的摘要、带图单轮和多轮、缓存费用、流结束状态及断开结算。客户已接受 GPT 官方 Chat 提供推理用量，通过 Responses 请求官方摘要的接口合同。

证据来自国内网关真实请求、Chrome 消费日志和授权请求证据，以及当前工作区的回归测试和合成上游对照。厂商直营端点未独立实测。Chrome 登录会话保留，浏览器用于只读核查。生产配置未调整，本轮未部署。

## 国内网关既有实测与本地对照

### 总体结论

**三款模型的 Responses 摘要与带图多轮均已取得正例，客户端需要自行回传历史并处理空摘要。** 五项本地修复已完成，覆盖 Claude Responses 取消结算和推理分项、Claude／Gemini 不支持状态字段的 HTTP 400、Claude Chat 显式缓存断点，以及两款模型的 Responses 流式终态。Claude Chat、原生 `/v1/messages` 和 Responses 的取消计费回归均通过。生产复验仍待验收。本次本地真实渠道缓存结果见后文。

此前国内网关的定向复测与最终对照共 **36 笔**。其中 **27 笔正常结束**，1 笔低输出预算用例按预期收到 incomplete，4 笔状态参数用例被拒绝，3 笔在客户端收到响应头前超时，1 笔在收到 200 和角色帧后主动断开。消费日志按请求 ID 匹配。客户端未收到响应头的三笔按专用测试 Key、模型、路径、发起时间和请求证据关联。北京时间 **13:26** 查询到的消费合计 **168,190 quota（$0.336380）**。定向样本含故障用例，不能用来估算生产故障率。

### 1. 摘要、带图多轮和输出完整性

首轮用合成图辨识左侧蓝色圆形、右侧红色方块，并生成预设数值及代码。第二轮带回历史，追问图形及前文结果。Responses 首轮使用 JSON，第二轮使用 SSE。Gemini Chat 显式启用 extra_body.google.thinking_config.include_thoughts。GPT Chat 使用 reasoning_effort，Responses 使用 reasoning.summary。

| 模型及入口 | 实测结果 |
| --- | --- |

| GPT 6.2 Sol /v1/responses | 回传完整历史的带图两轮回答正确、正常完成，视觉用例摘要可为空。同题控制中，summary=auto 返回 **517 字符**，包含流式摘要增量和最终摘要；summary=detailed 的单个样本为空。不能据此判定 detailed 不支持。 |
| Gemini 3.5 Flash /v1/chat/completions | 开启摘要后，带图首轮 JSON 返回 **1,145 字符**，第二轮 SSE 返回 **247 字符**，图片追问正确并正常结束。 |
| Gemini 3.5 Flash /v1/responses | 首轮 JSON 返回 **1,798 字符**，第二轮 SSE 返回 **220 字符**。图片追问与前文数值核对通过，摘要增量和最终快照一致。 |

### 2. Gemini／Claude Responses 服务端续接

两款模型分别用实际上一轮网关响应 ID 发起 previous_response_id 请求，并单独用结构有效的合成 conversation 对象验证。四笔均在转换阶段明确拒绝指定字段，返回 **HTTP 500 / convert_request_failed**，无消费。两款模型都会进入同一个字段校验器。回传完整历史则通过。GPT 本轮覆盖完整历史续接，未对其服务端会话 ID 做生产结论。[字段校验](../../relaykit/relayconvert/internal/oai_responses/to_oai_chat_req.go#L122)

修复前本地 HTTP 路由复现四例 `500 / convert_request_failed`，上游请求数与消费记录数均为零。修复后共用校验器返回已有的客户端错误类型，四例均通过原映射返回 `400 / convert_request_failed`，继续跳过重试，无上游请求和消费。回传历史继续可用。依赖服务端续接的客户需要另行确认状态存储、隔离和保留期。[转换错误映射](../../relay/convert_request_error.go) · [HTTP 回归](../../controller/responses_compatibility_test.go)

#### Gemini 与 Claude Responses 状态、计费和影响范围

`response_status` **表示响应的协议终态**。代码将 `ResponseOutcome()` 写入这个字段，用 `end_reason` 另记流如何退出，再根据传输、扫描错误及协议失败判定 `status`。客户要求的输出上限已经得到执行，请求进入结算，文本仍可能因预算耗尽而截断。这三件事可以同时成立。正常读到 EOF 的预算截断用例应同时记录 `status=ok`、`end_reason=eof`、`response_status=incomplete`。[字段定义](../../relay/common/stream_status.go#L24) · [消费日志写入](../../service/log_info_generate.go#L174)

修复前 Gemini 共用扫描器和 Claude Responses 的 `message_stop` 分支抢先写入 `completed`。修复后两款模型的 Responses 处理器使用实际生成的协议事件调用 `ObserveResponsesOutcome`，共享状态仍保留首个普通终态。Gemini 扫描器继续为其它入口记录原生结束状态。两款 Responses 流都验证了缺少上游结束信号时产生 `response.failed`，保留已知用量，避免把中断流记成正常完成。Claude `pause_turn` 的现有协议映射仍给出 `max_output_tokens`，该原因不证明模型实际用尽了预算。[Gemini 扫描器](../../relay/channel/gemini/relay-gemini.go#L225) · [Claude 结束原因映射](../../relaykit/reasonmap/reasonmap.go#L9) · [终态观察函数](../../service/responses_usage.go#L118) · [保留终态规则](../../relay/common/stream_status.go#L127)

Gemini 适配器沿用上游实际 `usageMetadata`，Responses 请求取适配器返回的用量进入文本结算。生产样本账单为 73 输入、124 输出、**$0.001226**。本地对照固定相同用量和定价，`STOP` 与 `MAX_TOKENS` 均只产生一条消费记录，日志中的实际扣费、钱包变动和 API Key 额度变动均为 **613 quota（$0.001226）**。标记 `incomplete` 不补算模型可能继续生成的 Token，不触发退款或补发请求。续写如果由客户另发请求，则按新请求的实际用量独立结算。[Gemini 用量采集](../../relay/channel/gemini/relay-gemini.go#L252) · [Responses 结算入口](../../relay/responses_handler.go#L74) · [实际扣费](../../service/text_quota.go#L519)

### 5. 取消与扣费

计费分界是网关收到有效上游响应。等响应头时客户端断开，应取消正在运行的请求、停止后续路由并走原退款。已收到有效响应，即使没有向客户端转发首字，仍沿用已有结算。客户端仍在等待时，404 重试照旧。

| 生产场景 | 证据与判定 |
| --- | --- |
| Claude Chat 收到 200 和角色帧后主动断开 | 客户端此时未收到摘要或正文。消费记 client_gone，网关已计入 **32 输入、24 输出**，扣 **$0.000456**。符合已接收有效响应继续计费。 |
| Claude Chat 45 秒内未收到客户端响应头 | 首个上游 404 后重试，最终记 client_gone、billing-usage-anthropic-estimated。**72 输入、0 输出**，扣 **$0.000216**。证据记录时刻不能反推上游收头准确时刻，仅凭该样本无法判应退。 |
| Claude 原生 100 秒内未收到客户端响应头 | 首个上游 404，之后消费记录扣 **$0.021638**。同样无法仅由记录时间判定有效响应在客户端断开之前还是之后到达。 |
| Claude Responses 100 秒内未收到客户端响应头 | **13:17:51** 首次 404 并立即换上游。客户端测试约 **13:19:31** 超时关闭。Chrome 只读复核确认 **13:20:55、13:21:13、13:21:34、13:22:18** 又发出四次上游请求，后续链路有 HTTP 200 响应及读取错误，**13:23:22** 记录最终 500。按请求 ID 查询 **13:16:20–13:30:00**，仅六条错误日志，各条 `$0`，查无消费记录。证据记录时间无法确定首次有效 200 响应头在客户端断开前还是之后抵达网关。 |

最终补丁在 `DoApiRequest` 的 Chat、Responses、Claude Messages 与 Gemini 文本生成路径接入响应头取消。控制器仅在这组同步文本请求取消后停止继续路由。表单、音频、图片和向量入口沿用原发送路径。现有 Chat 回归验证首个 404 的重试保留、等响应头时断开会关闭上游、不进入第三渠道、钱包与 Key 预扣退回；已经收到 200 和用量、没有送出首个数据帧时，则按 **40 输入、0 输出** 结算。独立的请求传输测试还确认共享发送器成功返回 200 响应头后，客户端取消不会直接关闭尚未读取的响应体。[同步取消处理](../../relay/channel/synchronous_request.go#L12) · [控制器停止分支](../../controller/relay.go#L210) · [Chat 回归](../../controller/relay_cancellation_billing_test.go#L25) · [已接收响应体用例](../../relay/channel/synchronous_request_test.go#L19)

修复前 Claude Responses 在收到 200 和 `message_start`（40 输入、0 输出）后，SSE 首帧写入因客户端断开失败，适配器把它当成请求失败。该路径跳过用量结算并退款。修复后记录 `client_gone`，保留已捕获的用量交给现有结算。永久端到端回归确认，Chat、原生及 Responses 均保留首个 404 的重试规则。等待响应头时断开，停止请求和选渠并释放预扣。已收到 200 和用量后断开，均保留一笔 **40 输入、0 输出**，余额与消费记录一致。[Claude 流处理](../../relay/channel/claude/relay_responses.go) · [Responses 结算分支](../../relay/responses_handler.go#L74) · [取消结算回归](../../controller/relay_cancellation_billing_test.go#L25)

追加 Claude 原生 `/v1/messages` 的常规 HTTP 适配器对照。连续三次验证首个 404 仍会重试，等响应头时断开后只尝试两个渠道，钱包和 API Key 预扣恢复且无消费。已获有效 200 与 `message_start` 后首帧送达前断开，均保留一笔按 **40 输入、0 输出** 的消费，钱包和 API Key 对账一致。

发送范围以实际适配器为准。Claude 常规 HTTP 和仓库内 Vertex HTTP 适配器都进入 `DoApiRequest`。AWS Mantle 及 Bedrock SDK 走独立发送路径并已绑定客户端 context。`providerplugin` 多步调用和 Jimeng 自行构造请求后进入 `channel.DoRequest`，未接入此次共享的响应头取消处理。普通客户端取消时，渠道告警跳过未成功的请求，性能统计也忽略该取消样本。这个豁免不改变扣费规则，也不适用于真实上游超时。生产制品是否包含本地补丁，以及各渠道是否走同一适配器，仍需部署核对。[Claude 适配器](../../relay/channel/claude/adaptor.go#L160) · [Vertex HTTP](../../relay/channel/vertex/adaptor.go#L342) · [AWS Mantle](../../relay/channel/aws/mantle.go#L99) · [Bedrock SDK](../../relay/channel/aws/relay-aws.go#L268) · [插件发送](../../relay/channel/providerplugin/chain.go#L148) · [Jimeng 发送](../../relay/channel/jimeng/adaptor.go#L111) · [告警采样](../../service/channel_alert_observe.go#L162) · [性能分类](../../pkg/perf_metrics/outcome.go#L38)

## 合入前追加修复

- 同步文本请求在底层 HTTP 传输交付响应头时完成交接，发生在证据捕获及 `http.Client.Do` 返回前。交接后客户端取消不再关闭待结算的响应体。尚未交接就取消时，停止发送和后续选渠并退回预扣。传输回归覆盖延迟响应体，Claude Responses JSON 回归覆盖取消后的实际用量、钱包和 API Key 结算。[传输交接](../../service/synchronous_text_transport.go) · [传输回归](../../relay/channel/synchronous_request_test.go) · [结算回归](../../controller/relay_cancellation_billing_test.go)
- Claude 与 Gemini Responses 在写最终 SSE 事件时遇到客户端断开，保留已收集的实际用量及上游协议终态。扫描器退出后在流状态内部记录 `client_gone`，渠道健康保持取消豁免。回归在两款模型最终帧注入断开，逐项检查消费、钱包、密钥额度和状态。[交付状态](../../relay/helper/responses_delivery.go) · [流状态写入](../../relay/common/stream_delivery_status.go) · [HTTP 回归](../../controller/responses_compatibility_test.go)
- Claude Responses JSON 和 SSE 使用共同的用量投影。上游显式报告 0 或正数时，标准 `output_tokens_details.reasoning_tokens` 均如实返回，兼容的 `completion_tokens_details` 继续保留。回归覆盖省略、0 和 30，50 个总输出均结算 300 quota。[Responses 用量投影](../../relaykit/relayconvert/internal/oai_chat/to_oai_responses_resp.go) · [回归](../../controller/responses_compatibility_test.go)
- 缓存断点解析限定在 Chat → Claude，回归也检查通用 Chat 解析行为。Gemini 原生流扫描器继续供原生和 Chat 入口使用。图片证据类型、渠道诊断保留既有观察行为，钱包更新恢复到既有流程。工作树已有的日报实现及验证记录保留为独立业务。[Claude 断点解析](../../relaykit/relayconvert/internal/oai_chat/claude_text_content.go) · [响应体清理入口](../../service/upstream_response_body.go)

### 工程验证及结论

根模块 `go build ./...` 通过。Controller、Relay、Service、Model 和性能分类相关测试通过。定向 `-race` 覆盖最终流事件断开计费、JSON 思考分项、200 响应头交接竞态、图片发送隔离和 Responses 路由判定。relaykit 在 `GOWORK=off` 下独立构建及全量测试通过。根模块全量测试的文档插件端到端用例仍在查看产物时从预期 200 得到 404。同一用例在干净 HEAD 源码上独立复现相同 404。[基线失败用例](../../e2e/doc_parse_test.go#L128)

评审中的文本计费和协议问题已完成代码修复与回归。当前工作区具备本地验收证据，国内目标渠道、Claude 上游输出预算及现存文档插件失败仍需单独核实后再作全面上线验收。
