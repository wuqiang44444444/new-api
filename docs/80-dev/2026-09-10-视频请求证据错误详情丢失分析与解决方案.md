# 视频请求证据错误详情丢失分析与解决方案

## 1. 问题与目标

客户调用视频创建接口时收到以下公开错误：

```json
{
  "error": {
    "code": "evidence_unavailable",
    "message": "request evidence unavailable",
    "request_id": "202609100223529906025878268d9d6v8u2qZCm"
  }
}
```

系统此前已拆分客户业务错误和内部诊断，并要求向客户保留脱敏后的具体原因。本次分析确认：
ModelArk 创建入口的证据采集分支没有接入这套处理，底层持久化还会提前丢失原因，导致客户端无法
区分请求超限、正文格式错误、存储故障和配置异常。

本次授权范围为分析与编写方案；尚未修改业务代码、运行行为回归或实施部署修复。
目标是恢复可操作的错误分类与诊断链，同时保留证据失败时停止发送、资金状态受既有事务保护的边界。

## 2. 当前实际情况

### 2.1 证据范围与未确认事项

- 代码基线：本地 HEAD `3f7e6f2a6` 加当前工作区。工作区存在其他任务未提交的合同及 Seedance 插件迁移改动，实施前需重新核对接线，不能覆盖这些改动。
- 已阅读当前证据架构、运维手册、公开错误文档、相关实现、测试及错误归一提交历史。
- 本地 `logs/` 未找到上述请求 ID。没有访问部署实例、生产数据库或真实 Provider。
- 可以确认当前代码中该响应的生成位置及错误丢失机制；不能确认这一次具体是正文超限、磁盘、数据库还是其他故障，也未核验部署版本与本地代码完全一致。

### 2.2 已有设计与此前改造

[Seedance 产品设计](../10-product/Seedance视频与素材产品设计.md)要求错误说明“什么不符合、需要修改什么”。
[音视频请求证据架构](../20-architecture/音视频请求证据架构.md)要求在发送前证据不可用时拒绝履约；
[运维手册](../40-operations/11-音视频证据运维手册.md)明确正文超限具有 413 语义。
这些要求可以同时满足：停止发送不等于丢弃错误原因。

提交 `dc2fe8e80` 引入任务错误公开归一，提交 `e855a9fde` 进一步统一创建与查询的脱敏边界。
当前 [common/task_error_public.go](../../common/task_error_public.go)分别提供公开文案与内部诊断净化；
[service/task_error_sanitize.go](../../service/task_error_sanitize.go)通过 `TaskErrorDetails()` 保留结构化业务错误；
[controller/task_protocol_error.go](../../controller/task_protocol_error.go)按客户端协议呈现结果。
这些提交保留版权、参数、审核等业务原因，未完成证据子系统的完整错误分类接线。

### 2.3 当前请求链路

```text
POST /api/v3/contents/generations/tasks
  → TokenAuth
  → TaskClientProtocol
  → TaskCreateResponseContract（捕获响应）
  → ModelArkVideoCreateConvert
      → BeginTaskRequestEvidence
          → 配置校验、读取正文、大小检查
          → 主库创建证据索引
          → 预留事件、正文脱敏、加密对象写入、事件完成
      → 任一步失败：直接写入固定 503 并 Abort
  → ResolveSeedanceChannel / RelayTask（此失败路径不会到达）
```

接线见 [router/video-router.go](../../router/video-router.go)。
这段入口拒绝发生在选渠、资金 hold 和 Provider 调用之前，不代表供应商创建任务失败。
该结论只适用于此入口错误，不能推广为所有证据错误或所有 503 都没有发送。

### 2.4 已确认的原因与影响

| 位置 | 当前行为 | 影响 |
| --- | --- | --- |
| `middleware/modelark_video.go`：`ModelArkVideoCreateConvert` | 对 `BeginTaskRequestEvidence` 的全部错误直接返回固定 `evidence_unavailable` / 503，未使用 `err` 详情 | 绕过统一任务错误处理；超限和部分格式错误也被报为服务不可用 |
| `middleware/task_create_response.go`：`TaskCreateResponseContract` | 未设置专用合同响应时原样写出捕获的状态与正文 | 外层不会自动补上分类，固定文案直接到达客户端 |
| `service/task_request_evidence_persist.go:16`：事件预留 | 预留失败只保留 `event reservation failed`，丢弃数据库 cause | 上层无法恢复具体数据库故障 |
| `service/task_request_evidence_persist.go:36`：事件完成更新 | 更新失败只保留 `event commit failed`，丢弃数据库 cause；即使此前脱敏或存储已失败，也先返回更新错误 | 双重故障时最初原因被遮蔽，完成更新自身的原因也丢失 |
| `service/task_request_evidence_redaction.go:245`：结构化正文脱敏 | JSON 解析失败在第 248 行被替换为 `structured evidence is incomplete`，未保留解析 cause | 仅在持久化层包装错误无法恢复语法错误类型；北向原文、南向正文及其他调用来源须分别判断归属 |
| `service/task_request_evidence_persist.go:40`：脱敏或对象写入失败 | 北向与南向的此类失败均统一为 `body could not be safely persisted` | 无法区分安全处理和存储故障，该分支也未留下对应诊断日志 |
| `service/task_request_evidence_capture.go`：`BeginTaskRequestEvidence` | 已区分不可用与正文超限，但配置异常只返回 `invalid configuration` | 已有分类未被 ModelArk 入口使用；配置根因需依赖其他配置日志 |
| `controller/task_protocol_error.go`：`taskProtocolErrorFields` | 所有本地 5xx 被统一为 `internal_error` 和固定文案 | 只把入口接到现有函数仍不足以输出证据故障类别 |
| `controller/relay.go`：`executeTaskSubmissionWith` | 北向超限映射 413，其他证据失败映射 500 | 同类错误在 ModelArk 和其他任务入口的状态不一致 |

此外，证据采集早于 ModelArk JSON 业务解析：`application/json` 正文在脱敏时解析失败，会先被转换为
证据不可用，从而遮蔽后面已有的 `invalid_request`。正文读取失败则须区分客户端中断与本地缓存故障，
不能一律归责于客户端。

### 2.5 可能触发条件，不等于本次已确认根因

根据 [配置实现](../../setting/system_setting/task_request_evidence.go)和
[本地对象存储实现](../../service/task_request_evidence_store.go)：

- 证据默认开启；正文默认上限 8 MiB，Base64 媒体也计入整个正文大小。
- 默认对象目录 `data/task-request-evidence`；创建目录、临时文件、写入、文件同步、硬链接提交或父目录同步均可能失败。
- 默认文件写入超时 5 秒；最多 8 个在途写入，槽位耗尽会立即返回繁忙。
- 主库证据索引、事件插入或完成更新失败也会阻断请求。
- 配置值非法、显式密钥格式不合法、正文或 Content-Type 不能安全解析均可能触发。
- 没有显式配置证据密钥本身不代表创建必然失败：当前会派生密钥；历史正文解密失败是另一条读取链路。

### 2.6 当前测试缺口

[middleware/modelark_evidence_test.go](../../middleware/modelark_evidence_test.go)验证转换前采集原始请求的成功路径。
现有公共错误测试覆盖业务原因保留、脱敏和协议信封；服务层另有配置失败及恢复后禁止发送测试。
尚未发现 ModelArk 实际入口针对证据超限、非法正文、数据库故障、存储故障的分类响应回归，
因此上述测试通过不能证明这个提前退出分支已完成错误归一。

## 3. 优化方案

### 3.1 错误职责与实现边界

1. 在证据专属新增文件中定义结构化错误：稳定类别、发生阶段、正文来源、原始 cause，以及可安全公开的必要参数。
   通过错误解包保留 cause；保持现有 `errors.Is` 对 `ErrTaskRequestEvidenceUnavailable`、正文超限等
   错误身份的识别，不因改造破坏不可重试识别和资金释放路径。
2. 在最接近故障的边界分类：配置、正文读取、北向容量、结构化解析、事件数据库、对象写入、写入繁忙、超时。
   使用错误类型或明确分支，禁止靠匹配 `err.Error()` 字符串判断故障。
3. 由一个证据专属分类映射结合错误类型、发生阶段和已验证的客户合同违例事实，产出 HTTP 状态、
   稳定公开 code、客户说明和处置建议；各入口仅适配已有协议信封。
   内部 cause 只进入净化后的运维诊断，不直接用 `err.Error()` 作为客户文案。
4. ModelArk 入口使用该映射替换固定响应；通用任务、音频和南向发送前证据失败复用同一分类事实。
   不把整套控制器逻辑迁入 middleware，不复制第二份错误映射。
5. 统一协议呈现仅对明确登记、已经安全投影的证据错误保留分类；未知本地 5xx 继续使用既有通用文案。
   不全量开放任意本地错误，也不修改无关 Provider 业务错误策略。

客户业务错误继续复用 `PublicTaskErrorMessageForModel` 等现有边界。此分类只负责证据采集阶段的错误投影，
可以呈现该阶段已证明的客户正文语法错误，不接管业务字段校验、供应商错误解析、任务状态或计费决策。

**JSON 与 Content-Type 的分类职责：**

- 解析发生处保留带类型的原始 cause，区分已证明的 JSON 语法错误与平台脱敏、转换或重新序列化失败。
  不能把所有 `Unmarshal` 错误一律认作语法错误，也不能在第 248 行先丢失类型、再由上层猜测。
- 调用边界显式提供正文来源和阶段：客户北向原始正文、平台生成的南向正文、响应正文或 multipart
  内嵌内容。通用脱敏器的 Content-Type 或 `{` / `[` 嗅探不能证明错误归属客户；递归解析不能丢失来源。
- 仅当请求合同要求 JSON、处理对象确为客户原始北向正文，且类型化 cause 证明语法非法时，映射为
  `400 invalid_request`。有效 JSON 的平台处理失败仍为 `503 evidence_processing_failed`。
- Content-Type 的客户违例须由对应请求合同校验边界确认。证据层解析非 JSON Content-Type 或
  multipart 编码失败，若没有独立、明确的客户合同违例证据，保持 `503 evidence_processing_failed`。
  这不改变既有业务校验已经确认的 400，也不把所有非 JSON 或 multipart 请求统一认定为错误。
- 南向或响应 JSON 处理失败不得因为底层具有同样的语法错误类型就归责客户。发送后故障仅记录诊断，
  不用本节分类覆盖已发生的业务结果。

**同一调用出现两个故障时：**

若脱敏或对象写入先失败，随后事件完成更新也失败，以最初处理故障作为主因，按主因确定公开类别；
完成更新故障作为次因单独保留阶段和 cause。这样不会因为记录失败又发生故障而改变最初拒绝原因。
若此前处理成功，只有事件完成更新失败，则数据库故障为主因，返回 `503 evidence_database_unavailable`。
例如，已确认的客户原始 JSON 语法错误加完成更新失败仍为 400；存储写入失败加完成更新失败仍为
`503 evidence_storage_unavailable`。内部诊断必须同时可追踪两个原因，不能仅保留其中一个。

错误解包须保留两条 cause 链及既有证据错误身份；公开类别只由显式主因确定，不靠遍历 cause 时首先
匹配到的类型决定。此优先级只决定错误解释，不改变持久化顺序、发送许可、unknown 或资金处理；
不得据 400/503 推导安全重发，不重试 Provider，也不把未完成事件补记为完整。

### 3.2 拟议公开错误合同

以下为待实施设计，新增 code 在实施前核对已有公开合同及客户端依赖；当前尚未发布。
既有协议信封保持不变，ModelArk 保留 `error.code`、`error.message`、`error.request_id`。
下表用于发送前拒绝的响应投影；发送后失败遵循第 3.3 节，仅记录证据不可用事实。

| 情况 | 拟议 HTTP / code | 客户文案与处置语义 |
| --- | --- | --- |
| 客户北向正文超过配置上限 | 413 / `request_body_too_large` | 说明本次允许的字节上限，要求减少正文或内嵌媒体；明确未受理 |
| JSON 请求合同下，客户北向原始 JSON 已确认存在语法错误 | 400 / `invalid_request` | 说明 JSON 语法问题；不回显原始输入；不能仅凭通用脱敏失败作此判断 |
| 请求合同校验已确认客户 Content-Type 违例 | 400 / `invalid_request` | 沿用明确的合同错误；不以证据层 MIME 解析失败替代此证明 |
| 客户请求体确认未完整接收，且仍可响应 | 400 / `invalid_request` | 说明请求正文未完整接收；与本地缓存读取失败区分 |
| 平台证据配置非法 | 503 / `evidence_configuration_error` | 说明服务配置异常，需管理员处理；不暴露配置值 |
| 证据索引、事件预留或完成更新为主故障 | 503 / `evidence_database_unavailable` | 说明请求记录保存失败；若完成更新只是次因，按第 3.1 节保留最初主因的公开类别 |
| 对象存储不可写、初始化失败或本地缓存故障 | 503 / `evidence_storage_unavailable` | 说明请求证据存储不可用；路径、挂载和系统错误只给内部诊断 |
| 对象写入等待超时 | 503 / `evidence_write_timeout` | 说明保存请求记录超时；是否可重新提交取决于发生阶段和 attempt 权威状态 |
| 对象写入槽位耗尽 | 503 / `evidence_store_busy` | 说明服务暂时繁忙；不将其混为客户限流或余额问题 |
| 北向正文无法安全脱敏，未证明客户合同违例；包括有效 JSON 的平台处理失败、非 JSON Content-Type 或 multipart 的证据解析失败 | 503 / `evidence_processing_failed` | 说明服务无法处理该请求记录；不把证据处理失败自动转换成客户 400 |
| 南向转换产生的正文超限或无法安全脱敏 | 503 / `evidence_processing_failed` | 说明服务无法处理该请求记录；不能因为平台转换导致超限就直接归责客户 |
| 无法进一步分类的证据处理失败 | 503 / `evidence_unavailable` | 保留通用兜底并给出请求 ID 与联系支持建议；内部必须有具体诊断 |

“详细返回”指稳定的可操作原因，不返回数据库 SQL、文件路径、堆栈、密钥、完整签名 URL 或原始正文。
面向客户端的固定文案统一使用现有英文 API 风格，后续公开文档解释其处理方式。
不新增 `retryable`、`accepted` 等字段；若将来需要，必须单独核对协议兼容性。

### 3.3 保留发送与资金语义

- 北向证据失败：不选渠、不调用 Provider、不创建 Task、不建立资金 hold；可明确说明本次未受理。
- 南向发送前证据失败：保持既有发送许可复核，只有权威状态允许拒绝释放时才走已有释放路径。
- `verifyEvidenceAttemptBeforeSend` 已发现恢复接管、unknown 或发送资格无法确认时，继续保留
  `SkipRequestRefund` 与既有未知结果处理，不能被新分类包装覆盖，也不能提示客户安全重发。
- 已发送后的响应采集、轮询或交付证据失败继续记录不可用事实，不改变业务结果、不退款、不补发。
- 对象写入超时后底层操作可能继续完成；不因迟到的对象写入成功恢复发送资格，不新增业务重试。
- 不把请求 ID、证据行或对象存在性作为 Task 状态或资金事实源；不借本次修改引入跨渠道 fallback。

### 3.4 运维诊断

在公开响应或发送拒绝边界记录一次带平台请求 ID 的净化诊断，至少包含内部类别、阶段、净化后的 cause。
双重故障在同一诊断事件中分别记录主因与次因的类别、阶段和净化后的 cause，避免只记录公开类别而
丢失数据库故障；发送后错误在其既有证据失败记录边界做同样处理，不改变原业务响应。
正文容量错误可记录观测字节数和上限；不记录正文、原始 Provider 响应或完整运行配置。
复用既有日志设施与 `SanitizeTaskDiagnostic`，对允许输出的诊断字段做显式控制。
新增类型的 `Error()` 可能包含内部 cause，必须逐一检查其日志和响应调用点，避免默认格式化泄漏。

本次优先不增加证据表字段或迁移：数据库写入本身失败时，诊断仍需通过后端日志可用。
已有 `unavailable` 事件保持事实语义，不能把未写成的正文标记完整。

### 3.5 文件范围与上游侵入控制

| 文件或区域 | 拟议动作 | 边界 |
| --- | --- | --- |
| 新增 `service/task_request_evidence_error.go` | 证据错误类型、单一公开分类映射及必要诊断封装 | 不创建全项目通用错误框架 |
| 现有 `service/task_request_evidence_*` | 故障现场分类并保留 cause | 保留持久化顺序、并发限制与 attempt 复核 |
| `middleware/modelark_video.go` | 将固定 503 换成证据错误呈现调用 | 不重排整个 ModelArk 转换和校验流程 |
| `controller/task_protocol_error.go` | 为已登记安全错误添加窄分支 | 保留未知本地错误及 Provider 处理规则 |
| `controller/relay.go`、`relay/audio_handler.go`、`relay/relay_task.go` | 仅替换既有证据错误包装接线 | 属于原生文件的现有扩展接线，必要性是避免同类错误在不同入口重新丢失；主体放新增文件，减少上游同步冲突 |
| 新增或补充对应测试文件 | 验证公开行为及发送、资金边界 | 不重构无关测试或现有 Provider adapter |

实施前需检查当前工作区插件迁移后的实际调用链，只改真实可达的证据接线，不恢复旧实现或增加兼容层。
当前方案不需要修改 `relaykit/`；若实施扩大到其 API，必须增加独立构建验证。

### 3.6 实施顺序

1. 确认部署版本、受影响入口与已有调用链，列出北向、南向、发送后证据边界。
2. 先按第 3.1 节固定正文来源、400/503 分类和双重故障优先级，添加可复现当前缺陷的确定性失败用例。
3. 实现结构化错误与唯一分类映射，在解析现场保留类型及 cause，验证两条 cause 链和原有错误身份。
4. 接入 ModelArk 及其他现有证据入口，补足安全诊断并保持协议信封；通过实际路由回归证明分类和停止发送，
   再验证资金与恢复竞态。
5. 更新证据架构、运维与公开错误文档；生产验证确认后记录发布状态，不提前声称已修复线上故障。

## 4. 验证与验收方案

### 4.1 行为矩阵

| 场景 | 必须证明的结果 |
| --- | --- |
| ModelArk 北向正文超限 | HTTP 413、稳定 code、正确容量提示和请求 ID；Provider 调用次数为零，无 Task/hold |
| JSON 请求合同下，客户北向原始 JSON 语法非法 | HTTP 400、`invalid_request`；穿过证据脱敏提前失败分支，Provider 调用为零，无 Task/hold；不回显输入片段 |
| 有效 JSON 的平台脱敏、转换或重新序列化失败 | HTTP 503、`evidence_processing_failed`；不误判为客户语法错误 |
| 非 JSON Content-Type 或 multipart 的证据解析失败，未证明客户合同违例 | HTTP 503、`evidence_processing_failed`；不能仅凭 MIME、正文嗅探或内嵌 JSON 错误归责客户 |
| 既有请求合同校验已确认 Content-Type 等客户违例 | 保持 HTTP 400 和既有错误语义，不被保守的证据分类规则改成 503 |
| 配置错误 | HTTP 503、配置类别和安全文案；无 Provider 调用 |
| 数据库预留失败，或前序处理成功后完成更新失败 | HTTP 503、`evidence_database_unavailable`；原始数据库 cause 可解包且日志净化后可关联；事件不伪造完整状态，无 Provider 调用 |
| 已确认的北向 JSON 语法错误加事件完成更新失败 | 保持 400 主因；两条 cause 链、阶段和原有证据错误身份均保留，日志同时包含净化后的两因；无 Provider 调用或 hold |
| 对象写入失败加事件完成更新失败 | 保持存储 503 主因；诊断同时包含完成更新故障，不因错误包装改变发送及资金语义 |
| 存储写入失败、繁忙、超时 | 三种类别可区分；使用可控测试替身或已隔离的临时存储故障，不依赖真实磁盘负载或睡眠竞争 |
| 本地正文缓存故障 | 不被归类为客户 JSON 错误 |
| 南向正文超限或解析失败 | 不归责客户；已有 hold 仅按既有拒绝事务释放 |
| 同样的 JSON 语法 cause 分别来自北向原始 JSON、南向正文、发送后响应 | 仅满足客户合同前提的北向原文返回 400；南向发送前为处理失败 503；发送后只记诊断，不覆盖业务结果 |
| 写入失败期间 attempt 已恢复或状态读取失败 | 不发送、不误退款、不提示安全重发；保持既有 unknown 边界 |
| 发送后证据失败 | 原业务响应、任务与资金不变，不重发 |
| 原有版权、审核、参数错误 | 仍保留可操作原因；模型身份、凭据、URL 与原始正文不泄漏 |
| 通用任务与音频入口 | 同一故障类别语义一致，各协议信封不变，分类不会被外层重新吞掉 |
| 证据关闭及正常开启 | 关闭时没有新增证据存储；开启成功时仍保存转换前正文并正常履约 |

测试使用 `require` 完成前置条件、`assert` 验证值，显式初始化数据库、用户上下文、配置和缓存，
清理全局替身。容量阈值可在测试配置中缩小；不能添加大循环或依赖真实 I/O 时间的伪压力测试。
至少保留一组穿过 `TaskCreateResponseContract` 和实际 ModelArk 转换中间件的 HTTP 测试，
防止只有分类函数测试通过而入口继续固定返回 503。
错误身份回归须覆盖单故障及双重故障的 `errors.Is` / 类型解包结果，并沿真实调用方验证不可重试识别、
`SkipRequestRefund` 与释放路径保持，不能仅以公开 HTTP 状态相同认定资金语义未变。
