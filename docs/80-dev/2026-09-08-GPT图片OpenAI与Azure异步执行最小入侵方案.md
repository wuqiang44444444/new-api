# GPT 图片 OpenAI 与 Azure 异步执行最小入侵方案

## 1. 问题与目标

客户携带 `Prefer: respond-async` 调用 `gpt-image-2` 时，原平台异步入口因渠道不在白名单而返回
`400`，影响原本可用的图片生成。会话中已完成本地止血修复：未接入平台图片任务执行器的渠道忽略
该偏好，继续原生调用；对应计费和幂等处理使用相同的执行模式判断。

后续目标是让 OpenAI、Azure 渠道上的 GPT 图片生成和编辑支持持久异步执行与查询，并保持
NEWAPI 原生文件最小入侵。客户模型别名、Azure 部署名及已有渠道配置应继续使用现有规则。

使用既有北向入口，路径中的 `images` 为复数：

- `POST /v1/images/generations`
- `POST /v1/images/edits`
- `GET /v1/tasks/{task_id}`

用户已确认实施。本文保留实施前基线与批准方案，并在第 4 节记录本地代码与验证结果。
当前已接通 OpenAI／Azure 持久异步执行，尚未部署线上；本地验证不代表真实 Provider／账单或生产灰度验收。

## 2. 当前实际情况

### 2.1 实施前已核对的代码基线

### 2.2 实施前验证与当时未确认项

本次会话的本地回归已验证止血行为：GPT 图片生成与 multipart 编辑携带异步偏好仍返回原生图片
响应；预扣发生在 Provider POST 之前，最终扣费一致；一并携带幂等键不会留下平台任务占用。
这些测试使用本机模拟上游，结论对应本次会话的本地止血修复版本，不代表任意 HEAD、其他工作区
或线上部署。方案评审阶段核对了代码，没有重新执行专家意见所列的全部测试，不能将该意见中的
“全部一致／实测通过”扩展为完整异步能力或真实 Provider 的验收结论。

实施前尚未确认（本次结果见第 4 节）：实际 Azure 部署与 API 版本对生成、编辑及字段的支持，真实上游用量、账单、失败语义，
以及 MySQL／PostgreSQL 的新增资金事务验证。渠道类型相同不能代替具体部署环境验收。

### 2.3 模式判定时序：实施前行为与接入风险

当前主要图片路由顺序为：渠道分发 → 图片幂等中间件 → Controller 完整请求校验 → 预扣判断 →
图片处理。携带幂等键时，中间件先调用 `ImageAsyncExecutionRequested` 并缓存结果，此时
Controller 尚未执行完整图片请求校验。该时序必须在接入 OpenAI／Azure 异步前明确处理。

三种情形不能混为一谈：

- 实施前止血代码将 OpenAI／Azure 判为原生执行，不认领图片任务幂等键，不存在因此导致的流式悬挂 claim。
- 若仅增加渠道资格而保留其他代码，带 `stream=true` 的请求会在异步入口返回 `400`，随后中间件
  尝试释放 creating 态 claim；不会直接演变为“返回 200 后留下 claim”。
- 若再增加晚期“流式转回原生”分支，却不调整早期模式判定，才可能出现成功响应后悬挂 claim；
  此前 Controller 还可能已跳过原生预扣，资金流程也会失配。

因此这是完整异步接入前的设计阻断项，不是实施前止血修复已发生的故障。采用第 3.1 节的早期一次性
判定，不采用晚期模式翻转或成功后补清理作为修复方案。

## 3. 优化方案

### 3.1 客户可观察行为

| 请求形态 | 拟采用行为 |
| --- | --- |
| 未携带异步偏好 | 继续原生同步请求、响应与计费 |
| OpenAI／Azure 图片请求携带异步偏好，且不是流式 | 完成持久受理后返回 `202` 和平台任务 ID，后台执行，客户查询结果 |
| OpenAI／Azure 同时携带异步偏好与 `stream=true` | 本方案选择优先保留原生流式，忽略异步偏好，避免重新影响现有客户；该选择尚待实施，不改变其他已发布异步族的互斥规则 |
| 其他尚未接入后台执行的渠道 | 维持止血行为，忽略异步偏好并继续原生调用 |
| 已选择平台异步但受理容量、存储或资金检查失败 | 按既有受理错误返回，不发送上游；不得在失败后悄悄转为同步再扣费 |

异步资格来自明确的 `ChannelTypeOpenAI`、`ChannelTypeAzure` 和图片生成／编辑操作，不按
`gpt-image-2` 字符串或模型名前缀推断，不按 Base URL、价格或模型映射猜测。
同一原生图片 adapter 上可用的其他图片模型可复用此执行能力，实际参数仍由原生合同负责。

不能直接开放所有 `APITypeOpenAI`：当前部分其他类型也会映射为该 APIType，包括 Seedance
共享元数据路径。资格必须保持类型边界。

**模式判定决策：在任何幂等认领和预扣之前，通过现有可重复读取的请求体设施取得 stream，
一次性确定本次请求的执行模式。** 实现放在本地图片执行模式文件及图片幂等中间件，复用
`common.UnmarshalBodyReusable`／`common.ParseMultipartFormReusable`，不修改原生分发器。

具体要求：

1. JSON 使用与原生一致的布尔解码语义；multipart 使用与原生一致的取值、`TrimSpace` 和
   `strconv.ParseBool` 语义，不使用宽松真值转换或字符串包含判断。
2. 对缺省、null、空值、显式 true／false、非法类型和重复字段，早期读取与原生解析结果必须一致。
   读取或类型解析失败不得默认选择异步并触发副作用；错误分类遵循既有请求校验语义。
3. 只读取执行模式所需字段，不复制完整图片 DTO 校验，不修改请求体，不引入不同的字段规则。
   这是一处有限的模式输入读取；是否保持单一语义由差异测试证明，不能只靠“不是第二套解析器”的命名保证。
4. 携带幂等键时，由本地幂等中间件在 claim 前调用统一模式判断；没有幂等键时，由既有计费接线
   在预扣决策前调用同一入口。两条路径均取得相同模式，不允许以“无幂等键”为由漏掉 stream 判定。
5. 只有 stream 语义确定后才缓存模式，之后不翻转。完整请求仍由 Controller 的原生校验负责；
   校验通过前不发送上游，既有失败 claim 释放逻辑继续履行其职责。

不选择“成功后补释放 claim”：它无法补救已跳过的原生预扣，也无法消除请求执行期间的错误幂等占用。

**原生合同分派决策：OpenAI／Azure 在调用 `ParseImageContract` 之前进入原生请求准备分支，
沿用原生请求校验与 adapter 转换，只追加异步持久化所必需的检查。** 不能先调用统一合同再在后面
豁免 mask；除 mask 外，还须整体核对数量、输入形态与预算，避免把其他图片族的限制套入原生路径。
原生已有的数量上界与计费安全校验继续生效，绕开统一族合同不等于取消安全校验。

### 3.2 在受理时准备并冻结原生请求

新增原生图片异步请求准备逻辑，复用现有模型映射、OpenAI adapter、参数覆盖、请求体透传与
请求头覆盖规则，只构造最终南向请求，不在此时发送 Provider POST。

拟冻结的执行内容：

- 已解析完成的目标 URL，包含 Azure 部署路径和 API 版本；
- 完成原生认证、组织信息生成及 Header Override 后的最终请求头；
- 最终请求体、Content-Type 和必要长度信息，multipart 的 boundary 必须与请求体一致；
- 当前选定的代理与连接设置；
- 独立的客户模型、资金来源、计价方式、价格／表达式、折扣及计费请求参数快照。

最终请求体含图片或 mask 时存入现有私有对象存储，Task 只保存对象引用与必要执行元数据。
认证头沿用现有作用域绑定的密文保存路径：先完成原生默认头生成与 Header Override，再将最终
请求头加密写入新分支使用的 `HeadersCiphertext`。现有 `freezeImageTaskHeaders` 只冻结解析后的
Header Override，并不自动包含默认 Authorization 或 Azure `api-key`，不能未经补齐就直接视为
“最终头已保存”。multipart Content-Type 必须对应最终请求体的 boundary。

新分支以冻结后的最终认证头为唯一发送来源，不再同时保存一份用于重建认证的明文 `ChannelKey`；
后台不读取当前渠道密钥，不再次执行默认认证与覆盖合并。现有其他图片族的凭据保存和发送方式
保持其当前职责，不借此次接入迁移全部存量任务。敏感连接内容不得进入公共响应、普通日志或公开文档。
这是现有图片执行快照的扩展，不建立新的客户素材资源、所有权表或素材 API。

保存实际请求体可以保持原生 JSON 字段、multipart 文件顺序、mask、参数覆盖以及显式零值，避免
为了后台重建而手写第二套 DTO 或转换规则。不得把客户的上游 `response_format` 缺省值强改成 `url`；
上游请求格式与平台任务结果交付格式分别处理。此决策依据是保持原生字段及缺省语义，不依赖
“所有 GPT 图片模型／所有 OpenAI 兼容中转都不接受 response_format=url”这一未经逐环境核实的断言。

请求体对象应在返回 `202` 前可读取；随后沿用受理事务原子提交 Task、容量、资金与幂等关系。
对象存储和数据库不能伪装成同一事务：受理失败可能留下输入对象，但不得留下已受理假象或已发出的
Provider 请求。对象保留与清理沿用现有运维边界，不顺带新增通用清理系统。

### 3.3 增加原生图片后台执行适配

拟在独立文件中实现 OpenAI 图片后台执行，OpenAI 与 Azure 共用响应处理，继续复用原生 URL
和认证逻辑形成的冻结结果。

这是有意保留的族间执行差异：现有 Gemini／Vertex 与图片中转继续在 worker 中根据冻结参数调用
adapter；新增 OpenAI／Azure 在受理时调用原生 adapter，worker 发送已保存的最终请求。
两者共享同一 Task、受理事务、状态机、查询和结算，不增加第二套业务合同。后续收敛架构文档时，
须按族说明转换时机，不能继续将“所有执行器都在 worker 调用 ConvertImageRequest”写成统一事实。

multipart 不能直接进入当前 JSON 编码步骤，并不意味着提前冻结是唯一技术解；本方案选择提前冻结，
是为了同时保留 multipart、参数覆盖、请求体透传及 Azure 连接语义，减少原生文件修改和重复转换逻辑。

```text
现有初步解析与渠道分发
  → 早期一次性确定执行模式
  → 实际异步时认领可选幂等键
  → Controller 原生完整校验及价格准备（Task 路径跳过原生预扣）
  → 原生合同分支准备并保存最终上游请求
  → 原子受理 Task、资金、容量与幂等关系
  → 返回 202
  → 现有 worker 持久提交 SENDING
  → 新执行适配读取冻结请求并发送一次
  → 归一图片与 usage，保存图片结果
  → 现有 Task 终态与结算
  → GET /v1/tasks/{task_id}
```

新的执行分支应位于现有“重建 DTO 并统一编码 JSON”之前，直接使用已准备的请求，避免把
multipart 错当成 JSON。不得在后台调用完整 `ImageHelper` 或重新进入 Controller：这些入口
包含面向客户 HTTP 响应的写入和请求级消费结算，会与 Task 生命周期冲突。

在 `relay/channel/openai/` 新增响应适配文件，可复用同包现有图片 usage 归一和必要处理函数。
只返回规范化的图片结果、实际用量和结果分类，由现有 worker 管理状态及资金。
返回的 `b64_json` 解码后入存储；返回的 URL 使用现有受保护下载流程保存图片，均复用结果清单
及逐图落存储机制。

**响应读取预算须显式处理。** 现有 `postFrozenImageRequest` 使用
`io.ReadAll(io.LimitReader(resp.Body, 64<<20))`，单次最多读取 64 MiB；`LimitReader` 达到上限后
结束读取，本身不会报告“响应超限”。新分支不能无检查地复用这段读取，也不能简单改成无限读取。
应根据已支持的多图数量、图片规格、Base64 编码体积及执行并发确定有界预算，明确检测超限
（例如读取上限加一后判定），同时控制响应缓冲与图片解码的内存占用。
明确超限与非法 JSON 使用不同的内部失败原因；两者都不能被误认为上游确定未生成，并触发自动重发或退款。
测试须覆盖上限以内、恰好上限和超出上限的读取行为，预算确定前不得宣称所有已发布图片规格均已覆盖。

已发送但结果未知、连接中断或进程退出时，保持待核实，禁止自动重发、换渠道或退款。
已成功生成但保存失败时，只恢复已有结果的交付，不再次生成。上游没有真实任务 ID 和查询能力时，
不伪造 Provider ID，也不承诺能自动找回进程已经丢失的生成响应。

### 3.4 保持原生计费语义

复用既有 quota 计算、表达式、饱和保护及幂等结算，按[表达式计费说明](../../pkg/billingexpr/expr.md)
处理实际用量，不另建 GPT 图片账本或独立定价表。

既有图片任务已支持冻结价格、表达式与加密计费探针，并通过 `imageTaskTargetQuota` 使用实际 usage
计算 Token／表达式费用；该部分复用现有机制。接入必须完成的工作与不变量如下：

1. **按图片数量收费**：按原生规则处理实际返回数量，不能在所有按次场景直接保留请求预扣金额。
2. **新增执行器的 usage 接入**：复用已有价格／表达式／加密探针快照及结算机制，由新执行器归一
   input、output、图片与缓存用量并持久化。使用创建时的计费参数，保留明确零值与缺失值的区别；
   不重建第二套 Token／表达式计算系统。
3. **资金来源**：保留客户已有钱包／订阅选择，复用现有资金机制；不能因为携带异步头而固定改扣钱包。
4. **单一资金归属**：受理成功后由 Task 独占资金生命周期；请求结束退款与原生同步结算不得再次处理。
5. **未知结果**：保持资金待核实；可信失败、成功后的差额和退款继续使用现有幂等入口。

钱包／订阅原子受理是资金合同缺口，必须独立核对现有事务能力后实施；不能为了表面上“少改一行”
将不在同一事务中的扣费和 Task 创建宣称为原子受理。

### 3.5 最小修改边界

下列新增文件名为建议命名，实施时可按职责调整，不视为已存在的文件。

| 位置 | 拟修改内容 | 原生侵入与合并影响 |
| --- | --- | --- |
| 原生 Router／Controller | 复用现有图片与任务查询入口和计费接线 | 目标零修改；早期 stream 读取与模式选择放在本地图片文件，无需为此改动原生分发器 |
| `service/image_execution_mode.go` 与 `middleware/image_create_idempotency.go` | 认领和预扣前以原生一致语义读取 stream，增加明确渠道资格，一次性确定模式 | 两者都是本地文件；有无幂等键复用同一模式入口，不增加晚期翻转或成功后补清理 |
| `relay/image_async.go` | 在统一合同调用前分派 OpenAI／Azure 原生请求准备，继续共享受理事务 | 增加窄分支；原生请求不进入统一 mask 拒绝及其他族限制，不复制 Task 状态机 |
| 新增 `relay/image_openai_request.go` | 准备及保存原生南向请求 | 隔离映射、覆盖、multipart 与连接快照的编排 |
| 新增 `relay/channel/openai/image_task.go` | 有界响应读取、明确超限检测、结果解析与用量归一 | 优先不修改原生 `adaptor.go`、`relay_image.go`；复用已有 usage 处理 |
| `relay/image_task_executor.go` 及新增执行文件 | 在 JSON 重建前分派原生图片执行 | 保持已有 Gemini／Vertex、图片中转分支稳定 |
| Task 私有快照、请求头冻结及新增类型文件 | 保存原生请求对象引用、连接事实和加密后的最终请求头；新分支不重复保存明文认证源 | 优先扩展现有 JSON 字段，无需新任务表；不增加旧合同兼容 decoder，不迁移无关任务 |
| 图片任务受理与计费 | 补齐资金来源、实际图片数；新增执行器持久化 usage 并接入既有快照与结算 | 限定在必要事务与结算边界；不重构通用资金或表达式系统 |
| 公开模型元数据及 API 文档 | 声明生成、编辑、异步与查询行为 | 不公开上游部署名、渠道身份或内部执行细节 |

本文只记录具体接入方案，通用边界继续以硬约束与专题架构为权威，不建立第二份架构合同。

### 3.7 验收标准

| 验收面 | 必须证明的行为 |
| --- | --- |
| 核心矩阵 | OpenAI／Azure × generations／edits × 同步／异步，覆盖所有组合 |
| 模式判定时序 | JSON／multipart × 有无幂等键 × stream 缺省／null／空值／布尔值／非法类型／重复字段，与各自原生解析结果一致；不适用组合按原生错误处理；模式在认领和预扣之前确定且不翻转 |
| 流式优先 | OpenAI／Azure 的 stream=true + Prefer + 可选幂等键继续原生流式，无平台 claim、无漏预扣；其他已发布异步族维持原互斥规则 |
| 原生请求等价 | 多图、mask、JSON／multipart、字段缺省与显式零值、图片顺序、参数覆盖、透传与请求头覆盖不因异步改变 |
| 合同分派 | OpenAI／Azure 在统一合同前分派，原生可用 mask 不被该合同拒绝；数量、输入形态及预算不被其他族限制收紧，原生安全上界仍有效 |
| Azure | 部署名映射、API 版本、组织／认证及相关渠道设置准确；排队期间修改配置不改变已受理请求 |
| 最终请求头 | 默认认证加覆盖后的结果被准确加密保存并直接发送；multipart boundary 一致；新分支无第二份明文认证源，渠道密钥轮换不重新解释已受理请求 |
| 响应读取 | 有界预算覆盖拟发布规格；上限以内／恰好上限／超限可区分，超限不伪装成普通 JSON 错误，不因读取失败重发或退款 |
| 北向生命周期 | 默认同步不变；实际异步只在持久受理完成后返回 202；缺少存储、容量或资金时不发送上游 |
| 计费 | 上游 POST 前完成必要预扣；实际图片数、Token 和表达式与同步一致；钱包／订阅、退款、差额均不重复 |
| 幂等 | 同键等价请求仅受理并发送一次；不同请求冲突；未选择平台异步的原生请求不产生悬挂 Task claim |
| 重启与异常 | 排队任务可恢复；发送后未知不重发、不自动退款；生成成功但保存失败只恢复交付 |
| 查询与安全 | 用户及 API Key 隔离；结果 URL 可续签；公共响应和日志不泄露请求体、凭据或上游身份 |
| 既有能力 | Gemini／Vertex、图片中转及原生流式处理无回归 |
| 数据库 | 新增或调整的受理、资金事务在 SQLite、MySQL、PostgreSQL 上验证 |
| 真实环境 | 使用部署方实际 OpenAI／Azure 渠道完成生成、编辑、用量、失败与账单核对，不以模拟测试代替 |

后续代码检查优先运行受影响边界的确定性测试；涉及 `relaykit/` 时额外执行独立模块构建。
方案文档检查执行 `task docs:check` 与 `task ai:check`；后续修改公开 API 文档时再执行
`cd web && bun run docs:validate`。

## 4. 本次实施与剩余验收

### 4.1 本地代码结果

- 在幂等认领和原生预扣之前确定模式；OpenAI（1）／Azure（3）非流式请求选择 Task，流式优先。
- 原生请求提前分派，不进入统一 mask 拒绝。受理时冻结 adapter 最终输出、URL、请求头和代理，
  worker 直发一次；认证加密、请求体按 8 MiB 分片存私有对象，不重复保存明文 ChannelKey。
- 原生响应预算定为 512 MiB，单张结果延续 50 MiB；超限、读失败和非法结果分别记录原因，均不自动
  重发或退款。该预算仍需结合真实图片规格及并发进行容量验收，不能据此声明所有最大规格已经验证。
- 按实际图片数结算，持久化归一 usage，保留缺失与显式零用量区别；计费副本沿用原生缺省处理。
  价格、表达式与原始请求探针冻结，资金来源按钱包／订阅偏好选择并与 Task、令牌、容量、幂等一起提交。
- 复用现有查询、结果存储、恢复及结算；公开元数据增加 edit 与 async，Azure 不透明部署名不影响
  客户 GPT 图片资料，也不对外泄漏部署名。

- 渠道参数覆盖可以让上游返回 SSE。为避免扩展早期请求解析或调整原生预扣，保持客户请求的
