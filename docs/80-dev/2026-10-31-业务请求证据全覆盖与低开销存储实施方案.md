# 业务请求证据全覆盖与低开销存储实施方案

## 1. 问题与目标

用户确认：扩大至业务 API 交换，排除管理、登录、静态、健康及证据自身接口；证据层不解析业务正文、
保存时不做 JSON 格式化，显式读取时按需格式化；上传文件不另存证据；普通大正文正常保存，不按大小检测后丢弃。改造以减少额外
CPU、内存复制与业务线程等待为目标。自动保留两天；新增要求为磁盘超过 90% 立即按一天规则清理。

代码已实施并进入本地验收，未修改生产配置、挂载、密钥或宿主配额。当前合同以
[硬约束第六节](../00-context/硬约束.md)、[请求证据架构](../20-architecture/音视频请求证据架构.md)和
[运维手册](../40-operations/11-音视频证据运维手册.md)为准，本文记录本轮取舍、接线和验证。
不归档任何文档，不更新 60/70/99。第 2—3 节描述当前实现；第 4、6—8 节保留阶段验证，
实验 B 的最终实现和正式构建重验见第 9 节，非核心数据取舍及资源修复见第 10 节。

| 故障隔离 | 资源不足、取证数据库或盘写故障只损失证据；不拒绝业务、不重发、不换渠、不改 Task/资金 |

历史 AES-GCM 只读且不重写，新对象使用 NEVSIO3 密文标记，解密后保留 v2 元数据封装与原字节。
新代码没有双写、正文分页、随机访问块索引、重放或第二套业务状态。重复方向的事实更新仅在变化时
回填，批量关联每窗一次，不为每个字节块执行数据库事务。

### 2.2 明确边界与待验收

- “不解析”指证据正文；元数据编码/解码与认证加密仍有成本。原生业务协议转换、校验、计费解析
  不在本次删除范围。
- 普通 JSON 内嵌 Base64/Data URL 不扫描，因此仍随普通正文保存。只排除操作/外层类型可判定的
  文件传输，不承诺识别所有隐藏文件。Batch/恢复输入/正式结果自身的业务存储保持独立。
- 正常资源下保存实际 I/O 字节；业务未读的输入不主动补采。资源不足会缺证据，不按正文长度丢弃。
  此次不能保证“扩大范围、大正文全存、总 CPU 必然下降”同时成立。
- 五秒采样后立即提交清理申请，不代表同步清理完成；已有互斥任务、主节点、慢盘和删除故障会延迟。
  只保留一天仍可能装满磁盘，因此高位暂停自身写入，专用卷/配额仍是生产开启条件。
- 支持文件流 API 的浏览器流式下载；兼容浏览器显式 Blob 下载仍可能占用整份文件内存。服务端对
  新对象保持流式；旧 AES-GCM 读取仍需整份认证，但密文上限为 32 MiB + 128 KiB，独立单槽
  原地解密并纳入八个总读取槽位，超限只拒绝该条读取。
- 初始回归使用 Go 1.26.5、darwin/arm64、SQLite 临时库、合成正文与 httptest Provider。
  本地隔离 MySQL 5.7.44/PostgreSQL 9.6.24 已通过迁移、窗口锁、清理和关联查询合同；后续真实
  Provider 与完整程序开关采样见第 8 节。生产数据库、共享卷多节点、配额耗尽和灰度性能未验收。

## 3. 优化方案与实现取舍

### 3.1 存储与生命周期

选择成熟 SIO 流式 AEAD，避免自行设计分块密码协议。读取本地依赖 API 并验证篡改、截断、重排、
跨对象替换与历史读取；最终文件不可覆盖发布，发布与清理锁共用主库窗口守卫。数据库与文件系统
不构成单一事务，崩溃可留下暂存或缺失对象，沿现有恢复清理回收，不由证据触发业务重发。

每个请求/后台周期独立索引，长连接窗口最长一小时；正文期限从窗口开始起算。删除关闭窗口不再
保留固定七天墓碑；访问审计仍从访问起七天，证据清理/监控任务历史三十天。最小 Task 关联只服务
已有可信批量轮询，不为 MJ/Suno 从原文反向恢复 ids。

高水位复用现有 SystemTask 类型、唯一活动键与持久 cutoff；首次采样超过 90% 立即申请，高位最多
每分钟申请一次。现有手动任务继续原范围，完成后再申请；恢复到 90% 或以下只恢复未来采集。
不新增第二套清理调度器，不删除一天内数据或正式业务文件。

### 3.3 验证与剩余风险

确定性回归覆盖：200/400/429 四方向、平台本地拒绝无补读、panic 最终响应、短写、原始查询串、
重复字段/非法 JSON/SSE、文件提前旁路、最终公开投影、durable sending、批量关联、旧任务新窗口、
清理与晚到发布、加密认证/历史读取、大于 32 MiB 完整下载、64 KiB 查看、资源预算、慢数据库不
阻塞响应、存储失败不改变调用次数与响应、磁盘 90% 边界和一天 cutoff。

性能验收仍应固定前后版本、Go/CPU/内存/存储、并发、采集范围及请求工作量，分别测同一媒体负载
和新增业务负载；计入 worker 排空后的 CPU、分配、峰值内存、GC、首字节/结束延迟、磁盘写入和
退让数量。不预填降幅，不用大量缺证据换性能。当前结构消除了整份新正文缓存，但尚无生产 CPU
下降百分比结论。

## 6. 合并评审后的修复与性能核对

### 已修复的根因

1. 业务入口：插件引擎已匹配的 relay 路由获得采集资格，覆盖豆包、阿里及自定义插件路径；未知路径
   不获得资格。通用任务查询和制品列表使用已授权 Task 附加关联，不从正文反推身份。
2. 单一 owner：图片查询不再创建第二个 capture/writer；媒体交付只附加事实，删除独立计数器和另建
   窗口的保存路径。后台图片执行也移除了不可达的旧 capture 分支和第二上下文键。
3. 文件边界：客户 writer 冻结原始路径，JSON/文本文件内容同样旁路；带代理的回源与 S3 文件操作
   显式去掉证据资格，超时派生 context 保留该标记，fallback 观察也遵守它。
4. 故障收尾：首次交付记录申请失败后不重开，避免保存后缀；异步写失败后的下一次观察会归还本地块。
   取得记录预算后才复制头，文件事件不复制原始头和查询串，减少压力时无效分配。
5. 消息与热点：讯飞单次编码后发送并观察同一字节（含原末尾换行），读取传真实类型；身份观察不再
   每次 Read/Write 重复访问 Gin 键。错误细节继续保存在加密元数据，不直接切 metadataOnly 丢信息。
6. 查询：证实旧 OR/相关 EXISTS 扫描风险后，改为两条 TaskID 索引候选 UNION 去重；新增关联 TaskID
   索引，保留外层过滤、计数和分页，直接与批量关联重叠时仍只返回一次。

### 性能与安全风险结论

- WS 已按五秒合并；每方向长期占用活动记录额度，片段对象/事务数以及主库索引增长仍是真实成本；inode、数据库空间、
  清理吞吐与物理 I/O 竞争均需监控，不能只检查证据目录字节数。
- 超过 90% 的暂停与一天清理只约束证据；其它业务仍可能占满系统盘，专用卷/配额与生产容量验收

## 9. 实验 B 正式实施

### 9.1 最终取舍与最小接线

本阶段把已测实验 B 写回原始工作树；性能基线工作树保持只读。正式构建直接来自源代码，
不使用实验 overlay，不新增配置、依赖、数据库结构、消息队列或 Provider 接线。

| 修改点 | 当前实现 | 必要性与上游同步影响 |
| --- | --- | --- |
| `service/request_evidence_runtime.go` | 活动记录和对象两处固定预算从 128 改为 512，正文块仍为 1024×64 KiB，worker 仍为四个 | 64 路双向通常需要 256 个方向记录，另需握手和 HTTP 余量；取证专属文件，不扩写原生逻辑 |
| `service/request_evidence_realtime_segment.go` | 片段时长从 5 改为 15 秒，正常关闭立即封存 | 降低事件/发布/文件同步的固定频率；保持流式写入、32 字节消息边界和原读取格式 |
| `relay/channel/openai/relay_realtime.go` | 两处高频输入/输出 Token 诊断由预格式化 INFO 改为现有 `LogDebug`，格式与参数直接传入 | 日志在这两处产生，公共 logger 没有只抑制这两类行的入口；两行原生修改避免全局日志政策变化，未来合并只需核对这两个日志级别；保留错误、完成用量与消费记录 |

512 是记录/对象数量上限，64 MiB 仅是正文块预算，SIO 缓冲和元数据另计。提高容量不是进程内存

十五秒片段延长可读等待和异常崩溃时可能损失的未封存窗口，不在内存中积攒十五秒正文。

每个片段继续使用事件预留、清理围栏内发布与文件/目录同步，不删除清理互斥事务，不把长连接
包在长期数据库事务中。磁盘仍每五秒采样，两天保留、超过 90% 暂停并申请一天清理不变。

## 10. 非核心数据优先级与资源风险修复

用户确认：证据用于偶发排查，绝大多数到期删除；主业务优先，接受正常停机、重启及故障损失少量
未封存/排队证据。不增加停止观察注册表、停机封存、补记、恢复或重放；删除 main.go 中此前增加的
证据 Flush 等待，原 HTTP Shutdown 和用量缓存保存不变。Flush 仅供确定性验收使用。

| 根因 | 最小处理 | 额外成本与边界 |
| --- | --- | --- |
| 根目录一次载入及逐目录查库，单目录文件同样一次载入 | 文件系统接口改为 256 项批次回调；存活 ID 用 GORM `IN` 批查；进度按批保存 | 不增加队列/调度器；内存与单批大小相关，遍历总成本仍随文件数增长 |
| 事件预留后窗口已清理，worker 才创建暂存 | 暂存创建后、写内容前读取窗口，已关闭/不存在即 Abort 并尽力移除空目录 | 每对象开始多一次普通 SELECT，后台执行；不增加事务或逐消息/逐块查询，最终发布仍由原主库守卫决定 |
| 旧格式预览绕过共享限流且整份复制 | 预览统一使用既有 Open 入口；旧密文限定 32 MiB + 128 KiB、单槽、原地解密；摘要顺序核验 | 超大旧对象返回不可用，不改文件、不迁移；新格式大正文保存与流式下载不受此上限影响 |

生产路径改动限于证据专属文件和孤儿清理调用方，新增一个 model 批查文件，无新依赖、配置、
数据库表或迁移。本轮对原生 main.go 仅删除三行证据等待，进一步减少未来上游合并冲突。
清理开始后原已打开的暂存可能继续接收字节直到片段结束，打开句柄可能延迟空间释放；最终发布
仍拒绝关闭窗口。接受这种尽力清理边界，不增加逐块查询或即时终止连接以追求证据强一致。

确定性回归覆盖：601 个目录跨批清理、存活窗口保留、符号链接不跟随、513 个文件跨批删除、取消扫描，
清理标记/索引删除早于暂存创建，历史预览 64 KiB 与全对象摘要校验、旧格式单槽和总八槽、超限稀疏
旧文件拒绝及新格式仍可读。本轮完整程序复验与最终检查见验收记录末节。
