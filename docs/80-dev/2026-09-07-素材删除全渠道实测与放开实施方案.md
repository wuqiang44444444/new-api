# 素材删除全渠道实测与放开实施方案

## 问题与目标

目标终态：放开所有 Seedance 渠道的**单素材删除**（北向 `DELETE /v1/assets/{asset_id}`），同时继续保持
**素材组删除不发布**（无路由、无 adapter 操作、不进公开元数据）。本文记录对全部在库启用渠道的实测
结果，并给出 FunCloud 放开删除的实施计划。

## 当前实际情况

### 测试环境与方法

- 环境：本地网关 `http://127.0.0.1:3501`（SQLite 库），临时平台 Token（user_id=1、group=default、
  测毕已删除）。
- 方法：对每个启用素材协议的渠道，先用保证不存在的假 ID 做删除探针（零副作用），再经平台
  `POST /v1/asset-groups` 建组、用代码 adapter 直连 Provider 创建真实图片素材（1024×1024 JPEG），
  然后全部改走平台北向：`GET`（删除前）→ `DELETE` → `GET`（删除后）→ 重复 `DELETE`（幂等语义）。
- 说明：本机 DNS 为 fake-ip（公网域名解析到 198.18.0.0/15），平台素材创建的服务端 URL 校验
  （SSRF）会拒绝任何公网 URL，故创建步骤用 adapter 直连完成；`GET`/`DELETE` 全部经平台北向，
  为发布面的真实证据。

补充事实：

- 素材组删除边界未变：`DELETE /v1/asset-groups/{id}` 仍返回 404 Invalid URL（路由不存在），
  8 协议均无 `DeleteGroup` 实现，公开元数据无 `delete_asset_group`。
- #90（火山官KEY-SD2-85折，已停用）未测；ark_assets_v1、byteplus_action 无在库渠道，未实测。
- Provider 侧残留：7 个测试素材组按平台保守合同保留在 Provider 侧（组名
  `del-probe-chNN-20260906`）；所有测试素材本身均已删除或经 Provider 端点清理，零素材残留。
- FunCloud 共享默认组 `aigctokenaigeneral` 现有素材 10 个（多人共享下游），再次印证组级联删除
  不可发布的边界。

### FunCloud 未文档化单素材删除端点（已验证）

- 端点：`POST /api/v2/open/material/delete?materialId=<id>`，未写入供应商素材库文档
  （文档仅登记组级联删除等 8 个端点）。
- 存在性证据：对不存在 ID 返回 HTTP 200 信封 `code=90003, msg="素材不存在或无权限"`；
  未知路由对照返回 HTTP 404 纯文本，签名截然不同。
- 真实删除证据：对本次创建的测试素材（`mat_1788711420_...`）调用返回 `code=0 success`，
  随后平台 `GET /v1/assets/{id}` 返回 404 `asset_not_found`，素材确已删除。
- 语义注意：`90003` 把「不存在」与「无权限」合并编码，映射决策见下。

### not-found 语义不一致（实测确认）

重复删除同一已删素材：joycreator / moxing_volc / tokensave → 204；volcengine（#81/#97）→ 404
`asset_not_found`；cmcc → 502。删除不存在素材的响应在四家协议间不统一，北向合同目前只承诺
「删除成功返回 204」，建议本次不强行统一（最小入侵），在实施记录中如实登记。

## 优化方案

### 实施范围（仅 FunCloud 一家）

1. `relay/channel/task/seedance/assets/funcloud.go`：`DeleteAsset` 桩改为真实实现——
   `POST {root}/delete?materialId=<id>`；`code=0` → `nil`（平台 204）；`90003` → 决策项：
   **建议映射 404 `asset_not_found`**（不吞「无权限」语义，与 volcengine 重复删除语义一致）；
   其余非 0 code 维持既有 `upstreamApplicationError` 映射（502）。
   `UpdateAsset`（单素材改名）不在本次范围，保持 unsupported。
2. `model/channel_seedance_public_catalog.go`：`FunCloudMaterial` 行
   `assetDelete = true`，公开元数据发布 `delete_asset`。
3. 单元测试：fake Provider 信封覆盖 `code=0` / `90003` / 其它非 0 code 三分支。
4. 文档：FunCloud 对接设计与能力元数据文档的素材操作表翻转删除行；
   `docs/50-planning/变更记录.md` 记变更；本文记录实测与实施。素材组删除边界所有文档保持不动。

### 验证方式

- 单测通过后，按 `docs/40-operations/04-素材库验收操作手册.md` 对 #72 三个客户模型各跑一轮
  平台北向全周期：建组 → 建素材 → `DELETE` 204 → `GET` 404 → 重复 `DELETE` 404。
- 回归确认 `DELETE /v1/asset-groups/{id}` 仍 404、元数据无 `delete_asset_group`。

### 风险与剩余事项

- 该端点无供应商文档，存在 Provider 侧变更风险；代码注释标注「2026-09-07 实测未文档化端点」。
- `90003` 的「无权限」分支只能在真实越权场景下才能区分，当前以 404 如实暴露。
- ark_assets_v1 / byteplus_action 无在库渠道，删除能力沿用代码实现与登记元数据，待有渠道后
  补实测。
- cmcc 删除后 `GET` 502（Provider HTTP 500）为 Provider 行为，平台如实映射，不在本次修复。
