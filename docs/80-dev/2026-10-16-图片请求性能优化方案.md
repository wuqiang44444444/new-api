# 图片请求性能优化方案：证据原样保存与按需解析

## 1. 问题与目标

**证据在保存时以保存为主；解析、美化和预览在管理员主动查看时进行。**

本方案仅重构请求证据的采集、保存与查看，降低每次媒体请求承担的正文处理成本。图片生成、协议转换、计费及业务状态仍由原业务链路负责；上游额度与冷却由[图片负载均衡与上游额度治理方案](2026-10-15-图片负载均衡与上游额度治理方案.md)单独处理。

CPU 验收以**固定请求集消耗的网关进程 CPU 秒数**为主要指标；主机 CPU 峰值和自保拒绝率作为部署效果单独观察。网关本地成本下降不等于主机必然不再过载，测量口径见 §5。

2026-10-16 用户已确认以下目标，实施时不再沿用“存前必须解析和脱敏”的设计前提：

- 保存实际捕获的原始内容，取消保存前的正文解析、脱敏、正则扫描、字段替换及重新编码。
- 允许 Authorization、Cookie、API Key、签名 URL、素材源 URL 等随原始证据进入受保护存储，供授权管理员查看。
- 取消证据自身的成功/失败、阶段状态、字节数和内容完整性管理；接受证据缺失、截断或无法解析。
- 管理员逐条查看时可以解析、美化、展示图片；解析失败仍能查看 raw 内容或下载原始对象。
- 证据采集、保存失败不阻断业务，不改变发送、响应、重试、资金或 Task 状态。

这是已确认的目标变更，当前工作区已按该目标实施；本地验证与真实部署验收分别记录。允许原始凭据进入证据，也意味着获授权管理员可能读到仍然有效的凭据。

## 2. 当前实际情况

### 重构前基线代码事实

本地基线为 `b9fe36a4e` 及 2026-10-16 工作区。重构前实现与目标之间主要有四处差异：

| 重构前实现 | 需要改变的职责 |
| --- | --- |
| [通用证据保存](../../service/api_request_evidence.go)先为格式标记完整脱敏并丢弃结果，保存时再次处理正文 | 保存路径直接接收原始字节，不判断业务正文是否合法 |
| 重构前 `service/api_request_evidence_redaction.go`（已删除）整包扫描 URL，再用正则枚举字符串，逐个解码、扫描及重新编码；[递归处理](../../service/task_request_evidence_redaction.go)还会重组 JSON 子树 | 删除保存前的内容解释和改写，不继续优化这套存前脱敏流程 |
| 重构前 `service/task_request_evidence_persist.go`（已删除）维护阶段、完成/失败、完整性、摘要等信息，部分取证入口以保存成功作为业务发送前提 | 缩减为必要的对象定位与存储操作，移除证据对业务发送资格的影响 |
| [详情查询](../../controller/task_request_evidence_query.go)批量读取事件预览，原文接口目前仅 Root 可访问 | 按管理员选择的单条证据读取、解析和展示，统一目标访问权限 |

当前采集范围是已登记媒体操作，普通聊天和 Responses 不因该开关自动进入证据采集，见[采集范围](../../service/media_evidence_scope.go)。本轮不扩大采集范围。

图片像素处理、格式交付及异步执行模块均实际存在，具体触发条件见 §4.4。代码存在只能证明有这条处理路径，不能据此排定生产 CPU 热点；本轮聚焦证据保存，是根据已确认的业务目标和重复处理事实收敛范围。

### 线上报告与验证边界

用户报告 pprof 样本中正文脱敏、正则和 JSON 处理占比较高，与上述代码中的重复工作相符。原始 profile 未在本次本地独立复核；中间件累计占比可能包含下游调用，正则与 JSON 子调用也可能重叠，因此不将报告中的 93.3% 换算为预期降幅。

这些信息足以支持删除存前处理，具体收益仍通过固定输入的前后对照与部署观察确认。

## 3. 优化方案

### 3.1 保存：保留原始字节与必要关联

目标流程：

```text
实际 I/O 有界捕获 → 原始字节保存到私有对象 → 按请求关联找到对象
```

正文不做 JSON/SSE/multipart 解析，不收集凭据用于正文回显扫描，不替换 URL，不因格式错误或片段不完整拒绝保存。请求头、查询参数等已采集内容如需保留，同样原样放入受保护证据对象，不扩充采集内容。

保存路径只保留定位、授权归属、对象位置和到期清理所需的关联，直接使用已有请求上下文。多个方向或重试交换通过固定内容名称及必要序号区分、防止覆盖，无需额外阶段字段或状态流转；业务成功/失败继续从业务数据库读取。

取消为证据内容额外维护的 `phase`、`complete`、`redacted`、格式有效性及字节统计，也不额外计算正文 SHA256 作为内容完整性证明。现有表按必要定位用途收敛，不为适配旧界面继续写入这些状态。

复用现有私有加密存储、访问控制及保留期清理。加密与底层写入属于保存基础，不要求改成公开对象或明文文件；本轮不另建证据框架、存储引擎、后台队列或跨请求去重系统。

### 3.2 查看：管理员按需解析、美化和预览

目标流程：

```text
管理员选择一条证据 → 鉴权读取 → 按需解析/美化/预览，或查看 raw / 下载
```

- 授权管理员可查看原始证据；按现有角色体系包含 Admin 与 Root，普通用户无权访问。
- 列表只加载定位信息；选中某条内容后再读取和处理，不因打开列表批量解析全部正文。
- 合法 JSON 可以美化，支持的图片或其它格式可以预览；这些能力不要求在保存时预先准备。
- 无法解析、被截断或含二进制的内容仍可查看 raw 或下载已有对象；展示转换不改写存储字节。
- 统一说明捕获内容可能不完整，不再为每条证据计算完整性结论。原始内容作为数据展示，不作为 HTML 或脚本执行。

### 3.3 故障与资源：业务继续，证据尽力保存

证据允许缺失。采集、存储或索引故障只能导致对应证据不可用，不能拒绝原本合法的业务请求、触发生成重试、改变结算或退款。业务本身的校验和必要存储仍按各自规则执行；异步任务恢复输入、正式结果等不属于可丢弃的证据。

保留有界缓冲、采集大小上限及有界存储等待，防止取证无限占用资源。达到采集上限即停止收集，不为此新增截断状态或完整性检查；可读时展示已有内容，无对象时显示无可用证据。

直接保存仍有捕获、缓冲、加密和 I/O 成本，也不会自动减少原有多个方向的落盘量。第一轮先删除正文处理与多余状态维护，再依据采样决定是否需要减少复制或改进写入方式；不以新增异步队列掩盖剩余成本。

## 4. 实施范围与顺序

### 4.1 功能影响：调整共用证据，保留日志业务

影响范围不止错误日志。错误日志、任务日志、使用日志和独立证据查询都调用同一套证据服务与组件；成功媒体请求也会保存证据，仅修改错误日志入口无法消除保存链路的主要开销。

| 功能与入口 | 需要适配 | 保持的业务能力 |
| --- | --- | --- |
| [错误日志详情](../../web/src/features/usage-logs/error/components/error-log-details-dialog.tsx)的“请求证据” | 共用组件切换为原始内容目录与逐条查看 | 错误分类、渠道归属、错误码、任务关联 |
| [任务日志详情](../../web/src/features/usage-logs/components/dialogs/task-details-dialog.tsx)的证据和请求快捷入口 | “用户请求详情”“转换后上游请求”改按内容名称定位，移除旧阶段、完整性及脱敏假设 | Task 状态、进度、结果、失败原因和账务 |
| [使用日志详情](../../web/src/features/usage-logs/components/dialogs/details-dialog.tsx)的“请求证据” | 复用调整后的证据查看组件 | 用量、费用、退款与统计 |
| [页面顶部证据查询](../../web/src/features/usage-logs/components/request-evidence-browser.tsx) | 同步新的定位信息、权限与逐条读取方式 | 按请求关联查询证据 |
| [证据清理](../../controller/system_task_evidence_cleanup.go)及监控 | 对象或事件定位结构变化时同步适配，不依赖已删除的证据内容状态 | 到期回收、对象可定位和清理健康检查 |

错误详情还展示独立的 `http_exchange` 诊断快照，由 [clienterrlog](../../clienterrlog/http_exchange.go)生成并保存到错误记录，单正文上限为 16 KiB。它不是私有证据对象，本轮不改其采集、脱敏或展示，也不把原始证据复制进错误记录。三类日志的业务记录与写入接口不因证据重构而重新设计。

### 4.2 共用改动：集中实现，入口复用

- [证据组件](../../web/src/features/usage-logs/components/task-evidence.tsx)及[请求接口](../../web/src/features/usage-logs/evidence-api.ts)：移除 `stage`、`phase`、`complete`、字节统计和服务端批量预览依赖，按内容名称与必要序号定位对象。各日志入口继续复用，不分别建立查看器。
- [任务请求快捷入口](../../web/src/features/usage-logs/components/task-request-details.tsx)：保留两个查看按钮，改用新的内容定位；不再按旧 `stage` 筛选，也不先批量下载全部原文。
- [原文弹窗](../../web/src/features/usage-logs/components/evidence-original-dialog.tsx)及[后端路由](../../router/task_request_evidence_router.go)：同步 Admin/Root 权限，删除“认证凭据已移除”等旧承诺；解析、美化按选中内容触发。
- [后端详情](../../controller/task_request_evidence_query.go)仅返回内容目录，选中后才读取对象；[正文读取](../../service/task_request_evidence_helpers.go)同步取消对新证据的正文 SHA256 强制比对，避免保存端不再生成摘要后仍被旧读取逻辑拒绝。真实对象缺失、过期或解密失败仍按读取结果呈现，不把解析失败当作对象不可读。

以上是依赖适配范围，不要求逐一改写所有调用页面。能由共用组件完成的变化集中实现，页面本身仅保留必要接线。

### 4.3 实施顺序

| 顺序 | 工作 | 完成标准 |
| --- | --- | --- |
| 1. 同步规则 | 将已确认的原始证据例外落实到[硬约束](../00-context/硬约束.md)第 5、6 节、相关入口约定及[证据架构](../20-architecture/音视频请求证据架构.md) | 明确只允许受保护证据保存原文，取消存前脱敏和取证失败阻断业务的旧要求；不扩大到其它业务数据 |
| 2. 简化保存 | 修改通用观察器及 Task 专属取证调用，删除保存前正文处理和非必要事件状态，复用对象定位与存储 | 原始捕获字节可保存；无论取证成功与否，原业务行为保持一致 |
| 3. 调整读取与入口 | 完成 §4.2 共用读取、权限、任务快捷入口及界面适配；定位结构变化时同步清理与监控 | 各入口可查阅同一份原始证据，管理员按需解析，内容解析失败不影响读取已有字节 |
| 4. 验证收益 | 按 §5 固定基线和请求集前后对照，再观察实际部署 | 确认网关进程 CPU 绝对成本下降，记录分配变化及主机效果，不预填提升比例 |

规则更新描述已确认的目标，代码及真实部署状态分别记录，不把方案当作已上线事实。当前事实文档已随本轮实现同步收敛；固定负载性能对照与真实部署验收仍是独立待办。

改动优先限于现有证据模块、读取接口及对应界面。图片响应交付、像素处理、通用请求缓存、CPU 自保、选渠和计费不纳入本轮。业务必需的协议解析与用量提取继续保留。

已有证据对象按原期限保留可读，已脱敏内容不能恢复为原文；不重写历史对象，不双写新旧内容，不新建平行证据体系。若涉及表结构调整，验证 SQLite、MySQL、PostgreSQL；确需修改原生接线时说明必要性及上游同步影响。

## 5. 验收与完成标准

### 5.1 行为验收

| 验收项 | 可观察结果 |
| --- | --- |
| 原始内容 | 合成凭据、转义 URL、重复字段、空白、Base64、multipart 和 SSE 的已捕获字节保存后保持一致；取证不重写正文 |
| 非法或不完整内容 | 格式错误、截断及读取中断不阻断业务；已有字节可 raw 查看或下载，不要求解析成功 |
| 业务不受取证故障影响 | 存储不可用、写入失败及取证上限不改变原业务响应、发送次数、Task 与资金结果；业务自身错误仍正常处理 |
| 管理员查看 | Admin/Root 可逐条解析、美化、预览及读取原文；普通用户被拒绝；列表不自动处理全部正文 |
| 共用入口 | 从错误日志、任务日志、使用日志及独立查询均能定位同一请求证据；任务两个快捷入口仍能找到对应内容，不因旧字段取消而显示假“不完整”或空结果 |
| 日志业务边界 | 错误分类、任务状态、用量与计费结果保持原行为；独立 HTTP 诊断快照保持现有规则，不混入原始证据 |
| 关联与生命周期 | 同请求多次交换不覆盖、不串请求；归属和到期清理有效；历史对象仍可读取 |

使用固定合成数据做确定性回归与 benchmark，按变化的行为更新旧测试：不再断言“凭据必须删除”“解析失败拒绝业务”或“每条证据必须完整”。不新增随机压力、sleep 计时或仅打印结果的性能测试。

### 5.2 可复现基线

`HEAD + 工作区` 仅用于说明本次事实核对范围，不能直接充当前后对照的可复现构建。实施测量时保留：

- 前后完整提交 SHA、未提交差异快照、实际构建产物标识，以及 Go 版本、构建参数；确认 profile 对应实际被测网关进程。
- 相同机器/容器配额、进程范围、存储介质及相关配置，包括证据开关、采集上限、保留期和并发设置；不保存配置中的密钥值。
- 固定合成请求与可控上游响应、请求数、图片数、载荷大小、并发及提交节奏。大 Base64、multipart、同步与异步路径分别报告，避免业务混合比例变化造成假收益。
- 测量起止、预热方式及原始 profile 的实际时长和总 CPU 样本。区间覆盖整个请求集及证据收尾，异步场景覆盖相应执行进程；不以客户收到响应或 GIN 结束时间代替全部工作结束。

管理员查看不混入保存基准，另做逐条读取与展示测量。profile 解读区分函数自身耗时与包含子调用的累计耗时，不能把相互包含的正则和 JSON 占比直接相加。

### 5.3 CPU 指标与判定

| 层次 | 指标与计算 | 用途 |
| --- | --- | --- |
| 主要指标 | 测量区间内网关进程用户态与内核态累计 CPU 时间增量之和；平均每请求 CPU 秒数 = 总 CPU 秒数 / 固定请求数 | 判断相同工作量是否减少本地计算；多进程执行时记录并汇总同一执行范围 |
| 辅助指标 | 分配字节/次数、证据保存耗时、峰值内存、实际保存量；平均使用核数 = 总 CPU 秒数 / 区间墙钟秒数 | 解释收益和剩余代价；耗时或内存改善不能替代 CPU 主指标 |
| 部署效果 | 可比负载下的主机 CPU 短窗口峰值、`system_cpu_overloaded` 拒绝数及其占经过同一自保入口请求的比例 | 判断是否缓解跨业务自保；保持阈值、采样和路由语义一致，记录主机其它负载 |

本地性能通过条件：行为验收通过，固定请求集的网关 CPU 总量及每请求成本确有下降，差异超过重复测量的波动；同时报告分配、存储和响应变化。未能区分测量波动时，标记收益未确认，不用调用栈占比下降宣称通过。

部署观察与本地验收分开记录。主机总 CPU 包含其它进程，进程级降幅不能直接套用到整机；Provider 排队、生成及网络耗时也不作为本地 CPU 收益。没有生产对照时不得承诺消除全部 503。

此前讨论的约 60% 或理想 80% 仅为有前提的测算情景，不是实施目标或验收门槛；93.3% 累计占比同样不代表可节省比例。实际降幅按 `(优化前 CPU 秒数 - 优化后 CPU 秒数) / 优化前 CPU 秒数` 报告。
