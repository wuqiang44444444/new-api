# 客户用量按计费单位拆分方案

## 问题与目标

客户用量用于查看调用和计费用量。全部客户与单客户的模型排行按客户模型和结算计费方式分组。同名模型在所选周期内采用 Token 和图片张数计费时分别展示两行，每笔调用、计量和净额只进入一个分组。

## 当前实际情况

只读核对本地 PostgreSQL 的 2026-11-11 发布日（2026-11-12 22:34 快照）。`gpt-image-2` 有 6,984 条 Token 结算记录，排行 Token 为 24,552,148。`gpt-image-2.6-sunburst-r` 有 103 条固定价乘图片张数的结算记录，合计 103 张，日志另有 481,891 Token 的调用遥测。两者分别有 76 和 8 个去重后的最终失败调用，缺少计费单位证据。这个样本的同名模型各自只有一种已知计费方式。

客户用量目前会根据图片请求路径标记完成张数缺项。全站排行与单客户排行又按模型名合并，因此把计费用量、调用遥测和交付张数混入同一展示。日志中的 `image_count` 是冻结结算使用的计费数量，`completed_image_count` 是独立的交付事实。详见 [计费表达式](../../pkg/billingexpr/expr.md#image-quantity)及[报表日汇总架构](../20-architecture/账单计费-报表日汇总架构.md#2-数据粒度与读取)。

## 优化方案

1. 在客户日投影合并前识别计费方式。以请求或任务当时的结算快照、结算单位和规则为准。固定价请求须有按图片数量计价的证据才归入按张，张数读取有界的结算数量。Token 行只汇总 Token 计量，按张行只汇总计费张数，已知按秒等口径沿用现有证据。缺少单位的失败、未归属的退款或旧冻结记录保留调用和金额，计费单位保持未知。上游用量、交付产物、钱包入账和正式账单各自沿用原合同。
2. 日报冻结客户模型和计费方式，再按周期合并。全站排行按该组合分页排序，单客户使用同一批次的分组数据。已有按模型聚合的读取方继续从同一份叶行合计。表格用明确的计费方式标签和单位列表达每行，非适用单位显示 `—`，适用但计量缺失时显示未记录。
3. 用量候选和发布指针记录计费单位投影版本。升级后由现有日报任务发现历史旧版本，按最近日期自动重建用量日报，并复用原有租约、资源门控、覆盖校验和失败重试。更新前继续提供已发布版。已受理的旧版导出引用保持有效。
4. 回归覆盖同名混合计费、按张数量与 Token 遥测并存、缺证失败和旧代际，核对全站排行、单客户分组及总计的调用和净额守恒。运行相关 Go、Vitest、类型检查、lint、`task docs:check` 和 `task ai:check`。

## 实施与验证

- 全客户和单客户排行使用冻结的模型及计费方式分组。旧代际的排行保留调用和净额，并标示未知计费方式。旧总览仍读取原快照，更新历史页面需发布重算后的日报。
- 从本地 PostgreSQL 只读提取两模型的 7,087 条消费记录所需结算字段，在隔离 SQLite 中运行新日报构建和排行读取。结果为 `gpt-image-2` 的 24,552,148 Token 与 `gpt-image-2.6-sunburst-r` 的 103 张。实际库的历史发布由升级后运行的后台任务负责。
- 在隔离库模拟程序升级后已存在 120 天前的旧版发布与旧版候选。运行现有日报任务可自动发现日期、重建候选并切换用量发布指针。同日账单指针保持原值，下一轮跳过已更新日期。
- 本地 PostgreSQL 只读复核确认，2026-11-11 日报已于北京时间 2026-11-12 23:24:35 发布计费单位投影版本 1。发布结果为 24,552,148 Token 和 103 张，两模型的缺证失败分别保留为 76 次和 8 次。
