# 公开 API 响应头与请求追踪迁移方案

## 问题与目标

客户评估 TokenAI 时将服务识别为 New API 网关。截图未提供其识别依据。源码中可确认两个响应头带有
上游项目标识，分别是 `X-New-Api-Version` 和 `X-Oneapi-Request-Id`。本方案拟收敛公开版本信息，
并让客户用统一的 `X-Request-Id` 向 TokenAI 查调用、费用和故障。变更范围为面向客户的 HTTP 响应；
具体域名、路由和代理层以上线前的实际拓扑清单为准。

请求 ID 迁移只改对外字段名。同一个本站 ID 应贯穿响应、既有错误响应体、消费日志和账单查单；
上游请求 ID 继续独立采集。模型调用、计价、资金扣退、Task 和历史账单沿用现有业务合同。

## 当前实际情况

以下结论来自仓库静态检查。生产实际响应、代理覆盖规则和仓库外的读取方待核对。

| 项目 | 已确认行为与改动影响 |
| --- | --- |
| `X-New-Api-Version` | 全局中间件发送运行版本。仓库内未发现读取这个头的业务代码。控制台版本检查读取 `/api/status` 的 `version`。公网版本头收敛的主要兼容风险是仓库外的探针和运维脚本。 [中间件](../../middleware/cors.go) · [状态接口](../../controller/misc.go) · [控制台版本检查](../../web/src/features/system-update/use-system-update.ts) |
| `X-Oneapi-Request-Id` | 中间件生成本站 ID，写入 Gin 上下文、Go 请求上下文和响应头。账单审核错误组件在响应体缺少 `request_id` 时读旧头，墨行 Seedance 验证脚本也直接读旧头。直接撤下旧头会破坏这些读取方及同类外部集成的查单和排障。 [请求 ID 中间件](../../middleware/request-id.go) · [账单审核错误组件](../../web/src/features/billing-reconciliation/components/source-review-error.tsx) · [验证脚本](../../cmd/verify-moxing-seedance/main.go) |
| 上游请求 ID | 上游请求 ID 提取优先读取直接中转的旧头，并兼容上游 `x-request-id` 等字段。响应头转发逻辑拦截旧头，避免上游同名字段覆盖本站 ID。全局替换 `common.RequestIdKey` 会同时改变这两处的识别行为。部分转发路径可能携带上游自己的 `X-Request-Id`，因此对外发布新头时必须明确唯一的本站值。 [上游请求 ID 提取](../../relay/channel/upstream_request_id.go) · [响应头转发](../../service/http.go) |
| 扣费与对账 | 消费日志分别记录已结算的 quota、本站 `request_id` 和上游 ID；账单以已落库的事实为准。只迁移响应头且保留 ID 原值，预期扣费和历史金额无变化。客户侧查单依赖能拿到本站 ID；上游对账依赖南向提取规则持续正确。 [消费日志](../../model/log.go) · [客户与上游对账架构](../20-architecture/账单计费-客户与上游对账架构.md) |

版本头直接携带 New API 版本元数据。仓库现行硬约束禁止删除、替换或弱化相关身份、署名、授权和
元数据，目前没有针对公开响应头的例外。**在执行公网隐藏前，需明确并记录这条规则允许调整的公开
范围**，包括如何处理仍带历史标识的旧追踪头。把规则放到代理层执行也受同一约束。新增中性追踪头和迁移
读取方可以独立推进。开源署名、原项目链接、许可证及相应源码入口继续按原约束提供。
[项目硬约束 §1](../00-context/硬约束.md#1-项目与技术) · [开源声明](../../NOTICE)

## 优化方案

### 目标响应

| 阶段 | 公开版本头 | 公开请求 ID |
| --- | --- | --- |
| 当前源码 | `X-New-Api-Version` | `X-Oneapi-Request-Id` |
| 兼容期 | 在明确允许的客户入口隐藏 `X-New-Api-Version` | 同时返回 `X-Request-Id` 和 `X-Oneapi-Request-Id`，两者值完全一致 |
| 迁移完成 | 沿用已确认的公开范围 | 在同一范围内只发布 `X-Request-Id` |

`X-Request-Id` 的权威值来自本站已经生成的请求 ID。客户端传入的同名请求头、上游响应头和边缘代理
自身的追踪 ID 都不能用来填充这个字段。新字段在交付响应时只写一个值；内部请求上下文、错误体已有的
`request_id`、日志字段和上游提取规则沿用当前实现。范围以外的响应继续按当前合同交付。

### 实施步骤

1. **核对部署基线。** 盘点公网域名、CDN／反向代理、源站可达性、管理入口和实际响应。覆盖原生 API、
   对外 Link API 和浏览器实际使用的入口。核对官方示例、SDK、监控、调用脚本和客户集成中对两个旧头的
   已知依赖。记录公网与源站返回头的差异，确认是否已有代理写入 `X-Request-Id`。
2. **发布新追踪头。** 首选在已有客户入口的最终响应阶段，将源站旧追踪头中已生成的本站 ID 复制到新头，
   并覆盖已有的同名响应值。若代理无法在去除旧头前稳定取到该值，再采用独立的响应交付逻辑和最小接线。
   `common.RequestIdKey` 继续服务现有内部上下文和南向采集。对浏览器跨域接口，仅在现有允许的来源和
   路由内按需暴露新响应头，并验证 JavaScript 可以实际读取它。
3. **迁移读取方。** 账单审核错误组件优先读取响应体 `request_id`，缺失时读新头，再兼容旧头。验证脚本
   同样优先读新头。同步更新受影响的公开 API 文档、示例及所维护的客户端。确认已知外部依赖的迁移，
   约定旧头下线窗口；服务端访问日志无法据此判断客户代码是否仍在读取旧响应头。
4. **收敛公开版本头。** 在明确第 1 节硬约束所允许的范围后，使用已有公网入口的响应头规则隐藏
   `X-New-Api-Version`，覆盖源站和上游透传的同名值。保留源站版本诊断、`/api/status` 的现有字段及
   开源信息入口，并复核不同公网入口的实际输出。版本头规则可独立上线和回滚。
5. **灰度撤下旧追踪头。** 已知读取方完成迁移、下列验收通过后，在明确的公网范围内先保留新头，再撤下
   旧头。确认代理仍能取到本站 ID，重复执行真实查单和对账核验后再扩大范围。

### 验收与回滚

| 验收面 | 通过条件 |
| --- | --- |
| 公网响应 | 非流式、SSE、应用 `4xx/5xx` 和一条已发布的异步任务入口均覆盖。兼容期两个头值逐字一致，且新头只出现一次。模拟上游也返回 `X-Request-Id`，确认客户拿到本站 ID；有 `request_id` 的错误体与本站 ID 一致。网关自身生成且未到源站的错误沿用其现有行为。 |
| 调用与计费 | 在固定价格和可控用量下，对比变更前后的状态码、接口响应结构、SSE 完成行为、用量、实扣及结算状态。通过公网发送一条真实低额度请求，用新头原值查到客户账单明细，核对扣费；再用已有请求 ID 查一条历史账单。 |
| 上游对账 | 在上游提供真实追踪头的样本中，核对后台分别保存本站与上游 ID，且双方 ID 仍可按既有方式筛选。公开的新头与本站 ID 一致。 |
| 运维与兼容 | 目标范围内确认版本头按计划隐藏，控制台版本检查和版本诊断可用。兼容期验证旧客户端、账单审核错误提示和墨行验证脚本；涉及跨域的调用用浏览器实测。 |

如果灰度出现新头缺失、查单关联不上或外部集成中断，恢复公开旧追踪头；如新头值正确可继续双发，
值错误则同时回滚新头规则。版本探针受影响时独立撤回版本头规则。回滚复核原调用成功、原账单可查和
双侧 ID 关联；账单、Task 和数据库也无需随响应头规则回滚。

本记录为实施草案。实际部署拓扑、外部依赖、规则允许的范围及真实调用结果待验证。
