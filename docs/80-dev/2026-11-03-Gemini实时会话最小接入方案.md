# Gemini 实时会话最小接入方案

## 1. 问题与目标

客户希望测试 `gemini-3.8-live-extended`。当前本地代码和本次核查的 NEWAPI 上游均缺少
Gemini 原生 Live WebSocket 履约链路，添加模型名称或同步上游不能直接提供该能力。

目标是在最小原生文件改动下，支持 Google Gemini Developer API 的原生 Live 会话，复用现有
Token 鉴权、模型权限、渠道、模型映射、资金和消费日志底座。本文是待实施方案，不代表代码完成、
真实 Provider 验收或生产发布；本次仅编写文档。

## 2. 当前实际情况

### 2.1 已核查的代码事实

- 本地 `router/relay-router.go` 仅提供 Gemini 生成类 POST 入口；`/v1/realtime` 使用
  `RelayFormatOpenAIRealtime`，不是 Gemini Live 协议。
- `relay/channel/gemini/adaptor.go` 的生成请求使用 `generateContent` 或
  `streamGenerateContent?alt=sse`；SSE 不提供 Live 双向会话。
- `relay/websocket.go` 和 `relay/channel/openai/relay_realtime.go` 依赖 OpenAI 实时事件和
  `RealtimeUsage`，不宜直接套用到 Gemini。
- `service/quota.go` 的现有 WebSocket 计费按 OpenAI 文本、音频结构处理，表达式结算入口不能
  直接完整承载 Gemini 音频、思考等用量；需要独立归一层。
- 可复用 `service.SelectChannelForRequest`、`middleware.SetupContextForSelectedChannel`、
  `relay/helper/model_mapped.go`、`service/billing_session.go` 的资金原语，以及 `pkg/wsmanager`
  和 `service/api_request_evidence_realtime.go`。

2026-11-03 通过 GitHub API 获取并读取官方 `main` 源码快照：
[`9b473a3fe4fed8d18980fd8d3c6a8908847a5f25`](https://github.com/QuantumNous/new-api/commit/9b473a3fe4fed8d18980fd8d3c6a8908847a5f25)，
提交时间为北京时间 2026-11-03 15:17。该快照没有 `BidiGenerateContent` 实现；
`relaykit/relayconvert/reasoning/gemini.go` 中出现旧 Live 模型名称只涉及思考参数处理，
不能作为 Live 支持证据。此结论限定于该源码快照，不代表官方演示站或本站生产实例的实测结果。

### 2.2 外部官方协议证据

| 项目 | 官方合同及接入影响 |
| --- | --- |
| 连接 | WebSocket 路径为 `/ws/google.ai.generativelanguage.v1beta.GenerativeService.BidiGenerateContent` |
| 首帧 | `setup.model` 为 `models/{model}`；必须读到首帧才能按模型鉴权和选渠 |
| 握手后消息 | 收到 `setupComplete` 后发送内容；客户消息包括 `clientContent`、`realtimeInput`、`toolResponse` |
| 用量 | `usageMetadata` 提供输入、输出、思考及模态明细；需要独立归一 |

依据：[Live WebSocket 协议](https://ai.google.dev/api/live)及
[连接与鉴权指南](https://ai.google.dev/gemini-api/docs/live-api/get-started-websocket?hl=en)。

官方模型 ID 为 `gemini-3.8-live-extended-thinking`。客户给出的短名称可通过已有
`model_mapping` 精确映射。该模型的 `turnComplete` 后仍可能产生后台推理、工具调用或音频，
不能把它当作会话结束信号。依据：[官方模型说明](https://ai.google.dev/gemini-api/docs/models/gemini-3.8-live-extended-thinking)。

Google Live 每轮重新计入当前上下文中的历史 token，不能只取最后一次会话用量，也不能把相邻轮次
的 prompt 数值相减当作新增消费。依据：[官方计费说明](https://ai.google.dev/gemini-api/docs/live-api/best-practices#pricing-billing)。

### 2.3 未确认项

- 实际 Channel 是否提供 Google 原生 Live 路径、账号是否有目标模型权限，尚未真实调用。
- 目标模型实际用量报告的触发时机、单轮多次报告的覆盖关系、思考 token 与输出总量的包含关系，
  必须通过官方说明和真实回包核对，不凭字段名称推断。
- Google 账单与本站计费结果、代理超时和部署反向代理的 WebSocket 行为，尚未验证。

## 3. 优化方案

### 3.1 首期边界

新增独立的 Gemini 原生 Live handler，沿用现有 Gemini Channel；不新增 Link 合同或第二套账本，
不通过模型名称包含 `live` 推断资格。现有 HTTP Gemini、OpenAI Realtime 和 Responses 路径保持原语义。

首期覆盖单连接多轮会话、文本/音频/图像输入、音频及文本输出、工具事件、打断和后台推理事件转发。
工具执行、音频采集播放及转码由客户应用承担。首期不包含 Vertex AI、OpenAI 实时协议转换、
临时 Token 签发和跨连接恢复；不发布为完整 Live API 全功能兼容。

恢复配置首期明确拒绝，不透传上游恢复句柄建立跨客户可复用能力；连接终止后客户新建会话。
若后续支持恢复，须另行解决用户/应用隔离、模型与 Channel 绑定、凭据变化及跨连接用量边界。
依据：[官方会话恢复协议](https://ai.google.dev/gemini-api/docs/live-session)。

### 3.2 请求与控制流

1. 注册官方形状的 GET 路径。路由局部将 `key` 或 `x-goog-api-key` 转为本站鉴权输入，调用现有
   `TokenAuth`；只接受本站 Token，不把客户凭据传给 Google。普通日志不得记录含 Key 的 URL。
2. 鉴权后升级 WebSocket，设置首帧超时、消息大小和会话资源限制；超时或非法首帧立即关闭。
3. 解析 `setup.model`，保留客户模型与上游模型的区别。按客户模型执行 Token 模型限制、分组、
   指定渠道、请求限流及现有适用策略；禁止通过直调选渠绕过这些检查。
4. 使用现有渠道选择服务，在候选过滤阶段限制为明确支持该入口的 Gemini Channel，指定渠道也必须
   通过相同检查。不得先随机选到其他类型再静默回退。模型映射后只改写 `setup.model`。
5. 校验 `maxOutputTokens` 等计费相关数量，复用现有同概念上界；可选标量保留缺失与显式零值。
   不静默删改官方合法的配置，未支持的恢复功能明确拒绝。
6. 冻结本连接的 Channel、Provider 模型、连接和价格事实，预扣成功后才建立上游连接并发送 setup。
   上游握手使用渠道凭据，保留 Channel Base URL、代理、TLS 和适用 header 配置的既有语义。
7. 上游返回 `setupComplete` 后进入双向消息转发；拒绝重复 setup，不因 `turnComplete` 关闭连接。
   不缓存完整音视频会话；使用有界背压，任一侧关闭时停止另一侧及后台协程。
8. 统一收尾处理正常结束、客户断线、Google 断线、额度不足和本地错误；发送 setup 后不自动重发、
   换渠道或恢复。上游错误和关闭原因净化后返回，不输出上游凭据及内部地址。

升级前错误使用现有 HTTP 错误合同；升级后使用 WebSocket 关闭码和净化原因，不能继续写 HTTP JSON，
也不伪造 `setupComplete` 或业务完成事件。

### 3.3 最小文件改动面

以下文件名为拟定位置，实施前以实际接口为准；不是已完成清单。

| 位置 | 责任 |
| --- | --- |
| 新增 `router/gemini_live.go` | 路由注册和局部 middleware 组合 |
| 原生路由注册入口 | 仅增加一行注册调用 |
| 新增 `middleware/gemini_live.go` | Live 路由的鉴权输入适配与首帧后的权限、限流接线 |
| 新增 `controller/gemini_live.go` | WebSocket upgrade、首帧约束及错误收尾 |
| 新增 `relay/gemini_live.go` | 选渠、映射、冻结和会话生命周期 |
| 新增 `relay/channel/gemini/live.go` | 上游 URL/凭据、双向转发及 Live 用量读取 |
| 新增 `service/gemini_live_billing.go` | 用量归一、预扣补充、结算和消费日志 |
| 渠道约束机制的必要接线 | 新增 Live 候选过滤；主体逻辑隔离到新增文件 |
| 对应新增测试文件 | 可观察协议、权限、计费和失败路径回归 |

原生文件改动仅用于路由注册与候选过滤，必要性是复用统一入口和选渠约束；不得修改 Gemini 普通生成
URL 或 OpenAI 实时 handler 来兼容此协议。未来同步上游的冲突面集中于这两个接线点；若上游提供
同一路径，必须合并为唯一 handler，不保留两套协议实现。

预计不需要数据库迁移、前端页面、新 ChannelType 或 `relaykit` 公共 API。若实施中证明必须修改
共享 DTO 或资金接口，应先在本文说明缺口和新增改动面，不能为了缩短代码把 Live 塞入 OpenAI DTO。

### 3.4 资金与用量

遵循[表达式计费设计](../../pkg/billingexpr/expr.md)及
[计费事实架构](../20-architecture/账单计费-异步任务与计费事实架构.md)的适用边界；Live 是在线会话，
不创建异步 Task/attempt，不建立独立余额或账本。

- 复用现有资金来源和 `BillingSession` 原语，建立 Live 专属用量归一和结算入口，不直接照搬
  `PreWssConsumeQuota` / `PostWssConsumeQuota` 的 OpenAI 事件假设。
- 每个确认的计费单元记录输入、输出、音频和思考等归一事实；按实际报告语义防止同一报告重复入账。
  不在报告缺少唯一 ID 时凭正文 hash 或 token 数相同推断重复；实现前先确定报告与计费单元的关系。
- 逐轮计入应计费的上下文，不能只对 prompt 增量收费；思考和模态明细不得与总量重复相加。
  每轮上下文长度与会话累计输入消费分开处理，避免用累计消费误触发表达式上下文档位。
- 连接开始先预扣；会话中通过现有额度 reservation 补充资金，额度不足时停止输入并关闭连接。
  用量报告存在延迟，第一版还应明确单连接时长和资源上限；不能宣称余额检查可消除所有在途成本。
- 每次消费使用创建时价格事实。终止时只结算一次已确认用量并释放剩余预扣，不因最后一次通信错误
  退掉已有消费；上游尚未受理时的失败释放预扣。
- 缺失用量不得伪造为零或套用 OpenAI 音频估算；停止继续放量，记录不完整用量和平台成本待核对，
  不把未知 Provider 成本冒充已确认客户收费。正式收费前必须确定缺失用量处置口径并真实对账。
- 复用集中 quota 安全换算及 clamp 审计，绑定客户模型、用户、Token、应用及所选 Channel 写消费日志。
  会话累计值不能通过单请求 int32 饱和丢失总消费；到达单条日志/单次结算容量边界前结束或分段结算，
  不引入新的余额事实源。

### 3.5 安全与观测

复用 `wsmanager` 的渠道关闭能力，以及现有私有请求证据的开关、隔离、容量和保留规则。未启用采集时
不存媒体正文；不得为 Live 新增普通原文日志。恢复句柄、系统指令、工具正文、媒体和完整上游 URL
不进入普通日志。日志保留请求关联标识、客户模型、渠道、结束分类、时长和用量完整性等净化摘要。

## 4. 验证与实施顺序

1. 先验证实际 Channel 原生端点和账号权限，明确用量报告及思考 token 口径，形成脱敏结论。
2. 新增独立入口与单连接转发，证明官方 SDK 可通过本站 Base URL 完成 setup 和多轮会话；检查
   SDK 实际拼接路径，不额外发布未经验证的版本别名或路由别名。
3. 接入首帧后的权限、限流、候选过滤和固定渠道，验证越权在发送上游 setup 前拒绝。
4. 接入资金、冻结价格、用量归一及一次性收尾，完成下表回归后再开放受控真实测试。
5. 完成真实账单核对和部署 WebSocket 验收后，才决定对外发布；实施完成事实另行收敛到对应当前文档。

| 边界 | 必须证明的行为 |
| --- | --- |
| 首帧 | 非 setup、无模型、重复 setup、超时和超大消息拒绝；显式零值不丢失 |
| 授权与选渠 | Token 模型限制、分组、固定渠道和模型映射生效；非 Gemini 候选不被选中 |
| 协议 | setupComplete、多轮音频、工具响应、打断正常；turnComplete 后后台消息继续转发 |
| 断线 | 双向关闭、有界背压、GoAway、取消及渠道禁用均能收尾，不自动重发或重选 |
| 计费 | 多轮上下文、模态、思考、不完整用量、预扣失败、余额不足及异常断线无重复扣费或整单误退 |
| 隔离与安全 | 客户 Key 不发送给上游，渠道 Key 不返回客户，恢复请求明确拒绝，日志无媒体和凭据 |
| 回归 | 原生 Gemini HTTP、OpenAI Realtime 和 Responses 行为不变 |

后端新增测试按项目要求使用 testify 的 require/assert，优先确定性协议与资金边界测试，不用大量循环、
sleep 或日志断言代替合同验证。实现时运行最窄相关测试；若触及 `relaykit/`，额外执行
`cd relaykit && GOWORK=off go build ./...`。

本方案文档执行 `task docs:check` 与 `task ai:check`；后续修改公开 API 文档时额外执行
`cd web && bun run docs:validate`。真实 Provider、账单及灰度验收当前均未完成。
