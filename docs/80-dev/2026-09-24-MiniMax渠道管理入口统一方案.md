# MiniMax 渠道管理入口统一方案

## 1. 问题与目标

当前管理端分别展示原生 MiniMax 与 MiniMax 标准视频渠道。管理员需要理解两个技术类型，容易将
同一品牌下的不同接入方式误认为重复实现。用户已确认采用“统一管理入口、保留执行边界”的方向。

本方案的可见结果：新建渠道只出现一个 **MiniMax** 选项，再明确选择“原生接口”或“京东云 · 标准视频”；
列表统一展示 MiniMax，并标明接入方式。两条渠道记录仍然独立，不合并配置、凭据、状态、用量或账单。
API 调用方继续使用已发布客户模型和对应接口，本次不改变客户请求形状或公开身份边界。

本文方案已完成代码实现和本地自动化验证；部署与管理页面人工验收仍待完成，不代表生产已发布。
实施未修改业务渠道数据、未调用 Provider、未触发视频生成或付费测试；数据库验证使用独立临时实例。

### 1.1 架构依据与范围

- [硬约束](../00-context/硬约束.md)第 2—4、7 节：原生与 Link 边界、类型化身份、冻结事实及最小入侵。
- [Seedance 专用渠道与 Link 架构](../20-architecture/Seedance专用渠道与Link架构.md)：统一北向、
  声明与实例配置分离、确定性选渠及不进入原生分发池的标准视频约束。
- [公开模型元数据投影架构](../20-architecture/公开模型元数据投影架构.md)：能力和参数由权威声明投影。
- [异步任务与计费事实架构](../20-architecture/账单计费-异步任务与计费事实架构.md)：执行及资金事实边界。
- [MiniMax 标准北向与京东云南向适配方案](../99-archive/2026/09/2026-09-23-MiniMax标准北向与京东云南向适配方案.md)：
  已有类型化接线的设计背景；当前实现及参数范围须结合代码和后续验证记录核对。

本方案只增加管理展示分组与必要的管理查询能力，不新增运行时身份、插件 ABI、Provider 能力表、
路由、Task 或计费账本。不得以管理展示分组改变 Link 的履约资格。

## 2. 当前实际情况

以下为实施前只读代码核对所得事实，记录本次改动的依据；实现后的管理行为见第 7 节及当前事实文档。
本轮未重新验收 Provider 能力或生产配置。

| 位置 | 当前事实 | 对设计的影响 |
| --- | --- | --- |
| `plugins/tasks/hailuo/plugin.js` | 绑定类型 35，已含 H3 多模态处理，调用 MiniMax 官方 `/v2` 视频协议 | 不应把原生渠道描述为“不支持 H3”；本次不改其协议实现 |
| `relay/relay_adaptor.go` | 类型 35 解析到 `hailuo`；类型 64 先进入专用适配器分支 | 展示统一不能合并适配器身份 |
| `router/video-router.go` | 原生视频和 ModelArk V3 使用不同的渠道解析入口 | 不把统一管理入口解释为统一所有北向 API |
| `model/task_video_snapshot.go` | 标准视频连接冻结依赖真实类型及协议事实 | 不修改存量 Channel 或 Task 的类型 |
| `web/src/features/channels/constants.ts` | 35、64 各有独立管理名称和选项 | 创建选择器需要管理展示投影，不应全局删除数字类型定义 |
| `web/src/features/channels/lib/channel-form.ts` | 类型 64 独立写入京东视频协议、无素材协议和声明版本相关字段 | 保存继续复用原路径 |
| `web/src/features/channels/components/drawers/minimax-protocol-fields.tsx` | 已读取配置声明，但说明仍硬编码早期文生 6 秒、768p 范围 | 删除过期能力说明，改读声明 |
| `controller/channel.go` | 列表及搜索接收单值 `type`；列表负责分页，返回按类型统计 | 聚合筛选需要服务端支持，不能拼接前端分页 |

会话中渠道 137 为原生类型、138 为标准视频类型，仅用于说明存量展示；实施不得硬编码这两个 ID。
渠道名称含 JD 不构成京东协议身份，实际展示必须读取持久化类型和已登记协议。

## 3. 优化方案

### 3.1 管理分组与真实身份

| 管理分类 | 接入方式 | 真实身份 | 履约规则 |
| --- | --- | --- | --- |
| MiniMax | 原生接口 | `ChannelTypeMiniMax = 35` | 沿用原生能力、通用分发及现有插件支持的入口 |
| MiniMax | 京东云 · 标准视频 | `ChannelTypeMiniMaxLink = 64`，`jdcloud_video_task_v1` | 沿用 ModelArk V3 标准视频、现有类型化校验和冻结执行 |

“MiniMax”分组只存在于管理界面。前端以局部、静态的展示映射组织选项，不持久化 `family`、
`mode` 或新的渠道身份字段；API 保存负载继续传真实 `type` 和现有配置。

原生方式使用“原生接口”，不称为“官方直连”：原生类型可以配置兼容代理地址，类型不能证明直连。
64 的京东标签应与已登记协议对应；未来未知协议显示明确的未识别配置状态，不默认标成京东。
不得根据模型名、渠道名、Base URL、价格或请求字段推断接入方式。

### 3.2 新建表单

流程为：选择 MiniMax → 明确选择接入方式 → 填写连接和模型配置 → 查看对应客户接口说明 → 保存。

1. 创建选择器中只保留一个 MiniMax 管理选项，其他渠道选择行为不变。接入方式带可见标签和简短说明，
   复用现有选择组件，不新增一套选择器或页面向导。
2. 新建 MiniMax 时要求显式选择接入方式；选择前不允许提交，不从 URL 或名称自动选中。
   未选状态仅为表单交互状态，不作为虚拟数字类型发送给后端。选择后直接设置真实 `type`。
3. 原生方式展示原生已有字段；京东方式复用现有协议字段、配置声明、模型映射、价格和版本校验。
   不向京东方式展示无效的 Priority、Weight 或 fallback 配置；不改变原生方式的这些能力。
4. 客户调用接口只读展示；京东明确展示 `/api/v3/contents/generations/tasks`。原生接口说明复用
   原生已有能力信息，不因选中 MiniMax 就声称全部模型支持同一视频接口。
5. 插件版本保留在可展开的诊断信息中，保存仍携带现有声明版本。不要求管理员填写协议 JSON、字段映射脚本。
6. 在未保存的新建表单切换接入方式时，保留名称、备注、分组等通用信息；清除密钥、连接、模型清单、
   模型映射、协议字段、声明快照及原方式专用选项。同步清理相关校验错误，提示需要重新填写专用配置。
   该行为只清理表单草稿，不能删除全局模型价格或修改其他持久配置。
7. 默认连接等配置优先读现有声明，只用于新建或明确切换后的空字段；不得覆盖管理员输入。
   不因京东官方示例使用 HTTPS 而收紧 Channel Base URL 的绝对 HTTP(S) 合同。

展示分组和接入方式的派生逻辑在一个局部模块集中维护。已有表单 `type` 仍为保存和字段分支依据，
不保留可与 `type` 独立漂移的第二份已选身份。异步声明响应必须绑定当前方式：切换后旧响应不得回填新表单。

### 3.3 编辑、复制与存量记录

- 编辑读取持久化类型和协议，回显 MiniMax 分类与接入方式；此管理入口不提供 35 与 64 的原地互转。
  现有 MiniMax 编辑器锁定整个类型选择，包括改为其他品牌；需要不同类型时新建渠道。
  本次不为原生写接口增加新的通用改型禁令，也不以界面锁定替代后端既有校验。
  锁定按原始已保存类型判断；其他原生渠道仍可选择原生 MiniMax，并可在保存前改回，沿用原生字段保留行为。
- 需要另一种接入方式时新建渠道。普通复制保留真实类型，沿用现有凭据复制、权限和默认配置处理规则，
  不新增跨类型复制或自动转型功能。
  京东标准视频的副本初始停用，避免与原渠道争用同一个已启用客户模型；原渠道状态不变。
- 原生类型 137 即使名称含 JD，仍显示“MiniMax / 原生接口”；138 显示“MiniMax / 京东云 · 标准视频”。
  列表保留两条记录，各自展示 ID、名称、状态、分组和用量。
- 不执行数据迁移，不批量重命名、启停或合并渠道，不修改密钥、价格、历史 Task、attempt、日志和账单。
- 未知类型或未知协议保留现有诊断能力，不能因为创建选择器合并了选项而丢失存量记录或错误归类。

### 3.4 列表、筛选与服务端查询

类型单元格统一使用 MiniMax 图标和主名称，以可见文字标注接入方式，不能只靠颜色或悬浮提示区分。
技术类型编号可在详情或诊断位置查看；不修改全局类型常量来掩盖真实类型。

筛选包括“MiniMax（全部接入方式）”“MiniMax · 原生接口”“MiniMax · 标准视频”。
标准视频子项按类型 64 筛选，不将该类型下未知协议误标为京东；具体接入方式仍在行内展示。
前者查询 35、64，后两者分别查询单个类型。实际计数为 0 的选项及已选项保留规则沿用现有列表约定。

现有管理列表与搜索接口新增可选 `types` 参数，前端聚合选项发送 `types=35,64`：

| 输入 | 约定 |
| --- | --- |
| 不传 `types` | 完全沿用原 `type` 和无筛选行为 |
| `types=35,64` | 按类型集合过滤；空格裁剪，重复数值去重 |
| `types` 显式为空、含空项、非整数、非正数或超出类型整数范围 | 返回 HTTP 400 管理参数错误，不扩大成全量查询 |
| 同时提供 `type` 和 `types` | 返回 HTTP 400，不建立隐式优先级 |
| 重复提供 `types` 查询键，如 `types=35&types=64` | 返回 HTTP 400；集合只接受单个查询键内的逗号分隔值 |
| 合法但没有记录的类型值 | 返回空匹配，不推断其他类型或自动回退 |

`types` 是管理查询条件，不是模型资格、路由或权限配置。解析与过滤实现放在新增文件，使用参数化
GORM 条件；不增加数据库列、索引或特定数据库语法。

列表、搜索、标签模式都必须在现有分页之前应用同一类型集合语义。排序、状态、分组、关键字及模型
筛选保持组合生效；`total` 沿用普通模式的渠道数或标签模式的标签数语义。
`type_counts` 继续按真实类型返回，并保持当前“应用其他筛选、排除类型筛选”的统计范围；前端仅将
35、64 计数相加显示 MiniMax 总数。不得两次拉取分页结果后合并，也不得重复计算子项与父项。

前端列表请求、搜索请求、query key 和可恢复筛选状态须一起接通 `types`。切换筛选重置到第一页，
行选择继续按真实 Channel ID，不使用管理分类作为行标识。批量操作继续作用于明确选中的记录。

### 3.5 插件声明、能力说明与测试操作

京东表单继续从 `/api/channel/minimax/configuration` 读取一次合法声明快照。模型、参数范围、
固定策略等只展示声明中已提供的信息；没有声明的数据不由前端复制常量、猜测或补成支持。
如现有前端类型不足，只补齐对现有响应的类型描述及展示，不借本任务扩展插件 ABI。

移除早期“仅文生、6 秒、768p”的硬编码说明。声明加载失败显示错误和重试操作，京东配置不得在
缺失有效声明版本时保存，也不能回退原生表单。保留现有版本过期的服务端拒绝机制，提示重新加载配置。
插件的激活、晋升、停用和旧任务精确版本解析规则均不改变。

测试及模型获取操作仍依据真实类型和已有能力决定，不使用 MiniMax 展示分组派发探针。
原生保留现有测试入口；京东不得误用 Chat 探针。不支持的操作明确展示不可用及原因。
业务调用记录与管理测试记录保持原含义，不用某次业务成功覆盖“未测试”字段。
本次不新增付费视频验收按钮，也不自动触发创建、轮询、下载或计费。

### 3.6 标准视频与原生边界不变量

| 边界 | 本次必须保持 |
| --- | --- |
| 北向合同 | 标准视频仍为统一 ModelArk V3；原生入口和 DTO 不变 |
| 路由与资格 | 64 不进入原生 Ability 或通用分发池；管理筛选不产生履约资格 |
| 渠道解析 | 保持现有类型化确定性选择及保存/启用唯一性校验，不新增请求时复检 |
| 插件职责 | 原生 `hailuo` 与类型化 `minimax-link` 各按现有合同运行，不互相替代或降级 |
| 执行与资金 | durable attempt、单次 POST、unknown 禁止重发、冻结连接/版本及资金保障规则不变 |
| 元数据与素材 | 已发布参数、素材支持和公开脱敏规则不变，管理界面不建立第二套能力事实 |
| 计费 | 计费身份、表达式、预扣、结算和 Provider 成本证据均不因管理分组改变 |

## 4. 实施范围与最小入侵

| 改动位置 | 必要性与最小接线 | 上游同步影响 |
| --- | --- | --- |
| 新增局部 MiniMax 管理展示模块 | 集中选项分组、标签及真实类型映射，仅供管理组件使用 | 新文件隔离，不推广成全渠道注册框架 |

| 管理查询新增文件及列表/搜索接线 | 现有单值条件无法保证聚合分页正确，必须在服务端过滤 | 只修改管理 handler 必需分支，记录冲突点，不改业务分发热路径 |
| 中英文 locale 与行为测试 | 覆盖新增管理文案、交互和查询合同 | 仅相关键及测试，不批量同步其他语言 |

实施时复用现有 Combobox、表单、抽屉、ProviderBadge、LoadingState 和 ErrorState。
不新增第三方依赖，不建立通用渠道家族配置后台，不重构插件框架，不修改数据库结构。
任何新增原生文件修改都须说明必要性、最小接线点和上游合并影响；无法说明则缩小范围。

| 场景 | 应验证的结果 |
| --- | --- |
| 新建 MiniMax | 只显示一个分类，接入方式未选不能提交；两种选择分别提交 35、64 |

| 编辑与复制 | 真实身份正确回显，编辑不提供原地互转，复制不改变类型 |

| 参数错误 | 新 types 非法及双参数冲突返回 400；旧单值请求行为保持 |
| 声明异常 | 加载失败、版本过期明确可见，保存失败关闭，不显示虚构能力或回退原生 |
| 权限与操作 | 敏感配置权限继续生效；测试和批量操作按真实类型/记录处理 |
| 展示与无障碍 | 中英文、键盘选择、可见标签、错误定位和移动端均可用 |

前端用 Vitest 与现有组件测试设施覆盖用户行为和提交负载；执行受影响测试、`bun run typecheck`、
所改文件 lint 及构建。后端以管理请求和结果验证 types 语义，覆盖 SQLite、MySQL、PostgreSQL，
不因没有迁移就省略新增过滤条件的数据库兼容验证。执行边界优先复用现有分派、保存和隔离回归。
不为纯显示改动新增真实付费 Provider 测试，也不以单元测试通过宣称真实视频或账单验收完成。

文档修改运行 `task docs:check` 与 `task ai:check`。若后续实际修改公开 API 文档，另运行
`cd web && bun run docs:validate`；本方案没有改变公开 API 合同。

## 6. 发布、回退与剩余事项

部署顺序为先更新支持 types 的管理后端，再更新前端；滚动部署须确保管理请求不会落到忽略 types
的旧节点。前端不静默退回全量查询，不采用双请求合并分页的兼容路径。纯管理变更不触发 Provider 请求。
回退先恢复旧前端展示，再按需回退管理查询扩展；数据库与执行身份未迁移，无需改型或重写历史任务。

- 已实施：局部展示模块、表单交互、服务端多类型查询、声明说明修正和中英文文案。
- 已完成：前后端自动化回归、SQLite/MySQL 5.7/PostgreSQL 9.6 查询兼容验证及前端构建。
- 待完成：前后端部署、管理页面人工验收和部署回退演练；未执行生产或真实 Provider 付费测试。
- 当前事实已同步至 [业务流程](../10-product/业务流程.md)、[交互模式](../90-ui-ux/交互模式.md)
  和 [架构概览](../20-architecture/架构概览.md)，执行合同不变。本文暂不归档。

## 7. 实施与验证记录

### 7.1 实现及必要修复
