# 聊天模型测试参数不兼容分析与修复方案

## 问题与目标

用户提供的渠道测试截图显示：客户模型 `chat-latest` 请求失败，HTTP 状态为 400，错误类型为
`invalid_request_error`，错误码为 `unsupported_parameter`，被拒绝的字段为 `max_tokens`。
错误信息要求改用 `max_completion_tokens`。本文仅保留脱敏错误摘要，不复制完整上游响应或截图文件。

用户随后反馈，在其称为 GPT-5.5、GPT-5.6、GPT-6 的多个模型中均出现同类问题。该反馈扩大了排查
范围，但各渠道最终发出的模型 ID、实际模型身份和失败请求尚未逐项核实。

目标是定位旧字段的来源，以可信的上游模型身份和接口合同为依据，在既有适配器内统一处理参数，确保
渠道测试与正式调用都能发送符合目标模型要求的请求。客户别名不能决定南向参数兼容性；管理员逐模型
配置参数覆盖仅作为临时处置，不作为长期修复方案。

初始分析基于同步前 rc.31 内容基线。随后已按用户授权将 rc.36 全量代码集成到工作区，并完成本地测试与
隔离数据库验证，详见[同步实施与验证记录](./2026-09-10-上游rc36同步实施与验证记录.md)。尚未提交、部署或
执行真实 Provider 请求，不表示截图中的故障已完成生产验证。

合并后已完成[参数兼容性复测](./2026-09-10-rc36聊天模型参数兼容性复测记录.md)：正确映射到标准模型的
渠道测试可转换旧字段；裸名 `chat-latest` 仍复现模拟 400，截图策略只在正式路径生效，未接入渠道测试。

## 当前实际情况

### 同步前已验证的代码事实

本节保留同步前 rc.31 的排查依据；链接现已指向集成 rc.36 的工作区，旧行号仅供定位参考。

| 环节 | 当前行为 | 代码证据 |

| 自动检测的渠道测试 | o 系列走新字段；`chat-latest` 会进入默认分支并设置 `MaxTokens = 16` | [controller/channel-test.go](../../controller/channel-test.go)，约 858—868 行 |
| 模型映射 | 先构造测试请求，再调用 `ModelMappedHelper`，随后将请求模型更新为映射后的上游模型 | [controller/channel-test.go](../../controller/channel-test.go)，约 264—308 行 |
| OpenAI 参数转换 | 仅在映射后的模型被识别为 o 系列或 GPT-5 系列时尝试转换旧字段 | [relay/channel/openai/adaptor.go](../../relay/channel/openai/adaptor.go)，约 371—378 行 |

| 正式 Chat 请求透传 | 全局或渠道请求体透传开启时直接使用原始请求体，绕过普通分支的适配器转换与参数覆盖 | [relay/compatible_handler.go](../../relay/compatible_handler.go)，约 100—173 行 |

现有适配器还有一个相关边界：仅在新字段按值判断为零且旧字段非零时，才赋值新字段并清空旧字段。
因此，两者都为非零值时，旧字段不会被清除。该边界是代码事实，但没有证据证明它触发了截图中的错误。

当前转换判断已经使用 `info.UpstreamModelName`，不能将故障简单归因于“适配器使用了客户别名”。
如果最终名称确实是 `gpt-5.5` 或 `gpt-5.6`，现有 `gpt-5` 前缀判断已经能够命中；如果是 `gpt-6`，
则不会命中该分支。这仅说明本地代码的字符串匹配行为，不证明对应模型的可用性或参数合同。

### 模型身份与适配依据

| 概念 | 示例 | 适配中的职责 |
| --- | --- | --- |
| 客户模型别名 | `chat-latest` | 用于客户侧请求、路由与展示等语义，不据此判断上游参数兼容性 |
| 映射后的上游请求名称 | 标准模型 ID、供应商别名或 Azure 部署 ID | 决定发送给上游的模型或部署标识；不保证它等于实际模型身份 |
| 可信的实际模型身份与接口合同 | 已确认的部署对应模型及 Chat Completions 参数要求 | 决定是否使用新字段、如何处理其它参数 |

标准模型 ID 可以在已确认的 Provider 和端点上下文中用于适配。对不透明的别名或部署 ID，必须先有
可信的部署与模型对应信息，例如供应商提供的权威元数据或经核实的部署配置；不能仅靠字符串猜测，
也不能假定网关在首次请求之前能自动发现背后的实际模型。
映射的目标仍应保持供应商要求的合法请求标识，不能为识别模型而改写部署 ID。

### 外部证据

[OpenAI Chat Completions 官方参数说明](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create)
在 2026-09-10 查阅时说明：`max_tokens` 已弃用，推荐 `max_completion_tokens`，且旧字段不兼容
o 系列模型；新字段约束可见输出 token 与推理 token 的合计上限。

官方文档解释了字段语义，但不能证明截图中的 `chat-latest` 对应哪个 Provider 或真实模型，也不能
推导出所有 OpenAI 兼容供应商都支持新字段。

### 根因判断与未确认项

**直接原因已明确：最终到达上游的请求包含目标模型不支持的 `max_tokens`。**

针对多个模型均失败的反馈，按完整请求链排查：

1. 核实每个失败请求的客户别名、映射最终结果、真实模型与端点。若最终名称已经是 `gpt-5.5` 或
   `gpt-5.6`，不得继续把“前缀未命中”作为默认解释；若是不透明部署 ID，应先核实背后的模型合同。
2. 核实部署代码版本、实际使用的适配器及转换分支是否执行。正式请求的全局或渠道透传可能绕过转换；
   不应将正式透传分支直接当作渠道测试失败的原因，两种入口应分别取证。
3. 正式客户端请求检查两个 token 字段的存在性和值，确认是否因二者都非零而未清理旧字段。渠道测试
   的初始请求只设置旧字段，该构造入口可排除“双非零”；后续参数覆盖须另行核对。
4. 检查适配器转换后的参数覆盖，确认是否重新写入旧字段。
5. 对最终名称为 `gpt-6` 等未命中现有分支的请求，核实供应商合同后确定适配缺口；不能只扩大 GPT-5
   前缀判断，因为当前分支还联动修改温度、采样参数和消息角色。

尚未核实渠道类型、实际测试端点、模型映射、参数覆盖、透传开关和部署代码版本。不得将上述候选原因
写成已经确认的生产根因，也不得仅凭 `chat-latest` 名称认定它属于 GPT-5。

## 优化方案

### 一、核实上游身份和最终请求

1. 核对受影响渠道的类型、测试端点和 `chat-latest` 的模型映射，以及部署版本是否包含当前转换逻辑。
2. 如果 `chat-latest` 是本站客户别名，将其映射到供应商实际支持的模型或部署 ID；如果它本来就是
   供应商要求的名称，则保持原值。不得为了命中前缀判断虚构上游模型名，尤其不能改坏部署 ID。
3. 逐项记录已核实的真实模型及端点要求；对于不透明部署名，明确对应关系的可信来源。缺少来源时保留
   待确认状态，不根据管理员命名、价格、版本大小或错误后的猜测建立模型身份。
4. 核对适配前、适配后、参数覆盖后和最终发送时两个 token 字段的存在性及数值，定位旧字段保留或
   重新引入的位置，同时检查参数覆盖和透传依赖。
5. 仅检查和记录必要的脱敏配置与字段摘要，不输出凭据、完整生产配置或原始请求正文。

### 二、优先采用上游能力表，剩余缺口单独核实

已接取 rc.36 的 `GetOpenAIChatCapabilities`，各参数由独立能力位驱动；包括 GPT-6 Astra 的登记，
没有在本地复制第二套转换规则。裸名 `chat-latest`、不透明部署标识和透传路径不能仅靠升级保证解决。
本节下列字段表是剩余缺口的候选语义，不是本次同步已经实现的额外行为。

长期修复以既有 Provider adapter 为唯一参数转换入口。保持模型映射先于适配，依据已确认的上游
模型身份与当前端点合同决定 token 字段行为，不依赖客户别名，不要求管理员为每个客户别名补一条规则。

以下语义仅适用于已确认要求 `max_completion_tokens` 的 Chat 请求，是待实施并验证的适配行为：

| 输入形状 | 目标请求形状 |
| --- | --- |
| 仅有合法 `max_tokens` | 保留原数值写入 `max_completion_tokens`，删除旧字段 |
| 仅有合法 `max_completion_tokens` | 保留新字段，不补旧字段 |
| 两个合法字段同时存在 | 候选方案为以显式新字段为准并删除旧字段；与 rc.36 双非零时保留两字段的行为不同，本次未修改，须单独核对合同并评估向上游反馈 |
| 两个字段都缺失 | 不凭空增加 token 上限，保持省略 |
| 显式零值或其它越界值 | 按目标端点合同在相应校验边界处理，不能预设零值合法，也不能把零值等同于未传 |

不得用固定数值覆盖所有客户请求的输出预算，也不得仅增加新字段而保留旧字段。

具体实施要求：

- 不把 `chat-latest` 硬编码成某个模型家族，不全局替换所有协议的 `max_tokens`；不能将“版本更高”
  或使用 OpenAI 兼容格式视为参数相同的证明。
- 在目标模型确实要求新字段时，按字段存在性处理转换和旧字段清理，避免用数值是否为零代替缺失判断。
- token 字段转换应与温度、`top_p`、`logprobs`、推理参数及消息角色转换分别判断。不得为了让新模型
  使用新字段而直接将其归入 GPT-5 分支，连带套用未经核实的其它行为。
- 同时覆盖自动检测与显式 OpenAI 端点测试，不在测试控制器复制一套与正式调用不同的模型适配规则。
- 保留合法的上游部署或模型标识；若现有信息不足以支持不透明部署的适配，先明确可信身份来源及最小
  接入方式，再实施。本文不预设新增数据库字段、远程探测、并行注册表或通用模型能力系统。
- 新增回归测试放入独立测试文件；确需较多转换逻辑时放入 OpenAI adapter 目录的独立文件，原生
  `adaptor.go` 仅保留必要接线或极窄修改，不扩展为通用模型能力系统或 Link 包装层。
- 原生文件修改的必要性应明确为“现有适配路径无法按已确认合同生成合法请求”；最小接线点为 token
  字段转换分支。未来上游同步的冲突面集中在该分支及必要的测试构造接线，禁止顺带重排其它参数逻辑。

当前测试上限 `16` 包含推理预算时可能不足以产生可见回答。修复参数后若出现空输出或长度截断，应
结合真实模型要求单独调整测试预算，并核对结束原因；不能把调高预算当作本次 400 错误的直接修复。

### 三、临时处置与透传边界

在适配器修复完成前，已经确认目标模型合同的渠道可以临时复用参数覆盖功能，限定到目标模型及适用
Chat 请求。不得将管理员逐模型维护规则作为最终交付，也不得把这套临时覆盖作为另一份模型合同。

现有 `moveValue` 在源字段缺失时会返回错误，且会覆盖目标字段，因此不能配置无条件移动；必须验证
字段存在性与显式新字段优先级。实现依据见 [relay/common/override.go](../../relay/common/override.go)
的 `checkSingleCondition`、`applyOperations` 与 `moveValue`。若规则无法清晰表达所需行为，不堆叠
难以验证的条件或引入临时私有字段。

正式调用启用了请求体透传时，应让客户端直接提交正确字段；如需网关转换，应先评估该渠道其它请求
依赖后关闭透传并验证。不要为修复本问题擅自改变全局透传语义。
修复验收后应检查并清理本次临时覆盖中重复或冲突的规则，防止旧字段在适配后被重新加入。

### 四、验证与验收

| 验证项 | 通过条件 |
| --- | --- |
| 字段组合 | 表格中的字段组合均符合预期，目标模型最终请求不含旧字段，新字段及合法显式值不被误覆盖 |
| 别名独立性 | 同一真实模型和端点使用不同合法客户别名时，最终 token 字段行为一致 |
| 模型身份 | 已知真实模型正确适配；不透明部署 ID 有可信对应依据且发送标识不被改写，未知身份不被猜测 |
| 多模型回归 | 对用户反馈的各模型分别核实真实 ID 与合同后覆盖回归，区分现有前缀已命中与未命中的路径 |
| 参数解耦 | 修复 token 字段不顺带删除或改写该模型合同允许的温度、采样、推理参数和消息角色 |
| 参数覆盖 | 规则只命中目标请求；缺失旧字段不报移动错误；旧字段不会在转换后重新加入 |
| 测试入口 | 自动检测与显式 OpenAI Chat 端点均验证最终发出字段，流式和非流式结果符合协议 |
| 正式调用 | 非透传路径正确转换；透传路径遵守原始正文语义，客户端使用正确字段后通过 |
| Provider 验收 | 使用实际渠道完成有限测试，不再出现该参数错误；检查可见输出、结束原因与用量摘要 |

代码实施时在最窄边界运行相关包的确定性回归测试，覆盖正式可观察请求而非内部常量。若修改
`relaykit/` 或其公开 API，另外执行 `cd relaykit && GOWORK=off go build ./...`。
本文为内部分析记录；同步代码的实际验证范围及结果以同步实施与验证记录为准。

- 待明确不透明上游部署的可信模型身份来源；不把未确认的映射字符串当作实际模型。
- rc.36 能力表与参数解耦已集成并通过本地回归；待按实际渠道复测剩余路径。如采用临时覆盖，验收时核查其退出。
- 待完成真实 Provider 验收；验收前不得标记故障已解决或生产可用。
