# 上游对账名称与渠道展开调整方案

## 问题与目标

根据本次页面截图与用户明确提出的三项要求，调整上游对账的展示与编辑流程：

1. 支持定义上游名称，替代卡片标题中直接使用基础 URL 的展示。
2. 在渠道行直接展开该渠道的模型用量，合并渠道折扣区与用量区，移除卡片内重复的
   “URL → 模型 → 渠道”树。
3. 编辑渠道折扣时移除“原因”输入项，不再要求管理员填写修改原因。

三项调整已按本方案实施；实施记录见文末“实施与验证记录”。前一轮合并与折扣实施记录见
[原方案](2026-09-20-上游对账合并与渠道月度折扣方案.md)。

## 优化方案

### 1. 可行性结论与范围

三项均可行，属于上游对账模块的配置与展示调整，不需要改变客户收费、Provider 调用或 Task 结算。

| 调整 | 建议实现 | 相对改动量 |
| --- | --- | --- |
| 定义上游名称 | 为现有 URL 分组持久化可编辑显示名称 | 中：新增管理配置与读写接线 |
| 渠道行展开模型 | 统一为渠道父行和模型子行，沿用已有用量、金额事实 | 中：调整汇总投影、表格、下钻和导出 |
| 移除原因输入 | 保存接口不再要求人工原因，服务端记录操作说明 | 小：前后端校验、审计与回归联动 |

本方案将“上游名称”理解为当前 URL 分组的别名：一个 URL 分组一个名称，跨月份复用。用户未提出
跨 URL 合并供应商、供应商账号管理或历史归属冻结，这些能力不纳入本次范围。

### 2. 上游名称

- 卡片标题显示自定义上游名称；下方保留可安全展示的基础 URL，便于辨认。未设置名称时继续展示
  安全 URL；清空名称恢复该默认展示，不自动猜测 Provider 名称。
- 名称绑定现有规范化 `url_key`，不按名称重新归组。相同名称的不同 URL 仍是不同卡片；同一 URL
  下所有渠道共享该名称，渠道名称继续独立存在。
- 在卡片标题旁提供管理员名称编辑入口；保存到主数据库中的独立对账配置，刷新、切换月份和更换
  浏览器后仍可读取，不依赖浏览器本地存储，不写入渠道连接配置。
- URL 筛选器显示“名称 + 安全 URL”，提交值仍为原 `url_key`。列表、筛选与导出使用同一名称投影。
- 地址不明或渠道已删除时沿用当前渠道专属分组键和提示；即使设置名称，也不能掩盖地址不明或删除
  状态，更不能用相同名称合并这些组。不得暴露无法安全展示的 URL 内容。
- 渠道基础 URL 改变后按新 URL 归组，读取新组的名称，不自动迁移旧组别名。旧组名称可以保留，
  不冒充请求发生时的供应商身份。名称修改只影响之后的读取与新导出。
- 汇总 CSV 增加上游名称并保留安全 URL、渠道 ID；异步导出在提交时冻结名称，重新生成沿用冻结
  内容，不在执行时读取新名称替换旧值。既有文件不改写。
- 名称写入只允许管理员，保留修改人和时间等审计；输入按普通文本处理，导出继续防止公式注入。
  新配置的迁移和读写须支持 SQLite、MySQL、PostgreSQL，不增加运行时 Provider 探测。

### 3. 渠道行直接展开模型

目标结构：

```text
账期月份
└─ 上游名称（卡片标题，下方显示安全 URL 和上游汇总）
   ├─ 渠道 A：当月系数、来源、用量合计、原价、折后参考金额、编辑/查看明细
   │  ├─ 模型甲 · 按 Token：该渠道的模型用量与金额、查看明细
   │  └─ 模型乙 · 按次：该渠道的模型用量与金额、查看明细
   └─ 渠道 B：独立折扣及独立模型明细
```

- 卡片内只保留一张渠道表；将原折扣编辑区的系数、来源、版本时间和编辑动作放到渠道父行。
  “从上月初始化”保留在卡片工具区。用量表不再重复渲染 URL 父行，也不再先展开模型寻找渠道。
- 渠道父行以稳定渠道 ID 标识，展开后直接显示模型 × 计费方式子行；同名模型分别留在所属渠道。
  上游模型已确认与 fallback 身份继续区分，同模型不同计费方式不得混行。
- 渠道合计由服务端累加同一批模型叶行；保留现有逐笔 quota 舍入结果，前端不重新计算金额。
  卡片合计等于渠道合计之和，渠道合计等于所属模型行之和；有未知金额时继续按既有完整性规则展示。
- Token、次数和秒数分别列示；缺失保留“未记录”，明确零保留零。测试调用只计用量、退款与结算
  调整的现有口径不变，不因调整层级改变请求数、质量计数或金额覆盖范围。
- 渠道“查看明细”携带账期、URL 分组与该渠道 ID；模型子行在此基础上增加 Provider 模型、fallback
  身份和计费方式。点击展开或收起不触发折扣保存，点击编辑不应同时展开或收起。
- 汇总导出按“上游 → 渠道 → 模型 × 计费方式”排序，只导出叶行，不同时导出父行合计造成重复计数。
  下钻和完整明细导出携带相同筛选，双方请求 ID 搜索保持可用。

建议将现有上游汇总响应一次性调整为“URL 组 → 渠道 → 模型”的单一投影，由服务端统一提供父子
合计，移除旧模型父级展示及旧并列折扣表。实施前核对仓库内调用方并同步更新类型与导出，不新增
另一套查询、计费计算或长期并行的两种树结构。

### 4. 移除折扣原因输入，保留审计

此处“原因列”指编辑渠道折扣时的“修改原因”输入框，不是现有“来源”列；来源继续展示默认、
上月继承或历史迁移信息。

- 编辑时仅填写折扣百分比，保留保存、取消；删除前端原因草稿、输入控件及必填校验。
- 保存请求不再要求 `reason`；后端移除人工原因必填条件，由服务端为人工保存生成明确的系统操作
  说明，例如“管理员修改渠道月度折扣”。不由前端伪造用户填写的原因。
- 保留账期、渠道 ID、折扣范围、`expected_version` 和管理员权限校验；同一事务追加旧值、新值、
  版本、操作人、时间及系统操作说明。并发冲突仍要求刷新，不能静默覆盖。
- 保留历史人工原因和自动初始化/迁移原因，不清表、不回写旧审计；人工保存后的来源按现有
  规则表现为当月人工配置，不能误标为默认、迁移或上月继承。
- 本次只取消上游渠道折扣的人工原因输入，不修改客户资金调整、账单更正、来源核验等操作的原因要求。

### 5. 实施边界与验收

优先在现有本地对账专属 Router、controller、model、前端模块中实现；新增名称配置使用独立文件，
复用现有对账迁移和审计入口。无需更改原生渠道结构、路由分发或计费热路径；如实施中发现必须改动
原生文件，应说明必要的最小接线点及未来上游同步的冲突影响。

实施时按以下可观察行为验收：

1. 名称保存后刷新和跨月读取一致；同名不同 URL 不合并，URL 改变不会错误沿用旧组名称；未命名、
   无效 URL 和已删除渠道均可辨认；普通用户无读写入口。
2. 同一上游下两个渠道包含同名模型时，展开每个渠道只看到各自用量；不同计费方式和 fallback
   身份不混合。页面不再出现重复 URL 树或第二张渠道折扣表。
3. 重组前后相同筛选的用量、金额、质量计数完全一致；覆盖缺失用量、未知金额、渠道测试、退款和
   小额舍入。各层已知金额可勾稽，不把部分合计标成完整。
4. 不填原因即可保存有效折扣；越界系数被拒绝、版本冲突被提示，审计完整且来源正确。切换月份
   清除旧月草稿，原月折扣和已导出文件不受影响。
5. 渠道和模型下钻范围精确；页面、汇总 CSV、完整明细导出的筛选和金额一致；新导出名称冻结，
   重新生成保持原名称，普通用户不能创建或下载管理员文件。
6. UI 新增或修改文案只验收简体中文和英文；执行相关后端回归与前端检查，名称配置执行三数据库
   迁移与读写验收。真实账单和生产交付未验证前不宣称生产可用。

实施完成后更新[产品说明第 8、10、12.2 节](../10-product/客户与上游对账单产品说明.md)与
[对账架构第 2、4、5、7.3、8 节](../20-architecture/账单计费-客户与上游对账架构.md)，将旧层级和

### 联合评审修复（2026-09-21）

- 恢复上游卡片的整组原价、折后参考金额、请求数和质量状态，直接展示服务端投影；缺失或不完整
  金额明确标记。工具区补回整组明细入口，导出携带账期与 URL，不误带单渠道或模型限制。

### 剩余评审项修复（2026-09-21）

- 记录说明随 URL 筛选范围切换：全部上游读取响应总体质量，单组读取该组服务端 `data_quality`，
  不重新计算质量计数，也不把其它上游的缺失信息显示在当前组。
- 名称投影优先读取所有分组的 `custom_name`，包括未识别与已删除组；筛选选项补充安全 URL 或
  异常状态，卡片与明细范围使用相同名称，查询与导出仍以原 `url_key` 定位。
- 名称限制统一为去除首尾空白后的 255 个 Unicode 码点，前端、控制器与模型分别校验；取消输入框
  按 UTF-16 长度截断，超长明确拒绝，拒绝后不改变已有名称或增加审计。
- 回归覆盖质量筛选切换、异常分组名称与下钻身份，以及英文、中文、emoji 的 255/256 边界。
  原筛选行为与多语言长度错误已复现；修复不涉及数据库结构变更。
