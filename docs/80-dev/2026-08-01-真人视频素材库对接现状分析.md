# 真人图片素材生成视频与 Moxing/BytePlus 中转接入方案

## 1. 结论

本文合并真人视频素材库现状和 Moxing/BytePlus 中转接入方案，并以以下已确认规则为准：

- 我方 BytePlus 账号已经完成当前业务所需的官方协议、Order Form、真人认证规则及相关补充协议签署；
- 中转站和接入它的多个应用均由我方建设并属于同一公司主体；
- 中转站是公司内部集中管理模型、素材、认证、凭据、路由、计费和审计的 API 基础设施，不是面向第三方转售 BytePlus 能力的多级中转商；
- 就中转站的客户端接入而言，各应用注册或接入时只需统一接受我方《API 服务规则》；
- 《API 服务规则》通过一个“真人能力使用”章节承载必要约束，不另设《真人 H5 专项协议》；
- 中转站不承担应用层协议展示和自然人同意证据托管；它仅提供 H5 技术跳转，因此会接收自然人打开跳转链接时的 HTTP 请求，访问日志必须最小化且不记录 token 或原始 H5 参数；
- 各应用如何向其用户告知、通过主动方式取得明确同意、保存时间/政策版本/同意方式并处理撤回，属于应用团队职责，不进入当前中转站的数据边界；
- 上一条是同一公司内的系统职责分工，不表示我方作为 BytePlus Customer 可以豁免最终用户同意、记录留存、撤回删除和按最终用户隔离素材的义务；
- BytePlus H5 仍是上游真人认证的技术步骤。中转站负责创建、路由、查询和清理认证会话，但不把 H5 作为本站协议签署流程；
- 中转站学习 Moxing 的是“平台账号统一接受服务规则、API 调用方不逐项签署上游协议”的接入形态；Moxing 的当前公开合同以 `tokensave.pro` 文档为准；
- **权益、IAM 和 BytePlus 官方账户接线都不是客户端应用接入条件。** 下游只使用我方 API Key 和统一业务接口，不接触 Moxing Key、BytePlus AK/SK、Project、Region 或上游账户配置；
- 若 Provider 选择 Moxing，中转站使用 Moxing Bearer Key；若 Provider 选择 BytePlus，中转站适配器使用管理员预配置的 BytePlus 调用凭据。两者只是中转站内部实现差异，不形成两套下游流程。

当前工作区代码已按本方案收窄为“应用接受 API 服务规则 -> Provider H5 -> 真人图片素材 -> 视频生成 -> 撤回”。平台不再提供自然人同意页或同意证据接口；Moxing 与 BytePlus 已共用同一套客户端编排。代码合同与回归测试已完成，真实 Provider 全链路仍需在上线前按第 11 节做受控环境验收。

当前素材能力还必须区分两个概念：

- 支持的是“使用通过真人认证的图片作为参考素材生成视频”；
- 不支持“把真人视频文件作为 `real_person` 素材上传或注册到素材库”。

`real_person` 目前必须是 `media_type=image`，并绑定已经进入 `authorized` 状态的真人认证。普通 `general` 素材才可以根据上游 profile 支持 `image`、`video` 或 `audio`。

> 方案状态：“Link 合同 + 隔离渠道适配”已实现；生产扩组仍以 Provider 真实环境验收为门禁。本文中“已实测”指 Moxing（`https://tokensave.pro`）会话创建与用户人工完成 BytePlus H5 页面；按用户要求未再查询该会话的最终 `GroupId`，因此不把后续素材创建、视频生成或清理记为已实测完成。

## 2. 最终确认：同一套 Link 全链路流程

### 2.1 系统边界与职责

```text
Moxing / BytePlus
  -> 作为中转站可选择的 Provider
  -> Moxing 提供 Bearer REST；BytePlus 提供官方 Action API
  -> 最终均通过 BytePlus H5 完成人脸采集、活体检测和同人认证

中转站
  -> 按渠道使用管理员预配置的 Moxing Key 或 BytePlus 调用凭据
  -> 向自有应用提供统一认证接口、短时 H5 安全跳转和认证状态
  -> 管理 API 规则、应用身份、匿名最终用户作用域、Provider 凭据、路由、资源映射、计费和技术审计

自有应用
  -> 注册或接入中转站，接受统一 API 服务规则，使用内部 API Key
  -> 在调用真人能力前完成最终用户明确同意、记录留存和撤回机制
  -> 为每个最终用户提供应用作用域内稳定、匿名的 end_user_subject
```

中转站只管理两类协议事实：

1. 我方已确认完成的上游账户协议事实；
2. 自有应用与中转站之间的 API 规则接受。

另外，中转站保存与人脸内容无关的技术作用域映射，用于防止一个最终用户的认证、素材或豁免被另一个最终用户复用。该映射不是自然人同意证据。

中转站不承担：

- 向自然人展示《用户服务协议》《隐私政策》或真人专项弹窗；
- 保存自然人的同意时间、同意正文、政策版本、勾选截图或其他同意证据；
- 逐请求审核或托管应用层的自然人同意证据；
- 要求每个真人请求携带 `consent_confirmed` 或上传授权证明；
- 把 Moxing、BytePlus 的协议、权益或账户权限配置交给应用处理；
- 管理不同应用内部的用户协议、隐私政策和撤回入口。

### 2.2 客户端：所有自有应用只对接一套公共 API

1. 应用在注册或接入中转站时，一次性接受统一 API 服务规则，并登记应用层同意记录的责任人与承载系统；中转站不复制具体同意证据。
2. 应用使用应用作用域内稳定、匿名的 `end_user_subject` 调用 `POST /v1/real-person-authorizations` 创建真人授权任务。
3. 中转站返回统一的 `rpa_*` 标识、归一化状态与平台自有 `verification_url`。
4. 应用打开 `verification_url`；中转站在服务端使用短时链接 `302` 到当次上游的完整 H5 地址。
5. 应用调用 `GET /v1/real-person-authorizations/{rpa_id}` 查询归一化结果；回调只作为触发查询的信号。
6. 授权成功后，应用调用 `POST /v1/assets` 通过公网 HTTPS URL 注册 `media_type=image`、`asset_kind=real_person` 的真人图片素材；素材自动继承认证的 `end_user_subject`。
7. 应用轮询 `GET /v1/assets/{asset_id}`，状态为 `ready` 后，使用同一 `end_user_subject` 与统一的 `asset://ast_*` 发起视频生成。
8. H5 失败或过期时，应用调用 `POST /v1/real-person-authorizations/{rpa_id}/retry` 创建全新上游 session；重试不得切换 Provider 账号、Project 或 Region。
9. 撤回时，应用调用 `POST /v1/real-person-authorizations/{rpa_id}/revoke`；中转站先立即禁止新任务和内容回源，再按 Provider 已验证能力执行素材与授权组清理。

客户端不暴露上游 `session_id`、`BytedToken`、`GroupId`、原始 H5 长链接或上游 `asset_id`。Moxing 与 BytePlus 对应用使用同一客户端认证、素材和撤回合同；上游清理能力差异通过独立 `cleanup_status` 表达，不伪造能力对称。

### 2.3 中间层：统一适配器合同

两种渠道实现使用同一业务编排和归一化结果，不得在客户端形成两套接口。共同必选能力为：

- `CreateVerificationSession`：创建 H5 技术认证会话；
- `GetVerificationResult`：主动查询并获取上游授权组标识；
- `CreateAsset`：使用授权组与真人图像创建上游素材；
- `GetAsset`：归一化素材处理状态；
- `DeleteAsset`：撤回后清理已验证支持删除的上游素材。

`DeleteGroup` 是可选 Provider 能力，不能因为统一接口存在就推断所有 Provider 均支持。未验证素材组删除的渠道，撤回后仍必须立即完成本地禁用，内部清理状态标记为 `manual_required` 或 `partial`，不得对外声称上游授权组已删除。

中转站统一保存 `provider`、账号/项目/区域快照、凭证指纹、上游标识与有效期，对客户端只映射为 `rpa_*` 与 `ast_*`。

### 2.4Provider：同一业务流程的两类协议实现

| 阶段 | Moxing（`tokensave.pro` 公开合同及实测端点） | BytePlus 官方 API 适配 |
| --- | --- | --- |
| 创建认证 | Bearer Key 调用 `POST /v1/ark/assets/visual-validate/session` | AK/SK + Project/Region 调用 `CreateVisualValidateSession` |
| H5 临时值 | `session_id` + `h5_link` | `BytedToken` + `H5Link` |
| 结果查询 | session/result 得到 `group_id`；本次实测未查询终态 | `GetVisualValidateResult`，得到 `GroupId` |
| 创建素材 | `POST /v1/ark/assets`；本次未实测真实素材创建 | BytePlus `CreateAsset` |
| 素材就绪 | 查询至 `Active`；本次未实测 | `GetAsset` 查询至 `Active` |
| 视频生成 | 使用 Provider 返回的素材 URI | 使用官方返回的素材 URI |
| 撤回清理 | Moxing 文档列出素材/素材组管理能力；当前适配器未猜测组删除路径，而是明确返回不支持并记为 `manual_required` | `DeleteAsset` + `DeleteAssetGroup` |

### 2.5 Link 全链路共同不变式

- 一个 `rpa_*` 及其素材、视频任务必须同时锁定 `app_id + end_user_subject + provider + 账号 + 凭证指纹`，并在 Provider 使用 Project/Region 时一并锁定；失败重试不得跨作用域或渠道切换。
- 上游回调不是最终真值；只有主动查询结果可以将状态推进为 `authorized`。
- 平台 `verification_url` 必须短时、绑定 `rpa_*` 且使用服务端重定向；重定向必须原样保留上游全部查询参数（BytePlus 官方示例包含 `pl` 与 `uid`）。一般链接预览、安全扫描或浏览器预取不得在用户进入 H5 前不可恢复地消费唯一凭证；失败或过期必须走 `retry` 创建新 session。
- Provider 返回有效过期时间时按其上限执行；Moxing 等未返回 `expires_at` 时，平台使用 30 分钟安全兜底，避免创建成功的认证链接立即过期。
- 原始 H5 链接、token 与上游 ID 需加密、限时保存，不进入应用日志、对话文本或客户端持久化。
- 公共授权状态统一为 `awaiting_verification` / `verifying` / `authorized` / `failed` / `expired` / `revoked`；不保留 `awaiting_consent`、`consent_rejected` 或 `consent_confirmed`。上游清理使用独立的 `cleanup_status=pending|partial|complete|manual_required`，避免把“已禁用”误报为“上游已删除”。
- 无论 渠道如何，对客户端均不支持真人视频作为素材上传，也不支持 Base64 或我方文件托管。
- Moxing Ark 真人素材绑定使用公开 SKU `seedance-2-0-oversea`，其能力注册同时允许 `third_party_relay` 与 `third_party_reverse_proxy`；携带真人 `asset://` 时，素材绑定会把请求限定到 `third_party_reverse_proxy + ark_assets` 渠道。BytePlus 使用 `official + official_action_assets`。两者共用 ModelArk 客户端请求，不通过放宽门禁混用渠道适配协议。

## 3. 应用接入中转站

### 3.1 统一注册与协议

```text
应用注册或接入中转站
  -> 发放或绑定内部 API Key（当前 Token ID 即 app_id）
  -> 获取并接受当前版本《API 服务规则》
  -> 登记应用合规责任人与最终用户同意记录承载系统
  -> 中转站保存应用级接受记录
  -> 应用调用统一 API
```

《API 服务规则》至少覆盖：

- API 使用范围、鉴权、配额、计费和安全要求；
- 禁止违法、侵权、冒用身份、绕过真人认证和批量滥用；
- 应用团队负责其输入素材、肖像、声音和使用目的的合法性；
- 应用在调用真人能力前，必须以弹窗、复选框或等价主动方式取得最终用户明确同意，并保存时间、告知/政策版本和同意方式；
- 调用真人能力表示应用已完成上述职责；这一内部职责声明不代替应用系统中真实的同意记录；
- 中转站可以为安全、审计、计费、投诉和违规处置暂停能力或清理资源；
- 上游能力、规则或接口发生实质变化时，中转站可以更新 API 规则和能力范围。

中转站只保存最小应用级接受记录：

```text
app_id
api_rule_version
content_hash
accepted_at
accepted_by
acceptance_method
compliance_owner
consent_record_system_ref
```

管理员先在 `/api/api-service-rules` 创建规则并调用 `/api/api-service-rules/{rule_id}/activate` 生效。应用随后用自己的 API Key 调用 `GET /v1/api-service-rules/current` 取得版本和正文哈希，再调用 `POST /v1/api-service-rules/acceptance` 提交一次接受。未配置生效规则时真人能力失败关闭；规则实质变更后，新版本需重新接受。同一应用对同一版本的接受记录不可变且重复提交幂等，不覆盖首次接受时间、操作人、责任方或承载系统；尚未到 `effective_at` 的版本不能提前激活，避免当前规则被提前退休。

该记录不包含自然人身份、人脸信息或应用层用户同意证据；`consent_record_system_ref` 仅指向公司内的责任系统或责任人，不引用单个自然人记录。

当前实现使用 Token ID 作为 `app_id`：一个应用使用一个独立 API Key。未来引入独立应用实体时必须做显式数据迁移，不应复用自然人同意模型记录应用协议。

### 3.2 多个自有应用

所有自有应用共用同一公司主体和中转站能力，但每个应用使用独立 `app_id` 或 API Key，以便计费、限流、审计和故障隔离。Moxing 或 BytePlus 的 Provider 账户由中转站集中管理，不下发给应用。每个应用还必须使用自己作用域内稳定的 `end_user_subject`，不得把应用级 API Key 当作最终用户级隔离标识。

应用数量增加不会形成多级中转关系，也不要求：

- 应用分别签署 BytePlus 协议；
- 中转站分别托管各应用的自然人同意证据；
- 应用感知请求实际选择 BytePlus、Moxing 或其他兼容渠道；
- 因内部渠道切换而重新接受没有实质变化的 API 规则。但如果 Provider 变更影响应用层隐私告知、委托处理关系或数据跨境信息，应用团队仍需按其规则更新告知或重新取得同意。

未来如果接入不属于我方同一公司主体的外部客户，本方案不自动适用，必须重新评估第三方服务、转委托、转售权限和责任划分。

## 4. 真人素材目标流程

### 4.1 完整流程

```text
应用已经接受中转站 API 服务规则
  -> 应用完成最终用户明确同意与记录留存
  -> 应用使用稳定匿名 end_user_subject 创建真人认证 rpa_xxx
  -> 中转站按固定 Provider 账号创建 H5 认证会话
  -> 应用把短时 verification_url 交给需要认证的人
  -> BytePlus 或其他已批准 Provider H5 完成活体和同人认证
  -> 中转站主动查询认证结果并建立真人素材组
  -> 应用提交公网 HTTPS 真人图片创建 ast_xxx
  -> 中转站在冻结的 Provider 账号下创建上游素材和 binding
  -> 素材进入 ready
  -> 应用使用同一 end_user_subject，在视频官方媒体字段中使用 asset://ast_xxx
  -> 网关校验应用、最终用户作用域、状态、认证、模型、渠道账号和多素材渠道交集
  -> 发送前建立 Task create attempt、资金 hold 和认证 reservation
  -> 网关把平台素材 ID 改写成选中账号的上游素材引用
  -> 创建视频并保存平台 Task
  -> 应用查询任务并通过平台内容代理下载
  -> 认证撤回后禁止新引用、阻断后续内容回源并安排取消或清理
```

上游 H5 链接必须由中转站包装，以隐藏 `BytedToken`、官方 H5 地址、Group ID 和回调参数。包装入口只承担安全跳转和状态刷新，不展示或收集中转站的人脸信息处理同意。实现不得因链接预览或安全扫描的普通 GET 而让用户丧失当次认证入口；需要不可恢复消费凭证时，必须有明确的用户主动动作或可用的 `retry` 恢复路径。

API 不增加逐请求 `consent_confirmed` 字段，也不要求应用上传同意截图。应用对《API 服务规则》的接受和实际 API 调用，构成公司内部职责确认，不构成中转站对自然人授权证据的托管。

### 4.2 创建真人认证

目标接口保持平台 Token 鉴权：

```http
POST /v1/real-person-authorizations
Authorization: Bearer <API_KEY>
Content-Type: application/json

{
  "model": "<平台明确开放的模型ID>",
  "end_user_subject": "<应用作用域内稳定、匿名的最终用户标识>"
}
```

目标响应向应用提供短时 `verification_url`。应用把该地址交给需要认证的人，完成 Provider H5 后轮询：

```http
GET /v1/real-person-authorizations/{rpa_xxx}
Authorization: Bearer <API_KEY>
```

只有状态为 `authorized` 才能继续创建真人素材。

`end_user_subject` 必须是 8～128 个 ASCII 字符，并同时包含字母、数字和 `._:-` 中至少一个分隔符；不得是姓名、手机号、邮箱或身份证件号码，也不得每次请求随机生成。格式校验会拒绝明显的直接标识，但应用仍负责保证没有把真实身份信息包装成合规格式。中转站使用 `HMAC(platform_secret, app_id || ":" || end_user_subject)` 生成 Provider 所需的稳定匿名安全标识。当前 `app_id` 取 Token ID，`platform_secret` 必须持久且稳定；更换该密钥会改变作用域摘要，必须通过独立数据迁移完成，不可无计划轮换。

当前实现已只返回 `verification_url`，不再展示平台同意页或要求成年确认。旧专项同意表、字段、状态和 token 已从模型及数据库迁移中彻底删除，不再存在可路由或可执行的旧实现。

### 4.3 创建真人图片素材

应用先把图片保存到自己的 OSS、S3、Blob 或 CDN，并提供 Provider 可访问、剩余 TTL 足够的公网 HTTPS 单对象 URL：

```http
POST /v1/assets
Authorization: Bearer <API_KEY>
Idempotency-Key: <本次业务操作唯一ID>
Content-Type: application/json

{
  "name": "authorized-person-reference",
  "asset_kind": "real_person",
  "media_type": "image",
  "model": "<与认证相同的模型ID>",
  "authorization_id": "rpa_xxx",
  "source": {
    "type": "url",
    "url": "https://cdn.example.com/person.png?...",
    "expires_at": 1784788800
  }
}
```

应用保存返回的 `ast_xxx`，通过 `GET /v1/assets/{ast_xxx}` 轮询。只有 `ready` 可以用于视频；`creating` 或 `processing` 应继续等待；`create_unknown` 应保留原素材 ID 和原幂等键等待平台对账，不能换键盲目重建。

### 4.4 使用素材生成视频

以 ModelArk 合同为例：

```http
POST /api/v3/contents/generations/tasks
Authorization: Bearer <API_KEY>
Idempotency-Key: <视频业务操作唯一ID>
Content-Type: application/json

{
  "model": "<同一模型ID>",
  "end_user_subject": "<与 rpa_xxx 一致的匿名最终用户标识>",
  "content": [
    {"type": "text", "text": "人物自然说话，镜头稳定"},
    {
      "type": "image_url",
      "role": "reference_image",
      "image_url": {"url": "asset://ast_xxx"}
    }
  ],
  "duration": 5,
  "resolution": "720p",
  "ratio": "9:16",
  "generate_audio": false
}
```

应用只使用平台 `ast_xxx`，不能提交上游素材 ID。网关必须校验视频请求的 `app_id + end_user_subject` 与每个真人素材完全一致。`asset://` 必须放在模型官方合同规定的媒体字段中，不能借 `metadata`、`extra` 或任意透传参数绕过合同。当前相关 SKU 未声明混用能力时，同一请求不能混用 `asset://` 和 HTTP/Data URL。

任务通过对应视频查询接口轮询；成功后使用：

```http
GET /v1/videos/{task_id}/content
Authorization: Bearer <API_KEY>
```

### 4.5 撤回与清理

```http
POST /v1/real-person-authorizations/{rpa_xxx}/revoke
Authorization: Bearer <API_KEY>
```

撤回提交后，平台应立即禁止新的真人素材引用；使用该认证的任务内容和 `last_frame` 每次回源前重新检查状态，撤回后返回 `real_person_authorization_revoked`，不再访问 Provider。

平台可以安排在途任务取消和上游素材清理，但不能收回此前已经下载或复制到平台之外的副本，也不能承诺 Provider 已处理或缓存的数据必然被撤销。这里的撤回接口属于平台可控制资源的技术停用和清理，不代表中转站托管应用层自然人同意撤回。授权状态进入 `revoked` 后必须立即禁用；上游删除是独立可观测的清理流程，Moxing 精确组删除路径在代码补齐并实测前必须标记 `manual_required`，不能返回 `complete`。

## 5. BytePlus 官方资料核对（仅约束渠道实现）

### 5.1 中转站边界

用户已确认我方 BytePlus 账号相关协议均已签署完成。本文不再把“权益确认、IAM 配置、官方直连验收”设计成应用接入步骤或客户端业务门禁，也不要求应用了解这些概念。对下游而言，BytePlus 与 Moxing 完全相同：只调用中转站统一 API。

BytePlus 官方资料仍用于确定中转站适配器的真实技术合同：

- 创建真人认证会话使用 `CreateVisualValidateSession`；
- H5 完成后使用 `GetVisualValidateResult` 取得 `GroupId`；
- 真人图片通过 `CreateAsset` 入库，状态达到 `Active` 后以 `asset://<asset_id>` 用于视频；
- 官方 Assets API 使用 Access Key 签名。这是中转站 Provider 调用凭据，不是下游应用的 IAM 或接入动作；
- BytePlus 真人 H5/API 使用规则把我方定义为向自身 End User 提供服务的 Customer，要求最终用户明确同意、记录留存及按最终用户隔离；本方案把这些职责放在自有应用层，中转站只保存技术作用域；
- BytePlus 的 Platform Customer 规则针对向外部企业或创作者开放注册和使用权限的平台。当前方案限定为同一公司主体的自有应用，不据此扩展为面向第三方的 API 转售；将来接入外部客户时必须重新评估。

因此，“我们是中转站”的直接含义是：把上游差异封装在渠道适配器内，而不是把 BytePlus 的账户、签名或管理概念转嫁给下游。若管理员尚未配置某个 渠道，路由层只需把该渠道视为不可用；Link 合同不增加任何 BytePlus 专属字段或协议步骤。

### 5.2 中转站如何提供真人认证能力

“中转站提供真人认证能力”不表示中转站自己采集人脸或执行活体算法，而是中转站代理 BytePlus 真人认证控制面：

```text
自有应用
  -> POST /v1/real-person-authorizations

中转站
  -> 使用官方素材 AK/SK 调用 CreateVisualValidateSession
  -> 传入 CallbackURL 和 ProjectName
  -> 加密保存 BytePlus 返回的 BytedToken 和 H5Link
  -> 向应用返回 rpa_xxx、verifying 和短时 verification_url

需要认证的人
  -> 打开 verification_url
  -> 浏览器跳转到 BytePlus 官方 H5
  -> 在 BytePlus 页面确认授权主体并完成活体和真人认证

BytePlus
  -> 完成后访问中转站 CallbackURL

中转站
  -> 把回调只作为状态刷新信号
  -> 使用 BytedToken 主动调用 GetVisualValidateResult
  -> 只有取得有效 GroupId 才把 rpa_xxx 更新为 authorized

自有应用
  -> GET /v1/real-person-authorizations/{rpa_xxx}
  -> 获得平台归一化状态，不接触 AK/SK、BytedToken 或 GroupId
```

BytePlus 当前官方流程要求：

- `CreateVisualValidateSession` 使用 Access Key 认证，返回 `BytedToken` 和 `H5Link`；
- `BytedToken` 有效期约 30 分钟，一个会话只允许完成一次认证；
- H5 完成后的 Callback 参数可以用于判断流程已返回，但不能替代服务端结果查询；
- `GetVisualValidateResult` 使用相同 `BytedToken` 和 `ProjectName` 查询，取得 `GroupId` 后才表示真人素材组已经建立；
- 创建真人图片素材时，将 `GroupId`、公网图片 `URL`、`AssetType=Image` 和同一 `ProjectName` 传给 `CreateAsset`；
- BytePlus 会把素材图片与认证参考人脸进行同人比对，素材状态达到 `Active` 后才能通过 `asset://<asset_id>` 用于视频。

中转站不自行实现：

- 人脸图片或活体视频采集；
- 活体检测、同人比对和真人认证算法；
- BytePlus H5 页面；
- 面向自然人的我方专项协议和同意证据；
- 根据 Callback 参数直接授予 `authorized`。

当前代码已实现 `CreateVisualValidateSession`、加密保存 `BytedToken/H5Link`、可预取安全的短时跳转、`GetVisualValidateResult`、`GroupId` 绑定以及后续素材状态机。应用级 API 规则记录、最终用户作用域、Moxing 清理失败关闭和 Link 合同收敛也已完成；平台同意页路由不再存在。

官方依据见 [BytePlus 私有真人素材库指南](https://docs.byteplus.com/en/docs/modelark/2333589)及 [GetVisualValidateResult API](https://docs.byteplus.com/en/docs/ModelArk/2333588)。

### 5.3 BytePlus Provider 技术配置（仅管理员内部）

| 能力 | 配置 |
| --- | --- |
| 视频上游方案 | `official` |
| 视频 Base URL | BytePlus 当前 Region 对应的官方 ModelArk 地址 |
| 视频凭据 | ModelArk API Key |
| 素材上游方案 | `official_action_assets` |
| 素材凭据 | 独立 Access Key ID / Secret Access Key |

两套凭据不得混填，也不得向应用回显。它们是中转站内部的 Provider 配置，不属于应用注册、协议接受或 API 调用参数。存在活动素材、素材组或真人认证会话时，凭据、Project、Region 和渠道身份继续受生命周期栅栏保护。

### 5.4 安全标识

应用不需要理解 BytePlus `safety_identifier`。中转站根据 `app_id + end_user_subject` 生成稳定、匿名的安全标识，不向 BytePlus 发送邮箱、手机号、姓名等用户明文，也不允许调用方用随机值破坏最终用户级任务追踪和素材隔离。

## 6. Moxing 当前是否采用相同操作

结论：**是。用户提供的 `https://tokensave.pro/docs/api/byteplus-ark-assets` 就是当前 Moxing“海外官Key 真人素材库”文档，不能再把该站点域名与 Moxing 拆成两个来源。其核心技术流程与我方目标相同。**

截至 2026-08-02，Moxing 当前公开的“海外官Key 真人素材库”文档展示了以下流程：

```text
调用方使用 Moxing Bearer API Key
  -> POST /v1/ark/assets/visual-validate/session
  -> Moxing 返回 h5_link + session_id
  -> 终端用户打开 H5 完成真人认证
  -> Moxing 平台不托管 H5 页面
  -> 调用方查询 sessions/{session_id} 或 result/{session_id}
  -> 状态进入 group_ready 并取得 group_id
  -> 调用方使用 GroupId + 公网图片 URL 创建素材
  -> 素材 Active 后通过 asset://{asset_id} 生成视频
```

其公开 session 状态为：

```text
pending
callback_received
group_ready
failed
expired
```

Moxing 文档公开的是“Bearer API 代理 + BytePlus H5 + Moxing 查询结果”的中转模型。它没有要求 API 调用方配置 BytePlus 权益、IAM 或 AK/SK，也没有逐请求上传授权证明字段；这些上游细节由 Moxing 封装。该模式正是我方客户端需要保持的形态：下游只接受统一 API 规则并调用统一接口。

### 6.1 Moxing 端点实测结论

2026-08-02 使用当前本地测试库中的 Moxing 渠道、Base URL `https://tokensave.pro` 执行了实际会话创建：

- `POST /v1/ark/assets/visual-validate/session` 返回 HTTP 200；
- 响应包含 `session_id`、`h5_link` 和初始 `pending` 状态；
- `h5_link` 的实际认证页面为 BytePlus 官方域名；
- 用户已在终端人工完成 H5 流程，并明确确认该方式可行；
- 按用户要求，完成后不再查询该 session，因此本次实测不将 `group_ready` 或 `group_id` 记为服务端已验证事实。

实测还确认，官方 H5 链接很长且包含不可缺少的查询参数。因此 Link 合同不应直接返回或转发原始 H5 长链接，必须使用平台短时 `verification_url` 在服务端原样重定向，避免对话、二维码或客户端存储过程中截断参数。不可恢复的“一次性”消费不得由链接预览或安全扫描触发。

与我方目标方案的差异如下：

| 范围 | Moxing 当前公开行为 | 我方已实现方案 |
| --- | --- | --- |
| 平台鉴权 | Moxing Bearer Key | 我方应用 API Key |
| 创建认证 | 返回 `h5_link + session_id` | 返回平台 `verification_url + rpa_xxx` |
| H5 承载 | 上游 H5，Moxing 不托管 | BytePlus H5，中转站不托管 |
| 结果查询 | session/result 接口返回 `group_id` | 平台状态接口返回 `authorized`，内部保存 `GroupId` |
| 上游标识 | 对外使用 `group-xxx/asset-xxx` | 对外使用 `rpa_xxx/ast_xxx`，隐藏上游标识 |
| 平台专项同意页 | 公开 API 文档未展示 | 不设置 |
| 应用级规则 | 账号统一服务协议和隐私政策 | 应用接入时统一《API 服务规则》 |

因此，我方可以保持与 Moxing 相同的客户端操作模型，同时保留平台 ID、安全跳转、最终用户作用域和 Provider 账号隔离。当前实测只证明了 Moxing 会话创建和 BytePlus H5 跳转；结果查询和素材全链路仍未在本次执行。Moxing 文档虽列出素材与素材组的查询、更新和删除管理，但当前 `ark_assets` 适配器仍因缺少已确认的精确组删除路径而失败关闭，代码补齐并实测前继续返回 `manual_required`。公开合同见 [Moxing 海外官Key 真人素材库](https://tokensave.pro/docs/api/byteplus-ark-assets)。

## 8. 为什么 `real_person` 只允许 `media_type=image`

这不是 JSON DTO 的偶然限制，而是当前已验证业务合同的边界。

1. **当前 Provider 真人认证合同以人脸图片和专属素材组为对象。**
   已实现的 `ark_assets` 和 `official_action_assets` 适配器只声明 `real_person + image`，认证成功后建立的 group 也按真人图片创建流程消费。当前没有经过验证的“真人视频素材创建、审核、引用、查询和删除”Provider 合同。

2. **当前产品场景是身份参考图生成视频，不是视频素材托管。**
   真人认证冻结 model、渠道账号、认证 scope 和图片素材；视频任务引用这张受控图片生成结果。如果允许真人视频入库，会新增参考视频、人物克隆、动作或声音等不同产品语义，不能只把 `media_type` 从 `image` 放宽为 `video`。

3. **真人视频会扩大敏感数据和处理目的。**
   图片主要涉及人脸身份；视频还可能包含连续人脸轨迹、身体动作、环境、其他人物和声音。当前 Provider 合同、保存期限、处理地区、撤回及删除能力没有证明覆盖这些额外范围。

4. **生命周期和撤回语义尚未为真人视频验证。**
   真人视频可能被 Provider 拆帧、提取音轨、生成身份或动作特征。平台需要确认这些派生数据的创建、保存、任务引用、取消、删除和审计合同，才能声称完成平台可控制范围内的治理。

因此，如需支持真人视频素材，应单独立项，至少补齐 Provider 官方合同、 Link 合同字段和值域、内容与派生数据生命周期、路由能力、计费、安全上限和真实环境验收，不能只修改媒体类型校验。

## 9. 为什么不支持 Base64 上传或平台文件托管

根据 [ADR-0004](../20-architecture/decisions/0004-中转型素材代理与上游绑定.md)，素材库被定义为“控制面代理”，不是对象存储服务：

- 应用负责把素材保存在自己的 OSS、S3、Blob 或 CDN；
- 平台只接受 Provider 可访问的公网 HTTPS URL；
- 平台不主动 GET/HEAD，不保存素材二进制或完整签名 URL；
- 平台只持久化 `ast_xxx`、上游 resource/reference、渠道账号指纹和认证 scope 的映射。

拒绝 Base64、multipart 和平台托管的主要原因是：

1. **避免网关承担二进制数据面责任。** 接受文件后就必须处理上传大小、流式写入、断点续传、对象存储、容量配额、备份、过期和删除一致性。
2. **避免扩大真人敏感数据持有范围。** 平台不成为真人原始图片或视频的长期事实来源，可以减少泄露、跨境存储、数据驻留和保留期限责任。
3. **避免引入下载型 SSRF 和内容扫描体系。** 自动导入远程文件需要处理重定向、DNS rebinding、云元数据地址、恶意文件、MIME 欺骗、病毒和内容安全扫描。
4. **避免伪造不可兑现的迁移能力。** 平台没有二进制副本时不能在任意 Provider 账号间自动重建素材；当前合同要求应用重新签发 URL 并显式迁移。
5. **保持网关定位和最小依赖。** 旧 Azure Blob 托管方案从未部署，已被 ADR-0004 取代；未来若增加托管数据面，必须独立做架构评审。

5. Moxing `ark_assets` 与 BytePlus `official_action_assets` 已实现统一认证适配合同；Moxing `seedance-2-0-oversea` 已登记 `third_party_reverse_proxy` 视频能力，可消费同账号真人素材；Moxing 组删除在精确端点未验证前固定为 `manual_required`。
6. 原始 newapi 热路只保留字段、路由和单行门禁接线；API 规则、作用域 HMAC 和数据回填逻辑放在新文件中，没有借此重构无关代码。
7. 上线前仍需分别用受控身份完成 Moxing 和 BytePlus 真实 Provider 的结果查询、素材创建、视频、撤回和清理验收；这是中转站内部运维门禁。
8. 对外能力边界不变：只支持通过认证的真人图片生成视频，不支持真人视频素材入库、Base64 上传和平台文件托管。

## 11. 验收标准

- 就中转站的客户端协议而言，每个自有应用只需在注册或接入时接受一次当前版本《API 服务规则》；
- 服务端可以证明接受规则的应用、版本、首次接受时间、正文哈希和操作人；重复接受不得覆盖原记录，未来规则不得提前退休当前规则；
- 每个应用已登记最终用户同意记录的责任人和承载系统，且该系统可以提供明确同意的时间、告知/政策版本和同意方式；中转站不保存这些自然人记录；
- 不存在独立《真人 H5 专项协议》；
- 中转站不展示应用层用户协议，不保存自然人同意证据；
- 真人 API 不要求逐请求上传授权证明或提交 `consent_confirmed`；
- 每个认证、真人素材和视频任务都绑定同一 `app_id + end_user_subject`，一个最终用户的认证不能被另一个用户复用；
- 不论选择 Moxing 还是 BytePlus，应用看到的客户 API 合同、ID、授权状态和撤回语义一致；上游清理能力差异通过独立 `cleanup_status` 如实表达；
- 下游应用不配置或感知 Moxing Key、BytePlus AK/SK、权益、IAM、Project、Region 和上游接线方式；
- 官方请求自动携带稳定、匿名的安全标识，应用无需处理 Provider 细节；
- H5 session、认证结果、真人素材组和视频引用始终绑定同一 Provider 账号、Project、Region 和凭证指纹；
- 应用只获得平台短时 `verification_url`，服务端重定向原样保留上游 H5 所有参数；链接预览不会不可恢复地消费凭证，失败/过期可通过 `retry` 创建新 session；Provider token、官方资源 ID 和回调参数不泄露给普通响应或日志；
- `real_person` 继续只允许 `media_type=image`，不接受 Base64、multipart 或平台托管文件；
- `POST /v1/real-person-authorizations/{rpa_id}/revoke` 撤回后平台立即禁止新引用、阻断内容回源，并按可验证能力执行取消和上游清理；Moxing 素材组精确删除端点未验证时固定为 `manual_required`，不得标记为清理完成；
- 现有平台真人同意页、专项政策、证据字段和 consent token 已彻底删除；仅保留 Provider H5 技术认证跳转。
