# 上游金额查询接口调研

## 问题与目标

为管理员菜单「上游金额」补齐可执行的查询合同：请求地址、鉴权、金额字段、单位、账户与 Key
口径，以及查询失败时的展示边界。调研完成后已按用户确认实施管理菜单与只读查询页面；未修改渠道
运行状态或计费行为。实现与验证记录见本文末节，尚未部署到生产。

### 用户已确认

- 复用渠道 URL 和 Key；按 Key 展示，即使多个 Key 属于同一上游账户也不合并钱包。
- 页面保留上游原币种，不做跨 Key 合计或消耗预测。初始范围不含提醒；用户后续追加低于 100 美元的
  SMTP 提醒，新增边界见本文「低余额邮件提醒追加需求」。页面仍不换算展示币种。
- 进入页面自动查询，提供手动刷新；不能查询的上游仍展示状态。
- 上游共享关系由管理员判断，不增加账户归并或平台资金账本。

### 本次证据范围

2026-09-24 至 09-25（Asia/Shanghai），只读检查工作区 `one-api.db` 的 81 个渠道配置。
该文件是本地样本，不据此宣称等于线上最新配置。相同 URL / Key 的请求可复用测试结果，展示仍按用户
确认的 Key 口径处理。非通用协议站点先查公开文档或公开前端代码，再验证其中已出现的查询接口。

测试只执行 GET，以及 FunCloud 官方查询页明确使用的两个只读 POST。未创建生成任务、充值、改 Key、
改渠道、调用本站批量余额刷新或写数据库。Key 只在内存中使用，未存入报告、脚本或日志；报告也不保存
实际金额、用户身份、完整上游响应和云资源实例地址。测试时限制响应大小、超时和并发，不跟随携带
凭据的重定向。公开网页/文档的读取与财务接口探测分开进行。

## 当前实际情况

### 1. 核心结论：接口成功不等于查到了余额

NEWAPI / One API 的兼容接口可能返回账户额度，也可能返回 Key 额度，取决于上游设置。
无限额度 Key 的 `hard_limit_usd` 可以是 `100000000` 占位值；再减去使用量仍不是账户资金。
因此上一轮“8 组连接返回可计算字段”的结果只证明响应结构存在，不能作为金额验收通过。

本轮已经进一步确认：

- Amutes 的 6 个不同 Key 均返回 `unlimited_quota=true`，兼容接口均使用上述占位值。
- MixAI、Synlink 的代表 Key 同样明确返回无限额度及占位上限。
- TokenSave、墨行的兼容接口同样返回该占位上限，但 `/api/usage/token` 两种尾斜杠形式都返回 404；
  只能判定“高度疑似无限 Key 上限，真实余额未取得”，不能仅以数值相等硬编码推断所有站点。
- 飞彩的 Key 为无限额度，但兼容接口返回有限金额，说明两路接口不表达相同的 Key 配额；
  根据标准实现推断兼容接口可能表达账户额度，该作用域仍需供应商确认。

权威代码：[NEWAPI billing.go](https://github.com/QuantumNous/new-api/blob/main/controller/billing.go)、
[One API billing.go](https://github.com/songquanpeng/one-api/blob/main/controller/billing.go)。
这些是调研时读取的可变分支，不构成对所有已部署 fork 的实现证明。

### 2. NEWAPI 通用查询合同

| 用途 | 请求 | 鉴权 | 提取与解释 |
| --- | --- | --- | --- |
| 订阅/额度上限 | `GET /dashboard/billing/subscription` | `Authorization: Bearer <渠道 Key>` | 校验 `object=billing_subscription` 和有限数值 `hard_limit_usd`；不能单独当余额 |
| 使用额度 | `GET /dashboard/billing/usage` | 同上 | 校验 `object=list` 和有限数值 `total_usage` |
| 兼容路径 | 上述两条路径前加 `/v1` | 同上 | 标准项目注册了两组路径；特定站点是否转发必须单独验证 |
| Key 配额 | `GET /api/usage/token/` | 同上 | 校验 `code=true`、`data.object=token_usage`；读取 `data.total_available`、`data.unlimited_quota` |
| 站点单位 | `GET /api/status` | 不携带 Key | 只读取公开的货币/额度元数据，不把整份站点配置转发给页面 |

兼容接口在排除无限上限、校验单位和响应语义后，才可计算：

```text
剩余额度 = subscription.hard_limit_usd - usage.total_usage / 100
```

对标准 NEWAPI 而言，`usage` 是累计使用量；本地/已查上游源码未按 `start_date` / `end_date` 过滤。
不能把该公式中的上限与任意月度消耗拼接。两次 HTTP 查询不是原子快照，活跃账户可能有短暂偏差；
有直接余额接口时优先采用已验证的直接余额字段。负余额不得静默钳制为零。

`/api/usage/token/` 的 `total_available` 是原始 quota，不天然是美元、人民币或 token 数。
`unlimited_quota=true` 时必须展示“Key 无限额度”，不能把它解释为无限资金，也不能拿占位 quota
换算金额。有限 quota 只有在供应商额度单位和换算规则明确时才能展示为金额。

`/api/status` 观察到至少两套元数据：

- NEWAPI 风格：`quota_display_type`、`quota_per_unit`、`usd_exchange_rate`。
- TokenSave fork：`currency_code`、`currency_symbol`、`currency_name`、`currency_unit`、`quota_per_unit`。

不能看到 `hard_limit_usd` 就显示美元，也不能只凭 `display_in_currency=true` 确认币种。
对兼容接口已经换算好的数值，不再额外应用站点汇率。对原始 quota 的单位转换属于解释上游单位，
不是用户未要求的跨币种换算；但其转换合同仍须逐协议验证，不能套用本站 `QuotaPerUnit`。

通用状态还必须区分 HTTP 错误、业务错误、HTML 页面和合法金额。`200 + error`、`success=false`、
缺少金额字段都不是零余额。404 只证明本次路径没有取到结果，不证明供应商完全没有余额能力。

来源：[NEWAPI 路由](https://github.com/QuantumNous/new-api/blob/main/router/dashboard.go)、
[Key 配额接口](https://doc.newapi.pro/en/api/token-usage/)、
[兼容计费接口文档](https://doc.newapi.pro/api/fei-account-billing-panel/)。文档对 `*_usd` 的描述应与源码
和部署实例证据交叉核对；成功探测仅使用 Bearer Key，不需要猜测或补造 `New-Api-User`。

### 4. 雪松的完整合同

```text
GET https://mm-internal-cn.leonecloud.com/api/v2/open/balance
Authorization: Bearer <渠道 Key>
Accept: application/json
```

- 要求 HTTP 成功、业务 `code=0`，读取 `data.balance`，接受有限数值的十进制字符串。
- 单位读取 `data.currency`。本次两个不同 Key 都返回 USD；官方文档示例写“积分”，不能写死示例单位。
- 文档提到 `frozen_balance`，但本次响应未取得可用的该字段；不能擅自减零或自行推算冻结金额。
- 文档一处称 `balance` 为可用余额，另一处写“实际可用余额 = 余额 - 冻结余额”，存在口径冲突。
  当前只原样展示“上游返回余额”，冻结字段出现后仍需先澄清其是否已经包含于 `balance`。
- `mm.leonecloud.com` 是已观察到的另一种渠道地址；余额应使用官方明确的查询 host，不跟随未知重定向，
  不让运行时逐域名试 Key，也不修改实际模型调用地址。

来源：[雪松余额查询 API](https://docs.leonecloud.com/docs/balance)。

### 5. FunCloud 的已找到路径与限制

官方公开 Key 查询页 [key-usage](https://funcloud.ai/key-usage) 加载的脚本明确将查询发向
`https://api.funcloud.ai`，不是保存渠道中 `https://funcloud.ai` 的页面地址。

```text
POST https://api.funcloud.ai/v1/model/key-usage/limit
Authorization: Bearer <渠道 Key>
Content-Type: application/json

{"data": {}}
```

代表 Key 实测 HTTP 200、业务 `code=200`，`resp_data.windows` 为空数组。
该接口表达分时段限额，字段包括 `enabled`、`window_sec`、`limit`、`used`、`remaining`；
空数组不能解释为零余额，更不能把周期限额剩余值当账户钱包余额。
同一公开代码还列出 `/summary`、`/daily`、`/models`，它们属于消费/使用量，本次未为了余额需求
额外查询使用明细。

官网登录态钱包使用：

```text
POST https://api.funcloud.ai/v1/api/userCenter/amountInfo
Content-Type: application/json

{"data": {}}
```

公开前端使用登录取得的用户 Token，在 `Authorization: Bearer ...` 和 `token` header 传递。
以当前模型 Key 按相同 header 形式验证，返回业务码 `10003`，没有金额数据。不能把模型 Key 当作
登录 Token，也不能仅因为路径已找到就声称账户余额已接通。

证据为官方公开页面及其静态模块 `KeyUsagePage-C6fv1j3t.js`、`index-Mo23BLSi.js` 的当次内容；
模块 hash 会随部署变化，这些页面内部接口还需要供应商确认长期兼容承诺。

### 6. Vidu 的完整合同

```text
GET https://api.vidu.com/ent/v2/credits
Authorization: Token <渠道 Key>
Accept: application/json
```

本次响应使用 `remains[]`，其中有 `type=metered` 和数值 `credit_remain`。
文档正文又把该集合写成 `remaining_credits`，实现前应以本次实测字段配合供应商版本承诺确定合同，
不能为未经验证的形状增加多套历史解析。

按套餐类型保留积分含义；不把 `packages[]` 和汇总集合相加，避免重复计算。
无需查询套餐详情即可得到本轮所需积分余额。它是 credits，不应按网页参考单价反算现金。

来源：[Vidu Get Account Info](https://platform.vidu.com/docs/get-account-info)。

## 优化方案

### 1. 最小实现边界

1. 新增独立的管理员只读查询入口与页面；余额查询协议与模型转发协议分开，不改变 Link/原生履约身份。
2. 用代码登记已经验证的查询路径、鉴权、金额字段和单位规则。研发阶段可探测路径，正式页面刷新
   不逐个尝试候选路径、不跨供应商发送 Key、不把错误时返回的其它单位/作用域当作兜底余额。
3. 服务端读取渠道 Key；前端只接收脱敏标识、金额字符串、原单位、更新时间和查询状态。
   金额为空与金额为零严格区分；业务错误不能经零值 DTO 变成成功。
4. 同 URL/Key 的同时查询可合并请求，但不由此自动归并账户或合计资金。独立 Key 分别展示。
5. 进入页面自动查询并允许手动刷新；限制并发与超时，逐项返回状态，单个慢上游不阻塞全部结果。
6. 上一次成功值如被保留，必须标明其时间和本次刷新失败；不伪装为当前金额。

### 2. 不能直接复用现有批量刷新

`controller/channel-billing.go` 的批量逻辑可能在结果不大于零时调用停用渠道逻辑。
此外，当前标准解码对缺失字段会得到数值零，没有显式识别全部业务错误；其 NEWAPI 计算也没有
排除无限上限。`model.Channel.Balance` 的注释为 USD，前端按 USD 格式化，不承载原币种/原单位。

因此新页不能直接调用 `/api/channel/update_balance`，也不能直接拿 `channels.balance` 作为已经
验证的原币种金额。保持原生文件最小侵入，新增查询逻辑放独立文件；只复用确实适用的 HTTP 基础设施。

### 3. 建议验收条件

- 雪松：业务成功、十进制金额与响应单位保留；保存地址是门户 host 的情况有明确查询 host 登记。
- NEWAPI：有限金额、无限 Key、原始 quota、币种缺失、HTTP 200 业务失败分别有正确状态。
- Amutes 的六把无限 Key 不出现合成的巨大“余额”；TokenSave/墨行未取到钱包金额时不得装作已查到。
- Vidu：credits 与法币区分，套餐明细不重复累加。
- FunCloud 空限额窗口不显示零余额，登录钱包拒绝 API Key 不视为通用 Key 无效。
- API Key 不返回浏览器，Provider 原始响应不进入普通日志或公共接口；任何查询不修改渠道启停状态。
- 页面与新增提示仅需中英文。

## 低余额邮件提醒追加需求

### 已确认与默认规则

- 用户追加要求：金额严格低于 100 美元时，发送到系统配置 SMTP 中的「报告收件人」。恰好 100 美元不提醒。
- 用户确认重复策略：首次提醒，持续低余额每 24 小时再次提醒；观测到恢复至阈值及以上后，再次跌破可重新提醒。
- 检查频率采用每 10 分钟的后台系统任务，受主节点调度和现有数据库任务租约控制，无需打开页面。
  调度间隔以现有系统任务执行完成时间为基准，单轮外部请求耗时会延长实际观测间隔。
- 币种采用已告知的推荐默认：USD 直接比较，CNY 按当前系统 `USDExchangeRate`（CNY/USD）比较
  `余额 < 100 × 汇率`，避免除法四舍五入影响临界值。此处只解释提醒阈值，页面及邮件金额保留原币种。
  汇率无效时跳过 CNY；积分、未知单位、无限 Key、未取得金额和查询错误均不当作低余额或恢复。
- 复用报告收件人，不依赖「每小时系统运行与错误邮件报告」开关。SMTP 区域保持收件人可编辑，并明确
  提示它被两种通知共享；清空收件人后不再发送低余额邮件。每次投递前重新读取主库收件人。

### 实现边界与投递语义
