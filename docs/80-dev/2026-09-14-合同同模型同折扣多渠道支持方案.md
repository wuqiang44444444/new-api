# 合同同模型同折扣多渠道支持方案

## 问题与目标

当前同一合同内一个公开模型只能绑定一个具体渠道。用户要求：不同渠道提供同一个公开模型时，
只要合同折扣相同，允许这些渠道的模型规则同时出现在同一合同中。

用户已于 2026-09-14 确认本次分析中的逻辑，并要求将方案写入 `docs/80-dev/`。
本文记录已确认的目标规则、实施边界和验收要求；当前仅完成分析与方案落盘，尚未实施功能，
不代表代码、数据库迁移、真实 Provider、真实账单或生产灰度已验证。

目标是把普通渠道合同从“同模型固定一个渠道”扩展为“同模型允许多个明确渠道，共享同一合同折扣”。
合同仍由 API Key 绑定，不扩大到未绑定该合同的 Key，也不改变合同所有权和启停语义。

用户补充确认：API 密钥处应显示该密钥绑定合同的具体模型和合同折扣，不显示渠道。
新建 API 密钥时，用户只有一份合同且该合同已启用，界面自动选中此合同；用户可以手动取消绑定。

## 当前实际情况

以下结论来自本次对当前工作区代码及合同专题架构的只读核对：

| 层面 | 当前行为 | 代码依据 |
| --- | --- | --- |
| 模型选择 | 已添加的模型从候选中排除 | `web/src/features/users/components/user-contract-add-rule.tsx` |
| 编辑器校验 | 按模型名忽略大小写拒绝重复添加 | `web/src/features/users/components/user-contract-drawer.tsx` |
| 后端校验 | 实体规则复用旧规则规范化，拒绝同模型或仅大小写不同的重复 | `model/customer_contract_entity.go`、`model/customer_contract.go` |
| 数据库 | 规则唯一索引为 `contract_id + public_model` | `model/customer_contract_entity.go` |
| 请求解析 | 命中同模型第一条规则立即返回其渠道、路由组和折扣 | `service/customer_contract_entity.go` |
| 渠道约束 | 通过合同 pin 固定具体渠道，采用单次执行约束 | `middleware/customer_contract.go` |
| 模型与价格投影 | 多处按规则逐条输出，尚未支持同合同同模型多渠道聚合 | `controller/customer_contract_models.go`、`service/customer_contract_pricing.go`、`service/customer_contract_view.go` |

因此只移除界面重复提示或后端校验并不足以支持本需求；即使可以保存，当前解析仍只使用第一条规则。

新建 API 密钥的当前默认值为 `contract_id = 0`，合同选择组件没有唯一合同自动选择逻辑。
`web/src/features/keys/components/__tests__/api-keys-mutate-drawer.test.tsx` 中现有测试明确使用
一份启用合同，并断言新建界面默认“不绑定合同”。`controller/token.go` 的创建入口按请求中的
`contract_id` 保存，不自动补绑。因此下述唯一合同默认选择属于待实现的新行为。

当前架构依据为[用户模型合同定价架构](../20-architecture/账单计费-用户模型合同定价架构.md)。
[用户模型合同定价产品文档](../10-product/用户模型合同定价.md)仍描述旧的用户级合同和组内原生选渠，
与已核对代码及当前架构存在差异；实施时需要同步修正，不能以旧描述推断新功能已经存在。

## 优化方案

### 1. 已确认的规则

“同模型”指客户请求中完全相同的公开模型名，继续使用精确匹配；不根据 Provider 模型、
`model_mapping`、名称相似度或价格推断模型等价。

| 同一合同内的配置 | 处理 |
| --- | --- |
| 公开模型相同、渠道不同、合同折扣相同 | 允许共存 |
| 公开模型相同、渠道不同、合同折扣不同 | 拒绝保存 |
| 公开模型相同、渠道相同，重复添加 | 拒绝保存，即使路由组不同也不构成另一条合法重复规则 |
| 模型名仅大小写不同 | 延续现有跨数据库一致性约束，拒绝共存 |
| 不同合同中的相同模型 | 保持各合同独立配置渠道和折扣的既有行为 |

折扣相等按现有八位定点 `ratio_units` 判断，不比较输入文本或浮点近似值。
例如 `0.8`、`80%`、`8折` 均规范化为 `80000000`；合法范围继续为 `1..100000000`，
不允许零折扣、负值、超过一或超出已有精度。

新增、编辑、完整替换和重新启用均须校验完整规则集。同模型已有多条渠道规则时，不能仅修改其中
一条折扣而留下不一致状态；管理员可以在同一次完整替换中把该模型的所有规则改为相同新折扣。
沿用既有停用入口的可操作性，渠道失效不能阻止管理员停用合同。

### 2. 价格语义

本次确认的是合同折扣相同，不额外要求路由组相同，也不承诺各渠道最终成交价格相同。
继续遵循既有计费顺序：

```text
客户模型费用 = 原生模型费用小计 × 有效原生组倍率 × 合同模型折扣
```

有效原生组倍率包含当前适用的特殊组倍率。以相同模型费用小计 100、合同折扣 0.8 为例：

| 渠道 | 绑定组的有效倍率 | 模型费用 |
| --- | --- | --- |
| A | 1 | 80 |
| B | 0.9 | 72 |

上述两条规则满足共存条件。模型价格、组倍率变化继续沿用现有语义；合同折扣不作用于独立工具费、
违规费、充值折扣或 Provider 成本。不能为获得同价效果而覆盖现有组倍率或新增平行计价规则。

若后续要求“无论选择哪个渠道，客户价格都一样”，应另行明确最终计价一致性要求，不视为本次目标。

### 3. 请求选择与执行边界

客户端仍只提交公开模型名，不要求客户新增渠道参数。

普通渠道首次选择的方向为：在合同中该模型明确列出的、当前能够履行本次请求的渠道范围内，
按渠道优先级和权重选择。必须保留对应规则的路由组，不得扩展到合同未列出的组内其他渠道。
实现前需核对既有选渠接口能否在这一范围内复用；不同路由组规则的统一选择接线和优先级、权重
解释需要在实现中明确并直接验证，不能退化为取第一条、各组自行分发或依赖数据库返回顺序。

选定渠道后，在资金预扣和 Provider 请求发送前冻结合同 ID、版本、公开模型、实际渠道、对应路由组
及折扣。继续采用当前单次执行约束，本需求不增加发送失败后的自动重试、跨渠道重发或 fallback。
首次选择时某渠道已停用或不具备履约资格，可以从其余合法合同渠道中选择；全部不可用则明确失败。
合同读取、版本或规则一致性异常仍失败关闭，不能视为普通渠道不可用后回退原生权限。

指定渠道和依赖既有任务原渠道的操作，必须验证该渠道属于当前合同中该模型的合法规则并能履约，
不能先随机选另一条规则再据此拒绝原渠道，也不能用指定渠道绕过合同。已受理任务继续按既有冻结
事实执行，不因当前合同删改、Key 换绑或渠道配置变化而重选、重定价。

专用入口继续遵守[硬约束](../00-context/硬约束.md)：

- Seedance 保留同一个启用客户模型只能对应一个 Seedance Channel 的约束，不因折扣相同放开多渠道。
- Azure Batch 等类型化入口不能仅凭模型同名、折扣相同就混入普通渠道池；其接口资格和计价方式仍由
  既有专用入口与代码协议决定。本次不扩展这些入口的独立多渠道分发能力。
- 异步创建结果未知时继续禁止自动重发、换渠道和退款；冻结事实及资金幂等不变量不变。

### 4. 数据与写入的最小改动

保留现有合同实体和规则表，不建立第二套合同或路由事实源：

1. 将实体规则唯一约束调整为 `contract_id + public_model + channel_id`；折扣不纳入唯一键，
   避免让同模型同渠道的不同折扣成为合法记录。
2. 在实体规则保存边界统一校验同模型折扣一致及模型、渠道组合不重复，保留精确模型名和合法组校验。
   不为本需求放宽旧迁移数据源的历史规则，也不增加新旧双读。
3. 显式迁移旧唯一索引，不能只修改 GORM 标签并假定旧索引会自动删除；保留现有单渠道规则数据，
   分别验证 SQLite、MySQL 和 PostgreSQL 的升级结果与重复执行行为。
4. 沿用完整替换事务、`expected_version`、合同行锁、版本递增、`auth_version` 缓存失效围栏及审计。
   错误提交不得留下部分修改；并发保存不得产生同模型不同折扣的混合状态。
5. 请求规则解析和模型聚合直接在现有合同专属代码内扩展。只有明确必需的选渠接线才触及原生热路径，
   并说明必要性及未来上游同步冲突面，不复制整套原生分发实现。

### 5. 管理端、客户投影与统计

- 管理端保留模型、渠道、路由组和折扣明细；已添加模型允许继续选择其他渠道，阻止相同模型与渠道
  重复添加，并对折扣冲突给出明确提示。保存时再次校验全部规则，不能仅校验新增操作。
- 同模型折扣修改应支持管理员一次完成所有关联规则的一致更新，使用现有一次完整替换提交。
- 客户模型列表按公开模型去重；某模型至少存在一条符合本次入口及计价要求的可用渠道规则时，
  才能投影为可调用。不得出现列表显示可用、调用却固定到失效首条规则的情况。
- 客户价格投影不能按模型名任取第一条价格；相同价格可合并，不同有效价格需要明确表达差异。
  具体展示形式在实施中按现有价格接口和界面确定，不暴露渠道、Provider、路由组或上游模型身份。
- 合同总览保留“规则数”作为渠道规则数量；需要展示“模型数”时单独按公开模型去重，不能混用两种
  口径。不可用规则数与模型整体是否可调用也应分别计算和解释。
- 涉及新增提示和界面文案时按项目 i18n 规范维护全部支持语言。

#### API 密钥处的合同折扣展示

API 密钥处须提供当前密钥绑定合同的折扣明细，展示字段为“模型”和“合同折扣”。例如：

| 模型 | 合同折扣 |
| --- | --- |
| model-a | 8折 |
| model-b | 9折 |

- 数据范围仅为该密钥绑定的合同，不合并同一用户的其他合同。密钥换绑或合同更新后，明细应随已提交
  的绑定和合同事实刷新，不能继续展示旧合同折扣。
- 同一公开模型绑定多个渠道且折扣相同时，只显示一行模型及折扣；按公开模型聚合，不能按渠道重复
  展示，也不能隐藏合同中其他模型。此明细表达合同约定，模型当前不可用不抹去其已约定折扣。
- “合同折扣”取该模型的 `ratio_units`，按既有精度格式化，不把组倍率、渠道折扣或最终有效倍率
  冒充合同折扣。例如合同八折、组倍率 0.9 时，此处显示“8折”，不显示“7.2折”。
- 不展示渠道名称、渠道 ID、路由组、Provider 或上游模型；客户侧数据投影不为此明细增加这些字段，
  不依靠前端隐藏管理员接口返回的渠道信息。此规则不改变管理员合同编辑器的内部渠道配置明细。
- 未绑定合同时明确显示未绑定状态，不虚构合同模型或默认折扣；合同已停用时明确标注未生效，
  保留的合同明细不能被解释为该密钥正在使用的折扣。合同读取失败时显示加载失败状态，不能伪装为
  未绑定或使用倍率 1 替代真实合同折扣。
- 具体入口和布局在实施中复用 API 密钥处现有合同展示；本补充要求展示模型及合同折扣，不要求在
  该明细中新增渠道或逐渠道价格。其他既有价格投影继续遵守前述准确表达价格差异的规则。

#### 新建 API 密钥的默认合同选择

用户已确认以下新建界面规则：

| 用户合同情况 | 新建界面默认选择 |
| --- | --- |
| 总共只有一份合同，且已启用 | 自动选中该合同，并显示其模型及合同折扣 |
| 没有合同 | 不绑定合同 |
| 总共只有一份合同，但已停用 | 不绑定合同 |
| 有多份合同，包括只有一份启用、其余停用的情况 | 不自动选择，由用户决定 |

判定依据为用户全部合同数量，不是筛选后的启用合同数量。自动选择仅作为新建表单的初始值，
不改变后端合同归属校验和绑定规则：

- 合同列表成功加载且新建表单尚未被用户手动选择合同时，初始化一次默认选择。加载失败或结果
  不完整时不能推断唯一合同，也不能用缓存中的其他用户数据初始化。
- 用户可以改为“不绑定合同”或其他合法选项；本次打开期间的重新渲染、数据刷新和其他字段修改
  不得覆盖其主动选择，包括主动选择 `contract_id = 0`。不能仅凭当前值为零判断用户尚未操作。
- 自动选中后，提交使用表单中的实际 `contract_id`；用户取消绑定后仍提交零。后端不依据合同数量
  补绑，直接调用创建 API 且未指定合同时继续保持未绑定语义。
- 编辑已有 KEY 保留已存绑定，包括未绑定及绑定已停用合同的情况；不能因用户只有一份启用合同就
  自动修改已有 KEY。关闭后再次打开全新创建表单，可以按当次加载的合同事实重新初始化。
- 初始化合同选择需与现有新建表单重置顺序协调，避免异步合同返回后被其他初始化覆盖，也避免
  数据刷新反复触发默认绑定。复用现有合同查询和表单状态，不新增持久化默认合同字段。

### 6. 验收与剩余事项

以下均为待执行验收项，不能作为已通过记录：

- [ ] 同模型不同渠道同折扣可保存并重新读取；等价折扣输入按定点数识别为相同值。
- [ ] 折扣冲突、同模型同渠道重复和仅大小写不同的模型均拒绝，失败不改变已提交合同。
- [ ] 编辑、重新启用及并发版本冲突保持一致性；合法更新后旧合同缓存不能继续生效。
- [ ] 首次选择只使用合同明确授权且适用本次请求的渠道；验证优先级、权重与不同路由组接线，
  不用随机大循环或时间比较代替可观察规则的确定性测试。
- [ ] 一条渠道不可用时仍可使用其他合法规则；全部不可用、合同异常和合同外指定渠道均失败关闭。
- [ ] 选择完成后不发生新增跨渠道重发；既有任务原渠道操作按对应规则校验。
- [ ] 相同折扣、不同组倍率按实际选中规则计算，并在预扣和异步冻结事实中保持一致。
- [ ] 模型列表去重、价格差异准确表达，统计区分模型和规则，不暴露内部渠道身份。
- [ ] API 密钥处展示所绑定合同的模型和具体合同折扣；同模型多渠道只显示一行，不混入其他合同。
- [ ] 合同八折且组倍率 0.9 时，折扣明细仍显示八折；渠道名称、ID、路由组及上游身份不出现在该明细。
- [ ] 密钥换绑及合同更新后折扣明细刷新；未绑定、已停用和加载失败状态准确，不虚构生效折扣。
- [ ] 仅有一份启用合同时，新建 KEY 自动选中该合同、显示模型与折扣，并提交正确的合同 ID。
- [ ] 无合同、唯一合同停用、多份合同均不自动选择；多份合同中仅一份启用也不自动选择。
- [ ] 手动取消绑定后提交零，数据刷新和表单重置不覆盖主动选择；编辑已有 KEY 保留原绑定。
- [ ] 合同异步加载与新建初始化顺序正确，读取失败不推断默认合同；后端创建 API 不自动补绑。
- [ ] Seedance、Batch 等专用入口边界与未绑定合同 Key 的原生行为保持正确。
- [ ] 三数据库完成旧索引升级、重复执行迁移、历史单渠道规则及新唯一约束验证。
- [ ] 在途异步任务按创建时事实结算，合同修改和 Key 换绑不改变历史收费。
