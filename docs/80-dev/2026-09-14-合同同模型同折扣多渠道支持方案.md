# 合同同模型同折扣多渠道支持方案

## 问题与目标

实施前，同一合同内一个公开模型只能绑定一个具体渠道。用户要求：不同渠道提供同一个公开模型时，
只要合同折扣相同，允许这些渠道的模型规则同时出现在同一合同中。

用户已于 2026-09-14 确认需求，并进一步明确：合同与分组不同，合同仅是折扣，不影响后续渠道选择，
包括优先级、权重等既有逻辑。本方案以这一最新边界为准。
本文记录已确认的目标规则、实施边界和验收要求。联合评审发现的价格投影、历史来源校验及失败状态问题已修复，相关本地回归通过。
真实 Provider、真实账单、MySQL/PostgreSQL 升级演练与生产灰度仍未验证。

## 联合评审修复范围（2026-09-14）

已按用户授权先更新方案再实施下列修复；本节记录实际验证范围，不以测试总数代替验收证据。

- [x] 普通与 Batch 分别由已有执行模式确定基础价格，再叠加合同折扣；管理员 Batch 来源预览不得
  误用同名同步价格。当前发现属于报价错误，没有证据表明实际 Batch 扣费因此出错。
- [x] 已接受来源的历史组删除后，仍可修改折扣、停用和重新启用；当前组存在性只校验新增或变更来源。
- [x] 密钥合同查询的 HTTP 200、`success:false` 也必须显示读取失败，不伪装为无合同或停用；
  客户模型去重保留后端为唯一权威，移除两处前端重复去重。
- [x] 用确定性渠道优先级比较绑定前后选择，覆盖缓存开与关；补普通与 Batch 同名同折扣共存，
  以及编辑已有密钥不自动改绑的行为测试。
- [x] 跨库测试补旧索引构造、历史数据保留、迁移重入与新唯一约束验证；原有空库建表测试不等于升级
  测试。未配置 MySQL/PostgreSQL 测试数据库时必须记为跳过，不能记为验收通过。

存量 Key 的原组、模型限制与指定渠道 pin 将按既有原生语义生效，应在升级核对中单独记录；
本次不修改原生 pin 的权限语义。偶发测试失败需要失败日志与复现证据，不预先认定为既有问题。

目标是允许同模型同折扣的不同渠道记录共存，并将合同从现有授权、固定渠道逻辑中解耦为客户折扣层。
运行时只按“绑定合同 + 精确公开模型”解析唯一折扣；渠道记录是管理配置明细，不构成路由候选集合。
合同仍由 API Key 绑定，保留合同所有权和启停；分组、模型权限、渠道资格和分发继续由既有机制决定。

此前提出的合同专属候选选择、跨组优先级比较、合同渠道过滤器、合同 pin 和合同单次执行限制，
均不属于本方案目标，不得实施。本文中的当前实现描述用于说明待移除的耦合，不代表应继续保留。

用户补充确认：API 密钥处应显示该密钥绑定合同的具体模型和合同折扣，不显示渠道。
新建 API 密钥时，用户只有一份合同且该合同已启用，界面自动选中此合同；用户可以手动取消绑定。

## 优化方案

### 1. 已确认的规则

“同模型”指客户请求中完全相同的公开模型名，继续使用精确匹配；不根据 Provider 模型、
`model_mapping`、名称相似度或价格推断模型等价。

| 同一合同内的配置 | 处理 |
| --- | --- |
| 公开模型相同、渠道不同、合同折扣相同 | 允许共存 |
| 公开模型相同、渠道不同、合同折扣不同 | 拒绝保存 |
| 公开模型相同、渠道相同，重复添加 | 拒绝保存，即使路由组不同也不构成另一条合法重复规则 |
| 模型名仅大小写不同 | 延续现有跨数据库一致性约束，拒绝共存 |
| 不同合同中的相同模型 | 各合同独立约定折扣，按 Key 当前绑定的合同生效 |

折扣相等按现有八位定点 `ratio_units` 判断，不比较输入文本或浮点近似值。
例如 `0.8`、`80%`、`8折` 均规范化为 `80000000`；合法范围继续为 `1..100000000`，
不允许零折扣、负值、超过一或超出已有精度。

新增、编辑、完整替换和重新启用均须校验完整规则集。同模型已有多条渠道规则时，不能仅修改其中
一条折扣而留下不一致状态；管理员可以在同一次完整替换中把该模型的所有规则改为相同新折扣。
沿用既有停用入口的可操作性，渠道失效不能阻止管理员停用合同。

管理明细中的 `channel_id` 表示模型配置来源；现有 `route_group` 若继续用于管理展示，也仅为配置
上下文。两者均不得参与运行时折扣匹配，不得据此覆盖实际执行渠道或组。运行时从同模型明细得到
一个唯一折扣，不按“模型 + 实际渠道”分支定价，不因选中其他合法渠道而失去合同折扣。

合同仅提供折扣的业务结果明确如下：

| 请求情形 | 目标行为 |
| --- | --- |
| Key 未绑定合同，或绑定合同已停用 | 原有权限、分发和计费，不应用合同折扣 |
| 已启用合同包含请求模型 | 原有权限及分发通过后，对模型费用应用该模型唯一合同折扣 |
| 已启用合同未包含请求模型 | 继续按原有权限和价格处理，不因合同未列出而拒绝，不虚构折扣事实 |
| 模型存在合同折扣，但原有模型权限或入口资格不满足 | 由原有机制拒绝；有折扣不授予调用权限 |
| 实际选中渠道未出现在合同管理明细中 | 不改变原有选择结果；同一公开模型仍应用合同折扣 |
| 合同读取失败、归属错误、版本或折扣一致性异常 | 计费前失败关闭，不擅自使用原价、旧折扣或倍率 1 |

“合同成功读取但未约定该模型折扣”与“无法确认合同折扣”是不同状态，不能混同。

### 2. 价格语义

合同折扣不要求管理明细的路由组相同，也不决定实际请求使用哪个组。价格以既有执行链得到的模型
费用和实际有效组倍率为基础，不承诺不同合法分组上下文的最终成交价格相同。
继续遵循既有计费顺序：

```text
客户模型费用 = 原生模型费用小计 × 有效原生组倍率 × 合同模型折扣
```

有效原生组倍率包含当前适用的特殊组倍率，来自既有分组规则，而非合同明细里的 `route_group`。
以相同模型费用小计 100、合同折扣 0.8 为例：

| 既有分组逻辑确定的请求上下文 | 实际有效组倍率 | 模型费用 |
| --- | --- | --- |
| 使用组 A | 1 | 80 |
| 使用组 B | 0.9 | 72 |

示例中的组来自原有分发，不假定渠道只有一个组。模型价格、组倍率变化继续沿用现有语义；
合同折扣不作用于独立工具费、违规费、充值折扣或 Provider 成本。不能为获得同价效果而覆盖
现有组倍率或新增平行计价规则。

若后续要求“无论选择哪个渠道，客户价格都一样”，应另行明确最终计价一致性要求，不视为本次目标。

### 3. 请求选择与执行边界

#### 3.1 分发职责

客户端请求形状不变。合同读取只提供折扣，不设置或覆盖 `UsingGroup`、`TokenGroup`、AutoGroups、
跨组重试开关，不添加 `PinSourceContract`，不筛选合同渠道集合，不参与 Affinity 或指定渠道仲裁。
Token 模型限制、用户组权限、原生模型匹配和各入口验证保持其原有权威，不与合同模型清单求交集。

普通请求继续使用原有分发，优先级、权重、组顺序及允许的重试均不因绑定合同而变化。
不新增合同专属选择器、跨组比较算法或渠道集合过滤器，也不为合同统一或修复原生缓存与数据库
路径的权重差异。选渠所需的查询、缓存、入口过滤和锁定渠道验证复用各入口原有实现。

指定渠道和既有任务的原渠道依赖仍按原有权限和任务亲和规则处理，不要求实际渠道出现在合同明细。
合同明细渠道停用或删除不使模型折扣自动失效，不据此改变运行时模型可用性。

#### 3.2 折扣解析与事实冻结

合同折扣按精确公开模型解析并验证同模型折扣一致性；不能沿用“返回首条规则的渠道与组”语义。
无需按普通、Batch 或 Seedance 类型选择合同规则：入口决定执行方式及基础计费，合同提供同一模型
的统一乘数。已有渠道身份与入口过滤仍在原有执行链完成，不能从合同反向推断入口或 Provider。

在首次计费前确认并冻结合同 ID、版本、公开模型和折扣。实际执行组、渠道、原生倍率与基础计价事实
由既有执行链确定；需要记录它们时，必须从真实执行上下文取得，不复制合同管理明细中的值。
可以在选渠前解析折扣，但不能把尚未确定的执行字段填为零或空值后作为完整执行快照交给计费或任务。

实现时应核对 `ContractBillingFact`、`RelayInfo` 和 Task/attempt 的已有字段及消费方，避免引入第二套
执行快照：折扣事实只负责折扣，已有执行快照负责实际渠道与组；保留在旧冻结记录中的渠道和组仍是
历史事实，不反向参与新请求分发。若当前结构仍携带执行字段，新写入值须与实际执行一致，且不作为 pin。

原有普通请求允许重试时，折扣不能随重试重新读取当前合同或重复叠乘；每次尝试的渠道、组及计费
上下文按原有流程更新，最终费用与实际执行事实一致。异步任务仍在受理或发送边界持久冻结实际执行
和折扣事实；合同修改、删除规则及 Key 换绑不得重解释在途或历史任务。

专用入口继续遵守[硬约束](../00-context/硬约束.md)：

- Seedance 保留同一个启用客户模型只能对应一个 Seedance Channel 的约束，不因折扣相同放开多渠道。
- 同模型的普通渠道和类型化渠道管理明细可以在折扣相同时共存；这只是折扣配置，不表示可在同一
  入口混用。Azure Batch、Seedance 等接口资格、选渠及计价方式仍由各自入口与代码协议决定，
  不进入普通渠道池，也不因合同新增独立多渠道分发能力。
- 异步创建结果未知时继续禁止自动重发、换渠道和退款；冻结事实及资金幂等不变量不变。

### 4. 数据与写入的最小改动

保留现有合同实体和规则表作为配置与折扣事实源，不建立第二套折扣表或合同路由事实源：

1. 将实体规则唯一约束调整为 `contract_id + public_model + channel_id`；折扣不纳入唯一键，
   避免让同模型同渠道的不同折扣成为合法记录。
2. 在实体规则保存边界统一校验同模型折扣一致及模型、渠道组合不重复。新增或替换模型来源时校验
   其引用合法性；已有来源渠道后续不可用不能自动取消折扣，也不能阻止保存其他折扣或重新启用
   合同。不得继续把“所有明细渠道当前可履约”作为合同生效条件。不增加旧数据源的运行时双读。
3. 显式迁移旧唯一索引，不能只修改 GORM 标签并假定旧索引会自动删除；保留现有单渠道规则数据，
   分别验证 SQLite、MySQL 和 PostgreSQL 的升级结果与重复执行行为。
4. 沿用完整替换事务、`expected_version`、合同行锁、版本递增、`auth_version` 缓存失效围栏及审计。
   错误提交不得留下部分修改；并发保存不得产生同模型不同折扣的混合状态。
5. 删除合同专属 pin、强制组、模型白名单和重试覆盖接线；折扣读取、聚合、审计与计费乘数保留在
   合同专属代码内。原生文件只做移除这些耦合和必要计费接线的最小修改，说明上游同步影响，不重写
   原生选择器。无调用方的合同 pin 标识和专属路由辅助逻辑直接删除，不留兼容分发开关。
6. 升级前核对绑定合同 Key 保留的原组、AutoGroups 和模型限制；解除合同路由覆盖后，这些配置将按
   原有语义生效。不得为了维持旧路由而将合同组自动写回 Key。旧任务冻结数据不重写，旧迁移入口
   仅负责生成折扣明细及绑定，不再由迁移产生运行时渠道授权。需验证升级对存量 Key 的实际影响。

### 5. 管理端、客户投影与统计

- 管理端保留模型来源及折扣明细，明确渠道和组不是执行绑定；已添加模型允许继续选择其他渠道，
  阻止相同模型与渠道重复添加，并对折扣冲突给出明确提示。保存时再次校验全部规则，不能仅校验新增操作。
- 同模型折扣修改应支持管理员一次完成所有关联规则的一致更新，使用现有一次完整替换提交。
- `/v1/models`、模型详情和控制台可调用模型选择继续按原有权限及入口可用性投影，不能只返回合同
  清单，也不能因合同包含某模型而新增原本无权调用的模型。API 密钥处的合同折扣明细另按公开模型去重。
- 客户价格投影先沿用原有可访问模型、执行模式和组倍率，再对已约定模型应用合同折扣；不按合同
  明细首条渠道或 `route_group` 取价。不同原生价格上下文继续准确展示，不暴露内部渠道身份。
- 合同总览保留“规则数”作为渠道规则数量；需要展示“模型数”时单独按公开模型去重，不能混用两种
  口径。来源渠道失效仅为管理信息，不能把它解释为 Key 零调用权限；现有 `zero_access` 等基于
  合同规则的状态需调整，不建立另一套模型可用性事实。
- 涉及新增提示和界面文案时按项目 i18n 规范维护全部支持语言。

#### API 密钥处的合同折扣展示

API 密钥处须提供当前密钥绑定合同的折扣明细，展示字段为“模型”和“合同折扣”。例如：

| 模型 | 合同折扣 |
| --- | --- |
| model-a | 8折 |
| model-b | 9折 |

- 数据范围仅为该密钥绑定的合同，不合并同一用户的其他合同。密钥换绑或合同更新后，明细应随已提交
  的绑定和合同事实刷新，不能继续展示旧合同折扣。
- 同一公开模型绑定多个渠道且折扣相同时，只显示一行模型及折扣；按公开模型聚合，不能按渠道重复
  展示，也不能隐藏合同中其他模型。此明细表达合同约定，模型当前不可用不抹去其已约定折扣。
- “合同折扣”取该模型的 `ratio_units`，按既有精度格式化，不把组倍率、渠道折扣或最终有效倍率
  冒充合同折扣。例如合同八折、组倍率 0.9 时，此处显示“8折”，不显示“7.2折”。
- 不展示渠道名称、渠道 ID、路由组、Provider 或上游模型；客户侧数据投影不为此明细增加这些字段，
  不依靠前端隐藏管理员接口返回的渠道信息。此规则不改变管理员合同编辑器的内部渠道配置明细。
- 未绑定合同时明确显示未绑定状态，不虚构合同模型或默认折扣；合同已停用时明确标注未生效，
  保留的合同明细不能被解释为该密钥正在使用的折扣。合同读取失败时显示加载失败状态，不能伪装为
  未绑定或使用倍率 1 替代真实合同折扣。
- 具体入口和布局在实施中复用 API 密钥处现有合同展示；本补充要求展示模型及合同折扣，不要求在
  该明细中新增渠道或逐渠道价格。该明细是折扣清单，不是此 Key 的全部可调用模型清单。
  其他既有价格投影继续遵守前述准确表达价格差异的规则。

#### 新建 API 密钥的默认合同选择

用户已确认以下新建界面规则：

| 用户合同情况 | 新建界面默认选择 |
| --- | --- |
| 总共只有一份合同，且已启用 | 自动选中该合同，并显示其模型及合同折扣 |
| 没有合同 | 不绑定合同 |
| 总共只有一份合同，但已停用 | 不绑定合同 |
| 有多份合同，包括只有一份启用、其余停用的情况 | 不自动选择，由用户决定 |

判定依据为用户全部合同数量，不是筛选后的启用合同数量。自动选择仅作为新建表单的初始值，
不改变后端合同归属校验和绑定规则：

- 合同列表成功加载且新建表单尚未被用户手动选择合同时，初始化一次默认选择。加载失败或结果
  不完整时不能推断唯一合同，也不能用缓存中的其他用户数据初始化。
- 用户可以改为“不绑定合同”或其他合法选项；本次打开期间的重新渲染、数据刷新和其他字段修改
  不得覆盖其主动选择，包括主动选择 `contract_id = 0`。不能仅凭当前值为零判断用户尚未操作。
- 自动选中后，提交使用表单中的实际 `contract_id`；用户取消绑定后仍提交零。后端不依据合同数量
  补绑，直接调用创建 API 且未指定合同时继续保持未绑定语义。
- 编辑已有 KEY 保留已存绑定，包括未绑定及绑定已停用合同的情况；不能因用户只有一份启用合同就
  自动修改已有 KEY。关闭后再次打开全新创建表单，可以按当次加载的合同事实重新初始化。
- 初始化合同选择需与现有新建表单重置顺序协调，避免异步合同返回后被其他初始化覆盖，也避免
  数据刷新反复触发默认绑定。复用现有合同查询和表单状态，不新增持久化默认合同字段。
