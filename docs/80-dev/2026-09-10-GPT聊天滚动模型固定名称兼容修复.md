# GPT 聊天滚动模型固定名称兼容修复

## 问题与目标

用户明确要求将精确模型名称 `gpt-chat-latest` 按当前 `gpt-5.6` 处理。
此前[rc36 复测](./2026-09-10-rc36聊天模型参数兼容性复测记录.md)已证明该名称未命中能力表，
渠道测试仍发送 `max_tokens`，在模拟上游复现参数 400。

## 当前实际情况

### 名称与版本依据

[Microsoft Foundry 模型目录](https://ai.azure.com/catalog/models/gpt-chat-latest)在本次查阅时列明
`gpt-chat-latest`、版本 `2026-08-06`、Preview、OpenAI 发布、Azure 托管，并列出 Chat completion 和 Responses。
用户提供其动态滚动更新的定位，本次将该字符串作为稳定匹配名称；不把版本日期拼入模型 ID，
不将实际发送的名称重写为 `gpt-5.6`。当前参数兼容决策来自用户明确要求，不代表模型后续每个版本
与 GPT-5.6 的全部能力永久相同。

### 已实施行为

- 在既有 `GetOpenAIChatCapabilities` 登记精确的 `gpt-chat-latest`，共用已有参数能力逻辑。
- 与当前 `gpt-5.6` 一致：启用 `max_completion_tokens`、使用 `developer` 系统角色，移除
  `temperature`、`top_p`、`logprobs`、`top_logprobs`。未传、`none`、`low`、`high` 推理档位的能力结果均已对照。
- 适配器继续使用映射后的模型名称。`chat-latest` 或任意客户别名准确映射到 `gpt-chat-latest` 时生效。
- 不将 `chat-latest` 裸名、`gpt-chat-latest-preview`、拼接日期名或不透明部署名自动纳入；
  客户名为 `gpt-chat-latest` 但最终映射到 `deployment-a` 时也不会凭客户名触发。
- 未修改模型家族识别函数、模型映射、测试控制器、正式处理器或透传行为。双非零 token 字段与
  参数覆盖重新加入旧字段仍遵循上游现状，未在本次扩大修复范围。

### 原生改动必要性与同步影响

生产代码只修改 `relaykit/dto/openai_request.go` 的一处能力准入条件并补一句注释。
现有登记函数没有外部注册入口；新增一个精确名称判断是将原生渠道纳入现有转换的最小修改，
无需本地包装器、第二套能力表或在控制器复制规则。
新增测试分别位于独立文件 `relaykit/dto/openai_chat_latest_test.go` 和
`relay/channel/openai/chat_latest_compatibility_test.go`。
未来同步应复查上游是否已经登记该名称；如已登记，应按上游事实消除本地重复条件并复跑回归。

## 优化方案与验证结果

用户后续要求的正式验收见[验收记录](./2026-09-10-GPT聊天滚动模型验收记录.md)。[联合评审修复与复验](2026-09-10-多方案联合评审问题修复与验证记录.md)已确认当前根模块构建及后端全量测试通过，素材协议残留引用阻塞已解除；真实 Azure 官方渠道仍待定位和调用。以下保留此前隔离验证的执行背景。

- 实际工作区：`cd relaykit && GOWORK=off go test ./dto`、`GOWORK=off go build ./...` 均通过。
- OpenAI/Azure adapter 测试覆盖精确名称、两个客户别名、反向映射到未知部署及裸名不匹配，
  每项覆盖流式和非流式，共 20 个序列化请求用例通过。
- 渠道全链路探针增加两个映射到 `gpt-chat-latest` 的别名，合计 69 个渠道用例：49 个模拟调用成功、
  20 个复现其余已知 400；另有 7 个正式发送行为用例。三个 `gpt-chat-latest` 场景的
  自动/显式 Chat、流式/非流式共 12 个用例全部成功，最终只有新 token 字段。
- 后两项在此前已验证的 rc36 隔离副本，通过 Go overlay 加载本次实际修改及新增测试后执行。
  原因是本次测试期间，实际工作区的另一个素材协议删除改动仍留下
  `VideoUpstreamProtocolMoxingMediaTaskV1`、`AssetUpstreamProfileMoxingJoyCreator` 引用，
  根模块因此编译失败。没有为运行测试恢复这些协议或加入兼容常量；隔离结果不能记作当前整个工作区构建通过。
- 上游 HTTP 全部由测试拦截，未调用真实 Azure/OpenAI、未部署；真实渠道验收仍待部署后完成。
- 内部文档执行 `task docs:check`、`task ai:check`。

本机隔离诊断文件与日志：`/private/tmp/yuan-chat-token-check/isolated-overlay.json`、
`isolated-fixed-results.log`；实际工作区失败日志保留在同目录 `fixed-results.log`。
