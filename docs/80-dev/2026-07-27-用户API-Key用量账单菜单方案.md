# 用户 API Key 用量账单设计与实施记录

## 1. 背景与目标

实施前，系统已经分别提供 API Key 管理、模型调用仪表盘、用量日志、钱包和充值记录，但这些信息分散在不同页面，尚未形成一个以“账单周期、API Key、模型和最终结算费用”为中心的用户账单入口。

本次实施在遵循最小入侵原则的前提下，新增了一个独立、正式、可追溯的用户账单菜单，满足以下需求：

1. 默认展示本周所有 API Key、所有模型的调用 Token、费用、资金和运行指标。
2. 展示输入 Token、输出 Token、总 Token、调用次数、费用等汇总。
3. 按 API Key 和模型提供正式的账单明细与调用下钻入口。
4. 历史费用以请求实际结算结果为准，不使用当前价格重新推算。
5. 不重构现有 Dashboard、Wallet、Usage Logs 或计费主链路。

当前页面定位为“用量账单（Usage Statement）”，用于展示平台用量和费用结算记录，不直接等同于税务发票。

## 2. 结论

账单使用独立路由：

```text
/billing
```

菜单位于“个人”区域的“钱包”之后：

```text
个人
├── 钱包
├── 账单
└── 个人设置
```

账单没有并入 Dashboard，原因如下：

- Dashboard 面向运行分析，账单面向周期结算，两者信息层级不同。
- Dashboard 当前默认最近一天，而账单要求默认本周。
- 账单需要余额、费用计算和明细下钻，继续扩展 Dashboard 会增加耦合与未来上游合并冲突。
- 独立 `features/billing/` 可以让绝大多数新增代码位于新文件中，现有文件只保留必要接线。

本次实施直接增加专用账单聚合接口，以消费与退款结算日志为数据源，一次性交付输入、输出 Token、最终费用和平均响应耗时。该实现不新增数据库结构，也不修改计费、结算和退款主链路。

## 3. 现有能力分析

### 3.1 数据源选择

当前账单没有复用 `/api/data/flow/self` 或 `quota_data`，而是通过专用接口 `/api/billing/self` 直接聚合消费与退款结算日志。原因是 `flow` 接口和 `quota_data` 只能提供总 Token 与额度，无法同时提供输入/输出 Token 拆分、平均响应耗时、流式请求和退款结算信息。

`quota_data` 原有能力包括以下小时级维度：

- 用户
- 模型
- API Key ID
- 渠道
- 节点
- 请求数
- 总 Token
- 最终消费额度

`/api/data/flow/self` 可以对当前用户按：

```text
API Key + 模型
```

汇总并返回：

- `token_id`
- `token_name`
- `model_name`
- `count`
- `token_used`
- `quota`

这些能力只用于说明现有数据基础，不是当前账单的数据源。当前账单不新增数据库字段，并在日志聚合结果中按 `token_id + model_name` 合并，形成清晰的 API Key × 模型账单行。

### 3.2 调用与计费明细

消费日志已经记录：

- API Key ID 和名称
- 模型名称
- 输入 Token
- 输出 Token
- 最终扣费额度
- 请求耗时
- 是否流式调用
- 请求 ID
- 上游请求 ID
- 计费扩展信息

计费扩展信息已经覆盖：

- 按 Token 计费的模型倍率
- 输出倍率
- 按次计费价格
- 缓存读取和缓存创建价格
- 图片、音频、文件搜索和联网搜索价格
- 钱包或订阅计费来源
- 动态计费表达式快照
- 动态计费命中档位
- 最终结算费用

现有用量日志详情已经能够展示上述费用计算过程。账单页没有复制费用解释器，而是从账单明细跳转到用量日志，并携带：

- API Key 名称
- 模型名称
- 开始时间
- 结束时间
- 日志类型为消费和退款

用户可在调用详情中查看单次请求的完整费用计算。

### 3.3 资金信息

现有用户和钱包接口已经能够提供：

- 当前余额
- 累计消费
- 累计请求数
- 充值记录
- 实际支付金额
- 充值额度
- 支付方式
- 订单状态

当前账单展示：

- 当前账户余额。
- 历史累计消费。
- 本周期消费、退款和非负净费用。

当前数据结构不能严格还原任意历史时点的期初余额、期末余额或将充值记录与模型用量逐笔勾稽。因此页面不展示期初余额、期末余额、本周期充值或账务级记账流水。

## 4. 数据准确性边界

### 4.1 结算日志边界

账单直接读取消费与退款结算日志，不依赖 `quota_data` 的小时级缓存。页面显示接口响应中的数据生成时间，最终扣费以查询周期内的结算日志为准。

消费日志的生成受 `LogConsumeEnabled` 控制，并可能受到日志清理策略影响。关闭消费日志或清理历史日志后，对应期间的 Token、调用次数和费用可能无法完整展示。

### 4.2 异步任务结算行的聚合规则

Suno、视频等异步任务可能先写入一次初始消费日志，任务完成后再写入带有 `"task_id"` 的退款、补扣或结算调整日志。当前聚合规则为：

| 指标 | 是否包含带 `"task_id"` 的结算调整行 | 规则 |
|---|---:|---|
| 请求数 `requests` | 否 | 只统计不带 `"task_id"` 的消费行，避免把同一个异步任务重复算作模型调用 |
| 平均响应耗时 | 否 | 只对不带 `"task_id"` 的消费行求平均 |
| 流式请求数 | 否 | 只统计不带 `"task_id"` 的消费行 |
| 输入、输出和总 Token | 是 | 消费与退款日志中的 Token 均参与汇总；异步任务的最终真实 Token 可能记录在退款或补扣行 |
| 消费额度 `gross_quota` | 是 | 只累计消费类型日志的 quota，包括补扣 |
| 退款额度 `refund_quota` | 是 | 只累计退款类型日志的 quota |

因此，“请求数”表示逻辑模型调用次数，而 Token 和费用表示这些调用在查询周期内记录的结算结果，两者不是简单的逐行一一对应关系。不能把 Token 限制为仅统计消费类型，否则会漏掉记录在退款结算行上的异步任务真实 Token。

对于没有生成结算调整日志的异步任务，账单只展示结算日志中已经存在的 Token，不从任务表或当前价格配置补算。

### 4.3 历史价格不能使用当前配置重算

模型价格、倍率和动态计费表达式可能随时间调整。

账单必须遵循：

```text
历史费用 = 请求当时已经结算并写入日志的 quota
```

禁止使用当前模型价格和当前倍率重新计算历史账单，否则可能造成：

- 历史账单金额变化。
- 动态计费档位丢失。
- 缓存、音频、图片、搜索等附加费用被遗漏。
- 订阅抵扣和钱包扣费来源不一致。

费用计算公式只用于解释单次结算过程，不作为账单汇总金额的重新计算依据。

### 4.4 跨周期退款与非负费用

账单采用“日志发生时间”口径：消费和退款只归入各自日志 `created_at` 所在的查询周期。如果消费发生在上一个周期、退款发生在下一个周期，两个周期不会按原请求重新归属。

每个 API Key × 模型明细行按以下公式计算：

```text
净费用 = max(周期内消费额度 - 周期内退款额度, 0)
```

因此，只有跨期退款而没有同期消费的明细行显示为 0，不产生负费用或余额抵扣凭证。这是用量账单的明确边界；如需跨期冲销、期初期末余额或逐笔勾稽，应另建账务级流水，本阶段不实现。

### 4.5 响应耗时精度

平均响应耗时使用消费日志中的秒级 `use_time`。值为 0 的非异步结算消费行仍参与平均值，因为它既可能表示亚秒级请求，也可能表示历史日志未记录更高精度耗时；直接排除会造成向上偏差。页面不得将该指标解释为毫秒级精确延迟。

## 5. 页面信息架构

### 5.1 页面标题

菜单名称：

```text
账单
```

页面标题：

```text
用量账单
```

页面说明：

```text
按 API Key 和模型查看 Token 用量、调用表现与实际结算费用。
```

### 5.2 顶部筛选区

提供以下筛选：

- 账单周期。
- API Key。
- 模型。

周期快捷项：

- 本周，默认值。
- 上周。
- 最近 7 天。
- 最近 30 天。
- 自定义时间。

本周定义为：

```text
用户当前时区的周一 00:00 至当前时间
```

页面明确显示：

- 账单开始时间。
- 账单结束时间。
- 当前时区。
- 数据生成时间。

单次查询最多 31 天，与现有用户数据查询边界保持一致。

### 5.3 汇总卡片

首行展示六项核心指标：

1. 本周期费用。
2. 总 Token。
3. 输入 Token。
4. 输出 Token。
5. 调用次数。
6. 当前余额。

次级运行指标展示：

- 平均 RPM。
- 平均 TPM。
- 平均响应耗时。
- 流式请求比例。

其中：

```text
平均 RPM = 周期内请求数 / 周期分钟数
平均 TPM = 周期内总 Token / 周期分钟数
```

实时 RPM/TPM 与周期平均值必须明确区分。现有日志统计接口的 RPM/TPM 表示最近 60 秒数据，不应标记为本周期 RPM/TPM。

API Key 或模型筛选在前端作用于已经返回的 `items`，筛选后汇总卡片会基于可见明细重新计算请求数、Token、净费用、周期平均 RPM/TPM、平均响应耗时和流式请求比例。

### 5.4 正式账单明细表

明细默认按最终费用降序展示：

| 字段 | 说明 |
|---|---|
| API Key | Key 名称，不展示完整密钥 |
| 模型 | 对外请求使用的模型名称 |
| 请求数 | 周期内不含异步结算调整行的逻辑消费调用次数 |
| 输入 Token | 已实现；汇总结算日志中的 `prompt_tokens` |
| 输出 Token | 已实现；汇总结算日志中的 `completion_tokens` |
| 总 Token | 已实现；输入 Token + 输出 Token |
| 平均耗时 | 已实现；按逻辑消费请求加权汇总秒级 `use_time` |
| 最终费用 | 已实现；消费额度减退款额度并限制为非负值 |
| 费用占比 | 当前行费用 / 周期总费用 |
| 操作 | 查看调用明细 |

删除后的 API Key 仍会保留历史账单行：

```text
已删除的 API Key（ID）
```

不得因 API Key 被删除而丢失历史费用归属。

## 6. RTM 指标处理

本阶段已将需求中的 RTM 确认为“响应时间”语义，并统一落地为：

```text
平均响应耗时
```

平均响应耗时来自消费日志的秒级 `use_time`，精度边界见 4.5 节。

页面同时显示周期平均 RPM 和周期平均 TPM，它们是整个查询区间的平均值，不是实时指标。本阶段不展示最近 60 秒的实时 RPM/TPM。

系统现有毫秒级延迟、TTFT、成功率和 TPS 不包含用户或 API Key 维度，不能用于用户账单，否则会混入其他用户的调用数据。

## 7. 已实施的最小入侵结构

### 7.1 前端新增文件

账单前端独立放在：

```text
web/src/features/billing/
├── api.ts
├── types.ts
├── index.tsx
├── lib.ts
└── components/
    ├── billing-date-range-picker.tsx
    ├── billing-filters.tsx
    ├── billing-summary.tsx
    └── billing-statement-table.tsx
```

路由文件为：

```text
web/src/routes/_authenticated/billing/index.tsx
```

账单组件没有反向放入 Dashboard、Wallet 或 Usage Logs 目录，避免形成跨功能依赖。

### 7.2 数据接口

本次实现使用：

| 接口 | 用途 |
|---|---|
| `GET /api/billing/self` | API Key × 模型的 Token、调用、耗时、消费、退款和最终费用聚合 |
| `GET /api/log/self` | 单次调用明细 |

前端使用 React Query，并使用独立查询键：

```text
['billing-statement', start, end]
```

当前前端按周期获取完整 `items`，API Key 和模型筛选在本地完成；专用接口仍支持可选的 `token_id` 和 `model_name` 参数，供直接调用或后续服务端筛选使用。

### 7.3 现有文件最小接线

现有文件的接线限制为：

1. 在根侧栏增加 `/billing` 菜单项。
2. 在侧栏默认配置增加 `personal.billing`。
3. 在 URL 到侧栏配置映射中增加 `/billing`。
4. 在管理员侧栏设置中增加账单开关。
5. 在用户侧栏个性化设置中增加账单开关。
6. 在后端默认用户侧栏配置中增加 `billing: true`。
7. 增加多语言翻译键。

不修改：

- Dashboard 页面结构。
- Wallet 页面结构。
- Usage Logs 表格和详情结构。
- 计费预扣、结算和退款主链路。
- 数据库结构。

旧用户的 `sidebar_modules` 中没有 `billing` 时，通过现有默认配置合并机制自动视为可见，不需要数据迁移。

### 7.4 页面下钻

账单行的“查看调用明细”跳转到：

```text
/usage-logs/common
```

并携带：

```text
type=2,6
token=<API Key 名称>
model=<模型名称>
startTime=<开始时间毫秒>
endTime=<结束时间毫秒>
```

这样可以直接复用现有日志筛选、费用详情和动态计费展示。明细视图会同时携带 API Key 和模型；按模型汇总时不携带 API Key，按 API Key 汇总时不携带模型。删除后且名称为空的 API Key 无法通过名称筛选，仍会保留周期和模型等可用条件。

### 7.5 当前实现边界

- 输入、输出 Token、调用次数和平均耗时来自结算日志聚合，并遵循 4.2 节的异步任务口径。
- 周期费用使用消费额度减去退款额度后的非负最终费用。
- 消费和退款按日志发生时间归属周期，不做跨期冲销。
- 单次请求的订阅抵扣、钱包来源和完整计算过程仍在用量日志详情中查看。
- 日志生成受 `LogConsumeEnabled` 和日志保留策略影响。
- 页面不展示期初余额、期末余额或账务级记账流水。

## 8. 专用账单聚合接口

本次已新增：

```text
GET /api/billing/self
```

请求参数：

| 参数 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `start_timestamp` | int64 | 是 | 查询开始时间，Unix 秒 |
| `end_timestamp` | int64 | 是 | 查询结束时间，Unix 秒，范围最长 31 天 |
| `token_id` | int | 否 | 大于 0 的 API Key ID |
| `model_name` | string | 否 | 最长 255 个字符的模型名称 |

响应结构：

```json
{
  "period": {
    "start_timestamp": 0,
    "end_timestamp": 0
  },
  "funds": {
    "current_balance": 0,
    "lifetime_consumed": 0
  },
  "summary": {
    "requests": 0,
    "prompt_tokens": 0,
    "completion_tokens": 0,
    "total_tokens": 0,
    "gross_quota": 0,
    "refund_quota": 0,
    "net_quota": 0,
    "average_rpm": 0,
    "average_tpm": 0,
    "average_use_time_seconds": 0,
    "stream_ratio": 0
  },
  "items": [
    {
      "token_id": 1,
      "token_name": "production-key",
      "model_name": "example-model",
      "requests": 0,
      "prompt_tokens": 0,
      "completion_tokens": 0,
      "total_tokens": 0,
      "gross_quota": 0,
      "refund_quota": 0,
      "net_quota": 0,
      "average_use_time_seconds": 0,
      "stream_requests": 0,
      "latest_request_timestamp": 0
    }
  ],
  "generated_at": 0,
  "data_source": "settlement_logs"
}
```

`items` 字段合同：

| 字段 | 类型 | 说明 |
|---|---|---|
| `token_id` | int | API Key ID |
| `token_name` | string | 该 ID 在周期内最新非空日志名称；可能为空 |
| `model_name` | string | 对外请求使用的模型名称 |
| `requests` | int64 | 不含异步结算调整行的逻辑调用次数 |
| `prompt_tokens` | int64 | 输入 Token，包含消费与退款结算行中的记录值 |
| `completion_tokens` | int64 | 输出 Token，包含消费与退款结算行中的记录值 |
| `total_tokens` | int64 | `prompt_tokens + completion_tokens` |
| `gross_quota` | int64 | 消费类型日志的 quota 合计 |
| `refund_quota` | int64 | 退款类型日志的 quota 合计 |
| `net_quota` | int64 | `max(gross_quota - refund_quota, 0)` |
| `average_use_time_seconds` | float64 | 不含异步结算调整行的平均响应耗时，单位秒 |
| `stream_requests` | int64 | 不含异步结算调整行的流式请求数，用于计算流式比例 |
| `latest_request_timestamp` | int64 | 被选为 `token_name` 的最新非空名称日志时间，Unix 秒；如果没有非空名称则为 0 |

实现边界：

- Controller 放在新增文件 `controller/billing_statement.go`。
- Model 查询放在新增文件 `model/billing_statement.go`。
- 现有 Router 只增加一条窄路由。
- 使用认证上下文中的用户 ID，禁止接受任意 `user_id`。
- 使用跨数据库的 GORM 聚合写法，目标兼容 SQLite、MySQL 和 PostgreSQL。
- ClickHouse 的 `logs.other` 列为 `String`，当前聚合使用的 `COALESCE`、`CASE WHEN`、`NOT LIKE` 和 `GROUP BY` 从语法与列类型上具备兼容基础；是否完成实际运行验证以 12.1 节为准。
- 返回原始 quota，由前端按照当前站点币种显示配置进行格式化。
- `summary` 和 `items` 中的请求数、Token、quota 使用 64 位聚合类型。`funds.current_balance` 与 `funds.lifetime_consumed` 沿用用户模型中的 `int` 类型，并在返回前限制为非负值。

## 10. 权限与隐私

- 当前只实现登录用户自助查询，路由使用 `UserAuth()`，Controller 只读取认证上下文中的用户 ID。
- 普通用户只能查询自己的账单。
- API 不接受前端传入的任意用户 ID。
- 页面只显示 API Key 名称和 ID，不显示完整密钥。
- 已删除 API Key 继续保留历史名称或使用 ID 回退文案。
- 当前没有管理员代查账单接口。管理员如果需要查看其他用户账单，应另行设计管理员接口和权限，不复用普通用户接口中的查询参数。
- 账单下钻到用量日志后继续沿用现有的用户字段脱敏规则。
