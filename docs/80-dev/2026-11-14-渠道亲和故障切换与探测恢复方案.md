# 渠道亲和故障切换与探测恢复方案

## 问题与目标

Claude 请求命中严格会话规则后，渠道 #20 返回 502，网关结束了本次请求。绑定没有被清除，同会话的后续请求在
有效期内继续命中 #20。默认一小时是绑定有效期，连续失败本身不会触发换渠。

**最终目标：正常时同一会话留在同一渠道以保持上游提示词缓存；渠道出问题时，网关能判断它当前不可用，
自动切到另一个合规渠道。** 这是对 NewAPI 现有渠道亲和（请求策略 → 会话与重试）的扩展，不新建平行的路由
或配置体系。

**探测负责判断渠道在特定协议和模型上是否可用，路由负责取舍候选，渠道启停仍由现有渠道管理流程负责。**

实施分为 A 故障切换、B 三级亲和、C 运营管理。各阶段的交付边界、验收和回滚见第 8 节。

## 1. 当前实际情况

- 截图显示已开启会话保持，全局为「优先原渠道，失败允许切换」，两条 CLI 规则单独为「必须使用原渠道」。
  默认有效期 3600 秒，缓存容量 100,000，切换成功后更新绑定开启，渠道不可用时保留绑定关闭。最多重试 5 次，
  自动重试状态码包含 502。截图记录的是页面显示的配置。
  [请求策略 → 会话与重试](https://tokenai.page/system-settings/request-policies/routing)
- 两条内建 CLI 规则在代码默认值中就是严格模式（`SkipRetryOnFailure: true`）。严格规则先于重试预算生效。
  [内建规则](../../setting/operation_setting/channel_affinity_setting.go) · [重试决策](../../service/relay_error.go)
- 默认 API Key 亲和是另一层已实现的选渠偏好，只覆盖三个文本入口里的自包含请求；显式规则一旦命中就跳过它。
  仓库文档记录为生产未发布。 [默认亲和](../../service/default_channel_affinity.go) ·
  [渠道亲和架构](../20-architecture/渠道亲和架构.md)
- 重试序号同时被当作优先级档位下标：第 n 次重试取过滤后的第 n 档，超出时固定在最低档。过滤发生在计算档位
  之前，因此不会出现空档，但会跳过同档内仍可用的备用。重试不排除已失败的渠道。
  [内存选渠](../../model/channel_cache.go) · [数据库选渠](../../model/ability.go) · [重试循环](../../controller/relay.go)
- 显式会话绑定在 distributor 中按 HTTP 状态 `< 400` 写入；默认 API Key 亲和才检查流式完整终态。
  [显式写入点](../../middleware/distributor.go) · [默认写入点](../../service/default_channel_affinity.go)
- 现有渠道告警按批次异步汇总上游结果，适合告警，不适合作为同步路由判断；它的观测钩子可以复用。
  [上游响应观测](../../service/channel_alert_observe.go)
- 现有探测能区分配置检查、只读连通与真实生成，但健康检查流程在相应设置下会执行禁用或启用；本方案只复用
  其执行能力和结构化结果。 [健康检查流程](../../controller/channel-test.go) ·
  [只读连接探测](../../controller/channel_connection_probe.go)

## 2. 实验结论（2026-11-14 本地执行）

### 2.1 网关行为实验

用现有 controller 测试夹具驱动真实的 `TokenAuth → Distribute → Relay(Claude)` 链路，上游为本地 mock，
`claude-sonnet-4-6`，重试次数 5。实验代码为一次性测试文件，执行后已删除，未提交。

| 编号 | 场景 | 观察结果 | 对方案的含义 |
| --- | --- | --- | --- |
| E1 | 严格规则，绑定渠道 A 开始返回 502 | 连续 3 次请求都只打 A，`stop/strict_session`，客户端收到 502；把 A 降到低于 B 的优先级后仍打 A | 复现事故：严格绑定在有效期内不会自行脱离故障渠道 |
| E2 | 优先原渠道，同档 {A 502, B 正常}，无亲和 | 首次落到 A 的 19 个请求中，12 个重试时**再次选中 A**；1 个请求 6 次尝试全部落在 A，客户端失败 | 重试必须排除本请求已失败的渠道 |
| E3 | 高档 {A, B}、低档 {C}，会话绑定 A，A 返回 502 | 第 1 次重试直接选 C，**跳过同档健康的 B**；成功后会话改绑到 C，后续请求都走 C | 补试应先在原档剩余候选中选；跨档改绑需要单独规则 |
| E4 | 显式会话，A 的流式响应输出 200 后未发 `message_stop` 就断开 | 客户端收到 200 和截断内容；策略记录为 `success/request_completed`；会话仍绑定到 A，A 降级后下一次请求继续走 A | 显式绑定写入必须以可信完整终态为准 |
| E5 | 优先原渠道，A 分别返回各类错误，B 正常 | 502、503、529、429、401 和连接失败都会补试到 B；504 为 `system_retry_exclusion` 不补试；连接失败被标为 `transport` 来源，可可靠识别 | 单次补试口径不变；渠道持续故障的计数口径需要单独收窄 |

### 2.2 Claude thinking 签名跨渠道迁移实验

目的：确认带 `thinking` 签名的历史能否交给另一个渠道继续，从而决定这类请求是否必须锁定原渠道。

方法：脚本直接调用本地开发库中的渠道上游（密钥只在进程内使用，不输出、不落盘）。源渠道开启 thinking 并强制
工具调用，得到「thinking + tool_use」助手轮；再把这一轮原样连同 `tool_result` 发给目标渠道，并开启 thinking。
同时在每个目标上做对照：签名末 8 位被篡改、删除 thinking 块但保持 thinking 开启、删除 thinking 块并关闭 thinking。

样本：#86 京东云、#47 Funcloud（Bedrock 映射）、#231 云枢 AWS、#237 红杏 CCMAX、#138 MixAI CCMAX；
`claude-sonnet-4-6`（budget thinking，执行两轮）和 `claude-opus-4-8`（adaptive thinking）。#59 Azure Foundry
因上游拒绝访问、#227 因 403 未能产生源样本。

| 结果 | 说明 |
| --- | --- |
| 75 次尝试中有 70 次收到 HTTP 200 | Sonnet 两轮各 25 次，Opus 一轮 25 次。5 次因 TLS 中断或握手超时未收到上游 HTTP 响应。Sonnet 的 2 个组合在另一轮返回 200。Opus 的 3 个组合（#47→#231、#86→#138、#231→#138）未复验 |
| #231 在对照中拒绝篡改签名 | #231 返回 Bedrock `ValidationException`，同时接受了 #86、#47、#237、#138 产生的签名。其他目标接受了篡改签名。HTTP 200 只能证明请求被接受，上游是否原样保留并使用了推理历史仍需验证 |
| 删除 thinking 块的请求在两个模型上都被接受 | 但删除会丢失推理上下文，属于改写客户请求，本方案不采用 |

结论与限制：

- 样本用于筛选值得复验的组合。放行范围按**源渠道 → 目标渠道、具体模型、内容类型和适配方式**登记。须验证历史原样传递且目标完成预期续接，单次 HTTP 200 不足以放行。未复验组合、`redacted_thinking` 和其他未验证入口继续走原渠道。影响兼容性的配置变化后重新验证。
- OpenAI Responses 的 `encrypted_content`、`previous_response_id`、Codex turn-state 未做实验，继续按依赖原上游
  状态处理。

## 3. 核心原则

1. **查绑定与换渠道分开。** WebSocket 和已有任务遵循各自的原渠道约束。原生 HTTP 续接有可信归属且原渠道在灰度范围内时，固定原渠道。原渠道失去选渠资格时返回 `upstream_continuation_unavailable`。归属不明或归属渠道在灰度外的请求沿用原有路由和重试，跳过 A 的绕开、补试和试用。普通会话缓存不能当作归属凭据。
2. **单次补试与持续故障分开计数。** 「会话与重试」继续决定这一单能否再试一次。持续故障判断只使用其中能代表
   渠道服务不可用的那部分，不另维护一份状态码列表。
3. **可迁移以实际请求和目标渠道的验证结果为准。** 已验证可携带的内联历史可参与切换。依赖原上游保存的状态、已建立连接和已有任务固定原渠道。
4. **存量严格规则保留原语义。** 代码默认值不变，故障例外按规则显式开启，降低与上游默认配置的冲突面。
5. **最小入侵。** 故障判断、候选排除和改绑逻辑放在新增服务文件，原生文件只加必要接线（第 7 节）。

## 4. 故障判断、排除与恢复

### 4.1 持续故障计数

| 计入 | 不计入 |
| --- | --- |
| 适配器拿到的真实上游 HTTP 502、503、529，且该码在现有「自动重试状态码」设置内 | 401–404、429 可按现有设置参与单次补试，不能作为整渠故障样本。401 仍由现有自动禁用流程处理 |
| `transport` 来源的连接失败（E5 已证明可识别） | 504、524：现有重试硬排除项，上游可能已执行 |
| | 网关本地生成或映射出的 5xx、客户端取消、探测执行器自身错误 |
| | 流式 200 后中断：先不计入持续故障，但必须阻止绑定写入（E4）；后续能区分上游中断与客户端断开后再评估 |

HTTP 故障计数取已配置可重试状态码与上述上游故障证据的交集。从重试列表移除 502 后停止新增 502 样本，按新口径重算尚未确认的连续计数。已判定的短期故障仍走复查和恢复流程，手工绕开按自己的有效期管理。探测有独立证据记录，连接失败按上表计数。

建议起始阈值为 **60 秒内同一渠道、配置版本、客户模型和协议操作连续 3 次**。可归因的非故障上游结果中断连续计数。首批在单 Key 渠道灰度。多 Key 渠道须能在实际选用 Key 时跳过故障槽位，所有合规可用槽位均有故障证据时才排除整条渠道。在证明这两个行为前，多 Key 渠道只观察。

### 4.2 状态与恢复

| 状态 | 进入条件 | 路由行为 |
| --- | --- | --- |
| 正常 | 未达阈值，或恢复验证通过 | 正常使用绑定 |
| 暂时不可用 | 达到阈值 | 对可迁移的新请求排除该范围；不可迁移请求仍走原渠道（第 5 节） |
| 冷却到期待复查 | 冷却时间到（建议 60 秒起，失败后递增） | 优先复用同协议、同模型的探测；配置检查或连通检查只能显示为「恢复待确认」 |
| 受控试用 | 同类探测可信成功，或缺少安全探测时由值班人员在冷却期后发起复查 | 同一故障范围只允许一条有合规备用、可安全补试且有剩余预算的可迁移请求试用。完整成功则恢复新会话选渠。失败则重新冷却，符合补试条件时转备用 |

同一范围只有一个复查或试用名额在途，多实例通过共享缓存竞争名额。共享状态读取设统一耗时上限（沿用默认亲和
10ms 的做法）并配短期本地缓存；读取失败时状态记为「未知」，不阻塞请求，仍保留手工绕开和本请求内已确认的失败
排除。没有安全试用机会时保持待确认，由值班人员复查。有效渠道配置变化后旧状态失效。管理员手动禁用的渠道即使探测成功也不路由，启停仍由现有流程负责。

### 4.3 单次请求内的补试

- 排除本请求已失败的渠道（E2）。
- 从失败尝试所在的档位继续选剩余候选，同档用完再降档；只有选不到可用渠道的空档不消耗重试次数（E3）。
  需要与 `auto` 分组跨组重试使用的分组下标、起始重试序号一起设计，避免两套计数互相干扰。
  [跨组重试](../../service/channel_select.go)
- 没有合规备用时保留原错误结束；首次选渠就没有候选的新请求返回 503。
- 已打开的流或已发送的响应不重放。

## 5. 可迁移请求

| 请求 | 原渠道不可用时 |
| --- | --- |
| A 阶段：Claude Messages、Chat Completions、Responses HTTP 中只含已验证可迁移内容的同步请求 | 按规则绕开或补试。文本和自包含函数工具历史先验证。内联图片、文档及 `thinking` 按实际内容、模型和目标能力逐项验证后放行 |
| 带 `previous_response_id`、上游文件、容器、会话 ID、`encrypted_content` 等原上游状态 | 可信归属在灰度内时固定原渠道，失败时返回原错误；其余按第 3 节沿用原有路由和重试 |
| 异步创建、已有任务和派生操作 | 不进入本方案，沿用现有异步创建安全规则；结果未知时不得换渠重发 |
| 管理员指定渠道、无法判断是否可迁移的请求 | 按原路由约束处理 |

现有自包含判定（[请求判定](../../service/default_channel_affinity_request.go)）继续只决定默认 API Key 亲和的
适用范围。故障迁移使用第 2.2 节的验证范围，并按实际源与目标对判断。首次选渠仍先检查已有会话绑定。
目标渠道以签名或状态校验错误拒绝迁移请求时，本次不再继续换渠，不改绑，并记录证据，供收紧白名单使用。

**严格规则的故障例外**默认关闭。按截图配置灰度时，为 `claude cli trace` 显式开启。适用行为分为两种：

- **首次选渠绕开。** 原绑定处于绕开状态时，先在现有授权候选内确认合规备用。备用处于冷却、待确认、待试用或手工绕开时退出备用候选。没有合规备用时仍向具备选渠资格的原绑定发起本次首个尝试。有合规备用时直接选备用，预算为 0 也可执行。
- **当次补试。** 严格规则仅在原渠道已判不可用时允许补试。触发阈值的这一单，还须满足尚未输出、错误属于现有可重试范围、还有预算且有合规备用，才补试一次。预算为 0 则返回本次错误。优先模式按现有设置逐单补试，可在达到持续故障阈值前跳过本次已失败的渠道。

**不可迁移会话**继续走具备选渠资格的原渠道，失败时返回原错误。原渠道已停用或已失去授权时直接返回明确错误。
HTTP 续接是否具备可信原渠道归属须在灰度前核实。A 使用已有的可信记录。缺少归属的续接请求不得进入自动选备用路径。

## 6. 绑定写入与回切

- A 仅接管三个目标入口的原生 HTTP 写入。Claude 须收到 `message_stop`，Responses 须有可信完成事件，Chat 须确认全部预期输出结束。非流式须确认请求完整成功。A 已接管时阻止 distributor 再按 HTTP 状态写入。其他入口继续使用原有写入路径。
  [Relay 结果记录点](../../controller/relay.go)
- 「切换成功后更新会话绑定」开启时，备用完整成功后才改绑并刷新有效期。并发改绑须比较读到的原绑定，迟到的
  旧结果不能覆盖已迁移的绑定。关闭时故障期间仍可绕开，但保留原绑定。
- 允许跨优先级改绑，前提是同档已无可用候选（第 4.3 节）。E3 中会话被改绑到低档后会一直停留在低档，因此原渠道
  恢复后只重新参与**新会话**选渠；已迁移会话在有效期内继续使用健康的备用，避免整批会话同时回切。
- 渠道正式停用或失去选渠资格时，沿用现有「渠道不可用时保留会话绑定」设置；临时不可用期间保留原绑定作为恢复依据。

渠道亲和设置结构末尾，前端改动限定在请求策略页面的现有分区。

## 8. 分阶段实施

| 阶段 | 范围 | 验收要点 |
| --- | --- | --- |
| **A 故障切换** | Claude Messages、Chat Completions、Responses HTTP。沿用现有规则和绑定缓存，交付故障绕开、补试、改绑和基本恢复 | 把 E1—E5 转为第 8.2 节的回归用例，分别验证启用和关闭时的预期 |
| **B 三级亲和** | 「会话 → API Key → 用户」、三级缓存与逐协议覆盖。用户层只在前两层未命中时借用，仍受权限、候选优先级和容量约束 | 会话缺失能读 Key，Key 缺失能读用户。覆盖权限隔离、按层写入与清理、过期、跨节点，以及多 Key 负载集中与 429 |
| **C 运营展示与自动化** | 渠道健康页显示当前判断、故障证据和下次复查。渠道管理提供立即复查和限时绕开。请求日志展示原渠道、跳过原因、备用和是否改绑。会话规则表展示系统默认规则、用户创建的规则和兜底层缓存 | 能区分「路由临时绕开」与「渠道已禁用」。读不到统计时显示「暂不可用」。管理页只显示汇总和脱敏信息。规则删除和缓存清理分别验收 |

### 8.1 A 如何使用现有设置

| 截图中的设置 | A 阶段生效方式 |
| --- | --- |
| 会话保持开启，全局优先原渠道，两条 CLI 规则单独严格 | 保持现有继承关系。只观察时记录将采取的动作。启用切换后，严格规则仍须单独开启故障例外。依赖原上游状态的请求、已有连接和已有任务继续固定原渠道 |
| 最多重试 5 次，自动重试状态码包含 502 | 5 次是现有单次请求按分组计算的预算。A 新增的故障补试最多用其中一次。达到持续故障阈值后，下一单首次绕开不占预算。去掉 502 时，后续 502 不触发当次故障补试，也不进入新的持续故障计数 |
| 切换成功后更新会话绑定开启，默认有效期 3600 秒 | 备用完整成功后改绑并刷新有效期。关闭改绑仍可绕开，旧绑定可在原渠道恢复后继续用 |
| 渠道不可用时保留会话绑定关闭 | 继续用于渠道正式停用或失去选渠资格。探测判定的临时故障保留原绑定，直至正常过期、被清理或备用成功改绑 |
| 渠道健康、自动启停 | 复用同协议同模型的探测能力。探测只更新可用性证据，渠道启停仍由现有管理流程决定 |

A 增加整体开关，支持关闭、只观察和指定范围启用。规则级故障例外只决定严格会话是否参与，整体开关同时约束优先模式和严格模式。A 上线前须通过现有日志和管理入口提供基本故障证据、立即复查、受控恢复和总开关，便于值班人员处理，无需等待 C 的完整页面。

### 8.2 A 如何验收和回滚

| 验收场景 | 预期 |
| --- | --- |
| 严格规则、真实 502、存在同档备用 | 例外关闭时保持原行为。开启后，前两次未达阈值仍不补试，第 3 次达到阈值且尚未输出、预算允许时补试一次。预算为 0 时当前失败，下一单直接绕开 |
| 优先模式、同档与低档都有备用 | 本次失败渠道退出候选，先用同档。空档不占预算，必要时再降档。普通分发、客户合同、数据库和内存选渠均验证。无合规备用保留原失败 |
| 状态引用、流已输出、异步任务 | 可信归属在灰度内时固定原渠道，失去资格返回 `upstream_continuation_unavailable`。归属不明或归属渠道在灰度外时沿用原有路由和重试，跳过 A 的绕开、补试和试用。流已输出不重放，已有任务不迁移。其他入口的既有亲和写入继续生效 |
| 首次选渠、唯一备用不合规 | 备用在冷却或迁移登记失效时仍尝试合规原绑定。原渠道当次失败且无合规备用时返回原错误。备用恢复合规后可绕开并在完整成功后改绑 |
| 成功、截断和并发 | 备用完整成功才按设置改绑，关闭改绑时保留旧绑定。流式截断、备用失败及迁移校验失败不写入。旧请求迟到不能把绑定写回原渠道 |
| 健康和恢复 | 502/503/529 按配置计入，401/429 和映射错误不使整渠进入故障。冷却到期后验证探测范围、试用名额唯一、无预算时保持待确认、失败重新冷却。恢复后已迁移会话继续使用合规备用 |
| 缓存异常、手动停用和回滚 | 共享缓存异常时仍按权限选渠并排除本次确认失败的渠道。手动停用优先。关闭 A 后，两个会话模式均回到原有选渠和重试路径 |

先做只观察灰度。以灰度范围内全部 Claude CLI 请求为分母，统计「可迁移且存在合规备用」的比例，同时按模型、内容和渠道对记录挡住的原因。启用前由产品与值班负责人记录观察窗口、最低样本量、最低可切换比例，以及可接受的失败率和首响应延迟变化。达到约定标准后才开启指定规则。扩大 `thinking` 范围前，须复验对应源、目标和模型的原样转发与续接，HTTP 200 单独记录。

发现跨授权选渠、原状态请求迁移、已输出后重放或流式截断导致改绑时，立即关闭 A。失败率或首响应延迟超过灰度约定时同样暂停。关闭后停止新增健康绕开、故障补试、试用和 A 的改绑写入，恢复原有写入路径。已成功写入且仍合规的绑定可自然过期，如需重新选渠，由值班人员按规则清理受影响缓存。核对两种会话模式恢复原行为、渠道启停未被回滚操作改动，再恢复观察。

### 8.3 B 和 C 的交付边界

B 交付逐协议默认亲和、「会话 → API Key → 用户」及三级绑定缓存。先处理可信的原渠道归属，再对可自由选渠的新请求逐级查找。已知归属的连接、请求和任务使用原渠道。首次选渠的亲和资格和故障时的迁移资格分别判断。表中的专用选渠按原合同处理。

| 层级 | 读取和写入 |
| --- | --- |
| 会话 | 有会话标识先查，会话尚未建立或允许绕开时查下一层。借用下层渠道并完整成功后可建立自己的绑定。会话改绑只更新该会话 |
| API Key | 使用当前已认证 Key。无合规绑定时查用户。没有会话身份时，按成功结果建立或更新当前 Key 的绑定 |
| 用户 | 只在前两层没有合规绑定时使用。同一用户也须校验协议、模型、授权分组和合同。用户是最具体的可用身份时才改写已有用户绑定。下层空位可用合规成功补建 |

B 沿用现有缓存配置，规则可覆盖默认有效期。Redis 部署共享绑定，无 Redis 时使用有限的本地缓存。正常过期、清理和未命中按层继续查找。共享缓存读失败时按已有路由约束安全选渠，当次避开不确定的绑定写回。清理亲和缓存后，渠道健康判断及原渠道归属仍有效。用户层验收覆盖多 Key 的负载集中与 429，上游提示词缓存命中按 Provider 用量单独观察。

C 交付后台完整展示与运营操作，复用 A 的故障判断、复查和恢复能力，以及 B 的三级缓存。页面按规则和层级显示生效模式、有效期、条数、刷新时间与共享或本地范围。统计不可用时显示「暂不可用」。清理规则缓存、按层清理与删除规则是独立操作。默认规则缓存为 0 也展示，保护同时覆盖可视化入口、JSON 编辑和服务端保存。

C 阶段的会话规则管理按以下方式验收：

| 规则来源 | 删除规则 | 清理该规则的缓存 |
| --- | --- | --- |
| 系统默认规则 | 不允许。可视化编辑和 JSON 保存都由服务端校验保护 | 允许。清理后规则仍显示，缓存条数为 0 时也展示 |
| 用户创建的规则 | 允许，由有规则管理权限的管理员操作 | 允许。清理后规则继续生效，后续请求可重新建立绑定 |

## 9. 事故处理

1. **出故障时**，先从 A 的请求日志和管理入口核实上游错误、影响范围、绕开和复查结果。C 交付后也可在渠道健康页查看。无备用时核对协议、模型、分组和合同限制，再补齐合规备用。
2. **需要人工接管时**，使用 A 的管理入口立即复查，可关闭规则故障例外或按第 8.2 节关闭整个 A。C 交付后可在渠道管理页设置有时限、有原因的「暂时绕开」。确需批量重选时使用现有按规则清理缓存。
3. **渠道恢复时**，先看同协议、同模型探测，再看受控试用结果；观察恢复后的重复故障、备用成功率和首响应延迟。

## 12. 国内模型真实渠道复验（2026-11-14）

一次性 SQLite 网关经 `TokenAuth → Distribute → Relay` 发起请求，渠道连接信息只读载入自开发 PostgreSQL。
模型 `glm-5.3-flash`：A 为 #94（墨行，经本地转发层，可注入 502），B 为 #256（电信），两者同档；C 为 #94 的
低档副本。所有渠道均经计数转发层访问真实上游，测试只输出渠道命中、状态码和绑定。

| 场景 | 实测 |
| --- | --- |
| 优先模式，绑定 A 返回 502（Chat 非流式） | 同一请求 A 502 → 同档 B 200，未访问低档 C；绑定改为 B，后续请求只走 B |
| 严格会话 + 故障例外（Chat 流式） | 前两次只打 A 并返回 502；第三次达到阈值后同一请求补试 B 成功并改绑；后续直接走 B |
| 严格会话，重试预算 0（Claude Messages → OpenAI 渠道，流式） | 三次均只打 A 返回 502；第四次首次选渠直接绕开到 B 成功 |
| 未登记内容（含合同外字段），A 返回 502 | 沿用原有重试，最终在其他渠道 200（修复前首次 502 即停止） |
| Chat 带 `session_id`，无已记录归属 | 原有路由 200（修复前返回 409） |

| 仅观察模式 | 绑定 A 的请求仍走 A，不改路由 |

### 推荐配置

| 阶段 | 设置 |
| --- | --- |
| 会话默认 | 保持当前：启用会话保持、全局优先原渠道、切换成功后更新绑定、渠道不可用时不保留绑定、默认有效期 3600 秒 |
