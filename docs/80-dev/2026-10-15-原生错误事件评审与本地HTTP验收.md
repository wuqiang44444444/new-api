### 严重问题：重试选渠失败沿用上一轮渠道（已修复）

- 编号与类型：S1 / P2，诊断事实来源错误；置信度高。
- 位置：`service/relay_error_diagnostics.go:29`、`clienterrlog/recorder.go:104`。
- 证据：模拟 Azure 首次返回 429 前，通过真实管理 API 停用两条候选渠道。重试无法选渠，
  客户得到 500，但原补丁仍从 Gin 读取上一轮渠道，记为 `relay/local_error`。
  关闭与开启内存缓存均复现；新增回归在修复前分别证实渠道应为 0 却为 149、原因分类不符。
- 影响：将最终的本地选渠失败归到已发生的上游尝试，误导按渠道统计和错误归因。
- 唯一权威事实：最终失败为 `get_channel_failed`；没有新的选定渠道。前次真实调用仍由
  `logs` 的尝试记录描述，不能代替最终错误的渠道事实。
- 最小修改：最终诊断将该错误记为 `channel_selection/channel_unavailable`，渠道为 0；
  记录器对渠道选择阶段的空渠道不再读取旧 Gin 渠道。没有清空业务上下文或修改分发器。
- 验证：新增缺失身份回填、最终诊断和真实 Relay 回归，并在两个实际服务实例上复验通过。

## 本地实际 HTTP 验收

### 环境与方法

- 2026-10-15，在本地从当前工作区执行 `go build`，运行独立二进制和完整应用 Router、正式鉴权、
  原生 Relay、退款与结算、异步错误记录器及管理接口。不是只调用测试函数或替换 Controller。
- 二进制 SHA-256：`afc1a11130a2d4434dd3a781f65ec4c7d9183e78ad123e95318b98ba80279755`。
- 两个独立实例分别关闭、开启内存缓存；使用随机空闲端口、全新 SQLite、独立运行目录和显式
  环境白名单，不读取仓库 `.env`，不连接用户既有服务或生产数据库。
- Root 初始化、登录、应用 Key、渠道、价格、重试、状态映射和入口限流通过真实管理 API 配置。
  只有不可见任务的隔离测试数据直接写入一次性数据库，不通过跨租户查询获取任务归属。
- Provider 使用本地 HTTP 模拟 Azure，返回确定的 429、成功结果或主动断连。仅使用合成图片
  请求与合成凭据，没有真实 Azure 调用。图片价格为每次 0.04，验证真实预扣、退款及结算路径。
- 按实际响应的请求 ID 查询 SQLite 和 `/api/error_log/`；核对持久化记录与管理展示一致，
  读取到最终渠道名称，并核对快照正文确实来自第二个模拟 Provider。

### 结果：32 个场景全部通过

每个缓存模式各执行下列 16 个场景，共 32 个，全部通过。

| 场景 | 每种模式数量 | 实际结果 |
| --- | ---: | --- |
| 图片编辑、生成均连续收到两个 429 | 2 | 两条尝试日志、一条最终事件；渠道、上游 ID 与正文均属于第二次尝试 |
| 上游 429 映射客户端 503 | 1 | 客户仍为 503，诊断保留真实上游 429 及限流分类 |
| 客户模型别名映射 | 1 | 南向发送 `gpt-image-2`，错误事件保留客户名 `review-image` |
| 第一次 429、第二次成功 | 1 | HTTP 200，无最终 API 错误；恰好一条正金额消费日志 |
| 第一次 429、第二次断连 | 1 | 连接失败分类正确；前次上游 ID 和响应快照不残留 |
| 第一次 429、第二次发送前校验失败 | 1 | 渠道覆盖将图片数量改成 129，HTTP 400；第二个 Provider 未收到请求 |
| 模型权限拒绝 | 1 | HTTP 403、空渠道、零上游调用，不误分类为上游限流 |
| 任务不存在、其他应用、其他用户、错误协议、已删除、DELETE 不存在 | 6 | 统一 404 和 `task_lookup/task_not_found`；无模型、渠道或上游调用 |
| 首次 429 后候选全部停用 | 1 | HTTP 500、`channel_selection/channel_unavailable`、空渠道，只有一次上游调用 |
| 网关入口限流 | 1 | HTTP 429、空渠道、零上游调用，不误分类为上游限流 |

所有图片失败场景均核对用户余额、调用 Key 剩余额度和累计消费以及渠道消费不变，且无消费扣费
日志；成功重试核对用户及 Key 扣款均与唯一消费日志一致，Key 累计消费只增加一次。

入口限流与旧原生模型权限拒绝仍可能保留既有 `unclassified` 分类，本补丁未宣称完成所有错误路径
的分类治理；已验证这些记录保持空渠道，并且不会被标记为 `upstream_rate_limited`。
