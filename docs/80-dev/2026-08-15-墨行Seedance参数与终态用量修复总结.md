# 墨行 Seedance 参数与终态用量修复总结

## 1. 问题与目标

本次修复处理墨行国内 Seedance 接入中的两个独立问题：

1. 北向 ModelArk V3 统一请求允许表达 `seed` 和 `camera_fixed`，但墨行各 Provider
   模型的实际支持范围不同。原适配会把字段继续发给上游，导致 Seedance 2.0 返回
   `media_task_failed / param_not_exist_is_this_api`。
2. 墨行 Fast 成功终态响应已返回真实 Token `usage`，但共享响应归一层受
   `IncludeVerifiedUsage=false` 控制而丢弃了该事实，使按 Token 计价的任务无法用实际
   completion tokens 结算。

目标是保留统一北向结构，在模型映射后按墨行文档明确校验南向能力；同时无条件
采集成功终态中可解析的用量事实，再由任务创建时冻结的计价单位决定如何结算。

## 2. 当前实际情况

### 2.1 已验证的 Provider 事实

- Seedance 2.0 失败请求显式带有 `seed: 24`，墨行拒绝该参数。
- 墨行四份当前接口文档显示：2.0、Fast 和 Mini 不支持 `seed`，2.5 支持 `seed`；
  四个模型都不支持 `camera_fixed`。
- Fast 的一次成功终态查询返回 `completion_tokens=40594`、`prompt_tokens=0` 和
  `total_tokens=40594`。墨行账单记录同样的 40,594 输出 Token，按¥37/百万 Token 计算为
  ¥1.501978，响应用量、上游账单和单价一致。

上述是修复的输入证据，不等于代码修复后已完成生产灰度。Fast、Mini 和 2.5 仍保持
“可配置但未发布”的边界。

### 2.2 参数合同的当前行为

北向 DTO 继续允许可选的 `seed` 和 `camera_fixed`，不为墨行收窄公共合同。模型映射得到
精确 Provider 模型后，逐模型 validator 在估价、资金 hold 和 Provider I/O 之前校验。该校验的
权威键是「协议 + Provider 模型」，下表仅覆盖墨行协议（`MoxingMediaTaskV1` /
`MoxingModelArkV1`）；TokenSave 官方协议使用同名 `doubao-seedance-2-0-260128` 时不做
该拒绝：

| 墨行协议下的 Provider 模型 | `seed` | `camera_fixed` |
| --- | --- | --- |
| `doubao-seedance-2-0-260128` | 拒绝 | 拒绝 |
| `doubao-seedance-2-0-fast-260128` | 拒绝 | 拒绝 |
| `doubao-seedance-2-0-mini-260615` | 拒绝 | 拒绝 |
| `doubao-seedance-2-5-260628` | 允许 | 拒绝 |

显式零值同样表示客户提供了字段，因此不支持的 `seed=0` 或 `camera_fixed=false` 也会返回
HTTP 400 `invalid_video_parameter`，不会静默丢弃或继续上送。

### 2.3 终态用量与计费的当前行为

- `IncludeVerifiedUsage` 及其上下文类型已从全局删除，没有替换为 Provider 开关、模型白名单
  或管理员配置。
- 只在成功终态采集用量。原始响应的任意层级出现明确 `usage` 数值或 Token 相关数值时，
  在通过非负、整数和 `int32` 上界校验后归一为合法用量。对象形态直接解析，`usage`
  中的 JSON 字符串只解码一层。
- 归一优先级为：明确 completion/output/generated Token；`total - prompt/input`；无 prompt
  字段时的单独 total。只有这三种语义可验证的形成能构成按 Token 结算的 completion；单独
  prompt/input、`total < prompt` 的不一致响应、`*_details` 内数值（如 `reasoning_tokens`、
  `cached_tokens`）和其它明确数值 usage 只作为用量证据与字段来源持久化，不冒充 completion
  触发结算或“明确零用量”。多个字段不累加。
- 用量存在性与数值分开传递和持久化，因此能区分“上游未返回 usage”与“上游明确返回
  0 Token”；计费用量的形成字段（`usage_source`）与全部采集证据（`usage_evidence`，
  字段路径到数值）一并写入 Task 私有计费快照，满足账单审计对字段来源的要求。这两个内部字段
  在写入公开 `task.Data` 前删除，只存在于私有快照，客户任务响应不暴露字段来源与证据明细。
  这些字段保存在现有 Task 私有 JSON 快照中，没有新增数据库列或迁移。
- 创建时冻结的计价方式是结算权威：墨行 2.0 仍按输出秒计费，即使返回 Token 也只保存用量
  事实；Fast、Mini 和 2.5 按实际 completion tokens 对预扣做幂等差额结算。
- 按 Token 计费时，终态没有用量会保留预扣；明确返回 0 Token 则按实际零用量结算，
  不再被误判为缺少 usage。

## 3. 优化方案

### 3.1 实施内容

本次按最小入侵原则把主体逻辑放在 Seedance Link 专属新文件中：

| 范围 | 实施位置 | 作用 |
| --- | --- | --- |
| Provider 逐模型能力 | `relay/channel/task/seedance/provider_model_specs.go` | 维护参数、时长、分辨率和素材数量边界 |
| 映射后校验 | `relay/channel/task/seedance/provider_mapped_validation.go` | 在计费和 Provider I/O 前明确拒绝不支持字段 |
| 终态用量归一 | `relay/channel/task/seedance/thirdparty/usage.go` | 无配置开关地扫描归一合法用量，区分可计费形成与仅证据字段并输出字段来源 |

必要的现有热路径改动仅用于接线：请求 adapter 调用映射后校验；第三方终态响应调用用量
归一；`TaskInfo` 传递“字段是否真实出现”；异步计费私有快照和结算 service 使用该事实。
未修改 NEWAPI 原生公共 Router 和北向 DTO，未增加隐式开关、兼容分支或数据库迁移。
