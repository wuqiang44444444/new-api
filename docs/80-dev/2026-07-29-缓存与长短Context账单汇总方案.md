# 缓存与长短 Context 账单汇总方案

## 目标

在现有用户账单之外增加一份只读的使用构成汇总，展示：

- 缓存读取命中、缓存写入及相关 token；
- 按模型阈值划分的长、短 Context 请求与已结算额度；
- 使用 tiered expression 的请求与已结算额度。

新增展示只解释现有结算日志，不重新计算价格，不改变扣费、退款、预扣费、结算或日志写入。

## 边界

- 新增独立接口 `/api/billing/self/breakdown`，原 `/api/billing/self` 继续作为正式账单和金额口径。
- 只读取 `Log` 既有字段和 `Other` JSON，不增加表、列或迁移。
- 汇总金额直接采用消费日志中的 `quota`，仅表示该类请求的已结算总额，不宣称是缓存或 Context 单项价格。
- 异步任务的 `task_id` 调整日志不作为新请求重复计数。
- Anthropic 核心计费差异仅记录现状，不修改 NEWAPI 核心计费；等待上游修复。
- 阈值使用内存配置 `billing_statement_setting.context_thresholds`，按模型名精确匹配。
- 模型没有阈值时不返回 Context 分类，前端保持空白，不显示 `unknown`。

## 归一化规则

### 缓存

- 读取 token：`cache_tokens`。
- 写入 token：优先 `cache_write_tokens`；缺失时取
  `max(cache_creation_tokens, cache_creation_tokens_5m + cache_creation_tokens_1h)`。
- `cache_tokens > 0` 计为一次缓存命中请求。

### 长短 Context

- 优先使用 `input_tokens_total`。
- Anthropic 语义日志使用
  `prompt_tokens + cache_tokens + cache_write_tokens`。
- 无可靠总输入 token 的历史日志不做分类。
- 总输入 token 大于阈值为长 Context，否则为短 Context。

### 动态计费

- `billing_mode == "tiered_expr"` 计入动态计费汇总。
- 不解析历史表达式，也不根据当前配置重算历史金额。

## 最小入侵接线

1. 新增独立配置包，复用 `GlobalConfig` 的加载与热更新。
2. 新增独立 model 文件，逐行读取日志并在内存聚合。
3. 新增独立 controller 文件和一条路由。
4. 账单页在正式账单加载成功后再加载使用构成；汇总失败不影响正式账单。
5. 系统设置增加 JSON 模型阈值编辑入口。

## 验收

- 原账单接口响应、核心计费结果和日志结构不变。
- 缓存读写兼容总量字段与 5m/1h 拆分字段。
- 未配置阈值的模型不出现长短 Context。
- 缓存、Context、tiered 分类均复用原日志 quota。
- SQLite、MySQL、PostgreSQL 查询兼容；ClickHouse 保持现有日志查询约束。
- 后端测试、前端类型检查/构建及 docs 检查通过。
