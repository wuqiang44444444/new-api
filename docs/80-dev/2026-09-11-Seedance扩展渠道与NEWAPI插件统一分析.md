# Seedance 扩展渠道与 NEWAPI 插件统一分析

## 1. 问题与目标

用户要求所有 Seedance 专用渠道统一进入插件，并明确期望保持 NEWAPI 的设计，把 Seedance 作为一个
扩展渠道。这里的统一应覆盖插件发布、渠道配置定义和 Provider 适配的维护方式，不能以所有代码都进入
JavaScript 或插件列表出现一张卡片作为完成标准。

本次是代码与方案复核，没有执行渠道切换、数据迁移或业务代码修改。用户随后已确认以持续同步
NEWAPI、减少冲突为首要目标，本分析结论已纳入[迁移方案](2026-09-09-Seedance独立插件迁移方案.md)。
本文保留取证和取舍依据，执行目标、职责及批次统一以迁移方案为准，不替代当前已发布 API 或资金合同。

### 2.2 NEWAPI 已有的设计

NEWAPI 把插件实现与 Channel 实例分开：插件声明模型、渠道适配范围、路由/宿主协议、用量字段，
实现创建、查询、结果与内容转换；Channel 保存用户配置的地址、凭据、模型列表与映射、分组和启停。
同一插件可服务多个 Channel，更新插件源码不等于修改各个 Channel 的账号配置。

原生支持两种关联方式：

| 方式 | 代码证据 | 含义 |
| --- | --- | --- |
| 既有专用渠道类型由插件驱动 | [Doubao manifest](../../plugins/tasks/doubao/plugin.js) 的 `channelTypes: [54, 45]` | 专用 ChannelType 与插件不矛盾；插件化不必改成通用渠道类型 |
| 通用 Task Plugin Channel 绑定插件 | [渠道保存校验](../../controller/channel.go) 的 `TaskPluginKey`；上游同样具备该路径 | 第三方任务插件可通过已有 Channel 与权限入口配置 |

已存在的插件管理、版本表和执行引擎应复用。当前本地的插件默认地址补全与额外展示字段不全都存在于
上述上游基线，不能把本地新增能力说成上游现成接口。

### 2.3 Seedance 当前统一到了哪里

> 取证时点说明：本节描述 U1—U3 实施前的状态（如"迁移登记只包含 `feicai_videos_v1` 的三个
> hook"）。实施后的全协议接线、配置合同与剩余工作以
> [配置统一实施记录](2026-09-11-Seedance配置统一实施记录.md)为准。

`seedance-link` 共享 JS 引擎、TaskPlugin 版本表和插件管理页面，但执行合同独立：

- [扩展编译器](../../pkg/jsplugin/seedance_extension.go)拒绝原生 `models`、`channelTypes`、
  `routes`、`protocols`、`usageSchema` 等声明，校验专用协议 hook。
- [控制面接线](../../controller/seedance_plugin_extension.go)将其从通用注册表分离并单独同步。
- [适配器入口](../../relay/relay_adaptor.go)遇到 Seedance 类型 62 优先返回 Go Seedance adapter。
- [迁移登记](../../relay/channel/task/seedance/plugin_extension.go)只包含 `feicai_videos_v1` 的三个 hook。
- [扩展版本解析](../../pkg/seedanceplugin/store.go)承担已冻结版本的履约保障，
  不能仅因希望统一加载逻辑就删掉这项能力。

因此当前交付是“Seedance Go 宿主内的协议转换插件”，尚不是完整的配置与适配维护统一。
这曾是降低首批迁移风险的合理选择，但不能直接作为用户新目标的最终形态。

### 2.4 现有插件 API 的实际缺口

| 目标 | 当前缺口与影响 |
| --- | --- |
| 插件声明完整渠道配置 | 当前 Meta 没有完整的渠道配置 schema；驱动上下文也没有完整 Seedance 视频/素材设置接口。不能把当前前端字段直接移入一个不存在的 manifest 字段 |
| 保持 ModelArk V3 API | 原生宿主协议表只有 Responses 与 OpenAI Video；Seedance 的 `/api/v3/contents/generations/*` 仍由本地 Router 管理，且 `/api` 是通用插件自定义路由的保留命名空间 |
| 素材、素材组与认证 | 原生声明式任务路由围绕 submit/query/dynamic 任务意图，不能据此认定已具备无状态素材操作合同；素材不应伪装成 Task |
| 客户自定义模型 | 原生 `meta.models` 进入全局模型索引与协议候选；Seedance 的 Provider 模型登记不能原样塞进去，否则可能影响原生模型归属与定价投影 |
| 保持现有费用 | 通用 JS TaskAdaptor 实现 `TaskUsageFactsProvider`；[任务计价入口](../../relay/relay_task.go)据此选择另一条表达式/用量路径。替换 adapter 类型本身即可改变计价语义 |
| 历史履约 | 原生按 platform 获取 adapter 的入口解析当前 generation；Seedance 已冻结的 key/version、连接与资金事实不能改用当前 active 版本 |

这些缺口说明完整接入需要受限的宿主扩展，不说明应另造插件平台，也不说明必须修改原生客户接口。

### 2.5 当前协议范围

[当前枚举与新配置校验](../../relaykit/dto/upstream_protocol.go)允许 9 个新受理视频协议：火山、
BytePlus、移动云、TokenSave、Moxing ModelArk、Ark、飞彩、FunCloud ModelArk V3、Synlink。
`moxing_media_task_v1` 与 `funcloud_seedance` 只为历史任务保留识别，不能因为原方案列出 11 项
而重新开放。素材有 7 个远端协议，加 `none` 和本站托管图片两种模式。

## 3. 优化方案

### 3.1 推荐的职责边界

建议保留一个 `seedance-link` 发布包服务全部 Seedance Channel，沿用 NEWAPI 的 Channel、插件
管理、版本存储与运行引擎。Provider 专属定义和转换由技术人员维护的插件承载；Go 保留平台合同。

| 内容 | 推荐权威与执行位置 |
| --- | --- |
| 视频/素材协议选项、配对、Provider 模型清单与 Provider 必填字段 | 插件内经过校验的类型化声明；这是目标扩展，不是目前已有能力 |
| Provider 路径、请求/响应转换、业务错误与用量提取 | 插件实现，统一由 Go 校验结果并发送 HTTP |
| 地址、凭据、客户模型、model_mapping、Project/Region 的实际值 | 现有 Channel 及其受保护配置存储；不写进插件源码或全局插件设置 |
| 客户 API 与请求语义、渠道权限、单模型唯一渠道、请求安全上限 | Go 宿主维持既有合同 |
| 素材普通组策略 | 在目标声明中保留固定枚举及北向语义，由运行时与元数据读取同一已校验结果；迁移完成后删除重复的 Provider 映射来源 |
| Task/attempt、版本冻结、quota、退款、账单与恢复 | Go 宿主及现有持久事实 |
| 签名、凭据注入、托管素材复制/所有权/临时 URL、流式传输 | Go 宿主受限能力；插件只描述获准操作 |

模型登记与配对一直保留在 Go，是旧方案的本地取舍，不是 NEWAPI 对插件的普遍要求。
如果采用上述目标，需要同步修订现有代码注册约定；在方案落定前不能在插件里复制一份然后让两处同时
决定资格。北向字段支持、资金上限和用户权限也不能随着 Provider 插件升级被任意改写。

统一维护不要求每个协议重复一份脚本：可以在源码中按协议组织实现并构建为现有单文件发布制品。
这只服务既有插件工具链，不引入另一套脚本引擎或运行时模块加载器。

### 3.2 保留专用类型 62，而非直接改成通用类型 61

保留 62 符合 NEWAPI 已有“专用渠道由插件驱动”的模式，也保留当前客户模型、素材租户与历史 Task
的身份。把 62 改成 61 会连带改变分发、保存校验、任务平台、价格归属和资源边界，收益不能用
“所有插件都叫通用渠道”证明。

这不意味着现在添加 `channelTypes: [62]` 即可完成：当前扩展编译器会拒绝该字段，adapter 仍优先走
专用分支，通用索引与计价也尚不满足当前合同。类型关联、实现调用和宿主策略必须一起核对。

推荐的管理体验仍是：在渠道页创建 Seedance 扩展渠道，填写该 Channel 的账号和模型配置；
插件提供协议选项与相关字段定义，插件页负责版本、启停、覆盖协议和执行依赖。多个渠道不共享一份
账号值，也不要求管理员为每个渠道复制或编辑 JS。

### 3.3 扩展上游已有机制，而非永久增加 Seedance 特判

优先使用现有插件元信息、引擎、TaskPlugin 表、管理 API 和发布同步，在已有装载流程旁增加明确的
扩展合同接入点。需要新增的能力限制为本次实际需求：

1. 类型化渠道配置声明与校验投影。前端协议选项、保存验证、运行时与公开元数据消费同一来源；
   显示条件不能成为权限校验，插件升级不能默默覆盖已保存的地址、租户或默认组。
2. ModelArk 与素材的宿主操作接线。沿用现有客户路径和处理职责，每个方法/路径只保留一个 handler；
   不伪造普通任务，不借插件元信息占用原生视频/Responses 路由。
3. 已冻结插件版本的解析与执行依赖保护。复用现有持久引用，激活只影响新受理；素材单次调用也应固定
   一个版本完成受限操作，不能在多步调用中混用新旧版本。
4. 区分管理用的 Provider 模型声明与原生路由资格。共用插件管理不要求所有声明无条件进入 `byModel`；
   元数据改动不得触发客户模型跨渠道资格或 NEWAPI 原生端点新增资格。

不预先承诺将所有代码合并进一个注册表类。应先证明这些扩展能以新增文件与窄接线实现，再决定哪些
Seedance 加载分支可以删除；仅为减少类或 map 数量侵入上游热路径，不符合最小入侵目标。
当前精确版本缓存的履约责任也不能与原生候选路由缓存混为一谈。

### 3.4 方案取舍

| 方案 | 结果 | 判断 |
| --- | --- | --- |
| 按旧 P3—P5 只扩大转换 hook 覆盖 | Provider 转换进入 JS，配置仍散落 Go/前端 | 能完成旧目标，不能独立完成本次配置统一目标 |
| 直接使用未扩展的通用 TaskAdaptor/61 渠道 | 表面接入原生插件，但 API、素材、计费、历史行为存在缺口 | 不采用直接替换 |
| 沿用 Channel 与插件底座，补足必要的配置/操作/版本扩展 | Provider 定义统一，平台合同和实例配置保持稳定 | 推荐；需先验证最小修改面 |
| 自建 Seedance 插件平台、配置表或通用工作流 | 扩大本地分叉和后续同步成本 | 不采用 |

## 4. 已纳入迁移方案的调整

迁移方案 §3 已调整配置定义的维护边界，增加最小宿主扩展、配置发布一致性与上游同步治理；§8 使用
U0—U5 覆盖基线、扩展合同、样板、全量协议、清理/同步演练和验收发布。本文不再另列执行排程。
P1/P2 已实现事实、历史发布制品和冻结引用继续保留，不因方案修订改写为未完成或删除。

复审确认该方向符合 NEWAPI 的职责分工，但完整配置声明、素材操作和冻结版本履约仍需有限的本地
扩展，不能据此认定同步成本已降低。迁移方案 §4.4 已纠正版本固定晚于请求构造的时序描述；§8.2
要求 U2 实际重放核心扩展补丁并通过原生回归后才进入全协议迁移，U4 再做完整同步演练。

## 5. 验收标准与本次验证

统一的主要验收标准：在既有北向合同和宿主能力内新增同类 Provider 模型、修改协议字段或修复响应解析，
应主要改插件制品及其 fixture，不再同步手改 Go 模型清单、前端选项和多份配对表。新增客户 API、资金
语义或新签名/存储能力仍需要宿主开发，不能宣称任何新 Provider 都只需上传脚本。

必须验证：原生 Doubao 不受影响、客户模型索引不串用、保存与运行时接受同一配置、API/素材语义等价、
预扣与结算整数 quota 相等、旧版本继续履约、缺版不回退、升级不改变已有 Channel 的敏感配置。
新增原生文件改动必须逐个说明最小接线必要性与上游同步影响。

本次只完成静态取证与分析文档，不运行 Provider 请求，不把既有测试报告当作本次迁移证明。
本次 `task docs:check`、`task ai:check` 与 `git diff --check` 均通过；不将本建议写成已实施架构。
