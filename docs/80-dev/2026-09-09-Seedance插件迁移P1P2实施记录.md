# Seedance 插件迁移 P1+P2 实施记录

本文记录[Seedance 独立插件迁移方案](2026-09-09-Seedance独立插件迁移方案.md)的 P1 宿主接入、
P2 首个协议 `feicai_videos_v1 + none` 及评审修复。总体方案仍是迁移范围与验收门槛的权威来源。

**代码实施与本地验证不等于生产验收。** 本批未执行真实 Provider、真实账单、三数据库实机、
容量与灰度验证；P0 生产矩阵及 P3—P5 的剩余工作仍须按方案推进。

## 1. 组件边界

- Seedance 专用渠道 62 与原生 Doubao 渠道独立。新增 `seedance-link` 扩展仅复用 JS 引擎、
  TaskPlugin 版本存储和管理入口，不进入原生 `DefaultRegistry` 或其模型、渠道、路由索引。
- 首个迁移协议为 `feicai_videos_v1`，素材仍为 `none`。其它视频、素材、托管与签名协议未迁移。
- 插件负责创建请求转换、创建响应与轮询观察解析；Go 保留路由、凭据、HTTP、同源校验、
  脱敏、Task 状态机与全部资金操作。插件没有 `TaskUsageBilling` 或原生用量编辑器资格。
- 历史无插件快照的 feicai Task 继续由旧 Go 轮询实现履约；新请求没有 Go 回退路径。
- P1/P2 初次制品为 **1.0.1**，修正 Base64 CR/LF 与错误引用转义。修改源码必须增加版本，不能覆盖
  1.0.0。已有 active 版本时，升级种子只新增非 active 行，管理员仍需明确激活。

## 3. 原生接线与最小入侵

| 原生文件 | 必要接线 | 上游同步影响 |
| --- | --- | --- |
| `controller/task_plugin.go` | 上传、列表、详情、激活、DryRun 委托编译 helper；同步前分离扩展行；列表投影和模型删除错误投影 | 保留既有管理入口，只需在对应语句边界重放调用，不修改原生编译合同 |
| `model/task_plugin.go` | 删除事务首部调用 `guardSeedancePluginDeletion` | 必须位于持久删除事务内，控制器预检查无法消除竞态；非 Seedance key 直接返回，原有删除/晋升逻辑不变 |
| `service/task_polling.go` | fetch 错误分支识别观察不可用并跳过本轮 | 仅增加错误分类，不改结算算法、退款入口或原生 Provider 错误语义 |

主体逻辑均放在新增 Seedance 文件。原生 `registry.go`、`engine.go`、`plugins/embed.go`、
`controller/relay.go`、`relay/relay_task.go`、`relay/relay_adaptor.go` 和 `main.go` 无需扩展接线。

本地接线包括：

- `middleware/seedance_channel.go`：选定专用渠道后、资金前 pin；未迁协议不 pin。
- Seedance adaptor / billing probe / video upstream：新请求使用插件转换；旧转换只保留差分 oracle
  与无快照历史轮询；probe 与发送 body 共享一次实例内转换。
- `service/task_create_attempt.go`：prepared 时冻结插件身份，并将类型化 pin 交给模型层锁定。
- `model/task_create_attempt.go`：prepared 事务首部取得版本锁，校验 pin 与持久 JSON 一致。
- `service/task_create_attempt_manual_recovery.go`：恢复模板记录执行快照。

没有新增数据库列、第二套账本、运行时模型推断、协议 fallback 或跨渠道重试。

## 4. 版本与执行依赖

### 4.1 受理和删除的原子关系

流程为：middleware 内存 pin → prepared 事务锁定精确版本并写入持久引用 → 既有 hold/sending
事务 → 单次 Provider POST → Task 创建、hold 转移与 attempt 完成原子提交。

删除在自己的事务首部取得同一版本锁，然后查询执行引用并删除。创建先取得锁时，删除必能看到
prepared 引用；删除先完成时，创建找不到版本，在 prepared/hold/POST 前拒绝。删除保护覆盖所有
版本，不受 active、enabled、factory 或 force 影响。原先 POST 前的重复存在性检查已删除，
它不能替代事务互斥，也不应增加热路径上的第二次判定。

MySQL/PostgreSQL 使用项目 `lockForUpdate`；SQLite 在任何读取前对精确版本做不改变值的写入，
取得数据库写入保留锁。锁仅覆盖数据库事务，不跨 JS、HTTP 或后续资金 hold。

依赖查询先读 attempt，再读 Task。attempt → Task 转移本身原子完成；此顺序避免 READ COMMITTED
下先看不到 Task、随后又看不到已完成 attempt 的漏查窗口。删除期间新增 prepared 受版本锁约束。

### 4.2 引用的唯一口径

- Task：平台 62，精确 `Execution.TaskPlugin.key + version`；空 version 用于管理列表聚合所有版本。
- attempt：prepared / sending / unknown / upstream_succeeded，匹配 FrozenConnectionSnapshot
  或 RecoverySnapshot 中的冻结身份。不能按当前迁移协议表过滤历史引用。
- `TerminalTaskStatuses()` 是唯一终态定义。已结算或空 billing state 的 FAILURE、
  PROVIDER_CONTRACT_FAILURE、CANCELLED、EXPIRED 不再仅因状态误计为永久依赖。
- `UNKNOWN` 不是终态，继续保护；pending / failed / debt / awaiting_usage 继续保护。
- **可查询的 SUCCESS 即使已结算也保留依赖**：`RefreshVideoTask` 对成功任务仍执行冻结插件查询。
  客户已删除且已结算的 SUCCESS 才可释放此项依赖。不能笼统地把所有已结算终态排除。
  对 feicai 该释放条件当前不可达，后果与决策见第 7 节。
- 列表 `InFlightCount = Task 引用数 + attempt 引用数`，启用、停用、无 active、编译失败使用同一
  查询。查询失败返回错误，不把数据库故障显示为零引用。该兼容字段表示执行依赖数，包含历史服务依赖。

### 4.3 编译失败和发布

保留 key 无论是否能通过通用编译，都必须再通过扩展合同，防止伪装为通用插件绕开协议约束。
原生非保留 key 正常源码仍只执行一次通用编译。

同步编译失败时记录诊断，失败的 active 版本不再接受新请求；不能静默沿用旧代码并显示健康。
已经持有的执行对象不被改写。后续冻结版本解析仍以数据库行与精确版本为准，无法解析则进入既有
失败关闭/对账路径，不换 active、不退款。正常停用只停止新受理，仍存在的合法历史版本可继续解析。

种子标记只在确认持久化后设置，并在下一次编译前检查。瞬时保存失败可重试；成功后同进程同步
不会重复编译嵌入制品，也不会复活管理员删除的无依赖版本。

## 5. 计费与协议修复

- 插件 probe 仅允许 feicai 的 resolution / ratio / size_multiplier / billing_mode。
  duration_seconds、has_video_input 等宿主事实不能由插件覆盖。
- body 的模型必须等于冻结 Provider 模型；duration 必须存在且等于客户请求。包括客户未传 duration、
  插件自行补 15 秒的情况，均在预扣前拒绝，避免宿主默认 5 秒与实际发送时长不同。
- Base64 校验与 Go StdEncoding 保持一致：允许 CR/LF，继续拒绝空格、非法字符及错误 padding；
  校验时忽略换行，发送内容保持原样。`quote` 的 bell 转义修复为 JS 的 `\u0007`，不再误转普通字母 a。
- 插件准入/执行超时或中断属于观察不可用，跳过本次轮询，不累计传输失败、不改业务状态、不退款。
  脚本逻辑错误仍进入合同异常/对账；既有整体任务超时清扫边界不变。
- 没有修改表达式、额度转换、hold、结算、差额、退款或日志金额计算算法。

## 6. 回归验证

新增或补齐的可观察回归包括：

| 边界 | 验证内容 |
| --- | --- |
| 版本互斥 | 两个真实 SQLite 事务，确定性控制创建先/删除先；前者删除被阻止，后者没有 prepared |
| 依赖语义 | 全部权威终态 × 各 billing state；UNKNOWN、可见/删除 SUCCESS；非 active 与 force；历史协议身份 |
| 管理面 | 保留 key 伪装通用插件被拒；停用与无 active 时仍计 Task+attempt；查询故障显形 |
| 发布失败 | 先成功 pin，再编译失败；新受理停止、错误可见、已 pin 对象不变；修复后恢复 |
| 协议差分 | 全部已登记模型；创建/响应/观察 fixture；Base64 CR/LF 与拒绝边界；错误字符串转义 |
| 资金 E2E | 成功预扣和结算、失败一次退款、未知创建保留 hold、版本受理前删除、改写/省略 duration 均在预扣前拒绝 |
| 轮询 | 插件连续超时不累计业务失败，不产生退款；槽位释放与后续调用可用 |
| 隔离 | 扩展加载前后原生 registry generation 与模型索引保持不变 |
| 三库锁并发 | MySQL 8.0 / PostgreSQL 16 真实服务器：受理先提交则删除被拒、删除先提交则受理失败关闭、依赖查询冻结身份语义 |
| 容量基线 | 冷编译/热 hook/观察解析耗时与分配、并发 8 信号量超订吞吐与槽位释放（本机实测，数字入盘点文档） |

## 7. 剩余验收与容量边界

- P0 本地部分已完成：本地快照脱敏盘点与数据迁移判定见
  [Seedance插件迁移P0本地盘点](2026-09-10-Seedance插件迁移P0本地盘点.md)
  （结论：本批不需要数据迁移；渠道 92 `seedance-2.0-cmcc` 无定价、不进入切换批次）。
  生产矩阵导出仍须在生产库用同一工具执行。
- MySQL 8.0 / PostgreSQL 16 实机验证已完成（[盘点文档](2026-09-10-Seedance插件迁移P0本地盘点.md) §5）：
  版本锁并发互斥、删除后受理失败关闭、依赖查询的冻结身份语义在两台真实服务器上通过。
  真实 Provider、账单、灰度尚未执行，不得写成生产已通过。
- JSON 中插件身份在 Go 层匹配是三库兼容取舍；查询已仅选择引用所需列，但 private_data 与恢复
  快照仍可能很大。它们位于管理/删除路径，不进入逐次轮询。上线前记录候选行数、快照体积、
  查询耗时和进程内存基线；规模证明确有问题后再评估批量扫描，不新增第二份持久身份或旁路缓存。
- create/poll 准入各 2s、引擎默认执行 5s / 并发 8 已有本机容量基线
  （[盘点文档](2026-09-10-Seedance插件迁移P0本地盘点.md) §5：热 buildCreate ≈77µs、
  观察解析 ≈13µs、超订吞吐 ≈17 万次/秒且槽位全部释放），JS 容量相对现有速率有几
  个数量级余量；多节点总量、素材请求叠加与真实流量分布仍须按 §8.3 实测后才能放行生产受理。
- awaiting_usage 与 debt 保持既有补偿路径，本批资金 E2E 未替代其真实 Provider 验收。
- `FAILURE + failed` 等未决账务状态继续保护，不能仅以业务失败推断账务完成。
- **SUCCESS 依赖使 feicai 插件版本实际不可删除（2026-09-10 已确认接受的保守语义）**：
  feicai 第三方合同 `SupportsDeleteTerminal=false`，客户端终端删除按已登记行为返回
  `delete_unsupported`，无法置位 `client_deleted_at`；因此任何含 SUCCESS 历史任务的插件版本
  永久计为执行依赖，删除保护始终拒绝，列表只显示引用数、无清理路径。本批按方案 §7.2
  "仍需该版本完成查询的历史 Task"字面口径保留该保护。两个候选改向都需要先改合同或方案：
  释放 SUCCESS 观察依赖（已核实版本缺失时成功任务观察失败可安全降级，不翻转任务状态、
  客户端拿到持久投影），或为 feicai 开放本地删除标记。P5 收敛时与账务/产品 owner 一并确认，
  在此之前不得为绕开删除保护改写 Task 快照或跳过保护。
- 删除 active 版本沿用原生自动晋升剩余版本行为；本次只加不可绕过的执行引用保护。
- 修改源码必须递增版本；已有 pinned 新版本时不能回滚到无法执行该版本的旧二进制。
- P3 远端素材、宿主签名前后向量及其余协议迁移仍按总体方案逐组实施和验收。
