# 原生错误事件渠道与分类修复方案

## 问题与目标

原生 Azure 同步图片请求经两个渠道尝试后均收到上游 429，用量日志保存了每次尝试与重试决策，
独立错误事件却缺少客户模型、渠道和原因分类。本次修复最终错误事件的诊断归属，并补齐
ModelArk 任务查询中已知的 `task_not_found` 分类，不改变选渠、重试、资金或任务状态语义。

## 当前实际情况

- 用户提供的生产只读分析证明：同一请求先后调用渠道 149、155，最终事件中的上游请求 ID 与
  第二次尝试一致，但 `channel_id=0`、模型为空、阶段与原因为 `unclassified`。
- 用户报告近七天存在大量未分类记录；这些统计未在本地独立复查，不作为已验证生产验收结论。
- 本地代码确认原生选渠写入 Gin 上下文，独立记录器却只从显式 Report 获取模型和渠道。
- Report 使用先写入者优先；在每次失败尝试中直接 Attach 会把第一次失败与最终上游 ID 混合。
- ModelArk GET 按用户、应用和协议查询本地任务，不可见时直接 404；此时空渠道是正确事实，
  不能将大量此类记录全部视为渠道漏采，也不能跨租户查询来补字段。

## 优化方案

1. 只在 `relay/api_error` 的缺失字段上读取既有 `original_model`、`channel_id`，显式诊断优先；
   选渠前错误保持空渠道，其他事件类型保持现有采集合同。
2. 原生 Relay 在最终错误出口调用独立诊断逻辑，不在每次失败时冻结分类。读取本次真实上游
   HTTP 状态，在状态映射后仍能准确标记 `upstream_rate_limited`。网关自身 429 不作此分类。
3. 每次尝试开始清理前次上游请求 ID 与诊断 HTTP 观测，防止后续连接失败或请求构造失败继承
   旧响应；不清理显式业务诊断，不修改重试次数与选渠条件。
4. ModelArk `task_not_found` 记录 `task_lookup/task_not_found` 与协议，保持租户不可见和不存在
   使用相同响应，不新增跨租户查询，不推断渠道或自动归责。
5. 不改数据库结构、不批量回填历史数据、不改前端。Azure 部署额度控制及 Retry-After 冷却为
   后续独立工作，本批只修诊断。

### 原生文件接线与同步影响

- `controller/relay.go`：最终错误出口与尝试开始各一行接线，新增逻辑放独立文件；未来上游同步
  仅需复核这两个生命周期位置，不重构原生 Relay。
- `clienterrlog/recorder.go`：本地诊断模块中的缺失身份回填；不改变已有 Report 合并优先级。
- `controller/video_modelark.go`：本地 ModelArk 错误响应函数增加一行诊断调用。

### 验证与验收

- 两个渠道均 429：最终错误事件只有一条，模型、渠道、上游 ID 和快照均对应最后一次尝试。
- 重试成功：不产生最终 API 错误事件；用量日志仍保留失败尝试。
- 前次 429 后发生连接或本地构造失败：不继承前次上游 ID、状态和响应，不误判限流。
- 上游状态码映射不改变客户响应，同时保留真实上游 429 分类。
- 已有显式诊断不被兜底覆盖；选渠前限流、模型权限和合同拒绝继续保留空渠道及原分类。
- 不存在、其他用户/应用、错误协议及已删除任务统一 404，分类明确、渠道为空，不泄漏归属。
- 执行窄边界 Go 回归、相关检查，以及 `task docs:check`、`task ai:check`。

## 实施与剩余事项

### 本地实施

- `clienterrlog/relay_attempt.go` 提供每次原生尝试的观测清理与原始上游状态读取，复用既有 HTTP
  诊断载体，不重复解析 Provider 正文；记录器只补 relay 最终 API 错误缺失的模型和渠道。
- `service/relay_error_diagnostics.go` 在原生 Relay 最终失败时登记稳定原因，区分真实上游 429、
  其它上游 HTTP 错误、本地错误和连接失败；保留已有显式诊断的合并优先级。
- `controller/video_modelark_diagnostics.go` 对明确的 `task_not_found` 分支补充查询阶段与协议。
- 新增四个表驱动回归测试，首轮包含 21 个场景，复评后扩展至 24 个；真实 Relay 集成使用本地 HTTP 模拟 Provider 和
  SQLite，同时检查 `logs` 尝试记录及 `error_events` 最终事件。

### 验证记录

- 定向回归 21 个场景通过，包括两个 Azure 渠道、成功重试、上游状态映射、连接失败和五种
  ModelArk 任务不可见情况。
- `go vet ./clienterrlog ./model ./middleware ./controller ./service ./relay/...` 通过。
- `task docs:check`、`task ai:check` 与 `git diff --check` 通过。
- 扩大回归中 `clienterrlog`、`model`、`middleware`、`relay` 及除下述 Seedance 用例外的
  relay 子包通过；Service 首次并行运行异常退出，串行完整复跑通过（25.738 秒）。
- Controller 完整回归暴露新增集成测试复用旧夹具时依赖全局工作池空闲；已改为独立 SQLite、
  合成免费请求和显式配置，不等待其它测试的后台 worker。修改后的定向回归和 Controller
  完整复跑均通过（完整复跑 66.547 秒）。
- `TestFunCloudFetchTaskUsesAIGCQueryAndReportedCompletionTokens` 在
  `relay/channel/task/seedance/funcloud_task_query_test.go:82` 失败。使用 Go overlay 将本次改动的
  三个已有 Go 文件替换为 HEAD 原文后，单独执行该用例仍在同一行失败；属于本次补丁之外的
  基线问题，未扩大修改。该用例未通过，不能把扩大回归写为全绿。

### 剩余验收

未访问生产数据库，未进行真实 Azure 调用或生产部署。部署后应检查新事件的模型、渠道与最后一次
上游 ID 一致，选渠前拒绝和不可见任务继续为空渠道，并核对新分类分布；历史事件保持原记录。
实际 Azure 429 的容量治理仍为独立后续工作。
