# 使用日志 RPM 与 TPM 手动刷新方案

## 1. 问题与目标

日志量大时，普通使用日志页的 RPM、TPM 容易等很久。将两个值保留在筛选区，旁边提供一个「刷新」按钮。
每次点击只统计截至服务器当前时间的最近 60 秒。日志列表继续按用户选择的日期查询，整段范围的总条数
和消费金额继续通过现有「查看范围统计」入口按需读取。本方案待实施。

## 2. 当前实际情况

- 普通使用日志的「查看范围统计」已由点击触发。当前前端把列表解析出的起止时间传给统计接口。
- 后端先执行该范围内的总条数和消费金额聚合，再计算范围内、时间戳至少为服务器当前时间减 60 秒的
  消费日志速率。两条 SQL 共用 3 秒的请求期限。昨天全天的筛选会得到零速率，包含当前时刻的一天只会
  得到最近约一分钟的速率。第一条 SQL 慢或超时时，两个速率值也随之等待或失败。
- 本地用 100 万条合成日志在 SQLite 执行现有统计函数，8 小时时间范围的条数与金额聚合中位耗时
  179.0 ms，速率聚合为 0.60 ms。前者走全表扫描，后者使用时间索引。生产库两段 SQL 的各自耗时、
  扫描量及连接池等待仍待核实。

现有入口见[统计组件](../../web/src/features/usage-logs/components/common-logs-stats.tsx#L95)、
[统计查询](../../model/log_cursor.go#L234)和[请求期限](../../controller/log_cursor.go#L99)。
分页与范围统计的背景见[使用日志查询减负设计与实施方案](../50-planning/2026-11-18-使用日志查询减负设计与实施方案.md)。

## 3. 优化方案

### 3.1 界面与统计口径

| 操作 | 预期行为 |
| --- | --- |
| 打开页面、翻页、切回页面 | 不自动查询速率。尚未刷新时显示 `—`。 |
| 提交新的筛选或切换账号、访问视图 | 清除旧速率结果和更新时间，取消已经过期的请求，等待用户点击刷新。 |
| 点击速率旁的「刷新」 | 只更新 RPM、TPM，显示「最近 60 秒」和本次统计时间。请求进行中禁止重复提交。 |
| 速率请求失败 | 保持列表和范围汇总可用。当前筛选下已有的数值保留原统计时间，并提供手动重试。 |
| 点击「查看范围统计」 | 按日志列表已解析的起止时间查询总条数和消费金额。 |

速率刷新使用已提交且在当前角色下有效的非时间筛选，例如客户模型、API Key 和渠道。由服务器在
请求开始时取一次当前 Unix 秒 `T`，只读取满足 `T-60 < created_at <= T` 的匹配消费日志。
日志列表选昨天、今天或一个月，都使用这个实时窗口。

RPM 是匹配消费日志的条数，TPM 是这些日志的输入和输出 Token 之和。筛选只允许非消费日志或没有
匹配消费日志时显示 `0`。这两个值用于日志观察。

### 3.2 后端读取

1. 在现有管理端和个人端的控制台统计入口增加 `mode=rate` 和 `mode=summary`。速率请求只传有效的
   非时间筛选，返回 `rpm`、`tpm` 和窗口结束时间。汇总请求沿用列表解析后的时间范围，只返回总条数和
   消费金额。未指定模式的调用沿用既有请求和响应语义。
2. 复用现有登录鉴权、日志筛选解析、角色过滤白名单与个人视图的服务端 `user_id` 条件。速率模式执行
   一条 `COUNT(*)` 加 Token 求和的普通只读查询。筛选确定无法命中消费日志时，在完成授权和参数校验后
   直接返回零。请求继续传递客户端取消信号，并受现有控制台查询期限约束。
3. 新模式请求省略旧版必需的 `range_count=true`，使旧控制台处理器在执行 SQL 前拒绝请求。滚动升级时，
   新前端收到模式不可用的结果，显示手动重试状态。
4. 改动限制在普通使用日志控制台的读取和界面。第一版使用现有索引，避免迁移和额外的日志写入成本。
   如果独立速率查询在生产高峰仍慢，再依据执行计划、实际扫描行数和日志写入尾延迟评估索引。

## 4. 验收

- **交互**：浏览器网络记录显示，首屏、翻页、切回页面和提交筛选均发出零次速率请求。点击刷新只发一次
  速率请求，列表和范围汇总无需刷新。覆盖连续点击、取消过期请求、手动重试和中英文文案。
- **计算**：固定服务端时间，验证 60 秒窗口两端、未来时间戳、非消费日志、零结果及多个筛选条件。
  选择昨天或一个月后，速率和相同非时间筛选下的实时结果一致。单独发起范围汇总，核对所选区间的总条数
  和消费金额。
- **权限与兼容**：分别验证管理及个人视图。个人只能统计本人的匹配日志。验证未指定模式的旧调用仍按既有
  语义响应，新模式发给旧版本时不会触发聚合。覆盖 SQLite、MySQL、PostgreSQL，以及部署使用 ClickHouse
  时的对应统计路径。
- **性能**：记录峰值下速率请求的 P95、扫描行数和超时率。选用一天和一个月的日志范围分别刷新，
  从 SQL 记录确认只有一条秒级窗口的聚合，无全范围条数或金额查询。灰度期间对比日志写入和核心 API
  的尾延迟。若速率查询实际出现查全表或影响写入，暂停扩大灰度并核对执行计划和连接池等待。
