# 图片交付故障与原始错误证据修复记录

## 1. 问题与目标

承接[真实渠道验收记录](2026-09-16-图片Task真实渠道验收记录.md)，修复图片 Task 交付失败
无法定位、恢复扫描覆盖首次失败码的问题。用户随后明确要求保存相关原始错误返回，并确认
本次范围为图片同步、流式和 Task 全链路。新增证据只用于诊断，不参与业务判定、重发或扣退。

## 2. 当前实际情况

### 2.1 默认 URL 交付失败的实测根因

原生异步图片已经实现“Provider URL 下载或 Base64 解码 → 私有 OSS → 产物登记 → 查询时
鉴权并签发 300 秒地址”。不需要再建立图片存储体系。

新增诊断的真实样本：

- `task_r8rmjOJI1UeNx43eOBNjC2ugHDSFDNfo`：上游生成 HTTP 200，失败码为
  `result_download_transport_failed`；恢复扫描后仍保留该码。
- `task_7G8BneVpkw95C138WtLBPWyFPcN9X4Er`：在受保护证据中保留生成响应与下载传输错误。
  响应形状为 HTTPS URL，无 Base64。下载错误明确指出 CDN 域名被解析到 `198.18.0.185`，
  安全下载器拒绝这个保留地址。完整 URL、响应正文及凭据不复制到本文。
- 公网 DNS 查询同一 CDN 返回公网 A 记录；本地故障与测试机返回保留地址的 DNS 环境有关。
  不能据此认定线上环境也出现同样故障。

此处不关闭 SSRF、不放行保留地址、不复用带 Provider 凭据的客户端下载任意媒体，也不因一次
下载失败重发生成 POST。部署应让安全下载进程获得真实、可验证的公网解析结果。

### 2.2 已完成的代码修复

| 问题 | 本次修改 | 保持的业务边界 |
| --- | --- | --- |
| 交付错误被转换为笼统 unknown | 保留清单提交、租约、下载请求/传输/状态/读取、解码、存储检查、上传和产物登记等固定错误码 | 交付失败继续待核实，不按图片 GET 的 4xx 退款 |

| 只有摘要，无法看原始返回 | 图片错误正文和传输原因通过非阻塞队列写入既有加密证据库 | 证据不成为状态、计费或重发许可的事实源 |

旧任务中已经被覆盖的失败码无法凭空还原，本次不批量修改历史任务或重新执行。

### 2.3 图片错误证据范围和访问

- 图片生成、编辑及既有图片兼容路径：入口参数错误、同步错误、HTTP 200 中的 SSE 错误事件。
- 上游生成/轮询响应：在 adapter 解析前旁路复制已读取字节。一次调用最终失败时，保留本次已
  捕获的关联响应；HTTP 非成功、读取/传输错误独立保留，成功请求无错误时不落正文。
- 图片 Task：原生 OpenAI/Azure、Gemini/Vertex 和图片中转执行器接入同一观察上下文；
  执行与恢复均覆盖；图片 URL 下载保留独立交换，存储/数据库交付错误保留私有原因。
  S3 保存已被原逻辑读取的错误响应，Azure Blob 保存 SDK 原始异常；存储 HEAD 的正常 404
  不误记为故障。客户端写出错误、签名和存储配置错误也进入证据。
- 图片任务查询：仍先校验归属；查询存储异常和返回错误使用同一证据机制。
- 原始错误正文不进入普通日志、Task 私有 JSON 或客户响应。复用 TaskRequestEvidence 索引、
  私有加密对象、管理员脱敏预览、Root 原始对象下载和访问审计，不新增证据数据库或公共状态。
- 按 `request_id` 或 `task_id` 在既有 `/api/task_request_evidence` 管理接口查询；索引类别
  为 `image_error`。对象包含响应头、业务正文、底层错误、Content-Type 与完整性标记。
  Authorization、Cookie、API Key 等凭据按既有规则替换；正文不是凭据未处理的字节级镜像。

### 2.4 不阻挡原流程的取舍

热路径仅进行有界内存复制与入队，不同步访问证据数据库、磁盘或加密存储，不新增等待证据
成功的条件；HTTP 状态、响应内容、SSE Flush、预扣与结算仍由原逻辑决定。

此要求意味着证据采集是尽力保存，不能承诺在存储故障、进程崩溃或容量耗尽时仍绝对零丢失：

- 不采样错误类型；内存预留和待写队列共同限制为 8 个采集上下文，满时只增加 dropped。
- 复用 `TASK_REQUEST_EVIDENCE_MAX_RESPONSE_BYTES`，默认每上下文 32 MiB，关联交换共享预算。
  超限、上游读取中断或原流程提前停止读取时明确标记 incomplete/truncated，不伪造完整正文。
- 不为了采集而主动继续读取原流程已经放弃的响应，也不延长供应商调用或客户端等待时间。
- 结构化正文无法安全脱敏时不保存该正文，保留 unavailable 事件；不得把潜在凭据写入证据。
- 既有健康接口增加 `image_evidence`，独立报告 active、queued、accepted、written、skipped、
  failed、dropped、truncated。skipped 表示成功且无错误的调用，不计为已写错误证据。
- 继续复用现有证据开关、目录、密钥和保留期；线上线下没有不同采集分支。默认启用，但显式关闭
  仍生效。稳定密钥和多节点共享证据存储是部署条件，不能以临时进程密钥保证重启可读。

## 3. 优化方案与验证

### 3.1 最小入侵说明

新增主体放在 `service/image_error_evidence*.go`、`middleware/image_error_evidence.go` 和
`relay/image_result_error.go`。原生 `router/relay-router.go` 仅挂一行图片限定中间件；
`relay/channel/api_request.go` 在 HTTP 调用后接一行观察函数，非图片上下文直接返回。
图片中转的直接 HTTP 调用各增加一行观察；没有修改 Provider 请求参数、认证和协议转换。
其它接线集中在已有本地图片执行、查询、存储与诊断文件；S3/Azure Blob 仅在原错误转换前
旁路观察响应/异常，非图片上下文无效。不重构原生同步/SSE 或账本。

### 3.2 自动化验证

- 完整相关包测试通过：service、model、controller、relay、openai、asyncimage、moxingimage、
  middleware、clienterrlog、logger。
- 定向竞态检查通过：图片错误证据、SSE/参数错误的响应保持、Task 交付失败、查询权限与签名。
- 模拟生成 200 / 图片下载 403：保留生成状态和请求编号，下载状态独立记录；恢复后首次错误码、
  钱包/令牌预扣不变，Provider POST 恰好一次。
- 大于 32 KiB 的合成错误正文、SSE 错误、底层连接错误可读取；虚构凭据不进入对象，磁盘内容为密文。
- 原生同步 400 与 Task 的 202 → 失败端到端测试：保留上游错误正文且脱敏，Provider 只调用一次，
  钱包与令牌均按原规则全额退回。
- 阻塞/失败证据存储不阻挡业务；容量耗尽、正文超限及不可安全脱敏均有可观察标记。
- 普通生产构建不依赖 DNS 对照覆盖；测试用 DNS 覆盖文件只位于临时目录，不进入仓库。
