# 任务失败原因与请求证据展示修复方案

## 1. 问题与目标

Vidu 视频任务在创建受理后因输入审核失败进入失败终态，任务详情没有显示失败说明，错误日志仅显示
`task_failed`，并重复展示四次“此事件未记录正文”。管理员无法从错误日志直接确认业务错误及当次请求。

本方案补齐三个环节：Vidu 失败响应归一化、任务失败事件的安全错误码与说明、错误日志关联已有请求证据。
复用现有 Task、错误事件和证据接口，不新增日志体系或正文副本。方案已于 2026-09-28 按 §3 实现，本地
自动化回归通过（见 §4.3 实施记录）；历史任务、事件与资金保持原记录，未执行新的 Provider 生成请求，
页面、真实 Provider 与线上验收仍未进行。

## 2. 当前实际情况

### 2.1 已验证事实

2026-09-28 本地数据库、应用日志和代码只读核查表明：

- 样本创建请求成功返回 HTTP 200 并取得上游任务 ID；约五秒后轮询得到业务状态 `failed`。
- 保存的规范化错误包含 `error.code = AuditSubmitIllegal`，没有 `error.message`；Task 的
  `FailReason` 为空。该失败任务已经全额退款并完成资金结算。
- 对应错误事件类型为 `task_failure`，分类为 `task_failed`，阶段为 `task_lifecycle`；
  `public_code` 为空，`detail` 只有 `platform`，没有 `fail_reason` 或 `http_exchange`。
- 已存在关联请求证据索引，客户请求、上游请求、创建响应、客户响应和失败轮询响应均有对象引用，
  标记写入完整且未过期。索引状态不等于当前对象可读取；本轮未通过受保护接口验收正文解密与读取。
- 错误日志详情仅展示错误事件自身的 `http_exchange`，没有关联请求证据；任务详情和消费日志详情
  已有可复用的 `TaskEvidence` 入口。

本文仅保存脱敏事实摘要，不记录真实任务 ID、完整请求 ID、上游任务 ID、请求正文、密钥或签名 URL。

### 2.2 外部依据与未确认项

[Vidu 官方错误码文档](https://platform.vidu.cn/docs/error-code)将 `AuditSubmitIllegal` 定义为
“输入没有通过安全审核”。核查日期为 2026-09-28。现有错误码不能说明具体触发审核的文本或素材，
不得推断具体违规类别。

尚未验证：修复后的端到端行为、历史证据当前可读性、部署后界面及真实 Provider 验收。

### 2.3 代码根因

| 环节 | 当前实现 | 缺口 |
| --- | --- | --- |
| Vidu 响应归一化 | `relay/channel/task/seedance/vidu.go` 保留错误码和消息 | 只有错误码时没有补充可读说明 |
| 任务结果解析 | `relay/channel/task/seedance/adaptor.go` 将 `error.message` 赋给失败原因 | 错误码不能形成 `FailReason` |
| 公开失败投影 | `model/task_public_error.go` 以持久化 `FailReason` 为消息权威 | Data 中的码仅在同为失败且消息一致时参与投影；只补一侧会继续丢码 |
| 错误事件生成 | `model/task_error_event.go` 读取 `FailReason` | 未写入具体 `public_code`，空原因不进入 detail |
| 错误日志正文 | `error-log-details-dialog.tsx` 调用 `ErrorLogHTTPExchange` | 未关联已有证据，无快照时固定出现四个空正文区块 |

异步失败事件没有对应的客户 HTTP 响应，`Status = 0` 是正确表达；不能把此前创建请求的 200 或
轮询传输层的 200 当成失败事件的客户状态。用户名和令牌名称为空属于独立的身份信息传递缺口，
不作为此次原因与证据展示修复的前置条件。

## 3. 优化方案

### 3.1 在 Vidu 专属归一化边界补齐说明

在 `normalizeViduTaskResponse` 已验证任务身份和可信失败状态后规范化错误，具体规则为：

| 上游错误内容 | 处理方式 |
| --- | --- |
| 有有效 message | 保留业务说明，经现有公开错误过滤脱敏 |
| 无 message，code 为已确认业务码 | 按精确错误码映射固定说明 |
| 无 message，code 未登记但满足安全代码规则 | 保留安全码，使用“视频生成失败，上游未提供详细原因”的通用说明 |
| code 不安全或没有可用错误字段 | 使用通用安全码和说明，不输出原始诊断 |

首个有据映射为 `AuditSubmitIllegal` → 输入内容未通过安全审核。映射由代码维护，不根据错误码
片段、模型名或消息关键词猜测业务含义；不为未验证的错误码编造原因。对过期状态继续遵守已有过期
合同，不因存在错误字段改变终态语义。

规范化后的 `error.message` 必须通过现有解析路径形成相同的持久化 `FailReason`，从而继续满足
`PublicVideoFailure()` 的消息一致性检查。只补前端文案或单独补 `FailReason` 都不是完整修复。
不放宽该检查，不让旧 Data 的错误码覆盖后来形成的另一种失败原因。

业务错误码保持稳定，界面可读文案提供中英文；上游有详细说明时保留脱敏后的细节。
Provider 原始响应仍由既有受保护证据保存，普通 Task 和错误事件只保留安全投影。

### 3.2 错误事件复用统一公开失败投影

调整 `submitTaskFailureEvent`，对适用的视频失败任务复用 `PublicVideoFailure()`：

- `reason` 继续为 `task_failed`，用于分类和筛选；
- `public_code` 写入安全业务错误码；
- `detail.fail_reason` 写入同一公开投影的可读说明，沿用脱敏和长度约束；
- 非视频任务、取消和过期等状态继续遵循各自既有合同，不强行套用 Vidu 解释。

事件仍只在正式失败终态成功提交后登记，保留现有 CAS 防重机制。日志生成不决定任务状态、退款、
重发或换渠道，不因诊断失败回滚已提交的任务与资金事实。

新事件的目标展示为：

```text
事件类型：任务失败
错误码：AuditSubmitIllegal
失败原因：输入内容未通过安全审核
阶段：任务执行
客户 HTTP 状态：无
```

错误事件只引用规范化的码和说明，不再创建另一套上游响应解析器。

### 3.3 错误日志复用请求证据入口

在 `web/src/features/usage-logs/error/components/error-log-details-dialog.tsx` 接入现有
`web/src/features/usage-logs/components/task-evidence.tsx`，有任务 ID 时仅按任务 ID 关联，无任务 ID 时
才按请求 ID 关联，展开时才加载。不能将两个 ID 作为交集条件，否则会漏掉没有请求 ID 的历史轮询补建索引。
沿用已有列表、详情和对象接口，不在错误日志列表查询时解密正文，不向 `error_events` 复制正文。

展示规则：

1. 事件已有 HTTP 正文快照时，继续展示其实际快照及采集状态。
2. 对没有快照且具备关联 ID 的任务失败事件，显示“请求证据”入口，去掉四个重复的空正文区块；
   尚未接入采集的 Midjourney 不显示入口。错误码、失败原因使用中英文标签独立成行，避免在附加信息中重复。
3. 证据按客户请求、上游请求、创建响应、客户响应和任务轮询区分阶段；创建返回 200 与轮询返回
   `failed` 可以同时成立，不能混成一个响应。
4. 保留“未记录”“已过期”“读取失败”等不同状态；索引存在但对象不可读时不能伪装为未记录。
5. 沿用管理员脱敏预览、Root 原始对象下载及访问审计，后端权限校验仍是权威。
6. 新增或调整界面文案只要求简体中文与英文，不扩展其他语言范围。

### 3.4 历史日志处理

已有请求证据可直接通过关联入口查询，无需修改旧事件或重新请求 Provider。当前对象和解密密钥是否
可用，以受保护证据接口的实际结果为准。

新事件生成逻辑不会自动补齐旧事件的 `public_code` 或 `fail_reason`。旧事件摘要保持原记录，管理员
通过关联证据查看历史原因；不增加历史 decoder、不在读取时静默改写 Task 或错误日志，不以当前渠道
配置重建历史请求，也不重新执行已结算任务。

### 3.5 修改边界与实施顺序

| 顺序 | 预计修改位置 | 目的 |
| --- | --- | --- |
| 1 | Vidu 专属归一化文件及专项测试 | 补齐 code-only 失败说明，保持 Data 与 FailReason 一致 |
| 2 | 任务错误事件文件及事件测试 | 保留统一安全业务码与失败说明 |
| 3 | 错误日志详情、证据入口及相关前端测试 | 关联已有证据，消除重复空状态 |
| 4 | 必要中英文文案、当前事实文档及验证记录 | 记录完成状态和实际验收边界 |

优先限定在本地 Link、错误事件和诊断界面扩展文件。预计不需要修改通用轮询、资金事务或 NEWAPI
原生 Provider 实现，不新增数据库列或迁移。实施时若确需修改原生文件，必须先说明不可替代性、
最小接线点及未来同步冲突面；不得借机重构。

实现完成后按实际行为更新错误投影与请求证据的当前事实文档；本文的收敛归档另按目录治理执行。

## 4. 验证方式与验收标准

### 4.1 后端合同回归

- 可信 Vidu 失败只有 `AuditSubmitIllegal` 时，归一化 Data、持久化 FailReason、公开 API 和新错误
  事件的码与说明一致。
- 已有有效说明不被固定文案覆盖；未知码不被误判为审核失败；不安全码、凭据和 URL 不进入公开输出。
- 旧 Data 与新失败原因冲突时，仍不能借旧 Data 输出错误码；成功、过期、合同违例和非视频任务保持
  既有合同。
- 以持久化任务和正式终态提交路径验证事件；重复观察和 CAS 失败不重复生成失败事件，退款恰好一次。
- 上游业务失败与 HTTP 传输状态分别保留，日志状态 0 不被创建或轮询的 HTTP 200 覆盖。

采用确定性输入和精确输出；新增或重写 Go 测试使用 `require` / `assert`，显式初始化数据库及全局状态。

### 4.2 前端与权限回归

- 无快照的任务失败事件显示请求证据入口，不出现四个重复空区块；已有 HTTP 快照仍可查看。
- 未展开不读取证据；展开后按任务／请求关联，并能区分创建和失败轮询事件。
- 覆盖加载失败、无记录、正文过期和对象读取失败，不误报为无正文。
- 管理员只使用受保护脱敏预览，Root 下载沿用既有鉴权和访问审计。
- 验证中英文错误说明及空状态；新增测试验证实际交互与数据展示，不锁定组件内部实现。

### 4.3 执行检查

实施时先运行 Vidu、任务错误投影、事件及必要资金边界的专项回归，再按改动风险扩展。
前端使用 Bun 执行相关测试、类型与必要构建检查。文档修改执行 `task docs:check` 和 `task ai:check`；
若变更公开 API 文档，追加 `cd web && bun run docs:validate`。若实际触及 `relaykit/` 或公共 API，
追加 `cd relaykit && GOWORK=off go build ./...`。

## 5. 风险与剩余事项

- 失败说明复用公开消息的脱敏与 512 字节正文限长（截断时追加省略号），保留空格和合法下划线；
  其他错误日志标识符继续原有净化方式。

  直接使用已校验结果，并在后续响应没有 ID 时清空旧值。创建任务关联时与 Task 冻结值保持一致。

实际 Provider 与部署后页面验收仍待完成，本地模拟 Provider 不代表生产已验收。

### 持续边界

- 错误说明映射必须有 Provider 文档或已验证合同依据；错误码本身不证明具体触发内容。
- 只修事件生产者不能恢复旧事件摘要，历史诊断依靠既有证据；正文丢失或密钥不可用时明确报告失败。
- 请求证据是诊断来源，不成为任务状态和资金的第二事实源，不承担重新发送许可。
- 用户名、令牌名称缺失留作独立问题，不为补齐展示而猜测请求时身份快照。
- 自动化本地回归已完成；页面验收、部署及真实 Provider 与资金验收必须另行记录，不能以本地测试代替。
