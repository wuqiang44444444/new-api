# 客户合同真实文本调用验收

## 问题与目标

完成全量复审问题修复后，按用户对本地环境的明确授权，使用真实文本模型验证合同路由、停用行为、计费和错误留痕。测试通过正式 HTTP 接口执行，不直接写数据库，不使用模拟 Provider。

## 当前实际情况

- 验收时间：2026-09-19 02:31—02:32（Asia/Shanghai）。
- 环境：本地后端 `http://127.0.0.1:3501`，SQLite；运行中的后端包含本轮 WARN 隔离和合同来源批量查询实现。
- 用户：`admin`（用户 ID 1）；现有 Key ID 146，合同 ID 1（`Legacy contract`）。不记录认证凭据。
- 合同初始启用、版本 3，共 3 条规则；经来源可用性和用户分组权限过滤，实际可用文本模型为 `gpt-5.6-sol`。
- Provider 调用：经本地已配置的渠道 50（合同启用）和渠道 14（合同停用）实际发送；北向使用 OpenAI Chat Completions。此处以渠道 ID 标识本次上游配置，不推断上游厂商身份、不保存连接或原始响应。
- 请求形状：`POST /v1/chat/completions`，`model=gpt-5.6-sol`，单条文本消息要求仅回复 `OK`，`max_completion_tokens=128`，`stream=false`。
- 合同外拒绝使用 `gpt-5.6-luna`；没有调用视频、素材或异步任务接口。

## 优化方案与验收方式

复用现有用户、Key 与合同，依次验证启用、临时停用、恢复启用；通过带版本校验的正式合同管理接口修改状态，恢复原名称与全部规则。交叉核对接口响应、消费日志、错误事件、WARN 日志、用户余额和 Key 累计用量。凭据仅在请求进程内使用，不落入脚本、记录或输出。
