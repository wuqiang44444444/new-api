# 渠道 93 与 99 图片生成及计费问题分析

## 问题与目标

管理员测试客户模型 `nano-banana-2` 时，渠道 93 报计费错误，渠道 99 的截图报上游 HTTP 500 与
“只支持 Imagen”。本次结合截图、本地配置、实现与长期回归，记录修复范围和未完成目标。

用户已明确：

- 标准图片入口与原生 Gemini 共用客户模型及管理员配置的 Token 价格。
- 管理员配置是收费方式的权威；渠道类型负责协议适配，不替管理员决定收费方式。
- 适配器提供可验证用量，结算执行管理员配置；不得伪造 Token 或用修改价格掩盖适配缺口。

标准图片入口为 `POST /v1/images/generations`；Gemini 原生入口使用
`/v1beta/models/{model}:generateContent` 等已配置版本路径。Gemini 渠道可以接收标准图片请求并转换，
因此“渠道类型”和“客户请求端点”需要分别记录。

**当前结论：渠道 99 的后台测试尺寸缺陷及错误展示已修复；用户随后授权渠道 93 改用独立模型名
和按张价格，取代此前渠道 93 与 99 共用 Token 价格的目标。** 独立名称、价格配置及在线实施状态见
本文后半部分。前次 `tokenai.page` 测试针对远端，不能验证用户重启的本机程序；环境纠正及
本机验收以文末最新记录为准。已使用本机保存的渠道连接与凭据直连验证三个 Provider 模型均成功生图；三个客户模型也已通过
本机标准图片入口全部返回 HTTP 200 和 1 张图片，消费记录落库。
截图 Imagen 500 的历史事件归因及供应商账单核对仍需独立证据，不将本机成功等同于远端部署完成。

### 2. 修复前本地快照及共享价格影响

下表仅描述前序本地 SQLite 检查结果；在线配置及后续变更以文末实施状态为准。

| 项目 | 渠道 93 | 渠道 99 |
| --- | --- | --- |
| 渠道类型 | `ChannelTypeAsyncImage`，63 | `ChannelTypeGemini`，24 |
| 南向协议 | `funcloud_aigc_v2` | Gemini |
| 客户模型 | `nano-banana-2-lite`、`nano-banana-2` | `nano-banana-2` |
| 模型映射 | 无映射，原名发送 | `nano-banana-2` → `gemini-3.1-flash-image` |
| 请求体透传 | 关闭 | 关闭 |
| 检查时状态 | 已启用 | 已启用 |

`nano-banana-2` 使用 `tiered_expr`，依赖输入 Token `p` 与图片输出 Token `img_o`；两条渠道共享
该客户模型的计费配置。渠道 93 的 lite 模型也依赖这两个变量，必须一并处理。本文不复制管理员费率。

**把 `nano-banana-2` 改成按张计费会同时影响渠道 99。** 仅补 `ModelPrice` 而保留 `tiered_expr`
模式，仍会进入表达式校验，不能解决渠道 93 的拒绝。前序代码修复保留共享价格；后续用户明确授权
拆分渠道 93 的客户模型名后，采用本文独立定价配置。该决定没有补齐或伪造 FunCloud Token 用量。

### 3. 渠道 93：当前用量适配不足，保留发送前拒绝

```text
标准图片请求 → 渠道 93 → 解析 funcloud_aigc_v2 合同
→ 读取管理员 Token 表达式 → 当前图片中转计费校验拒绝 → 未发送上游
```

[计费校验](../../relay/helper/image_relay_billing.go)遇到依赖用量的表达式即拒绝。原因不是价格缺失。
[FunCloud 同步适配器](../../relay/channel/asyncimage/adaptor.go)的 `apiEnvelope` 解析任务 ID、
状态与结果，同步图片响应返回空 `dto.Usage`；[异步适配器](../../relay/channel/asyncimage/headless.go)
也没有向后续结算提供表达式所需 Token。前序文档调查未发现本协议已验证的所需用量字段，当前没有
依据补齐 `p` 与 `img_o`，更不能通过删除限制、猜测 Token 或使用预扣金额冒充实际结算。

限制可以防止错误结算，但它仍然意味着用户的 Token 成功调用目标未实现。“安全拒绝已验证”和
“成功计费已交付”是两个验收项，不能互相替代。当前代码按图片中转类型统一拒绝用量表达式；
将来开放某协议必须同时完成可信用量接线与按所需事实校验，不能只增加渠道白名单。

本轮将公共错误修正为：

```text
the current image adapter cannot supply the verified usage required by this billing expression
```

它描述当前适配能力，不再断言所有 Provider 都不返回 usage，不包含上游协议身份，也不要求管理员
改变收费方式。仍复用 `model_price_error`，没有新增错误码、协议推断或 capability 注册表。

这一措辞适用于公共校验的实际范围：[Moxing 结果解析](../../relay/channel/moxingimage/result.go)
已读取 `output_tokens` 与 `input_images`，所以“所有图片协议都没有用量”不成立。但现有解析不等于
已提供 `PromptTokens` 与 `CompletionTokenDetails.ImageTokens`，也不能未经语义验证把总输出
Token 当成 `img_o`。本轮不放开 Moxing、不伪造用量映射。

### 4. 渠道 99：修复后台测试尺寸，保留真实转换链回归

修复前，客户别名 `nano-banana-2` 使测试请求取到 `size="1K"`，Gemini／Vertex 分支直接返回，
随后映射为 `gemini-3.1-flash-image` 并被 Gemini 标准图片合同拒绝，尚未发送上游。
北向尺寸 `1K` 与南向 `imageConfig.imageSize="1K"` 不是同一合同。

[测试请求构造](../../controller/channel_test_image_profile.go)的 Gemini／Vertex 分支现在显式设置
`1024x1024`。修改限于本地图片扩展文件，不改变客户请求、原生聊天、FunCloud 或 Moxing 的转换。

[长期回归](../../controller/channel_test_image_profile_test.go)覆盖：

- Gemini 普通／lite 客户别名、直接上游模型名，以及 Vertex 客户别名。
- 默认测试端点 → 请求构造 → 实际 `ModelMappedHelper` → 实际适配器转换 → 南向路径。
- 映射后客户计费模型身份不变，合法尺寸转换为 `TEXT`、`IMAGE` 模态的 `generateContent` 请求。
- 显式图片测试端点下，映射到 Imagen 的别名仍转换成 Imagen 请求并走 `predict`。
- 既有测试继续验证按所选图片中转协议生成测试请求，不把 Gemini 的尺寸规则扩散到其它协议。

不再把只断言尺寸字符串或临时 overlay 测试称为完整跨模块回归。

### 5. 截图 Imagen 500 仍需同一请求取证

截图有 HTTP 500、`only imagen models are supported`、`convert_request_failed` 的上游响应包装；
本地尺寸错误发生在发送前。当前证据未把二者关联为同一事件，不能把尺寸修复称为截图 500 根因修复。

需按同一请求核对运行实例与构建版本、当时渠道类型及映射、手选端点、实际南向路径、请求结构摘要
和脱敏错误码。上游中转版本、部署版本或实际路径差异均为待验证假设，没有证据排列优先级。

手选 Gemini 原生端点的后台测试只发送 `hi`，可以验证普通文本连通性，不能验收图片能力；
这也不能证明它就是 Imagen 500 的原因。图片验收需明确生图请求与图片响应，不能以文本返回成功代替。

### 2K／4K 分档表达式草案：需要先开放请求合同

[当前适配器](../../relay/channel/asyncimage/adaptor.go)的 `validateModelFields` 明确拒绝普通版
非 1K 分辨率；lite 拒绝任何显式尺寸／resolution。价格页面证明有报价，不能证明当前代码已支持。
因此不能只改一个价格就宣称 2K、4K 已能请求，本轮文档与配置工作不修改协议支持范围。

为后续开放规格准备的普通版表达式如下，适用于渠道 93 的 `size`／`extra_fields.resolution` 档位
合同，**尚不是可直接用于共享 Gemini 原生入口的全规格配置**。两字段同时提供时仍须相同；非法档位
必须由请求合同拒绝。该草案不负责替代字段校验，也不把错误档位降级成 1K。

```text
v1:(param("size") == "4K" || param("extra_fields.resolution") == "4K")
  ? tier("4K", 0.1512 * 1000000)
  : (param("size") == "2K" || param("extra_fields.resolution") == "2K")
    ? tier("2K", 0.1008 * 1000000)
    : tier("1K", 0.0672 * 1000000)
```

若使用该草案，模式为 `tiered_expr`，表达式填写到 `billing_setting.billing_expr`；这与上面的
固定价方案是替代关系，不同时启用。图片表达式沿用 `exprOutput / 1000000` 换算，所以按张美元
常数必须乘 `1000000`；不能直接填 `tier("1K", 0.0672)`，也不能套用视频 Task 的 USD 表达式单位。
它不引用 `p`、`img_o` 或 `u()`，无需虚构 Token。lite 当前仅有固定一档，不需要分档表达式。

后续开放 2K／4K 时须同时验证：请求校验与南向分辨率转换、公开规格投影、请求探针冻结、按上述
价格预扣／结算、共享模型或独立模型的明确计价范围，以及真实 Provider 图片与账单。该工作未由
“报价和配置已编写”替代，原截图 Imagen 500 的取证也仍是独立事项。

#### 渠道 93：计价副本意外修改原请求，后台测试映射被撤销

已在当前工作区以两个真实客户别名稳定复现同一错误：

1. 管理测试 `controller/channel-test.go` 先执行 `ModelMappedHelper`，把请求模型从
   `nano-banana-2-image` 映射为 `nano-banana-2`，再执行 `ModelPriceHelper`。
2. 本地扩展 `relay/helper/image_relay_billing.go` 的 `prepareImageRelayBilling` 使用
   `mappedInfo := *info`。这只复制结构体，`mappedInfo.Request` 仍然指向调用方原请求。
3. 随后的 `mappedInfo.InitChannelMeta(c)` 会调用 `info.Request.SetModelName(info.OriginModelName)`
   （`relay/common/relay_info.go`），通过共享指针把原请求模型重置为客户别名。
4. 计价内部的 `mapped` 局部请求随后重新映射，所以价格检查成功；但调用方原请求仍是
   `nano-banana-2-image`。后续适配器按 Provider 模型合同检查它，便报 `unsupported image relay model`。
   Lite 同理。此时映射元信息仍是 Provider 模型，而请求正文却已变回别名，两者不一致。

这是代码副作用，不是管理员映射填错或按张单价失效；继续改价格、把客户别名加入 Provider 注册表，
或者在转换前再次补做映射，都没有消除副作用根因。

最小修复位于本地扩展文件，在初始化计价副本之前，绑定独立请求副本：

```go

mappedInfo := *info
mappedInfo.Request = &mapped
mappedInfo.InitChannelMeta(c)
```

不修改原生 `InitChannelMeta` 的合法重置行为，不改管理员价格语义，不需要修改渠道类型或名称。
分析阶段先使用临时 Go 编译覆盖文件验证候选修复；用户随后授权完整修复后，已正式写入本地扩展
