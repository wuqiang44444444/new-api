## 1. 问题与目标

这里有两个不同问题：

1. 原渠道上游是否接受附带该请求头的普通图片请求：本次直接调用现有渠道连接验证，不创建平台 Task。
2. 网关是否因旧“三类渠道白名单”本地返回 400：必须通过网关验证。之前的网关实测可证明已测样本没有该 400，但带 Prefer 的成功样本使用了新增 Task 机制。

### 2.7 Token 对应与计费边界

- 表格中的 Token 是响应 usage 的输入/输出/总量；网关异步行的 Token 来自隔离数据库中的任务归一 usage。异步任务查询响应本身没有返回 usage，不写成客户响应字段。
- 原渠道直连使用渠道现有认证，没有使用网关客户 API Token，不产生网关 Task、客户预扣或消费日志。102 未返回 usage，Provider 是否收费未知；不填零成本。
- 前一轮网关使用隔离测试 Key `image-prefer-native-20260908`（副本 token_id=1，user_id=1）；首轮对应 `image-final-live-20260908`。仅说明认证映射，不展示密钥，也不与原数据库同号记录混淆。
- 首轮账本：结算 1,005,260 quota、待核实占用 10,420 quota；来源及完整逐项 Token、参数、图片见原报告。这是测试客户额度，不是供应商账单。

### 2.8 代码证据与结论限制

当前 [模式选择](../../service/image_execution_mode.go) 已明确纳入 OpenAI/Azure：非流式且有效的 Prefer 请求选择异步 Task。旧“只支持三类渠道”的描述不再准确。仅凭此前六项 202 成功，不能宣称“带 Prefer 仍按普通同步处理”。

原生 [请求头设置](../../relay/channel/api_request.go) 默认拷贝 Content-Type、Accept，不自动转发 Prefer。直连测试将 Prefer 实际发送给上游，与网关默认转发行为不同；它回答的是原渠道上游头部兼容问题。

### 2.9 403 后续诊断：测试客户端 User-Agent 触发 Cloudflare 1010

2026-09-09 使用渠道 102 的同一连接与认证，只读请求 `/v1/models`；不创建图片、不经过网关、不创建 Task。结果：

| 客户端 User-Agent | Prefer | HTTP | 可公开响应摘要 |
| --- | --- | --- | --- |
| Python urllib 默认值 | 无 | 403 | Server=cloudflare；非 JSON，17 字节；错误码 1010 |
| Go-http-client/1.1（网关默认值） | 无 | 200 | application/json，合法模型列表 |
| Go-http-client/1.1（网关默认值） | respond-async | 200 | application/json，合法模型列表 |

第一、第二项使用同一 Python HTTP 客户端，只改变 User-Agent；第三项再增加 Prefer。无代理、凭据及 URL 变化。原数据库与前两次测试副本的渠道 102 地址、凭据、模型映射、参数/请求头覆盖及 setting 均一致，未发现这些配置发生变化。

Cloudflare [1010 官方说明](https://developers.cloudflare.com/support/troubleshooting/http-status-codes/cloudflare-1xxx-errors/error-1010/)将该码定义为按客户端浏览器签名拒绝访问；[Browser Integrity Check](https://developers.cloudflare.com/waf/tools/browser-integrity-check/)也明确检查 User-Agent 等请求头。原始拒绝体未写入报告，错误码通过 17 字节响应的 SHA-256 精确匹配确认。

因此，本次只读对照证实了一个与 Prefer 无关的客户端 User-Agent 拦截因素。它高度解释前次 Python 直连四项快速 403，也与此前 Go 网关同步曾成功相符。前四项未留存原始拒绝体，不能逐项追溯确认为 1010；本次只读 200 也不等于生成/编辑已重新出图。

测试方法存在偏差：前次直连只对齐了渠道地址、认证与业务参数，没有对齐网关默认 User-Agent；脚本又把非 JSON 响应统一压成泛化错误，丢失了诊断信息。四次 403 应归为客户端访问被拦截样本，不用于判定模型/Prefer 不兼容。后续图片复测应使用与网关一致的 HTTP 客户端/请求头，并只保留脱敏错误码、来源标识和响应摘要；不需要为此修改网关业务代码或渠道配置。

## 3. 优化方案

1. Azure 15 原渠道普通生成/编辑的 Prefer 对照已获得成功证据；无需因该请求头对该样本认定上游不支持。
2. OpenAI 兼容 102 的 403 已在只读对照中定位到客户端 User-Agent 拦截；下一次图片验证应匹配网关实际请求特征，重新建立有头/无头生成、编辑对照。此次诊断没有新增图片 POST，不覆盖原四次结果。暂不改变凭据或渠道配置，不重发历史结果未知的请求。
3. 如果产品要求“当前网关 OpenAI/Azure 普通非流式请求带 Prefer，仍然同步返回且完全不进入新增 Task”，这是与当前分流实现不同的行为目标，需要另行明确并调整策略；本次测试不通过隐藏开关或临时改代码制造通过结果。
4. 文档整合保留各批次来源，不更新生产验收状态，不将此次直连测试作为所有渠道、所有请求参数或异步查询均可用的证明。
