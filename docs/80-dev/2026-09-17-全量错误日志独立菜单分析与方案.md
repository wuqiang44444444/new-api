# 全量错误日志独立菜单分析与方案

> **当前权威范围（2026-09-17 用户收窄，优先于正文全部建议）**：本站是 token 网关，
> 业务目标是客户报错时快速定位。实施只覆盖 **API 调用错误**（relay/asset 已鉴权请求的
> 最终 4xx/5xx）；页面错误、鉴权失败、渠道测试、业务 200 失败、SSE 中断、异步终态、
> Nginx 入口均不在范围。第一轮已按此范围实现并通过本地验证（见文末「实施记录」）；
> 正文保留的全量分析作为后续潜在扩展的建议，不代表当前范围或已确认排期。

## 问题与目标

### 1. 需求与结论

用户提出：新增一个菜单，专门记录和查询所有错误使用日志，包括全部 4xx。
本方案最初以运营人员能够查全错误、定位原因、找到请求 ID、准确判断渠道问题为目标。

为此建议过新增独立的“错误日志”菜单，并建设统一错误采集、持久化与查询能力；
只增加菜单、筛选既有 `type=5`，或者开启 `ERROR_LOG_ENABLED`，对全量目标而言均不足够。

原始分析按上述全量目标书写。实施确认时用户将目标收窄为仅 API 调用错误（见顶部声明），
第一轮已按收窄范围实现：`error_events` 表、`GET /api/error_log/`、「错误日志」菜单。
正文中的覆盖清单、字段表、阶段划分是全量建议，与已实现范围的差异以文末实施记录为准；
已实现能力未通过生产验收，不表述为生产已发布。

### 2. 触发背景

本次讨论源于对 2026-09-16 本地渠道记录的分析：Funcloud 正向 Claude 渠道 #38 有 11 次
HTTP 500 健康检查失败，其中 4 次诊断指向账号不允许访问 Bedrock 模型，7 次仅说明 Bedrock
无法处理请求。对应错误及相邻测试日志没有保存可用的网关或上游请求 ID，无法补齐关联信息。
本地数据库当时未发现 `type=5` 错误日志。

这些是本地数据观察，不等同于线上全量业务失败统计，也不能证明线上进程的错误日志开关实际取值。
当前仓库代码默认关闭该开关，仓库示例 Compose 显式开启；用户提供的实际部署片段未显式配置它。
镜像内置环境变量、实际运行环境和线上镜像与工作区的一致性均未核验。

### 3. 业务上必须回答的问题

1. 请求是否到达网关？
2. 在鉴权、参数校验、渠道选择、上游调用、结果交付的哪个环节失败？
3. 原因属于客户、平台、上游，还是暂时不能判断？
4. 网关请求 ID、上游请求 ID、任务 ID 分别是什么？
5. 是否发生重试，客户最终成功还是失败？
6. 对异步任务，是否已受理、结果是否明确、资金状态是什么？

记录对象应为业务过程中发生的错误事件，不能只依据最终 HTTP 状态判断。
“覆盖所有错误类型”“每个错误都产生记录”和“任何故障下记录绝不丢失”须分别定义与验收。

## 当前实际情况

### 1. 审计范围与验证边界

已核对当前工作区的请求入口、鉴权、渠道测试、原生转发、流式状态、异步任务诊断、日志存储和菜单。
已读取仓库目录规范、硬约束、前端约定及相关异步架构事实。
工作区存在其他任务未提交的账单、导出、使用日志页面等改动；本方案没有修改这些实现。

分析期间运行 `GOPROXY=off go test ./clienterrlog`，结果通过。
该结果只验证当前“已鉴权 4xx 后台诊断”的既有合同，不代表本文新范围已实现。
未执行真实 Provider、外部数据库、生产流量或线上镜像验收。

本方案扩展了此前 [系统 4xx 日志分析](2026-09-16-系统4xx日志缺失问题分析与修复方案.md)
的业务目标。该方案及其现有实现只覆盖已通过正式鉴权的最终 4xx，不应被误描述为全量错误中心。
本文件也不替代当前 [异步任务与计费事实架构](../20-architecture/账单计费-异步任务与计费事实架构.md)
或 [图片服务与异步 Provider 适配架构](../20-architecture/图片服务与异步Provider适配架构.md)。

### 2. 与新目标的差距

下列发现均有当前代码证据，置信度高。其中部分行为符合原来的窄范围设计，不能直接认定违反旧需求；
但对本次“所有错误可查询”目标，必须补齐。

| 优先级 | 类型与已确认事实 | 影响 | 最小修改方向 | 验证方式 |
| --- | --- | --- | --- | --- |
| 高 | 覆盖缺口：通用错误入库受开关和“不记录”标记控制；部分额度不足明确不记录 | 开启开关后仍漏记 | 新全量采集不沿用旧日志的排除条件，不改变旧标记控制的其他业务行为 | 额度不足、余额不足、请求取消等分支仍有可查询事件 |
| 高 | 覆盖缺口：统一 4xx 机制要求鉴权通过，且只写后台日志 | 无效 Key、鉴权拒绝不能完整查询，已记录 4xx 也不进入使用日志数据库 | 鉴权前建立上下文，失败时保留事件，新增持久化出口 | 未认证与已认证请求均覆盖，身份归属不串号 |
| 高 | 记录路径不一致：渠道测试失败通常提前返回，成功才写消费日志 | 成功可查、失败不可查 | 手工和定时测试统一记录结果 | 不开启自动禁用也能查到测试失败与测试 ID |
| 高 | 错误语义缺口：部分接口以 HTTP 200 返回业务失败 | 单纯拦截 4xx/5xx 仍漏记 | 正式业务失败出口显式标记 | `success=false` 的正式失败有事件，正常 200 不误记 |
| 高 | 生命周期缺口：流式异常与异步终态不等于创建请求 HTTP 失败 | 200/202 后出错无法完整展示 | 接入流式结束及已提交的任务状态变更边界 | 流式中断、异步失败、结果不明分别可查 |
| 中 | 交付可靠性缺口：4xx 诊断采用有界内存队列，满时丢弃 | 故障高峰可能丢掉排障证据 | 明确持久化、积压、丢失告警与恢复机制 | 队列满、写入失败、重启与恢复均可观察 |

  业务 200 失败、流式与异步终态。
- 部分补齐：交付可靠性——`persisted`/`persist_failed`/`dropped` 计数已可观察，

### 3. 上游请求 ID 的现有限制

[上游 HTTP 请求](../../relay/channel/api_request.go) 的响应接收处会保存上游请求 ID，
并在后续尝试覆盖该字段，防止最终成功日志残留前次失败 ID。
因此，新功能若需要完整失败链，必须在每次尝试结束时冻结该次 ID，不能在请求结束时只读取最后的上下文。
上游响应头取值及不同 Provider 的身份字段还需逐协议核验，不能宣称所有 Provider 都会返回请求 ID。

收窄实现采纳了折中：请求结束时读取上下文中最后一次尝试的上游请求 ID。对最终失败请求，
该值即最后一次（交付失败）尝试的上游 ID；完整失败链的逐尝试冻结未实现，列为已知限制。

## 优化方案

### 1. 全量覆盖清单

> 收窄说明：下表为原始全量目标。按当前权威范围，仅「各 4xx 与全部 5xx（应用内、
> 已鉴权 relay/asset 流量）」相关行生效并已实现；401 鉴权失败、200 业务失败、
> SSE/WS、异步、渠道测试、管理 API、Nginx、系统异常各行均范围外。

应按下表逐项验收全量目标，不以“已加全局中间件”代替完整性证明。

| 场景 | 目标 | 必须保留的区别 |
| --- | --- | --- |
| 400：JSON、参数、模型、素材不合法 | 全部记录 | 字段、阶段、稳定错误码 |
| 401：缺少、无效、过期凭据 | 全部记录 | 未认证身份不能冒认用户 |
| 403：权限、IP 限制、用户额度不足 | 全部记录 | 本地拒绝与上游拒绝 |
| 404、405：资源、路径、方法不匹配 | 全部记录 | 未匹配路由与资源不存在 |
| 408、409、413、422、429 等 | 全部记录 | 超时、冲突、大小、能力、限流的来源 |
| 其他 4xx 与全部 5xx | 全部记录 | 没有细分类也记为未分类，不能漏记 |
| DNS、TLS、连接失败、上游超时 | 全部记录 | 可能没有上游 HTTP 状态及请求 ID |
| HTTP 200 但业务明确失败 | 全部记录 | HTTP 仍显示真实 200，业务结果另记失败 |
| SSE、WebSocket 开始后异常 | 全部记录 | 上游异常、平台异常与客户端断开 |
| 异步任务失败、过期、交付失败 | 全部记录 | 原始请求、任务、渠道与错误发生时间 |
| 创建结果不明、待核实 | 记录为结果不明 | 不算确定失败，不触发自动退款 |
| 手工和定时渠道测试失败 | 全部记录 | 标记渠道测试，不混入客户请求统计 |
| 中途失败但重试后成功 | 保留失败尝试 | 客户请求最终结果仍是成功 |
| 管理 API 业务失败 | 记录并单独分类 | 不与模型调用错误混算 |

Nginx 直接产生的 413、限流 429、无法连接网关产生的 502/504，可能没有进入 Go 程序。
若目标覆盖线上入口的所有使用错误，必须接入 Nginx 错误访问记录，并设计可信关联 ID。
未完成该接入前，只能描述为“网关应用内错误覆盖”。Nginx 与应用对同一失败的两条观察不能重复算成两个请求。

数据库启动失败、后台调度器崩溃等没有具体使用请求的故障，可放在同菜单的“系统异常”分类，
但不能混入渠道业务失败率。系统异常接入范围须形成明确清单，不能由此默认扩展为采集全部操作系统日志。

### 2. 菜单、查询与详情

建议新增与使用日志、任务日志、审计日志并列的“错误日志”菜单，首期面向管理员。
默认展示所有来源，提供以下快捷筛选：

`全部 / 业务请求 / 渠道测试 / 异步任务 / 管理接口 / 入口与系统异常`

已实现差异（收窄范围）：快捷筛选为时间范围 / 模块（relay / asset）/ HTTP 状态，
高级筛选为请求 ID / 模型 / 用户 / 令牌 / 渠道 / 原因；上行的来源分类筛选未实现。
字段表中「应用」「独立上游 HTTP 状态列」「最终结果枚举」未实现——上游相关状态仅在
relay 出口的 `detail.source_status`；时间精度为秒（与既有日志表一致，耗时字段为毫秒）；
异步详情整段未实现。

| 列表字段 | 作用 |
| --- | --- |
| 发生时间 | 毫秒精度，明确时区 |
| 来源、失败阶段 | 区分业务请求、测试、鉴权、上游、交付等 |
| 用户、应用、API Key 名称 | 仅使用已确认身份，不展示凭据 |
| 客户模型、渠道 | 未选到渠道时显示未选渠，不猜测归属 |
| 客户 HTTP 状态、上游 HTTP 状态 | 两个字段分别展示，不以一个覆盖另一个 |
| 错误码、脱敏摘要 | 识别具体问题 |
| 网关请求 ID、上游请求 ID | 支持搜索和复制 |
| 最终结果 | 失败、重试后成功、客户端取消、结果不明等 |
| 耗时 | 区分请求耗时与某次上游调用耗时 |

详情按同一关联请求展示过程，例如：参数通过 → 渠道 A 返回 503 → 原生重试 → 渠道 B 成功 →
客户最终收到 200。示例仅解释现有允许重试的原生路径，不为 Link 引入跨渠道重试。

异步详情展示：创建受理 202 → 后台执行 → 上游失败 → 当前任务状态及账务状态。
账务与任务状态读取现有权威数据；错误事件只描述观察事实，不建立另一套 Task 状态或资金账本。
新页面不自行决定退款，也不默认增加一键重发或退款操作。

查询和导出接口必须校验权限，菜单隐藏不构成权限边界。
普通管理员不能通过新页面绕过现有 Root 诊断数据限制。
若以后开放客户自查，仅返回其有权访问的请求，按适用的用户与应用边界隔离，
不返回内部渠道身份或上游敏感信息；未认证请求不能仅凭客户端提交的字段归属用户。

### 3. 数据存储与唯一采集入口

建议新增独立错误事件表，复用现有日志数据库配置、鉴权、分页、表格与脱敏能力。
不直接把全部错误塞进消费日志，原因如下：

- 鉴权失败可能没有用户、API Key 或渠道。
- 一次请求可能出现多个上游错误，需要独立尝试身份。
- 异步错误可能在创建请求结束很久后发生。
- 错误事件需要独立保留期限和统计口径。
- 消费记录、退款记录及其计费语义不应因错误记录改造而改变。

新表的迁移、查询、去重和清理须支持项目要求的 SQLite、MySQL、PostgreSQL。
复用现有独立日志库配置时还须支持 ClickHouse，不能只验证本地 SQLite。
实施设计已确定（代码见 `model/error_event.go`）：表名 `error_events`；MySQL/PostgreSQL/SQLite
走 AutoMigrate，ClickHouse 走手写 MergeTree DDL（`ORDER BY (created_at, request_id)`），
与 audit_logs 同先例、刻意无 TTL；`Detail` 以预编码 JSON 字符串列存储以规避 CH Valuer
问题；当前单粒度（请求级一事件）下以 `request_id` 为事件身份，未设独立去重键。外部数据库
仅完成本地 SQLite 验证，MySQL/PostgreSQL/ClickHouse 实库迁移未验证。

建议分三类正式采集边界：

| 边界 | 职责 |
| --- | --- |
| 请求入口与结束 | 鉴权前生成关联 ID，覆盖全部最终 4xx/5xx 与异常结束 |
| 正式业务失败出口 | 提供结构化原因，覆盖业务 200 失败、上游调用失败和流式异常 |
| 后台执行与测试 | 覆盖定时测试、已提交任务终态、首次结果不明与交付异常 |

现有 `clienterrlog` 的请求上下文、安全字段和原因分类应复用或扩展，不另建一套平行 4xx 分类。
错误判定仍来自正式业务错误或任务状态接受点；日志层不能自行重判 Provider 结果。
新页面查询统一错误事件，不在每次查询时拼接后台文本、消费日志和 Task 表猜测错误。

实施时明确每个事件的唯一写入 owner。业务出口负责提供原因，请求结束负责统一完成请求级记录；
上游尝试、后台任务和测试分别产生其自身粒度的事件，不能把同一错误再当成不同请求重复统计。
旧 `type=5` 与新事件的写入、查询关系需在编码前明确：保留真实原生接口消费者和历史记录，
不新增另一套独立错误分类，不把两份观察相加当作失败总数，不为新目标扩大原生计费日志职责。
（已明确并落地：请求级事件唯一写入 owner 为 `clienterrlog` Recorder；`type=5` 原生
行为、开关与消费者完全不变，两套互不影响。）

### 4. 最小入侵与正式副作用边界

- 不缓存、扫描全部响应正文来猜测失败，尤其不能干扰 SSE、WebSocket 或大文件传输。
- HTTP 200 业务失败由正式失败出口提供标记，不按任意响应文本或关键词判断。
- 全局记录器须核对 Recovery 顺序和插件嵌套路由，覆盖可恢复异常，且不吞掉业务 panic。
- 新观测逻辑不改变原生重试、自动禁用、Link 不重试和任务结算规则。
- 新记录、查询、展示逻辑优先放入独立文件；原生热路径仅保留必要接线，并逐处说明必要性和上游同步影响。
- Task 状态和账务只有原有正式入口能够推进。日志只能记录已接受事实，不触发重发、换渠道或退款。

### 5. 请求 ID 与事件去重

| 标识 | 目标语义 |
| --- | --- |
| 网关请求 ID | 每个进入应用的请求在鉴权前生成，可关联响应和诊断 |
| 测试 ID | 每次后台渠道测试独立生成，不能只复用触发管理请求的 ID |
| 上游调用序号 | 同一请求的每次实际调用独立编号，不与 durable TaskCreateAttempt 混为一谈 |
| 上游请求 ID | 在对应尝试结束时冻结，不被后续重试覆盖 |
| Task ID、创建尝试 ID | 关联异步生命周期与原始请求事实 |
| 错误事件 ID | 对事件写入、交付重试及重复采集进行稳定去重 |

收窄实现现状：仅请求级单一粒度，`request_id` 即事件身份，WARN 行与持久化是同一事件的
两个出口而非两条记录；测试 ID、上游调用序号、Task ID 关联随对应来源引入时才需要。

上游未返回 ID 时显示“上游未提供”；未调用上游时显示“不适用”，不能生成伪造上游 ID。
历史记录没有保存的字段显示未记录，不用当前配置、时间接近或文案相同推造关联。

同一错误可能同时经过业务出口、结束中间件和任务通知，必须使用稳定事件身份去重。
不能按时间窗口或错误文案去重，否则会合并真实的不同请求。
异步来源事件须在持久状态提交后产生；恢复补写应依赖已保存事实，不猜测已丢失的过程。

### 6. 统计口径

| 指标 | 定义 |
| --- | --- |
| 错误事件数 | 发生过多少次错误，包含同请求的不同失败尝试 |
| 受影响请求数 | 出现过错误的不同请求数 |
| 最终失败请求数 | 客户请求最终失败的去重数量 |
| 结果不明数 | 尚不能确定结果的请求或任务数量 |
| 渠道测试失败数 | 独立于客户调用的测试结果 |

4xx 不自动等于客户责任，5xx 也不能单凭状态码定位根因。
应区分本地状态、原始上游状态与正式错误归属；未知原因保留未知。
客户端断开属于需要排查的事件，但不默认计入供应商故障。
退款及结算差额返还也不能反推任务是否失败。

只有错误数据无法计算可靠成功率。展示渠道失败率前，还需取得同窗口、同来源、同粒度的总调用数，
并区分请求数、上游尝试数、已受理异步任务数和健康检查数。
消费日志条数不能替代全量尝试分母，未接通的统计必须显示不可计算。

### 7. 可靠交付与可观察性

已有内存队列存在满载丢弃及关闭不等待排空的行为，不能直接承诺零丢失。
考虑本次本地分析曾观察到数据库损坏报错，建议设计以下交付目标：

1. 正常运行时全量记录，不因 4xx、低严重度或重复文案采样丢弃。
2. 数据库短暂不可用时使用持久化缓冲，恢复后按事件 ID 补写。
3. 展示积压、写入失败、缓冲空间和记录缺口，不能让无记录被误认为无错误。
4. 仅重试日志交付，不重放客户 Provider 请求，不改变资金与任务事实。
5. 明确缓冲容量、写入时限、关闭处理和恢复策略，禁止无界内存队列或每条事件无界启动 goroutine。

持久化缓冲是待设计和验证的可靠性建议，不是现有能力；其耐久边界、确认时点和与日志库的一致性需在实施前明确。
磁盘同时不可用、持久化前进程被强杀等情况下，不能承诺绝对无丢失。
业务优先与记录完整性之间的故障行为也须写入验收标准，不能默默丢弃后仍宣称全量。

已实现的可观察部分：队列满丢弃、WARN 写失败与持久化失败分别以 `dropped`/`failed`/
`persisted`/`persist_failed` 计数暴露（Root 健康端点），持久化缓冲与恢复补写未实现。

### 8. 安全、权限与保留策略

- 只保存受控结构化诊断、稳定错误码与脱敏摘要。
- 不保存 Key、Token、Cookie、原始提示词、原始 Provider 响应或完整签名 URL。
- 路径优先保存路由模板；未匹配路径采用受控表达，不默认保存查询参数或敏感路径内容。
- 未认证记录保留真实认证状态；仅凭上下文存在用户 ID，不能视为已通过鉴权。
- 必须查看已有受保护证据时，沿用当前权限和审计入口，不把证据正文复制到错误表。
- 查询与导出复用相同服务端权限和脱敏规则；普通管理员不能读取 Root 专属诊断。
- 设置独立保留及清理策略，普通使用日志清理不应顺带删除错误排障证据。
- 保留期限、导出规模和容量预算尚待确定，不在分析中承诺未经验证的吞吐与保留量。

保留策略现状：第一轮未接清理（表无 TTL，对齐 audit_logs 先例），后续可接入 Root
log-cleanup 系统任务；普通使用日志清理当前不会触及本表。

Recovery 的 panic 盲区不因本次扩展自动进入范围。

### 当前实际情况与代码分析

以下为本地代码检查所得事实，不代表线上版本已经部署或经过真实 Provider 验收。

| 位置 | 已有事实 | 对最小实现的影响 |
| --- | --- | --- |

| `controller/channel_seedance_link_health.go` | Seedance 自动健康检查走专用只读探针 | 在健康检查外层收口才能包含专用探针；不改变探针能力与渠道启停规则 |

| `relay/channel/openai/relay_responses.go` | `response.failed` 等分支尚未统一登记到流错误状态 | 须在现有协议分支补诊断标记，公共扫描器无法自行推断协议失败 |

### 优化方案：公共事件合同

建议新增两个普通字段，其余优先复用已有字段和白名单详情，不新建另一张错误表。

| 字段 | 建议值或含义 | 用途 |
| --- | --- | --- |
| `event_type` | `api_error`、`channel_test`、`stream_error`、`task_failure` | 唯一区分事件类型，支持展示和筛选 |
| `task_id` | 公开任务 ID；非任务事件为空 | 支持直接定位异步失败，不拿任务 ID 冒充请求 ID |

`stage` 继续描述错误发生阶段，`module` 继续描述模块，不能因省一个字段让它们同时承担事件
类型。后台事件通过类型明确的入口提交，不伪造 HTTP 路由、用户 Token 或鉴权成功标记。
已有记录按 `api_error` 归类；实施时补齐已有表升级与存量分类，验证 SQLite、MySQL、
PostgreSQL；独立 ClickHouse 日志库还须补既有表增列，不能只修改 `CREATE TABLE IF NOT EXISTS`。

| 场景 | `status` 与页面含义 | 详情说明 |
| --- | --- | --- |
| 普通 API 错误 | 客户实际收到的 4xx/5xx | 延续当前合同 |
| SSE 已返回 200 后异常 | 200，配合“流式异常”类型展示 | 不伪造 500，也不修改业务响应 |
| 手工测试管理接口返回 200，但探针失败 | 200，配合“渠道测试失败”展示 | 探针上游状态与内部错误码独立保留 |
| 后台健康检查或异步终态失败 | 建议沿用整数列，以 0 表示不适用，页面显示“—” | 不把原始创建的 202 或轮询的 200 当作终态事件的客户 HTTP 状态 |

现有接口以状态零值表示不筛选；增加“无 HTTP 状态”过滤时必须区分“未指定”与“指定为 0”，
例如显式检查参数是否存在或使用可空过滤值，不能让这两个条件混淆。200 同样需要精确过滤。

新事件入口统一执行受控字段白名单与净化，不把原始响应、异常字符串、完整 URL、凭据或
Task 私有数据塞入 `detail`。现有 `SanitizeLogValue` 主要处理控制字符和长度，不能替代秘密
脱敏。需要可读说明时，优先使用既有公开安全错误投影或由固定原因码生成的说明。

队列交付应按明确的事件合同选择持久化出口。普通 HTTP 错误保留原采集门槛；流式错误通过
请求载体显式标记；测试和后台任务由专用入口产生。不能扩大成全部管理模块入库，也不能让
新的 200／无状态事件意外改变原生 WARN 的 4xx 统计口径。保持原生 type=5 与
`ERROR_LOG_ENABLED` 的既有行为。

### 优化方案：渠道测试与健康检查

建议新增独立的渠道测试事件构建文件，接入两处已有结果出口：

1. `TestChannel()` 得到结果后：`localErr` 或 `newAPIError` 非空时记录一次。
2. `testChannelForHealthCheck()` 完成探针及响应时间阈值判定后：按本次最终测试结果记录一次。

不能在底层 `testChannel()` 和两个外层同时写入，以免重复；只改底层又会漏掉 Seedance
专用探针及外层生成的超阈值错误。手工与自动均使用同一个事件构建实现。

保存渠道、实际测试模型、测试方式、时间、耗时、受控原因码、测试关联 ID，以及实际取得的
上游请求 ID。手工测试的管理员身份表示操作人，不能计成普通客户调用；自动检查的系统执行
身份也不能伪装为客户。后台检查可生成新的测试关联 ID，但不能宣称它是原客户请求 ID。

当前测试代码会把某些上游非 200 响应包装为内部 500。需在读取响应时冻结真实上游状态到
测试结果，再写入白名单详情；不得从包装后的错误反推上游状态。不支持测试、配置错误、
响应时间超阈值与 Provider 拒绝分别分类。执行任务取消应标记取消或跳过，不计为渠道故障。

### 优化方案：SSE 流式异常

优先在 `Relay()` 退出时调用独立观察函数，读取最终尝试的 `StreamStatus` 和已知错误，
通过请求载体标记流式异常，再由记录器写入一条请求事件。观察顺序须保证适配器完成处理、
流状态可安全读取，且请求最终状态由最外层记录器读取；不得让多个 goroutine 竞争写事件。

| 信号 | 拟处理方式 |
| --- | --- |
| 超时、扫描错误、处理异常 | 记录流式异常，保留受控结束原因 |
| `Stop(err)`、结束错误或错误计数大于零 | 纳入观察；区分致命失败与发生过可恢复处理错误，不把后者一律描述成最终生成失败 |
| 客户端断开或写回失败 | 收录并区分客户端／传输方向；无充分证据时不归因于 Provider |
| 正常完成且没有错误 | 不产生事件 |
| 单独 EOF | 依据现有协议的合法结束条件判断，不全局改为失败；要求完成标记的协议在其适配器识别缺失 |
| 明确的协议错误事件 | 在已有解析分支登记受控标记；不同的失败、取消、未完成状态按协议分别分类 |

必须补充检查 Responses 的 `response.failed` 等已识别分支，以及 AWS SDK 事件流和独立扫描
循环的错误出口。此类分支只添加诊断调用，不重写协议解析、不改变返回值、重试、结束语义或
计费。不使用原始 SSE 内容的关键词搜索来推断失败。

同一次客户请求最多产生一条请求级错误事件。若最终已是 4xx/5xx，则在这条事件中合并流式
诊断；不能再额外写一条重复事件。存在重试时，观察最终尝试，避免前次失败状态残留导致最终
成功请求被误报。渠道测试中的流式探针由测试事件出口负责，不再作为客户流式事件重复入库。

### 优化方案：异步任务失败

以已有持久化生命周期为唯一失败判定源：首次进入明确失败状态且事务提交成功后，构建并
提交一条任务错误事件。日志只观察已经发生的事实，不决定退款、重发、换渠道或任务终态。

| 正式写入路径 | 拟接线位置与注意事项 |
| --- | --- |
| 通用视频／插件任务 `Task.UpdateWithStatus()` | 条件更新成功后；覆盖 Seedance 提前返回分支，不遗漏其事务结果 |
| 异步图片 `transitionImageTask()` | 事务成功且本次确实完成状态迁移后；不能只桥接可能包含待核实的图片诊断日志 |
| Midjourney 自有 `UpdateWithStatus()` | 其独立条件更新成功后，复用统一构建逻辑 |
| Azure Batch 专用观察流程 | 首次可信失败终态已持久化后；不能等资金结算成功才可见，也不能每次终态轮询重复记录 |
| 人工核实失败等直接事务写入 | 在对应事务提交后补窄接线，核对是否绕过上述公共函数 |

实施前需枚举上述路径的状态写入调用，确认覆盖当前启用的异步能力，不能把通用 Task 钩子
描述为所有任务的唯一提交入口。新增任务事件构建文件统一取值；原生文件保留最小接线。

去重首先使用已有状态条件更新、版本或锁保护：只有实际提交者且旧状态与目标失败状态不同
时才发事件。同状态补写、轮询、退款重试和结算补偿不再次记录。必须比较真实已保存状态，
不能仅凭内存对象的失败状态判断发生了迁移。

事件保存公开任务 ID、任务所属用户、创建时冻结的客户模型与渠道、失败状态、安全原因及
可用的创建关联 ID。信息缺失时明确留空，不查当前渠道配置重新解释历史执行事实，不记录
Task 私有快照。创建时已保存的上游请求 ID 不能宣称是失败轮询当次的上游请求 ID。

| 状态／情况 | 本轮处理边界 |
| --- | --- |
| 已确认执行失败、已确认执行过期 | 收录，分别分类 |
| 单次轮询失败、结果 unknown、待核实 | 不直接记为任务执行失败，不改动既有核实流程 |
| 用户主动取消 | 若展示则单独分类，不计为渠道执行故障 |
| Batch 整体成功但部分行失败 | 属于部分失败；可扩展为一条任务级摘要，是否纳入本轮及其统计口径尚待明确，不默认逐行铺开 |

### 最小改动范围与上游同步影响

| 层次 | 拟修改内容 | 必要性与冲突控制 |
| --- | --- | --- |
| 本地错误底座 | 类型定义、后台提交、请求显式标记、受控详情与持久化映射 | 复用现有实现，不引入第二套队列或分类系统 |
| 表与查询 | 两个普通字段、必要索引、旧表升级、类型／任务 ID／状态过滤 | 同一页面统一查询，验证多数据库升级与已有数据 |
| 渠道测试原生文件 | 手工、自动结果各一次调用，必要的上游状态证据字段 | 否则无法获取真实测试结果；构建与净化放新文件，避免重排测试实现 |
| Relay 与特定适配器 | Relay 最终观察调用；遗漏协议分支及独立流出口的诊断调用 | 公共 HTTP 记录器无法识别流内错误；只补观察，保留上游协议权威实现 |
| 任务提交边界 | 各正式提交出口的窄调用 | 捕获实际失败迁移并避免重复，不通过全局 ORM 回调猜测业务失败 |

原生文件的具体数量取决于独立流式适配器及直接任务写入口的覆盖清单，当前不承诺固定行数。
实施中每一处原生修改都应列明必要性、最小接线点及未来同步冲突；不得借日志扩展调整业务
返回、重试、渠道启停、资金规则或做无关重构。

### 验证方式、可靠性限制与剩余事项

以下为待实施验收要求，不是本次已执行测试：

| 验证场景 | 验收结果 |
| --- | --- |
| 手工／自动测试、Seedance 专用探针失败 | 每次失败一条，成功不记录，取消与不支持测试正确分类 |
| 测试上游返回 400、内部包装为 500 | 客户响应、内部错误与真实上游状态不混淆 |
| HTTP 200 后超时、明确 SSE 错误事件 | 记录一条流式异常，HTTP 保持 200 |
| 正常结束、合法 EOF、可恢复错误、客户端断开 | 正常路径不误报，其余分类不混成渠道故障 |
| AWS 等非公共扫描器路径 | 已有异常出口可记录；必须有代表性回归，不以公共扫描器测试替代 |
| 请求同时有流式异常与最终 HTTP 错误、测试流式探针 | 不重复；重试最终成功不被旧尝试污染 |
| 异步失败重复轮询、并发状态迁移、同状态补写 | 同一次失败迁移只记录一次 |
| 状态事务回滚、竞争更新未成功 | 不产生任务失败事件 |
| 日志输出失败、写库失败、队列满 | 不改变业务响应、状态或资金；故障计数可观察 |
| 新建／旧表升级、原有数据、200／无状态筛选、任务搜索 | 各受支持数据库与页面行为符合字段合同 |

本方案延续现有内存异步队列的可靠性水平。提交者判定能避免正常执行时的重复，但任务状态
提交后、事件入队前进程崩溃，以及队列满、写库失败或进程退出，仍可能导致事件缺失。
不承诺 exactly-once 或零丢失，也不跨主库／日志库伪造原子提交。现有 4xx WARN 写入失败会
提前结束该事件交付的问题，在调整出口时应隔离处理，避免日志文件故障阻断独立持久化。

如果业务进一步要求“每个失败任务一定可查且可重放补齐”，需单独设计持久化投递／补偿与
幂等事件标识，并验证分库及 ClickHouse 的去重语义；不能靠一次存在性查询冒充并发唯一性。
该可靠性交付升级、历史回填和保留清理均未纳入本次最小修改承诺。

剩余实施事项：完成流式独立出口与任务状态写入口清单；确定 Batch 部分失败等边缘分类；
落地字段升级与跨库验证；完成代表性协议、并发迁移及页面回归；更新当前范围说明后再按
真实验收结果记录交付状态。本次文档补充不代表新增功能已通过测试或生产验收。
