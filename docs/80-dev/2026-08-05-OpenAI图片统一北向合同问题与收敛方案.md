# OpenAI 图片统一北向合同问题与收敛方案

## 1. 业务目标与结论

本方案只服务两个业务目标：

1. NEWAPI 已有接口、请求字段、响应、路由、Provider adapter 和计费语义不允许因本地图片统一化而更新、
   包装或收紧；`gpt-image-2` 等已有模型继续以 NEWAPI 原生实现为权威。
2. Nano Banana、Seedream 和 Qwen Image 3 按“精确模型 + 精确渠道 + 精确客户入口”核对：
   NEWAPI 已支持时零代码改动；只有确认不支持的精确组合，才可以在现有
   `POST /v1/images/generations` 入口下增加最小南向适配。

当前结论：

- **不实施旧方案中的图片 capability v2 全面迁移。** 不删除 K 档、`image`、`watermark`、
  `aspect_ratio` 等 NEWAPI 已有 DTO 或已发布本地合同正在使用的字段，不强制迁移到
  `/v1/images/edits`。
- **Nano Banana 优先使用 NEWAPI 已有 Gemini/Chat 和 Gemini 原生入口。** 不为了路径统一再建
  一套 `/v1/images/generations` adapter。已存在的本地 `nano-banana-2` Link 合同本轮保持不变，
  不用它反向包装 Google 原生能力。
- **Seedream 按 Provider 分类。** 火山方舟等能履行 NEWAPI 原生图片链路的渠道继续原生透传；
  只有 Moxing 这类可能返回私有异步任务的渠道保留已有 Link implementation 和共享 Task。
- **Qwen Image 3.0 Pro 先零代码验证。** 精确 Provider 模型名为 `qwen-image-3.0-pro`；它能命中
  NEWAPI 已有阿里同步图片识别、多模态请求转换和图片响应归一化。第一选择是渠道配置
  与真实账号黑盒验证，不是新增 Router、DTO 或 adapter。

## 2. 范围与非目标

### 2.1 本方案处理

- 判定一个精确图片模型是否已由 NEWAPI 原生支持。
- 对 Nano Banana、Seedream 和 Qwen Image 3.0 Pro 给出当前代码事实、协议差距和最小动作。
- 对确认缺失的模型定义 `/v1/images/generations` 最小接入门禁。
- 保护 `gpt-image-2` 等已有 NEWAPI 原生图片能力。

### 2.2 本方案不处理

- 不重写 NEWAPI Router、`ImageRequest`、Relay、Provider adapter、模型发现或计费。
- 不要求所有已支持图片模型都改用 `/v1/images/generations`；“原生已支持”优先于“路径观感统一”。
- 不把 NEWAPI 已有扩展字段删除或改义，不把统一路径误解为“所有字段和枚举值都必须与
  OpenAI 某一个官方模型完全相同”。
- 不新建平行 Images Router、平行 Task、第二套计费账本或仅由模型名推断的 Link SKU。
- 不在本文档中宣称邀测模型、未黑盒验证渠道或未对账价格已生产发布。

## 3. 判定规则

### 3.1 “NEWAPI 已支持”的含义

必须对下列四个维度同时取证，不能只看模型列表或名称相似：

| 维度 | 判定标准 |
| --- | --- |
| 客户入口 | NEWAPI 已有公开路由能表达该模型的请求，例如 Chat、Gemini 原生或 Images |
| 请求转换 | 已有 DTO/adapter 能构造 Provider 要求的字段、路径与鉴权，不静默丢失关键语义 |
| 响应处理 | 已有链路能向客户交付图片结果、错误和 usage，不泄漏 Provider 私有响应 |
| 计费与运行 | 预扣、结算、数量上界和同步/异步责任边界可依已有机制履行 |

如果模型已经通过 Chat 或 Gemini 原生入口可用，按本轮业务目标就属于“NEWAPI 已支持”；
不为了再增加 Images 路径而改原生代码。如果产品后续改为“所有图片模型必须从
`/v1/images/generations` 调用”，那是另一项公共协议需求，需要重新评审，不得隐含在本方案中。

### 3.2 “标准 `/v1/images/generations`”的含义

对于确认不支持的模型，“标准入口”表示：

- 客户调用 NEWAPI 已有 `POST /v1/images/generations`；
- 客户使用现有 `relaykit/dto/openai_image.go` 中的 `ImageRequest`，不新建平行 DTO；
- 同步完成时返回现有 `ImageResponse`；
- Provider 私有路径、`messages`、任务信封和参数嵌套只在南向 adapter 内部出现；
- 只在模型确实不支持的字段上失败关闭，不收紧其他 NEWAPI 原生模型。

这不意味着需要删除 NEWAPI `ImageRequest` 现有的 `image`、`images`、`watermark`、`stream`、
`Extra` 等字段，也不意味着 Provider 官方定义的 `2K`、`4K` 或像素尺寸必须在网关中互相伪装。

### 3.3 最小改动顺序

按以下顺序选择，上一层可履约时不得进入下一层：

1. 原生模型 + 原生渠道 + 原生入口。
2. 只修改 Channel、`models`、`model_mapping` 或已有可编辑模型配置。
3. 普通 Advanced Custom route + `converter=none`。
4. 复用已有 Provider adapter，只新增窄的模型登记或适配分支。
5. 仅当 Provider 存在私有请求、响应或异步生命周期时，才新增独立 Link implementation。

## 4. 当前代码基线

### 4.1 上游基线与本地扩展

当前仓库已同步 NEWAPI `v1.0.0-rc.23`，上游目标提交为
`0ab02020603d22e5613bc4cf46bfab06f8567769`。在该基线中：

- `/v1/images/generations` Router、`ImageRequest`、原生 Image Relay 和多个 Provider adapter 已存在；
- Qwen 图片、火山 Seedream、Gemini 图片模型的相关原生代码均来自该上游基线；
- `model/image_sku_capability.go`、图片 publication、Moxing 媒体任务转换和
  `/v1/images/tasks/:task_id` 等属于后续本地 Link 扩展，不能反向定义 NEWAPI 原生能力。

本方案的“原生支持”必须以上游基线中的 Router、DTO、Relay 和 Provider adapter 为证据，不以
本地 Link SKU 是否已注册为证据。

### 4.2 原生图片公共边界

当前 `ImageRequest` 已包含 `model`、`prompt`、`n`、`size`、`quality`、`response_format`、
`stream`、`image`、`images`、`watermark` 和额外字段承载机制。这是当前 NEWAPI 原生 DTO 事实，
本轮不删除、不重命名、不改为第二个“更纯”DTO。

同一个 DTO 能解析某个字段，不代表所有模型都必须支持它。模型或 Provider 需要缩小字段范围时，
约束应位于该精确 adapter/渠道合同内，不能上移到全局原生 validator。

### 4.3 `gpt-image-2` 保护线

`gpt-image-2` 继续走 NEWAPI OpenAI 原生图片链路，不进入 Link SKU、Moxing converter、图片 Task 或
图片 publication 推断。已有 JSON、multipart、分发、并发幂等和计费回归是本方案的黄金基线。

任何后续图片模型接入如果使下列任一项变化，必须阻断发布：

- `gpt-image-2` 的请求体或上游路径；
- 原生选渠、优先级、权重或 affinity；
- 同步响应信封、错误或流式行为；
- 预扣、结算、日志或原生请求产生零 Link Task/claim 的行为。

## 5. Nano Banana 完整分析

### 5.1 精确模型身份

Nano Banana 是 Google 对 Gemini 原生图片生成能力的产品名，不是单一稳定 API 模型 ID。
当前官方模型包括：

| 产品名 | 精确 Gemini 模型 ID | 当前仓库默认登记 | 当前 NEWAPI 能力 |
| --- | --- | --- | --- |
| Nano Banana | `gemini-2.5-flash-image` | 是 | Gemini 原生和 OpenAI Chat 转 Gemini |
| Nano Banana Pro | `gemini-3-pro-image` | 是 | Gemini 原生和 OpenAI Chat 转 Gemini |
| Nano Banana 2 | `gemini-3.1-flash-image` | 是 | Gemini 原生和 OpenAI Chat 转 Gemini |
| Nano Banana 2 Lite | `gemini-3.1-flash-lite-image` | 否 | 当前默认配置未登记；需先配置与黑盒验证 |

Google 官方使用 Gemini `generateContent`/Interactions 语义生成和编辑图片，输出可以同时包含文本与图片。
它不是 OpenAI Images 的原生 Provider 协议。

### 5.2 当前 NEWAPI 支持情况

当前上游代码已经：

- 在 `relay/channel/gemini/constant.go` 登记 `gemini-2.5-flash-image`、`gemini-3-pro-image`、
  `gemini-3.1-flash-image` 及部分 preview 名称；
- 在 `setting/model_setting/gemini.go` 把上述模型注册为 `SupportedImagineModels`；
- 在 OpenAI Chat/Responses 转 Gemini 时为支持图片的模型设置图片响应 modality；
- 通过 Gemini 原生 `/v1beta/models/{model}:generateContent` 路由支持原生请求。

但 `relay/channel/gemini/adaptor.go` 的 `ConvertImageRequest` 当前明确只允许 `imagen*` 模型进入
`/v1/images/generations`。因此：

- Nano Banana 已是 NEWAPI 原生支持的 Gemini/Chat 图片能力；
- Nano Banana **不是**当前 Gemini adapter 下的 OpenAI Images 原生模型；
- 根据本轮“已支持则不改”的业务目标，不为它增加第二个 Images adapter。

### 5.3 本地 `nano-banana-2` 的边界

当前本地 `nano-banana-2` 不是 Google 原生模型登记的简单别名。它已经作为 Link 客户模型，
绑定 Moxing `gemini-3.1-flash-image-preview-usage` 媒体任务实现，并使用 `1K/2K/4K`、
`aspect_ratio`、URL 参考图和共享 Task 语义。

本轮处理：

- 保留已有客户合同和 publication，不强制迁移、删字段或改响应。
- 不把 Google 原生 `gemini-3.1-flash-image` 自动推断为 `nano-banana-2` Link SKU。
- 新增 Google 官方渠道时使用精确 Gemini 模型 ID 和原生入口，不借用本地 Link 合同。
- `gemini-3.1-flash-lite-image` 先通过现有 `supported_imagine_models` 配置与渠道模型配置试验；
  只有配置不能履约时，才评估接取已支持该模型的新版 NEWAPI 上游。

## 6. Seedream 完整分析

### 6.1 不能把 Seedream 当作一个单一模型

Seedream 是一个模型家族，当前仓库同时出现：

- NEWAPI 上游 Volcengine adapter 默认登记的 `doubao-seedream-4-0-250828` 和
  `seedream-4-0-250828`；
- Moxing Provider 模型 `seedream-5-0-260128`；
- 本地客户模型 `seedream-5-moxing`。

这些名称代表不同的客户模型、Provider 模型和履约方式，不能因为都包含 `seedream`
就使用同一个 adapter 或 Link SKU。

### 6.2 火山方舟原生链路

上游 NEWAPI 已经支持：

- 客户从 `POST /v1/images/generations` 进入原生 Image Relay；
- Volcengine `ConvertImageRequest` 对图片生成请求原样传递；
- 南向路径使用 `/api/v3/images/generations`；
- Seedream 官方语义本身包含 `image`、`2K`、流式、组图、URL/Base64 返回和 `watermark`。

因此，对精确 Volcengine Seedream 模型或 Endpoint ID，应先用原生 Volcengine 渠道黑盒验证。
已成功履约时：

- 不新建 Link SKU、publication 或 converter；
- 不把 `2K`、`image` 或 `watermark` 视为必须清理的“非标准污染”；
- 不为统一到 OpenAI 官方像素枚举而增加尺寸猜测转换。

### 6.3 Moxing 同步/异步联合链路

Moxing 当前可能：

- 在 `/v1/images/generations` 同步等待后返回 `data[]`；
- 或通过 `/v1/media/generations` 返回任务信封，再查询 `/v1/media/tasks/:task_id`；
- 使用 `capability=image_generation`、K 档、URL 参考图和私有扩展。

这不是单纯 `converter=none` 能完整履行的原生同步链路。已有
`media_task_image_blocking`、durable create attempt、共享 Task 和计费责任转移有存在必要。

本轮不重写该实现，也不把已发布合同强制转成同步 OpenAI drop-in。只保留以下边界：

- 只有显式 publication 的客户模型才进入 Link；
- 原生 Seedream 模型不得因名称相似进入 Moxing converter；
- 可能建立 Provider 任务的 POST 继续遵守发送前 create attempt 与资金 hold 约束；
- 已有 K 档、URL 参考图和异步响应是本地已发布合同事实，只能通过单独产品迁移改变。

## 7. Qwen Image 3.0 Pro 完整分析

### 7.1 官方合同

当前精确模型 ID 为 `qwen-image-3.0-pro`。官方合同的核心形状为：

- 当前处于邀测，账号必须获得模型权限；
- 南向调用 `/api/v1/services/aigc/multimodal-generation/generation`；
- 请求使用 `model + input.messages[] + parameters`；
- 文生图只包含一个文本 content；图生图/编辑可包含 1–3 个图片 content 和一个文本 content；
- `n` 支持 1–6，`size` 使用 `宽*高`，可选 `prompt_extend`、`negative_prompt`、`seed` 和
  `watermark`。

### 7.2 现有 NEWAPI 原生支持证据

当前上游 NEWAPI 已有阿里图片 adapter：

1. `setting/model_setting/qwen.go` 的同步图片模型规则包含 `qwen-image`，判定方式为
   `strings.Contains`，所以精确名 `qwen-image-3.0-pro` 可命中现有同步图片分支。
2. `relay/channel/ali/adaptor.go` 对同步图片使用官方要求的
   `/api/v1/services/aigc/multimodal-generation/generation`。
3. `relay/channel/ali/image.go` 已经把 NEWAPI `prompt`、`size`、`n`、`watermark` 转成
   `input.messages` 和 `parameters`，并把 `1024x1024` 类型尺寸转为阿里 `1024*1024`。
4. 现有响应处理支持从 `output.choices[].message.content[].image` 提取图片，并归一化为
   NEWAPI `ImageResponse.data[]`。

因此，Qwen Image 3.0 Pro 当前应判定为“原生 adapter 形状已覆盖，待账号与精确模型黑盒验证”，
而不是“必须开发新 adapter”。

### 7.3 最小配置方案

第一阶段不修改代码：

1. 使用 NEWAPI 已有 Ali 渠道类型。
2. 渠道 `models` 直接配置 `qwen-image-3.0-pro`。
3. 第一轮不设客户别名，使客户模型和 Provider 模型都为 `qwen-image-3.0-pro`。
4. 不建立 Link SKU、publication、Advanced Custom route 或新计费状态机。
5. 先验证最小文生图，再逐一验证 `size`、`n`、返回数量和账单。

第一轮保留精确模型名很重要：当前 Ali adapter 使用 `OriginModelName` 判断是否进入同步图片分支。
如果立即把客户模型改成不包含 `qwen-image` 的别名，可能误入旧异步 text-to-image 路径。如后续必须
使用自定义客户名，应先通过已有 `qwen.sync_image_models` 配置显式登记该别名并完成回归，
不为别名再写一个 adapter。

### 7.4 待验证边界

代码形状匹配不等于已生产发布。至少需要真实账号验证：

- 邀测权限与区域 Base URL；
- `prompt` 是否正确转为唯一文本 content；
- `size=1024x1024` 是否正确发送为 `1024*1024`；
- `n=1`、`n=6` 和 `n>6` 的成功/拒绝边界；
- 响应图片是 URL 还是 Base64，以及现有 parser 是否完整提取；
- Provider usage、本地图片数量和客户结算是否一致；
- 编辑场景的 1–3 张图如何经现有 `/v1/images/edits` 链路表达。本轮只要求文生图，
  编辑不能因文生图成功而自动宣称已支持。

## 8. 当前情况对比与决策

| 对象 | NEWAPI 已有入口/适配 | 当前缺口 | 本轮决策 | 代码改动 |
| --- | --- | --- | --- | ---: |
| `gpt-image-2` | OpenAI 原生 Images | 无本轮缺口 | 冻结原生行为，只跑黄金回归 | 0 |
| `gemini-2.5-flash-image` | Gemini 原生 + Chat 转换 | Images 路由不支持 | 已支持，不为统一路径增加 adapter | 0 |
| `gemini-3-pro-image` | Gemini 原生 + Chat 转换 | Images 路由不支持 | 已支持，保持原生 | 0 |
| `gemini-3.1-flash-image` | Gemini 原生 + Chat 转换 | Images 路由不支持 | 已支持，保持原生 | 0 |
| `gemini-3.1-flash-lite-image` | 可复用 Gemini 原生链路 | 默认列表/图片配置未登记 | 先配置验证，再优先接取上游 | 目标 0 |
| `nano-banana-2` 本地 Link | 已有 Moxing 媒体任务扩展 | 真实账单与更完整黑盒验证 | 保留现状，不做 capability v2 迁移 | 0 |
| Volcengine Seedream | 原生 Images + Volcengine adapter | 精确新模型需账号验证 | 原生优先 | 0 |
| Moxing `seedream-5-0-260128` | 已有 Link 同步/异步 adapter | 生产与账单门禁 | 保留现状 | 0 |
| `qwen-image-3.0-pro` | Ali 同步图片 adapter 形状已覆盖 | 静态模型列表未预置；邀测实测缺失 | 渠道手工配置精确模型名后黑盒验证 | 0 |

这张表中的“0”表示目标状态不需要业务代码变更；渠道、模型、价格和分组配置仍需要按真实账号完成。

## 9. 实施方案

### P0：冻结原生与已发布合同

- 停止执行旧方案中的 capability v2、K 档清理、参考图路由迁移和 publication 切换。
- 不修改 `relaykit/dto/openai_image.go`、OpenAI/Volcengine/Gemini/Ali 原生 adapter 和公共 Image validator。
- 冻结 `gpt-image-2`、已发布 `nano-banana-2` 和 `seedream-5-moxing` 的当前客户可观察行为；
  任何迁移另立产品决策。

### P1：建立精确模型实测矩阵

每个模型记录：

```text
客户入口
  -> 客户模型
  -> Channel type
  -> model_mapping
  -> Provider 模型/Endpoint ID
  -> 上游路径
  -> 请求转换
  -> 实际响应
  -> 计费与账单
```

至少验证：

- Nano Banana：精确四个 Gemini 模型 ID 的原生/Chat 入口，不测 Images 路由作为发布前置。
- Seedream：Volcengine 原生与 Moxing Link 分开验证，不混成一个模型结论。
- Qwen Image 3.0 Pro：使用精确模型名、Ali 渠道与 `/v1/images/generations`。
- 每条链路都验证错误、超时、结果数量、预扣、结算和脱敏日志。

### P2：只做配置收敛

- Nano Banana 使用精确 Gemini 模型 ID；需要新官方模型时，先修改可编辑
  `supported_imagine_models` 和渠道 `models`。
- Volcengine Seedream 使用原生渠道与精确模型/Endpoint ID。
- Qwen Image 3.0 Pro 首轮直接使用 `qwen-image-3.0-pro`，不设不包含 `qwen-image` 的别名。
- 客户价格、Ability 和分组只在实测通过后开放；它们不创建 Link 身份。

### P3：只在验证证明有缺口时改代码

只有出现以下证据才允许进入代码实施：

- 精确模型无法命中任何已有 Provider adapter；
- 配置和 `converter=none` 无法构造 Provider 请求或解析结果；
- 当前 NEWAPI 上游与更新版上游都没有覆盖该能力；
- 业务仍明确要求在 `/v1/images/generations` 入口发布该缺失能力。

实施时必须：

1. 优先向 NEWAPI 上游提交或接取上游已实现支持。
2. 如确需本地扩展，新增独立 Provider/Link 文件，只在原生热路径保留单行调用或极窄分支。
3. 复用现有 `ImageRequest`、`ImageResponse`、分发、计费和日志，不新建平行公共状态。
4. 只有 Provider POST 可能创建持久异步任务时才复用 durable create attempt 和共享 Task。
5. 不支持字段在上游发送前拒绝；`n` 等计费乘数使用项目统一上界与 checked 换算。

### P4：发布与回滚

- 新模型先只在测试分组与独立 Channel 开放。
- 先验证文生图；参考图、编辑、多图、流式和高级参数按独立证据发布。
- 黑盒请求成功不等于完成发布；还必须核对账单、错误、日志、数量与超时。
- 回滚只撤销新模型 Ability/渠道配置或本轮独立扩展，不回滚或重置 NEWAPI 原生代码。

## 10. 验收标准

### 10.1 原生零变更

- `gpt-image-2` 的 JSON、multipart、分发、affinity、并发幂等、响应和计费回归结果不变。
- Nano Banana 的 Gemini/Chat 原生入口不因本方案新增 Images 推断、Link publication 或字段限制。
- Volcengine Seedream 和 Ali Qwen 原生 adapter 不被重写或包装。
- `GET /v1/models`、已有 `ImageRequest` 和原生错误信封结构不变。

### 10.2 三类模型结论可追溯

- Nano Banana 使用精确 Gemini 模型 ID，并明确记录它走 Gemini 原生还是 Chat 转换。
- Seedream 每个结论都标注 Volcengine 或 Moxing，不写模糊的“Seedream 已支持”。
- Qwen Image 3.0 Pro 使用 `qwen-image-3.0-pro` 真实账号核验，且不依赖未配置别名。
- 每个“已发布”结论都有请求、响应、计费和账单证据；未完成时保持“待验证”。

### 10.3 如有新增扩展

- 客户仅使用现有 `POST /v1/images/generations` 和 `ImageRequest`。
- Provider 私有路径、鉴权、请求嵌套和任务 ID 不进入客户合同。
- 不修改无关原生文件；每个原生文件接线点都有必要性和上游合并冲突说明。
- 同步成功、上游拒绝、超时、数量越界、预扣、结算和失败关闭均有可观察测试。
- 如涉及 `relaykit/`，另外通过 `cd relaykit && GOWORK=off go build ./...`。

## 11. 风险与待闭合事项

1. Nano Banana 2 Lite 是官方当前模型，但 rc.23 默认列表尚未登记；需配置验证或后续上游版本评估。
2. Qwen Image 3.0 Pro 当前为邀测模型，没有真实账号权限时不得宣称生产支持。
3. Qwen Image 3.0 Pro 的文生图形状已与现有 adapter 匹配，但 `n<=6`、编辑多图和 usage 仍需真实回归。
4. Moxing `nano-banana-2` 与 Google 官方 Nano Banana 是不同履约链路，文档和运维不得混用它们的模型 ID、字段或账单结论。
5. 现有本地 Images Router 已接入 Link publication 和图片幂等 middleware；虽有 `gpt-image-2` 专项回归，
   后续任何路由调整仍必须以原生行为零差异为门禁。

## 13. 被本版取代的旧结论

下列旧结论不再作为实施依据：

- “所有 Link 图片模型必须迁移到 capability v2”；
- “`1K/2K/3K/4K`、`image`、`watermark`、`aspect_ratio` 必须从北向全面删除”；
- “使用参考图时一律迁移到 `/v1/images/edits`”；
- “为 Nano Banana、Seedream 和 Qwen Image 统一建立新 Link 图片合同”；
- “只要 Provider 模型名属于图片家族，就可以由模型名自动创建 Link SKU 或 publication”。

新的唯一主线是：**NEWAPI 原生优先，配置优先，普通透传优先，只对有精确证据的缺口增加最小南向适配。**

## 14. 当前 Link 图片合同代码基线

### 14.1 核对范围与结论

本节是对 2026-08-07 当前工作区代码的只读盘点，比较起点为 NEWAPI
`v1.0.0-rc.23` 目标提交 `0ab02020603d22e5613bc4cf46bfab06f8567769`，当前 HEAD 为
`72461018c13fcd605519e778b00473ca2ca7c10a`。结论如下：

- 本地没有为 Link 图片新建平行 Images Router 或 DTO，而是在现有
  `POST /v1/images/generations` 上增加 publication、SKU capability、implementation/execution binding、
  Moxing 南向转换和共享异步 Task 生命周期。
- 当前业务保留的 Link 图片客户模型只有 `seedream-5-moxing` 和 `nano-banana-2`；
  两者共用 `moxing.images.media-task/v1` implementation，但绑定不同 Provider 模型和南向路径。
- 代码注册只表示“可被验证和发布”，不表示生产已发布。客户可用仍需主数据库
  `LinkModelPublication`、合格 Channel、Ability、分组和价格同时成立。
- 本节只列当前业务保留的模型。代码中未列入下表的历史图片注册项不构成本方案的
  支持或发布承诺，也不得因注册仍存在而恢复业务支持。

### 14.2 当前业务有效的 Link 图片模型

| 客户模型 / Link SKU | Provider 模型 | 南向路径与转换 | 当前北向 capability | 任务语义 |
| --- | --- | --- | --- | --- |
| `seedream-5-moxing` | `seedream-5-0-260128` | `/v1/images/generations` -> `/v1/images/generations`，`media_task_image_blocking` | 必填 `model/prompt/size`；`size=2K/3K`；最多 14 张 HTTP(S) 参考图；`n=1`；仅 URL 响应；不支持流式；可传 `watermark` | 可接收同步 `data[]`，也可接收任务信封后进入 `shared_image_task` |
| `nano-banana-2` | `gemini-3.1-flash-image-preview-usage` | `/v1/images/generations` -> `/v1/media/generations`，`media_task_image_blocking` | 必填 `model/prompt/size`；`size=1K/2K/4K`；最多 10 张 HTTP(S) 参考图；`n=1`；仅 URL 响应；不支持流式；支持白名单 `aspect_ratio` | 通过媒体任务协议进入 `shared_image_task`，可同步等待或返回 `202` |

两个 SKU 的共同合同基线为：

- `ContractID=newapi.images.generations.v1`，capability 版本为 `public-image-contract-v1`；
- `prompt` 最长 3000 个 Unicode 字符，最多交付 1 张图，`response_format` 只接受空值或 `url`；
- 参考图当前只接受 HTTP(S) URL，不接受 Data URL、Base64 或 Provider 私有文件 ID；
- `SupportsLinkAssets=false`，因此当前未发布 `asset://` / `ast_*` 输入能力；
- `TaskContract=shared_image_task`，`BillingContract=newapi_quota`。

`gemini-3.1-flash-image-preview-usage`、`seedream-5-0-260128` 是 Provider 履约模型，不是客户
Link SKU。`doubao-seedream-4-5-251128` 虽然在 converter 中存在模型专属校验分支，但当前
没有被上表 implementation 绑定，不得因“代码能转换”而宣称为已发布 Link 模型。

### 14.3 Link 图片适配执行流程

```text
Client POST /v1/images/generations
  -> resolve LinkModelPublication by customer_model
  -> validate ImageSKUCapability
  -> retain channels passing implementation and execution binding checks
  -> NEWAPI native Distribute
  -> exact route/model selects media_task_image_blocking
  -> create durable TaskCreateAttempt and billing hold before provider POST
  -> synchronous data[] -> native Images response
  -> trusted task_id -> persist shared Task -> poll and settle
       -> terminal result -> standard data[]
       -> still active -> 202 + Location + X-Task-ID
                       -> GET /v1/images/tasks/:task_id
```

为了履行该流程，当前代码增加了以下行为：

1. **显式发布。** `ResolveLinkModelPublication(image_generation)` 只按客户模型查主数据库；
   普通模型查不到 publication 时继续 NEWAPI 原生路径，内部 Link SKU 被直接请求时失败关闭。
2. **选渠前限定履约实现。** 渠道必须同时满足 implementation、route family、converter profile、
   `model_mapping` 后的 Provider 模型和 Link SKU 绑定；零合格候选返回 503，不降级到普通渠道或另一 SKU。
3. **只校验已发布 Link 子集。** 在公共 `ImageRequest` 解析后，拒绝空 prompt、非法尺寸、
   `n=0`、结果超发、流式、非 URL 响应、非 HTTP(S) 参考图和合同外字段；普通模型继续使用原生 validator。
4. **增加 Moxing 同步/异步联合 converter。** `media_task_image_blocking` 负责添加
   `capability=image_generation`、转换参考图和 `aspect_ratio`、限定高级字段，并识别同步
   OpenAI `data[]`、HTTP 200/202 任务信封与任务状态。
5. **对可能建立 Provider 任务的 POST 建立耐久边界。** 精确命中媒体图片 route 时才开启
   `TaskCreateAttempt`、全额预扣和 `Idempotency-Key` claim。未取得可信 task ID 时不创建 Task；
   发送结果不明时标记 `unknown`，不自动重发、换渠道或盲目退款。
6. **同步优先，必要时转为客户可查任务。** 默认在请求超时上限内等待；客户发送
   `Prefer: respond-async` 或等待结束时任务仍未终态，返回 `202` 和脱敏 `ImageTask`。
7. **异步账单跟随冻结任务事实。** Task 冻结客户模型、publication 版本、capability hash、
   implementation ID/version/hash、Channel 连接、请求数量和计费快照；按可信 usage 或实际交付数量结算。
8. **保护 NEWAPI 原生图片路径。** 只在“Advanced Custom + 精确 route/model +
   `media_task_image_blocking`”同时成立时启用任务分支。`gpt-image-2` 等原生模型不创建 Task、
   attempt 或幂等 claim，仍使用原生同步响应和计费。

### 14.5 对 NEWAPI 原生文件的最小接线

与上游目标提交比较，Link 图片大部分逻辑已放入新增独立文件；上游热点仅保留以下接线：

| 原生文件 | 必要接线 | 冲突面 |
| --- | --- | --- |
| `router/relay-router.go` | 在现有 Images POST 上挂 publication、候选限制和精确任务幂等 middleware；增加 Task GET | 路由组局部变更 |
| `controller/relay.go` | 在解析、选渠和价格确定后，仅对持久媒体图片准备 attempt | 通用 Relay 增加极窄分支 |

### 14.6 当前已知边界

- 当前 Link 图片只承诺文生图和 HTTP(S) URL 参考图子集，不承诺 multipart edit、mask、
  Base64 输入、流式或平台托管 Asset。
- 北向 capability 的最大输出固定为 1。converter 内存在更宽的通用数量校验，不会自动扩大
  已发布 Link SKU 的客户合同。
- 当前客户任务公开面只有创建结果和 `GET /v1/images/tasks/:task_id`，未提供 Link 图片取消或删除端点。
- Provider 返回的结果 URL 会被校验、去重和限数，平台不保存图片二进制。
- `gpt-image-2`、Volcengine Seedream、Ali Qwen 和 Google Gemini 原生图片能力不在本 Link 支持表内；
  它们继续以 NEWAPI 原生入口、adapter 和计费为权威。
