# OpenAI 图片原生主路径与通用异步机制收敛方案

## 1. 问题与目标

当前仓库已经具备成熟的 NEWAPI 原生 Images Router、公共 DTO、分发、Provider adapter、同步响应和
计费链路，但本地图片扩展又逐步加入 publication、SKU capability、implementation、Provider 专属
converter、创建等待、任务轮询和结算处理。继续按“每接一个图片 Provider 就增加一套完整逻辑”的方向
推进，会形成多套请求校验、任务状态、轮询、计费和错误解释。

本次收敛不是从零建设图片异步系统，而是按当前代码事实校准并约束三个边界：

1. **原生 Images 是图片能力的唯一主体。** 这已经是当前 Router 和公共 DTO 的事实，也是后续不得回退的
   设计红线。能由 NEWAPI 现有
   `POST /v1/images/generations`、`ImageRequest`、分发、adapter、响应和计费履约的能力，不再建立
   平行 Link 图片实现。
2. **异步是通用执行机制，不是 Provider 产品。** 当前共享 `TaskCreateAttempt`、`Task`、后台轮询、
   终态条件更新和结算退款底座已经落地；本方案保留这些既有权威，不重建任务系统。剩余工作是把仍然
   混在 Moxing adapter 和共享 service 中的 Provider 协议职责分开，避免未来 Provider 继续复制或侵入
   生命周期。
3. **Provider 只保留薄适配。** 当前 adapter 已经委托共享 service 完成大部分持久化和资金状态，仍需
   收敛的是请求内 channel-test 轮询、重复结果归一，以及共享 service 中固定为 Moxing 信封的查询解析。
   最终每个 Provider 只负责确实不同的请求字段、创建结果、查询请求、状态、结果和 usage 映射，不拥有
   公共 Router、客户 DTO、任务表、幂等状态机或计费账本。

本方案不要求所有图片模型都使用同一个 Provider 协议，也不为了路径观感统一，把已经通过 Gemini 原生、
Chat 或其它 NEWAPI 原生入口稳定履约的模型强行改造成 Images adapter。

## 2. 当前实际情况

### 2.1 NEWAPI 原生 Images 已覆盖的公共能力

当前原生链路已经提供：

- `POST /v1/images/generations` 与 `POST /v1/images/edits`；
- `ImageRequest`、`ImageResponse`、JSON 和 multipart 解析；
- 模型映射、Ability、分组、优先级、权重、Affinity 和渠道重试；
- OpenAI-compatible 透传与 OpenAI、Ali、Gemini Imagen、Volcengine、MiniMax、Replicate、
  SiliconFlow、智谱等 Provider adapter；
- 同步 `data[]`、OpenAI 图片流式响应、错误处理、结果数量和统一 quota 计费；
- Advanced Custom `converter=none` 与渠道参数覆盖，可承载只支持图片端点的标准兼容上游。

因此，路径、字段、模型映射或 Provider 名称不同，均不是创建 Link 图片合同或新 adapter 的充分条件。

### 2.2 当前异步图片职责分布与真实重复

当前代码已经形成一套共享图片异步底座，而不是每个 Provider 各有一套完整实现：

- `StageMediaImageTaskCreateAttemptRecovery` 负责发送前恢复模板；
- `PersistMediaImageTask` 负责可信 task ID 后的 Task 持久化、hold 转移和消费记录；
- `WaitMediaImageTask` 与 `PollMediaImageTaskOnce` 负责请求内等待和单次状态推进；
- `UpdateMediaImageTasks` 已接入统一后台任务轮询；
- `settleMediaImageTask`、共享退款与 exposure 逻辑负责终态资金处理；
- 共享 Task 及其 OpenAI Images 投影负责客户 `202` 和后续查询。

`media_task_image_blocking` 当前直接保留的职责主要是：

- Moxing 请求字段转换、Provider 模型专项校验和创建请求发送；
- 同步 `200 + data[]` 与 `200/202 + task_id` 创建结果的分支识别；
- 对共享 service 的创建、持久化、等待和响应编排；
- 只在 channel-test 路径使用的 `pollMediaTaskImage` 请求内轮询循环；
- 与 service 重复的结果 URL、状态、错误和请求 ID 解析，以及 `ImageResponse` 合成。

同时，当前共享 `PollMediaImageTaskOnce` 仍直接解析固定的 Moxing 风格查询信封、状态别名、结果和 usage，
查询模板也固定为 `/v1/media/tasks/{task_id}`。因此当前已经共享的是 **Task 生命周期与资金状态机**，还没有
完全形成 **Provider 协议无关的轮询内核**。本方案只收敛这条剩余边界，不重写已在使用的共享底座。

### 2.3 已确认的原生与非原生边界

| 上游形状 | 当前应走的路径 | 是否需要 Link 图片扩展 |
| --- | --- | --- |
| 接受现有 `ImageRequest`，同步返回 `data[]` | 原生 Provider adapter 或 Advanced Custom `converter=none` | 否 |
| 仅需固定补充普通 Provider 参数 | 原生 Images + 已有参数覆盖 | 否 |
| 需要少量请求/同步响应字段转换 | 原生 Images + Provider 薄适配 | 仅在形成显式本地扩展时 |
| 可能返回持久 `task_id`，需要跨 HTTP 生命周期恢复 | 原生 Images + 通用异步机制 + Provider 薄适配 | 是 |
| 通过 Gemini 原生或 Chat 已稳定生成图片 | 保持对应 NEWAPI 原生入口 | 否，不为 Images 路径再造 adapter |

### 2.4 现有文档和实现中的过度范围

以下内容不再属于本方案：

- 图片 capability v2 全量迁移；
- 删除 NEWAPI 已有 `image`、`images`、`watermark`、`stream`、K 档或 Provider 合法尺寸；
- 为参考图统一改用 multipart `/v1/images/edits`；
- 为 URL-only Provider 建设临时文件上传、对象存储和签名 URL 服务；
- 为每个 Provider 新建图片 Router、DTO、Task 表、轮询器、状态枚举或计费状态机；
- 仅凭模型名、Channel、Ability、价格、profile 或 `model_mapping` 创建 Link SKU；
- 把原生同步图片请求纳入 create attempt、图片 Task 或 Link publication。

URL 参考图模型继续使用 JSON `/v1/images/generations` 的 `image` 字段。multipart
`/v1/images/edits` 只服务原生支持该合同的模型，不为 Moxing URL 输入建立文件转 URL 子系统。

## 3. 优化方案

### 3.1 总体原则

新的唯一主线是：

> **原生 Images 负责公共请求、分发、同步结果和普通计费；共享异步机制负责跨请求生命周期；Provider
> 薄适配只负责协议差异。**

不得通过“再增加一个统一 wrapper”同时保留全部旧实现。归一化必须选择现有原生 Images 与共享 Task
为权威，再迁移真实 Provider，最后删除 Provider 专属的重复生命周期。

### 3.2 唯一权威边界

| 事实或行为 | 唯一权威 | Provider 不得重复实现 |
| --- | --- | --- |
| 客户图片路径与请求 DTO | NEWAPI 原生 Images Router、`ImageRequest` | 新 Router、新公共 DTO |
| 普通模型分发 | NEWAPI Distributor、Ability、Channel、模型映射 | Provider 私有选渠器 |
| 同步图片响应 | 原生 `ImageResponse/data[]` 处理 | Provider 专属客户响应 |
| 普通同步计费 | NEWAPI 原生预扣、结算和日志 | Provider 专属账本 |
| 异步创建耐久边界 | 共享 `TaskCreateAttempt` | 每 Provider create journal |
| 异步业务事实 | 共享 `Task` | 每 Provider 任务表 |
| 异步轮询调度和状态迁移 | 现有共享图片 Task service | 每 Provider goroutine/生命周期 |
| 终态结算、退款和 exposure | 共享 Task 计费状态机 | 每 Provider 补偿逻辑 |
| Provider 请求、查询和结果差异 | 精确 Provider adapter/profile；这是当前剩余收敛点 | 上移到公共 DTO、全局 validator 或共享资金状态机 |
| Link 客户模型发布 | `LinkModelPublication` | Channel、Ability 或模型名推断 |

### 3.3 统一数据流

```text
Client POST /v1/images/generations
  -> 原生 ImageRequest 解析与公共安全上界
  -> 如有显式 Link publication，解析已发布 capability
  -> NEWAPI 原生分发、模型映射与候选约束
  -> Provider 薄适配构造请求
  -> 如果该精确实现可能创建持久任务：
       通用 create attempt + hold 在发送前提交
  -> Provider POST
       ├─ 同步完成：原生 data[] -> 原生结算 -> HTTP 200
       ├─ 接受异步：可信 task_id -> 共享 Task -> 通用轮询
       │    ├─ 等待窗口内完成：原生 data[] -> HTTP 200
       │    └─ 仍在执行：统一 ImageTask -> HTTP 202
       ├─ 明确拒绝：原生错误处理 -> 按统一资金规则结束
       └─ 创建结果未知：attempt=unknown，不重发、不换渠道、不盲目退款

Client GET /v1/images/tasks/:task_id
  -> 读取共享 Task
  -> 按 openai_images 客户协议投影状态、结果和脱敏错误
```

原生同步模型在上述流程中不会创建 attempt、Task 或幂等 claim。异步能力由精确 implementation/profile
声明，不能按路径、模型前缀或 Provider 名称猜测。

## 4. 原生 Images 主路径

### 4.1 标准兼容判定

上游满足以下条件时必须使用原生路径：

1. 能接收现有 `ImageRequest` 已开放的字段，或只需现有参数覆盖补充固定值；
2. 模型映射后可以由现有 adapter/route 构造正确 URL、鉴权和请求；
3. 同步成功直接返回可由原生处理的 `data[]`；
4. 不需要跨 HTTP 生命周期保存 Provider 任务；
5. 请求数量、响应数量和计费可以由原生链路可靠确定。

标准兼容上游可以使用原生 Channel type，也可以使用普通 Advanced Custom
`converter=none` 做端点级隔离。后者仍然是原生图片能力，不是 Link。

### 4.2 原生请求字段不做全局收紧

当前 `ImageRequest` 已包含 `model`、`prompt`、`n`、`size`、`quality`、`response_format`、
`stream`、`image`、`images`、`watermark` 和其它现有字段。本方案不删除、重命名或建立第二个更窄 DTO。

公共层只保留与所有模型共同相关的解析、安全和计费上界。模型或 Provider 的精确字段限制发生在：

- 已发布 Link SKU 的 capability 边界；或
- Provider 薄适配发送前。

同一客户字段不得在公共 validator、capability validator 和 Provider converter 中无依据地重复执行
相同校验。客户合同校验一次，Provider adapter 只验证转换后仍满足精确上游协议；如果 adapter 从
`Extra`、嵌套 `parameters`、multipart 或其它绕过公共 DTO 的路径读取计费乘数，仍必须在本地执行相同
上界，不能把“去重校验”解释为放弃计费防线。

### 4.3 原生同步行为保护线

`gpt-image-2` 等原生模型必须保持：

- 原有 JSON、multipart、流式、分发、Affinity 和重试行为；
- 原有请求和响应信封；
- 原有预扣、结算、数量更新和消费日志；
- 零 Link publication 推断、零图片 Task、零 create attempt 和零任务幂等 claim。

通用异步接线只能由选渠后精确实现触发，不得让每个 `/v1/images/generations` 请求都进入额外状态机。

## 5. 现有图片异步底座与剩余协议收敛

本节同时描述当前已落地的合同和仍待完成的边界，不是新建一套通用异步服务。`TaskCreateAttempt`、共享
`Task`、持久化、后台调度、条件终态、结算退款和 exposure 继续以现有 `service/`、`model/` 实现为权威；
实施不得另建表、状态机、调度器或资金账本。

### 5.1 进入条件

只有满足任一条件的精确实现才进入通用异步机制：

- 创建接口可能返回可信 Provider task ID；
- 创建响应可能在 HTTP `200` 或 `202` 中表达 queued/running；
- 请求超时或连接中断后需要恢复“Provider 可能已创建”的事实；
- 客户合同允许 `202 + GET /v1/images/tasks/:task_id`；
- 终态 usage 或实际交付数量只能在后续查询中确定。

“Provider 很慢”“路径叫 media”“渠道属于 Advanced Custom”均不是进入条件。

### 5.2 通用创建结果

Provider adapter 只把创建响应归一为四种结果：

| 通用结果 | 必要事实 | 统一处理 |
| --- | --- | --- |
| `completed` | 可交付 `data[]`，结果数量可信 | 原生同步响应和结算 |
| `accepted` | 可信 task ID 和当前状态 | 原子创建共享 Task、转移 hold |
| `rejected` | 明确未创建或可信业务失败 | 统一失败与资金处理 |
| `unknown` | 无法证明创建或拒绝 | 不重发、不换渠道、不盲目退款，进入对账 |

HTTP 状态码只是输入证据，不直接等于通用结果。`200 + queued/task_id` 是 `accepted`；
`202` 但缺少可信 task ID 不能创建伪 Task；网络错误也不能自动解释为 `rejected`。

当前 `media_task_image_blocking` 已经通过分支行为实现上述四类语义，包括同步 `data[]`、可信 task ID、
明确失败和发送结果 unknown；但它们仍是 adapter 内的隐式分支，还不是可由其它 Provider 复用的创建结果
边界。收敛时只形式化现有证据和责任转移，不再增加一套与现有 relay 错误处理并行的响应框架。

### 5.3 通用轮询结果

Provider adapter 把查询结果归一为：

```text
queued
in_progress
completed
failed
unknown
```

目标状态下，adapter 只负责：

- 用冻结的 Base URL、查询模板、task ID 和鉴权构造查询；
- 解析 Provider 状态、结果 URL、usage、请求 ID 和错误；
- 把 Provider 私有值映射为通用结果。

共享服务继续负责：

- 轮询调度、SLA、退避和有界对账；
- 条件状态更新与并发终态保护；
- 客户 `ImageTask` 投影；
- 结果数量校验、结算、退款和 exposure；
- 敏感字段不进入普通响应和日志。

当前实现与该目标仍有一个明确差距：`PollMediaImageTaskOnce` 在共享 service 内直接定义并解析
`task_id/id/status/state/result/usage` 信封、Moxing 状态别名和固定查询路径。收敛时应保留其 Task 加载、
快照复检、CAS 状态推进、终态保护、数量校验和资金处理，把查询构造与 Provider 私有响应解析移动到精确
协议 adapter/profile，再向共享 service 提交最小归一结果。不要为当前并不存在的回调、取消、删除或
多版本协议预建注册中心和兼容层。

### 5.4 Task 冻结事实

异步图片继续复用共享 `tasks` 表，并至少冻结：

- 客户模型、Link SKU、publication version 和 capability hash；
- implementation ID/version/hash、Provider 模型和精确执行 profile；
- Channel、Base URL、查询模板、凭据作用域和代理；
- 请求图片数量、响应格式和结果数量上限；
- 创建时价格、分组倍率、附加倍率和表达式快照；
- 创建/轮询请求 ID 和必要的对账期限。

不得保存 prompt、参考图内容、完整签名 URL、完整请求、原始 Provider 响应或客户 Authorization。

### 5.5 同步完成不创建长期 Task

潜在异步实现如果同步返回可信 `data[]`：

- 不创建长期 Task；
- 使用原生图片响应；
- 由共享 attempt 完成同步结算和责任关闭；
- 如使用了 `Idempotency-Key`，只记录“已完成但不可重放结果”的稳定事实，不伪造响应缓存。

## 6. Provider 薄适配

### 6.1 允许承担的职责

每个 Provider 图片适配只允许包含：

1. 北向字段到 Provider 请求字段的必要转换；
2. Provider 创建 URL、鉴权和固定参数；
3. 创建响应到 `completed/accepted/rejected/unknown` 的解析；
4. 查询 URL 和鉴权构造；
5. Provider 状态、结果、usage、请求 ID 和安全错误的解析。

如果两个实现使用相同 Provider 任务协议，应共享同一薄适配/profile，通过精确模型绑定表达差异；不得按
客户模型复制 converter、轮询和结算代码。

### 6.2 禁止承担的职责

Provider adapter 不得：

- 注册新的客户公开路径或响应类型；
- 自己实现选渠、重试或 Affinity；
- 创建 Provider 专属 Task 表；
- 自己维护幂等 claim、资金状态或退款补偿；
- 在请求 goroutine 内复制另一套长期轮询状态机；
- 因 Provider 返回字段不同而修改全局 `ImageRequest`；
- 静默删除、钳制或改义客户已发送字段；
- 把 Provider 模型或任务 ID 暴露给普通客户。

## 7. Moxing 收敛

### 7.1 当前精确事实

当前保留的 Moxing 图片履约包括：

| 客户模型 | Provider 模型 | 创建路径 | 特殊点 |
| --- | --- | --- | --- |
| `seedream-5-moxing` | `seedream-5-0-260128` | `/v1/images/generations` | 可同步 `data[]`，也可能返回任务；URL 参考图；`2K/3K` |
| `nano-banana-2` | `gemini-3.1-flash-image-preview-usage` | `/v1/media/generations` | 媒体任务协议；URL 参考图；`1K/2K/4K` 与 `aspect_ratio` |

两者可以复用同一 Moxing 任务协议适配和通用异步机制，但客户 capability、Provider 模型、创建路径和
字段值域仍分别绑定，不能因为共享任务协议就合并为一个 SKU。

### 7.2 Moxing adapter 收窄后的职责

Moxing 只保留：

- 固定补充 `capability=image_generation`；
- `image` 与 Provider `reference_images` 等必要字段映射；
- `watermark`、`aspect_ratio` 等已发布字段的精确嵌套转换；
- `200/202` 创建信封、Moxing task ID、查询响应和 usage 解析；
- Moxing 状态和安全错误到通用结果的映射。

create attempt、Task 持久化、后台调度、终态 CAS、结算退款和 exposure 已经委托给共享 service，继续保留
该唯一权威，不做迁移式重写。剩余收敛动作是：

- 删除只服务 channel-test 的 `pollMediaTaskImage` 长轮询循环，使测试与运行时复用同一协议解析和状态语义；
- 合并 adapter 与 service 中重复的结果 URL、状态、错误和请求 ID 归一；
- 把共享 service 内固定的 Moxing 查询信封解析移回精确协议边界；
- 保留现有 relay 所需的同步 `ImageResponse` 合成，只有在替代调用路径和真实消费者全部确认后，才删除
  `mediaTaskImageSuccessResponse` 或其它 wrapper；
- adapter 只编排一次“Provider 归一结果 -> 共享 Task 生命周期”，不再拥有第二套等待或终态规则。

### 7.3 Moxing URL 参考图

Moxing 生成和 URL 参考图编辑统一使用：

```http
POST /v1/images/generations
Content-Type: application/json
```

客户端使用现有 `image` 字段提交 HTTP(S) URL。不得为 Moxing 新建 multipart edit converter、临时文件
上传服务或对象存储。客户端请求级 URL 不自动获得 Link Asset、迁移、授权或撤回语义。

## 9. 多套实现归一化

| 能力 | 当前状态或重复 | 保留的权威 | 收敛动作 | 删除项 |
| --- | --- | --- | --- | --- |
| 图片客户入口 | 原生 Images + Provider 方案设想 | 原生 `/v1/images/generations` | 所有扩展接回原生 Router/DTO | 新公共 Router/DTO 设想 |
| 同步响应 | 原生 handler + Moxing 同步合成 | 原生 `data[]` handler | Provider 只产出可交付结果 | Provider 专属客户响应 |
| 客户合同校验 | 公共 validator + capability + converter 重复校验 | capability 或原生合同边界一次校验 | adapter 只复检转换后协议 | 相同字段重复校验 |
| 异步创建 | adapter 隐式分类 +共享 attempt/持久化 | 共享 `TaskCreateAttempt` 与 `PersistMediaImageTask` | 只形式化现有创建结果边界 | Provider 内资金/attempt 编排 |
| 任务持久化 | 已由图片 service 复用共享 Task | 现有共享 `Task` 生命周期 | 保持不动，只收窄协议输入 | 新 Task 表或第二状态机 |
| 轮询 | channel-test 长轮询 +共享请求内/后台轮询 | 共享调度、Task CAS 与终态处理 | Provider 只查询并返回归一结果 | `pollMediaTaskImage` 重复循环 |
| 结果归一 | adapter 与 service 各自校验 URL、状态、错误和请求 ID | 精确协议 adapter +共享结果不变量 | 建立一次协议解析、一次公共数量/终态校验 | 重复 URL 和信封解析 |
| 结算退款 | 原生同步计费 +图片 Task 计费分支 | 原生同步计费与共享 Task 计费 | 按创建结果选择唯一责任方 | adapter 内补偿逻辑 |
| URL 参考图编辑 | JSON generations + multipart 暂存方案 | JSON `image` 字段 | 客户直接提交 HTTP(S) URL | Moxing multipart/暂存方案 |
| 标准兼容渠道 | ordinary Advanced Custom + Link 注册 | ordinary `converter=none` | 实测兼容后迁移 Ability | 无协议差异的 Link 注册 |

归一化完成后，只允许两条执行路径：

```text
原生同步 Images
原生 Images + 通用异步机制
```

两条路径共享客户 DTO、分发、日志和基础计费，不再按 Provider 增加第三条公共路径。

## 10. 实施顺序

### P0：冻结客户行为与原生黄金基线

- 冻结 `gpt-image-2` 和其它原生模型现有行为；
- 冻结已发布 `seedream-5-moxing`、`nano-banana-2` 的字段、响应、任务和计费可观察行为；
- 停止 capability v2、multipart 暂存和逐 Provider Task 扩张；
- 不修改 `relaykit/dto/openai_image.go` 来承载 Provider 私有协议。

### P1：盘点并锁定既有共享合同

先用现有测试与真实代码确认以下能力已经由共享 service 履行，禁止重写：

- attempt 恢复模板、hold 和 sending 耐久边界；
- Task 持久化、账单责任转移和客户 Task 投影；
- 请求内等待、后台轮询调度和条件终态更新；
- 数量上界、usage 安全、结算、退款和 exposure。

再用当前两个 Moxing 图片模型的真实协议锁定剩余最小输入和输出：

- 创建结果四分类；
- 通用任务状态；
- task ID、查询模板、鉴权和请求 ID；
- 结果 URL、usage 和错误；
- 同步完成、等待完成、202、unknown 和终态计费责任。

只抽取已经被真实实现共同使用的行为，不为假想取消、删除、回调或多版本协议增加接口。

### P2：从既有生命周期中拆出 Moxing 协议边界

- 保留独立 Moxing 请求/响应解析文件；
- 保留现有 attempt、Task、等待、后台调度、202 投影和计费实现，不新建“通用服务 v2”；
- 让 Moxing adapter/profile 负责冻结查询模板、构造请求并解析为最小归一轮询结果；
- 让现有 service 继续负责快照复检、Task CAS、终态、结算、退款和 exposure；
- `media_task_image_blocking` 只保留协议转换和一次编排接线，不再持有 channel-test 专用生命周期。

### P3：收窄真实调用方

1. 确认 `seedream-5-moxing` 与 `nano-banana-2` 已复用同一 Task、资金和后台调度；
2. 迁移两者共同使用的查询信封、状态和结果解析，不迁移既有 Task 数据；
3. 让 channel-test 复用同一协议解析和归一结果，不保留第二套轮询状态语义；
4. 标准兼容 Qihang 若黑盒通过，迁回普通 `converter=none`；
5. 以后新增异步图片 Provider 只新增协议 adapter/profile，不新增任务系统。

### P4：删除已证实的重复实现

- 删除 `pollMediaTaskImage` 及其只服务重复长轮询的等待、退避和状态分支；
- 在共享协议解析可覆盖全部消费者后，删除重复的 URL、请求 ID、错误和信封解析；
- 逐个核对同步 completed、持久 Task 等待完成和 channel-test 消费者后，再决定是否删除或收窄
  `mediaTaskImageSuccessResponse`，不得先删 wrapper 再补兼容分支；
- 删除已迁移调用方不再使用的 converter 分支、类型和测试；
- 删除无真实消费者的 Link 图片注册；
- 不保留 feature flag、旧 wrapper 或静默 fallback 作为“过渡保险”。

### P5：真实验证与发布

- 新实现先在测试分组和独立 Channel 验证；
- 对每条链路记录客户模型、Provider 模型、路径、请求、创建结果、轮询、终态、usage 和账单；
- 只有真实 Provider、客户账单和 Provider 账单闭合后，才开放生产 Ability；
- 回滚只切回上一份已验证 implementation/version 或关闭本轮候选，不改变原生 Images 行为。

## 11. 验收标准

### 11.1 原生路径

- `gpt-image-2` 等原生请求的 Router、DTO、分发、响应、流式和计费无行为变化；
- 普通原生请求不访问 Link publication 时，不创建 Task、attempt 或幂等 claim；
- 标准兼容 Advanced Custom `converter=none` 直接使用原生同步响应；
- Gemini 原生/Chat 图片不因本方案增加 Images 路由推断。

### 11.2 通用异步机制

- 现有 attempt、Task、后台调度、Task CAS、结算退款和 exposure 行为保持不变；
- 同步 `data[]`、`200 + queued`、`202 + task_id`、明确拒绝和网络 unknown 均进入唯一正确分支；
- Provider 请求字节发送前，适用请求的 attempt、hold 和 `sending` 已原子提交；
- 没有可信 task ID 不创建 Task；
- Task 创建、hold 转移和 attempt 完成原子提交；
- 同一终态只结算或退款一次；
- 创建结果 unknown 不自动重发、换渠道或退款；
- 结果超发、无效成功结果和不可信 usage 失败关闭并留下审计；
- 客户只看到平台 task ID、统一状态、结果和脱敏错误。

### 11.3 Provider 薄适配

- Moxing adapter 不再持有通用 Task 状态机和资金编排；
- 两个 Moxing 图片模型复用同一异步机制和协议解析，不复制轮询与结算；
- 共享 Task service 不再直接硬编码 Moxing 查询信封；新增不同异步 Provider 时无需修改资金和状态机；
- Provider 私有字段不进入公共 DTO 或普通客户响应；
- URL 参考图继续使用 JSON `image`，不存在 Moxing multipart 暂存实现；
- 新增异步图片 Provider 时，只需实现协议映射并通过共享合同测试。

### 11.4 验证命令

至少运行：

```bash
go test ./model ./middleware ./relay/channel/advancedcustom ./relay ./service -run 'ImageSKU|MediaTaskImage|GPTImage2|PersistentImage|OpenAIImageTask|ImageTask|MediaImage' -count=1
go vet ./model ./middleware ./controller ./service ./relay/...
task docs:check
task ai:check
```

如修改 `relaykit/` 或其公开 API，另外运行：

```bash
cd relaykit && GOWORK=off go build ./...
```

## 12. 风险与待闭合事项

1. Moxing `/v1/images/generations` 返回 `202` 的精确信封、错误和 usage 仍需真实账号复核；不能用状态码映射冒充同步 `200`。
2. Moxing 创建 unknown、晚成功和 Provider 实际费用需要继续与客户退款分账。
3. Qwen Image 3.0 Pro、Gemini 新模型和精确 Seedream Endpoint 仍需真实账号与账单验证；代码形状匹配不等于发布。
4. 当前共享轮询 service 仍固定解析 Moxing 风格信封和 `/v1/media/tasks/{task_id}`，不能把“生命周期已共享”
   写成“任意异步 Provider 已可无改动接入”。
5. 协议边界抽取必须基于当前真实 Moxing 两个调用方，不预先设计未出现的回调、取消、删除、注册中心或
   多版本兼容层。
6. `mediaTaskImageSuccessResponse` 同时服务同步 completed、持久 Task 等待成功和 channel-test，不是无消费者
   wrapper；只有替代路径覆盖三类调用后才可删除。
7. 当前 Link 图片代码基线仍包含重复职责；在迁移和测试完成前，不得把本文目标状态描述为生产事实。
