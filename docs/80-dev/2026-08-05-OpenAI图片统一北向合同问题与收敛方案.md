# OpenAI 图片统一北向合同问题与收敛方案

## 1. 结论

图片北向应继续使用 NEWAPI 已有的 OpenAI Images 路由，并把 Link 图片模型收敛为该合同的
**模型级子集**：

- 文生图使用 `POST /v1/images/generations`。`/v1/image/generation` 不是标准路径。
- 北向字段名、JSON 类型和字段值只采用 OpenAI Images 标准语义；Provider 私有字段和值只存在于南向适配器。
- 不接受 `1K`、`2K`、`3K`、`4K` 与像素尺寸并存的近义词，也不在北向新增
  `aspect_ratio`、`watermark` 等 Provider 方言。
- 每个客户模型显式声明它支持的标准字段和值；模型不支持的字段在选渠、计费和 Provider 请求之前
  返回稳定的 `400`，不得静默删除、钳制或改义。
- `/v1/images/generations` 不承载参考图扩展。需要参考图时，应使用 OpenAI 标准
  `POST /v1/images/edits`；在 Link edits 合同未完成之前，相应模型能力保持未发布。
- 不修改或收紧 NEWAPI 原生图片协议。Link 的发布、模型能力和失败关闭校验应隔离在 Link 专属接线中。

这个方向能使请求参数适配 OpenAI Images 标准，但当前实现尚不符合该目标；特别是当前 Link 图片
使用了非标准参考图字段和 K 档尺寸，且异步任务响应也不是 OpenAI 图片生成的原生响应。因此，在
请求与响应都完成收敛前，只能描述为“基于 `/v1/images/generations` 的网关合同”，不能宣称完整的
OpenAI SDK drop-in compatibility。

## 2. 范围和不变量

### 2.1 本方案处理

- Link 图片模型在 `/v1/images/generations` 下的请求字段、值域和模型能力声明。
- 标准尺寸到 Provider 分辨率档位、比例或宽高参数的南向转换。
- 文生图与参考图编辑的标准路由边界。
- OpenAPI、运行时 capability、客户端文档和测试的单一事实来源。
- 当前非标准合同的迁移和发布门禁。

### 2.2 本方案不处理

- 不重写 NEWAPI 原生 Images Router、DTO、Relay 或 Provider adapter 的公共语义。
- 不把 Channel、Ability、模型映射、价格或 profile 当作 Link 合同注册来源。
- 不把 OpenAI Responses API 的图片能力合并到 Images API。
- 不在本次文档工作中实现新的 `/v1/images/edits` Link 能力。
- 不把图片 Provider 的 K 档、比例、水印、负面提示词等私有参数透传给客户。

## 3. 标准基线

### 3.1 路由分工

| 客户意图 | 标准路由 | 北向媒体形态 | 本方案判定 |
| --- | --- | --- | --- |
| 纯文本生成图片 | `POST /v1/images/generations` | JSON | Link 文生图唯一标准入口 |
| 使用参考图编辑或变换 | `POST /v1/images/edits` | multipart/form-data | 参考图标准入口；需独立发布能力 |
| 在多轮模型交互中生成/编辑图片 | Responses API | Responses content | 属于另一 NEWAPI 原生协议，不与 Images 合同混用 |

`generations` 的标准请求不包含一个 JSON 顶层 `image` URL 字段。当前把 URL 或 URL 数组放入
`/v1/images/generations` 的 `image` 字段，属于本站扩展而不是 OpenAI Images 标准。

### 3.2 字段和值域原则

OpenAI Images 是“公共字段集合 + 模型级字段和值域”的合同，而不是所有模型共享一个无条件的字段
并集。北向 capability 至少应表达：

- `model`、`prompt` 等核心字段；
- 模型支持的 `size` 精确值；
- 模型支持的 `quality`、`background`、`output_format`、`output_compression`、`moderation`、
  `n`、`stream`、`partial_images`、`response_format`、`style`、`user` 等标准字段子集；
- 必填字段、默认值、数值上下界和字段组合约束；
- 同步图片响应或平台扩展异步任务响应的明确响应 profile。

具体模型不得因为 DTO 能解析某字段，就自动获得该字段的合同资格。标准本身后续变化时，应先更新
标准基线，再显式提升单个 Link SKU capability 版本。

### 3.3 尺寸标准化

北向 `size` 只接收标准像素尺寸或官方定义的标准值，例如模型实际支持的
`1024x1024`、`1536x1024`、`1024x1536` 或 `auto`。具体有效值必须来自该客户模型的 capability，
而不是一张全局枚举。

以下值不得作为同义词继续暴露：

- `1K`、`2K`、`3K`、`4K`；
- `720p`、`1080p` 等视频式分辨率；
- 单独的 `aspect_ratio` 用来补充或覆盖 `size`；
- 大小写、空白或自造缩写的宽松归一化。

南向可以把标准 `size` 转成 Provider 所需的 K 档与比例，但该映射必须由精确 implementation
版本冻结并可测试，不能由字符串猜测。

## 4. 当前仓库事实

### 4.1 当前 Link 图片 capability

`model/image_sku_capability.go` 当前注册了三个客户模型：

| 客户模型 | 当前 `size` | 当前扩展字段 | 当前参考图上限 |
| --- | --- | --- | --- |
| `seedream-5-moxing` | `2K`、`3K` | `image`、`watermark` | 14 |
| `seedream-5-qihang` | `2K` | `image` | 2 |
| `nano-banana-2` | `1K`、`2K`、`4K` | `image`、`aspect_ratio` | 10 |

这三个 capability 都使用 `newapi.images.generations.v1`，要求 `model`、`prompt`、`size`，并把
`image` 放在 JSON 生成请求中。`model/image_sku_contract.go` 对这些 K 档值和 HTTP(S) URL
参考图执行严格校验。因此这不是“文档写错但运行时已标准化”，而是当前运行时合同本身采用了
非 OpenAI 标准语义。

### 4.2 OpenAPI 与运行时漂移

`docs/openapi/relay.json` 中 `ImageGenerationRequest` 当前：

- `additionalProperties: false`；
- 未声明运行时使用的 `image` 和 `aspect_ratio`；
- `size` 仍是旧的固定像素枚举；
- `quality` 只声明 `standard`、`hd`；
- `n` 上限为 128；
- 同一路由响应声明为标准图片或异步 `ImageTask` 的 `oneOf`。

与此同时，`docs/30-engineering/图片模型API用户调用指南.md` 明确指导客户在
`/v1/images/generations` 中发送 `image` URL、K 档 `size` 和 `aspect_ratio`。这导致至少三套事实：

1. OpenAPI 声明的旧 OpenAI 字段和值域；
2. Link runtime capability 的 Provider 风格字段和值域；
3. 工程指南对非标准扩展的公开描述。

### 4.3 原生边界侵入

`relay/helper/valid_request.go` 当前在通用图片请求校验中识别 Link 图片 SKU，并限制它只能走
`/v1/images/generations`。这一接线虽然能失败关闭，但把 Link 资格判断放入了 NEWAPI 原生热路径。
目标实现应把完整判断移动到 Link 专属文件或 middleware，原生文件只保留不可避免的极窄接线点。

## 5. 目标与当前差距

| 维度 | 目标 | 当前 | 差距 |
| --- | --- | --- | --- |
| 文生图入口 | `/v1/images/generations` | 已使用 | 路径一致 |
| 请求字段 | OpenAI 标准字段子集 | `image`、`watermark`、`aspect_ratio` 扩展 | 未闭合 |
| 尺寸 | 模型级标准像素值/`auto` | `1K`—`4K` | 未闭合 |
| 参考图 | `/v1/images/edits` | generations JSON `image` URL | 路由和媒体编码不兼容 |
| 模型发现 | 可用模型与 capability 分离 | `/v1/models` 只有身份，OpenAPI 不是精确模型投影 | 缺机器可发现能力 |
| 响应 | OpenAI 标准响应，或明确声明平台扩展 | 标准图片/异步任务 `oneOf` | 不能宣称完整 drop-in |
| 权威 | runtime capability 生成文档投影 | runtime、OpenAPI、指南各自维护 | 存在漂移 |
| 原生隔离 | Link 专属校验，NEWAPI 最小接线 | 通用 validator 内有 Link 分支 | 冲突面偏大 |

## 6. 目标北向合同

### 6.1 合同分层

```text
OpenAI Images 标准基线
        ↓ 取模型级子集
Link Image SKU capability（客户语义）
        ↓ publication 绑定
不可变 Provider implementation + adapter version
        ↓ 确定性转换
Provider 私有请求
```

各层职责：

1. 标准基线定义允许进入 Link 图片合同的字段名、类型和标准值表达。
2. SKU capability 定义客户模型真正支持的标准字段、值域、默认值、组合和响应 profile。
3. publication 只发布已完成证据和端到端验证的 capability 版本。
4. implementation 固定 Provider、Provider 模型和适配器语义。
5. adapter 只做确定性转换，不创建能力、不补猜客户未选择的语义。

### 6.2 capability 最小结构

建议下一版本 capability 至少包含：

```json
{
  "public_model": "example-image-model",
  "contract_id": "openai.images.generations.v1",
  "version": "...",
  "request_fields": ["model", "prompt", "size", "n", "quality"],
  "required_fields": ["model", "prompt"],
  "sizes": ["1024x1024", "1536x1024", "1024x1536"],
  "default_size": "1024x1024",
  "field_values": {
    "quality": ["medium", "high"]
  },
  "max_output_images": 1,
  "supports_stream": false,
  "response_profile": "openai_image_response"
}
```

`field_values` 只包含 OpenAI 标准字段，不包含 Provider 参数。若某个 Provider 只能表达 `2K + 16:9`，
adapter 必须有一条经过验证的标准像素尺寸映射；无法无歧义映射时，该尺寸不发布。

### 6.3 参考图的闭合决策

在“图片均使用 OpenAI Images 标准参数”的目标下，参考图只有两个合规状态：

1. Link 显式实现并发布 `/v1/images/edits`，接受其标准 multipart 字段；或
2. 模型只发布文生图，参考图编辑保持未发布并明确拒绝。

不得继续把 JSON `image` URL 塞进 `/v1/images/generations`，也不得把这种扩展描述为 OpenAI
标准。若产品必须保留 URL 参考图且拒绝实现 edits，则应承认它是独立 Link 扩展合同，并使用独立
namespace/route，而不是污染标准 generations 合同。

### 6.4 响应兼容性

OpenAI Images 标准生成调用返回图片结果；当前 Link 允许同一路由返回异步任务。目标需要明确二选一：

- 要求完整 OpenAI drop-in：该 Link SKU 必须在路由上返回标准 `ImageResponse`，内部异步性不得改变
  客户响应合同；做不到的 Provider 不在该合同发布。
- 保留平台异步响应：请求字段可以 OpenAI-compatible，但响应是 Link extension；OpenAPI、SDK 和文档
  必须显式标注 response profile，不能宣称完整 OpenAI 兼容。

在“不改变当前 NEWAPI 协议与能力”的约束下，近期应采用第二种描述，并把是否升级为完整同步兼容
作为独立产品决策，不能在南向适配器中偷偷改变。

## 7. 客户调用规则

客户应按模型 capability 稀疏序列化，只发送实际选择的字段。示例：

```json
{
  "model": "example-image-model",
  "prompt": "一座雨夜中的未来城市",
  "size": "1536x1024",
  "n": 1
}
```

客户端不得：

- 发送 `size: "2K"` 再依赖中转站猜测宽高比；
- 同时发送 `size` 与 `aspect_ratio`；
- 在 generations 中发送 `image` URL；
- 发送 capability 未声明但 DTO 恰好能解析的字段；
- 依赖中转站静默忽略字段或替换为 Provider 默认值。

`GET /v1/models` 继续只回答当前 Key 可见的模型身份和 endpoint type，不增加 Link 私有字段。精确
capability 应通过由运行时 registry 生成的 OpenAPI vendor extension 或独立静态能力文档提供。

## 8. 迁移方案

### P0：冻结目标合同

- 停止为 Link 图片新增 K 档、`aspect_ratio` 或 generations 参考图扩展。
- 将现有三个模型标为待迁移合同，不再把当前 `public-image-contract-v1` 描述为 OpenAI 标准。
- 冻结现有 publication 和调用量基线，识别依赖非标准字段的客户。

### P1：建立标准 capability v2

- 以独立新增文件定义 OpenAI Images 标准字段基线和模型级 capability v2。
- 增加 `DefaultSize`、标准字段值域、组合约束和 `ResponseProfile`。
- 为每个 implementation 建立“标准尺寸 → Provider 参数”的显式转换表和版本/hash。
- 若 Provider 证据不能证明映射，保持 SKU 未发布。

### P2：隔离 Link 校验

- 将 Link 图片完整校验迁入 Link 专属 middleware/service/adapter 文件。
- NEWAPI 原生 validator 只保留完成路由接线所必需的窄调用，不改变原生模型行为。
- 不允许普通模型映射或 Channel 配置使模型自动获得 Link 合同资格。

### P3：收敛 OpenAPI 和客户端文档

- 从 runtime capability 生成模型级 OpenAPI vendor extension，避免手写第二份值域。
- CI 对 runtime capability 与文档投影做精确深比较。
- 修订图片用户指南，移除 K 档、generations `image` URL 和 `aspect_ratio` 示例。
- 明确参考图 edits 的发布状态，以及异步 response profile 是否为 Link extension。

### P4：客户迁移和切换

- 对旧合同提供有截止日期的显式迁移窗口，不在服务端长期接受双值域。
- 给出每个旧 K 档在精确模型上的唯一标准尺寸替代；不存在唯一映射时要求客户重新选择。
- 新旧 capability 使用不同 publication version；不得按请求内容猜测合同版本。
- 完成调用方迁移、Provider 黑盒验证、计费和响应回归后再切换 publication。

## 9. 验收标准

- `/v1/images/generations` 的 Link 请求只接受模型 capability 声明的 OpenAI 标准字段和值。
- `1K`、`2K`、`3K`、`4K`、`aspect_ratio`、`watermark` 和顶层 `image` 被稳定地在 Provider
  请求与计费之前拒绝。
- 每个标准 `size` 到 Provider 请求的转换唯一、可测试，并固定到 implementation/adapter 版本。
- `/v1/images/edits` 未发布时，参考图能力不出现在模型 capability；发布后只接受标准 edits 合同。
- runtime capability、OpenAPI 投影和用户指南不存在模型字段或值域漂移。
- `GET /v1/models` 响应结构不变。
- NEWAPI 原生图片模型、路由、DTO、Relay 和现有回归测试行为不变。
- `n` 等计费乘数在请求边界使用项目统一上限校验，预扣与结算不发生溢出或负收费。
- 异步响应若继续存在，OpenAPI 和 SDK 明确标为 Link extension，不宣称完整 OpenAI drop-in。

## 10. 尚未闭合的事项

1. 三个现有客户模型分别支持哪些 OpenAI 标准像素尺寸，仍需用精确 Provider 模型和账号黑盒验证。
2. 当前 K 档是否能一对一迁移为标准像素尺寸，不能仅凭档位名称推断。
3. Link 是否正式发布 `/v1/images/edits`，以及 URL 参考图如何转换为标准 multipart 输入，需单独设计。
4. 图片异步 Provider 是否保留同路由 `ImageTask` 响应，还是只发布可返回标准 `ImageResponse` 的实现，
   需要产品合同决策。
5. OpenAI 标准随模型演进，生成投影必须带 capability version，不能让文档更新隐式改变已发布合同。
