### 原因一：历史尺寸倍率被误当成未知计量单位（5 条，已修复）

日志 74504、74508、74526、74529 保存了冻结表达式：

```text
v1:tier("base", param("_task.duration_seconds") * 145689.000000 * param("_task.size_multiplier"))
```

退款 74528 通过完整用户、应用、Key、渠道、模型和 Task 身份匹配，从冻结 Task 132 取得相同表达式。
公共分类器已识别 `_task.duration_seconds`，却把 `_task.size_multiplier` 归为不明参数，
使 4 笔初始消费和 1 笔退款都保持 unknown。

历史提交 `0169fd5a9` 的 `relay/channel/task/doubao/billing_probe.go` 将尺寸注册结果的
`size.Multiplier` 写入该字段；同提交 `thirdparty/mediaarrays/size.go` 定义其为尺寸倍率。
当前 `pkg/seedancebilling/contract.go` 也明确记录这一旧字段的倍率性质，同时禁止新合同使用它。
它是无量纲倍率，不引入第二种计量单位。仅解析已冻结表达式时，把它列入已知条件/倍率，
仍须有明确的秒数依据才能判为按秒；仅有尺寸倍率、客户自定义同名字段、未知参数、混合秒数/Token
或未声明的 `u()` 单位仍保持未知。没有修改今天的计价合同、倍率值或实际费用。

### 原因二：早期任务关系未满足当前完整身份条件（14 条，保留未知）

- 用户 80 的 9 条消费：21706、21905、21914、21934、21966、21990、21992、22021、22449。
- 用户 91 的 4 条消费：22816、23726、23805、23816；以及退款 23727。

13 条消费均有上游请求标识，可在同用户、Key、渠道下找到唯一候选 Task（17–29）；这比仅按时间、
金额匹配更强。但日志未保存 Task ID 或表达式，候选 Task 的 `app_id` 和私有应用身份均缺失，
也没有对应 durable create attempt。当前初始关系补修工具要求完整身份和已转移持款，不能直接应用。
退款 23727 有显式 Task ID，其 Task 27 的表达式包含 Token 计量依据，但应用身份同样缺失，
现有按 `user_id + app_id` 查询的补证路径按规则不采纳它。

因此这些是“有候选历史证据、尚未满足正式补证条件”，不是宣称事实永远无法恢复。
需要另行核准旧应用归属和历史关联证据后制定补证；本轮不填造 app_id，不放宽应用隔离，
不把候选 Task 或当前价格直接当成正式账单事实。

### 原因三：缺少可用任务关联及计价依据（3 条，保留未知）

用户 80 的日志 20156、20222、20223：只有任务标记、零 model_price、组倍率和视频入口等信息；
没有 Task ID、上游请求标识、冻结表达式或有效 Token 用量。普通网关 request_id 本身没有对应的
冻结任务关系，不能按模型名、相同金额或邻近时间代替归属证明。

初始日志的 `is_task` 实际是 JSON 布尔 true。把它兼容成数字 1 不会解决这些记录；
零 model_price 加正向消费也不能证明按次。三条继续保持未知。

## 生成按钮禁用的后续核验与入口补齐

本地实际库只读核验：`BillingStatementVersionEnabled=true`，维护控制行 enabled=0、generation=1；
用户 91 和 80 的 8 月没有来源保留核验记录，也没有正式版本。缺记录被读取为 `retention_status=unknown`，
前端据此禁用“生成待确认版本”。计费方式未知条数不参与该按钮的禁用判断。

原后端已有 Root 专用来源核验接口 `/api/billing/admin/customer-statement-source-verification`，
界面只提示核验却没有完成入口。现以新增 `statement-source-verification.tsx` 复用项目 ConfirmDialog，
为超级管理员提供“核验账单来源”，填写非空核验依据并提交既有接口；普通管理员显示联系超级管理员的
说明。同库条件失败显示原因；来源已标为 partial 时保留阻断，页面不提供直接覆盖入口。
成功登记后刷新服务器状态，符合条件才启用生成；失败保持禁用并保留输入，不乐观改成完整。
客户、月份切换重置核验表单，不继承前一范围的依据。接口权限、数据库屏障及资金路径均未修改。

登记是人工核验结论，必须核对备份、日志保留记录和已知金额差异，不能以当前汇总等于明细代替证明。
既有后端登记会推进维护代际，使登记前的待确认草稿需要重新生成；页面明确提示此影响，已确认版本保留。
生成后的计费解释缺项可由管理员阅读并知悉后确认；确认文案不再把“有日志记录”直接称为“金额完整”。

再次只读检查原持款清单：用户 91 的 8 月 **5 笔 / 3,667,520 quota（USD 7.33504）**初始日志仍为零，
尚未在实际本地源库补正。这与计费方式未知的 5 条不是同一组问题。正式确认前仍需对已知金额差异逐笔
核验、批准和处置；本轮没有代填核验依据，没有登记 intact，也没有生成或发布账单。

部署时前端与匹配的后端共同升级，使用目标环境自己的核验依据和既有权限接口；不复制本地核验状态。
推荐顺序为：先核验/处置金额差异 → 超级管理员登记来源核验 → 生成待确认版本 → 审阅金额及缺项 →
确认发布。应集中完成相关来源核验后再生成草稿，避免后续核验使较早草稿失效。

前端回归先证明入口缺失失败，再验证登记成功后解锁、空白依据不提交、非 Root 不显示入口、失败保留输入、
跨库阻断、既有部分解释可知悉后确认，以及接口的客户/月份参数。两文件共 16 项测试通过，类型检查和
涉及文件 lint 通过；中英文文案通过项目脚本写入并完成同步。

账单前端模块完整回归 17 文件 / 99 项测试及生产构建通过；生成的文档、品牌产物校验通过。
本轮只补齐现有核验流程的界面和说明，实际库的来源状态仍未登记，资金和历史账单未修改。
