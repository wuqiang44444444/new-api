## 目标

存放编码过程中临时产生的问题分析、排障记录、实施方案和验证记录，作为当日工作的可追溯草稿区。

## 放什么

- 带日期的问题分析、临时实施方案和排障记录；
- 真实 Provider、接口、账单或页面的阶段性验证记录；
- 尚未形成长期事实、但后续工作仍需要追溯的开发上下文。

## 不放什么

- 当前有效的产品、架构、工程或运维事实，分别放入 `10-product/`—`40-operations/`；
- 路线图、跨批次阶段计划和正式变更记录，放入 `50-planning/`；
- 长期 UI/UX 规范，放入 `90-ui-ux/`；
- 已完成的原文在事实收敛并获得用户明确授权后才能移动到 `99-archive/`；不得在本目录复制归档原文。

## 命名格式

- 文件名必须使用真实日期前缀 `YYYY-MM-DD-中文主题.md`；
- 日期表示文件首次形成的日期，不因后续编辑而改名；
- 主题必须说明具体问题、实施或验证对象，避免 `TODO.md`、`记录.md`、`最终版.md` 等含糊名称；
- `README.md` 是唯一不使用日期前缀的文件。

## 内容格式

增量文档至少包含以下三段，标题可按主题继续细分：

1. `问题与目标`：说明触发原因、范围和本次要解决的结果；
2. `当前实际情况`：区分已验证事实、假设、外部证据和未确认项；
3. `优化方案`：说明拟采取的动作、验证方式、风险和剩余事项。

真实测试记录必须标出环境、Provider、请求形状、可公开的结果摘要和结论，不保存密钥、完整签名 URL、
Task 私有数据或未经脱敏的原始响应。

## 编写要求

- `30-engineering/` 回答“以后开发者应该怎么做”，本目录只回答“本次具体问题分析、实施和验证了什么”；
- 每日复核当天增量：稳定产品、架构、工程、运维和 UI 事实分别收敛到对应事实目录，未完成事项进入
  `50-planning/`；
- 每周复核滞留文件，删除失效链接和已被取代术语，并列出等待用户授权的归档候选；
- 未经用户针对当前任务明确授权，不读取或更新 `60-marketing/`、`70-research/`、`99-archive/`；
- 不把代码完成或单元测试通过写成真实 Provider、真实账单或生产灰度完成。
