# 01 计费与分组运维手册

## 1. 操作入口

| 操作 | 后台入口 |
| --- | --- |
| 模型价格 | 系统设置 → 计费与支付 → 模型定价 |
| 分组、折扣、自动分组 | 系统设置 → 计费与支付 → 分组定价 |
| 渠道所属分组与模型 | 渠道管理 |
| 用户身份分组 | 用户管理 |
| API Key 分组与模型限制 | 令牌管理 |
| 扣费核对 | 用量日志 |
| B 端用户模型合同 | 客户合同总览，或用户管理 → 行操作 → 管理模型合同 |

所有价格都配置在客户端使用的公开模型名上，不配置在渠道映射后的上游模型名上。
合同客户的配置、倍率影响提示和回滚步骤见[用户模型合同运维手册](10-用户模型合同运维手册.md)。

## 2. 模型价格

### 2.1 选择计费方式

| 场景 | 计费方式 | 填写内容 |
| --- | --- | --- |
| 文本、按 Token 结算 | 按 Token | 输入、输出、缓存及多模态的 `$/1M Token` |
| 图片、按次任务 | 按次 | `$/次` |
| 按分辨率、输入类型或阶梯结算 | 动态表达式 | 已审核表达式；异步任务另填预扣 Token 上界 |

单次请求使用一种生效的推理计费方式。动态表达式启用后，推理使用表达式价格。支持小时存储的模型可以另设小时存储价格。

最终消费价按以下口径核对：

```text
模型基础费用 × 有效消费分组倍率 × 请求规格倍率
```

充值倍率不参与调用扣费。

### 2.2 配置步骤

1. 新增或编辑公开模型名。
2. 选择计费方式。
3. 填入已审批价格。
4. 异步动态计费模型填入预扣 Token 上界。
5. 保存后在模型广场核对基础价和分组价。
6. 使用测试分组发起一次请求，在用量日志核对公开模型、计费方式、分组、倍率和最终费用。

### 小时缓存存储费

在「模型管理 → 编辑模型 → 价格」填写**小时缓存存储表达式**，或通过模型价格接口在同一模型的 `pricing` 中保存
`billing_setting.storage_hourly_expr`。示例中的 `0.0025` 是美元／百万 token·小时，表达式返回美元金额。

```text
tier("storage_hourly", u("storage_token_hours") * 0.0025 / 1000000)
```

保存小时存储价格后，直连火山方舟且公开模型已绑定到 `doubao-seed-2-1-lite-260915` 的已启用渠道默认受理
显式 Session。选渠沿用已有模型、分组和渠道权限。已绑定合同的 Key 按合同授权选择渠道，接入分组内符合条件的
无合同 Key 也可发起收费 Session。普通调用继续执行站点既有的合同策略。系统无需设置 `ARK_PREFIX_CACHE_PILOT`。
已有的观察或专用渠道配置会继续优先适用。

客户以普通 API Key 调用 `POST /v1/responses`，提供 `caching.type=enabled`、`store=true`、纯文本
及 `Idempotency-Key`。首轮传 `expire_at`，有效期上限 30 分钟，续接传上轮返回的
`previous_response_id`。使用 `DELETE /v1/responses/{response_id}` 提前结束已确认的生命周期。
默认每 Key 最多 8 个活跃写入和 100 quota 存储预留，同渠道共享每个 UTC 自然小时 8 次写入许可。

此计量版本按平台保留量收费。每轮采用可信回执的输入量减去读取命中量，再加输出量，按每个与该轮有效
生命周期相交的闭合自然小时计一次。使用日志及月账单显示「缓存存储费」、账期、用量、冻结单价与金额。
按冻结表达式精确计算每笔的累计存储金额，预留向上取整，实扣按四舍五入得到 quota。
采用人民币单价时可通过 `usd_exchange_rate()` 使用系统汇率。价格与汇率变更适用于之后受理的写入。
清空表达式停止新的收费写入，已受理写入沿用冻结价格补结。
未配置小时缓存存储表达式的模型沿用原生请求处理。

### 按尺寸分档的图片单张价

先确认图片入口接受像素尺寸，并已使用按张分档计费。在目标版本验证价格试算及读回后，由管理员显式导入
可识别的旧价表或选择对应价表，逐格核对 USD/张金额，通过版本化价格入口保存。带请求倍率的配置继续用原公式编辑。

试算覆盖 1024/1025、2048/2049、4096/4097 的选档边界、横竖互换、字面档、`auto`、缺省尺寸与质量，
以及超界和未识别输入。对 JSON 与 multipart 各核对一次已冻结的计价输入。支持多张的模型验证预扣两张、
实际结算一张。试算金额用于价格核对，真实输出尺寸和供应商账单使用独立证据。规则见
[计费表达式架构](../20-architecture/账单计费-计费表达式与协议探针架构.md#按图片尺寸分档的价格编辑)。

第 2.3.0—2.6 节保留的供应商差异模板只用于理解旧配置，不再作为当前 Seedance 标价依据。
新配置与人工改价均使用本节费率和已登记模型的可信实测 Token 合同。

- 终态 `usage.completion_tokens` 大于 0；

- 最终费用按真实 Token 结算；
- 没有进入 `debt`。

暂停该模型新受理并补核 Provider 账单。若业务改为固定价，需审批新的 USD 表达式，只影响后续任务。

#### Seedance 媒体模式修正的发布核对

墨行统一协议整合同时修正了 Seedance 共享媒体事实函数；影响范围包含使用该函数的官方线路新请求。
含非空视频或音频参考时，共享探针的 `input_mode/control_mode` 为 `multi_modal/reference`，任务动作
显示为“参考生视频”，不再因缺少图片被识别为纯文本。纯音频仍保持 `has_video_input=false`，
`generate_audio` 继续表达输出声音开关。TokenSave 的协议专属探针保留 `multi_image/reference`；
其它具有独立探针处理的协议应以其实际结果为准，不把共享值机械套用到全部线路。

发布前，核对启用客户模型的计费表达式是否读取 `_task.input_mode` 或 `_task.control_mode`。
对依赖这两个字段的表达式，使用纯文本、参考图、无图视频参考、纯音频及混合媒体样例检查命中档位，
特别检查只列举 `text/single_image/multi_image` 的条件和默认分支。按现有价格政策确认
`multi_modal/reference` 的预期金额；必要时调整表达式，不自动改价，也不增加协议 fallback。
仅依赖 `has_video_input` 的价格分支不因这两个模式字段的修正而改变。

发布后抽查新任务的冻结探针、价格档位和账单。旧 Task 继续使用创建时冻结的 BillingProbe、表达式
及分组比例；不得批量重算或回写历史探针。代码回归通过不替代部署环境中的价格配置核对。

### 2.4 TokenSave doubao Seedance 2.0 按秒模板

TokenSave 客户模型为 `doubao-seedance-2-0-260128-tokensave`，按输出秒数、分辨率和图片控制类型
列价。当前协议只开放文字和图片参考；Provider 完整报价中的视频输入档位只保留在 research 文档，
不进入当前运行时表达式。

将计费方式设为“动态表达式”，并使用以下 USD 表达式；下面保留底稿系数，完整结果除以一百万：

```text
(
u("resolution") == "1080p"
  ? tier("1080p", u("duration_seconds") * 364700)
  : u("resolution") == "720p"
    ? (u("input_mode") != "text" && u("control_mode") != "reference"
      ? tier("720p_image", u("duration_seconds") * 146100)
      : tier("720p_text_or_reference", u("duration_seconds") * 146200))
    : tier("480p", u("duration_seconds") * 67900)
) / 1000000
```

该表达式只覆盖当前已发布的文字和图片输入档位。该协议仍要求配置 Token 预算，但此表达式不读取它，不参与最终
价格，填写 `1`。按秒结算只读取冻结请求探针，不依赖 Provider `usage`。

智能时长 `-1` 在预扣阶段按 15 秒上界处理。生产启用前至少各跑一次文本、首帧、参考图和拟开放
分辨率，并将平台扣费与 Provider 账单逐项核对。

### 2.5 FunCloud Seedance 四模型 Token 价格

FunCloud 不再使用旧 Standard/Fast 按秒价或通用模型别名。四个独立客户模型都配置为
`tiered_expr`，单位为 USD/百万 completion tokens：

| 客户模型 | 无视频输入 480/720 | 无视频输入 1080 | 有视频输入 480/720 | 有视频输入 1080 | 预扣 Token 上界 |
| --- | ---: | ---: | ---: | ---: | ---: |
| `seedance-2-funcloud` | 6.74 | 7.48 | 4.11 | 4.55 | 920000 |
| `seedance-2-fast-funcloud` | 5.43 | 不支持 | 3.23 | 不支持 | 420000 |
| `seedance-2-mini-funcloud` | 3.37 | 不支持 | 2.05 | 不支持 | 420000 |
| `seedance-2-5-funcloud` | 10.26 | 不支持 | 6.16 | 不支持 | 860000 |

表达式使用 `u("has_video_input")`、`u("resolution")` 与 `tier(name, value)` 选择上表档位，
实测计量为 `u("tokens")`，各档位金额为 `u("tokens") × 单价 / 1000000`。下列只是费率选择示意，
保存时必须写成完整的 `tier()` 表达式：

```text
seedance-2-funcloud      = (has_video ? (1080p ? u("tokens")*4.55 : u("tokens")*4.11) : (1080p ? u("tokens")*7.48 : u("tokens")*6.74)) / 1000000
seedance-2-fast-funcloud = (has_video ? u("tokens")*3.23 : u("tokens")*5.43) / 1000000
seedance-2-mini-funcloud = (has_video ? u("tokens")*2.05 : u("tokens")*3.37) / 1000000
seedance-2-5-funcloud    = (has_video ? u("tokens")*6.16 : u("tokens")*10.26) / 1000000
```

不得使用 `duration_seconds` 改回按秒计价，也不得使用当前价格重算历史 Task。可信成功终态直接使用
查询响应的 `completionTokens`；缺失、类型错误或非正数时任务必须进入
`RECONCILIATION_REQUIRED` 并保留预扣，不估算、不退款。上报值超过协议信任上界（adapter 按冻结
探针推导，≥2.4 倍实测余量）时按合同违例进入 reconciliation，`FailReason` 自带脱敏原因。

预扣上界只决定创建时暂挂金额，按满规格真实用量 × 1.25–1.3 余量取值（实测 token 速率
480p ≈ 10.1k/s、720p ≈ 21.9k/s、1080p ≈ 48.7k/s）；不要把预扣上界当作成功证据上限或结算上限——
真实费用高于预扣时系统自动对冻结资金来源原子补扣差额，客户资金确实不足时任务进入可重试 `debt`
（业务任务保持 `SUCCESS`），补足额度后补偿扫描按冻结目标补扣一次并转 `settled`。配置通过管理台
选项入口更新即时生效；直接改数据库需要重启进程，且只影响新任务的创建时冻结值，不解冻存量任务。

部署含差额补扣的版本后，核对应有 `debt` 记录是否按冻结目标转为 `settled`、差额日志是否一次且
仅一次；失败终态任务确认已原子退款，不被错误标为 `settled` 保留预扣。

运维人员只在管理员日志 `other.admin_info.provider_billing_evidence` 核对 Token 来源
`completionTokens`、Provider 报告 Token 和可选的原始 `pointConsume`。生产开放前必须逐模型、输入
类型、分辨率和账号与 FunCloud 后台 Token/美元账单核对。

上述客户模型均使用 `tiered_expr`。下式沿用表中底稿系数，最终除以一百万输出 USD：

```text
(
tier("base", u("duration_seconds") * <表达式系数>)
) / 1000000
```

Pro PI 表达式不使用 duration，例如 `tier("base", 2.185335)` 只计算一次固定 USD 价格。`default` 分组消费倍率 `1` 作用于最终扣费。
历史配置中出现的 `size_multiplier` 只作为存量表达式兼容字段，当前运行时恒为 `1`；新表达式不得依赖它。
价格配置不自动证明 Provider 实际成本、利润、税费或失败暴露已经闭合，也不会建立模型 publication 或
size evidence；Provider 成本继续使用独立账单证据对账。

### 2.7 Seedance u() 表达式迁移与发布窗口

Seedance 新受理和所有价格保存统一使用 u() 美元合同（字段与单位见架构文档）；旧 `c/_task`
当前价格必须在恢复受理前迁移，只有已创建 Task 的历史快照继续按冻结事实履约。固定价也按 USD
填写，例如 `tier("fixed", 0.5)` 表示 $0.5。批量迁移走离线工具与维护窗口，在线路径不自动转换：

1. **只读预检**：`go run ./cmd/seedance-p0-inventory -dsn <快照>` 输出精确客户价格键的模式、
   表达式、预扣、依赖与未完成资金矩阵；该工具只读本地 SQLite 快照，不能以不完整快照宣称已覆盖
   生产库或证明存量资金为空。
2. **转换预览**：输入必须是切换前的旧计价快照；禁止对已迁移配置二次转换，常量表达式无法从语法识别单位。
   `go run ./cmd/seedance-price-migrate -dsn <快照>` 按原算术顺序替换输入，再将完整结果除以一百万，
   逐模型比较 USD、最终整数 quota、档位及规则追踪；只完整枚举实际引用字段的条件组合，保留相关中间枚举值；超出验证规模则转人工。`converted/blocked/manual` 分类中，blocked 与 manual 模型不得进入自动批次，
   人工重写并单独验证。动态调用、未声明字段、无法保持规则追踪、价格或必要预算缺失均不得跳过。
3. **生成批次**：`-emit changes.json` 输出每模型 `expected_version` 变更与恢复清单；版本冲突时
   整批停止，由管理员重新生成，不强制覆盖。
4. **维护窗口应用**：暂停 Seedance 新视频受理与价格/渠道/插件写操作，等已入入口请求结束并核对
   prepared/sending/unknown attempt、awaiting_usage、debt 与退款补偿，旧业务与资金依赖完成后才切换；全节点部署候选版本后，
   用新版本保存器在事务中应用批次（旧版本保存器拒绝 u()，不得先在旧进程写入），再恢复受理。
5. **回退**：未应用新配置时撤销部署即可；已应用且无新受理时，在入口隔离下回到可校验旧合同的版本，
   用恢复清单按价格事务与版本校验精确恢复（新保存器不会接受旧表达式）；
   已有新任务时保留能识别新快照的版本完成结算，不回滚整个数据库、不把新任务改写为旧快照。
6. **验收**：恢复受理前先以受控账号验证预扣、成功、缺用量等待与退款全链路；逐类检查账单分类
   （token/enum/boolean 可识别，秒数与混合计量保留 unknown，日志修复命令继续拒绝非 Token 分类）。

## 3. 分组与折扣

### 3.1 字段口径

| 配置 | 用途 |
| --- | --- |
| 消费倍率 | 该计费分组的默认调用倍率 |
| 充值倍率 | 该用户分组的充值倍率，不参与调用扣费 |
| 用户专属倍率 | “用户身份分组 × 计费分组”的消费倍率覆盖 |
| 用户可选 | 是否允许用户创建该分组的 API Key |
| 自动分组 | `auto` Key 的选组顺序 |
| 特殊可用分组 | 给指定用户分组增加或移除可选分组 |

用户专属倍率是覆盖值，不与普通消费倍率再次相乘。

### 3.2 配置普通分组

1. 在“分组定价”新增分组。
2. 填写消费倍率。
3. 按需填写充值倍率。
4. 需要用户自行选择时开启“用户可选”并填写说明。
5. 在渠道管理中把目标渠道加入该分组。
6. 保存并使用固定到该分组的测试 Key 验证。

### 3.3 配置专属折扣

仅 VIP 使用某分组时打折：

```json
{
  "vip": {
    "economy": 0.6,
    "premium": 0.9
  }
}
```

`vip` 使用 `economy` 时最终消费倍率为 `0.6`，不是普通倍率再乘 `0.6`。

### 3.4 GLM 六折、GPT 七折

| 需求 | 操作 |
| --- | --- |
| 所有用户统一折扣 | 将每个 GLM 公开模型价格乘 `0.6`，每个 GPT 公开模型价格乘 `0.7` |
| 分渠道池折扣 | 建立 `glm-discount`、`gpt-discount`，消费倍率分别为 `0.6`、`0.7` |
| 仅 VIP 折扣 | 两个分组普通倍率设为 `1`，在用户专属倍率中分别覆盖为 `0.6`、`0.7` |
| 一个 Key 调两类模型 | 将 Key 设为 `auto`，并按顺序配置两个自动分组 |

使用自动分组时，GLM 渠道只能进入 GLM 分组，GPT 渠道只能进入 GPT 分组。模型能力未隔离时不要上线。

## 4. 上线验收

- [ ] 价格配置在公开模型名上。
- [ ] 每个模型只启用一种计费方式。
- [ ] 异步动态计费已配置足够的预扣 Token 上界。
- [ ] 普通倍率、专属倍率和充值倍率未混用。
- [ ] `auto` 分组顺序和模型隔离正确。
- [ ] 测试用户与普通用户均完成对照请求。
- [ ] 用量日志中的公开模型、计费分组、倍率、Token、档位和最终费用正确。
- [ ] 失败、取消和超时任务只退款一次。

## 5. 回滚

1. 先从生产分组移除目标模型或渠道。
2. 动态计费异常时改回最近一次已验收的固定价。
3. 恢复最近一次已验收的分组倍率。
4. 保留在途任务和计费日志，不删除任务记录。
5. 对 `debt`、重复退款或价格倒挂逐笔对账后再恢复流量。

## 6. 用户累计消费启动校正与回退

单实例（旧实例已退出）、主库与日志同库的部署升级到含启动校正的版本后，系统在开放业务前自动执行
历史累计校正（政策 `recorded-refunds-v1`），无需逐用户生成清单或手工运行修复命令。主库与日志分库
或 ClickHouse 拓扑不执行校正，受影响用户累计展示「用量待核对」。

**部署验收顺序：**

1. 确认旧单实例已退出后部署新后端与前端；启动自动执行容量检查与统计迁移。
2. 查看启动汇总 corrected / unchanged / blocked；存在 blocked 时按启动日志中的用户原因定位，
   异常修复后需重启重新评估（无运行期自动重试）。
3. 核对目标用户在首页、用户搜索、详情三处累计一致，余额与请求数未因校正改变。
4. 新增正常业务后再次查询应显示最新累计；重启不重复扣减，已有成功审计保持。
5. 生产库实际校正结果核对完成前，不宣称线上累计金额已修复。

**回退（仅逆转本次统计变更）：**

```bash
go run ./cmd/repair-user-usage -dsn /path/to/source.db -user-id <ID> \
  -operator-id <OP> -confirm-stop-write -backup /path/to/new-backup.db -rollback-recorded
```

只允许逆转负差额；当前累计、日志、Task、交付与原审计基线不满足原约束时拒绝。回退后再次启动
不会自动把金额减回去，而是显示待核对。生产 DSN 与凭据不得写入文档或脚本；离线 `-apply/-rollback`
仍绑定来源库与文件 SHA，仅用于例外维护。


## 客户账单历史原价回补

负责系统任务的后端主节点完成数据库迁移后，支持的关系型日志部署默认按分钟调度 `usage_report_day`。
每次按主日期及关联退款日期确定发布范围。完成时间取决于日期规模和前台负载。
重启后日账单复用已验证的写入检查点，日用量复用完成的候选，未完成的用量聚合重新计算。
在系统任务中查看日报执行与失败记录，并核对已发布日报的原价覆盖、逐笔入账金额和待核对原因。
Root 在「日报诊断」查看尚未发布的失败日期、原因和可重试时间。到期后由后台调度自动补跑，执行时间仍受
共用准入约束。账单页面显示未发布日期，导出任务显示申请时的缺口。补齐后按最新账单版本发起导出。

原价解析升级后使用同一任务自动发布新日报。通过唯一候选补齐的原价在明细和逐笔导出标注来源。
冻结合同应收与实际扣款的差额仅随报表发布，历史回补不会触发退款或钱包更正。

需要核对基线或定位缺项时，可使用本次发布制品和目标主库、日志库的只读账号盘点可追溯的北京时间日期范围。
`SQL_DSN` 和分库部署的 `LOG_SQL_DSN` 通过部署环境注入。SQLite 设置 `SQL_DSN=local`，并通过 `SQLITE_PATH` 指定带 `mode=ro` 的文件 URI。

```bash
go build -o customer-original-replay ./cmd/customer-original-replay
./customer-original-replay -from 2026-11-11 -through 2026-11-11
```

命令按日输出读取边界、旧代际、可复算笔数和不可复算原因。指定 `-user-id` 可核对指定客户。
需要定向重试时，Root 可调用 `POST /api/billing/admin/reports/rebuild`，请求体提供 `date`。

### 日报数据库预算与灰度

日报默认调度，北京时间 03:00 后优先生成已结束的昨日。今天的重算请求在该日结束后处理，待生成时可通过
使用日志核对已入库记录。应用按前台请求、结算和日志写入反馈自动调节后台批次。日报与账单明细导出共用数据库批次执行租约。
在线节点提供前台观测，健康窗口、短查询期限和调节步长由代码维护。后台数据库压力或前台观测失效时
停止启动新批，资源恢复后从已保存进度继续。普通账单接管时重读并校验已提交候选，再恢复聚合。
无发布指针且无有效候选引用的废弃数据在一小时保护期后分批清理，旧发布代际保留八天。

目标环境使用相同数据快照、数据库参数和固定的前台负载，多轮交替验证开启与停用时核心 API、结算及
日志提交的吞吐、错误率和 P95/P99。用有旧版本的大流量日和历史证据复制覆盖重建，同时记录 I/O、
WAL、连接池等待、发布耗时和核验读量。同负载对照方法见[日志与报表性能验收](../30-engineering/日志与报表性能验收.md)。隔离库已有联合发布、
暂停和接管证据，现有端到端对照尚未达到前台尾延迟放行条件。出现可复现的业务回退时按既有部署流程
回滚应用制品，验证检查点及已发布代际的兼容性。共库达不到门槛时，评估独立报表实例后重新验收。

需要恢复既有日报代际时，通过盘点记录确定原代际及目前指针。Root 调用
`POST /api/billing/admin/reports/rollback`，请求体提供 `date`、`current_generation` 和
`restore_generation`。两个代际需处于可读保留期，当前指针需匹配，并且恢复后仍覆盖同一组入账事实。
已有迟到资金事件使旧代际覆盖不足时保留当前发布结果。已确认月账单需按其更正流程处理。

### 大客户账单明细导出

- 明细导出复用现有主库连接信息，使用独立单连接池和短只读事务。执行前确认冻结发布版本仍然可读，
  任务引用的退役版本继续按既有保留规则处理。单库部署直接使用现有配置。
- 明细导出与日报共用应用内准入。前台健康时按实际处理成本自动升速，压力抬升时降速，越线时暂停。
  逐笔读取每批最多 1,000 行、两秒，低速时自动缩小批量。单客户单日明细每片最多 100 万行或 500 MB，
  全账期每片最多 50 万行或 300 MB，其他筛选范围每片最多 10 万行或 32 MiB，均以先达到的上限为准。
  分片逐行写入临时目录，保留 256 MiB 可用空间，根据可写空间提前封片。上传及游标提交完成后显示持久进度。
- 灰度比较相同峰值流量下开启和停用导出时的核心 API、结算和日志写入，并验证暂停、接管、恢复提速、
  全量分片导入及金额核对。以阶段耗时和独立对账结果判定目标环境是否可上线。

### 账单导出格式升级

- 客户按日明细版本 30 使用新的对象键和恢复规则。共享导出队列的部署应先排空并停止旧执行器，再开放新版本
  的提交入口。版本 28 执行器不支持版本 30，混跑时可能将新任务标记为格式不匹配。
- 版本 26 的旧账单任务如果已冻结来源且尚未登记导出产物，执行时会升级至新字段和简体中文。提交时的范围、
  覆盖和报表版本仍然有效。
- 发布前先让已登记 CSV 分片的旧格式任务完成，以便各分片使用同一表头。仍未完成的旧任务可通过导出历史重新生成。
  已生成的文件继续按原格式下载。

### 管理员用量记录字段迁移

新版字段版本为 28。解析脚本继续通过 `field_version` 识别版本 25，并通过「字段版本」识别版本 28。

| `customer_id`、`customer_username`、`token_name`、`token_id`、`customer_model` | 客户 ID、用户名、令牌、令牌 ID、客户模型 |
| `net_amount`、`original_amount`、`quota`、`original_quota` | 净额、原价、入账额度、折前额度 |

| `billing_mode`、`request_count`、`counts_toward_customer_bill` | 计费方式、计入请求数、是否计入客户账单 |

「用量及单价明细（USD，折扣前）」使用可读文本。依赖原 JSON 分项的脚本需调整解析入口，金额汇总可使用
净额、原价及原始额度字段。计费组、折扣计算内部状态和生成时间等技术字段从逐笔表移出。切换脚本前，用
同一账期的两版产物对比脚本读取的行数、入账净额及换算结果。

## 日报解析版本切换

1. 停止旧日报 worker 并确认旧租约已结束。核对待运行、执行中和已生成的异步日报导出，以及待投递的用量日报与客户情况日报；
   已受理的日报导出在切换前排空，无法完成的请求保留既有失败状态。停止旧日报入队后，以旧版本邮件投递器排空已授权发送的正文，等待在途投递结束。对暂时失败的邮件先恢复投递条件；决定取消时记录操作人、投递 ID、原因及数量。待办清零或逐条处置完成后再切换邮件投递器。
2. 先在隔离库用计量版本 10 和原价解析版本 12 重建已知历史日期。按来源充足、仅有冻结证据和来源不足逐日
   核对客户、Key、净额和退款。验证只恢复部分日志时保留覆盖更强的投影，完整恢复后能发布。部署后由任务按既有
   租约与资源预算推进全部已知日期，在 Root「日报诊断」核对进度。未完成的日期显示重建中，缺证日期显示来源不足。
3. 记录日志源的库类型、日期、固定上界、行数及首批和后续批次的冷暖执行计划、读块和耗时。
   核对控制台关键接口延迟、跨日退款关联、排队导出、显式旧引用与邮件去重等行为。
4. 新版代码就绪后，先用已冻结样本对五份图片旧式执行试算和回放。管理员在模型价格编辑中导入现价，
   核对每格金额及默认分支，经版本检查保存。留存变更前后配置的受保护副本、内容版本及生效时点。历史入账与
   已确认正式月账单遵循原冻结事实。日报回退只允许同一日期的当前解析版本。

生产发布时间、运行预算及真实供应商结算以部署记录和已核实的账单为准。


在切换前对主库执行以下只读盘点。该查询也可用于尚未增加邮件代际字段的旧库。

```sql
SELECT e.resource, d.status, COUNT(*) AS deliveries
FROM resource_alert_deliveries AS d
JOIN resource_alert_episodes AS e ON e.id = d.episode_id
WHERE e.resource IN ('personal_usage_report', 'platform_usage_report', 'customer_status_report')
  AND d.status IN ('pending', 'retry_wait', 'sending')
GROUP BY e.resource, d.status
ORDER BY e.resource, d.status;
```

本地切换前样本有 10 条重试中的投递（客户情况 6、个人用量 2、平台用量 2）。部署现场重新盘点。
部署前也应盘点已绑定上一计量版本的邮件。新版检查已绑定正文的计量版本与可读性，同版本普通重建可继续投递。切换后发现无法证明版本的正文时，
原记录进入 `retry_wait`，每 24 小时复核一次。按投递 ID 查看 `stop_reason = 'report_version_unavailable'` 及系统告警。遇到投递结果未知的记录需先核对投递回执，保留原去重键。
日志清理截在自然日中间时，在 Root 日报诊断中核对已发布与候选来源行数和逐笔来源。如果旧覆盖为 100 行而仅剩 80 行，
应从可信备份恢复缺少的来源，再按该日定向重建并核对客户净额、退款和分组。没有可恢复证据时保留阻断记录。
