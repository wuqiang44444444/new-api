# 请求策略：会话与重试设置手册

## 适用范围

本手册说明后台「系统设置 → 请求策略 → 会话与重试」（`/system-settings/request-policies/routing`）
页面各项设置的作用、相互关系和推荐用法。同一请求策略下的「请求检查」「渠道健康」是独立分区，不在本手册范围。

页面设置决定一次 API 请求**选哪个渠道、失败后能否换渠道、下一次请求是否回到同一渠道**。
设置只影响 NEWAPI 原生分发；Seedance、MiniMax 等 Link 专用渠道按专用合同选渠，不受会话保持、重试或故障切换影响。
原理见[渠道亲和架构](../20-architecture/渠道亲和架构.md)。

## 页面结构

页面自上而下分为四块，右上角统一保存；只提交有变化的项，保存后整页生效：

| 区块 | 作用 |
| --- | --- |
| 会话默认设置 | 会话保持总开关和全局会话模式，规则可继承或覆盖 |
| 渠道故障切换 | 渠道临时故障时自动绕开、补试、探测恢复，以及三级亲和兜底 |
| 会话规则 | 定义如何识别「同一个会话」以及该会话的保持方式 |
| 重试预算 | 单次请求失败后最多换几次渠道，哪些状态码可以重试 |

## 会话默认设置

**会话保持**让同一会话的后续请求尽量落在同一渠道，以命中上游的提示词缓存、保持上游会话状态。

| 设置 | 作用 | 默认 |
| --- | --- | --- |
| 启用会话保持 | 总开关。关闭后所有会话规则、默认 API Key 亲和与三级亲和都不读写绑定 | 开 |
| 不保持 | 规则命中后不读取也不写入绑定，按普通权重选渠 | — |
| 优先原渠道，失败允许切换 | 优先走已绑定渠道；该渠道失败时按「重试预算」换其他渠道。界面提示「会降低缓存命中率」，因为换渠后缓存不再命中 | 全局默认 |
| 必须使用原渠道 | 只走已绑定渠道，失败不重试；绑定渠道已停用或失去资格时返回 503 | — |
| 切换成功后更新会话绑定 | 开启：换渠成功后，后续请求改用新渠道。关闭：保留原绑定，后续仍回到原渠道 | 开 |
| 渠道不可用时保留会话绑定 | 绑定渠道被停用或不再满足分组、模型、合同条件时，开启则保留绑定，关闭则清除绑定后重新选渠 | 关 |
| 最多缓存会话数 | 本地内存中会话绑定的容量上限，超出按最近最少使用淘汰。配置 Redis 时绑定共享存储 | 100000 |
| 默认会话有效期（秒） | 规则 TTL 为 0 时使用的绑定有效期；每次成功请求刷新有效期 | 3600 |

会话保持开启且请求未命中任何会话规则时，`/v1/chat/completions`、`/v1/messages`、`/v1/responses`
三个入口中不引用上游状态的请求，按**认证 API Key** 建立默认亲和；该默认亲和没有独立开关。

### 会话有效期怎么选

绑定有效期是**滑动**的：每次成功请求都会把有效期重新计满，失败请求不刷新。只要会话两次成功请求的间隔
小于有效期，绑定就一直保持；超过有效期没有成功请求，绑定过期，下一次请求重新选渠。

选择时考虑两件事：

| 作用 | 有效期要求 |
| --- | --- |
| 命中上游提示词缓存 | 不短于上游缓存的保留时间即可。上游缓存一般在无访问后数分钟到一小时失效（Anthropic 默认约 5 分钟、可选 1 小时；OpenAI 通常数分钟到一小时，可选更长保留），以各 Provider 文档为准。绑定比上游缓存更长不会多命中，但也不会造成额外费用 |
| 保护依赖原上游状态的会话 | 必须长于用户正常的停顿时间。Codex CLI、Claude CLI 等客户端在停顿后继续对话时，请求可能携带只有原上游能识别的状态；绑定过期后换到其他渠道会失败或丢失上下文 |

建议：

- 全局「默认会话有效期」保持 3600 秒。过去为了「绑定卡在故障渠道」而缩短有效期，现在应改用渠道故障切换解决；
- 对只追求缓存命中、不依赖上游状态的「优先原渠道」规则，可在规则里单独设置较短 TTL，例如 600–900 秒，
  略长于上游缓存保留时间即可；
- 不要缩短内建 `codex cli trace`、`claude cli trace` 等严格规则的 TTL。360 秒只比常见的 5 分钟缓存略长，
  用户停顿超过 6 分钟就会换渠，对缓存收益很小，却会让严格会话更容易丢失上游状态。

## 渠道故障切换

用于解决「绑定渠道持续故障，会话一直卡在故障渠道」的问题。默认关闭，按渠道 ID 灰度启用。

| 设置 | 作用 |
| --- | --- |
| 故障切换模式 · 关闭 | 不记录故障证据，不改变选渠与重试 |
| 故障切换模式 · 仅观察 | 记录故障证据，并在请求决策记录中写「将绕开」等事件，不改变路由；未填灰度 ID 时观察全部渠道 |
| 故障切换模式 · 对灰度渠道启用 | 对「灰度渠道 ID」中的渠道执行自动绕开、补试、探测与受控试用；必须填写灰度 ID |
| 灰度渠道 ID | 逗号分隔的渠道 ID。只有这些渠道的故障会被接管；灰度外渠道沿用原有重试 |
| 已验证迁移对 | JSON 数组，登记经过技术验证、可跨渠道迁移的特殊请求形状（目前为 Claude CLI 的 `context_management`）。见下文 |
| 启用 API Key 和用户亲和兜底 | 三级亲和开关。见下文 |

### 什么算渠道故障

同一渠道、同一配置版本、同一客户模型、同一协议入口，60 秒内连续 3 次出现以下结果即进入冷却：

- 上游真实返回 502、503、529，且该状态码在「自动重试状态码」内；
- 连接上游失败（未收到任何 HTTP 响应）。

401–404、429、504、524、网关本地错误、客户端取消、流式 200 后中断都不计入；其中可归因的非故障结果会打断连续计数。
多 Key 渠道只记录证据，不自动绕开。渠道配置变化后旧故障记录自动失效。

### 启用后的路由行为

| 情形 | 行为 |
| --- | --- |
| 绑定渠道已进入冷却，新请求可迁移 | 首次选渠直接绕开到同档其他合规渠道，不占重试预算；没有合规备用时仍走原绑定 |
| 无显式绑定，冷却中的渠道是唯一可选渠道 | 仍按原有方式选它；渠道已探测通过时，这条请求就是它的受控试用 |
| 优先模式，失败尝试在灰度渠道上 | 当次补试排除已失败渠道，先选同优先级的其他渠道，同档无可用再降档；补试也失败或没有合规备用时，剩余预算继续按原有重试，仍尽量避开本次已失败渠道 |
| 严格模式，规则开启「严格会话的原渠道故障时允许切换」 | 未达阈值仍只走原渠道；达到阈值的那一单在尚未输出、预算允许、且有合规备用时补试一次，补试失败或没有合规备用即结束；之后的请求首次即绕开 |
| 严格模式，规则未开启该例外 | 与关闭故障切换时完全相同 |
| 备用渠道以 4xx（429 除外）拒绝迁移过去的请求 | 本次停止，不再换渠，不改绑 |
| 失败的灰度渠道本身不符合下文的合格条件（如开了请求透传、多 Key、类型不在范围内） | 不受故障切换影响，沿用原有重试 |
| 请求内容不在已登记迁移范围（媒体、未知字段、签名历史等） | 不受故障切换影响，沿用原有选渠与重试。原渠道停用或失去资格时也沿用原有行为：优先会话重新选渠；普通分发的严格会话返回 503 `strict_session_binding_unavailable` |
| 带上游状态引用（如 `previous_response_id`），但查不到可信归属 | 沿用原有路由，不进入绕开或补试 |
| 原生 Responses 已记录归属，且归属渠道在灰度内 | 固定走归属渠道；该渠道失去资格时返回 HTTP 409 `upstream_continuation_unavailable` |
| 已开始输出、已有异步任务、管理员指定渠道 | 不重放、不迁移 |

当前可迁移内容为纯文本和自包含函数工具。灰度渠道与备用渠道使用同一合格条件：类型为 OpenAI、NewAPI 或
Anthropic，单 Key，渠道和全局均未开启请求透传。全局请求透传开启时，故障切换不迁移任何请求。
备用渠道仍须满足原有的权限、分组、模型和客户合同条件。

### 恢复

1. 冷却到期后，系统任务每分钟用同协议、同模型向故障渠道发起一次流式探测，每轮最多处理 4 个故障范围；
   探测成功转为「待受控试用」。自动探测只针对单 Key、未开请求透传、且渠道自动检测范围为真实生成的渠道；
   不满足条件或探测结果无法确认时保持「待确认」，需在渠道列表「渠道故障切换」中「立即复查」或「允许受控试用」。
2. 下一条可迁移的新请求在存在合规备用、仍有重试预算时试用该渠道；没有任何其他可选渠道时，这条请求直接在该渠道试用。
   同一范围同时只有一个试用名额。
3. 试用完整成功后恢复为可选渠道；失败则重新冷却并延长间隔。中断而未确认的试用只释放名额。
4. 已迁移到备用的会话在有效期内继续使用备用渠道，避免集体回切。

探测与试用只改变路由判断，不启用或停用渠道；渠道启停仍由渠道管理和渠道健康设置负责。

### 已验证迁移对

仅当技术人员已在本环境验证某个源 → 目标方向能原样承接特定请求形状时才登记。格式：

```json
[{"source_channel_id": 86, "target_channel_id": 231, "model": "claude-opus-4-8"}]
```

- `model` 为客户请求模型；`upstream_model` 可选，默认等于 `model`，两端渠道的模型映射结果都必须等于它；
- 保存时系统自动写入两端渠道当前的配置版本。之后任一端渠道配置变化即失效，重新验证后清空
  `source_revision`、`target_revision` 再保存；
- 渠道编号属于具体环境，不能从其他环境照抄。

### 三级亲和（API Key 和用户亲和兜底）

开启后，可自由选渠的新请求按「会话 → API Key → 用户」逐级查找绑定，上一级没有可用绑定才查下一级；
绑定只在现有候选优先级层内作为偏好，不越过权限、分组和合同。覆盖文本、Completions、Embeddings、Rerank、
Moderation、音频、图片、原生 Gemini、视频与任务创建等入口；带上游资源引用的请求（如 Gemini `cachedContent`、
上传文件）沿用原有路由。开启或关闭会改变会话绑定的缓存键，已有会话绑定会各重建一次。

### 多个模型怎么配置灰度

灰度名单**只按渠道 ID 配置**，但故障判定和绕开**按「渠道 + 模型 + 协议入口」分别计算**：

- 把一个渠道填进名单，等于允许故障切换管理该渠道上的所有模型；
- 同一渠道上某个模型持续故障时，只有这个模型的请求绕开该渠道，其他模型照常使用；
- 备用渠道也按模型分别查找：同模型、同分组、符合上文合格条件。
  没有合格备用的模型，故障时保持原来的行为，不会更糟；
- 备用渠道不需要填进名单。

需要只让部分模型参与时：

| 需求 | 做法 |
| --- | --- |
| 严格会话只让某些模型切换 | 故障例外是规则级开关，规则又按模型正则匹配。给需要切换的模型单独建规则并勾选例外，其他规则不勾 |
| 优先模式只让某些模型切换 | 把该渠道按模型拆成两个渠道（同一上游、不同模型清单），只把需要的渠道填进名单 |
| Claude CLI 带 `context_management` 的请求 | 「已验证迁移对」按模型登记，只登记验证过的模型 |

### 上线步骤

1. 确认要保护的模型至少有一个合格备用渠道。
2. 模式选「仅观察」，灰度 ID 留空，运行一段时间。在使用日志的「请求决策」中按模型查看：
   - 「将绕开绑定渠道（仅观察）」：该渠道在这段时间被判定为故障；
   - 「符合条件的备用渠道」：这类请求能够切走；
   - 「没有符合条件的备用渠道」：先为该模型补备用渠道；
   - 「请求内容超出已验证迁移范围」：这类请求本身不迁移，例如 Claude CLI 的 `context_management` 请求需要先登记迁移对。
3. 模式改为「对灰度渠道启用」，灰度 ID 填各模型的主力渠道，从风险最低的模型开始。
4. 严格会话需要切换时，再编辑对应规则勾选故障例外。
5. 关注失败率和首响应延迟；异常时把模式改回「关闭」即可回到原行为。

## 会话规则

规则决定「哪些请求属于同一会话」。请求按列表顺序匹配，第一条匹配成功且能取到会话标识的规则生效。

| 字段 | 作用 |
| --- | --- |
| 名称 | 规则标识，参与缓存键时用于隔离不同规则 |
| 模型正则 / 路径正则 / User-Agent include | 匹配条件；模型正则必填，其余为空表示不限制 |
| Key 来源 | 会话标识来源，按顺序取第一个非空值：`request_header`（请求头）、`gjson`（请求体 JSON 路径）、`context_string` / `context_int`（网关上下文） |
| Value 正则 | 会话标识须匹配该正则，否则不命中 |
| 会话行为 | 继承全局默认，或单独设为不保持、优先原渠道、必须使用原渠道 |
| 严格会话的原渠道故障时允许切换 | 仅对「必须使用原渠道」生效，并需同时开启故障切换；默认关闭 |
| TTL（秒，0 表示默认） | 本规则绑定有效期 |
| 包含分组 / 包含模型 / 包含规则名 | 决定缓存键的组成：包含分组时不同分组各自绑定，包含模型时不同模型各自绑定 |
| 参数覆盖模板 (JSON) | 命中规则时合并到渠道参数覆盖，内建规则用它透传 CLI 请求头 |

内建的两条「系统默认规则」：

| 规则 | 匹配 | 会话标识 | 模式 |
| --- | --- | --- | --- |
| `codex cli trace` | `^gpt-.*$` 且路径 `/v1/responses` | 请求体 `prompt_cache_key` | 必须使用原渠道 |
| `claude cli trace` | `^claude-.*$` 且路径 `/v1/messages` | 请求体 `metadata.user_id` | 必须使用原渠道 |

系统默认规则可以编辑，不能删除；可视化编辑、JSON 编辑和服务端保存都会拦截删除。

缓存操作彼此独立：「清空该规则缓存」只清该规则的会话绑定，规则继续生效；「清空全部缓存」清空会话、
API Key、用户三层绑定；「分层亲和缓存」可单独清某一层。清缓存不影响故障记录与续接归属。

## 重试预算

| 设置 | 作用 | 默认 |
| --- | --- | --- |
| 最多重试次数 | 首次请求失败后最多再尝试几次，不含首次。`auto` 分组：令牌未开启跨分组重试时，只在选中的分组内重试；开启后沿用 NewAPI 原有设计，每个分组各自使用本预算，当前分组的优先级层用完后切到下一个分组，总尝试次数最多为（本值 + 1）× 分组数。故障切换接管后的补试不重置计数 | 视部署配置 |
| 自动重试状态码 | 上游返回这些状态码时允许重试，支持单值与区间，如 `401, 403, 429, 500-599` | 视部署配置 |

无论如何配置，2xx、504、524 都不重试（上游可能已执行）。渠道级错误总会重试；「必须使用原渠道」的会话、
管理员固定渠道的请求不重试。普通重试按序号逐级取更低优先级，可能再次选中本次已失败的渠道；
故障切换接管的补试会排除已失败渠道。

## 推荐配置

### 各项设置推荐值

| 区块 | 设置 | 推荐值 | 说明 |
| --- | --- | --- | --- |
| 会话默认设置 | 启用会话保持 | 开 | 关闭会同时停用规则、默认 API Key 亲和与三级亲和 |
| 会话默认设置 | 全局会话模式 | 优先原渠道，失败允许切换 | 兼顾缓存命中与可用性；需要严格保持的场景由规则单独设置 |
| 会话默认设置 | 切换成功后更新会话绑定 | 开 | 换渠成功后会话跟随可用渠道 |
| 会话默认设置 | 渠道不可用时保留会话绑定 | 关 | 渠道停用或失去资格后重新选渠 |
| 会话默认设置 | 最多缓存会话数 | 100000 | 按活跃会话数评估；配置 Redis 时注意共享实例的淘汰策略 |
| 会话默认设置 | 默认会话有效期 | 3600 秒 | 不为规避故障渠道而缩短，原因见「会话有效期怎么选」 |
| 渠道故障切换 | 故障切换模式 | 先「仅观察」，再「对灰度渠道启用」 | 按下文分阶段推进 |
| 渠道故障切换 | 灰度渠道 ID | 先空（观察全部），再按阶段填写 | 只填主力渠道，备用渠道不用填 |
| 渠道故障切换 | 已验证迁移对 | `[]` | 仅 Claude CLI 的 `context_management` 请求在技术验证后登记 |
| 渠道故障切换 | API Key 和用户亲和兜底 | 关 | 缓存收益与首响应延迟另行验收后再开启 |
| 会话规则 | `codex cli trace`、`claude cli trace` | 保持「必须使用原渠道」，TTL 0（使用默认） | `codex cli trace` 不勾故障例外；`claude cli trace` 在登记迁移对后再勾 |
| 会话规则 | 自定义规则 | 按场景 | 只为缓存命中的优先模式规则可设 600–900 秒 TTL |
| 重试预算 | 最多重试次数 | 5 | 覆盖同档多渠道与跨分组 |
| 重试预算 | 自动重试状态码 | `401-404,408,429,500-503,505-523,525-599` | 504、524 系统始终排除；故障判定只计其中的 502、503、529 |

### 按模型族分阶段启用故障切换

先按「上线步骤」观察，再按风险从低到高逐步把各模型族的主力渠道加入灰度名单。每一步观察失败率和首响应延迟，
稳定后再进行下一步。

| 阶段 | 模型族 | 加入灰度的渠道 | 预期效果与限制 |
| --- | --- | --- | --- |
| 1 | 全部 | 不加入，模式「仅观察」 | 只记录「将绕开」与可切换比例，不改路由 |
| 2 | 国产文本模型（GLM、Kimi、Qwen 等） | 各模型的 OpenAI 类型单 Key 渠道 | 普通对话请求无 CLI 会话状态，可直接切换；厂商原生类型渠道（DeepSeek、阿里、Moonshot 等）不参与 |
| 3 | GPT 对话 | OpenAI 类型渠道 | Chat Completions 可切换；Codex CLI 的 Responses 请求通常带加密推理或续接状态，不迁移，仍走原渠道；Azure 渠道不参与 |
| 4 | Claude | 观察期内备用充足、故障证据可信的 Anthropic 渠道 | 普通 API 文本请求可切换；Claude CLI 请求需技术验证、登记迁移对，并在 `claude cli trace` 勾选故障例外后才切换 |

不参与的情况：只有一个合格渠道的模型、只部署在 Azure 或厂商原生类型渠道上的模型、多 Key 渠道、图片等非文本入口。
它们保持原有重试行为。

具体渠道编号随环境不同，每个环境须按「多个模型怎么配置灰度」重新确认。本地开发库的逐模型分析与灰度名单见
[故障切换方案第 13 节](../80-dev/2026-11-14-渠道亲和故障切换与探测恢复方案.md#13-本地开发库渠道分析与推荐灰度配置2026-11-15)。

## 成功信号与排查

- 使用日志详情的「请求决策」逐步显示规则命中、绑定使用、选渠、失败、重试、`backup`、`rebind`、
  `trial` 等事件。失败请求只有在部署开启错误日志（`ERROR_LOG_ENABLED=true`）时才写入日志行。
- 渠道列表行操作「渠道故障切换」显示该渠道各模型与协议的当前路由状态、故障证据、下次复查和探测/试用结果；
  具备渠道操作权限的管理员可「立即复查」「允许受控试用」「暂时绕开」（需填写时长和原因）或「清除临时绕开」。
- 会话一直卡在故障渠道：确认规则是否为「必须使用原渠道」、故障切换是否启用、该渠道是否在灰度 ID 中、
  规则是否打开故障例外，以及请求内容是否在可迁移范围内。
- 发现跨授权选渠、续接请求被迁移、已输出后重放或截断响应导致改绑时，立即把故障切换模式改回「关闭」；
  关闭后恢复原有选渠与重试，已写入且合规的绑定自然过期，必要时按规则清空缓存。
