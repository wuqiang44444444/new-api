# 客户合同管理总览设计

## 1. 问题与目标

当前管理员只能在“用户”列表定位到某个用户，再从行操作打开“管理模型合同”。该入口适合已知客户的
单次配置，但不能直接回答以下运营问题：

- 当前建立过合同的客户有哪些；
- 哪些合同正在生效、处于零模型权限或已经停用；
- 每份合同有多少规则，是否存在因渠道变化而不可履约的规则；
- 最近由谁、在什么时间修改了合同；
- 如何从全局合同清单快速进入既有合同编辑器。

本次新增管理员“客户合同”菜单及全局总览页。目标是把合同从用户列表中的隐蔽行操作提升为可巡检的
独立运营入口，同时保持合同、审计、路由和计费只有一套权威实现。

## 2. 当前实际情况

### 2.1 已验证事实

- 一个客户合同严格属于一个 `User ID`，不存在独立于用户的合同主体。
- `users.contract_mode`、`users.contract_version`、`customer_model_contracts` 和
  `customer_contract_audits` 是合同状态、规则与审计的持久化事实。
- 用户列表已经返回合同模式、版本和规则数，并区分原生、生效、零权限、停用四种状态。
- 合同读取、写入、选项和审计接口均位于 `/api/user/:id/contract...`。
- `UserContractDrawer` 已完整承载规则维护、价格预览、启停、乐观锁冲突恢复和审计历史。
- 管理员只能管理角色低于自己的用户；Root 沿用既有目标用户权限语义。

### 2.2 当前缺口

- 管理员侧边栏没有合同总览入口。
- 没有只返回“已经建立过合同的用户”的分页聚合接口。
- 没有按合同状态、客户身份或公开模型进行全局检索的界面。
- 若前端逐用户调用现有详情接口拼装总览，会产生明显 N+1，并重复可用性计算。

### 2.3 不在本次范围

- 不新增法律合同文件、付款周期、发票、签署或审批工作流。
- 不改变合同折扣、渠道组、模型白名单、计费公式和异步任务冻结语义。
- 不提供合同批量启停、批量折扣或批量规则替换。
- 不把原生模式用户显示为一份合同；未建立合同的用户仍从“用户”页面建立第一版合同。
- 不新增第二套合同编辑器、保存接口、缓存或审计表。

## 3. 产品与信息架构

### 3.1 菜单位置与命名

管理员导航顺序调整为：

```text
管理员
├── 渠道
├── 模型
├── 用户
├── 客户合同
├── 账单对账
└── …
```

菜单使用“客户合同”，页面标题使用“客户模型合同”。“合同管理”过于宽泛，容易让管理员误以为页面包含
法律文件或付款条款。路由固定为 `/admin/customer-contracts`，只对管理员及 Root 可见。

### 3.2 页面结构

页面自上而下由三部分组成：

1. **状态摘要**：全部合同、生效合同、零模型权限、已停用；摘要统计不随当前分页变化。
2. **检索区**：客户/模型统一关键词搜索，合同状态单选筛选。
3. **分页列表**：展示合同运营摘要，行尾提供“管理合同”，打开现有 `UserContractDrawer`。

列表字段：

| 字段 | 含义 |
| --- | --- |
| 客户 | 用户名、可选显示名、User ID |
| 合同状态 | 生效、零模型权限、停用 |
| 规则 | 总规则数；存在不可履约规则时额外显示异常数 |
| 合同版本 | 当前 `contract_version` |
| 最近修改 | 当前版本审计的时间与管理员用户名 |
| 操作 | 打开现有合同侧边栏 |

移动端使用共享 DataTable 的卡片布局，不强制横向滚动。空状态区分“尚无客户合同”和“当前筛选无结果”。

### 3.3 状态口径

只要 `contract_version > 0` 即视为“建立过合同”，进入总览：

| 条件 | 状态 |
| --- | --- |
| `contract_mode = true` 且规则数大于 0 | 生效 |
| `contract_mode = true` 且规则数为 0 | 零模型权限 |
| `contract_mode = false` | 停用 |

原生模式且 `contract_version = 0` 的用户不进入合同列表。已删除用户不进入可操作总览；其既有审计仍按
当前数据库保留策略存在，但本页面不承担历史归档查询。

## 4. API 设计

新增管理员只读接口：

```http
GET /api/customer-contracts?p=1&page_size=20&keyword=&status=
```

参数：

| 参数 | 规则 |
| --- | --- |
| `p` | 从 1 开始 |
| `page_size` | 复用公共分页上限，最大 100 |
| `keyword` | 匹配 User ID、用户名、显示名或公开模型名 |
| `status` | 空、`active`、`zero_access`、`inactive` |

响应：

```json
{
  "success": true,
  "data": {
    "page": 1,
    "page_size": 20,
    "total": 1,
    "summary": {
      "total": 1,
      "active": 1,
      "zero_access": 0,
      "inactive": 0
    },
    "items": [
      {
        "user_id": 42,
        "username": "customer-a",
        "display_name": "Customer A",
        "contract_mode": true,
        "contract_status": "active",
        "contract_version": 3,
        "rule_count": 4,
        "unavailable_rule_count": 0,
        "updated_at": 1786982400,
        "admin_user_id": 1,
        "admin_username": "root"
      }
    ]
  }
}
```

该接口只读聚合用户、规则数和当前版本审计。合同写入继续只允许：

```http
PUT /api/user/:id/contract
```

### 4.1 查询与性能

- 主查询分页读取已建立合同的未删除用户。
- 规则数通过按 `user_id` 聚合的子查询一次连接，不逐用户 Count。
- 最近修改信息通过 `user_id + contract_version` 连接当前版本审计，不扫描完整审计历史。
- 当前页规则一次批量读取；可用性按当前页涉及的唯一渠道组缓存计算，避免逐用户详情请求。
- 摘要使用受角色约束的 Count 查询，不受关键词与状态筛选影响。
- 默认按当前版本审计时间倒序，其次按 User ID 倒序，保持翻页稳定。

## 5. 权限与安全边界

- 路由使用 `AdminAuth`。
- 普通管理员只看到并操作低于自身角色的用户；Root 沿用既有管理目标语义。
- 响应不返回密码、Token、AccessToken、渠道凭据、Provider 身份或上游模型。
- 渠道组不出现在总览响应；管理员需要查看组时进入现有合同编辑器。
- 删除、停用或修改合同仍需既有写接口、必填原因、`expected_version` 和审计事务。
- 聚合接口失败时页面显示失败状态，不使用旧数据冒充当前合同清单。

## 6. 最小入侵方案

### 6.1 后端

- 在新增的 model/controller 文件中实现列表与聚合查询。
- 原生 Router 只增加一条管理员 GET 路由。
- 不修改合同保存、鉴权围栏、分发或计费热路径。

### 6.2 前端

- 新增独立 `customer-contracts` feature、路由和页面组件。
- 复用共享 `SectionPageLayout`、`DataTablePage`、`StatusBadge` 与现有
  `UserContractDrawer`。
- 侧边栏与路由映射各增加一个窄接线项。
- 不复制合同表单逻辑，不把合同编辑字段重新实现为列表内联编辑。

## 7. 交互与异常处理

- 输入搜索词后使用现有防抖工具刷新服务端分页。
- 更改状态筛选时回到第一页，URL 保存分页、关键词和状态，可刷新恢复。
- 打开合同抽屉后保存成功，关闭抽屉时刷新当前页和状态摘要。
- 版本冲突、停用确认、未保存关闭确认继续由现有抽屉负责。
- 当前页存在不可履约规则时仅显示数量和警示状态；修复入口仍是“管理合同”。
- 列表请求失败显示错误提示与空数据，不降级为用户列表的当前页客户端筛选。

## 8. 验收标准

1. 管理员侧边栏出现“客户合同”，普通用户不可见且不能访问路由。
2. 页面只列出 `contract_version > 0` 且未删除、当前管理员可管理的用户。
3. 生效、零权限、停用状态与现有用户列表口径一致。
4. 摘要统计为全局合同统计，不因当前分页、搜索和筛选改变。
5. 关键词能够命中 User ID、用户名、显示名和公开模型。
6. 当前页规则可用性不存在逐用户详情请求；不可履约数量准确。
7. 点击“管理合同”打开现有抽屉，保存后列表和摘要刷新。
8. 没有新增合同写入口，原生合同计费、路由、异步结算测试结果不变。
9. SQLite、MySQL、PostgreSQL 查询语义一致，不使用方言专属函数。
10. 前端类型检查、目标组件测试、后端目标测试、文档检查全部通过。

## 9. 风险与控制

| 风险 | 控制 |
| --- | --- |
| 总览页形成第二套编辑逻辑 | 只复用现有抽屉和写接口 |
| 普通管理员看到同级或更高角色合同 | model 查询按既有角色边界过滤，controller 测试覆盖 |
| 聚合列表出现 N+1 | 规则数、审计和当前页规则批量查询 |
| 可用性计算随渠道组数量增长 | 只计算当前页，按唯一渠道组缓存；分页最大 100 |
| 合同列表与用户列表状态不一致 | 前端复用同一状态判定语义，后端测试三种合同状态 |
| 批量操作造成账单事故 | 本次不提供任何批量写入 |

## 10. 待验证事项

- 真实管理员账号下的桌面和移动端页面走查。
- 大量合同、渠道组和规则数据下的查询耗时。
- 真实 MySQL、PostgreSQL 环境的聚合查询与排序结果。
- 生产灰度与真实账单不属于代码测试完成的结论。

## 11. 实施结果

本设计已按最小入侵方案完成：后端以新增 model/controller/router 文件提供只读聚合，原生 Router 仅
增加一处注册；前端新增独立 feature、管理员路由和菜单，合同编辑仍复用 `UserContractDrawer` 与
`PUT /api/user/:id/contract`。没有新增合同写接口、状态源、数据库表或计费分支。

自动化验证覆盖三种合同状态、原生与删除用户排除、Admin/Root 角色边界、客户和公开模型搜索、摘要
稳定性、安全响应字段、路由注册、前端摘要/空态/失败关闭/抽屉刷新，以及既有合同路由和计费回归。
前端完整测试、类型检查、生产构建、i18n 同步和文档检查均通过。

真实 MySQL/PostgreSQL 数据、浏览器视觉、生产数据量和灰度账单仍属于第 10 节的发布验证，不据此声称
生产已发布。
