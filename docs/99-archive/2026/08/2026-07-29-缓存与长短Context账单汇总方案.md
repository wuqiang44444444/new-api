# 专业用量账单与缓存、长短 Context 明细最终方案

## 1. 文档目的

本文档在已实现的「缓存与长短 Context 账单汇总」基础上，合并用量透明、价格可追溯、结算可核对、异常可识别的专业客户对账单要求，作为后续实现和验收的唯一方案。

本方案交付的是「专业用量结算单」，不是税务发票、支付订单或复式记账账本。如需正式发票，必须在本方案之外建立独立的发票与财务域。

## 2. 业务目标

### 2.1 业务动机

客户不仅需要知道「花了多少」，还会持续追问「为什么会产生这些费用」「缓存、长 Context、退款和附加调用如何影响结果」「数据是否已经结算并可以信任」。如果页面只提供总量与总额，客户就无法自助对账，只能反复联系客服或技术支持。

本方案的核心业务目标是：

- 向客户提供专业、详细、可解释、可追溯的用量对账单。
- 让客户在不提交工单的情况下，自助理解主要用量和已结算费用的构成。
- 在发生异议时，客户与支持人员可以基于同一口径、同一时间区间和同一 request ID 快速定位。
- 通过可信数据和明确的能力边界建立客户对平台计费的信任，而不是为了字段完整而展示推测值。

### 2.2 目标客户与使用场景

主要用户是对当前个人账户 API 用量和费用负责的开发者或账户所有者。他既要核对花了多少，也要通过缓存、Context 和模型构成优化自己的应用成本。

次要阅读者是获得页面或 CSV 进行核对的财务、采购或其他费用责任人。其核心关注点是查询区间、原始消费、退款/冲正、净费用、数据是否已结算，以及能否追溯到原始记录。

客服和技术支持是间接受益者：专业对账单应减少重复解释性咨询，并为真正的计费异议提供统一调查入口。

信息优先级因此固定为：

1. 原始消费、退款、净费用、结算状态与可追溯性是主表 P0。
2. 缓存命中、长短 Context 和其他 Token 构成是明细 P0，在主表展示摘要，完整数据放入行展开详情。
3. 5m/1h 缓存写入、复杂价格档位和附加调用属于开发者详细解释，不占用主表核心列。
4. RPM、TPM、平均耗时和流式比例属于运行分析，保留在次级区域。

### 2.3 业务范围

本方案只覆盖「个人 → 账单」，即当前认证用户自己的 API Key、模型用量和已结算费用。当前的 `group` 或计费分组不自动等同于组织账单维度。

组织、子账户、项目、部门、成本中心、预算归属和内部转分摊不在本轮范围；如后续需要，必须先定义组织所有权、成员权限和成本归属合同。

本轮查询的是「客户选定的时间区间，最长 31 天」，不是已封账的法定计费周期或月结单。不可变月结只能在阶段 C 实现。

### 2.4 客户应能回答的问题

客户在「个人 → 账单」中应能回答以下问题：

1. 在选定的时间区间内用了哪些 API Key 和模型，产生了多少请求与 Token？
2. 输入 Token 中有多少是普通输入、缓存读取和缓存写入？
3. 缓存命中率如何，分母是全部请求还是可缓存请求？
4. 哪些请求属于长 Context 或短 Context，分类阈值和 Token 数是多少？
5. 实际使用了哪种计费方式、价格档位、资金来源和附加费？
6. 原始消费、退款/冲正和净费用各是多少？
7. 数据是上游返回、网关归一化、本地计数还是估算，尚有多少请求未分类？
8. 如对某条汇总存疑，能否下钻到平台请求 ID 和单次用量日志？
9. 当前数字是否已全部结算、是否已封账，以及是否仍可能因异步任务、退款或后续调整而变化？

### 2.5 目标与阶段追溯

| 客户问题 | 阶段 A：现有数据展示 | 阶段 B：结算快照 | 阶段 C：待结算与封账 |
| --- | --- | --- | --- |
| Q1 API Key、模型、请求与 Token | 完整回答 | 不需额外能力 | 不需额外能力 |
| Q2 普通输入与缓存读写 | 展示总输入与缓存读写；历史普通输入无法可靠拆分时明确标注限制 | 用结算时归一化快照固定口径 | — |
| Q3 缓存命中率与分母 | 历史回退使用全部已结算请求并明确标注 | 使用真正的可缓存请求与 Token 分母 | — |
| Q4 长短 Context | 使用当前阈值，展示请求、Token 和覆盖率 | 使用不可变的阈值与分类快照 | — |
| Q5 计费方式、档位、资金来源与附加费 | 只展示既有日志中可信的部分 | 使用完整价格、档位和费用组成快照 | — |
| Q6 消费、退款与净费用 | 回答实时已结算日志 | 增强费用组成解释 | 提供封账、调整引用和严格周期语义 |
| Q7 数据来源与未分类 | 映射公共安全来源并展示覆盖率 | 结算时固定来源和版本 | 增加待结算覆盖 |
| Q8 request ID 与日志下钻 | 按 API Key、模型和区间下钻，在单次日志中查看平台 request ID | 可增加更精确的 request 关联 | — |
| Q9 是否已结算、已封账或仍可变 | 明确标记「仅已写入结算日志，尚未封账」 | 提供一致 `as_of` 查询快照 | 完整提供 pending、provisional 与月结状态 |

阶段 A 不宣称已经完整回答 Q2、Q3、Q4、Q5、Q7 和 Q9 的审计级问题；页面必须同时告知客户当前可以回答的范围和无法证明的部分。

### 2.6 顶层非目标

- **本轮不回答「缓存为我节省了多少钱」。** 阶段 A 只能展示缓存命中请求数、缓存读/写 Token、命中率和缓存命中请求的整单已结算费用。`hit_request_gross_quota` 不是缓存费用或节省金额。
- 仅有价格快照仍不足以证明缓存节省金额；动态计费、最低收费和附加费都可能使查询端反算失真。只有结算主链能生成可信的「无缓存对照费用」或明确的 `cache_savings_quota` 快照后，才允许展示节省金额。
- 本轮不提供正式发票、不可变月结单、组织成本分摊、会计期初/期末余额勾稽或使用当前价格重算历史费用。

当前可以合法提供的缓存代理指标只包括：缓存读取 Token、缓存写入 Token、请求命中率、Token 命中率以及缓存命中请求的整单已结算费用。

### 2.7 业务成功指标

本方案的业务结果不以「增加了多少字段」衡量，而以客户能否自助完成对账、支持人员能否快速解决异议衡量。

业务结果指标：

- 每千名付费客户的账单/对账类咨询数。
- 账单异议从提交到解决的中位时长。
- 客户无需提交工单即可完成对账的比例。
- 客户从账单页成功下钻至用量日志并找到目标请求的比例。
- 使用页面或 CSV 可完成自助核对的企业 POC/客户比例。

产品质量护栏：

- statement 与 breakdown 合并一致率。
- 可靠总输入 Token 覆盖率、Context 分类覆盖率和缓存分母可识别率。
- breakdown 查询成功率、响应时间和失败降级成功率。
- 只能使用历史回退或无法解释的账单行比例。

上线前先采集基线，不在无数据支持时填写「下降 X%」等虚假目标。至少经过一个完整观察窗口后，再根据实际客户咨询和页面使用数据设定目标值。

## 3. 当前实现与剩余差距

### 3.1 已实现

- 正式账单接口 `GET /api/billing/self`，按 `API Key × 模型` 汇总请求数、输入/输出/总 Token、消费、退款、非负净费用、平均耗时和流式请求。
- 使用构成接口 `GET /api/billing/self/breakdown`，按相同粒度返回缓存命中及明确分母、缓存读写 Token、5m/1h 写入拆分、长短 Context 请求与输入 Token、未分类请求、覆盖率、请求整单费用和动态计费请求。
- 页面使用 `token_id + model_name` 将 breakdown 合并到正式 statement 行；桌面表格和移动卡片均可展开查看用量构成、Context 分类与结算明细。
- 主表、展开详情与全量 CSV 同时保留原始消费、退款/冲正和净费用；CSV 同时提供展示值和稳定的原始 quota/比例列，保留 UTF-8 BOM 并防止公式注入。
- statement 正常但 breakdown 失败、不一致或历史元数据无法解析时，页面继续展示正式金额与基础 Token，将构成标为不可用并提供重试，不用零值伪造明细。
- 页面明确标注缓存命中率分母为全部已结算请求、Context 使用当前模型阈值、缓存命中请求费用不是缓存费用或节省金额，以及当前结果尚未封账并可能变化。
- 使用 `input_tokens_total` 和 `usage_semantic` 归一化 OpenAI、Anthropic 与 Gemini 的输入 Token 口径。
- 有 `task_id` 的异步补扣日志同时进入 statement 与 breakdown 的总费用，但不重复增加逻辑请求数；breakdown 通过 `unallocated_adjustment_quota` 单独披露尚不能归入缓存、Context 或动态计费类别的金额。
- statement 与 breakdown 的合并一致性同时校验请求数和原始消费，避免异步补扣在请求数相同时被误判为完整构成。
- statement 的应用层二次汇总使用统一饱和加法；触顶时通过 `data_quality.saturated` 标记，页面提示客户先核对用量日志。
- 页面已有缓存、长短 Context 和动态计费汇总卡片，并支持按当前筛选导出 CSV 与下钻用量日志。

### 3.2 与专业账单的差距

- 缓存命中率当前使用「命中请求 / 全部消费请求」，无法识别不支持缓存的请求。
- `hit_request_gross_quota` 是「发生缓存命中的整次请求费用」，不是缓存单项费用或节省金额。
- Context 分类使用查询时的当前模型阈值；管理员修改阈值后，历史账单可能改变。
- 没有对普通输入、推理、图片、音频、工具调用等用量与附加费做统一账单投影。
- 仅提供当前阈值、缓存分母和分类覆盖率等阶段 A 来源信息；还没有结算时不可变的完整计数来源、估算状态和版本快照。
- 没有「待结算」投影；页面只能证明查询时已写入的结算日志。
- 当前时区、周期边界和生成时间不等于月结封账，也不保证与用户余额严格勾稽。

## 4. 产品定位与边界

### 4.0 最小入侵是最高优先级

本方案的默认实施边界是「基于已有结算日志完成专业明细展示」，不因界面需求扩大对预扣、结算、退款、日志写入和数据库结构的改动。

实施必须遵守：

1. 本轮默认只实施阶段 A；阶段 B/C/D 是独立的后续能力，必须在用户或项目明确授权并完成影响评估后才能启动。
2. 优先扩展已有 `/api/billing/self/breakdown` 的可选字段，不修改 `/api/billing/self` 的已有字段语义、聚合键或金额口径。
3. 新类型、归一化、聚合、导出与测试原则上放入独立新文件；现有后端和前端热路径只保留必要的单行调用或极窄接线。
4. 允许新文件内少量、局部且清晰的重复，不为抽象复用扩写、重排或重构现有上游文件。
5. 阶段 A 不增加表、列、索引或迁移，不改变核心计费结果，不为展示单项费用而在查询端重建价格。
6. 历史数据不足时使用「未知/不可分类」降级，不为填满页面字段修改 Provider 语义或引入无依据的兼容路径。
7. 如完成某项需求必须扩大上游文件改动或修改计费主链，应停止实施并单独评审，不得在本轮界面改造中顺带扩展。

### 4.1 个人与组织边界

- 页面与接口只面向当前认证用户，只汇总该用户自己的日志、API Key、用量和已结算费用。
- 页面中的「分组倍率」是计费解释，不是组织、部门或成本中心。
- 本轮不增加管理员代查、组织汇总、子账户归并、部门分摊或跨用户 CSV。
- 如后续扩展组织账单，必须作为独立项目定义组织资源所有权、成员角色、数据隔离、成本归属、调整与导出权限。

### 4.2 账单与日志的分工

- 账单是客户选定时间区间内已结算用量与费用的汇总投影。
- 用量日志是单次请求的审计与计费解释。
- 账单不复制 prompt、请求体或上游响应；通过平台 `request_id` 下钻到用量日志。
- 主表只展示最稳定的核对字段，细分用量、价格和质量信息放入行展开详情。

### 4.3 不可变计费口径

1. 历史费用只来自请求当时已结算的日志 `quota`，不使用当前价格重算。
2. 缓存、Context、动态计费等分类中的费用，在没有结算时单项费用快照时，只表示该类请求的整单已结算费用。
3. 不得把「缓存命中请求费用」标注为「缓存费用」或「节省金额」。
4. 如要展示缓存节省、分 Token 费用或工具附加费金额，必须在结算时写入版本化快照，不得在查询或前端重建历史价格。
5. `gross_quota` 表示消费日志金额，`refund_quota` 表示退款/冲正日志金额，`net_quota = max(gross_quota - refund_quota, 0)`。
6. 跨期退款按退款日志的发生时间归属当期；页面必须单独展示退款/冲正，不得因净费用截断为零而隐藏。
7. 有 `task_id` 的异步调整影响 Token 和费用，不重复增加请求数、耗时或流式请求数；其中异步补扣进入 statement 与 breakdown 的 `gross_quota`，同时记入 breakdown 的 `unallocated_adjustment_quota`，不得伪装为缓存、Context 或动态计费费用。
8. 任何汇总加法和费用转换必须保持饱和、非负与可审计不变量。

### 4.4 结算状态

账单必须明确区分：

- `settled`：已写入消费或退款日志，可进入正式费用汇总。
- `pending`：异步任务或上游结果尚未终态，只展示数量和已预留/预估值，不计入「已结算净费用」。
- `adjusted`：已发生退款、补扣或冲正，展示调整金额与可用的关联标识。
- `provisional`：查询周期尚未封账或存在待结算项，页面必须标记「数据仍可能变化」。

第一阶段仍以已结算日志为权威费用来源；`pending` 是独立的运行状态投影，不得与已结算费用相加。

## 5. 页面信息架构

### 5.1 页面级汇总

保留已有的周期费用、总/输入/输出 Token、请求数、当前余额、RPM、TPM、平均耗时和流式比例。

新增或补强：

- 已结算原始消费、退款/冲正、净费用。
- 结算状态、待结算项数与「数据可能变化」提示。
- 缓存请求命中率、Token 命中率及各自分母口径。
- 长/短 Context 请求数、输入 Token 和分类覆盖率。
- 动态计费请求数及已结算整单费用。

RPM、TPM、平均耗时和流式比例属于运行分析，保留在次级指标区，不与主要结算金额混排。

### 5.2 账单主表

桌面端主表默认展示：

| 列 | 内容 |
| --- | --- |
| API Key | 当前或最新历史名称，删除后仍以 ID 可识别 |
| 模型 | Link 公开模型/SKU，不显示渠道或上游私有模型 ID |
| 请求数 | 逻辑调用次数 |
| Token | 输入 / 输出；悬浮或展开查看缓存与其他构成 |
| 缓存 | 请求命中率与读/写 Token 摘要 |
| Context | 长/短请求数或长 Context 占比 |
| 费用 | 净费用；展开查看原始消费与退款 |
| 费用占比 | 当前筛选范围内的净费用占比 |
| 操作 | 展开详情、跳转用量日志 |

按模型和按 API Key 视图保留；合并时所有比率必须使用原始分子/分母重算，不得对行百分比做算术平均。

### 5.3 行展开详情

每个 `API Key × 模型` 行展开三个区域：

#### 用量构成

- 总输入 Token、普通/非缓存输入 Token、缓存读取 Token、缓存写入 Token。
- 缓存写入拆分：5m、1h 和未拆分总量。
- 普通输出 Token、推理 Token、图片 Token、音频 Token。
- 可计费工具调用名称与次数，例如 Web Search、File Search 和图片生成。
- 缓存请求命中率、Token 命中率、两者分母口径。

#### Context 分类

- 分类阈值、阈值来源、分类版本。
- 长/短 Context 请求数、输入 Token 总数、整单已结算费用。
- 未分类请求数与分类覆盖率。
- 如同一汇总行包含多个历史阈值，按阈值快照分段展示，不得伪装成一个统一阈值。

#### 计费与结算

- 计费方式：按 Token、按次或动态表达式。
- 动态计费的命中档位、表达式版本/哈希和已结算总额；不在账单端重新执行表达式。
- 历史价格快照、分组/专属倍率和可用的费用组成快照。
- 资金来源：钱包、订阅；如同一行混合，分开显示请求数和费用。
- 原始消费、退款/冲正、非负净费用。
- 工具、图片、音频等附加费的数量、单位、结算时单价与已结算额。
- 平台 `request_id` 和用量日志下钻入口。

## 6. 数据口径与归一化

### 6.1 缓存

历史日志兼容规则保持：

- 读取 Token：`cache_tokens`。
- 写入 Token：优先 `cache_write_tokens`；缺失时取 `max(cache_creation_tokens, cache_creation_tokens_5m + cache_creation_tokens_1h)`。
- `cache_tokens > 0` 计为一次缓存命中请求。
- 5m/1h 拆分值与总量同时存在时，总量只作为校验与回退，不重复相加。

最终指标：

```text
request_hit_ratio = hit_requests / eligible_requests
token_hit_ratio   = cache_read_tokens / cache_eligible_input_tokens
```

新日志应在结算快照中记录 `cache_eligible`、`cache_eligible_input_tokens` 与分母口径。历史日志无法判定可缓存性时，可继续使用全部已结算请求作分母，但响应和页面必须标记 `denominator_scope = all_settled_requests`，不得与 `cache_eligible_requests` 口径混用。

普通/非缓存输入 Token 只能从可靠的归一化总输入扣除缓存构成；计算结果下限为零。无可靠总输入时返回未知，不得猜测。

### 6.2 长短 Context

历史日志归一化规则保持：

- 优先使用 `input_tokens_total`。
- Anthropic 语义且无显式总输入时，使用 `prompt_tokens + cache_tokens + cache_write_tokens`。
- OpenAI/Gemini 语义且无显式总输入时，`prompt_tokens` 可作为总输入。
- 无可靠语义或总输入 Token 的日志计入 `unclassified_requests`，不得默认为短 Context。
- `input_tokens > threshold` 为长 Context；等于阈值归入短 Context。

新日志必须在结算时快照以下事实：

```text
normalized_input_tokens
context_threshold_tokens
context_class = short | long | unclassified
context_threshold_source = request_snapshot
classification_version
```

历史日志继续使用 `current_model_config` 回退，但必须向用户显示「按当前阈值分类，历史结果可能改变」。

### 6.3 输出、推理、媒体与工具

- `completion_tokens` 保留为对外总输出口径。
- 上游可靠提供时，将推理 Token 、普通文本输出 Token 分开快照；两者不得与总输出重复累加。
- 图片、音频、视频时长、批量数等计费乘数必须使用结算时的规范化值。
- 工具调用以名称、次数、结算单位和单项已结算额快照，不得根据当前工具价格回算。

### 6.4 计数来源与质量

普通用户可见的数据来源只返回公共安全枚举：

```text
upstream_reported
gateway_normalized
locally_counted
estimated
unknown
```

不向普通用户返回渠道 ID、渠道名称、上游密钥、管理员审计字段或内部计费路径。

页面至少展示：

```text
classified_requests
unclassified_requests
exact_requests
estimated_requests
classification_coverage = classified_requests / eligible_or_total_requests
```

## 7. 结算时版本化快照

新结算日志应在 `other.billing_detail` 下写入版本化、公共安全的快照；历史扁平字段作为兼容回退。快照只记录已参与计费的规范化事实，不记录 prompt、请求体或上游响应。

## 8. 账单接口合同

### 8.1 现有接口

- `/api/billing/self` 继续是周期金额和核心用量的权威账单接口。
- `/api/billing/self/breakdown` 继续是使用构成和费用解释接口。
- 两个接口均只使用认证上下文中的用户 ID，不接受任意 `user_id`。
- 最长查询周期保持 31 天。

### 8.2 一致查询快照（后续独立改造）

两个接口应支持同一 `as_of_timestamp`，并使用一致的：

```text
user_id
start_timestamp
end_timestamp
as_of_timestamp
token_id (optional)
model_name (optional)
```

页面必须使用同一 `as_of_timestamp` 请求正式账单与 breakdown，避免两次查询之间新结算日志造成行数或金额不一致。

半开区间 `[start_timestamp, end_timestamp)` 可以防止相邻周期在边界秒重复计数，但它会改变现有包含式结束边界的接口语义。因此阶段 A 保持当前周期合同；如确认收敛为半开区间，必须作为独立合同变更，同步更新前端周期构造、后端查询、用户文档和回归测试。

响应统一补充：

```text
billing_timezone
generated_at
as_of_timestamp
data_source = settlement_logs
is_provisional
pending_items
classification
```


历史日志无法提供的字段应省略或明确返回 `unknown`，不得使用虚假零值。

## 9. 前端实现

1. 使用 `token_id + model_name` 将 statement item 与 breakdown item 合并为页面行。
2. statement 为主数据；breakdown 失败时仍展示金额和基础 Token，并将使用构成标记为不可用。合并完整性必须同时校验同一明细键的 `requests` 与 `gross_quota`。
3. breakdown 多出的行不能创建无正式金额来源的账单行，也不能进入顶部构成汇总；应记录一致性异常并提供重试。
4. 明细使用可展开行/抽屉；移动端使用卡片或抽屉，不要横向堆叠全部列。
5. 缓存、Context、计费方式和数据质量字段为可选数据；历史请求未分类时显示「未提供/不可分类」，不显示为零用量。
6. 费用占比使用当前筛选行的净费用计算。
7. 分类比率、缓存命中率和数据覆盖率均展示分子/分母提示。
8. CSV 导出包含行展开详情的所有可用字段，并为金额和比例保留稳定的原始数值列；保留 UTF-8 BOM，并防止以 `=`、`+`、`-`、`@` 开头的单元格被表格软件解释为公式。
9. 所有用户可见文案纳入 i18n，数字、货币、日期和时区使用当前语言及站点配置格式化。
10. `unallocated_adjustment_quota > 0` 时将构成标为「部分可用」并显示异步补扣金额；该金额已包含在原始消费中，不得再次相加，也不得分摊到缺少可靠语义的构成类别。

## 10. 安全与隐私

- 接口必须继续使用 `UserAuth()` 并强制 `user_id` 隔离。
- 账单只返回 API Key ID 与历史名称，不返回 Key 值。
- 普通用户不得看到渠道、上游凭证、渠道私有模型 ID、内部调度路径、`admin_info`、IP、prompt、请求体或上游响应。
- 平台 `request_id` 可对日志所有者显示；上游 request ID 仅在已明确公开且不泄露 Provider 信息时可见。
- 价格快照只显示用户实际适用的公开单价、折扣/倍率和已结算结果，不暴露上游成本或内部利润信息。
- CSV 继承当前用户权限和筛选范围，并必须执行公式注入防护。

## 11. 兼容性与性能

- 不在共享 SQL 中引入数据库专属 JSON 操作符。
- SQLite、MySQL >= 5.7.8、PostgreSQL >= 9.6 继续使用 GORM 和通用 `CASE WHEN` / `COALESCE` / `SUM` 等能力。
- ClickHouse 保留独立 SQL 合同测试。
- 第一阶段可继续逐行读取 `other` 并内存汇总，但必须设置查询范围和响应大小上限。
- 如日志量导致延迟或内存超过可接受边界，后续优先增加专用结算投影或预聚合，不为了查询便利破坏三数据库兼容。
- 账单读取失败不得影响模型调用、预扣、结算、退款或钱包。

### 阶段 B：结算时快照与可审计口径（P0/P1）

本阶段不在本轮默认实施范围内。启动前必须单独评估日志大小、三数据库与 ClickHouse 兼容、历史回退、隐私和计费主链风险。如获批实施，快照构建、类型与测试放入独立文件，现有结算日志写入热路径只增加单行调用或极窄分支，不顺带重构原计费逻辑。

1. 在新消费日志写入 `other.billing_detail.version = 1`。
2. 快照归一化输入、缓存、输出、推理、媒体与工具用量。

4. 快照计费模式、动态档位/哈希、资金来源和公共安全的价格信息。

### 阶段 C：待结算与周期封账（P1）

1. 将异步任务计费状态投影为 `pending_items`，不与已结算金额混算。

### 阶段 D：正式发票（独立项目）

### 13.1 后端行为
