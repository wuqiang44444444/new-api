# Link 合同架构修复实施方案

> 2026-08-04 边界更新：本文当时“不恢复 OpenAI Videos/Sora”的范围结论已被
> [ADR-0016](../../../20-architecture/decisions/0016-原生OpenAI-Videos与Link合同并存边界.md)取代。
> Link durable attempt、能力和素材结论继续有效；rc23 原生视频按独立原生合同恢复。

## 1. 结论

本方案把已经接受的 Link 合同架构约束落到当前代码，修复以下五类缺口：

1. 为正式视频和可能返回持久化 Task 的图片 route 增加发送前耐久
   `TaskCreateAttempt`，不依赖客户端是否提供 `Idempotency-Key`；
2. 统一同步图片的幂等结果：媒体任务 route 同步成功后保留
   `completed_no_replay` claim，同键重放返回
   `409 idempotency_result_unavailable`，不得再次调用上游；
3. 增加内部 `PROVIDER_CONTRACT_FAILURE` Task 终态，明确零目标结算、billing
   `settled/failed` 与 exposure 的原子关系；
4. 在发送前为真人素材建立 authorization reservation，与撤回事务在同一授权行上线性化，
   并在任务内容回源前逐次回查授权；
5. 实现并冻结 `VideoSKUCapability(version + hash)`，让候选发布、运行时选渠和发送前复检使用
   同一个能力事实。

这些修复不改变客户端官方合同，不新增供应商专用 Task、worker 或进程。ModelArk、Kling、即梦
继续使用各自客户端 DTO 和投影；Provider 仍由供应商中立 profile 适配。恢复和对账继续由现有
`async_task_poll` 系统任务与 `service.RunTaskPollingOnce` 承载。

本文是实施现场方案，不表示以下能力已经存在。当前代码截至 2026-07-30 仍只有部分基础：

- `TaskCreateIdempotency` 依赖客户端 Key，没有覆盖无 Key 创建，也没有发送前资金 hold 状态机；
- 图片媒体任务同步成功时会释放 claim，与新合同相反；
- Task 终态尚无 `PROVIDER_CONTRACT_FAILURE`；
- 没有 `task_asset_authorizations`、authorization reservation 和内容下载授权回查；
- 没有版本化 `VideoSKUCapability`。

- 不为真人内容下载增加有撤回延迟的缓存；
- 不增加供应商专用进程、任务表或幂等域；
- 不从请求级 URL/Data URL 自动识别真人；
- 不重构现有 Router → Controller → Service → Model 分层。

## 3. 必须保持的不变量

| 不变量 | 实现要求 |
| --- | --- |
| 客户端与 Provider 正交 | `northbound_contract_id/version` 决定对外投影，profile/adapter 决定渠道执行 |
| 一个 SKU 一个合同 | 冻结的 `VideoSKUCapability(version + hash)` 是字段、媒体组合和生命周期权威 |
| 发送前可恢复 | `prepared` 先于预扣；hold 与 `sending` 原子提交后才能发送任何请求字节 |
| 客户端 Key 可选 | 无 Key 仍有内部 attempt；有 Key 只增加客户端重放 claim |
| unknown 不重发 | 发送后无法证明结果时保持 hold，有界对账，不换渠道、不重新 POST |
| 终态分类分离 | 不可采信响应、确定不可交付、明确失败和 SLA 到期使用四条独立路径 |
| 资金状态独立 | 业务终态确定不代表资金写入必然成功；billing `failed` 必须可补偿 |
| 真人撤回线性化 | 授权 reservation 与撤回锁定同一授权行；内容访问始终逐次回查 |
| 三数据库兼容 | 所有恢复、撤回和 exposure 扫描依赖普通列/索引，不依赖 JSON 查询 |
| 单一调度底座 | 扩展 `async_task_poll` 扫描，不新增图片、视频或供应商专用 worker |

## 4. 当前代码差距

### 4.1 创建 attempt

当前 `middleware/task_create_idempotency.go` 只在客户端提供 Key 时调用
`ClaimTaskCreateIdempotency`。`model/task_create_idempotency.go` 的恢复快照是在已取得上游
Task ID 后写入，无法覆盖“POST 已成功但进程尚未来得及记录响应”的崩溃窗口。

图片的 `middleware/image_task_create_idempotency.go` 已正确位于 `Distribute` 之后，能判断
是否命中持久化媒体任务 route；但 `middleware/task_create_idempotency.go` 会在同步图片没有
持久化 Task 时删除 claim。该行为必须改为 `completed_no_replay`。

当前 `async_task_poll` 的 `Enabled()` 只检查 `model.HasUnfinishedSyncTasks()`。如果系统只剩
unknown attempt、终态 billing `failed` 或 exposure outbox，调度器可能不启动。复用现有调度
底座还必须扩展“是否有工作”的普通索引查询，不能只把扫描函数塞进
`RunTaskPollingOnce`。

### 4.2 计费与合同失败

现有 `model.TaskStatus` 终态只有 `SUCCESS/FAILURE/CANCELLED/EXPIRED`。
`service.refundTaskWithReconcile` 与 `model.ApplyTaskBillingTarget` 已具备零目标结算及失败重试
底座，但尚未区分 `PROVIDER_CONTRACT_FAILURE`，也没有可查询的 exposure 事实。

### 4.3 真人撤回

`middleware.AssetRouteConstraint` 会在选渠前读取真人授权，但该读取与实际发送没有事务关系。
`service.RevokeRealPersonAuthorization` 只清理素材和素材组；`controller.VideoProxy` 在回源前
不检查原授权。当前不存在 task/attempt 与 authorization 的普通关系表。

### 4.4 SKU 能力

当前视频路由能按 protocol/profile 分发，但没有一次性解析并冻结
`VideoSKUCapability(version + hash)` 的实现。候选发布、运行时过滤和发送前复检还没有共享同一
能力快照。

## 5. 目标数据模型

### 5.1 `task_create_attempts`

新增独立表，不把无 Key attempt 伪装成 `TaskCreateIdempotency`：

```text
id
attempt_id                 unique
public_task_id             index
user_id / token_id / subscription_id
client_protocol
request_hash
northbound_contract_id / version
sku_capability_version / hash
channel_id / upstream_profile / adapter_version
frozen_connection_snapshot
status                     index
billing_hold_state         index
held_quota
upstream_request_id / upstream_task_id
reconcile_attempts
outcome_unknown_at          index
next_attempt_at            index
hold_deadline_at           index
task_deadline_at           index
created_at / updated_at
```

状态：

```text
prepared -> sending -> upstream_succeeded -> complete
             |                |
             +-> unknown <----+
prepared/sending -> rejected
unknown -> complete | released_with_exposure
```

资金门闩：

```text
unheld -> held -> transferred
             \-> released
```

要求：

- `attempt_id` 和预生成 `public_task_id` 不可预测；
- 查询扫描字段使用普通列；
- 冻结连接中的单个 Key 只保存在后端敏感快照，不进入日志、metrics 或用户响应；
- 不保存 prompt、媒体 URL/Data URL、Cookie、完整请求或原始幂等键；
- `outcome_unknown_at` 首次进入 unknown 时写入且不随后续恢复清除，用于按事件 cohort 计算
  unknown 转 exposure 比例；
- `prepared`、hold/`sending`、Task 转移、release 都用条件更新和行锁保证幂等。

### 5.2 `task_create_idempotencies`

现有表保留为可选客户端 claim，并新增：

```text
attempt_id                 index
status = creating
       | upstream_succeeded
       | complete
       | completed_no_replay
       | unknown
```

规则：

- 同键同请求关联同一个 attempt；同键异请求冲突；
- 无 Key 不创建 claim，但必须创建 attempt；
- 异步成功关联 Task，重放返回 Task/结果；
- 媒体任务 route 同步成功后写 `completed_no_replay`，保留到幂等 TTL；
- `completed_no_replay` 重放固定返回 `409 idempotency_result_unavailable`；
- 明确发生在发送前的拒绝可以删除 claim；发送后的任何模糊结果不得删除或重用。

### 5.3 Task 终态与 exposure

新增：

```text
TaskStatusProviderContractFailure = "PROVIDER_CONTRACT_FAILURE"
```

该状态：

- `IsTerminal() == true`；
- `ShouldRefundOnTerminal() == true`；
- 加入 `TerminalTaskStatuses()` 和终态 billing 扫描；
- 对 ModelArk/Kling/即梦/OpenAI Images 分别投影到各自合法的失败状态；
- 对外稳定错误码为 `provider_contract_failure`，不得声称 Provider 明确业务失败。

计费映射：

| 结果 | Task/attempt 状态 | 目标额度 | 成功后的 billing | 写入失败 |
| --- | --- | ---: | --- | --- |
| Provider 明确失败 | `FAILURE` | 0 | `settled` | `failed` 后补偿 |
| 可信但不可交付 | `PROVIDER_CONTRACT_FAILURE` | 0 | `settled` | `failed` 后补偿 |
| SLA 到期 | `EXPIRED` + `upstream_outcome_unresolved` | 0 | `settled` | `failed` 后补偿 |
| 创建未知到期 | attempt `released_with_exposure` | release hold | 不进入 Task billing | attempt 补偿 |

新增 `provider_cost_exposures` 普通表，唯一键为
`source_kind + source_id + reason`。零目标结算与 exposure 同事务提交；无法跨资金存储同事务时
使用唯一 outbox。Provider 金额未知时保持空值，以 `customer_quota_released` 作为独立字段，
不能冒充供应商货币成本。

### 5.4 `task_asset_authorizations`

新增：

```text
id
attempt_id
task_id                     预生成公开任务 ID
user_id
asset_id
authorization_id
asset_kind
state                       reserved | task_bound | closed
created_at / updated_at
```

约束与索引：

- 唯一 `attempt_id + authorization_id + asset_id`；
- 唯一 `task_id + authorization_id + asset_id`；
- 索引 `task_id`；
- 复合索引 `authorization_id + state`；
- 不通过 `Task.private_data` JSON 反向查找。

### 5.5 `VideoSKUCapability`

新增版本化、只读解析结果：

```text
public_model
version
content_hash
request_fields / value_domains
media_types / media_combinations
supports_direct_media
supports_managed_assets
supports_mixed_media_paths
lifecycle_capabilities
required_profile_capabilities
```

请求进入 Link 合同层后解析一次，后续规范化、Ability 候选过滤、素材交集、分发、发送前复检和
attempt/Task 快照只使用该对象，不重新读取当前配置。

## 6. 核心时序

### 6.1 视频与潜在异步图片创建

```mermaid
sequenceDiagram
    participant C as Client
    participant R as Relay
    participant DB as Database
    participant U as Provider
    participant S as Shared Scheduler

    C->>R: create request
    R->>R: freeze SKU capability, route, adapter and billing
    R->>DB: insert prepared attempt and optional client claim
    R->>DB: lock authorization rows; preconsume + held + sending + reservations
    DB-->>R: commit (authorization use accepted)
    R->>U: POST create
    alt trustworthy async task id
        U-->>R: task id
        R->>DB: create Task + transfer hold + bind reservations + complete attempt
        R-->>C: public task id
    else synchronous image result
        U-->>R: data[]
        R->>DB: settle + complete attempt + completed_no_replay claim
        R-->>C: HTTP 200
    else ambiguous outcome
        R->>DB: mark unknown; keep hold and reservations
        R-->>C: create_outcome_unknown
        S->>DB: bounded reconciliation
    end
```

`prepared` 必须在预扣前耐久化。授权 reservation、预扣、hold 与 `sending` 在一个事务提交；
只有提交成功才能进入 Provider POST。

### 6.2 真人撤回并发

创建和撤回都按 authorization ID 升序锁定授权行，避免多真人素材请求产生死锁：

- 撤回先取得锁并提交：后续 reservation 校验失败，请求在上游发送前返回
  `real_person_authorization_revoked`；
- reservation 先提交：该请求已经在平台语义上被接受。撤回按
  `authorization_id + state` 找到 attempt/Task，记录审计并按冻结生命周期能力尝试取消；
- 不持有数据库锁跨越网络请求；
- 无论哪一方先提交，`VideoProxy` 都在实际回源前查询关系及授权，撤回后不向 Provider 发起
  视频或 last-frame GET。

### 6.3 合同失败结算

收到可信、完整且确定不可交付的终态结果时：

1. CAS 把 Task 推进为 `PROVIDER_CONTRACT_FAILURE`；
2. 固化 `operation=refund`、`target_quota=0`、`reason=provider_contract_failure`；
3. `ApplyTaskBillingTarget(0)` 与 exposure/outbox 原子执行；
4. 成功后 `billing_state=settled`；
5. 写入失败时 `billing_state=failed`，现有终态补偿扫描重试同一目标；
6. 重复轮询和补偿不重复退款、不重复 exposure。

## 8. 实施顺序

### P0：状态和数据表

1. 增加 `TaskCreateAttempt`、`TaskAssetAuthorization`、`ProviderCostExposure` 模型和索引；
2. 增加 `PROVIDER_CONTRACT_FAILURE` 及 Task 状态辅助函数；
3. 增加 `completed_no_replay` claim 状态；
4. 只完成迁移与纯模型测试，不接入流量。

### P1：计费映射

1. 让新增终态使用 `ApplyTaskBillingTarget(0)`；
2. exposure 与资金结果同事务或唯一 outbox；
3. 验证成功直接 `settled`，注入失败后 `failed` 可补偿到 `settled`；
4. 验证 `released_with_exposure` 不创建 Task、不进入 Task billing。

### P2：发送前 attempt

1. 在渠道、能力和价格均已确定后建立 `prepared`；
2. 把预扣、hold、`sending` 和真人 reservation 放入同一事务；
3. 接入正式视频，再接入 `media_task_image_blocking`；
4. 删除发送后普通错误路径中的即时退款/换渠道；
5. 扩展 `RunTaskPollingOnce` 扫描陈旧 `sending/unknown`；
6. 扩展 `async_task_poll.Enabled()`，保证只有 attempt/billing/outbox 工作时仍会调度。

### P3：图片幂等

1. 媒体任务 route 同步成功改写 `completed_no_replay`；
2. 同键重放返回 409，不触发 converter；
3. 异步 Task 仍按现有方式回放；
4. 普通同步 route 保持不创建 claim。

### P4：真人撤回

1. 发送前 reservation 与撤回事务锁定同一授权行；
2. Task 创建时绑定 reservation；
3. 撤回扫描覆盖 reserved attempt 和 task-bound Task；
4. `VideoProxy` 在任何 URL 解析、Data URL 输出或上游 GET 前执行授权门；
5. 暂不增加缓存。

### P5：SKU 能力冻结

1. 增加能力注册与稳定 hash；
2. Ability 发布时拒绝不等价候选；
3. 运行时在素材交集前过滤；
4. adapter 发送前使用同一快照复检；
5. attempt/Task 保存版本、hash 和生命周期能力；
6. 逐个公开 SKU 对账开发者指南与 `docs/openapi/relay.json` 中的字段、值域、媒体数量/组合和
   生命周期；注册表、文档或 OpenAPI 任一不一致时阻断发布。

### P6：告警、灰度与清理

1. 增加 exposure 金额、数量、速率、转换率和最老年龄指标；
2. 告警事件包含受影响 SKU 及剩余等价候选数；
3. 唯一候选被停用时整个 SKU fail closed；
4. 完成人工恢复入口、审计和内部灰度；
5. 删除被新模型取代的旧释放/退款分支，不做无关重构。

## 9. 迁移与兼容

- 新表为空上线，不根据 `private_data` 执行数据库 JSON 反向更新；
- 真人能力当前不实际使用时，先上线 reservation 与内容门，再开放相关 SKU；
- 如果存在历史真人 Task，应用层分批读取 Task 并在 Go 中解析私有快照生成关系；无法证明完整
  授权关系的历史任务内容 fail closed，不能默认放行；
- 历史 Task 没有 `PROVIDER_CONTRACT_FAILURE`，无需状态回填；
- 现有 `TaskCreateIdempotency` 行没有 `attempt_id` 时继续走只读兼容恢复；新创建必须关联
  attempt；
- claim TTL 到期前不得复用 `completed_no_replay`；TTL 到期后的新业务请求按新操作处理；
- 渠道配置变更只影响新请求；在途 attempt/Task 始终使用冻结连接。

## 10. 测试计划

### 10.1 数据模型与三库

- attempt 状态转换和资金门闩只允许合法边；
- claim/attempt、reservation 和 exposure 唯一约束；
- `next_attempt_at`、deadline、`authorization_id + state`、exposure 维度命中普通索引；
- SQLite 测试通过；MySQL/PostgreSQL 环境验证迁移、行锁和条件更新；
- 不使用数据库 JSON 查询发现恢复或撤回对象。

### 10.2 创建故障注入

- `prepared` 后预扣失败：没有上游请求，attempt 安全关闭；
- hold/`sending` 提交后、POST 前进程退出：陈旧 `sending` 转 unknown，不退款、不重发；
- POST 成功后响应读取前退出：hold 和 reservation 保留，可人工恢复；
- 已取得上游 ID、Task 提交前退出：从 attempt 恢复，不重复 POST；
- unknown 到期：只释放一次，exposure 只写一次，晚成功不补扣客户。
- 数据库只有到期 attempt、billing `failed` 或 exposure outbox 而没有活动 Task 时，
  `async_task_poll` 仍被启用并完成处理。

### 10.3 图片幂等

- 媒体任务 route 返回同步 200 后 claim 为 `completed_no_replay`；
- 同键同请求返回 409，mock Provider 调用次数仍为 1；
- 同键异请求返回 `idempotency_conflict`；
- 异步 202 同键重放返回同一 Task；
- 无 Key unknown 的后续请求是新操作，错误文案不宣称可恢复原 attempt；
- 普通同步 route 不创建 claim/attempt。

### 10.4 计费与 exposure

- `PROVIDER_CONTRACT_FAILURE` 目标为 0，成功后 billing `settled`；
- 注入资金持久化失败后 billing `failed`，补偿后变为 `settled`；
- `FAILURE`、`EXPIRED` 与合同失败 reason/指标互不混用；
- exposure 与退款之间不存在单边提交；
- 重复轮询、补偿、人工确认不重复退款或记录 exposure。

### 10.5 真人授权

- 创建和撤回两个提交顺序均用同步屏障构造，而非 sleep；
- 撤回先提交：Provider POST 次数为 0；
- reservation 先提交：撤回能索引 attempt/Task 并只安排一次取消；
- 主视频与 `?part=last_frame` 在撤回后均返回
  `real_person_authorization_revoked`，Provider GET 次数为 0；
- 多真人素材按固定 authorization ID 顺序加锁；
- 不同用户、缺失关系和损坏关系均 fail closed。

### 10.6 SKU 能力

- 能力缺失、版本/hash 不匹配的候选在发布和运行时都被拒绝；
- 管理员在请求处理中升级能力，只影响后续新请求；
- 发送前复检仍使用原冻结对象；
- 唯一等价渠道自动停用时不回退到不等价 profile；
- 当前三个 Seedance SKU 的 `duration`、`resolution`、`ratio`、媒体角色/数量，以及 Kling/即梦
  已发布字段与生命周期，均与能力注册、OpenAPI 和各自用户文档逐项一致；任何一侧漂移都使
  合同校验失败。

## 11. 上线门禁

以下任一项未完成不得启用新视频 profile、持久化图片 converter 或真人托管素材任务：

- 发送前 attempt 与 hold/`sending` 原子性通过故障注入；
- 同步图片 409 幂等合同与客户端文档一致；
- 新 Task 终态、零目标结算和 exposure 原子性通过；
- 真人 reservation/revoke 并发和内容回查通过；
- SKU 能力版本/hash 冻结与三重等价校验通过；
- shared scheduler 能处理 sending、unknown、reconciliation、billing failed 和 outbox；
- exposure warning、paging、自动停用和人工恢复阈值已配置；
- 公开 API Reference 和 `docs/30-engineering/` 用户指南只描述已生效行为；目标态能力在实现前
  必须明确标为未生效，不能用上线门禁代替用户文档中的当前状态说明；
- `task docs:check`、`task ai:check`、相关 Go 测试和根模块构建通过；
- 若改动 `relaykit/`，额外执行 `cd relaykit && GOWORK=off go build ./...`。

## 12. 灰度与回滚

灰度顺序：

1. 仅迁移表和读路径，保持功能开关关闭；
2. 开启 exposure/attempt shadow 指标，不发送新类型流量；
3. 内部单 SKU、单渠道开启视频 attempt；
4. 开启持久化图片 route，分别验证同步 200 与异步 202；
5. 真人路径只使用测试授权与受控素材，不进入真实业务；
6. 稳定后逐 SKU 扩大。

回滚要求：

- 先移除新 Ability/关闭新流量，不删除表或历史记录；
- 保持 `UPDATE_TASK=true` 和 `async_task_poll`，继续处理在途 attempt、Task、billing 与 outbox；
- 不释放 unknown hold、不批量重发 POST；
- 不修改在途冻结连接或 capability；
- 唯一渠道被停用时保持 SKU 不可用，修复和对账完成后人工灰度恢复；
- 全部在途记录闭合后才允许下线兼容读取。

## 13. 完成标准

- Link 合同、渠道 profile、SKU 能力和任务快照各自只有一个权威来源；
- 有无客户端 Key 都不存在未记录的上游创建窗口；
- 同步图片同键重放不会重复生成或重复扣费；
- 四类轮询/终态情形在状态、计费、错误和指标上可区分；
- `PROVIDER_CONTRACT_FAILURE` 成功退款为 billing `settled`，资金失败可补偿；
- 真人撤回与创建具有明确线性化点，内容端点撤回后零上游回源；
- 所有恢复、撤回和 exposure 查询使用普通索引并兼容三种数据库；
- 自动停用唯一渠道时 SKU 明确 fail closed，恢复只能人工审计后执行；
- 稳定架构文档、开发者指南、运维手册和实际实现一致。
