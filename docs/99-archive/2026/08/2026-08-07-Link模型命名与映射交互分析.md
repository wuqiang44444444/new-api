# Link 视频模型命名与映射交互分析

## 1. 目标与设计原则

本文只分析 Link 视频渠道选择服务合同后的模型命名与 `model_mapping` 交互。普通 NEWAPI
渠道保持上游原有行为，图片模型不因本文自动采用同一交互。

本文所述后端映射、execution binding 与失败关闭链路是现有权威实现；第 4 节所述新建表单默认
投影也已落地。它只影响未保存的 Link 视频渠道表单，不构成存量配置迁移或生产发布声明。

核心设计原则是：

> 任何用户只操作自己关心且有权决定的内容；不需要由该用户决定的内容由系统根据权威事实
> 默认提供或自动处理，也不必在常规界面中展示。

这不是尽量隐藏所有细节，而是按角色划分最小关注面：

- 客户只关心请求时使用的模型名和返回结果；
- 管理员或运维人员只关心自己定义的客户模型名，以及该名称最终映射到的真实模型名；
- 系统内部负责 Link SKU、implementation、execution binding、capability、publication 和发送前复检；
- 审计和故障诊断可保留全部内部事实，但不因此把它们变成常规配置项。

## 2. 管理员真正关心的两个模型名

对管理员而言，模型配置只有两个可操作概念：

| 概念 | NEWAPI 字段 | 管理员决定什么 |
| --- | --- | --- |
| 客户模型名 | `channels.models` | 客户在模型列表中看到、在请求中填写的名称 |
| 真实模型名 | `model_mapping` 的最终目标 | 选中渠道在 Provider 请求中实际使用的模型名 |

本文中的“真实模型名”特指所选 Link implementation 在
`execution_bindings[].provider_model` 中显式登记、最终发送给 Provider 的模型名。
它不是 Link SKU、方案展示名或 Provider 展示名。

管理员不需要关心 Link SKU 的字符串名称。SKU 是系统用于能力校验、等价履约、计费和审计的
内部合同身份，不进入管理员的模型命名工作流。

## 3. 回归 NEWAPI 原有的模型映射方式

NEWAPI 的原有翻译方向保持不变：

```text
客户模型名
  -> 渠道 model_mapping
  -> 真实模型名
```

没有 mapping 时使用身份翻译：

```text
客户模型名 == 真实模型名
```

Link 不增加第二张映射表，不把 SKU 塞入 `models` 或 `model_mapping`，也不在没有
mapping 时根据 execution binding 暗中把 SKU 或客户名改写为 Provider 模型。

系统内部在 NEWAPI 映射完成后继续处理：

```text
真实模型名
  + 精确 implementation
  + route family / action / profile
  -> execution binding
  -> Link SKU
  -> capability 校验
  -> 创建或核对 publication
```

这条内部链路必须可持久化、可审计并在 Provider POST 前复检，但不必把 SKU 名称暴露为管理员
必须理解的配置概念。

## 4. 选择 Link 服务合同后的默认行为

### 4.1 默认模型来源

精确 Link 接入方案已经在代码注册了 Provider、profile、路径、adapter 和 execution bindings。
后端现状是先按 NEWAPI 原生方向把客户模型解析为 Provider 模型，再由 execution binding 正向
推导 Link SKU。管理端默认投影则从当前 implementation 的 create execution bindings 中读取真实
模型名：

```text
execution_bindings
  -> 过滤 action=create 和当前 route/profile
  -> provider_model
  -> 真实模型候选
```

不得使用以下信息生成真实模型候选：

- `public_skus` / Link SKU；
- Provider 或方案展示名；
- `plan_name`；
- 模型名相似度；
- 其它渠道的映射或当前 publication。

### 4.2 默认投影

新建 Link 视频渠道、`models` 与 `model_mapping` 均为空且管理员选择 Link 方案后，管理端把唯一
route、当前视频 profile 下登记的真实模型名填入现有 `Models` 编辑器，作为可编辑的默认值。这只是
提供已登记的事实，不代表后台已保存、发布或替管理员决定了客户名称。无法唯一确定 route 时不填充。

选择方案时必须保持 `model_mapping` 不变：

- 不自动生成 `Link SKU -> 真实模型`；
- 不自动生成 `真实模型 -> 真实模型` 自映射；
- 不自动生成 `客户自定义名 -> 真实模型`；
- 不覆盖、合并或删除管理员已经维护的 mapping。

如果 `models` 或 `model_mapping` 已有内容，切换 Link 方案时不得自动改写。界面可以提供真实
模型候选和不兼容提示，最终变更必须由管理员在 NEWAPI 原有字段中显式完成。

## 5. 渠道管理交互

### 5.1 常规配置面

管理员继续使用 NEWAPI 原有的两个入口：

1. `Models`：决定客户可见、可授权、可路由的模型名；
2. `Model Mapping`：在需要时由管理员显式配置“客户模型名 -> 真实模型名”。

界面不增加以下第二套工作流：

- 单独的“客户展示名称”字段；
- 修改展示名后由系统自动生成 mapping；
- 客户模型到 Link SKU 的可编辑映射；
- SKU 选择器、SKU 模型输入框或要求管理员理解 SKU 命名的常规提示。

真实模型候选可作为 `Models` 或 `Model Mapping` 的受控建议项，但选择、改名和映射仍是管理员
的显式操作。

### 5.2 系统管理的内部事实

选择 Link 方案后，系统仍自动投影并锁定管理员不需要自由编辑的内容：

- Provider implementation ID/version/content hash；
- 视频与素材 profile；
- 创建路径、查询路径和 adapter；
- route family、action 和 execution binding；
- Link SKU capability、publication version 和当前履约资格；
- Task、计费、素材、授权和审计快照。

这些事实必须被保存和复检，但常规渠道编辑界面只需展示会影响管理员当前决策的摘要。
完整 SKU、binding 和 publication 身份可仅在审计、高级诊断或需要解释冲突时按权限展开。

## 6. 配置示例

### 6.1 直接使用真实模型名

管理员不需要自定义客户名称时：

```text
models = seedance-2.0-vip-720p-azhw-feicai
model_mapping = 空
```

请求与发送方向为：

```text
seedance-2.0-vip-720p-azhw-feicai
  -> 身份翻译
  -> seedance-2.0-vip-720p-azhw-feicai
```

系统内部再通过精确 execution binding 证明该真实模型履行对应 Link SKU。

### 6.2 管理员自定义客户模型名

```text
models = my-seedance-standard

model_mapping = {
  "my-seedance-standard": "seedance-2.0-vip-720p-azhw-feicai"
}
```

请求与发送方向为：

```text
my-seedance-standard
  -> model_mapping
  -> seedance-2.0-vip-720p-azhw-feicai
```

客户只看到 `my-seedance-standard`；管理员看到自定义名与真实模型的对应关系；系统内部处理
SKU、capability 和 publication。

## 7. 保存、发布与失败关闭

前端候选和默认填充只是未保存的编辑辅助，不触发后台保存、Ability 发布或 publication 创建。
管理员显式保存或启用渠道时，后端继续执行权威校验：

1. 每个 `models` 条目沿既有 `model_mapping` 解析到最终真实模型；
2. 真实模型必须在精确 implementation、route family、action 和 profile 下唯一命中 execution binding；
3. 系统内部推导 Link SKU，校验 capability、路径、adapter、素材能力和 exposure 资格；
4. 启用时创建或核对以客户模型名为键的 publication，再发布 Ability；
5. Provider POST 前复检映射后的真实模型、implementation 和冻结合同仍一致。

以下情况必须失败关闭：

- mapping 最终目标不是已登记的真实模型；
- 无 mapping 时，`models` 中的名称无法作为真实模型命中唯一 binding；
- mapping 循环、空目标、多义或绕过已登记执行形状；
- 新的真实模型导出的内部合同与已有 publication 不一致；
- 已发布合同没有合格候选、实现未知或发送前复检失败。

普通保存不得静默改变已有 publication 的内部合同。需要改变时仍必须通过具备权限、
expected version 和原因的显式 rebind。常规界面可将这一影响表达为“该客户模型对应的服务能力
将发生变化”，不必要求管理员依赖 SKU 字符串完成日常决策。

## 8. 可见性与信息分层

| 角色 | 默认展示 | 默认不展示 |
| --- | --- | --- |
| 客户 | 客户模型名、请求与结果 | 真实模型、SKU、implementation、Provider 路径 |
| 渠道管理员 | 客户模型名、真实模型名、mapping、可操作的兼容性错误 | SKU 字符串、content hash、完整 binding 键、内部快照 |
| 审计/高级诊断 | publication、SKU、implementation/version/hash、binding、冻结快照 | 无权限客户不应看到的凭据或原始 Provider 响应 |

不展示不等于不记录或不校验。内部合同事实必须完整、可追溯、可复检；但只在对当前角色的任务
有实际作用时才展示。

## 9. 当前已配置视频模型的影响

评审于 2026-08-09 进行；以下事实依据最后修改于 2026-08-07 17:13 +0800 的工作区
`one-api.db` 快照。现有 8 条 Link 视频渠道中 6 条启用、2 条手动禁用；该快照不代表外部生产
数据库状态。

| 渠道 | 当前形态 | 影响与处理 |
| --- | --- | --- |
| Channel 48 BytePlus 官方 | 客户名映射到 Endpoint ID；渠道禁用 | Endpoint ID 与当前 execution binding 的身份边界尚未一致；不自动迁移，闭合设计前不启用 |
| Channel 49 墨行、50 墨行（官 KEY） | 客户名与真实模型同名，但保留自映射 | 可单独删除冗余自映射；真实模型、Ability、计费和 publication 不变，不需 rebind |
| Channel 51 飞彩稳定 VIP | 5 个客户名显式映射到 5 个真实模型 | 已符合本设计；必须保留当前 `models` 和 mapping，不自动替换为真实模型名 |
| Channel 52 飞彩非稳定 933／实验 | 自定义客户名 `seedance-2.0-unstable-720p` 显式映射到真实模型 | 已符合本设计；保留当前客户合同与 mapping |
| Channel 53/54 FunCloud Standard/Fast | 无 mapping，使用身份翻译 | 已是目标状态，无需调整 |
| Channel 55 飞彩待验证四模型 | 4 条真实映射；渠道与 Ability 全部禁用 | 保留配置和隔离状态；不因真实模型已登记而自动发布 |

影响边界：

- 真实模型默认填充只用于新建且 `models` 为空的 Link 视频表单；编辑存量渠道时不改写模型或 mapping。
- 现有客户模型名继续作为 Ability、Token 权限、价格、计费、日志和 publication 的权威键，不做自动重命名。
- 当前 4 条历史或不活跃的视频 publication 继续保留；配置清理不删除或改写历史发布事实。
- 当前普通 OpenAI-compatible Seedance 和阿里 `happyhorse-*` 等非 Link 视频模型继续服从 NEWAPI 原生语义，不受本设计影响。

## 10. 验收不变量

1. 本交互只覆盖 Link 视频渠道，不改变普通 NEWAPI 渠道和图片模型行为。
2. 选择 Link 方案后，真实模型候选只来自当前 create execution bindings 的 `provider_model`。
3. 新建空表单可以默认填入真实模型名，但不保存、不启用、不创建 publication。
4. 选择、切换或清除 Link 方案都不会自动创建、改写或删除 `model_mapping`。
5. 无 mapping 时使用身份翻译，不生成自映射。
6. 管理员自定义客户模型名时，只通过 NEWAPI 原有 `Models` 和 `Model Mapping` 显式完成。
7. 客户模型名可以自定义，mapping 最终目标必须唯一命中已登记的真实模型和 execution binding。
8. SKU 不进入 `models` 或 `model_mapping`，也不作为管理员日常模型配置的必填、必选或必读信息。
9. 界面不增加“客户展示名称 -> 自动生成 mapping”的第二套配置流程。
10. 现有 `models` 和 `model_mapping` 在方案切换时不被静默覆盖。
11. 真实模型未登记、binding 不唯一、资格不完整或发送前复检不一致时失败关闭。
12. 普通保存不能静默改变已有 publication；rebind 仍需权限、expected version 和原因。
13. 客户、渠道管理员和审计人员只默认看到完成各自任务所必需的信息。
