# 用户邮件通知改造方案

> 本文是已完成业务评审的待实施方案，不是当前生产事实。实施后必须把长期边界收敛到
> `20-architecture/`，并完成真实 SMTP、三数据库与灰度验证。本文不得用于声称功能已经生产发布。

## 1. 背景与目标（Context）

需求：对用户发送**事件即时**通知邮件，覆盖三类事件——账户创建、密码修改、密钥（Token）创建。（"账户余额"提醒已存在，不在本期范围。）

现状摸底结论：

- SMTP 收发（`common.SendEmail`）与多通道分发（`service.NotifyUser`）**已完整存在**，支持 email/webhook/bark/gotify、每用户每小时限频、`NotificationEmail` 地址覆盖。
- **余额低提醒已存在**：`service/quota.go:457 checkAndSendQuotaNotify`，全局 `QuotaRemindThreshold` + 每用户 `QuotaWarningThreshold`。
- 但三类目标事件的通知**不存在**。
- 关键事实：**今天所有通知在调用点都是硬编码 always-on，没有 per-event 开关**；全产品唯一的"发生 X 就发邮件"配置是 Operations → Monitoring & Alerts 里的 `QuotaRemindThreshold`（一个阈值，不是开关）。

目标：补齐三类事件通知，做成**系统配置驱动的 per-event 开关**，贯彻最小入侵（新逻辑进新文件、后端现有文件只单行接线 + 极窄校验；"邮箱强制"需求会在前端带来两处不可避免的表单改动）、中英双语、异步 fire-and-forget。

## 2. 评审决策（已锁定）

1. **事件即时**，内联触发，放在 **controller 提交事务之后**——不放 model 尾部，避免 `model → service` 循环依赖。
2. **异步** `gopool.Go`，失败不重试（"失败了问题不大"）。
3. **配置驱动**：新建注册块 `notification_setting`（Pattern b：`config.GlobalConfig.Register`，自动接进 GET/PUT `/api/option`，不写 case、不 seed OptionMap），三个 bool 开关。
4. **统一走 `service.NotifyUser`**（复用地址解析、`NotificationEmail` 覆盖、限频、未设 NotifyType 默认 email）。
5. **中英双语**，`i18n.Translate(lang, key, ...)`；新增一组 key；旧邮件不动。
6. **邮箱强制**：`Register` + `CreateUser` 两处要求 `Email != ""`；OAuth/微信不强制（provider 没返回邮箱则欢迎信静默跳过）；存量用户前端设置页给一行提示；**不做邮箱验证、不加 `email_verified` 列**。
7. **不做**同意/退订/法律分类；**不改**现有 always-on 通知。
8. 开关 UI **塞进现有 Operations → Monitoring & Alerts** section，不新建 tab。

## 3. 改造范围与挂钩点（最小入侵设计）

### 3.1 后端新增文件（零上游入侵）

- `setting/operation_setting/notification_setting.go`
  照搬 `monitor_setting.go` 的 Pattern (b) 形状：结构体 `NotificationSetting{ SendEmailOnAccountCreated, SendEmailOnPasswordChanged, SendEmailOnTokenCreated bool }`，默认全 `false`，`init()` 里 `config.GlobalConfig.Register("notification_setting", &notificationSetting)`，导出 `GetNotificationSetting()`。

- `service/user_lifecycle_notify.go`
  三个封装函数：`NotifyAccountCreated(userId)`、`NotifyPasswordChanged(userId)`、`NotifyTokenCreated(userId)`。每个函数内部统一做：读 `GetNotificationSetting()` 对应开关 → 关闭则直接 return → `gopool.Go` 异步 → 取 `model.GetUserLanguage(userId)` → `i18n.Translate` 构双语标题/正文 → `NotifyUser(userId, email, setting, dto.NewNotify(...))`。**调用点因此只剩一行**。
  复用：`service.NotifyUser`、`model.GetUserLanguage`、`model.GetUserById`+`GetSetting()`、`i18n.Translate`、`relaykit/dto.NewNotify`。

- i18n：`i18n/locales/{en,zh-CN,zh-TW}.yaml` 追加一组 `notify.account_created.*` / `notify.password_changed.*` / `notify.token_created.*`（标题 + 正文）；`i18n/keys.go` 追加对应常量。

校验用现有 i18n 错误消息常量（如 `i18n.MsgUserEmailVerificationRequired` 同类），不新增错误码。另：`CreateUser` 的 `cleanUser` 当前丢弃 email（`user.go:1032`），需补 `Email: user.Email`，否则即便校验通过也存不进库。

### 3.3 前端

**开关 UI（小改，复用现有模式）：**

- `web/src/features/system-settings/types.ts`：`OperationsSettings` 加三个 bool 字段（PascalCase option key，如 `SendEmailOnAccountCreated`，与 `QuotaRemindThreshold` 同型）。
- `web/src/features/system-settings/integrations/monitoring-settings-section.tsx`：在 `QuotaRemindThreshold` 旁加三个 `SettingsSwitchItem` + zod 字段；**复用现有逐字段 diff + `updateOption.mutateAsync` 保存循环**，不写新保存逻辑。

**邮箱强制带来的表单改动（真实工作量，非"+2 行"）：**

- 注册表单 `web/src/features/auth/sign-up/components/sign-up-form.tsx`（`:299`）：邮箱字段当前包在 `emailVerificationRequired && (...)` 内 → 拆出**始终渲染且必填**；验证码字段保留条件渲染；标签 "Email (required for verification)" → "Email"。
- 管理员建号抽屉 `web/src/features/users/components/users-mutate-drawer.tsx`：当前**无邮箱字段** → 新增 email 输入 + 必填校验。
- 个人设置页：`Email == ""` 时显示一行提示文案（条件渲染，i18n key）。

### 3.4 最小入侵自检

- 新逻辑 100% 在新文件（`notification_setting.go`、`user_lifecycle_notify.go`、i18n yaml/key 常量）。
- **后端**现有文件改动两类：(a) 单行 `service.NotifyXxx(...)` 接线（5 处 controller）；(b) 校验 + `CreateUser` 补 `cleanUser.Email` 字段。无重命名、无重排、无抽象提取。
- **前端**有两处真实表单改动（注册表单邮箱字段重构、管理员建号抽屉新增邮箱字段），由"邮箱强制"需求决定、无法再压扁；开关 UI 与个人设置提示为复用现有模式的小改。
- 每处 controller 接线说明必要性（事件唯二/唯一触发点）与上游冲突面（单行，冲突极易解决）。

## 4. 不做（Out of Scope）

- 不引入事件总线 / observer（沿用内联机制）。
- 不改现有 always-on 通知（渠道禁用、额度耗尽）。
- 不修余额提醒的电平 vs 边沿问题、不补异步任务计费路径缺口（单独事项）。
- 不做邮箱验证、不加 `email_verified` 列。
- 不做退订 / 同意 / 营销分类。
- 不新建 settings tab。

## 5. 验证

- 后端：`go build ./...`；`go vet`；触发三类事件手动验证（需配真实 SMTP 或本地 mailhog）。
- `relaykit`：`cd relaykit && GOWORK=off go build ./...`（确认注册块在主模块、不影响 relaykit 独立构建）。
- 三数据库：`notification_setting` 走 `options` key-value 表，**无 schema 迁移**，天然兼容 SQLite/MySQL/PostgreSQL。
- 前端：`cd web && bun run build`；Operations → Monitoring & Alerts 切换三个开关，验证 `PUT /api/option` 持久化与重载。
- 端到端矩阵：开关关 → 不发；开关开 + 有邮箱 → 发中英邮件；开关开 + 无邮箱 → 静默跳过；注册自动 token → 只收欢迎信、不收密钥信。

## 6. 风险与权衡

- **model → service 循环**：通过把通知放 controller 层规避，model 层零改动。
- **NotifyUser 限频可能压掉 password-changed**：单人小时级改密不现实，可接受；若后续要绝对保证，可让该事件单独直发 `common.SendEmail`（与现有重置密码邮件一致）。
- **邮箱不可信**：本期接受"发到注册/管理员填写的邮箱"，不做验证；未来需要可信送达时再加 `email_verified`。
- **上游同步冲突面**：5 处单行 controller 接线，冲突极小且语义独立。
