# 飞彩十模型双渠道专用协议设计

## 问题与目标

飞彩 Seedance 2.0 首批需要一次上线 10 个客户模型。当前代码把飞彩线路表达成通用
`url_media_arrays_v1` / `third_party_json_video_media_arrays`，只有 3 个 720p Provider 模型的
size evidence，且计费探针对该 profile 固定返回按秒计费。这不足以区分飞彩的固定输出分辨率、
SD2 图片必填、Pro PI 固定 15 秒/按次计费以及音视频输入差异。

本次目标是：

1. 将飞彩明确定义为 Provider 专用协议 `feicai_videos_v1`，不与其它渠道复用；
2. 精确登记 10 个 Provider 模型的固定输出分辨率、时长、媒体输入和计费模式；
3. 首版仅开放北向 `aspect_ratio=16:9`，统一转为飞彩南向 `size=1280x720`；
4. 使用两个 `ChannelTypeSeedanceLink` 渠道分别承载 VIP 与性价比五模型；
5. 删除旧 profile、旧 Channel 及其历史 Task、attempt 和直接关联数据，不保留兼容分支。

## 当前实际情况

### 已验证事实

- 模型名称中的 `720p` / `1080p` / `4k` 表达该 Provider 模型的固定输出分辨率；
  SD2 和 Pro PI 需要精确表格，不能靠名称模糊推断。
- 飞彩文档将 `size` 定义为画幅尺寸。已有黑盒证据表明：对 1080p/4K 模型发送
  `1280x720` 仍分别产出 1920x1080 和 3840x2160，因此输出清晰度由模型决定，
  `size` 只表达 16:9 画幅。
- 当前运行时会在模型映射后进入计费探针，再建立 durable create attempt，最后调用 adapter
  组装 Provider 请求。因此模型专用校验必须在计费探针阶段就失败关闭，不能等到持有资金后才拒绝。
- 本地数据库没有 `ChannelTypeSeedanceLink` 飞彩渠道。现存飞彩渠道是旧
  `DoubaoVideo` 类型，不具备 ModelArk V3 Link 履约资格。
- 历史任务曾使用 `third_party_json_video_media_arrays`；经明确清理授权，这些 Task、attempt 与直接关联数据
  已删除，因此运行时不再需要识别该 profile。

### 不作为当前事实的内容

- 未做真实 Provider 十模型全链路、真实账单和生产灰度验收；
- 不声明 9:16 或更宽画幅可对客户开放；
- 不根据域名、Key、模型名或旧 Channel 自动推断飞彩身份；
- 不把代码登记表解释为可由管理员编辑的逐模型 capability 系统。

## 优化方案

### 1. 协议与 profile 边界

```text
新 Channel 管理协议：feicai_videos_v1
新 Task 内部 profile：third_party_feicai_videos
素材协议：none
```

`url_media_arrays_v1` 从新 Channel 可选枚举中移除，不保留 alias、双读、自动迁移或回退。旧 profile
及其 poll/content dispatch 已随历史任务清理一并删除。

### 2. 两渠道与十模型

| 渠道 | 客户模型 | Provider 模型 |
| --- | --- | --- |
| 飞彩 VIP | `seedance-2.0-mini-720p` | `seedance-2.0-vip-720p-mini-azhw` |
| 飞彩 VIP | `seedance-2.0-fast-720p` | `seedance-2.0-vip-720p-fast-azhw` |
| 飞彩 VIP | `seedance-2.0-standard-720p` | `seedance-2.0-vip-720p-azhw` |
| 飞彩 VIP | `seedance-2.0-standard-1080p` | `seedance-2.0-vip-1080p-azhw` |
| 飞彩 VIP | `seedance-2.0-standard-4k` | `seedance-2.0-vip-4k-azhw` |
| 飞彩性价比 | `seedance-2.0-sd2-720p` | `seedance2.0-sd2` |
| 飞彩性价比 | `seedance-2.0-value-720p` | `seedance-2.0-933-720p-azhw` |
| 飞彩性价比 | `seedance-2.0-value-1080p` | `seedance-2.0-933-1080p-azhw` |
| 飞彩性价比 | `seedance-2.0-value-4k` | `seedance-2.0-933-4k-azhw` |
| 飞彩性价比 | `seedance-2.0-pro-pi-720p` | `seedance-933-pro-pi` |

两个 Channel 分别固定自己的 Base URL 和单一凭据。拆分的原因是凭据与运营作用域不同，不是为了
失败重选或 fallback。任一客户模型只能出现在其中一个已启用 Channel。

### 3. Provider 模型登记表

adapter 使用精确 Provider 模型名查表，不做字符串模糊推断。每个登记项包含：

- 固定输出分辨率：720p、1080p 或 4K；
- 允许时长范围，Pro PI 为固定 15 秒；
- 图片、音频和参考视频数量边界，SD2 图片必填，Pro PI 可用参考视频；
- 计费模式：Pro PI 按次，其余九个按秒。

校验函数同时为计费探针和创建请求服务，保证计费和真实 Provider POST 使用同一份模型事实。

### 4. 首版 size 合同

```text
客户 resolution = 当前 Provider 模型的固定分辨率
客户 aspect_ratio = 16:9
飞彩 size = 1280x720
```

任意分辨率不匹配、非 16:9 或缺少显式分辨率/画幅的请求都在建立资金 hold 前返回 400。
不静默默认、钳制、改义或将 4K 模型降级为 720p。

### 5. 对其它渠道的影响

- ModelArk V3 北向、确定性选渠道、durable attempt、Task 冻结、内容代理和结算底座不变；
- 火山、BytePlus、`media_task_v1`、`ark_media_v1` 和 FunCloud 的协议/profile 不变；
- 飞彩分支只由类型 61 + `feicai_videos_v1` 精确选中，不通过模型名影响通用代码；
- 以后线协议形状相似的其它 Provider 仍需建立自己的协议和 adapter，不复用飞彩名称或登记表。

### 6. 数据库目标状态

- 新建两个初始停用的类型 61 Channel，分别登记 VIP 五模型和性价比五模型；
- 用精确 `model_mapping` 完成客户模型到 Provider 模型转换；
- 设置 `video_upstream_protocol=feicai_videos_v1` 和 `asset_upstream_protocol=none`；
- 删除旧飞彩 `DoubaoVideo` Channel、Ability、历史 Task、attempt、幂等记录及直接关联的日志和计费审计数据；
- 删除 `third_party_json_video_media_arrays` profile、adapter revision、响应归一和内容代理兼容代码；
- 两个新 Channel 只能在真实 Provider 与计费验收通过后手工启用。

## 验证与风险

- 单元测试覆盖 10 个精确模型的 size、时长、媒体边界和计费模式；
- 协议注册、路径、adapter version、飞彩轮询/内容代理分别回归；
- 渠道管理 UI 只显示飞彩专用协议，七种语言文案同步；
- 数据库变更前做可恢复备份，不输出或复制密钥；
- 本地代码与测试通过不等于十模型真实上线。真实视频、任务成本和生产灰度仍是启用门槛。
