# Seedance 视频统一北向合同完整实施方案

## 1. 文档目的、权威边界与状态

本文把当前 Link 架构约束落实为 Seedance 统一北向合同的实施方案，重点补全并迁移既有 capability、
发布门禁和南向适配机制，补充规范字段值、全部已注册 Seedance SKU 的差异、迁移步骤和验收条件。
本文不是另建一套视频合同系统，也不创建新的合同权威：

- 当前架构事实以 `docs/20-architecture/` 的 Link 合同、视频、资源、计费文档为准；
- 当前运行时能力以代码显式注册的 `VideoSKUCapability`、`LinkImplementation` 和 execution binding 为准；
- 当前客户模型发布身份以主数据库 `LinkModelPublication` 为准，不能从本文表格、代码存在、Channel、
  Ability 或 OpenAPI 反向推断；
- 本文中的“目标”“应”“建议”和阶段任务仍是待实施事项，不得写成已经生产发布。

当前仍有精确官方模型、部分画幅和 Provider size、真实账单、外部数据库及生产灰度未闭合，因此本文
状态保持 `in-progress`。

## 2. 架构结论

Seedance 北向应统一使用 ModelArk v3 视频任务合同：

```text
POST /api/v3/contents/generations/tasks
```

统一的含义是：

- Seedance 客户模型使用相同的字段名、JSON 类型、媒体 content 结构和异步任务语义。
- `resolution` 统一使用 `480p`、`720p`、`1080p`、`4k` 中模型明确支持的值。
- `ratio` 统一使用 `16:9`、`4:3`、`1:1`、`3:4`、`9:16`、`21:9`、`adaptive` 中模型明确
  支持的值。
- 不同时接受 `2k`、`2048x1152`、`4K`、`horizontal` 等近义词；值不在 capability 中就拒绝。
- 每个客户模型显式声明支持字段、必填字段、精确值域、默认值、媒体数量/role、组合约束和生命周期。
- 南向 adapter 负责把统一语义转换成精确 Provider 请求，不允许 Provider 私有字段反向污染北向。

统一不表示所有视频模型共用一张字段并集，也不表示所有 Provider 支持相同能力。客户端必须根据
`model` 对应的 capability 构造稀疏请求。

## 3. 协议边界

### 3.1 必须保持分离的合同族

| 合同族                    | 北向入口/DTO                         | 适用模型                        | 本方案动作                   |
| ------------------------- | ------------------------------------ | ------------------------------- | ---------------------------- |
| NEWAPI 原生 OpenAI Videos | `/v1/videos` 等原生路由              | Sora/OpenAI-compatible 原生模型 | 不修改、不包装、不收紧       |
| ModelArk v3               | `/api/v3/contents/generations/tasks` | Seedance Link 客户模型          | 统一字段和值，按模型发布子集 |
| Kling v1                  | 既有 Kling 合同                      | `kling-*`                       | 保留 Kling 官方语义          |
| 即梦                      | 既有即梦合同                         | `jimeng_*`                      | 保留即梦官方语义             |

不得为了“统一视频”把 Sora、Kling 或即梦强制转换为 ModelArk DTO。合同统一发生在 Seedance
ModelArk 家族内部；不同 route family 只共享鉴权、Task、计费、资源和日志底座。

### 3.2 内部重写不是北向合同

`middleware/modelark_video.go` 当前先完成严格 DTO 解析并把 typed contract 保存到 context，然后在
Link publication、capability、资源和渠道资格检查之前，把内部请求路径临时重写到
`/v1/video/generations` 并调用后续 middleware，以复用任务基础设施。该路径是实现细节，不能作为
客户入口，也不能让后续代码重新按另一个 DTO 解释请求。后续资格检查、Provider 发送和任务快照必须
继续消费 context 中的原始 typed contract；middleware 顺序不得按“重写后才开始解析合同”来重排。

## 4. ModelArk 统一字段合同

`dto/video_contract.go` 的 `ModelArkVideoCreateRequest` 已覆盖本地统一字段主干。目标字段如下：

| 字段                      | 类型    | 统一语义                            | 发布规则                             |
| ------------------------- | ------- | ----------------------------------- | ------------------------------------ |
| `model`                   | string  | 客户模型，不是 Provider model ID    | 必填，必须有 publication             |
| `content`                 | array   | 文本及参考媒体序列                  | 按模型要求必填并校验组合             |
| `end_user_subject`        | string  | 平台匿名最终用户作用域              | Link 扩展，模型可拒绝                |
| `callback_url`            | string  | 客户回调                            | 只有完整回调合同发布后可用           |
| `duration`                | integer | 秒；`-1` 仅在模型声明自动时长时有效 | 精确范围/离散值/默认值               |
| `resolution`              | string  | 统一输出分辨率档位                  | 精确模型值域                         |
| `ratio`                   | string  | 统一画幅比例                        | 精确模型值域                         |
| `service_tier`            | string  | Provider 服务等级语义               | 只对明确支持的精确模型发布           |
| `generate_audio`          | boolean | 是否生成音频                        | 显式 `false` 也必须保留              |
| `watermark`               | boolean | 是否加水印                          | 模型级字段，不是全局字段             |
| `return_last_frame`       | boolean | 是否返回末帧                        | 模型与生命周期共同声明               |
| `execution_expires_after` | integer | 执行过期秒数                        | 模型级范围                           |
| `draft`                   | boolean | 官方草稿模式                        | 只对官方明确支持的模型发布           |
| `tools`                   | array   | 官方工具列表                        | 子结构也必须严格校验                 |
| `safety_identifier`       | string  | Provider 安全标识                   | 与 `end_user_subject` 不等价         |
| `priority`                | integer | Provider 优先级                     | 模型级范围                           |
| `frames`                  | integer | 帧数语义                            | 与 duration 的互斥由 capability 表达 |
| `seed`                    | integer | 随机种子                            | 不支持的精确模型必须拒绝             |
| `camera_fixed`            | boolean | 固定镜头语义                        | 不支持的精确模型必须拒绝             |

`content` 项统一采用：

| `type`      | 载荷            | 标准 role 示例                                 |
| ----------- | --------------- | ---------------------------------------------- |
| `text`      | `text`          | 无                                             |
| `image_url` | `image_url.url` | `first_frame`、`last_frame`、`reference_image` |
| `video_url` | `video_url.url` | `reference_video`                              |
| `audio_url` | `audio_url.url` | `reference_audio`                              |

客户媒体输入分为两条明确路径：

- 请求级直接媒体：只接受当前 SKU capability 与精确 profile 共同声明支持的 HTTP(S) URL 或 Data URL；
  它不自动获得 Asset、binding、迁移、真人授权或撤回语义；
- 平台托管资源：只使用 `asset://ast_*`，并进入 Link Resolver、所有权、App、publication、授权、
  implementation、凭据和 TTL 门禁。

Provider asset ID、账号、上游模型、完整签名 URL 和内部 implementation 不得出现在北向合同中。某个
DTO 能解析 Data URL 或 `asset://` 不代表全部模型和 profile 自动支持该输入形态。

## 5. 统一值域和缺省语义

### 5.1 分辨率

全局允许进入 Seedance capability 的规范值集合为：

```text
480p | 720p | 1080p | 4k
```

这只是标准词汇表，不表示每个模型都支持四个值。模型 capability 必须声明其精确子集或固定值。
北向不接受 `2k`、`4K`、`1920x1080` 等别名；南向允许确定性转换为 Provider 私有值。

### 5.2 画幅

全局规范值集合为：

```text
16:9 | 4:3 | 1:1 | 3:4 | 9:16 | 21:9 | adaptive
```

“部分画幅未闭合”表示：某些 Provider/模型只验证了少数 ratio，或者还没有可审计的官方证据、真实账号
黑盒结果和尺寸组合结果，因而不能证明其完整可用集合。这些模型不能用空数组或猜测值发布；只能发布
已验证子集，无法满足产品最低能力时保持未发布。

规范词汇的强制分两层：注册时由后端一致性测试对全部 ModelArk SKU 逐项校验，非规范值使 CI 失败；
北向请求时由 capability 成员资格拒绝别名——客户端传入 `2k`、`4K`、`1920x1080` 等不在该 SKU
`Resolutions`/`Ratios` 中的值，即返回稳定 `400`，而非静默改写为近义规范值。

### 5.3 缺省值

缺省值属于客户合同，不能来自 Provider 当前默认，也不能通过数组顺序或 adapter 硬编码推断。
当前 `VideoSKUCapability` 已包含：

```go
DefaultResolution string
DefaultRatio      string
ResolutionRatioCombinations []VideoResolutionRatioCombination
```

它们与现有 `DefaultDuration` 一并进入 capability hash 和请求校验。FunCloud adapter 已只消费
`DefaultDuration`、`DefaultResolution` 和 `DefaultRatio`；缺少任一默认值时失败关闭，不再从
`Ratios[0]`、数组顺序或硬编码 `720p` 推断。合法组合不是分辨率与画幅笛卡尔积时，使用
`ResolutionRatioCombinations` 显式登记。

仍未取得精确 Provider evidence 的默认值或组合不能为了填满 capability 而猜测；这类 SKU 应要求客户
显式传值或保持不可履约。

### 5.4 字段存在性

客户端应稀疏序列化。未选择的可选字段应完全省略；以下值一旦出现就属于明确客户意图：

- `false`；
- `0`；
- `-1`；
- `"default"`；
- 空数组或空对象（如果 schema 允许解析，也必须按合同校验）。

不得因为 Provider 不支持而静默移除。只有合同明确把某个值定义为“等价于字段缺失”时，才可在北向
标准化阶段转换，并且该规则必须写入 capability/version，而不能由渠道 profile 临时决定。

## 6. 当前全部 Seedance 模型及必须区分的能力

### 6.1 区分原则

当前代码注册了 15 个 ModelArk/Seedance Link SKU。它们共享 `modelark.contents.generations.v3` 客户接入
合同，但不能合并为一个大而全的 capability。至少必须区分：

1. 客户模型/SKU 与 capability version/hash；
2. 精确 implementation ID/version、profile 和 Provider 模型；
3. 必填字段、规范 resolution/ratio、时长和缺省值；
4. 参考图、视频、音频的数量、role、互斥关系和资源解析方式；
5. 生命周期、计费维度及 Provider size 证据；
6. 代码注册、机器公开投影、数据库 publication、Ability 开放和生产验收五种不同状态。

代码注册只证明模型有可校验身份。本文无法从仓库判断某个客户模型当前是否在生产数据库拥有
publication 或对某个分组开放 Ability；表中的“已登记”不得解释为“已生产发布”。

### 6.2 当前实现与能力身份

| Seedance Link SKU | capability version | 当前 implementation | profile | execution binding 的 Provider 模型 | 当前文档判定 |
| --- | --- | --- | --- | --- | --- |
| `seedance-byteplus` | `public-video-contract-v2` | `byteplus.seedance-ark/v1` | `official` | `seedance-byteplus` | 已登记；需复核精确官方模型与高级字段 |
| `seedance-2-0-oversea` | `moxing-media-task-v2` | `moxing.seedance-media-task/v2` | `third_party_relay` | `seedance-2-0-oversea` | 已登记严格子集；旧 Ark implementation 只读历史任务 |
| `doubao-seedance-2-0-260128` | `tokensave-media-task-v2` | `tokensave.seedance-media-task/v2` | `third_party_relay` | `doubao-seedance-2-0-260128` | 已登记严格子集；v1 implementation 已 deprecated |
| `seedance-2.0-standard` | `public-video-contract-v2` | `funcloud.seedance-json/v1` | `third_party_funcloud_seedance_v2` | `seedance-2.0-standard` | 已登记；显式默认值已迁入 capability |

表中的 `implementation/version` 只是把两个独立身份并列展示；斜线不是 implementation ID 的组成部分，

由模型名相似、Provider 同源或请求字段相同推断。

这些 implementation 都声明 `shared_video_task + newapi_quota`，复用同一耐久 Task 与客户 quota 事实，
不建立 Provider 专用任务系统或账本。

默认值。FunCloud 的 720p/16:9 已冻结为 capability 默认并由 adapter 消费。`seedance-byteplus` 没有

当前明确拒绝关系：

- `seedance-byteplus` 拒绝 `callback_url`、`frames`；其高级字段仍需官方模型级复核；
- 墨行与 TokenSave 两个严格子集拒绝 `end_user_subject`、`callback_url`、`service_tier`、`watermark`、
  `return_last_frame`、`execution_expires_after`、`draft`、`tools`、`safety_identifier`、`priority`、
  `frames`、`seed`、`camera_fixed`；
- FunCloud Standard/Fast 拒绝 `callback_url`、`service_tier`、`return_last_frame`、
  `execution_expires_after`、`draft`、`tools`、`safety_identifier`、`priority`、`frames`。

飞彩十个 SKU 统一只允许 `model`、`content`、`duration`、`resolution`、`ratio`；统一要求文本，最多
9 张 `reference_image`，不支持 `generate_audio` 和其它高级顶层字段。它们仍必须按 Provider 模型、
固定 resolution、时长、媒体和计费模式分别履约：

| Link SKU / Provider 模型 | 固定 resolution | duration | ratio capability | 最大图/视频/音频 | 计费形状 | 当前精确 Provider size 证据 |
| --- | --- | --- | --- | --- | --- | --- |
| `seedance-2.0-mini-720p` / `seedance-2.0-vip-720p-mini-azhw-feicai` | 720p | 4–15，必填 | `16:9` | 9/0/3 | per-second | 720p + 16:9 → `1280x720` |
| `seedance-2.0-sd2-720p` / `seedance2.0-sd2-feicai` | 720p | 11–15，必填；至少 1 图 | 未闭合 | 9/0/0 | per-second | 无 |
| `seedance-2.0-fast-720p` / `seedance-2.0-vip-720p-fast-azhw-feicai` | 720p | 4–15，必填 | 未闭合 | 9/0/3 | per-second | 无 |
| `seedance-2.0-value-720p` / `seedance-2.0-933-720p-azhw-feicai` | 720p | 4–15，必填 | 未闭合 | 9/0/3 | per-second | 无 |
| `seedance-2.0-standard-720p` / `seedance-2.0-vip-720p-azhw-feicai` | 720p | 4–15，必填 | `16:9` | 9/0/3 | per-second | 720p + 16:9 → `1280x720` |
| `seedance-2.0-value-1080p` / `seedance-2.0-933-1080p-azhw-feicai` | 1080p | 4–15，必填 | 未闭合 | 9/0/3 | per-second | 无 |
| `seedance-2.0-standard-1080p` / `seedance-2.0-vip-1080p-azhw-feicai` | 1080p | 4–15，必填 | `16:9` | 9/0/3 | per-second | registry 请求 size 为 `1280x720`；E2E 产物观察到 1920×1080（黑盒观察，逐任务 Provider 账单仍未闭合） |
| `seedance-2.0-value-4k` / `seedance-2.0-933-4k-azhw-feicai` | 4k | 4–15，必填 | 未闭合 | 9/0/3 | per-second | 无 |
| `seedance-2.0-standard-4k` / `seedance-2.0-vip-4k-azhw-feicai` | 4k | 4–15，必填 | 未闭合 | 9/0/3 | per-second | 无 |
| `seedance-2.0-pro-pi-720p` / `seedance-933-pro-pi-feicai` | 720p | 固定/默认 15 | 未闭合 | 9/3/3 | per-request | 无正式 registry 证据 |

当前正式 size registry 只登记 evidence version `feicai-prod-2026-08-05-r1` 的前三个精确组合：Mini
720p、Standard 720p、Standard 1080p 的 16:9。北向 `resolution` 和 `ratio` 闭合仍不是发布充分条件；
adapter 必须使用以下完整键唯一得到非空 size、倍率、billing class 和 evidence version：

```text
(implementation ID/version, Provider model, resolution, ratio)
  -> Provider size + multiplier + billing class + evidence version
```

其中 Standard 1080p 当前映射到 `1280x720`，与客户分辨率名称存在明显需要复核的风险；在真实输出、
Provider 账单和交付质量证明完成前，不应仅因 registry 有值就宣称该 SKU 可生产发布。未登记组合必须在
预扣和 Provider POST 前 fail closed，不能复用同档位兄弟模型的像素值。

### 6.5 参考媒体与资源能力区分

| 模型组 | 图片 role / 上限 | 视频 role / 上限 | 音频 role / 上限 | Link Asset |
| --- | --- | --- | --- | --- |
| `seedance-byteplus` | 模型级 image roles 待精确官方复核；最多 9 | 最多 3 | 最多 3，且需要视觉参考 | 支持 |
| `seedance-2-0-oversea`、`doubao-seedance-2-0-260128` | 空 role、`first_frame`、`last_frame`、`reference_image`；最多 9，参考模式互斥 | 不支持 | 不支持 | 支持 |
| `seedance-2.0-standard`、`seedance-2.0-fast` | `reference_image`、`first_frame`、`last_frame`；最多 3 | `reference_video`；最多 1 | `reference_audio`；最多 1，且需要视觉参考 | 支持 |
| 飞彩 Pro PI 720p | `reference_image`；最多 9 | `reference_video`；最多 3 | `reference_audio`；最多 3 | 支持 source URL；size 未闭合，当前不可发布 |
| 其它飞彩 SKU | `reference_image`；最多 9 | 不支持 | 支持数量见上表；有音频时需要视觉参考 | 支持 source URL；未闭合组合不可发布 |

参考媒体能力是 SKU 合同，不由 content DTO 或 Provider 名称推断。直接媒体与 `asset://` 还必须分别
满足精确 profile 的 URL/Data URL 规则和 Resolver 规则。

### 6.6 publication 与开放状态必须独立表达

不在 capability 中增加一个可变的 `PublicationReady` 来代替现有发布模型。当前代码已有独立的
`ValidateLinkSKUAbilityPublicationReadiness` 发布门禁；它对每个 resolution/ratio 组合调用显式
Provider size evidence 检查，并在组合为空时失败关闭，从而阻止无精确 size 证据的候选开放。该门禁
不新建第二个 readiness 系统；后续只新增经验证的精确组合。稳定身份仍由以下对象分别承担：

- capability registry：SKU 能力身份及 version/hash；
- implementation 与 size/evidence registry：精确 Provider 履约证明；
- `LinkModelPublication`：客户模型稳定指向哪个 SKU；
- Ability、分组和 exposure：当前是否对某范围可用；
- 真实 Provider、账单、三数据库和灰度验收：是否获准生产开放。

publication 已存在但没有合格候选时保留发布事实并返回“已发布但暂不可履约”，不能删除 publication、
降级普通 NEWAPI 语义或按请求内容猜测另一个 SKU。客户模型需要换 SKU 时只能执行显式改绑。

### 6.7 非 ModelArk 视频模型

`kling-v1`、`kling-v1-6`、`kling-v2-master` 和 `jimeng_vgfm_t2v_l20` 也位于通用视频 capability
registry，但使用各自合同 ID。它们共享能力基础设施不代表必须采用 ModelArk 字段；本方案不改变它们。

## 7. 当前主要差距

严格 DTO 解析、未知字段拒绝、SKU capability 校验、capability 驱动的稳定 `400`、publication 解析和
发布准备门禁均已存在。以下差距是对既有机制的补全、证据迁移和南向收敛，不是从零建设另一套校验、
发布或任务体系。

### 7.1 `seedance-byteplus` 是过宽的跨版本能力

当前 capability 同时声明 4k、9/3/3 多模态和较大的高级字段集合，并允许 `service_tier`、`draft`、
`seed`、`camera_fixed` 等字段。BytePlus 当前文档对 Seedance 2.0 的限制与该并集并不完全一致：

- Seedance 2.0 当前只支持在线模式，不应配置 `service_tier`；
- `draft` 当前只属于特定旧模型能力；
- Seedance 2.0 当前不支持 `seed`；
- Seedance 2.0 当前不支持 `camera_fixed`。

除上述字段外，还必须按精确 Provider model/version 复核 4k、图片/视频/音频 9/3/3 上限、每类媒体
role、`generate_audio`、resolution/ratio/duration 默认值、媒体组合与互斥规则，以及 callback、取消、
删除和 last-frame 等生命周期能力。仓库已登记的 9/3/3 是当前代码事实，不等于已取得生产发布证据。

必须先确定客户 SKU 绑定的精确 Provider model/version，再逐字段建立证据。无法确定时应停止新增
候选和 Ability，使既有 publication 保持不可履约并 fail closed；需要改变客户模型所代表的 SKU 时，
只能显式改绑。不能删除 publication，也不能根据 DTO/官方全局文档拼接能力。

### 7.2 机器可发现能力已落地

`GET /v1/models` 继续只回答当前 Key 的客户模型可见性和 endpoint type。模型字段、值域、默认值、
媒体上限和生命周期已经由两种机器入口提供：

- `ModelArkVideoCreateRequest.x-modelark-model-capabilities` 投影获准公开的静态模型子集；
- `GET /api/v3/contents/generations/models` 返回 15 个代码登记候选，并按当前 Key 追加已发布客户模型
  alias，分别标记 publication、`/v1/models` 可见性和当前可用性。

OpenAPI 投影由 `go run ./cmd/generate-modelark-capabilities` 从 runtime registry 生成；后端一致性测试对
规范化结构做深比较。客户模型 alias 通过 publication 的 `CustomerModel -> LinkSKU` 投影 capability，
响应不暴露 Link SKU、Provider 模型或 implementation。

### 7.3 默认值已经自包含

`VideoSKUCapability` 已包含 `DefaultDuration`、`DefaultResolution`、`DefaultRatio` 和组合矩阵；校验、
FunCloud adapter、计费探针和公开 capability 投影均消费同一冻结事实。没有默认值的模型要求客户显式
传参，不再回退 Provider 当前默认。

### 7.4 字段静默删除风险

模型不支持字段时，`ResolveVideoSKUCapability` middleware 调用统一的 `ValidateContractRequest`，再按
合同分派到 `ValidateModelArkRequest`，在发送前返回稳定 `400`。`seedance-2.0-fast + service_tier`
已经由该 capability 拒绝链覆盖。

当 ModelArk capability 允许 `service_tier`、但所选 channel/profile 不能等价发送时，当前 typed 路径也会
明确返回 `400`，包括显式 `"default"`，不会静默省略。只有 legacy `/v1/video/generations` metadata
路径保留历史行为：不支持的 `default` 可以归一化为缺失；该兼容语义不得反向进入 ModelArk 合同。

### 7.5 发布准备门禁可进一步精确化

现有 `ValidateLinkSKUAbilityPublicationReadiness` 已提供独立发布门禁，并已对每个 resolution/ratio
组合调用 `ResolveVideoProviderSizeEvidence` 消费显式 implementation/Provider model/resolution/ratio/size
证据；缺证据的组合失败关闭，不新建第二个 readiness 开关。剩余差距更窄：当 SKU 未显式登记
`ResolutionRatioCombinations` 时，门禁会先按 `Resolutions × Ratios` 笛卡尔兜底，再以空组合哨兵拦截。
这条兜底路径的可读性和审计性不如显式组合登记。后续可要求 media-arrays 等精确档位 SKU 显式登记
`ResolutionRatioCombinations`，逐步退役笛卡尔兜底与空数组哨兵；合同身份、Provider 证据、数据库
publication、Ability 开放和生产验收仍分别表达。

## 8. 目标权威模型

### 8.1 六层结构

```text
1. ModelArk v3 protocol schema
   字段名、JSON 类型、content 结构、任务路由
                         ↓
2. Canonical Seedance vocabulary
   resolution/ratio 等唯一值表达
                         ↓
3. Link Video SKU capability
   模型字段、值域、默认值、媒体组合、生命周期
                         ↓
4. LinkModelPublication + immutable implementation binding
   客户模型 → SKU/version → Provider implementation/model/profile
                         ↓
5. Southbound adapter
   仅执行确定性字段和值转换
                         ↓
6. Durable task snapshot
   冻结 publication、capability、implementation、连接、素材和计费事实
```

### 8.2 单一事实来源

- 代码显式 registry 是 Link SKU 身份和客户 capability 的权威。
- `LinkModelPublication` 是客户模型到 SKU/version 的持久化发布权威。
- implementation ID/version/hash 证明 Provider 履约方式，不得与客户 SKU 混为一体。
- OpenAPI 和静态 capability 文档由 registry 生成，不再手写第二份模型值域。
- Channel、Ability、模型映射、价格和 profile 只参与候选路由，不能创建或扩张合同。

### 8.3 版本与 publication 规则

| 变化 | 必须提升的身份 | 不应改变 |
| --- | --- | --- |
| 客户入口、请求/响应、错误或生命周期协议不兼容 | 客户接入合同 version | 不用 Provider profile 代替合同版本 |
| SKU 的客户可见字段、值域、默认值、媒体或生命周期变化 | capability version/hash | 不因同一 SKU capability 升级而提升 publication version |
| Provider 路径、profile、adapter、execution binding、size 或资源方式变化 | implementation version/hash | 不原地改写同一 implementation 版本 |
| 客户模型从当前 SKU 改绑到另一 SKU | `publication_version + 1` 并写不可变 audit | 不由普通保存、Channel 或请求形状隐式完成 |

Task、create attempt、Asset 和 Binding 继续冻结创建时的 publication version、capability version/hash
和 implementation version/hash。后续当前版本变化不能重解释历史执行。

### 8.4 当前 capability v2 与公开投影

`VideoSKUCapability` 已具备 request/required/unsupported fields、resolution、duration、ratio、显式
默认值、组合矩阵、媒体上限与 role、profile/channel 约束和 lifecycle；这些字段均进入 capability hash。
下面 JSON 是从同一 runtime registry 生成的客户公开投影视图，不是第二套手写权威：

```json
{

  "contract_id": "modelark.contents.generations.v3",
  "version": "...",
  "request_fields": [

    "end_user_subject",
    "content",
```

## 9. 请求处理与失败关闭

### 9.1 创建流程

```text
严格解析顶层字段和 content 子结构
  → 解析客户模型 publication
  → 校验 SKU capability/version/hash
  → 校验字段存在性、值域、默认值和媒体组合
  → 对 asset:// 校验 user/app、状态、类型、publication 和真人授权
  → 计算全部素材可执行 implementation/channel 交集
  → NEWAPI 按 Ability、分组、优先级、权重和重试选渠
  → 应用 model_mapping 并复检精确 implementation/profile/Provider model/account
  → 每次 Provider 尝试前复检 binding/source、凭据、授权和 TTL
  → Resolver 把 asset:// 改写为本次执行引用
  → adapter 按冻结 capability 与 implementation 确定性构造最终请求
  → 建立 durable create attempt、资金 hold 和 sending 状态
  → 发送 Provider 请求
  → 取得可信 Provider task ID 后原子创建 Task
```

任何不支持字段、非法值、未闭合组合、publication 缺失、资源交集为空或 implementation 冲突，都应
在发送请求和收费前失败。Resolver 是 `asset://` 的唯一转换权威；adapter 不自行查库、解密 URL 或
猜测 Provider asset ID。不得换到另一 SKU、降级成普通 NEWAPI 语义或静默删除字段。

### 9.2 原始失败示例

原调用向 `seedance-2.0-fast` 发送了：

```json
{
  "service_tier": "default",
  "return_last_frame": true,
  "execution_expires_after": 86400,
  "draft": false
}
```

这些字段即便看起来是“默认值”或 `false`，仍是显式请求。Fast capability 不支持时，正确行为是
中转站在北向返回稳定的 `400`，例如 `service_tier is not supported by this model`；客户端应省略
这些字段，而不是把它们固定写入所有 Seedance 请求模板。

合法的最小调用应类似：

```json
{
  "model": "seedance-2.0-fast",
  "content": [
    {
      "type": "text",
      "text": "主角惊恐时使用希区柯克变焦，环绕展示电梯内部，门打开后跟随走出电梯"
    }
  ],
  "duration": 4,
  "resolution": "720p",
  "ratio": "16:9",
  "generate_audio": true
}
```

## 10. 南向适配规则

adapter 输入必须是已经通过 capability 校验、冻结了 publication/implementation 的 typed request。
每个 adapter 只允许：

- 字段重命名，例如 `generate_audio` → `generateAudio`；
- 把统一值映射为 Provider 精确值；
- 对 media-arrays 使用冻结 implementation、Provider model、resolution、ratio 的精确 evidence registry
  解析 Provider `size`、倍率和 billing class；
- 把已解析的 `asset://` 转换为当前执行允许的 HTTPS/Provider 引用；
- 组装 Provider 要求的内容数组；
- 使用 capability 的显式默认值补全 Provider 必填字段。

adapter 不允许：

- 从 `Ratios[0]` 推断默认值；
- 硬编码 `720p` 作为跨模型默认；
- 接受 `2k` 后猜测为 `1080p` 或其他分辨率；
- 从兄弟模型、同分辨率名称或研究样例推断 Provider `size`；
- 删除不支持字段后继续请求；
- 根据 Channel/Profile 临时扩张 SKU 字段；
- 把 Provider 当前默认当成冻结的客户合同；
- 在未知创建结果时自动重发或换渠道。

## 11. 计费、Provider exposure 与 API Key 账单闭环

### 11.1 计费身份

- 客户模型名继续作为 Token 权限、价格、分组倍率、消费日志、API Key 账单和客户响应的模型键；
- Link SKU 只用于 capability、实现等价、素材资格和内部审计；
- Provider 模型、profile、渠道成本和权重不能动态改变客户售价；
- 当前 Seedance implementation 使用 `newapi_quota`，不得另建 Provider 专用客户余额或账本。

飞彩的 `per-second` / `per-request` 是 SKU 的受控计费形状，不直接等于客户价格。若通过
`tiered_expr` 计费，表达式和请求探针必须在预扣时冻结；同一表达式是价格事实，不在 adapter 或倍率表
外再增加隐式规则。duration、resolution、是否有视频输入和 Provider size multiplier 等所有乘数必须
来自已经校验、设有上界且冻结的请求/capability/evidence 事实。

### 11.2 create attempt、预扣和结算

- Provider POST 前必须建立 durable create attempt；资金 hold、必要授权 reservation 与 `sending`
  在同一事务提交后才允许发送字节；
- 没有可信 Provider task ID 时不创建 Task；Task 创建、hold 转移和 attempt 完成原子提交；
- unknown 不自动退款、重发或换渠道；到期释放客户 hold 时单独记录 Provider exposure；
- 成功、失败、取消、过期、差额和补偿保持幂等，quota 转换使用统一 checked 饱和函数；
- 可信终态 usage 才能参与精确结算；usage 未验证或缺失时按冻结合同保持安全预扣/待对账语义，不能
  用客户 quota 冒充 Provider 成本；
- Provider size registry 的 multiplier/billing class 只有在精确 implementation、Provider model、
  resolution、ratio 和 evidence version 全部命中时才能进入预扣与结算。

### 11.3 API Key 用量账单验收

API Key 账单只聚合已经写入消费和退款日志的结算事实，不按当前价格重新计算历史任务：

- 一次视频创建只计一个逻辑请求；带 `task_id` 的终态结算、差额或退款日志影响 Token 和费用，但不
  重复增加请求数、RPM、平均耗时或流式请求数；
- `gross_quota` 与 `refund_quota` 分别累计，`net_quota = max(gross_quota - refund_quota, 0)`；
- 跨期退款按退款日志发生时间进入账单，不回写原消费周期；
- 客户退款与 Provider exposure 分账，exposure 不伪装成客户消费或退款；
- API Key 账单查询保持只读，不能反向修改 Task、余额、日志或计费状态。

## 12. 机器可发现合同

### 12.1 保持 `/v1/models` 不变

`GET /v1/models` 继续只负责当前 Key 的模型可见性，不加入 Provider、价格、implementation 或庞大的
能力对象，避免改变 NEWAPI 原生模型协议和缓存语义。

全部已登记 Seedance capability 通过 `GET /api/v3/contents/generations/models` 提供。响应把
`published`、`visible_in_v1_models` 和当前 Key 的 `available` 与参数 capability 分开，未完成发布门禁的
模型保持 `available=false`，不得为了让 `/v1/models` 看起来完整而启用无合格候选的 Ability。

### 12.2 OpenAPI capability 投影

OpenAPI vendor extension 已从 runtime registry 生成模型级投影，包含：

- `contract_id`、capability version/hash；
- request/required/unsupported fields；
- resolutions、ratios 和显式 defaults；
- duration 范围、离散值和自动时长规则；
- content type、role、数量和组合约束；
- lifecycle；
- 响应和错误合同版本。

生成器和后端一致性测试已经对投影做规范化深比较。任一获准公开 SKU 的 runtime 值域变化而 OpenAPI
未同步，或 OpenAPI 宣称 runtime 不支持的值，都会使测试失败。飞彩 SKU 在 ratio、精确 Provider size
或其它发布证据未闭合时不得进入静态公开投影；代码注册本身不构成公开资格。

## 13. 与官方标准的关系

### 13.1 已对齐

- 创建路径与 ModelArk v3 一致。
- 核心字段名、JSON 类型、content 媒体判别和异步 task ID 语义高度一致。
- 参考图、参考视频、参考音频使用 `image_url`、`video_url`、`audio_url` 与对应 role。
- `resolution`、`ratio`、`duration`、`generate_audio` 等主干字段沿用官方语义。

### 13.2 平台有意扩展或收紧

- 客户模型名通过 publication 绑定 Link SKU，不是官方 endpoint/model ID 直传。
- `end_user_subject` 是 Link 匿名最终用户作用域扩展，不等于官方 `safety_identifier`。
- 客户使用 `asset://ast_*`，Resolver 再产生执行引用，不暴露 Provider asset ID。
- 每个 Link SKU 可以发布官方合同的严格子集，包括更小的媒体数量和更少的高级字段。

### 13.3 尚未完全兼容

- `draft_task` content 尚未进入本地 content 白名单。
- `frames` 虽有 DTO 字段，但当前公开 SKU 均拒绝。
- FunCloud 当前默认 ratio 与官方 Seedance 2.0 默认语义需要按精确模型复核。
- `seedance-byteplus` 对 `service_tier`、`draft`、`seed`、`camera_fixed` 的声明需按精确模型修正。
- 平台客户模型名、资源身份、授权和任务生命周期决定其不是任意 BytePlus SDK 请求的无修改直通。

因此当前和目标对外表述应为 **ModelArk v3-compatible northbound contract with per-model
capability subsets**，而不是“100% BytePlus SDK drop-in compatible”。

## 14. 分阶段实施

P5 的 Provider evidence 是贯穿 P1–P4 的横向发布门禁，不表示所有证据工作只能在最后开始。字段、hash、
投影和 adapter 代码可以按阶段实现，但任何 SKU 的默认值、组合或候选开放都必须等待对应的 P5 精确
证据；未取证模型继续失败关闭。

### P0：冻结词汇表和新增别名

- 固定规范 resolution/ratio 词汇表。
- 停止新增 `2k`、像素尺寸、大小写别名或 Provider 私有字段。
- 冻结当前公开 publication、调用量和外部客户端依赖基线。

### P1：capability v2 与精确模型清理（结构已完成）

- `DefaultResolution`、`DefaultRatio`、组合矩阵、规范词汇和 hash 已进入现有 `VideoSKUCapability`；
  request/media/lifecycle 没有建立第二份权威。
- FunCloud 默认值已由 capability、校验、adapter、计费探针和公开投影共同消费。
- 复核 `seedance-byteplus` 的精确 Provider model/version、4k、9/3/3 媒体上限与 role、默认值、组合和
  生命周期；无法证明时停止新增候选和 Ability，使既有 publication 保持不可履约；需要换 SKU 时走
  显式改绑。
- `ValidateLinkSKUAbilityPublicationReadiness` 已消费独立 Provider size evidence registry；后续只新增
  经验证的精确组合，不新建平行 readiness 开关。

### P2：OpenAPI 投影和 CI（已完成）

- 已从 registry 生成 `x-modelark-model-capabilities`。
- 已增加 runtime 与 OpenAPI 获准公开模型的精确一致性测试和生成器。
- 保持 `/v1/models` 响应结构和 NEWAPI 原生 OpenAI Videos schema 不变。

### P3：adapter 只消费 capability（核心已完成）

- FunCloud 已移除 `Ratios[0]` 和 `720p` 的隐式默认推断，只消费 capability 默认值。
- 保持飞彩 size registry 以 implementation/version + Provider model + resolution + ratio 为精确键；
  补证据只能新增经验证组合，不能从兄弟模型推断。
- ModelArk `service_tier` 已与 legacy metadata 兼容路径分离：typed 合同不能等价发送时明确拒绝。
- 后续工作只剩按 P5 精确 Provider evidence 复核各 adapter 的已声明字段和值转换。
- 保持现有 capability 阶段的不支持字段 `400`，补齐所有 ModelArk SKU 的确定性回归覆盖，不把已实现
  拒绝链重复下沉到 adapter。
- 未取证 SKU 不得用 Provider 当前默认填补缺口，应保持不可履约。

### P4：合同与客户端迁移

- 客户可观察能力变化提升 capability version/hash；Provider 执行语义变化提升 implementation
  version/hash，不为同一 SKU 的 capability 变化创建 publication version。
- 只有客户模型显式改绑另一 SKU 时才 `publication_version + 1` 并写不可变 audit。
- 发布模型级迁移表和截止日期；客户端改为 capability 驱动的稀疏序列化。
- 对现有固定模板重点移除无条件发送的 `service_tier`、`draft`、`return_last_frame`、
  `execution_expires_after` 等字段。

### P5：Provider 和生产门禁

- 用精确账号与模型逐项黑盒验证字段、值域、默认值、媒体组合、回调和生命周期。
- 验证结果写入显式、不可变的 implementation/Provider model/resolution/ratio/size evidence；只有证据
  完整后，才能填入 P1 新增的 SKU 默认值/组合并允许相应候选开放。
- 对每个飞彩可发布组合验证实际输出、Provider size、billing class、倍率和账单，并冻结 evidence version。
- 验证 durable create attempt、未知创建结果、轮询、归档、退款和 Provider exposure 分账。
- 验证 asset scope、授权、TTL 和撤回后的失败关闭。
- 未完成真实 Provider、真实账单、外部数据库和灰度验证的模型不得标为生产已发布。

## 15. 验收标准

- 所有已发布 Seedance 模型使用同一 ModelArk v3 字段结构和规范值词汇表。
- 现有 capability 拒绝链持续保证每个模型只接受自身声明的字段和值；不支持字段在 Provider 发送与
  收费前返回稳定 `400`，且没有 adapter 平行拒绝规则。
- `2k`、`4K`、像素尺寸、方向别名等均不作为北向近义词接受。
- 显式 `false`、`0`、`-1`、`default` 不被南向静默删除或改义。
- 默认 duration/resolution/ratio 全部来自冻结 capability，不来自 slice 顺序、硬编码或 Provider 当前默认。
- 飞彩 Provider `size` 只来自精确 implementation/Provider model/resolution/ratio evidence；Standard
  1080p 当前 `1280x720` 映射在实际输出和账单复核前不得开放。
- OpenAPI capability 投影与 runtime registry 对所有公开模型精确一致。
- `/v1/models`、NEWAPI 原生 OpenAI Videos、Kling 和即梦合同不变。
- 飞彩画幅或尺寸组合证据不完整的模型继续未发布。
- `seedance-2.0-fast + service_tier` 在北向稳定失败；省略该字段的合法请求完成 Provider 创建。
- capability 允许 `service_tier` 但候选不能等价发送时，候选被排除或发送前失败关闭；`default` 不再因
  channel/profile 策略被静默删除，除非该等价规则已进入带版本 capability。
- `asset://` 在选渠前约束候选交集、每次 Provider 尝试前复检并只由 Resolver 改写；请求级 URL/Data
  URL 不自动获得 Asset 与真人授权语义。
- Task 冻结 publication、capability、implementation、连接、素材和计费事实，后续配置变化不重解释历史任务。
- Provider 创建结果为 unknown 时不自动重发、换渠道或退款。
- capability 变化只提升 capability version/hash；publication version 只在显式改绑另一 SKU 时提升。
- 一次视频创建只计一个账单请求；异步调整只影响 Token/费用，净费用不为负，历史费用不按当前价格重算。
- 客户退款与 Provider exposure 分账，API Key 账单不把 exposure 投影为客户消费或退款。

## 16. 尚未闭合的事项

1. `seedance-byteplus` 的精确官方模型/版本，以及 4k、图片/视频/音频 9/3/3 上限、媒体 role、
   `generate_audio`、resolution/ratio/duration 默认值、组合互斥和生命周期证据。
2. 飞彩十个固定分辨率候选的完整 ratio、精确 Provider size、实际输出和账单黑盒结果；尤其是
   Standard 1080p 当前 `1280x720` 映射。
3. FunCloud Standard/Fast 当前冻结 720p/16:9/5 秒默认；仍需用精确 Provider 合同和生产黑盒持续复核，
   变化时提升 capability version/hash，不能由 adapter 临时改变。
4. 是否发布 `frames`、`draft_task` content、callback 等官方子集能力。
5. OpenAPI vendor extension、生成器和 CI 深比较已经实施；后续新增公开模型必须同步更新公开投影。
6. 全模型真实账单、回调、资源授权、删除/取消和外部数据库灰度结果。

## 17. 收敛与退出条件

本文是 `80-dev` 临时实施载体，不作为长期架构权威。满足以下条件后才可退出活动状态：

1. 已验证的合同边界、权威关系和不变量已回写 `20-architecture/`；
2. 稳定的 capability 投影、adapter、测试和发布操作规则已进入 `30-engineering/`；
3. P4/P5 等未完成迁移、Provider 实测和生产门禁已进入 `50-planning/`，且有明确负责人和验收条件；
4. 本文不再承载唯一的当前事实或未完成事项，并通过 `task docs:check`、`task ai:check`；
5. 补齐 `status: historical`、`archived-at`、`source-path`、`superseded-by` 后，按归档闸门移动到
   `99-archive/`。归档后的文件永久只读。

P0–P3 完成不是单独的归档充分条件；若 P4/P5 事项尚未迁入当前权威载体，本文仍保持 `in-progress`。
