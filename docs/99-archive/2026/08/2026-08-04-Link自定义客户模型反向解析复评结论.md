# Link 自定义客户模型反向解析复评结论

## 1. 评审目的与范围

本文综合以下三类证据，再次评审 Link 自定义客户模型方案：

1. [Link 服务合同概念与协作关系](2026-08-04-Link服务合同概念与协作关系.md)；
2. [Link 接入方案与自定义客户模型映射实施方案](2026-08-04-Link接入方案与自定义客户模型映射实施方案.md)；
3. 上一轮专家提出的“复用 `model_mapping`，再从 Provider 模型反向解析 Link SKU”分析，以及
   2026-08-04 查询到的 NEWAPI 官方文档、官方仓库和正式版本记录。

本轮重点是**方案设计是否成立、是否优于当前方案、是否符合 NEWAPI 图片/视频中转的架构方向**。
代码只用于确认设计边界，不以文件改造数量或具体实现细节作为主结论。

本文最初是编码前复评结论。2026-08-05 已按本文建议实施稳定 publication、保存期推导和发送前复检；
当前技术事实以 [Link 服务合同注册与履约架构](../../../20-architecture/Link服务合同注册与履约架构.md) 为准。
真实 Provider、生产账单和灰度验收尚未完成，因此本文继续保留为开发期决策证据，不作为上线完成
声明。

## 2. 结论先行

### 2.1 总体判断

管理侧已经确认：管理员当前可以在渠道配置中自定义客户模型名，Link 不能破坏该能力。因此，
“任意客户模型名”不再是可选需求，而是本方案必须满足的兼容性约束。原方案应拆成三个决定：

| 决定 | 结论 | 原因 |
| --- | --- | --- |
| 保留管理员在渠道 `models` 中自定义客户模型名 | **必须保留** | 这是 NEWAPI 既有管理和分发语义，Link 不能要求客户模型名等于内部 SKU |
| 管理端将 Provider、视频/素材协议、路径、Adapter 收敛成一次“Link 接入方案”选择 | **通过，优于当前自由拼装** | 降低无效组合和管理员认知负担，且不改变 NEWAPI 选渠职责 |
| 允许任意客户模型名，并仅靠当前可达渠道的 Provider 模型反向解析 Link SKU | **不通过，不能作为通用架构** | 合同身份依赖渠道可用性，可能静默改义，并把合同解析耦合到 NEWAPI 动态分发状态 |

因此，本轮修正上一版复评中的两个过强结论：

- “B2 不能直接塞进现有 `model_mapping` 链”是正确的；
- 但“反向解析是唯一正确方案”不成立；
- “不增加第二个管理员手工配置项”也不等于“不能存在一份独立于当前候选、持久且可审计的合同发布
  事实”。

### 2.2 推荐决策

任意客户模型名已经确认为硬约束，因此本轮推荐采用**稳定的客户模型发布事实**，不再把“公开模型直接
使用 Link SKU”作为最终方案，也不把纯候选反向解析作为通用合同来源。这里先确定的是业务语义，
**不是提前决定必须新建 `LinkModelPublication` 表**。物理承载方式仍需按最小入侵原则完成专项比较。
推荐设计边界是：

1. **NEWAPI 原有 `models`、`model_mapping`、Ability、Token 权限、价格和 Distributor 语义保持不变。**
   客户模型名继续由管理员自定义，并作为 NEWAPI 北向访问和分发键。
2. **系统保留一份稳定、可审计的 Link 客户模型发布事实。** 它由同一次渠道配置操作自动生成或校验，
   不要求管理员维护第二张手工映射表；其载体可以是 Link 独立对象、受约束的既有持久元数据，或经
   证明能跨 Ability 生命周期存在的扩展，不能仅是随当前候选消失的缓存。
3. **反向解析保留为保存期推导和执行期复检机制。**
   它可以证明某个实现正在执行哪个 SKU，但不应单独承担长期客户合同身份。
4. **Link 接入方案负责收敛南向结构。** Provider、视频/素材合同、路径、Adapter 和 execution binding
   随 implementation 固定，NEWAPI 仍负责最终选渠。

推荐的稳定链路是：

```text
(客户合同命名空间, 路由族, 客户模型名)
  -> 已发布的 LinkContractSKU
  -> 允许履约的 Link implementation/version 集合
  -> 渠道 model_mapping 与 implementation execution binding
  -> Provider 请求
```

而不是：

```text
客户模型名
  -> 当前恰好可达的渠道集合
  -> 当前映射到的 Provider 模型集合
  -> 临时推导 Link SKU
  -> 把临时推导结果当作客户合同身份
```

### 2.3 符合 NEWAPI 规则的职责边界

最终设计应保持以下分工：

| 层级 | 权威职责 |
| --- | --- |
| NEWAPI `models` | 管理员定义的客户模型名，参与模型发现、权限、价格、Ability 和分发 |
| NEWAPI `model_mapping` | 选中渠道后，将客户模型翻译为 Provider 实际模型 |
| NEWAPI Distributor | 按分组、路径、优先级、权重、Affinity、自动分组和重试选择渠道 |
| Link 模型发布事实 | 说明某个客户模型在某个路由族中代表哪个稳定 Link SKU；物理存储方式尚待决策 |
| Link implementation execution binding | 证明选中渠道的 Provider 模型、路径和协议如何履行该 SKU |
| Task/attempt/binding 快照 | 冻结本次执行使用的客户模型、SKU、实现、渠道和上游模型 |

因此，Link 增加的是一层更严格的合同治理，不修改普通 NEWAPI 模型的含义，也不接管 NEWAPI 的渠道
选择算法。

## 3. NEWAPI 官方设计事实

### 3.1 NEWAPI 的核心是“模型参与分发，渠道负责执行”

NEWAPI 官方将渠道定义为连接 AI 服务商的核心配置单元。渠道配置包含支持的模型、优先级、权重、
`model_mapping`、参数覆盖和自动禁用；官方说明中，`model_mapping` 的语义是“将用户请求的模型名
映射为实际模型名”。

官方项目介绍同时把智能路由定义为多渠道负载均衡、自动故障转移和加权随机分发。结合官方当前实现，
实际边界是：

```text
客户模型名 + 分组 + 请求路径
  -> Ability/渠道候选
  -> 优先级、权重、Affinity、自动分组与重试选渠
  -> 选中渠道的 model_mapping
  -> 上游模型与 Provider Adapter
```

这说明 NEWAPI 的公共模型名首先是**北向访问、权限、价格和分发键**；`model_mapping` 是选中渠道后的
**南向执行翻译**。官方没有把 Provider 模型名称设计成独立的公共合同注册中心。

### 3.2 NEWAPI 已显式区分原始模型和上游模型

官方渠道文档的参数覆盖变量同时提供：

- `original_model`：重定向前的客户模型；
- `model` / `upstream_model`：重定向后的上游模型。

官方当前模型映射实现也会从原始模型沿映射链走到链尾，再把链尾作为上游模型。由此可以确认：

- 客户模型和 Provider 模型本来就是两个身份；
- Link 增加 `LinkContractSKU` 作为第三个身份是合理的；
- 但第三个身份属于 Link 自己增加的合同治理层，不是 NEWAPI 现有 `model_mapping` 自动提供的语义。

### 3.3 图片中转仍是同步 Relay，但协议分支独立

NEWAPI 官方当前图片入口包括 `/v1/images/generations` 和 `/v1/images/edits`，均先经过 Distributor，
再进入图片 RelayFormat 和具体 Provider Adaptor。图片编辑还存在 JSON 与 multipart 等不同载荷形式。
官方 v1.0.0-rc.11 继续增强了 OpenAI Images API 的流式图片和图片编辑兼容，v1.0.0-rc.23 又补充了
New API 渠道的 multipart 图片编辑中转。

设计含义是：

- 图片模型仍使用客户模型名参与 NEWAPI 选渠；
- Provider 差异由渠道 Adaptor 和请求转换吸收；
- 路径、载荷形式和具体图片动作是执行语义的一部分，不能只看一个 Provider 模型字符串；
- Link 的图片 SKU 可以增加更严格的公开能力合同，但不应把所有图片中转重构成 Link 合同解析。

### 3.4 视频中转是异步任务系统，不能按同步图片模型简化

NEWAPI 官方当前同时支持多种视频入口和协议族，例如：

- `/v1/video/generations`；
- OpenAI 兼容的 `/v1/videos` 与 remix；
- `/kling/v1/...`；
- 即梦官方格式入口；
- Sora、Kling、即梦、豆包、Gemini、Vidu 等独立 Task Adaptor。

视频提交仍使用客户模型参与选渠；选中渠道后进入对应 Task Adaptor 生命周期，再完成请求验证、
渠道模型映射、时长/分辨率等计费估算和任务创建。任务查询则以已持久化任务为权威，不重新随机选渠。官方已经
合并的 #5133 也明确保持了“按 task ID 查询时不重新选渠”，只从任务快照恢复原始模型用于权限校验。

官方 v1.0.0-rc.16 对 Seedance 2.0 的素材 API、分辨率计费、视频输入计费和 4K 计费继续扩展，进一步
表明视频产品身份不仅由 `model` 字符串决定，还包括：

- 路由族与 action；
- 文生视频、图生视频、视频输入、remix 等请求形态；
- 时长、分辨率、素材角色和组合；
- 异步任务的提交、查询、结果代理和结算生命周期。

### 3.5 路由和分组正在变得更动态

NEWAPI 最新正式版本 v1.0.0-rc.23 已增加自动分组路由，并修复跨分组重试后的最终分组计费；
Advanced Custom 渠道也会按请求路径和客户模型过滤路由。

因此，任何“在正式 Distributor 之前读取候选集合并据此确定合同”的 Link 方案都必须回答：

- 是否复用了与 Distributor 完全相同的自动分组、Affinity、路径过滤、优先级和重试候选源；
- 重试切换分组时，客户合同身份能否保持不变；
- Distributor 新增路由规则后，Link 的前置枚举是否会自动同步。

原实施方案的 §6.3 并没有自己执行优先级、权重选择后再让 NEWAPI 选择一次，因此不能笼统称为
“影子分发”。只有实现复制了 Distributor 的候选生成或选择逻辑，才会形成一套影子分发并与上游
长期分叉；如果直接复用同一权威候选源，真实风险应表述为**合同解析对请求期候选集合的耦合**。

## 4. 对上一轮专家分析的采纳部分

上一轮分析有以下重要贡献，本轮继续保留：

1. **三模型身份必须拆开。** `OriginModelName`、`LinkContractSKU`、
   `UpstreamModelName` 不能由一个字符串兼任。
2. **现有 `model_mapping` 的链尾会直接发送给 Provider。** 因此不能简单配置
   `客户模型 -> Link SKU`，再期待现有映射逻辑自动完成 SKU 到 Provider 的第二次翻译。
3. **`RequiredModelMappings` 只是实现配置约束，不是第二段运行时翻译器。**
4. **不允许从候选中任取一条就认定 SKU。** 若使用反向推导，至少必须检查所有相关候选是否一致。
5. **保存期、发布期和发送前都需要闭环校验。** 仅靠 UI 校验或一次保存校验不足以维持合同不变量。
6. **图片和视频可以共用“合同身份”概念，但不能误写成同一中间件或同一执行协议。**
7. **Task、attempt、AssetBinding、exposure 和计费审计必须冻结明确的合同与执行身份。**

这些结论证明反向解析**技术上可实现，也适合做执行验证**；但它们没有证明反向解析应该成为唯一的
客户合同身份来源。

### 4.1 必须显式化的架构前提：SKU 是能力合同还是执行身份

对反向解析的裁决取决于一个必须先说明的前提：Link SKU 到底表示稳定的客户能力合同，还是只表示
选中渠道后的单次执行身份。两种模型都可以在抽象上成立，但不能混用：

| 维度 | SKU 是稳定能力合同 | SKU 仅是运行时执行身份 |
| --- | --- | --- |
| 客户模型含义 | 发布后稳定指向一个 SKU | 可随当前渠道和 `model_mapping` 改变 |
| 无可用渠道 | 仍知道已发布能力，只是暂不可履约 | 无法仅凭当前候选知道原能力 |
| 改绑 SKU | 显式合同变更，需要版本与审计 | 等同普通渠道配置变更 |
| 请求前能力校验 | 可依据稳定 SKU 完成 | 通常要延后到选中渠道后 |
| 跨渠道等价 | 先由 SKU 约束，再允许选渠 | 只能依赖当前候选逐次证明 |
| 所需状态 | 需要独立于在线候选的发布事实 | 可以只冻结 Task/attempt 执行快照 |

NEWAPI 的客户模型、Token 权限、价格和 Ability 足以定义访问与分发，却不完整表达 Link SKU 已经承担的
字段值域、分辨率、时长、素材角色、`asset://` 支持、任务生命周期及计费能力维度。因此，不能仅凭
“NEWAPI 模型是北向分发键”推出“SKU 只需是运行时身份”。

本项目当前接受的 [ADR-0015](../../../20-architecture/decisions/0015-Link服务合同发布与实现身份绑定.md) 已明确：
Link 身份不能由 Ability、模型发现、渠道配置或运行时探测反向创建；一个 Link SKU 对应一份公开客户
合同和能力声明。[硬约束](../../../00-context/硬约束.md) 同样要求公开 Link 模型是稳定、可计费、可验证的
合同 SKU。基于这些现行权威，本轮采用“SKU 是稳定能力合同”的前提。

如果产品希望改成“SKU 仅作运行时执行身份”，这不是对存储实现的轻量调整，而是新的产品架构选择：
必须先修订或取代 ADR-0015 和相关硬约束，并重新说明字段、素材、任务、跨渠道等价和零候选语义由谁
负责。在该治理决策发生前，不把运行时身份方案作为默认路线。

## 5. 原反向解析方案仍不自洽的关键问题

### 5.1 “当前唯一”不等于“合同稳定”

原方案要求请求时遍历当前可达候选，并证明只得到一个 SKU。这只能证明**此刻候选集合内部一致**，
不能证明该客户模型没有随时间改义。

例如：

```text
T0: sd-standard -> 当前全部渠道 -> SKU-A
T1: SKU-A 渠道全部禁用或删除
T2: 新增一组渠道，sd-standard -> SKU-B
```

T0 和 T2 的候选集合各自都只有一个 SKU，原方案都会通过；但同一个客户模型已经从 SKU-A 静默变成
SKU-B。过程中从未出现“同时存在两个 SKU”的冲突，所以跨候选唯一性校验无法发现这次改义。

如果 Link SKU 代表客户已发布的字段、素材、任务和计费能力，这就是合同变更，必须显式发布、版本化
和审计，不能由当前在线渠道集合隐式决定。

### 5.2 零候选时无法区分“合同不存在”和“履约暂不可用”

当全部渠道禁用、熔断、分组暂不可用或缓存未命中时，纯反向解析得不到 SKU。仅凭这一解析结果无法
区分：

- 客户模型从未发布；
- 客户模型已发布，但当前没有可用渠道；
- 客户模型已发布，但当前渠道配置损坏；
- 客户没有访问权限。

权限层可以另行判断客户访问资格，但纯反向解析本身仍无法区分其余状态；若对外只返回“解析不到
SKU”，就会把不同问题压成同一结果。这会使参数校验、错误码、模型发现、Asset 预创建和运维告警
依赖渠道健康状态。合同知识本应在没有可用 Provider 时仍然存在；可用性只决定“现在能否履约”，
不应决定“客户买的是什么”。

### 5.3 Provider 模型不是普适的执行判别键

`(implementation version, provider_model) -> Link SKU` 对部分实现足够，但不能被声明为普适真理。
NEWAPI 官方的视频设计已经证明，真实执行身份还可能取决于：

- route family / endpoint；
- action；
- Provider profile 或协议转换器；
- 文本、图片、视频、音频素材组合；
- 时长、分辨率和任务类型。

本项目的部分实现也存在“路径或 profile 才是关键判别信息”的情况。此时只登记 Provider 模型会把
两个不同执行产品错误合并，或为了适配特例不断向模型目录添加隐式规则。

因此更准确的概念应是 **implementation execution binding**，其判别维度由实现显式声明；
`provider_model` 只是可能的一个维度。

### 5.4 选渠前合同解析耦合于 NEWAPI 候选集合

原方案为了在 capability 校验前得到 SKU，先读取客户模型对应的 Ability 候选派生事实，随后仍由
NEWAPI 正式选渠。原方案没有自己执行优先级、权重选择，不能直接定性为“影子分发”；真实耦合点是：
合同身份依赖请求期能够观察到哪些候选，以及该集合是否与 Distributor 实际使用的候选源和过滤时序
一致。

若 Link 读取的候选集合未复用 Distributor 的权威候选源，就会产生两种错误：

- Link 认为某渠道不可达，但 NEWAPI 后续可以选到；
- Link 用某渠道证明了 SKU，但 NEWAPI 后续永远不会选到该渠道。

随着自动分组、Affinity、路径过滤和跨分组重试继续演进，如果 Link 复制候选生成或选择逻辑，长期
一定会形成分叉；即使共享同一候选源，只要合同身份仍由当前集合决定，§5.1 的跨时间改义和 §5.2 的
零候选语义仍然存在。因而该机制适合用于发布校验和选渠后复检，不宜单独承担稳定合同身份。

### 5.5 同名 Link 与非 Link 候选没有完整定义

NEWAPI 原生允许同一客户模型名由多个渠道提供。如果 `sd-standard` 同时出现在 Link 渠道和普通渠道，
纯反向解析会遇到未定义状态：

- 普通渠道没有 Link SKU，是否忽略；
- 若忽略，NEWAPI 后续选中普通渠道时，前置 Link capability 校验是否仍有意义；
- 若不忽略，同一个 NEWAPI 模型是否因此强制全部 Link 化。

最终方案必须选择其一：

1. 同一合同命名空间和路由族内，Link 发布模型禁止与普通渠道混用；
2. 显式区分 Link 与普通模型命名空间；
3. 允许混用，但将它定义成另一种明确的降级合同，并单独设计计费、素材和审计语义。

原方案目前没有完成这个决定。

### 5.6 图片与视频同名模型必须按路由族隔离

NEWAPI 的图片和视频入口、载荷、Adaptor、任务生命周期完全不同。同一个客户模型字符串即使都叫
`creative-pro`，在 `/v1/images/generations` 和 `/v1/videos` 下也可能代表两个不同产品。

因此稳定绑定键至少应包含：

```text
(customer_contract_namespace, route_family, customer_model)
```

如果还允许按租户或分组发布不同合同，应把该维度写入命名空间定义；不能只使用
`(group, customer_model)`，也不能把所有媒体入口混成一个全局名称空间。

### 5.7 “不让管理员重复配置”与“没有持久合同事实”是两回事

原方案担心增加 `客户模型 -> Link SKU` 会形成第二张需要手工维护的映射表，这个担心合理；但可以通过
一次配置、系统原子派生解决：

```text
管理员：选择 Link 接入方案 + 填写客户模型/Provider 模型映射
系统：解析执行绑定 -> 生成或校验客户模型发布绑定 -> 发布 Ability
```

管理员仍只操作一次。系统持久化的是**发布后的客户合同事实**，不是要求管理员再次输入同一关系。
删除或禁用最后一条渠道时，不应自动删除合同绑定；改绑到不同 SKU 时，应要求显式变更并留下审计。

## 6. 方案比较与决策边界

| 维度 | A. 公开模型直接使用 Link SKU | B. 纯候选反向解析 | C. 稳定客户模型发布事实 |
| --- | --- | --- | --- |
| 任意客户模型名 | 不支持 | 支持 | 支持 |
| 无可用渠道时仍知道合同 | 支持 | 不支持 | 支持 |
| 防止客户模型静默改义 | 强 | 弱 | 强 |
| 对 NEWAPI Distributor 的耦合 | 最低 | 取决于候选源；复制逻辑时高，共享权威候选源时中等 | 中等，可隔离 |
| 管理员操作复杂度 | 低 | 低 | 可保持低，由系统自动派生 |
| 图片/视频路由族隔离 | 直接明确 | 必须额外补齐 | 可在绑定键中明确 |
| 适配多维 execution binding | 支持 | 容易被 Provider 模型限制 | 支持 |
| 合同审计与版本化 | 清晰 | 依赖当前配置快照 | 清晰 |
| 是否满足已确认的管理约束 | 不满足 | 部分满足但合同不稳定 | **满足，语义上推荐** |
| 相对当前实现的收益/风险 | 仅可作为迁移基线 | 可作执行校验，不能单独维持现行合同不变量 | 满足需求，但物理载体需权衡侵入和维护成本 |

### 6.1 方案 A：公开 Link SKU，先改善 UI

该方案只作为现有实现和迁移基线：

- 公开模型名就是 Link SKU；
- NEWAPI 按该模型正常分发；
- Link 接入方案锁定 Provider、视频/素材合同、路径和 Adapter；
- 渠道 `model_mapping` 只负责 SKU 到上游模型的执行翻译；
- Task 和审计仍冻结客户模型、SKU、实现和上游模型。

由于任意客户模型名已经确认是必须保留的管理能力，本方案不能作为最终形态，但现有
`customer_model = Link SKU` 渠道仍应作为合法特例无损迁移。

### 6.2 方案 B：纯候选反向解析

只有同时满足以下条件时才可局部使用：

1. 产品接受“无候选时无法解析合同”；
2. 客户模型允许随当前渠道集合显式重绑定，并有审计规则；
3. execution binding 的判别维度完整，不假设只有 Provider 模型；
4. 候选枚举直接复用 Distributor 的权威候选源，不复制选渠逻辑；
5. 同一范围内禁止 Link 与非 Link 候选混用；
6. route family、自动分组、Affinity、重试和指定渠道语义已有明确规则；
7. Asset 预创建等先于实际选渠的流程不要求稳定合同身份。

这些限制使它更适合作为保存期推导、迁移审计和选渠后复检工具，而不是系统级客户合同架构。

### 6.3 方案 C：稳定客户模型发布事实

本轮在**语义层**推荐该方案：客户模型一旦作为 Link 产品发布，就必须有一份不随当前在线渠道集合
消失的权威事实。为便于讨论，暂用以下逻辑对象表示；这不是已经决定新建同名数据库表：

```text
LinkModelPublication（逻辑名）
  contract_namespace
  route_family
  customer_model
  link_contract_sku
  publication_version / audit metadata
```

本轮先确定其最小语义：

- 它是客户合同的权威发布事实，不是运行时缓存；
- 它不随渠道启停、熔断或临时无候选自动消失；
- 第一个渠道发布时可由 execution binding 自动生成；
- 后续渠道只能加入同一个 SKU 的履约集合；
- 改绑 SKU 是显式合同变更，必须版本化和审计；
- Distributor 仍使用客户模型名选渠；
- 选渠后对 implementation、execution binding 和已冻结 SKU 做一致性复检。

物理承载方式必须另行比较，不得把“需要发布事实”直接等同于“必须新建一套完整状态机和独立表”：

| 候选载体 | 优点 | 必须证明的问题 |
| --- | --- | --- |
| Link 自有独立持久化对象 | 语义独立，可隔离在 Link 新文件，零候选时仍存在 | 三库迁移、事务、审计和运维成本是否可接受 |
| 既有模型元数据扩展 | 可能减少新对象 | 是否污染 NEWAPI 原生模型语义，是否扩大上游合并冲突 |
| Ability 扩展或保留 tombstone | 接近现有发布流程 | 删除/禁用最后一条 Ability 后是否仍是唯一权威，缓存清理会否丢失合同 |
| 仅缓存或当前候选派生索引 | 实现最轻 | 不能满足重启、零候选和跨时间防改义，不可作为最终权威 |

“最小入侵”衡量的是未来接取上游的冲突面、热路径改动、迁移和长期维护总成本，而不是简单按“是否
新增表”判断。独立 Link 对象可能增加数据库复杂度，也可能比扩写 Ability、渠道缓存和 Distributor
更少触碰上游核心代码；必须用实际接线设计比较后再决定。

默认绑定键为：

```text
(contract_namespace, route_family, customer_model)
```

`group` 默认不决定产品身份：分组继续控制访问、价格倍率和渠道路由，但同一合同命名空间、同一路由族
中的同一客户模型必须代表同一个 SKU。若业务确实需要同名模型在不同客户范围表示不同产品，应通过
显式 `contract_namespace` 隔离，不能隐式依赖自动分组或重试最终落到哪个 group。

### 6.4 渠道配置与发布流程

管理员继续只使用 NEWAPI 已有模型配置，再额外选择一次 Link 接入方案：

```text
管理员：
  1. 选择 Link 接入方案
  2. 在 models 中填写任意客户模型名
  3. 在 model_mapping 中映射 Provider 实际模型

系统：
  4. 使用与 NEWAPI 一致的链式 model_mapping 解析上游模型
  5. 使用 implementation execution binding 推导 Link SKU
  6. 创建或校验稳定的客户模型发布事实
  7. 校验该 implementation 完整履行 SKU 的图片/视频、素材、任务和计费能力
  8. 发布原有 NEWAPI Ability
```

例如管理员只配置：

```text
models: sd-standard
model_mapping: sd-standard -> seedance-2.0-vip-720p-azhw
```

系统自动形成：

```text
(openai-video, sd-standard)
  -> seedance-2.0-standard-720p
```

这不是第二次要求管理员配置模型关系，而是把一次渠道配置转换为可持续、可审计的客户合同发布事实。

### 6.5 发布事实的最小生命周期语义

发布事实与渠道可用性分离。编码前只要求以下最小不变量，不预先建设超出需求的完整状态机：

- 禁用、熔断或临时失去全部渠道，不删除发布事实；“是否已发布”和“当前是否可履约”分开计算；
- 新渠道解析为相同 SKU 时，可以加入既有履约集合；
- 新渠道解析为不同 SKU 时，保存或 Ability 启用失败；
- 删除最后一条渠道不应自动释放客户模型名；
- 将客户模型改绑到不同 SKU 必须走显式合同变更，提升版本并记录审计；
- 已创建的视频 Task、attempt 和 AssetBinding 继续使用旧快照，不受后续改绑影响；
- 是否需要“暂停、退役、释放名称”等完整状态，应由真实运营需求决定；在规则未定义前默认不自动释放
  或复用已经发布的客户模型名。

### 6.6 请求执行流程

```text
1. 从请求取得 customer_model 和 route_family
2. 查询权威客户模型发布事实，冻结 LinkContractSKU 与发布版本
3. 按 SKU 校验字段、值域、素材和计费维度
4. NEWAPI 按原客户模型、分组、路径和现有规则选渠
5. 应用选中渠道的 model_mapping，取得 UpstreamModelName
6. 使用选中 implementation 的 execution binding 反向复检 SKU
7. 一致才允许发送 Provider；不一致则在发送前 fail closed
8. 冻结客户模型、SKU、上游模型、渠道、实现和计费快照
```

图片同步请求在第 8 步后返回结果；视频异步请求在第 8 步创建任务。视频查询、remix 和结果代理必须
沿用任务快照，不根据当前发布绑定或当前渠道重新解释历史任务。

这使合同校验不依赖请求期候选是否为空；NEWAPI 仍只进行一次正式选渠。它能否保持最小入侵，取决于
发布事实最终采用何种载体以及需要修改哪些上游热路径，不能在存储设计前预先下结论。

## 7. 对原方案各部分的最终裁决

| 原方案内容 | 裁决 | 修订要求 |
| --- | --- | --- |
| Link 服务合同、客户接入合同、SKU 能力、资源、任务与南向实现分层 | 保留 | 明确哪些是客户发布事实，哪些是执行事实 |
| 管理员可以自定义客户模型名 | 新增为硬约束 | 保持 NEWAPI `models`、权限、价格、Ability、日志和响应语义 |
| Link 接入方案一次选择并锁定结构字段 | 保留并优先实施 | 作为 Link 渠道的统一南向配置入口 |
| 三模型身份 | 保留 | `LinkContractSKU` 必须来自稳定发布事实或明确的受限解析模式 |
| `model_mapping` 继续表示客户模型到上游模型 | 保留 | 不把 Link SKU 插入其链尾 |
| Provider 模型目录反查 SKU | 降级为执行绑定的一种实现 | 键必须允许 route/action/profile 等实现维度 |
| 不新增第二个管理员手工映射区 | 保留 | 不等于禁止系统持久化发布绑定 |
| 不新增任何持久化客户模型合同事实 | 删除 | 现行合同前提下必须保留能跨 Ability 生命周期存在的发布事实，但不预断定必须新建独立表 |
| 请求前遍历全部候选来发现 SKU | 删除为默认路径 | 仅用于校验或受限模式，不作为合同权威 |
| 当前候选 SKU 集合唯一即可证明合同一致 | 删除 | 还必须防止跨时间静默改义 |
| Task/attempt/AssetBinding/exposure 冻结身份 | 保留 | 视频查询不得重新选渠，沿用已冻结任务事实 |
| 普通 NEWAPI 渠道不受 Link 语义影响 | 保留并加强 | 明确同名 Link/非 Link 模型的排他或命名空间规则 |

## 8. 编码前必须补齐的设计决定

已经确认且不再讨论的前提是：任意客户模型名必须保留，管理员不能被要求使用内部 Link SKU。
在实现开始前，还必须补齐以下架构决定：

1. 客户模型的 `contract_namespace` 是系统全局、租户还是显式客户合同；默认不以动态 group 作为产品身份；
2. 图片生成、图片编辑、通用视频、OpenAI Video、Kling、即梦等 route family 如何定义；
3. 同一客户模型是否允许在不同 route family 绑定不同 SKU；
4. 同一范围是否禁止 Link 与普通 NEWAPI 渠道混用；
5. “已发布”和“当前可履约”如何分离；暂停、退役和释放名称是否确有业务需要，避免预建过度状态机；
6. 客户模型改绑 SKU 的版本、灰度、价格、模型发现和审计规则；
7. 自动分组和跨分组重试如何保证同一个 LinkContractSKU；
8. execution binding 除 Provider 模型外还需要哪些 route/action/profile 判别维度；
9. Asset 创建先于任务选渠时，如何从发布绑定取得稳定 LinkContractSKU；
10. 发布事实采用 Link 独立对象、现有模型元数据还是 Ability/tombstone 扩展；比较上游文件改动、热路径
    接线、三数据库迁移、事务边界、缓存失效、审计能力和未来合并冲突后再选型；
11. 原 ADR-0015 对“SKU 是稳定能力合同”的决定继续有效；任意客户模型别名如何发布到 SKU 应补充新
    决策。只有选择“SKU 仅作运行时身份”时，才需要显式取代 ADR-0015 和相关硬约束；
12. 术语文档、实施方案和 ADR 如何避免同时保留两套互相冲突的权威说法。

以上均为架构通过条件；其中最小生命周期、改绑规则、发布事实载体和 ADR 权威链未确定前，不应进入
实现。载体选型必须遵守项目“最小入侵”最高约束，但不能以牺牲已确认的合同不变量换取表面上的少改文件。

## 9. 最低设计验收场景

最终方案至少要在设计层回答以下场景，不应等编码后再发现：

1. 客户模型名可以与 Link SKU 完全不同，并继续用于 NEWAPI 模型发现、Token 权限、价格、Ability、日志和响应；
2. 已发布客户模型的全部渠道暂时不可用时，仍能确定 SKU，并返回“暂不可用”而非“模型不存在”；
3. 删除 SKU-A 的最后一条渠道，再新增 SKU-B 渠道时，不会把同一客户模型静默改绑；
4. 自动分组或重试切换分组时，SKU、字段能力、素材能力和价格合同不改变；
5. 同一客户模型在图片和视频 route family 中可以按明确规则隔离；
6. Link 与非 Link 同名候选会被发布期拒绝，或按已定义的命名空间规则处理；
7. Provider 模型同名但 endpoint/action/profile 不同时，不会解析到错误 SKU；
8. 图片 JSON、multipart 编辑和流式响应不改变客户合同身份；
9. 视频提交冻结客户模型、SKU、上游模型、渠道、实现和计费事实；查询、remix 和结果代理不重新随机选渠；
10. Asset 预创建在没有可用渠道时仍能依据已发布合同校验素材；
11. 修改 `model_mapping`、Link 接入方案或 implementation version 时，合同变更和执行变更被分别审计；
12. 普通 NEWAPI 自定义模型、图片、视频、Affinity、自动分组和重试不因 Link 功能改变语义；
13. UI 只要求一次配置，但后台能够展示“客户发布合同”和“当前履约实现”两个不同事实。
14. 删除或清理最后一条 Ability、重启服务和重建缓存后，已发布客户模型的 SKU、版本和改绑审计仍
    不丢失；如果选用 Ability 扩展，必须证明保留事实与普通 Ability 生命周期不会互相污染。
15. 最终载体没有为普通 NEWAPI 模型引入 Link 专属状态，也没有把大量 Link 生命周期逻辑写入上游
    Distributor、Ability 或渠道热路径。

## 11. 当前推荐判断

本文是实施前复评的历史推导。物理载体比较和合同语义已由 ADR-0015 裁决并落地，当前事实以
[Link 服务合同注册与履约架构](../../../20-architecture/Link服务合同注册与履约架构.md)为准；官方证据与
备选方案已分别收敛到 `70-research/参考资料.md` 和 `70-research/备选方案.md`。原评审结论为：

- **管理员自定义客户模型名是必须保留的 NEWAPI 兼容性约束，不再讨论是否支持；**
- **Link 接入方案的产品化收敛明显优于当前实现，应继续；**
- **三模型身份和执行期反向校验是正确方向，应保留；**
- **纯“当前候选反向解析”不适合作为客户合同身份的唯一来源，原方案在合同稳定性、零候选语义、
  NEWAPI 动态分发耦合和图片/视频路由族隔离上仍不自洽；**
- **语义上推荐“稳定客户模型发布事实”：管理员继续只配置 `models`、`model_mapping` 和 Link 接入
  方案，系统自动生成或校验该事实；当前不预断定它必须由独立 `LinkModelPublication` 表承载；**
- **SKU 仅作运行时执行身份是另一套产品架构，不是本方案的轻量存储替代；如要选择，必须先修订或
  取代 ADR-0015，并重新定义字段、素材、任务、计费和零候选语义的权威来源；**
- **最小入侵与合同稳定性必须同时评估：独立 Link 对象和 Ability/既有元数据扩展都不是天然胜者，
  应以实际上游冲突面、热路径接线、迁移和生命周期总成本裁决；**
- **当前公开 SKU 方案只作为无损迁移特例，纯反向解析只用于保存期推导、选渠后复检和审计解释。**

反向解析最合适的定位是：

```text
保存时：从渠道执行配置推导并校验要发布的 SKU
发布时：保证所有履约渠道符合既有客户模型发布绑定
选渠后：复检实际 implementation execution binding 未偏离冻结 SKU
审计时：解释客户模型最终由哪个 Provider 模型和协议履约
```

它不应承担：

```text
在每次请求中，根据当前在线渠道临时决定客户模型到底是什么产品
```

据此，实施保留了一次配置、Ability 参与 NEWAPI 分发、execution binding 和发送前复检的主体结构，
并以持久 publication 关闭请求期候选耦合、跨时间改义和零候选语义问题。本文不再承担当前规范。
