# 共享上游账号调用方自管素材方案评审

## 1. 问题与目标

当前 Seedance Link 建立了平台 `Asset` / `AssetGroup` 资源层：客户只使用 `ast_*`、`astgrp_*`，平台在
视频发送前校验 `user_id + app_id`、状态、创建模型、`ChannelID`、素材协议和 Provider 作用域，再把
平台引用改写为 Provider `asset://<id>`。

真实使用中，Volcengine 同一账号、Project 和 Region 下的多个 Seedance 模型共用同一套私域素材和
素材组。现有实现仍把素材固定到创建时模型和 Channel，导致同一上游素材作用域内跨模型使用被平台
提前拒绝为 `409 asset_channel_mismatch`，Provider 没有收到请求。

本方案讨论另一种合同：中转站的一个客户用户就是一个自行管理最终用户和素材的应用；不同客户用户
对应不同应用。应用保存 Provider 素材 ID，中转站不提供素材列表、不维护统一素材所有权映射，也不在
视频发送前判断素材是否存在、就绪或兼容当前模型。Provider 是素材可用性的最终裁决者。

2026-08-17 已按 ADR-0017 完成代码、公开合同、当前事实文档和真实 Provider 验证。当前权威事实见
[Seedance 官方素材库与素材引用设计](../20-architecture/Seedance官方素材库与素材引用设计.md)与
[硬约束](../00-context/硬约束.md)；ADR-0017 已取代 ADR-0016。

## 2. 当前实际情况

### 2.1 已确认的业务前提

| 前提 | 当前结论 |
| --- | --- |
| 一个中转站用户代表什么 | 一个由调用方自行管理的应用，不代表应用内最终用户 |
| 最终用户素材隔离由谁负责 | 调用应用负责，中转站不建立最终用户身份域 |
| 上游账号形态 | 多个应用可以共享中转站配置的 Provider 账号和 Project |
| 应用是否可信 | 按“应用自律”处理；应用应只提交自己保存的素材 ID |
| 是否要求应用间技术强隔离 | 不要求；已知另一个应用的素材 ID 时，上游可能查询或使用成功 |
| 是否提供素材列表 | 不提供，不允许通过中转站分页、搜索或枚举整个 Provider 素材库 |
| 是否提供单项查询 | 提供可选的按模型和素材 ID 查询，不作为生成前置条件 |
| 素材增删改查由谁执行 | 应用携带客户模型和 Provider 资源 ID，中转站通过对应协议 adapter 无状态代理 |
| 错误 Provider 素材如何处理 | 只发送给客户模型选定的 Provider；该 Provider 拒绝后直接返回，禁止 fallback |
| 素材最终可用性由谁决定 | Provider 在单项查询或实际生成请求中决定 |
| 客户端公开路由身份 | 只有客户模型名；不返回 Provider、ChannelID、模型映射或上游原始模型名 |

上述合同的安全属性是“受信应用自管”，不是“多租户素材强隔离”。如果未来恢复“不同应用即使知道
对方素材 ID 也绝对不能使用”的要求，本方案立即失效，必须改用独立 Provider 账号/Project 或恢复
本地所有权映射。

### 2.2 已验证的代码事实

1. 素材 CRUD 直接按客户模型选择唯一 Seedance Channel 和 adapter，不读写本地 Asset/AssetGroup 表。
2. 客户素材与素材组列表路由已移除；GET/DELETE 查询参数和 PATCH/POST 请求体均执行 Token 模型授权。
3. 创建和单项查询返回 Provider opaque ID；公开响应和模型元数据不含 Provider、ChannelID、账号、
   Region/Project、协议或上游原始模型。
4. 视频创建链路不再调用素材 resolver；ModelArk V3 只检查 `asset://` 后存在非空值，Provider adapter
   不解释 opaque ID 的所属关系。
5. 错误 ID 只进入客户模型选择的 Provider；网关返回脱敏错误，不探测或 fallback。
6. 无素材协议或不支持具体操作的模型明确返回 `unsupported_asset_operation`。
7. 一个客户模型一个 Channel 保持不变；Channel 只表达 Provider 连接、凭据、模型映射和代码协议，
   不配置共享素材组、跨模型绑定或素材作用域。

### 2.3 外部证据与未确认项

火山方舟官方文档已经公开私域素材的创建、素材列表和素材组列表操作：

- [创建素材资产（CreateAsset）](https://www.volcengine.com/docs/82379/2318271?lang=zh)
- [查询素材资产列表（ListAssets）](https://www.volcengine.com/docs/82379/2318273?lang=zh)
- [查询素材资产组合列表（ListAssetGroups）](https://www.volcengine.com/docs/82379/2318272?lang=zh)

这些文档证明 Provider 存在账号级私域素材控制面，但没有证明中转站应用身份会被 Volcengine 识别或
隔离。中转站多个应用共享同一 Provider 凭据时，Volcengine 只能按其收到的账号、Project 等上游
身份授权，不知道中转站的 `user_id + app_id`。

2026-08-17 已使用当前测试环境真实创建 AIGC 人像普通素材，并确认同一素材组与素材可分别通过
Volcengine 2.0、Fast、Mini、2.5 四个客户模型单项查询，均返回 HTTP 200。随后使用 Mini 与同一
`asset://<opaque-id>` 创建 480p、4 秒视频，任务成功并通过内容代理取得 `video/mp4` 的 Range 响应。
这些结果是本次 Provider 行为证据，不构成平台对未来跨模型兼容性的永久保证。

## 3. 优化方案

### 3.1 目标责任边界

```text
调用应用
  -> 保存 Provider 素材组 ID / 素材 ID
  -> 可选：按 model + asset_id 查询单项状态
  -> 提交 model + asset://<ProviderAssetID> 生成视频

中转站
  -> 鉴权并检查当前 API Key 是否允许使用该客户模型
  -> 由客户模型确定唯一 Channel 和代码协议 adapter
  -> 素材 CRUD 只调用该 Channel 对应的 Provider，不尝试其它 Provider
  -> 不查 Asset/AssetGroup 表，不做所有权、创建模型或 ChannelID 校验
  -> 脱敏转发 Provider 成功或错误

Provider
  -> 判断素材是否存在、账号/Project 是否可访问、是否就绪
  -> 判断当前模型是否接受该素材并执行最终内容审核
```

中转站仍负责模型访问授权、协议选择、请求结构边界、敏感信息保护、Task、计费和审计；“不验证素材”
不能扩大为“不验证模型权限”或“透传任意 Provider 私有请求字段”。

客户模型名是唯一公开路由身份。Channel、Provider、`model_mapping` 和上游原始模型名只在中转站内部
使用；素材成功响应、错误响应和异步 Task 响应均不得直接返回上游原始模型名。

### 3.2 北向素材控制面

所有已由代码 adapter 和 Provider 合同确认支持素材库的模型只开放单资源操作，不提供集合查询：

| 操作 | 建议北向合同 | 说明 |
| --- | --- | --- |
| 创建素材组 | `POST /v1/asset-groups`，请求体必须包含 `model` | 返回 Provider 素材组 ID，应用持久化 |
| 查询素材组 | `GET /v1/asset-groups/{group_id}?model=...` | 只查询调用方明确给出的单个 ID |
| 删除素材组 | `DELETE /v1/asset-groups/{group_id}?model=...` | 单资源直通，Provider 最终裁决 |
| 创建素材 | `POST /v1/assets`，请求体必须包含 `model` | 接受 Provider 素材组 ID，返回 Provider 素材 ID 与 `asset://` 引用 |
| 查询素材 | `GET /v1/assets/{asset_id}?model=...` | 可选预检；不证明所有权或生成兼容性 |
| 更新素材 | `PATCH /v1/assets/{asset_id}`，请求体包含 `model` | 单资源直通 |
| 删除素材 | `DELETE /v1/assets/{asset_id}?model=...` | 单资源直通 |
| 素材列表 | 不注册 `GET /v1/assets` | 不代理 Provider `ListAssets` |
| 素材组列表 | 不注册 `GET /v1/asset-groups` | 不代理 Provider `ListAssetGroups` |

这里的 `{asset_id}` / `{group_id}` 是调用应用自行保存的 Provider 资源 ID，不再是平台 `ast_*` /
`astgrp_*`。所有需要选择上游的请求必须显式提供客户模型；仅凭资源 ID 不推断 Provider、Channel 或
协议。

创建成功使用统一最小响应，不增加 `provider`、`channel_id` 或 `upstream_model` 字段：

```json
{
  "object": "asset",
  "id": "provider-returned-opaque-id",
  "model": "customer-model-name",
  "reference": "asset://provider-returned-opaque-id",
  "status": "processing"
}
```

`model` 始终回显客户模型名。`id` 是 Provider 返回的不透明素材 ID，应用不得解析其前缀、长度或字符
规律；`reference` 由中转站按 adapter 结果返回，应用保存后原样用于视频请求。应用持久化
`model + id + reference`，不依赖 Provider 名称完成后续操作。

如果应用把另一个 Provider 的素材 ID 携带给当前模型，中转站仍然只调用当前模型确定的 Provider。
上游可能返回资源不存在、ID 格式非法或其它业务拒绝；中转站脱敏归一化后直接返回，不查询 ID 实际
属于哪个 Provider，不尝试其它 Channel，也不 fallback。由于裸 Provider ID 没有可靠的全局命名空间，
中转站不能在 Provider I/O 前保证识别“来自另一个 Provider”。

该边界不增加 `asset://<provider>/<id>`、加密句柄或 Provider 探测兜底。Provider 素材 ID 的外观可能
间接提示其来源，这属于已接受结果；唯一必须隐藏的是中转站不得直接返回上游原始模型名称。

单项查询不是生成前强制步骤。查询与生成之间存在状态变化窗口，查询成功也不能证明素材一定支持当前
模型或最终内容审核一定通过；强制预检只会增加延迟和上游调用量。

### 3.3 视频请求合同

视频内容直接接受并转发：

```text
asset://<ProviderAssetID>
```

对于这类引用，中转站只让既有 ModelArk V3 DTO 完成普通字符串/请求结构处理，不执行以下素材语义：

- 不加载 `Asset` / `AssetGroup`；
- 不验证 `user_id + app_id` 所有权；
- 不验证平台 ready 状态；
- 不比较创建模型；
- 不比较 `ChannelID`；
- 不预查 Provider；
- 不把 Provider 拒绝改写成平台推断的兼容性结论。

调用方自管路径统一使用 Provider 原生引用，不再由中转站区分公共预置与账号私域身份：

```text
asset://<ProviderAssetID>
```

公共资格、私域权限、存在性和可用性均由当前模型对应的 Provider 判断。`pubref_*`、`ast_*` 不继续
作为该路径的兼容别名，避免保留两套解释和改写逻辑。

### 3.4 Channel 配置边界

本方案不要求多个 Volcengine 模型合并到同一个 Channel。继续保持以下结构是合法且清晰的：

```text
客户模型 2.0   -> Channel 69 -> Volcengine 2.0
客户模型 Fast  -> Channel 70 -> Volcengine Fast
客户模型 Mini  -> Channel 71 -> Volcengine Mini
客户模型 2.5   -> Channel 72 -> Volcengine 2.5
```

每个 Channel 只配置正常履约所需的 Provider、Base URL、凭据、Region、Project、客户模型到 Provider
模型映射、视频协议和素材 CRUD 协议。中转站不新增以下配置：

- 共享素材组；
- 跨模型素材绑定；
- Channel 素材作用域组；
- 素材兼容模型白名单；
- 素材迁移或 fallback 规则。

若多个 Channel 实际使用相同 Provider 账号、Project 和 Region，能否复用同一个素材组和素材由
Provider 自然决定。中转站不需要知道或声明它们“属于同一素材作用域”。如果配置漂移导致另一个模型
无法访问素材，直接返回 Provider 错误，不自动修正配置或切换 Channel。

### 3.5 模型元数据

外部应用必须能在发送前从模型元数据确认这是“调用方自管”合同。建议在现有 `api.assets` 中明确：

```json
{
  "supported": true,
  "management_mode": "caller_managed_stateless",
  "reference_format": "asset://<asset_id>",
  "requires_model": true,
  "operations": {
    "create_asset": true,
    "get_asset": true,
    "update_asset": true,
    "delete_asset": true,
    "list_assets": false,
    "create_asset_group": true,
    "get_asset_group": true,
    "delete_asset_group": true,
    "list_asset_groups": false
  }
}
```

逐模型元数据仍只发布代码 adapter 和真实 Provider 证据确认的操作。没有素材协议的模型必须明确
`supported=false`；不能因为视频模型名称相似、使用同一供应商或共享账号就推断支持素材库。客户端
不需要素材 Provider 名称，因此 `api.assets` 不新增 `provider` 字段；上游原始模型名、ChannelID、
`model_mapping`、Region 和 Project 也不得进入该公开元数据。

### 3.6 当前错误语义

| 场景 | 当前合同 |
| --- | --- |
| 客户模型不存在 | 本地 `model_not_found` |
| API Key 无权使用客户模型 | 本地 `model_forbidden` |
| 当前模型未配置素材协议或不支持该操作 | 本地 `unsupported_asset_operation` |
| Provider 明确返回资源不存在 | 脱敏映射为 `asset_not_found` |
| 当前模型的 Channel、凭据或连接不可用 | `asset_upstream_unavailable` |
| 向当前模型提交另一个 Provider 的 ID | 按选定 Provider 的结果返回 `asset_not_found` 或 `asset_upstream_error`；不查找真实 Provider，不 fallback |
| Provider 返回其它业务拒绝 | `asset_upstream_error`，不猜测“不支持” |
| Provider 网络或服务异常 | `asset_upstream_error` |

新合同不再由本地 Resolver 产生 `asset_channel_mismatch` 或 `asset_scope_conflict`。错误归一化不得返回
原始 Provider 响应、上游原始模型名、Provider 名称、凭据、签名 URL、账号信息或内部诊断数据。普通
上游拒绝统一使用 `asset_upstream_error`，不增加 Provider 专属错误码或猜测 `asset_provider_mismatch`。

## 4. 方案复评

### 4.1 复评结论

**结论：设计通过且已实施。**

在“每个中转站用户就是受信应用、应用自行管理素材 ID、不要求共享 Provider 账号下应用间技术强
隔离”的明确前提下，该方案能够满足应用对已知素材 ID 的创建、单项查询、更新、删除和视频调用基本
要求，也能消除同一 Volcengine 账号内由模型/Channel 强绑定造成的本地误拒绝。

当前实现已经完成应用自管、无列表、单资源无状态 CRUD、视频引用直通、Provider 最终裁决和不公开
Provider/上游模型身份的合同切换；平台不再声称提供素材所有权隔离。

### 4.2 通过理由

1. **责任一致**：应用创建并保存素材 ID，Provider 判断实际可用性，中转站不复制 Provider 素材库。
2. **消除错误裁决**：中转站不再用客户模型名或本地 ChannelID 代替 Provider 的兼容性判断。
3. **避免目录暴露**：不提供列表、搜索和分页，不能通过正常 API 浏览共享账号完整素材库。
4. **控制面仍确定**：每次操作携带客户模型，由唯一 Seedance Channel 和代码协议确定上游，不引入
   随机分发或运行时协议推断。
5. **错误更可信**：只有 Provider 明确判定资源不存在时才单独映射为 `asset_not_found`；其它上游失败
   统一映射为 `asset_upstream_error`，避免本地伪造 `asset_channel_mismatch` 或猜测“不支持”。
6. **配置更小**：一个模型一个 Channel 可以继续保留，不新增共享素材组、素材作用域或跨模型绑定。

### 4.3 接受的剩余风险

| 风险 | 影响 | 处置 |
| --- | --- | --- |
| 已知其他应用素材 ID 时可能查询或使用成功 | 不具备应用间强隔离 | 作为信任合同明确接受；若不可接受则本方案失效 |
| 单项查询仍是存在性探针 | 可验证一个已知/猜测 ID 是否存在 | 信任合同下接受；沿用全局访问日志，不新增专用限流或失败查询业务审计；不把“无列表”宣传为所有权保护 |
| 查询成功后生成仍失败 | 状态、模型兼容性或审核可能变化 | 查询保持可选，实际生成结果为最终事实 |
| 应用遗失 Provider ID | 中转站无数据库映射可恢复 | 应用必须持久化；平台不提供找回或全量列表 |
| 应用误删共享账号资源 | Provider 会按共享账号权限执行 | 按应用自律合同接受；删除只作用于明确 ID，禁止列表和批量删除 |
| 错误 Provider ID 无法本地识别 | 裸 ID 没有可靠全局 Provider 身份 | 只调用模型选定 Provider，返回其错误且禁止跨 Provider fallback |
| Channel 凭据或 Project 漂移 | 同一 ID 在另一模型查询/生成可能失败 | 不自动迁移或 fallback，直接返回 Provider 错误 |
| Provider ID 进入客户合同 | ID 可能间接提示来源，但不应直接暴露上游模型名 | 接受 ID 原样公开；日志脱敏，不增加 Provider 标识字段 |

单项查询无法解决所有权问题；它只能降低应用传入过期或错误 ID 的概率。方案成立的根本原因是业务
主动接受应用自律，而不是因为删除列表后获得了技术隔离。

### 4.4 必须保留的边界

1. 所有素材控制面操作，包括 GET/PATCH/DELETE，都必须校验 API Key 的客户模型访问权。
2. 模型只能选择代码注册的协议和唯一 Seedance Channel，不得让客户传 ChannelID、上游 Base URL、
   AK/SK、Project 或私有 Action 名称。
3. 不提供素材和素材组列表；内部连通性测试可以调用 Provider List，但不能成为客户目录接口。
4. 错误素材只发送到客户模型选定的 Provider；任何失败都不得触发其它 Provider、Channel 或模型重试。
5. Provider 错误必须脱敏；不记录完整素材源 URL、凭据、签名 URL 或原始响应。
6. 不因单项查询成功而缓存“可用”结论，也不在生成前强制查询。
7. 不把共享账号下跨应用访问描述为安全隔离；需要隔离时使用独立上游账号/Project。
8. 公开响应只使用客户模型名，不返回 `provider`、`channel_id`、`upstream_model` 或 `model_mapping`；
   不为隐藏素材 ID 来源增加加密句柄、Provider 命名空间或其它兜底层。
