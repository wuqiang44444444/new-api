# 渠道不可用邮件告警首期实施方案

## 1. 目标与范围

代码已接入。两台本地网关进程共享 Redis 和 PostgreSQL，在关闭自动禁用时完成故障确认、收件、跨节点
成功恢复和再次告警。告警事务已用 SQLite、MySQL 5.7 和 PostgreSQL 15 核验。已使用后台配置的
Microsoft Graph 完成本地灰度实际收件。峰值验收结论见第 6 节。

发现上游渠道持续不可用或出现可处置的降级时，使用站点已配置的发信通道，及时通知运维收件人。告警
独立于全局自动禁用、渠道 AutoBan 和 Root 个人通知设置。告警只观察和发信，渠道启停、路由、重试、
计费和异步任务状态继续由原有流程处理。

原有渠道状态通知由自动禁用或恢复触发。新增链路记录统一的故障确认时间、逐收件人首次提交时间和用于
多实例判定的成功汇总。首期以现有业务调用和已登记巡检为
信号来源，覆盖普通转发、流式响应、视频和图片异步履约、Seedance 素材操作。发信仅使用邮件。图片和
视频的自动检查沿用无生成副作用的边界。尚无有效探针或业务结果时，相关操作显示为未验证。

现状依据见[渠道状态通知](../../service/channel.go)、[转发尝试](../../controller/relay.go)、
[渠道自动检查](../10-product/渠道自动检查与配置诊断.md)及
[系统错误报告与资源告警架构](../20-architecture/运维-系统错误报告架构.md)。

## 2. 故障判定

### 2.1 判定范围与规则

默认按渠道、客户模型和实际南向操作判定。连接、文本或图片生成、视频提交、任务查询、视频生成终态和
素材操作各按自身能力解释。只有证据覆盖共享连接、共享账号或全部当前可选凭据，才将故障扩展到整条
渠道。多 Key 渠道记录内部槽位及对应配置代次。换 Key、改映射或切换上游连接后，以新配置重新观察。
旧任务继续使用其冻结的执行事实，只有能归属当前配置的结果才参与当前故障判定。

| 已观察到的事实 | 首期处理 |
| --- | --- |
| adapter 明确识别生产凭据已停用，且影响唯一凭据、全部可选凭据或对应的共享账号 | 按已证明的范围立即确认故障。通用 `401`、`403` 和单 Key 失效本身不足以证明整条渠道不可用。 |
| 同范围的上游 `5xx`、连接失败或超时持续出现 | 试运行规则为任意连续 120 秒内至少 3 个独立有效失败，且这段连续失败期间无同范围有效成功。不同节点只在观测完整、范围一致时合并。单节点连接异常只描述该节点的观察范围。 |
| 部分 Key 明确失效且其他 Key 仍能履约，或同范围持续限流且仍有成功 | 发降级预警，正文说明影响范围。限流试运行口径为 120 秒内至少 3 个独立的上游限流结果并观察到同范围成功。单次 `429` 只记录。上游低余额继续使用现有邮件。 |
| 客户参数或额度问题、客户端取消、内容审核拒绝、单个任务业务失败、探针不支持 | 排除出上游渠道不可用判定。能确定阻断实际操作的本地配置错误按配置故障报告，正文标明原因和范围。 |

同一客户请求在同一判定范围内的多次重试只计一个失败。一次上游批量查询波及多个任务时只计一次，
同一次调用在传输层和 adapter 层观察到的结果也只形成一条信号。上游 HTTP `200` 后的流中断按已知
错误来源判断。客户端断开不计入上游失败。视频提交获可信任务 ID 只证明提交可用，任务查询成功只证明
查询可用，生成恢复须看到同范围的可信成功终态。只读探针可以确认它实际检查的操作。

持续故障合并到一次开放事件。只有晚于该事件失败证据的同范围有效成功，才可结束该故障事件并允许
下次告警。明确凭据或配置故障的恢复需看到受影响能力的新证据。配置代次失效可关闭旧事件并记录原因，
新代次从未验证开始。降级期间仍有业务成功，只有失效凭据恢复、限流退出或对应配置失效才结束降级。
首期恢复留状态和时间。降级首次达到门槛时发一封预警，随后升级为同范围确认故障时可发一封故障邮件。

### 2.2 采集和汇总

| 来源 | 复用与最小接线 |
| --- | --- |
| 普通转发、流式请求 | 在每次渠道尝试结束、重试前取得结果。复用映射前的实际 HTTP 状态及 adapter 错误分类。流式在结束时提交一次结果。 |
| 定时巡检 | 复用现有检查时间、范围、连接尝试和收到响应的事实。使用巡检实际验证的操作范围。 |
| 异步图片和视频 | 在已有上游提交、查询及生成终态边界取得结果。保留任务创建结果不明和轮询结果不可采信的既有语义。 |
| 素材操作 | 在既有 Provider 操作及错误分类处观察成功和失败。区分 Provider 调用、本地存储及素材源站错误。 |

观察只含发生时间、来源、节点、渠道、模型、操作、必要的内部凭据槽位或配置代次、去重标识、结果类别
和实际状态码。请求路径复用已有字段。每次成功只更新进程内对应范围的最近成功时间，按需增加降级判断
使用的计数。成功不逐条入队、不逐条写主库或 Redis。后台按批上报有变化的汇总。

失败在进程内按判定范围和短时间段合并，保留计数和足够核验规则的少量去重样本。计数不代替独立失败
证据。正常流量和故障集中时都按批次写入 Redis，成功汇总、失败样本、活跃范围数和每批字节数均设上限。
队列满、达到容量上限或上报滞后时，计数并丢弃不完整批次。压缩后证据不足时等待新的有效样本。
确认故障时在主库冻结首个有效失败、确认时间、规则版本和必要证据。

接线依据见[原始上游状态](../../clienterrlog/relay_attempt.go)、
[巡检网络观察](../../controller/channel_test_network.go)、[视频任务轮询](../../service/task_polling.go)及
[素材错误分类](../../service/asset_service.go)。

接取 NEWAPI 上游时，按下表复核这些接线。汇总、判定及投递逻辑集中在独立的 `channel_alert*` 文件。

| 原有入口 | 复核内容 |
| --- | --- |
| `middleware/distributor.go`、`controller/relay.go` | 选择渠道时保存配置代次及槽位，实际尝试返回时记录结果。重试流程改动时保留逐次观察及原请求标识。 |
| `relay/channel/api_request.go`、`relay/channel/aws/relay-aws.go`、`relay/channel/xunfei/relay-xunfei.go`、`relay/responses_websocket.go` | 共用 HTTP 和直接连接上游的 adapter 各自在实际传输边界记录结果。上游重排传输代码时，将调用保留在状态码映射前或真实流终态。 |
| `controller/channel-test.go`、`service/task_polling.go` | 自动巡检及轮询完成后按其实际验证的能力记录结果。接取上游时复核巡检或任务判定的正常结束点。 |
| `model/main.go`、`model/task.go` | 注册事件与投递模型迁移，并在已有任务快照中保存可选的告警范围。接取上游时保留迁移注册与旧任务可读性。 |
| `common/email_context.go`、`common/mail_graph.go` | 在现有发送实现中标记第一次 SMTP 提交或 Graph `sendMail` 开始时间。接取上游时保留标记与实际提交调用相邻。 |

## 3. 多实例合并与防误报

1. 每个运行实例以独立的启动身份上报。试运行每 5 秒封存一个 Redis 批次，同一有界记录保存最近成功
   汇总、失败证据和覆盖区间，原子写入并设置 TTL。空批次显式上报。写入失败时丢弃该批次，下一轮继续
   上报新数据。成功时间按观测时间取最大值，失败按原始观测时间排序和去重。
2. 后台判定复用现有主节点调度边界。试运行的批次检查间隔为 5 秒，避免将及时性依赖于常规巡检或日报
   周期。对“连续失败且没有成功”的规则，等待在该窗口内可能承接相同范围的实例都提交到最后一条候选
   失败之后，再核对其间有无成功。时间差处于允许的时钟误差内时等待可信的新样本。只看到某节点本地
   连续失败时，可保留该节点的连接异常。全渠道结论要等覆盖满足。
3. Redis 不可用、批次缺失或参与节点变更时，放弃受影响范围尚未确认的窗口，计数后从下一轮完整批次
   重新累计。旧批次随 TTL 自然过期，采集继续写入新批次。新样本达到判定阈值即可确认，120 秒是累计
   上限。按部署参与范围核对节点上报，缺少任一应上报节点的批次时该轮不作全渠道判定。灰度邮件写明
   实际覆盖范围。
4. 已具备完整覆盖的故障证据进入主库确认事务，事务内复核配置代次，并用开放事件和事件与收件人唯一键
   防止重复确认和重复投递。明确、范围充分的凭据停用证据可由后台直接提交确认事务。采用跨 SQLite、
   MySQL、PostgreSQL 的事务和条件更新。

首期复用站点共享 Redis 存放临时观测批次。试运行 TTL 为 5 分钟，覆盖 120 秒判定窗口和正常上报延迟，
具体值按灰度实测校准。未配置共享 Redis 的部署暂不启用这条窗口判定链路。已确认的故障、待投递邮件及
防重状态保存在主库，Redis 中断期间后台仍可处理已入库邮件。

接入依据见[站点 Redis 客户端](../../common/redis.go)和[项目缓存约束](../00-context/硬约束.md#6-安全与数据)。

## 4. 独立邮件投递

- 复用现有运维报告收件人名单和活动 SMTP 或 Microsoft Graph 配置。渠道告警使用独立开关，灰度期间
  可运行判定并记录结果，再启用实际投递。收件人配置独立于日报开关和 Root 个人通知选择。
- 故障确认与逐地址待投递记录在同一事务提交。主节点确认后立即唤醒发信，其他节点确认的事件由主节点
  每 5 秒扫描领取。有界并发、租约和定期扫描支持重启后续跑。发送前复核收件人。发信槽位繁忙时 5 秒
  后可重新领取，明确失败按现有退避模式重试，结果不明记录为待核对，避免重复发送。
- 按收件人记录首次实际进入发信传输的时间、通道受理时间、次数和状态。排队、领任务、发信槽位忙或
  本地配置失败不能计为首次提交。SMTP DATA 受理和 Graph HTTP 202 记录为通道受理，实际到达用收件箱核验。
- 主库仅保留故障事件、必要的判定摘要和投递进度。待投递、待核对和仍开放的记录供续跑、核对和去重，
  已结束且投递处理完成的记录按运维排障所需期限清理。
- 主题区分渠道故障、降级预警和配置故障。正文采用简体中文与英文，包含事件编号、影响范围、首次观察及
  确认时间、受控原因与后台排查入口。模板只使用脱敏元数据。

复用依据见[运维收件人](../../model/upstream_balance_alert.go)、[发信入口](../../common/mail_transport.go)及
[持久化资源告警投递](../../service/resource_alert_delivery.go)。

## 5. 功能与时效验收

| 指标或场景 | 验收方式与通过条件 |
| --- | --- |
| 首个有效失败到确认故障 | 按同一事件冻结的两个时间戳计算。在覆盖完整的条件下，明确故障证据到达后拟在 15 秒内确认。连续失败规则在 120 秒窗口内凑齐样本后，拟在末条证据发生后的 15 秒内完成跨节点核对并确认。分别报告失败积累时间和后台处理时间。流量不足和覆盖缺口单独计数。 |
| 确认故障到首次提交邮件 | 按事件与每位有效收件人核对。试运行目标为确认后 60 秒内发起首次提交。超过 60 秒仍无首次提交证据的待投递也计为超时。投递受理与实际收件分别核验。 |
| 跨节点成功迟到 | A 节点出现三次失败，B 节点在中间成功，刻意延迟 B 的成功汇总。确认前等待 B 的批次，合并后连续失败不成立。追加缺批、乱序、重复批次、时钟偏差、实例重启和滚动发布场景。 |
| Redis 数据缺失 | 删除 B 的成功批次或模拟 Redis 中断。丢失前两次失败与恢复后一次失败不能合计为三次。恢复后从新批次累计，达到阈值即可确认。已有待投递记录仍可续跑，同一事件只创建一次。 |
| 范围及重试 | 覆盖单 Key 失效与全部 Key 不可用、仅某模型不可用、重试换渠后客户成功、流中断、批量轮询、只读探针正常但生成持续失败、配置变更后旧任务迟到。 |
| 投递及重启 | 并发确认同一故障，每位收件人只生成一条投递。分别覆盖确认后重启、发信槽位忙、明确失败重试、提交结果不明及恢复后再次触发。用本地 SMTP 验证端到端，用部署实际发信通道和测试收件箱验收。 |

故障发生到首个可观察信号的间隔取决于真实业务流量和已登记探针。没有可用观察时明确显示未验证，
不纳入已确认样本的时效分布。15 秒、60 秒和观察阈值为拟定试运行目标，灰度前以实测校准。

本地双节点故障注入完成两次确认与 SMTP 收件，中间通过另一节点的成功请求恢复。两次从首条有效失败到
确认为 3.036 秒和 4.706 秒，从末条有效失败到确认为 3.008 秒和 4.701 秒，确认至首次 SMTP 提交为
13 毫秒和 14 毫秒。测试使用合成上游和本地 SMTP 收件器。

本地灰度使用已配置的 Microsoft Graph。观察模式在首条失败后 6.311 秒确认，投递表没有新增记录。
邮件模式关闭自动禁用，由两个节点合计收到三次合成上游 `503`。渠道 `#900002` 的故障从首条失败到确认
为 5.531 秒，确认后 501 毫秒发起提交，Graph 受理又耗时 1.062 秒。Gmail 收件箱显示同一事件 `#3` 的
渠道故障邮件，收件显示时间与确认均为 16:15。一次独立故障还验证了另一节点成功后记录 `recovered`。

## 6. 百万请求量下的性能验收

日均 100 万次约为 11.6 次请求/秒。容量按生产单节点峰值、重试后的南向调用峰值、同时活跃的判定
范围数和网关节点数计算。假设单实例每秒 1,000 次成功、50 个活跃范围、每 5 秒一次汇总，则
5,000 次成功最多生成 50 条变化汇总，连同有限失败证据和覆盖进度封装成一次 Redis 批次写入。
每节点每 5 秒上报一个批次、TTL 为 5 分钟时，稳态约保留 60 个批次，内存按活跃节点数与实测批次
字节数估算。主库的新增写入随确认事件和投递变化增长。峰值、并发争用及资源增量以目标部署实测为准。

邮件模式在完整观测且无开放事件、无待投递时，主节点每 5 秒执行一次事件扫描、三次领取查询、一次租约
扫描和一次首次提交超时统计，合计约每秒 1.2 次告警查询。主库在这条正常流量路径没有告警数据写入。

同一版本在功能关闭和开启时，用相同实例规格、Redis、数据库、合成上游和流量形状做对照。至少覆盖
正常流量、单范围热点、多范围高基数、集中 `503` 和超时、流式同时结束、多实例、Redis 变慢或中断、
主库写入变慢及发信服务变慢。按生产峰值持续压测，并用至少百万次请求的长跑检查堆、Redis 占用和待投递积压。
记录请求速率和重试放大倍数，以同一批次的故障与投递记录同时核验时效。

| 检查项 | 验收口径 |
| --- | --- |
| 客户请求 | 沿用现有运维邮件性能门槛。模型请求 P95 延迟增幅不超过 5%，超时率不升高。 |
| 网关资源 | 记录每实例峰值与稳态 CPU 核数、RSS、Go 堆、每请求分配和 GC。拟用每实例额外 CPU 不超过该实例配额的 5%、峰值 RSS 增量不超过 32 MiB 作为首轮容量预算，按生产规格和实际余量校准。 |
| Redis 与缓冲 | 记录批次速率和字节数、Redis 内存、命令延迟、超时和淘汰、队列水位、丢弃批次和重新计数次数。健康负载下采集无丢失。模拟 Redis 变慢和断连时内存保持有界，从新批次重新计数，客户请求仍满足延迟和超时门槛。 |
| 主库 | 检查告警事件与投递写入量、事务尾延迟、连接池和锁等待，核对预扣、结算耗时。正常无告警流量和持续故障期间均应证实主库没有观测批次写入。 |
| 业务时效 | 报告首个有效失败到确认、确认到各收件人首次提交的分布及超时数量。按范围核对无误报和无重复投递。 |

## 7. 实施顺序与发布门槛
