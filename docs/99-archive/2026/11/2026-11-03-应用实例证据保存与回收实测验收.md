## 问题与目标

按用户要求，在用户已经启动的应用实际调用文本、图片与 4 秒 mini 视频，验证请求证据原文保存、
读取格式化和真实回收。证据是非核心数据；本轮不增加停机封存、补记或恢复机制。

## 当前实际情况

  完整 Go 应用，端口 3501，主库为工作目录的 SQLite WAL；本轮没有重启或替换应用。

### 真实样本结果

| 场景 | 请求形状 | 实际结果 |
| --- | --- | --- |
| 文本 | GPT-4.1，普通 Chat Completions，32 tokens 上限 | HTTP 200，2.077 秒，回复精确符合指定标记 |
| 图片 | GPT-image-2，`n=1`、1024×1024、Base64 JSON | HTTP 200，17.201 秒；PNG 311,893 B，实测 1024×1024 |
| 视频创建 | mini、4 秒、480p、16:9、无音频 | 创建 HTTP 200、0.374 秒，随后 `succeeded`，Task SUCCESS、billing settled |

视频业务托管与测试样片属于独立业务/测试存储。证据仅保留实际请求、结果 JSON 和其中 URL，
不因证据保存或读取额外下载媒体；媒体内容入口只留最小事件，没有证据正文对象。

### 保存、加密与按需读取

- 按 RequestID 逐项授权下载 14 个前台样本的对象，26 项可独立比对的北向请求/客户响应
  SHA-256 全部一致。文本、图片和视频创建的四个方向对象均可读取；上游方向单独核验可读性，
  不把它与北向原文相同当作要求。
- 在盘对象均为 `NEVSIO3` 流式认证密文、权限 0600，管理员下载得到封装及原文；没有把原文写入
  验收报告。正文请求的排版原样保存，不因业务 DTO 转换而混淆两个方向。
- 图片上游响应 416,327 B、客户响应 416,273 B，分别完整保存；图片 Base64 随普通 JSON 保留，
  没有提取图片文件到证据目录。
- 文本默认预览不格式化；显式 `format=json` 才返回 `formatted`，读取前后密文摘要不变。
  大图片预览恰为 65,536 B，`display_limited=true`，格式化返回 `display_limited`，完整下载仍一致。
- 视频媒体下载的 north_receive/client_delivery 只有元数据，读取对象 HTTP 410；这不影响
  302/200 的业务下载，也不把跳转响应中的签名信息复制到媒体证据对象。
- 本轮所有窗口期限均为 `created_at + 172800` 秒；普通错误事件中没有重复 `http_exchange` 正文。

## 优化方案与验证边界

- 本轮真实保存、授权读取和手动固定截止回收通过，没有发现需要修改业务代码的证据缺陷。
- 本轮没有等待自然两天到期，也没有把磁盘填到 90% 以上。两天期限已从实际窗口核对；自动期限、
  一天压力清理及严格截止规则另运行现有确定性回归。手动回收通过不冒充这两个自然触发场景实测。
- 视频尺寸差异来自本次 Provider 结果，保留如实记录，不裁剪或变更分辨率合同。生成成功与交付
  准备中是两个状态，下载前等待托管 ready；不因 409 重发创建。
- 本轮是单组真实样本，不代表吞吐、长期留存、磁盘满或生产灰度验收，也不重用此前 CPU 百分比。
- 实际证据查询会发起访问审计。回收不清除仍在七天审计保留期内的访问记录；这不是正文回收遗漏。
