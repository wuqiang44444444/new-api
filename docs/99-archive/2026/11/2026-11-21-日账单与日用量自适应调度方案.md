# 日账单与日用量自适应调度方案

## 1. 问题与目标

在支持日报的部署中，日账单和日用量默认参与后台调度。应用在有前台容量余量时自动提速，业务流量上升时
主动降速，受压时停开新批，恢复后从原进度继续。日报可以跨多个低谷窗口完成，业务请求、扣费与退款、
在线日志提交优先。部署方无需设置开关、许可文件、速率或压力阈值。

现有 `usage_report_day` 按北京时间自然日生成两类数据。日账单归集扣款、退款及净额，并保留对账所需的
逐笔证据。日用量归集逻辑调用的结果及 Token、图片和秒数等计量。后台生成和发布可以延期，扣费、退款、
余额更新及正式月账单继续遵循各自的在线流程和已确认版本合同。

[日报发布合同](../../../20-architecture/decisions/0022-日报当前版本发布与历史证据迁移.md)

## 2. 当前实际情况

- 调度依赖 `DAILY_REPORT_ENABLED`，生产任务还需要 `DAILY_REPORT_CAPACITY_FILE`。候选每批最多
  25 行，写入默认每秒 50 行，上限每秒 200 行。逐笔候选主要是从消费及退款日志派生的
  `billing_report_lines`，日用量汇总、排行和历史复制也使用这份写入预算。25 行约束单次提交，
  每秒 50 行约束持续速度。约 157 万条来源仅写逐笔按 50 行/秒估算需约 8.7 小时。
- 隔离 PostgreSQL 等长复测中，停用日报的在线日志提交 P99 为 16.71–23.19 ms，小批固定
  200 行/秒时为 38.97–39.46 ms。仅写候选也使整窗 WAL 增量上升约一个数量级。
  这些结果说明当前测试负载下，固定速率会与前台争用资源。宿主噪声和合成负载限制了归因，现有数据
  尚无法确定生产低谷的安全速度。旧方案保留为压测和实现记录。
  [四组对照与小批续跑复测](2026-11-21-大流量日报争用分析与低优先级上线方案.md#4-实施前四组对照)
- 当前门控读取工作池短探测、在线连接池等待、主机资源和 PostgreSQL WAL 等信号。现有采样器
  缺少在线日志写入尾延迟的直接反馈，进程内连接池指标也只反映本节点。普通构建可在同一进程内暂停
  并保留聚合和游标。账单接管后会重读并校验已提交的前缀，复用已有候选。用量遇到进程退出时
  尚未完成的聚合需要重算。
  [当前任务入口](../../../../service/usage_report_day.go) ·
  [数据库采样器](../../../../model/daily_report_database_load.go) ·
  [账单检查点](../../../../model/daily_report_billing_checkpoint.go)
- PostgreSQL 最终来源校验按小时组织范围，但整日仍在同一条 SQL 内完成，查询期限为 5 秒。
  客户账单明细导出也读取 `DAILY_REPORT_CAPACITY_FILE`，并维护单独的读取速率。移除许可文件时，
  两条执行路径需要在同一版本切换。
  [整日覆盖校验](../../../../model/daily_report_log_coverage.go) ·
  [账单导出准入](../../../../service/customer_statement_export_execution.go)

## 3. 优化方案

### 3.1 默认调度与配置收敛

主库和日志库初始化成功、既有报表迁移完成、系统任务处理器已注册且调度器可领取任务时，
支持日报的来源默认安排日账单、日用量、历史回补及必要重建。沿用日期选择、重试和租约。
取得租约的任务按来源能力和实时压力逐批准入。手工重建继续登记日期，使用同一执行准入。

实施时移除日报启用开关、容量许可文件、日报专用速率和压力环境变量，以及启动脚本中的本地快速旁路。
批次期限、采样窗口和调节系数由代码维护，有效速率由运行时反馈决定。SQLite、MySQL、PostgreSQL
各自的准入策略按来源能力写入代码，随通过验收的应用版本交付。某种来源或共库拓扑尚未通过前台保护
验收时，版本发布范围须排除该策略。若代码无法识别待验证环境，则完成验证后再交付默认运行版本。
部署方无需提供开关、许可文件或速率配置。

### 3.2 自动退让与多节点基线

优先复用在线请求量、在途量、错误与超时指标。在线日志提交耗时覆盖取连接、执行及提交确认。
需要补采时，在现有公共写入边界做最小接线，有界内存采样器独立放在新文件中，评审时说明上游
合并的影响。在线路径沿用原 SQL、事务、索引和持久性。采样无同步数据库访问、网络调用或等待队列，
额外开销以独立对照验证。低样本窗口用慢样本数、在途量和短探测判断，P99 只在样本量足够时参与判断。
[日志写入边界](../../../../model/log.go#L100) · [原生代码最小入侵](../../../00-context/硬约束.md#7-newapi-原生代码最小入侵)

复用工作池短探测、连接池等待及数据库支持的实例统计。PostgreSQL 的 WAL 和可用 I/O 等待用于
佐证。MySQL、SQLite 使用各自可用的信号并独立验证，SQLite 重点验证并发写竞争。主库和日志库
分开时，每批访问的资源都要获准，采用其中最保守的预算。

多节点限额以共享资源为范围。日报租约限制执行者数量，节点本地请求指标只覆盖该节点。
优先复用已有跨节点观测，逐个节点核对样本时间、覆盖和当前流量。允许在已有后台通道携带有界摘要，
其时效必须满足退让目标。节点心跳用于判断节点存在和样本是否过期。秒级退让仍依赖实时前台
和共享库压力。实时跨节点信号缺失但共享库的必要探测新鲜且健康时，仅在该来源及
拓扑已验收的最低预算内试探。共享库必要信号过期、探测失败或相互矛盾且无法确认余量时自动暂停。
重复故障按代码内置退避减少探测。有可验证的恢复信号时自动重试，不要求外部监控服务或新增部署配置。
[当前数据库采样器](../../../../model/daily_report_database_load.go) · [节点心跳](../../../../service/system_instance.go)

用等长、同负载的停用对照建立前台波动范围。持续有积压时，代码按周期安排短暂静默窗，暂停共享
资源上的报表与导出新批，等待在途 SQL 结束和后台写回影响回落，再获取同负载的前台样本。
以共享资源、观测覆盖和相近流量区间维护基线。有持续压力或样本质量不足时冻结基线。
样本稀疏时按低档规则处理，避免把无请求和观测中断合并为健康。静默窗结束后按恢复规则执行。

| 运行状态 | 代码行为 |
| --- | --- |
| 启动或租约接管 | 从最小工作批起步。先验证观测与探测，接管时重算预算。 |
| 连续健康且存在余量 | 每个合格窗口最多升一档，主要缩短批间隔。保留单批行数、字节和时限边界，空闲时间不累积突发预算。 |
| 流量、在途请求或连接等待持续上升 | 当轮降档，拉长批间隔，并按批次代价缩减读写量。 |
| 前台越线、共享资源拥塞或必要信号失效 | 同一调度轮进入暂停。等待间隔结束后及每次开批前复查。已执行的 SQL 按短期限排空或取消，释放连接和事务。 |
| 恢复 | 连续健康窗口达到门槛后从最小批恢复。再次出现压力立即降档或暂停。 |

实施起测值为每 1 秒检查已采集的前台快信号，连续 3 个健康窗口后可恢复或升一档，
升档时最多增加约四分之一的等效预算，提前降档时先减半。数据库探测采用受限频率，样本过期与查询
超时分别处理。压测按数据库和部署拓扑定稿这些代码内置值，并记录最小样本量与基线失效条件。
验收分别计时「压力发生到检测」「检测到停止开批」「已在途 SQL 排空」。已观测到严重压力后，
下一批启动数应为零。记录状态转换、退让原因、批耗时和来源留存余量，避免逐批打印。

### 3.3 共享执行预算与最终校验

读源、逐笔写入、历史复制、清理、发布校验及客户账单明细导出共用所访问数据库的容量预算。
同库并发时核算两种后台任务的合计读写量。首版优先在重负载批次间分配一个执行名额，避免日报与导出
各自独立提速。账单导出随日报一并移除容量文件与读库速率依赖，迁移到同一准入，沿用其版本引用、
续跑分片、磁盘和对象存储保护。读库延期时保留已完成分片，恢复后从已有检查点继续。
[客户账单导出执行路径](../../../../service/customer_statement_export_execution.go)

发布仍核验来源覆盖、旧边界、逐笔资金、依赖及租约。当天保留共同构建上界，已结束日期在最终核验前
刷新来源边界。关联日期与跨日退款沿用原有发布事务，完成验证后才切换指针。

最终来源校验单独计量。在代表性大流量日验证整日查询的资源消耗、取消与排空延迟，并把流量突增
注入查询执行期间。已开始的校验使用经实测的短期限。若整日执行超过安全工作量，按日期范围缩小
单次校验工作量，并证明新旧上界、逐类型计数和版本摘要等价。拆成多次 SQL 时，同一自然日内账单、
用量及旧边界的见证必须来自同一一致性快照。压力打断时丢弃该次可变来源见证并释放快照，下次
重新核验；暂停期间不保留事务。若短低谷中反复无法完成校验，该来源暂缓进入发布，并纳入
资源隔离评估。 [当前覆盖校验](../../../../model/daily_report_log_coverage.go)

### 3.4 续跑、积压与版本回滚

- 同一进程内，普通构建在批间保留游标、冻结上界与聚合，旧逐笔证据比对在已完成批次处暂停。
  跨进程接管时，账单逐笔与检查点原子提交。接管者重读、校验前缀并复用已提交的明细和已完成汇总。
  冻结历史复制从已提交主键继续。日用量复用完整候选，未完成的聚合在进程退出后需要重算。
  验收记录接管后的重扫代价和净推进量。若短低谷反复接管导致实际进度停滞，补足可恢复进度后再验收。
- 监控最老待生成日期、最后有效进度、延期原因和来源留存余量。持续延期逼近留存线时提前告警，
  优先用现有受保护的证据迁移或来源副本保全证据。容量允许时，在同一准入预算内优先推进接近
  留存线的范围。缺失证据沿用冻结来源和待核对规则。日报积压不得放宽前台保护。
  [来源留存与隔离依据](2026-11-21-大流量日报争用分析与低优先级上线方案.md#3-优化方案)
- 观测中断或前台受压由代码暂停。若控制器本身发生缺陷，使用现有部署的应用版本回滚流程。
  回滚前确认目标制品和原部署依赖可恢复，按现有流程替换进程并等待在途操作退出或租约失效。
  验证旧版能读取仍受支持的已发布代际及导出引用，且会拒绝不兼容的未完成候选或忽略其进度并安全重建。
  保留兼容的检查点与有效发布指针。隔离环境先演练新旧进程交接和再次升级，确认同一范围不会并行发布、
  资金事实与旧指针仍能核验。

### 3.5 实施与上线验收

先在隔离环境复现停用基线并验证采样成本，再落地代码准入、限速和恢复规则。账单导出迁移与旧许可清理
在同一版本完成。应用支持默认运行的交付范围以来源策略和代表性目标拓扑的验收结果为准。

| 验收场景 | 通过条件 |
| --- | --- |
| 前台保护 | 在相同来源、旧账单代际、数据库参数和等长窗口下，对照停用、原固定小批与自适应调度。用真实网关请求、结算与日志路径，重复低谷、突增、持续高负载、恢复。分别比较各阶段 P95/P99、吞吐、错误率及停顿后的 WAL 与 I/O，前台指标保持在同负载基线预先记录的自然波动范围。 |
| 提速与自动退让 | 在可测余量的低谷，日报实际推进明显快于原固定 50 行/秒基准。突增时满足检测与排空时限，进入暂停后没有新批启动。稀疏样本、必要观测失效及恢复场景按预定状态转换。 |
| 数据库与多节点 | SQLite、MySQL、PostgreSQL 独立验收。节点 A 跑后台、节点 B 承担业务突增，验证 A 自动退让。验证主库与日志库分开时实际访问资源的联合准入，以及日报和客户账单导出并发的合计压力。 |
| 最终校验与账务 | 使用代表性大流量日和同量级旧代际覆盖最终校验、迟到来源及跨日退款。核对来源见证、新旧边界、逐笔金额、归属、用量去重与联合发布。暂停后同一候选继续前进，已提交账单逐笔无重复写入。 |
| 积压与回滚 | 模拟多低谷、进程退出、租约接管、来源留存逼近、清理积压及控制器故障。验证恢复进度、同一范围的发布指针、旧版读取和版本回滚流程。 |

本方案接替前方案中的许可文件、人工启用及固定速率发布姿态。原隔离压测继续作为证据，
前台延迟、吞吐、错误率、账务完整性和来源覆盖继续作为验收条件。业务保护与低谷推进同时达标
才交付对应来源策略。若最小工作批仍会使前台退化，代码继续延期，高负载由既有资源隔离路径承接评估。

实施验收后同步修订报表日汇总架构与计费运维手册，清理配置样例和旧旁路说明。ADR-0022 继续约束
资金证据与发布一致性。仅当自动资源调节形成独立的长期架构取舍时评估另记 ADR。

## 4. 实施与复测

### 4.1 停用基线和采样开销

使用独立的 PostgreSQL 18.4 容器，限制为 2 CPU、约 1.25 GiB 内存。
每组从同一快照克隆，日志约 56 万行，历史目标日 6 万行，原发布版本 2 万行。
测试使用本地 HTTP 路由和实际账户查询、消费日志写入。后台日报均不运行，按基线、采样、
采样、基线顺序执行。每轮测量窗 10 秒，约 200 请求/秒，每轮采到 2,000 次写入，均无失败。

| 前台路径 | 日志 P95（ms） | 日志 P99（ms） | HTTP P99（ms） |
| --- | ---: | ---: | ---: |
| 原日志写入 | 2.10–2.19 | 3.59–5.61 | 7.04–13.39 |
| 接入初版采样 | 2.69–3.26 | 6.02–8.09 | 11.76–21.96 |

短窗数据库尾延迟差异尚未通过保护验收。初版采样的闭包在单进程微基准中产生了 1 次分配，
已改为值类型记录器。改后日志、结算和请求采样的微基准均为 0 B/op、0 allocs/op。
微基准测量内存采样开销，线上验收仍需用真实网关的等长测量确认端到端影响。

### 4.2 实施边界与首次复测

日报已接入默认调度。代码按前台样本、数据库连接等待与实例压力控制节奏。
进程内以短批互斥，同一任务库的执行者共用可接管的执行租约。候选写入、最终来源核验、
发布事务和账单明细读取均按该租约进入数据库。候选、已发布指针和续跑格式沿用原有模型。
采样接线位于现有请求、结算及公共日志写入边界，统计主体存放在独立文件中。

首次联合负载复测使用同一隔离模板，另建 4,000 行目标日与 1,200 行旧版本，
HTTP 路由调用应用结算入口与真实日志写入。阶段负载约为 100、600、100 请求/秒。
停用组在突增场景已有失败和队列积压，恢复段仍受前段积压影响。这轮自适应组继续推进候选，
但未在 120 秒试验窗口内联合发布。该轮无法证明业务尾延迟或发布速度达到上线门槛。

将突增调整为约 300 请求/秒后，下一轮在 92.64 秒完成日账单和日用量各 1,600 行的联合发布。
