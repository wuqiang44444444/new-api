# 日报日志扫描与发布校验优化方案

## 1. 问题与目标

2026-11-21，本地用数据库备份启动网关后，账单和用量日报共用的 `usage_report_day` 后台任务出现首游标
查询超时。随后上游账单读取出现多批 500 行查询耗时超过 1 秒，统计更新后首游标和历史日尾批仍发生超时。

**业务服务的可用性、请求性能和在线日志写入优先。** 日报使用业务高峰剩余的数据库容量，受压时先暂停
历史回补，必要时推迟日报。生产上线要求业务请求和日志写入的吞吐、尾延迟及错误率均无可归因于日报的
回退。应用侧复用现有日志索引、写入语句和事务路径，优化集中在日报读取、校验及候选投影。

当前发布规则见 [报表日汇总架构](../../../20-architecture/账单计费-报表日汇总架构.md)及
[ADR-0022](../../../20-architecture/decisions/0022-日报当前版本发布与历史证据迁移.md)。

## 2. 当前实际情况

### 2.1 本地复测

环境为从备份恢复的独立 PostgreSQL 18.4 实例。以下时间均为北京时间。测试使用后台日志和只读
`EXPLAIN (ANALYZE, BUFFERS, TIMING OFF)`。日志表约有 618 万行、表数据约 12 GB，11 月 20 日
有 1,574,210 条消费与退款日志符合复测条件。该副本的 `shared_buffers` 为 128 MB，
`random_page_cost` 为 4，`max_wal_size` 为 1 GB，使用跳过 CPU 与内存门控的本地快速模式。
下列数字用于定位问题与比较查询形状，目标环境性能以生产参数和并发写入复测为准。

| 阶段 | 已验证事实 |
| --- | --- |
| 首游标 | `dailyReportFirstLogCursor` 先对整个日范围求 `MIN(id)`。13:51:45 首次超时，统计缺失时可复现 5 秒超时，计划估计 2 条命中，实际为 1,574,210 条。13:57:13 自动统计后，14:06:46 的用量首游标再次超时，耗时 5,004.527 ms。 |
| 常规批次 | 13:54:06 至 13:54:12 的六批分别耗时 1108.232、1250.174、1638.757、1077.291、1195.420、1038.396 ms，均返回 500 行。一次日志采样记录了 220 条超过 200 ms 的满批，最后一条与自动统计发生在同一秒。随后旧查询首批和中段实测约 2.37、4.05 ms。历史慢批的计划未采集，时间关联支持统计失准放大了普通批次耗时。 |
| 历史尾批 | 11 月 20 日空尾批实测 494.14 ms，沿主键检查约 14 万条无效日志。11 月 17 日用量尾段在 14:10:16 耗时 5,001.167 ms，超时前已返回 395 行。其 ID 区间从 2,636,375 到 6,179,361。历史日距全局上界越远，沿主键读取时可能检查的其他日期日志越多。 |
| 日志来源校验 | 自动统计后，账单的 `COUNT + SUM(行版本摘要)` 曾实测 5.36 秒，并行顺序扫描从共享缓冲区外读取约 150 万块。复审时，整日按类型合并聚合在 8 秒限制下仍超时。按小时分段、在同一条 SQL 内聚合的两次复测约 2.9–3.5 秒，其中一次核对了账单行数与基线一致。完整摘要和旧边界等价性仍待验证。 |
| 发布事务 | 13:59:55，在 5 秒发布事务内统计候选问题行耗时 1,052.508 ms。评审另一次执行计划测得约 3.29 秒，扫描了整张逐笔投影表。候选规模和旧代际保留都会影响这一步。 |
| 请求结果证据 | 13:53:59，`applyFinalErrors` 按最多 200 个 `request_id` 查询用时 10,990.788 ms，发生在自动统计之前。该查询受构建阶段上下文约束，当前缺少单批时限。 |

分页 SQL 的关键形状如下。它读取 `content`、`other` 等逐笔证据，并计算 `tuple_revision`。

```sql
WHERE type IN (2, 6)
  AND created_at >= :start AND created_at <= :end
  AND id > :cursor AND id <= :upper
ORDER BY id ASC
LIMIT 500
```

日期范围由 `created_at` 决定，分页顺序由 `id` 决定，`LIMIT 500` 只约束返回行数。数据库可能沿
主键过滤较大的 ID 区间，也可能先取得日期范围内的候选再排序。11 月 20 日账单约有 3,149 个非空批次。
常规分页在统计更新后已明显恢复，首尾超时、候选写入与发布校验是后续优化重点。11 月 20 日曾有
157 万行账单候选等待重试，复审时账单和用量均已发布，当天的重试记录已清除。

对应代码见[首游标](../../../../model/daily_report_scan_start.go#L14)、
[上游账单分页](../../../../model/billing_upstream_reader.go#L77)、
[用量分页](../../../../model/usage_analytics_scan.go#L297)和
[发布前校验](../../../../model/daily_report_stage.go#L105)。
PostgreSQL 建议在恢复后补齐优化器统计，统计可改善计划选择。应用改造应同时覆盖统计已就绪时仍出现的
空尾批和发布校验问题。 [PostgreSQL 恢复文档](https://www.postgresql.org/docs/18/app-pgrestore.html#APP-PGRESTORE-NOTES)

### 2.2 复合游标原型

用同一日期、相同的查询字段和固定的 ID 上界，在有统计的本地副本测试按 `(created_at, id)` 续读。
以下是数据库端单次执行时间。首批和中段均返回 500 行，尾批均为空。

| 位置 | 当前按 ID 读取 | 按日期和 ID 读取 |
| --- | ---: | ---: |
| 首批 | 2.37 ms | 0.95 ms |
| 中段 | 4.05 ms | 1.52 ms |
| 空尾批 | 494.14 ms | 0.83 ms |

首批和中段原型使用现有 `idx_created_at_id (created_at, id)`，尾段也观察到
`idx_created_at_type` 加增量排序。另用相同字段比较 PostgreSQL 行值谓词和展开的等价 `OR` 谓词，
11 月 17 日尾段分别为 2.5 ms 和 895 ms，11 月 20 日中段分别为 2.0 ms 和 1,024 ms。
当日仍有大量高于冻结 ID 的新记录时，采用复合游标的空批也可能读取较多数据页。一次模拟日中冻结的复测
返回 0 条，读取 2,606 个共享缓冲区外的数据块，耗时约 80 ms。

### 2.3 候选写入与业务争用

`billing_report_lines` 为每条源日志写一行，存储客户和上游逐笔证据，并维护 4 个索引。复审时该表
`pg_table_size` 约 9.2 GiB，含索引约 12 GB。11 月 20 日的 157 万行候选说明每次重建的写入规模。
评审记录的账单构建约 4 分 12 秒。源日志读取、解析、关联查询、候选写入与提交的耗时占比
仍需分开采样。14:05:40 多个无关查询同秒变慢，连数据库取时也用了约 271 ms。
副本同时出现大量请求触发的检查点，累计值包含数据库恢复及其他工作。日报的独立 WAL 增量、检查点
贡献和对在线写入的影响须通过对照压测核实。 [PostgreSQL WAL 与检查点](https://www.postgresql.org/docs/18/wal-configuration.html)

## 3. 优化方案

### 3.1 使用日期与 ID 推进日报分页

1. 为 PostgreSQL 账单和用量日报共用一个明确的构建读取入口。从日期起点直接读取首批，移除整日
   `MIN(id)`。后续以 `(created_at, id) > (上批最后一行的 created_at, id)` 续读，排序与游标一致。
   两类日报各自传入现有日期边界、日志类型、筛选及字段，保留固定的 `UpperLogID`、500 行批大小、
   短读连接、单批期限和取消信号。以现有索引执行，并在目标版本记录实际计划与扫描读量。
2. 三库共用相同的日期与来源边界语义。PostgreSQL 使用通过复测的行值谓词，初次实施先复验
   SQLite、MySQL 的既有路径。后续采用复合游标时，以各库的正确性与实际执行计划选择谓词。ClickHouse
   按现有报表支持范围处理。日报显式启用新的读取入口，历史盘点工具的 `ReadOnlySource` 仍表示
   只读来源。导出、交互查询和正式月账单使用各自入口。 [历史盘点调用点](../../../../model/billing_original_replay_inventory.go#L132)
3. 将依赖原有 `id ASC` 的规则写成明确的来源选择。**折扣组合的首条来源**采用最小来源 ID，
   **任务补证秒数**采用最小合格来源 ID 对应的秒数与证据，**Token 展示名**采用最大来源 ID
   对应的非空名称。对秒数同时更新所选行及汇总贡献，保证跨批后出现更小 ID 时结果一致。
   以跨批、同秒、时间与 ID 反序的样本核对旧基线，并覆盖消费及退款的跨批关联。 [折扣组合](../../../../model/billing_statement_discount_combinations.go#L185) ·
   [计费秒数证据](../../../../model/billing_upstream_evidence_coverage.go#L59) ·
   [Token 展示名](../../../../model/billing_customer_summary_accumulator.go#L34)

### 3.2 缩短来源校验与发布事务

1. **将问题行计数移到候选构建阶段。** 在补齐历史原价字段后，按现有诊断条件对成功写入的逐笔行
   计数，每行最多计一次。将计数随同代候选的完成状态持久化，并区分已计算的零和未计算。
   历史迁移及升级前遗留候选使用同一口径，在发布事务外核实计数。发布事务直接读取已完成的计数，
   继续核对租约与旧指针，再更新发布状态。 [候选批写](../../../../model/billing_report_build.go#L89) ·
   [旧原价补齐](../../../../model/billing_report_diagnostics.go#L169) · [发布前补算](../../../../model/daily_report_issue_rows.go#L14)
2. **让校验实际按日期范围读取。** PostgreSQL 首选在单条 SQL 内按半开区间分段读取自然日，
   以小时分段原型作为起点，依据目标环境的执行计划、读页和时限决定段宽及查询形状。同一日志库、
   自然日及有效当前 ID 上界的校验可共享按类型聚合，其中账单使用消费和退款，用量按既有类型取值。
   各旧代际的 ID 边界分别计算覆盖行数，可用带边界条件的聚合在同一扫描完成。使用同一语句的读取
   快照，保留当前边界的 `xmin` 摘要和旧边界的覆盖比较。若选用多语句分段，须保持一致读取快照，
   测量快照持续时间、连接占用和在线写入影响。 [当前边界和旧边界](../../../../model/daily_report_stage.go#L105) ·
   [PostgreSQL 事务隔离](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-READ-COMMITTED)
3. **将候选复用与发布核验按各自需要执行。** 对已经完成且不可变的同一候选与旧代际，评估在同一轮
   内复用精确逐笔核验结果。发布前根据有效来源边界核验日志变化、旧版本覆盖、金额、资金归属和依赖，
   发布事务内继续核对租约和旧指针。跨重试轮次重新核对可能变化的来源。用已有旧代际的大流量日
   验证 `verifyCustomerOriginalCoverage`，记录它的总耗时及候选复用阶段重复校验的开销。 [候选复用](../../../../model/daily_report_stage.go#L72) ·
   [逐笔金额校验](../../../../model/billing_report_original_coverage.go#L32) · [发布事务边界](../../../../model/daily_report_stage.go#L200)
4. 为 `applyFinalErrors` 的两段批查询设置受父上下文约束的单批期限，复用已有重试路径。
   复测使用现有请求 ID 索引，保持跨午夜归并范围、按用户隔离、日志 ID 上界以及最终请求归因。
   若正式参数下仍慢，再按实际计划调整查询形状。迟到补报回看作为独立观测项，
   以既有有界入口运行。 [最终请求归并](../../../../model/usage_analytics_evidence.go#L24) ·
   [迟到补报回看](../../../../model/billing_report_schedule.go#L138)

### 3.3 业务优先的运行时保护

1. 保留日报现有租约与读连接上限。对候选批写设置可按对照压测校准的行数速率预算，
   覆盖正常日报构建、全日重建及历史复制。单个连接和 CPU／内存门控之外，使用可用的库端
   I/O 与 WAL 速率、在线连接池等待或业务及日志写入尾延迟判断是否退让。通过现有数据库和应用
   指标观察压力，采样和退让逻辑在日报 worker 内执行。
2. 把退让接入批读、候选批写和发布前重校验的执行边界。压力超过由写入基线校准的阈值时，停止
   开启新批次并释放连接后等待，优先延期历史回补。单条查询继续受期限约束，已开始的发布事务保持
   短小原子。压力恢复后沿现有租约、候选和重试机制继续，依照正常规则复验来源。
3. 如果在保护业务的速率下仍达不到日报发布预算，先测量并减少逐笔投影的重复字节或重复构建，
   同时保留审计、下钻、导出及已有版本引用所需的证据。若共库资源仍不足，再评估隔离报表读写资源。
   生产容量验收使用正常门控并持续测量业务表现。 [候选批写](../../../../model/billing_report_build.go#L89) ·
   [现有日报门控](../../../../service/usage_report_day.go#L29)

### 3.4 实施顺序与上线验收

先实现复合游标和顺序等价，随后将问题行计数移出发布事务，再完成有界来源校验及重建链路复测。
运行时写入预算与退让机制须在生产灰度前完成。按同等数据和负载对照账单构建、日志来源校验、
新旧逐笔比对、问题行计数、候选批写与发布事务各阶段的耗时、读写量和错误。

| 验收项 | 验证方法与通过条件 |
| --- | --- |
| 结果一致 | 在同一固定来源上对比旧、新结果。逐笔核对来源 ID、客户与渠道归属、消费、退款、净额和冻结金额，随后核对汇总、折扣组合、秒数来源、Token 展示名及问题行数。覆盖午夜、同秒跨批、时间与 ID 反序及空尾批。 |
| 来源完整 | 核对分段和旧、新 ID 上界的行数与版本摘要。并发晚提交、更新、清理及跨日退款场景须保持覆盖拦截、重试与发布原子性。覆盖旧候选问题计数未知、明确为零和候选复用。 |
| 日报性能 | 用生产 PostgreSQL 版本、参数、正常门控与写入流量复测冷缓存、繁忙日、历史重建和当日持续写入时的尾批。记录执行计划、P95/P99、实际扫描量及从启动构建到发布的总耗时。分别核对 5 秒查询和发布事务预算、8 分钟单类构建预算及 16 分钟任务总预算。 |
| 业务与日志写入 | 在同一生产峰值写入负载与数据库配置下，多轮交替对照关闭日报、旧版日报和优化后日报。对比业务请求吞吐、可用性、错误率和 P95/P99，以及日志提交吞吐、错误率和 P95/P99，辅以 I/O、WAL 速率和连接池等待。预先约定如何辨别测量波动。优化后开启日报时，以关闭日报的同负载基线判定真实回退。 |
| 灰度与退让 | 验证压力升高时日报暂停或延期，恢复后能够继续且结果正确。发现业务服务或日志写入有真实回退时，先降低日报速率或暂停回补，再复测。业务服务、日志写入及日报发布三项同时通过后扩大灰度。 |

## 4. 第一阶段实施与验证

- PostgreSQL 的账单、用量日报构建现已显式启用 `(created_at, id)` 续读。首批使用原日期下界和冻结
  ID 上界，后续按时间和 ID 推进。到达最大 ID 的页面仍继续读取当天时间上更晚的低 ID 日志。读取复用
  现有索引，在线日志提交沿用原有 SQL、事务和索引。历史盘点继续按照 ID 顺序读取同一范围。
- 报表仍按既有 ID 顺序的优先级选择折扣组合、冻结倍率、计费秒数和 Token 名称。用量任务的计费模式
  与 API Key 采用首条合格来源的 ID，计费图片数量采用最后一条合格范围日志，随后按原顺序合并直接
  交付证据。
- 在 SQLite、独立 PostgreSQL 18.4 和 MySQL 5.7.44 测试库通过真实日报构建、发布和读取对照。
  样本包含同秒 500 行、最大 ID 位于首批末尾、时间与 ID 反序、上下界外日志、退款、折扣和秒数补证。
  发布的账单净额、逐笔退款、用量、显示名称和证据来源与 ID 顺序基线一致。PostgreSQL 另通过
  来源行数相同但行版本变化时拒绝发布的回归。
  [复合游标](../../../../model/daily_report_log_cursor.go) · [日报等价测试](../../../../model/daily_report_log_order_test.go) ·
  [来源版本回归](../../../../model/daily_report_reliability_test.go#L204)

## 5. 第二阶段实施与验证

- 账单候选批写成功后累计问题行，并把计数和所属代际随候选完成状态保存。已计算的零直接用于发布。
  历史明细复制沿用原诊断口径计数。缺少计数或计数属于其他代际的旧候选在发布写事务外补算。
  发布事务读取对应代际的计数，并执行现有租约检查、版本核对和发布指针更新。迁移增加的字段仅位于
  日报候选表。 [候选计数补算](../../../../model/daily_report_issue_rows.go) · [发布事务](../../../../model/daily_report_stage.go#L255)

  worker 在进入发布校验前复查现有资源门控。 [日期校验 SQL](../../../../model/daily_report_log_coverage.go#L45) ·
  [发布校验接线](../../../../model/daily_report_stage_log_checks.go#L19) · [资源门控](../../../../service/billing_report_day.go#L74)

### 6.1 隔离数据库合成负载

在限用两个 CPU 的 PostgreSQL 18.4 容器中，使用约 38 万条合成日志、目标日 61,000 条和既有日报代际。
每组从同一模板恢复，15 秒内约每秒发起 800 次日志提交和 160 次简单业务读。真实网关接口和原恢复库
未参与压测。一轮初测的日志提交结果如下，耗时包含客户端等待。

| 模式 | 成功提交 / 发起 | 提交 P95 | 提交 P99 |
| --- | ---: | ---: | ---: |
| 停用日报 | 12,000 / 12,000 | 3.65 ms | 6.21 ms |
| 优化前日报 | 11,823 / 12,000 | 26.23 ms | 61.33 ms |
| 新日报，初始默认预算 | 12,000 / 12,000 | 16.18 ms | 26.69 ms |

新旧日报都完成目标日重建，核对的客户净额一致。初始默认预算下仍出现高于停用基线的尾延迟。
同一合成库中，200 个请求 ID 的错误归并示例使用现有 `idx_logs_request_id`，执行 3.52 ms。

随后用两轮交换顺序的对照验证主机保护。主机压力触发后，两轮各完成 12,000 次提交，日报在构建前退让。
另在本地模式下保留数据库门控，将合成环境的 WAL 阈值设为 1 MiB/s，两轮都在约 3 秒后因 WAL 压力退让，
各完成 12,000 次日志提交，提交 P95 为 1.78–1.80 ms，P99 为 3.02–4.80 ms。两组退让测试都保留
原日报版本。该 WAL 阈值只用于触发合成负载下的保护，生产预算需结合目标实例校准。

生产参数与峰值流量对照、目标环境灰度，以及保护业务预算下的大流量日完整发布时限仍按 §3.4 验收。

## 7. 综合评审后的修复

- 账务逐笔核验之后先逐批验证依赖，再读取最终来源覆盖。最终校验和发布入口遇到压力即退出，下一轮
  从全部可变证据开始复验。独立 PostgreSQL 回归在账单查依赖时修改同日用量错误日志，两类发布指针均
  保持原状。SQLite 回归覆盖首个范围已校验后第二个范围退让，以及重试时来源变化。
- 冻结历史复制把进行中的代际登记在候选表，从各投影表已提交的最后主键续跑。复制进行中不能发布，
  旧 worker 也会拒绝其版本。完成后按原发布规则核对金额和证据。两次中断回归分别覆盖逐笔行和复合
  主键的证据分片，重试发布同一代际，金额、问题行数和分片内容保持一致。
- 旧候选或恢复后缺少准确问题行数时，按主键分批重新统计，每页受五秒约束。停用或退让时沿用旧发布
  指针。废弃未发布数据满一小时后可由后台按预算清理，仍被已发布指针或有效候选引用的数据受到保护。
- 已开始的日志构建对持续压力最多等待 12 秒，短时恢复时保留本轮内存聚合。超过上限后按压力原因延期约
  一分钟，普通构建下轮重扫。PostgreSQL 用估计单行 WAL 与总
  WAL 阈值共同约束行速率，集群实际 WAL 继续是退让信号。观测的每行总 WAL 超过初始预算时，当轮
  降低写入速率。启用事务速率阈值后在同一探测中读取数据库
  累计事务数，低 WAL 的高频业务也能阻止日报进入构建。 [PostgreSQL 数据库累计统计](https://www.postgresql.org/docs/18/monitoring-stats.html#MONITORING-PG-STAT-DATABASE-VIEW)
- 报表生成由 `DAILY_REPORT_ENABLED=true` 显式开启，已发布结果沿用现有读取入口。在线日志继续使用
  既有表、索引和写入事务。 [配置与灰度](../../../40-operations/01-计费与分组运维手册.md#日报数据库预算与灰度)

### 7.1 HTTP 与在线日志写入复测

隔离 PostgreSQL 18.4 使用 3 个 CPU、256 MiB shared buffers 和 2 GiB max_wal_size。通过本机
HTTP 测试路由读取账户并调用现有 `RecordConsumeLog`，分别测量 HTTP 和日志写入。使用同一模板的
两个交替顺序，目标日 80,000 条来源、已有 20,000 条旧报告。每轮约 18 秒，每秒发起约 800 次请求。
为单独测试数据库门控，两版 worker 都跳过宿主 CPU 和内存采样。

| 模式 | 每轮成功 HTTP／日志提交 | HTTP P95 / P99（ms） | 日志写入 P95 / P99（ms） | 日报 |
| --- | ---: | --- | --- | --- |
| 停用日报 | 14,400／14,400 | 3.64–36.38 / 7.71–86.91 | 2.07–25.08 / 4.90–58.93 | 保留旧版本 |
| 优化前 | 14,400／14,400 | 7.09–23.04 / 17.85–71.15 | 4.44–14.15 / 15.68–50.57 | 两轮均发布，耗时 9.26–9.79 秒 |
| 新版，初始行数和 WAL 预算 | 14,400／14,400 | 9.55–15.07 / 22.38–47.40 | 5.81–8.64 / 15.07–29.56 | 两轮均发布，耗时 24.86–31.71 秒 |

新旧版本发布的来源行数和净额一致。停用基线的尾延迟跨轮波动很大，现有数字无法证明并行运行时无回退。
新增事务速率门控后，用 500 事务/秒做了两轮峰值触发试验。两轮均在约 3 秒后退出并保留旧版本，每轮
14,400 次 HTTP 和日志提交全部成功。参数只对合成负载有效。真实业务、渠道和生产峰值仍按 §3.4 验收。

### 7.2 大流量日完整发布复测

更换为 1,574,210 条合成来源，同一日初始已发布 20,000 条。活动日志来自同一路径，约每秒 20 次
HTTP 结算样例。第一次以 24 MiB/s 总 WAL 上限和初始行预算运行，约 39 秒后按压力延期。两个已发布
指针均保留旧版，已写入的未发布账单明细为 88,600 条。同期 783 次 HTTP 和日志均成功，提交
P95/P99 为 12.43/106.47 ms，实例 WAL 位置增加约 682.7 MiB。该次结果触发了基于观测 WAL 的
当轮自适应降速改进。

第二次用同一来源模板，在隔离库开启 `wal_compression=pglz`，总 WAL 阈值为 48 MiB/s，事务上限为
500 次/秒。预算随观测降至 3,757 行/秒。账单和用量在 **8 分 12 秒** 内完成联合发布，来源行数均为
1,574,210，账单净额为 157,421,000 配额单位。前 8 分钟内 9,600 次 HTTP 和日志提交均成功，HTTP
P95/P99 为 39.16/152.21 ms，日志提交为 28.94/132.03 ms，采样窗 WAL 约 4,495.9 MiB。
同一模板和 WAL 配置停用日报，另取 40 秒对照窗。同样每秒约 20 次，800 次 HTTP 和日志提交均成功，
HTTP P95/P99 为 9.48/16.73 ms，日志提交为 5.01/10.98 ms。两组窗口长度不同，这轮仍明确显示
该共享数据库配置下大流量日报完成时伴有明显的业务和日志尾延迟回退。可执行性验证通过，启用验收未通过。
生产上按业务优先保持默认停用，目标环境若无法同时通过 §3.4 的两项门槛，应在隔离报表资源后再复验。
