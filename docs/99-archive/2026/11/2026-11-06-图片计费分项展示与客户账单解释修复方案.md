# 图片计费分项展示与客户账单解释修复方案

当前工作状态：用户已明确恢复代码修复，要求核对线上价格，正确则复用。最新价格核对、修复及部署
边界见第 11—13 节；尚未部署生产。第 6—12 节保留此前实施、暂停、浏览器验收及分类方案的阶段记录，
其中“暂停”“待修”和仅合成样本验收的描述，以第 13 节最新结果为准。

## 1. 问题与目标

客户根据模型详情卡片与图片消费日志，无法直观看出文本输入是否收费、图片输入是否独立收费，以及
缓存价格为何在不同区域显示不一致。原展示修复阶段不调整计费表达式、历史扣费、渠道路由或缓存策略；
第 10 节另列价格配置与旧程序限制的待评审处理方案。本文件同时记录方案与本地实施结果；前一轮本地
修复已完成；补充实施已恢复，尚未部署或完成线上验收。

验收目标：

- 客户能区分价格表、实际计费用量与本笔分项金额，明确文本输入已计入总费用。
- 图片分项金额只使用该次请求冻结的表达式、实际计费用量与折扣事实；缺少证据时明确不可展开。
- 无缓存用量、上游未报告缓存计量和接口不支持缓存保持不同含义，不承诺客户必然获得缓存优惠。
- 价格卡片与日志的缓存展示采用一致规则，中英文均可理解。

权威合同仍见[计费表达式语言](../../pkg/billingexpr/expr.md)、
[计费表达式与协议探针架构](../20-architecture/账单计费-计费表达式与协议探针架构.md)及
[用户模型合同定价架构](../20-architecture/账单计费-用户模型合同定价架构.md)。本方案不另建计费引擎。

## 2. 当前实际情况

### 2.1 用户提供的线上样本

用户提供了一笔 `/v1/images/generations` 日志及模型详情截图。样本显示动态计费、命中 `base`、
分组倍率和合同折扣均为 1。以下数值来自用户提供内容，尚未直接查询线上数据库或原始 usage：

| 项目 | 计费用量 | 单价（USD / 百万 Token） | 复算金额（USD） |
| --- | ---: | ---: | ---: |
| 文本输入 | 76 | 5 | 0.00038 |
| 图片输入 | 0 | 8 | 0 |
| 图片输出 | 1372 | 30 | 0.04116 |
| 合计 | — | — | 0.04154 |

复算与该日志总费用一致，说明这笔账单包含文本费用；不能由一个无参考图、无缓存的样本证明所有图片
输入或缓存分支正确。其余线上五笔复算、24 份回执及大批量统计属于用户转述，未独立核验。

截图已经列出五项价格：输入 5、输出 30、缓存读取 1.25、图片缓存 2、图像输入 8。问题是通用
“输入/输出”名称缺少场景解释，不是该截图漏掉文本单价。

此前本地 `one-api.db` 只读核查显示三款 GPT Image 2/2.5 模型保留旧倍率配置且未显式启用表达式；
本次用户提供的线上日志明确使用动态计费。两者不能继续视为同一份生效配置，必须分别核实版本、
当前配置与该笔冻结价格；本方案不迁移或覆盖任一环境的配置。

### 2.2 实施前本地代码证据

| 问题/行为 | 证据入口 | 判断 |
| --- | --- | --- |
| `p/c` 采用通用“输入/输出”名称 | `web/src/features/pricing/lib/billing-expr.ts` 的 `BILLING_VARS` | 价格语义不清晰，不能直接把通用变量全局改名为文本/图片 |
| 图片输入单独定价时从 `p` 排除 | `service/tiered_settle.go` 的 `BuildTieredTokenParams` | 输入分类已有计费逻辑，本方案复用而不重写 |
| 日志保存实际计费用量 | `service/log_info_generate.go` 的 `InjectTieredBillingInfo`、`pkg/billingexpr/settle.go` | `billing_tokens` 保存 `p/c/img/img_cr/img_o` 等；字段出现不代表每项都参与收费 |
| 图片表达式无法展开逐项金额 | `service/customer_billing_explanation.go` 的 `customerBillingLines` | 普通 Token 表达式引用 `img/img_o/ai/ao` 即返回空行，未利用已有 `billing_tokens` |
| 空金额明细退化为单价展示 | `web/src/features/usage-logs/components/dialogs/details-dialog.tsx` 的 `BillingBreakdown` | 前端已有分项金额渲染能力，优先补齐后端证据读取 |
| 缓存摘要与表格过滤不一致 | `web/src/features/usage-logs/lib/format.ts` 的 `getTieredBillingSummary`；`web/src/features/pricing/components/token-billing-breakdown.tsx` | 摘要无缓存时隐藏缓存组；表格只隐藏 `cr/cc/cc1h`，遗漏 `img_cr` |

`c` 与 `img_o` 都显示 1372 不等于重复收费。只有冻结表达式实际引用的项才参与费用；如果只引用
`c * 30`，不得再额外把 `img_o` 加入小计。`c` 本身是未单独计价的输出，不能无条件解释为纯图片。

### 2.3 外部证据与结论边界

核查日期为 2026-11-06：

- [OpenAI 官方图片文档](https://developers.openai.com/api/docs/guides/image-generation#cached-input-pricing)
  明确 GPT Image 2/2.5 缓存输入优惠适用于 Responses 图片工具，不适用于直接 Images 请求；图片工具
  缓存计量也不在 Responses 输出中公开。该证据不能直接替代 Azure 对具体部署的承诺。
- [Azure 通用缓存说明](https://learn.microsoft.com/en-us/azure/foundry/openai/how-to/prompt-caching#in-memory-prompt-cache-retention)
  将适用操作限定为 chat-completion、completion、responses、real-time，不能据“支持图片缓存”
  推导 Images 生成接口会报告缓存。
- [Azure Images 规范](https://learn.microsoft.com/en-us/azure/foundry/reference/rest/images-create-image)
  未定义缓存模态明细，但仍保留部分旧 usage 描述。字段未定义、样本未出现、实际没有缓存命中、
  供应商没有缓存优惠，是四种不同结论。

当前本地解析测试已验证标准位置的缓存字段能经过 JSON、SSE 和 Task 路径保留，区分缺失、零值与
正值，并保留图片缓存明细；合成测试不能证明 Azure 实际返回这些字段。重复请求两次也不能保证命中
或保证响应出现缓存字段。不得将“没有拿到计量”写成“客户没有多付钱”或“客户一定应得缓存折扣”。

## 3. 优化方案

### 3.1 先取得线上最小证据

由线上操作方只读提供脱敏核查结果：

1. 部署代码版本和前后端构建版本，实际数据源与运行时配置是否一致；不输出连接凭据。
2. 指定样本的 `expr_b64` 解码结果、`matched_tier`、`billing_unit`、`billing_tokens`、组倍率及合同
   事实；当前模型配置与历史冻结事实分别记录。
3. 日志查询响应中的 `billing_display`、`billing_explanation.lines` 及不可用原因；确认是否命中本地
   所述的空明细路径。
4. 经既有单条授权取证入口检查该笔 usage 的输入/输出分类、缓存字段是否存在；只输出脱敏计量摘要，
   不输出原始 Provider 响应、媒体、签名 URL 或请求正文。
5. 追加一笔 `img > 0` 的已有日志，核对 `p` 已排除单独计价图片、分项与总额能对账。缓存有真实
   正样本则核对，无样本写“未验证”，不以全零代替验收。
6. 供应商缓存优惠适用性单独由 Azure 计费计量记录或 Microsoft 针对模型、入口、API 版本的答复
   确认，不通过网关零值统计推断供应商成本。

证据不足不阻碍已确认的展示修复，但限制对线上根因和供应商费用的结论。

### 3.2 价格与用量名称

- 保留通用变量合同：`p/c` 默认解释为“未单独计价的输入/输出”。依据已存在的明确图片入口事实及
  冻结用量分类，在图片日志中补充文本/图片解释，不从模型名、价格或数值猜测模态。
- 公共模型卡片可能同时覆盖多个入口：有现成明确协议证据时展示对应场景说明；证据不足时保留
  “输入/输出”并解释其兜底语义，不声称 `c` 必然是图片输出。
- 图片场景向客户明确展示“文本输入、图片输入、图片输出”的适用关系。缓存注明按上游实际提供的
  计量结算；计量未报告时显示“上游未报告”，明确这是状态说明而非新的 Token 数量。
- 仅维护 `zh/en`；实际改文案前读取项目 i18n 技能，复用现有标签、价格组件与单位格式化工具。

### 3.3 补齐冻结事实驱动的逐项金额

- 在既有 `customerBillingLines` 中增加极窄接线，图片等多模态分项验证与取值优先放入独立新增文件。
  复用现有表达式价格投影和金额对账流程，不增加另一套解析器、计费求值或价格缓存。
- 读取该笔已保存的 `billing_tokens`；仅使用命中价格分支实际引用的变量。验证所需字段存在、有限、
  非负，并与该笔冻结计费/计算事实一致，不能把缺失字段补成 0。
- 复用现有组倍率、合同折扣、附加费用和舍入处理，明确逐项是折前模型费还是折后金额。计费用量、
  模型费、附加费用、最终扣费分别解释，不把逐项浮点和当作账本权威。
- 对本样本应能输出 `76 × 5 / 1000000 = 0.00038`、`1372 × 30 / 1000000 = 0.04116`，
  合计与已记录费用一致。零用量可显示 0，但必须已有明确计量事实。
- 若历史 `billing_tokens` 缺失、不完整、冲突，或公式无法精确投影，保留历史已扣金额并明确“分项
  费用证据不足”。不得用当前模型配置、当前折扣或重新执行表达式来重算历史费用。
- 前端复用已有 `billing_explanation.lines` 渲染；证据不足时说明原因，不把空明细伪装成不存在费用。

### 3.4 统一缓存价格展示

- 价格表展示表达式定义的价格；本笔用量与费用展示实际发生的计量。价格存在和本笔命中不能互相替代。
- 日志摘要和档位表统一保留冻结表达式中的全部缓存价格，包括显式零价；移除“按本笔缓存数量隐藏
  已配置价格”的过滤差异，不再遗漏或单独特判 `img_cr`。
- 本笔缓存用量旁单独显示已报告为 0、未报告或未验证状态。旧日志缺少存在性证据时显示未记录，
  不伪造缺失或命中结论；不为此改动实际计费逻辑。

### 3.5 最小改动与上游同步影响

优先修改本地账单解释新增文件及现有展示组件的小范围分支。预计必要接线点为
`service/customer_billing_explanation.go` 的多模态解释分派、现有价格标签/说明及日志价格过滤。
实施前核对这些文件的上游归属；原生文件如确需修改，只保留必要调用/分支，不整理结构或全局改名，
在变更说明中记录原生接线必要性与未来合并冲突点。展示修复不得侵入请求选渠、预扣、结算或退款热路径。

## 4. 验证与交付

| 边界 | 必须保护的行为 |
| --- | --- |
| 后端逐项费用 | 本文样本精确复算；参考图独立计价；`c/img_o` 不重复相加；图片缓存交集不重复计算 |
| 历史与异常证据 | 字段缺失、非法数值、价格分支不明、用量冲突或金额对账失败时不输出伪造明细，不修改扣费 |
| 折扣与单位 | 冻结组倍率/合同事实、显式零价、舍入和附加费用；Token 单位不误成按张/按次 |
| 页面可理解性 | 卡片与日志显示对应价格；逐项金额与总额易于核对；缓存价格过滤一致；中文与英文验收 |
| 回归范围 | 普通文本、显式图片输出变量、通用兜底输出及历史未知模态，不被图片场景说明改义 |

实施测试必须使用项目真实说明生成与组件链路，禁止通过复制生产算法来证明自身正确。
后端新增/大改测试使用 testify；前端通过 `bun run test` 运行定向 Vitest，再执行 typecheck、
涉及文件 lint 与构建。若实际改动 `relaykit/` 或其公开 API，额外执行独立模块构建。

本地实施与验证结果见第 6 节。文档检查执行 `task docs:check` 与 `task ai:check`；公开 API 文档未修改。
Azure 供应商账单核验、生产部署与真实页面验收均待执行。

## 5. 实施顺序与非本轮范围

1. 收集第 3.1 节线上脱敏证据，锁定线上版本及分项为空的实际原因。
2. 修复后端分项解释与缺失证据提示，完成定向回归。
3. 补充场景名称说明并统一缓存价格展示，完成中英文页面验收。
4. 用现有线上账单在部署后只读核对，保留无法验证的缓存项说明。

本轮不修改模型生效价格、不自动迁移旧倍率、不切换 Azure 请求入口、不发起付费缓存实验、不追补或
重算历史扣费，不承诺 Azure 缓存可用性。未来如需改变价格或调用协议，另行明确目标与验收证据。


## 6. 本地实施与验证结果

### 6.1 已完成

- 新增 `service/customer_billing_token_quantities.go`，读取已记录的实际计费 Token，校验有限、非负、
  整数与单项容量，并按冻结表达式的归一变量集合核对输入/输出总量；沿用原有单价投影、分项金额、
  折扣与扣费对账。字段缺失、总量冲突或与扣费不符时不生成完整费用解释。
- 依据明确的 Images 请求路径和已保存模态事实，在能够证明时将费用行标为文本输入、图片输出。
  通用模型卡片保留通用标签并增加共享说明，不依赖模型名或价格推断模态。Anthropic 独立缓存语义
  未扩展到新增冻结多模态说明分支，保持证据不足时不可展开。
- 日志已有逐项金额组件现可展示图片费用说明；无可用说明时显示账单证据无法核实的提示，保留原扣费。
- 取消日志价格摘要和档位表按本笔缓存数量过滤价格的逻辑，并删除已无调用方的隐藏缓存列参数，完整
  显示投影中的缓存价格，包含显式零价。
- 在用量区区分缓存“上游已报告 / 上游未报告 / 未记录”；未新增 Provider 能力推断。这个状态对应
  已有总缓存计量存在性标记，不证明图片缓存模态明细存在，更不证明供应商应提供缓存优惠。
- 共享说明组件复用于模型卡片和 Token 账单，解释通用输入/输出、图片分项与缓存优惠限制；中文、
  英文各新增 6 个键，经脚本写入并执行 `bun run i18n:sync --locales en,zh`，其他语言未修改。

### 6.2 最小接线与同步影响

- 原有 `service/customer_billing_explanation.go` 只增加冻结用量分派分支、图片缓存标签及缺失事实
  拒绝范围；校验主体与新增回归测试独立放入新增文件。该接线必要性是复用唯一的客户费用解释入口，
  不另建平行账单解释流程。未来同步冲突集中于分派位置与标签表，未修改资金或 Provider 热路径。
- 模型详情组件仅增加共享说明的 import 与一次渲染；日志详情组件复用现有 `DetailRow`、
  `DetailSection` 和逐项金额渲染，增加证据状态及不可展开提示。价格过滤修改限于原有相关分支；
  不重排或格式化整份原生文件。未来上游同步须检查这些展示接线与已删除的缓存过滤参数。
- 新增前端组件不引入依赖、数据请求、缓存、持久状态或路由；所有账单说明只改变查询响应/页面展示，
  未写数据库、未切换模式/渠道、未重算历史扣费、未发送付费请求，也未修改 `relaykit/`。

### 6.3 本地验证

  折扣、缺失/非法/冲突用量及扣费不符、单独图片输出与其余输出不重复相加。

- 前端相关日志组件、用量解释、价格组件与价格汇总测试：38 个文件、457 个用例通过，包含无缓存
  用量时保留全部价格及显式零价、三种缓存报告状态、逐项金额和中英文说明。
- `bun run typecheck`、涉及文件 oxlint、`bun run build`：通过；构建同时通过公开文档与品牌产物检查。
