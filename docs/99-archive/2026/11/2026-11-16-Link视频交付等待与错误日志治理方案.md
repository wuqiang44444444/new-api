# Link 视频交付等待与错误日志治理方案

## 1. 问题与目标

API Key 客户已经通过 `/v1/videos/{task_id}/content` 查询视频结果，并解析文件准备期间返回的
`409 video_delivery_preparing` JSON。生成成功到文件可下载之间的等待是正常交付过程，当前错误面板却将
这类查询记为 `unclassified`，使运维难以从正常轮询中发现真正的故障。

本期治理 Link 托管视频的 `GET/HEAD /v1/videos/{task_id}/content` 日志采集。客户沿用原接口、HTTP 状态
和 JSON 解析逻辑，无需改代码。正常等待只记访问日志，实际交付故障仍进错误日志。

## 2. 当前实际情况

- Link 的生成状态与文件交付状态来自不同事实。生成成功后，后台领取结果部件、读取文件、转存私有对象
  存储并提交 `ready`。此后 `/content` 返回签名下载地址。
  见[托管交付架构](../../../20-architecture/Link视频结果OSS托管交付架构.md#5-公共交付状态合同)。
- 下载入口对尚未生成成功的任务返回 `400 video_not_ready`。对已生成且交付等待的部件返回
  `409 video_delivery_preparing`，就绪返回 `302`。终态不可用返回 `410`，就绪对象签名失败返回 `503`，
  读取交付记录失败返回 `500`。见[Link 内容入口](../../../../controller/video_proxy_link.go)、
  [交付响应](../../../../controller/video_result_delivery.go)和[公开 API 文档](../../../../web/public/docs-content/zh/api-reference/videos/modelark.md#下载视频或末帧)。
- 统一采集依据鉴权标记与最终 HTTP 状态，将 relay 的 `4xx/5xx` 写入 `error_events`，并为已鉴权 `4xx`
  写 WARN。交付等待分支没有单独分类，因此进入面板时显示为 `unclassified`。日报从既有错误事件汇总。
  见[采集实现](../../../../clienterrlog/recorder.go)、[视频诊断](../../../../controller/video_modelark_diagnostics.go)
  和[错误日报架构](../../../20-architecture/运维-系统错误报告架构.md)。
- 用户提供的线上时间线显示任务成功后曾返回 `409`，随后下载请求返回 `302`，与交付准备过程一致。
  面板样本只有 HTTP 状态，逐条归因仍需核对结构化错误码。样本中的等待时长仅用于排查，交付时限待评估。
  本次依据仓库代码与用户提供的样本拟定，线上未访问或修改。

## 3. 优化方案

### 3.1 客户继续使用 `/content`

客户继续使用现有 API Key 和任务 ID 请求 `/v1/videos/{task_id}/content`。

| 客户查询时的情况 | 客户收到的现有响应 |
| --- | --- |
| 视频已生成，文件正在准备 | `GET` 原样返回 `409` 和原有 JSON，保留 `error.code=video_delivery_preparing`、`error.message` 和 `error.request_id`；`HEAD` 仍返回 `409`，无响应体 |
| 文件已就绪 | `302`，签名下载地址仍通过 `Location` 返回 |
| 交付记录查询失败、签名失败或文件不可交付 | 沿用对应的 `500`、`503` 或 `410` 和原有响应 |

客户现有的请求、JSON 解析和重试逻辑可直接沿用。

### 3.2 错误采集与故障归因

1. **在 Link 交付分支明确标记正常等待。** 已鉴权且生成成功的任务，所请求部件处于待转存、转存中或补扫
   窗口内待登记时，在返回 `409 video_delivery_preparing` 前给当前请求附加结构化标记。在统一采集出口，
   仅当路由、最终状态和该标记吻合时跳过 WARN 和 `error_events`。访问日志继续保留原 HTTP 状态和请求 ID。
   其他 `409` 及真实限流 `429` 沿用既有采集。历史记录沿用原有留存策略。
   `400 video_not_ready` 分支当前覆盖所有非成功任务，包含正常生成和失败终态。本期先落地已能准确识别的
   交付等待，后续如要治理生成期下载请求，应按已确认的任务状态区分，避免一起过滤失败终态。
2. **在故障发生点保留诊断。** `/content` 的交付记录读取失败、签名失败继续产生 `500/503` 错误事件，
   并附交付阶段和受控原因码。明确的存储故障与真实 Provider 读取失败按各自来源记录，即使客户这次
   查询仍看到 `409 video_delivery_preparing`，运维也能查到后台故障。Azure 上传在通用脱敏和存储错误
   记录前保留读流故障的类型。
3. **由后台报告交付失败。** 转存重试耗尽或确认不可交付时，以 `unavailable` 的持久状态转换为依据，按
   任务与部件登记一条待写诊断，与终态转换同事务提交。客户主动删除只关闭交付。后台独立重试写入
   错误日志，持久事件身份用于写入成功但确认丢失时去重。日志库慢请求期间主库无需持有事务。
   下载返回的 `410` 仍可追查具体访问，主动故障统计按任务与部件去重。补扫窗口外的历史缺口单独识别，
   以免访问历史结果时被计为本次转存失败。
4. **观察一直未就绪的任务。** 主节点在独立后台循环检查转存积压和补扫窗口内的登记缺口，使用独立探测
   对象，图片就绪探测及 CPU、内存、磁盘告警沿用各自循环。存储故障事件与待写诊断同事务提交。
   存储不可用可能令转存调度停用，因此健康观察需覆盖调度停止期间。先在目标环境测量队列和转存耗时，
   再确定滞留告警阈值。告警依据真实滞留状态，客户轮询次数不参与判定。

采集变化位于 Link 内容入口、后台交付和本地错误采集出口。交付状态继续以现有任务及对象登记为事实源，
沿用授权、签名和计费合同。诊断使用公开任务 ID、请求 ID、部件与受控原因码等允许字段，遵守
[安全与数据硬约束](../../../00-context/硬约束.md#6-安全与数据)。

### 3.3 验收与待办

| 验收场景 | 预期结果 |
| --- | --- |
| 用客户现有请求和解析逻辑反复查询待转存、转存中和窗口内待登记的结果 | `GET` 的 `409` 和 JSON 原样返回，现有解析和重试照常工作；`HEAD` 保持原有 `409` 和空响应体；每次等待只记访问日志 |
| 用同一 `/content` 请求查询已就绪的结果 | 从准备中的 `409` 转为就绪后的 `302`，`Location` 可用于下载；尾帧按独立状态处理 |
| 其他 `409`、真实 `429`、未确认生成成功时的 `400 video_not_ready` | 本次窄规则保持既有响应与采集行为 |
| 交付记录读取失败或签名失败 | `/content` 保留 `500/503` 及对应错误事件 |
| 无客户端查询时转存重试耗尽，或永久失败后并发重跑 | 后台仍可发现故障；同一任务与部件只计一次持久终态；生成状态和资金事实保持不变 |
| 日志库不可用后恢复，或写入成功后主库确认失败 | 待写记录保留并在后续领取中补录，面板最终只有一条故障 |
| Azure 和 S3 转存时 Provider 读流中断，或视频存储探测变慢、失败 | 读流故障保留上游来源；视频探测无需占用图片就绪探测或资源告警循环 |
| 存储故障导致调度停用、旧历史缺口及无权限访问 | 即使客户查询仍返回 `409`，存储故障也有独立错误记录；历史缺口可区分；无授权请求不得取得下载地址 |

## 4. 本地实施与验证

- 已通过 `/content` 路由测试核对等待中的 `409` 与原 JSON、就绪后的 `302`、签名失败的 `503` 和交付查询
  失败的 `500`。日志采集测试覆盖同路由无标记的 `409`、其他路由的 `409` 和真正的 `429`。
- 已在隔离 SQLite 与模拟存储中验证转存失败只由终态提交成功的一方登记，生成状态和费用保持原值。
  已验证独立日志库恢复后可补录、确认丢失后写入去重，以及仅有登记缺口或结果退避时的存储故障去重和恢复。
- 已用本地模拟 Azure 和 S3 覆盖上游断流类型，以及视频探测阻塞和失败时图片就绪检测继续工作。
- 已在隔离容器中验证 PostgreSQL 15 和 MySQL 5.7 同库写入，以及 PostgreSQL 15 主库搭配 ClickHouse 25.8
  日志库时的迁移、状态提交、确认丢失后补录与去重。
- 错误面板和错误日报已提供「视频交付故障」分类。转存任务结果提供积压数量和当轮最大交付耗时，可用于
  目标环境评估滞留阈值。线上样本核对、真实存储验收和滞留阈值评估待完成。
- 已将本地实现同步到[托管交付架构](../../../20-architecture/Link视频结果OSS托管交付架构.md)和
  [错误日志架构](../../../20-architecture/运维-API错误日志架构.md)。线上环境未访问、未部署。
- 主库迁移入口仅登记待写错误事件表，启动入口仅从主节点启动独立视频监控与补录循环。同步上游时保留
  这两个接线点即可，现有请求入口和资源告警循环沿用原实现。

## 5. 本地真实渠道验收（2026-11-16）

从本机开发库只读载入启用的 Vidu #140 渠道和模型配置，用当前构建、独立 PostgreSQL 主库和日志库、
独立测试 API Key 发起一次真实生成。客户模型为 `seedance-2-0-mini-v`，纯文本，4 秒、480p、16:9，
关闭音频。Azure 对象存储使用本机 HTTP 模拟端点。下表的故障由隔离环境注入，真实 Provider 只收到一次
生成提交。

| 验收场景 | 实测结果 |
| --- | --- |
| 真实 Provider 提交与生成 | 创建返回 HTTP `200`，任务从 `queued`、`running` 到 `succeeded` |
| `/content` 准备中 | 两次 GET 的 `409` 与原 JSON 字段和文案一致，HEAD 返回 `409` 且响应体为空。三次请求均可在访问日志按请求 ID 查到，错误日志为零。非法部件请求返回 `400` 并正常入错误日志 |
| 仅有登记缺口且存储禁用 | 对象登记为零，后台仍发现一个存储故障。日志表不可用期间，主库保留一条待写事件 |
| 日志恢复与确认丢失 | 恢复日志表后补录一条事件。人为阻断主库确认再解除，重试后错误事件仍为一条，待写记录清空 |
| 真实成片交付及存储恢复 | `/content` 的 GET、HEAD 均返回 `302`。本机存储下载、HEAD 分别返回 `200`，Range 返回 `206`。成片为 864 × 496、4.042 秒，通过完整视频解码；存储故障事件关闭 |
| Azure 转存遇到上游读流中断 | 隔离库中的同一任务进入最后一次转存，并读取本机提前断开的 HTTP 流。持久诊断保留读流错误标记，错误日志记录一条 `video_delivery_source`，`/content` 返回 `410`，原任务状态和配额不变 |

同轮定向测试通过，覆盖 S3 和 Azure 读流中断、视频探测阻塞及失败时的图片就绪检查、资源告警，以及登记
缺口与补录回归。隔离网关已停止，两个测试库已清理，原本机网关进程保持运行。真实 Azure 云存储及生产
环境验收仍待完成。
