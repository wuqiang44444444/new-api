# 客户账单明细自适应导出与验收方案

## 1. 问题与目标

大客户整月账单明细包含数百万条入账事件。现有后台任务支持暂停、续跑和分片交付，固定限速却让
资源充足时的导出也要等待很久。明细导出使用频率低，任务应按当时可用资源调速。资源充足时提速，
业务压力上升时降速，持续受压时暂停。资源恢复后从已提交分片继续，并逐步恢复处理速度。

以 `yuanli` 的冻结账单为验收样本。目标是在健康窗口内 **10 分钟可下载**，同时验证业务高峰时可以
主动退让，资源恢复后可以继续推进。8 小时属于用户对等待体验的判断。已观测的耗时和验收范围见下文。

业务请求、结算、退款和日志写入优先。导出沿用提交时冻结的账单版本及筛选条件，保留逐笔金额、退款符号、
覆盖日期和阶段性截止时间。

## 2. 改造前的运行情况

- 当前默认限速为 **750 行/秒**，可配置上限为 **2,000 行/秒**。按 4,927,997 行估算，仅读取和生成
  的限速下界分别约为 **110 分钟**和 **41 分钟**，上传与暂停时间另外计入。
- 这笔账单已在本地 PostgreSQL 恢复库跑完全量。验收使用隔离测试执行策略和本地文件存储。读取、生成
  **99 个 CSV 分片**、校验并导入 SQLite 合计约 **3 分钟**，总文件约 **2.45 GB**。导入的行数、扣款、
  退款和净额与冻结来源一致。测试还验证了压力暂停、租约过期恢复和分片续跑，范围是受理时冻结的
  18 个日报版本。该结果用于证明全量可交付和估计提速空间。
- 现有任务沿用独立读取连接、批次超时和容量许可。资源退让和正常执行窗口结束目前都依赖周期发现重新
  调度。生产对象存储吞吐、目标环境稳定速率及高峰期间的核心业务影响，仍待对照验证。

## 3. 优化方案

### 3.1 与日报共用前台观测和准入

导出接入日报方案的应用内前台观测与准入组件。共用组件是后台工作的唯一前台压力判断入口，负责采样、
健康窗口和退让判定。优先复用现有前台指标，观察请求量和在途量、错误与超时、核心 API 尾延迟、结算和
日志写入延迟，以及主库和日志库的共享压力。窗口长度、信号有效期、健康与降档门槛随共用组件统一维护。
采样在现有边界聚合，前台请求路径保持原有 SQL、事务和持久性。

多节点部署通过现有跨节点观测和共享库指标判断受影响资源。单节点样本只用于本地资源，必须能确认共享
余量后才进入快档。低样本窗口参考在途量、慢样本数和短探测，监测失效时暂停新批次。日报与导出同时访问
同一资源时，在共用准入中考虑两者的合计开销。日报执行器管理写入和 WAL 成本，导出执行器管理报表查询、
解码、CSV 生成和上传成本。

保持单个明细导出 worker，从现有主库的独立单连接池以短只读事务读取，检查冻结发布版本完整可见。按
查询耗时、查询取消和实测读取量判断主库余量。将 worker 的 CPU、内存、磁盘、网络和上传耗时作为导出
自身的资源边界。快档影响核心业务时，调整自动降速和暂停策略，并在同一单库拓扑复测。

本次实现通过既有节点心跳交换前台计数，日报与导出共用数据库批次租约。同一时刻仅放行一个后台数据库
批次。主库提供冻结逐笔数据，同时持久化分片检查点和挂起状态。导出放行还需要冻结发布版本可读和
本地分片所需的临时空间。目标环境验收记录共库争用和上传带宽。

实施时随共用准入移除导出对 `DAILY_REPORT_CAPACITY_FILE` 的依赖，并删除
`CUSTOMER_STATEMENT_EXPORT_ROWS_PER_SECOND` 的读取、示例和运维说明。运行时根据观测自动调速，
小批起步、调整步长和安全边界在代码中维护，按发布前实测校准。每日运营无需维护任何导出速率、压力阈值或
许可文件。导出复用既有主库及对象存储配置。

### 3.2 提速、降速与暂停续跑

优先调整批间隔，以批次实际耗时和字节量估算下一批成本。单批保留短期限和工作量上限。每个任务固定
分片行数、字节上限和编号方式，调速只改变处理节奏。空闲期间的预算按当前余量重新计算。

| 状态 | 触发条件 | 动作 |
| --- | --- | --- |
| 启动或接管 | 新任务、worker 更换，或上次观测已过期 | 从最小已验证工作批起步。取得可信的健康观测后才允许提速。 |
| 提速 | 连续健康窗口内，前台和导出侧均有余量 | 逐档缩短批间隔。每次升档后观察一个完整窗口，再决定下一档。 |
| 降速 | 共用准入检测到前台压力抬升且尚有余量，或导出侧接近资源边界 | 从下一批降低速率，直到压力稳定。连续健康后再升档。 |
| 暂停 | 前台越线、关键观测失效、最小工作批仍受压，或冻结版本暂不可读 | 停开新批，正在执行的读取和上传按短期限结束或取消。释放执行租约和读取连接，保留任务、冻结版本及已提交检查点。 |
| 恢复 | 共用准入重新给出连续健康窗口，且冻结版本仍完整可读 | 从已提交分片后的游标以保守档续跑，随后自动逐档提速。 |

正常执行窗口结束时立即重新调度，按现有队列公平规则领取下一轮工作。压力暂停由共用准入恢复触发，
周期发现负责补偿通知丢失。重复短低谷时检查每个健康窗口是否有持久进度，并用固定分片边界校准每段
工作量。已登记但未提交的分片按原行数和校验值重建，检查点继续只在上传成功后提交。

本次实现从每秒 1,000 行起步。每三个连续健康采样提速约 25%，上限为每秒 16,000 行。新降速观测将
当前速率减半，暂停后从保守档恢复。每批按当前速率缩小或放大读取量，上限为 1,000 行、两秒，固定分片
上限为 50,000 行、100 MiB。定期采集前台基线期间保留当前速度和分片上下文，采集结束后继续读取。
有额外筛选条件时，先从索引定位候选窗口，再在该窗口内匹配和读取明细。整窗没有匹配行时只保存游标，
这样稀疏筛选也能在下次执行时从已读位置继续。

展示已提交行数、分片数、等待原因和最后推进时间。已有可信总数时显示百分比。连续健康窗口内停滞时
记录无进展原因，并通过已有运维观测暴露积压和重复恢复情况。全部分片核验成功后开放下载，相同冻结
版本已有可用文件时沿用现有复用规则。

### 3.3 十分钟目标与耗时预算

**10 分钟目标适用于 `yuanli` 的 4,927,997 行、18 个冻结日报版本、约 2.45 GB 的首次生成任务。**
验收时只运行这一笔明细导出，冻结版本完整可见，共用准入在整个窗口持续确认健康且未触发压力暂停。
从受理成功计时到全部分片可下载，计入排队、读取、CSV 生成、上传、正常窗口交接和发布。分片导入作为
交付后的准确性验收，单独记录耗时。更多日期、更大体积和高峰暂停场景分别测量。高峰场景同时记录完整
墙钟耗时和实际等待时长。

以 **12,000–15,000 行/秒**作为测量候选区间。本样本的读取和生成约需 **5.5–6.9 分钟**，若保持
串行上传，剩余时间对应约 **9–13 MB/s** 的最低平均上传吞吐，实际还要扣除交接和发布。按阶段实测后
再决定是否让生成与上传重叠。记录完整路径的每档速率、物理读取量、查询和编码耗时、出网吞吐及交接
时间。上线目标数据库测量首批、中段、尾批和稀疏条件的执行计划，跨库回归覆盖 SQLite、MySQL 和 PostgreSQL。

### 3.4 验收通过标准

1. **峰值对照。** 使用同一数据快照、请求模型与类型分布、固定输入速率及等长采样窗。保持日报等其他
   后台任务的配置一致，并覆盖与日报同时运行的情况。先做重复的关闭组对照，量出停用组自身波动，
   测试前锁定各指标的允许差值和现有业务目标线，随后至少做三轮交替开关导出的配对对照。核心 API
   吞吐、P95/P99、错误率，以及结算和日志写入的成功率和耗时，每轮开启组均须在预定差值和业务目标线
   以内。样本不足的窗口延长采样。结算和日志核查还须确认逐笔语义、提交成功与可恢复性一致。
2. **调速和恢复。** 覆盖健康、流量抬升、持续受压、观测失效和恢复。压力上升后下一批降速；达到暂停
   条件后停开新批，在已验证的取消与超时边界内释放读取和上传资源。恢复后在同一冻结任务上续跑，
   重新提速前须重新取得健康观测。重复短暂停顿、上传后提交进度前中断、跨 worker 接管及恢复后变速
   均须通过检查点对账。健康窗口完整跑一次，受理到可下载不超过 **10 分钟**。
3. **全量对账。** 从同一冻结版本、同一筛选范围独立取得预期行数和资金汇总。下载并导入全部分片，
   校验每片的 SHA-256、行数和分片顺序，并以冻结来源事件身份核对全量无重复、无遗漏。扣款、退款和
   净额先按原始结算单位精确核对，再按冻结换算和逐行八位小数口径核对导入金额。缺失日期和阶段性
   截止时间应与受理时的覆盖范围一致。本样本退款为零，另用非零退款用例验证暂停续跑后的退款符号和金额。

先验证单库连接池、共用准入和调速续跑，再做峰值对照和全量账单验收。任一核心
指标越线时自动停止新批，保留对照证据。所有通过标准满足后再进入上线步骤，并随实施更新导出架构及运维文档。

## 4. 本地验收记录

使用 `yuanli` 的原失败任务所引用的 18 个冻结版本。任务库与只读报表源分别连接两个本地 PostgreSQL
实例，分片通过应用的 S3 写入路径上传到隔离的 S3 兼容存储。

- 修复 S3 签名查询参数中空格的编码后，从新任务受理到全部分片发布、首个签名下载收到 HTTP 200 用时
  **7 分 55.271 秒**。共 **99 个 CSV 分片**、**4,927,997 行**、**2,446,902,946 字节**。账单范围保持冻结，
  缺失日仍为 11 月 8 日至 10 日。
- 全量签名下载、逐片 SHA-256 校验及金额投影导入用时 **13.630 秒**。原始结算单位的扣款、退款、净额为
  **161,795,822,190 / 0 / 161,795,822,190**。导入金额为 **323,591.64438000 / 0.00000000 /
  323,591.64438000 USD**。
- 独立逐行对账和全字段导入用时 **46.585 秒**。按冻结来源的 `source_id` 排序，对比 CSV 的请求 ID、入账
  时间、事件类型和金额，用来源 ID 作为导入表主键。全部 **4,927,997 行** 匹配，未发现重复或遗漏。
- 复测时模拟准入观测不可用后 **5.031 秒** 内暂停，保留已提交的 50,000 行。观测恢复后 **31.761 秒** 内，
  原任务续跑到 100,000 行。原分片和冻结范围保持一致。非零退款、上传后提交前中断及租约接管另有回归覆盖。
- PostgreSQL 首批、中段、尾批的查询执行约 **4.2 / 6.5 / 2.7 毫秒**，均使用分版本索引归并。无匹配的
  稀疏请求 ID 原查询触发两秒期限，改用候选窗口后本次抽样耗时 **8.91 + 3.63 毫秒**。另用小样本完成
  PostgreSQL、MySQL 与 SQLite 的筛选、跨页和游标恢复验证。
- 本地峰值回放使用 32 个测试钱包，每窗 **2,111 个请求**，平时 34 请求/秒，单秒冲高至 105。HTTP 测试
  入口调用真实的钱包结算和日志持久化。三次关闭组校准后锁定 API P95、API P99、结算 P99、日志 P99 的
  允许增量为 **7.394 / 40.666 / 21.063 / 21.639 毫秒**。第一轮版本通过 **1/3** 个开关对照。两组超线，
  其中第二组的 API P99 由 28.298 升至 156.225 毫秒，结算 P99 由 19.252 升至 108.961 毫秒。全程零错误，
  18,999 笔钱包扣款与提交日志的笔数和额度一致。随后在共用准入中补入请求和结算的尾延迟反馈。

沿用锁定阈值复测，六个窗口共 12,666 个请求，零错误，钱包扣款与成功入账日志一致。延迟对照 **0/3** 通过。
