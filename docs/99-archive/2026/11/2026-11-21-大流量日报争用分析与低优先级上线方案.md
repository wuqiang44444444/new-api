# 大流量日报争用分析与低优先级上线方案

## 1. 问题与目标

在隔离 PostgreSQL 上，停用日报时在线日志写入 P99 为 10.98 ms，运行 157 万条来源的日报时为
132.03 ms。日报具备完整发布能力，这组配置的业务性能验收失败。

业务请求、结算、退款和在线日志持久化优先。日报、派生账单报表、历史重建和报表导出利用剩余容量，
可以跨多个低负载窗口进展。日结果继续按完整代际发布，数据未就绪时沿用既有的截至时间及未完成状态。
已经入账的金额、余额、退款时点、正式账单确认和已冻结版本继续遵守现有合同。背景生成和导出可以排队。
保留现有在线日志提交、索引和事务持久性。此前方案的复合游标、来源边界和发布校验继续使用。其
8 分钟构建及 16 分钟任务预算用于约束执行尝试，新方案拟将其与整日的完成目标解耦。
[已有压力复测](2026-11-21-日报日志扫描与发布校验优化方案.md#72-大流量日完整发布复测) ·
[日报发布合同](../../../20-architecture/decisions/0022-日报当前版本发布与历史证据迁移.md)

## 2. 当前实际情况

### 2.1 测量结论和边界

两组使用同一合成来源模板和 WAL 配置，前台均约每秒发起 20 次本地测试 HTTP 请求。测试路由读取账户并
执行 `RecordConsumeLog`。开启日报一组包含账单、用量生成及发布，目标日有 1,574,210 条来源，
原已发布版本有 20,000 条。库为隔离 PostgreSQL 18.4，3 个 CPU，`shared_buffers=256 MiB`，
`max_wal_size=2 GiB`，启用 `wal_compression=pglz`。合成测量时跳过宿主 CPU 和内存门控，
仍使用数据库门控。

| 模式 | 前台采样窗 | HTTP／日志成功数 | 日志 P95 / P99 | HTTP P95 / P99 | WAL 位置增量 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 停用日报 | 40 秒 | 800／800 | 5.01 / 10.98 ms | 9.48 / 16.73 ms | 约 1.7 MiB |
| 日报运行 | 前 480 秒 | 9,600／9,600 | 28.94 / 132.03 ms | 39.16 / 152.21 ms | 约 4,495.9 MiB |

日志 P95 约为停用时的 5.8 倍，P99 约为 12.0 倍。HTTP 尾部也同时上升。约 4,495.9 MiB 的实例 WAL
位置增量平均约 9.37 MiB/s，明显低于本轮配置的 48 MiB/s 总阈值。平均值看不出三秒窗口峰值、刷盘延迟
或磁盘队列。位置增量覆盖整个实例，是生成活动的代理指标，不能分摊到单条业务日志、日报明细或检查点。
压测计时在应用侧包住写入调用，其中可能包含取连接、数据库执行及提交确认。没有同期会话等待、I/O 队列
和检查点事件记录。两组窗口长度不同，停用组也可能遗漏周期性尖峰。因此本轮证据足以阻止灰度，约
121 ms 的 P99 差值不能精确归给某次刷盘，也不能外推为生产倍率。
[原始测量摘要](2026-11-21-日报日志扫描与发布校验优化方案.md#72-大流量日完整发布复测) ·
[PostgreSQL 统计口径](https://www.postgresql.org/docs/18/monitoring-stats.html)

### 2.2 原因排序及验证方法

日报工作池和业务池独立，源和主库 DSN 仍接到原实例。在线消费日志同步调用 `LOG_DB.Create` 并等待返回。
账单候选逐笔保存客户和上游证据，写表主体、主键及三个二级索引；每约 100 行一批，重建时还会读旧版
逐笔原价。用量、依赖和来源校验增加对日志及相关表的读取。限速以批次行数和 WAL 估算控制工作量，现有
三秒采样用实例 WAL、事务速率、应用本进程连接池等待、短探测及主机信号来退让。它没有直接观察在线日志
提交尾延迟、存储等待和检查点 I/O。连接池未满时，已有连接上的提交也可能排在 I/O 队列中。
[在线日志入口](../../../../model/log.go#L100) · [日报工作池](../../../../model/usage_report_source.go#L26) ·
[候选批写](../../../../model/billing_report_build.go#L92) · [逐笔表和索引](../../../../model/billing_report_store.go#L50) ·
[门控信号](../../../../service/daily_report_budget.go#L153)

| 假设及排序 | 推断依据 | 能区分原因的预期观测 |
| --- | --- | --- |
| **1．WAL 写入和持久化排队** | 大量候选写入和业务提交共用实例的 WAL 服务。短探测和低平均字节率可以与高提交延迟同时出现。 | 单独回放候选批写时，前台慢样本与 WAL 写入、同步或相关轻量锁等待重叠，暂停批写后下降。单独扫源时该现象明显减轻。 |
| **2．检查点与关系页写回加剧短时存储争用** | 堆和索引写入产生脏页，检查点写回与在线提交可能争用同一设备。检查点后首次修改的页又可能增加整页 WAL。合成运行的 WAL 增量支持继续排查。 | 尾延迟与检查点写时段、数据页写入或同步耗时、设备写延迟及队列深度对齐。仅替换测试库的检查点或整页压缩设置，改变尖峰出现时机或幅度。 |
| **3．来源扫描和校验挤占缓存、数据读 I/O 或 CPU** | 账单和用量轮次均读取宽日志，发布前还会做范围聚合和旧明细比对。复合游标减少无效扫描，实际命中数据仍需读取。 | 只读回放也能抬升前台尾延迟，伴随数据页读取等待、缓存驱逐或 CPU 运行队列增加。候选仅写回放中此类读侧信号减少。 |
| **4．应用连接池、锁、宿主抖动或同步复制** | 现有结果没有逐阶段等待样本，停用日报的其他复测也曾出现较大波动。生产同步复制配置未知。 | 对齐连接池等待、会话等待和设备指标。若主要等待在客户端取连接、锁或同步复制确认，将这些因素与 WAL 或检查点分开归因。 |

前两项是当前优先验证的解释。样本中已开启 `wal_compression`，该设置压缩整页 WAL 镜像，仍会有常规
WAL 记录和脏页写回。应用侧 48 MiB/s 是退让阈值，和 PostgreSQL 管理检查点的 `max_wal_size`
分别校准。当前证据支持资源争用，尚不能认定某次检查点或某一种等待占主导。
[WAL 与检查点配置](https://www.postgresql.org/docs/18/wal-configuration.html) ·
[整页 WAL 和压缩](https://www.postgresql.org/docs/18/runtime-config-wal.html#GUC-WAL-COMPRESSION) ·
[PostgreSQL 等待事件](https://www.postgresql.org/docs/18/monitoring-stats.html#WAIT-EVENT-TABLE)

## 3. 优化方案

### 3.1 先取得可归因的对照

保留现有 157 万行模板、旧版本和写入索引作为压测数据形状。隔离环境使用相同的数据库版本、磁盘和缓存热度，
在同峰值负载、并且长度相同的窗口交替运行以下四组。每轮分别采集任务前、任务中及停止后写回稳定的窗口，
覆盖完整的构建与写回周期。先建立重复的停用日报基线，再判断差异。业务压测接入真实网关的测试环境，复现
账户读、结算与日志提交的实际组合。

1. **停用日报**，记录同负载前台基线。
2. **仅回放读取与校验**，使用账单／用量分页、依赖和覆盖查询，以及旧明细只读比对。
3. **仅回放候选写入**，用离线准备好的同形状候选及现有索引，维持原批大小和提交节奏，按轮切换相同初始快照。
4. **完整生成**，区分读源、旧价读取、逐笔写入、汇总、发布校验、发布事务及清理各时段。

用应用侧既有计时或隔离压测钩子分开记录取连接、插入及提交确认，连同 HTTP 延迟、吞吐、失败数、
SQL 连接池增量与每阶段耗时。按会话角色标记日报 worker，在受控采样中用 `pg_stat_activity`
按时间对齐前台等待。PostgreSQL 18 用 `pg_stat_wal` 看 WAL 记录及整页镜像，用 `pg_stat_io`
看 WAL 和关系页的写入／同步耗时，用 `pg_stat_checkpointer` 看检查点次数及写入、同步时间。低版本按
支持的统计视图采集。数据库耗时统计的开关先在隔离环境验证成本。结合实际承载卷的读写延迟、队列深度、
CPU 和可用时的同步复制等待，使用相同的采样配置做对照。生产灰度使用现有网关和数据库监控，在线日志
请求路径沿用原 SQL 和原事务。 [PostgreSQL 累计统计](https://www.postgresql.org/docs/18/monitoring-stats.html)

### 3.2 共库上线的最小方案

1. **先保护容量，再获取日报执行资格。** 默认停用，显式开启前按停用日报时的峰值和空档分别校准。
   用业务吞吐、错误率、请求和日志尾延迟作为验收信号，用已有的前台遥测、WAL／数据盘等待、连接池
   和数据库压力作为准入信号。日志量少时查看慢样本数、提交耗时和持续窗口，避免用极少量请求的 P99
   触发恢复。在缺少可信或新鲜信号、业务受压、数据库维护或性能超过已验收边界时停止开启新批次。
   恢复要连续多个健康窗口，并以最小批次开始。已有写事务按短期限结束，后台期间释放连接。
2. **把低优先级从限速落实到执行。** 一个实例只运行一个经验证的重负载报表切片。给读页、候选字节、
   写批和清理时长都设上限，保留全实例 WAL 保护。以测得的单批 I/O、持续时间和前台尾延迟缩小突发，
   高压时按**暂停**处理，空档按**匀速小批**处理。发生压力时日报、历史重建和报表清理优先退让，手工
   重建也走同一门控。若报表导出或月账单制品生成在同实例形成已观察到的争用，将这些低优先级作业纳入
   同一准入。正式账单版本合同和入账服务继续独立执行。
3. **整日可以慢，单次执行和恢复成本要小。** 把普通全日构建改为短执行片和可恢复候选。复用已有
   候选、租约和复合游标机制，按日期、类型、代际和阶段提交稳定进度。冻结来源边界及依赖版本，
   使片内产物和相应进度原子提交，或以稳定身份幂等恢复。下一轮从最后已提交进度继续，减少重新扫描
   及重写。对用量和资金事实按原稳定身份合并，跨片退款、去重、时间与 ID 反序均纳入回归。保留源
   变化后的复验、旧代际逐笔资金核对和跨日关联范围原子发布。来源变化能够精确定位时重算受影响的片，
   无法确认覆盖时保留候选待核对或按既有规则重建。
   冻结历史复制已有续跑功能，普通日志构建仍会在持续压力后重扫，本阶段补齐普通构建的续跑。
4. **以新鲜度和积压替代对整日完成时长的刚性要求。** 展示数据截至时间、最老待发布日期、最新
   进度和延期原因。监控积压是否逼近日志留存线，并用既有受保护证据迁移能力或隔离环境的来源副本
   保护尚未处理的日期。证据范围不足时按现有合同显示覆盖状态。1,574,210 行按 100、200、500 行/秒
   仅逐笔写入分别约需 4.37、2.19、0.87 小时，未含读取、暂停和校验。这些数字只说明跨窗口推进的
   量级，生产速率由前台基线决定。

### 3.3 共库仍有回退时的上线路径

共库即使使用两套连接池、不同 schema 或同实例内的不同数据库，仍使用实例资源。若最小可用切片和
低谷准入也导致前台尾延迟持续回退，线上保持停用，将报表计算与报表投影迁到独立 PostgreSQL 实例和
独立存储性能配额。优先使用现有只读副本或备份恢复出来的一致来源副本，生产主库避免临时全日扫描。
只有源读取挪走仍不足以移除主库的候选写压力，派生明细、汇总、校验、历史回填和清理应共同迁移。

隔离方案实施前单独确定报告读取、导出与邮件如何切换到同一发布代际。源日志、任务、扣费和退款事实仍
以业务库为权威。物理副本必须证明已回放到对应的已提交边界，并监控复制延迟、WAL 保留和回放冲突。
分库时分别验证各来源的进度和关联事实。若采用逻辑复制或离线导出，显式验证删除、更新、迟到提交
和旧覆盖边界，保留可靠的来源版本凭证。保持现有一套面向用户的发布状态，冻结引用和读侧切换只在覆盖
核验通过后推进。副本异常或积压由报表延期消化。
[只读副本的一致性和冲突](https://www.postgresql.org/docs/18/hot-standby.html#HOT-STANDBY-CONFLICT)

### 3.4 上线顺序、验收与回退

| 顺序 | 行动与通过条件 |
| --- | --- |
| 0．保持保护 | 保持默认停用。记录停用基线与业务可接受的自然波动区间，明确容量信号失效时自动退让。 |
| 1．隔离验证 | 按四组同负载复测，找出具体争用，并证明短片可以在峰值骤升时停止开新批，恢复后无重复逐笔或汇总。 |
| 2．小范围灰度 | 先在一个 worker 以少量日期、最小预算运行，覆盖写回尾部。业务吞吐、错误率、请求和日志 P95/P99 相对停用基线无可归因的回退，才能扩大日期与预算。 |
| 3．容量与积压验收 | 用至少一个代表性大流量日和同量级旧代际复测，允许跨多个低谷窗口完成。核对明细、金额、来源覆盖、晚提交和跨日退款，观察积压可持续消化。前台保护条件优先于新鲜度。 |
| 4．回退 | 若发现前台回退或压力信号失效，自动停止日报新批，排空已开始的短事务，保留最后有效发布指针和可恢复进度。运维可用现有开关停用 worker。 |

隔离前仍需记录安全容量和留存余量。若连最小工作片都持续影响业务，转入资源隔离验证，继续按正常业务
写入基线验收。 [当前开关及配置](../../../40-operations/01-计费与分组运维手册.md#日报数据库预算与灰度)

## 4. 实施前四组对照

使用独立 PostgreSQL 18.4 容器，限制为 2 CPU、1.27 GiB 内存。每组克隆相同的 156 万行合成日志源，
其中目标日 6 万行，旧发布代际 2 万行。数据库共享缓冲 256 MiB，WAL 上限 2 GiB，使用
`wal_compression=pglz`。先按停用、仅读、仅写、完整执行，再反向重复。每组预热 3 秒、测量 30 秒、
回落 3 秒。每组计划约 300 HTTP 请求/秒，路由查询账户并使用实际 `RecordConsumeLog`。写入计时包含
取连接和提交确认。仅读执行来源、用量和校验查询，约 1.2–1.6 秒完成。仅写提交 6 万条同形候选和既有索引，
完整组生成账单和用量并确认两个指针，分别用时 18.16 秒、21.71 秒。

| 轮次 | 模式 | 日志 P95 / P99（ms） | HTTP P95 / P99（ms） | 失败／丢弃样本 | 整窗 WAL 增量（MiB） | 在线会话 WAL 同步／写锁样本数 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| 1 | 停用 | 2.70 / 7.73 | 5.38 / 15.69 | 0 | 14.0 | 7 / 4 |
| 1 | 仅读 | 7.58 / 29.71 | 14.44 / 49.36 | 0 | 14.1 | 9 / 15 |
| 1 | 仅写 | 23.70 / 59.98 | 40.23 / 90.00 | 0 | 139.1 | 26 / 56 |
| 1 | 完整 | 14.25 / 47.44 | 22.73 / 71.09 | 0 | 159.1 | 19 / 40 |
| 2 | 完整 | 54.11 / 107.66 | 83.82 / 163.13 | 0 | 158.8 | 29 / 87 |
| 2 | 仅写 | 24.34 / 62.56 | 40.72 / 118.43 | 0 | 185.7 | 10 / 33 |
| 2 | 仅读 | 15.80 / 56.45 | 25.55 / 84.67 | 0 | 14.3 | 9 / 18 |
| 2 | 停用 | 64.99 / 156.81 | 103.91 / 268.35 | 12 | 14.4 | 39 / 133 |

两轮仅写都把 WAL 增量提高约一个数量级，第一轮同时观察到更高的 WAL 同步和写锁等待。候选写入是可以独立
转入低优先级的争用来源。整个实验未观测到检查点计数增加。第二轮停用组回落窗日志 P99 达 453.98 ms，
表明宿主或共享存储存在显著扰动，无法从本试验给峰值回退分摊比例，也无法确认仅读的独立影响幅度。
样本来自单机合成路由，完整组目标日小于 §2.1 的 157 万行。测试未采集设备队列和同步复制，数字仅用于验证
拆分方向。

## 5. 已实施内容与验收边界

- 日报仍默认停用。非本地 worker 要求现有前台监控交付短时许可，并叠加主机、数据库探测、连接池、
  PostgreSQL WAL 和可选事务速率检查。缺少、过期或拒绝的许可会在下一批开始前阻止执行。恢复需要连续
  两次健康采样。门控作用于日报任务，在线日志依旧用原表、原索引和原持久化设置。
- 每次常规调度只推进一个主日期及按既有契约必须联合发布的范围。普通读源每页最多 128 行，页间至少 20 ms。
  典型候选每批最多 25 行，行预算默认 50 行/秒，上限 200，常规批次超时 2 秒。新汇总分片约 64 KiB，
  逐笔写入按约 128 KiB 切批，单笔超过目标时独占一批。发布覆盖仍保留原 5 秒的单语句一致性校验。
- 普通构建和不可变旧明细比对遇压停在批间，释放数据连接和事务，保留进程内游标及聚合，复用既有租约心跳。
  可以在 24 小时的执行生命周期内跨多个低谷窗口继续。历史复制、清理及最终可变来源校验遇压延期。
  清理每轮每类最多推进一个小步骤，暂停期间不执行清理。
- 普通账单候选冻结来源上界。每批逐笔、进度、问题行数及校验摘要在同一短事务提交。接管者重读已提交
  前缀重建聚合，验证前缀后跳过已写逐笔及已完成汇总。前缀已变化时废弃候选，保留旧发布指针。
  冻结历史复制仍按各表主键继续。已结束日期在最终校验前刷新日志上界，当日仍按构建的共同上界发布
  截至该时点的结果。旧边界、逐笔资金核验和联合发布校验继续生效。
- 仍待验证生产监控许可供应、峰值在线 P95/P99、同量级旧代际的低谷交替发布和清理积压。普通用量的进程内
  游标可跨低谷，进程退出后的聚合需要重算。账单进程重启后仍会重读前缀。日期级一致性扫描和关闭后再开启的
  恢复成本需纳入灰度验收。生产继续保持停用。

### 5.1 续跑和前台复测

在同一 PostgreSQL 模板上增加一个 6,000 行的目标日，旧代际含 2,000 行。新版在第 1,000 和第 2,500
条逐笔提交后注入压力，让构建函数退出，在下一低谷以同一候选重入。两轮均保留旧指针直到联合发布，
最终用量和账单各覆盖 6,000 条来源，构建、两次停顿和发布共 36.05–36.45 秒。此轮按 200 行/秒压测，
由试验注入停顿。停止日报组采用同样的 42 秒前台窗口，仍使用相同的前台合成路由。

| 模式 | 在线日志 P95（ms） | 在线日志 P99（ms） | HTTP P99（ms） | 整窗 WAL（MiB） |
| --- | ---: | ---: | ---: | ---: |
| 停用 | 5.02–6.75 | 16.71–23.19 | 27.19–30.65 | 18.9 |
| 低优先级小批 | 13.27–13.90 | 38.97–39.46 | 45.94–52.84 | 33.6 |
