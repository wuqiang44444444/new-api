# 普通文本请求默认渠道亲和实施方案

## 1. 问题与目标

在原生 HTTP 文本分发上补充按用户的默认渠道亲和。现有配置、目标范围、风险和发布门槛以
[已确认方案](../50-planning/2026-11-10-普通文本请求默认渠道亲和方案.md)为准。本文件记录接线顺序、
回归和证据要求。代码已实现，生产发布仍按方案的验收门槛执行。

## 2. 当前实际情况

| 代码事实 | 实施影响 |
| --- | --- |
| [现有亲和读取](../../service/channel_affinity.go)按顺序匹配规则，返回值主要表达有没有缓存到渠道。 | 必须区分规则是否匹配与缓存是否命中，包括规则 `off`、缓存缺失和读取异常。仅在未匹配时启动默认规则。 |
| [普通选渠](../../service/channel_select.go)和[合同选渠](../../service/customer_contract_routes.go)都有现有亲和入口。普通选择最终由[内存路径](../../model/channel_cache.go)或[数据库路径](../../model/ability.go)确定优先级及权重。 | 默认绑定要在原选渠结果的候选层内择优。两个候选来源都要覆盖，避免内存开关改变策略。合同仍由现有渠道和分组事实决定费用。 |
| [HTTP 分发](../../middleware/distributor.go)现有规则在返回状态小于 400 时尝试记录，通用[流状态](../../relay/common/stream_status.go)把 EOF 也视为正常结束。 | 默认绑定接入已有请求完成事实。对有明确协议终态的流，仅 HTTP 200、收到首包或单独 EOF 均不足以写入。 |
| [Responses HTTP 流](../../relay/channel/openai/relay_responses.go)通过用量累加器调用 [ObserveResponsesOutcome](../../service/responses_usage.go)，已识别完成、失败、取消和不完整。现有 [MarkRequestPolicySuccess](../../service/request_policy.go)允许终态为空。 | 在默认绑定的写入判断使用已有终态，不复用宽松成功谓词，也不在原生 adapter 重复标记终态。正常结束且已有完成标记可以写入，截断 EOF 不写。 |
| [请求策略](../../model/request_policy.go)加载时持久化规则覆盖内置规则，[Redis 缓存](../../pkg/cachex/hybrid_cache.go)读写当前设有 2 秒操作超时。 | 默认行为在运行时兜底，避免重写 `rules`。默认缓存读写需要单独短预算，避免将现有较长等待扩散到全部目标请求。 |
| [现有亲和缓存](../../service/channel_affinity.go)的 `MaxEntries` 用于本地 LRU。启用 Redis 时，[HybridCache](../../pkg/cachex/hybrid_cache.go)直接读写 Redis，本地上限不生效。 | 默认绑定要隔离本地容量。共享 Redis 的额外键量和淘汰需要单独验证，键名前缀不提供实例内配额。 |
| [Responses WebSocket](../../relay/responses_websocket.go)会在连接内冻结渠道和 Key，已有会话规则可在上游接受后记录。 | 本期只接入 HTTP，WebSocket 路径和绑定时点沿用当前语义。 |

## 3. 改代码前的 Opus 固定渠道对照

1. **确认样本。** 从管理日志的 `request_policy` 区分有没有 `session_rule_matched`，结合 `use_channel`、渠道配置和
   `multi_key_index` 核对实际落点。统计未匹配会话规则、首选层有多个直管渠道并实际跨缓存域的请求量与输入
   token 占比。记录样本窗口、日志缺失和未知缓存域。不能确认缓存域时，不把不同渠道 ID 算成已证实的跨域分流。
2. **配置两个对照组。** 在隔离测试环境复制同一 Opus 渠道池的路由配置，使用两份测试配置或分轮切换。A 组用
   当前版本和现有优先级、权重选渠，至少有两个首选层渠道。B 组用同一版本，在同一测试分组内只保留一个原本
   可选的直管渠道，并确认其上游账号或工作区稳定，且不会被渠道内 Key 轮换或第三方网关再次分发。保持实际
   Provider 模型、协议、计费组和请求设置一致。不要为 B 组使用会禁止重试的固定渠道方式，也不要改线上池或
   全局会话规则。记录两组的实际候选与渠道轨迹，确认样本均未匹配已有会话规则。
3. **按同一脚本发请求。** 用测试账号请求 `POST /v1/messages`，不带会触发现有会话规则的会话标识。使用相同
   长度和结构的稳定前缀，缓存断点放在固定内容的末尾，动态内容放在断点之后。
   确认前缀达到所测 Opus 的缓存门槛。每轮每组用独立且等长的前缀标识放在断点之前，避免交叉预热。串行轮
   各组先发一次预热并记录写入，再在有效期内按相同间隔发等量请求。冷并发轮使用新的前缀，按相同并发度从
   空缓存开始。交换组别运行顺序并重复，分别报告预热、串行和并发结果。A 组若未实际跨域分流，该轮不能证明
   跨域的影响。
4. **按 token 判定。** 逐组汇总 `cache_read_input_tokens`、`cache_creation_input_tokens` 和 `input_tokens`，
   以读 token 总量除以三项合计计算读缓存比例，同时记录单位输入费用、成功率、`429`、重试和 P95 首 token
   时间。标记缺失上游用量的样本，避免把缺失当零。客户侧输入收费与可核实的上游输入成本分开记录。留存脱敏
   配置摘要、请求数、时间窗口和用量汇总即可。
5. **据此决定是否实施。** 只有目标流量存在跨域分流，且 B 组的缓存读比例提高、单位输入费用下降并可复现，
   才进入实施。没有改善先排查前缀、断点、有效期和上游账号轮换。实现后加 C 组，在与 A 相同的多渠道配置下
   开启默认亲和，评估可获得的实际收益和用户体验。B 组用于判断缓存收益的空间，其单渠道可用性不作为
   C 组的发布基线。

## 4. 优化方案

### 4.1 识别请求与规则优先级

1. 完成鉴权和请求识别后，按下表的方法与精确路径判断首期资格。三类请求都须走原生分发，且为输入自包含的普通文本生成。

   | 入口 | 可进入默认 API Key 亲和的请求 |
   | --- | --- |
   | `POST /v1/chat/completions` | 未匹配任何现有会话规则的普通聊天补全请求。 |
   | `POST /v1/responses` | 未匹配任何现有会话规则的自包含 Responses 请求。缺少 `prompt_cache_key` 仅表示不能通过该字段匹配 Codex 内置规则，仍须检查其他规则。 |
   | `POST /v1/messages` | 未匹配任何现有会话规则的自包含 Messages 请求。缺少 `metadata.user_id` 仅表示不能通过该字段匹配 Claude 内置规则，仍须检查其他规则。 |

   `/v1/responses/compact`、`/v1/completions`、`/pg/chat/completions` 和 WebSocket 不命中。复用现有请求信息判断
   输入是否自包含，排除上游已有响应、会话、文件、向量库和工具容器等引用。无法安全判定时沿用原请求处理和错误响应。
   Responses 的内联 `function_call` 与文本 `function_call_output` 按 `call_id` 在本次输入内配对后可进入默认亲和。
   同一路径转入专用插件或任务履约时也跳过默认亲和。默认亲和只检查已经缓存在内存且不超过 1 MiB 的 JSON，
   更大的正文、磁盘正文、媒体和无法判定的输入继续走原有路由。此限制只影响是否启用默认亲和。
2. 依次处理已有固定渠道、已有会话规则和默认 API Key 亲和。选渠时分别判断「规则是否匹配」和「渠道绑定是否命中」。
   - 已匹配规则但绑定未命中时，沿用现有选渠，保留匹配规则的上下文、头透传和重试语义。满足原规则的写入条件时，
     按原规则的键写入会话绑定。本次跳过默认绑定的读取和写入。
   - 已匹配规则但读取异常或模式为 `off` 时，沿用原有处理，同样跳过默认绑定的读取和写入。
   - 未匹配任何规则且符合首期资格时，才执行默认亲和。保留现有全局关闭设置，默认模式为 `prefer`。
3. 默认绑定复用现有亲和缓存底座，使用与显式规则隔离的键。以鉴权已写入的 `token_id`、客户模型、协议入口
   和有效路由范围组成键。普通分组、Auto 的有序可用范围和客户合同分别按现有范围事实区分。
   同一账号的不同 Key 独立绑定，缺少有效 `token_id` 时走普通选渠。键不包含原始 Token、请求正文或状态引用。

### 4.2 选渠与绑定更新

1. 默认亲和命中只作为现有选渠器的偏好输入。先按权限、模型、协议、分组和合同过滤，得到本次首次尝试使用
   的优先级层，再在其中择优。Auto 仍由现有分组顺序确定首个有效组，合同沿用 `FilterContractRoutes`。DB 和
   内存路径都在原有候选查询及层筛选结果内判断，不走现有显式亲和的快速返回，也不额外查 `MAX(priority)`。
   以原本不匹配任何会话规则的普通路由为基线，验收时核对 DB 查询次数和耗时。原生文件只保留必要接线。
2. 默认绑定独立判断成功。非流式采用已有请求成功事实。Responses HTTP SSE 复用已识别的 `completed` 终态，
   同时排除异常断开和流错误。`failed`、`incomplete`、`cancelled` 或只有 EOF 都不写入。Chat Completions 请求
   多个流式结果时，按本次流中收到的不同结果索引确认所有结果均已结束。已有会话规则与共享终态语义照旧。
3. 绑定记录同一首选范围及层内实际成功的渠道。跨层或跨 Auto 分组的重试成功不覆盖仍有效的首选绑定。
   关闭「切换成功后更新会话绑定」时，换渠成功保留旧绑定，无旧绑定时此次不建。首次并发不等待绑定写入，
   同范围同层的有效成功仍按完成顺序更新。

### 4.3 缓存容量、故障与回退

- 默认绑定使用独立的 `new-api:default_channel_affinity:v1` 命名空间。本地 LRU 每进程最多 10,000 条，
  条目有效期复用现有亲和默认 TTL，缺省一小时。绑定键从账号 ID 切换到 Key ID 后，旧账号键留待过期或全量清理。
  本地管理接口保留统计字段名 `default_user_entries`。Redis 使用独立命名空间
  在运维窗口通过 `SCAN` 抽查规模，不在管理页面刷新时发起额外 Redis 扫描。Redis 部署按活跃 Key、模型、范围
  和 TTL 估算新增峰值键量，检查 `maxmemory`、淘汰或拒写情况、旧规则命中与延迟。共享实例余量不足或旧规则
  退化时，调整容量预算或隔离存储后复测。管理日志区分默认绑定命中、未命中和跳过，默认键规模单独统计，
  不混入已有规则的 `unknown`。全局关闭时不添加默认亲和的逐请求事件。已有全量清理覆盖两个绑定命名空间，按规则清理范围不变。
- 默认 Redis 读写各限时 10 ms，建立 TLS 连接也受本次操作期限约束。读取超时或失败立即走普通选渠，当次不再写默认绑定。写入失败不改变原结果，不因缓存失败多发上游
  请求。故障日志限频，不输出密钥或原始请求正文。用持续慢响应与不可达测试验证等待预算和用户影响，若超出
  门槛，再评估短暂停用默认读取。首期不预先引入跨实例负缓存。
- 发布前用上一已验证制品和已保存配置演练多实例版本回退，记录触发条件、执行顺序、实例回退时间和验收
  结果。核对已有会话规则、头透传、普通选渠和用户指标恢复。已有全局开关会一起关闭旧会话规则，不作为仅
  撤销默认亲和的手段。无法在可接受时限内回退时，暂停发布并评估仅停用默认亲和的方式。

### 4.4 回归与交付顺序

| 阶段 | 任务与验收证据 |
| --- | --- |
| 0. 实施前取证 | 完成第 3 节的覆盖率核查和 Opus A/B 对照，记录是否值得实施。 |
| 1. 路由回归 | 在数据库和内存路径验证同层复用、不同层拒绝、资格变更、Auto 范围和合同组。验证同账号不同 Key 独立建立并复用绑定，以及没有有效 Key ID 时走普通选渠。逐一验证三个入口符合资格且无规则匹配时进入默认亲和。为 Codex 和 Claude 各构造规则已匹配但无会话绑定的请求，即使已有可用默认绑定，也须沿用原选渠及会话写入行为，不读取或写入默认绑定。验证固定渠道和原有重试。 |
| 2. 生命周期与升级 | 验证 Responses 正常完成写绑定、200 后失败或截断 EOF 不写、同级和低级重试成功、切换开关关闭、首次并发、容量满载和 Redis 持续故障。验证已有规则、全局关闭和多实例回退。用 HTTP 状态引用、非首期路径、WebSocket 和专用入口样例验证隔离。 |
| 3. 本地检查 | 后续实施时从 `go test ./service ./model ./middleware ./controller` 中选取覆盖实际改动的测试，包含现有合同和会话规则回归。文档执行 `task docs:check` 和 `task ai:check`，按实际改动补充入口的必要检查。 |
| 4. 发布前对照 | 加入 C 组，按[方案发布门槛](../50-planning/2026-11-10-普通文本请求默认渠道亲和方案.md#上线前验收与发布)记录可比流量、上游用量、旧规则表现和用户指标。验收报告区分自动化、真实 Provider、实际账单和生产发布。 |

### 4.5 原生接线及上游合并点

- `service/channel_select.go` 和 `service/customer_contract_routes.go` 在现有规则及固定渠道之后传入默认偏好。
  读取和写入范围、协议判断及状态放在 `service/default_channel_affinity*.go`。上游同步时检查选渠入口和合同过滤参数。
- `model/channel_cache.go` 和 `model/ability.go` 在原有候选及优先级筛选后接收偏好，并返回实际层级。复用同一组查询，
  保留原有对外函数签名和权重算法。上游若调整候选或优先级逻辑，偏好仍应在其实际首选层内生效。
- `controller/relay.go` 在原生 HTTP 请求成功出口调用一次绑定更新。Responses SSE 复用现有终态，上游同步时检查成功出口和终态事实。
  完整响应发出后客户端关闭连接，不能单凭请求上下文取消否定已经确认的上游成功。流中断仍由流终态和错误判断。
- `relay/channel/openai/relay-openai.go` 在已有 `finish_reason` 解析处传递结果索引。上游同步时保留这一调用，
  使默认亲和能验证多结果流，无需重新解析 SSE 或改变共享终态。
- `relay/compatible_handler.go` 在渠道参数覆盖成功后调用一次亲和观测，读取该次实际发送的 Chat JSON 中的 `n`。
  上游同步时保留观测位置在覆盖之后、发送之前，确保绑定写入使用本次尝试的结果数。
- `pkg/cachex/hybrid_cache.go` 增加可选操作时限，`common/redis.go` 在共享客户端初始化处接入遵守上下文期限的 TLS 拨号。
  上游同步时核对依赖的 TLS 拨号是否已遵守上下文期限，并保留旧缓存操作时限。
- `service/channel_affinity.go` 接入独立本地条目统计，`controller/channel_affinity_cache.go` 沿用原接口并处理全量清理失败。
  上游同步时保留统计口径和按规则清理语义，确认全量清理覆盖两个独立实例。

## 5. 开发环境验收记录（2026-11-11）

- `service`、`model`、`middleware`、`controller`、`router` 的测试及根模块构建通过。亲和相关的服务和 HTTP 回归
  通过竞态检测。普通、Auto、合同路径覆盖同层复用、
  低层和跨 Auto 分组不改绑、切换开关、会话规则缓存未命中、插件与状态引用排除。本地默认 LRU 满时，旧规则绑定保留。
- 原生 Responses HTTP 在 SQLite、PostgreSQL 15 和 MySQL 5.7 上通过正常完成及截断流回归。隔离 Redis 8.2 暂停
  时，默认缓存读写实测约 10–11 ms 返回，解除暂停后读恢复。读写失败分别覆盖普通选渠和业务响应保留。
- 综合评审修复后，新增多结果 Chat SSE、合同内同层换组重试、TLS 握手超时和双命名空间清理回归。
  用 `./start.sh --redis-only` 启动隔离 Redis 7，把输出的连接 URL 设为 `YUAN_AFFINITY_TEST_REDIS`，执行
  `go test -race ./service -run '^TestDefaultChannelAffinityClearAll$' -count=1 -v`。
  本地实测 Redis 暂停期间默认缓存读写约 11 ms 返回，解除后读恢复。全量清理删除两个命名空间中的绑定，其他 Redis 键保留。
- 两个开发实例共享隔离 Redis，逐个替换为移除本次接线的对照构建。新版本能跨实例读取默认绑定。回退后普通路由恢复，
  Codex 原会话绑定继续命中。生产仍须用实际的上一发布制品和部署配置核对回退时限。
- GPT‑6 Astra 真实上游第一次复测每组 27 次。新默认亲和组的 12 次预热后串行请求均命中网关绑定，但稳定段和变化段同在
  一条 `input` 时，三组上游读缓存比例均为 0，固定渠道也一样。固定渠道把稳定段放到 `instructions` 后，预热后 4 次
  请求均读到缓存。两种请求形状按各自证据报告，避免把请求形状引起的差异归因给选渠。
