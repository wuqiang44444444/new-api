# MiniMax 官方 H3 标准视频接入实施方案

## 1. 问题与目标

Hailuo Video 已能以原有 OpenAI Videos / Responses 合同调用 MiniMax 官方接口。新增需求是让官方
H3 线路也能接受本站 ModelArk V3 请求，并完成后台查询、资金结算和 OSS 交付。本文规划首批接入
`MiniMax-H3` 基础版，保留原生 Hailuo 和京东云标准视频两条线路。客户模型名由部署方配置，
示例使用 `h3-official-example`。H3 其它型号、Hailuo V1 型号、再生成、Context-IR、上游回调及
素材库均在首批范围之外。

拟在 `ChannelTypeMiniMaxLink`（69）和现有 `minimax-link` 制品下登记
`minimax_official_video_v2`。该标识是建议命名，实施时由代码固定。客户沿用现有 ModelArk V3
路径、鉴权、任务 ID、状态和下载合同。管理员新建官方标准视频渠道，显式选择协议、凭据、
Base URL、精确模型映射、客户分组和定价。官方、京东云和原生线路使用独立客户模型名，按已有管理
保存／启用规则维护标准视频模型唯一性和原生价格键隔离。

沿用现有 Link 入口、Task、资金和制品版本约束，此变更属于新增南向协议。依据
[硬约束](../00-context/硬约束.md)、[MiniMax 管理流程](../10-product/业务流程.md#minimax-渠道管理)、
[ModelArk V3 北向合同](../20-architecture/Seedance专用渠道与Link架构.md#6-modelark-v3-北向合同)、
[异步任务与计费事实架构](../20-architecture/账单计费-异步任务与计费事实架构.md)和
[OSS 托管交付架构](../20-architecture/Link视频结果OSS托管交付架构.md)。

## 2. 实施前的实际情况

### 2.1 三条执行路径

| 路径 | 当前实现 | 与本次接入的关系 |
| --- | --- | --- |
| 原生 Hailuo | 类型 35 映射到 `hailuo`。插件声明 `openai_video`、`openai_responses`，用 `per_task` 查询。精确匹配 H3 时发送 V2，较早型号发送 V1。H3 从 `task.content.url` 取结果，V1 用 `file_id` 调 `/v1/files/retrieve`。 | 可用现有 V2 请求、回包和用量测试作样本。原生插件支持 `metadata.content`、私有字段透传和自己的任务状态解释，均留在原生入口。 |
| MiniMax 标准视频 | 类型 69，ModelArk V3 北向。创建经 `ModelArkVideoCreateConvert → ResolveStandardVideoChannel → RelayTask`。当前 `minimax-link` 仅声明 `jdcloud_video_task_v1`。 | 新增官方协议，继续使用同一套选渠、Task、持久占款、投影和交付接线。 |
| Seedance Link | 同一 ModelArk V3 Router，独立类型及制品，标准渠道共享客户模型唯一性。 | 复用其所在的标准入口和通用资金／交付基础设施。 |

代码入口见 [原生插件映射](../../relay/relay_adaptor.go)、
[Hailuo 插件](../../plugins/tasks/hailuo/plugin.js)、[Hailuo 测试](../../plugins/hailuo_responses_test.go)、
[视频 Router](../../router/video-router.go)、[标准视频选渠](../../middleware/standard_video_channel.go)和
[跨类型唯一性校验](../../model/channel_standard_video_uniqueness.go)。架构概览将标准视频类型写为 64，
代码及管理端当前枚举为 69，实施后的事实文档按代码校正。

## 3. 优化方案

### 3.1 协议登记、版本与责任边界

1. 在 MiniMax 本地扩展层登记官方协议及固定创建、查询路径。以代码注册作为路由资格，
   以 `minimax-link` 制品声明作为支持模型和参数的权威。插件声明不得提供自定义 URL、方法、鉴权、
   资金指令或调度策略。沿用绝对 HTTP(S) Base URL 语义及单凭据校验。
2. 新版 `minimax-link` 在现有 hook 根下新增官方协议的 `buildCreate`、`parseCreateResponse`、
   `parseTaskObservation`，保留既有 JD hooks 和声明。Go 宿主按协议选择固定路径，验证 hook
   结果后才使用。转换主体和官方回包解码隔离在 MiniMax 本地文件，继续复用稳定的内容保真、
   状态映射和错误脱敏原语。原生插件可提供测试样本，标准链运行时只依赖冻结的 `minimax-link`。
3. 将 `PinMinimaxExtensionForChannel` 改为使用已选渠道的 `video_upstream_protocol`。准入、
   声明和转换复用同一 pin。查询和回源按 Task 的协议、制品 key/version 及可用的现有制品身份校验
   取精确制品。未知协议、缺失凭据、缺失上游 ID 或版本与协议不匹配时失败关闭。官方新任务
   必须有冻结路径和私有上游 ID，避免借用 JD 历史缺路径默认值或通用 `GetUpstreamTaskID`
   的平台 ID 回退。
4. 部署新制品只入库。验证旧版只声明 JD 也能被新宿主编译、查询和回源。激活用现有事务检查
   所有类型 69 渠道，已有活动任务和 create attempt 继续引用原制品。所有执行节点先部署兼容
   新协议的宿主，再激活双协议制品，最后创建官方渠道。无需为协议新增表或回填存量记录。

### 3.2 创建、输入与发送屏障

首批建议对齐现有 H3 北向公共缺省值，省略时使用 6 秒、768p、16:9。显式 `adaptive` 在
纯文本场景于占款前返回 `400 invalid_request`。首尾帧模式由图片决定画幅，合法 ratio 可保留
出站，由上游按其条件语义处理。参考模式允许合法具体画幅和 adaptive。若验收要改成参考模式
缺省 adaptive，先保证声明、投影、宿主保真和账单探针能表达同一个按场景的默认值。

| 北向事实 | 南向和验证 |
| --- | --- |
| `model` | 先校验客户分组和渠道，再用 `model_mapping` 得到官方模型，宿主核对出站 model。 |
| `content` | 一项非空文本，允许文生视频、首帧／尾帧／首尾帧、参考生视频。首尾帧各一张且与参考组互斥。参考模式最多 9 图、3 视频、3 音频。保留合法媒体节点和顺序。官方角色、媒体编码限制以实测后的声明为准。 |
| 请求级媒体 | 复用 `PrepareVideoReferenceAudio` 处理 HTTPS、内联 Base64 和 multipart，先完成媒体结构、组合及可支持字段校验，再上传需转存的音频并校验实际出站体，均发生在 hold 之前。仅签发本次南向所需 URL，冻结引用事实，下载链接和输入正文留在现有受保护边界。官方没有可兑现的 `asset://` 资源入口，遇到该引用在占款前明确拒绝。 |
| `duration/resolution/ratio` | 校验 4–15 秒整数、`768p/2k` 和合法画幅。官方出站分辨率为 `768P/2K`，宿主核对大小写转换与等价性。显式零值按字段本身的合同校验。 |
| 其它标准及私有字段 | 按新协议声明逐项审查。现有 H3 文档发布 `watermark=false`，先证明官方默认行为或经官方确认的等价控制能兑现，再对官方线路发布该能力。可按统一合同忽略的条件生效字段在 adapter 内处理。无法履约的操作明确报错。保持上游回调、`extra`、`metadata.content` 等私有入口在首批范围之外。 |

`RelayTaskSubmit` 依次完成标准 DTO、映射、转换校验、价格准备、attempt 和发送。官方请求体采用
精确字段集合，宿主检查转换没有改写模型、content、时长、分辨率或画幅。可重用现有的字符串、
数量和内容验证，JD 的嵌套 `parameters`、提示词优化及 watermark 策略继续由 JD 分支处理。

官方创建成功只按已确认 HTTP/回包形状接受有界、非空、无控制字符的 `task_id`。带错误和 ID 的
矛盾回包、2xx 缺 ID、断连、未登记错误形状及 5xx 均为结果未知。只对有官方证据及验证样本的
确定拒绝执行释放。分类键至少包含协议、HTTP 状态和结构化错误类型，避免从提示文字猜测。
复用当前「发送前资金 hold + `sending` 原子提交」及「可信 ID 后 Task + hold 转移 + attempt 完成」
两个事务。POST 超时、重定向、客户端断开和本地提交失败均验证无隐式重发。unknown 保留原始
attempt，按现有 24 小时保障、人工查证恢复和 Provider exposure 流程处理。ModelArk V3 的每次
POST 是独立创建意图，沿用现有请求合同。

### 3.3 后台查询、状态和交付

1. 后台 `async_task_poll` 用冻结 Base URL、固定查询路径、代理和受保护凭据查询官方 V2。
   按状态映射 `queued → QUEUED`、`running → IN_PROGRESS`、`succeeded → SUCCESS`、
   `failed → FAILURE`、`cancelled → CANCELLED`。Go 核对 `task.id` 与冻结 ID 完全一致。
   如提供 model、task_type 或 modality，核对已登记的官方身份与操作。已接受终态保持单调。
2. 网络、408、429、5xx 表示临时观察不可用，保持最后可信状态及资金。有效 `Retry-After`
   可走已持久的单任务退避，但只对官方协议明确登记后启用，避免借 JD 身份判定。404、认证错、
   未知状态、错误 ID、损坏 JSON、无可信成功结果均不能一次触发失败退款。错误归入观察不可用
   或合同待核实，诊断只保留稳定码和脱敏信息。可信失败／取消才进入共享幂等退款。
   复用 `ErrUpstreamObservationUnavailable` 跳过临时失败的连续错误计数，结构违例走
   `UpstreamContractViolation`。保留现有整体超时治理，对官方任务可接受的处理窗口单独实测。
3. 北向 `GET /api/v3/contents/generations/tasks/{task_id}`、同一路径的集合 GET 及控制台读取
   本地快照，授权沿用 `user_id + app_id`。只投影平台 ID、客户模型、
   状态及经校验的标准字段。官方 URL 不随状态、日志或普通 Task.Data 写入。投影可展示合法的
   输出画幅、分辨率与时长，明确区分请求选择和实际输出。计费字段从已接受的账本事实读出。
4. 成功 CAS 后沿用 `RegisterVideoResultObjects`，仅登记主视频。由 `ResolveContentURL` 按
   冻结协议解析，必要时在转存 worker 内重新查询同一任务获得 URL。此 GET 专供回源，不能写状态
   或重算账单。CDN 请求无 Provider Key，沿用结果下载的 SSRF、重定向校验、响应和大小限制。
   成功后输出 `preparing/ready/unavailable`、授权 `302` 和 24 小时 OSS 签名。无真实尾帧事实
   时使用现有部件不存在语义。转存故障只影响交付。
5. 第一阶段复用现有 `cancellation_unsupported` / `delete_unsupported`。第二阶段先独立评估终态
   删除。待本地终态可信、资金已收敛且成功结果已托管，再用冻结连接调用 DELETE。只有任务 ID 与
   冻结值一致且 `action` 和 `status` 均为 `deleted` 才软删除。账单与内部审计保留。
   排队取消需要上游原子限制其操作为取消。即使发 DELETE 前读到 queued，也可能在两个请求之间生成成功，
   因此仅检查回包不足以防止误删。等官方确认可防竞态的契约后，再接现有取消 CAS、`action=cancelled`
   校验和退款。单查／列表始终以本地事实为准，无需接官方列表。

### 3.4 官方实际用量与资金

建议首批商业定价采用按媒体计量的 `tiered_expr`。客户单价由管理员按客户模型配置和审核，
冻结语义遵循现有表达式合同。 [任务用量表达式](../../pkg/billingexpr/expr.md#task-usage-expressions)新增官方协议的
schema 与 JD schema 分离，价格保存、预览、渠道诊断、公开价格和运行时预扣统一读取同一份
官方字段定义。下面的键是实施建议，确定后作为官方协议计量合同冻结。

| 表达式字段 | 预扣事实 | 成功结算事实 |
| --- | --- | --- |
| `u("output_seconds")` | 已验证的有效请求秒数。商业启用前验证实际输出不会突破该估算，或改用合同上界。 | `task.usage.output_seconds`，保留官方数值精度和来源，按验证后的计量边界检查。 |
| `u("input_video_seconds")` | 请求含视频时按总上限 15 秒估算，否则按冻结的无视频事实给 0。 | `task.usage.input_seconds`。含视频时要求可信数值，按总量上界校验。缺失与显式零区分。 |
| `u("input_image_count")` | 按已验证的图片节点计数，最多 9 张。 | `task.usage.input_image_count`，严格非负整数且不能超过冻结输入数量。首尾帧是否计入以实测为准。 |
| `u("resolution")` | 冻结有效的北向分辨率 `768p/2k`。 | 使用相同冻结计价选择。实际报告单独记录，出现不一致进入对账，禁止静默改档。 |

Token、总秒数、音频秒数可保留为合法上游证据，不用于该版本客户计费。官方账单对应的成本字段
与客户 quota 分开。媒体秒数需要可选数值，现有 `ActualUsageEvidence map[string]int` 仅适合整数证据，
建议在现有私有计费 JSON 内加官方协议的有界可选数值及字段来源。继续使用标准 Task 和账单表。

- **预扣。** 在 `BuildTaskBillingProbe` 中从已验证的请求和固定声明派生估算，禁止 JS 返回乘数。
  先校验数量和时长上限，再使用统一 checked quota 转换。含参考视频用 15 秒估算，无需下载或测量
  输入媒体。上线价式须证明预扣覆盖已验证的实际用量范围，首批采用经评审的非负单价和单调用量项。
  普通表达式试算仅证明样本正确，不能证明任意表达式的上界。仍使用现有差额、欠费和补偿机制。
- **接受实测。** 由冻结协议归一，宿主从有界上游回包读取字段，拒绝异常类型、负数、越界、
  缺失假零或互相矛盾的证据。成功状态与实测是否齐全分别处理。按冻结表达式引用的精确 `u()`
  字段判断是否可结算。无对应媒体可以用冻结的结构事实确定 0，存在该媒体且缺字段时保持待用量。
  在现有 Task 行锁合并中按字段接受第一份可信实测。后来观察可补齐缺项，不能覆盖已接受值。
  差异写脱敏审计。重复终态、补查与结算并发最终只产生一个资金目标。
- **补查。** 当前 `awaitSeedanceUsage`、`ClaimTaskUsageCheck` 和人工 review 入口分别有
  Seedance 或 token 条件，`RequiresMeasuredTaskUsage` 也只有现有 token 语义。新增官方的
  明确待量判定，复用既有 `awaiting_usage` 调度、领取和审核流程。补查仅 GET 同一任务。
  超出补查窗口进入待核实，保留原预扣。人工若用正式账单补齐字段，走现有有权限的审核入口和
  同一接受事实事务，并记录证据引用。官方字段独立校验，继续保留既有 Token 审核合同。创建
  attempt 24 小时释放规则独立于成功 Task 的实测补查。实测补查沿用最多 12 次、24 小时窗口
  以及人工重查一次的机制。
- **结算。** `HasMiniMaxBillingFacts` 识别经注册的两类 MiniMax 标准协议及冻结资金快照，
  `IsMiniMaxJDTask` 继续用于 JD 特有查询节奏。官方协议在 `ComputeTaskTieredBilling` 使用
  冻结请求条件和已接受的实测，写入唯一资金目标及复算记录，再交给 `ApplyTaskBillingTarget`、
  退款补偿和 `TaskBillingDelivery`。结算求值和资金写入前的目标校验应共用同一个
  官方用量就绪判断，确保人工操作和并发补偿同样遵守门槛。媒体计量保存在官方字段，由现有
  异步资金事务使用。失败和取消走现有终态退款，OSS 状态独立。
