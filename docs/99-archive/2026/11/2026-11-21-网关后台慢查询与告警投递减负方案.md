# 网关后台慢查询与告警投递减负方案

## 1. 问题与目标

2026-11-21，本地开发网关出现多组约 0.5 秒的后台 SQL 告警，涉及节点同步、插件加载、心跳、异步任务、
视频交付诊断和渠道告警邮件。分析目标是分清已观察到的业务影响，找出可以减轻主库负载且保持客户请求、
计费、退款和账单行为的优化。当前优先项是减少渠道告警邮件的重复空查，保留告警发现、唤醒和恢复时效。

账单明细导出曾在同一启动会话中失败。导出修复已经进入独立方案，本文件只保留用于区分两类现象的证据。
[客户账单明细自适应导出与验收方案](2026-11-21-客户账单明细自适应导出与验收方案.md)

### 2.3 账单导出复核

同一启动会话早些时候，账单列表和汇总各成功一次，两次明细导出在 5 秒批次期限结束时取消。复查历史参数，
旧分页跨 18 个冻结版本全局排序，在约 2,536 万行、48 GB 的 `billing_report_lines` 上选择并行顺序扫描。
按冻结版本分支取候选再归并，同一组参数的首批 1,000 行在 PostgreSQL 内约 18 ms。该测量只覆盖单批 SQL。
账单明细当前代码对稀疏筛选使用有界候选窗口，空窗口也可持久推进。已运行的测试覆盖空窗口续跑、压力暂停、
租约恢复、冻结版本可见性、退款符号和 100,001 行账单 CSV 完整性。此次没有在运行实例提交真实导出。

## 3. 优化方案

### 3.1 优先收敛渠道告警邮件空查

1. 保留先领取、领不到再准备的流程。首次查询为空时直接返回该结果。若查到候选但条件更新受其他 worker
   抢先领取影响，在同一次领取调用中最多再查并尝试领取一次，继续按 `next_attempt_at, id` 选择。数据库
   错误直接返回。没有领取到记录时，准备逻辑仅在新投递所在的事务提交成功后报告已入队。准备成功且实际
   有新投递时立即再次领取。若某个告警的准备事务失败，之前已提交的记录仍可领取，失败告警的待准备标记
   随事务回滚并由后续轮次恢复。资源告警继续使用原有准备入口。
2. 主节点保留三个 worker、每个 worker 5 秒定时补扫、容量为 1 的非阻塞唤醒及每轮最多连领 8 次。
   `next_attempt_at, id` 顺序、收件人及偏好复核、失败退避和过期租约转 `unknown` 沿用现有逻辑。
   租约回收和已入队逾期统计仍在独立循环每 5 秒运行。并发 worker 准备的新投递由已获得提交结果的
   worker 再领，未领到的记录由其它 worker 或定时补扫处理。
3. 保留表结构和投递状态。回退后恢复空准备也进行第二次领取的流程，使用相同的待准备标记、投递记录
   和在途租约。空查数回升属于回退后的预期行为。

三个空闲 worker 的领取读取 **6 → 3**，准备读取仍为 3 次，合计 **9 → 6**。加上每周期固定的一次
租约扫描和一次逾期统计，空闲时每 5 秒 **11 → 8**，回退后恢复 11 次。领取发生竞争时的额外尝试单列。
独立准备循环的探针曾测得 **9 → 4**，但混合积压对照中，提前准备将队列从 1 条增加到 17 条，并让新邮件
排在已到期的重试前。
本轮保留领取优先级。若目标环境测得仍有明显资源成本，再按实际语句耗时评估独立准备或逾期统计。
逾期时间会随时钟推进，即使投递状态没有变化，也需保留按时间发现逾期的能力。

### 3.2 归因与验收

- 开发进程按端口或实例拆分日志，给 SQL 告警保留可归因的实例信息。在同一观测窗口对齐客户 API 尾延迟、
  结算与日志写入时延、待退款积压、网关 `WaitCount` / `WaitDuration` 增量和 PostgreSQL 等待事件。
  复用已有前台计数，避免在每个客户请求里增加数据库操作。后台空查数下降和半秒尖峰消失分别验收。
- 本地隔离回归覆盖空闲空查数量、无收件人准备、三个 worker 并发准备与领取、到期重试优先，以及批次部分
  提交后失败并在后续轮次恢复。两条就绪邮件的回归强制两名 worker 首次查到同一条，验证落败方在本轮
  只追加一次领取，并将另一条就绪邮件提交。该场景在 SQLite、隔离 MySQL 和 PostgreSQL 通过，SQLite 同时
  通过 Go 竞态检测。既有测试覆盖本地告警送达、重启重试、租约到期与渠道告警 Redis 窗口。
- 目标环境按主节点本地唤醒和跨节点定时补扫分列告警时延。Redis 部署的非主节点也可以直接确认明确故障，
  各节点的内存唤醒只作用于本进程。分别核对确认至入队和入队至首次提交的时长。现有 60 秒逾期查询只统计
  已有投递记录，验收时另核对 `mail_pending` 中的数量和最老确认时间，覆盖配置不可读和积压场景。
  [本地确认与主节点投递](../../../../service/channel_alert.go#L188) · [逾期统计范围](../../../../service/channel_alert_delivery.go#L31)
- 使用相同前台流量与账单负载做基线和变更后对照。关注客户 API P95 / P99 与失败率、结算时延、
  预扣及退款结果、已发布账单金额和导出完整性。若出现可复现的前台退化或告警漏投，回退后台调度变更。
- 已运行的基线测试包括渠道告警持久化及租约、系统任务历史、异步轮询边界的 SQLite / MySQL / PostgreSQL
  三库测试，MySQL / PostgreSQL 节点同步，以及 Redis 告警窗口。客户鉴权、模拟上游的 Seedance / MiniMax
  请求、预扣、结算、幂等退款和视频诊断补写回归通过。上述结果属于本地与隔离测试，仍待目标环境对照验收。
