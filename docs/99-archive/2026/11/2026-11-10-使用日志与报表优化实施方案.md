# 使用日志与报表优化实施方案

## 1. 目标与范围

以现有页面为基础交付[汇总与详情体验](../10-product/使用日志与报表产品设计.md)，按
[报表日汇总架构](../20-architecture/账单计费-报表日汇总架构.md)减少交互扫描和 API 路径等待。
首期复用生产库。调度启停只看 CPU 和内存，API Key 调用优先。实施进展和未完成的切换门槛见第 5 节。

## 2. 实施前基线

| 路径 | 当前行为 | 实施切入点 |
| --- | --- | --- |
| 用量缓存落库 | [请求写缓存和后台刷库](../../model/usedata.go)共用互斥锁。后台持锁逐条查写 | 缩短临界区，核对失败重试和累加语义 |
| 使用日志 | [日志查询](../../model/log.go)列表执行精确计数和 OFFSET，统计另行聚合 | 首屏及翻页采用有界查询，精确统计按需触发 |
| 账单对账 | [客户列表](../../model/billing_customer_statement_list.go)先扫描后分页，[下钻](../../controller/billing_statement_logs.go)的列表和统计都读取完整候选范围。上游短缓存未命中时仍扫描账期 | 优先复用已确认版本，其余读报表投影，下钻与导出绑定发布版本 |
| 用量统计 | [现有聚合](../../model/usage_analytics_scan.go)按请求扫描日志、Task、交付和 Batch 事实 | 复用现有口径，移到日汇总任务。按天复核跨日退款和迟到交付 |

实施前用脱敏副本核对生产数据库方言、日志拓扑、已有索引列序、日峰值行数、90 天覆盖、源保留期
和报表新增存储量。抽样同等负载下的 API 请求、日志写入和后台读写开销。CPU 和内存用于调度，
API 时延、错误率和数据库等待只用于上线前对照验证。阈值、批量大小和截止时间以实际环境试跑记录确定。

## 3. 交付批次

### 批次一 · API 保护与使用日志

1. 将缓存交换限制在现有互斥锁内。用单一刷库执行将旧批次分小块写入，正在收集的增量继续进入新缓存。
   区分已提交、明确未提交和提交结果不明。需要重试的块使用稳定标识，将应用记录与增量同事务提交，
   避免提交响应丢失后重复累加。缓存刷库失败与日志、余额及结算写入分别处理。
2. 为控制台日志列表接入取消、查询时限和游标翻页，限制首屏默认查询范围，列表只读摘要。Request ID
   精确查找复用现有索引，详细计费解释、精确总数和费用统计按需读取。按
   [使用日志查询设计](../20-architecture/账单计费-报表日汇总架构.md#3-使用日志查询)验证首页与深页
   执行计划，并核对既有 API 消费者依赖的分页合同。
3. 验收阻塞中的刷库与并发请求写缓存、部分批次失败、提交结果不明后重试，以及同秒多条日志和持续
   插入下的翻页。管理员和客户分别核对可见字段、精确 Request ID 查询与时间筛选。

### 批次二 · 日汇总、关联与发布

1. 在独立报表文件中添加持久化投影和迁移，接入现有系统任务的调度和租约。先跑两个自然日的小范围
   样本，验证单执行槽、分批普通读、CPU／内存暂停、恢复和 03:00 触发。验证采样与生产库的部署
   拓扑匹配。
2. 将账单和用量的现有计算器接到同一发布过程。先做个人范围，按同样流程接入管理员用户和上游视角。
   上游视角由现有渠道核算结果生成 URL 汇总，并冻结 URL 与渠道的范围。
   同一报表生成汇总和最小明细，验证消费、退款、计量和缺失状态后短事务发布。启用正式月账单时，
   另验确认版的金额、明细与下载版本一致。
3. 检查现有日志、交付和 Task/Batch 更新路径能否覆盖迟到变化。以现有交付事实定位原完成日，保留
   有界回看并测试提交顺序交错。原记录补证、历史修复及月度渠道系数变更通过已知作用域触发定向重算。
   覆盖证据不足时明确标记待核对，再按故障原因恢复。当前部署若使用 ClickHouse，单独验收身份、
   排序和来源覆盖后开放该日志来源的历史发布。

### 批次三 · 页面、导出与灰度

1. 沿用现有侧栏，个人区提供我的账单和用量统计，管理员区提供账单对账和用量统计。两个用量统计
   入口都提供每天和每周。管理员账单对账提供用户和上游 URL 两个视图。汇总先显示业务指标，用户、
   API Key、模型和渠道详情按需加载。状态提示按项目要求提供中英文。
2. 复用既有导出任务和授权。新发起的历史导出冻结当前发布批次及筛选范围。使用日志继续走普通明细
   路径，账单与用量下钻使用历史批次。故障时保留上一份已发布结果或显示待生成。
3. 在脱敏生产数据副本上对照既有计费口径，先验证「周一完成、周三退款」，再由少量范围扩大到 90 个
   已结束自然日。检查逐日覆盖、存储增长和 API Key 调用的延迟及错误率。关系库部署启动后自动排程；
   待生成范围在页面显示进度，页面与导出读取已发布批次。

## 4. 验收与上线门槛

| 验收项 | 通过条件 |
| --- | --- |
| 资金事实 | 周一消费 100、周三退款 30 的账单按发生日展示；用量周一净额 70、调用一次。负净额、跨月和零差额结算保持原口径 |
| 净费用与费用明细 | 个人和管理员默认直接看到净费用。同日扣 100、退 30 显示净费用 70，展开和逐笔导出为两笔。跨日完成退款同样按常规费用展示 |
| 待退款 | 验证确认应退款后恰满 24 小时、超过 24 小时仍未退清、以及已退清三种情况。只有第二种显示待退款。另验资金已退而日志未交付时的显示，以及重复刷新后净费用一致 |
| 可追溯性 | 同一发布版本的历史汇总、筛选下钻、导出可对上。重复交付、刷新中断和重跑结果一致；缺失证据明确标记 |
| 页面与日志查询 | 两个用量入口都支持每天和每周，管理员可从 URL 汇总展开所属渠道。使用日志首屏与深页无精确计数、无深页 OFFSET，精确 ID 查询命中目标库可用索引 |
| 用量排行 | 模型和管理员渠道排行可按调用次数、Token 或金额切换，读同一发布批次。用调用最多但费用较低的模型验证排序切换。排行分页不影响总览；补扣和退款不增加客户调用次数；缓存子项不重复计入总 Token；客户净费用和上游参考费用分别核对 |
| 迟到与批次 | 已保存的 90 天以前日期可修正；多实例只执行一份；重启后复用已经完成的候选投影；用户查看期间版本切换时仍能读取原批次 |
| API 保护 | CPU 或内存越线时按批停止，恢复后继续。数据库变慢时取消和批级时限生效。用同等 API 流量对比有无报表任务，验证 API 时延、错误率、日志写入和结算表现满足现网要求 |
| 共库与权限 | SQLite、MySQL、PostgreSQL 迁移和核心查询通过；实际启用 ClickHouse 时补验日志侧。普通用户、管理员和导出任务按现有授权范围取数 |
| 历史交付 | 最近 90 日逐日有发布或明确覆盖状态。迟到事实入库到修正版发布的 24 小时目标以实测验收；持续高压时保留延迟状态，由 API 优先规则决定恢复时间 |

代码实施按批次运行相关 Go 模型、控制器和服务测试，前端用 Bun 验证查询取消、状态和权限。完成
真实数据核对和共库压力验证后，再将当前事实收敛进现有文档并按归档规则处理方案。

## 5. 当前接线与切换门槛

- 控制台使用日志已接入游标分页、近期默认范围、取消、时限和按需统计。列表返回摘要，计费解释与原有
  扩展详情按单笔读取。现有页码接口仍可用。控制器接线集中在列表和统计入口的显式参数分支。
- 日周用量已接入独立后台任务。生成使用单槽租约和每个来源一个连接的独立池，保存可合并的日投影；
  读页面按范围合并已发布日，用户下钻、周到日下钻和 CSV 绑定页面的版本。缺少发布记录时显示未发布。个人模型排行、
  管理员渠道排行和可由既有视频资金事实证明的待退款状态已接入。旧代际至少保留八天供已提交导出读取。
- 个人账单、管理员客户账单及上游对账已接入日投影。原有自然月页面按日版本合并，客户汇总沿用未取整
  中间值，上游参考金额沿用逐笔取整。每个自然日冻结 URL 归属，渠道可在同一账期内出现在不同 URL 下。
  账单汇总、展开、逐笔及 CSV 使用同一日期版本集合。正式已确认月账单及下载优先沿用现有确认版本。
- 正常同日扣退款合并为净费用。跨日退款按发生日入账。个人与管理员账单的待退款提示独立读取已确认的
  退款意图和完成状态，超过 24 小时仍未退清才显示。
- 关系库部署自动运行报表生成，控制台与新导出统一读取已发布版本。今天的估算统一每 180 分钟更新。
  昨天在北京时间 03:00 后开始生成。用量和账单共用一个任务槽及独立连接池，CPU 达 70% 或内存达
  80% 时在批次之间等待。ClickHouse 日志源的日汇总尚未验收，生产验收按 PostgreSQL 拓扑进行。
- 已完成的候选投影持久化后可以跨进程复用。自动、回填和重算批次失败均按日期退避，其他日期可以继续。
  同一组已投递跨日退款的相关日期在同一事务内切换发布引用。候选投影内部的原始扫描中断后会重新扫描。
- 账单后台按已投递的任务事件、日志追加游标和近期回看发现迟到数据。渠道月度系数更正按渠道范围重排。
  Root 可通过 `POST /api/billing/admin/reports/rebuild` 提交 `{"date":"YYYY-MM-DD"}` 定向重算。
  已发布旧版本保留至少八天，执行中的导出继续保留引用。发现已知源清理时标记覆盖不完整，已有更完整
  版本时保留该版本。
- SQLite、MySQL 5.7.44 和 PostgreSQL 15 已验证账单投影及冻结明细读取。真实生产的 90 天容量、
  迟到记录覆盖和 API 延迟对照仍是切换门槛。在脱敏副本验证覆盖、资源使用与读取。
