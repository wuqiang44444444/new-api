# 上游对账按计价依据核算方案

## 1. 问题与目标

账单只回答「这笔按什么算、能不能算」。每笔按当时生效的计价合同、计量与结算事实核算。
计量采集、字段格式与日志完整性的诊断由对应组件负责。账单读取这些组件提供的事实，
只在无法确定所展示的金额时说明缺少哪项计价依据。

本次拟调整上游对账的核算状态、逐笔原因和汇总口径。客户账单继续以实际资金流水展示净结算，
上游对账继续以可核验的本站原价和渠道月度系数计算参考金额。供应商实扣由供应商侧账单或成本明细核验。

## 2. 当前实际情况

以截图所用的 2026 年 11 月账期和已发布日报为准，在本地 PostgreSQL 只读核对了逐笔投影及源日志。
截图截至北京时间 2026-11-13 00:00:26，页面显示已发布 12 天、共 13 天。

| 账单记录 | 共 110,755 条。48,060 条按现有口径证据齐全，62,695 条金额可核算但标记用量缺失，原价无法核算 0 条 |

当前逐笔分类将缓存读写不可确认直接计入用量缺项；汇总据此提示待核对。日报发布覆盖也有独立的状态，
因此仍需保留「已发布 12 天、共 13 天」的覆盖提示。供应商实际账单及历史原始响应未在此次核对中验证。

## 3. 优化方案

### 3.1 逐笔金额的确定顺序

1. 读取同一事件已保存且可核验的折前金额；渠道测试沿用自己的已结算定价记录。明确的零金额照常入账和展示。
   实际扣减与退回继续来自资金事件。只有现有中性倍率规则的条件全部满足时，才可直接把入账金额作为折前金额。
2. 需要复算时，按当次冻结的公式、计费方式、档位、单价、汇率和实际参与计价的量计算，只要求会影响
   该笔金额或档位的输入。优先采用已冻结的计价输入，复用现有用量归一化、取整和入账核验。
   按 Token 运行原计价规则；按次用冻结单价乘已确认次数；按秒用冻结单价乘已确认计费秒数。
   按次与按秒的计价无需缓存 Token。
3. 已保存金额不可用，且关键计价依据不足或复算无法与原入账核验时，原价留空并标为「待核算」，
   原因指向具体的计价输入或核验结果。历史金额使用历史配置，缺少金额依据时保留已知金额小计。
4. 渠道折后参考金额逐笔应用该记录日期有效的渠道月度系数，按现有精度取整后汇总。
   解析系数时沿用当月设置、上月有效系数和默认 ×1 的既有规则。当月系数明确待确认时，只提示折后参考
   金额缺口。页面随当前有效系数计算，导出按提交时冻结的系数计算。退款和任务差额沿用既有事件口径。

### 3.2 缓存计量的计算规则

| 情况 | 计价输入与结果 |
| --- | --- |
| OpenAI 兼容接口约定写入量可省略，`cache_write_tokens` 和 `cached_creation_tokens` 均未上报 | 当次计价的写入量为 `0`。写入项贡献为零，基础输入量无写入扣减 |
| 任一别名提供有效非负整数，包括显式 `0` | 使用该值。另一个别名同时提供有效值时，沿用当前归一化规则取较大值一次 |
| 公式和档位判断均无需写入量 | 跳过写入项；缺省、非法或无法辨认的写入字段均不影响已能确定的金额 |
| 需要写入量，且已冻结当时采用的计价值 | 使用冻结值。原响应是否上报该字段不改变已记录的计价输入 |
| 需要写入量，且历史记录无法证明是合法省略，也无可用冻结值 | 先读取可信已结算金额；仍需复算且缺少该输入时，原价待核算 |
| 缓存读取或图片缓存细分 | 优先用冻结计价输入。合同约定可省略的读取总量缺省按 `0`；只有模态细分缺省时沿用原有聚合缓存计价，保留已知的读取总量 |
| Anthropic 独立缓存计量 | 按原规则解释写入总量、5 分钟和 1 小时分项。总量明确为零时，两项均为零；正数总量已知但计价依赖的分项不可用时，复算还需对应分项或可核验的已结算金额 |

正常省略以当次接口或日志写入合同为依据。显式 `null` 仅在合同定义其等同省略时采用缺省值；
负数、非整数和格式错误沿用原采集或归一化规则。仅凭历史日志的 `reported=false` 无法区分字段缺省与
不可解析。已有可信金额或该变量不影响计价时，账单无需作此判断。
Claude 专用 writer 和旧渠道测试按各自历史合同复算，不能套用普通图片与文本结算 writer 的省略规则。

沿用既有 Token 归一化。OpenAI 兼容输入总量中的子项按原规则拆分，避免重复计费。
表达式的档位条件也可能使用计量，例如 Anthropic 的 `len` 包含缓存读取和写入；核算所需输入须包含
这些间接依赖。具体规则见[计费表达式设计](../../../../pkg/billingexpr/expr.md)。

### 3.3 报表投影与发布

- 「原价待核算」以逐笔本站原价是否可核验为唯一条件。原价为零属于已核算。同一条账单记录只计一次，
  原价已核算数等于记录总数减原价待核算数。折后参考金额缺口在渠道与汇总金额列说明，沿用待确认渠道数。
- 总览、渠道与模型汇总、逐笔筛选和 CSV 共用日报的 `amount_gap` 分类及其计数。
  既有的用量与其他证据分类继续支持授权追溯，保持原诊断口径，脱离账单主状态和待核算原因。
  计费用量按可核验的已记录计价值展示，明确为零时显示零，缺少可展示的值时留空。日报发布覆盖独立显示。
- 实施从上游逐笔金额及分类投影接线，复用现有原价和折后参考金额入口。原生结算、日志采集和
  客户资金流程保持原口径，原始日志禁止回写。将 `CustomerOriginalReplayVersion` 从 4 升到 5，
  通过现有游标重建历史日报，先校验候选再切换发布指针。将共享 `dailyBillingExportFieldVersion`
  从 23 升到 24，按现有格式检查处理未完成旧任务。总览、逐笔和导出使用同一组日报代际；
  重新生成的导出按其绑定的日报、范围和折扣解释，既有产物和已确认月账单继续绑定原版本。
  见[报表日汇总架构](../../../20-architecture/账单计费-报表日汇总架构.md)。
- 实施完成后同步修订对账架构的证据覆盖统计与缓存计量说明。

### 3.4 验证与剩余事项

- 覆盖正常缺省、显式零、单一别名、双别名不重复累加、字段非法、冻结计价值优先、公式直接或间接
  依赖计量、Claude 分项不可复算、按次及按秒无需缓存、可信金额为零、原价已知而渠道系数缺失。
- 用同一批日报来源重建候选版本。截图中的 62,695 条退出账单缺项提示，原先 48,060 条已核算记录继续通过。
  110,755 条记录均可核算本站原价。原价 $5,829.251498、折后参考金额 $5,634.783894 和
  19,666 条已计价测试均应一致。比较总览、逐笔及导出的待核算计数，核对旧代际重生成和新版新导出，
  并确认发布天数提示仍由日报覆盖决定。
- 核对历史无上报标记、原价可核算但折扣待确认及已有可信金额但用量异常的反例。对照客户账单、
  原始日志、扣减和退款，逐笔确认相同。

## 4. 实施与本地验证

- 页首、模型状态筛选、逐笔原价状态和汇总 CSV 采用本站原价核算口径。折扣待确认按渠道去重，
  在参考金额旁提示。逐笔记录及逐笔 CSV 仍保留独立的用量诊断。
- 日报解析版本升至 5，日报导出格式版本升至 24。上游导出重新生成测试验证保留已绑定日报版本、
  渠道系数与筛选范围，并使用新导出格式。
- 在隔离的本地 PostgreSQL 副本重建 2026-11-01 至 11-11 的有记录日报，并带入截图对应的
  11-13 空日报。分别读取原代际、混合代际和重建代际，均复现已发布 12 天、共 13 天，
  110,755 条记录、原价待核算 0 条、原价 $5,829.251498、折后参考金额 $5,634.783894。
  19,666 条已计价测试保持一致。逐笔对照两版记录身份、客户扣减或退款、原价及计费请求数，差异为零。
- 目标环境部署及其历史日报切换待执行。生产切换范围以实际已发布日报和可用来源为准。

- 当前账单复算版本为 10，缓存写入兼容字段取较大值；只有已识别的写入合同允许将省略解释为零。
