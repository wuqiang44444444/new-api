# 邮件明细与错误分析增强方案

## 1. 问题与目标

钱包拒绝摘要目前只列账户 ID 和汇总次数。收件人需要打开后台，才能确认客户身份、了解具体失败和判断
先查哪里。将这一改进扩展到现有通知邮件。让收件人从邮件正文就能看到发生了什么、有哪些记录可以核对、
接下来可以做什么。

对于错误类邮件，提供当前报告范围内最新五条相关错误。对于资源、资金和账户操作类邮件，提供相应的读数、
流水或操作事实。保留既有收件权限、开关、发送频次、事件去重和持久投递规则。

## 2. 当前实际情况

- **系统错误日报仍会发送。** 报告收件人已配置、该类邮件开启且活动发信通道可用时，系统在北京时间次日
  06:00 后、汇总完成时发送前一自然日的报告。它已有错误分类、重点错误组、分析和筛选链接。
  API 错误事件仍按既有规则写入后台。旧小时错误邮件已停止，运行中的错误日报与钱包拒绝摘要分别受各自开关控制。
- 钱包拒绝摘要按北京时间十分钟窗口汇总本站钱包不足拒绝，显示账户数、拒绝次数及最多十个账户 ID，
  附带时间窗和错误原因筛选。账户纳入摘要后按自然日去重。
- 错误事件已有时间、账户 ID、用户名快照、请求 ID、接口、模型、HTTP 状态、阶段和结构化原因等可用字段。
  邮件类型和收件规则已有[统一目录](../../../../model/mail_preferences.go)。邮件生成与安全边界见
  [账户与邮件架构](../../../20-architecture/运维-用户生命周期邮件通知架构.md)和
  [系统错误报告架构](../../../20-architecture/运维-系统错误报告架构.md)。
- 本方案依据代码、当前文档和本地预览拟定。当前部署的邮件到达情况及 Microsoft 365 真实收件尚未在本轮核对。

## 3. 优化方案

### 3.1 各类邮件正文

| 邮件类型 | 相关明细 | 分析及去向 |
| --- | --- | --- |
| 系统错误日报 | 保留全日分类和重点错误组，增加上一自然日已记录的最新五条错误。适用时附客户名称和 ID | 优先指出已确认渠道异常、主要错误类型和受影响范围，链接当日错误日志 |
| 客户钱包拒绝摘要 | 展示最多十个本封覆盖账户的名称、ID、窗口内拒绝次数。另列这些账户在当前窗口内最新五条钱包拒绝 | 用全量窗口统计说明失败是否集中在少数客户，指向钱包余额和预扣所需额度的核查入口 |
| 渠道故障、渠道欠费和巡检结果 | 按告警渠道、操作及判定窗口展示最新五条相关失败。已有巡检结果时，展示巡检时间及结果。上游低余额邮件展示可用余额及查询时间 | 说明失败集中于哪个操作、模型或渠道范围，指向渠道配置、巡检或筛选后的错误日志。恢复通知展示已确认的恢复时间 |
| 资源、证据清理和资金告警 | 展示与事件直接相关的记录。例如资源读数与阈值、清理失败阶段、占款释放或退款状态。源头有多条明细时，最多展示最近五条 | 说明触发条件、影响范围和建议检查的后台任务或流水 |
| 平台用量、客户情况和个人用量日报 | 有失败记录时，增加报告日期内、报告范围内最新五条。平台和客户日报可显示客户名称和 ID。个人日报仅展示自己的记录 | 解释计数、覆盖范围和集中情况，分别链接管理员用量或个人用量 |
| 钱包回执、财务日报和财务告警 | 使用已提交的操作事实。回执带受影响账户名称、ID、流水号和余额变化。日报与告警保留汇总并附相关操作记录 | 根据故障类型或变更阈值建议核对交易、人工操作或审计记录 |
| 用户余额或订阅提醒、账户安全、验证码、欢迎和 API Key 创建通知 | 展示与当前收件人相关的必要事实。例如低余额与阈值、已确认的拒绝、操作类型及可用时间、验证码有效期 | 提供打开钱包、检查账户、查看 API Key 或完成验证等对应操作 |

### 3.2 样本、名称和分析口径

1. **按邮件自己的范围取样。** 复用现有事件分类、时区和权限范围。按事件时间倒序，再按事件 ID 倒序稳定排序，
   取全局最新五条。少于五条时展示实际条数。钱包摘要只取本封已纳入的账户，渠道邮件只取当前告警范围，
   日报只取指定自然日。明确区分无匹配记录、记录不完整和暂时无法读取。
2. **名称和 ID 一起展示。** 批量从主库读取显示名称，空值时用用户名。账户已不可查询时，可用该错误事件已保存的
   用户名快照，缺失则显示「名称不可用」并保留 ID。后台以 ID 或请求 ID 核对归属。只按收件人可见范围展示名称。
3. **样本字段使用白名单。** 展示北京时间、客户名称与 ID、API 路径、客户模型、HTTP 状态、可读原因、请求 ID 中
   实际可用的字段。没有客户归属的运维事件省略客户字段。对名称等动态字段做长度限制和 HTML 转义。
   请求与响应正文、自由文本错误、凭据、完整签名 URL 和邮件地址留在原有授权边界内。
4. **分析来自全量统计及已确认事实。** 例：三位客户共七次拒绝，其中某客户占四次，建议先核对其钱包与预扣额度。
   样本用于说明具体情况。全量统计、时间或覆盖不足时标出限制，余额、实际损失和根因仅在有可信记录时展示。
5. **沿用双语 HTML 模板。** 邮件顶部放摘要，中段用纵向卡片展示最近明细，最后给出排查动作和主按钮。
   钱包摘要保留窗口和原因筛选，首版请求 ID 供复制。需要单条直达时，再补后台路由的请求 ID 参数及权限测试。

### 3.3 实施顺序及接线

1. **先做系统错误日报、钱包拒绝摘要和渠道故障告警。** 在各自的后台生成阶段调用有明确范围、字段及时间预算的
   查询。共用错误样本的呈现规则和模板片段。钱包摘要先确定候选账户，样本读取、批量补名在入库事务外完成，
   入库时复核纳入集合，集合变化时重新准备该窗口。正文、收件地址和既有去重记录保持原子提交。
2. **接入其他日报、资金和资源通知。** 优先使用对应系统任务、发布版用量或财务流水的已存事实。个人日报用账户
   权限收窄查询，后台链接仍走现有授权。验证码、安全邮件等直接复用各自操作的结构化输入。
3. **保持错误采集和发信入口稳定。** 样本与名称在后台限时读取后随正文冻结，投递重试使用既有快照。主摘要已
   生成时，补充信息读取失败可标记「明细暂不可用」，同时记录脱敏诊断。邮件明细不增加 Relay 热路径的数据库
   查询或网络发信操作。现有错误日报开关、发信时间和错误日志留存分别沿用既有配置。

### 3.4 验收与风险

- 验证 0、少于五条、超过五条及同秒事件，确保按范围选对样本。同一窗口混入不相关账户或渠道时，相关邮件
  范围不扩大。历史已冻结邮件及投递重试的正文保持一致。
- 验证缺失名称、账户改名、已删除账户、HTML 特殊字符和较长内容。名称读取失败时，账户 ID 仍可用。
  确认分析基于全量统计，样本和覆盖说明与邮件展示一致。
- 验证错误日报继续独立发送。关闭钱包摘要、改变收件名单、待投递重试及上游明确拒收，仍符合各自邮件规则。
- 用隔离数据库和模拟事件渲染简体中文、英文、桌面及 390 像素宽度的预览，核对金额、名称、五条明细、
  换行、按钮和后台筛选。个人、运维、财务邮件分别验证数据范围。真实邮箱验收单独授权后进行。
- 分开验证 SQLite、MySQL、PostgreSQL，并覆盖主库与日志库分离。部署使用 ClickHouse 日志库时，按现有支持
  范围核对查询。重点观察高基数窗口的查询预算、邮件大小和报表积压。

## 4. 实施与验收记录

- 系统错误日报、钱包拒绝摘要、渠道故障告警已接入各自的错误来源。渠道样本只使用纳入告警判定的失败。
  钱包摘要在持久化时复核账户集合，邮件和去重状态在同一事务提交。
- 平台及个人用量、客户与财务日报已补充各自范围内的明细。巡检、资源、请求证据清理、占款退款、钱包和
  账户通知附带相应的业务事实和后台入口。源码当前边界见[账户与邮件架构](../../../20-architecture/运维-用户生命周期邮件通知架构.md)
  和[系统错误报告架构](../../../20-architecture/运维-系统错误报告架构.md)。
- 本地预览使用模拟数据及隔离 SMTP，核对 31 个简体中文及英文预览的桌面和移动版。SQLite、MySQL 5.7、
  PostgreSQL 16 已覆盖钱包汇总和错误样本查询，独立的 ClickHouse 25.8 日志库已覆盖同秒客户筛选及分页。
- 待目标环境验收实际邮件客户端表现、后台权限、已配置发信通道和真实收件，并观察高基数时间窗的查询预算和队列积压。


## 5. 复审修复

附加邮件允许样本缺项、迟到日志和统计近似。金额、补单状态和告警确认只依赖业务事实。邮件读取使用普通查询，
不对资金、渠道或配置加显式数据库锁。邮件任务通过唯一键、条件更新和投递租约控制重复发送。

- 财务邮件准备从资金事务移出，改由后台读取已提交的新流水，逐类创建幂等投递。
- 渠道、资源与证据清理告警先持久化，再准备邮件。渠道明细读取失败时，使用已有样本，发送前保留收件范围和偏好复核。
- 渠道欠费保留真实网关请求 ID。巡检展示结构化原因。用量日报标注诊断样本和统计口径，财务及 Root 页面链接给出对应的核查指引。
