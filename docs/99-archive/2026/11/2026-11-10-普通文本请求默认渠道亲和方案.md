# 普通文本请求默认渠道亲和方案

## 目标与状态

让同一 API Key 的连续文本请求优先复用本平台管理的同一渠道，减少跨上游缓存域造成的重复写入。客户无需修改
请求。优化以保持现有调用可用性为前提，不承诺每次命中上游缓存。首 token 时间、缓存用量和费用用于验收，
不作为实时选渠变量。

综合评审认为，同级分流跨越上游缓存域时，默认亲和可以减少重复写入。实际收益取决于目标请求占比、渠道
对应的缓存域及可复用前缀。已匹配会话规则、首选层只有一个渠道或仅在第三方网关内部换渠的请求，不会因
新增默认亲和减少这类分流。开发环境的 GPT‑6 Astra 固定渠道对照验证了直连样本的收益空间。Opus 预检未形成
可用对照，客户的中转结果也不能直接归因于本平台路由。

代码已实现。双缓存域 Opus 开发对照验证了预热后串行的缓存和输入费用收益，冷启动并发仍无可归因的亲和收益。
生产发布仍需验证目标流量占比和负载。对照步骤、接线和结果见
[默认渠道亲和实施方案](../80-dev/2026-11-10-普通文本请求默认渠道亲和实施方案.md)。

## 首期行为

首期按方法和精确路径识别以下入口。新增覆盖须同时满足原生分发、普通 HTTP 文本生成、输入自包含，且未匹配任何现有会话规则。

| 入口 | 新增覆盖的请求 |
| --- | --- |
| `POST /v1/chat/completions` | 未匹配现有会话规则的普通聊天补全请求。Codex 和 Claude 的内置规则原本不覆盖此入口。 |
| `POST /v1/responses` | 未匹配现有会话规则的自包含 Responses 请求，例如缺少 `prompt_cache_key` 且没有匹配其他规则的请求。 |
| `POST /v1/messages` | 未匹配现有会话规则的自包含 Messages 请求，例如缺少 `metadata.user_id` 且没有匹配其他规则的请求。 |

引用 `previous_response_id`、`conversation`、上游文件、向量库或既有工具容器等状态，或无法确认输入自包含时，
沿用现有路由。WebSocket、媒体、异步任务及其他专用入口沿用现有行为。
Responses 中的函数调用和文本结果可以参加默认亲和，前提是两者按 `call_id` 在同一请求内配对。

- 显式固定渠道和现有会话规则优先。**已匹配会话规则但未命中渠道绑定**时，沿用该规则原有的未命中处理。
  本次照常选渠，保留该规则的键、请求头透传、重试和写入行为。满足该规则的原有写入条件时，仍可建立会话绑定。
  已匹配规则但读取异常或模式为 `off` 时，也沿用原有处理。这些请求均跳过默认绑定的读取和写入。
- 以鉴权后的 API Key 内部 ID、客户请求模型、协议入口和有效路由范围区分绑定。同一账号的不同 Key 各自建立绑定。
  缺少有效 Key ID 时走普通选渠。多个对话使用同一 Key 且没有匹配会话规则时，共用同范围的渠道偏好。
  普通、Auto 和客户合同路由均使用本次请求原有的权限、模型、协议、分组、优先级和合同约束。默认绑定只在
  普通选渠本次首次尝试会使用的**有效优先级层**内生效，未命中时按现有权重选择。Auto 先确定首个有候选的
  分组，合同先汇集授权的候选。重试继续遵守现有可重试条件、次数和分组规则。
- 只有实际成功的请求可建立或刷新绑定。流式请求须有可信成功终态，失败、中断或结果不明确时跳过写入。
  Responses HTTP SSE 使用现有的协议终态标记，正常完成可写入，只有 EOF 不写。Chat Completions 请求多个流式
  结果时，需要确认所有请求的结果都已结束。仅首次选择所在范围及优先级层内
  的成功渠道可更新该层绑定，跨层或跨 Auto 分组的重试成功不覆盖仍有效的首选绑定。沿用「切换成功后更新会话
  绑定」。关闭后，换渠成功保留旧绑定，无旧绑定时此次不建。允许首次并发在绑定建立前分散，后完成的同范围、
  同层有效成功请求可以覆盖先写入的绑定。
- 亲和缓存是尽力使用的选渠提示。无可用绑定或缓存异常时，短时限内回到普通选渠。亲和写入失败不改变已完成
  请求的结果。默认策略不新增客户端字段、管理开关或数据库迁移。
- 后台「清空全部渠道亲和性缓存」覆盖显式规则与默认 API Key 绑定。按规则清理只处理所选规则。

## 已知风险与边界

| 风险 | 首期处理 |
| --- | --- |
| 渠道 ID 稳定，实际缓存域仍会变 | 渠道内多 Key、第三方网关二次分发、输入前缀变化和缓存过期都可能产生未命中。只对本平台直接管理的渠道落点作结论。 |
| 单个大流量 Key 绑定后造成渠道负载集中 | 首次仍用现有权重分配，保留重试和全局关闭能力。上线前看每渠道并发、限流和实际流量份额，首期不增加动态调度。 |
| 同一账号使用多把 Key | 绑定数量随活跃 Key 增长。新 Key 独立预热，跨 Key 轮换发送相同前缀时，缓存收益取决于实际渠道落点。 |
| 高优先级渠道仍启用但持续限流 | 下次首选继续遵守现有优先级，可能再次尝试该渠道。对照检查重试与尾部延迟，不增加新健康状态或回切逻辑。 |
| 同名分组、协议或合同造成误复用 | 用实际候选资格复核绑定。不同的 Auto 范围、合同或协议不能靠相同的分组名共享绑定。 |
| 默认绑定挤占现有会话容量 | 默认绑定使用独立命名空间及有界的本地容量，不共享旧规则的本地 LRU。Redis 部署须按新增键量和峰值负载验证内存余量、淘汰和旧规则的命中。共享实例上的键前缀本身不能隔离淘汰。 |
| Redis 异常增加等待、流已返回 200 后失败 | 默认亲和读写使用独立短时限，读取异常时回到普通选渠，故障日志限频。持续慢响应必须通过延迟验收，是否需要临时跳过默认读取由故障测试决定。 |

渠道亲和与上游提示词缓存是两层机制。Anthropic 的缓存域依平台而异，匹配需要稳定前缀，冷启动并发还可能
遇到缓存尚未写入。OpenAI Responses 的 WebSocket 连接内状态在断线后消失，同渠道重连无法恢复该连接状态。
依据：[Claude 提示词缓存](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)、
[OpenAI 提示词缓存](https://developers.openai.com/api/docs/guides/prompt-caching)、
[OpenAI WebSocket 重连](https://developers.openai.com/api/docs/guides/websocket-mode#reconnect-and-recover)和
[Envoy 亲和负载上限](https://www.envoyproxy.io/docs/envoy/v1.33.2/api-v3/extensions/load_balancing_policies/ring_hash/v3/ring_hash.proto)。
共享实例的容量限制见 [Redis 淘汰机制](https://redis.io/docs/latest/develop/reference/eviction/)。

## 改代码前的收益验证

先从现有路由日志估算未匹配会话规则、首选层有多个直管候选、实际跨缓存域分流的请求量和输入 token 占比。
在隔离测试环境，用现有路由和固定到一个已确认缓存域的渠道做 Opus 对照。保持请求、模型、计费组和节奏可比，
各组独立预热，冷启动并发单独测试。确认现有路由样本确实发生跨域分流，再比较读写缓存 token 和单位输入费用。
没有可复现的收益时，先排查缓存域、前缀和断点，不将提高同渠道率作为实施依据。样本与操作要求见
[改代码前的 Opus 固定渠道对照](../80-dev/2026-11-10-普通文本请求默认渠道亲和实施方案.md#3-改代码前的-opus-固定渠道对照)。

## 上线前验收与发布

1. **路由与兼容。** 同 Key、同模型、同接口和同范围的请求建立绑定后在同层复用。同一账号的不同 Key 独立建立绑定。
   首次按权重、停用或移出范围后重新
   正常选渠、较低优先级成功后不抢占下次首选或挤掉仍有效的首选绑定。覆盖普通组、Auto、合同、旧会话规则、
   管理员关闭和带上游状态引用的 HTTP 请求，验证原有鉴权、重试、计费组和响应行为。
2. **故障与流式。** 对照冷启动并发、已绑定并发、上游 `429`、Redis 慢读或读写失败、流式正常终止和中途断开。
   验证请求不会因亲和缓存异常失败或被明显拖慢，且没有成功证据时不写绑定。验收须记录实际缓存等待预算和
   故障注入的观测结果。分别验证本地容量达到上限、Redis 峰值和持续故障时，已有会话行为无实质退化。
3. **缓存收益与用户影响。** 实现后在改代码前的两组基础上加入默认亲和组，按同一口径复测。比较同渠道率、
   读缓存 token 占总输入 token 的比例、
   写缓存 token、实际输入费用、失败率、重试次数、每渠道负载和 P95 首 token 时间。读缓存与写缓存可以发生在
   同一次请求。客户反馈的 120 次中 111 次写、9 次读来自含第三方二次分发的场景，不作为本次发布的效果基线。
4. **发布门槛。** 对照前记录适用的现有服务指标或可接受波动范围。只有缓存收益可复现，且用户成功率、重试、
   延迟和渠道负载无实质退化时，才能发布。按渠道和高并发 Key 分别检查。发布前演练多实例版本回退，确认原有规则
   和路由恢复时间在允许范围内。测试环境的开关对照不等于生产灰度。

通过验收后，新部署默认开启，存量部署升级后直接全量生效，保留已保存的规则和关闭设置。出现用户可感知的
回归时，按演练步骤回退到上一已验证制品。关闭全局「会话保持」会同时暂停现有会话规则，仅作为明确接受该影响
后的应急手段。回退时限无法满足要求时暂停发布，再评估能单独停用默认亲和的方式。上线证据与生产结论在实际
验证后补记。
