# 在线日志尾延迟归因与日报减负方案

## 1. 问题与目标

上次隔离压测在低负载段测得在线日志写入 P99 从 41.21 ms 升到 270.62 ms，
自适应组全程计了 26 个失败，停用组计了 0 个。需要区分报表共库争用、前台采样开销以及
宿主与测试负载波动，找出减少后台工作量的方案。在线请求、资金结算、退款和日志持久化优先，
日账单、日用量和导出可以晚一些交付。正确定义已发布、待生成和待核对状态。部署方无需新增
开关、许可文件或调速配置。 [上次实施与复测记录](2026-11-21-日账单与日用量自适应调度方案.md#4-实施与复测)

## 2. 原始数据能确认什么

26 是原压测的**全程合并计数**。当时压测器把发送队列满、HTTP 客户端异常、
HTTP 非 204 和消费日志 SQL 报错加到同一个计数。账户查询和结算异常经 HTTP 非 204 计入。
消费日志 SQL 错误由 `RecordConsumeLog` 记录日志，测试路由仍可返回 204。一条请求也可能
同时命中 SQL 错误和客户端异常。原始逐请求产物已随临时库清理，保留下来的结果没有按请求、
按阶段的错误明细，**因此无法把原先 26 次逐项分到具体环节**，也无法用它推断 26 笔请求、
26 笔日志丢失或 26 笔结算失败。41.21 和 270.62 ms 属于低负载窗，26 属于全程，
两个统计口径不能对应到同一批请求。 [实际消费日志入口](../../../../model/log.go#L342) ·
[在线日志持久化边界](../../../../model/report_log_write_observation.go)

原压测集中向同一钱包做结算。结算入口会访问账户并写事务，日志测量则在日志写入入口开始。
因此钱包事务本身的耗时在结算指标中。如果大量钱包事务占着在线池连接，后来到达的日志写入
也会通过等连接及事务开始阶段受影响。要区分这一现象和日志表的慢 INSERT，应对同一条请求
同时标记账户、结算、日志事务及客户端结果。 [结算入口](../../../../service/billing.go#L66) ·
[钱包写入路径](../../../../service/quota.go#L429)

## 3. 隔离复测

使用同一台宿主上的两个 PostgreSQL 18.4 容器，各限 2 CPU、1 GiB 内存。前台实例各组从同一
快照克隆，日志 56 万行。报表目标日 6 万行，旧发布代际 3 千行。前台走本地 HTTP 测试路由，
实际执行账户查询、钱包结算、消费日志持久化。压测器分开记录发出前队列、HTTP 结果、账户查询、
结算和日志 SQL 错误。日志成功样本再拆事务开始、INSERT、提交。阶段按发送计划标记，
每段统计五秒。两类对照使用同一个测试二进制，采样的开闭只存在于临时测试覆盖文件。

四组分别是关闭采样且无日报、开启采样且无日报、同库账单构建回放、旁库账单构建回放。
后两组都使用账单构建函数和现有逐笔候选，按相同速率回放，测的是构建阶段。
旁库独立于前台 PostgreSQL 进程和 WAL，仍与前台共用宿主及实际磁盘。每一轮的随机宿主波动
以等长的重复基线估计。等待事件是定时抓取的活动会话样本，无法给单个请求分摊耗时。
[PostgreSQL 等待事件与统计口径](https://www.postgresql.org/docs/18/monitoring-stats.html#WAIT-EVENT-TABLE)

### 3.1 同钱包复现

单钱包承受约 100、300、100 请求/秒。第一轮原口径的前台尾延迟在完全无日报时也能复现。
关闭采样且无日报时，突增段日志 P99 为 388.23 ms，日志事务开始 P99 为 298.06 ms，
INSERT 为 73.42 ms。一轮开启采样且无日报时，低负载段日志 P99 为 749.95 ms，事务开始
P99 为 618.64 ms，INSERT 为 6.40 ms，结算 P99 为 2,655.27 ms。
这两组的前台活动会话占多数的是 `Lock:transactionid` 和 `Lock:tuple` 样本。
这些结果支持同钱包结算排队与在线连接竞争可以把慢点传到日志写入。

| 复现组 | 发送前队列满 | 客户端等待超时且日志 SQL 成功 | 账户、结算或日志 SQL 报错 |
| --- | ---: | ---: | ---: |
| 无日报、无采样出现积压的一轮 | 892 | 78 | 0 |
| 无日报、有采样出现积压的一轮 | 1,227 | 94 | 0 |
| 同库回放出现超时的一轮 | 0 | 7 | 0 |

计数只覆盖三个测量窗。以上为本次复现分类，与原先 26 次属于不同试验。
同样的无日报、无采样组在另一轮的突增日志 P99 为 18.55 ms，三个窗没有失败。
这表明同钱包测试容易受外部负载和队列起点影响，只对照一对运行无法给原先差值归因。

### 3.2 八钱包低于饱和点的正反序对照

将同形请求分散到八个钱包，以约 50、150、50 请求/秒分别运行四组，并反向重跑。
各组都在两个实例克隆快照、做检查点并等待写回后启动，减少旁库组多一次复制带来的启动偏差。
三个窗口的已测请求均成功，约为 250、750、250 次。表中 WAL 为**前台实例**整轮增量，
连接等待次数来自**前台应用连接池**，报表固定回放按 250 候选行/秒运行。

| 模式 | 低负载日志 P99（ms） | 突增日志 P99（ms） | 回落日志 P99（ms） | WAL（MiB） | 连接等待次数 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 无日报、无采样 | 4.89–5.34 | 4.38–20.60 | 4.01–9.79 | 3.94 | 0–104 |
| 无日报、有采样 | 2.91–5.34 | 4.03–107.68 | 6.85–14.22 | 3.91–3.94 | 0–283 |
| 同库账单构建 | 3.40–19.89 | 11.51–77.34 | 6.81–7.05 | 12.62–12.89 | 191–516 |
| 旁库相同账单构建 | 3.31–7.35 | 2.77–7.99 | 3.29–8.58 | 3.94 | 0 |

同库两轮分别推进 3,725 和 3,650 条候选，旁库两轮均推进 3,725 条。**共库构建的增量争用可以重复观察**。
相近的报表工作留在同一宿主、切到独立 PostgreSQL 后，前台 WAL 从约 12.6–12.9 MiB 降到
约 3.9 MiB，连接等待从 191–516 次降到 0。前台日志最慢样本既有事务开始占主导，也有 INSERT
或提交占主导。以上数据不能将全部差异分摊给 WAL、数据库 CPU 或 I/O 的某一项。

采样组一轮突增为 4.03 ms，另一轮为 107.68 ms。无采样的基线也有明显波动，两轮分别为
4.38 和 20.60 ms。前台 WAL 基本相同，采样没有表现出可重复的尾延迟增幅。
在同一 Go 二进制中单独测在线日志采样函数，双线程、四轮测得开启为 60.53–63.03 ns/次，
绕过为 0.96–1.62 ns/次，均为零分配。这测的是内存采样本身，端到端影响以 HTTP 对照为准。
旁库、反序和基线对照能区分共实例的增量竞争与测试环境波动，尚无法把环境波动精确归因于
宿主 CPU、磁盘写回或压测进程调度。单钱包补跑同样的 50、150、50 请求/秒时无失败，
突增日志 P99 为 2.88 ms，说明集中钱包在更高压力下更容易放大排队，其影响也依赖负载水平。

使用实际自适应准入补跑一次同钱包突增，前台未记录失败，三个窗的日志 P99 分别为
4.71、8.54、6.72 ms，短窗内保留了 100 条已提交候选。该轮验证了可退让的执行形状，
完整大流量日报发布与生产前台保护仍需共同验收。

综合两轮对照，**原先 41.21 → 270.62 ms 无法做逐毫秒归因**。新证据确认了共库日报会
增加前台竞争，单钱包测试可在日报停用时复现严重排队，前台内存采样尚无可重复的放大效应。
优先减少全量、重复和时效要求较低的报表工作。

## 4. 业务减负方案

### 4.1 优先生成已结束日期

日账单和日用量继续默认调度。按北京时间在自然日结束后优先生成昨日，延用现有昨日调度时间，
在线繁忙时顺延到后续可用窗口。已生成且来源覆盖有效的日期直接复用。今天的账单和用量页面
显示仍符合当前口径的已发布版本及数据截至时间，缺少已验证结果时显示待生成，已知证据缺失时
显示来源不足。零金额及零用量继续由已验证事实给出。建议将对开放日期的定时全日重建
移出常规调度。当前实现会按三小时刷新窗口将当天再次列为候选，取消这份重复工作后，
每日高流量日的逐笔候选和来源校验集中在确实需要发布的时点。

需要看当下业务时，客户继续通过现有余额、任务和使用日志入口查询。后台日报延后不改变扣款、
退款、余额和正式月账单。今天的历史报表状态可明确呈现，已有数据截至时间承担展示语义。
实施后，开放日期不定期生成。仍有效的既有阶段性快照可以读取，下一自然日进入发布窗口后，按结束日覆盖重新验证。
[当前日期调度](../../../../model/daily_report_schedule.go) ·
[现有逐日用量合同](../../../10-product/客户与上游对账单产品说明.md#16-用量的逐日查看与售后退款)

### 4.2 让历史修正和导出只做有明确用途的工作

- 迟到消费、结算交付、退款和主动重建继续走现有发现及登记路径。将同一日期与关联范围中的待办合并，
  优先复用已验证候选。历史缺失回补分多个低谷消化，接近来源留存线的范围优先。长期繁忙时展示延期和
  证据状态，由现有保全流程处理有留存风险的证据。
- 客户账单导出按已受理请求执行，读取同一个已验证发布代际。所需日期仍待生成时，沿用等待或范围提示，
  让导出与历史回补使用同一低优先级容量。保留已完成分片与版本引用。
- 保留来源与旧边界复验、逐笔资金归属、租约以及跨日退款的联合发布。一笔真实入账由既有资金链路决定，
  报表仅展示可证明的结果。后台工作减少后，仍要通过逐笔一致性和同代际消费方验收。
  [账务发布合同](../../../20-architecture/decisions/0022-日报当前版本发布与历史证据迁移.md)

### 4.3 验证顺序

先验证减掉当天重复重建和历史重复候选后，系统每个自然日实际新建的代际数、候选行数和扫描量。
沿用现有小批、检查点和共享执行预算，低谷提速、繁忙时暂停。前台保持原有日志写入、持久性、
资金事务及索引。压测逐请求分类即可定位失败，方案无需新增线上采样、可调阈值或额外并发层。

并行覆盖两种业务流量。代表性多钱包流量用来评价正常业务保护，单钱包突发用来评价极端情况下
日报会否退让。对照组先能稳定完成计划负载，再比较业务延迟、在线日志写入 P95/P99、失败及吞吐。
使用相同请求身份、数据快照、数据库资源和交换顺序，单独核对发出前丢弃、HTTP 超时、账户、
结算、日志 SQL 及日志实际持久化。存在控制组拥塞时按压力结果记录。

已结束大流量日必须在多个低谷内持续推进，并核对账务逐笔、退款、用量、导出和邮件引用。开放日期
没有可用版本时应正确显示待生成。保留查询一致性与来源证据，验收仍以在线业务和日志写入无可复现
退化为准。超过此边界时后移日报处理时间，再验证实际仍需解决的读写争用。

## 5. 实施与复测

日账单和日用量继续默认调度，北京时间 03:00 后优先生成昨日。开放日期的定时重建、计量升级和
手工重算执行统一延后。升级前已发布的有效阶段性快照可继续读取。预备阶段的旧候选不能替代已结束日的来源覆盖。

迟到日志与已有待办按日期合并。跨日退款按入账日与任务完成日查找相关投影，再展开相关投影所涉及的未覆盖退款。
同一批次只构建每个日期、每种投影一次，关联日有可合并的修正待办时一并处理。
同日两种投影成功发布后，在发布事务中删除本批覆盖的请求。只发布一个投影、保护覆盖更完整的旧版本或
构建期间有新修正时，待办继续保留。保留已有面向无独立游标来源的单次近期回看，例如晚到的 Task 或 Batch 更新。

客户账单汇总与明细继续绑定提交时的已发布版本，沿用文件及已完成分片复用。没有发布版本时，给出缺失日期，
直接结束该导出申请。部分发布时导出已发布范围，附缺失日期。正式月账单、资金链路和在线日志入口不参与日报调度。

### 5.1 在线写入对照

隔离 PostgreSQL 18.4 限 2 CPU、1 GiB，统一从包含 54 万条日志的快照克隆。每轮经过相同的
数据库和前台采样预热。HTTP 测试入口执行实际账户查询、钱包结算和消费日志写入。八钱包各轮依次
运行 50、150、50 请求/秒，每段 8 秒。旧组在测试二进制中复现旧调度选中开放日期的条件，
接着进入同一构建器和自适应预算。新组执行本方案调度。基线没有运行日报任务。六轮按基线、
旧、新、新、旧、基线的顺序执行。每轮计划 2,000 条请求。

表中 P99 计自真实消费日志写入事务开始至结束，每格为两轮的范围。WAL 为同一 PostgreSQL
实例在整轮内的增量。候选行是测量窗结束时已经提交的账单明细行数。

| 八钱包组 | 低负载 P99（ms） | 突增 P99（ms） | 回落 P99（ms） | WAL（MiB） | 已提交日报候选 | 前台连接等待次数 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 无日报基线 | 8.95–74.20 | 2.02–37.91 | 2.16–7.78 | 2.70–2.71 | 0 | 0–301 |
| 旧开放日调度 | 2.69–9.64 | 2.08–163.12 | 15.93–48.23 | 3.61–4.52 | 400–800 | 0–2,287 |
| 新闭日调度 | 2.61–3.09 | 1.96–39.62 | 4.02–106.84 | 2.66–2.68 | 0 | 159–201 |

六轮 12,000 条日志全部入库。发送队列满、HTTP 超时、其他传输异常、非成功 HTTP 响应、账户查询失败、
结算失败和日志 SQL 失败均为 0。取消旧组的测试构建只用于结束等长测量，不计入前台请求故障。
新调度消除了可重复观察的开放日候选写入，WAL 回到同批无日报量级。一轮新调度在候选为零时
回落段仍有 106.84 ms，对照基线也有较大尾部波动。结果证明减少了数据库工作量；本机的短窗样本
不足以确认生产 P99 达标。

### 5.2 单钱包与已结束日期构建

单钱包按 100、300、100 请求/秒运行。无日报基线的日志 P99 依次为 3.14、2.68、2.97 ms，
新调度依次为 1.82、1.98、2.51 ms。两轮各 4,000 条日志全部入库，各失败环节均为 0，
前台连接等待为 0。样本没有复现先前的同钱包饱和状态。

另用同一快照将昨日设为待生成，按八钱包流量曲线启动实际默认调度及自适应预算。
测量窗末已提交 800 条昨日候选，在线日志 P99 为 12.73、7.05、3.09 ms。
2,000 条日志全部入库，各失败环节均为 0。

前台测量结束后继续完成昨日账单和日用量发布。账单逐笔 60,000 行、已入账合计 6,000,000 quota，
一个样本钱包的发布用量合计 750,000 quota，均与已知来源一致。该样本验证了本机从默认调度到联合发布的路径。
恢复库 157 万行日期与目标环境中的实际前台峰值延迟仍列为上线验收项。

### 5.3 业务回归

- SQLite 相关模型、服务和控制器回归通过。覆盖北京时间开窗、旧阶段性快照读取、
  迟到后补、不同天退款联合发布、覆盖下降时保留原版、账单明细复用和范围全缺时返回缺失日期。
- PostgreSQL 18.4 和 MySQL 5.7.44 各 11 项回归通过，每项独立数据库。覆盖校验旧上界与晚提交、
  恢复已提交候选、同日合并、并发修订保留、仅单种投影发布时保留待办，以及发布金额与来源一致。
- `go build ./...`、`go vet ./model ./service`、`task docs:check`、`task ai:check` 和 `git diff --check` 通过。
