# 用量导出与分组定价交互修复方案

## 1. 问题与目标

### 1.1 用户反馈

| 反馈日期 | 问题或需求 |
| --- | --- |
| 2026-10-12 | 用量统计导出 CSV 持续失败，需要支持按模型名称导出用量。 |
| 2026-10-12 | 导出任务目前只能从账单对账的导出记录查看，用量统计页面也需要入口。 |
| 2026-11-02 | 系统设置 → 计费与支付 → 分组定价 → 定价分组 → 添加分组，每输入一个字符都会出现列表刷新，干扰连续填写。 |
| 本次会话 | 点击导出会提交生成任务，用户却经常将其理解为打开下载页面，需要优化动作语义。 |

目标是恢复用量导出、稳定分组编辑，并让用户在用量页面完成生成、查看进度与下载。
本方案区分缺陷修复、功能补充和交互优化，不将全部现象归为单一原因。

### 1.2 状态与范围

- 本文记录分析基线、修复方案和本地实施结果；业务代码已实施，本地自动化、组件浏览器验收及完整程序真实浏览器 E2E 已完成，详见第 8 节。
- 源码结论以 2026-11-04 当前工作区为准，不能据此断言 2026-10-12 生产故障一定具有相同根因。
- 未读取生产任务记录、生产配置或服务日志；已通过本地真实 S3 兼容存储的写入、签名与浏览器下载，尚未完成文件到期、MySQL/PostgreSQL、生产部署及业务验收。
- 不修改计费、退款、历史日志、Provider 调用或模型路由语义，不建立新的导出队列、资源表或资金事实。
- 本轮维护本文和目录索引；长期事实收敛及归档仍须经过确认，不自动执行。

## 2. 当前实际情况

本节保留首次分析时的修复前证据，用于解释方案依据；修复后的实现与验证结果以第 8 节为准。

### 2.1 已验证事实与证据边界

| 事项 | 结论 | 证据与限制 |
| --- | --- | --- |
| 用量导出失败 | 当前实现存在确定性的格式版本冲突。 | 临时用例经过提交、领取和真实执行器，任务进入失败且未上传文件；生产原因仍需部署版本与任务信息核对。 |
| 模型导出 | CSV 有模型列，但缺少按模型筛选的完整请求和执行链路。 | 用量导出 DTO 无模型字段，CSV 生成遍历全部客户模型。 |
| 导出记录 | 共享记录已经支持用量任务，用量页未接入口。 | 现有抽屉识别 `usage_summary`，记录查询包含相关任务。 |
| 分组输入刷新 | 新建分组输入后发生输入框重新挂载和焦点丢失。 | 组件临时用例确认原输入框脱离 DOM；没有证据证明每次输入都在请求后端列表。 |
| 重复导出 | 页面按钮执行提交，终态后再次点击可产生新任务。 | 后端已有进行中相同申请合并，不应描述为完全没有重复提交保护。 |

用户截图显示多个已失败的“日／周用量统计”任务，以及统一的“稍后重新提交”提示。
它能证明用户看到的失败状态，不能单独证明对象存储、跨域、编码或具体生产异常。
首次分析时尚未完成运行中产品的完整浏览器流程验收；后续完整程序验收见第 8.6 节。

### 2.2 用量导出格式版本冲突

实际链路为：提交请求 → 创建任务 → 后台领取 → 校验格式 → 生成 CSV → 上传私有存储 → 授权下载。

当前有三处关键实现：

1. [用量导出服务](../../../../service/usage_analytics_export.go)的新建任务写入 `FieldVersion: 4`，重新生成也写入版本 `4`。
2. [共享 CSV 定义](../../../../service/customer_export_csv.go)中的 `customerExportFieldVersion` 为 `21`。
3. [共享执行器](../../../../service/customer_export_runner.go)在分派 `JobType` 前，用公共版本校验所有任务；不相等即停止生成。

因此，在任务成功受理并由当前执行器处理的前提下，用量导出在 CSV 写入前就会失败。
“重新生成”沿用相同冲突，等待或反复提交不能解决。

临时复现结果：

```text
submitted_version=4
runner_version=21
status=failed
error_code=generation_failed
uploaded_files=0
```

执行器将该异常归为 `generation_failed`，没有在普通完成路径保留具体错误文本；
[记录抽屉](../../../../web/src/features/billing-reconciliation/export-jobs-drawer.tsx)除队列超时外主要展示统一失败提示。
确定性格式错误被表现为稍后可重试的临时问题，扩大了重复提交。

### 2.3 模型列不等于模型筛选

[用量导出请求](../../../../controller/usage_analytics_export.go)接受周期、日期、视角、客户、语言和客户搜索条件，
没有模型筛选字段；客户 CSV 按 API Key → 客户模型输出每日行、周期合计行及总计行。
通用导出筛选结构中存在 `model_name`，不表示日周用量执行器已经使用它。

“按模型导出”有两种不同需求：

- 按模型筛选：仅输出指定模型，保留日期、API Key 等既有粒度。
- 按模型汇总：跨 API Key 合并同名模型，改变输出粒度。

本方案优先实现前者。跨 API Key 汇总若有业务需要，应明确列为独立范围，不能隐式改变现有 CSV。
现有每日、周期合计及总计行不能不区分行类型直接相加，否则会重复计算。

### 2.4 导出记录入口与查询刷新

[共享任务查询](../../../../model/customer_export.go)按发起人查找记录，并对普通用户继续约束目标用户；
[共享抽屉](../../../../web/src/features/billing-reconciliation/export-jobs-drawer.tsx)已支持用量类型、分页、活动任务轮询、取消、重新生成与授权下载。

[自助用量页面](../../../../web/src/features/usage-analytics/index.tsx)和
[管理员用量页面](../../../../web/src/features/usage-analytics/admin.tsx)只提交任务，再提示前往账单导出记录。
自助页提交成功后失效的查询键为 `self-export-jobs`，而共享抽屉使用 `customer-export-jobs`；管理员提交也未失效该共享查询。

缺口主要在入口、提交反馈和查询刷新，不需要复制后端任务系统。

### 2.5 分组输入重建的机制

[分组可视化编辑器](../../../../web/src/features/system-settings/models/group-ratio-visual-editor.tsx)的行为为：

1. 输入调用 `updateRow`，随后 `emitRows` 序列化全表并回写四个表单字段。
2. [分组表单](../../../../web/src/features/system-settings/models/group-ratio-form.tsx)订阅这些字段，再将值传回编辑器。
3. 编辑器的 effect 比较 `groupPricingSignature` 和 `sourceGroupPricingSignature`。
4. 新建的可选分组描述为空时，前者省略空描述，后者合并可用分组描述映射时保留空值，两种签名不一致。
5. effect 调用 `buildGroupPricingRows` 重建全表，所有行重新取得 `_id`，作为 React key 后导致输入框重新挂载。

临时组件复现记录：

```text
originalInputConnected=false
sameInput=false
focusRetained=false
```

这属于草稿同步和行身份错误。正常渲染本身不是缺陷；只加防抖、`memo` 或减少网络请求不能解决行身份被替换。
序列化还会跳过空名称，因此修复时必须覆盖清空重输等编辑中间态，不能只验证输入非空字符。

### 2.6 重复提交保护的实际边界

[任务受理逻辑](../../../../model/customer_export.go)已经合并相同条件的进行中申请，其他申请受个人活动任务限额约束。
用量页面仅在提交 HTTP 请求期间禁用按钮；请求完成后，用户仍可再次点击。
任务结束后相同条件可以新建任务，而格式冲突使任务很快失败，容易累积多条失败记录。

完成文件不宜仅凭条件相同、未过期就自动作为最新结果复用：后续结算、退款或历史更正可能改变用量。
历史文件下载与重新读取数据生成必须分别表达。

## 3. 优化方案

### 3.1 修复各导出类型的格式版本校验

- 明确日周用量 CSV 与其他导出格式的版本归属，执行器按任务类型校验对应版本。
- 用量新建、重新生成及执行校验使用同一用量版本定义，避免多处数字分别演进。
- 保留版本校验，不通过删除校验或接受任意历史版本绕过问题。
- 不将所有用量版本直接追随通用 CSV 版本作为长期方案，避免其他格式变更再次阻断用量导出。
- 使用现有任务类型分派实现最小接线，不为本次问题新建通用协议框架、兼容 decoder 或任务体系。
- 不批量改写历史任务及已有文件；不兼容的历史任务明确提示新建申请，重新生成须通过当前格式校验。
- 区分格式不支持、执行超时、权限变化、存储不可用等安全失败类别；不向客户返回原始异常、存储地址或凭据。
- 后台按任务编号记录脱敏阶段与失败分类，使排障不依赖客户反复尝试。

### 3.2 支持按客户模型筛选导出

首期建议支持自助用量与管理员单客户详情中的客户模型筛选。管理员客户总览保持其客户汇总语义，
需要模型明细时进入客户详情；上游模型筛选属于管理员视角，若实施必须独立定义，不能混用客户模型身份。
这是本方案的建议范围，不表示用户已经确认排除其他视角。

具体动作：

1. 默认“全部模型”，支持搜索后选择单个模型；模型选项来自所选客户和周期的实际用量。
2. 选项搜索可模糊匹配，提交后的模型身份使用精确匹配，避免相似名称被意外一起导出。
3. 将模型条件贯穿前端参数、后端校验、任务筛选快照、实际生成和记录展示。
4. 服务端负责应用条件，不从当前浏览器表格序列化 CSV；查询与导出继续复用既有用量口径。
5. 明细、每日小计、周期合计和总计应用同一范围，不能只过滤叶行却保留全量总计。
6. 模型条件未选择时保留全量语义；无匹配时成功返回明确空结果，不伪装成生成失败。
7. 按原条件重新生成保留模型条件；历史已生成文件保持原样。
8. 不重算历史价格，不改变退款、异步任务、未知金额和未来日期的既有统计语义。

若后续确认需要跨 API Key 按模型汇总，应另行明确汇总键、计费方式、折扣构成及金额缺项的合并规则。

### 3.3 用量页面复用导出记录

- 自助与管理员用量页接入现有 `ExportJobsDrawer` 及共享 API，不新增平行记录表、状态或下载接口。
- 提交后失效正确的 `customer-export-jobs` 查询，切回首屏并显示本次返回的任务；若合并已有任务，则定位已有任务。
- 用户可在当前功能查看进度、失败原因、文件和重新生成操作，不再被要求转到另一业务页面。
- 首期可共用现有全部记录并清楚标识任务类型；如增加类型、模型或范围过滤，必须由服务端筛选后分页，保证总数正确。
- 记录继续按发起人及现有权限展示，不能把“增加用量入口”解释为允许查看其他人的导出。
- 仅在抽屉打开且存在活动任务时轮询；不通过重复查询源用量来充当任务进度。

### 3.4 明确生成、记录与下载三个动作

推荐页面入口命名为“导出与下载”。点击只打开复用的抽屉，抽屉展示当前周期、视角、客户和模型范围，
并提供“生成 CSV”按钮与已有任务列表。允许用户调整导出条件，但页面和抽屉必须明确显示最终提交范围。

| 操作 | 行为 | 是否提交生成 |
| --- | --- | --- |
| 导出与下载 | 打开抽屉，查看条件和已有记录。 | 否 |
| 生成 CSV | 明确提交当前条件；进行中相同申请沿用既有合并逻辑。 | 是，或返回已有活动任务 |
| 查看进度 | 查询既有任务状态。 | 否 |
| 下载文件 | 对已生成文件申请短期授权地址并下载。 | 否 |
| 刷新下载链接 | 重新签发授权链接，不重新计算用量。 | 否 |
| 按原条件重新生成 | 以原条件发起新尝试，按当前允许的格式重新读取数据。 | 是，或返回已有活动任务 |

提交期间展示明确加载状态并阻止重复操作；受理后留在抽屉显示排队或生成状态。
下载历史文件显示原生成时间，重新生成显示新的生成时间；冻结条件不等于冻结所有底层用量数据。
不使用全局固定冷却时间、永久禁止相同条件或未经来源验证的完成文件自动复用代替清晰交互。

### 3.5 稳定分组草稿与行身份

- 优先沿用现有表单草稿管理编辑状态，明确编辑器内部更新与外部配置加载的边界，避免两个状态相互回灌。
- 修正空描述等字段的规范化差异；编辑器自己发出的值回传时不能重建全部行。
- 行 ID 在添加到删除之间保持稳定，不能使用可编辑名称充当 key，也不能每次输入重新生成 ID。
- 可视化草稿保留空名称、空描述、尚未完成的小数与输入法组合态；最终序列化前做完整校验。
- 名称为空、重名或数值非法时明确阻止保存，不静默跳过、覆盖或丢弃正在编辑的分组。
- 点击“保存分组设置”才执行服务端配置更新；普通输入只改变当前草稿，不触发配置列表重新加载。
- 保存失败保留草稿；保存成功后更新基线，再按必要范围刷新外部数据。
- 切换分组子页、可视化与 JSON 模式时保持已有草稿一致；不得通过切换模式规避输入问题。
- 不借机改变既有分组重命名语义或自动迁移其他分组引用；跨配置迁移不属于本次缺陷修复。

### 3.6 改进任务记录的信息

截图中的状态同时使用文字和颜色，有明确时间范围，这是可保留的部分。
需要改善的是重复标题、范围辨识度不足，以及所有失败都鼓励稍后重试。

记录卡片建议直接展示：任务类型及客户/上游视角、客户身份、日期范围与时区、全部或所选模型、
创建时间、状态；生成成功后展示生成时间与到期时间，失败后展示安全分类和适用的恢复动作。
进一步的细节继续放在“导出范围”内，避免每张卡片展开全部技术字段。

键盘焦点、抽屉打开后的焦点位置、状态播报与屏幕阅读器表现需要实施后的浏览器验收；
不能仅凭截图或组件测试宣称可访问性全面通过。新增文案及 CSV 表头仅要求简体中文和英文。

## 4. 实施顺序与最小修改边界

| 顺序 | 交付项 | 主要位置 | 完成条件 |
| --- | --- | --- | --- |
| 1 | 导出格式版本修复与安全错误分类 | 用量导出服务、共享执行器、既有记录错误展示 | 新建和重新生成均走真实执行器成功；不兼容格式仍明确失败。 |
| 2 | 分组编辑稳定性修复 | 分组可视化编辑器、表单保存边界 | 连续输入、清空重输和中文输入保持焦点、光标及草稿。 |
| 3 | 用量页导出记录与动作分离 | 自助/管理员用量页、共享抽屉和查询键 | 打开记录和下载不新建任务；明确生成才提交。 |
| 4 | 模型筛选端到端接线 | 用量 DTO、筛选快照、生成、页面和记录 | 筛选、合计、重新生成及权限一致。 |
| 5 | 集成与部署验收 | 相关测试、受控环境和当前事实文档 | 完成下述矩阵，剩余环境差异逐项说明。 |

尽量限于已有本地用量、账单导出和分组编辑模块。稳定新增逻辑与测试优先放独立文件，
共享执行器只保留必要的窄接线，不扩写原生 Relay、Provider、资金及配置存储基础能力。
实施前逐个确认文件归属；若必须修改 NEWAPI 原生文件，说明必要性、最小接线点及未来上游合并影响。

## 5. 验证方案

### 5.1 已运行的分析检查

- 相关 Go 测试通过：`go test ./service -run 'TestUsageAnalytics(Export|Regeneration|Period|Stream)' -count=1`。
- 前端三个文件共 20 个用例通过：分组工作区、用量导出重新提交、导出记录抽屉。
- 临时 Go 用例 `TestAnalysisUsageExportRunnerVersionMismatch` 通过覆盖文件方式接入真实执行链；
  断言成功时实际得到失败，复现版本冲突。
- 临时组件用例在新建分组输入一个字符后，确认旧节点不再连接、节点身份变化且焦点未保留。
- 临时复现位于仓库外，未提交测试文件；实施时必须将真实行为覆盖补入模块专属测试。

上述已有测试通过不能证明两个问题不存在：已有用量测试主要覆盖行生成和提交，未保护完整执行链；
已有分组用例未保护新建分组后的节点连续性与焦点。

### 5.2 实施验收矩阵

| 边界 | 必测行为 |
| --- | --- |
| 导出执行 | 有效任务提交、领取、生成、上传与发布成功；重新生成成功；不支持格式明确失败；失败不发布部分文件。 |
