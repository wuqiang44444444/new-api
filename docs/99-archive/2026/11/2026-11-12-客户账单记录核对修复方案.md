# 客户账单记录核对修复方案

## 1. 问题与目标

管理员在营业时间打开「核对账单记录」时，线上曾出现英文冲突提示，无法取得结果。修复后，系统按核对
开始时可见的记录完成检查，之后的正常入账留到下一次核对。目标是白天也能查到结果，并在满足条件时提交。
本次修复核对弹窗、查询和提交反馈，并增加小额差异的人工关闭。营业时间的表现以目标环境复验为准。

## 2. 当前实际情况

核对比较任务结算金额与可关联的扣退款净额，并检查已留存的计费依据。正式账单按扣退款日志汇总，
客户余额来自实际资金操作。目前金额差异会阻断出账，管理员无法直接关闭。记录是否齐全仍须另查备份、
日志清理及恢复证据。

线上截图显示当月已发布账单的汇总和明细入口，核对弹窗显示英文冲突。普通入账使客户级修订变化是当前首要排查方向，
具体失败分支仍待核实。见[客户月账单产品说明 §14](../../../10-product/客户与上游对账单产品说明.md#14-客户月账单确认与更正)。

## 3. 优化方案

- **首屏给出结论和下一步。** 显示客户、账期、核对时间、已检查的扣退款条数，以及当前出账状态。
  即使零异常，也说明是账期未结束、待登记记录完整性、需重新核验，还是可进入出账流程。金额不符时
  显示两边金额和差额。缺计费依据、缺关联记录或身份冲突时直接说明缺项及出账影响，明细可展开。
- **管理员直接处理差异。** 有处理权限的管理员在弹窗内核对。查实错账或扣款有误，按现有流程更正后重查。
  若关联有效、任务结算记录一致，且**扣退款日志净额低于任务结算额**，由管理员逐笔判断
  差额是否值得继续追查。管理员认定为小额时，填写原因并「关闭小额差异」。例如任务结算 US$ 10.00、
  日志净额 US$ 8.00，关闭后仍按日志记载的 US$ 8.00 出账。反方向继续核对。
- **关闭后继续出账流程。** 关闭只解除这一笔的阻断。原记录、差额、理由和操作人保留在处理历史里，
  客户账单继续按日志汇总，实际扣退款和余额保持原状。若发现实际多扣，仍走更正流程。来源完整性须
  单独登记，登记入口默认折叠。
- **失败时留在弹窗。** 维护、超时、超限和读取失败显示可确认的原因。可恢复时提供「重新检查」，反复失败
  时用请求 ID 排查。检查未完成时停用提交。提交时证据变化则保留备注，管理员重新核对后手动提交。
- **客户照常查账。** 弹窗注明核对的是该客户自然月的来源记录，核对时间与账单数据截止时间分别标注。
  核对失败时，客户仍可查看和下载已发布的汇总与明细，余额保持原有入账结果。已确认版本继续可查，
  更正版本经正式确认后生效。

## 4. 验收

1. 定位线上 409，再用活跃客户和稳定历史账期走完「打开核对 → 提交处理决定或登记来源完整性」。
   普通入账期间读取应成功。本账期证据或前一决定变化时拒绝旧提交。若其他账期的普通入账仍反复阻断
   提交，记录可执行的处理路径，验收结论标明仅恢复查看。
2. 验证管理员可关闭符合条件的差异，历史可查，账单金额和余额均无变化。反方向、
   缺关联日志、身份或结算依据冲突均拒绝关闭。关闭后，同月无关入账不重开该笔，该笔证据变化则重新阻断。
   同时验证来源完整性仍须登记、失效登记须重核和只读管理员无法提交。
3. 用客户账号验证当月汇总、明细和下载，以及已确认版本发现异常后的原版读取。回归生成、确认、草稿
   失效和提交幂等，核对过程中金额及余额无变化。

## 附录：实施与诊断

- 用请求时间、请求 ID、状态码、部署版本和脱敏日志定位 409。接口返回稳定的错误原因，弹窗按中英文
  文案处理。旧服务的通用错误使用通用提示，核对请求在弹窗内承接 500。
- 同库部署的只读 GET 复用现有扫描，在一个可取消的读事务内读取维护和来源状态、扣退款、Task、
  跨月退款补证、修订及处理历史。将 `usageReportMainDB(ctx)` / `usageReportLogDB(ctx)` 接入同一事务。
  事务结束后在同一时限内复读维护状态和代际。保留批读、30 秒期限、64 MiB 证据预算及 20,000 个依赖上限，
  超时、超限或读失败时整次失败。
- 小额关闭使用独立处理决定，复用现有审计和权限。金额大小由管理员判断。服务端按精确入账额度校验
  `关联日志净额 < 任务结算额`，并校验显式关联有效、任务结算金额与结算目标一致。
  提交时重查并在原有锁内复验报告指纹、前一决定、维护及修订。已保存的关闭决定绑定单笔任务及其
  关联记录证据。核对结果与来源登记共用该判定，仅有效关闭的该笔退出待处理和阻断计数。
  出账状态继续以实际完整性凭据及依赖修订为准。分库部署沿用现有支持范围。
- 在真实 MySQL、PostgreSQL 验证只读可重复读，在 SQLite 验证事务可见性与写锁影响。用批读中插入日志、
  更新 Task、跨月退款、历史更新及维护切换验证一致性。对比部署前后的成功率、失败原因、耗时、连接占用和
  写入延迟，使用脱敏摘要记录结果。目标环境复验完成后再更新方案状态。

本地隔离的 SQLite、MySQL 5.7 和 PostgreSQL 15 已通过快照并发、维护代际和差异关闭回归。
目标环境仍待定位原始 409，并使用高频入账客户验证查询、提交和正式出账。

复评后，小额关闭复用原预扣退款的身份及全额规则，跨月重复引用继续阻断。
一条退款同时声明任务和原预扣时，两条关联路径均保留冲突证据，任何关联任务均不可据此关闭差异。
