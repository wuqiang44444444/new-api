# 按张与 Token 冻结计价汇算方案

## 问题与目标

账单侧按同一批冻结的请求日志逐笔汇算。按张和按 Token 都使用请求发生时冻结的价格公式、命中档位和计价输入。先复现单笔计价，再按原有资金事件、渠道系数和舍入口径汇总。日志采集、实际产物确认和定价配置由各自写入方负责。

上游用量和对账需能核对「计费张数」「实际出图张数」以及对应的计价依据。客户扣款按实际入账汇总，公式复算用于核验计价和折前金额。供应商实扣及余额依供应商账单核验。本方案补充[上游对账按计价依据核算方案](2026-11-13-上游对账按计价依据核算方案.md)的计量与汇总部分。

## 当前实际情况

- 客户用量已按冻结表达式和命中档位识别按张记录，读取有效的 `image_count`。上游用量目前只累加 `completed_image_count`，上游对账保存完成张数和计费调用次数。两处均缺少独立的计费张数投影。[客户计量](../../../../model/usage_customer_billing_meter.go) · [上游用量聚合](../../../../model/usage_analytics_scan.go) · [上游对账聚合](../../../../model/billing_reconciliation.go)
- 本地截图对应的 #229 已冻结日报共 587 次调用，其中 553 次成功。客户按张 541 笔，计费 561 张，扣减 1,684,683 quota。另有 1 笔客户历史 Token 扣费 355,860 quota，业务已接受该笔原定价。11 笔渠道测试包含 6 笔按张计价，合计 6 张，以及 5 笔 Token 计价。渠道测试的参考计价不产生客户扣款。这份本地快照没有可核验的实际完成张数。
- 同一快照的客户扣减合计为 2,040,543 quota，折后参考金额为 $9.468892。参考金额包含渠道测试，冻结渠道系数为 1。渠道名中的「¥0.04/张」没有参与上述汇算。生产 #240 的 11 月 12 日正式日报已核实含 48 张实际产出，该样本可用于验证完成张数独立保留。

## 优化方案

### 1. 逐笔复算与核验

复用 [计费表达式引擎](../../../../pkg/billingexpr/expr.md)、[历史复算入口](../../../../model/billing_statement_original_replay.go)及已有计费单位解析。冻结日志中的公式、版本、实际命中档位和结算单位共同决定计价分支。涉及参数、时间、汇率、分组或合同时，使用当时冻结且对该笔求值有影响的值。旧格式只有在已有规则能验证等价档位或还原计价输入时参与复算。

| 冻结计费方式 | 复算输入及输出 |
| --- | --- |
| 按张 | 读取命中档位和冻结的结算 `image_count`，按原公式计算，保留单价、数量和适用的尺寸、质量或其他冻结条件。按张数量为有界正整数。任务在已有结算事件和冻结计量能证实时读取其计费用量，例如公式引用的 `u("image_count")`。预扣记录不计作结算张数。 |
| 按 Token | 按原公式使用冻结的 `billing_tokens` 或现有历史规则能唯一验证的同笔计价用量。输入、输出、缓存和模态分项以实际参与公式或档位判断的变量为准，保留显式零。请求可以同时有实际出图数。 |
| 按次及其他既有单位 | 沿用其冻结计量和复算规则。固定请求价须有按张分支证据才计入张数。 |

逐笔以原精度求值，按当时的 quota 换算、倍率、折扣和舍入方式与已入账额勾稽。复算输出应区分折前价、按冻结条件算出的应收和实际入账。已保存的可信折前金额可作为对照和现有展示依据。公式或必要输入缺失时，复算标为待核算，已有可核验金额照常保留。公式与实际入账冲突时保留原入账和差额，记录具体原因。金额由逐笔结果加总，禁止用汇总张数或 Token 套用单一现价重算。

原价核验沿用既有严格规则。单价或倍率缺失时，按现有证据规则解释，禁止从渠道名称、当前价格或平均单价推导。按张分支缺数量时标记缺项，禁止默认 1、把调用次数当张数、用 `completed_image_count` 回填计费数量或按金额反推张数。金额已知、数量未知和完成证据未知分别保留。

### 2. 计量投影与读取

1. 在逐笔投影保留冻结计费方式及计费用量。按张叶行累加计费张数和数量缺项，Token 叶行累加对应计价用量。总 Token 若继续表示请求遥测，名称应与「计费 Token」区分。实际出图继续读取完成证据，允许与计费张数同屏出现。
2. 客户侧按原入账记录汇总计费张数和金额。上游用量和对账展示「本站计费张数」，渠道测试单列，保留既有的测试参考金额口径。普通退款和异步差额沿用原资金事件归属。仅明确的最终计量事件贡献计费数量，同一任务只计一次。
3. 日报叶行、渠道和模型汇总、排行、下钻及 CSV 使用同一已发布代际。前端为计费张数和实际出图使用独立标签，CSV 使用独立列。适用但无数量证据显示「未记录」，有已知数量和缺项时显示已知小计。上游折后参考金额仍按逐笔原价乘对应日期的渠道系数并取整后求和。[日报架构](../../../20-architecture/账单计费-报表日汇总架构.md) · [对账架构](../../../20-architecture/账单计费-客户与上游对账架构.md)

### 3. 历史重建与验收

- 先接入现有逐笔解析，再更新用量日报和对账日报所需的投影版本及导出格式。使用已保留的冻结请求日志和既有关联事实，通过现有后台任务生成候选版本。核对来源覆盖、入账金额与逐笔身份后发布。来源缺失的日期保留已发布结果及缺项。原日志、客户钱包、已确认月账单与已生成的导出文件保持原样。
- 用同一模型的混合按张及按 Token 记录验证档位识别。覆盖计费张数和实际出图不同、Token 行含出图数、冻结输入显式零、必要输入缺失、公式复算与入账不符，以及测试、预扣、退款和差额。修改当前模型价格后，绑定同一冻结批次的结果应完全一致。
- 用截图对应的 #229 本地冻结范围验收。客户按张 **561 张**，渠道测试按张 **6 张**单列，客户的 1 笔历史 Token 费用保持 **355,860 quota**。客户总扣减仍为 **2,040,543 quota**，折后参考金额仍为 **$9.468892**，实际出图仍为未记录。对比逐笔、日报、排行与导出，逐笔计价和合计一致。用生产 #240 的正式日报复核实际出图 **48 张**，避免计费张数混入实际产出。
- 实施后先在本地隔离库验证新旧代际和导出，再到目标环境以只读方式核对已发布结果。供应商实际扣款与余额仍需供应商账单。目标环境的部署与业务验收以发布记录为准。

## 实施与本地验证

- 已接通用量日报、上游对账日报、渠道排行、逐笔下钻及 CSV。用量计量版本为 7，账单复算版本为 10。逐笔复算保存命中档位、参与计价的 Token 输入、折前 quota、应收、入账与差额。证据不足时返回具体原因。实际出图、客户计费张数与测试计价张数独立累计。
- 在本地 PostgreSQL 只读提取 #229 截图范围的 593 条源记录，用脱敏计价字段在隔离库重建 12 天日报。复现 587 次上游调用、客户 561 张、渠道测试 6 张、客户入账 2,040,543 quota 和折后参考已知小计 $9.468892。542 笔客户消费与 11 笔渠道测试逐笔复算一致。日报、排行、对账下钻、用量 CSV 和逐笔 CSV 的计费张数与扣减核对一致。
- 复评补齐原公式归一化、冻结请求倍率、旧日报读取、计费 Token 汇总及独立实际出图列。新版上游用量 CSV 为 9，已受理导出保留绑定的格式和计量。
- 倍率轨迹须明确记录每条规则的布尔结果。唯一匹配的冻结固定档位和单价可与冻结倍率组合复算，保留原公式的乘法顺序，并复核已入账金额。
- 档位和实际执行的倍率规则使用同一条件时，条件结果须一致。原始日志或结算快照的同一对象内出现多份倍率数组时，拒绝复算。
- 每条倍率轨迹的条件、倍率和结果各只能出现一次。冻结计量能否排除所选档位须独立核验，混合条件无法安全拆解时保留待核算。
- 上线和目标环境历史版本切换待验证。异步记录继续使用冻结的结算事件与既有任务核验路径。缺少独立结算数量的旧异步图片记录保留缺项。
