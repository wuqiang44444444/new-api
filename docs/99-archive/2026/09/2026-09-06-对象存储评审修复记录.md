# 对象存储评审修复记录

## 问题与目标

对照[对象存储方案](2026-09-05-对象存储系统配置与Azure接入方案.md)，修复存储位置变更、
长期凭据、签名错误泄漏、对象前缀、表单重新编辑和连通性测试清理的实际问题。
用户明确要求保持简单，极端场景允许通过业务维护解决，不新增自动迁移或多存储兜底。

## 当前实际情况

对象存储已有数据库设置、Azure Shared Key adapter、S3 adapter 和管理界面。
此次只修复对象存储边界，不变更客户 API、计费、上游 Provider 或既有音视频证据合同。
此前 Python 脚本对 Azure SAS 的真实测试，不代表本次修改后的 Go adapter 已完成生产验证。

## 优化方案

- 已启用存储的账号、backend、Endpoint、容器、前缀及区域不可在线变更或关闭；管理接口仅支持
  同位置更新凭据。数据库事务内比较旧配置，保存与环境导入共享限制，不依赖任务扫描证明无引用。
- 变更存储位置由管理员安排维护窗口：暂停所有节点业务受理和 worker，确认输入、历史产物及
  待交付文件的保留需求，备份配置和数据库，完成对象复制及校验，由运维离线变更唯一配置，
  所有节点重新加载后验证历史查询与新请求，再恢复流量。远端原文件不自动删除。
- 每个部署明确配置稳定 CRYPTO_SECRET 或 SESSION_SECRET；同数据库节点保持一致。缺失时
  拒绝加密保存，避免随机进程秘密造成重启后不可解密。主密钥轮换必须另行安排维护，不能只
  修改环境变量后重启。
- 对象引用统一是相对 key，存储 adapter 仅在构造远端对象地址时增加配置前缀一次。存量 S3
  若曾配置非空前缀却将图片写在根路径，运维在上线前迁移到对应前缀；不增加双路径读取。
- 签名下载失败只返回脱敏错误，存储请求不跟随重定向；后台账号字段回填，秘密字段不回显。
- 连通性测试只有在清理和删除后确认都成功时才整体成功；清理使用独立的短时 context。

在接口就绪后仅适配本轮新增测试并做联合编译验证，不归属或重构其健康探测设计。后续并行修改
需要由对应任务重新验证，不能把本轮通过解释为未来工作区快照也已验证。

数据库回归在 SQLite 测试库执行；事务与行锁使用 GORM 及项目 lockForUpdate，未宣称真实
MySQL/PostgreSQL 已验证。本次没有重新调用真实 Azure，也未验证 HK/US 节点或浏览器 CORS。
没有新增 relaykit 依赖或修改其源码。未读取或写入真实密钥、签名 URL 或 Provider 原文。

本轮修改限于本地对象存储扩展文件、对应前端和本记录，没有新增对 NEWAPI 原生文件的侵入；
此前实现的普通 Option/router 接线保持原有窄分支，不扩大上游同步冲突面。
