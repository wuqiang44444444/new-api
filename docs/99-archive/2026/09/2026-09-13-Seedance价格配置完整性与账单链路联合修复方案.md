# Seedance 价格配置完整性与账单链路联合修复方案

本方案承接 [表达式统一方案](2026-09-12-Seedance表达式预扣配置修复与任务用量计费统一方案.md)，
合并两轮评审并独立记录本轮修复范围、验证证据及仍需真实数据验收的事项。


## 1. 问题与目标

### 1.1 已验证问题与修复范围

两轮只读复审扩展到模型配置、客户月账单、管理员汇总、上游对账、明细、CSV、退款补偿及历史修复。
表达式引擎、原生任务提交与轮询主流程保持零新增修改；所有新修复优先位于本地扩展文件。

| 问题 | 事实与影响 | 本轮最小修复与验收 |
| --- | --- | --- |
| 预算完整性判断分散 | 保存可清空必需预算；运行时才拒绝；盘点仅检查键存在 | 唯一协议预算规则供保存、预扣、迁移、盘点使用；最终配置校验覆盖清空、reset 与免预算例外 |
| 盘点未覆盖创建资金 | 只统计 Task 无法证明 attempt 的 unknown/held 已结束 | 增加创建尝试状态/资金聚合；非法配置明确报告，不吞 JSON 错误 |
| 旧任务验证残留 | 旧 taskModel=true 验证只有测试调用 | 删除旧任务探针分支及无生产调用的批量 wrapper，保留通用模型验证 |
| 上游用量漏计 | 实际 Token 可记录在差额退款行，上游只读消费行 | 上游只读汇总识别结算调整用量；客户退款金额仍不作为供应商冲正 |
| 零差额用量漏记 | 预扣等于实扣时直接返回，不记录完成用量 | 在既有原子结算胜出后记录零金额调整日志；重试不增加请求/用量 |
| 结算明细仍显示预算 | usage_facts / matched_tier 取提交快照 | 结算日志从冻结条件、已接受实测和同一引擎结果投影；不回写初始预算快照 |
| 新表达式不能补修初始日志 | 修复命令只注入 C，没有 u() 用量 | 与正式结算共用冻结事实输入与折扣计算；只修日志、不调用资金 API |
| 非有限结算金额进入合同换算 | 实测命中除零等表达式边界时，浮点无穷不能转换为十进制合同金额 | 统一求值拒绝非有限结果，保留预扣、失败状态及饱和审计，不让折扣换算崩溃 |
| 非有限饱和审计无法持久化 | QuotaClamp.Original 为 NaN/Inf 时直接 JSON 编码失败，会连带拒绝 Task 失败状态和日志 | 有限值维持数字，非有限诊断编码为具名字符串；同一格式支持冻结事实读取与管理员审计 |

## 2. 当前实际情况

2026-09-13 01:47—01:53 对本地 one-api.db 的只读结果（不是线上库验收）：8 个启用 Seedance
渠道共 28 个客户模型，27 个仍为旧表达式，渠道 92 缺少模式/表达式/预算；渠道 104 另有 3 个
Token 模型缺预算。24 个已配预算合法，无启用重复归属或跨原生同名冲突。离线转换预览为
14 个可转换、4 个阻止、10 个因 size_multiplier 转人工。未知且持款的 attempt 共 35 条。

账单只读核对发现 555 条包含实际输出 Token 的差额退款日志；458 个可关联唯一初始日志的 Task
与相关日志净额一致，另有 291 个历史 Task 未找到带同 Task ID 的日志，原因未核实，不据此断言资金丢失。
停用原生渠道 41 的一个模型缺少表达式，重新启用前必须补齐。

本轮代码修复不等于已迁移真实价格或处理未知持款。缺失价格/预算需要明确业务值，unknown 必须有
可信 Provider 证据才能按既有恢复流程处理；不得猜定价格、改状态清空、自动退款或改写历史账单。
完整迁移仍受前置方案第 8 节维护窗口、节点一致性及存量资金闸门约束。

## 3. 优化方案与验证要求

- 客户金额继续按消费减退款聚合，不按当前价格重算；上游只汇总已持久化用量，不使用客户金额冒充成本。
- 金额调整与最终用量是不同事实：补扣、差额退款、零差额都记录一次最终用量；真正业务退款不重复用量。
- 预估事实留在创建日志；完成日志只显示已接受实测与冻结条件。异常/退款缺实测时不得展示预算为实测。
- 原生 u() 任务仍使用原生计费生命周期；本地历史 Token 快照按冻结单位读取，不恢复旧新受理入口。
- 按秒、纯固定及混合单位账单继续按当前合同返回 unknown；本轮不新增价格分类、PriceBook 或第二账本。
- 回归覆盖预算删改、零差额、跨档、退款/补扣、重复补查、客户与上游汇总、CSV 数据口径、修复幂等。
- 必须运行相关 Go 测试、前端账单与价格测试、docs:check、ai:check；外部三库、Provider 和生产切换单列未完成。

### 3.1 最小入侵与唯一权威实现

本轮不新增运行开关、兼容入口、计价语言或独立账本；增加一个主库日志交付记录表，以保存资金提交后仍需交付的日志事件。新增请求只接受前置方案确定的
Seedance `u()` 美元合同；旧快照按其冻结单位结清是读取历史事实，不要求运营维护第二套配置。

| 责任 | 唯一权威实现 | 接线说明 |
| --- | --- | --- |
| 协议字段、实测依赖、预算必要性 | [pkg/seedancebilling/contract.go](../../pkg/seedancebilling/contract.go) | `RequiresTokenBudget` 由保存、预扣、离线迁移和盘点共用；旧快照实测依赖通过冻结单位分派 |
| 渠道归属 | [model/seedance_pricing_channels.go](../../model/seedance_pricing_channels.go) | 沿用前置方案的类型归属及启用优先选择，不新增模型名猜测 |
| 最终价格完整性 | [model/seedance_billing_expression_validation.go](../../model/seedance_billing_expression_validation.go) | 必须具备客户键模式、表达式及该协议/表达式必需预算；数值上限仍由 billing_setting 校验 |
| 价格事务 | [model/model_pricing_config.go](../../model/model_pricing_config.go) | 校验移到既有事务内，覆盖 reset 后的最终值和旧单项配置入口；失败整体回滚 |
| 冻结 Task 求值 | [service/task_tiered_calculation.go](../../service/task_tiered_calculation.go) | 唯一纯计算入口；同一表达式引擎、单位、组倍率、合同折扣及饱和审计 |
| 正式资金动作 | [service/task_tiered_settle.go](../../service/task_tiered_settle.go)、[service/task_billing_state.go](../../service/task_billing_state.go) | 保留目标持久化、资金状态与幂等接线；计算入口不操作账户 |
| 完成日志投影 | [service/task_billing.go](../../service/task_billing.go) | 仅在成功 settle 状态注入实际档位/用量；异常与退款不再复制提交预算 |
| 客户/上游账单分类 | [model/billing_statement_task_facts.go](../../model/billing_statement_task_facts.go) | 冻结表达式和 UsageUnits 分类；上游识别退款行中的结算用量 |
| 离线账单补修 | [cmd/repair-task-billing-logs/main.go](../../cmd/repair-task-billing-logs/main.go) | 共用冻结求值；保留范围、唯一 attempt、资金转移与净额相等校验 |
| 饱和诊断持久化 | [common/quota_math_json.go](../../common/quota_math_json.go) | 数值换算不变；NaN、+Inf、-Inf 仅作为诊断字符串写 JSON，读取还原诊断值 |

原生表达式引擎既有文件、`relay/relay_task.go`、`service/task_polling.go`、`controller/relay.go`
相对本轮基线均无新增差异。本轮对原生 `controller/option.go` 只有一行参数接线：删除本地验证器的
无效 `extraFields/taskModel` 参数后，同步调用签名。保留无用途参数会延续虚假任务分支，故这行修改必要；
未来上游合并只需处理该调用点，不改原生插件分流、语法引擎或资金生命周期。

另有原生 `common/quota_math.go` 的一行必要接线：`AuditMap.original` 调用新增文件中的 JSON 诊断值转换。
只给结构体增加序列化方法无法覆盖现有 AuditMap 日志出口，故需要这一行；四则运算、饱和阈值、返回 quota
和有限值结构都不变。其余实现与测试隔离在新增文件，未来合并仅需核对审计字段接线与上游是否已有同类修复。

原生 `service/task_billing.go` 保留三处必要接线：`LogTaskConsumption` 用窄分支把已登记本地交付任务
交给新增投递器，防止同时直接写日志而重复计数；`taskBillingOther` 只在没有异步事实时沿用预估用量，
其余交给新增纯投影入口，避免完成日志仍显示预算；缺少 BillingContext 时从冻结异步快照投影组倍率。
HTTP 交付直接使用 `c.Request.Context()`，因为 Gin 默认不保证转发请求取消；这是已有分流中的单行接线，
不全局修改 Gin 行为。主体计算、交付与测试位于新增文件。未来接取上游须复核这三处日志入口/字段归属，不扩展原生资金路径。
`pkg/billingexpr/async_determinism.go` 是原生包目录内的本地新增文件；“既有文件零差异”不代表包级零扩展，
上游同步需保留其本地调用关系，或在上游提供同义能力后完成替换，不可只依据 tracked diff 遗漏该文件。

删除无生产调用的 `ValidateBillingExpressionsJSON`、旧 taskModel 探针分支，以及清理后已无调用的
`task_billing_smoke_requests.go`。通用 Token 模型继续使用既有通用样本与规则；Seedance 不再回到该验证器。

### 3.2 配置保存与存量盘点

保存必须校验最终替换结果，不能只看请求包含的字段：删除预算、删除模式、清空表达式和 reset
都不能留下无法受理的 Seedance 定价。旧单项 option 接口同样受约束；新建配置应通过模型级事务一次提交
模式、表达式与预算，而不是先保存半套配置。原生模型不增加此 Link 完整性限制。

FunCloud V3 / Synlink 的纯固定或冻结条件表达式仍可不配置 Token 预算；一旦引用实测 Token 就必须配置。
其余协议沿用预扣所需 Token 预算规则。已配置预算必须为合法正整数且不超过既有
`MaxTaskPreConsumeTokens`，不新增第二个金额/Token 上界。

盘点保留“旧表达式可编译”与“符合当前 Seedance 合同”两个独立结果，避免把可运行历史语法误报为已完成迁移。
渠道映射和配置 JSON 解析失败不再被吞掉；报告不输出完整表达式、连接或密钥。
创建 attempt 按状态和持款状态聚合，冻结 ModelArk V3 身份使已删渠道、尚无 Task 的记录仍可见。
历史表达式依赖分析只服务离线盘点，不参与新请求受理。

### 3.3 全部账单功能的影响与处理

| 功能 | 本轮结果与边界 | 验证依据 |
| --- | --- | --- |
| 客户月账单、API Key / 渠道分组 | 净額继续消费减退款，调整不增加请求；跨期退款保留负净额 | model 账单范围、分组、明细与净额回归 |
| 管理员客户汇总 | 沿用同一客户结算范围和冻结折扣；不按当前模型价格重算 | model/controller 现有回归 |
| 上游对账 | 补回退款调整行携带的实测 Token；普通客户退款不计供应商冲正 | 新增跨期调整/普通退款对照测试 |
| 账单明细、下钻 | 完成日志显示实际档位和实际用量；创建日志仍是预估事实 | 新增跨档、退款、零差额和补扣回归 |
| CSV | 使用账单响应与既有导出映射；后端修正用量会自然反映到导出 | 前端上游汇总工具及表格回归 |
| 折前金额、优惠、合同折扣 | 保留冻结倍率计算，缺事实继续未知；正式结算复用同一合同计算 | service 合同与新 u() 生命周期回归 |
| 钱包、订阅、应用/Key 额度、欠款、退款补偿 | 沿用现有原子资金函数；待补查不拿预算冒充实测 | model/service/controller 资金与失败路径回归 |
| 用户请求累计 | 补扣只更新用量金额，不再额外增加请求计数 | 实际 User.RequestCount 在三种差额下均保持一次 |
| 历史补修 | 新 u() 初始日志可按冻结实测验证；重复执行无新增记录/元数据变化 | 新增补修幂等与冻结 Task 不变回归 |
| 支付、充值、上游折扣配置/审计 | 本轮没有修改这些写入入口；不将未专项联调写成已验收 | 变更边界检查，相关包现有测试 |

零差额现在有一条金额为零的完成日志，因此明细行数会增加，逻辑请求数与客户净额不会增加。
上游历史用量可能因补入此前漏读的 555 条调整日志而上升，这是只读统计修正，不会重新扣款。
仅在已持久化实测存在时才能补回；历史零差额没有完成日志的用量不会凭预算自动生成。

按秒、固定或混合单位的 `unknown` 分类是现有账单表达能力的边界，不是本轮误分类回归。
这些日志的已知金额仍可聚合；不能为了清空 unknown 而将它们伪装成 Token。

### 3.5 上线风险与具体处置

| 风险 | 处置与通过条件 | 本轮状态 |

| 多节点加载旧新配置不一致 | 按前置方案维护窗口暂停新受理；统一部署；以 expected_version 事务应用全部配置；验证节点一致后恢复 | 未做线上切换 |

| 账单补修的适用范围有限 | 仅支持工具已验证的 Token 表达式及完整证据；含客户合同、混合单位、跨范围或冲突日志仍拒绝自动处理 | 保留限制，不能拿测试通过替代个案复核 |
| 三数据库和真实 Provider 未验收 | 运行现有 MySQL/PostgreSQL CI；对每种上线协议完成创建、实测、差额、缺用量补查与账单抽样核对 | 未完成外部验证 |

资金幂等测试证明的是正常重试不重复执行，不能证明任意故障下资金与独立日志数据库原子提交。
新增交付记录提供最终一致恢复，不宣称跨库分布式事务或任意数据库故障下绝对不丢失。主库损坏、日志独立清理、复制读延迟和外部数据库验收仍有明确边界。

执行顺序为：代码回归与文档校验 → 当前库再次脱敏盘点 → 缺失业务值与人工表达式核价 → 存量资金证据处理 →

### 4.2 日志交付与唯一资金入口

`TaskBillingDelivery` 是主库交付检查点，记录 Task 行号、事件、前后额度、实测数量、时点及交付状态。
它不保存价格配置、不计算资金、不创建第三方任务，也不成为第二份资金余额。

- 本地异步 Task 创建和初始交付事件同事务；结清、退款、零差额结清与最终事件同事务。
  创建 attempt 恢复与幂等恢复均使用相同接线。缺少交付表或插入失败会使事务回滚，不能静默跳过。
- `BuildTaskBillingDeliveryLog` 从冻结 Task 及事件投影；在线交付与显式历史完成日志补修共用。
  Token 单位、美元单位、客户折扣仍由 `ComputeTaskTieredBilling` 唯一求值。
- 交付先取得主库事件锁。同一 Task 按创建、完成顺序交付。请求编号由 Task 行号与事件确定，
  日志已写但主库确认失败时，重试比对金额、身份和用量后复用已有行，不再写第二份。
- 同库时日志、看板、用户/渠道统计和交付确认同事务；分库时以持久事件与固定编号恢复。
  恢复过程不调用预扣、退款或补扣 API。日志故障不会让已经成功的资金操作重放。
- 日志消费开关在事件建立时冻结；关闭消费日志仍按原行为完成统计，退款日志保留。
  看板只统计实际交付的日志，调整 Count 为零、退款金额为负，实测 Token 仅记一次。
- 图片异步保留原资金事务内的用户/渠道累计，交付层只补日志和看板，避免重复计数。
  图片没有初始消费行，最终按一个完成请求记录。
- Batch 明确排除在本交付器外，继续由 `CompleteBatchSettlement` 的作业确认负责恢复。
  补入同事务看板投影；按既有 `LineCount` 统一账户、客户账单和供应商汇总的请求数，
  汇总日志明确为完成请求而非差额。未改变 Batch 行金额、资金或执行流程。
- NEWAPI 原生 TaskUsage 路径不进入本地交付器。同步 Token、原生插件、支付及充值写入口不改。

原生接线最小范围：`model/main.go` 只注册新表；`model/task.go` 的插入调用接入事务写入；
