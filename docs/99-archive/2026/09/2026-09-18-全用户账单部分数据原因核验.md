# 全用户账单部分数据原因核验

## 问题与目标

承接 randy 的质量告警与累计已用差异调查，核验其他用户账单为什么显示“部分数据”，判断
它与退款未回减累计统计的关系。此次任务是只读分析，不修改资金、历史日志或生产部署。

用户明确说明数据库从未中断、没有移除数据。后续按历史数据完整的业务前提核验，不把缺少新
展示字段等同于记录丢失，不以“历史不完整”作为默认解释。验收目标是业务对账正确，文案只是
结果表达；日志之间能相加并不足以证明资金与任务结算一致。

此前历史恢复修复的真实数据验收集中于 randy，未覆盖全部客户与全部协议路径；不能将该用户
告警归零视为全站历史事实恢复完成。本次补充全量证据与后续修复范围。

## 当前实际情况

### 数据范围与验证方法

- 数据源为本地 `one-api.db`，按 SQLite `mode=ro` 与 `query_only=ON` 读取；没有连接线上库。
- 全部现存客户结算记录共 **123,772 条、47 个历史用户 ID**。只取消费和退款，并应用正式
  客户结算范围排除原生渠道测试。最新客户结算记录为北京时间 **2026-09-17 11:09:26**。
- 覆盖有结算记录的 2026 年 4、6、7、8、9 月。运行当前工作区的正式客户列表、单用户账单、
  退款补证、输入口径解析与估算规则；没有用简化脚本替代业务解析器。
- 对所有用户月分别比较列表与单用户账单，质量计数、净额均一致；各月消费与退款合计又与
  独立 SQL 汇总一致。不存在负 quota 记录。版本表为空，本地没有旧确认版本造成状态滞留。
- 临时 Go 核验入口只在显式环境开关下运行，打开源库后不调用迁移，运行后移除；代码与结果
  摘要保存在配套核验 notebook。以下数字不代表线上已更新代码后的实时结果。

### 原因一：历史写入与新读取规则之间缺少完整衔接

新读取规则要求 `input_tokens_total` 或明确 `usage_semantic`，用于区分“输入包含缓存”与
“输入不包含缓存”。旧记录虽然保存了输入、缓存读取或写入数量，很多没有这两个新字段。
当前恢复函数只覆盖明确 Gemini 标记以及满足严格条件的单段 OpenAI Chat 路径。

9 月 14,249 条的精确分解：

| 历史调用路径 | 记录数 | 当前未恢复的直接原因 |
| --- | ---: | --- |
| `/v1/responses`，单段 `OpenAI Responses`，`usage_billing_path=upstream` | 14,229 | 恢复函数只接受 Chat 路径，直接排除 Responses |
| `/v1/messages`，`Claude Messages → OpenAI Compatible` | 14 | 恢复函数要求单段链，排除协议转换 |
| `/v1/chat/completions`，单段 OpenAI，带缓存写入 | 6 | 恢复函数把任何缓存创建字段的存在作为排除条件 |

Responses 占本月未知输入记录的 **99.86%**，分布于 7 位用户，时间从 9 月 1 日到
9 月 15 日；全部 prompt 为正且缓存读取不超过 prompt，其中 10,543 条含非零缓存创建量。

历史代码 `4d46ebb79` 与当前 `NormalizeResponsesUsage` 均将 Responses 的
`input_tokens` 复制为 `PromptTokens`，另行保留缓存子项。因此这批存在可追溯的历史写入
证据，不能笼统解释为“上游没有返回数据”。但仍需逐分支验证原生缓存写入、历史 Claude 派生
转换及流式合并的语义，不能仅删除判断或把缓存再次加到输入总量。

重要边界：缓存写入字段本身并非 Claude 身份证明；原生 Responses 同样保留这些字段。
上一轮针对特定 Chat 历史路径的保守排除条件，不能作为全协议通用规则。

证据入口：
[输入恢复](../../model/billing_statement_breakdown.go)、
[历史与当前 Responses 规范化](../../relaykit/relayconvert/internal/oai_responses/to_oai_chat_resp.go)、
[新文本日志语义写入](../../service/billing_statement_usage.go)。

### 原因二：单个指标缺项被扩大为整张账单的统一状态

`finalizeBillingReconciliationQuality` 将输入、缓存写入、解释数据、计费方式、上游模型及
历史价格六类指标用“任意一项大于零”的规则合并为 `partial`。它不检查用户累计已用是否与
账单净额一致，也不验证钱包余额。

客户列表只显示一个“部分数据”徽标，并且只对“计费方式未知”提供行内原因。本月八位用户
的计费方式未知计数全部为零，实际原因是输入口径，故页面没有解释他们为什么被标记。

因此问题不只是文案不清楚：质量状态把金额、用量和估算三个不同业务问题混合了；“完整”也
容易让客户误以为已完成资金对账。

证据入口：[质量聚合](../../model/billing_reconciliation.go)、
[客户列表展示](../../web/src/features/billing-reconciliation/components/customer-statements-list.tsx)。

### 原因三：工具附加费被归到“历史价格缺失”

9 月唯一一条估算受阻记录为用户 136、日志 134870，原因码实际为 `auxiliary_charge`。
该记录已保存工具调用次数 2、单价 10，当前规则仍把含附加费的整笔消费标成不能反推模型
原价，并累计到 `missing_historical_price_rows`。一条记录即可使该客户整月原价/优惠为空。

阻止整笔费用直接除以模型折扣是有依据的：工具费不一定适用相同合同折扣。问题在于对外
字段名称和原因表达不准，以及尚未使用已有附加费事实进行独立核验与分项解释。
全部历史 40 条估算受阻都属于附加费原因；没有发现它们是缺合同或缺组倍率造成。

证据入口：[估算原因](../../model/billing_statement_estimate.go)、
[费用聚合](../../model/billing_reconciliation.go)、[工具费写入](../../service/text_quota.go)。

### 原因四：另有少量确实缺少历史计量依据的记录

7、8 月合计 37 条视频记录缺少足以确认计费方式的冻结事实，包括非零收费而固定价格为零、
无可用表达式/用量的历史情况。现有净额仍可记录，但不能根据今天的模型价格或名称补造当时
按次、按 Token 或按秒计费的结论。它们与 Responses 输入解析遗漏须分别处理。

### 与“累计已用偏大”的关系

对现存 39 个有账单或非零累计用量的账户做全历史比较，6 个累计值与现存日志净额不一致：

| 用户 ID | 累计已用减账单净额（quota） | 已观察到的事实 |
| --- | ---: | --- |
| 91 | 2,715,838,759 | 见 randy 专项核验，历史/人工退款漏回减及少量残差 |
| 143 | 24,912,250 | 差额恰好等于全历史退款，累计已用等于消费总额 |
| 110 | 9,024,316 | 同上 |
| 106 | 6,919,763 | 同上 |
| 95 | 2,100,000 | 同上 |
| 117 | -1,755 | 历史小额差异，未完成逐笔归因 |

其余 33 个现存账户在该比较下相等；另 8 个历史用户 ID 已无用户表行，无法比较其当前
累计字段。这里仅描述本地用户表的关联结果，不推断线上发生数据移除。相等只表示这两个来源
在当前截面一致，不构成充值、余额与采购成本的全链路证明。

9 月用户 91、143、110 的账单质量是“完整”，累计统计却不一致；用户 131 等显示“部分数据”，
累计统计与净额却一致。这直接证明两个问题**不能用同一个状态或同一种数据修复处理**。

### 按业务对账继续穿透：已确认 66 笔预扣事实与初始日志金额不一致

继续以 `用户 + 应用/API Key + 渠道 + 客户模型 + Task ID` 精确关联 Task、创建持款与事件，
并通过显式原预扣日志引用接入七笔人工退款，发现 randy 的 **66 笔已结算任务**同时满足：

- 创建 attempt 有非零钱包持款，状态为已转移；
- 唯一初始消费日志存在，但 quota 为 0；
- 后续结算明确记录相同的非零 `pre_consumed_quota`；
- 最终 Task quota 与结算 `actual_quota` 对应，Task 金额减日志净额恰好等于该预扣；
- 差额合计 **51,874,820 quota（$103.749640）**。

例如 Task 行 159：持款 733,504；初始日志 80680 记 0；结算日志 120260 记补扣 29,634，
并明确记载从 733,504 调整到 763,138；最终 Task quota 为 763,138。资金持款、结算差额
和任务最终值彼此一致，初始消费日志没有表达这笔预扣。

这是现有记录之间的金额矛盾，不是数据库中断或日志行被删除；仅重算 `SUM(log.quota)`、
把累计已用改成这个合计或消除 `partial` 都不能修复它。此前 $4,901.429036 必须继续限定为
“现存日志净额”，不能升级为已核准实际消费，也不能直接作为账户累计校准目标。

此次任务对照仍有历史初始事件未携带同一显式 Task 关系的情况；这些不能被错误算成缺扣款。
本轮只将上述多份事实一致的 66 笔列为已确认差异，不将简单关联未命中的记录当成金额错误。
七笔人工退款按原预扣引用关联后可与 Task 零费用闭合，不属于这 66 笔。

## 优化方案

1. **先对资金事实，再校准统计**：以已发生持款、移交、补扣和退款对照 Task 最终费用与账单
   明细，输出逐笔差异和修复依据。先处理上述 66 笔预扣投影不一致，再以已核准明细生成累计
   净额，不能直接拿现有日志和覆盖 `used_quota`。历史投影修复不得再次扣款或退款。
2. 全协议恢复历史事实：按真实 writer、规范化与结算路径建立可证明的规则，覆盖 Responses、
   Chat 缓存写入、协议转换；保留明确字段优先级、冲突拒绝和不重复累加缓存的约束。
3. 分开表达客户关注的三件事：已记录扣退款金额、用量完整程度、原价优惠估算状态。缺少
   Token 口径应显示具体条数与受影响字段，不能只给整单“部分数据”；未做资金对账不得用
   “完整”暗示余额、累计已用已经核对无误。
4. 把附加费与模型费用的估算理由分开。先验证冻结单价、计数、组倍率、单位与舍入，能证明
   的部分按各自折扣解释，不能证明时明确具体费用缺项，避免误报“历史价格缺失”。
5. 累计已用另走审计与校准流程，覆盖自动退款、人工退款、补扣和历史残差，不能用消除
   `partial` 或再退一次钱修复累计字段。
6. 验收从单用户扩大为全量矩阵：全部历史客户、全部活跃账期、原生与转换协议、流式与非流式、
   缓存读写、工具附加费、退款。要求逐笔资金事实与净费用一致，明细之和等于 API/模型汇总、
   月账单及导出，校准后累计净额与账户统计一致；余额按期初、入账、消费、退款与未结持款
   单独闭合。只修解析时金额不变；修复错误日志投影时金额变化必须由逐笔已发生资金事实证明。
   上线后的真实环境验收另行记录，不能以本地通过替代。

本次完成只读核验及原因分析；没有实施上述扩大范围的修复，也没有把未知项强制标成完整。
