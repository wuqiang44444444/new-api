# 图片同步与异步典型场景复验记录

## 1. 问题与目标

按用户要求，在[交付与错误证据修复](2026-09-16-图片交付故障与原始错误证据修复记录.md)后，
再次实际执行同步、SSE 和 Task 的生成、编辑及错误场景。验证范围包括真实供应商调用、
图片交付、幂等重放、预扣/结算/退款，以及加密错误证据能否读取。

**结论：11 次独立请求中，6 次成功交付，2 次参数拒绝符合预期，1 次被限流，2 次编辑传输失败。**
Azure 同步与 Task 的生成、编辑均有本轮成功样本；渠道 105 的 SSE 生成和默认 URL Task
生成成功，但同步/Task 编辑均发生 `unexpected EOF`，不能将整体验收标为全部通过。

### 2.5 错误证据与问题定位

本轮匹配的十条错误证据事件均可从私有加密存储解密，摘要校验通过；已存在的凭据头均脱敏。
其中八条为 HTTP 错误/错误查询的业务正文，两条为没有收到 HTTP 响应的底层传输异常。
400、429 的上游正文与平台返回，以及同步/Task 的 EOF 原因均已保留。本文不复制原始正文、
完整签名地址或凭据。证据正文经过脱敏与 JSON 归一，完整性不等于未处理的逐字节镜像。

1. **105 两笔编辑：传输中断，原因均为 `unexpected EOF`。** 没有收到上游 HTTP 状态，
   不能解释为参数拒绝、审核拒绝或不支持编辑。两笔异常在接近的时间收尾，网络/代理/上游
   连接链路是进一步排查方向，但现有证据不能确定具体责任方。
2. **原生同步取消与退款存在等待窗口。** `relay/channel/api_request.go` 的 `DoFormRequest`
   使用 `http.NewRequest`，未绑定客户请求的取消上下文；本次未设置总超时，默认响应头超时为
   1800 秒。观测到客户端 420 秒退出后平台继续等待，直到 557 秒的 EOF 才走原生退款。
   这是本轮确认的既有行为，不是 Task 创建失败，也不应将它描述为客户端已收到 500。
3. **Task 对未知执行结果保持保守处理。** #5 保留 `native_image_outcome_unknown` 和 5210
   预扣；后续恢复扫描未改成 `no_provider_task_id`，没有自动重发或退款。Provider 实际成本未知。
4. **Azure 同步编辑的首次失败是限流。** #9 返回 429；之后 Task 编辑与冷却后的同步编辑
   均成功。该样本不支持“Azure 不支持编辑”的结论。

## 3. 优化方案与剩余事项

- 同步/Task 生成、Azure 同步/Task 编辑、SSE、默认 URL → OSS → 查询签名、幂等及客户额度
  对账已有本轮真实成功证据。保留 105 编辑传输异常与限流样本，不以补测成功覆盖失败记录。
- 105 编辑仍需结合渠道/代理链路和 Provider 记录核对 EOF 及实际账单，不自动重放未知任务。
- 若要缩短原生同步客户端断开后的悬挂窗口，需单独评审取消、超时及原生退款语义，不能借日志采集
  修改业务执行。本轮只测试并记录，没有改动这些规则。
- 官方 OpenAI 直连、外部数据库、多节点、供应商账单与生产灰度仍未验收。
- 收尾时无排队/执行中 Task；3502 测试服务和临时 DNS 桥接均已停止。原 3501 服务保持运行，
  私有副本和证据受限保留，新增一笔待核实 Task 未重发或退款。
