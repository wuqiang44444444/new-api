# 图片 Task 真实渠道验收记录

## 1. 问题与目标

使用实际数据库配置的渠道验证图片 Task 修复：异步受理、生成与编辑、原生同步与 SSE、
幂等重放、用量结算以及拒绝后的诊断和退款。对应
[实施方案](2026-09-16-图片Task最小接入与原生计费一致性方案.md)。

**结论：核心 Task 链路已真实跑通，但整体验收尚未通过。** Azure 生成与编辑成功；
OpenAI 类型渠道显式使用 `b64_json` 时生成与编辑成功。本记录 §2—§3 保留首轮验收事实；
后续默认 URL 生成已在公网 DNS 对照下成功，编辑仍遇到下载读取超时，见 §4。

### 2.4 未通过项与根因边界

**已验证：105 默认形式的三笔 Task 已取得生成用量，但没有可交付产物。** 数据库中存在
生成完成标记、单张结果计划和归一用量，未登记产物；显式 b64 的同渠道生成、编辑均成功。
因此不能将它们归因为“异步未启用”或“请求未发送到上游”。

**推断：默认返回形式／URL 图片获取与交付路径是优先排查方向。** 当前证据不足以断言是
URL 403、下载网络故障、解码、对象存储还是产物登记问题，也不能断言改成 b64 是所有模型的通用修复。

## 3. 优化方案

1. 最小增量补充交付阶段的固定错误码和脱敏诊断，复用非阻塞 Sink；不记录 URL、图片正文或原始异常。
   错误记录失败不得影响既有任务执行、资金状态或原生响应。
2. 恢复流程保留首次失败证据，区分“原生无供应商任务 ID”与真正丢失异步 Provider ID，
   不以新的通用失败码覆盖已知交付原因。
3. 获取具体交付失败证据后再修复相应分支，重新验证同渠道默认格式的生成与编辑；
   不直接修改客户端默认参数，不绕过安全下载检查，不自动重发已产生用量的任务。
4. 原库历史任务与测试副本待核实任务分别人工核实；结合 Provider 账单判断实际执行和支出。
   本次平台 quota 对账不等于供应商账单核对。
5. 官方 OpenAI 直连、供应商账单、重启与多节点、生产灰度仍未验收。Azure／105 的真实成功样本
   仅证明上述请求矩阵，不能外推到所有模型、参数和部署环境。

本轮只运行实际渠道测试并补充验收记录，没有进一步改变业务代码，也未把默认交付失败标为通过。
