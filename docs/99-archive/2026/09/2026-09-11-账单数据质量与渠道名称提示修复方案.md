# 账单数据质量与渠道名称提示修复方案

## 实际数据与原因

只读核对本地 SQLite 中 randy（91）2026-09-01 至 09-10 北京时间的客户账单：

- 12,313 次请求，结算原价 956,064,294 quota，优惠 124,288,358 quota，净额 831,775,936 quota。
- partial 仅由 370 条计费方式未识别的日志产生；用量元数据不可读、历史价格缺失、缓存写入不可用、
  上游模型身份回退计数全部为 0。
- 370 条日志均属于渠道 76 的 seedance-2-0-m：354 条扣减请求、16 条退款调整。
  冻结表达式按 `_task.duration_seconds` 乘费率计算，并按分辨率和视频输入选择费率；当前账单分类
  不能把此类表达式归入 Token 或按次。因此“计费方式未记录”和“刷新后再导出”均不能准确解释原因。
- 渠道 97 的 channels 行在当前数据库及本轮已有备份中均不存在；371 条消费/退款日志未保存渠道名称。
  当前查询只能保留历史 ID。未查到渠道删除审计，不能断言删除时间或猜测原名称。
  该渠道 153 次请求，扣减 230,573,421 quota，退回 58,175,440 quota，净额 172,397,981 quota。

## 修复范围

- 详情按后端质量计数显示具体原因，不再一概声称用量丢失、快照冲突或要求刷新。
- 未知计费分类的文案改为“暂未识别”，不伪造按次用量；原始扣减和退回继续纳入金额。
- 缺失渠道记录显示本地化编号和“记录不存在，历史费用仍保留”的说明；现存渠道继续显示名称。
  不恢复渠道、不回填猜测的历史名称、不修改历史日志或资金。
- 修复模型级质量状态与总体质量状态不一致；现存但空名称的渠道不得被标成已删除。
- 补齐七种语言和截图中的请求总数翻译；测试真实截图数据、各质量原因及渠道缺失边界。

本轮不扩展计费单位合同：按秒表达式仍保持未识别状态，不把秒数误标为 Token，不据此重算费用。

## 验证

已完成本轮展示和质量状态修复：

- 前端回归复现旧提示缺少原因；修改后账单模块 5 个文件、18 个测试通过，包含真实中文翻译、
  全部质量计数、渠道缺失说明、现存名称、明细筛选及未知分类不显示按次零用量。
- 新增后端回归验证未知表达式的模型/汇总质量一致、原价/净额保留，以及不存在与空名称渠道的区别。
  `go test ./model ./controller -count=1` 全部通过。筛选运行曾触发既有控制器测试缺少初始化导致的
  空 SQL 列名错误，完整包测试通过；没有修改无关价格配置逻辑。
- `bun run typecheck`、涉及文件 oxlint 与 `git diff --check` 通过；10 个相关翻译键在七种语言齐全，
  插值保留，已执行 i18n:sync 并清理临时脚本。
- 同一数据库修复后只读复核：请求总数、原价、优惠、累计扣减/退回、净额完全相同；370 条未识别
  记录仍如实保留，所属模型的质量状态由错误的 complete 改为 partial，与汇总一致。

改动位于本地账单扩展文件，不侵入 NEWAPI 原生资金或渠道逻辑。未写入生产数据、未恢复渠道，
也未重启或部署运行服务。按秒计费分类仍未支持，不能把本轮展示修复解释为所有计量单位已完整支持。
