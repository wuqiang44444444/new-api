# 合同模型全量展示与来源统一方案

## 1. 问题与目标

管理员在合同编辑器搜索 MiniMax H3 时，候选列表只出现 MiniMax M3。代码核对发现，合同管理端
分别维护模型选项和渠道选项的专用渠道名单，MiniMax Link 未被纳入；模型已接入系统，不代表
能够被这两套查询完整发现。

用户已确认产品方向：所有接入系统的模型都应能在合同管理中按所属路由组找到，不应每增加一种渠道，就再为
合同增加一次专门接入。需求仅为补齐原有选择器的模型来源，保留“路由组 → 模型 → 渠道”的操作；
模型与渠道均支持多选和全选，不新增全局发现入口或独立诊断面板。本方案已实施并完成本地回归；线上配置核验与真实调用验收仍待执行，详见第 6 节。

### 1.1 目标定义

- 管理发现范围覆盖两类已有事实：所有 Channel 模型清单中的客户模型，以及关联到现存普通渠道的
  Ability 模型—组来源。两者按精确模型、组和渠道去重；不包括仅存在于 Provider 文档、插件支持
  列表、价格配置或上游模型映射目标中的名称。普通渠道身份复用现有路由分类，不另建类型名单。
- 所有已接入模型均进入管理员合同来源目录，不按供应商、渠道类型、价格存在性或当前启用状态
  决定是否展示。目录是现有数据的只读投影，不建立模型发布表或另一份模型注册事实。
- 模型可选、渠道可选、规则可保存和请求可履约分别表达。后台目录保留不可用来源及原因，
  前端沿用原有无有效渠道提示和失效规则提示，不增加独立诊断界面，不绕过保存和运行时校验。
- Channel 配置与 Ability 不一致是独立的配置诊断，不直接等于来源不可用。仅存在于普通渠道
  Ability 的来源仍可发现，是否可选、可保存继续使用共享资格校验，避免缩小原有发现范围。
  展示来源的并集不直接授予路由资格，也不要求把普通渠道资格改为两类事实的交集。
- “出现在合同中”指可被管理员发现、选择和配置，不自动加入已有合同或模板，不自动扩大 Key 权限。
- 新渠道只需完成系统本身的接入与路由资格登记；合同目录不得额外要求登记供应商或渠道类型名单。

### 1.2 依据与范围

当前合同范围、计费与执行边界继续以以下文档为准；本文保留管理目录改造方案与验收记录，不替代当前事实文档：

- [硬约束](../../../00-context/硬约束.md)：原生与 Link 边界、主数据库事实源及最小入侵。
- [用户模型合同定价](../../../10-product/用户模型合同定价.md)：新增来源必须有效，已保存失效来源保留。
- [用户模型合同定价架构](../../../20-architecture/账单计费-用户模型合同定价架构.md)：范围授权、来源资格和模板边界。
- [开发与验证指南](../../../30-engineering/用户模型合同开发与验证.md)：数据库、授权与回归要求。

实施覆盖用户合同编辑器、合同模板编辑器、管理选项 API、来源及价格参考投影和对应测试。
不改 Provider 协议、原生分发算法、资金流程、Task 生命周期或公开客户模型发现的授权范围。

## 2. 当前实际情况

### 2.1 已核对的代码事实

| 位置 | 当前行为 | 问题或可复用边界 |
| --- | --- | --- |
| `model/customer_contract.go` 的 `customerContractAvailableModelsForGroup` | 启用 Ability 与启用 Channel 求交后，仅补充 Seedance | MiniMax Link 遗漏；Azure Batch 的模型及价格参考也可能缺失 |
| `model/customer_contract_entity.go` 的 `GetCustomerContractEntityChannelOptions` | 原生 Ability 加 Seedance、Azure Batch | MiniMax Link 遗漏，与模型选项口径不同 |
| `model/channel_type_gating.go` 的 `channelSkipsGenericAbilities` | Seedance、Azure Batch、MiniMax Link 不进入通用 Ability | 属于路由隔离政策，不能为修展示而取消 |
| `model/customer_contract_availability.go` | 普通来源按 Ability，跳过通用 Ability 的来源按 Channel 精确组和模型成员校验 | 已有共享来源资格判断，应继续作为保存及可用性投影依据 |
| `contractRouteFacts.validate` 与实体保存校验 | 普通渠道通过启用状态、组倍率和有效 Ability 校验后，不再检查 Channel 模型/组成员；新增来源保存复用同一判断 | 模型从 Channel 清单移除或组配置不同，不必然使普通来源失效；不得仅凭差异宣告合同不可用 |
| `IsChannelEnabledForExactCustomerContractModel` | 本次全仓库 Go 引用检索仅发现定义，无调用方 | 列入本轮旧判断清理，实施时复查后删除，不作为新目录入口 |
| `controller/customer_contract.go` | 分别加载模型及渠道选项；组来自现有组倍率配置且排除 auto | 两次来源读取可能漂移；未配置倍率的组在选择器中不可见 |
| `controller/customer_contract_template.go` | 模板再次组合两种选项查询 | 同样受遗漏影响；模板价格不得套用某个客户的特殊倍率 |
| `web/src/features/users/components/user-contract-add-rule.tsx` | 展示所选路由组的模型，模型与渠道分别多选 | 原有交互符合需求；需要补齐模型数据来源，不应扩展为全局搜索或诊断界面 |
| `web/src/features/users/components/user-contract-utils.ts` | 新增规则依赖渠道候选，部分缺失价格/倍率使用占位值 | 全量目录接入后需避免把不可用来源或未知价格当成有效默认值 |

根因是管理目录复用了部分运行时可用集合，又自行列举专用渠道补集。系统接入事实、候选资格和
页面选项分别维护，新增渠道时需要同步多个位置，缺少“全量可见且资格一致”的行为回归。

### 2.2 证据限制与待核对项

- 截图只能证明当前 `default` 组搜索未出现目标名称；尚未查询线上 H3 渠道状态、实际客户模型名、
  分组、部署版本或接口响应，不能把本地代码缺陷直接写成线上配置已验收。
- `channelSkipsGenericAbilities` 当前只列出上述三类。异步图片等其他来源必须按真实接线验证，
  不能仅凭“异步”或文档中的类型名称假定其 Ability 行为，更不能在本方案中顺手改变原生路由政策。
- 本轮只核对来源资格代码；没有证明所有 Provider 配置、插件状态与请求级条件都由合同可用性覆盖。
  管理端“可选”只表示通过当前合同来源校验，不承诺真实 Provider 调用必然成功。

## 3. 优化方案

### 3.1 一个目录来源，复用已有资格政策

在独立的 `model/customer_contract_catalog.go` 中实现合同管理目录的批量只读查询，使用现有
Channel、Ability 与组配置，不新建数据表、持久化目录、后台同步任务或长期缓存。

处理过程：

1. 读取 Channel 的必要字段，例如 ID、名称、类型、状态、模型和组。不读取密钥、连接凭据或原始
   Provider 数据，不按启用状态或渠道类型排除目录记录。
2. 按渠道配置拆分客户模型与真实组；同时批量读取关联现存普通渠道的 Ability 必要字段，包括模型、
   组、渠道 ID 和启用状态。Ability 来源不要求模型或组仍在 Channel 清单内，也不因停用而隐藏。
   仅配置清单项裁剪边缘空白，Ability 按现有精确身份保留；不合并大小写不同的模型。
   不从 `model_mapping` 目标、价格表或 Provider 支持列表生成额外模型。
3. 合并模型—组—渠道来源组合并去重，记录来自 Channel 配置、Ability 或两者。对有真实组的组合
   复用 `GetContractRouteAvailability` 及其底层批量资格判断。普通来源仍要求有效 Ability；
   专用来源仍按已有路由分类检查 Channel。跳过通用 Ability 的渠道不通过残留 Ability 补充资格
   或发布额外模型；已删除渠道的残留 Ability 不作为可配置渠道来源。
4. 双向比较普通渠道配置与 Ability：记录“配置有而 Ability 无/停用”和“Ability 有而配置缺少
   模型或组”等差异。诊断与可用性分别输出，前者不覆盖共享校验结果。对未配置组的 Channel
   模型记录标记缺少配置组，不创造 `default` 或 `auto` 来源；同渠道若另有 Ability 真实组来源，
   保留该来源并独立校验。对真实来源组缺少倍率的情况，使用既有分组无效诊断。
5. 有真实组的来源按模型和组聚合，至少一个来源有效才可在该组新增规则；其余来源仍返回受控原因。
   无组配置记录按“客户模型＋渠道 ID”平铺在独立诊断集合中，仅保留为后端管理诊断数据，
   不要求新增 UI 展示，不放入组聚合、不生成规则或组价格。其诊断不能覆盖同模型其他真实组来源的资格。
   同一模型多个来源混合有效时，不得用模型级状态覆盖渠道级状态。
6. 管理模型选项、渠道选项和价格参考从本次目录结果派生。不能再分别查询一套“支持的专用渠道”。

目录枚举统一不意味着把 Channel 当作普通路由资格的替代来源。普通渠道缺少 Ability 时，模型仍
可见，但该组合不可选；普通渠道 Ability 有效而配置清单缺少对应模型或组时，仍按共享校验判断，
不能仅凭配置差异禁选。不自动修复 Ability、不写影子渠道、不修改通用分发缓存。

数据库读取异常使本次目录请求整体失败，不能返回空目录、部分成功结果或把异常伪装成模型不可用。
组合较多时沿用现有有界分批读取，避免按模型逐条查库；不为了分页或限额静默截断模型集合。
现有每 200 条规则一批的读取可能跨批重复加载同一渠道。允许在本次目录请求内复用已读 Channel
和 Ability 事实，调整投影接口或增加目录级读取编排，但继续调用同一 `validate` 判断。
“一次装载”指请求内事实复用，不要求一次无界 SQL；查询参数、OR 条件和分批错误处理继续有界，
不新增长期缓存，不把性能优化扩成第二套资格算法。是否优化根据实际目录规模和查询证据决定。

### 3.2 管理接口与价格参考

- 用户合同加载改为一次取得统一目录及该用户上下文中的价格参考；模板加载复用同一目录查询，
  仅使用普通组倍率。优先在本地合同管理接口中合并响应，具体路由和 DTO 名称在实施时确定。
- 管理投影保留客户模型、真实路由组、渠道 ID/名称，并增加来源可用性和受控不可用原因；
  无真实组的记录通过独立诊断集合返回，只能展示，不转换为可提交的规则。
- 来源出处和配置差异使用管理诊断字段，与 `available` / `unavailable_reason` 分开表达。
  配置差异可以与 `available=true` 同时存在；不得塞入不可用原因并误导前端禁选。
- 继续复用现有 `channel_disabled`、`capability_missing`、`route_group_invalid` 等诊断类别。
  只对既有类别无法表达的配置事实补充明确类别，不建立第二套资格算法。
- 价格参考沿用已有计价服务与客户特殊组倍率政策。价格缺失或无法解释时显示“未配置/无法预览”，
  不隐藏模型、不推断模型身份、不以价格为 1 或 0 伪装有效报价。
- 价格参考状态与来源资格分开表达；是否阻止请求继续由既有计费入口决定，不新增合同专属价格准入。
- 清点旧管理查询的全部调用方；同批迁移用户编辑器与模板编辑器，删除已无调用的重复查询和内部类型。
  不保留按类型拼接的第二实现或失败回退。若管理 API 存在外部调用方，实施前列出其迁移影响。
- 清理清单明确包含 `IsChannelEnabledForExactCustomerContractModel`：实施时复查全仓库引用，
  仍无调用则随本次删除；若已有新调用方，先迁移至共享来源校验，不保留第三套判断或兼容别名。
- 管理诊断字段不进入客户 Key 明细、公开 `/v1/models` 或公开报价中的内部身份字段。

### 3.3 保留原有组、模型、渠道选择流程

合同编辑器和模板编辑器保留原有新增规则区域：先选择路由组，再选择模型，最后为选中模型选择
渠道；模型和渠道均支持多选、全选与清空。不新增“全部路由组”搜索框、发现步骤或独立来源详情区。
前版方案把补齐模型来源扩大成 UI 改造，已按用户澄清纠正。

- 模型选项直接来自统一目录的当前真实组，包含该组全部已配置模型及普通 Ability 独有来源。
  不因渠道类型、没有普通 Ability、缺价格或暂时没有可用渠道而从模型选择器中隐藏。
- 模型全选覆盖当前组的全部模型，不只覆盖当前搜索结果。选择其他组时清空待添加模型和渠道，
  其他组的模型通过切换到所属组选择，不增加跨组搜索步骤。
- 选中模型后仍使用原有渠道多选控件；渠道全选覆盖该模型当前组的全部有效渠道，不只覆盖搜索结果。
  保留原有单渠道默认选中、多渠道由管理员选择的行为。不可用渠道不被自动选择或全选带入规则。
- 模型可选与来源可保存分开：模型暂时没有有效渠道时可选中查看，但显示原有“无符合条件渠道”提示；
  缺组倍率或有效来源时不生成可保存规则，仍由现有校验处理。
- Channel/Ability 差异和无组记录保留为后端目录事实，不为这些元数据额外增加 UI 面板。
  无真实组且没有有效 Ability 组来源的记录不能被虚构到 default/auto；管理员先在渠道配置中补齐组。
- 已保存失效规则保留原有失效提示和编辑行为。价格缺失显示“未配置”，合法零价正常显示。

前端仅消费共享资格校验结果，不按渠道类型、模型名或价格重新判断来源资格；后台全量目录和
保存、运行时边界维持不变。复用原有组件及中英文文案，不借本次修复重排其他管理 UI。

### 3.4 保存、并发与运行时边界

- 新增或改变规则来源仍在保存时重新检查权威事实，不能信任页面加载时的可选状态。
  加载后停用渠道、删除组倍率、移除/停用普通来源 Ability，或移除专用渠道的模型/组导致共享
  校验不通过时，保存应拒绝新增来源且不部分写入。仅从普通 Channel 清单移除模型/组、但 Ability
  仍满足共享校验时，不新增拒绝条件；配置差异不自动使新来源或已有规则失效。
- 已保存的失效来源仍按现有规则允许保留、编辑折扣及停用/重新启用；不借目录改造删除历史条款。
- 不自动给既有合同追加新模型，不自动绑定 Key，不改变同模型折扣、版本控制、审计和缓存失效机制。
- 请求继续由 `EffectiveContractRules` 与对应入口判断有效范围；范围内没有可用来源时拒绝，
  不回退到合同外渠道。目录可见不等于获得调用权限。
- MiniMax、Seedance、Batch 和原生渠道继续各自的入口与履约机制，不合并协议、不扩大同步资格、
  不给确定性视频入口增加权重或重试，也不改变普通/Batch 报价的执行模式区分。
- 现有运行时资格代码不是本轮重写对象；若联调发现独立缺陷，应先记录具体证据和最小修复范围。

### 3.5 改动位置与上游同步影响

| 改动位置 | 计划内容 |
| --- | --- |
| 新增 `model/customer_contract_catalog.go` 及行为测试 | 全量目录与共享来源校验编排 |
| `model/customer_contract.go`、`model/customer_contract_entity.go` | 移除被替代的管理候选枚举和确认无调用的旧判断，保留无关实体行为 |
| `model/customer_contract_availability.go` | 优先直接复用；有查询证据时最小调整投影接口或目录级请求内事实装载编排，共享同一资格判断 |
| `controller/customer_contract.go`、`controller/customer_contract_template.go` | 统一目录和价格参考装配，保持用户与模板上下文差异 |
| 用户合同与合同模板的 API、类型、编辑组件 | 原有组→模型→渠道流程，完整模型选项及模型/渠道多选、全选 |
| 本地管理路由接线（如需要） | 仅新增或替换必要的合同管理接口接线 |

主体位于本地合同扩展文件，预计不需要修改原生 Provider adapter、Ability 写入或原生选择算法。
不得为抽象复用重排或重构上游文件；实施中如确需改动原生文件，逐处说明必要性、最小接线点与
未来同步冲突影响。无需业务数据迁移、历史合同重写或价格回填。

## 4. 实施步骤与验收

### 4.1 实施顺序

1. 建立确定性测试夹具，复现 MiniMax Link 已配置但两个管理选项遗漏的问题，并覆盖 Azure Batch
   两种选项口径不一致。补齐 Channel/Ability 双向不一致及资格不变回归，明确当前原生、专用视频、
   Batch、异步图片的真实资格来源。
2. 完成全量目录查询及来源诊断；以既有共享校验验证有效组合，不增加合同类型白名单。
3. 一次性迁移用户合同与模板的接口、模型来源和价格参考装配，移除重复查询。
4. 将完整目录接入原有模型、渠道选择器，保持多选、全选、清空及分组切换行为。

6. 实施完成后，将已验证行为收敛到产品、架构及工程文档；本文保留实际执行结果和未完成事项。

### 4.2 必测行为

| 场景 | 验收标准 |
| --- | --- |
| 原生文本/图片/视频、Seedance、MiniMax Link、Azure Batch、异步图片 | 已配置客户模型均能找到；来源是否有效与各自现有共享校验一致 |
| 无 Ability 的 MiniMax Link/Seedance/Batch | 目录可见，合法组合可保存；查询与保存不产生 Ability，不误报缺少 Ability 的配置差异 |
| 客户自定义模型名、上游映射目标不同 | 展示和保存客户模型；不额外生成上游名称，不按名称推断渠道类型 |
| 新增一种渠道或协议 | 目录枚举无需修改合同类型名单；资格仍由系统已有路由政策决定 |
| 停用、无组、缺倍率、Ability 缺失及数据库读取失败 | 不可用来源有原因；读取失败整体报错；不伪装可选或有效报价 |
| 普通 Channel 配置存在，Ability 缺失或停用 | 目录可见，差异与不可用原因分别返回；新增规则拒绝，不自动修复数据 |
| 普通 Ability 有效，Channel 已移除对应模型或组 | 目录仍能发现该精确来源，展示配置差异；其他前提有效时来源可选、新规则可保存、既有规则仍通过共享资格校验 |
| 普通 Ability 独有来源同时遭遇渠道停用或组倍率删除 | 来源仍可见，但共享校验返回不可用并拒绝新增，不因来自 Ability 就直接授权 |
| 无组配置记录与同渠道的 Ability 真实组来源并存 | 无组记录保留在后端诊断集合、不可提交，不要求新增面板；真实组来源独立校验，不被诊断区状态覆盖，不创造 default/auto 组 |
| 专用渠道模型/组移除但存在残留 Ability | 不通过残留 Ability 补充该来源；既有规则依专用 Channel 事实判定失效，不回退普通资格 |
| 同模型跨渠道、跨组、大小写不同 | 精确身份、去重、同模型折扣及同模型同渠道唯一规则保持一致 |
| 同模型部分渠道有效、部分停用 | 模型可选，有效渠道可多选/全选；停用渠道不能被全选或默认选择 |
| 用户与模板、模型与渠道选项 | 来源集合一致；客户特殊倍率仅影响用户价格参考，不污染模板 |
| 价格缺失、模型只在其他组 | 在各自所属组均可选择模型；不自动改组，目录与已保存规则不把缺失价格当成免费或默认倍率；显式合法零价正常显示 |
| 加载后来源发生变化 | 共享校验不通过时新增来源原子失败；仅普通 Channel 清单变更而 Ability 仍有效时不额外拒绝；既有条款保留并据实展示资格 |
| 目录组合跨越分批边界，同一渠道出现多次 | 复用事实前后投影与共享资格结果一致、组合无遗漏；任一批读取失败整体报错，不发布部分成功 |
| 范围外请求和错误入口 | 合同外模型/渠道继续拒绝；目录可见不授予错误协议或同步入口资格 |
| 接口权限和客户投影 | 管理目录仅管理员可见；客户响应不增加内部组、渠道或 Provider 身份 |

后端测试使用 `testify/require` 与 `testify/assert`，断言目录、保存和授权等实际行为，不测试私有
常量或文件布局。先跑 `model`、`controller` 的合同专项；仅在实际触及执行代码时扩大到相关
`service`、`middleware` 和协议边界回归。数据库查询覆盖 SQLite、MySQL、PostgreSQL，外部数据库
仅用专用空库，未运行时明确记录跳过，不能声称三库验收完成。

前端使用 Bun 执行类型检查、受影响的合同/模板组件测试及构建；新增 UI 文案按现有 i18n 流程
验收中英文。文档变更执行 `task docs:check`、`task ai:check`；本方案不修改公开 API 文档，后续

## 5. 风险与剩余事项

- 全量目录比启用候选集合更大：采用必要字段读取和有界分批校验；若需服务端搜索或分页，必须保证
  搜索覆盖全部已接入模型并明示分页，不能重新引入隐式遗漏。
- 模型选择不授予来源资格：没有有效渠道时保留原有提示，添加与保存继续校验有效来源。
- 普通渠道清单与 Ability 的双向不一致均纳入发现和诊断；仅存在于 Ability 的来源不再被静默排除。
  来源并集只扩大展示覆盖，不直接授予资格；实际可选和保存结果继续由原共享校验决定，不自动修复
  生产数据，也不把配置差异当作禁用条件。配置来源与资格事实分开表达，避免误称为 Channel 已配置。
- 已删除渠道的残留 Ability 不作为新配置来源；已保存规则继续展示渠道不存在。专用渠道不使用
  残留 Ability 补回已移除模型。仅普通 Channel 清单移除、Ability 仍有效时，不宣称规则必然失效。
- 跨批事实复用仅是可选的读取优化；未测量实际规模前，不要求重构运行时加载器或引入全量无界查询。
- 前后端管理响应需同批发布，部署方式需确认；本方案不授权生产配置修改或自动回滚。
- 待部署验收：线上 H3 的客户模型名、渠道状态和组；旧管理 API 外部调用方；全部渠道家族的实际
  资格路径；目录规模；数据库与界面验收结果。以上未完成项不得写成生产已验证。
