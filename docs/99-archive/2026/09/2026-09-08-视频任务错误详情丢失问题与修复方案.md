# 视频任务错误详情丢失问题与修复方案

本文记录代码核查发现、用户要求、修复方案及本地实施结果。**错误返回修复已在工作区实现，验证状态见第 7 节；尚未部署或逐一完成真实 Provider 验收。** 第 2 节保留修复前的核查基线。

## 1. 问题与目标

用户明确要求向调用方返回详细的视频失败原因，特别是以下两类消息：

- `The request failed because the output video may be related to copyright restrictions.`
- `输入内容可能包含敏感信息，请检查后重试。`

当前部分入口会把上游已提供的具体原因替换为通用提示，导致用户无法区分输入敏感、输出版权限制、素材不可访问或服务故障，也可能因误解原因重复提交。

目标是：**完整保留可安全公开的业务错误详情，准确表达发生阶段和原因；保护凭据与内部信息，并保持各北向协议的现有响应结构。** 上述两条消息本身不含凭据或内部地址，应完整返回。不能把“输出视频可能涉及版权限制”改成“输入内容敏感”，也不应只返回 `Video generation failed`。

## 2. 当前实际情况（修复前核查基线）

### 2.1 已确认的代码事实

| 位置 | 当前行为 | 影响 |
| --- | --- | --- |
| [ModelArk 任务投影](../../model/task_modelark.go) 的 `ToModelArkVideoTask` | `TaskStatusFailure` 固定输出 `generation_failed` / `Video generation failed` | V3 查询与列表中的具体业务失败原因丢失；不限于 FunCloud |
| [V3 查询及列表](../../controller/video_modelark.go)、[公开结果投影](../../controller/modelark_video_projection.go) | 共用上述投影，没有恢复详细错误 | 上游原因即使已保存，客户仍只能看到通用错误 |
| [FunCloud V3 响应适配](../../relay/channel/task/seedance/thirdparty/funcloud_modelark.go) | 解析失败结果的 `error.code` 和 `error.message`，并脱敏 | 该路径并非没有获取错误详情 |
| [Seedance 结果解析](../../relay/channel/task/seedance/adaptor.go)、[共享轮询](../../service/task_polling.go) | 解析错误消息为失败原因，可信失败时写入 `Task.FailReason` | 失败消息可进入持久化流程，但公开投影未统一使用 |
| [创建错误投影](../../controller/task_protocol_error.go) 的 `taskProtocolErrorFields` | 非本地 401/403 一律映射为上游凭据错误；5xx 一律映射为内部或上游服务错误；部分其他状态保留消息 | 若内容限制以 403 返回，会被错误解释为凭据故障；详情保留取决于返回状态 |
| [通用任务查询](../../controller/task.go)、[Kling 查询](../../controller/video_kling_jimeng.go) | 分别返回已有的 `fail_reason`、`task_status_msg` | 与 V3 的错误可见性不一致；具体内容仍依赖对应 adapter 是否正确解析 |

[上游 HTTP 错误解析](../../relay/task_upstream_error.go) 已能从受支持的响应结构提取错误码和消息；[错误文本脱敏](../../service/task_error_sanitize.go) 及各 adapter 仍有各自处理逻辑。修复需要沿真实调用路径接入，不能仅新增一个没有调用方的统一工具。

### 2.2 已验证与未验证的边界

前一轮只读核查运行了 `model`、`controller`、`relay` 和 Seedance `thirdparty` 中与 ModelArk 投影、协议错误响应及上游错误解析相关的现有测试，均通过。**现有测试通过不代表详细错误返回已满足要求**，尤其不能代替下文两条原文的端到端回归。

本次文档工作未新增真实视频生成请求，未逐一验证所有 Provider 的错误码、HTTP 状态和错误响应形状。对尚未核实的错误，不能猜测其业务分类，也不能宣称全部协议已经修复。

## 3. 优化方案

### 3.1 对外返回规则

| 上游明确提供的原因 | 对外处理 |
| --- | --- |
| 输出视频可能涉及版权限制 | 保留完整业务消息，明确是输出视频及“可能”涉及限制 |
| 输入内容可能包含敏感信息 | 保留输入敏感提示，不改写成输出审核失败 |
| 输出内容敏感 | 保留输出侧含义，不归为输入错误 |
| 素材不存在、不可访问或 URL 过期 | 保留可操作原因，移除内部对象地址、签名或租户信息 |
| 参数不合法 | 保留客户可见参数名、原因和上游明确给出的合法范围；南向私有参数或上游模型身份不得直接泄露 |
| 上游凭据、账户余额、内部服务异常 | 返回明确的服务级说明，通过既有请求 ID 关联排查；不暴露上游账号、凭据和余额，不冒充客户鉴权或客户余额错误 |
| 可安全公开但未分类的业务拒绝 | 保留详细消息，使用现有协议允许的通用业务错误码，不虚构具体分类 |
| 没有原因，或无法安全提取业务含义 | 才使用通用失败提示，不自行补造解释 |

错误码优先使用经核实且允许公开的上游业务码，或映射到北向协议已有的等价码。分类只依赖明确的 Provider 合同和可信响应字段，不用模糊关键词推断用户内容，不把 HTTP 状态作为唯一业务依据。

接口默认保留原消息语言，不强制翻译导致语义漂移。若以后增加界面翻译，应与 API 原始业务含义保持一致，并遵循前端 i18n 规范。

### 3.2 创建阶段错误

1. 按所选协议解析上游错误响应，提取受支持的结构化业务码和消息，不扫描或转发任意原始响应。
2. 在脱敏及可信分类后决定北向错误码、消息和 HTTP 状态；具体 HTTP 映射遵守该北向合同，不能一律改成 400 或 200。
3. 明确的内容限制优先按业务含义表达，不因上游返回 403 就替换为“凭据不可用”。没有足够证据的 403 应表达为未明确分类的上游拒绝，不能武断认定凭据故障。
4. 客户自身鉴权失败、额度不足继续使用原有客户错误语义；不得因保留上游错误而混淆资金与认证责任。
5. 按原协议已有字段输出，沿用现有请求 ID 关联方式，不新增 Provider 私有公开字段。

错误文案处理不改变 durable create attempt 的结果可信性判断。HTTP 成功但结果不明、响应无可信任务 ID 等情况，仍执行现有未知创建规则；不能仅从消息包含“失败”判定可以退款或重发。

### 3.3 异步生成失败与持久化

可信终态失败被接受时，形成并持久化一份**可公开错误码和脱敏后的详细消息**。实施时先盘点现有 `Task.FailReason`、任务数据与协议投影，选择一个权威位置，不为不同界面建立多套独立失败事实，也不未经必要性分析就增加新表或通用错误框架。

处理链路应为：

`Provider 可信失败结果 → 协议解析与安全规范化 → 与终态一起持久化 → 各北向协议按既有字段投影`

- 主动查询和后台轮询走相同规则。
- 单任务查询、列表、控制台详情读取相同的失败事实；字段名称可以遵循各自协议，但含义和详细原因一致。
- 服务重启或渠道配置变更后仍能返回已保存原因，不依赖再次查询上游。
- 后续网络超时、不可解析响应或其他不可信观测不得覆盖已接受的终态原因。
- 历史任务若已有合法失败原因，应能安全展示；不存在的详细信息不能恢复或编造。不要为历史原始数据新增多套探测 decoder 或自动回查机制。

ModelArk V3 查询成功仍返回 HTTP 200，通过 `status: failed` 与 `error` 表示任务业务失败。以下仅为必要字段示意，不代表完整响应：

```json
{
  "id": "task_example",
  "status": "failed",
  "error": {
    "code": "generation_failed",
    "message": "The request failed because the output video may be related to copyright restrictions."
  }
}
```

示例中的 `generation_failed` 仅表示上游未提供可公开错误码的情形，有可信且符合合同的错误码时保留或等价映射。素材查询、视频内容下载等其他操作的错误不能混同为已确认的视频生成失败。

### 3.4 安全边界

“详细错误”不等于透传原始 Provider 响应：

- 不返回密钥、Token、Cookie、Authorization、完整签名 URL、内部主机地址、渠道配置、上游账号及原始模型身份。
- 不返回任意 JSON、HTML、堆栈、响应体或客户输入内容回显。
- 能可靠识别敏感片段时局部脱敏，保留业务说明；不能可靠分离时使用安全提示，不尝试以宽松规则放行全文。
- 采用有边界且保持 UTF-8 完整的长度限制；正常版权和敏感信息提示不得被截断或整体替换。
- 公开错误规范化规则保持一致，必要的协议差异留在 adapter；不在每个查询入口复制一份关键词和脱敏规则。

最终公开边界也要保护历史数据和其他 adapter 输入，不能假定所有已保存文本天然安全。此检查只能确保安全，不重新猜测业务原因。

## 4. 实施范围与顺序

1. 梳理当前实际注册的视频入口、错误解析及结果投影，列出已覆盖和未覆盖协议；优先修复已确认的 ModelArk V3 详情丢失及创建 403 误分类。
2. 确定可公开失败事实的唯一保存位置、协议字段映射和脱敏职责，保留现有合法业务详情返回路径。
3. 调整可信终态写入及公开投影，让查询、列表和控制台读取相同事实；创建错误使用相同的安全与分类原则。
4. 对其余视频协议逐项检查和接入必要修改，保持其现有北向结构。不要求所有 Provider 都返回并不存在的详细错误码。
5. 完成回归后更新相关架构、API 和运维事实文档，分别记录自动验证、真实 Provider 验证及部署状态。

遵守 NEWAPI 原生代码最小入侵：本地新增逻辑优先隔离在 Link 专属或新增文件，通过已有边界最小接线；对原生文件的必要改动说明接线点和上游合并影响。不借此重构无关视频、计费或素材实现。

本方案覆盖错误获取、保存和展示，不通过消息文本决定退款、补扣、终态转换或自动重试。资金仍依据可信任务状态和既有幂等规则执行。

## 5. 验收标准

| 场景 | 必须证明的结果 |
| --- | --- |
| 两条用户指定原文 | 英文版权提示和中文敏感提示均完整返回，不变成通用生成失败，不互相改义 |
| 创建阶段业务拒绝 | 在受支持响应形状中正确提取原因；有可信内容错误码的 403 不被归为凭据故障 |
| 未明确分类的 403 | 不误报客户鉴权失败或断言上游凭据失效 |
| 真实认证及余额错误 | 客户与上游责任明确，不泄露上游内部信息 |
| 后台轮询与用户查询 | 两条路径观察相同可信失败时，持久化并展示相同错误 |
| 单查、列表及控制台 | 错误原因一致，各协议保持现有字段结构 |
| 重启与冻结事实 | 不重新访问上游也能展示已保存原因；配置变化不改写历史失败 |
| 失败后的异常查询 | 网络错误和不可信响应不覆盖已有失败详情，不改变资金状态 |
| 缺失消息与历史任务 | 无详情时安全返回通用提示；有可安全使用的既有原因时不丢失，不编造历史错误码 |
| 敏感信息 | 含凭据、签名地址、原始响应、堆栈及客户内容的输入不会泄露；可安全分离的业务解释仍保留 |
| 长消息与中文边界 | 长度限制有效、UTF-8 合法，两条正常提示均完整保留 |
| 无关状态 | 成功、取消、过期、未知创建与退款幂等行为无回归 |

以确定性测试覆盖真实 Provider 错误响应结构，不以日志输出、随机输入或内部函数调用次数代替行为断言。先运行相应边界测试；涉及数据库结构时验证三种支持数据库，涉及 `relaykit` 时独立构建，涉及公开 API 文档时运行公开文档校验。

真实验证应优先使用已授权留存且已脱敏的失败证据；确需请求上游时记录环境、协议、请求形状与可公开结果，不为取得策略拒绝而刻意构造违规内容，也不把本地模拟结果标注为真实验收。

## 6. 剩余事项与完成条件

- 各 Provider 内容错误码、响应结构与 HTTP 状态组合尚需按实际支持范围核实。
- 权威失败字段的具体存储和接线方式在实施中确定；本方案不宣称已有统一结构。
- 存量任务未保存的原因无法凭空补齐，需在发布说明中明确历史数据限制。
- 自动测试通过后仍需验证真实接口展示与控制台一致性，不能只核查数据库中存在错误文本。
- 当可公开详情在创建与异步路径均完整保留、所有已发布视频入口覆盖情况明确、脱敏与资金回归通过后，才能将相应能力记为实现完成；生产发布单独记录。

原方案阶段仅保存文档；后续用户已授权完整修复，实施状态如下。


## 7. 本地实施结果（2026-09-08）

### 7.1 已采用的简化实现

用户进一步明确：让用户看懂原因优先，隐藏渠道 ID、上游名称和凭据即可，不增加复杂框架。本次没有新增数据库表、错误状态机或错误分类配置。

- `Task.FailReason` 继续作为失败消息权威。视频失败接受点规范化新消息；公开读取保护历史记录，通用 CAS 不改写文案。正常版权、敏感内容、素材和参数提示完整保留；URL、凭据、已知供应商名称、渠道 ID 与不同于客户模型的冻结上游模型名被移除或替换。原始 JSON/HTML、明确的 `body={...}` 诊断正文不当作业务消息返回，普通 `request body:` 参数说明保留，长文本按 UTF-8 安全截断。
- ModelArk V3 的普通 `failed` 使用详细消息；只在规范化 `Data` 同为 `failed` 且消息与该失败一致时读取其业务码。取消、过期及合同失败的本地文案保持既有语义。其他形状或不同次观测不探测错误码，不新增兼容 decoder。
- 创建阶段通过错误对象的结构化详情传递业务码和消息，不从 `Error()` 的 HTTP 拼接前缀反向拆解。403 保留可公开的拒绝原因，缺少原因时明确表示服务拒绝，不再一概声称凭据失效。安全可读的上游 5xx 消息也保留；客户本地 5xx、上游 401/402 继续按内部、认证或服务不可用语义保护，不把上游余额问题表述为客户余额不足。
- 通用查询、任务列表/控制台、Kling、Jimeng、OpenAI Video 和插件 Responses 的同步/流式/查询路径接入详细消息。插件 Responses 任务失败以持久化原因为准；原生 OpenAI Video 插件已有的错误投影保持其协议权威并过滤，插件渲染异常继续使用既有观测错误，不获得修改任务或资金的权限。
- 已失败、取消、过期等终态的主动查询直接使用持久化结果，不再发起上游查询覆盖原因；成功任务的既有用量补查保持原样。
- 未识别轮询响应不再拼入失败原因，也不以该不可识别正文覆盖 `Task.Data`；已有受保护证据通道不变。批量查询失败的新文案不包含渠道 ID。

### 7.2 专家评审收敛

| 评审问题 | 本次处理 |
| --- | --- |
| 历史 FailReason 含渠道 ID 和原始响应 | 写入规范化与公开读取保护同时接入；删除轮询正文拼接；保留必要业务解释 |
| 错误码来源未明确 | 使用既有规范化 Data 与同次失败消息校验；不复用整数 TaskInfo.Code 承载字符串业务码 |
| 多套截断规则及中文字符损坏 | 共用公开消息处理，FunCloud V2/V3、第三方公共处理和飞彩均使用 UTF-8 安全结果 |
| 本地终态语义及 HTTP 前缀 | 普通生成失败展示详情；本地特殊终态不改；创建响应显示业务消息，不显示诊断包装前缀 |

### 7.3 原生文件最小接线说明

| 接线位置 | 必要性与范围 |
| --- | --- |
| `model/task.go` | 仅在 OpenAI Video 投影中填入错误；已撤除 CAS 前的文案改写，不修改 CAS 条件或资金逻辑 |
| `controller/task.go`、`relay/relay_task.go`、`service/task_plugin_view.go` | 将直接读取 FailReason 改为公开消息方法；旧记录无法仅靠写入端修复 |
| `service/error.go`、`controller/relay.go` | 分别接入结构化创建详情与立即失败消息规范化，保留原有创建结果判定 |
| `service/task_polling.go` | 去掉原始正文拼接，删除 New API 格式解析分支的提前 Data 赋值，仅在状态可接受后保存响应；计数、终态阈值、退款规则不改 |
| 既有协议投影及 adapter | 只替换错误字段来源与消息处理，不改请求形状、路由、用量或协议选择 |
