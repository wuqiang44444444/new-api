# 客户账单数据质量提示问题分析与解决方案

> 当前生效边界（2026-09-19）：本文保留分析与阶段记录。历史退款引用已改为完整历史游标核验，不再以 1000/1001 行停止；历史 Token 恢复按实际写入语义识别 OpenAI、Responses、Claude、Gemini 的冻结证据，不采用统一的原始上游输入假设。合同状态保留“适用 / 不适用 / 未记录 / 未知”，未记录按因子 1 参与估算并显式披露，冲突未知阻断估算。当前事实以[对账架构](../20-architecture/账单计费-客户与上游对账架构.md)为准；本次来源保护与资源预算见[修复记录](2026-09-19-账单启动与邮件评审修复记录.md)。历史数量为当时样本，不代表当前生产数据。

## 问题与目标

客户账单持续提示：

```text
部分计费信息尚不能完整展示，已记录的扣减和退回仍计入金额。

输入 Token 总量不可确认：4640 条
计费方式暂未识别：780 条
历史价格不可用：7 条
```

本方案分别处理历史用量语义缺失、计费分类能力不足、人工退款解释信息缺失，以及工作区代码与页面
结果不一致的问题。目标是让有证据的记录得到正确解释，让确实缺少证据的记录继续明确标注未知。
不能把消除提示作为修改历史金额、猜测用量或隐藏质量问题的理由。

本次交付仅为方案。前序分析进行了只读数据库核对和工作区代码调用；没有修改日志、资金或任务状态，
没有部署服务。本文的拟实施项不代表已经完成或生产可用。

本方案补充[使用记录与客户账单优化方案](2026-09-16-使用记录与客户账单优化方案.md)中的历史信息与
数据质量部分，不另建账单、导出或计费实现。此前视频平均费用偏高主要由分辨率和时长构成导致，
与本次三类质量提示分开处理；本方案不调整模型价格或视频请求参数。

## 当前实际情况

- 环境：本地工作区及 `one-api.db`，数据库连接使用只读模式。
- 数据范围：客户 ID 91，2026 年 9 月，Asia/Shanghai 自然月内本地已有消费和退款日志；不是仅
  API Key 50，也不是仅截图中的两个模型。
- 时间范围：`1788192000 <= created_at < 1790784000`。直接调用现有闭区间接口时结束时间为
  `1790783999`。月份尚未结束，数字仅代表本次核对的数据截面。
- 代码基线：已提交版本 `9f5ce504b`；工作区另有未提交的按秒分类、退款事实解析和账单展示等修改。
  实施前须再次确认版本与差异，复用现有修改，避免覆盖其他任务成果。
- 未核实：页面实际连接的服务版本、进程是否已更新、页面是否保留旧响应；未查询生产服务或供应商账单。
- 三项提示按日志行计数，不是去重后的任务数；同一行可以同时命中多项。

### 4. 计费方式未知：780 条

| 原因 | 数量 | 当前工作区处理结果 |
| --- | ---: | --- |
| `seedance-2-0-m` 使用冻结的按秒表达式 | 730 | 已归为按秒 |
| 退款日志没有表达式，但对应 Task 有冻结表达式 | 43 | 已从严格匹配的 Task 恢复分类 |
| 人工退款仅保存管理员元数据 | 7 | 仍未知 |

730 条中包括 694 条消费与 36 条退款；冻结表达式明确引用 `_task.duration_seconds`。旧逻辑主要
识别 Token 或固定按次，无法把此类表达式表达为按秒，因而返回 unknown。这是展示分类缺口，
并不意味着表达式无法计费。

43 条退款缺少日志内表达式，且固定单价为零、没有输出 Token，单看退款日志无法确认计量方式。
本地已验证它们都能按用户、应用/API Key、渠道、模型及 Task 身份匹配冻结任务事实。
当前工作区已经增加这种只读分类补充，不改变退款金额。

证据入口为[计量分类](../../model/billing_statement_task_facts.go)和
[退款冻结事实读取](../../model/billing_statement_refund_facts.go)。后者在核对时属于未提交新增文件。

页面 780 与旧逻辑精确一致，应优先核查“运行构建未包含工作区分类修复”。如果目标服务按已提交
基线 `9f5ce504b` 构建，同一截面的查询就不包含上述修复，单纯重启原构建不会解决问题。
但未提交代码也可能直接启动运行，因此不能由 Git 状态反推服务版本，更不能认定线上一定运行
`3947cb13c` 或 `9f5ce504b`。目标服务版本、构建来源及真实响应仍待核验。

### 5. 历史价格不可用：7 条

| 模型 | 人工退款数 | 已入账退款金额（美元） |
| --- | ---: | ---: |
| `seedance-2-0-s` | 4 | 12.707152 |
| `seedance-2-0-fast-s` | 2 | 5.110484 |
| `seedance-2-0-mini-s` | 1 | 0.953036 |
| 合计 | 7 | 18.770672 |

这些记录均发生于 9 月 15 日，只在 `other.admin_info` 中保存人工退款标记、操作信息、Task 关联和
`original_preauth_log_id`，没有账单可直接读取的计费表达式、组倍率和历史价格快照。
质量提示中的“历史价格不可用”实际表示无法完整还原折前金额，并不等于退款金额未知。

已逐条验证：

1. 7 个原预扣日志引用均存在，并指向消费日志。
2. 原记录与退款记录的用户、API Key、渠道和模型一致。
3. 原记录均保存 0.87 组倍率及计费表达式。
4. 7 条退款金额均等于所引用的原预扣金额。

因此存在可用的历史证据，缺口在于当前账单没有读取这条人工退款关联。
当前剩余的“未知方式 7 条”和“历史价格不可用 7 条”是同一批记录，不能相加为 14 条异常请求。

缺价还产生明确的用户可见后果：模型行的 `originalQuotaComplete=false` 会使该行原价不可还原，
经 `finalizeBillingReconciliationOriginalQuota` 与 `finalizeBillingCustomerStatementOriginalQuota`
逐层使所属分组及整账单的原价、优惠汇总为空。不是所有行的整列都被隐藏：不受影响的模型、分组
仍可显示自己的已知金额。因此阶段 A 只修复分类，阶段 B 才能在本次截面恢复受影响汇总的原价与优惠；
4,640 条输入语义提示本身不要求把已知金额汇总置空。

## 优化方案

### 1. 先确认现有修复在目标页面生效

1. 固定客户、账期、筛选条件及数据截止点，记录目标环境、运行构建版本与来源；优先确认构建是否
   包含工作区修复，而不是先尝试重启或刷新。提交时间不能代替部署证据。
2. 对照已存在的按秒分类及 Task 退款关联修改，完成必要代码检查和测试；不得另写第二套分类器。
3. 发布时确认后端与前端使用配套版本：后端支持 `per_second`，前端标签、筛选、明细与导出能处理它。
4. 读取目标服务的真实账单响应，再检查页面展示；响应仍为 780 时排查后端版本和实例一致性，
   响应为 7 但页面为 780 时排查页面旧数据和刷新。不能只靠刷新按钮推断发布完成。
5. 同一固定数据截面应从 `4640 / 780 / 7` 变为 `4640 / 7 / 7`，消费、退款及净额保持不变。
   整账单原价与优惠汇总此时仍为空，不把该现象误判为阶段 A 分类修复失败。

### 2. 补齐人工退款的只读解释

推荐扩展现有本地账单退款事实读取模块，以明确的原预扣引用补充缺失的分类和价格解释，不修改资金，
不回写历史日志，不根据当前渠道或价格配置推断历史。

可复用的备选是：将人工退款 `admin_info.task_id` 作为显式关联候选，经既有身份校验后复用 Task
冻结表达式分类，原预扣关联负责价格解释。该字段仍需校验，不能只改读取位置就直接信任；Task 与
原预扣证据冲突时保持未知。若一次读取原预扣已足以取得分类和价格，则调用现有分类器即可，不强制
为同一事实再查一次 Task。实施时按最小查询与复用现有校验原则选定单一路径，不并行维护两套规则。

#### 2.1 关联与证据优先级

- 已有且有效的退款自身快照优先；关联读取只补缺失事实，不覆盖已存在事实。相互冲突时保留未知并
  记录可定位的脱敏原因，不静默选取一方。
- 仅识别已验证的人工退款元数据形状，读取 `original_preauth_log_id` 的明确引用；不按时间接近、
  同模型、相同金额或当前配置猜测原记录。
- 必须校验原记录存在且为消费、用户/API Key/渠道/冻结客户模型一致；涉及 Task 时继续校验已有
  用户与应用隔离边界。不能仅凭数据库行 ID 放宽访问范围。
- 首轮仅覆盖本次验证的全额原预扣退款，并检查重复或冲突关联。部分退款、多个退款共享同一预扣、
  混合附加费用等情形在没有明确可归属证据时继续未知，不套用全额退款规则。
- 引用 ID 必须是原始持久化日志身份。日志后端若不提供可验证的唯一身份，不能把 API 展示序号当作
  引用；保持未知并标明该后端尚未支持。不得跨库猜测相同数值 ID 的含义。

#### 2.2 投影与计算

- 从原预扣的冻结事实取得计量分类、有效组倍率、合同倍率及可解释的计价信息，继续使用唯一的账单
  分类和金额还原逻辑。只读补充不构成第二套计费计算。
- 退款金额仍取退款日志自身已入账 quota，并按退款日志时间进入账期；原预扣记录只提供解释证据，
  不能因为关联查询而被再次计入当前账期消费或 Token。
- 原价与优惠冲回保留负号及“估算”属性，不因为原记录可关联就宣称能还原未舍入的精确原价。
- 不复制原预扣预算 Token 到退款用量；恢复计费方式不代表产生新的请求或最终用量。
- 原预扣允许位于更早账期；查找范围按明确身份取证，汇总范围仍严格限定退款发生账期。
- 后端按引用 ID 分批读取，避免每行查询；SQL/GORM 查询兼容 SQLite、MySQL 和 PostgreSQL，
  支持主库与日志库分离，不要求跨库 JOIN。
- 自助账单、管理员客户列表与详情、账单专属明细/统计及共用导出读取相同解析结果。普通用户输出
  继续剥离管理员操作信息、内部关联和 Provider 身份。

#### 2.3 防止新增同类缺失

实施时先追踪这 7 条人工退款的真实写入入口；不能仅凭元数据断言来自某个服务或修复脚本。
对仍在使用的正式入口，在已有退款日志交付流程中保存所需冻结解释事实及原扣费关联，复用现有快照
写入方式，不新建人工退款资金入口，不因补快照再次退款。

#### 2.4 查询成本与日志后端边界

当前账单明细每次分页请求都会先扫描 SQL 筛选范围内的退款并批查 Task，随后遍历候选结算日志，
再按解析后的模型/计费方式筛选、统计和截取当前页。模型及分类过滤未必能直接下推，所以成本不仅
来自退款关联；“没有逐行查询”不等于查询已具备可接受的规模和翻页成本。

- 记录筛选范围、候选日志数、退款数、唯一关联数、SQL 次数及耗时；用代表性真实范围比较首屏与
  连续翻页，不用随机大循环或时间阈值单测代替性能核验。
- 本次新增原预扣关联须按去重引用分批读取，并受查询上下文、取消和资源预算约束；不能在已有扫描
  之外再为每页无条件增加整月原预扣扫描。
- 复用工作区已有 `buildBillingStatementRefundModes` 的分批能力，协调共用导出扫描实现；不能
  通过反复调用分页明细接口导出全部数据。是否还需调整明细扫描，按观测结果纳入独立最小改动。
- ClickHouse 的排序键、原始持久化身份与用户响应展示 ID 必须分别核实。支持普通日志排序不等于
  支持人工退款的原预扣 ID 关联；不能确认唯一来源时保持价格解释未知，不能跨库数字 ID 对接。
- 查询超时、取消或扫描不完整必须返回明确失败，不把部分扫描结果作为完整账单；无证据的单条记录
  则继续保留未知，两种状态不能混用。

### 3. 对 4,640 条输入语义缺失分两步处理

#### 3.1 确保新记录完整

- 已排除项（只读核对结论）：`quota.go` 的 wss 与 audio 结算路径不写 `cache_tokens`，
  不会命中“带缓存但无冻结语义”的缺失条件；`batch_progress.go` 的批量结算路径完整写入
  `usage_semantic`、`input_tokens_total` 与 `cache_tokens`。阶段 C.1 的盘点面可限定为

#### 3.2 历史记录只做有证据的恢复

以下工作从已复核的 290/4,350 两类证据开始，不再把行内证据盘点作为空白待办：

| 验证对象 | 已有证据 | 剩余核验 | 核验通过后的候选解释 |
| --- | --- | --- | --- |
| Gemini 290 条 | 明确 `billing-usage-gemini`，请求链终点为 Gemini | 核对历史窗口的标记生成、规范化用量与日志写入链，确认记录值包含缓存且没有后续改义 | 总输入采用已记录 `prompt_tokens`，缓存作为子项，不再次相加 |
| OpenAI 4,350 条 | 单段 OpenAI 请求链、`upstream`、无正数缓存写入 | 核对历史 adapter/结算分支，排除 Claude 派生、缓存扣减、估算或其他特殊改义；不能仅凭请求链放行 | 仅在证明记录值已含缓存后采用 `prompt_tokens` |

实施步骤与边界：

1. 对照记录发生窗口内的相关源码版本和冻结字段，而非只阅读最新 adapter。形成“字段组合、已证明
   的历史写入行为、适用范围、排除条件”的小型证据清单，记录核验通过与仍未知的数量。
2. 原有有效 `input_tokens_total` 或 `usage_semantic` 仍优先。只有直接字段缺失、候选证据满足
   已验证条件且互不冲突时，才在现有账单解析路径增加局部只读解释，不改计费或 Provider 请求。
3. 复用现有归一规则；已含缓存的输入不得再加缓存。协议字段缺失、未知组合、相互冲突、仅有
   `upstream` 或涉及未核实特殊转换时继续未知。估算路径标记不能直接解释为实测总输入。
4. 不使用当前 ChannelType、模型映射、模型名称、价格或费用反推历史；不按“DeepSeek/Gemini”
   名称硬编码恢复，也不为消除提示引入通用猜测或多层回退框架。
5. `prompt_tokens >= cache_tokens` 与无缓存写入只用于一致性检查，不能替代历史语义证明。
   不承诺全部清零；若最终证明 290 条均可恢复，则该固定截面从 4,640 降为 4,350；若两类全部通过，
   才可降为 0。任一不符合条件的记录保留未知，金额、缓存量和输出量均不变。
6. 本方案不执行历史批量回写。如后续确有回写需求，应另行列出精确范围、证据、预览差异、备份与
   回滚措施，不能以本方案的展示修复自动扩大为数据库修改。

### 4. 提示文案与核对口径

- 区分“历史字段未记录”“已有证据但未解析”“当前写入仍缺字段”，避免把所有情况统称计费失败。
- 保留“已记录扣减和退回计入金额”的说明；总输入、折前金额、优惠不可完整解释时，不把已知部分
  冒充完整合计。

- 更准确的价格提示可表述为“部分历史折扣或计价依据缺失，折前金额无法完整还原”。具体文案在实施

## 二次评审修复（2026-09-17）

### 问题与目标

原预扣补证的候选上限曾由当前批次包含的客户与 Key 集合共同决定；相同退款可能在月汇总、

不能仅检查同名字段是否相等。目标是在保留实际净额的前提下统一质量解释。

### 当前实际情况

- 候选扫描改为固定 user_id＋token_id，每范围最多 1,001 条历史退款候选，仅取 other。
  范围内超过 1,000 条则该范围不恢复；其它 Key 不再挤占额度。查询沿用请求/导出批次上下文，
  不跨页长期缓存，不补写原始日志，不增加自动退款行为。
- 退款自身与原预扣的合同适用三态冲突、或单条“未适用＋正合同因子”内部冲突时，原价与优惠
  保持未知；已有净额不变。前端同时取消冲突记录的最终折扣展示。
- 新增确定性测试：同一客户两个 Key 各 600 条退款；汇总、明细及 500/1,000 条批次导出的分类、
  数量与净额一致。覆盖原预扣和退款两侧方向的合同冲突，以及退款内部冲突。
- 非默认额度换算、原生图像/音频分项和大金额页面精度等相邻修复统一见
  [优化方案第 18 节](2026-09-16-使用记录与客户账单优化方案.md#18-2026-09-17-二次评审修复)。

### 优化方案与剩余事项

阶段 B 的候选预算仍是“该客户＋Key 的全部历史退款行数”，不是显式引用数；一个重度 Key 超过
1,000 条仍可能长期保持未知。不能把失败关闭改成默认无合同来清零。阶段 A/B 的实际质量计数、
多 Key 查询成本、翻页重复补证及真实数据库执行计划，需要目标部署用固定截面验证。
本轮本地测试与 100,001 条导出复验均通过，不替代目标环境的 4640/7/7 截面核验。
