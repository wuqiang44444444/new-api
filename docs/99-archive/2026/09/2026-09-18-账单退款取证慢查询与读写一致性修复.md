# 账单退款取证慢查询与读写一致性修复

> 完成范围仅为 `logs` 退款筛选及读取顺序，不代表整条退款取证链路没有慢查询。
> 后续发现的 Task 快照读取索引缺口与补修见
> [Task退款取证索引补齐与链路验证](2026-09-19-Task退款取证索引补齐与链路验证.md)。

## 问题与目标

用户报告 `GET /api/billing/statement/self` 的退款取证 SQL 返回零行仍耗时 616 ms。
本次保持账单、扣费、退款、写入事务与权限语义，补齐查询索引并验证读写一致性。

## 当前实际情况

- 前一日的任务轮询优化针对 `tasks`，实际数据库已有 `idx_task_usage_poll` 且查询可使用；本次是
  `logs` 的客户账期查询，两者不是同一个问题。
- 交互账单已经恢复单游标与一次退款取证，但原日志表没有 `(user_id, type, created_at)` 索引。
  取证原计划只有 `idx_logs_user_id(user_id=?)`，需要检查该客户历史日志才能排除没有退款的账期。
- 未确认月份仍按既有合同读实时日志；不能用强制确认账单、跳过取证、缓存空退款或提高慢查询
  阈值代替修复。
- 交互读取此前无显式顺序，而历史名称和前 300 个折扣组合依赖遍历顺序，单独加索引存在改变
  展示结果的风险。

## 优化方案与实现

1. 新增 `model/billing_statement_log_index.go`，用独立 GORM 索引描述创建一个非唯一三列索引。
   描述类型禁止 AutoMigrate；不改 Log 字段、默认值、已有索引或任何历史记录。
2. `model/main.go` 只在主节点的同库日志初始化和独立关系型日志迁移完成后接入索引迁移。
   ClickHouse 不执行该 B-tree 索引迁移；已存在的索引不重复创建。
3. `model/billing_statement_reader.go` 保持一次取证和单游标，将关系型交互读取明确为 `id ASC`，
   与原有导出顺序对齐；ClickHouse 原路径保留。金额、退款身份校验、组合上限和聚合算法未改。
4. 新增回归验证完整账单、旧自助账单、使用构成、导出与原始日志在迁移前后相同；覆盖改名、
   301 个折扣组合、跨期原消费补证、时间边界、用户隔离和原生渠道测试排除。验证相同索引键
   可重复写入、事务回滚与持有读游标时并发写入成功，下一次读恰好看到两条提交记录。
5. 审计控制器测试在调用生产 `InitLogDB` 前补齐 `Log` 表，与真实启动前置条件一致；不改变
   审计行为或为不完整测试环境增加生产回退。

### 最小入侵说明

原生 `model/main.go` 的两处迁移调用是必要接线，索引主体和测试均在新增文件。未修改
`model/log.go` 写入入口、Relay、Provider adapter、资金公式或 Task 状态机。未来上游同步需保留
上述日志初始化接线；控制器既有测试只增加一个测试表迁移。
当前架构事实见[客户与上游对账架构](../20-architecture/账单计费-客户与上游对账架构.md)。

### 本地验证

- SQLite 使用项目 Go/GORM 驱动；文件并发测试采用部署已有 WAL、busy timeout 与事务设置。
- MySQL 8.0、PostgreSQL 16 使用无业务挂载、仅绑定本机回环的临时容器，每项测试新建隔离数据库。
  三库均验证迁移幂等、同库/独立日志库迁移、完整账单对照及并发读写。
- SQLite 另在单连接池和反转未排序扫描的条件下验证读取不依赖隐含索引顺序，退款取证计划使用
  新索引的用户、类型及时间三个约束。
- `model`、`controller`、`service` 完整包测试通过；`go vet` 与文档、AI 入口检查通过。控制器
  首轮发现审计测试漏建日志表，补齐该测试前置条件后完整重跑通过。

本机只读抽取 183,282 条日志到临时副本，沿用已有索引定义；主库身份使用测试记录，未复制主库
配置或凭据。通过项目 Go 驱动在副本中运行相同账单查询和合成写入；全部写入、删除和建索引仅
发生在副本。迁移前后的账单投影逐字段一致，每轮 200 条合成写入均可读且无新增错误。

| 测量 | 加索引前 | 加索引后 | 范围 |
| --- | --- | --- | --- |
| 退款取证中位耗时 | 16.694 ms | 0.047 ms | 每轮新建连接，10 次 |
| 完整账单中位耗时 | 35.116 ms | 18.188 ms | 5 次 |
| 单条日志写入 P95 | 0.234 ms | 0.176 ms | 100 次，约 1 KiB 合成正文 |
| 与账单并发的写入 P95 | 0.248 ms | 0.143 ms | 100 次写入、5 次账单读取 |

副本建索引约 158 ms，索引页约 3,072,000 字节。新连接重置 SQLite 连接页缓存，不代表清空操作
系统缓存。该轮没有观察到写入退化，但后测缓存状态、样本量和本机负载影响结果，不能据此声称
索引让写入更快、没有写入维护成本，或承诺生产延迟。

### 部署边界与剩余验收

- 本次未重启正在运行的服务，未给在用数据库建索引；新代码在主节点下次日志初始化时执行迁移。
- SQLite 首次创建索引可能阻塞写入，应先备份并在受控窗口停止其它写入者后启动新版本。
  多节点或独立日志库也需避免多主并发迁移，并观察 DDL 锁等待和可用空间。
- 上线核对实际索引列顺序和退款查询计划，比较完整账单、写入失败率、锁等待和读写延迟；出现
  业务结果差异应停止发布并保留现场，不能通过修改金额或删日志处理。
- MySQL 5.7.8、PostgreSQL 9.6 最低版本、ClickHouse 和目标部署峰值负载本轮未实测；不得据
  本机回归宣称这些环境或生产发布已验收。ClickHouse 本次未改变行为。
