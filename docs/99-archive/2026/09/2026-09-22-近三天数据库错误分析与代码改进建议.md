# 近三天数据库错误分析与代码改进建议

## 问题与目标

根据当前服务数据库近三天的错误记录，区分需要代码修复的诊断缺口、需要进一步验证的实现问题，
以及调用方、配置或上游负责的问题，为后续定向修复提供证据、最小修改范围和验收标准。

本文是一次排障分析与建议记录，不替代当前架构合同，也不代表已批准全部建议。
2026-09-23 已按第 8 节顺序实施四个代码项（合同拒绝诊断、渠道状态变更审计、素材安全诊断入库、Gemini schema 结构诊断）；其余事项仍为建议，未实施。
本次落文档不修改数据库、渠道配置、重试策略、任务状态或资金。

本文已吸收 09-23 的[专家分析复核](2026-09-23-近三天错误专家分析复核.md)，作为本次排障的综合结论与后续事项入口。
复核文档保留逐项证据和推断纠正，实施跟踪以本文“最小侵入、实施顺序和剩余事项”为准。
原 72 小时统计窗口保持不变，延伸窗口单列；已实施范围以第 8 节及实施阶段验证记录为准。

### 用户确认与范围调整

用户已确认：**429 的原因是上游渠道并发不足，暂不处理。** 这一结论来自用户在本次会话中的补充，
不是本地测试对 Provider 容量的独立验证。

因此，429 仅作为历史观测保留，不列入本轮优先修复项；不调整并发、重试次数、退避、换渠策略或
429 的异步结果分类，也不处置由这次 429 引起的两笔图片待核实任务及其资金。
与限流无关的通用待核实可观测性建议保留为后续评估项，不作为本次立即实施任务。

### 5. 关键归因与证据边界

**合同 503：** 09-22 19:01:59 有渠道 56 上游 503；19:05:19 的自动探测则是 HTTP 200、
耗时 263.643 秒，超过 90 秒阈值。系统任务 155477 记录 `disabled=1`；紧接着出现 100 次合同 503。
系统任务 155682 后续记录 `enabled=1`，渠道 56 的成功探测和当前状态时间均为 19:37:27。
两个合同的历史 GPT 路由只指向该渠道，因此自动保护与单渠道依赖可以解释集中不可用。
当前默认禁用码是 401，500—503 属于自动重试范围；不能把最初 503 认定为按状态码触发禁用。
`status_time` 会被覆盖，汇总计数也不是逐渠道提交回执；同轮另有 6 个渠道探测拒绝，不能声称其他流量全部正常。
代码依据见[测试阈值逻辑](../../controller/channel-test.go)、[状态码范围](../../setting/operation_setting/status_code_ranges.go)
和[渠道状态写入](../../model/channel.go)。

**合同 403：** 历史审计表明合同 16 于 09-14 已包含相关 GPT 模型并启用；09-20 14:52 的变更
仅为已有图片模型增加渠道，未增加公开模型名。[规则保存](../../model/customer_contract_entity.go)
会删除并重建规则，所以当前行的 created_at 不是首次授权时间。
缺少请求模型、令牌限制和拒绝分支，不能把 101 次拒绝统一解释为授权尚未配置，也不能证明全是误拒。
同秒成功/拒绝不足以判定客户端主模型与辅助模型不同。
模型未授权的 403 与已授权但无可用渠道的 503 含义不同，应细分内部原因，不直接统一状态码。

**取消流用量：** 用户 106 的 495 笔零扣费全部关联断连，按日期为 124 / 5 / 366 笔；
其中 307 笔 frt=-1000、188 笔 frt>=0。前者是首响应时间未设置的哨兵值，后者也不等于收到文本。
全用户相同缺用量零扣费日志为 505 笔，其中 499 笔关联断连，不得将用户子集外推为全局规律。
[Responses 流处理](../../relay/channel/openai/relay_responses.go) 已在缺 usage 时对收到的文本估算 token，
有输出 token 时再补估算输入 token；“没收到最终 usage 就必定零扣费”不符合当前实现。
这些断连主要发生于其他时段，不能全部归因于 09-22 晚间故障；中位断连耗时也不是慢首包证明。
未取得 Provider usage/账单，实际供应商成本、应收客户费用和少收金额均不能由这 495 笔直接确定。

### 6. 延伸窗口：渠道测试与运行环境

本节统计截止 09-23 14:15:45，不并入前述 72 小时汇总。
渠道测试从 69 次增加至 **78 次、26 个渠道**；互斥原因是上游拒绝 42、超阈值 21、不可达 10、
配置错误 3、素材探测失败 2。21 次超阈值中，detail.upstream_status 为 200 的 12 次、504 的 8 次、666 的 1 次；
这些状态是原因分类的子集，不能再次累加，也不能用事件 status 代替上游 HTTP 状态。
新增记录为不可达 7、超阈值 1、素材探测失败 1；未观察到新增已入库 API 错误或客户 Task 失败。
这不等同于完整请求成功率证明。

夜间另有 **9 个系统任务**租约过期：6 个 channel_test、3 个 error_report，不是 9 个客户生成任务。
电源日志证实本机反复休眠/唤醒；例如 02:45:05 创建测试，随后休眠，03:00:16 唤醒后于 03:00:29 标记过期。
结合[系统任务租约回收](../../model/system_task.go)，休眠导致无法及时续租是高置信度解释。
若该实例需要持续承载客户流量，应优先解决主机持续运行和网络可用性，不通过取消租约掩盖。
另有人报告 SQLite 只读连接失败，但缺连接路径、权限、环境和扩展错误码，不能据此认定写负载或锁竞争导致业务故障。

## 优化方案

以下保留方案与验收要求；四个已实施代码项及仍待处理的事项以第 8 节为准，不构成修改线上配置或历史资金的授权。

### 1. P1：合同授权与选渠诊断补齐（已确认缺口，高置信度）

**代码证据：**

- [合同入口](../../middleware/customer_contract.go)：`applyCustomerContractDistributeGate` 将错误
  转成通用合同不可用响应，未在该出口附上客户模型和具体拒绝诊断。
- [分发入口](../../middleware/distributor.go)：合同选渠失败继续使用相同通用响应。
- [合同路由](../../service/customer_contract_routes.go)：`EffectiveContractRules` 只保留可用项；
  `customerContractRoutes` 在空路由时返回通用范围错误。
- [资格判断](../../model/customer_contract_availability.go)：内部已有渠道、分组和模型资格判断，
  其具体错误被压成 `Available` 布尔值，不能从最终事件复原。
- [统一事件构建](../../clienterrlog/recorder.go)：未附加的阶段和原因最终成为 `unclassified`。

**最小修改方向：**

1. 在模型已解析的位置传入客户模型名，不依赖正文采集成功。
2. 在实际拒绝点记录固定阶段和原因，区分令牌模型限制、合同未列出模型、全部候选不可用、
   渠道禁用、能力缺失、路由读取失败和入口不匹配。原因来自既有判断，不用模型名、错误消息关键词或另一次选渠推断。
   全部候选不可用不必然等于自动禁用；只有关联真实状态变更证据时才记录自动禁用来源。
3. 如需保存合同版本、候选数量等管理诊断，先扩展 `clienterrlog` 的受控白名单并限制大小；
   仅向 `Report.Detail` 传值不会自动落库。
4. 保持客户公开错误脱敏，不直接暴露管理员合同细节、渠道信息或数据库原始错误。
5. 复用已有合同路由与资格判断；诊断不能变成第二套准入规则，也不能引入绕过合同的 fallback。
6. 拆分内部原因，保留授权拒绝与服务不可用的状态语义；不因两处复用 ErrCustomerContractScope
   就把所有 403/503 统一成同一个状态码。

**实际收益与限制：** 下一次类似七分钟内集中失败时，可以区分授权、资格与基础设施问题。
这项修复本身不证明、也不保证消除本次 100 次 503 的底层故障。

**验收：** 覆盖令牌模型限制、合同未列出、渠道停用、能力缺失、路由读取失败、入口不匹配和正文超限；
每个请求只产生一条最终事件，模型、合同版本、候选数量与原因可查询。
授权拒绝仍为 403，已授权但无可用候选仍为 503；不放宽权限，也不向客户泄露渠道身份。

### 2. P1：渠道状态变更审计（已确认历史追溯缺口）

**代码与数据证据：** [渠道状态更新](../../model/channel.go) 覆盖写入 status_reason/status_time；
[自动测试](../../controller/channel-test.go) 的 disabled/enabled 是汇总计数，不能替代逐渠道状态提交事实。
当前记录支持本次自动禁用解释，却不足以持续复原任意时间的实际转换与触发来源。

**最小修改方向：** 在现有状态提交路径记录状态前后、自动/手工来源、受控触发原因和关联测试/请求。
实施前核对所有实际状态写入口，复用已有审计基础设施；如需新增记录载体，只保存不可变事件，
不建立第二套渠道当前状态或独立健康判断。
记录必须与已成功提交的转换对应，明确提交失败、没有变化与成功变更的区别，不把调用尝试写成已禁用。
自动测试结果与该记录关联，不通过重跑测试或再次选渠推断历史。

**验收：** 自动禁用、自动恢复、手工操作、重复请求、并发竞争及提交失败均可区分；
写入失败不得出现“当前状态未变但审计声称已成功变更”的记录。
关联合同不可用时只能使用已确认事实；保持既有自动禁用策略及合同范围。

### 3. P1：素材上游安全诊断进入持久化事件（已确认缺口，高置信度）

**代码证据：**

- [素材 adapter 诊断](../../relay/channel/task/seedance/assets/diagnostic.go) 已能区分超时、连接、
  重置、HTTP 拒绝、业务错误和响应解析失败，并限制 Provider code 的字符和长度。
- [素材 service](../../service/asset_service.go) 将安全诊断写到文本日志后，返回通用
  `ErrAssetUpstreamError`。
- [素材诊断映射](../../service/asset_client_diag.go) 主要覆盖 4xx；5xx 进入空阶段、空原因。
- [素材 controller](../../controller/asset.go) 最终返回脱敏的 `asset_upstream_error`。

**最小修改方向：** 从现有 adapter 的错误类型产生一份受控结构化诊断，供文本日志和统一事件共同使用。

### 4. P2：流式取消、用量证据与交付诊断

**当前实现：** [流式扫描器](../../relay/helper/stream_scanner.go) 在请求上下文取消后关闭上游响应，
停止继续消耗；[流式分类](../../service/relay_stream_error_event.go) 记录 `client_disconnected`；

当前 [Responses 流处理](../../relay/channel/openai/relay_responses.go) 已有文本 token 估算，
本项补足观察证据，不再新建另一套估算或结算实现。

**建议：**

- 将“观察到连接取消”和“确定调用方责任”区分，避免报表暗示已确认是用户主动停止。
- 在已有受控诊断内区分首响应时间未设置、收到首事件但无文本、收到文本、取得 usage，
  记录现有估算是否实际使用及协议完成/结束阶段；不记录流式正文。
- 展示首响应指标时将 -1000 解释为尚未观察到首事件，不显示成负延迟或零延迟；
  首事件、文本交付和供应商计费用量分别统计。
- 如果同时存在协议失败和连接取消，保留两种观察，不因最终连接状态丢失已确认的协议异常；
  不能反向把没有协议异常证据的取消推断为 Provider 故障。
- 原始事件仍完整保留，统计展示按客户端取消、协议失败、读取/超时异常分开。

**边界：** 不直接增大超时，不关闭取消传播，不自动重放请求；消费、实际用量和完整交付是不同事实，
不因断开统一退款，也不因存在消费日志声明生成成功。
495 笔零扣费仅作为潜在成本暴露调查对象，不称为已确认损失；按请求关联 Provider 用量/账单后，
分别确定实际成本与收费合同是否有缺口。不得用完整成功请求均价估算取消请求损失，
不增加最低收费、不直接补扣、不无上限继续读取取消流。

**验收：** 正常完成、主动取消、流内失败、读失败及失败后断开可区分；流式 HTTP 已提交为 200 时不伪造
HTTP 失败状态；一次请求仍只产生一个最终事件，计费逻辑不被诊断修改。
覆盖无首事件、仅元数据事件、有文本无 usage、有 usage 的场景；验证已有文本估算路径得到正确标记，
观察代码不重复结算，不把未知 Provider 成本写成零或客户 quota。

### 3. 复核查询口径

以下只读查询用于复核核心数量，不导出详情正文。Task 当前状态可能随后台执行变化；
历史窗口事件也可能因后续回填产生差异，不能把重跑结果当作已保存的历史快照。

```sql
SELECT event_type, module, COUNT(*) AS events
FROM error_events
WHERE created_at BETWEEN 1789830794 AND 1790089994
GROUP BY event_type, module;

SELECT COUNT(*) AS error_rows, COUNT(DISTINCT request_id) AS requests
FROM logs
WHERE type = 5 AND created_at BETWEEN 1789830794 AND 1790089994;

SELECT status, billing_state, COUNT(*) AS tasks
FROM tasks
WHERE created_at BETWEEN 1789830794 AND 1790089994
GROUP BY status, billing_state;

-- 同一窗口内缺用量的零扣费；用 EXISTS 防止连接放大计数。
SELECT COUNT(*) AS zero_usage_logs,
       SUM(CASE WHEN l.user_id = 106 THEN 1 ELSE 0 END) AS user_106_logs,
       SUM(CASE WHEN EXISTS (
         SELECT 1 FROM error_events e
         WHERE e.request_id = l.request_id AND e.reason = 'client_disconnected'
           AND e.created_at BETWEEN 1789830794 AND 1790089994
       ) THEN 1 ELSE 0 END) AS disconnect_overlap
FROM logs l
WHERE l.type = 2 AND l.quota = 0
  AND l.content LIKE '%上游没有返回计费信息%'
  AND l.created_at BETWEEN 1789830794 AND 1790089994;

-- 延伸窗口独立统计；不要把上游状态子集再次加到 reason 汇总中。
SELECT reason, COUNT(*) AS events
FROM error_events
WHERE event_type = 'channel_test'
  AND created_at BETWEEN 1789830794 AND 1790144145
GROUP BY reason;
```

已复核的零扣费查询结果依次为 505、495、499；用户 106 的零扣费与取消交集为 495。
合同历史通过 before_state/after_state 的模型与渠道集合比较，不以规则行创建时间代替授权时间。
