# 门窗双图编辑本机调用分析

## 问题与目标

用户要求用 `gpt-image-2.5-flare`、长中文门窗合成提示词与两张 HTTPS PNG，通过本机程序真实调用，
分析 API 故障与业务效果风险。最终明确：使用本机渠道中转，不直接测试上游。
本文不保存完整用户提示词、图片地址、凭据、图片内容或原始 Provider 响应。

## 当前实际情况

### 真实检查与测试

- 本机后端监听 3501，使用本地 SQLite；已登录管理页面为 `http://localhost:3500`。
- 模型配置在渠道 29、48、105、108；本次后台定向测试选择 105（OpenAI 兼容类型）。
- 两张输入图可读取 PNG 文件头，HTTP 206；尺寸分别为 1511×844、5000×5000。
  仅验证本机能读取文件头，未完整解码，不代表供应商侧下载一定成功。
- 旧测试 Key 已软删除，本机原请求返回 HTTP 401，没有进入 Provider。
- 在用户“使用本地渠道”的表述尚未澄清时，曾使用本地保存的 105 连接直发原 JSON 一次，
  返回 HTTP 403、非 JSON 正文；未保留足够正文诊断，原因未确定。该结果不是本机中转结果，
  不能用于判断本机代码有无缺陷。用户澄清后停止直接调用上游。
- 本机渠道 105 的快捷“测试连接”走聊天端点，返回 `model_not_supported`：图片模型不可走聊天接口。
- 在本机渠道 105 的模型测试弹窗明确选择 `Image Generation (/v1/images/generations)`，
  对 `gpt-image-2.5-flare` 实际测试一次，页面显示成功，耗时 21.01 秒；本地渠道记录同步为
  response_time=21006ms。未取得图片内容，不把页面成功扩大为像素/图像质量验收。

### 为什么后台测试不能复现用户 JSON

`controller/channel-test.go` 的 `TestChannel` 只读取 model、endpoint_type、stream。
图片请求由 `controller/channel_test_image_profile.go:14` 构造，提示词固定 `a cute cat`、
数量为 1、该模型尺寸为 1024×1024，无参考图。不能把这个成功结果称为用户门窗编辑请求成功。

`/v1/images/edits` 是本次语义对应的正式客户入口。`relaykit/dto/openai_image.go` 已声明
`images` 与 `mask`；OpenAI adapter 的 JSON 编辑分支直接返回请求，不自动替换提示词变量，
也不自动创建蒙版。当前代码证据不支持“JSON images 必然被网关丢弃”的说法。

本机管理员原先无有效客户 API Key。经用户确认，通过已登录页面创建受限临时测试 Key：
限本模型、仅回环 IP、USD 1、1 小时到期、测试后禁用。随后已向本机 3501 正式编辑接口发送
原 JSON，利用原生管理员选渠功能固定 105 中转；没有绕过鉴权、恢复已删除 Key 或借用其他用户 Key。

### 请求本身的问题

1. 六处模板变量未展开：winW、winH、houseTypeLine、demandLine、envLine、crowdLine。
   JSON 字符串不会自动插值；网关当前路径也未实现业务模板展开。模型没有收到实际毫米尺寸及装修条件。
2. 提示词反复要求“蒙版选中区域”，请求却没有 mask。文本不能提供确定的像素区域边界。
3. 没有 size、quality 等输出规格。提示词里的“8K”不能当作输出分辨率配置或承诺。
4. “蒙版外像素级不变”需要软件在结果交付时按明确蒙版合成原图并核验区域外像素；
   仅靠模型提示词不能作为这个业务指标已经满足的证据。
5. “100% 复刻全部产品零件”和透视/光影调整是需要验收的产品保真要求；需逐项比对，不能以
   HTTP 200 或一张生成图自动判定达成。

## 优化方案

- 将连接测试与业务验收区分：当前后台测试手工指定图片端点；原门窗请求走本机 `/v1/images/edits`。
- 调用方在发送前展开变量并校验必填尺寸；缺值时先提示用户，不让占位符进入实际生成请求。
- 提供与基底图对齐的实际蒙版；具体传输形状依渠道协议验证，不能未经验证凭模型名宣称 mask 支持。
- 如果业务必须保证区域外完全不变，应在最终交付阶段保留原图外部像素。此建议尚未实施，且不意味着
  修改网关原生通用图片协议；更适合门窗合成业务层负责。
- 完成原请求真实调用后分别核对：HTTP 状态、实际选渠、图片交付、用量和本站扣费，再讨论视觉效果。
  本轮已取得原 JSON 经本机中转返回 HTTP 200、图片 URL 和本站结算的证据，详情见下；
  图片实际下载及视觉质量仍未验收。


## 原 JSON 经本机渠道中转的实际结果

用户明确批准后，创建受限临时 Key 并只向
`http://127.0.0.1:3501/v1/images/edits` 发送一次原 JSON，利用管理员原生选渠语法固定 105。
不替换占位符，不补蒙版，不变更参考图，不添加 size／quality／response_format，不使用异步任务。

| 项目 | 实际观测 |
| --- | --- |
| 本机 HTTP 结果 | 200 |
| 耗时 | 24.25 秒 |
| 响应图片项 | 1 个 URL |
| 输入 Token | 2751 |
| 输出 Token | 439（图片输出 439） |
| 图片输入 Token | 上游报告为 0 |
| 本机消费日志 | 182570，渠道 105，路径 `/v1/images/edits` |
| 钱包结算 | 13463 quota，约 USD 0.026926 |
| 临时 Key | 测试后已禁用，status=2；剩余 486537、已用 13463 quota |

结算与当前配置一致：`round((2751 + 439 × 6) × 2.5) = 13463`。
未叠加 prompt/input 或 completion/output 等同义字段；用户额度与 Key 记录的业务含义分别保留。
本轮只核对消费日志和临时 Key 已用/剩余额度，没有以并发期间全账户余额推导单笔金额。

**结论：原 JSON 能通过本机编辑入口和渠道 105 获得成功响应，不能把现有问题笼统归为接口调用失败。**
这次只保留脱敏摘要，未保留或下载响应图片 URL，因此不宣称图片 URL 可交付、成图符合门窗要求、
两张图确实被语义使用、蒙版外像素不变或 8K 已达成。`image_tokens=0` 是实际报告，但它既可能反映
供应商统计口径，也可能暴露参考图处理问题；需要成图比对或供应商记录才能区分，不能直接判定
网关丢图。当前 JSON DTO 和 adapter 路径保留 images 字段。

本轮未改业务代码、模型价格、渠道连接、模型映射或自动禁用策略；新增测试凭据按授权在结束时禁用。
文档检查 `task docs:check`、`task ai:check` 通过。


## 后续客户错误：images 元素类型不符合标准

用户随后提供 `invalid_type` 错误：`images[0]` 期望 object，实际为 string。
核对 2026-09-17 的 [OpenAI 官方编辑接口](https://developers.openai.com/api/reference/resources/images/methods/edit)，
JSON 参数 `images` 为对象数组，元素使用 `image_url` 或 `file_id`；URL 输入形状应为
`{"images":[{"image_url":"https://example.com/base.png"},{"image_url":"https://example.com/reference.png"}]}`。
`image_url` 在该接口内为字符串，不是 Chat Completions 的嵌套 `{url: ...}` 结构。

前述原请求使用 URL 字符串数组，不符合这份原生 JSON 合同。105 单次返回 HTTP 200 只能证明当时
该连接接受这个请求，不能把它泛化为各渠道支持的标准形状，也未验证该次输出确实使用了参考图。
先前提供的 curl 沿用字符串数组，未明确这个协议差异，应纠正为对象数组。

代码证据：`relaykit/dto/openai_image.go:33` 使用 RawMessage 保留 images；
`relay/channel/openai/adaptor.go:504` 的 JSON 编辑分支原样返回请求，不执行字符串到对象转换。
因此这种类型不匹配可以透传到上游才被拒绝。当前本机近期普通日志未找到与客户新错误对应的
失败事件，客户未提供请求编号／实际选渠；尚不能断言本次错误来自 105、108 或其它部署。

建议客户端按所调用原生协议发送对象数组；不要为修正一个 curl 示例而在 NEWAPI 原生路径中
加入按模型名猜测和无依据双格式转换。此类型错误发生在 images 参数结构校验，与此前提示词
变量未展开、缺少蒙版属于不同层次的问题。对象数组修正本轮仅核对文档和代码，未再次收费调用。
