# 我的账单复核与下载实施方案

## 问题与目标

本次承接“我的账单”代码评审，修正可确认的数据解释问题，并增加用户下载当月账单的按钮。
用户已明确：日志完整性由管理员负责，不引入日志覆盖率、账期完整性状态、保留闸门、额外账本或补偿机制。
本方案先记录再实施；保持消费与退款日志为金额事实源，不改变实际扣款、合同折扣或上游原生计价。

## 当前实际情况

1. 净额为日志消费减退款；合同在计费时已经生效，账单不读取当前合同重新计价。跨期退款保留负号，
   异步调整不增加逻辑调用次数。同月合同生效/停用的倍率变化已有测试。
2. 原价目前按每笔整数 quota 除以冻结分组倍率和合同折扣反推。100 × 0.87 × 0.8 舍入成 70 后，
   反推约 100.5747，不能等同于实际折前金额。这是展示精确性边界，不是合同重复扣款。
3. 同步日志可能按计价模型入账，而合同匹配客户公开模型。现有账单快照只保存 Provider 模型；
   带修饰符的多个客户模型可能汇总到同一计价名称。
4. 新客户账单直接累加 prompt_tokens；OpenAI 与 Anthropic 的缓存包含关系不同。
   旧用量构成已有 input_tokens_total / usage_semantic 的解释规则，可在本地账单复用。
5. Batch 行级事实保存 CachedTokens，完成日志却只汇总输入和输出，缓存读取会在账单中显示为零。
6. 我的账单没有下载按钮。现有接口已经返回整月完整汇总，已有上游 CSV 的下载和转义模式。
7. 本次以当前工作区为基线；已有渠道图片测试相关修改不属于本任务。尚未访问生产数据或验证真实外部数据库。

## 优化方案

### 1. 原价、优惠与预扣文案

- 保留既有历史倍率反推算法，界面和下载明确使用“估算原价”“估算优惠”，说明整数扣款反推存在
  舍入误差；无法解释的历史数据继续显示未知，不补当前价格，不新建折前金额账本或扩展全部计费入口。
- 期间消费减退款不改值；说明其中包含任务预扣和退差额，不能等同于所有任务都已最终结清。
- 客户账单列表与客户明细复用同样文案，防止相同接口在两个入口有不同解释。

### 2. 客户模型身份

- 在现有本地 statement_snapshot 中补 customer_model，来自创建/请求时的 OriginModelName。
- 客户账单和专属下钻按这个冻结身份聚合、筛选和展示；旧日志无此字段时保留原记录模型，不根据
  当前配置猜测历史身份，不回写日志。
- 原生日志 model_name、原生定价和通用日志接口保持现有语义。专属账单在读取已有日志时完成投影，
  不引入跨数据库 JSON 方言或新的索引/迁移。

### 3. 用量投影

- 输入定义为总输入，缓存读取/写入为其中的子项；依据已保存 input_tokens_total 或 usage_semantic
  归一。没有缓存时保留已记录输入；存在缓存而缺少可确认语义时，返回输入不可用计数，页面和 CSV
  显示未知，金额不受影响。这只是字段解释质量，不新增管理员负责的日志完整性检测。
- Batch 完成日志从既有行级事实合计缓存读取并记录 OpenAI 输入语义；不改变行级定价或资金目标。

### 4. 用户下载

- 采用 UTF-8 BOM CSV，普通用户在“我的账单”点击“下载账单”；复用当前已认证的 self 接口响应。
- 导出当月全部 API Key 与模型行、后端总计、累计扣减/退回/净额、冻结分组和合同倍率、用量、
  字段解释质量、账期和生成时间；不依赖展开状态，不从 DOM 提取、不重新计算正式汇总。
- 金额按当前展示币种进行格式化，CSV 最多保留八位小数；未知为空/不可用，负退款保留符号。
- 无数据、加载、刷新或错误时不能下载；只允许自助 API Key 维度，文件不含渠道、Provider、凭据或
  请求私有信息。文本做 CSV 转义和公式前缀保护。无需新增导出服务、任务、对象存储或下载授权机制。
- 使用现有 Button、Hugeicons、通知和七语言 i18n 流程。

### 5. 验证与最小侵入

- 先增加行为回归：客户模型聚合/下钻/租户隔离、混合用量语义、Batch 缓存实际日志、CSV 全量与
  脱敏、未知/负数、下载成功/失败/切月加载/空数据。
- 后端限定 model/service/controller 相关账单、合同与 Batch 测试；前端执行受影响测试、typecheck
  和变更文件 lint；文档执行 task docs:check、task ai:check。
- 优先修改已有本地账单文件和增加独立测试；本次不修改 NEWAPI 原生扣费文件。若发现必须扩大
  原生接线范围，先在本文件写明必要性、接线点和上游同步影响。

## 实施与验证记录

### 二次质量评审修复方案

本次用户已授权完整修复后续评审的四项问题。逐项补失败回归后实施：

1. 页面和 CSV 复用账单专属金额格式（八位精度，禁用非零金额向上抬高），覆盖微小消费、退款及
   当前币种转换；不改变系统通用余额格式。
2. 文本结算日志冻结当次已经确定的输入语义。原生文本结算文件只增加一行本地日志投影调用，
   不改计价、扣款或 Provider 响应。必要性是只有该入口同时拥有最终用量和结算语义；上游同步只需
   保留这一行接线，具体投影与独立回归放入新增文件。
3. 异步图片完成日志从已持久化 usage 投影缓存读写、输入语义与总输入，复用已有缓存计数规则；
   不修改任务结算金额，验证重复交付不会增加扣款或用量。
4. Batch 保留 int64 原始批次用量到既有日志元数据，原生 int32 日志列仍按原有界限保存。
   账单读取完整批次事实，不使用被截断的列作为总用量。客户汇总、明细统计及上游用量使用一致事实，
   不新建账本或数据库列。覆盖跨 int32 的输入、输出、缓存及重复结算。

最终重新运行相关账单、合同、文本、图片和 Batch 回归、前端测试、类型检查、lint 与文档检查。

### 二次质量评审修复结果

四项均已实施。先运行回归，分别复现小额金额被放大、普通 OpenAI/既有 Claude 转换的缓存输入未知、
异步图片缓存计数为零、Batch 大数输入/输出/缓存及明细被截断，再确认修复后通过。

- 客户明细、管理员客户列表与 CSV 复用现有账单模块内的金额格式；1 quota 在默认 USD 下均显示
  `$0.000002`，退款保留负号；同时验证 CNY、额度显示和低于展示精度的汇率换算不会被抬高。
- 新增 `service/billing_statement_usage.go` 承载用量日志投影，文本原生结算文件只新增一行调用。
  原生计价、Provider 响应和实际资金计算均未改变。
- 图片结算测试贯通预扣、完成、日志交付和账单，核对 1000 输入、800 缓存读取、100 缓存写入、
  260 quota 合同折后净额，重复结算与重复交付不增加扣款或用量。
- Batch 测试使用两条已经持久化的行级事实，合计输入 26 亿、输出 30 亿、缓存读取 22 亿；
  客户汇总、专属明细和上游统计一致，重复结算后净额仍为 20 quota。
- 扩展后端回归：175 个顶层用例通过，1 个 ClickHouse 用例因无连接配置跳过。
- 前端账单及接口回归：11 个测试文件、48 个用例通过；类型检查与变更文件 lint 通过。
- 文档检查：`task docs:check`、`task ai:check` 均通过。

未新增日志完整性检测、自动补历史数据、数据库迁移或额外账本。历史日志中已经缺失或截断的事实
不自动回写；修复后的程序从新结算日志开始保存完整信息。生产账单及真实外部数据库仍待实际验收。

- 已在现有账单快照补充客户公开模型，客户汇总与专属明细使用同一身份；历史无快照行继续使用原记录。
- 已复用既有输入语义解释，修复跨协议输入汇总，并把 Batch 行级缓存事实带入完成日志。
- 已将客户明细和管理员列表的原价、优惠标为估算值，补充预扣及调整说明；金额算法、合同匹配和
  实际扣款未改动，没有增加日志完整性检测、账本、数据库迁移或导出服务。
- 已增加自助账单 CSV 下载及七语言翻译，包含折叠模型；加载、切月、失败、空数据时不能导出。
- 实现放在本地账单与 Batch 文件及新增独立测试中，未扩大 NEWAPI 原生扣费接线面。
- 产品与架构当前事实已更新到 `docs/10-product/客户与上游对账单产品说明.md` 和

- 未运行真实 MySQL/PostgreSQL/ClickHouse 或生产账单对账；本地通过不代表真实 Provider、生产账单
