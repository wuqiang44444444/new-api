# 客户合同添加模型多选分析与方案

## 问题与目标

客户合同编辑器的添加渠道已支持多选，但模型仍需逐个选择、配置渠道并添加。管理员为多个模型
配置合同时存在重复操作，需要评估并设计模型多选能力。

用户明确要求遵守当前模型添加规则。本方案仅扩展管理端批量录入方式，沿用现有模型、组、渠道、
折扣和保存合同的语义。2026-09-23 已按本方案完成前端实现与自动化测试：两个入口共用模型多选、
逐模型渠道选择与整批校验逻辑，新增批量交互与折扣/冲突回归用例，并补齐中英文文案；
页面人工验收仍未执行，本文件保留方案与验收清单，不作为生产发布依据。

### 必须保留的规则

| 规则 | 多选扩展的约束 |
| --- | --- |
| 模型候选来源 | 使用当前路由组的精确模型候选，不开放自由创建，不根据模型名称或价格推断资格 |
| 渠道候选来源 | 每个模型独立使用当前组下对应的有效渠道，不将全部模型和全部渠道无条件组合 |
| 单渠道默认选择 | 某模型恰有一个候选渠道时自动选中；多个候选渠道时由管理员明确选择，不自动全选 |
| 已有模型仍可选 | 已列入合同的模型可以继续添加其他渠道，不因模型已经存在而从候选中排除 |
| 模型名称 | 保持精确名称；同一合同中仅大小写不同的模型名不能共存 |
| 组合唯一性 | 同一合同内模型＋渠道不能重复；路由组不是该唯一性的附加维度，换组不能绕过重复检查 |
| 折扣范围与格式 | 继续支持 `0.8`、`80%`、`8折`；归一化后大于零且不超过一，沿用八位精度及各输入格式的小数位限制 |
| 同模型折扣一致 | 同一模型跨渠道、跨组必须使用相同折扣；不同模型允许不同折扣，批量操作不能覆盖已有折扣 |
| 冲突处理 | 重复组合、名称冲突、折扣冲突必须明确提示，不静默跳过、覆盖、合并或替换 |
| 新旧来源区分 | 新增或改变来源须当前有效；已保存且来源未改变的失效规则允许保留和编辑，运行时仍排除失效来源 |
| 添加与保存分离 | 添加只修改草稿；最终保存仍提交完整规则集、变更原因和更新所需版本，沿用现有事务、审计和冲突处理 |

### 可行性与主要问题

后端已能保存多个模型的规则，候选接口也已提供每个模型对应的渠道。现有数据结构能够承接前端
批量展开后的规则，因此本方案预计无需新增后端接口、数据库表或迁移。

真正需要处理的是模型与渠道之间的对应关系。不同模型可能没有共同渠道，但分别具有合法来源，
仍应能够按现有规则加入合同。把模型下拉框直接改为多选、继续共用一个没有模型归属的渠道数组，
会导致无法表达各模型选择，或生成渠道不支持的组合。

“所有已选模型必须具有共同渠道，否则分批添加”不是当前业务约定，不作为本方案的限制条件。
同样，取渠道并集后静默跳过不支持的组合，会使实际新增范围与管理员预期不一致，不采用该方案。

## 优化方案

### 交互方案

1. 保留路由组单选，将模型选择改为可搜索的多选，复用已有 `MultiSelect`，支持全选、清空和紧凑的
   已选数量展示。全选沿用公共组件对全部候选的语义，文案应避免让管理员误以为只选当前搜索结果。
2. 选中模型后，逐模型展示渠道多选行。每行标明精确模型名称，只提供该模型在当前组下的渠道。
   唯一候选自动选中；多个候选保持未选择，管理员可以逐项勾选或显式全选。
3. 保留本次添加使用的折扣输入。同一次批量添加使用该折扣，但不将其升级为合同级统一折扣。
   需要不同折扣的模型可以分批添加；已有模型折扣不匹配时提示冲突，不自动改写已有规则。
4. 添加前显示待添加模型数与规则数。规则数是各模型已选渠道数之和；任何模型未选渠道时明确提示
   对应模型，不能将它当作零条规则静默略过。
5. 点击添加时检查整个待添加集合以及它与已有草稿的冲突。全部通过后一次追加到草稿；任一失败
   则本次整批不追加，保留输入，并指出具体模型及相关渠道或折扣冲突。
6. 成功后清空待添加模型和各模型的渠道选择，保留路由组及折扣，沿用当前连续添加习惯。
   最终保存继续使用现有合同保存入口。

示例：同组内模型 A 仅支持渠道 X，模型 B 支持渠道 Y、Z。多选 A、B 后，A 自动选择 X，B 由管理员
选择 Y、Z；添加生成 A/X、B/Y、B/Z 三条规则。A、B 无共同渠道也可以完成这次批量添加。

共同渠道批量勾选仅作为后续可选便利功能，不是第一版必需项，也不能替代逐模型渠道选择或自动
扩大已选范围。

### 选择状态与校验

- 待添加状态改为模型列表和按精确模型名记录的渠道选择；渠道候选仍由现有组模型数据推导，不复制
  一份新的来源资格规则，不修改候选接口的原生及类型化渠道边界。
- 切换组时清空待添加模型和渠道。增加模型时只初始化新增模型的渠道；保留仍选中模型的显式选择。
  移除模型时同步移除它的待添加渠道；重新选中时按当前候选重新初始化。
- 候选刷新导致模型或渠道失效时明确标识并阻止该待添加项提交，要求重新选择，不自动替换渠道或
  静默减少规则。该处理仅针对待添加区，不清理已有合同中的历史失效规则。
- 校验同时覆盖待添加批次内部及已有草稿：精确模型来源、每个模型至少一个有效渠道、规范化折扣、
  大小写冲突、模型＋渠道重复、同模型跨组跨渠道折扣一致。
- 批次内部需要先完整校验再生成并一次追加规则，避免循环调用旧 `addRule` 造成部分成功、提前清空
  输入或读取旧状态。失败时保留原草稿和待添加选择。
- 每条新规则使用对应模型的价格预览及当前组倍率事实，不能复用第一项模型的价格。服务端保存继续
  是最终校验边界；候选加载后发生的渠道停用等变化仍由原有保存校验处理。

### 验收与验证计划

| 场景 | 预期结果 |
| --- | --- |
| 单模型、单候选渠道 | 保持自动选中，添加结果与当前行为一致 |
| 单模型、多候选渠道 | 不自动选择，显式多选或全选后逐渠道生成规则 |
| 多模型、无共同渠道 | 各模型按自己的选择成功添加，规则数为渠道数之和 |
| 多模型、部分共享渠道 | 不产生任何模型不支持的组合，不扩大授权范围 |
| 某个已选模型未选渠道 | 指出对应模型，整个批次不追加 |
| 已有模型新增其他渠道 | 相同折扣允许添加，模型仍在候选中 |
| 重复组合或跨组重复组合 | 明确报错，整个批次不追加，不覆盖已有规则 |
| 仅大小写不同的模型名 | 批次内或与草稿冲突均拒绝 |
| 折扣输入与冲突 | 等价格式按原规则归一化；无效输入、超精度及同模型折扣不一致均拒绝 |
| 不同模型不同价格 | 每条规则使用其模型的价格，不复用其他模型价格；已有不同模型折扣不被覆盖 |
| 切组、增选、移除与重选模型 | 无残留错误绑定，保留仍选中模型的显式选择，新增模型按候选初始化 |
| 待添加候选失效 | 明确要求修正，不自动替换或跳过；保存时的服务端资格校验继续生效 |
| 已有历史来源失效 | 不被模型多选逻辑删除，原有保存与运行时边界保持不变 |
| 合同与合同模板 | 两个入口的批量添加规则一致，各自的版本、原因和保存流程保持有效 |
| 空候选、长模型名与大量选项 | 空状态清晰、已选项紧凑可查、布局可滚动；搜索、全选、清空和键盘操作可用 |
| 中英文界面 | 新文案、数量和错误信息均正常展示，逐模型渠道控件具有可区分的可访问名称 |

实施后先运行两个入口受影响的 Vitest/React Testing Library 用例，再执行前端 typecheck、相关文件
lint、format 检查及适用的构建检查。页面验收需覆盖窄屏、长名称、搜索与多选状态。
如实施意外涉及后端合同校验，须增加对应的行为回归，不能仅凭前端测试宣称后端兼容性已验证。

### 风险与剩余事项

- 模型数量较多时逐模型渠道行会变长，实施时需验证滚动、紧凑展示与错误定位，不能隐藏未处理项。
- 候选读取与保存之间存在配置变化，前端提示不能代替服务端最终资格校验。
- 合同与模板当前各有添加逻辑，实施时应同时覆盖，防止一个入口遗漏同模型折扣或重复组合检查。
- 代码实现与自动化测试已完成（2026-09-23）；页面人工验收（窄屏、长名称、搜索、多选状态、中英文界面）仍未执行，完成前不得视为生产可用。
- 完成后再按文档治理规则收敛已验证事实；本次不执行事实文档更新或归档。
