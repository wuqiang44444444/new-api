# 账单生产修复安全边界与验证

## 问题与目标

修复代码评审确认的三个问题：旧解析草稿跨升级发布、离线补修绕过维护代际、分批导出重复扫描
同一 Key 的退款历史。复用已有版本、维护控制和来源修订机制，不建立第二套资金账本。

## 当前实际情况

- 现有 ParserVersion 未参与生成和发布校验；导出字段版本不能约束已经生成的草稿。
- 现有 SQLite 补修工具独立连接数据库，没有维护状态检查；备份不等于账单发布屏障。
- 完整历史退款核验保留正确业务范围，但每个导出批次重复遍历历史；单批超时可能限制大客户。
- 全用户原因核验中的 66 笔及专家补充的其他缺口属于历史数据裁决，不能凭本地数字自动更改生产
  日志或 used_quota。本轮代码修复不执行真实资金、历史日志或生产配置写入。

## 优化方案

1. 冻结并检查解析规则版本，拒绝旧规则草稿的生成及发布，既有确认版本继续幂等读取。
2. 补修写入必须持有当前维护代际；进入维护关闭确认，失败和进程中断保持维护状态。结束维护
   需要明确核验依据，不自动开启确认。修复日志不会改变已有正式版本，需另建更正版本。
3. 在一次读取内复用退款引用核验，复用必须有一致性依据，内存和执行时间有界；取消、来源变化
   应失败，不把未完成核验当作唯一引用。缓存空间不足时仍对未缓存引用扫描完整历史，不设业务记录
   数量门槛；分库不复用没有事务修订保障的计数。
4. 验证升级前 pending/queued、升级后新草稿、旧确认版本、维护并发与失败、退款重复/跨月/取消、
   多批读取成本，以及用户/Key/Task 金额和余额不变。覆盖 SQLite/MySQL/PostgreSQL 支持边界。

## 历史金额补正的生产约束

- 已确认月份保留原确认版及下载产物，以更正草稿记录客户可见原因、逐笔差额和依据；管理员确认
  后切换当前版本。已发送或已对账账单须走客户告知流程，需要重新确认的客户按其既有对账约定
  执行；技术补修不得自动代替客户确认。没有确认版的月份也应记录补正前后对照和告知范围。
- 66 笔只能在生产一致性快照上重新满足全部证据条件后列入批准清单。用户 106、80 及 randy
  其余缺口逐组裁决或记录排除理由；未裁决不得生成“全账户已核准”累计校准目标。
- 固定快照标识、核验时间及日志 ID 上界；仅 MAX(id) 不能识别旧行修改。不得把开发库数量硬编码
  为生产修复清单，不再次扣款或退款，不直接覆盖 used_quota。
- Responses、多段转换链、缓存写入和工具附加费的扩大解析仍须按历史 writer 证明。无法证明
  单位换算的附加费继续标记 auxiliary_charge，不强行估算；这是独立的历史规则扩展，不由维护
  屏障或版本升级自动授权。

## 验证记录

### 实现范围与最小入侵

- 解析版本为 2，受理时冻结，在生成、分批写入、待确认发布和最终确认边界校验。旧 pending 确认
  被拒绝、标记 invalid 并释放占位；旧 confirmed 幂等读取，缺失优惠保持缺失，不按当前公式补算。
- SQLite 工具复用维护控制表，显式 begin/apply/end；apply 必须通过当前代际事务锁。begin 持久
  关闭确认，end 必须提供匹配代际及核验依据，操作审计与控制状态同事务，失败不自动解除维护。
- 退款引用仅在一次读取内按用户/Key 复用，读取前后与发布前验证来源修订和维护代际。缓存空间
  上限约 20,000 个引用/Key 条目，超出部分完整扫描；既有 500 行分页、取消和单批超时继续生效。
- 代码均在本地账单扩展及既有专用修复工具中。未改原生 Relay、Provider、资金计算或扣退款入口，
  未改数据库余额/历史业务数据，也未执行生产修复或部署。无新增表或列。

### 已运行验证

- SQLite：model/service/controller/补修工具定向回归通过；覆盖旧 queued/pending、新草稿、旧确认
  版不变、维护期间禁止重新开启确认、过期代际拒绝、失败持久保护、原有补修幂等和资金不变。
- 退款测试在两个历史分页和两个消费批次之间验证只发生一次完整历史扫描，并验证跨月重复、其它
  Key 不干扰、本 Key 新退款失效、发布前复验、取消、缓存容量不足不丢证据及无保留行时的失败屏障。
- MySQL 8.0、PostgreSQL 16：使用本机回环、无业务挂载的临时容器，每项测试创建独立数据库；
  定向验证解析升级、维护/修订、退款复用和索引通过；最终版本再次回归通过，临时容器已清理。
- `go test ./model ./service ./controller ./cmd/repair-task-billing-logs -count=1` 完整通过。
- `go vet ./model ./service ./controller ./cmd/repair-task-billing-logs`、`task docs:check`、
  `task ai:check`、`git diff --check` 通过。没有前端、公开 API 或 relaykit 改动。

### 部署验收边界

测试不代表生产已发布。目标部署先备份并验证迁移、关闭确认、升级全部实例，再使用生产一致性副本
复演；核对旧确认版本/文件不变、旧草稿被拒绝、修复前后逐笔差额、资金余额和导出一致性后恢复确认。
本轮未实测 MySQL 5.7.8、PostgreSQL 9.6 最低版本和生产峰值负载；分库正确性保留完整读取，但
没有跨批计数复用的性能收益。SQLite 补修工具不扩展为未经验证的跨数据库修复器。
