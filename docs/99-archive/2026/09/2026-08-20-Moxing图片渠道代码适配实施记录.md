# Moxing 图片协议并入统一图片中转实施记录

## 问题与目标

Moxing 图片最初以独立 `ChannelTypeMoxingImage=63` 接入，而 FunCloud 使用名称泛化的
`ChannelTypeAsyncImage=62`。两个类型北向都复用原生 `/v1/images/generations`、普通 Ability、管理员
`model_mapping` 和同步图片计费，只是南向协议不同。管理端并列展示两个相近渠道类型会让管理员误以为
它们拥有不同北向能力，并且不利于后续增加其它图片中转协议。

本次目标是把管理身份收敛为一个「图片中转」渠道，同时保留 FunCloud 和 Moxing 各自已验证的请求、轮询、
响应和错误合同。协议必须由管理员显式选择，不能从模型名、mapping、价格、Base URL 或响应推断；协议
选择也不能生成、补齐或改写管理员 `model_mapping`。

## 当前实际情况

代码已形成以下候选事实：

- 管理面和运行时只登记 `ChannelTypeAsyncImage=62` / `APITypeAsyncImage`，展示名为「图片中转」；
- `ChannelOtherSettings.image_upstream_protocol` 是必填代码协议，当前只允许：
  - `funcloud_aigc_v2`；
  - `moxing_images_v1`；
- `relay/channel/imagerelay` 只按显式协议委派现有 `asyncimage` 或 `moxingimage` adaptor；两套南向 DTO、
  路径、轮询和响应解析未合并；
- 每条渠道只能选择一个协议，但所选协议下可以配置多个客户模型；同时使用两个 Provider 时必须创建两条
  同为「图片中转」类型的渠道；
- 保存校验对当前 Models 逐项执行 NEWAPI 原生 `ResolveModelMapping`，再校验最终 Provider profile；
  Models 不必等于 mapping 键集合，mapping 可多跳并包含无关管理员条目，客户模型也可直接使用 Provider
  模型名；
- 两种协议都关闭 body pass-through，并禁止 Param Override 和 Advanced Custom route；strict image 热路径会在
  发送前再次拒绝 Param Override，防止旧配置或直接数据库修改绕过 adaptor profile；
- 管理端协议下拉框会在当前地址为空或仍为已知默认地址时切换 Provider 默认 Base URL，但不修改 Models、
  mapping 或价格；
- 管理端渠道测试先解析管理员 mapping，再按协议和最终 Provider profile 选择测试尺寸；
- 旧类型 63 由启动迁移原子改为类型 62 并写入 `moxing_images_v1`；旧类型 62 缺少协议时写入
  `funcloud_aigc_v2`。空 Base URL 按旧语义物化，settings 的其它 JSON 字段无损保留，存在 Param Override
  时拒绝迁移；迁移以 Option marker 幂等执行；
- master 负责执行迁移，所有节点在启动时只读验证 marker、旧类型、协议、Base URL 和 Param Override；发布
  必须停止旧版本后再迁移，禁止新旧版本滚动混跑；
- 迁移后运行时、APIType、前端和 endpoint 映射都不再识别类型 63。`ChannelTypeDummy=63` 与
  `ChannelBaseURLs[63]` 空槽只保留计数和安全索引，不是兼容类型。

Moxing 当前仍只登记：

| Provider 模型 | 当前代码合同 |
| --- | --- |
| `doubao-seedream-5-0-260128` | Lite、固定 `2K`、`n=1`、单 URL |
| `doubao-seedream-5-0-pro-260628` | Pro、固定 `2K`、`n=1`、单 URL |

FunCloud 继续登记 `nano-banana-2-lite`、`nano-banana-2`、`seedream-5.0-lite` 和
`seedream-5.0-pro`。两个协议共享北向严格图片合同和同步计费链，但不共享南向请求或状态语义。

真实 Provider、供应商账单、超时/取消后的 Provider exposure 和生产灰度仍未完成，因此渠道配置应保持
禁用；代码候选不构成生产发布声明。

## 优化方案

### 1. 稳定身份

```text
ChannelTypeAsyncImage=62
  -> APITypeAsyncImage
  -> image_upstream_protocol
     -> funcloud_aigc_v2 -> FunCloud adaptor
     -> moxing_images_v1 -> Moxing adaptor
```

禁止增加以下兼容路径：

- 根据客户模型或 Provider 模型猜协议；
- 根据 Base URL、价格或 Key 格式猜协议；
- 发现所选协议不支持后尝试另一个 adaptor；
- 保留类型 63 的运行时 alias、双读或 fallback；
- 由代码生成固定客户别名或 `model_mapping`。

### 2. 保存和迁移失败关闭

渠道保存必须具备显式协议、显式 Base URL、至少一个客户模型，并确认每个客户模型最终落到所选协议的
代码 profile。切换协议后若现有 mapping 不兼容，保存失败并由管理员修正，不自动重写。

启动迁移遇到非法 settings、类型 63 已配置冲突协议或行更新数量异常时必须整体回滚并阻止新版本启动。
迁移只转换渠道身份和补齐协议/Base URL，不修改客户模型、mapping、价格、Key、分组或既有 Ability。

### 3. 测试边界

代码回归至少覆盖：

1. dispatch 只按显式协议产生不同南向 URL，协议缺失时失败；
2. 单一 ChannelType/APIType 和图片 endpoint 注册，类型 63 不再可用；
3. 管理员多模型、多跳 mapping、额外 mapping 条目和直接 Provider 模型均保持 NEWAPI 原生语义；
4. 跨协议 Provider 模型、透传、Param Override、Advanced Custom 和空 Base URL保存失败；
5. 数据库迁移为旧 62/63 写入正确协议和默认 Base URL，无损保留未知 settings，拒绝 Param Override，
   重复执行不重复修改，冲突时回滚；
6. marker 完成后重新出现类型 63 时，所有新节点启动检查都失败；
7. 管理端只显示一个图片中转类型，协议切换更新已知默认 Base URL、保留自定义 URL 和 mapping，且不提供
   模型抓取；
8. 管理端测试按最终 Provider profile 选择尺寸，不依赖客户别名。
