# 启动异常与证据密钥持久化问题分析及修复方案

> 当前启动行为（2026-09-19）：按用户明确要求，`start.sh` 完整校验参数后停止配置端口的原监听进程，再启动后端和前端；TERM 等待后仍占用则 KILL。本文 2026-09-17 的“不终止占用者”实现与测试记录已经被这一要求替代，仅保留为过程记录。当前操作见[本地搭建](../30-engineering/本地搭建.md)，回归结果见[修复记录](2026-09-19-账单启动与邮件评审修复记录.md)。

## 问题与目标

用户在本地执行 `./start.sh` 时先遇到账单代码编译失败，第二次启动成功后出现每 15 秒一次的
用量补查慢查询、前端代理错误，以及证据临时密钥、Cookie、可信代理配置告警。

本记录汇总本次会话已经核实的问题、尚未证实的风险、解决方案和验收条件。用户明确要求：
**所有修复不得破坏当前业务；如需密钥，可以在 Docker Compose 中配置。**

本文前半部分保留首次分析时的证据快照；末尾记录本次代码实施和验证范围。
本次代码修复不切换现用密钥、不修改业务数据或现存证据、不重启运行服务。不能把本地回归通过
解释为存量密钥已迁移、整条轮询链性能已验收或生产已发布。

相关记录：[异步任务轮询闸门慢查询优化方案](2026-09-17-异步任务轮询闸门慢查询优化方案.md)。

## 当前实际情况

### 环境、方法与验证边界

- 证据来自用户提供的 2026-09-17 启动日志、当前工作区代码、本地日志和只读 SQLite 查询。
- 本地运行方式为 `./start.sh`，不是 Docker Compose；Compose 配置不会自动作用于这个宿主机进程。
- 使用项目实际 Go SQLite 3.50.4 驱动复现慢查询；另在仅含必要非私有字段的内存实验库验证统计信息
  和候选索引。未对运行库执行 ANALYZE、建索引或数据更新。
- 仅请求本机 `/api/status` 验证连通性，不读取输出接口正文、不触发 Provider 调用。
- Provider：无；没有真实生成、账单调整、退款、重发或生产密钥轮换验证。
- 工作区存在其他正在开发的代码；不能将所有当前改动归因于此前一行轮询查询优化。

### 问题清单与结论

| 编号 | 问题 | 已确认结论 | 风险与状态 |
| --- | --- | --- | --- |
| K1 | 证据默认依赖临时派生密钥 | 未配置三类相关环境变量时，证据密钥来自进程随机主密钥 | 高优先级：跨重启历史正文可读性存在机制缺陷；尚未逐项验证现存对象 |
| K2 | 主密钥随机变化影响其他业务 | 登录签名、产物访问签名、部分图片计费快照也使用这些主密钥 | 高优先级：关联业务路径已确认，具体存量受影响任务尚未盘点 |
| Q1 | 用量补查存在性查询慢 | SQLite 选 status 索引，当前需要检查大量 SUCCESS 行才能返回空 | 已复现，约 320ms；覆盖索引迁移已实现，运行库尚未部署 |
| E1 | 解密失败在证据详情中表现不清 | 正文预览失败被跳过，has_body/complete 不反映当前可读性 | 已增加当前正文读取状态，历史采集事实保持不变 |
| P1 | 前端代理错误缺少详情 | Rsbuild 日志适配器丢弃格式化参数 | 已增加脱敏代理错误日志；六次历史请求的错误码不能还原 |
| S1 | 启动就绪及进程清理不足 | 两端并行启动、只检测端口；日志显示前次退出后端口仍有残留 | 已采用健康检查和进程组清理；隔离测试验证父进程退出后的子进程清理 |
| C1 | `undefined: v` 编译失败 | 当前对应代码不再引用 v，`go build ./service` 已通过 | 历史错误当前不可复现，不应重复修补已经变化的代码 |
| D1 | Cookie/Origin 与代理信任告警 | 当前启用本地 HTTP 兼容模式及默认私网代理信任 | 正式部署需按 HTTPS 和实际代理拓扑处理，不直接套到本地 HTTP |

### K1：密钥从哪里来

用户未配置 `TASK_REQUEST_EVIDENCE_ENCRYPTION_KEY`。评审时项目根目录没有 `.env`；启动告警
对应的代码分支证明，当时证据初始化没有取得显式证据密钥，`CRYPTO_SECRET` 和 `SESSION_SECRET`
环境变量也均为空。该结论针对日志对应的本机进程，不推断其他部署环境的配置。

初始化链路：

1. [main.go](../../main.go) 的 `InitResources()` 先尝试加载根 `.env`，再调用 `common.InitEnv()`。
2. [common/constants.go](../../common/constants.go) 的包变量以 `uuid.New().String()` 初始化
   `SessionSecret` 和 `CryptoSecret`。
3. [common/init.go](../../common/init.go) 在未配置 `SESSION_SECRET` 时保留随机 SessionSecret；
   未配置 `CRYPTO_SECRET` 时，将 CryptoSecret 赋为 SessionSecret，覆盖它最初的随机初值。
4. [证据配置](../../setting/system_setting/task_request_evidence.go) 默认开启取证。若没有专用密钥，
   按下面的固定算法派生实际证据密钥：

   ```text
   evidenceKeyHex = hex(SHA256("task-request-evidence:" + common.CryptoSecret))
   ```

5. 结果存入进程内配置，使用 `sync.Once` 初始化；[证据存储](../../service/task_request_evidence_store.go)
   将其解码为 32 字节密钥并初始化 AES-GCM。当前实现没有把此密钥持久保存到数据库、配置文件或对象中。

这不是用户曾经手工配置了某个未知 KEY，也不是程序自动写入了同名环境变量；它是运行时的内存派生值。
已有实现可追溯至提交 `0a6a7d867`，不属于本次轮询 SQL 优化新增逻辑。

调度器检查[证据保留期处理器](../../controller/system_task_evidence_cleanup.go)是否启用时，就会调用
`GetTaskRequestEvidenceConfig()`。即使保留期为 0、没有清理任务，也会初始化配置，所以启动时
尚无新的生成请求就能出现该告警。

### K1/E1：什么还能查询，什么可能读不出来

下表只描述证据专用密钥变化的直接影响，不等于 K2 主密钥变化的全部影响。

| 查询对象 | 证据密钥变化后的行为 |
| --- | --- |
| 普通任务的数据库状态、模型、时间等字段 | 不依赖证据正文解密，记录不会因此消失 |
| 已记录消费日志、账单、余额、金额 | 不因证据解密失败而被改写或删除；不代表所有未结算任务都能继续结算 |
| 证据索引与事件元数据 | 请求关联、阶段、HTTP 状态、时间、字节数、已存摘要等仍可读取 |
| 已采集的客户请求、南向请求、上游响应/错误、轮询及客户响应正文 | 对应旧密钥遗失时无法解密；实际范围取决于哪些路径曾采集正文 |
| 复用该存储的图片错误证据正文 | 同样受影响 |
| Root 下载旧证据对象 | 解密错误会被对象接口映射为 HTTP 410、正文不可用 |

[预览读取](../../service/task_request_evidence_helpers.go)遇到解密或完整性失败直接跳过；
[详情接口](../../controller/task_request_evidence_query.go)仍可返回成功及空 preview。
`has_body` 只表示存在对象引用，`complete` 表示采集当时完整，并不证明当前能读。
[前端证据展示](../../web/src/features/usage-logs/components/task-evidence.tsx)仅在 has_body=false 时
显示正文不可用，因此可能出现“显示完整、有下载按钮、预览却为空、下载报 410”。

这会影响参数争议、失败原因定位、供应商追责和历史审计，不能作为无关紧要的日志告警处理。

只读盘点时有 2796 条证据索引、166962 条事件，其中 163359 条带对象引用；默认本地目录内发现
1121 个文件。这些是不同口径的数量，未完成配置目录、保留期、其他部署副本和引用去重核对，
**不能直接相减认定文件丢失，也不能证明这些文件的密钥归属或可读性**。

### K2：共同主密钥的额外业务影响

| 使用方 | 代码依据 | 可能影响 |
| --- | --- | --- |
| 登录访问令牌与认证相关签名 | [service/auth_token.go](../../service/auth_token.go)、[model/auth_flow.go](../../model/auth_flow.go) | SessionSecret 改变后，既有签名可能验证失败，需要重新认证 |
| 任务产物访问链接 | [service/task_artifact_access.go](../../service/task_artifact_access.go) | CryptoSecret 改变后，已签发链接可能失效；不表示媒体文件被删除 |
| 部分异步图片表达式计费快照 | [service/image_task_billing.go](../../service/image_task_billing.go)、[service/image_native_billing.go](../../service/image_native_billing.go)、[common/secret_envelope.go](../../common/secret_envelope.go) | 跨重启且仍需恢复快照的任务可能解密失败，无法得到合法结算目标 |

图片结算代码在快照求值失败时记录告警并返回，不以捏造的目标金额结算。因此应核对未结算任务与
持款状态，不能把问题描述成“只是重新登录”，也不能未经核实声称已经错扣或已影响全部图片任务。
只固定证据专用 KEY 不会解决这些主密钥用途的问题。

### Q1：用量补查慢查询

实际查询位于 [model/task_usage_recovery.go](../../model/task_usage_recovery.go)：

```sql
SELECT id FROM tasks
WHERE billing_state = 'awaiting_usage' AND status = 'SUCCESS'
  AND (usage_review_at IS NULL OR usage_review_at = 0)
  AND (usage_check_next_at IS NULL OR usage_check_next_at <= :now)
LIMIT 1;
```

评审时任务总数 3538，SUCCESS 为 3313，awaiting_usage 为 0；未审核与已到期/未设置时间的条件
均覆盖 3538 行。优化器选择 `idx_tasks_status`，需要检查大量成功任务，才能确认没有待补查工作。
项目实际驱动只读复现约 320ms；诊断性指定现有 `idx_tasks_billing_state` 后同样返回空，耗时不足 1ms。
指定索引仅用于验证根因，不是拟提交到生产的 SQLite 专属强制分支。

运行库没有 sqlite_stat1/stat4。仅复制必要字段与索引的内存实验库中，ANALYZE 后查询改选
billing_state 索引；候选复合索引 `(billing_state, status, usage_review_at, usage_check_next_at)`
则可提供覆盖索引路径。这些实验不代表已验证所有数据分布或三库迁移。

每 15 秒检查是总调度闸门现有职责。成功但缺少用量的任务仍需补查，不能删除此检查、降低频率、
把 NULL 改为排除、提前退出或缓存“无工作”来消除日志。rows=0 只是结果数量，不是扫描数量。

此前已优化的 `HasUnfinishedSyncTasks()` 仍使用进度范围索引，本次慢的是总闸门的另一条查询。
“其他查询有索引，所以没有性能问题”的早期判断不足，修正为整链按实际数据验证。

其余闸门本次 EXPLAIN 结果：

| 探测 | 当前本地执行计划摘要 | 不能由此推导的结论 |
| --- | --- | --- |
| 未完成任务 | progress 两段索引范围 | 所有非完成候选增长都无成本 |
| 到期 create attempt | status 索引 | 所有历史 attempt 分布下都足够快 |
| 失败欠退款 | status 索引 | FAILURE 很多时仍只读一行 |
| 终态待计费 | billing_state 索引，并有排序临时结构 | Go 层过滤、重试时间与分页完全无成本 |
| 待交付日志 | delivered_at/next_retry_at 复合索引 | 所有积压场景已经性能验收 |

### C1/P1/S1：编译与前端代理

- 用户第一次日志出现 `service/billing_statement_version_artifact.go:544:159: undefined: v`。
  当前[对应函数](../../service/billing_statement_version_artifact.go)已不再引用 v，`go build ./service`
  通过。只能认定历史源码曾编译失败，不能确定修改者或仅凭历史行号修改当前代码。
- `Terminated: 15` 与启动失败后的 SIGTERM 清理一致，不代表第二个 Go panic。
- 只读探测 `127.0.0.1:3501`、`localhost:3501`、`[::1]:3501` 及经 `3500` 代理的
  `/api/status` 均返回 200；这是状态接口的当前结果，不代表所有业务接口已验收。
- 本机 Rsbuild 2.1.6 的代理适配器 `error: (msg) => ...` 只接收首个参数，而其代理库传入
  `logger.error(format, request, target, errorCode, ...)`，导致 `%s` 原样输出且错误详情丢失。
  不能从现有六条日志确定 ECONNREFUSED、超时或其他原因。
- 前端日志修改时间早于后端就绪，结合 [start.sh](../../start.sh)两端并行启动，启动窗口请求失败
  是有依据的解释，但不是已证实的每次请求根因。
- 脚本只检查端口监听；用户第二次启动仍发现前端端口残留。父/子进程退出竞态和端口所有权需要
  专门复现，不能据此直接扩大 kill 范围。

### D1：其余启动信息

- `SESSION_COOKIE_SECURE=false` 使本地 HTTP 可用，同时关闭 refresh/logout 的 Origin 校验；
  直接在 HTTP 环境设为 true 可能导致浏览器不发送 Cookie，必须配合实际 HTTPS 部署验证。
- TRUSTED_PROXIES 未设置时采用 loopback、私网及 IPv6 ULA 的默认信任范围。正式部署需要核对
  反向代理与客户端 IP 获取路径；不能无条件改为 none，破坏既有代理识别。
- `SQL_DSN not set`、Redis 未启用、0 个自定义 OAuth 等是当前配置状态，不是本次启动失败证据。
- ephemeral evidence key 告警必须按 K1/K2 处理，不能通过调高日志阈值或删日志隐藏。

## 优化方案

### 1. 密钥：优先使用部署配置，避免新增自动生成或自动轮换机制

用户已确认可以在 Docker Compose 中设置密钥。现有代码已支持环境变量注入，**新环境稳定配置
不需要修改加密算法，也不需要新增自动落盘密钥、后台轮换、业务 fallback 或第二套解密合同**。

| 配置项 | 用途 | 稳定性要求 |
| --- | --- | --- |
| `SESSION_SECRET` | 登录/认证签名；CRYPTO_SECRET 缺失时也是其来源 | 同一部署持续保持有效值，多实例一致 |
| `CRYPTO_SECRET` | 产物链接、部分加密计费快照等；证据未显式配置时从它派生 | 保持现有有效字节，不能为消告警随意替换 |
| `TASK_REQUEST_EVIDENCE_ENCRYPTION_KEY` | 证据专用密钥，显式设置后优先于主密钥派生 | 64 个十六进制字符，解码为 32 字节；长期保存、备份，多实例一致 |

**用户最终偏好为减少运维配置、不使用 env 文件，并保持当前 Cookie 配置。**
全新部署只固定 `SESSION_SECRET` 即可：未显式配置的 CRYPTO_SECRET 继承它，证据 KEY 再从
CryptoSecret 派生。三个变量不是业务启动必填项；不新增强制校验、不自动生成或轮换密钥。

最小 Compose 示例（占位符必须替换为确认可使用的固定值，不是可直接上线的真实密钥）：

```yaml
services:
  new-api:
    environment:
      - SESSION_SECRET=REPLACE_WITH_APPROVED_STABLE_SECRET
```

此前按用户要求生成的三项独立候选值已直接写入本地 Compose 文件，没有启动或重建服务。
本次不删除或改写这些值，因为尚未确认它们是否已经被用户用于生产。若三个独立值已投入使用，
删除 CRYPTO_SECRET 或证据 KEY 会切换到不同的派生值；必须保留原有效字节，不能套用最小示例。
真实值不进入本文或日志，含密钥的本地 Compose 文件不得提交到版本库。

宿主机 `./start.sh` 的进程另需通过它的启动环境或根 `.env` 提供配置；只改 Compose 不会修复
当前正在运行的宿主进程。当前配置和存储均为进程内一次性初始化，修改文件不会自动热切换现用密钥。

### 2. 存量部署：先保全，再配置，不直接重启换钥

按实际密钥来源分别处理：

| 情况 | 安全处理路径 |
| --- | --- |
| 原本已有稳定专用 KEY | 保持同一值注入，不换值，核对容器重建后的读取 |
| 原本从稳定 CRYPTO_SECRET/SESSION_SECRET 派生 | 保持原来源；若改显式专用 KEY，必须是原派生结果的同一字节值，而不是新随机值 |
| 当前仍运行在临时密钥下 | 先评估受控保全现用密钥及未结算任务的可行方式；现有代码没有常规导出现用密钥入口，不能从新进程重算旧随机值，不通过日志打印或通用诊断接口暴露密钥 |
| 旧进程已退出且旧密钥没有保全 | 新 KEY 无法恢复旧密文；盘点受影响对象与任务，明确不可恢复范围，保留原数据，不能假装迁移完成 |

需要保护的不止证据 KEY，还包括仍有消费者的 SessionSecret/CryptoSecret。不得为了配置证据 KEY
顺手更换主密钥；即使仅换专用 KEY 也会改变历史证据的解密条件。

实施前对数据库、对象目录与现有受保护密钥材料建立可恢复的一致备份，明确存量任务、产物链接、
证据的依赖。若临时密钥无法安全保全，不承诺无损切换；不能静默重启、丢弃旧记录或自动退款。
新请求可读、重启后可读、旧对象可读和未结算任务可继续推进必须分别验收。

### 3. 保持对象路径与持久化挂载

仓库 [Dockerfile](../../Dockerfile) 的运行目录是 `/data`，[docker-compose.yml](../../docker-compose.yml)
挂载 `./data:/data`，开发 Compose 挂载命名卷到 `/data`。证据默认相对目录是
`data/task-request-evidence`：在该容器默认运行目录下解析为 `/data/data/task-request-evidence`，

### 7. Cookie 与可信代理

保持本地 HTTP 的可用性。正式 HTTPS 部署单独核对 Secure Cookie、refresh/logout Origin、
可信代理、真实客户端 IP 和登录流程；实际代理确定后再配置，不能通过关闭保护或统一设置 none
掩盖告警。此项与密钥持久化分开实施和回归。用户已决定本次继续不配置 Cookie 两项，本次保持现状。

用户补充的生产拓扑为“浏览器 HTTPS → 反向代理 → HTTP 服务”。此拓扑适合设置
`SESSION_COOKIE_SECURE=true`：Secure 属性约束浏览器访问，不要求代理到服务的内部连接也使用
HTTPS。当前应用不会因为外部有 HTTPS 代理就自动开启此配置。

只有显式开启 Secure 时，才必须同时设置 `SESSION_COOKIE_TRUSTED_URL`，否则 `InitSessionCookieSettings()` 会返回错误并
阻止启动。该值填写实际浏览器前端的 HTTPS Origin，例如 `https://console.example.com`，多个
Origin 用逗号分隔，不包含业务路径或通配符；它不是内部服务地址，也不是代理 IP 白名单。
代理应保留浏览器 Origin/Referer，启用后验证登录、刷新和退出。当前 OriginGuard 不通过
X-Forwarded-Proto 推断外部来源，不能用设置该请求头代替可信 Origin 配置。

`TRUSTED_PROXIES` 独立控制代理信任，需按实际代理地址设置，不是启用 Secure Cookie 的替代项。
依据：[Cookie 配置校验](../../common/session_cookie.go)、
[OriginGuard](../../middleware/auth_origin.go)、
[MDN Secure Cookie 说明](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie#secure)。
