# 历史渠道测试未纳入金额原因核查

## 问题与目标

渠道测试实际调用上游，应计入本站上游原价及渠道折后核算金额。用户反馈 Google 渠道 103 有
619 条测试未计金额，其中 414 条提示缓存写入明细缺失。进一步检查全月记录，修复按旧格式整体
排除测试、把不参与计价的字段缺省认作金额缺口，以及新测试未使用完整计价规则的问题。

本次由“分析周期切换与逐日明细”任务统一完成；“分析渠道测试计费归属”任务已停止共享修改并交接。
不修改原始日志、客户钱包或历史资金，不按当前价格和当前渠道配置回填旧数据。

### Google 渠道 103

同一批 5,386 条账单记录含 627 条测试。用户页面旧结果为 8 条已计价、619 条待核算；
本次恢复后 627 条测试全部计入金额，待核算为 0，测试缓存写入缺项为 0。

其中 414 条是旧 Gemini 原生转换路径。日志冻结的转换链可证明使用 Google Gemini 计量，
该路径把缓存命中映射为缓存读取，没有独立的请求缓存写入计量。读取端曾错误地要求它提供
缓存写入字段。修复按发生时的转换事实解释此维度为本请求计价零贡献，不涉及独立缓存存储费用。
显式字段、未上报标记及损坏数据优先，不能覆盖为零。其余历史表达式等记录按同一恢复规则处理。

### 根因与已实施修复

1. 旧代码按是否存在新版计价记录整体排除历史测试。现在优先使用新版折前金额，其次验证历史
   固定价、冻结表达式成功结果或用量与倍率；缺版本不再等同缺金额。
2. 历史表达式只要求实际使用的输入。仅使用输入／输出时不强制要求缓存；Claude 仅用上下文
   总量时不强制要求缓存 TTL 拆分；使用具体 TTL 价格时仍要求对应证据。
3. 冻结 Gemini 路径和输入计费的 embedding 测试可按其实际计量合同解释缺省写入；普通
   OpenAI 兼容／Claude 旧测试不能据此推断零，模型名和当前配置不参与判断。
4. 旧普通倍率先校验原简化报价，再按冻结的缓存折扣和正式取整核算；明细与导出保留原金额、
   复算金额和依据，不反除已舍入的客户折后费用。
5. 新测试复用原生计价和用量归一化，保存折前金额、模式、版本、状态及实际参与定价的字段；
   明确估算、附加费、饱和与公式错误不会写成可靠实测金额。
6. 上游汇总、渠道／模型、逐笔明细、CSV 和日／周上游统计使用同一金额入口及原因。
   客户账单继续排除渠道测试，测试费用不会变成客户钱包扣款。

## 渠道测试没有缓存时的请求复核

继续检查请求构造、adapter 发送边界、返回用量与日志：默认 Chat、Responses、Claude 和 Gemini
文本测试均使用单条 `hi`，模板没有主动设置缓存控制字段；embedding 使用 `hello world`。
实际发送前仍经过协议转换及渠道参数覆盖，因此模板不等同每次历史请求最终形状。

读取时现有 22,769 条测试中，缓存读取正数 2,061 条、零 20,708 条；原始缓存写入字段正数
76 条、显式零 6,496 条、未保存 16,197 条。这是原始字段统计，不等于金额待核算数；
冻结协议或表达式结果已能恢复其中部分缺省记录。一条实际计量样本为输入 3、输出 14、
缓存读取 0、缓存写入 1,622，表明“读取为零”不能证明“写入为零”，测试身份本身也不排除缓存。

旧版 `buildTestLogOther` 只向通用 writer 传入缓存读取值，未传入缓存写入量；后来的
`appendChannelTestCacheUsage` 才完整保存写入总量和 TTL。因此历史缺字段存在明确的本地
记录遗漏，不能表述为上游实际没有返回。按渠道及上游请求 ID 核对现存运行日志，未找到
能与该批待核算倍率测试唯一关联的原始响应，无法逐笔确认遗漏值。

本地 HTTP 集成测试已在真正发送边界验证模板为单条 `hi` 且没有主动缓存配置，随后分别返回：

- 完整用量且缓存读写明确为零：正常计价并保存零写入。
- 完整输入／输出用量，省略 OpenAI 兼容可选缓存明细：按原生计价语义正常计算，不要求缓存存在。
- 完整用量且缓存命中为正：应用缓存单价。
- 整个 usage 缺失：保留估算状态，不冒充实际结算。

新增上述回归及已有缓存写入留存回归通过，未发起真实上游调用。当前无缓存调用正常计价；
历史漏存写入字段与当次正常省略可选字段不能合并为同一种情况。

## 估算测试与发送事实的费用边界

对 245 条本地估算测试进一步只读核对：全部属于渠道 101、模型 `gemini-3-flash-preview`，
时间为 2026-09-02 至 09-08，保存的网关入口为 `/v1/chat/completions`。输入合计 0、
输出合计 8,820、原日志 quota 合计 13,230，均有 `admin_info.local_count_tokens=true`。
不能将渠道 102/105 混入这批计数，也不能据网关入口推断南向不兼容；Gemini adapter 会执行协议转换。
模型并非图片生成模型，图片输入能力也不等于图片生成能力。缺失可信 usage 不证明调用免费。

按已确认规则实现：

1. 本地校验在调用 adapter 前失败：新失败事件保留 `upstream_cost_status=not_sent`，不创建消费金额。
2. 已进入 adapter 调用但没有可靠金额：保留 `pending`。连接失败、上游拒绝、响应损坏及仅有本地
   估算，都不能据此确认为零成本。调用 adapter 是保守边界，不宣称字节已经发送；原 transport
   的 attempted/response_received 事实继续单独保存。
3. 成功测试具有完整冻结计价依据：标为 `priced`，金额纳入原价和渠道折后核算；这仍是本站定价
   口径，不代表供应商账单已核对。按次固定价不依赖 Token 明细时，仍按其有效计价合同处理。
4. 已知媒体／不支持生成检查沿用现有自动检查边界，只做已支持的只读检查或本地配置诊断；
   不回退为聊天生成探针，不因某次 usage 缺失停用渠道，也不按模型名称推断历史零成本。

新失败事件及自动检查详情保存受控费用状态，未知旧事件不补写。失败事件不混入消费账单，不伪造
一条零价账单；这不是新增供应商应付账本。手工与自动失败事件共用状态读取和事件白名单。
原生 `controller/channel-test.go` 仅增加本地初始化、调用前标记、成功定价标记和退出时保留上下文；
证据读取隔离在本地 service 文件，后续合并上游时只需核对这些接线与原有定价调用。

修正历史估算逐笔投影：即使没有新版 `test_pricing`，也显示估算状态。页面和 CSV 明确解释
“费用待确认，暂不计入已核算金额；不代表费用为零”，现有“查看记录”继续定位这 245 条。
不改写其历史金额，不把估算值升级为实测值，不从待核对记录中删除。

验证覆盖本地 HTTP 实际发送次数、发送前价格校验失败、上游 400、响应无法解析、完整用量、
缺少 usage、客户钱包及渠道累计不变、错误事件白名单、历史估算状态及中英文导出解释。


本轮相关后端回归通过，前端 29 项回归、类型检查、变更文件 lint、后端构建及文档检查通过。
本地服务已加载修复；浏览器核对 245 条估算记录的入口与逐笔状态均显示费用待确认、未计入
已核算金额，金额仍为待核算。验收时总记录因新调用增至 91,514 条，待核算测试仍为 8,193 条；
