# Azure 批处理与多合同渠道定价实施方案

## 1. 问题与目标

本文整理 [20260908 需求](<../10-product/20260908 需求.md>) 及后续会话的最终结论，覆盖三个独立交付项：

1. 接入 Azure Batch 的真实异步作业、文件、任务跟踪和计费。
2. 将用户级单合同调整为用户可有多份合同、每个 API Key 至多绑定一份合同，以相同客户模型名选择不同渠道和折扣。
3. 修复合同模型阶梯价格详情空白，展示所选合同规则的有效价格。

本文是待实施方案，不是当前架构事实、已实现功能或生产发布声明。本次仅进行代码核查、官方资料查询和方案编写，没有实现业务代码，也没有完成真实 Azure、账单、三数据库或生产灰度验证。

会话中用户明确确认的结论以第 1.1 节为准；后续章节标注为“建议”的结构、字段和接线方式属于实施设计，不应误读为已经存在的代码。代码命名可以在实现时调整，业务边界不得自行改变。

### 1.1 已确认决策

| 编号 | 已确认内容 |
| --- | --- |
| B1 | 需求 1 只考虑 AI 原厂或云厂商真实支持的能力，首先核实接口支持和计价支持；首期仅接入 Azure Batch |
| B2 | 使用 Azure Batch 专用渠道类型；首期支持纯文本 Chat Completions 批处理 |
| B3 | 客户使用本站地址、本站 Key，沿用官方“上传 JSONL → 创建作业 → 查询 → 下载结果”的流程，支持取消 |
| B4 | 每批最多 **10,000 条请求**、输入文件最多 **20 MiB（20,971,520 字节）**，两项限制同时满足；10,000 条取代早先讨论的 1,000 条 |
| B5 | 每条请求必须设置适用于所选模型的输出上限；提交时按输入估算和输出上限冻结预计费用 |
| B6 | Batch 售价按模型配置，复用现有计费体系，不固定为普通价格的五折；作业创建时冻结计价规则 |
| B7 | 完成后按实际用量结算并释放差额；取消后仍结算已产生的费用；支持部分成功与部分失败 |
| B8 | 复用现有 OSS；文件保留、过期和垃圾回收由 infra 负责，应用层不增加自动清理或过期调度 |
| B9 | 暂不增加每客户活动作业数量限制，不增加平台业务排队机制；保留原有鉴权、余额、Key 额度、系统保护及上游限制 |
| B10 | 对齐现有 Task、创建尝试、SystemTask、日志和账单机制；分别跟踪执行、交付、结算，支持重启恢复和幂等处理 |
| C1 | 管理员为一个客户预先配置多份合同；一份合同可包含多个模型，每个 Key 至多绑定一份合同 |
| C2 | 同一客户模型可以出现在不同合同中，分别指定具体渠道及折扣；渠道可以属于同一路由组 |
| C3 | 同一合同内同一客户模型保持唯一，由合同规则明确渠道和折扣；不采用同一合同重复模型再运行时猜选的方案 |
| C4 | 客户创建 Key 时以友好方式选择合同，展示合同名称、模型及价格，隐藏内部渠道、上游身份和路由组细节 |
| C5 | 有合同的客户也允许创建不绑定合同的 Key；无合同客户继续原有创建与调用逻辑，不增加合同选择负担 |
| C6 | 管理员不为新建 Key 指定自动绑定的默认合同；选择由客户完成 |
| C7 | Key 绑定启用合同后使用合同授权、渠道和折扣；未绑定或合同停用时恢复该 Key 原有逻辑及原有组，不强制改为 Default |
| C8 | 原有组设置保留；合同折扣继续作用于原生有效组倍率后的模型费用，合同不是固定价格承诺 |
| C9 | 存量用户合同迁移为一份合同，并让该用户存量 Key 绑定它，尽量保持原有行为；这不等于新 Key 自动绑定默认合同 |
| P1 | 修复合同用户展开阶梯价格详情空白的问题，显示当前所选合同规则对应的有效阶梯价格 |

文件本地校验失败时整批拒绝并指出行号、账单按 Batch 汇总并提供逐条明细，是会话收尾采用的实施默认值；它们不增加新的客户业务审批流程。

### 1.2 首期不包含的范围

- OpenAI 原厂、Claude、Gemini、Bedrock 等其他提供方的 Batch 接入，以及 Fast、Flex、Priority 等其他档位。
- 将普通同步调用改名为 Batch 后打折，或由价格、模型名称后缀推断 Batch 身份。
- Responses、图片、音频、视频或 Embeddings 的 Batch 扩展；现有普通接口继续其原有行为。
- 平台业务排队、自动拆批、自动重提失败行、跨渠道补跑、按客户增加新的活动作业配额。
- OSS 定时清理、文件迁移、多套存储配置和为本需求建设通用文件网盘。
- 本期强制把 Azure 适配器做成可上传脚本插件。专用渠道类型已确定，首先按代码适配器实施，不扩建插件协议框架。

## 2. 当前实际情况

### 2.1 代码核查结论

| 边界 | 已核对事实 | 对方案的影响 |
| --- | --- | --- |
| Batch 路由 | [relay-router.go](../../router/relay-router.go) 未实现原厂异步 Batch 作业路由，Files 路由仍为 `RelayNotImplemented` | 需要新增文件与 Batch 专用业务入口，替换必要的占位接线 |
| Gemini | [Gemini adaptor](../../relay/channel/gemini/adaptor.go) 有同步 `batchEmbedContents` | 不能据此认定已支持异步 Batch 作业 |
| 插件 | [插件协议注册](../../pkg/jsplugin/routing.go) 的宿主协议主要为 Responses 和视频 | 一个 submit/query 插件不足以补齐文件、所有权和部分结算 |
| OSS | [存储接口](../../service/task_artifact_store.go) 与 S3、Azure Blob 实现可复用；现有上传会整体读取内容到内存 | 保留配置和底层存储能力，补充适用于 Batch 的受限读写与流式处理 |
| 创建安全 | [创建尝试模型](../../model/task_create_attempt.go)、[资金冻结事务](../../model/task_create_attempt_hold.go) 已有耐久记录和原子 hold | 复用数据库与资金底座，新增 Batch 快照构建，避免套用视频字段 |
| 取消结算 | [取消结算](../../service/task_cancellation_billing.go) 按退款处理；[计费补偿](../../service/task_billing_reconcile.go) 有依赖终态的退款分支 | Batch 需要独立决定最终费用，不能继承取消即全退的行为 |
| 任务超时 | [Task 查询与扫描](../../model/task.go) 和 [轮询](../../service/task_polling.go) 有通用超时判定与退款 | 必须让 Batch 由自身生命周期处理，避免误退款 |
| 系统调度 | [SystemTask runner](../../service/system_task.go) 已有处理器注册、数据库租约、心跳及执行记录 | 新增 Batch 处理器，沿用既有调度框架 |
| 任务展示 | [任务控制器](../../controller/task.go) 已有用户、管理员列表和分角色诊断信息 | 为 Batch 增加类型与详情投影，复用现有任务入口 |
| 合同定义 | [合同模型](../../model/customer_contract.go) 当前以用户为范围，规则唯一约束是用户与客户模型，规则只有路由组，没有具体渠道 | 需引入合同实体、合同规则的渠道绑定及 Key 合同引用 |
| 合同调用 | [合同解析](../../service/customer_contract.go) 按用户与模型解析；[合同中间件](../../middleware/customer_contract.go) 覆盖运行时组 | 改为由 Key 绑定合同选择规则，同时保留原始 Key 组 |
| 原生渠道池 | [Ability](../../model/ability.go) 允许组、模型对应多个渠道，模型展示进行去重 | 相同模型名不能用来区分渠道，需要明确入口或合同选择 |
| 阶梯计费 | [billingexpr](../../pkg/billingexpr/expr.md) 已支持 Token 分类、阶梯和请求条件 | 复用计算能力，补齐 Batch 计价上下文与冻结事实；不能称为已有 Batch 结算 |
| 计价时间 | [表达式运行](../../pkg/billingexpr/run.go) 的时间函数目前读取 `time.Now()` | 保存表达式本身不能冻结时间，必须新增显式计价时间上下文并验证跨时段结算 |
| 价格空白 | [合同价格视图](../../service/customer_contract_view.go) 在阶梯模式提前返回，未携带阶梯价格；[详情组件](../../web/src/components/contract-price-details.tsx) 未渲染阶梯详情分支 | 需要前后端共同修复，不能只更改折扣摘要 |

上述结论针对本次核查的仓库代码；没有检查生产部署是否另装了私有插件。

### 2.2 官方资料与容量取值

2026-09-09 查询的 [Azure Batch 使用文档](https://learn.microsoft.com/en-us/azure/foundry/openai/how-to/batch) 明确：

- 普通输入文件上限为 200 MB、每文件 100,000 条请求，同一文件使用同一部署。
- 建议状态查询间隔至少 60 秒；24 小时是处理目标，超过后不自动证明作业失败。
- 取消后返回已经完成的工作，并对已完成工作收费。
- Batch 受排队 Token 配额约束，输入文件条数和大小不代表上游一定受理。
- 不设置文件过期时，上游输入文件数量存在资源级上限；本站 OSS 与 Azure Files 是不同存储边界。

[Azure Batch REST 文档](https://learn.microsoft.com/en-us/rest/api/microsoft-foundry/azureopenai/batch) 提供创建、查询、列表、取消，以及请求计数、文件 ID 和状态等字段；创建请求的 `completion_window` 必填且仅支持 `24h`。它是处理目标字段，不是本地强制截止或退款时间。具体部署、鉴权、API 版本、每行参数与用量字段仍需真实验收。

使用文档还说明 Azure 输入文件的 `expires_after` 和输出文件的 `output_expires_after` 可设置 14–30 天、以 `created_at` 为锚点。它们属于上游文件保留措施，是否启用需验证所选 API 版本和恢复窗口，不等于本站 OSS 生命周期或新增客户配置项。

200 MB、100,000 条限制在本次读取的 how-to 页 `Batch limits` 中直接列出；[Azure quotas/limits 页](https://learn.microsoft.com/en-us/azure/foundry/openai/quotas-limits#batch-limits) 也列出相同限制，作为交叉引用。原 how-to 引用有效，不按来源错误处理。

未找到可证明“通常每批多少条”的可靠行业统计。最终 **10,000 条、20 MiB** 是用户明确选择的首期平台边界，不是 Azure 官方推荐值，也不是行业平均值。请求较长时先触发文件大小限制；输出文件可能显著大于输入文件，不能套用 20 MiB 截断结果。

### 2.3 对原需求分析的修正

- 需求 2 的最终方案已替代“同一合同内允许重复模型并显示折扣 1/2”：使用多合同与 Key 绑定。
- 需求 1 已明确为真实 Azure Batch 作业，与合同能力没有必然依赖，能够独立交付。
- “计费完全没有档位维度”过于绝对：当前已有请求条件表达式，但没有原厂 Batch 生命周期与实际结算。
- 不沿用原文对其他厂商 Flex/Priority 不支持或固定倍率的未经当前验证结论；这些能力不在首期范围。

## 3. 优化方案

### 3.1 总体职责与依赖

| 组件 | 唯一职责 |
| --- | --- |
| 专用路由与 Controller | 接受并校验 Batch/文件协议，执行鉴权，返回脱敏的客户响应 |
| Batch service | 文件引用、创建编排、进度、结果归集、恢复和计费目标计算 |
| Azure Batch adapter | 吸收 Azure 的地址、鉴权、部署名、文件接口、状态和 usage 差异 |
| Channel | 保存管理员明确配置的连接、模型映射及 Batch 渠道身份 |
| TaskCreateAttempt / Task | 分别保存发送前创建事实和取得可信上游 ID 后的业务任务事实 |
| SystemTask | 执行一轮后台推进，记录调度结果；不替代客户作业状态 |
| 现有资金与日志底座 | hold、差额调整、幂等结算、欠费/异常处理和账单投影 |
| OSS | 存放输入、结果、错误文件内容；infra 管理其生命周期 |
| 合同与 Key | 决定已绑定合同的模型授权、具体渠道和折扣，独立于 Batch 产品本身 |

共享底座以 [硬约束](../00-context/硬约束.md)、[异步任务与计费事实架构](../20-architecture/账单计费-异步任务与计费事实架构.md) 和 [用户模型合同定价架构](../20-architecture/账单计费-用户模型合同定价架构.md) 为现行依据。本文的多合同和 Batch 部分结算属于对现行适用范围的计划变更，必须按 §4.2 的清单同步修订权威文档，不能只改代码而保留冲突规则。不借此改造 Seedance 协议、图片执行器或 NEWAPI 普通请求语义。

### 3.2 Azure Batch 渠道与请求路由

建议新增 `ChannelTypeAzureBatch`，编号在实施时从可用范围分配，不在本文提前占号。

首期 Batch 按 Link 类本地类型化扩展治理，由专用入口、ChannelType 和代码 adapter 明确身份；不因此继承 Seedance 专属的模型唯一性、素材或视频合同。当前 NEWAPI 尚未实现这些业务路由，本地补齐已确认范围；不等待未来原生支持，也不声称这是现有原生能力。

`/v1/files`、`/v1/batches` 是可能与未来上游实现重合的标准路径，必须登记为明确的合并冲突面。每个方法与路径只注册一个权威 handler；不得通过注册顺序、NoRoute fallback 或双读文件 ID 猜测归属。以后接取上游时，按 [上游代码合并指南](../30-engineering/上游代码合并指南.md) 对比协议、所有权、历史文件/任务和资金事实，形成一次明确的接线或迁移方案；能由原生完整承接时移除对应本地重复实现，承接前继续由当前唯一入口负责，不能并列发布两套公共状态。

管理员配置资源地址、凭据、已验证 API 连接方式、客户模型及到 Azure Batch 部署名的精确映射。渠道类型明确能力，普通 Azure 渠道不会自动获得 Batch 履约资格。渠道测试应验证连接和配置，不以测试连接为由自动创建收费 Batch 作业。

客户仍使用原来的客户模型名：普通 Chat Completions 进入原有普通入口，Batch 通过 `/v1/batches` 的入口身份选择专用渠道。建议 Batch 渠道不写入普通 Ability 分发池，以免相同模型的同步请求误选 Batch 渠道；模型与价格展示采用明确的只读投影。

上传文件时不确定最终执行渠道。创建作业时，依据文件内客户模型、当前调用 Key 的授权/组及适用合同规则，选择有资格的 Batch 渠道并冻结映射。文件内模型统一转换为该渠道的部署名，原始客户输入保持可追溯。创建后查询、取消和结果获取均使用冻结渠道，不重新选渠。

没有合同的客户可以直接使用 Batch。合同 Key 调用 Batch 时仍遵守既有授权边界；若所绑定规则无法由 Batch 渠道履约，应在预扣前明确拒绝，不能绕过合同自动换用普通渠道。该集成不构成 Batch 首期必须依赖需求 2 上线的理由。

### 3.3 文件与北向接口

首期按下面的最小流程实现；属于待发布接口设计，不代表已宣称完整 Files API 兼容：

| 接口 | 首期行为 |
| --- | --- |
| `POST /v1/files` | 接收用途为 Batch 的 JSONL，保存本站私有 OSS，返回本站文件 ID |
| `GET /v1/files` | 按调用者归属分页列出本站 Batch 文件 |
| `GET /v1/files/{file_id}` | 返回归属校验后的文件元数据 |
| `GET /v1/files/{file_id}/content` | 经鉴权读取文件内容，保持 SDK 可消费的文件响应 |
| `POST /v1/batches` | 接收本站输入文件 ID、Chat Completions 端点及必填 `completion_window: "24h"`，校验、冻结费用后提交 |
| `GET /v1/batches` | 按调用者归属分页列出 Batch 作业 |
| `GET /v1/batches/{batch_id}` | 返回作业阶段、可信计数及可用的本站结果/错误文件 ID |
| `POST /v1/batches/{batch_id}/cancel` | 向冻结渠道提交取消请求，并继续跟踪最终结果和费用 |

文件删除、更新及其他用途不作为首期承诺，也不借 Files API 引入 OSS 自动清理。确需发布文件删除操作时，另行明确“撤销平台访问”与“删除物理对象”的语义，不能从通用兼容口号推导 infra 职责变化。

现有 `DELETE /v1/files/:id` 保留未实现语义，可保留原占位 handler；若为路由整理而移动，也只能接到明确的未实现响应，不新增文件撤销或物理删除。不得同时保留同方法同路径的两个注册。

创建请求必须携带 `completion_window`，值仅接受字符串 `24h`；缺失、类型错误或其他值在本地返回 400，并在上传 Azure 文件、资金 hold 和作业创建前拒绝。不能给缺失字段静默补默认值，也不能把客户传入的其他窗口改写为 `24h`。字段合法不代表平台承诺 24 小时内完成。

输入校验包括：字节和请求数上限、JSONL 格式、唯一且有界的 `custom_id`、每行方法与端点、同一客户模型、文本请求结构、模型权限、适用的输出上限，以及影响费用的可控数量边界。`stream=true` 不作为批处理流式输出能力发布。其他文本参数复用原生 DTO 的含义，并以首期真实部署验收的支持范围为准。

格式错误、模型混用或缺少输出上限，在发送推理作业和资金 hold 前整批拒绝，指出行号与脱敏原因。解析器不能保留默认的小行长度限制而把合法长文本误判为文件错误，也不能无界读取单行。

校验时机统一为：上传阶段执行完整的文件格式与内容校验，用于提前反馈；创建阶段从 OSS 全量流式重解析，重新完成容量、每行合法性、当前模型权限、文件归属/可读性与渠道资格校验，并按本次冻结的价格逐行估算。上传成功或已有校验摘要不能代替创建时的最终校验。模型与渠道确定后，在同一冻结价格上下文下处理全部行；遇到后续坏行则整批拒绝，不因前面行已通过就部分提交。首期不增加跨创建请求复用的校验缓存机制。

文件数据库事实至少包括本站文件 ID、`user_id + app_id`、用途、对象引用、大小、创建时间、必要校验摘要，以及作业关联。文件内容只进私有 OSS，不进 Task、日志、缓存或普通响应元数据。文件上传 Key 仅用于审计；作业使用创建它的 Key 冻结计费和授权事实。

复用既有存储配置与凭据管理，新增 Batch 所需的受限/流式读写入口。上传、下载和逐行处理要有明确的内存预算与工作并发控制；这些属于系统资源控制，不增加客户活动作业配额。结果处理中断只重试读取、保存或核算步骤，不重新生成内容。必要临时缓冲的释放不等同于 OSS 生命周期管理。

对象缺失返回明确的文件不可用错误；网络或存储服务错误不能伪装为文件已删除。已经结算的资金不因之后文件被 infra 清理而回滚。正式发布前应在相关硬约束和架构文档登记 Batch 正文存私有 OSS 的范围，不能误套普通日志或素材代理的存储规则。

Azure Files 的数量上限由 Azure 资源单独管理。输入 `expires_after` 与输出 `output_expires_after` 可作为部署侧保留策略的缓解选项，在验证目标 API 支持、有效范围和后台恢复所需时间后，由适配器按明确配置提交；不借此新增本站客户保留期选择、后台删除任务或 OSS GC。未启用时明确记录 Azure 侧运维责任；不能假定开启本站 OSS 就消除了 Azure Files 上限，也不能把 14–30 天参数当成作业执行截止时间。

### 3.4 创建流程与耐久执行

建议流程：

1. 鉴权并校验创建请求字段，包括必填的 `completion_window="24h"`，验证本站输入文件归属与可读性。
2. 全量流式重解析输入文件；从客户模型确定 Batch 渠道并冻结模型、Azure 部署、协议/adapter 版本、连接、价格和计价时间，完成全部行的合法性、权限、容量校验及逐行预算，生成仅供上游使用的转换文件。整批通过且预算确定后才进入上游上传和资金操作。
3. 完成必要的 Azure 文件上传并保存可信文件引用。文件上传不等同于已创建收费推理作业。
4. 建立 `TaskCreateAttempt`，再以同一事务提交资金 hold、Key 额度变动与 `sending`，成功后才允许发送 Azure 作业创建请求。
5. 取得可信上游 Batch ID 后，原子完成 Task 创建、hold 转移和 attempt 完成，返回本站 Batch ID。
6. 后台按冻结事实查询、下载结果、保存归一明细、计算目标金额并幂等结算。

没有可信上游 Batch ID 时不伪造 Task。创建超时、连接中断或无法判断是否受理时，保留 attempt 与 hold，使用既有请求追踪信息帮助查询；不能把返回错误解释成“上游肯定没有创建”。已取得并持久化可信上游 ID、但本地 Task 尚未提交的情况，通过既有恢复入口补全本地事务。

复用 model 层创建/资金事务，新增 Batch 专用的 service 快照构建。现有 `PrepareTaskCreateAttempt` 使用视频协议和视频截止时间，不能整段套用。首期不承诺客户端重复 POST 自动合并；SDK 自动重试配置与网络中断行为必须列入真实验收，不能假定 Azure 提供了已验证的创建幂等保证。

### 3.5 任务跟踪、调度与恢复对齐

一个 Batch 对应一条客户 Task；行级请求是该作业的明细，通过 `custom_id` 关联，不为 10,000 行分别创建轮询 Task。主数据库保存唯一业务事实，任务页面、API、日志和账单只做投影。

建议在现有 SystemTask 注册独立的 Batch 处理器，一轮处理到期作业、结果归集和未完成结算后结束。复用调度租约、心跳、运行记录与进度报告；仅在有待处理工作时调度。默认同一上游作业查询间隔不小于 60 秒，失败后退避；客户刷新页面或调用 GET 不触发额外的无节制上游轮询。

必须分开持久化三类事实：

| 事实 | 必须表达的内容 |
| --- | --- |
| 上游执行 | 当前可信阶段、总数/成功数/失败数、关键时间、最后可信观测；临时查询失败保持既有事实 |
| 文件交付 | 结果/错误文件待获取、处理中、已持久化或异常；仅完整对象可发布下载引用 |
| 资金结算 | 已冻结、待结算、已结算或异常/欠费；目标金额与用量来源可追溯 |

北向状态与页面投影必须有明确映射表，保留 validating、in_progress、finalizing、cancelling 及终态的区别。内部存储阶段不直接作为新的官方 Batch `status` 值返回。正常完成交付前保持平台 finalizing；已确认取消/失败的任务仍可有结果归集和结算待办，查询应明确反映结果文件尚未就绪。最终 DTO 映射要通过 SDK 契约测试验证，不能只把 SUCCESS/FAILURE 粗略替换成字符串。

Azure `request_counts` 缺失时显示阶段而不是伪造进度。取消请求已接收不等于已经取消；已取消不等于零费用；上游 completed 不等于全部行成功。文件已保存和财务已结算也不能彼此代替。

任务列表复用当前页面，增加 Batch 类型/筛选和详情投影，展示客户模型、请求计数、阶段与更新时间、输入/结果/错误文件、预扣/实际/退回金额和行级用量入口。管理员沿用既有角色权限查看渠道和追踪信息；上游 Batch ID、连接与敏感诊断不泄漏给普通客户。

追踪链应能串联：平台请求 ID → attempt → 本站 Batch ID → 上游 Batch ID → 文件引用 → `custom_id` 明细 → 计费与日志。创建结果不明且尚无 Task 的 attempt，也必须从现有运维核实入口可发现，避免只在业务列表跟踪已创建成功的作业。

以下后台入口都需要检查 Batch 归属，不能只修改主轮询：通用超时扫描、失败退款扫描、创建尝试恢复、终态计费补偿、主动查询和人工恢复入口。Batch 处理器拥有生命周期推进权；其他入口只调度同一处理逻辑或跳过，不建立第二套判定。

现行异步架构 §6.5 和不变量 13 将失败、取消、过期等终态统一交给原子退款。Batch 扩展必须正式修订该规则的适用范围：明确注册的 Batch 在可信终态下按实际可计费事实形成资金目标；其他既有任务继续各自已经发布的退款合同。不得把该变更泛化为所有异步任务失败后都按 Token 收费。仅超过 24 小时目标或一次查询超时，不属于可信终态，不能据此开始最终结算、自动退款或重发。对应文档交付和验收见 §4.2、§5.1。

| 异常 | 处理要求 |
| --- | --- |
| 超过 24 小时仍执行中 | 继续按上游事实跟踪，可观测超时目标，不自动终止或退款 |
| 一次查询失败或计数缺失 | 保持最后可信状态，记录脱敏诊断并退避 |
| 创建结果不明 | 保持 unknown 与资金 hold，人工核实，不自动重发/换渠/退款 |
| 进程重启或租约丢失 | 从数据库恢复阶段；旧 worker 停止写入，通过条件更新防止覆盖新结果 |
| 结果下载或 OSS 写入失败 | 重试结果归集，不能重提 Batch；不发布半个结果文件 |
| 结算数据库失败 | 保留已确认用量和目标金额，通过同一幂等事务补偿 |
| 配置、渠道状态或价格变化 | 已创建作业按冻结事实继续；凭据实际失效时进入可观测恢复/核实流程，不换渠道 |
| infra 清理了尚需使用的对象 | 明确文件不可用，保留业务和资金事实，依据已有证据恢复或核实，不猜测费用 |

### 3.6 Batch 定价与结算

遵循 [表达式计费规范](../../pkg/billingexpr/expr.md)。建议以明确的执行模式区分普通价格与 Batch 价格，在现有计价配置入口新增 Batch 规则；不创造客户模型别名，也不把所有厂商的档位倍率写死到公共公式。

同一模型的 Batch 输入、输出和缓存等已支持维度采用现有表达式引擎计算；规则保存在现有配置事实源。内部选择 Batch 价格的能力放在新增文件中，避免修改普通模型的价格键含义。管理和客户价格展示均标识 Batch。缺少 Batch 价格不能静默使用普通价或零价。

修复后的明确实现边界：配置键为 `batch_billing_setting.batch_billing_expr`；预算器对 token 算术及条件/tier
分支求保守上界，不能安全预算的表达式在保存或创建前拒绝，结算只调用既有 Go 引擎。必要请求条件只冻结允许的
标量参数及计价时间，不存储任意 header/正文探针。客户会话价格页明确选择原生、Azure Batch 或合同；不自动推断
默认合同。当前本地验证与外部验收边界以 [实施记录 §3–4](2026-09-10-Azure批处理与多合同渠道定价实施记录.md#3-验证状态) 为准。

单行先按其自身请求上下文和实际 usage 算模型费用，再应用已有适用组倍率及合同事实；Batch 总费用是逐行费用之和。组特殊倍率应替代普通组倍率，不能二者同时相乘。需求 1 不强制创建合同，也不把合同折扣当成 Batch 优惠。

需要冻结：价格/表达式与版本、模型、组及适用折扣、每行输出上限、必要的请求条件、资金来源、Key 跟踪规则和预扣金额。表达式使用时间条件时，应冻结创建时的计价时间上下文；结算不能重新读取当前时间使价格漂移。只保存计算必需的归一条件，原始文本保留在受保护文件中。

计价时间冻结是新增引擎能力：在 [现有运行入口](../../pkg/billingexpr/run.go) 的请求上下文中增加可选的明确计价时刻，Batch 创建时持久化同一个 UTC 时刻，预扣、最终结算和恢复均传入该值。`hour/minute/weekday/month/day` 再按表达式指定时区转换；不能把时间捕获到共享编译缓存中。未传入时间上下文的原生调用保留当前行为，历史已结算任务不重定价。实现时同步更新表达式规范，并验证跨小时、跨日、跨周、时区边界及重启后结果一致，不能仅靠保存表达式字符串宣称已经冻结时间。

预扣与结算要求：

- 预扣逐行估算输入并结合输出上限；缓存未知时采用不会依赖预期缓存优惠的预算。适用的 `n` 等数量也必须验证并纳入预算，不能只检查 max tokens。
- 输出上限只能约束输出预算，不能保证本地 Token 估算与上游完全相等；不得宣称预扣是任意表达式下的数学绝对上界。动态/非单调规则的可预扣性需在启用前验证，无法可靠预估时明确拒绝该配置用于 Batch。
- 按每行实际输入、输出及可信缓存用量归一后计算，阶梯也按每行判定；不能汇总全部 Token 后套一次阶梯。
- 行级明细保留足够精度，再按既有 checked quota 规则形成作业资金目标；明确舍入时机，确保展示明细与最终账单可对齐。
- 完整终态证据到齐后执行一次最终结算。取消、部分失败均根据实际费用求目标；有明确零费用证据才结算为零。
- 对已经明确取消且未执行的行，依据可信终态和执行计数归入未发生费用部分，不要求其返回成功响应的 usage。已执行但用量缺失的行与未执行行必须区分，不能用缺少结果一概推断免费。
- 客户结算所需用量缺失、结果明细与计数不一致或收费依据不明时保持待核实，不把估算伪装为实际用量，也不因等待超时直接全退。仅 Provider 成本金额未知、但客户计费依据完整时，不阻止按已冻结售价完成客户结算。
- 实际费用高于预扣时遵循现有原资金来源补扣/欠费机制；不能伪造失败、把实际费用截到预扣值或跨资金来源偷偷补扣。
- 逐行结果归集使用稳定的作业与 `custom_id` 身份去重；重复内容无副作用，不同内容冲突进入核实。重复轮询、取消、结算补偿不能重复扣费或退款。
- 客户资金与 Provider 成本风险分开，无法取得供应商金额时保持未知，不能用客户 quota 冒充上游成本。

账单按 Batch 汇总，详情提供行级 `custom_id`、结果类别、输入/输出/缓存等用量、适用价格及费用。行级明细是核算证据，不生成第二套资金账本，也不重复增加普通调用次数。账单关联原创建 Key；后续查询或下载使用其他有权 Key 不改变费用归属。

### 3.7 多合同、Key 与具体渠道

本节计划变更的权威文档是 [用户模型合同定价架构](../20-architecture/账单计费-用户模型合同定价架构.md)。其用户级模式、组内选渠、`UNIQUE(user_id, public_model)`、唯一写接口和相关不变量都需要按新合同身份修订；不能继续把该文档的“一用户一份合同、组内原生选渠”表述作为新实现事实。异步架构 §6.2 的 `ContractBillingFact` 描述也须补齐合同 ID、版本、具体渠道及路由组，详见 §4.2 的交付清单。

建议的数据关系：

| 实体 | 建议字段与约束 |
| --- | --- |
| 客户合同 | ID、用户 ID、客户可读名称、启停状态、版本、创建/修改时间及审计 |
| 合同规则 | 合同 ID、客户模型、具体 Channel ID、路由组、八位定点折扣；同一合同客户模型唯一 |
| API Key | 可空合同 ID；原 Group、AutoGroups、模型限制和其他原生配置保留 |
| 请求/任务计费事实 | 合同 ID/版本、规则、客户模型、具体渠道、路由组和折扣的冻结事实 |

路由组继续决定适用的原生组倍率，Channel ID 决定合同的具体执行渠道。管理员保存时验证客户模型、渠道、路由组及协议资格一致；同组存在其他同名模型渠道不影响明确绑定。

例如，合同 A 将模型 M 绑定渠道 X、折扣 0.25；合同 B 将同一模型 M 绑定渠道 Y、折扣 0.55。两个渠道可以属于相同组。客户分别创建绑定 A、B 的 Key，调用时都传模型 M；后台根据 Key 的合同执行。

Key 创建/编辑的绑定操作必须验证合同属于当前用户，不能以猜测合同 ID 绑定他人合同。提交后立即失效对应 Key 授权缓存。无合同用户的原生界面和路径保持不变；有合同时提供名称、模型/有效价格说明和“不绑定合同”，不自动选中管理员指定的默认合同，不要求客户理解渠道或路由组。

运行时行为：

| Key / 合同情况 | 授权、路由与计费 |
| --- | --- |
| 无绑定 | 完整使用原生 Key/用户组与模型规则 |
| 绑定启用合同 | 模型必须在合同内且符合 Key 原有模型限制；固定合同具体渠道与有效组倍率、折扣 |
| 绑定合同停用 | 保留绑定关系与原生组设置，本次调用恢复原生逻辑 |
| 启用合同缺少模型或具体渠道不可用 | 保持既有合同失败关闭边界，明确错误；不能当作合同停用而回退普通池 |
| 合同读取失败、版本冲突或绑定数据异常 | 明确失败并恢复/刷新事实，不能把技术错误当成未绑定而扩大权限 |

未绑定 Key 可能拥有与合同不同的模型范围，这是已接受的原生逻辑，不新增强制合同限制。模型发现与客户价格查询使用调用 Key 的有效合同；控制台查看多份合同则按合同分别展示。客户侧不返回内部 Channel ID、路由组或上游模型身份。

合同生效状态只决定新请求。已创建异步任务继续其冻结合同事实；后续合同修改、停用或 Key 换绑不能重算在途任务。合同停用保留绑定，重新启用后新请求重新满足“绑定启用合同”的条件；首期不引入硬删除合同所需的级联与追溯问题。

合同缓存按合同身份与版本解析，用户合同列表与 Key 授权缓存一并失效。保存规则、版本更新和审计沿用现有事务及授权屏障；管理员并发编辑不能静默覆盖。运行时不双读两套合同规则作为长期兼容逻辑。

### 3.8 存量合同迁移

迁移目标是把现有一份用户合同转换为显式合同实体，并绑定其存量 Key；无合同用户保持无绑定。合同开启/停用状态、版本和折扣精度必须保留。Key 原始组设置不被迁移覆盖。

重要限制：旧规则只有路由组，没有渠道 ID。一个组内可能存在多个同名模型渠道，因此“旧 Key 绑定迁移合同”能够保留合同选择和折扣，却不能自动证明具体渠道行为完全不变。

建议迁移步骤：

1. 在数据库备份和离线预检中列出旧规则、已有 Key 及可用渠道候选。
2. 唯一且资格明确的渠道可形成确定迁移映射；没有候选或有多个候选的规则，由管理员在切换前指定目标，禁止选第一个或随机选。
3. 创建合同实体、迁移规则和 Key 引用，校验记录数、折扣、归属及启停状态；迁移标记只有校验完成才写入。
4. 验证 SQLite、MySQL、PostgreSQL 的索引变更、断点重入和失败回滚；应用运行不保留旧用户级规则的双读路径。
5. 对已有异步任务继续使用其合法冻结计费事实，不借迁移用新合同重写历史。新旧任务事实的可读取性应在升级前验证。

上述多候选映射是实施前必须解决的数据问题，不是让客户新增选择步骤。出现不完整映射时停止迁移切换，保留旧运行版本，不通过业务请求 fallback 掩盖问题。

### 3.9 合同阶梯价格详情修复

后端补齐该模型的阶梯表达式、适用的 usage schema 和当前规则的有效倍率。原生有效组倍率计算继续复用 `ResolveCustomerContractNativeGroupRatio`，不重复乘特殊组倍率。

前端优先复用 [现有动态价格详情](../../web/src/features/pricing/components/dynamic-pricing-breakdown.tsx) 及其解析逻辑，补齐合同详情的阶梯分支。展示包含阶梯条件、输入/输出及已配置缓存价格、单位和有效合同价；阈值保持原值，折扣只作用于价格结果。一个合同规则只展示自己的倍率，不能取同模型其他合同的折扣。

对于无法静态展开为固定阶梯的请求条件表达式，使用现有可解释展示能力，明确条件与计价方式，不能返回空白、伪造固定报价或执行第二套价格解释器。缺少/无效价格数据应给出明确不可用说明。

管理员合同界面、客户合同列表、Key 选择预览统一消费同一价格视图。公共内容不暴露内部渠道信息；新增文案遵循项目 i18n 和前端技能要求。此修复能够独立先行交付，再适配需求 2 的合同 ID。

## 5. 验证与验收

### 5.1 Azure Batch

| 场景 | 必须满足的结果 |
| --- | --- |
| 10,000 条且不超过 20 MiB | 通过本地容量校验；实际能否受理由余额和 Azure 事实决定 |
| 10,001 条，或超过 20,971,520 字节 | 明确拒绝，无推理作业提交和资金 hold |
| completion_window 缺失、非字符串或非 24h | 本地 400，无 Azure 文件上传、作业创建或资金 hold；合法值仍不承诺 24 小时内完成 |
| 重复 custom_id、坏行、混合模型、缺少输出上限、数量溢出 | 指出合法范围或行号，在提交前拒绝；不能静默删行或截断参数 |
| 上传已通过，但创建时文件或权限已变化 | 创建阶段全量流式重解析并完成最终校验与预算；失效内容/权限整批拒绝，不能依赖上传摘要放行 |
| 多批连续提交 | 不触发本期新建的客户活动数限制，不进入平台业务队列；原有系统/额度限制正常生效 |
| 普通与 Batch 使用同名模型 | 分别进入合法渠道，普通请求不误选 Batch 渠道 |
| 全部成功 | 文件可下载，用量可追溯，逐行费用汇总等于最终结算目标 |
| 部分失败/取消 | 保留已完成结果，只释放未发生费用对应差额，不整批全退 |
| 无变化重复轮询/重复结果/重复结算 | 不重复写资金，不重复增加账单或请求次数 |
| 创建断线及事务边界故障 | 未发送可安全拒绝；可能已发送保持 unknown；可信 ID 已保存可恢复 Task |
| 重启、双 worker、租约丢失 | 唯一推进，不覆盖新状态，不重复发送创建请求 |
| 超过 24 小时 | 不因通用媒体超时规则自动失败或退款 |
| 可信失败/取消/过期与其他任务退款回归 | Batch 按完整收费证据形成目标，证据不足待核实；其他已有任务仍遵循原合同，不能被 Batch 分支改义 |
| 结果大于 20 MiB | 按真实完整结果流式处理，不截断；内存与临时资源保持有界 |
| OSS 或数据库故障 | 交付与结算分别恢复；不重做推理、不对缺失 usage 猜账 |
| 上游用量与预估不同 | 按可信实际用量及冻结规则结算，差额/欠费遵循既有资金语义 |
| 阶梯、缓存、数量、时间条件 | 按单行冻结上下文定价，非线性规则不按总 Token 错套阶梯 |
| 跨小时/日期/周界及时区、结算重启恢复 | 同一 Batch 始终使用冻结计价时刻；编译缓存复用不串作业时间，原生无时间参数调用行为不变 |
| Azure 输入/输出文件过期选项 | 若启用，验证目标版本、14–30 天范围及归集恢复窗口；不触发本站 OSS 删除任务或新客户保留期配置 |
| 路由注册与 DELETE 占位 | 发布的方法只注册一次，DELETE 仍明确未实现；文件或路由不通过双实现 fallback 猜测归属 |
| 权限与隐私 | 跨 user/app 文件与作业访问失败；客户不看到内部渠道、上游模型、凭据或签名 URL |
| Key/合同/渠道配置变化 | 已受理任务仍按冻结事实跟踪与结算，新请求按最新授权处理 |

容量验证至少包含 10,000 条边界、长单行、较大输出、多批并发和归集中断恢复；采用确定输入与资源观测，不以随机循环或仅打印耗时的测试作为通过依据。

### 5.2 多合同与价格详情

- 两份合同同名模型、不同渠道、不同折扣；分别绑定 Key 后路由和金额准确，包括渠道同组场景。
- 同一合同重复模型保存失败；不属于用户的合同不能绑定；版本冲突不会覆盖管理员变更。
- 未绑定 Key、无合同用户和停用合同均走原生路径；原始 Group/AutoGroups 保留，不能强制 Default。
- 启用合同缺模型或渠道失效保持失败关闭；缓存读取失败不被当成无合同。
- 旧用户合同和存量 Key 迁移准确，原状态/折扣/归属保留，多候选渠道不自动猜选；三库可重入。
- Key 模型发现、合同价格、控制台选择和实际请求使用同一合同身份；客户侧隐藏内部信息。
- 阶梯详情不空白，组特殊倍率只应用一次，阈值不打折；同模型不同合同详情不串价。
- 价格展示与真实计价/舍入测试一致；动态条件不可静态报价时有明确说明。

### 5.3 工程检查与真实验收
