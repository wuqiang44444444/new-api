# 客户月账单确认与版本固化方案

> 实施与修复记录（2026-09-17）：步骤 1—5 已有实现，本轮修复审计发现的并发唯一性、来源跟踪、
> 清理集合、任务受理、CSV 完整性及页面金额口径问题。具体落点、测试与限制见第 16 节。
> 第 16 节记录本次实际选型；前文的候选讨论不能替代验收证据。
> 能力开关仍默认关闭。本地 SQLite、真实 MySQL/PostgreSQL 与配置的对象存储已完成部分验收；核心业务延迟和部署恢复演练尚未完成，
> 本地测试通过不等于可直接生产启用。未改动扣款、退款算法或余额。

## 问题与目标

### 1. 本次范围

在现有“账单对账 → 客户账单”和客户“我的账单”中增加月账单确认、版本固化与更正能力。
客户账单已经按月份查询，本次优化该功能，不新增另一套账单菜单、计算规则或资金账本。

解决两个问题：

1. 管理员核对后，客户与管理员能够持续查看、下载同一份正式版本，历史数据变化不悄悄改变已确认账单。
2. 已确认账单的汇总、明细与下载不再反复扫描原始日志、关联 Task 和退款证据，降低数据库读取压力。

本文是待实施方案。业务选择已经用户确认（见文首范围声明与第 10.5 节技术选型）；数据模型、实现机制、资源参数是工程建议，必须完成下文验证后才能作为已交付事实。
实施前先完成第 10.5—10.7 节的机制核对与选型评审，再按第 15 节步骤推进本轮三个交付包。

### 2. 已确认的业务决定

| 事项 | 已确认规则 |
| --- | --- |
| 页面 | 优化现有客户账单，管理员与客户继续复用主体、数据口径和导出能力 |
| 粒度 | 每个客户的每个自然月独立确认，不要求全部客户一起完成 |
| 时间 | 只允许确认已结束的自然月；当月保持实时查询，标记“本月进行中” |
| 流程 | 后台生成待确认版本，管理员核对后确认发布 |
| 角色 | 同一位有权限的管理员可以生成并确认，记录操作人与时间 |
| 固化内容 | 汇总、明细、组与合同折扣、费用解释和数据质量提示一起固化 |
| 确认门槛 | 影响账单金额的未解决问题阻止确认；解释信息缺失可在明确知悉后保留 |
| 变化处理 | 生成后、确认前，影响该账单的来源数据变化必须阻止确认，要求重新生成并核对 |
| 更正 | 保留旧版，生成更正版，记录公开原因和差异，重新确认后发布 |
| 默认展示 | 首次确认前客户看未确认实时账单；更正版确认前继续看旧确认版；发布后默认看最新确认版 |
| 历史版本 | 客户可以查看自己的历史确认版本、更正说明与金额差异；内部备注不公开 |
| 资金边界 | 确认、更正不扣款、不退款、不改变余额；不得直接修改账单金额替代资金处理 |
| 保留 | 已确认版本及被替代的旧版长期保留，首期不自动过期；失效草稿允许清理 |
| 下载 | 每次重新鉴权，链接短期有效；链接过期不代表账单过期 |

新版本内部统一使用 `Asia/Shanghai` 自然月左闭右开区间。现有 `GetBillingCustomerStatement` 查询终点为包含式，
接入时必须把新版本的排他终点转换为 `end_exclusive - 1` 秒；不得直接传入下月零点，也不借本功能改写既有接口语义。
正常跨月退款按退款发生月份入账，不因原消费月份已确认而移动退款账期。
例如 9 月实际发生的退款计入 9 月；8 月原记录被证实错误并修正，才属于 8 月更正版本处理范围。

### 3. 成功标准与非目标

- 同一账单版本，管理员和客户可见的公共金额、用量、折扣、质量信息一致，管理端额外维度不改变金额口径。
- 同一版本在重新登录、修改当前价格/合同、清理原日志、更新代码后，已冻结的业务内容保持不变。
- 不发布部分明细、混合时间截面的结果，未知字段不伪装为零或完整金额。
- 已确认账单的正常浏览、翻页与下载不查询原始日志或退款证据；当前余额等实时辅助信息另行标注。
- 更正可追溯、确认幂等；旧确认版始终可访问，不因更正版失败而受损。
- 生成过程有界、可取消、可恢复，不以异步为理由无限扫描或占满数据库。

不包含供应商对账、余额流水建设、税务发票、批量确认全部客户、人工录入应收金额或自动资金调整。
本功能名称中的“确认”表示管理员确认指定版本和核对范围，不等于已完成客户余额、充值、供应商发票等全部外部对账。

#### 3.1 最小侵入优先级：允许局部重复

本方案的实现优先级为：**账单正确性与事务不变量 → 减少原生代码改动和上游合并冲突 → 局部可读性 → 消除重复**。
用户明确允许重复。后文的“复用”“统一”“集中接入”描述业务口径或必要资源协调，不构成抽取公共框架、合并所有流程的要求。

| 内容 | 首期取舍 |
| --- | --- |
| DTO 适配、字段组装、薄校验、状态提示、局部任务循环、临时文件处理 | 可以在新增账单文件中保留少量明确重复，避免改造已有调用方 |
| 组/合同折扣、退款分类、原价还原、精度及舍入 | 调用现有权威函数；不复制一套可独立变化的计价解释规则 |
| 日志写入与修订、确认与维护、全局资源占用 | 必须共享真实事务或协调事实；代码看起来相似或复制同一算法不能替代互斥保证 |
| 页面主体与现有公开接口 | 保留已有入口；可新增局部组件/适配代码，不要求重写整页、统一所有 DTO 或改变旧字段类型 |
| 长期账单与临时导出的状态和保留策略 | 可以独立实现各自编排，不能为复用强塞进同一任务生命周期 |

选择接入方式时依次判断：已有函数能否直接调用；能否在新增同包文件中完成；是否只需极窄接线；最后才考虑扩大原文件修改。
Go 同包的新文件可以直接调用现有未导出函数，不为这个目的扩大公共 API、移动文件或创建 `common`/`utils` 包。
“新增文件更多”可以接受；减少文件数、追求一次扫描或删除几段重复代码，都不能单独成为重构原生模块的理由。

具体限制：

- 不建立通用 SnapshotEngine、版本化 Repository、任务策略注册框架或全局 ORM 拦截层。
- 不为此改造 Provider、relay、预扣、扣款或退款算法，不把既有资金多步流程重写为新事务。
- 不统一改造所有日志类别；只有影响账单的消费、退款及证据变更进入必要接线，其他日志保持原行为。
- 不为抽取复用移动、重命名或格式化既有实现；少量字段组装重复应留在各自业务文件。
- 允许重复不等于允许两套金额规则或两份互不协调的容量计数。共享的应是这些必要事实和规则，不是所有业务代码。

既有账单/导出扩展文件也不是任意重构的区域。实施时按已提交基线区分上游原生文件、已有本地扩展和新增文件，
不把当前未提交改动当成可随意移动的代码；优先减少原生冲突，其次控制既有本地模块的回归范围。
以上是实现约束，不能代替完成后的实际 diff、事务测试和部署验证。

## 优化方案

### 6. 页面与操作流程

#### 6.1 管理员：沿用现有客户账单

```text
账单对账 / 客户账单
客户：张客户          [下载账单 ▾] [2026-08 ▾]
账单状态：未确认      [生成待确认版本]

消费金额 | 退款金额 | 净费用 | 估算原价 | 估算优惠
折扣组合：组倍率 × 合同折扣 → 最终倍率
数据质量：已知信息 / 缺失信息 / 金额阻断问题
既有 API Key / 渠道分组、模型行和明细入口
```

```text
账单状态：待确认      生成时间：09-17 10:00
当前查看：待确认版本  [查看客户当前账单] [放弃草稿]

完整性校验：通过      金额核对：通过
解释信息缺失：输入用量 N 条、原价或优惠未知 M 条
[ ] 我已知悉上述缺失，确认时保留这些提示
[确认账单]

若来源变化：
此待确认版本已失效，来源数据发生变化。
[重新生成]           确认按钮不可用
```

```text
账单状态：已确认 v1   确认时间：09-17 11:00
[下载账单 ▾] [2026-08 ▾] [历史版本] [发起更正]

发起更正 → 填写客户可见原因、可选内部备注 → 后台生成
当前客户可见：v1      管理员预览：更正草稿

项目          v1        更正草稿       差异（新－旧）
消费金额      100.00     103.00         +3.00
退款金额       10.00      10.00          0.00
净费用         90.00      93.00         +3.00
质量信息      对比新增、消除、仍未知的项目
[查看变化明细] [确认更正版]

确认成功 → 发布 v2；v1 保留并标记“历史版本”
```

以上数值仅为交互示意，不是实际客户数据。更正版还应展示用量、折扣组合及解释变化；金额相同不代表没有更正。

#### 6.2 客户：沿用“我的账单”

```text
我的账单             [下载账单 ▾] [2026-08 ▾]
已确认 v2            确认时间：09-18 09:00
本次更正：补入已核实的漏记记录；净费用增加 3.00
[查看历史版本]

既有汇总、折扣、质量提示、分组与明细
所有下钻及下载均绑定当前所选版本

历史版本
v2  09-18 09:00  当前版本  [查看] [下载]
v1  09-17 11:00  历史版本  [查看] [下载]
```

客户不访问生成中的内容、待确认草稿或内部备注。历史版页面醒目标记“历史版本”，不能误认为当前应核对版本。
当月显示“本月进行中”；已结束但尚未确认显示“未确认，数据可能变化”。
初次草稿生成后，客户仍看实时账单；更正草稿生成失败或被放弃，不影响旧确认版。

#### 6.3 下载与列表

- “下载账单”继续放在月份控件前。已确认版本的汇总和明细下载带版本号、账期、确认时间、质量说明及公开更正原因。
- 未确认实时导出明确标记“未确认／生成时间”，不能伪装成正式版本。通用使用记录导出不冒充已确认账单明细。
- 草稿预览下载仅管理员可用并标记“待确认”，不得对客户发布。
- 更正说明可独立形成版本间差异文件；它是已有版本的派生物，不重新读原始日志。
- 现有客户月度列表增加确认状态与最新确认版本。已确认客户使用确认版金额，未确认客户使用实时金额；
  顶部总计明确注明“各客户当前展示账单合计”，并展示已确认/未确认数量，不能把混合结果标为全月已确认总额。
- 列表、详情、明细和下载返回实际选中的版本。一次列表请求先固定版本映射，再计算分页与总计，不能在同一响应中混入刚发布的新旧版本。
- 首期不增加批量确认，也不依赖打开全客户列表来生成单客户版本。

### 7. 版本状态与唯一权威

```text
客户＋月份（账单主记录）
  ├─ current_confirmed_version_id → 当前确认版，首次确认前为空
  └─ active_draft_id              → 至多一个活动草稿

草稿：排队 → 生成中 → 待确认 → 已确认
        └──────┴──────┬→ 失败 / 已取消 / 已失效
                     └→ 重新生成新的草稿 ID

已确认 v1 → 生成更正草稿 → 已确认 v2
  v1 的内容和确认事实不变；当前版指针原子切换到 v2
```

“历史版本”由是否为当前版判断，不需要修改旧版业务内容。“来源发生后续变化”也是单独状态信息，不能撤销已经发生的确认事实。
用户放弃、失败或清理草稿后不能复活同一草稿。正式版本号只在确认成功时分配，失败草稿不占正式版本号。
正文、明细、金额、公开原因、质量确认内容在确认后均不可编辑；补充或修正通过新版本表达。

建议主库持久化以下本地扩展事实。表和类型名称可调整，不要求每行都拆成独立抽象层；
不同事实可使用相似字段和局部代码，但同一版本的正式金额、确认状态、清单归属各有唯一权威记录：

| 模型 | 内容与约束 |
| --- | --- |
| 月账单主记录 | 稳定客户 ID、账期、时区、当前版、活动草稿、单调行版本；唯一键为客户＋账期 |
| 账单版本 | 草稿 ID、正式版本号、基于哪个确认版更正、状态、来源版本向量、生成与确认人/时间、公开原因和内部备注分列、质量知悉记录、汇总及维度投影、换算/格式/解析规则版本 |
| 版本明细 | 版本 ID＋稳定源记录身份唯一；客户字段白名单、最小管理维度、精确 quota、用量、折扣三态、费用解释与质量事实；保留稳定排序序号 |
| 版本产物清单 | 版本 ID、角色投影、语言/格式版本、分片、存储身份、对象引用、字节数/行数/内容摘要、上传状态、保留类别 |
| 账单操作审计 | 生成、失效、放弃、确认、更正及失败动作；操作人、请求幂等标识、原因与结果；只追加 |
| 来源修订记录 | 来源库内的稳定作用域、修订号及代际，服务第 10 节；不是资金账本 |

来源修订记录还需承载或关联来源保留状态（正常保留、已发生清理、尚未核实）与必要的维护代际。
这些是确认资格与恢复依据，不是另一套计费事实；优先放在本地修订/审计模型中，不为此另建通用维护平台。

主库维护正式版本、明细与授权的持久事实；OSS 保存其不可变下载产物。Redis 和进程缓存只能加速读取。
版本明细按 `version_id + sequence` 分页，按既有明细筛选所需稳定字段建最小索引，不保存原始 `other`、Task 私有数据或 Provider 响应。
保留客户级总览身份，同时保留各行真实 Key/app 归属；不得因客户按月汇总而泄露其他客户或不该公开的渠道字段。

采用主库明细投影是为了支持现有筛选、统计与分页，避免每页从 OSS 下载并解析整份文件。
该方案会新增存储和写入成本，必须纳入容量验证；若主库容量不满足要求，应另行评估带索引的不可变分片读取，
不能悄悄回退原日志分页，或只保存汇总而宣称明细已固化。

### 8. 复用计算与冻结内容

#### 8.1 同一稳定来源与同一计算口径，不强制单条流水线

```text
来源修订、依赖与维护代际覆盖整个生成窗口
  ├→ 既有汇总入口 / 已有累加函数 → 月汇总、两种维度、折扣、质量
  └→ 有界明细读取 / 既有 parser 与 evidence → 白名单版本明细
                         ↓
            校验同一范围、来源未变、金额与质量一致
                         ↓
              冻结版本事实 → 页面、统计和 CSV
```

正确性要求是各输出来自同一个可证明稳定的来源窗口，使用相同金额/退款/质量规则；不要求共享同一个内存对象、SQL 或完整执行循环。
当前 `GetBillingCustomerStatement` 将读取、分组、累加、名称装配和输出组织在一起，不能为了接收新输入，把整个函数拆成通用流式引擎。

优先按以下顺序评估，选择通过正确性和资源预算验证且原生 diff 最小的方式：

1. 在新增同包编排中直接调用既有汇总入口，再通过已有有界明细能力生成快照。两种维度和明细可采用固定、有限轮次读取，
   每轮都计入同一任务预算；依赖与修订必须覆盖所有轮次及其关联读取，在最后统一复验。不能分别生成几份仅净额相同的结果就认为一致。
2. 如果固定多轮读取超过目标环境预算，或无法在窄接线下覆盖依赖，再在新增版本模块中调用已有 parser、evidence、累加与 finalize 函数，
   允许重复少量分组容器、字段赋值和排序编排。不要复制原价公式、合同三态、退款恢复条件及舍入逻辑。
3. 只有上述方式均不能满足已验证需求，才对已有聚合器增加最小事实输入接线；说明无法直接调用的证据，
   原调用签名和实时行为尽量保持不变，不把整个导出与查询模块迁移到新框架。

有限多轮读取不是无限重扫的许可：若超过查询、证据、时间或内存预算，该方案不合格；不能牺牲核心业务换取较小代码 diff。
无论选择哪种方式，依赖修订必须在对应证据首次读取前取得；若旧入口不提供这个边界，只能补必要接线或采用另一种已验证方式，不能省略检查。
同一草稿只用一个解析规则版本；汇总不受页面筛选、当前页和导出数量影响，不循环调用交互分页接口。

#### 8.2 必须冻结的事实

- 客户稳定 ID、账期边界、时区、客户可见名称、Key/模型/组/合同的可用历史标识与展示标签。
- 消费、退款、净额的原始精确 quota；分项用量及其是否未知；逻辑调用、调整行、退款分类。
- 发生时有效组倍率、合同适用三态、合同倍率/版本及组合结果；缺失保持未知，不读取当前合同补齐。
- 估算原价和优惠的已验证计算结果、估算标识、未知原因；不将估算升级为实际折前金额。
- 可证明的费用表达式展示项，不重新执行历史计价或补造缺失数量。
- 本版本显示使用的 `QuotaPerUnit`、币种、汇率、精度及舍入规则。它们是版本显示口径，不能证明此前未记录的历史换算事实。
- 汇总和行级质量信息、核对结果与核对范围、来源依赖、字段/解析/格式版本。

继续沿用原价还原条件：有效组倍率、合同状态可证明、无不可拆分附加费等条件全部满足才还原；
用十进制逐行累计、在既有输出边界舍入；退款和负净额保留符号；工具费不参与模型折扣。
客户端不得重新计价。新增冻结明细的 quota/token 整数使用十进制字符串；金额格式化只按冻结换算参数执行整数运算、最终舍入八位小数，CSV 使用同样精度。
汇总仍复用原账单响应类型：页面对超出 JavaScript 安全整数范围的 quota 明确拒绝展示，不给出失真的金额；
该边界不代表已交付全站大整数响应迁移，精确 CSV 下载保持可用。跨不同换算版本的列表合计与更正差异由服务端提供 USD 十进制字符串。

客户当前余额不属于历史月账单冻结金额，若保留显示必须单列“当前余额”，不得冒充该月期末余额。
已冻结公开内容不会随当前客户名称、合同名称、币种配置或代码规则变化而重算；当前授权仍按当前身份重新校验。

### 9. 核对与确认门槛

| 分类 | 例子 | 处理 |
| --- | --- | --- |
| 金额/完整性阻断 | 源数据读取失败、扫描中断、缺分片、重复源身份、范围不完整、已知清理造成月内金额记录缺失、来源保留范围尚未核实、净额不一致、溢出、来源变化、无法证明生成过程一致 | 不进入可确认状态；不能人工勾选绕过 |
| 解释信息不足 | 原价或优惠未知、合同适用未知、历史输入语义缺失、计费模式未知，但已入账金额可完整核对 | 保留原提示；管理员明确知悉后可确认 |
| 范围之外未核验 | 是否有未落日志的上游调用、钱包流水完整性、供应商真实账单差异 | 明确说明不在自动校验结论内，不能标为已通过 |

确认前至少校验：

1. 明确完整账期、稳定来源范围及第 10.6 节来源保留状态，扫描正常结束；明细逐条写入成功，源身份唯一。
2. 消费合计－退款合计＝净额；明细、客户汇总、两种管理维度与折扣组合的净额一致。
3. 用量按原有口径处理调整和退款，不能拿日志行数强行等同调用次数；所有质量计数同源。
4. 估算值保留既有舍入规则；导出既有结果，不通过逐行显示值相加改变正式汇总。
5. CSV 行数、净额、分片清单与快照一致；导出含父行/总计时明确记录类型，不能重复加总。
6. 产物完整且可读，数据库和对象摘要一致；来源修订及规则版本仍符合第 10 节。
7. 当前管理员有权限，确认请求指向具体草稿、基准确认版与质量报告。

“未知计费方式”本身不等于金额错误；明确发生的部分退款可以如实计入净额，不能因为解释无法恢复就改写退款金额。
质量确认必须绑定该草稿和报告摘要，不能继承旧草稿的一次勾选。确认后保存具体知悉内容、操作人和时间。
若发现真实漏单或扣款错误，先通过受授权的已有事实/资金处理流程解决；本功能不提供金额编辑入口。

### 10. 来源变化与一致性：实施前置门槛

#### 10.1 不能采用的替代证明

账期结束时间、`MAX(id)`、行数、净额、最近更新时间、Redis TTL 或一次全量内容 hash，均不能单独证明
“生成后直至确认提交，没有影响账单的数据变化”。即使前后净额相同，也可能发生两条互相抵消的改动。
生成文件的摘要只证明产物内容，不证明来源仍有效。

必须同时解决：生成期间一致、确认前未变化、检查与确认提交之间没有竞争窗口。
在可靠机制未完成时，只能继续现有未确认实时查询/临时导出，不能开放正式确认或降级跳过校验。

#### 10.2 推荐候选：来源库内的事务修订记录

在真正拥有数据的数据库内，为影响账单的写入同步更新修订记录；业务行变化与相应修订递增必须处于同一事务。
记录修订号及数据库代际，防止恢复备份或重新初始化后修订号重复导致旧草稿误通过。
生成前后读取依赖的版本向量，不变才能进入待确认；发生任何相关修订就使草稿失效，不能靠结果巧合相同继续确认。

依赖与失效范围至少覆盖：

| 来源 | 必须捕获的变化 | 建议作用域 |
| --- | --- | --- |
| 月内消费/退款日志 | 新增、补录、修改、删除、批量清理；修改客户/时间归属时旧新作用域都递增 | 客户＋自然月 |
| 历史退款唯一性候选 | 增删改同客户/Key 下参与预扣关联判定的任意历史退款，包含账期外记录及候选数量跨过预算 | 客户＋Key 的退款证据作用域 |
| 引用的原预扣日志 | 原扣金额、身份、快照修改或删除；之前缺失的引用后来出现 | 来源身份或明确覆盖它的证据作用域 |
| Task 计费证据 | 相关冻结事实新增、修改、删除；缺失变为存在、唯一变为歧义 | 客户＋应用/Key＋Task 业务身份 |
| 显示参数与标签 | 生成使用的换算、名称等来源变化 | 对应配置/实体修订，或生成时冻结且明确其采集时点 |
| 解析规则与数据库恢复 | 账单语义升级、来源库重建或恢复 | 规则版本、数据代际 |

生成时保存实际依赖，同时覆盖“未找到”的查询作用域；仅记录查到的行无法发现后来补入的证据。
动态发现的证据依赖必须在第一次读取证据前取得修订号，结束时统一复验；不能先读证据再登记其“初始版本”。
当前合同价格不作为历史计价依赖，不因为合同配置改变而重新解释历史折扣。
名称类非金额字段可以按生成时点冻结，不把确认动作解释成“名称仍与当前配置相同”；必须在字段合同中明确，避免无谓失效。

不得用一个全站修订号使任何消费都使所有草稿失效，也不得每次写入遍历该客户所有历史月份。
跨月退款证据可以保守失效相关草稿，但应量化活跃客户被反复失效的概率。
普通消费路径需要的修订写入、索引和事务成本必须实测；不能为了对账持有长事务或长期暂停核心业务。

#### 10.3 确认提交的原子边界

**同一事务数据库的候选实现**：确认事务先参与第 10.7 节维护控制，再锁定月账单主记录与依赖修订行，检查草稿版本向量、有效性、基准确认版、权限及完整性结果，
然后原子写入确认事实、操作审计并切换当前版指针。源写入必须遵循相同修订/锁协议，不能先无保护地改数据再异步补修订。
对象上传、原始数据扫描、全量 hash 计算不得放入确认事务。

SQLite、MySQL、PostgreSQL 分别验证。标准行锁使用 `lockForUpdate`；SQLite 不能把该 helper 跳过行锁理解为已有同等并发保护，
必须通过写事务串行化与条件更新验证竞争行为，且仅有限次重试，不长时间占用写锁。
唯一客户月份行配合条件更新管理活动草稿，避免依赖数据库特有的局部唯一索引或进程锁。

**主库与日志库分离的候选实现**：各自维护本地事务修订，生成使用跨来源版本向量；
确认需要经过验证的跨来源写入协调/短时围栏，确保最后检查到主库确认提交之间相关写入无法穿过。
依次查询两个修订号后直接提交主库，不满足此保证；`SystemTask` 租约也不是来源写入围栏。
跨库方案必须明确锁顺序、锁丢失、网络中断、确认结果未知、恢复与核心写入延迟上界，不能假设一个 GORM 事务覆盖两个数据库。

本次讨论尚未验证跨库原子机制，**它是待解决的技术阻断项**。实施第一步必须通过原型给出结论：
若只能证明同一事务数据库可安全确认，则仅在经过验证的部署拓扑启用，分库部署保持实时账单并明确不支持确认；
第 10.5 节据此给出本轮同库支持的工程限制；必须在交付说明中披露分库尚不支持，不能据此宣称跨库需求完成。

#### 10.4 备选与取舍

| 候选 | 收益 | 代价与不足 |
| --- | --- | --- |
| 来源本地事务修订＋确认围栏（推荐研究方向） | 检查成本随依赖作用域变化，避免每次确认重扫整月 | 必须覆盖所有写入口；分库确认协议、热路径事务成本需要验证 |
| 数据库变更序列/CDC＋提交屏障 | 可以捕获较底层变更，减少应用写入口遗漏 | 三数据库及部署差异大，有额外基础设施；异步追上水位仍不等于确认无竞争窗口 |
| 每次确认前全量重扫比较 | 可用于独立复核、排查修订遗漏 | 扫描成本高，比较后仍有竞争窗口，不能单独作为正式方案 |

实施第一步产出写入口清单、依赖清单、并发证明和压力数据后再固定最终机制，不预先把候选写成已实现架构。
维护脚本、数据导入、清理和人工 SQL 也必须纳入协议。应用内自动清理应在持久化边界参与事务修订；
离线脚本和人工 SQL 按第 10.7 节进入维护状态、阻止已经进入执行的确认、结束后更新代际并使旧草稿失效。
只把入口开关改成关闭不构成维护屏障。数据库运维权限与维护流程必须配合，不能用“管理员会注意”替代约束。
日志原本是否完整仍是独立边界：修订机制不能追回启用前已经丢失的消费或证明从未落库的调用。

#### 10.5 代码核对结论与机制选型分析（2026-09-17 实施前）

2026-09-17 对工作区的聚合入口、读取链路、导出基础设施、主要来源持久化入口和数据库拓扑做只读核对。
以下区分已查到的代码事实与拟采用的接入方式；不把现有调用点清单当成“所有写入已经覆盖”的证明。
完整覆盖需要实施时逐项追踪并通过测试验证，真实三数据库与故障注入尚未验收。

**账单读取与导出复用面（已有能力与必要接线）**

- 单客户月账单聚合入口 `model.GetBillingCustomerStatement`（billing_reconciliation.go）已有汇总、分组、折扣组合与质量输出；还接收分组/模型/计费模式筛选。正式整月生成不传明细筛选，并遵循第 2 节的包含式终点转换。
- `scanBillingStatementFacts` 已有有限 ID 上界、keyset 500 行/批和批级超时；关系数据库批次使用 `buildBillingStatementRefundEvidence`，ClickHouse 分支使用 `loadBillingStatementRefundEvidence`。复用 parser 和 evidence 的业务语义，增加依赖修订采集及冻结输出的必要接线；现有 reader 尚不能原样提供一致性快照。
- SystemTask 继续负责已有调度/租约底座；版本生成可以有自己的本地 handler 和短循环，允许与导出有少量编排重复。
  不复制基础调度系统、不把所有 Job 强制改成通用接口。不同任务类型必须显式共用第 11.2 节资源预算，不能各有一个“全站唯一”读取器。
- `writeCustomerExportSummaryCsv` 已接受 `BillingCustomerStatement` 参数，可复用其纯制表部分；其上层导出流程仍会调用 `GetBillingCustomerStatement` 查询来源。
  版本产物应把冻结汇总传给该制表函数，复用 `BuildCustomerExportRows` 的明细投影语义，不调用会重新扫描来源的整段导出编排。
- 关键限制：现有 `data_version = period.EndTimestamp`（controller/billing_reconciliation.go 响应包装器），只是账期月末时间戳，**无任何固化语义**；`CustomerExportLogUpperBound` 注释已明确否认其版本语义。版本固化必须新建实体，不能复用这两个字段。

**修订记录表位置分析（用户要求认真分析的决策点）**

**首期限定经过验证的同库部署，修订表放主库。** 这是范围内的最小方案，不是认定“修订表放其他库在理论上不可行”。

1. `LOG_DB == DB` 表示当前程序使用同一 GORM 数据库句柄，已有 Task 日志交付和 Batch 结算在该分支使用传入的 `tx`。
   SQLite、MySQL、PostgreSQL 都可能采用这种部署；不能把“同库”等同于 SQLite，也不能凭数据库类型或 DSN 字符串相同判定事务共享。
2. **同库不等于同事务。** 当前 `createLog` 直接执行 `LOG_DB.Create`；在另一处调用 `DB.Update` 递增修订，即使两者指向同一库也不原子。
   必须让日志写入和修订实际使用同一个 `tx`，批量写入与现有事务内写入同样如此。
3. 分库时，关系型日志库中的日志与放在该日志库的修订，仍然可以在日志库内同事务提交；Task 证据与主库修订也可在主库内同事务提交。
   两个来源各自拥有修订不违反“单一权威”，因为它们描述不同来源。困难是如何在确认主库版本时同时保证两个来源未变化，不能用两个本地事务假装一个跨库事务。
4. 账单关联 Task 时按用户、应用/Key、Task 业务身份及其他冻结身份验证，依赖特定表达式/单位快照；
   不因此把订阅、钱包或所有 Task 资金状态都纳入账单版本依赖。原预扣关联还会读取日志库的原扣与历史退款候选，应分别列出依赖。
5. 同库首期让版本、日志、关联证据与修订可以共用一套本地事务，不增加跨库协调实现。
   未来若支持分库，应重新设计来源本地修订与确认协议；当前不预先建设 CDC、双写或通用分布式锁框架。

同库支持必须在写入口覆盖、并发、维护切换、故障和压力验证后才能启用，不能仅凭表位置或 `LOG_DB == DB` 宣称原子性成立。

**来源写入口盘点（修订机制必须接入的写入口，按作用域分组）**

调用方多不等于必须逐个修改。首先按实际落库位置收敛，区分“需要覆盖”与“需要编辑”：

| 入口类别 | 最小接入位置 | 禁止扩大为 |
| --- | --- | --- |
| `RecordConsumeLog` / `RecordTaskBillingLog` 等经 `createLog` 新增日志 | 在 `createLog` 保留必要的窄接线，主体放新文件；同一个日志事务内更新相关修订 | 在 text_quota、WSS/Audio、violation_fee、各 Provider 或退款服务调用处重复加修订 |
| `DeliverTaskBillingLog`、`CompleteBatchSettlement` 等直接使用现有 `tx` 写日志 | 在原插入事务内调用账单修订逻辑，保留现有插入和幂等判断；只有确实更小才改用已有写入器 | 另开事务、改变资金提交顺序、在幂等命中时重复新增日志 |
| Task 身份及账单实际读取的冻结证据 | 按 reader 依赖列出字段，优先在现有模型写入边界覆盖新增、修改、删除和身份迁移 | 把所有 quota、轮询进度、结果 URL、非账单私有字段更新都视为账单变化 |
| `DeleteOldLogBatch` 应用内清理 | 有界批次内确定删除集合、更新修订和保留状态并删除同一集合 | 要求管理员每次手工关开关，或重写整个清理调度器 |
| 离线修复脚本、人工 SQL | 使用第 10.7 节维护协议；若转为在线受支持修改，再接入明确的模型事务入口 | 建设通用 SQL 拦截、自动纠错或新资金账本 |

Task 通用写入可能携带账单字段，即使调用意图只是更新状态，也必须证明不会覆盖旧证据；不能仅凭函数名豁免。
反之，明确只更新非依赖列的入口不应引入修订写入。身份修改时覆盖旧新作用域，业务身份重复与不存在的查询也必须保护。
持久化逻辑应接收并使用真实事务，禁止 helper 内部回到全局 `DB` 导致脱离调用方事务。
GORM callback 也不能被假定覆盖原始 SQL、批量更新、删改条件和维护脚本；是否使用取决于可证明的覆盖与改动成本，不作为默认新框架。

集中入口是优先选项，不是必须重构成的新统一层。若某条现有事务内直接插入只需一个本地修订调用，而改走统一写入器会重排现有事务，
则允许保留直接插入及少量相似接线；二者必须使用同一 `tx`，修订语义调用同一规则。不能为了“所有写入只有一个函数”扩大资金路径修改。
每个确需修改的原生文件须记录：为何需要该处接线而无法仅新增文件完成、最窄接线点、事务及失败语义、上游同步冲突面和回归测试。
修订机制只跟踪账单来源变化，不修复旧资金多步流程的原子性，也不能用“修订兜底”声称资金已与日志原子一致。
修订失败不得被吞掉后仍允许确认；也不得为此新增自动退款或改变已有资金结果。实施原型必须验证失败传播和恢复失效策略，
尤其当前普通日志写入失败只记录错误，不能因新增修订故障扩大日志丢失却继续宣称完整。

**重要边界**：`common.LogConsumeEnabled=false` 可令普通消费日志路径跳过写入；Task 交付的 `event.SuppressLog` 是另一条明确的跳过条件，
不能混写成所有记录函数都接收 SuppressLog。修订机制不能假设“扣费必有日志”，也不能追回从未持久化的调用。
这不允许忽略已经知道的日志关闭区间、丢失故障或清理缺口；已知影响所选月份金额完整性的问题按第 9、10.6 节阻止确认。

**分库拓扑结论（10.3 跨库阻断项的落地判断）**

- 主库 model.DB（SQL_DSN），日志库 model.LOG_DB（LOG_SQL_DSN 为空时 LOG_DB=DB）。logs 表在日志库；tasks/quota_data/subscriptions/task_billing_deliveries 在主库。
- `common.UsingLogDatabase`/`UsingMainDatabase` 区分数据库类型，不单独证明两个句柄共享事务。首期复用现有 `LOG_DB == DB` 的保守判断，不扩展 DSN 猜测。
- `DeliverTaskBillingLog` 使用 `task-billing:<taskRowID>:<event>`；`CompleteBatchSettlement` 使用 Batch job ID 并按日志类型核对。二者不能被描述成同一幂等键，也不能用幂等投递推导跨库原子确认。
- **同库是候选可支持拓扑，完成全部前置验收后才能启用。** 分库下本地日志写入是否有事务由实际代码决定；缺失的是与主库版本发布协调的保证。
  首期分库拒绝新增生成/确认，保留实时查询和已经存在的正式版本读取。这是首期交付限制，必须明确披露，不能宣称完整支持分库。
- 开关打开、同库判断成立只是必要条件；还需迁移、来源覆盖、维护门槛、完整性及读路径接入完成。不得把它们简化为一个布尔表达式就是“安全证明”。

**能力开关（用户确认：要，运行时开关，默认关）**

- 新增主库 Option 键（如 `BillingStatementVersionEnabled`），布尔字符串，默认 `false`。管理端设置页可切换（“账单计费”分组）。
- 开关控制生成、确认、更正的写能力；现有正式版本读取不受影响。入口可提前拒绝，但最终确认仍在数据库事务内校验开关和维护状态，不能仅依赖进程缓存。
- 关闭与确认必须通过第 10.7 节共同控制点建立先后关系。关闭成功后，之前已进入接口但尚未正式提交的请求也不得越过关闭边界发布。
- 不允许关闭开关就停止修订跟踪、重新开启后继续确认旧草稿。普通关闭后若持续跟踪且来源未变可按原规则重新核验；
  维护或任何跟踪中断必须变更代际、使此前草稿失效，恢复覆盖后才可重新生成。

#### 10.6 日志清理后的来源完整性与更正

**修订号回答“是否变化”，保留状态回答“当前来源是否仍足够重建该月”。这两个判断不能互相替代。**
例如 v1 有 100 条消费，保留策略删掉其中 80 条，再从剩余 20 条生成草稿：新修订号可以稳定，20 条明细与汇总也可以完全一致，
但它仍不是完整的该月账单。不能把减少的 80 条自动解释为业务退款或账单更正。

| 场景 | 行为 |
| --- | --- |
| 原日志清理后查看已确认版 | 继续读取冻结事实，金额和下载不变 |
| 已发生月内金额记录清理后首次生成或生成更正版 | 阻止生成可确认版本，说明受影响范围，要求恢复并核验完整来源 |
| 草稿生成中或待确认后清理了相关来源 | 递增修订，草稿失效；不能只重新采集修订号而沿用原草稿 |
| 清理不相关客户/月份且没有跨期证据依赖 | 不应让该草稿无谓失效；可保守判定时须说明范围与成本 |
| 仅跨期解释证据被清理，月内金额记录仍完整 | 重新生成并按现有 evidence 保持未知，作为解释缺失知悉；不能虚构原价，也不把这种情况等同于月内金额缺失 |
| 经过核实的业务纠错删除，例如删除证实重复的日志 | 记录纠错原因和修订，按完整纠错后的事实生成；不能与无业务冲正含义的保留清理混为一谈 |

首期采取以下最小规则：

1. 应用内清理在执行前取得有界批次的实际源身份及必要作用域，在同一事务内更新相关修订、记录清理影响并删除该集合。
   受影响字段包括客户/月份及实际需要的跨期证据作用域；候选集合与真正删除集合必须一致，不能先统计一批后用宽条件删另一批。
   不要求逐条复制待删日志或读取每条完整正文；可用保守时间范围标记，但不得漏掉受影响账期。
2. 清理影响必须能识别“这个客户该月曾有记录但现已清空”。不能因为日志查询为空或重新生成修订行，就恢复成“从未消费”的零账单。
   保留状态与修订应持久化，不能跟随临时任务记录或原日志一起过期。
3. 生成开始、进入待确认和最终确认都核验保留状态与代际；任一环节发现已知金额来源缺口即阻止发布。
   如果来源已被清理，质量信息中的“解释未知可知悉”不能用来豁免这个金额完整性问题。
4. 功能启用前的历史保留范围必须有迁移/部署核验记录。无记录表示尚未核实，不能默认“历史从未清理”。
   可使用可验证的完整备份、保留/清理记录及已有金额记录核对建立可用范围；不能只比较当前表的 count/sum 或勾选声明。
   该核验仅针对已持久化来源的保留完整性，不宣称证明从未落日志的调用不存在。
5. 首期不实现“旧确认版＋当前剩余日志＋新增日志”自动拼接。旧版是解释投影，不保证保存所有原始关联证据，
   直接拼接还可能重复计费、遗漏修改或错误处理删除。来源不足时保留旧确认版可读，明确暂停更正。
6. 恢复必须通过第 10.7 节维护协议，核验范围、唯一身份、金额及关联证据后，记录恢复依据、更新代际并重新生成。
   恢复本身不触发资金操作，不删除已确认版本，也不能未经验证直接清除“来源不完整”标记。

因此，“已确认版本长期可查”与“任何时候都能从原始日志重新生成”是不同能力。本方案保证前者；后者依赖完整可用来源，
界面应在更正受阻时明确原因，不能显示笼统的生成失败或返回缩水后的账单。

#### 10.7 开关、维护与正在执行的确认

**入口拒绝只阻止新请求，不能撤回已经进入服务层的确认。** 举例：确认请求先通过开关检查，管理员随后关闭开关并运行修复脚本，
原请求最后仍可能用旧校验结果提交。单靠前端禁用按钮、进程内布尔值、SystemTask 租约或等待若干秒都不能消除该竞争。

首期同库采用以下待验证协议，协调范围仅限账单发布，不持有覆盖维护全程的数据库长事务：

1. 在主库定义一个账单维护控制记录，可由修订模型的专用维护作用域承载，记录维护状态与单调代际。
   产品开关仍以 Option 为配置权威；维护状态表达正在执行的操作，不建立另一套独立可配置的启用政策。
2. 最终确认事务与“关闭/进入维护”操作共同锁定该控制记录，遵循一致的锁顺序，再读取主库中的开关及维护状态。
   确认只在允许发布且草稿代际匹配时继续锁月账单与依赖修订并提交。SQLite 必须通过实际写事务/CAS 实现等效顺序，不能靠被跳过的行锁。
3. 如果确认先取得控制权并提交，随后关闭成功，则该版本属于关闭之前的合法发布；如果关闭先提交，后续取得控制权的确认必须拒绝。
   **对外返回“已关闭”时必须已经建立这个边界**。旧请求即使入口已放行，也不能在该边界之后提交。
   不要求关闭回滚此前已合法确认的账单。
4. 离线维护先关闭写能力并持久化“维护中”和新代际；成功后才允许脚本/人工 SQL 开始写。
   已经生成的旧草稿因此失效；正在生成的旧任务在批次/发布检查时退出，不能覆盖控制状态或发布新草稿。
   不必等慢上传自然结束才开始维护，但必须证明旧执行器失去所有发布权限。
5. 脚本结束后核验来源保留范围、数据和修订接入状态，再更新完成代际、退出维护；恢复开关是后续显式动作，不自动打开。
   维护中断、脚本报错或重启时，持久的维护状态继续禁止生成与确认；超时不自动解除。
6. 应用内 `DeleteOldLogBatch` 不走人工离线流程：它使用第 10.6 节批次事务与相同修订锁协议，
   删除先提交则确认发现变化并拒绝；确认先提交则删除不影响已冻结版本。正常自动清理不依赖管理员配合关开关。
7. 控制记录只在短时确认/开关切换期间锁定，不包住日志扫描、OSS 上传或整个维护过程。
   核心消费写入不需要争用这个全局维护锁；它继续在自身持久化事务维护实际来源作用域的修订。

所有 Option 更新入口，包括通用设置接口，对这个开关键都必须遵循同一操作边界；不得绕过专用控制逻辑直接写 Option。
具体接线放本地账单文件，通用设置入口仅保留必要分支，不重构整套设置系统。开关与维护状态缓存只作提前拒绝，最终发布以主库事务为准。
如果没有能力证明正在执行的确认已受控，维护开始必须失败；不能提示关闭成功后依赖人工估算“请求应该结束了”。

以上只保护账单确认相对于维护写入的顺序，不使离线 SQL 具备业务正确性，也不声称源修订已经覆盖全部写入口。
灰度期间所有旧应用实例、绕过维护协议的脚本和直接数据库写权限都需纳入部署检查；不可控的旧写入仍存在时不启用确认。

### 11. 后台生成、资源保护与失败处理

#### 11.1 执行顺序

1. 受理时校验管理员、客户稳定身份、已结束月份、存储能力及已核实的来源保留范围；通过开关/维护检查后原子占用该客户月份的活动草稿位置。
2. 冻结生成参数、基准确认版与规则版本，取得来源依赖的初始版本和维护代际，进入既有后台执行体系。
3. 按第 8.1 节选定方式，通过唯一游标分批读取整月结算范围及所需证据，写入草稿明细并使用已有计算规则生成汇总和质量信息；
   如采用固定多轮读取，来源依赖、代际与总预算覆盖全部轮次，不强制为一次扫描重构原聚合器。
4. 从该草稿事实生成所需客户/管理投影与文件。对象名预先记录到 staged 清单，上传使用唯一且不覆盖旧版的键。
5. 完成数量、金额、产物、来源保留状态及修订/代际复验；全部通过后进入待确认。来源被清理或维护使代际失效时明确标记原因，不提供正式下载。
6. 管理员确认时执行第 10 节的原子校验与发布，包括事务内开关/维护校验；重复相同请求返回同一确认结果，不再次生成版本。

源读取期间的批次事务要短；后台写入草稿也分批提交，不能把十万行作为一个大事务。
半成品由状态隔离而非大事务保护，只有完整校验后的快照才能进入待确认。
进程重启可发现持久草稿与执行任务；首期建议中断生成后明确失败、重新生成新草稿，避免未经证明的跨来源断点续算。
不能由新执行器接管后继续混用旧执行器产生的事实；租约过期的执行器不得发布产物。

#### 11.2 共用资源上限，允许独立业务编排

- 直接使用 SystemTask、keyset/CSV/对象存储能力；账单版本事实与长期产物属于账单模块，不使用业务 Task。
  本次选择复用 `CustomerExportJob` 的内部执行队列，增加明确的 `statement_version` 类型；它只承载执行权与共享资源占用，
  不承载正式版本、正式文件或长期保留权威。普通导出列表不展示该内部任务，临时导出 TTL 不清理版本事实与正式产物。
  这一选择替代“独立版本 handler 再协调槽位”，避免第二个客户草稿丢失执行机会，也避免新增通用资源调度器。
- 正式账单生成与普通导出的原始数据读取使用同一全局资源预算，不因为新增任务类型而各开一个重扫描槽。
- 建议首期全站 1 个源读取执行槽、2 个等待位置，账单生成和源数据导出合计计算；同客户月份至多一个活动草稿。
- 初始候选参数沿用已有 500～1,000 行批次、单批 5 秒、任务 10 分钟、排队 30 分钟；
  这些是待测起点，按最坏两个前序任务约 20 分钟推导排队空间，必须包含切换开销并独立验证故障场景。
- 超过预算明确失败，不输出截断账单；批次大小与超时联动调节，不能把 1,000 行/5 秒当成部署必然吞吐。
- 限速衡量扫描候选行及关联证据读取，不只统计最终写出行；退款证据有界加载，不能每批重复执行相同全历史扫描而不计成本。
- 当前导出具有文件/字节预算，正式账单需单独核算数据库明细、临时磁盘、对象分片和并发上传预算。
- 已确认版本下载、分页及小汇总制表使用独立轻量限流，不排在十分钟源数据任务后。
  大规模重建 CSV 虽不读日志，仍需对快照库读取、CPU、磁盘和 OSS 带宽限流。
- 不设 100,000 条产品硬上限；至少验证 100,001 条，并在目标环境建立明确的容量范围。超过资源预算时完整失败，不截断。

异步和独立连接池都不能消除数据库 CPU、IO、锁竞争。监控核心请求/结算延迟、连接池等待、数据库查询耗时、
扫描/写入速率、草稿失效率、队列等待和对象上传失败；压力升高优先延缓或停止账单生成。
阈值以目标环境基线确定，本方案不编造生产 SLA。

**共享预算的实际改动边界**：当前 `CustomerExportSlot` 与导出 Job 的认领、释放、失败恢复绑定，
不能只把版本 ID 写入 `job_id` 就认为已完成复用，也不能为版本生成再复制三个位子而把总容量翻倍。
实施原型优先在现有本地槽位能力附近增加仅面向这两类任务的拥有者识别和占用/释放接线，使两类任务使用唯一容量权威。
确需执行租约协调时也只增加这两类源读取的必要控制，不扩展 SystemTask 为通用多资源调度器。
具体保留或扩展现有槽位结构，应根据失败恢复与调用点核对决定，不能未经验证直接改表或再引入一套竞争计数。

两类任务可以分别维护业务排队状态、进度、错误与清理，只有受理总容量、源读取互斥及租约失效约束必须协调。
调度顺序需避免普通导出或版本生成长期饥饿；不要求为此统一各自的状态机、返回类型或保留策略。
验收要同时检查受理满额、取消、排队超时、崩溃恢复及过期执行器，不能只证明正常情况下不会同时执行。

### 12. 长期保存与下载

1. 正式账单使用独立私有命名空间，例如 `billing/statements`，直接调用现有存储运行时、后端和凭据。
   可在账单专属文件中重复少量上传编排与清单字段组装，不调用绑定导出 Job 及其 TTL 的整段上传流程，也不为此重构全部 artifact store。
2. 每个草稿对象先登记预期键，再上传；进入待确认后已经完整可读。确认只改变保留类别并发布引用，不依赖确认后复制文件成功。
3. 清理与确认共用状态/条件更新保护：清理先把失效草稿标记为清理中，使其无法确认，才删除对象与草稿明细。
   有效待确认草稿不被通用 TTL 偷偷清理；正式版本及其必要产物永不进入临时导出删除集合。
4. OSS 与数据库无跨系统事务，必须依靠 staged 清单、唯一对象键、可重试清理和完整性检查处理崩溃。
   删除对象失败保留引用，不先删记录制造无法追踪的孤儿。
5. 正式版对象缺失时明确报告文件不可用并告警；可以从同一冻结版本重建同口径产物，不重新扫描原日志“补一个看起来相同的版本”。
   若版本事实自身损坏，仅允许从已校验备份恢复或报告不可用，不能静默重算。
6. 文件名含月份和正式版本号；下载前鉴权，签发短时 URL，不持久化或日志输出完整签名 URL。
7. 对象摘要证明内容完整，不能代替访问控制。客户文件只含客户白名单，不能把管理字段藏在同一个下载文件里。
8. 存储身份变化不能静默指向新桶同名对象。迁移须验证行数、摘要、权限和引用切换，保留失败可恢复能力。
9. 正式数据与对象纳入备份、恢复演练和容量告警；部署侧桶生命周期也必须排除正式命名空间，单改应用 TTL 不够。

待确认时尚无确认时间和正式版本号，不能预先伪造这些字段。生成阶段的基础 CSV 绑定不可变快照 ID，
确认后由数据库提供正式版本号、确认时间和公开说明，下载文件名使用正式版本号，并提供与快照 ID 绑定的确认说明文件。
若要求把确认信息直接写入 CSV 表头，则在确认后从冻结快照生成该格式的派生文件；生成失败只影响这份文件下载，
不回退实时查询、不修改确认内容。确认前必须完整可读的是基础事实和已校验基础产物，不能把尚未生成的正式格式标为下载就绪。

长期保留不等于宣称存储系统永不丢失。需验证数据库、对象和清单可配套恢复，以及恢复后旧草稿的代际失效。
用户/Key/渠道删除不级联删除历史账单；当前客户失去登录权限后不能继续下载，管理员按既有历史客户权限查看。

### 13. 查询接口与前后端落点

继续使用现有自助和管理员查询入口，通过本地账单服务选择来源：

```text
请求未指定版本
  ├─ 有当前确认版 → 读取该版本
  └─ 无当前确认版 → 现有实时查询

请求明确版本 → 校验归属、状态、角色 → 读取该版本
管理员明确草稿 → 校验管理员权限 → 读取草稿
```

版本不存在、无权限或存储损坏时返回明确错误，不回退实时数据。客户即使猜到草稿 ID 也不能访问。
普通用户身份从认证上下文取得；管理员选择显式客户 ID；版本必须属于该客户与月份，不信任客户端传来的状态或金额。
历史查看、明细分页、统计、缓存键、导出和下载全程携带版本 ID。页面并发加载时，先解析一次实际版本，再锁定其他请求，
避免管理员发布新版时汇总为 v1、明细为 v2。实时查询缓存和版本缓存分开，发布仅失效“当前版本指针”相关缓存。

在现有账单路由模块中增加生成草稿、查询生成进度、确认、放弃、历史版本和版本差异动作。
沿用后台鉴权与写入保护；确认输入只接受草稿标识、基准版本、幂等键、原因/知悉内容等，不接受客户端金额或校验结论。
具体 URL/DTO 在实施时统一设计，本方案不发布未经实现验证的公共 API。

| 落点 | 最小改动 |
| --- | --- |
| `model/` 新增账单版本文件 | 主记录、版本/明细/清单/审计/修订及事务；不把正式版本塞进普通导出状态 |
| 现有账单 reader、聚合器 | 优先直接调用；仅在依赖采集或已验证资源预算要求下补窄接线，不默认拆解为新引擎 |
| `service/` 新增账单版本编排 | 允许少量独立循环/组装；调用既有计费语义、CSV 制表和存储原语，独立管理正式版本生命周期 |
| `controller/` 与既有账单路由 | 新增版本动作、原查询选择来源；不扩展上游对账 |
| 现有 `CustomerStatementView` / 明细页 | 状态、操作、预览、历史版和差异展示；金额仍来自服务端 |
| i18n | 实施时按项目 skill 补齐全部语言，本次文本图不是已交付 UI |
| 原生日志及关联写入入口 | 仅在完成修订机制评估后接入必要的窄调用；列清必要性、事务语义和上游合并影响 |

`data_version` 不继续承担两种含义。新增字段明确区分正式账单版本、来源修订和生成时间；旧字段的兼容策略需检查现有调用方，不能静默改义。
当前账单解析规则升级只影响实时数据和新草稿；已确认版本继续读取冻结结果，不用新版 parser 重解释。

#### 13.1 修改预算与验收证据

实施前形成简短修改表，每个已有文件写清：文件来源（上游/本地扩展）、当前入口、确需修改原因、
可新增文件的主体逻辑、必要接线、保留行为、事务与失败测试、上游合并影响。按以下边界审查实际 diff：

| 边界 | 默认要求 |
| --- | --- |
| Provider、relay、扣款/退款算法、表达式引擎 | 不改；不能以版本修订为由重新实现或整理计费链 |
| 日志新增、已有关联证据写入、清理、设置保存、模型注册与路由 | 允许可证明必要的窄接线，主体放新增文件，禁止顺手重命名和重排 |
| 既有本地账单/导出扩展 | 保留公开行为，只增加必要版本选择、依赖采集和资源协调；不要求所有路径迁移 |
| 新增版本文件 | 可以局部重复，保持直观函数和领域命名，不创建仅为合并重复而存在的框架层 |
| 前端账单主体 | 增加小组件与版本参数接线；避免为了新字符串型精确值改写全站金额类型或旧 API |

“窄接线”以语义范围衡量，不是强制每个修改点恰好一行。把大段逻辑压成一行或藏入有隐式副作用的 callback 不算减少侵入。
在有既定事务的入口加入修订虽可能只改一行，仍可能改变失败传播和锁竞争；必须单独测试，不能凭行数宣称低风险。

不设置凭空的文件数/行数硬指标。复用若导致原生改动扩大，应明确比较“新增文件保留局部重复”的方案，
仅在正确性、既有接口或目标环境预算无法满足时扩大改动。代码重复量不作为拒绝实现的理由，新的独立计费规则或无协调事实源才是问题。

### 14. 验收矩阵

| 场景 | 必须证明的结果 |
| --- | --- |
| 当月、未来月份生成请求 | 服务端拒绝；不能通过改客户端日期绕过 |
| 不同客户同月 | 可独立确认，当前版互不影响 |
| 同客户月份并发生成/确认 | 只有一个活动草稿；一次确认事实及正式版本；幂等重试不重复发布 |
| 来源在扫描期间变化 | 草稿失效，不发布混合时间截面 |
| 来源在待确认后或最终检查与提交间变化 | 确认与源写入按协议有明确先后；不能把确认前的变化漏过去 |
| 新增/修改/删除、改客户或账期、批量清理 | 正确失效旧新作用域，覆盖零行月份后来补入数据 |
| 跨期原扣、退款唯一性与 Task 证据变化 | 对依赖账单失效；包括之前没有查到的记录后来出现 |
| 来源恢复备份、规则部署切换 | 旧草稿失效；已确认版本可继续读取，不能误认修订号相同 |
| 金额一致但明细缺失/重复 | 阻止确认，不只核对一个净额 |
| 历史解释未知 | 原提示保留、质量知悉可追溯；不补造合同倍率、Token 或原价 |
| 实际退款及零金额用量调整 | 符号、账期和调用次数正确；不重复计请求 |
| 非默认换算、超安全整数 | 页面、汇总、明细、CSV 一致，无硬编码换算或浮点丢精度 |
| 更正版金额不变、解释改善 | 可以解释变更并保留两版，不要求必须有金额差才能更正 |
| 发布 v2 的同时查询 v1 | 一次页面会话/下载引用始终一致；v1 可继续按显式版本访问 |
| 原日志清理、当前价格/合同变化 | 已确认页面、明细、统计和下载不读原始来源且结果不变 |
| 确认 v1 后清理月内金额记录，再发起更正 | v1 保持可读；阻止从残缺来源发布 v2，即使剩余行的汇总与明细一致 |
| 全月被清空、功能启用前保留范围未知 | 不误生成零账单；缺少来源保留核验不能视为正常完整 |
| 仅跨期解释证据被清理 | 月内金额完整时可以重新生成，缺失解释保持未知并重新知悉 |
| 恢复来源或业务纠错删除 | 恢复有核验与代际变化；合法纠错与保留清理可区分，不自动拼接旧版与残留日志 |
| 已放行确认与关开关/进入维护并发 | 建立明确提交先后；关闭成功边界后旧请求不能继续发布 |
| 维护脚本失败、控制进程重启、旧 worker 恢复 | 维护状态不因超时解除，旧代际不能发布，已有正式版本可读 |
| 开关关闭期间写来源，再重新开启 | 不漏修订；若跟踪中断则更新代际并使旧草稿失效 |
| 应用清理与确认并发 | 清理和修订/保留标记同事务；确认要么先提交旧版，要么拒绝已变化草稿 |
| 集中日志入口、直接事务插入、批量修改及 Task 依赖字段更新 | 全部实际来源变更被覆盖；非依赖字段更新不无谓失效，资金结果和原幂等行为不变 |
| 保留局部重复的版本编排 | 与实时账单同输入核对金额、用量、质量与 CSV，重点覆盖组/合同、退款、未知和舍入；不写只断言函数结构的测试 |
| 有限多轮读取方案 | 中间任一相关来源变化均使草稿失效；全部轮次计入资源预算，不漏统计证据扫描成本 |
| 普通导出与版本生成共享容量 | 总受理容量和执行并发不翻倍，失败/取消后配额可恢复，旧执行器不能继续读或发布 |
| 原生改动清单 | 每个改动有必要性与事务证据，无为消除重复产生的无关抽取、接口扩展、移动或格式化 |
| 修订写入故障、旧实例未接入 | 不允许无可靠跟踪继续确认；不能新增自动退款或用日志打印代替故障处理 |
| 对象上传失败、进程崩溃、租约丢失、取消 | 无部分版本发布；staged 引用可追踪并最终清理 |
| 草稿清理与确认并发 | 不能发布正在删除的版本；正式引用不被导出清理误删 |
| 客户越权、管理员降权、已删除客户、草稿 ID 猜测 | 重鉴权生效，无对象键/内部备注/渠道隐私泄露 |
| SQLite/MySQL/PostgreSQL | 迁移、唯一约束、并发和失败恢复均在真实数据库验证，不能仅靠 SQLite 单测宣称兼容 |
| 主库/日志库分离 | 通过真实故障注入证明确认协议；未通过则明确禁用该拓扑确认能力 |
| ClickHouse | 现有导出唯一游标未验收，首期不启用正式版本生成，不能伪造唯一 ID |
| 100,001 条、稀疏筛选、重退款证据、同时普通导出 | 无截断；量化数据库/核心业务压力、等待、磁盘、存储和失败预算 |
| 长期存储恢复 | 旧版本、精确金额、历史说明、权限和对象清单配套恢复 |

真实备份回归使用只读快照或独立测试库，不在备份源上迁移或写入正式账单。固定同一输入截面核对实时结果与草稿结果，
确认后修改测试来源再验证快照不变。所有并发测试应断言最终事实，不用随机循环、睡眠或只打印耗时替代正确性证明。

### 15. 实施顺序、风险与交付边界

1. **先证明来源机制**：盘点日志、Task、预扣证据、清理/脚本写入口和数据库拓扑；完成候选机制、跨库边界及热路径成本原型。

2. **再建立版本持久化**：迁移、角色字段白名单、精确数值、活动草稿唯一性、审计与来源依赖。
3. **接入后台生成**：按第 8.1 节选择最小改动的读取与聚合方式，直接调用可用的 CSV/存储能力，允许独立业务编排；补齐一致性校验、共享资源预算与失败恢复。
4. **实现确认、更正及保留**：原子发布、差异、幂等、历史读取；完成清理后更正阻断、维护竞争和存储恢复测试。
5. **优化现有页面与接口**：两端统一版本选择，列表/汇总/明细/下载保持一致，补齐 i18n 和权限测试。

本轮可以交付步骤 1—4 的后端实现，但不能在步骤 5 的现有查询、明细、导出全部绑定版本之前向真实客户开放确认。

本方案不会把“功能已编码”“本地测试通过”“真实部署验收通过”合并为一个结论。实施后的事实收敛与归档仍按 docs 治理流程另行完成。

#### 16.2 历史来源的明确核验入口

没有保留记录等于 unknown，不再默认视为 intact。只有已核验的 intact/none 基线可受理可确认草稿；
解释信息未知的知悉按钮不能绕过这一来源门槛。

Root 可在完成真实备份、保留清单及关联证据核验后调用：

```text
POST /api/billing/admin/customer-statement-source-verification
     ?user_id=<客户ID>&start_timestamp=<自然月起点>&end_timestamp=<包含式月末>

{"status":"intact","evidence":"备份/保留清单标识、核验范围、核验结论"}
```

确认为该范围无历史结算记录时使用 `none`。该入口登记人工核验依据并推进维护代际，使先前草稿重新生成；
不会自动修补日志、改变余额或把 count/sum 相等当作完整性证明。恢复 partial 必须先按维护协议恢复并核验来源，
不能仅为解锁按钮调用此接口。此入口不是新的客户业务页面，也不是“管理员随手勾选即可认定完整”。

本地真实备份仅作只读检查：月记录、版本记录、版本明细三表均为 0 行；未对备份执行迁移、写入或确认。
因此本次没有给该备份补造保留基线。新增唯一索引不会自动合并重复月份；部署已有重复月份或旧试验投影时，
必须先离线核验，不自动删除、更改或兼容解读正式金额。
