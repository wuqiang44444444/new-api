# Task退款取证索引补齐与链路验证

## 问题与目标

账单退款取证在 `billing_statement_refund_facts.go` 读取 Task 快照时出现 743.056 ms 慢查询，
返回 19 行。补齐该查询的主库索引，验证既有退款分类、身份隔离、金额与读写事务语义不变。
此前日志表退款筛选和任务轮询优化各有独立范围，不能据此宣称整条账单取证链路已完成性能验收。

## 当前实际情况

- 本地业务库只读核验：此前两个日志索引及任务轮询索引已存在；Task 查询只有相关单列索引。
- 项目 Go SQLite 驱动为 SQLite 3.50.4。同形查询抽样返回 19 行，执行计划使用
  `idx_tasks_app_id(app_id=?)`，所选用户/应用作用域有 2,205 条任务；数据库没有 `sqlite_stat1`。
- 抽样耗时约 2—3 ms，未重现 743 ms。原慢日志没有参数，不能声称抽样就是原来的 19 条。
  GORM 计时包括连接获取、执行及结果扫描/反序列化；当时各部分贡献没有取证，不能全部归因于索引。
- 查询已按用户/应用隔离、ID 去重、每批 200 条，并在打开日志游标前完成补证；无需改动这些规则。

## 优化方案与实现

1. 新增独立索引描述 `model/billing_statement_task_index.go`，创建非唯一联合索引
   `idx_tasks_user_app_task(user_id, app_id, task_id)`；通过 GORM 创建已有列的索引，不对描述类型
   执行 AutoMigrate，不改变 Task 字段、默认值、原有索引或历史快照。
2. 接入本地扩展 `migrateBillingReconciliationDB`，沿用主节点启动迁移入口。迁移只依赖主库，
   已存在时跳过；失败沿启动错误路径返回，不在请求期建索引或隐藏错误。
3. 保留退款取证 SQL、列投影、冻结快照优先级和金额算法。重复任务仍可写入，身份不匹配、
   证据缺失或歧义仍保持未知；不加缓存、强制索引、截断历史、自动 ANALYZE 或提高慢查询阈值。
4. 回归直接捕获生产 Task 查询并检查 SQLite 计划同时使用三个条件；比较迁移前后的完整账单、
   明细、导出及原始记录。201 个任务覆盖跨批次补证，另验证跨用户同 ID、重复事实、事务回滚、
   取消与持有读游标时并发提交。既有身份隔离及主/日志分库失败回归在新索引下继续执行。
5. CI 复用已有 MySQL/PostgreSQL 测试服务，通过既有隔离数据库夹具运行两种账单索引回归；
   每项测试创建并删除独立测试数据库，不修改连接配置指定数据库的业务表。

### 最小入侵说明

生产代码仅新增索引文件并在本地账单迁移函数接线，不修改 NEWAPI 原生 Task、主库启动文件、
Relay、Provider 或计费写路径。CI 仅在既有后端作业追加一个测试步骤；上游同步需保留该步骤，
未调整原有构建、服务和测试配置。

### 验证与剩余验收

本轮通过以下验证：

| 验证 | 结果与边界 |
| --- | --- |
| Task 退款索引、历史退款分类、身份隔离与分库读取定向回归 | SQLite 通过；实际补证查询的计划包含 `user_id=? AND app_id=? AND task_id=?` |
| `go test ./model -run '^TestBillingStatement(TaskIndex\|LogIndex)' -count=1` | MySQL 8.0、PostgreSQL 16 通过；覆盖两种索引迁移、账单及并发读写 |
| `go test ./model ./middleware ./controller ./service ./relay/...` | 全部通过；首轮沙箱禁止监听本机 HTTP/Redis 测试端口，在允许本地测试服务的环境重跑通过 |
| `go vet ./model ./middleware ./controller ./service ./relay/...` / `go build ./...` | 通过 |
| `task docs:check` / `task ai:check` | 通过 |

三库均验证 Task 索引迁移幂等、迁移前后完整账单/明细/导出与原始记录一致、跨 200 条边界补证、
同 ID 跨用户隔离、重复身份继续可写且分类保持未知、更新回滚、取消及持有读游标时并发提交。
SQL 执行计划断言限于 SQLite；不强制 MySQL/PostgreSQL 在小数据集选择某个计划。
外部数据库使用本轮创建的无业务挂载、仅回环端口临时容器，每项测试新建隔离数据库；已清理临时容器。

本轮不重启在用服务、不直接给业务库建索引；部署新版本后，由主节点初始化执行迁移。首次 DDL
应按部署流程备份并安排受控窗口，避免其它节点并发迁移；上线后核对实际索引及执行计划，
并观察账单、写入延迟、锁等待和慢查询。SQLite 首次建索引仍有写入阻塞与磁盘开销。

本地三库回归不能代替最低支持版本及生产峰值负载验收，索引也不保证所有请求恒小于 200 ms。
若索引就绪后仍有慢查询，应继续拆分连接池等待、数据库执行、结果扫描和快照解码耗时，
不得把未复现的 743 ms 标记为已定位或以增大阈值隐藏。

## 后续读写平衡调整

首轮新增索引方案已由[索引读写平衡优化与验证](2026-09-19-索引读写平衡优化与验证.md)中的替换方案
更新：当前目标为非唯一 `idx_tasks_task_user_app(task_id,user_id,app_id)`，替换原 Task ID 单列索引，
而不是额外保留一棵用户/应用/任务索引。旧方案已部署时由迁移清理；全部查询条件与业务语义不变。
本文件前文记录的是首轮实现和当时验证，不代表最终索引集合。
