# 评审剩余项修复与本地基础设施验收

## 问题与目标

继续十份 2026-09-17 方案的剩余修复，保持 NEWAPI 原生代码最小入侵。用户授权使用本地环境及本地
SMTP、对象存储配置；配置只读，合成测试不写现有客户账本，不启动真实收费 Provider 生成。
本记录补充各原方案的验收跟踪，不能替代逐渠道、业务图像效果或生产灰度验收。

## 当前实际情况

### 本轮修复

| 问题 | 最小修复 | 证据 |
| --- | --- | --- |
| PostgreSQL 的修订递增 UPSERT 报字段歧义，正常来源被标记不完整 | 使用 GORM 列表达式限定目标表的 revision；保留原事务与故障围栏 | 真实 PostgreSQL 复现后，同组账单回归通过；MySQL 同组通过 |
| 小时报告一次性保留所有事件、片段和邮件正文 | 单次 SQL 游标读取；私有、打开后立即取消目录链接的临时文件暂存；按批渲染及逐卷事务发布 | 601 条跨批次记录逐项核对；重复 request_id 不去重，窗口右端排除，序号连续，正文不超过 48 KiB |
| 暂存读取中途失败可能导致部分发布 | 所有分卷和投递行继续在一个事务提交，迭代读取失败整体回滚 | 首卷写入后注入读取错误，分卷和投递行均为零，重建后 ready；整卷缺失的提前 EOF 也不能当作完成 |
| building 报告在进程退出后无法恢复 | 复用已存在报告行，不重新插入同一窗口；发布继续由原行锁串行化 | 模拟 building 落库后退出，重启生成 ready 并推进下一窗口，只有一份报告 |
| 已有 building 报告生成再次失败时未写失败状态 | 不再在报告已存在时提前退出失败记录 | 既有报告正确变为 failed，下一轮可重建 |
| MySQL 存量 TEXT 迁移缺少真实验证 | 增加隔离数据库迁移回归，不修改生产迁移流程 | 旧投影保留、重复迁移成功、三个字段可完整写回超过 64 KiB 文本 |

本轮生产代码修改全部位于账单/报告本地扩展文件，没有增加 NEWAPI 原生文件接线，没有改变资金算法、
Provider adapter、重试或退款语义。临时文件不是持久状态；最终事实仍是原报告、分卷与投递表。

### 有界生成合同

- 错误源使用一次有序 SELECT，不使用翻页重查，因此不会因迟到插入改变已读取集合；ClickHouse 同排序键
  的行全部保留，不推断唯一性。渠道名称在关闭源游标后按 500 个 ID 读取，支持主日志同库且仅一个连接。
- 明细按最多 200 条或约 1 MiB 源记录一批渲染；单条序列化上限 8 MiB，摘要每维最多 10,000 个分组、
  文本键累计上限 4 MiB，源快照与分卷临时文件合计上限 256 MiB，单窗口生成/发布期限 2 分钟。
- 超预算或取消明确失败；不抽样、不截断、不推进窗口、不发布半份报告。预算为工程初值，超限窗口需排查
  数据规模并调整实现预算后复验，不能通过删除错误记录解锁。临时文件关闭或进程退出后由操作系统释放。
- 所有分卷总数确定后才包装最终主题与 HTML；发布逐卷读取临时文件，既有 ready 报告不可重写。
  性能摘要读取同样受 context 与分组上限约束；失败显示统计数据不足，不伪造全站成功率。

### 本地验收结果

环境为 macOS arm64、Apple M5。数据库为无业务挂载、仅绑定回环端口的临时 MySQL 8.0 和 PostgreSQL 16
容器；每个账单/报告测试另建随机数据库并清理。普通本地库仅作为只读配置来源。

| 验证 | 结果与边界 |
| --- | --- |
| MySQL / PostgreSQL 账单回归 | 通过：同月并发受理、来源变化与确认阻止、修订故障保存点、精确证据依赖、大投影及冻结读取等；不等于最低支持版本与生产负载验收 |
| 两库报告并发领取 | 通过：四个并发 worker 只领取两个地址各自的首卷，不重复领取、不越过同地址前卷 |
| 三库轮询闸门 | SQLite、MySQL、PostgreSQL 的真实状态边界回归通过；不代替生产数据分布的查询计划和延迟观察 |
| 本地配置的真实 Azure Blob | 上传、HEAD、鉴权读取、签名读取、删除及删除后不存在确认通过；只操作随机测试对象 |
| 真实导出文件 | 1,440,000 字节含中文 CSV 经文件上传、带中文文件名签名下载后逐字节一致，测试对象删除及不存在核对通过；完整轮次约 98.7 秒 |
| 本地配置的真实 SMTP | 返回 535 认证拒绝，邮件未发出；未修改 SMTP 配置。需更新本地账号/授权码后复测，不能宣称邮箱投递通过 |
| ClickHouse | 官方 24.8 镜像下载超过 15 分钟仍未完成，已停止本轮下载；保留显式 opt-in 回归入口，未宣称真实 ClickHouse 通过 |
| 后端回归 | model/service/controller/router/clienterrlog/common 全包通过；新增预算与迁移另作定向回归 |

真实导出下载曾在 30 秒、90 秒预算下超时；90 秒时收到 1,310,028 / 1,440,000 字节。最后使用
150 秒下载预算完成核对（仅调整验收测试，不改变生产下载期限），证明本次内容完整但不证明网络吞吐达标。
测试清理均使用独立 context，只操作本次随机对象。

报告基准使用每条约 420 字节合成详情、20 个渠道，动态生成源记录、逐卷消费结果，没有在测试中保留整个
源切片或报告正文。独立测试进程（不含 Go 编译器）的单次测量如下：

| 事件量 | 分卷 | 渲染与暂存时间 | 进程峰值 RSS | 累计分配 |
| --- | --- | --- | --- | --- |
| 1,000 | 16 | 约 34 ms | 59,162,624 字节 | 约 19.9 MB |
| 10,000 | 151 | 约 372 ms | 62,390,272 字节 | 约 194.0 MB |

累计分配仍随记录量增长，文件序列化增加了 CPU 与临时 IO；不把累计分配当作峰值，也不把本机合成基准
扩大为数据库扫描、发布事务、SMTP 吞吐或任意单条大小的容量保证。

### 可复现入口

- 默认 `go test` 跳过真实基础设施；必须显式启用。
- 隔离服务库：设置 `TEST_BILLING_STATEMENT_DIALECT=mysql|postgres` 与
  `TEST_BILLING_STATEMENT_DSN`，执行 `go test ./model -run 'Test(BillingStatement|AcquireDraft|Confirm|ErrorReportServerContract)' -count=1`。
  fixture 只允许回环地址，创建/删除随机测试数据库，不迁移 DSN 指定的已有数据库。
- ClickHouse：`TEST_ERROR_REPORT_CLICKHOUSE_DSN` 指定本机隔离容器，执行
  `go test ./model -run '^TestErrorReportClickHouseDuplicateKeys$' -count=1`；同样创建随机数据库。
- 本地 SMTP/OSS：`RUN_LOCAL_ACCEPTANCE=1` 与 `LOCAL_ACCEPTANCE_DB_PATH` 指向只读配置库，运行
  `TestLocalInfrastructureAcceptance`。SMTP 收件人仅为配置的发件人本人；内容明确标记合成验收。
  对象存储只清理本次随机命名对象；测试不输出凭据、完整签名 URL 或原始上游正文。
- 容量：`go test ./service -run '^$' -bench '^BenchmarkErrorReportWindowCapacity$' -benchtime=1x`；
  RSS 单独构建测试程序后使用系统进程资源统计测量，不把编译器进程计入。

## 优化方案与剩余事项

1. ClickHouse 镜像就绪后执行独立日志库回归；当前未完成，不能用 SQL/SQLite 测试代替。
2. SMTP 认证配置更新后，复测服务器接受、收件箱到达及真实客户端多卷展示；535 是当前实际阻塞。
3. 账单开关保持默认关闭。目标部署仍需多实例灰度、恢复演练、真实来源保留基线核验及主请求/结算延迟验收；
   本地真实数据库验证只覆盖代码合同，不代替生产放行。最低支持的 MySQL 5.7.8、PostgreSQL 9.6 未实测。
4. 渠道失败、未知结果和未测组合保持原记录；没有新增收费渠道/预算授权，不重发已知未知结果。
   门窗替换等业务视觉目标需原始输出与明确视觉标准，HTTP 200 不能代替该验收。
5. 错误日志仍是已登记应用内采集范围；进程崩溃/队列丢弃、WSS 等原方案明确未接入项不通过本轮报告改造
   冒充已覆盖，不新增持久投递框架或历史原文批量改写。

本轮最终检查：后端六包完整回归通过，后续改动的报告/迁移定向回归通过；`go build ./...`、
`go vet ./model ./service`、`task docs:check`、`task ai:check`、`git diff --check` 通过。
本轮未修改前端或公开 API 合同；临时 MySQL/PostgreSQL 容器在验收后移除，不修改本地配置与客户账本。
