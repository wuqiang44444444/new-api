# 图片视频自动检查与配置失败诊断优化方案

## 1. 问题与目标

用户提供渠道 `Funcloud-Seedream-85折（#109）`、模型 `seedream-5.0-lite` 的渠道测试失败日志：
计划路径为 `POST /v1/chat/completions`，阶段为 `config`，原因为
`test_config_error · model_price_error`，显示耗时 `0.00s`，未记录上游 HTTP 状态。

本次目标是完成自动检查的成本控制与配置诊断改造：图片、视频自动检查不产生额外生成费用，同时保留清晰、
可操作的配置失败诊断，让管理员能够定位并修复问题。

### 1.1 用户确认的范围

- **不修改手工测试。** 保持现有手工单项、批量测试入口、请求、参数、收费行为、结果展示和日志行为；
  不新增确认步骤，不拆分或替换手工测试按钮，也不把本方案的自动检查限制套到手工测试。
- 最新运维确认：自动任务只执行无生成副作用的连接检查；早期允许文本自动真实测试的约定由第 6 节取代。
- 图片、视频不通过定时生成图片、视频或创建素材来判断健康。
- 配置失败必须显示，管理员能够据此查看具体问题；减少重复通知不等于隐藏失败。
- 已按后续授权实施第 3.6 节的前三步与评审修复；不修改生产配置、不触发真实 Provider 调用。

## 2. 初始评审事实

### 2.1 实施前已核对的代码事实

本表保留问题发现时的证据；修复后的行为以第 5 节为准。

| 事实 | 代码依据 | 含义 |
| --- | --- | --- |
| 通用渠道测试先调用 `ModelPriceHelper`，失败后返回 `model_price_error`，上游 `DoRequest` 在后面执行 | [channel-test.go](../../controller/channel-test.go) 的 `testChannel` | 本例在本地计费校验阶段停止，没有发送本次生成请求 |
| 价格错误包含未配置价格、表达式缺失或求值失败，以及其他计费准备失败 | [price.go](../../relay/helper/price.go) 的 `ModelPriceHelper`、`modelPriceHelperTiered` | 不能把 `model_price_error` 一律解释为价格未配置 |
| 默认路径为 Chat；类型化图片渠道等分支能够明确选择图片端点 | [channel-test.go](../../controller/channel-test.go) 的 `normalizeChannelTestEndpoint`、`testChannel` | 日志中的路径是本地构造路径，不证明已发出上游请求 |
| 仓库已有 `seedream-5.0-lite` 图片测试样例 | [channel_test_image_profile.go](../../controller/channel_test_image_profile.go) | 本例选择 Chat 值得核对，但不能仅凭渠道名确定生产渠道类型或协议 |
| 后台通用健康检查调用真实测试；除 Seedance 分支外，失败后也会更新渠道响应时间 | [channel-test.go](../../controller/channel-test.go) 的 `testChannelForHealthCheck` | 自动图片检查可能产生真实生成费用；本地失败耗时也可能覆盖渠道延迟 |
| 后台测试错误进入通用自动禁用判断 | [channel-test.go](../../controller/channel-test.go)、[channel.go](../../service/channel.go) 的 `ShouldDisableChannel` | 配置错误是否触发禁用取决于现有状态码、关键词及渠道设置，不能断言本例已被禁用 |
| Seedance 自动检查只使用已登记的素材只读探针，不创建收费视频或素材，不据此更新视频渠道启停和延迟 | [channel_seedance_link_health.go](../../controller/channel_seedance_link_health.go) | 素材控制面结果不能代表视频生成能力；探针不可用目前仍进入失败记录 |
| 渠道测试失败事件保留阶段、原因和公共错误码，没有保存具体价格失败诊断 | [channel_test_error_event.go](../../service/channel_test_error_event.go) | 管理员仅看本条日志不能知道应修复哪个价格字段 |
| 部分价格错误由普通 `fmt.Errorf` 构造，没有稳定的业务错误类型或标识 | [price.go](../../relay/helper/price.go) | 错误链可解包不等于可以可靠细分全部失败原因 |
| 后台事件 Detail 使用字段白名单，并限制字段数量与值长度 | [backend.go](../../clienterrlog/backend.go) 的 `sanitizedBackendDetail` | 可复用现有存储，但仅添加 map 字段会被过滤，需同步扩展受控采集与展示 |
| 渠道测试没有上游状态时统一展示“未记录上游 HTTP 状态” | [error-log-status.tsx](../../web/src/features/usage-logs/error/components/error-log-status.tsx) | 无法直接区分未发送、已发送但未取得响应和状态未采集 |

日志详情的 `0.00s` 来自持久化事件实际耗时的格式化展示，不是上游延迟；手工测试接口另在
`localErr` 响应分支硬编码返回 `time: 0.0`，两者不能混淆。本方案只补充该事实，不修改手工行为。
已有 Request ID 是事件关联标识，不构成上游接收请求的证明。

### 2.2 未确认项与验证边界

- 未读取生产 #109 的 ChannelType、协议、模型映射、定价表达式与自动任务来源，无法确认具体配置根因。
  价格未配置、映射错位等均只是排查假设，现有日志不足以判断哪一种“大概率”成立。
- 未验证该 Provider 是否提供适用于图片生成凭据、确认无生成费用的只读检查接口；不得自行假定存在。
- 未调用真实 Provider，未验收真实生成、账单、外部数据库或生产灰度。
- 现有错误记录与性能采样不能直接拼接出渠道成功率，分母完整性未被证明。
- 当前事实边界参见[硬约束](../00-context/硬约束.md)、[API错误日志架构](../20-architecture/运维-API错误日志架构.md)
  和[图片渠道运维手册](../40-operations/03-图片渠道与异步任务运维手册.md)。

## 3. 优化方案

以下定义目标与验收口径；实施进度见第 5 节，不代表已经上线。所有行为调整限定在自动检查及其诊断展示范围。

### 3.1 自动检查分开表达三项事实

| 维度 | 数据来源 | 结果表达 | 证明范围 |
| --- | --- | --- | --- |
| 本地配置 | 现有协议注册、渠道配置、模型映射和计费校验 | 通过／失败／依赖前置项未检查 | 当前检查项及样例成立，不证明所有业务输入或上游可用 |
| 上游只读检查 | 代码登记、确认无生成费用且无资源创建副作用的接口 | 通过／失败／不支持／本次未执行 | 仅证明对应接口、凭据和操作的结果 |
| 最近业务生成 | 现有真实请求结果或持久化任务终态 | 最近成功／最近失败／暂无样本／近期未验证 | 历史实际生成事实，不承诺下一次一定成功 |

配置失败仍然是明确失败，不能合并为笼统的“跳过”。没有只读能力属于“不支持检查”，
不应伪装成 Provider 故障。页面不以单个绿色“健康”覆盖这三个不同范围的结论。

### 3.2 自动检查的执行与成本边界

1. 在自动执行入口确定检查种类，再决定是否发送网络请求；不能先调用共享真实生成流程后再屏蔽结果。
2. 保留既有文本自动探测路径及有界输出，不因普通渠道缺少模型能力声明而大面积停止自动测试；
   不要宣称仅输出 Token 上限即可严格封顶所有模型的总成本。
3. 图片、视频自动任务禁止调用生成 POST、创建素材或创建其他可能收费的资源；不使用“创建后立即取消”、
   故意发非法请求或空请求等方式假设不收费。
4. 仅使用已验证、由代码协议明确登记的只读接口，不猜测 URL，不将 GET 自动等同于免费。
   无适用接口时保留配置检查与业务结果观察，不退回 Chat 探测。
5. 只读接口成功只显示对应能力。例如素材列表成功不证明视频生成、视频凭据或指定模型可用。
6. 优先复用现有目标解析结果，在自动调用前拦截已识别的图片、视频生成目标，不另建一套模型能力表。
   专用 ChannelType、已登记协议、AdvancedCustom 明确端点声明属于配置事实；应覆盖 AsyncImage、
   Gemini/Vertex 图片分支、AdvancedCustom 多端点情况及既有 VolcEngine 图片分支。仅缺少能力声明
   不构成停止普通渠道 Chat 探测的理由；已有图片/视频信号而目标存在歧义时，明确显示需确认目标。
   `VolcEngine + seedream` 是既有名称启发式，不是显式能力声明；此类启发式仅可作为阻止自动生成的
   保守依据，不能用来新增 Link 身份、生成资格或发出生成请求。手工目标解析与调用行为保持不变。
7. 对已确认可复用同一只读检查结果的渠道级接口，避免按渠道内每个模型重复调用；不由共享结果推断
   所有模型均有权限或均可生成。

### 3.3 配置失败诊断

- 复用正式路径已有的配置、协议和价格校验，不新增第二套定价规则或模型能力表。
- 检查覆盖模型映射合法性、协议必填配置、已声明能力与测试样例的一致性、价格配置及必要计费输入。
  校验过程不预扣、不创建 Task/attempt、不调用生成接口。
- 可独立执行的本地检查一起展示；依赖无效协议、映射等前置项的检查标为“前置项失败，未检查”，
  不伪造下游错误，也不承诺一次发现全部问题。
- 保存受控原因码、中文/英文安全摘要和可确认的问题字段。例如区分价格未配置、表达式缺失、
  表达式求值失败、计费输入缺失；具体分类以正式校验能够提供的结构化事实为准。
- 优先按既有类型化错误或稳定标识分类。普通 `fmt.Errorf` 没有这些信息时，测试侧 wrapper 即使解包
  也不能自动还原业务类别；禁止靠匹配中英文文案或复制定价校验逻辑伪造结构化诊断。暂不能可靠细分的，
  明确显示“计费校验失败”，不猜测具体字段。需要精确细分时评估补充稳定错误标识的最小接线，说明原生
  文件修改必要性与上游冲突面，并保持原有外部错误码、文本和手工行为。不能同时预先承诺零原生修改和
  全部错误精确分类。
- 优先复用现有 Detail 存储，预期无需数据库迁移；新增字段必须同步纳入后台事件白名单，遵守数量、
  长度和脱敏限制，并验证保存与查询后的结果。管理入口由前端按受控配置项标识生成，不在日志中保存
  任意 URL。具体字段可用性不足时只提供能够确认的管理入口。
- 同时明确客户模型与实际定价对象，避免模型映射后仅凭一个模型字段引导管理员修改错误对象。
  不输出凭据、完整签名 URL、客户正文或上游原始响应。
- 自动检查日志记录检查对象、来源、时间、阶段和实际网络执行情况；无状态码不能直接推断未发送。
  明确在本地终止时显示“未发送上游请求：本地计费校验失败”。
- 最小执行事实应区分检查种类、是否尝试上游调用和是否取得响应，不能只增加含义模糊的“上游已执行”
  布尔值。进入 `DoRequest` 后仍可能在建立连接时失败；尝试调用不证明请求字节已发送，未取得响应
  也不证明 Provider 未受理。仅对发送前明确终止的路径声明“未发送”，不为此引入复杂状态机。

本例的拟议自动检查展示如下，具体原因必须来自真实校验，不能预填为“未配置价格”：

```text
配置检查：失败
渠道：Funcloud-Seedream-85折（#109）
模型：seedream-5.0-lite
失败项：计费配置
具体原因：<结构化校验返回的安全摘要>
上游请求：未发送
生成能力：本次未验证
处理入口：对应模型定价
```

### 3.4 配置失败与健康控制隔离

- 配置错误保持可见且计入配置检查失败，不计入上游调用失败或生成失败统计。
- 本地失败不覆盖上次有效上游延迟，不因通用状态码、关键词或本地执行时间进入上游故障自动禁用规则。
- 配置恢复只代表配置检查通过，不能据此自动恢复因真实上游故障而被禁用的渠道。
- 启停判断以检查种类及其证明范围为依据，不能仅看“尝试过上游调用”或无错误返回；只读接口通过
  不具备恢复生成渠道的资格。上游测量与本地检查耗时分开，进入调用但未取得响应不能显示成功响应延迟。
- 正式请求继续遵守现有校验与失败关闭语义，不以本方案放开未配置价格的模型。
- 不实施重复告警聚合、次数累计或新状态机。按第 6 节区分自动探测与业务错误，保留真实异常。

### 3.5 用真实业务结果补充生成证据

- 第一阶段优先展示最近成功时间、最近失败时间及受控原因，不急于引入健康评分或成功率。
- 同步图片采用有效生成响应与交付事实；异步图片、视频采用可信任务终态及已有交付状态。
  受理成功、取得任务 ID、HTTP 202、排队或轮询成功均不等于生成成功。
- 按实际 Channel、客户模型与操作范围展示；不把某个模型、某种操作成功扩展为整个渠道健康。
- 无近期有效样本时显示“近期未验证”，不能因长期没有请求自动判定故障，也不能无限期沿用历史成功。
- 连接、凭据、协议或映射变化后，旧记录保留为历史，不作为当前配置已验证的证据。
  实施时核对现有快照和修改事实能否建立关联；无法证明匹配时显示未验证，不为此引入 execution binding、
  内容 hash 证明或第二套公共合同。
- 若后续需要成功率，应先定义完整请求/任务样本、观察窗口、在途与未知结果口径，以及输入错误、
  内容审核和基础设施故障的分类；不可把所有失败都归咎于 Provider。

#### 被动发现的代价与通知边界

取消收费生成探针后，无合适只读接口的图片、视频渠道失去周期性验证生成能力的手段，故障可能直到
首个真实客户请求失败才暴露。低流量渠道可能长期缺少有效证据；该成本取舍必须在实施和运维说明中
显式呈现，不能将“配置通过”包装成同等强度的生成可用保证。

- 对已启用、配置通过但超过约定窗口仍无当前配置有效生成证据的渠道，可复用现有通知机制发送
  “长期未验证”提醒；窗口与去重口径实施前确定。缺少记录只表示缺少证据，不能直接解释为没有流量
  或渠道故障；提醒本身也不能恢复主动生成探针的检测能力。
- 对实际观察到的业务失败按具体失败类别通知；“连续失败”需要完整有序样本支持，没有足够证据时
  只报告观察到的失败事件。错误事件数量增加不等于失败率上升或 Provider 故障。
- “业务失败突增”需先明确观察窗口、样本完整性和比较基线。现有性能采样与错误事件不得拼接计算
  成功率，依据见 [error_report_render.go](../../service/error_report_render.go) 的统计边界。
- 通知复用既有机制并去重，在进入长期未验证、原因变化或取得新有效证据等有意义变化时更新，
  不在每次调度重复发送相同提醒。配置失败诊断始终保持可见。

### 3.6 最小实施顺序与代码边界

先通过实际错误和配置核实 #109 的根因；这属于独立排障，不凭概率猜测修改价格或映射，也不阻塞
以下自动检查改造。代码实施顺序如下：

1. 先阻断图片、视频自动检查中的生成副作用，保留既有文本自动测试及现有手工测试；覆盖所有现有
   图片目标分支，避免普通渠道因缺少能力声明而停止探测。
2. 完善自动配置检查及具体失败诊断，区分不支持只读检查与实际检查失败。
3. 修正自动检查的延迟写入和启停判断，并提供分项结果展示。
4. 在确认既有事实来源与配置关联后，增加最近业务生成结果和长期未验证提醒；重复告警聚合按已有
   日志机制最小扩展。该阶段不阻塞前面三个步骤的成本控制和正确性修复。

主体逻辑优先放在自动检查专属新增文件；原生自动入口仅保留必要窄接线，并说明上游合并冲突面。
共享校验可复用，但不得因此修改 `TestChannel`、手工测试对话框或手工日志语义。若共用日志组件需要
展示新字段，应仅针对明确标记为自动检查的事件生效，原有手工事件保持原行为。

## 4. 验证方案与剩余事项

### 4.1 待实施验收

- 使用本地模拟 Provider，验证图片、视频自动检查不会到达生成或资源创建接口；文本请求仍有输出上限。
- 覆盖 AsyncImage、Gemini/Vertex、VolcEngine 既有图片分支及 AdvancedCustom 单/多端点；普通渠道
  缺少能力声明不导致文本探测停摆，名称启发式不新增生成资格，手工解析结果保持不变。
- 配置缺失、非法映射及表达式错误按实际结构化证据诊断；无法可靠细分时显示计费校验失败，不误报
