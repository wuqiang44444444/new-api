# Seedance 插件迁移评审问题修复方案

## 1. 问题与目标

本文合并本轮代码质量审计与用户提供的专家评审，作为
[独立插件迁移方案](2026-09-09-Seedance独立插件迁移方案.md)的缺陷修复清单，
不替代该方案的架构职责与业务合同。首要目标仍是保持 NEWAPI 的扩展渠道设计，并降低后续同步上游的冲突与回归风险。

保持 `ChannelTypeSeedanceLink = 62`，由一个 `seedance-link` 插件承载 Provider 配置定义与南向差异；
Channel 继续保存实例值、模型映射和凭据，Go 宿主继续拥有鉴权、签名、资源、Task、资金和公共用量归一职责。

第 2 节保留首次评审快照，第 3—5 节为修复与验收要求；第 6—7 节记录后续实施及复审修复结果。
本轮没有激活生产候选、修改生产渠道、重写历史制品或发布。
修复不引入新插件平台、渠道账号表、公共状态机、原生路由资格或计费表达式体系。

## 3. 优化方案

### 3.1 唯一权威及修改边界

| 能力 | 保留权威 | 迁移或删除项 | 必须保留的消费者 |
| --- | --- | --- | --- |
| Provider 配置规则 | 固定版本的插件声明 | 组策略、凭据管理的旧 Go 映射与前端旧选项来源 | Go 固定宿主能力与资源安全规则 |
| 用量推导 | 既有 Go 公共归一语义 | 新制品只提供 Provider 字段定位；删除新增制品中的重复 completion/total/prompt 算法 | 历史制品和冻结 Task 按原合同履约，不重算既有资金事实 |
| 新视频创建 | 固定插件版本的转换 | 无调用旧创建函数及仅测试使用的生产校验表 | 仍有冻结身份依赖的历史查询、响应与内容处理 |
| 上游同步证据 | 保留双方变化的合并结果 | 不再以完整反向覆盖本地基线作为合并验收 | 已有配置合同局部重放与本机回归作为补充证据 |

优先修改 Link 专属新增文件。若确需再改原生文件，必须逐项写清必要性、最小接线点和同步影响，
禁止借修复整理原生目录、格式或无关功能。保留工作区已有账单、墨行模型、翻译等其他任务修改。

### 3.2 R1：恢复完整前端回归，并修正文档验证口径（F1、F8）

1. 旧表单测试接入现有 `seedance-plugin-fixture.ts`，从真实仓库制品取得声明。
2. 保留可读标签、视频/素材配对、飞彩 none、FunCloud 配对、渠道边界提示等可观察契约；
   根据声明检查对应选项，避免另抄一份完整 Provider 清单。不能只断言非空，也不能删除失败断言。
3. 在调用点核查后，将必须有声明才能工作的展示组件 `configuration` 改为必传；加载/失败状态由已有
   configured 父组件承担，不为测试增加旧表 fallback。修复后覆盖父组件真实加载到交互的路径。
4. 同步更新实施记录中的完整相关测试结果；分析文档明确标注实施前取证时点，并链接当前实施状态。
   原方案“当前基线”也要区分历史取证和实施进度，不改写当时的事实。

验收：4 个相关文件的原有 34 项全部通过，新增必要场景单独计数；声明缺失或请求失败仍阻止保存，
声明刷新不改变正在编辑的版本。涉及新增 UI 文案或 locale 时先遵循项目 i18n skill。

### 3.3 R2：补齐声明完整性（F2）

在 `pkg/jsplugin` 的 v2 编译边界统一完成以下校验，管理写事务继续复用编译后的声明：

- `listed`（含省略 modelPolicy 的现有语义）中的每个模型必须具备有效 `modelMetadata`。
- `configured` 允许未枚举的精确上游模型，因此必须有有效 `defaultModelMetadata`，已枚举模型可覆盖默认。
- 仅检查业务需要的自洽性：公开上下界、显式默认值与允许范围、已声明能力与必要字段；不增设模型名称推断。
- 缺少 metadata 不能在运行时补 Go 默认表，不能通过隐藏模型来代替发布拒绝。
- API v1 历史制品不强加 v2 声明；不得修改历史源码、自动补字段或将新版声明套到旧任务。

验证：分别覆盖 listed 缺少一个模型、configured 缺少默认、合法覆盖/默认、无效默认范围，以及
“候选拒绝→active 不变→渠道不变→公开模型列表不变”。已有配置事务测试夹具补齐合法声明，
不能让无效夹具继续被当作正常 v2 制品。先跑 jsplugin，再跑 model/publicmodel 的发布与投影测试。

### 3.4 R3：归一素材组和凭据管理决策（F3）

组策略：

- 远端 adapter 使用固定声明；托管 adapter 明确表达宿主的 hosted 语义，并在工厂入口核对声明与该能力一致。
- 删除 `seedanceAssetGroupPolicy` 的旧 Go 协议表回退；缺少合法策略应返回配置不可用，不能自动解释为 none。
- 默认组状态查询仅对明确的 none 表达“不适用”；其他协议按同一次固定声明/adapter 判断。
  插件缺失时明确失败，不能伪装为配置正常但不需要默认组。
- 不因 adapter 实现了 `GroupAdapter` 就重新推断业务能力；既有操作支持以声明与有限宿主能力为准。

凭据保护：

- `DeleteChannelAssetCredential` 在管理事务内按固定声明的凭据槽位判断，保留“正在使用独立 AK/SK 时不能删除”的行为。
- 与 Channel 保存、插件激活复用现有发布协调机制，先核对锁顺序，避免渠道锁与插件锁反向等待。
  声明无法读取时失败关闭；没有合法声明不能成为删除许可。
- 不改变凭据存储表、租户确认、默认组清除规则、审计和 Channel 实例值，不调用 Provider 删除资源。

验证：显式组原值优先、空白读默认、默认缺失稳定错误、none 忽略组、hosted 归属与不适用状态、插件缺失；
独立凭据在用拒删、不再使用时允许删除、配置发布/渠道修改与删除并发。SQLite 与一次性 MySQL/PostgreSQL
分别验证，禁止用生产数据库。协议声明若与宿主固定能力不可能匹配，应在编译/发布边界拒绝。

### 3.5 R4：收敛计费用量归一职责（F4）

先依据原方案 §4.2 和 `pkg/billingexpr/expr.md`，固定现有各协议的成功终态用量样例及最终整数 quota。
随后按以下顺序处理：

1. 保留 Go 公共归一算法作为唯一可维护推导入口；插件负责解开 Provider 包裹、定位获准字段和保留来源路径。
2. 在既有 Seedance hook 输出中设计最小、有限的候选事实结构，写清类型、数值范围、字段来源、缺失与无效状态。
   不能先丢弃非法 completion 再只交 total，否则会改变原有阻断语义；不得只传已经推导好的 completion。
3. 宿主校验候选事实后使用既有规则形成用量及证据，再进入原 Task/资金流程。
   官方协议与各第三方已有的字段选择、整数接受规则继续保持；不借公共归一之名改变原生 Provider 合同。
4. 删除新制品中重复的通用扫描/推导逻辑，保留 Provider 的包装和字段选择。不得建立新账本、表达式版本或价格配置。
5. 在实现前明确旧/新 hook 合同的版本判别。改变返回语义时必须显式版本化；新请求只走新合同，
   已冻结旧制品继续按原合同输出并履约。不能修改同版本源码、按字段存在性猜版本或失败后换实现。

验证必须包含：缺失、显式零、负值/溢出、无效 completion 阻断 total 回退、total 小于 prompt、
嵌套/字符串包装、来源路径、证据与用量的差别，以及各协议冻结输入下预扣、最终 quota 和差额等价。
原始旧制品恢复、插件切换中在途任务、unknown 保留 hold、重复失败退款幂等均须继续通过。

没有真实 Provider 证据时只报告样例等价，不将“算法统一”写成真实账单已核验。

### 3.6 R5：补齐 TokenSave 模式一致性（F5）

在现有 `decodeMediaPluginCreate` 的 hold 前边界，将南向 `input_mode`、`control_mode` 与宿主按北向
内容得到的计费模式比较；复用既有模式语义，不再新增一份内容分类表。保持时长、音频、分辨率和视频输入检查。

验证：纯文本、首帧、首尾帧、参考图片、参考音频/视频与已支持混合输入的合法转换全部通过；
构造只改变一个模式而其他字段不变的插件输出，必须在 attempt/hold 和 Provider POST 前拒绝。
验收观察实际无扣款、无发送，不仅断言私有辅助函数返回错误。

### 3.7 R6：删除无用途旧代码（F6）

在 R3/R4 活跃调用方迁移后，再核对 import、路由、CLI、测试、反射/注册及公开消费者：

- 删除 `video_upstream.go` 中无调用的 `convertVideoCreateRequest`。
- 将仅供等价测试的 `provider_mapped_validation_cmcc.go` 移入测试文件，或用真实插件测试替代后删除；
  不删除 CMCC 的字段拒绝、时长、分辨率和资金保护覆盖。
- 对 `ResolveAssetChannelCredential` 及私有 resolver 确认无外部消费者后删除；保留存储、掩码和删除保护。
- 逐个移除随上述函数失去用途的符号；不能按文件名批量删除。`modelSeedance20` 仍被计费入口使用，不能作为死常量删除。
- 保留仍有精确冻结消费者的历史查询、响应、内容与连接解释；退出依据是执行依赖，不是“已搬进 JS”。

本清单包含上一轮被自动审批拒绝而未执行的动作。文档记录不等于解除该阻止；实施时遵守当时适用的
授权与审批结果，不通过分拆命令、换目录或换工具绕过拒绝。每个根因的变更和回归证据应可独立审阅。

### 3.8 R7：完成真正的上游合并演练（F7）

遵循[上游代码合并指南](../30-engineering/上游代码合并指南.md)，在隔离工作树或临时仓库执行：

1. 记录目标上游、共同祖先、本地基线及本次修复后的补丁清单。只有使用已获取目标时，才可沿用 §2.1；
   不把旧目标称为最新上游。当前工作区的其他任务变更单独列明，不覆盖或混记为本次插件修改。
2. 保存可追溯的本地修改快照，在隔离环境以共同祖先做三方合并，保留目标上游的独立新增与修复。
   禁止先用 upstream→本地 HEAD 全量差异恢复成本地树，再把成功应用补丁当作合并验收。
3. 冲突逐项记录文件、符号、双方目的、解决方式及本地保留必要性；上游已提供的等价能力按项目白名单处理，
   不默认保留整份本地文件。复核上游独有变化确实存在于结果中。
4. 对实际合并结果运行原生相关回归、插件配置/协议/资金/历史任务回归、必要三库迁移检查及前端验证。
   记录未解决冲突和未覆盖边界，不用构建成功代替业务兼容。
5. 现有配置合同独立重放保留为局部证据；运行时重建脚本可明确标注其重建用途，但不再承担 U4 合并验收。

验收产物包括：固定提交、补丁/合并结果标识、依赖与原生修改清单、冲突清单、上游变化保留证据和测试结果。
只有这些产物齐备，才能将本轮目标上游的 U4 同步演练标为通过；不承诺未来任意上游版本零冲突。

## 4. 实施顺序与验证闸门

按 R1→R2→R3→R4→R5→R6→R7 推进，每个根因独立检查，F8 文档修正在开始时披露缺口、结束时更新结果。
本顺序不以优先级数字代替风险判断：R1 用于恢复可用验收基线，计费与发布问题未修复前不得关闭本次修复。

| 批次 | 最小验证 | 放行结果 |
| --- | --- | --- |
| R1 | 4 个相关前端文件、类型检查、改动文件 lint | 旧 34 项全部通过，失败场景仍有有效断言 |
| R2 | jsplugin、model、publicmodel 发布/投影测试 | 不完整声明拒绝发布，原 active 和模型可见性不变 |
| R3 | 素材服务、管理控制器、模型事务及三库并发 | 组策略/凭据许可单一来源，保护不被绕过 |

### 8.2 当前实际情况与修复

- **存量制品校验**：v2 制品在激活、配置读取、冻结版本恢复时都会经过当前编译器，严格元数据校验
  对不完整的旧自定义制品有回溯影响。现有 P0 盘点工具增加独立 `-check-plugin-artifacts` 模式，
  仅从只读 SQLite 快照读取全部 Seedance 制品（包括非 active、disabled），逐份编译并核对存储身份。
  输出版本、状态、源码摘要和脱敏诊断；任一不兼容即非零退出，不修改制品、激活标志、渠道或 Task。
  该模式检查全部已存版本以避免漏掉历史任务使用的停用版本，不读取 Task 私有数据。
- **激活诊断**：管理错误现在保留宿主生成的配置语义校验原因，例如 listed 模型缺元数据、默认时长
  超出声明上限。只允许专用校验错误类型通过诊断边界，校验消息不插入制品字段值；JavaScript 异常、
  源码和未知元数据字段仍返回通用提示。原来的候选可存、激活失败时 active/渠道/公开投影不变的
  回归继续保留，并增加脱敏检查。
- **孤儿转换器**：删除 `thirdparty.RelayCreateRequest` 及四个私有请求类型，保留仍被历史路径调用的

## 9. 2026-09-12 部署后自动使用最新内置插件

### 9.1 问题与目标

用户发现卡片仍显示 v1.0.1，要求当前及后续线上部署直接使用最新版，无需寻找手动激活入口。
只读核实本机 3501 网关实际打开的数据库：1.0.1 为 active；1.0.2、1.2.0、1.3.0 已入库但未激活。
运行程序包含当前 1.3.0 完整源码，其数据库制品与工作区逐字一致。原因是原 seeding 只插入新版；
当前代码已有“详情 → 版本历史 → 激活/回滚”，但旧默认要求部署后手动操作。

本节以用户最新要求替代此前“新版入库后保持旧版 active，等待手动激活”的部署行为。

### 9.2 当前实际情况与实施

- [内置同步](../../pkg/seedanceplugin/store.go)自动晋升更高的内置版本，兼容“制品已入库、未激活”场景；
  成功后才记录进程内完成标志，失败下轮可重试。
- [专属晋升事务](../../model/seedance_embedded_plugin.go)复用发布锁及现有渠道校验。语义版本比较覆盖
  1.9.0 → 1.10.0，旧部署节点不能回降新版。旧源码与精确版本保留；同版本源码冲突拒绝覆盖。
- [专属同步接线](../../controller/seedance_plugin_extension.go)在晋升后重新读取 active，避免调用方
  晋升前的快照让首次运行时继续使用旧版。晋升失败清除新请求入口，旧冻结任务仍可恢复。
- 不新增前端入口或重构原生插件功能。管理员仍可使用已有停用/回滚能力；同版本重启不重开显式停用。
  以后部署更高版本时自动启用新内置制品，不按上传时间盲目选择任意候选版本。

本机已通过同一 `EnsureSeeded` / 晋升事务完成切换，返回 active_version=1.3.0、api_version=3、
enabled=true。没有直接修改 active SQL、绕过渠道校验、删除旧制品或改写 Task。旧进程通过原有同步
轮询读取新 active；自动晋升的 Go 实现随后续程序构建部署生效。
