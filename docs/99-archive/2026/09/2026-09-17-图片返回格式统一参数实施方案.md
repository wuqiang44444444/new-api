# 图片返回格式统一参数实施方案

## 1. 问题与目标

用户已确认：标准图片生成与编辑接口统一使用已有的 `response_format` 控制返回格式，
不再新增 `return_url`。适用入口为 `POST /v1/images/generations` 与 `POST /v1/images/edits`。

本文件保留已确认的实施方案。代码、元数据与文档收敛已完成，本地回归已通过，并已开展配置渠道的真实调用验收。
实施结果与外部阻碍见[实施与渠道验收记录](2026-09-17-图片返回格式实施与渠道验收记录.md)；尚未部署，不能视为线上已发布行为。

目标：

- 客户显式传 `response_format=url` 时得到 `data[].url`；传 `b64_json` 时得到 `data[].b64_json`。
- **参数缺失时，保持各渠道、模型和执行模式原有行为**，不统一修改默认返回格式。
- 由渠道 adapter 吸收上游格式差异；客户不需要增加第二个布尔参数。
- 代码、公开模型元数据、OpenAPI 与调用文档表达同一合同。
- 返回格式转换不触发重复生成、重复计费或对成功生成的错误退款。

约束来源：[硬约束](../00-context/硬约束.md)、
[图片服务架构](../20-architecture/图片服务与异步Provider适配架构.md)、
[公开模型元数据投影架构](../20-architecture/公开模型元数据投影架构.md)。
本文是实施增量，不建立第二套长期合同；完成后的事实应收敛到对应架构与用户文档。

## 2. 当前实际情况

### 2.1 已核对的代码路径

| 路径 | 当前实现 | 本次需要处理的差异 |
| --- | --- | --- |
| Gemini / Vertex 的 generateContent 图片路径 | 标准接口识别 `response_format`，默认 Base64；显式 URL 时平台存储交付 | 复用现有能力，确保只上传一次，并核对交付失败的计费出口 |
| FunCloud / Moxing 同步图片路径 | adapter 只接受缺省或 `url`，返回 Provider URL | 北向补齐 `b64_json`，南向继续使用各自支持的格式 |
| 原生 OpenAI / Azure GPT Image 路径 | 原生参数转换与透传；尚未统一提供标准参数驱动的 Base64 转 URL | 按实际上游协议处理不支持的参数，并增加平台格式转换 |
| Imagen predict 等其他图片路径 | 与 generateContent 路径不同，存在直接返回 Base64 的实现 | 逐一登记、核对，不能由渠道名称推定全部支持 |
| 平台显式异步图片任务 | 冻结交付格式；查询显式 `b64_json` 返回 Base64，其余沿用 URL；统一图片族已分离南向格式 | 保持既有任务、格式冻结、查询及计费语义，移除布尔参数覆盖 |

主要代码证据：

- `relaykit/dto/openai_image.go`：已有 `ResponseFormat`。
- `relay/channel/gemini/image_generate_content.go` 与 `relay/channel/vertex/adaptor.go`：标准图片格式处理。
- `relay/channel/gemini/relay-gemini.go`：Imagen 响应路径。
- `relay/channel/asyncimage/adaptor.go` 与 `relay/channel/moxingimage/adaptor.go`：同步 URL 限制。
- `relay/image_async.go` 与 `controller/image_task_query.go`：异步交付格式冻结与查询。
- `pkg/publicmodel/image.go`、`image_gemini.go`、`image_native_gpt.go`：公开参数投影存在差异。

此前核对的 [OpenAI 生成接口文档](https://developers.openai.com/api/reference/resources/images/methods/generate)
说明：GPT Image 模型原生返回 Base64，不支持 DALL·E 使用的 `response_format` 参数。
因此，“网关标准接口接受该参数”不能等同于“所有上游均接受该参数”。对 GPT Image 提供 URL
交付属于网关扩展，应在本站文档明确说明；Azure 与其他兼容 Provider 仍须按其实际协议验证。

### 2.2 前序实现与已发现风险

方案形成时工作区存在 `constant/image_delivery.go`、`middleware/image_oss_delivery.go`、
`relay/image_oss_delivery.go` 及对应测试、元数据和文档，以 `return_url` 为开关；现已按本方案移除或替换。
本会话未部署该实现；实施时须核实发布状态，不将已有草稿当成已发布兼容合同。

前序审查发现：Gemini 已经生成平台 URL 后，布尔开关层还会再次下载并上传，既增加耗时，
也可能被 URL 下载安全限制拦截；第一次上传失败还可能先进入旧的 adapter 错误出口。
因此本次不能只把字段重命名，必须消除重复交付，并覆盖完整失败与计费链路。

## 3. 优化方案

### 3.1 客户参数与返回合同

| 客户输入 | 目标行为 |
| --- | --- |
| 缺失 `response_format` | 完整保留该渠道、模型及同步/异步模式原有默认值、响应与上游请求行为 |
| `response_format=url` | 返回 URL；已有合法结果 URL 时直接复用，只有 Base64 时才存储并签名 |
| `response_format=b64_json` | 返回 Base64；已有 Base64 时直接复用，只有 URL 时才安全下载并编码 |

`url` 表示返回形式，**不承诺全部使用本站对象存储域名**。保留 Provider URL 的原有有效期和行为，
不能为了统一域名无条件转存。平台签名 URL 复用当前 300 秒有效期；仅在掌握过期事实时返回
`url_expires_at`，不推测 Provider URL 的过期时间。同步临时 URL 不新增续签接口；异步沿用任务查询。

转换保留 `usage`、`revised_prompt`、图片顺序及其他既有结果元数据，不修改生成内容、编码格式或质量。
输入字段 `image_url` 与输出字段 `data[].url` 分别表达输入引用与结果引用，不新增输出 `image_url` 别名。

缺失、空字符串、`null`、非法类型及非法枚举的处理须按现有解析路径建立基线：不因全局新增解析
而收紧已有合法请求。对明确发布的两种格式保证履约，错误输入不能静默当成另一种交付格式。

### 3.2 唯一交付实现与最小接线

1. 枚举两个标准入口实际可达的全部图片 adapter，按“操作、协议、默认格式、两种显式格式、
   同步/异步/流式”建立矩阵。当前已核对渠道不是全量验收结论。
2. 分开保存客户交付意图与南向请求格式。上游原生支持时沿用 adapter；不支持时只在对应协议
   边界消费或转换字段，不把 GPT Image 不支持的字段盲目透传。
3. 每个请求只允许一个组件负责最终格式转换。复用现有存储和安全下载底座；Gemini/Vertex
   已生成 URL 时不得再次下载、上传。不得并存旧托管流程与新的无条件转存流程。
4. 同步普通 JSON 响应仅在确需转换时处理；默认请求不新增存储依赖，不做无意义的正文重写。
   不重构原生 Controller、计费算法或渠道分发；新增逻辑独立放置，现有文件只保留必要窄接线。
5. 覆盖 JSON、multipart、透传及参数覆盖路径。不能只修改 DTO 而让原始正文仍携带上游不支持的字段；
   必须保留文件、重复值、mask 和其他原生参数。客户最终交付意图不得被渠道南向参数覆盖悄然改变。
6. 异步任务在受理时冻结客户格式与合法南向请求；worker 不重新解释当前配置。
   幂等摘要保留客户格式差异，同键不同格式继续按既有冲突语义处理。

每处原生文件变更须说明必要性、最小接线点及未来上游同步的冲突影响。
不增加新的 Link 模型推断、能力注册体系、Task 表、资源列表、存储配置或计费账本。

### 3.3 流式与异步边界

两种格式保证首先适用于完整图片 JSON 结果与平台异步查询。原生 SSE 是独立事件协议，
不能用响应缓冲器把事件流改成普通 JSON，也不能为了本次修改改变未传参数的流式行为。

实施前必须单独核对显式格式与 `stream=true` 的已有组合行为；未完成验证前，不宣称 SSE 事件
支持 URL 转换，不全局拒绝原来可工作的组合。必要的限制须在调用上游前明确，并同步到适用
模型元数据及文档。OpenAI/Azure 的显式异步加流式仍遵循已有执行模式优先级。

### 3.4 失败、计费、安全与耗时

- 确定需要平台存储的转换，应在调用上游与预扣前检查所需存储；已有 URL 直接交付不能依赖平台
  存储就绪。无法预知上游返回形式时，须覆盖生成后才发现转换依赖缺失的错误路径。
- 可信生成成功后发生下载、编码、上传或签名失败，记录为交付失败，按生成事实结算一次；
  不进入生成重试、换渠道、上游禁用或自动退款。同步沿用明确的 `image_delivery_failed` 错误表达。
- 不能仅保护最后的响应转换器：Gemini 原托管分支等较早发生的交付错误也必须到达正确出口。
  上游生成失败与结果未知仍遵循现有规则，不一概视为成功收费。
- URL 下载复用 SSRF 防护、重定向校验、超时和大小限制；平台存储读取复用受信存储接口，
  不通过放宽 SSRF 策略解决重复回源问题。日志不得记录图片正文、完整签名 URL 或凭据。
- 复用已有图片数量、单图字节数、总响应及存储预算，并验证多图内存占用；不引入无限缓冲。
- 网关内新增下载、编码、上传、签名应纳入服务端处理耗时；客户收到 URL 后另行下载的时间不在
  原生成请求日志内。不得从网关总耗时臆造上游下载、排队和生成各阶段耗时。

### 3.5 删除旧参数并同步公开说明

- 移除 `return_url` 的常量、中间件、上下文开关、异步覆盖、元数据、示例与专属测试；
  在未发布前提下不保留 alias、双参数优先级或兼容读取。
- 保留可复用的交付与计费保护逻辑，按最终职责命名，删除失去调用方的旧实现。
- 保留前序独立的 GPT Image 编辑 `images` 对象数组、模型标识与其他元数据修复，不随参数清理撤销。
- 按实际支持范围更新 `pkg/publicmodel/`，确认模型列表、详情、价格目录对同一模型的一致投影；
  枚举包含实际支持的格式，默认值仍按模型与执行模式表达，不能全局写成 URL。
- 同步 `docs/openapi/relay.json`、公开生成/编辑文档、模型参数说明、内部图片架构与调用指南；
  更新公开文档版本和搜索索引。说明 GPT Image 的平台扩展及 Provider URL 与平台 URL 的差异。

## 4. 验证与完成标准

| 验证对象 | 必须证明的结果 |
| --- | --- |
| 全渠道清单 | 两个入口所有实际可达图片路径都有结论；不支持的操作不被新增元数据误发布 |
| 未传参数的旧客户端 | 上游请求、响应默认格式、流式、状态码、调用次数及账单保持基线；无新增存储依赖 |
| 两种显式格式 | 各适用渠道的生成与编辑均正确返回；已有目标格式不发生多余下载或上传 |
| GPT Image 原生边界 | 不支持的南向字段被正确处理；JSON/multipart、mask、透传和参数覆盖不受损 |
| Gemini/Vertex | URL 只上传一次；存储失败不会通过其他出口触发重生成或错误退款 |
| FunCloud/Moxing | URL 默认保持，Base64 可安全获取；失败不重复调用生成接口 |
| 异步 | 202 受理、格式冻结、幂等冲突、查询归属和终态计费沿用原合同 |
| 交付失败与安全 | 下载/上传/签名失败及超限、恶意 URL 均明确失败；成功生成仅一次结算，无自动重生成 |
| 元数据与文档 | 参数、枚举、默认值、操作支持范围与真实路由行为一致，不残留旧布尔开关 |

回归测试必须接入实际使用的新路由或窄接线，不以仍走旧中间件栈的测试证明兼容性。
使用确定性的模拟 Provider 与存储验证 API 和资金不变量；不新增只锁定内部实现形状的测试。

按修改边界执行 Go 测试；涉及 `relaykit/` 时执行 `GOWORK=off go build ./...`。
文档执行 `task docs:check`、`task ai:check`；公开文档修改后追加 `cd web && bun run docs:validate`。

真实 Provider、真实对象存储、账单与生产灰度须单独验收，不能由本地测试替代。
路径盘点、实现与旧参数清理、兼容性回归及公开资料同步已完成；真实渠道按验收记录区分通过与失败。
剩余事项为外部渠道故障处置后的定向复验、真实供应商账单核对及生产灰度；不将未通过的渠道写成全量验收通过。

## 评审修复与验收跟踪（本轮）

状态：评审完成，未发现需要扩大原生接口改动的新增缺陷。

保留 response_format 唯一参数、缺省原生路径、SSE 透传与交付失败不重生成的边界。
本轮未建立第二套图片协议、选渠或计费机制；实际渠道通过范围以渠道验收记录为准。
