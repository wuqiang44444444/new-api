# 图片返回格式实施与渠道验收记录

## 1. 问题与目标

实施[已确认方案](2026-09-17-图片返回格式统一参数实施方案.md)：两个标准图片入口统一使用
`response_format`，删除新增布尔开关，保证缺省请求继续按原有路径执行，并直接测试已配置渠道。
本记录描述工作区代码和本机验收，未部署到生产。

## 2. 当前实际情况

### 2.1 已完成的实现

- 缺省参数不捕获响应、不重写正文、不引入平台存储依赖；明确选择 `url` / `b64_json` 才转换。
- 已有目标格式直接交付；URL 不强制换成本站域名，不重复下载或上传。平台签名 URL 有效期 300 秒。
- Gemini/Vertex 标准图片路径以 Base64 交给统一交付层，图片中转以 URL 交付；Ali/Replicate 的
  既有结果下载在显式选择格式时统一到交付层，避免下载失败触发生成重试。
- GPT Image 不支持的南向格式字段在转换、透传和参数覆盖之后移除，覆盖 JSON 与 multipart；
  Azure 不透明部署名沿用原生已知客户模型配置判断协议，不改变选渠或模型映射。
- 原生 SSE 不转换成 JSON 或 URL；渠道覆盖产生的 SSE 也直接转发。
- 异步沿用原 Task、幂等、冻结格式与查询链路。生成成功后的格式交付失败仍只结算一次，
  返回 `image_delivery_failed`，不重生成、不进入上游禁用或自动退款出口。
- 已删除布尔开关实现和公开说明；保留前序独立的原生 GPT Image 编辑对象数组与模型元数据修复。
  模型参数、OpenAPI、公开调用示例、内部架构、指南、文档版本与搜索索引已同步。

主要实现为 `relay/image_response_format.go`、`relay/image_delivery.go`。
原生文件必要接线及同步影响：

| 文件 | 必要接线 | 后续上游同步核对项 |
| --- | --- | --- |
| `controller/relay.go` | 在预扣前调用一次格式与存储依赖检查 | 保持请求已解析、资金尚未预扣的顺序；非图片请求立即返回 |
| `relay/image_handler.go` | 请求格式准备、最终南向正文处理、响应交付与结算前后接线 | adapter 仍负责响应解析与 usage；交付失败不返回生成错误路径 |
| `relay/image_native_request.go` | 冻结原生异步最终请求前处理不支持字段 | 参数覆盖、透传与 multipart 边界优先级保持一致 |

Router 无额外格式中间件；未增加 DTO 参数、任务表、模型能力注册或计费账本。

### 2.2 全量代码路径盘点

| adapter 路径 | 本次格式处理 | 操作边界 |
| --- | --- | --- |
| OpenAI / Azure、NewAPI、Moonshot、Advanced Custom 的 OpenAI 图片路径 | 原生支持格式保留；GPT Image 显式格式由平台消费并交付 | 不新增模型或路由操作资格；Advanced Custom 仍须已配置图片路由与 none converter |
| Gemini / Vertex generateContent | Base64 归一后由统一交付层转换 | 生成、编辑；流式限制不变 |
| Gemini / Vertex Imagen predict | 既有 Base64 结果由统一交付层适配 URL | 不新增原本不支持的编辑能力 |
| Image Relay → FunCloud / Moxing | 南向 URL，北向两种格式 | 已登记生成与编辑合同不变 |
| Ali / Replicate | 原生解析结果与 usage，显式格式转换统一处理 | 按各 adapter 已有操作范围 |
| SiliconFlow | 已有 URL 结果可转换成 Base64 | 不扩展操作资格 |
| Jimeng / MiniMax / xAI / Volcengine / Zhipu V4 图片分支 | 原生字段转换与结果解析保留，完整图片响应按需补足格式 | 不把生成支持推定为编辑支持 |
| 其余未实现图片转换或明确不支持图片的 adapter | 保持原有不支持行为 | 不因新增交付层发布图片能力 |

代码盘点与已配置渠道实测是两种证据；没有实际配置的 adapter 不宣称完成真实 Provider 验收。

### 2.3 本地回归证据

- 图片 Controller、Relay、模型投影的定向回归共 **121 个叶子用例通过**，其中新增返回格式相关
  **48 个叶子用例通过**，无失败。含 Gemini、Vertex、Imagen、FunCloud、Moxing 的默认/URL/Base64，
  两个图片入口、原生 JSON/multipart/透传/覆盖、不透明 Azure 部署名、异步冻结及原生 SSE。
- 无存储时的缺省或 Base64 请求、Provider URL 直接交付均有覆盖；Gemini URL 只上传一次，
  上传失败仍只调用一次 Provider、结算一次且不退款；URL 转 Base64 的受保护下载失败不重生成。
- `pkg/publicmodel` 与 OpenAI、Gemini、Vertex、Image Relay、Ali 适配器完整测试通过；
  Replicate 包可编译，当前没有独立测试文件，不能把编译写成其独立测试通过。
- `relaykit` 独立构建通过。文档校验、AI 入口校验、公开文档校验和 12 个文档示例用例通过。

### 2.4 真实渠道验收方法

日期：2026-09-17，环境：本机最新工作区编译的 Controller/Relay 验收程序。
从本地 `one-api.db` 只读取得启用渠道配置与现有对象存储配置，经真实标准图片请求链路调用上游，
使用真实对象存储上传与签名，验证 URL 实际下载和 Base64 解码后的非空图片、MIME 与摘要。

用户、Token、消费日志与资金使用隔离的内存数据库及固定测试价格；不会写入现有客户账本，
真实 Provider 调用仍可能计费。本次不能证明供应商账单金额或生产部署状态。

每个渠道选取一个明确图片模型，未穷举渠道内所有模型、尺寸和质量档位。生成提示词为简单图标；
编辑使用本地合成参考图，之后对 Gemini 的空图片结果改用白底蓝色方块重新核验，仍未得到图片。
限流后错峰验证使用新的独立请求；超时或交付失败不作为自动重生成触发器。没有保存凭据、
原始 Provider 响应、图片正文或完整签名 URL，记录仅保留状态、格式、时长、大小与摘要。
