# 图片 Task 最小接入与原生计费一致性方案

## 1. 问题与目标

客户端报告：模型目录声明支持异步，提交图片请求时携带 `Prefer: respond-async` 和
`Idempotency-Key`，却直接收到 Azure 格式的 HTTP 400，没有平台任务号。随后对当前代码、本地
网关、Azure 渠道直连结果和数据库账单进行了对照。

**用户已确认的目标：显式选择 Task 时先返回任务号；未选择 Task 时完整保留 NEWAPI 原生同步和
流式模式；价格配置和用量计费沿用既有原生设计。** 不增加第二套价格、资金账本或任务系统。

**本文是待实施方案。** 当前 OpenAI／Azure 图片 Task 已有实现，本次是调整执行模式优先级并修复
已发现的缺口，不是从零新建异步系统。本轮只新增本文；尚未实施本文的代码变更，不能将新规则
视为当前线上行为，也不能将本地测试等同于生产验收。

范围为 OpenAI（类型 1）和 Azure（类型 3）的 `POST /v1/images/generations`、
`POST /v1/images/edits`。Gemini、Vertex、图片中转、视频、Azure Batch 和其它渠道不在本次模式
优先级调整范围内；共享图片用量解析修复按实际调用边界验证，不能借机改变其它协议。

约束来源：

- [硬约束](../00-context/硬约束.md)：原生最小入侵、图片受理与资金事务、未知结果禁止自动重发／退款。
- [图片架构](../20-architecture/图片服务与异步Provider适配架构.md)：当前执行路径及现有合同。
- [图片运维手册](../40-operations/03-图片渠道与异步任务运维手册.md)：对象存储、根密钥、worker 与恢复要求。
- [计费表达式规范](../../pkg/billingexpr/expr.md)：管理员表达式是定价权威，用量分类必须忠实传递。

## 3. 讨论分析与已确认决策

### 3.1 同步、流式、Task 的区别

- 普通同步：同一次 HTTP 连接等待完整结果。
- 流式：同一次连接逐步返回事件或内容；不是一个可断开后查询的平台任务。
- Task：先持久受理并返回任务号，后台继续执行，客户端随后查询。

`stream` 描述结果传输方式，`Prefer: respond-async` 在本方案中明确选择平台 Task 生命周期。
业务客户端应展示清晰的同步／Task 选择，不要求用户自行理解两种参数的组合。

### 3.2 取代此前“只在客户端关闭 stream”的方案

前序排查建议客户端关闭 `stream`，可以绕开当前问题，但不能独立保证显式 Task 请求的语义。
用户随后确认采用 **Task 优先**：OpenAI／Azure 只要显式选择 Task，合法的 `stream=true` 也不能
使请求回到前台流式。客户端可以省略 stream 简化请求，但网关正确性不能依赖客户端自律。

| OpenAI／Azure 请求 | 当前行为 | 本方案目标 |
| --- | --- | --- |
| 无异步头，stream 省略／false | 原生同步 | 保持原样 |
| 无异步头，stream=true | 原生流式 | 保持原样 |
| 有异步头，stream 省略／false | Task | 保持 Task |
| 有异步头，stream=true | 原生流式优先 | **Task 优先，202 后由后台接收上游流式结果** |

**兼容性变化仅针对最后一种组合，不应宣传为所有请求行为都不变。** `stream_priority=true` 的
目录声明和当前文档必须随新实现一起调整。没有异步头的请求，包括原有无效参数及幂等键校验，
保持已有行为；本方案不把无异步头的 `Idempotency-Key` 改成合法。

### 3.3 原事件能与不能得出的结论

正常 Task 路径先保存任务，后台才调用 Azure；后台 Azure 400 应成为已有任务失败，不能倒过来
解释为“Azure 拒绝所以平台 Task 从未存在”。但 202 前的平台校验、额度或存储检查仍然可以拒绝。
Task ID 在内部生成／落库早于客户端收到 202；客户端未拿到 ID 也不能单独证明数据库无任务。

已有实测复现了旧规则下 `Prefer + stream=true` 直接返回 400，但原客户事件缺少最终请求和线上
版本证据，不能直接归因为 stream。其它待排除项包括实际渠道类型、首次分发结果和实例版本。
仅丢失 Prefer 而保留 Idempotency-Key 时，当前网关会本地拒绝，不足以解释 Azure 原生错误体。
客户端的 `providerJobId` 究竟保存平台 Task ID 还是供应商任务号，须查看客户端赋值逻辑。

## 4. 代码评审问题清单

### F1／P1：图片输出用量分类丢失【已复现】

Azure 实测摘要为 `output_tokens=196`、`output_tokens_details.image_tokens=196`。
[Usage](../../relaykit/dto/openai_response.go) 未接收 `output_tokens_details`；
[normalizeOpenAIUsage](../../relay/channel/openai/relay_image.go) 只迁移输入明细。
使用该数值形状调用真实 `ImageTaskUsage` 与 `BuildTieredTokenParams`，得到：

```text
输入=19，输出=196，标准图片输出明细=0，表达式 c=196，表达式 img_o=0
```

影响：普通输出倍率仍计入 196 个 token，当前成功账单正确；使用 `img_o` 分别定价时会把图片输出
错误归入普通输出或漏计相应金额。同步与异步共享缺口。不能通过改倍率掩盖用量解析问题。

### F2／P1：部分待核实任务无法自动收敛【代码与任务样本已确认】

[原生执行器](../../relay/image_native_executor.go) 将网络异常、408、429、5xx 等归入 unknown。
[GetReconcilableImageTasks](../../model/task_image_lifecycle.go) 只自动恢复有 ProviderTaskID
或 GenerationComplete 证据的待核实任务。原生 Azure／OpenAI 丢失结果且无此证据时，没有自动
查询原生成结果的路径，预扣可能长期保留。

保留真实未知结果符合资金安全约束；问题是分类过粗与核实闭环不足，不能通过无条件退款或重发
“修复”。本地编辑样本已进入此状态，具体上游原因未知。

### F3／P2：后台失败诊断不足【代码已确认】

原生执行器对非成功 HTTP 响应没有保存足够的状态码、错误码和 Provider 请求 ID，只留下
`provider_rejected`／`native_image_outcome_unknown`。不同参数拒绝、安全审核、限流及传输错误
难以区分；已返回 202 的请求也不会自然落入 HTTP 4xx 请求日志。

需要 Task 关联的脱敏后台事件；不能把所有后台错误改成前台 HTTP 4xx。与
[鉴权后 4xx 日志方案](2026-09-16-系统4xx日志缺失问题分析与修复方案.md)复用可用日志底座，
分别定义请求事件和任务执行事件，避免重复记录或改变该方案的统计口径。

### F4／P2：显式 Task 与流式优先规则不符合本次目标【已确认调整】

旧代码、目录及测试对于“流式优先”自洽，不属于漏写 Azure 异步资格。但用户希望明确选择 Task
就使用 Task，因此需要同时修改模式选择、原生异步入口组合校验和公开目录声明，不能只改某一处。
`Idempotency-Key` 是 Task 的重复提交保护，不是另一种模式开关。

### F5／P2：异常收费政策存在条件性差异【静态分析，未实测触发】

[同步错误出口](../../controller/relay.go) 调用 `NormalizeViolationFeeError` 和
`ChargeViolationFeeIfNeeded`；[异步失败结算](../../service/image_task_billing.go) 对可退款终态
将目标置零。若既有违规扣费设置启用且命中其规则，可能出现同步／异步收费差异。

该政策当前使用 Grok 设置及特定错误标记，不能把所有 Azure 安全拒绝都视作应收费；本次没有
生成违规请求，未证明原事件命中该政策。实施前需清点实际适用政策，而非新增一套图片违规费。

## 5. 优化方案

### 5.1 在已有分派处调整 Task 优先级

1. 保留 `ImageAsyncExecutionRequested` 作为唯一模式选择点，在首次分发之后、幂等认领和预扣
   之前确定并缓存模式。OpenAI／Azure 已收到合法异步偏好时，不再因 stream=true 切回原生。
2. 保留 `PreferRespondAsync` 的既有解析规则，不新增 `preferasync` 请求字段、入口或第二开关。
   渠道资格来自类型，不根据模型名、上游域名或错误体推断；其它渠道资格及行为保持原样。
3. 继续由原生请求校验器处理非法 JSON、非法布尔值、数量上限等，不因 Task 优先而跳过校验。
   不复制第二套图片参数校验，也不把非法值静默改成 false。
4. 在 `imageAsyncHelper` 内精确调整 OpenAI／Azure 的 stream 组合检查；其它图片协议原有不支持
   流式的检查保持原样。控制器、幂等中间件和 ImageHelper 继续引用同一个已缓存模式。
5. 原有请求级预扣与退款不拥有 Task 资金；Task 受理失败按事务回滚，成功后只有任务结算处理差额。

目标流程：

```text
鉴权与首次分发 → 选择并固定执行模式
  ├─ 未选择 Task → 原生校验、同步／流式、原生请求计费
  └─ 选择 Task   → 原生校验、准备受保护请求快照
                  → 容量 + 资金 + Task + 幂等绑定提交
                  → 202 + id + query_url + Location
后台发送许可提交 → 原生 adapter 准备的请求 → 上游 JSON／SSE
                  → 最终图片及实际用量 → 既有 Task 结算 → 查询
```

202 表示已持久受理，不保证上游成功，也不承诺固定“秒回”：受理仍有输入准备和存储检查耗时。
存储或额度检查失败不得调用上游，也不得静默退回同步执行。

### 5.2 保留原生请求及后台流式处理

保留模型映射、Azure 部署名／API 版本、认证、JSON／multipart、图片／mask、参数覆盖及透传
的既有语义。不要为了进入 Task 强行删除 stream，也不要静默修改用户其他参数。

后台复用现有 JSON／SSE 解析：只将完成事件对应的最终图片作为交付结果，部分预览不算最终成功，
usage 不重复累计。创建连接只返回一次 202；即使上游在流式连接中返回错误事件，也只能推进已有
Task 的状态，不能再向已结束的创建连接写 SSE 或第二个错误响应。消费 SSE 不要求为 Task 新建
客户端进度推送接口。上下文应由 worker 生命周期控制，不能继承创建 HTTP 请求结束后的取消。

### 5.3 沿用原生计费并修复 F1

价格权威继续是已有模型价格／倍率、分组、表达式和适用客户合同；资金来源继续是原生钱包／订阅
偏好。同步和 Task 使用相同实际用量计算规则，Task 仅冻结受理事实并改变结算时机。

F1 的最小修复：

- 在既有图片用量解码边界接收 `output_tokens_details`，映射到统一输出明细。
- JSON、原生 SSE、后台 JSON、后台 SSE 共用同一归一规则，不分别维护换算公式。
- 保留字段缺失与显式零值；总 token 不重复相加。当两种输出明细字段同时存在且冲突时，明确
  图片协议权威字段的优先级，禁止把重复表示相加；不推断缺失明细一定全部属于图片。
- 普通倍率、按张定价及缺失 usage 的既有规则保持原样；本次只纠正有上游证据的分类。
- 如必须扩展公共 Usage DTO，只增加必要的可选字段及归一接线；字段定义进入 `relaykit/` 时
  必须保持模块独立，不引入根模块依赖。

同一请求、同一价格快照、同一实际用量应得到相同最终收费。两次真实生成的用量可能不同，不能
仅比较两笔金额就判断模式计费不一致。异步任务存续期间配置变化不应反向改写已冻结的计费事实。

### 5.4 先补证据，再修异常分类与核实闭环

为 F2／F3 在后台执行边界提取最小、受限、结构化诊断：平台 Task ID、渠道类型／内部渠道 ID、
操作、执行阶段、上游 HTTP 状态、白名单错误分类、Provider 请求 ID、结果是否可信。
错误正文只做有大小限制的解析，不持久化或记录原始 message、prompt、媒体、认证头、签名 URL；
外部字符串须限制长度并清理换行。不能直接保存任意 Provider code/type 作为可信分类。

日志只作观察，不成为任务／资金事实源；提交不等待日志磁盘或网络 I/O，写入异常不阻挡受理、
执行、响应或结算，不改变错误分类。采用既有可用的非阻塞底座及独立丢失计数，禁止同步回退、
无界队列或每事件新建 goroutine。业务状态和资金仍必须按原事务提交，不可因“日志不阻塞”而
跳过必要的持久化。

| 执行证据 | 处理方向 |
| --- | --- |
| 已证实未发送的准备失败 | 安全结束、按已有资金规则释放占用 |
| 已验证为明确拒绝的 Provider 响应 | Task 失败，执行既有退款／适用收费政策 |
| 只知道 HTTP 429／5xx，缺少可采信语义 | 不仅凭状态码新增自动退款或重发 |
| 发送后断连、超时、流式不完整，结果不可确认 | 保留 unknown，不自动换渠道／重发／退款 |
| 已持久化完整结果证据 | 复用结果恢复与幂等结算，不重新生成 |

先依据脱敏证据和对应 Provider 合同登记哪些拒绝可安全结束，再添加精确分类。不同 Provider
不能共享未经验证的状态码退款推断。对无自动恢复依据的任务，梳理已有管理员核实入口，补齐证据、
操作人和审计关联；最终结算复用 `ApplyTaskBillingTarget` 等正式入口，禁止直接改库或另建账本。
本次测试留下的待核实任务单独跟进，不能通过重新提交相同请求证明此前是否成功。

### 5.5 对齐 F5 的适用收费政策

先列出既有错误收费政策、启用条件、匹配依据、资金来源及重试行为；用无害的模拟响应验证。
对确实适用于两种模式的政策，复用原生判定语义，将所需事实冻结到已有任务计费上下文，以幂等
资金目标结算。不能在后台直接重复调用带请求级资金副作用的函数，也不能复制第二套标记或金额。

政策未启用／未命中的普通参数拒绝继续最终收费为零。若政策依赖原始错误字符串，只在受限解析
时转换为既有判定所需的稳定事实，不将原文持久化；结论及适用边界完成验证前，不声称异常计费
已全面等价，更不能默认所有安全拒绝都收费。

| --- | --- |
