# FunCloud 托管素材与统一视频引用实施方案

本文记录已确认设计、代码实施与评审修复。**主体实现与本地回归已落地，真实 Provider、对象存储部署、生产数据库升级和账单验收尚未完成，不代表生产已发布。** 第 2 节保留实施前背景，当前实施状态见第 8、9 节。

## 1. 问题与目标

本次改造是为了支持官方“创建素材组 → 创建素材 → 使用素材生成视频”的调用流程。根据用户与上游确认的设计前提，FunCloud 通过真人模式（`realPersonMode`，V3 准确字段拼写另行核定）使用这类素材能力，不能直接按官方素材引用方式履约；平台需要在内部吸收这一差异。

目标是让用户保持统一的官方调用方式，由平台在 FunCloud 南向转换为 URL 加真人模式。明确保留两条路径：

1. **用户走官方素材流程**：用户创建素材组、创建素材，再传素材引用生成视频；平台内部创建并管理对应的素材组和 asset，将源图片复制到本站 OSS，使用时把 asset 转成内部签发的 URL，再交给 FunCloud。
2. **用户直接传 URL**：平台直接传递该 URL 给 FunCloud，不创建素材组或 asset，不复制文件。

两条路径都由 FunCloud V3 adapter 固定启用真人模式。用户无需传 Provider 私有开关，也无需知道内部签发的 URL。**“南向无需创建上游素材”不等于“北向省略官方素材组与素材流程”。** 既往素材引用失败是排障背景，不是取消北向官方流程的理由。

首期仅实现 **FunCloud V3**。保留以后接入其他模型渠道的实现边界，但本期不建设通用跨 Provider 素材框架，不改造 V2 或其他 Provider 的素材语义。

## 2. 当前实际情况

### 2.1 已验证事实与外部说明

此前测试使用隔离数据库和本地测试服务连接真实上游，未以测试结果替代生产验收。相关请求只记录脱敏摘要：

| 类型 | 请求与结果摘要 | 可以得出的结论 |
| --- | --- | --- |
| FunCloud 素材创建 | 蓝色咖啡杯图片成功上传，接口返回素材 ID、引用和可用状态；随后视频引用失败，提示素材不存在 | 上传成功不能证明视频侧素材可见 |
| 普通 URL 对照 | 此前同一蓝色咖啡杯图片通过 FunCloud 普通 URL 路径生成成功 | 普通图片 URL 路径存在真实成功记录 |
| V3 固定模式试验 | 通过临时构建分别测试 `real_person_mode: true` 与 `realPersonMode: true`；原素材引用均失败 | 增加开关没有解决已有素材 ID 的引用问题 |
| V3 普通 URL 加模式试验 | 上游示例图片 URL 的两种字段拼写试验分别被版权或内容策略拒绝 | 尚不能证明 V3 开关的准确字段及成功履约；不得把策略拒绝归结为素材存储失败 |
| 上游口头说明 | 普通图片 URL 配合 `realPersonMode: true` 即可，不必创建上游素材；提供的示例路径为 V2 | 支持调整设计方向，但不能直接当作 V3 字段合同 |

V3 文档使用 `real_person_mode`，上游给出的 V2 示例使用 `realPersonMode`。实施前必须核定 **V3** 的准确字段，并用允许生成的实际图片完成成功测试；不同时发送两种拼写，不通过猜测字段或自动切换协议解决。

### 2.2 与现有实现的关系

当前素材架构仍以 [Seedance 无状态素材代理架构](../20-architecture/Seedance无状态素材代理架构.md) 为事实记录：平台代理 Provider opaque ID，不建立客户素材记录、不复制媒体、不在视频入口解析本地素材所有权。

[9 月 7 日实施方案](2026-09-07-FunCloud新版视频协议与统一素材库实施方案.md) 中继续使用既有 FunCloud 上游素材代理的设计前提，被本文的首期托管素材方向取代；其中已有测试、计费和排障记录仍需按各自证据理解。**这只是设计方向的替代，不意味着旧实现已经迁移。**

## 3. 优化方案

### 3.1 已确认的业务决策

| 事项 | 已确认方案 |
| --- | --- |
| 客户入口 | 北向保持统一 ModelArk V3，支持官方“创建素材组 → 创建素材 → 使用素材”流程，不增加 Provider 私有开关 |
| 素材组与素材 | 用户走官方流程，平台内部保存对应素材组及 asset；对 FunCloud 视频履约时转为 URL，不依赖上游素材 ID 直传 |
| 南向开关 | FunCloud V3 adapter 固定启用真人模式；确切字段名以 V3 核实结果为准 |
| 素材来源 | 用户提交**他们自己的 OSS URL**；可以是长期 URL，也可以是当次有效的签名 URL |
| 文件归属 | 创建时复制到本站 OSS，形成平台控制的独立私有对象 |
| 命名 | 平台生成 asset ID 和目标对象名，不使用客户 URL 的文件名作为对象名或身份 |
| 重复创建 | 每次新建 asset 并复制新文件；同 URL、同用户、跨用户、客户端重试均不去重、不合并，不增加幂等键机制 |
| 创建完成 | 同步复制成功且素材记录持久化后，才返回可用的 asset；失败不返回可用素材 |
| 共享与隔离 | 同一用户账号下所有 API Key 共享；不同用户隔离；更换或删除 Key 不使素材失效 |
| 凭据更换 | FunCloud 上游账号或凭据变化不使平台已保存的素材失效 |
| 视频引用 | 客户传 `asset://<平台素材ID>`；平台校验用户归属后，在内部转换为上游可读 URL |
| 内部 URL | 调用时签发临时访问 URL，客户不需要知道，也不向客户返回该 URL |
| 直接 URL 生成 | 客户直接传 URL 时，按既有安全边界直传；不创建 asset、不复制文件 |
| 删除素材 | 停止该 asset ID 的新引用，已经提交的视频继续；不删除 OSS 文件 |
| OSS 清理 | 系统完全不管理 OSS 文件清理，不做定时清理、孤儿扫描、过期删除或失败补偿删除 |
| 首期扩展范围 | 先满足 FunCloud 的复用及账号更换；不承诺自动跨 Provider 复用或历史素材迁移 |

来源决策以本表为准：此前讨论中的“只允许本站 OSS URL”已被用户明确更正。**客户 OSS 是复制来源，本站 OSS 是受控保存目的地。**

### 3.2 官方素材组与素材创建流程

1. 用户按统一北向协议创建素材组。平台通过现有鉴权取得用户身份，在 FunCloud 托管路径内部保存对应素材组并返回统一组 ID，供后续素材创建使用；不要求用户去 FunCloud 另建素材组。
2. 用户按官方流程提交素材创建请求，携带素材组 ID、客户模型与自己的图片 URL。平台校验素材组归属，不能把其他用户的组作为自己的素材容器。
3. 根据明确注册的素材实现选择 FunCloud 托管路径，校验请求结构、源 URL 和媒体边界。不得通过模型名猜测托管能力。已发布的可选素材组语义仍由统一合同规定，不因本方案反向收紧。
4. 为本次创建生成独立 asset ID 和随机目标对象名；安全读取源图片并复制到本站私有 OSS。
5. 复制完成后持久化该用户的可用素材记录及所属素材组关系。
6. 返回统一的素材 ID、引用和可用状态，用户随后按官方流程引用素材；不返回来源 URL、目标存储位置或内部签名 URL。

最小持久化信息建议为：素材组的 ID、`user_id` 和必要的北向属性；素材的 ID、`user_id`、所属组、稳定的目标存储位置及对象 key、必要媒体信息、有效状态和时间。素材组只是支持官方流程所需的组织关系，不增加独立授权系统。具体字段属于实现设计，不在本方案预先固定完整数据库结构。

源 URL 仅用于当次复制，不作为素材身份、不长期持久化、不进入普通日志或公开响应。内部签名 URL 同样不作为持久化身份；持久化事实是平台自己的对象位置。

OSS 复制与数据库写入无法组成同一个数据库事务。复制失败应返回创建失败；复制成功但素材记录写入失败，也不能返回可用 asset。后一情况允许留下无引用对象，**不得为此增加删除补偿或后台清理**。客户端再次创建会得到另一个新素材和文件。

### 3.3 使用素材生成视频

1. 客户继续在统一视频请求的媒体引用位置传 `asset://<平台素材ID>`。
2. FunCloud 托管路径读取平台素材事实，校验 `user_id` 与有效状态。同账号不同 Key 可以引用，跨用户、失效或不存在的引用明确拒绝，且应在资金 hold 和 Provider POST 前拒绝。
3. 解析为本站对象，并根据上游实际取图窗口签发内部临时 URL。访问期限必须覆盖正常排队和取图时间，不能随意选一个短期限。
4. 在既有 durable create attempt 流程中冻结已接受的素材身份和对象事实；FunCloud V3 adapter 将媒体引用转换为普通 URL，固定启用核实后的真人模式字段，保持其他北向字段语义。
5. 后续任务使用已经冻结的事实，不重新依赖当前素材有效状态、当前 Key 或当前渠道凭据解释已提交请求。

已发给上游的临时 URL 可能在有效期内继续可用，因此删除素材的含义是阻止新的引用，不能承诺立即撤回上游已取得的访问能力。任务已受理后的生命周期继续遵循现有异步合同；创建结果不明时不自动重发。

签发时机、冻结内容和错误返回需在实现中接入现有 durable attempt 边界，不另造一套异步任务系统。对签名 URL 的必要瞬时处理不得扩大为日志、公开结果或长期明文存储。

### 3.4 直接 URL 生成视频

客户直接传图片 URL 时，FunCloud V3 adapter 直接向上游发送该 URL，并固定启用已核定的模式字段。该路径不写素材表、不复制到本站 OSS、不自动把 URL 转成 asset。

源 URL 的可访问性和有效期由客户提供；直传不意味着平台代为延长客户 URL 的有效期。平台复制后可长期复用的保障仅属于显式创建成功的 asset。

### 3.5 查询、删除与复用边界

最小实现必须覆盖官方素材流程所需的素材组创建、查询，以及素材创建、查询、删除和视频引用入口。FunCloud 路径在内部履约，北向请求和响应保持统一。不得以“南向只需 URL”为由删去素材组步骤；也不额外扩展列表、批量操作或通用资源管理框架。具体可用操作必须由代码登记及统一公开元数据一致表达。

素材组及素材均按用户账号鉴权，同账号不同 Key 共享。素材删除只改变平台素材的可引用状态；没有 OSS 删除调用。删除与并发创建视频的交界必须有明确接受点：已接受并冻结的引用继续执行，之后的新引用被拒绝。

素材记录不得绑定创建时的 API Key 或 FunCloud 上游账号。账号或凭据更换不会改变素材对象归属；这不改变已存在视频任务继续使用冻结连接的要求。

旧 Provider opaque ID 不自动视为新平台 asset，不探测、不迁移、不双读、不在本地解析失败后回退上游引用。启用托管路径后的历史引用处置应明确告知调用方重新创建素材；其他 Provider 原有 opaque ID 路径保持既有合同。

## 4. 架构调整范围

以下是已确认业务方案所需的**局部边界变更**，实施前应同步唯一权威事实文档。本文不作为第二套长期架构合同。

| 当前约束 | 本期拟调整范围 |
| --- | --- |
| 素材及素材组全部为无状态 Provider 代理 | 为明确登记的 FunCloud 托管路径增加支持官方流程的平台素材组、素材记录和文件复制；其他 Provider 不变 |
| `asset://` 原样发送且不查本地库 | FunCloud 托管引用按用户校验并解析本站对象；不建立通用 Provider 探测或 fallback |
| 客户资源默认按 `user_id + app_id` 隔离 | 托管素材组和素材以 `user_id` 共享；Task、资金及其他资源继续既有隔离合同 |
| 平台不保存媒体 | 本期由本站 OSS 保存独立私有图片；源 URL 和签名 URL 仍非公开或长期素材事实 |
| 复用域与上游素材租户相关 | 托管素材不因上游账号轮换失效；公开复用元数据需随新实现核定，不沿用会错误失效的租户推导 |

实施涉及更新 [硬约束](../00-context/硬约束.md)、素材专题架构和相应产品/API/运维说明，以及 AGENTS 中重复陈述的当前素材边界。只调整已确认的 FunCloud 托管例外，不放宽其他原生能力、资金、异步任务和安全规则。

代码尽量放在 Link 专属新增文件，仅在必要入口接线；不借此引入 publication、SKU、binding、跨 Provider fallback 或通用资源框架。对接独立 `relaykit` 时，通过明确输入传入已解析的媒体事实，不让其依赖根模块数据库或配置。

## 5. 安全与失败语义

- 读取客户源 URL 必须执行既有 URL、重定向、内网访问、媒体类型及大小限制；用户提供的是 OSS URL，不代表可跳过取图安全校验。不存在现成边界的部分应明确补齐，不能直接无界下载。
- 所有素材操作只依据鉴权得到的用户身份，不接受客户自行指定 owner。不可用及跨用户引用不得泄漏其他用户的素材存在性或存储位置。
- 用户源签名失效、源文件不可读、媒体不合法或本站存储失败时明确返回创建失败，不返回虚假的 `ready`。
- 本站对象被外部删除或存储不可用时，不能伪装素材仍可履约，也不重新下载原客户 URL。对象长期保存依赖本站 OSS 的外部运维策略，系统自身不承诺或执行清理。
- Provider 的内容策略拒绝继续按业务失败处理，不以修改图片、改协议或自动换渠道规避。
- 密钥、完整签名 URL、Task 私有数据和原始上游响应不得进入方案、普通日志和公开响应。

## 6. 实施顺序与验收

1. **先核实 V3 合同**：确认模式字段，使用允许生成的图片取得普通 URL 加固定模式的真实成功结果。未通过前不得声称托管素材已可生产履约。
2. **更新边界文档**：把账号共享、私有复制、内部签发、无清理和旧引用处置写入权威事实的待实施边界；实现完成后再标注当前能力和验收状态。
3. **完成官方素材流程的内部实现**：素材组创建/查询、组内素材创建、同步复制、平台生成名称、用户所有权、素材查询/删除和稳定对象记录，不加去重、幂等机制或后台复制任务。
4. **接入 V3 视频路径**：asset 解析与直接 URL 分支保持明确，接入 durable hold 前的失败校验及冻结事实，并核对公开元数据。
5. **执行回归和真实验收**：通过后再完成接口说明与部署步骤，不用本地自动测试替代真实 Provider、数据库或账单验证。

| 验收项 | 必须证明的行为 |
| --- | --- |
| 官方完整流程 | 用户创建素材组、在组内创建素材、再通过素材引用生成视频；平台内部保存组与 asset，实际向 FunCloud 发送 URL 加真人模式，不要求用户改变官方请求流程或提供私有开关 |
| 素材组隔离 | 同账号不同 Key 可以在同一组创建素材；跨账号不能查询或使用该组创建素材 |
| 普通源与临时源 | 两种可读 URL 均能复制；源 URL 之后失效仍可用平台 asset |
| 同 URL 重复创建 | 同用户和不同用户均生成独立 ID、独立目标对象，不继承源文件名 |
| 同账号共享 | 同账号不同 Key 可查询、删除和引用；Key 更换不影响素材 |
| 跨账号隔离 | 其他账号无法查询、删除或生成视频，失败不产生 hold 或上游创建请求 |
| 创建失败 | 下载、存储、数据库写入任一步失败均不返回可用 asset；不触发文件删除补偿 |
| 素材删除 | 新引用被拒绝，已受理视频不因删除而中断，无 OSS 文件删除 |
| 账号轮换 | 更换 FunCloud 上游账号后，原有平台 asset 仍可生成新视频 |
| 直接 URL | 不建素材组或素材、不复制文件，保持 URL 内容和统一字段语义；南向固定启用真人模式 |
| 请求字节与资金边界 | 北向请求经素材处理、durable hold 到实际 Provider 请求字节完整可验证；只有核定的模式字段，内部 URL 不公开 |
| 签发窗口 | 排队期间上游可读本站图片；失效和取图失败得到可信错误，不自动重发未知创建 |
| 真实业务 | 使用复制后的实际素材完成 V3 成功视频并获取结果；对承诺支持的模型逐一验证，不能从单模型推广 |
| 兼容与构建 | 其他协议不受影响；涉及迁移时验证 SQLite/MySQL/PostgreSQL；涉及 `relaykit` 时独立构建通过 |

后续实现应运行对应边界测试、根模块构建及必要文档检查。入口测试应验证可观察请求和资金行为，不只断言内部函数被调用。

## 7. 剩余事项与已接受代价

- V3 真人模式准确字段及真实成功生成仍待验证。上游口头说明与 V2 示例不能替代此项。
- 内部签名有效期需匹配实际 Provider 取图窗口；不预设未经验证的分钟数或自动续签能力。
- 每次新建的选择意味着重复调用、网络重试和部分失败可能产生重复或无引用文件；用户已选择保持简单，系统不处理这些文件的清理。
- 新托管路径不修复旧上游素材 ID；调用方需重新创建平台 asset。上线说明必须清楚区分，不建立历史兼容机制。
