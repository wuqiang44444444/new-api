# 任务日志视频详情与音视频请求证据方案

## 1. 问题与目标

线上任务日志中，成功视频任务的“详情”列显示 `-`。用户确认线上为 rc23，本地为 rc31，要求分析
本地实现是否覆盖自定义 Seedance/Moxing 渠道，并形成视频详情修复方案。

目标：任务始终可以查看基本详情；视频任务可以查看已记录的视频参数，在结果可用时预览、打开、
复制平台视频链接和下载；管理员按权限查看必要诊断信息。

用户进一步明确：所有视频与音频请求都应保存完整请求证据，用于客户问询和高成本故障排查，不能
依赖再次收费生成来复现。本方案据此扩大范围至完整业务请求、最终南向请求、上游响应与客户交付的
全过程证据。只补少量视频字段已不足以满足目标；第 6 节为此次新增需求的待实施设计。

本文为待实施方案。本轮仅完成代码分析和文档记录，未修改业务代码，未连接线上数据库，未进行真实
Provider 调用或页面验收。用户提供的线上排障摘要仅作为背景，不保存其中的私有任务 ID、上游 ID、
渠道配置或原始媒体地址。

## 2. 当前实际情况

### 2.1 旧版显示问题

本地 Git 历史中，`2023de5d1` 合并前第一父提交的任务详情列使用 `fail_reason`：成功视频任务只有在
该字段以 `http` 开头时才显示视频预览，字段为空则显示 `-`。同期后端已通过 `result_url` 返回
`task.GetResultURL()`，前端仍依赖失败原因判断视频是否存在，存在字段使用不匹配。

该逻辑与线上截图一致，但尚未核验线上实际构建提交和接口响应，不能把本地历史提交等同于线上部署。
按秒计费、Token 为零、任务成功没有报错，都不能解释或合理化“任务详情应为空”。任务详情、消费日志
与失败原因是不同内容。

### 2.2 本地 rc31 已有能力

| 能力 | 已核对的代码行为 |
| --- | --- |
| 详情入口 | 每条任务固定显示“查看详情”，不依赖成功状态、失败原因或插件身份 |
| 通用信息 | 展示任务 ID、状态、进度、动作、时间、模型；管理员增加渠道、额度等 |
| 上游任务 ID | 后端从私有任务数据投影给 Root，前端 Root 诊断区展示，不要求插件身份 |
| 平台请求 ID | 来自 `Execution.RequestID`；不是 Provider 的 `upstream_request_id` |
| 视频预览 | 独立“产物”列按需调用 `/api/task/{task_id}/artifacts` |
| 非插件视频 | 成功、视频动作且有结果 URL 时，返回平台 `legacy_content_url`，不要求 Seedance 改成插件渠道 |

以上为本地代码行为核对，不代表真实页面、外部存储或线上部署验收。普通用户任务查询在
`TaskGetAllUserTask` 中使用 `Omit("channel_id")`，虽基础 DTO 仍有 `channel_id` 字段，该查询路径不取
真实渠道值，不能仅凭 `TaskModel2Dto` 无条件赋值就认定真实渠道 ID 已泄漏。`quota` 则仍由用户接口
返回；“详情弹窗仅管理员展示额度”与“后端禁止用户读取自己的额度”不是同一个合同。

### 2.3 本地尚缺内容

- 详情弹窗未整合视频预览、打开和复制链接操作；现有视频展示在独立产物入口。
- 任务详情 DTO 未包含上游请求 ID、冻结视频协议和 adapter 版本。
- 详情未展示时长、分辨率、比例、音频开关等视频参数，也未展示完整用量与结算事实。
- 保存的数据不保证包含所有生成参数。`TaskClientRequestSnapshot` 仅含部分字段，上游任务结果也未必
  返回完整参数，不能假设所有历史任务都能补齐。
- 计费探针含 `generate_audio` 等归一化参数，但 `AttachAsyncTaskBilling` 仅在
  `TieredBillingSnapshot != nil` 时持久保存 `BillingProbe`。探针不是全量任务必有数据，也不是原始请求。

## 3. 优化方案

### 3.1 详情内容与权限

| 区域 | 内容 | 规则 |
| --- | --- | --- |
| 基本信息 | 任务 ID、客户模型、状态、进度、提交/完成时间、耗时 | 所有任务展示 |
| 视频结果 | 播放器、打开视频、复制视频链接、下载 | 成功且有结果时展示 |
| 视频参数 | 时长、分辨率、比例、音频开关等 | 只展示可信记录，区分请求参数和实际结果 |
| 异常信息 | 失败原因、待核实状态 | 按实际任务状态展示 |
| 管理信息 | 渠道、额度、平台请求 ID | 弹窗管理员区域；额度沿用既有用户接口语义，见下文 |
| 上游诊断 | 上游任务 ID、上游请求 ID、冻结协议、adapter 版本 | 沿用 Root 权限 |

本次新增投影不向客户暴露 Provider 身份、上游模型和内部协议。新增字段权限须在后端投影及资源访问
入口落实，不能只依赖前端隐藏。既有字段采用以下明确口径：

- 保留普通用户接口对本人 `quota` 的既有返回行为，本次不将其重新定义为管理员秘密字段。
- 保留普通用户查询对真实 `channel_id` 的排除，验收返回内容不携带真实渠道身份；不为去除零值字段
  而重构通用 DTO，也不把数据库层已有保护误述为“仅前端隐藏”。
- 新增 Root 诊断和证据信息在 controller 的既有按角色投影处接线；主体放新增文件，不必为本次需求
  修改通用 `TaskModel2Dto`。若发现其他入口确有既有敏感字段泄漏，另列证据和最小修复，不扩大本次
  范围去重定义全部原生接口。

账户级后台继续使用既有账户/管理授权，不能声称当前后台列表已经按 app 筛选。新增证据必须保存真实
`user_id + app_id`；面向应用的 Link 查询按两者授权，账户后台和管理人员访问按明确权限允许跨本人
应用或管理范围查询。无有效 app 事实的历史记录不伪造 app 身份，新增证据不借用旧接口绕过权限。

### 3.2 在现有详情内复用视频展示

打开详情且任务成功时，按需调用已有产物接口；复用现有播放器、加载状态和重试逻辑，增加打开视频、
复制平台链接及下载操作。表格“产物”列可保留快捷入口，但与详情共享展示实现，不复制第二套请求或
媒体加载逻辑。列表加载本身不批量获取产物或视频内容。

视频链接使用现有平台内容接口生成的 URL，不返回 Provider 原始结果地址，不把结果重新写入
`fail_reason`。现有链接为绑定任务及产物的长期访问链接，不能在文案中宣称为短期链接；本方案不改变
它的授权机制。链接仅在经授权的结果操作中提供，不写入通用日志、遥测或文档。

平台链接仍依赖结果源可访问，不承诺永久保存视频。成功但没有结果地址时显示“任务已成功，未记录视频
结果”；播放失败时显示重试操作，不改变任务成功状态。平台内容地址配置或接口请求失败应显示可理解的
错误，不静默显示 `-`。

### 3.3 补充明确的视频详情投影

在 Link 专属新增文件中提取允许展示的字段，通过既有任务详情数据流最小接线，避免新增平行任务体系。
前端不解析完整 `private_data`、计费探针或原始 Provider 响应。

实施时先逐字段核对可用数据源：请求快照表示客户请求，冻结履约记录表示实际采用参数，上游结果表示
Provider 明确报告的结果；不可互相冒充。只从已保存事实投影，不根据当前 Channel、模型配置或价格
重新解释历史任务，不为了展示触发 Provider 查询。

摘要先展示已有可靠时长、分辨率等字段；新请求同时按第 6 节保存受保护的完整业务证据，摘要从可信记录
投影，不用摘要代替原文。完整内容不塞入通用 Task 字段或消费日志。历史缺失显示“未记录”；
`false`、`0` 与缺失值必须区分。
音频使用统一北向名称 `generate_audio`，不要求客户理解 Moxing 南向 `with_audio`。

已有计费探针可用于独立于第 6 节的详情补齐，但只能标为“计费采用参数”，并以实际持久存在为前提。
例如智能时长 `-1` 会转为计费上限，音频缺失值可能应用默认值；这些结果既不能冒充客户显式传值，也
不能证明 Provider 最终收到的参数。摘要需区分“客户请求”“计费采用”“上游报告”三类来源。

### 3.4 补齐上游诊断

保留现有上游任务 ID 展示，新增 Root 专属上游请求 ID、冻结协议和 adapter 版本投影。平台请求 ID 与
上游请求 ID 分开命名。已有任务字段可直接读取；不存在的快照不从当前配置推断，不伪造历史记录。

普通详情接口不得返回完整 Task 私有数据、凭据、Provider 原始响应或原始结果 URL；第 6 节的受保护
证据查看走独立授权和访问审计，不使用公开详情 DTO 透传。改动原生 DTO、controller
或通用弹窗前，需说明新增字段和最小接线的必要性及上游合并影响；主体提取和 Link 逻辑放新增文件，
不顺带重构原生生成、轮询、分发和计费路径。

### 3.5 实施范围

第 3 节可独立实施：利用现有任务和产物接口补齐详情，不等待全量证据系统，不为历史请求填造原文。
最终交付范围为完整音视频请求证据采集与受保护存储、按请求关联的详情查询、视频结果操作和上游诊断。
UI 字段补齐只是其中一部分，不能以完成视频弹窗宣称完成全部需求。
计价方式、实际用量与结算结果关联既有冻结计费事实，不重建账本，不因按秒计费就把 Provider 用量视为
不存在。实现可以分步进行，但全部音视频路径的覆盖清单通过前，不宣称全量覆盖。

## 4. 验证与验收

- Moxing/Seedance 成功任务且 `fail_reason` 为空，仍显示详情并可获取视频结果。
- 详情和产物快捷入口复用同一视频获取能力，普通非插件视频及插件产物不回归。
- 新增字段按普通用户、管理员、Root 在后端分级；普通用户查询不返回真实渠道 ID，用户自己的 quota
  保持既有返回行为。新增证据与应用接口拒绝未授权的跨用户/跨应用读取，账户后台按 §3.1 明确授权。
- 历史任务缺少新字段、结果地址缺失、平台地址配置错误、产物请求或播放失败均有明确反馈。
- 显式 `generate_audio: false` 保留，缺失值显示未知；请求时长不冒充实际视频时长。
- 探针不存在时不补造；计费默认音频和智能时长上限仅显示为计费参数，不作为原始请求或南向发送证据。
- 列表不预加载视频；受保护字段、原始 Provider URL 和凭据不泄露到列表、详情或通用日志。
- 代码测试采用确定性任务夹具，验证字段投影、权限及结果操作；页面人工验收覆盖成功、失败、待核实和
  缺少历史数据四类任务。真实 Provider/线上播放验收单独记录，不能以单元测试替代。
- 前端新增文案遵循项目 i18n 技能，补齐全部语言并执行相关 Bun 检查。
- 文档执行 `task docs:check` 与 `task ai:check`；若后续修改公开 API 文档，增加
  `cd web && bun run docs:validate`。

## 5. 剩余事项与边界

待实施：第 6 节完整证据采集与存储、覆盖矩阵、字段来源核对、详情视频区域接线、复制链接、Root
诊断扩展及测试。保留周期、存储容量、故障缓冲和访问权限配置需在上线前明确。
待外部确认：线上 rc23 实际提交、接口响应、前后端部署一致性及实际媒体可访问性。

本方案不修改已有归档、营销或研究文档，不执行数据回填。新请求增加证据可持久保存的受理条件，但不
调整 Provider 生成协议、已发送任务的轮询和终态语义、既有资金幂等规则。
完成后按文档治理流程另行确认事实收敛和归档。

## 6. 所有视频与音频请求的完整证据记录

### 6.1 业务验收目标

客服或运维拿到平台请求 ID、任务 ID 或消费记录后，应能回答：

1. 客户实际提交的请求是什么，字段是缺失、null、false、0 还是明确值？
2. 平台选中了哪个 Channel、Provider 模型和协议，使用哪个部署提交和 adapter 版本？
3. 映射、默认值和参数转换后，实际准备发送给 Provider 的请求是什么？
4. 网络发送进行到哪一步，Provider 返回什么状态、请求 ID、任务 ID 和内容？
5. 每次轮询或回调观察到了什么，何时成功、失败、不可采信或结果未知？
6. 平台向客户返回了什么，客户连接何时中断，结果获取是否失败？
7. 此次预扣、结算、退款或待核实状态是什么，依据哪个既有账务记录？

以音频参数问题为必测案例：北向 `generate_audio: true`，南向 `with_audio: true`，必须可在同一请求
证据页对照；若南向字段丢失，可定位丢失环节；若南向字段存在但结果无声，只能据此确认平台发送内容，
不能自动归因为 Provider 模型故障。

### 6.2 全量覆盖边界

| 请求类别 | 证据范围与关联方式 |
| --- | --- |
| Seedance ModelArk 及其他已有视频协议 | 创建前北向正文、每次实际出站、创建响应、所有轮询/回调、平台响应、结果交付 |
| NEWAPI 原生视频与视频插件 | 相同证据能力，保持其原生协议、分发和重试语义，不添加 Link 模型识别 |
| TTS `/v1/audio/speech` | 输入文本、声音/格式/语速等完整参数、南向正文、响应元信息及音频字节记录 |
| 转写/翻译 `/v1/audio/transcriptions`、`/v1/audio/translations` | multipart 文本字段及上传文件、南向实际表单、响应内容 |
| Suno 等异步音频与相关插件 | 提交、上游任务关联、轮询、生成结果和客户交付 |
| Chat/Responses/Gemini 等统一入口承载的音视频 | 按入口协议及已解析媒体类型识别，记录对应请求与响应，不能只覆盖 URL 含 audio/video 的路由 |
| Realtime / WebSocket 音频 | 会话、双向事件顺序、配置变更、音频帧、断连与关闭原因，不能只记录握手请求 |
| 结果下载、Range、HEAD | 关联生成请求，记录状态、范围、实际传输字节数、上游/客户端取消与网络错误 |

采集覆盖成功和失败请求，不采样。没有可信 Provider task ID 的提交失败、超时、请求校验失败仍需有
可查询记录；不能等消费日志或 Task 创建成功才开始记录。按原生重试规则发生的每个出站尝试独立记录，
不得覆盖前一次。Link 禁止自动重发的既有规则保持不变。

实施前逐项登记真实 Router、转换、HTTP/流式/插件发送入口和异步查询入口。尚未接入的路径必须明确列为
缺口，不能以只接通共享 HTTP helper 代表全部视频和音频均已覆盖。

覆盖按以下阶段组织，最终全量目标不变：

| 阶段 | 必须覆盖 | 明确的阶段缺口 |
| --- | --- | --- |
| 详情独立交付 | §3 现有数据投影、视频操作、Root 诊断 | 不代表已记录任何历史完整请求 |
| 证据一期 | 有限正文 HTTP 创建、JSON/multipart 音频、HTTP 音视频响应（含 SSE/分块）、视频/音频异步轮询及回调、结果代理 | WebSocket/Realtime 与尚未完成盘点的特殊直连不得算作已覆盖 |
| 证据二期 | Realtime 双向事件、Volcengine TTS 等 Provider 独立 WebSocket、全部剩余媒体传输 | 清单中仍有未验收入口时不得宣称全量完成 |

一期的接入清单至少包括共享 `doRequest`、Seedance/插件轮询直连、两套视频内容代理和 multipart
转换前后。HTTP 音频若内部实际通过 Provider WebSocket 履约，仍属于二期，不能因北向为 HTTP 就标为
一期完整覆盖。Chat/Responses/Gemini 等承载音视频的入口也按实际传输和接线测试逐项验收。

multipart 当前 OpenAI adapter 使用可复用表单解析并重建到 `bytes.Buffer`；不能把所有 multipart
路径都当作不可重读的单次流。必须分别保存转换前业务输入与重建后的南向内容，避免日志重复读取耗尽
真正不可重读的其他 reader。Realtime 当前满即跳过的通道保存转发后的副本，代码先完成消息转发，
不能据此断言网络转发丢帧；但该副本通道不能作为完整证据采集源。

最小入侵策略：索引、存储、脱敏、权限和采集器主体放新增文件；各实际 I/O 边界只增加必要窄调用。
每个原生文件接线都列出必要性、是否存在不改原生文件的替代方案、受影响路径和合并冲突面。不得为了
日志重构全部 Provider 传输，也不能用“最小入侵”作为永久遗漏困难路径的理由。

### 6.3 采集内容与真实阶段

| 阶段 | 必须保存的证据 |
| --- | --- |
| 北向接收 | 原始方法、路径、业务查询参数、必要业务头、转换前完整正文或 multipart 内容；已认证 user/app 与请求 ID |
| 履约选择 | 冻结客户模型、Provider 模型、Channel、协议、adapter 版本及部署提交；不保存认证凭据 |
| 南向发送前 | 所有参数转换及 override 完成后的实际请求正文、方法、目标及非认证业务头 |
| 传输过程 | 每次尝试序号、时间、建连/写请求进度、HTTP 状态、响应头中追踪信息和网络错误 |
| 上游响应 | adapter 解析前的响应正文；异步创建、轮询及回调分别追加，不仅保存最后一次状态 |
| 客户交付 | 归一化后的客户响应、流式事件、已写出字节及写出错误；不能把成功写 socket 说成客户已收到 |
| 计费关联 | attempt、Task、消费/退款记录及冻结账务结果引用，不以证据记录替代资金事实 |

中间 `TaskSubmitReq` 不能冒充原始北向请求；构造出的请求不能直接标成 Provider 已收到。
区分“已准备”“开始发送”“请求写出”“收到响应”“响应完整”“中断/未知”。没有响应或只有部分响应
必须明确展示，不伪造空响应或成功结果。完整性记录包含原始/已存字节数、完成标志、异常原因和校验值。

JSON 记录保留业务字段、类型、数组顺序及缺失语义；脱敏副本不是字节完全相同的原文，需明确标识。
multipart 保留字段多值、part 类型、文件名及实际文件内容；上传音频、base64 和流式媒体不能只记大小或
hash 后宣称保存了完整请求。二进制放私有对象中，通过证据索引关联，普通详情不内联大文件。

URL 型输入保存原始业务引用到受保护证据。平台本来会读取的媒体可记录当时读取的字节；平台未读取而
由 Provider 自行下载的远端素材，不为日志新增自动抓取，不声称已保存远端内容。结果仅返回 URL 时同样
明确“已记录结果引用，未归档媒体”；只有实际经过平台的媒体字节或已有结果对象才能作为内容证据。

### 6.4 存储与权限

采用“主库索引 + 私有加密对象”的证据存储：主库负责请求、用户/应用、attempt/Task、时间、事件序号、
对象引用和完整性状态；正文、表单文件和响应媒体进入私有对象存储。证据仅描述发生过的输入输出，
不得成为任务状态、资金或重放许可的第二事实源。

对象存储底层能力经独立核验后才可复用，并使用独立命名空间、访问策略和保留策略；不得复用公开产物
下载授权暴露原始请求。当前工作区存在其他任务尚未提交的 S3 实现，不把它视为已上线依赖，也不在本轮
文档工作中修改其代码。

复核时区分通用 `TaskArtifactStore.Persist` 与图片 `PutImageObject`：前者缺少生产调用不能证明所有
写路径缺失；当前图片输入和结果已有后者调用。反过来，存在代码调用也不代表真实存储闭环验收通过。
接入前分别验证写入/读取、私有权限、加密、故障与清理，核对遗留“未来预留”注释和实际实现，不能用
过时注释替代判断或把图片存储验收自动等同于证据存储验收。

用户本轮明确要求保存完整音视频业务请求，取代本方案此前“仅保存少量参数”的限制。落地时需同步
收敛硬约束和相关架构文档：新增受保护证据存储的明确例外，通用日志、Task/attempt 字段和公共接口的
敏感数据限制继续成立。不扩大到素材控制面或其他无关请求，不创建客户素材所有权/资源管理系统。

Authorization、Cookie、API Key、支付凭据和代理认证不保存，使用脱敏占位，保持字段存在性。
业务提示词、模型参数和素材引用需要保留；签名素材 URL 仅可加密保存在受保护正文中，普通界面默认
遮盖签名部分，导出必须具备原始证据权限。Provider 响应中的认证凭据同样剔除。脱敏规则必须避免把
合法 `max_tokens` 等业务字段误当密钥删除。

默认普通用户只查看自己的任务摘要及输出；受授权支持人员查看脱敏业务证据，Root 或单独授予的原始
证据权限才可访问完整业务内容。每次查看、下载和导出记录操作者、目标、时间和操作，不记录正文。
后端强制 user/app 边界与管理授权，查询列表不带正文，不允许凭可猜测任务 ID 获取对象。

保留期必须可配置，待部署决策后固化；可评估普通记录 30 天、异常记录更长的容量成本，但这些数字不是
当前已接受或已实现的合同。清理需要考虑进行中的任务、未解决工单和对账记录；不自动清理现有生产
数据。正文过期后保留允许保留的索引和明确“正文已过期”状态，不能显示成从未收到请求。

### 6.5 证据持久化、资金顺序与故障处理

#### 6.5.1 有 attempt 的视频 Link 路径

现有 `PrepareTaskCreateAttempt` 先保存 prepared，再以事务提交 hold、必要 reservation 和 sending，
随后 `BuildRequestBody`，最后经共享发送入口调用 Provider。采用保留该主顺序的最小接线方案：

1. 北向认证及必要大小检查后，在正文改写前保存完整北向业务证据；生成独立请求证据 ID。没有 Task
   或 attempt 时也可检索。证据写入不可用则拒绝出站，不创建资金 hold。
2. 按既有流程验证、选渠及冻结计费，调用 `PrepareTaskCreateAttempt`，将证据索引关联 attempt。
3. 完成 `BuildRequestBody` 及最终请求构造，保存最终南向证据。对象写入在 hold 事务外执行，不持有
   数据库事务等待网络存储；不得在此之后再次改变业务正文而不更新证据。
4. 确认证据已提交、请求未取消及既有发送许可有效，才调用 `MarkTaskCreateAttemptUpstreamStarted`
   并进入实际传输。一次本地发送标记不能证明 Provider 已收到请求。

hold 后、实际发送前，证据写入或关联失败时，必须返回本地不可重试错误并阻止换渠，进入既有
`ReleaseRejectedTaskCreateAttempt` 释放路径。只在当前执行能确认从未进入传输时如此处理；不要先
设置 upstream-started 再尝试保存证据。当前 controller 已有失败释放出口，应复用其幂等处理并测试
不与通用预扣退款重复；不是新增一套资金补偿。

释放失败不能宣称已退款，也不能只写一行错误后丢失处置线索。返回可关联请求 ID 的失败，保存可用的
证据/attempt 关联与告警，余额状态以主库为准；按既有对账与人工核实路径处置，不自动重发。记录存储
本身故障时只保证错误与可用索引可追踪，不能承诺故障期间仍生成完整正文。

#### 6.5.2 hold 后的崩溃窗口

若进程在 hold/sending 提交后、开始发送前崩溃，仅凭重启后缺少南向证据或发送事件，无法证明未调用
Provider。当前恢复逻辑把遗留 sending 转为 unknown；本方案保留该保守语义，不依据证据缺失自动
退款或重发。人工核实已未发送的情况走既有释放入口。

该窗口是保留原状态机的明确代价，不能宣称记录系统能消除所有未知结果。若后续需要自动区分它，须
另行设计与实际发送许可原子衔接的耐久边界，不能以第二套“日志状态”冒充事务事实。

对象写入超时、并发恢复和取消需在接线前做时序测试：存储等待必须有界，并与 attempt 的恢复扫描窗口
协调。恢复已把 attempt 改成 unknown/rejected 后，不得继续发送；沿用或最小补齐既有发送许可校验，
不能以进程内未设置 upstream-started 代替耐久许可。

#### 6.5.3 无 attempt 的音频与原生路径

TTS、转写、Suno 和原生 Chat 等路径不因记录证据就建立视频 `TaskCreateAttempt`。证据索引用平台
请求 ID 和尝试序号建立，已有 Task/消费记录产生后再关联，不创建伪视频任务。

尽量在原生预扣前保存北向证据；最终南向证据保存失败时，不执行 Provider 请求，返回明确本地不可
重试错误。若原生预扣已发生，复用该路径自己的退款/额度释放出口并验证只处理一次；释放失败需保留
可追踪告警，不调用仅适用于视频 attempt 的释放函数，也不向客户承诺退款已完成。

原生允许重试的正常上游失败仍按原规则执行，每次实际尝试独立采集；证据系统自身不可用不是自动
切换 Channel 的理由。发送后发生的未知结果、进程恢复与资金处理继续由该原生路径决定，不因日志
强行套用 Link 的状态机。

#### 6.5.4 响应与流式故障

流式/Realtime 无法在会话开始前拥有全部正文，采用分块追加与有界持久缓冲。不能无限内存缓存或为了
日志先读完整流再转发；在真正接收/发送边界采集，不依赖可丢弃副本通道。二期接入前必须明确每条
流的持久缓冲容量、写入时限和背压策略，并在对应传输实现中测试缓冲满、磁盘满、断连和退出恢复。

Provider 已发送后发生的证据写入故障，必须标记记录不完整并告警，优先保存已获得的可信业务结果与
Task/资金事实；不得为了补日志自动重发、退款或把成功任务改成失败。客户端断开后，已接收的响应证据
使用有界的独立持久化流程收尾；不承诺在进程崩溃或网络断开时仍获得未接收到的字节。

先明确支持的请求/文件大小、会话时长及持久缓冲容量，记录限制不能静默截断合法业务请求。超限必须
在可拒绝的边界给出明确结果；已执行中的异常显示具体缺失范围和原因，不能标记为“完整”。完整记录
成功请求很重要，因为参数错误和交付争议常常发生在任务状态成功之后。

### 6.6 详情与客服操作

在任务详情和音频消费记录中提供同一“请求证据”入口，支持按平台请求 ID、任务 ID、上游请求 ID
检索；无 Task 的失败请求也可检索。详情分为客户请求、上游请求、上游响应、客户响应和事件时间线。

默认展示可读的脱敏业务内容，可对照关键参数并展开完整内容；原始业务内容和媒体按权限下载。
查看界面不重新调用 Provider，不提供默认“一键重放”。对照可以展示确定性结构差异，但不能猜测
Provider 内部行为或用模型推断缺失请求。客服导出仅包含其获授权的证据和确定事实。

### 6.7 必须通过的验证

- 使用用户的 `generate_audio` 请求，验证转换前记录为 `true`，最终 Moxing 出站记录为
  `with_audio: true`；`false`、null、缺失及其他可选零值分别验证。
- 使用本地假 Provider 捕获实际接收内容，与南向证据对照；验证模型映射和最终 override 之后采集。
- 成功、4xx/5xx、连接失败、发送后超时、解析失败、无可信 task ID、客户端取消均可检索，阶段状态准确。
- 轮询、回调、原生重试和多次内容下载分别追加；任务和账务仍按原有幂等、unknown 与冻结事实处理。
- JSON、multipart 文件、base64、TTS 二进制、SSE 及 WebSocket 音频验证内容/顺序/完整性和不破坏转发。
- 脱敏覆盖头、查询和嵌套正文中的认证凭据；业务参数不误删，普通日志和无权限响应不包含正文。
- 对象写入失败、缓冲满、进程中断与保留期清理有明确结果，不重复发起付费请求。
- attempt 的 prepared/held/sending、证据写入、实际发送之间逐个注入失败；确认未发送时释放只执行
  一次，释放失败不伪报退款，崩溃后 sending 按 unknown 处理，不凭证据缺失自动退款。
- 慢存储与恢复扫描并发时不得绕过发送许可；无 attempt 路径保持各自预扣释放和重试合同，证据故障
  不触发付费重试或换渠。
- 验证真实渠道 ID 不进入普通用户查询、新增诊断严格分级、本人 quota 保持原接口语义。
- Realtime 的转发消息与缓冲副本分别验证；证据不能因为副本通道满而静默缺失，也不得宣称已归档尚未
  收到的媒体字节。
- 每个视频/音频入口及 Provider 特殊传输的覆盖矩阵验收通过后，才可宣称全量记录；真实存储与生产
  灰度验证另行记录。

### 6.8 实施顺序与当前状态

第 3 节详情可独立推进，权限按 §3.1、新旧参数来源按 §3.3 验收。第 6 节按以下闸门实施：

1. 设计准备：完成入口/传输覆盖矩阵和原生文件接线清单；明确 §6.5 的 attempt 与非 attempt 失败
   出口、存储超时和恢复窗口；固化保留周期、容量、权限与加密方案。未定项不得隐含为默认实现。
2. 证据一期：独立核验存储后，实现索引、受保护读写、北向和最终南向采集；接入 §6.2 一期 HTTP、
   轮询/回调及结果代理，完成请求对照与客服查询，验证存储故障和账务释放。
3. 一期验收：逐项记录已覆盖 Provider 与入口、实际接收内容对照和媒体交付结果。明确列出 Realtime、
   Provider 独立 WebSocket 和其他未接通路径；一期可交付，但不得宣布全量完成。
4. 证据二期：为每套 WebSocket/Realtime 拨号和双向循环完成窄接线，落实缓冲、背压与完整性策略，
   验证实际转发不被破坏；补齐所有剩余入口。
5. 全量验收：覆盖矩阵无未验收项，真实对象存储及生产灰度通过后，才宣称全部视频/音频请求接入。
   各阶段已验证事实按文档治理收敛，未完成事项明确保留，不能以 UI 上线或共享 helper 接通代替验收。

当前状态：第 3 节详情与证据一期（含覆盖矩阵、接线清单与配置决策）已实施，见
[实施记录](2026-09-05-任务日志视频详情与证据系统实施记录.md)；二期 Realtime、Provider 独立
WebSocket 与剩余媒体入口未实施。历史未记录的请求不可恢复，本地复现或当前代码不能
替代当时实际请求，客服必须明确区分已有事实和推测。
