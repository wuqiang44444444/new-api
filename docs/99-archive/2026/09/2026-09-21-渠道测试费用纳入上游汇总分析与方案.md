# 渠道测试费用纳入上游汇总分析与方案

> 用户已确认按本次分析更新文档。代码方案已于 2026-09-21 本地实施并通过回归（见文末实施记录）；
> 最新本地恢复率及同范围复核见文末与[历史渠道测试核查](2026-09-21-历史渠道测试未纳入金额原因核查.md)；
> 真实供应商账单与生产部署验收仍未完成，不代表生产已发布。
> 当前行为以[产品说明](../../../10-product/客户与上游对账单产品说明.md)和
> [对账架构](../../../20-architecture/账单计费-客户与上游对账架构.md)为准。

## 问题与目标

上游对账多次出现“743 次渠道测试仅计入用量”等提示。测试调用已经产生上游用量，部分日志也保存了
计算费用，但金额汇总统一排除了测试，导致用量和参考金额覆盖范围不同。

2026-09-21 用户进一步要求：渠道测试应纳入上游费用，并核查缓存读写、视频秒数／图片张数以及
历史价格缺失提示。本次扩展本方案，统一处理费用覆盖、计量证据和错误原因展示；代码已实施，以下历史分析用于解释需求；最新修复与验证见文末。

目标是将有可靠历史计价依据的渠道测试费用纳入上游原价与渠道折后参考金额，并在汇总、明细、导出及
日／周上游统计中使用一致的金额依据。客户账单、客户用量视角和钱包继续排除原生渠道测试；测试费用
只用于平台上游参考展示，不成为客户扣款、已核实供应商成本或应付金额。

“743”来自用户反馈，尚未读取对应实际记录，不能据此宣称全部可以恢复金额，也不能据此判断存在
743 次失败、重复调用或重复扣费。
本轮已另行核实本地 9 月数据的 22376 条测试记录，见下文；两次反馈的筛选范围不作等同处理。

## 当前实际情况

### 测试费用不能直接套用客户原价还原公式

- 普通倍率测试使用输入、输出及模型倍率的简化公式，固定单价测试使用模型单价；这两条测试路径
  没有乘客户分组倍率。现有客户原价还原会除以历史分组倍率及合同折扣，直接复用可能重复放大金额。
- 表达式测试复用现有表达式结算，结果可能包含分组倍率。表达式失败时还可能采用预估费用；日志有
  `Quota` 不等于已经按实际用量成功计价。依据见[表达式结算](../../../../service/tiered_settle.go)。
- 普通倍率测试的简化公式未完整体现缓存读写等差异价格；即使日志保留了缓存用量，也不能据此把
  简化结果声明为完整官方原价。依据见[测试用量记录](../../../../controller/channel_test_usage_log.go)。
- 流式测试缺失有效 usage 时可能退回估计输入 Token，不能只凭存在 Token 数值认定是实际计量。
- 新旧日志的价格、倍率、计量、表达式执行结果覆盖尚未按实际数据盘点。不得根据当前配置、模型名、
  相邻记录或“通常为 1”的假设补造历史事实。

### 2026-09-21 本地只读核查

环境为本地工作区 SQLite `one-api.db`，以只读连接扫描上海时区 2026 年 9 月已有数据；
通过当前 `ScanUpstreamBillingDetails` 解析入口累计质量计数，准确复现用户反馈的五个数字。
核查未调用真实 Provider、未修改日志或资金，也未证明当前部署与本地代码版本一致。

| 提示 | 复现数量 | 已核实原因 |
| --- | ---: | --- |
| 渠道测试不计金额 | 22376 | 月度上游及日／周上游代码仍按测试身份直接跳过金额计算 |
| 历史缓存读取无法确认 | 9769 | 缺字段或图片旧零值缺少字段存在性证据；同时混入任务创建预扣等非最终计量记录 |
| 历史缓存写入无法确认 | 62259 | 缺少缓存写入字段或存在性证据；同样混入任务创建预扣等记录 |
| 缺少秒数或单位 | 698 | 全部使用含 `_task.duration_seconds` 的旧表达式，日志均未保存 `usage_facts`、`usage_units`；时间为 9 月 5 日至 9 月 13 日 |
| 缺少历史价格或折扣 | 1 | 日志 134870（9 月 10 日 18:02:02）实际返回 `auxiliary_charge`，保存了价格／折扣字段及工具附加费明细；被笼统归入价格缺失 |

缓存两组缺失计数均包含 681 条任务创建预扣、2206 条任务结算调整。681 条已核实为
`is_task=true` 且无 `image_count` 的创建记录，不是图片完成日志借用 `create` 事件的情形。
2206 条调整记录是否与其他最终用量重复，尚需按可靠 Task 关联逐项核验，不能直接全部删除。
这些数字是当前代码下的日志行计数，不等于独立请求数，也不能在父子分组或读写两类之间再次相加。

代码中的“历史”按证据字段是否存在分类，不检查记录日期；新记录漏写字段也会进入此类。
因此不能把全部缺失都归因于旧数据，或认定新采集路径已经完整。

## 优化方案

### 1. 目标金额口径

| 项目 | 目标处理 |
| --- | --- |
| 请求数、实际 Token 等用量 | 沿用已有上游范围与计量证据规则，不因金额不可恢复而删除调用 |
| 测试原价 | 使用测试发生时的可靠价格、用量及计价结果，剔除客户分组与合同折扣影响；已知原价可进入上游原价汇总 |
| 测试折后参考金额 | 对逐笔测试原价应用对应账期的渠道月度综合系数 |
| 客户账单与钱包 | 继续排除原生渠道测试，不追加扣款、退款或余额流水 |
| 价格或计量依据不足 | 保留用量，金额未知并说明原因；未知不变成零，也不计入完整总额 |
| 明确零费用 | 只有历史价格与计价结果能证明免费时显示零；`Quota=0` 本身不足以证明免费 |

```text
逐笔测试原价 = round(依据当次计价事实得到的折前原价，1 quota)
逐笔测试折后参考金额 = round(逐笔测试原价 × 渠道对应月份系数，1 quota)
上游原价汇总 = 原有非测试原价汇总 + 可确认测试原价合计
上游折后参考金额 = 原有非测试参考金额 + 可确认测试折后参考金额合计
```

沿用半值远离零的舍入方式，各层仅累加同一逐笔结果，不对父级再次计算折扣或舍入。金额存在未知项时，
保留已知小计并将完整总额标为不完整；不得让有测试但无可靠金额的渠道继续被当作总额完整性的例外。
未配置渠道折扣沿用默认 1，历史迁移冲突仍待确认。

普通消费和退款的现有金额规则不在本次重定义。月度对账与日／周统计保留各自现有时间归属、生命周期
和退款范围；共享测试逐笔金额依据，不强行要求不同统计范围的总额相同。日／周跨月时逐笔使用归属
月份的渠道系数，不把整周都套用同一个月份。

### 2. 新测试记录与历史恢复

新测试应复用现有权威定价引擎和计量归一化，在测试费用记录边界保存足以解释的折前原价、计价模式／
版本和计算状态，区分成功按实际用量计价、仅有预估结果和计价失败。请求条件、分组及合同影响不能
依靠查询时的配置还原；不为此另建价格表、客户结算账本或保存原始请求、Provider 响应。

表达式、普通倍率、固定单价分别按各自可靠事实生成同一测试金额投影。原价不得依赖测试管理员所属
分组；免费分组不能使有成本的测试原价消失。对于表达式，优先利用引擎已有折前结果，不从已经舍入
甚至为零的折后费用强行反推；计算失败或预估用量不能冒充已知实际金额。

历史恢复只读进行，先核实样本与记录形成路径，再分类处理：

1. 历史价格、用量和成功计价依据充分：按对应计价模式恢复原价；涉及已舍入费用反推时保留估算说明。
2. 只有简化费用、预估结果，或不能确认倍率是否已应用：保留待核算状态，不直接把 `Quota` 当作原价。
3. 缺少必要价格或计量：保留未知及具体缺项，不用当前价格回算，不补写旧日志。

历史恢复与新记录统一使用一个测试金额解析入口，不增加兼容别名、双写账本或另一套表达式引擎。
本方案不要求所有历史记录都能恢复金额；实际恢复比例以脱敏样本盘点结果为准。

### 3. 查询、展示与导出

- 上游汇总、逐笔明细、汇总导出、逐笔导出、日／周上游统计及导出复用同一测试原价与状态结果，
  不在前端根据 Token 和当前价格补算。
- 测试已计价时可显示“{{count}} 次渠道测试已计入参考金额”；部分缺失时分别显示已计价数与待核算数。
  数字必须来自当前筛选范围，不能固定使用反馈中的示例值。
- 纯测试渠道在价格证据充分时也应有金额；“仅计用量，无结算金额”不再统一适用于所有测试。
  参考金额与客户结算金额的名称需要区分，不能把测试标为客户已付费用。
- 测试类型、原价来源及未知原因保留在明细和导出中。测试身份不再自动导致金额被排除；计量缺项与
  金额可用性仍独立展示，不把可选缓存字段缺失自动解释为计价失败。
- 层级提示说明各自范围，父子统计不重复相加。已经生成的导出文件不回写，新导出记录当次系数与版本。
- `usage_without_amount_rows`、`UsageOnlyRows` 和 `usage_only` 等现有字段的消费者须一并核对，避免
  只取消后端排除后，页面、完整性判断或导出仍按“所有测试无金额”解释。

### 4. 缓存计量的统计对象与缺失分类

先修正统计对象，再讨论历史字段能否恢复。缓存质量统计以应承载最终实际用量的记录为对象，
不能对所有 Token 计费日志无差别要求缓存字段。

- 排除真正的任务创建预扣；不能仅凭 `task_billing_event=create` 排除，现有异步图片完成日志也使用
  此事件值，须结合已有执行事实区分。普通退款不新增缓存观测。
- 结算调整按可靠 Task／交付关联承载最终用量，同一最终用量只计一次缺失；不能把调整行都当成
  独立请求，也不能统一丢弃。没有可靠关联的历史行保持覆盖限制，不凭金额或相近时间合并。
- 沿用现有计量归一化与事实解析入口，区分明确零、已知非零、历史未保存、上游明确未返回；
  “不适用”必须有发生时协议或冻结事实的明确依据，不能用缺字段或当前模型名代替。
- 无字段存在性证明的旧图片零值保持未知；有明确存在性证明的零值保留为零。不得为了消除提示
  把未知补零，也不能把图片旧默认零当作缓存未命中。
- 对新增请求逐路径检查 Provider 返回、DTO 归一化、Task 持久化和日志投影；新记录缺少应有证据
  属于采集覆盖问题，不能仅以“历史问题”解释。复用现有字段，不新增平行计量账本。
- 缓存计量完整性与金额可还原性分别显示。修复后对同一数据截止范围重新统计并说明减少原因，
  不要求质量计数必须降到零，也不将 9769／62259 固定写入业务逻辑。

### 5. 视频秒数、图片张数与历史时长恢复

业务用量单位与计费方式分开表达：视频时长为秒，图片数量为张；图片可同时报告 Token，视频也可能
按 Token 计价。不能仅依据 `billing_mode`、模型名称或当前价格决定该记录有哪些实际用量。

本轮 698 条的旧表达式已能证明时长单位为秒，但不能证明实际生成了多少秒。处理顺序：

1. 使用稳定 Task 身份检查已有完成事实，区分请求／预算时长和可信完成时长；按现有冻结合同读取，
   不输出 Task 私有数据，不增加任意历史 decoder 或按模型名猜测的回退路径。
2. 有可信完成值及明确单位时只读投影；只有已知单位、没有完成值时提示“历史实际时长未记录”，
   不再笼统暗示单位也未知。不能从金额反算或把预算时长直接当实测值。
3. 对图片读取已记录的实际张数，不能用请求次数当张数；缺失时提示“实际图片数量未记录”。
   对其他确实缺单位或存在多计量歧义的记录单独说明原因。
4. 核查新任务完成与交付路径是否完整保存既有实际计量及单位，防止新增同类缺口；有保留预算值的
   结算逻辑时，结算成功本身不构成该值为实测的证明。

目前仅确认 698 条日志缺项，尚未证明关联 Task 能恢复多少条。实施后分别报告可恢复数、不可恢复数和
阻断原因；不补写旧日志、不改变 Task 生命周期、结算结果或钱包。

### 6. 原价还原失败按实际原因展示

日志 134870 的唯一解析阻断原因是 `auxiliary_charge`，不是缺少历史价格或折扣。
当前 `MissingHistoricalPriceRows` 接收全部原价还原失败原因，造成语义混用。

- 复用现有 `EstimateReasons`，按实际原因区分缺分组倍率、合同证据不足、事实冲突、附加费不可拆分
  和金额越界等情况。汇总、逐笔、前端与导出采用同一分类；一条记录有多个原因时，总缺失行数只计一次。
- 该记录应提示“包含工具附加费，原价暂无法完整还原”；真正缺少价格／折扣证据的记录才使用对应文案。
- 在已有工具明细与冻结定价语义能独立证明模型费用、工具费用及各自倍率时，再分别还原并汇总；
  核验前保留已知净额与附加费原因，不能对整笔费用统一除以模型折扣，也不能忽略附加费。
- 工具明细已有次数和价格，不代表本轮已证明其单位、倍率和舍入依据足以完整还原；这是后续核查项。
  不使用当前工具价格补算，不修改客户已结算金额。
