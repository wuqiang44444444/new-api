# 使用记录与客户账单优化方案

> 后续实现说明（2026-09-19）：早期“自动复用尚未交付”的记录仅描述当时状态。当前同范围、同来源版本、同存储身份且未过期的成功导出可按既有权限复用；Task/Log 修订失败或来源不完整时不复用。当前合同见[对账架构](../20-architecture/账单计费-客户与上游对账架构.md)，本轮修复见[修复记录](2026-09-19-账单启动与邮件评审修复记录.md)。

## 问题与目标

本文记录本次需求讨论形成的实施方案，并用文本图说明页面、费用解释与导出交互。
本文保留方案与阶段实施记录。2026-09-17 评审修复后的实现和验证边界见第 17—19 节；第 19 节为最新复核，早期阶段记录不能替代该节的验收结论。文中目标和参数建议不代表目标部署已完成性能验收。

### 1. 客户要解决的问题

1. 单笔算得清：能够从实际用量、命中单价、分组倍率和合同折扣理解扣费。
2. 优惠看得明白：知道哪个组、哪份合同参与优惠，最终打几折，总共减免多少。
3. 月底对得上账：导出的结算明细、折扣组合小计和月账单在相同数据范围内可以核对。
4. 大量导出不拖慢核心业务：异步支持超过 10 万条，10 万条作为首轮验证规模；通过并发、速率和查询预算控制数据库压力。

### 2. 用户已经确认的决定

| 项目 | 已确认要求 |
| --- | --- |
| 使用记录 | 增加明确的分组、合同及最终折扣展示 |
| 费用详情 | 展示“用量 × 单价 = 金额”，覆盖 Token、按次、按秒；复杂公式不得伪装成简单等式 |
| 折扣顺序 | 模型折前费用 × 实际有效组倍率 × 当次生效的合同模型折扣 |
| 原价基准 | 采用实际命中的计费阶梯，不把阶梯与其他基准价的差额算作优惠 |
| 月账单折扣 | 按实际折扣组合分开展示，不能用单个折扣代表整月所有消费 |
| 优惠金额 | 显示总优惠；退款同时冲回对应优惠，跨月退款计入退款发生月份 |
| 展示语言 | 主要显示“5 折、3 折、最终 1.5 折”，同时保留 ×0.5、×0.3、×0.15 |
| 历史信息 | 能证明才展示；反推明确标注估算；缺失显示未记录，不拿当前配置补算 |

| 导出规模 | 异步支持超过 10 万条；不再以 100,000 条为产品硬上限，不截断交付 |
| 产物保存与复用 | 完整导出文件保存到私有 OSS；权限、条件、格式和可靠数据版本一致且文件有效时复用 |
| 数据库保护 | 核心调用与结算优先；导出必须限制并发、读取速率和查询资源，不因异步而无界扫描 |
| 两端对齐 | 我的账单与管理员客户账单共用主体、金额解释和导出规则；管理入口负责选择客户与权限 |
| 按钮位置 | “下载账单”放在账单月份选择器前面 |

### 3. 方案建议与范围边界

异步导出、私有 OSS 文件复用和数据库保护方向已确认。以下具体参数仍是本方案建议：CSV 格式、
每人一个未完成的源数据读取申请、全站一个源数据读取执行槽、小容量队列、文件保留期限。需经验证后固化。

第一版不承诺未经验证的千万级容量，不做跨客户批量打包、PDF 发票、XLSX 多工作表、长期报表归档、新消息队列集群、

### 2. 必须沿用的计费事实

- 合同是 **API Key 绑定的合同**对精确客户模型提供的折扣，不是“用户有一份合同就全部生效”。
  同一个用户可以有多份合同，不同 Key 可以绑定不同合同。
- 分组倍率取当次实际有效原生倍率，包括已生效的用户专属倍率；专属倍率与普通倍率不是两层再次相乘的折扣。
- 合同只作用于模型费用小计；工具费、违规费等附加收费不参与合同折扣，按原实现保留实际收费。
- 异步任务按冻结事实结算。预扣、补扣、退差额和终态用量不是多次独立调用；零差额完成日志也可能有最终用量。
- 原生 Token 表达式与 Task usage 表达式的单位换算不同，不能统一对所有表达式再除一次百万。
- 缓存、图片和音频子类是否从基础输入/输出扣除，由实际表达式及用量语义决定，不是固定减法。

## 优化方案

### 1. 金额与折扣的统一解释

#### 1.1 单次模型费用

```text
实际计费用量 + 当时命中单价/阶梯 + 已冻结请求计价规则
                              |
                              v
                         模型折前小计 B
                              |
                  × 实际有效分组倍率 G
                              |
                   × 当次合同模型折扣 C
                              |
                              v
                    模型折后金额 B × G × C
                              |
                + 按原规则收取的附加费用 A
                              |
             按既有 quota 换算与舍入规则入账
                              |
                              v
                 实际扣费：以资金/结算日志为准
```

没有附加收费且不涉及舍入时：原价为 B，优惠为 B − B×G×C。
附加收费完整可分离时：展示原价 B+A，并单列 A“不参与合同优惠”；不能对总费用再次乘合同折扣。
A 表示按原收费规则确定的实际附加金额，不意味着本次修改附加费用自己的组倍率规则。
请求计价规则产生的系数属于形成 B 的过程，不混入分组与合同优惠，不隐藏在等式中。

实际落账经过舍入时，详情展示未舍入计算结果、可证明的舍入调整和实际扣费；不得把舍入差额冒充额外合同优惠。
账单展示仍满足“展示原价 − 展示优惠 = 实际净额”，并说明优惠净额可能包含已展示的入账舍入影响。
只有倍率与已舍入 quota 的历史记录继续标“估算原价/估算优惠”；不能宣称新增前端算式让历史金额变精确。

#### 1.2 合同与分组的展示状态

| 事实 | 客户展示 | 计算处理 |
| --- | --- | --- |
| 当次组倍率 0.5、合同 0.3 | 企业组 5 折 × 年度合同 3 折 = 1.5 折；同时显示 ×0.15 | G×C |
| 明确未适用合同 | 未适用合同优惠 | 计算中的 C=1，不伪装成生效合同 |
| 明确适用合同但倍率 1 | 合同名称：无额外折扣（×1） | 保留适用事实 |
| 合同倍率已知、名称未冻结 | 合同优惠 3 折；历史名称未记录 | 不查询当前 Key 绑定反推历史名称 |
| 折扣是否适用无法确认 | 合同优惠：未记录 | 不用缺失值自动构造“无合同” |
| 组倍率大于 1 | 组倍率 ×1.2（加价 20%） | 保留真实系数，不称“12 折优惠” |
| 明确零价或零倍率 | 免费/零收费，并解释已知来源 | 不通过除零反推原价 |

普通组倍率与用户专属组倍率只显示最终实际生效的一项，并注明“专属组价”等来源。
表格列标题建议使用“分组折扣/倍率”，避免把所有倍率都解释成优惠。
折扣名称来自发生时冻结的客户可读事实；不暴露合同内部规则中的渠道、Provider 或路由组配置。

#### 1.3 月账单、退款与数据质量

- 每笔消费和退款按各自日志时间归属自然月，沿用 Asia/Shanghai；跨月退款不改写原月。
- 净额 = 累计扣减 − 累计退回。由于可能包含未完成任务的预扣，页面不把所有净额称为“已最终结清”。
- 折前金额、优惠冲回都保留符号；退款月份可能出现负净额、负原价和负优惠，不能截为零。
- 同一月、同一模型、同一 API Key 也可能出现多种折扣组合，必须继续拆分。
- 折扣组合按历史有效组事实、合同身份/版本（已知时）、倍率、适用状态和数据质量区分；不能只按当前名称合并。
  身份缺失但倍率相同的旧数据只能汇总成明确标注“历史身份未记录”的组合，不能指定某份合同。
- 总体金额的唯一计算入口仍在后端。顶部金额、API Key/模型树、折扣组合视图只是同一批事实的不同投影，不能相加两次。
- 任一行原价未知时，所属汇总原价和优惠总额显示“无法完整计算”；已知部分可以另列“已知部分”，不能冒充全部。
- 全部已知但部分为估算时，汇总也标估算；实际净额不因此变成未知。
- 若净优惠小于零，依事实标为“净加价”或“优惠冲回”，避免展示无法理解的“节省负数”。

#### 7.1 任务模型与复用边界

拟新增轻量 `ExportJob` 保存每次用户申请和文件交付状态；现有 `SystemTask` 只负责唯一导出调度器的唤醒、
租约与调度，不为每个客户发明一个 task type，不放松现有同类型互斥，不挤占 Provider 轮询的类型锁。
一个调度周期按预算处理任务，不能让永不退出的循环占据调度设施。

| 申请字段组 | 拟保存内容 |
| --- | --- |
| 身份与权限 | 不透明 job ID、发起用户、受信应用范围（已有时）、目标客户、导出类型、权限视图 |
| 条件 | 规范化筛选、时间区间/时区、语言、字段版本、币种与展示换算设置、可靠源数据版本 |
| 生命周期 | queued/running/succeeded/failed/cancelled/expired、创建/开始/完成/过期时间、取消请求 |
| 执行 | 执行代次或租约标识、读取边界、已扫描/匹配/写出条数、脱敏失败原因 |
| 交付 | 私有产物引用/文件清单、文件字节数、校验摘要、行数、生成时的金额质量说明、是否复用 |

不在任务行保存整批日志、原始请求体、密钥、管理员 other 原文或长期签名 URL。
任务的唯一持久状态由主数据库维护；缓存只能加速读取，不能成为任务或队列的唯一事实。
配额与领取全部在主数据库内原子化，不需要主库与日志库之间的分布式事务；三种关系库兼容性与源数据跨库
可见性是两个不同问题。源数据版本见8.3。受理机制拟固定为：

1. 个人申请与物理生成工作分开关联；共享工作保存唯一执行进度、租约与生成状态，申请保存各自权限、取消和交付状态。
   需要读源数据的未完成申请使用可空唯一 `active_key`，值按发起用户生成，不因目标客户或应用不同绕过用户限额；
   终态置为NULL。沿用现有SystemTask的可空唯一键模式，不使用数据库专属的条件/局部唯一索引。
2. 预建3个固定容量槽位。新增物理生成工作时，在同一短事务内以“槽位空闲”为条件更新占槽，检查影响行数，
   创建工作和个人申请；配额冲突或无空槽则整体回滚。相同可信版本的工作以规范化条件键唯一去重，已有工作可关联
   新的授权申请而不重复占槽。生成去重键仅约束活动工作，终态清空；显式重新生成使用独立尝试标识，仍受同一配额。
   槽位以固定主键幂等初始化；版本不可信时只处理本人重复提交，不跨申请宣称数据相同。
3. 唯一冲突后回滚并重新鉴权、比较完整规范化条件：本人相同申请返回原记录，不同申请返回忙碌；
   不能把唯一冲突一概当作成功。共享工作关联、最后一个申请取消与工作终态转换必须相互串行化。
4. SystemTask独立类型租约约束全站一个读取执行器；领取与发布同时校验工作状态、执行代次和租约。
   仍有其他有效申请时，取消只解除本人的等待并原子释放本人的配额，继续共享工作。
   最后一个申请取消后请求停止读取，在实际停止前保留物理工作占槽、个人配额和取消中状态，避免反复取消制造后台扫描。
5. 确认读取已停止后，在同一主库事务中结束工作并释放容量槽与对应个人配额；工作失败、进程恢复和重复完成均须幂等。
   不因租约超时直接释放执行资格并叠加旧查询；恢复约束见7.2。

行锁调用统一使用 `lockForUpdate(tx)`，但不以SQLite上的空操作充当互斥保证；唯一约束、条件更新及事务回滚共同
保证正确性。SQLite写冲突仅允许有界重试整个短事务。可空唯一键、并发占槽和失败回滚必须在SQLite/MySQL/PostgreSQL
分别验证，不把现有SystemTask使用此模式视为本功能已验收。事务中不扫描日志、不上传文件、不锁客户资金行。
资源按发起人及已有受信应用边界隔离，管理员权限与目标客户范围另外校验；不凭任务 ID 猜测所有权。
产物元数据与个人申请分开：同一客户的安全文件可以被多个已授权申请引用，申请权限与状态不能共享。
取消单个申请不能删除其他有效申请引用的产物；产物保留期由其生成时间决定，反复下载不自动无限续期。

#### 7.2 任务状态与恢复

```text
queued --> running --> succeeded --> expired
   |          |
   |          +----> failed
   |          +----> cancelled
   +---------------> cancelled / failed（排队超时）

failed / cancelled / expired --用户重新生成--> 新job
```

取消独占执行工作先登记取消请求，执行器在当前短批次结束时退出，删除/作废未发布产物；共享申请遵循7.1的解除关联规则。
进程退出后 queued 任务仍存在；running 租约过期后第一版标为失败、允许用户重新生成，暂不做复杂断点续传。
任务完成使用执行代次/租约条件更新，旧工作进程不能发布已取消或已失去租约的文件。
新执行器领取工作前必须确保旧读取操作已经受到数据库超时/取消约束；仅租约过期不等于旧查询已停止。
执行中的短时资源等待可保留 running 状态及明确的 waiting_resources 原因；释放数据库连接，
仍受任务总时长与取消控制，不新增一个无期限暂停状态。进程重启恢复与资源等待不等同，第一版不承诺断点续传。

#### 7.3 防止阻塞核心业务

异步不会自动隔离数据库、CPU 或 IO。第一版需要同时落实：

1. 全站导出并发独立限制，日志读取池建议最多一个活动连接，不与核心查询/结算连接池混用；
   多实例的连接总量也必须纳入部署预算，不能每个实例各开一组大连接池。
2. 每批通过索引限定客户、时间和游标；取完批次释放 Rows 和连接，不持有整次导出的长事务。
3. 避免 OFFSET 深分页、每行跨库查询、每条日志读取一次合同或价格，以及反复全量 COUNT。
   生成进度按已处理条数展示，不为一个精确进度百分比多扫描一次全月。
4. 计量候选行而不只是最终写出行。客户模型可能藏在历史快照中，匹配少量数据也可能扫描大量源行。
   读取速率与查询时间/扫描字节预算共同约束，不能把200,000等任意候选行阈值当新的产品硬上限。
5. 相同条件和版本先合并生成工作并复用已完成产物；复用判断只查询小型元数据，不能全月COUNT或全表hash。
6. CSV顺序写出，达到分片大小后生成下一文件；上传同样流式/分块，不把完整文件读入内存。
   全部所需分片成功后才发布该导出产物的完整清单；压缩不是首期必需项。
7. 读取队列满时快速拒绝新的扫描工作，已有文件仍可下载；存储不可用时拒绝新生成，
   运行中的导出支持取消和超时停止；核心业务继续沿用自身路径。
8. 第一版采用固定并发、批量、读取速率及时间预算，不增加独立总开关或运行时配置；
   保留压力退让、任务取消和预算耗尽失败。数据库查询必须有可验证的超时/取消机制，不能只有 HTTP 超时。
9. 导出读取不加资金行锁，不查询 Provider，不触发定价、退款或补偿流程。
10. 对象存储承担下载流量；本地临时文件仅作受限生成缓冲，不能成为多实例共享文件的权威位置。
11. 上线前核对实际SQL的执行计划及过滤/排序索引。LIMIT 1,000不代表只扫描1,000行；缺失索引、
    全量排序、稀疏过滤及宽other解析都必须纳入验证。禁止从状态轮询或点击下载触发第二次聚合。
12. 进度持久化按时间或批次节流，不每行UPDATE任务表；版本标记不能让每笔扣费新增整月共享热点行锁。
13. 预算覆盖整个读取链路，包括退款分类预查、主库Task事实补查和解析，不只限制主日志游标。
    当前工作区退款分类函数先一次性读入范围内退款，再按Task批查；导出不能直接以整月范围复用这个无界预加载流程。
    应沿用其分类语义，按当前有界日志批次收集必要标识、批量取事实并释放内存；辅助查询串行执行，计入总时长、
    主库连接与扫描预算，不逐行查Task，也不跨批无限积累缓存。相关字段修改同样属于8.3的产物依赖。

数据库负载退让应有确定行为：

| 观测条件 | 动作 | 恢复条件 |
| --- | --- | --- |
| 连接等待或批次延迟连续升高 | 降低读取速率/批量，停止新增领取 | 连续多个采样窗口回落后逐步恢复 |
| 核心请求延迟越过约定预算、数据库持续超时或IO压力达到阈值 | 不启动下一批查询，归还连接后等待 | 压力稳定回落且仍有任务时间预算 |
| 无法证明旧查询已取消或租约失效 | 禁止新执行器叠加同份读取；旧产物不得发布 | 查询已停止，任务明确结束或重新受理 |
| 资源等待或执行总预算耗尽 | 明确失败，不自动立即重试全月扫描 | 用户重试或后续按受控策略重新受理 |

阈值使用目标部署的基线、连接池等待与现有监控信号，采用冷却期，避免一高一低频繁启停。
监控不可用时采用保守固定限额并暂停提速；若取消/超时保护不可用，则不得启用该后端的大量导出。

单独工作进程或只读副本可作为后续容量手段，不是第一版必须新增的基础设施。
不能宣称独立连接池消除了数据库 CPU/IO 竞争，是否满足业务延迟目标仍须实测。

#### 7.4 建议初始参数

下表全部是待验证的实施起点，不是已承诺的 SLA；10 万条已从硬上限改为首轮验证规模。

| 参数 | 建议起点 | 说明 |
| --- | --- | --- |
| 规模验证 | 10万条起，追加超过10万条及分片场景 | 不在第100,001条拒绝；最大已验证规模须记录 |
| 候选扫描预算 | 固定查询时长、读取速率与空间预算，实测扫描成本 | 不把固定行数上限作用于全月统计范围 |
| 单次日期范围 | 最长 31 天 | 使用记录可跨月但不超过31天，提交前明示；账单固定自然月 |
| 每用户未完成源数据读取申请 | 1 个 | 按发起人计；不阻塞已有文件下载或有效汇总制表 |
| 全站源数据读取执行并发 | 1 个 | 跨实例共同约束，包含需重新扫描的汇总计算 |
| 导出日志连接 | 最多1个活动连接 | 另算短时任务元数据事务；实例总连接量必须有预算 |
| 全站源数据读取队列容量 | 3 个，含执行中 | 1执行+2等待；原子受理，超限直接返回忙碌 |
| 读取批量 | 最多1,000行起步，自适应降低 | 联动查询/解析耗时、返回字节与实际扫描成本，不作为最低吞吐承诺 |
| 最大读取速率 | 2,000 候选行/秒 | 批次间节流时不持有数据库连接 |
| 单批查询超时 | 5 秒 | 需按实际驱动验证取消行为 |
| 单任务执行预算 | 10 分钟 | 到期失败，不无期限占槽 |
| 最大排队等待 | 30 分钟 | 到期明确失败，不误报仍在运行 |
| 单个CSV分片大小 | 100 MiB | 到达后生成下一文件；分片仍保留相同字段与版本 |
| 产物总量/临时空间预算 | 512 MiB，目标部署仍须验证余量 | 总预算耗尽明确失败；不能无界占用磁盘或OSS |
| 文件保留 | 完成后 24 小时 | 用户界面显示准确到期时间 |
| 任务记录保留 | 7 天 | 独立于源日志保留；不形成永久账单档案 |
| 下载地址有效期 | 5 分钟 | 地址过期可重新鉴权签发 |
| 页面状态轮询 | 可见时 5 秒起、逐步退避至 30 秒 | 隐藏或关闭抽屉暂停；不每秒请求 |

容量与等待时间一起确定：单槽、容量C、执行预算T时，无暂停且调度正常的尾部名义等待上界为 `(C−1)×T`。
本起点为 `(3−1)×10=20分钟`，30分钟等待预算留出调度余量；持续高压或服务中断时仍可能超时，不能承诺必达。
原20容量在每项都接近10分钟时，尾部约需等待190分钟，与30分钟等待预算不匹配；不能据此声称第4项起在所有
实际负载下一定失败，但应避免以大队列承诺无法兑现的受理。扩容时同时重算容量、等待预算与实测耗时分布。

轻量通道仅查询有界元数据、序列化有效完整汇总、上传小文件或签发下载；另设并发、请求速率、字节和短时限预算，
不占上述读取槽。任何源数据扫描或退款/Task补查都返回统一读取队列，不因汇总CSV只有几十行获得额外数据库并发。
汇总结果本身过大时也不进入轻量通道。具体轻量阈值由第12节首步测定并记录，不允许默认无上限。

批量控制按真实SQL执行、结果读取、解析与辅助查询分别计时，达到时延/字节预算时降低下一批大小并节流；连续健康
窗口才缓慢恢复，最多1,000行。5秒是数据库查询取消边界，不代表最低200行/秒；稀疏筛选查询计划未改善时，缩小
返回批量也不能保证少扫描。查询超时直接按失败/退让规则处理，禁止不停缩批重试同一昂贵查询。

月账单统计始终覆盖所选整月，不适用导出行数或CSV分片限制。全月查询成本过高时，优化聚合/索引、
受控后台计算或可靠版本缓存；查询未完成时显示生成中或失败，绝不能缩短账期或返回部分金额冒充总额。
账单汇总与明细文件可以独立下载；明细导出失败不能改变月账单统计结果或让已完成的汇总账单不可用。
支持超过10万条不等于无限容量，配置预算必须与实测支持规模相符，不可用过低固定时间预算变相制造10万条门槛。

### 8. 数据截止、一致性与日志数据库

#### 8.1 导出数据范围

提交时保存客户与筛选；执行开始时记录读取边界、数据生成起点和源库类型。标准关系库可用真实内部唯一键
做 keyset 游标与上界，不能使用对客户重新编号的展示 ID。
日志时间筛选统一为左闭右开；接入既有含末秒接口时在边界处显式转换，验证月末和同秒记录。

“生成时间 + 最大键”不等于严格数据库事务快照：晚提交、延迟交付和日志清理仍可能改变可读数据。
第一版不新增月结封账、不冻结日志清理、不创建账单覆盖率/保留闸门，也不持有长时快照事务。
对客户承诺的是：**文件记录生成时实际读取并纳入的事实；同一批数据生成的汇总与对账明细可核对。**
不承诺两次独立导出、稍后刷新的在线账单或在途任务完成后的账单永远相同。

#### 8.2 全月统计、账单文件与对账明细解耦

```text
所选自然月全部已入账结算事实（不受导出条数限制）
                    |
              共用账单计算口径
              /             \
         全月统计结果      对账明细导出申请
              |                 |
         页面 / 账单CSV      分批写明细CSV
              |                 |
         汇总独立可用      全部分片完成后可下载
              \                 /
          范围和可靠数据版本相同时可直接核对
```

月账单统计不依赖导出任务存在，也不依赖明细文件写入成功；下载汇总只生成账单文件，
逐笔对账明细由独立动作发起。二者可以拥有独立任务和状态，禁止为下载几十行汇总强制生成整月明细文件。
资源通道按实际成本划分：有效完整汇总转文件走轻量通道，冷汇总需扫描则与明细共用读取预算。
已有汇总可直接交付，不能被本人的大明细导出占满配额阻塞；“独立下载”不等于另开一个无约束全月查询。
同时确有两种产物需求且范围、版本相同时，可以共用受控扫描及既有解析器，减少重复读库；
每种产物独立发布完整结果，不建立“全部文件必须一起成功才能查看月账单”的条件。

一次明细导出有多个CSV分片时，所有分片都成功才将该份明细标为完整。汇总的原始quota与对应明细
使用同一纳入规则；重试不得在旧文件后续写导致重复行。
分别生成的文件只有在数据范围与可靠版本一致时才能标为可直接勾稽；不同时提示版本差异并允许生成同版本结果。
若没有可重建的历史版本，不能承诺任意旧账单版本都能补出明细，应生成当前版本并明确标记。
通用使用记录的非账单事件保持单独类型，不因导出而进入月账单金额。

#### 8.3 OSS产物复用与版本失效

```text
申请下载
   |
当前权限校验 + 规范化客户/筛选/格式
   |
读取可靠源版本与产物元数据（不全月扫描）
   |
   +-- 条件/版本一致，完整且未过期 --> 引用私有OSS产物 --> 鉴权下载
   |
   +-- 已有同条件同版本生成中 ----> 合并生成工作，保留各自授权申请
   |
   +-- 无可复用结果或版本不可信 --> 有限队列 --> 限速读取 --> 完整产物
```

复用键至少包括目标客户与数据权限范围、导出类型、账期/筛选/时区、源数据版本、字段/解释格式版本、
语言、币种和展示换算设置。名称等可变展示依赖若来自当前主数据，也必须纳入版本，或明确冻结在生成版本中。
当前余额不属于月结算文件事实，不因充值改变历史月份文件；若某种文件确实包含实时余额，则不能忽略该依赖。

可靠版本必须覆盖影响产物的日志新增、补录、退款、修正与删除。不能用现有账期结束时间形式的
`data_version`、TTL、记录条数或单个最大ID当作完整变更证明。文件校验摘要只证明产物内容，不证明源数据未变。
历史月份同样检查变更，不能因月份结束就视为永久不变。

**候选设计与首期选择。** 优先验证A在目标关系日志库上的可行性；B仅在后端已有可信能力时评估，不默认同时建设两套系统。
主库单独维护一个异步更新的月度水位不能自动解决日志库可见性，故不作为独立可靠方案。

| 候选 | 版本事实与读取方式 | 成本与适用门槛 |
| --- | --- | --- |
| A：源库事务绑定的分片修订标记 | 在日志所在关系库，将日志变更与对应客户/月份/固定分片的修订递增放入同一短事务；版本取相关分片修订向量，并包含必要的清理/修复代次 | 新增源库元数据写入和短锁；分片减少单客户整月热点，但不能消除锁竞争，须测扣费/日志交付影响；所有变更入口必须受控 |
| B：后端可验证的已提交变更流 | 使用具备完整新增/修改/删除证据及提交屏障的变更流，形成范围失效索引；达到与读取可见性一致的屏障后才能判断未变化 | 需证明完整性、顺序、保留期限、消费者恢复和可见性；可能新增基础设施，不假设SQLite、MySQL、PostgreSQL、ClickHouse能力相同 |

A的实施设计必须满足以下条件，否则该后端不启用自动最新版本复用：

1. 版本标记与日志行在同一源库事务内提交；不能先推进主库水位、稍后才交付日志。只读查询使用同一权威源及
   新鲜的已提交视图，版本检查不可继续命中旧缓存。自增ID分配顺序不是提交顺序，不能替代修订机制。
2. 新增、补录、退款、原位修正及删除均推进受影响范围；变更客户或发生月份需使旧、新范围同时失效。
   批量清理无法经济地逐客户标记时，可在同一事务推进较粗的清理代次，允许多失效，不允许漏失效。
   受控外部修复先停用复用，完成校验后推进修复代次；无法识别外部直写的部署不具备可靠复用条件。
3. 分片数量固定且有上界；检查一个账期只查该范围的少量修订行及清理代次，不扫描全部历史月份或全月日志。
   迁移启用前完成写入入口切换、基线初始化和交界验证；未初始化范围不能把“没有修订行”当作无变化证明。
4. 将退款分类读取的Task冻结事实、可变展示依赖等非日志依赖列入矩阵；证明不可变的字段可直接引用冻结事实，
   可变字段必须有各自提交绑定的修订或固定在产物内。主库/日志库都变化的业务需有交付完整性屏障，
   屏障未完成时不得把暂时一致的版本向量视为业务交付完成；此方案不承诺跨库事务快照。
5. 生成前读版本向量，完成后再次读取；只有两次一致且依赖完整、交付屏障满足时才发布为该版本可复用。
   数据发生变化时不将结束时的新版本贴到先前扫描的文件上。缓存命中表示“校验时版本一致”，并非永久最新承诺。

B必须证明消费追上一个可信的已提交屏障，而不是仅报告“延迟很小”；消费者掉线、序列缺口、变更流过期或不可见的
删除/修正使可靠性失效。ClickHouse单独评估其提交、修改和清理语义，不能套用A的关系库事务保证；未通过前保持禁用。

**实施前交付物。** 按后端列出变更入口/依赖矩阵、事务与可见性时序图、分片与清理策略、失败恢复、增加的读写成本，
并验证回滚、晚提交、乱序交付、历史补录、跨月修正、清理、消费者滞后及主库/日志库分离。选择一个可行候选并记录理由；
不能把“后续增加水位”作为完成验收。若A需要扩大原生热路径或引入明显锁竞争，先否决该接法，不能为了缓存收益牺牲核心业务。

**明确的降级形态。** 任一可靠性条件不满足时关闭自动最新版本命中及跨申请工作合并，保留私有OSS历史文件的再次下载，
界面显示原生成时间及“历史文件”；用户要求当前数据时建立受控的新生成申请。当前月持续变化也不无限自动重跑，
本次完整读取结果可作为生成时文件交付，但不标成已验证最新版本。
若目标部署最终无法实现可靠版本，这可以长期运行，但属于功能缩减：必须明确列出“自动同版本复用未交付”，
经用户确认调整范围后才能视为阶段完成；不能以历史文件下载替代原已确认的可靠复用目标。6.2的复用说明只在验证通过时出现。

管理员与客户可共享同一目标客户、同一客户可见字段范围的产物，但个人申请、任务列表和下载鉴权独立。
不能向未授权用户暴露产物存在性；角色变化时重新校验。内部去重键不因管理员身份就给产物加入内部字段。
文件复用不等于成为资金事实源；日志仍为权威，OSS只保存可过期的派生产物，不能反向回填账单。
“重新生成”明确创建新版本尝试；普通下载可复用有效版本，并显示真实生成时间而不是本次点击时间。

#### 8.4 各数据库的实现验证

- SQLite/MySQL/PostgreSQL：优先复用 GORM、参数化范围条件、真实唯一键；核对索引计划和取消行为。
- ClickHouse：现有 created_at + request_id 排序不能直接证明全局唯一。实施前确认可用的持久唯一键或
  有界单次流式读取方案，不允许用不唯一游标跳过同键行，也不能改用无界 OFFSET 作为兜底。
- 如某日志后端无法同时满足无遗漏读取与资源预算，该后端的导出不得启用，并明确列为该部署的未完成项；
  不能用关系库测试通过宣称所有已支持日志后端都可用。正式交付前需解决目标部署实际使用的后端。
- 将来使用只读副本时必须核对复制水位和数据版本，不能用主库最新版本给滞后副本生成的文件标记版本一致。
- 扫描过程中发生查询错误、连接断开或读取结果损坏时失败，不把已写前缀发布为完整账单。
  源日志既有缺失/清理边界按现有事实说明，不新增无证据的“账期完整”标签。

### 9. 文件内容与权限

#### 9.1 使用记录 CSV

建议字段按照阅读顺序组织，最终名称在实现时随字段版本固化：

| 字段组 | 内容 |
| --- | --- |
| 范围标识 | 导出job ID、生成时间、时间区间、时区、客户可读标识 |
| 记录标识 | 可公开 Request ID、记录事件类型、日志发生时间、API Key ID/名称、客户模型 |
| 计费解释 | 模式、命中阶梯、计量单位、实际计费用量、单位价格、各项费用；不可用为空并附状态 |
| 折扣 | 生效组名称/来源、组系数、合同适用状态、历史名称/版本（已知时）、合同系数、最终模型系数 |
| 金额 | 折前金额、优惠、实际扣减、实际退回、有符号净额、附加费、舍入说明 |
| 核对 | 原始消费/退款quota及符号约定、币种、换算配置、是否计入客户账单、质量状态 |

一个日志事件一行，不把预扣、补扣和退款悄悄合并成一次调用。
常用 Token 类别用独立数值列；按秒/按次保留单位及量值。复杂构成放客户安全的说明列，不把内部 JSON 整体倒出。
合同未适用与历史未知分别用显式状态表示，空值不能被电子表格解释为零折扣。

#### 9.2 客户账单 CSV

包含账期、生成时间、客户、净额/扣减/退款、原价/优惠及质量标记、API Key与模型、折扣组合。
父级总计、模型行和组合叶行若放在同一文件，以 `row_type` 和层级标识区分，说明仅对叶行加总，
避免把总计与子行重复累计。金额全部来自后端同次聚合，前端不重新算一次。

文件统一 UTF-8 BOM；正确转义逗号、引号和换行，客户名称/模型名等文本防 CSV 公式注入。
负数金额作为受控数值保留，不能为了防注入把正常退款变成正数或丢掉符号。
小额费用沿用现有账单高精度格式，不使用余额显示的最小非零金额下限。中间金额使用定点/十进制，
原始 quota 保留可核对精度；大整数序列化不经 JavaScript 浮点截断。
显示舍入不得逐行累积成新的金额事实；子项显示舍入与总计不一致时展示明确的舍入说明。

#### 9.3 下载授权与清理

- 创建、列表、详情、取消、重新生成和下载每一步都检查发起人/应用范围；管理员接口另外校验角色与目标客户。
- 管理员为客户生成的文件默认在管理员自己的导出记录中，不自动发给客户或暴露给其他管理员。
  客户独立发起同范围申请时可以经权限和版本校验复用底层产物，不意味着能查看管理员任务列表。
- 文件只包含角色允许且当前导出类型需要的字段。禁止密钥、Cookie、原始请求体、原始 Provider 响应、
  完整签名 URL、内部上游身份和整包管理员快照。
- 文件对象采用不可猜测名称，存放私有空间；数据库保存对象引用，不保存长期签名地址。
- 下载地址签发前重新鉴权；签发后的短期地址可能在有效期内继续可用，不承诺即时撤销已发地址。
  需要即时撤销的场景应另评受保护下载代理，不能在本期伪称对象存储地址具备此能力。
- 导出文件使用独立命名空间与有限保留；不修改素材、任务结果或证据文件的保留规则。
- 清理任务有独立小预算，过期文件立即在应用层失效，物理删除可重试且不影响核心结算。

### 10. 代码改动边界与数据补足

#### 10.1 唯一计费事实，多个只读展示入口

```text
现有结算器 / 冻结Task事实
       |
       +-- 最小接线补充客户费用解释证据 --> 原有日志
                                             |
                                 客户安全的只读费用投影
                                      /      |      \
                                 记录详情  月账单   服务端CSV
```

不建立第二套前端扣费引擎。新的解释投影从既有结算结果和冻结依据构建，不能反向决定实际扣费。
能复用现有解释器/解析器的地方先复用；只为确有多个调用方的稳定计费概念提取公共逻辑。
按秒等解释字段不意味着必须扩展现有账单筛选枚举；现有 unknown 保持诚实，展示计量单位可单独增强。

新记录最小补足目标：客户模型、最终有效组及客户可读名称、合同适用状态/名称/版本、
实际计费用量与单位、命中阶梯/请求规则、折前小计、附加费用适用范围及实际舍入依据。
先盘点哪些字段已存在；已有字段不双写第二份，缺口只在实际完成结算的窄接线点追加。
合同名称随当次合同事实冻结，不能结算时读取已经被修改的合同名称冒充发生时事实。
未覆盖的计费模式保持“解释不可用”，列为未完成项；不为了凑展示字段扩大到所有原生入口重构。
原始请求参数、媒体内容和 Provider 私有数据不因解释需求新增保存。

| 区域 | 拟修改位置/新增文件 | 边界 |

| 计价证据 | 已有本地快照 helper；必要时原生日志入口极窄调用 | 只补解释证据，不改公式与结算顺序 |

目录与文件名属于拟定实现落点，不表示当前已经存在。
原生 `model/main.go` 若需接迁移，只增加必要调用；日志热路径若缺接线，新增主体逻辑放独立文件。
实施时逐处记录必要性、接线行和未来上游合并影响；不能借机格式化或重构原生文件。
不删除对外账单查询 API；新导出接入后替换页面旧浏览器下载入口，避免同名按钮提供两种账单口径。
数据库迁移、JSON 编解码、quota checked 转换继续遵守现有硬约束。

**存储复用的具体边界。** 现有 [TaskArtifactStore](../../service/task_artifact_store.go) 接口与Provider Task绑定，
不能创建假Task来保存账单；复用的是现有存储运行时、后端连接、签名与引用机制，在独立文件增加导出所需的窄接口。
现有 [S3上传](../../service/task_artifact_store_s3.go) 使用 `io.ReadAll`，不能因参数是Reader就宣称已支持有界流式上传；
通用Azure产物上传也需检查同类缓冲，不能未经核实直接用于大文件。

导出拟逐个生成有界临时CSV分片，关闭写入后以文件长度和流式摘要签名，再用可重开的文件Reader上传；
支持分块上传的后端可用受限并发分块。两者都禁止将整片重新读入内存，上传成功后释放该临时分片，
并约束单记录大小、总字节、临时磁盘、重试次数、上传时限及未完成上传清理。已有小产物路径不顺带重构。
所有分片完成前对象保持私有且不对客户发布清单。

现有TaskArtifactStore接口没有通用删除方法，不能声称现成具备导出保留期清理。
复用后端能力实现独立命名空间下的到期/孤儿清理，或使用已验证的对象生命周期规则；清理不能误删其他Task产物。
共享文件先使全部下载资格到期，再执行幂等清理；失败记录并受控重试。签名URL有效期不超过产物剩余有效期。

接口路径在实现前按现有 router 命名确定，下面表达职责，不构成已经发布的 API：

| 动作 | 普通客户 | 管理员 |
| --- | --- | --- |
| 创建申请 | 从认证上下文取客户，不接受任意 user_id | 显式目标客户，限单客户 |
| 列表/详情 | 仅本人发起且所属应用范围的任务 | 默认同样只看本人发起任务 |

创建成功建议返回 202 和任务标识；超过速率/队列配额返回明确忙碌状态；服务不可用快速失败。

列表、详情和进度接口只读任务小表，不能顺便重新扫描日志。已有会话认证、CSRF 与限流措施按项目惯例接入。

### 11. 验收标准与测试计划

#### 11.1 业务与金额验收

| 场景 | 必须观察到的结果 |
| --- | --- |
| 折前 $10，组0.5，合同0.3 | 模型实付 $1.5，优惠 $8.5；两层和最终1.5折均显示 |
| 用户有合同但Key未绑定/模型不在合同 | 不擅自应用合同优惠；已知未适用与未知分开 |
| 同月两份合同/版本变化/有无合同切换 | 分成真实组合，汇总金额一致，不展示单个伪整月折扣 |
| 存在用户专属组倍率 | 只用最终有效倍率，普通组倍率不再相乘 |
| 模型费用外有工具费 | 合同只作用于模型费用；总扣费与原日志完全一致 |
| 图示Token用量 | 总输入69,000；普通输入10,000；各计价项总计$0.08，不重复算缓存 |
| 表达式未使用缓存变量 | 缓存包含在基础输入，不再次单独收费 |
| Task按秒/Token单位表达式 | 单位换算正确，避免重复除百万；使用最终已确认用量 |
| 动态请求规则/复杂表达式 | 已知系数不遗漏，不可靠拆解明确说明，实际金额照常显示 |
| 新旧、估算、缺失混合 | 质量状态传播到模型、组合、客户总计和CSV，部分原价不冒充全额 |
| 退款/负净额/跨月退款 | 保留负号和发生月；原价、优惠和实际净额关系成立 |
| 异步预扣/调整/零差额完成 | 金额只累计实际事件一次；请求数和最终用量不因流水行数重复 |
| 舍入、小额费用、大整数 | 原始quota精确；显示可核对，不以显示数回写或重算资金 |

所有示例按确定输入和明确期望编写回归，不通过大量随机输入或仅跑通代码替代验证。
新增/大改 Go 测试按项目要求使用 require/assert；为真实行为、跨模块金额合同与失败路径建立测试。

#### 11.2 导出与权限验收

- 验证0、1、99,999、100,000、100,001条：第100,001条不再触发固定上限失败；超过10万条必须完整交付。
- 追加更大规模、CSV分片及总资源预算耗尽场景；超预算不公开残缺明细，完整月账单不按导出上限截断。
- 同一筛选跨多页、同秒多记录、相同 Request ID 的不同事件不丢失、不重行，不使用展示序号游标。
- 同次账单与对账明细以原始 quota 核对；父行/叶行不重复累计；模型、组合、总计一致。
- 同一用户并发重复提交、不同条件并发提交、多个实例领取、队列容量竞争均不突破配额。
- 3个读取工作占满后第4个新工作快速拒绝；同版本共享工作不重复占槽。大明细执行期间，有效汇总制表与已有文件仍可交付；冷汇总不能绕过读取槽。
- 三种主库验证可空唯一键、多NULL终态、条件占槽、唯一冲突整体回滚、取消共享工作与释放配额；旧租约不能发布或叠加读取。
- 数据未变的有效产物命中后，查询轨迹中无日志表扫描；同客户同范围的管理员和客户申请可经鉴权复用内容。
- 新增/补录/退款/原位修改/删除导致可靠版本变化；即使条数和最大ID不变，也不能误用旧版文件。
- 验证生成过程中数据改变、版本失效通知滞后、复制滞后、格式/币种变化、文件过期与丢失，均不误标为最新可复用。
- 覆盖源事务回滚、ID先分配后晚提交、修复/清理、主库Task依赖变化；未初始化或版本不可证明时只提供明确标注的历史下载与重新生成。
- 浏览器离开/刷新后仍可查询；只轮询任务状态，不触发重复生成；失败和过期不会返回成功文件。
- 取消、查询超时、租约丢失、重启、上传失败、文件缺失和清理重试都能进入明确状态。
- 客户A不能用客户B的job ID查询、取消或下载；管理员降权后不能取得新地址；应用边界不能被篡改。
- 文本公式注入、逗号/引号/换行、大整数、负退款、未知字段与七语言列名的CSV行为正确。
- 切月份、切客户、切筛选期间不下载旧范围；旧文件始终显示自己的范围与生成时间。
- 普通客户与管理员代客户导出都不包含内部上游身份、凭据、原始响应或管理快照。

#### 11.3 资源与部署验收

测试环境需记录数据库种类/版本、索引、实例资源、日志字段大小、源记录量和对象存储位置。
用固定构造的10万条代表性数据开始验证，追加50万/100万等目标规模及分片场景，按目标部署资源选择并记录结果；
不能只测10万条就宣称更大规模已受支持。这属于容量验收，不在普通单元测试中堆随机循环或计时断言。
同时施加有代表性的模型调用与结算负载，对照无导出时的基线。

建议验收目标（上线前由实际部署复核）：

- 导出受理接口不扫描日志，正常无拥塞时 p95 小于 500ms；不承诺总生成时间固定。
- 核心接口 p95 延迟相对基线增加不超过 5%，p99 增加不超过 10%；无新增结算失败、连接池耗尽或资金锁等待异常。
- 内存不随日志行数线性保留整批对象；峰值由批次、CSV缓冲和有界聚合键控制，并记录实测值。
- 全站只有一个源数据读取执行；日志及辅助主库查询连接总量受控；单批查询有超时，候选扫描速率、成本、字节数和任务总时长不越界继续运行。
- 记录数据库连接等待/占用、SQL扫描与返回行数、批次耗时、CPU/IO和任务元数据写入次数；分别验证索引良好和稀疏筛选场景。
- 退款密集场景计入预查和Task补查，内存不因全月退款数量增长；宽字段/慢解析场景验证批量与超时联动，而非只测每批行数。
- S3及目标存储后端验证分片上传峰值内存、取消和孤儿清理；不能以CSV写出流式替代上传链路的实测。
- 注入持续慢查询/资源高压，验证停止下一批、释放连接、冷却恢复、等待超时以及取消后的查询确实终止。
- 反复提交同条件导出，首次生成后命中产物复用不增加日志扫描；不得为检测复用而再次全量聚合。
- SQLite、MySQL、PostgreSQL 验证操作表迁移、并发领取与查询；目标使用 ClickHouse 时必须追加真实日志导出验收。

超出延迟预算时先降低导出速率/批量或暂停导出，不以提高并发来缩短排队；仍不能满足时再评估独立执行部署。

### 17.3 版本复用采用的降级决定

### 19.2 当前实际情况

- 合同状态未知或存在独立附加费时，仅保留有独立证据的用量×冻结单价分项，不据此重建总费用。
