# 媒体图片异步任务运维手册

## 1. 适用范围

本文适用于 Advanced Custom `media_task_image_blocking` 路由创建的共享 `media_image` Task，包括：

- `seedream-5-0-260128`
- `doubao-seedream-4-5-251128`
- `gemini-3.1-flash-image-preview-usage`

北向只支持 `response_format=url`。固定尺寸价 `Gemini-3.1-Flash-Image-Preview` 和 `b64_json` 不属于当前生产合同。

架构边界见 [ADR-0006](../20-architecture/decisions/0006-media-image-shared-task-persistence.md)，实施与验收边界见 [图片异步任务共享 Task 持久化闭环方案](2026-07-27-图片异步任务共享Task持久化闭环方案.md)。

## 2. 上线前配置检查

1. 保持异步任务轮询启用，即 `UPDATE_TASK=true`。
2. `TASK_TIMEOUT_MINUTES` 推荐保持默认 `1440` 分钟，并至少大于上游任务 P99/SLA 加安全余量。
3. `media_image` 在代码中具有 30 分钟保护性生命周期下限；即使全局值配置得更小，也不会在创建后 30 分钟内被超时清理。`TASK_TIMEOUT_MINUTES=0` 仍表示禁用生命周期超时。
4. 持久化图片路由只使用 Advanced Custom 路由 `auth` 或默认 Bearer。不得依赖渠道级、客户端级或运行时 header override。
5. usage 模型完成真实账单核验前，不得启用 `tiered_expr`；使用管理员配置的固定 `ModelPrice`。
6. 用真实 Key 验证 HTTP 200、HTTP 202、成功、失败、长任务和上游查询错误样本。

## 3. 客户端接入要求

异步图片调用强烈建议携带：

```text
Idempotency-Key: <一次业务生成的稳定随机值>
```

同一次业务生成发生网络重试时必须复用原键；新的生成意图必须使用新键。本站不会按 prompt 或请求体哈希隐式合并重复请求，因为相同参数可能是用户有意触发的随机再次生成。

客户端可使用：

```text
Prefer: respond-async
```

该首部仅在上游返回 HTTP 202 时让本站持久化后立即返回本地任务；若上游同步返回 HTTP 200，本站仍直接返回图片结果。

收到本站 HTTP 202 后，保存响应中的本地 `task_xxx`，并按 `Location` 查询：

```text
GET /v1/images/tasks/:task_id
```

## 4. 重点监控

至少监控以下指标和日志字段：

- 图片创建 HTTP 200/202 比例。
- `media_image` 的 queued、in_progress、unknown、failed、completed 数量和完成耗时。
- 上游创建请求 ID、最后轮询请求 ID、轮询次数和查询错误。
- HTTP 429、查询频率和上游是否对查询计费。
- `billing_state` 的 pending、failed、debt 数量。
- 失败退款、生命周期超时退款和计费补偿次数。
- 同步或异步上游返回结果数超过请求 `n` 的协议违规告警。
- 本地任务已失败或退款后发现的上游晚成功。

上游 Key、完整鉴权头、原始 prompt、参考图和完整上游响应不得写入普通日志或工单。

## 5. 必须人工对账的红色窗口

### 5.1 上游可能已接受，但本地未取得 task_id

典型原因是创建 POST 返回前网络中断。系统禁止自动重提，也不会在无法确认上游未计费时自动退款。

- 有 `Idempotency-Key`：创建幂等记录进入 `unknown`，相同键重试不会再次创建。
- 无 `Idempotency-Key`：无法建立可恢复的创建记录，只能通过请求日志和上游请求 ID人工查询。

### 5.2 已取得 task_id，但恢复日志或 Task 写入失败

此时上游任务已经存在，但本地没有可靠执行事实。系统禁止重新 POST 和请求级退款。必须使用管理员日志中的渠道、上游任务 ID和请求 ID查询上游最终状态。

### 5.3 生命周期退款后发现上游晚成功

Task 进入终态后不再自动轮询。如果上游在生命周期超时后才成功，需核对本站退款、上游账单和结果状态，并按运营政策处理成本差异。

### 5.4 usage 与真实账单不一致

立即停止为对应模型使用 `tiered_expr`，回退到固定 `ModelPrice`。保留脱敏后的 usage、上游请求 ID、本站计费日志和账单差异，完成字段语义核验后再恢复。

## 6. 对账步骤

1. 用本站 request ID定位请求日志，确认用户、令牌、渠道、模型和创建时间。
2. 如果存在本地 `task_xxx`，查询 Task 状态、`billing_state` 和退款/结算日志。
3. 仅在管理员受控环境中使用创建时渠道凭证，按上游请求 ID或上游任务 ID查询最终状态；不得把凭证复制到工单。
4. 比较本站预扣、结算、退款和补偿日志与上游账单。
5. 根据已确认事实处理：
   - 上游明确未创建：释放或关闭未知幂等状态，并按现有运营流程退款。
   - 上游失败：确保本站只退款一次。
   - 上游成功且本站 Task 存在：优先让现有 Task 计费补偿完成。
   - 上游成功但本站无 Task：记录人工对账事项，不重新创建。
   - 上游超发图片：同步请求或异步 Task 应失败退款；同时记录渠道协议违规。
6. 工单记录本站 request ID、本地 task ID、脱敏上游请求/任务 ID、最终状态和资金处理结果。

## 7. 查询去重边界

请求内等待器与 15 秒后台轮询可能在短时间内重复执行只读 GET，但共享终态 CAS 和计费状态机保证不会重复创建、结算或退款。当前不启用跨实例轮询租约；只有监控确认查询限频或成本问题后，才评估带 TTL 且支持故障接管的去重机制。
