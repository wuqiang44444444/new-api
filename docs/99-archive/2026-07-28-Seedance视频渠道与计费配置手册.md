# Seedance 视频渠道与计费配置手册

> 面向运维：从接入上游、配置价格、配置倍率、开放用户到上线验收的完整操作手册。
> 协议与计费的架构原理见 [视频上游接入与异步任务架构](../20-architecture/视频上游接入与异步任务架构.md)；阶梯表达式的完整语法见 [表达式计费系统设计](../../pkg/billingexpr/expr.md)。本文只讲运维要做什么、在哪做、怎么验。

Seedance 视频模型统一用 **DoubaoVideo** 渠道接入，无论是 BytePlus 官方直连还是第三方中转/反代，差别只在渠道里几个字段，客户端调用方式完全一样。

---

## 1. 上线前必读：几个关键认知

动手配置前，先理清三件最容易搞混的事。理解了这三点，后面配置不会反复返工。

### 1.1 一条视频调用，从配置到计费的简化流程

```text
1. 配渠道     在「渠道管理」建 DoubaoVideo 渠道，填上游地址、Key、模型映射
2. 配价格     在「系统设置 → 计费 → 模型定价」给公开模型名定一个计费方式
3. 配倍率     在「系统设置 → 计费 → 分组定价」决定不同用户/线路的价格系数
4. 开放使用   把模型放进某个分组，让用户/KEY 能选到这个分组
5. 验收       用 CURL 跑一遍：创建任务 → 查询状态 → 下载结果，并核对计费日志
```

这五步分别在不同菜单完成，**任何一步缺了，调用都会失败或算错钱**。

### 1.2 三个最容易搞混的概念

**①「用户分组」和「调用分组」不是一回事**

- **用户分组**：用户的身份等级（如 `default` / `vip` / `svip`），决定用户享有什么权益和专属价格资格。
- **调用分组**：一次请求实际走的线路（如 `default` / `economy` / `premium`），决定这次调用用哪些渠道、按哪个倍率计费。

一个用户只有一个身份分组，但可以被允许使用多个调用分组。KEY 可以指定把请求送进哪个调用分组。

**② 模型映射只改「发往上游的名字」，不改「计费的名字」**

渠道里的「模型映射」把客户端用的公开模型名（如 `seedance-2-0-oversea-key`）翻译成上游真实模型名。但**计费永远按公开模型名算**。所以价格一定要配在公开模型名上，不要配在映射后的上游名上——配错了等于没配，会按默认值计费或报错。

**③ 模型广场显示的「起步价」不一定是某个 KEY 的实付价**

模型广场在不选具体分组时，显示的是该模型在用户可用分组里的**最低价**。如果某个 KEY 固定走 `premium` 分组，实际计费按 `premium` 的倍率，可能比广场显示的起步价高。答疑时要以用量日志里的实际倍率为准。

## 2. 第一步：接入视频上游（配置渠道）

在「渠道管理」新建或编辑一个渠道，类型选 **DoubaoVideo**。

### 2.1 三种视频上游方案，怎么选

渠道里有个「视频上游方案」下拉框（对应配置项 `视频上游方案`），三个选项：

| 选项                                                      | 适用场景                             | 要不要额外填路径                         |
| --------------------------------------------------------- | ------------------------------------ | ---------------------------------------- |
| **官方协议**（`official`）                        | BytePlus Ark 官方直连                | 不用，系统内置任务路径                   |
| **第三方反代协议**（`third_party_reverse_proxy`） | 兼容官方 Ark 接口的第三方代理/反代   | 要，填「创建路径后缀」和「查询路径模板」 |
| **第三方中转协议**（`third_party_relay`）         | 提供统一媒体任务接口的第三方中转平台 | 要，填「创建路径后缀」和「查询路径模板」 |

怎么选：直连 BytePlus 官方就选「官方协议」；上游是一个把 Ark 接口原样转发的代理，选「第三方反代协议」；上游是另一套媒体任务接口（请求结构不同），选「第三方中转协议」。**不要按模型名或地址猜**，选错了请求会发到错误的路径上。

客户端入口与这里的上游方案是两层概念：客户端无论调用 `/v1/video/generations` 还是 ModelArk v3 的 `/api/v3/contents/generations/tasks`，都可以选中上述任一已实现方案。ModelArk v3 只是北向请求/响应格式，不要求渠道必须是 `official`；最终仍按调用分组、公开模型、能力记录、渠道状态和素材兼容性选渠。

官方协议内置的任务路径是固定的（不需要填）：

```text
创建任务  POST /api/v3/contents/generations/tasks
查询任务  GET  /api/v3/contents/generations/tasks/{task_id}
```

### 2.2 配置官方渠道（BytePlus 直连）

```text
类型:           DoubaoVideo
视频上游方案:    官方协议（official）
API 地址:        https://ark.ap-southeast.bytepluses.com
API Key:         <BytePlus 提供的真实 Ark Key>
模型:            <公开模型名，如 seedance-byteplus>
模型映射:        <公开模型名> -> <BytePlus endpoint 或模型，如 ep-2026xxxx>
```

要求：

- **API 地址**只填根地址，**不要**追加 `/api/v3/...` 任务路径（系统会自动拼）。
- **API Key** 填官方给的真实调用 Key，不是某个用户的访问令牌。
- **映射目标**必须是这个 Key 实际有权限调用的 endpoint 或模型。
- **Seedance 2.0 不支持 `service_tier`**：渠道不要开启该字段透传。客户端显式传 `default` 时系统会在提交前省略；传 `flex` 时会在本地返回 `unsupported_parameter`，不会预扣费或请求上游。

下面的 CURL 直接访问上游，只用于在保存渠道前校验 Base URL、上游 API Key、模型和协议是否匹配；它们会绕过 new-api 的选路和计费。经 new-api 做完整验收时，使用第 6 节的 CURL。

**创建任务：**

```bash
curl --fail-with-body \
  --silent \
  --show-error \
  --request POST \
  'https://ark.ap-southeast.bytepluses.com/api/v3/contents/generations/tasks' \
  --header 'Authorization: Bearer <BytePlus-Ark-API-Key>' \
  --header 'Content-Type: application/json' \
  --data-raw '{
    "model": "<BytePlus endpoint 或模型>",
    "content": [
      {
        "type": "text",
        "text": "一只橘猫坐在窗边看雨，电影级光影，镜头缓慢推进"
      }
    ],
    "duration": 5,
    "generate_audio": true,
    "ratio": "16:9",
    "resolution": "720p",
    "watermark": false
  }'
```

创建成功后保存响应中的 `id`，用它查询任务：

```bash
curl --fail-with-body \
  --silent \
  --show-error \
  --request GET \
  'https://ark.ap-southeast.bytepluses.com/api/v3/contents/generations/tasks/<创建响应中的id>' \
  --header 'Authorization: Bearer <BytePlus-Ark-API-Key>'
```

### 2.3 配置第三方反代渠道（Moxing Seedance 2.0 海外官 Key）

上游文档：[Seedance 2.0 海外官 Key](https://www.moxing.pro/docs/models/dreamina-seedance-2-0-260128)

该线路的请求和响应与 BytePlus ModelArk 原生格式一致，Moxing 只做鉴权、路由、估价和账务，因此归类为 **第三方反代协议**，不是 V2 统一媒体中转协议。

```text
类型:           DoubaoVideo
视频上游方案:    第三方反代协议（third_party_reverse_proxy）
API 地址:        https://www.moxing.pro
创建路径后缀:    /v1/ark/media/generations
查询路径模板:    /v1/ark/media/tasks/{task_id}
API Key:         <Moxing 提供的真实 API Key>
模型:            dreamina-seedance-2-0-260128
模型映射:        无（公开模型名与 Moxing 上游模型名相同）
```

系统按渠道填的地址和后缀直接调用：

```text
POST https://www.moxing.pro/v1/ark/media/generations
GET  https://www.moxing.pro/v1/ark/media/tasks/{task_id}
Authorization: Bearer <渠道 API Key>
```

方舟直通线路的创建与查询路径都以 `/v1/ark/media/` 为前缀（带 `ark`），与 2.4 节中转线路的 `/v1/media/` 前缀不同；路径前缀用错，上游会返回 `400 invalid_request`。

服务端调用该上游时保持 Ark 原生结构，例如使用 `content`、`duration`、`generate_audio`、`ratio` 和 `resolution` 等字段；不会转成 `capability`、`input_mode`、`control_mode` 和 `duration_seconds` 组成的 V2 结构。客户端始终调用 new-api 的统一视频接口。如果需要用独立的客户端公开模型名区分路由和计费，可另行配置 `seedance-2-0-oversea-key -> dreamina-seedance-2-0-260128` 模型映射。

**创建任务：**

```bash
curl --fail-with-body \
  --silent \
  --show-error \
  --request POST \
  'http://localhost:8100/v1/video/generations' \
  --header 'Authorization: Bearer sk-WuLI4mjVZLAmCPENqYbWdikUaa0xqFZQ2sRsv03Xe20PSX85' \
  --header 'Content-Type: application/json' \
  --data-raw '{
    "model": "dreamina-seedance-2-0-260128",
    "prompt": "一只白猫坐在窗边看雨，电影级光影，镜头缓慢推进",
    "seconds": "5",
    "metadata": {
      "generate_audio": true,
      "ratio": "16:9",
      "resolution": "720p",
      "watermark": false
    }
  }'
```

创建响应由 new-api 返回；保存其中的公开任务 `id` 后查询：

```bash
curl --fail-with-body \
  --silent \
  --show-error \
  --request GET \
  'http://localhost:8100/v1/video/generations/task_CSqsRPzaczMI703cHkOPT79fqmVJIRoo' \
  --header 'Authorization: Bearer sk-WuLI4mjVZLAmCPENqYbWdikUaa0xqFZQ2sRsv03Xe20PSX85'
```

「创建路径后缀」和「查询路径模板」的填写规则：

- 都必须以单个 `/` 开头，只能填路径，不能填完整 URL。
- 创建后缀**不能**含 `{task_id}`；查询模板**必须且只能**含一个 `{task_id}`。
- 都不能带 `?` 查询参数或 `#` 锚点。
- 保存时前端会实时预览最终 URL，并就地校验，填错会直接提示。

### 2.4 配置第三方中转渠道（Moxing Seedance 2.0 海外版）

上游文档：[Seedance 2.0 海外版](https://www.moxing.pro/docs/models/seedance-2-0-oversea)

该线路使用 Moxing V2 统一媒体任务结构，因此归类为 **第三方中转协议**。

```text
类型:           DoubaoVideo
视频上游方案:    第三方中转协议（third_party_relay）
API 地址:        https://www.moxing.pro
创建路径后缀:    /v1/media/generations
查询路径模板:    /v1/media/tasks/{task_id}
API Key:         <Moxing 提供的真实 API Key>
模型:            seedance-2-0-oversea
模型映射:        无（公开模型名与 Moxing logical key 相同）
```

系统按渠道填的地址和后缀调用：

```text
POST https://www.moxing.pro/v1/media/generations
GET  https://www.moxing.pro/v1/media/tasks/{task_id}
Authorization: Bearer <渠道 API Key>
```

**创建任务：**

```bash
curl --fail-with-body \
  --silent \
  --show-error \
  --request POST \
  'http://localhost:8100/v1/video/generations' \
  --header 'Authorization: Bearer sk-WuLI4mjVZLAmCPENqYbWdikUaa0xqFZQ2sRsv03Xe20PSX85' \
  --header 'Content-Type: application/json' \
  --data-raw '{
    "model": "seedance-2-0-oversea",
    "prompt": "一只黑猫坐在窗边看雨，电影级光影，镜头缓慢推进",
    "seconds": "5",
    "metadata": {
      "ratio": "16:9",
      "resolution": "720p",
      "watermark": false,
      "generate_audio": true
    }
  }'
```

创建成功后保存 new-api 响应中的公开任务 `id`（兼容字段为 `task_id`），再查询：

```bash
curl --fail-with-body \
  --silent \
  --show-error \
  --request GET \
  'http://localhost:8100/v1/video/generations/task_vVgrWSpqJCDkSzgPGUZJxcByqkjrlMqE' \
  --header 'Authorization: Bearer sk-WuLI4mjVZLAmCPENqYbWdikUaa0xqFZQ2sRsv03Xe20PSX85'
```

```
export NEW_API_KEY='sk-WuLI4mjVZLAmCPENqYbWdikUaa0xqFZQ2sRsv03Xe20PSX85'
task_id='task_vVgrWSpqJCDkSzgPGUZJxcByqkjrlMqE'

curl --fail-with-body \
  --location \
  --progress-bar \
  --output video.mp4 \
  "http://localhost:8100/v1/videos/${task_id}/content" \
  --header "Authorization: Bearer ${NEW_API_KEY}"
```

中转协议下，系统会把客户端的统一视频请求**转换**成中转平台需要的结构（`capability`、`input_mode`、`control_mode`、`duration_seconds` 等字段），再按配置的地址和后缀调用。当前转换支持：

- 文生视频；
- 单首帧图生视频；
- 首尾帧控制；
- 多参考图；
- 分辨率、比例、时长、随机种子、固定相机、水印、音频开关等已接入字段。

不支持的媒体类型，或互相冲突的首尾帧/参考图组合，会在请求阶段直接报错，不会静默降级。

字段映射需特别注意：内部的 `duration`、`ratio`、`generate_audio` 出站时分别转换为 Moxing 合同的 `duration_seconds`、`aspect_ratio`、`with_audio`。显式 `0` 或 `false` 会被保留；上游请求中不应再出现旧字段名。若任务能创建但画幅或音频开关未生效，优先抓取脱敏后的上游请求体核对这三组字段。

### 2.5 API Key 怎么填（单 Key / 多 Key）

上游 API Key **只在渠道的「API Key」里填一次**，不要为某个供应商再建第二套凭证、地址或绑定配置。

- **单 Key 渠道**：直接填一个 Key。
- **多 Key 渠道**：一个渠道填多个 Key（一行一个），选择调度模式「随机」或「轮询」。系统每次创建任务时只**选中其中一个 Key** 用。

> **重要：任务创建时会「冻结」当时选中的那个 Key。** 之后管理员修改渠道的 Key，只影响之后新建的任务，**不会改变已经在跑的任务的查询凭证**。所以：
>
> - 单 Key 渠道换账号，在途任务仍用旧 Key 查询，不受影响。
> - 多 Key 渠道，每个任务只用创建时选中的那个 Key，不会把整组 Key 拼成一个凭证。
> - 如果上游有多个独立账号，**推荐一个账号建一个渠道**，用渠道优先级/权重/分组来路由，更清晰。

第三方上游**不需要**任何供应商专用环境变量或专用 Redis。`start.sh` 只启动 new-api 前后端就够。旧方案里的 `MOXING_API_KEYS`、`MOXING_BASE_URL`、`MOXING_REDIS_URL` 等配置不要再使用。

## 3. 第二步：配置模型价格

价格在「**系统设置 → 计费 → 模型定价**」里配。先决定用哪种计费方式，再填具体价格。

### 3.1 三种计费方式，视频怎么选

每个模型可以选一种计费方式（模型定价里的「计费类型」下拉）：

| 计费方式                          | 怎么算钱                             | 视频适用吗                            |
| --------------------------------- | ------------------------------------ | ------------------------------------- |
| **按 Token 计费**（倍率）   | 按输入/输出 token 数 × 各倍率       | 视频一般不用（视频不按文本 token 算） |
| **按次固定价格**            | 每次调用一个固定价，再按分辨率等微调 | **视频最常用**                  |
| **表达式计费**（阶梯/动态） | 一行表达式定义完整计费逻辑           | 高级场景，适合复杂阶梯定价            |

视频模型**绝大多数用「按次固定价格」**；只有需要按时长/分辨率做复杂阶梯定价时，才用「表达式计费」。下面分别说明。

### 3.2 按次固定价格（最常用）

在模型定价里，给公开模型名填一个**固定价格**（单位是内部额度，界面会换算成美元显示）。

计费时会自动这样算：

```text
本次费用 = 固定价格
          × 视频输入倍率（按分辨率、是否图生视频自动查表）
          × 最终分组倍率（见第 4 节）
```

其中「视频输入倍率」是系统内置的：根据请求里的分辨率（720p / 1080p / 4K 等）和是否包含视频输入（图生视频 vs 文生视频）自动套用一个倍率。**运维只需要填固定价格，倍率会自动生效**，不用单独配。

举例（数字仅示意）：

```text
固定价格 = $0.04/次
请求是 1080p 图生视频，视频输入倍率 = 1.5
分组倍率 = 1.25
本次费用 = 0.04 × 1.5 × 1.25 = $0.075
```

### 3.3 表达式计费（高级，由产品/商务定价）

> 写表达式是**产品或商务定价人员**的事，运维一般不需要自己写。这一节只让运维看懂「这个模型用了表达式计费」「表达式能读哪些维度」「有哪两条红线不能碰」。完整语法见 [表达式计费系统设计](../../pkg/billingexpr/expr.md)；当前配置见 [01 计费与分组运维手册](../40-operations/01-计费与分组运维手册.md)。

**视频表达式能读取的请求维度**（通过 `param("_task.字段名")` 读取；字段在创建任务时由 DoubaoVideo 适配器冻结，预扣与结算读到的是同一份）：

| 字段                                | 含义           | 取值示例                                      | 注意                                                          |
| ----------------------------------- | -------------- | --------------------------------------------- | ------------------------------------------------------------- |
| `param("_task.resolution")`       | 输出分辨率     | `480p` / `720p` / `1080p` / `4k`      | **4K 是小写 `4k`**；比较写 `== "4k"`                |
| `param("_task.has_video_input")`  | 是否含视频输入 | `true` / `false`                          | **只有视频生视频为 `true`；文生、图生都是 `false`** |
| `param("_task.duration_seconds")` | 视频时长（秒） | 整数（0–3600）                               |                                                               |
| `param("_task.generate_audio")`   | 是否生成音频   | `true` / `false`                          |                                                               |
| `param("_task.input_mode")`       | 输入模式       | `text` / `single_image` / `multi_image` |                                                               |
| `param("_task.control_mode")`     | 控制模式       | `none` / `reference` / `end_frame`      |                                                               |

> **视频的 token 用量只走 `c`，不走 `p`。** 视频任务结算时 `p` 恒为 `0`；上游返回的 token 用量（`usage.completion_tokens`，缺失时回退 `usage.total_tokens`）注入到 `c`。所以按 token 计费的表达式必须写成 `c * 单价`，**写成 `p * 单价` 会恒为 `0`、算不出钱**。

**Seedance 2.0 海外官 Key（按 Token 计费）——直接复制即可**

BytePlus 官方对该模型（`dreamina-seedance-2-0-260128`）按「输出分辨率 × 是否含视频输入」定价，单位 **USD / 百万 tokens**（Moxing 报价是同一价格的 ¥7 倍，逐档一致）。文生/图生/视频生三种方式单价相同，合并 6 个唯一价：

| 分辨率      | 含视频输入（视频生视频）        | 不含视频输入（文生 / 图生） |
| ----------- | ------------------------------- | --------------------------- |
| 480p / 720p | $4.3（¥30.1） | $7.0（¥49）   |                             |
| 1080p       | $4.7（¥32.9） | $7.7（¥53.9） |                             |
| 4k          | $2.4（¥16.8） | $4.0（¥28）   |                             |

> 系数直接填 **BytePlus 官网 USD 价**，无需汇率换算（系统额度按美元计，经 `QuotaPerUnit` 换算，与 3.2 节固定价同口径；Moxing ¥ 报价 = USD × 7）。价格来源：[BytePlus ModelArk 定价](https://docs.byteplus.com/en/docs/ModelArk/1544106)。

**直接复制这段表达式**（6 档，`c` = 上游返回的 `completion_tokens`）：

```text
param("_task.has_video_input") == true
  ? (param("_task.resolution") == "4k"     ? tier("4k_video",      c * 2.4)
    : param("_task.resolution") == "1080p" ? tier("1080p_video",   c * 4.7)
    :                                       tier("480p720p_video", c * 4.3))
  : (param("_task.resolution") == "4k"     ? tier("4k",            c * 4.0)
    : param("_task.resolution") == "1080p" ? tier("1080p",         c * 7.7)
    :                                       tier("480p720p",       c * 7.0))
```

- 末尾 `else` 同时覆盖 `480p`/`720p`（同价）并兜底未匹配值，保证总有 `tier()` 命中（校验要求每个分支都被 `tier()` 包裹）。
- **中转·海外版**（`seedance-2-0-oversea`，2.4 节）：价格相同，只到 1080p（无 4k），用上面**同一段**表达式即可（4k 分支不会触发）。

**可选简化**——若商务决定不区分视频输入（统一按「不含视频输入」价），用这个 3 档版：

```text
param("_task.resolution") == "4k"
  ? tier("4k", c * 4.0)
  : param("_task.resolution") == "1080p"
    ? tier("1080p", c * 7.7)
    : tier("480p720p", c * 7.0)
```

> 以上都用 `c`，结算依赖上游终态回填 usage（反代已透传、中转已解开回填，见下方「前置条件」）。若某渠道上游不回填 usage，改用按秒计费：`tier("per_sec", param("_task.duration_seconds") * <每秒价>)`。

**按 Token 结算的前置条件（务必先验）**

按 token 计费的表达式，结算阶段会把上游真实 token 数代回 `c` 重算：低于预扣时退还差额，超过预扣上界时进入 `debt`。**这要求上游在任务终态返回 `usage.completion_tokens`**，否则结算退化为「保持预扣额度」，不会重算：

- **第三方反代协议**（2.3 节，`dreamina-seedance-2-0-260128`）：系统会**透传**上游返回的 `usage.completion_tokens` / `usage.total_tokens`。上线前**必须用 CURL 确认 Moxing 反代响应里带 `usage` 字段且数值非 0**。
- **第三方中转协议**（2.4 节）：系统已归一化回填上游 usage，与反代使用同一终态结算合同；上线验收仍需确认非零 `completion_tokens`。
- **若上游不返回 usage**：最终扣费 = 预扣 Token 上限 × 命中档单价。此时预扣上限就是真实扣费，必须按典型一次生成的 token 数来定，否则会系统性多扣或少扣。

**两条必须遵守的硬约束**（违反会报错或算错）：

1. **异步任务表达式不能用时变/请求头函数**：`header()`、`hour()`、`minute()`、`weekday()`、`month()`、`day()` 都禁止。因为预扣费和最终结算会对同一表达式求值两次，这些函数两次结果不一致会导致扣费出错。
2. **用表达式计费的模型，必须同时配「预扣 Token 上限」**：在「系统设置 → 计费」里给该模型配一个预扣 token 数（配置项 `任务预扣 Token`）。值可为空，非空时必须是 `1` 到 `1,073,741,823` 的整数；没配、填 `0` 或越界时创建任务会直接报错。这个上限是**预扣阶段代入 `c` 的估算值**，**必须按该渠道的最坏情况设定**（最高分辨率 × 最长时长；含视频输入再加输入视频时长，上限 15 秒，再 × 1.2 余量）——异步视频任务会强制全额预扣，即使令牌设为无限额度也不会绕过；实际用量若超过预扣，tiered 任务**不会补扣，而是进 `debt`（欠款）待人工处理**（[`task_billing_state.go`](../../service/task_billing_state.go#L104)）。当前取值与操作口径见 [01 计费与分组运维手册](../40-operations/01-计费与分组运维手册.md)。

> 保存表达式时，系统会自动校验：用几组 token 和请求输入试算，要求结果非负、每个价格分支都用 `tier()` 包裹。校验不过会拒绝保存。
>
> 管理后台保存配置会立即刷新内存；若运维绕过后台直接修改 `options` 表，需等待下一次 `SyncOptions` 周期（默认不超过 60 秒）或重启后再验收，避免把尚未同步误判为配置无效。

### 3.4 价格配在哪个模型名上（关键提醒）

**价格永远配在「公开模型名」上**（客户端请求用的那个名字），不是映射后的上游模型名。

```text
客户端请求模型:  seedance-2-0-oversea-key      ← 价格配在这里
模型映射:        seedance-2-0-oversea-key -> <上游真实模型>
```

配在映射后的上游名上等于没配，系统找不到价格会按默认值计费或报错。

### 3.5 异步任务的预扣与结算

视频任务是异步的（创建后要轮询等结果），计费分两步：

1. **预扣**：创建任务时，先按估算用量扣一笔额度，防止任务跑完后用户余额已经不够。
2. **结算**：任务进入终态（成功/失败）后，按真实用量重算。成功且费用较低时退差额；超过预扣上界时进入 `debt`，不自动补扣；失败则退还预扣额度。

所以用量日志里会看到预扣和最终扣费两个数，以最终扣费为准。成功结算或差额退款日志应记录真实 `completion_tokens`；失败或超时退款没有可用 usage，Token 显示为 `0` 属正常现象。

## 4. 第三步：配置分组倍率

不同用户、不同线路常常要卖不同的价格。这部分在「**系统设置 → 计费 → 分组定价**」里配。

### 4.1 普通分组倍率

给每个调用分组定一个售价系数：

```json
{
  "economy": 0.8,
  "default": 1,
  "premium": 1.3
}
```

意思是：同一个模型，走 `economy` 线路打 8 折，走 `premium` 线路加价 30%。

### 4.2 用户等级专属倍率

如果想让某些身份等级的用户走特定线路时有专属价，配一个二维矩阵（用户身份分组 × 调用分组）：

```json
{
  "vip": {
    "premium": 1.1,
    "economy": 0.7
  }
}
```

意思是：VIP 用户走 `premium` 时按 `1.1`（覆盖公共的 `1.3`），走 `economy` 时按 `0.7`（覆盖公共的 `0.8`）。

**最终倍率的确定规则**：

```text
如果配了 [用户身份分组][调用分组] 的专属倍率 → 用专属倍率
否则                                        → 用普通分组倍率
```

### 4.3 最终价格怎么算

```text
最终费用 = 模型计费结果（第 3 节算出来的）
          × 最终分组倍率（本节算出来的）
```

举例（数字仅示意）：

```text
模型按次固定价 = $0.04，1080p 图生视频输入倍率 1.5
用户是 VIP，KEY 固定走 premium 分组，VIP 在 premium 的专属倍率 = 1.1
模型计费结果 = 0.04 × 1.5 = $0.06
最终费用 = 0.06 × 1.1 = $0.066
```

### 4.4 充值倍率 vs 消费倍率，别搞混

系统里有两个都叫「倍率」但完全不同的东西：

- **消费分组倍率**（本节讲的）：用户**调用时**的售价系数，影响每次扣费。
- **充值倍率**（在支付/充值设置里）：用户**充值时**的金额或折扣系数，比如充 100 送 20，跟调用计费无关。

答疑时一定要分清用户问的是「充值」还是「调用」，两者改错地方不会生效。

## 5. 第四步：开放给用户（KEY 与分组）

配好渠道和价格后，还要让用户**能选到**这个模型。

### 5.1 让用户能用 Seedance

一个模型对某用户可调用，需要同时满足：

1. **某分组下有该模型的启用渠道**（渠道建好、模型加进渠道、渠道启用，系统会自动形成「分组 + 模型 + 渠道」的能力记录）。
2. **用户属于这个分组**（用户身份分组允许使用该调用分组，或 KEY 指向该分组）。

缺任何一个，调用都会报「无可用渠道」或「模型不可用」。

### 5.2 KEY 怎么选分组

每个 KEY 有一个分组设置，三种填法：

| KEY 分组                             | 行为                                                                         |
| ------------------------------------ | ---------------------------------------------------------------------------- |
| **不指定**（空）               | 跟随用户的身份分组                                                           |
| **固定分组**（如 `premium`） | 每次都走这个分组；用户没有该分组权限会报 403；模型缺失时不会自动跨组         |
| **`auto`**                   | 系统在用户有权的多个分组里自动找有该模型渠道的分组；不同请求可能落到不同分组 |

> **调试技巧**：管理员想强制某次请求走指定渠道，可以在管理员令牌后追加渠道 ID：`sk-<管理员令牌>-<渠道ID>`（如 `sk-xxxx-17`）。只有管理员令牌能用这个语法，普通用户会报「普通用户不支持指定渠道」。

### 5.3 KEY 模型白名单

KEY 可以设「模型白名单」限制只能调某些模型。注意白名单是**收窄权限，不是扩权**：把一个分组外的模型写进白名单，并不会让它在当前分组变得可用——还得该分组本身有这个模型的渠道。

### 5.4 ModelArk 入口提示「无可用渠道」

通过 `/api/v3/contents/generations/tasks` 调用第三方渠道时，按下面顺序排查：

1. 渠道类型必须是 `DoubaoVideo`，状态为启用。
2. `视频上游方案` 必须为空（历史官方兼容）或系统当前登记的 `official`、`third_party_reverse_proxy`、`third_party_relay`；未知值会在 ModelArk 渠道约束阶段被拒绝。
3. 调用分组中必须存在“分组 + 公开模型 + 渠道”的启用能力记录；价格和模型映射不能替代能力记录。
4. 请求含 `asset://` 素材时，素材绑定的可用渠道集合还会与协议兼容集合取交集；素材与上游账号或 profile 不兼容时，不能靠放宽 ModelArk 入口绕过。
5. 若兼容渠道集合非空，最终仍可能因公开模型、分组或渠道状态不匹配而由分发器返回“无可用渠道”。

不要把 ModelArk 北向入口误当成“只能走 ModelArk 官方渠道”。部署了支持第三方 profile 的版本后，只重启旧二进制不会改变行为；验收应同时覆盖任务创建、终态查询、结果下载和用量日志。
