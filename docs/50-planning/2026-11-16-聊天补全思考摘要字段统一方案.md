# 聊天补全思考摘要字段统一技术设计与实施方案

## 目标与范围

为 `POST /v1/chat/completions` 增加一个固定返回的响应扩展。所有渠道的合法成功响应在已有的
每个 `message` 或流式 `delta` 对象中都包含 `reasoning_content`，允许为 `null`。
以当前网关即将写出的响应为基准，只给缺失的键补值，已有字段及其 JSON 值保持原样。
请求校验、参数转换、上游请求体、渠道选择、响应状态、流式交付、用量和账单沿用当前行为。
`/v1/completions`、`/pg/chat/completions`、`/v1/responses` 及 Claude、Gemini 的原生入口
保留各自现有合同。

## 当前行为与证据

| 响应路径 | 当前行为 |
| --- | --- |
| Gemini 原生 → Chat Completions | 按候选分别将标有 `thought: true` 的文本写入 `reasoning_content`，非流式按上游顺序拼接分段。[Gemini 响应转换](../../relaykit/relayconvert/internal/gemini_chat/to_oai_chat_resp.go) |
| Claude Messages → Chat Completions | 将可见的 `thinking` 文本和 `thinking_delta` 写入 `reasoning_content`。已有适配器会将 `signature_delta` 转成换行增量，本期保留该值。[Claude 响应转换](../../relaykit/relayconvert/internal/claude_messages/to_oai_chat_resp.go) |
| 上游 Responses → Chat Completions | 非流式在每个 reasoning 条目中优先读取 `content[].text`，没有文本时读取 `summary[].text`。流式接收 `response.reasoning_summary_text.delta` 与 `response.reasoning_text.delta`，转成 Chat 推理增量。[非流式转换](../../relaykit/relayconvert/internal/oai_responses/to_oai_chat_resp.go) · [流式转换](../../relaykit/relayconvert/internal/oai_responses/to_oai_chat_stream_resp.go) |
| 上游 OpenAI 兼容 Chat Completions → Chat Completions | 默认保留上游字段。DTO 可以读取 `reasoning_content` 和 `reasoning`，对外序列化时仍按原字段名输出。`force_format` 重新序列化 DTO，现有分支也没有别名映射。[`Message` DTO](../../relaykit/dto/openai_request.go) · [流式 DTO](../../relaykit/dto/openai_response.go) · [Chat Completions 输出](../../relay/channel/openai/relay-openai.go) |

TokenAI 线上曾用相同的摘要开启参数请求 `gemini-3.8-flash`。一次返回 `reasoning_content`，
另一次响应的 `model` 为 `ge-3.8-fl-b` 且字段缺失。响应模型标识足以记录差异，具体命中渠道和
上游是否返回可见文本待后台按请求 ID 核对。此前 `/v1/responses` 已实测 Gemini 3.8 Flash 和
GPT-5.5 返回 `summary_text`，Claude Opus 5.5 的请求返回 HTTP 404，仍需可用渠道完成验收。

## 接口合同

| 客户端响应 | 可见推理文本的读取位置 |
| --- | --- |
| 非流式 Chat Completions | 每个已有的 `choices[].message` 对象均包含 `reasoning_content`。 |
| 流式 Chat Completions | 每个已有的 `choices[].delta` 对象均包含 `reasoning_content`。客户端按 choice 的 `index` 拼接字符串增量，跳过 `null` 和空字符串。 |
| 客户端调用 `/v1/responses` | 摘要仍从 `output[]` 中 `type: "reasoning"` 条目的 `summary[].text` 读取。流式摘要仍读取 `response.reasoning_summary_text.delta`。 |
| Gemini 和 Claude 原生入口 | 继续按原生协议读取 Gemini 的 `thought: true` 片段和 Claude 的 `thinking` 块。 |

- 已有 `reasoning_content` 时保留原值，包括 `null`、空字符串和非空文本，哪怕同一对象还有
  `reasoning`。缺键时，复制同一对象中语义明确的字符串 `reasoning`，且仅在 `len(s) > 0` 时
  复制。流式纯空白属于有效增量。缺少可用文本时补 `"reasoning_content": null`。
- 补值只读取已有别名。结构化 `reasoning`、签名、加密内容、正文和用量都不能提供补值。Claude
  适配器已写出的签名换行属于已有值，按相同规则保留。
- `thinking_to_content` 先按原逻辑交付正文。对经该模式改写过的帧，缺键时补 `null`，避免
  重复交付同一文本。首个 `<think>` 帧、`</think>` 帧和主帧按相同规则处理。
- 错误响应、`choices: []` 的用量帧、SSE 注释和 `[DONE]` 按原样写出。
  沿用现有解析和错误处理。OpenAI 兼容非流式的结构化 `reasoning` 仍会在 DTO 解码时返回错误，
  进入 DTO 解码的流式格式化分支也沿用原有错误行为。快速透传路径中，合法 JSON 的结构化别名
  原样保留，缺键的对象补 `null`。原本就透传的非 JSON 或畸形帧继续透传，属于合同例外。
  [非流式解码](../../relay/channel/openai/relay-openai.go#L278) · [流式快路径](../../relay/channel/openai/relay-openai.go#L23)
- 思考深度与摘要请求继续按现有协议生效。是否展示思考区取决于收到的可用文本。流式客户端应按
  choice 的 `index` 拼接，旧客户端可继续读原别名和正文。

## 技术设计

1. 将补键放在已注册的 `POST /v1/chat/completions` 成功输出边界。按方法和 Gin 注册路径限定，
   只处理最终响应中的 `message` 或 `delta` 对象。`RelayModeChatCompletions` 也包含 Playground，
   `RelayFormatOpenAI` 还服务其他路径。共享请求 DTO 及其序列化保持现状。
2. 补键放在现有协议转换、`force_format`、`thinking_to_content` 和用量处理之后。
   共享流式路径在 `StringData` 写出前处理最终帧，`ObjectData` 序列化后也经此路径。共享非流式路径
   在 `IOCopyBytesGracefully` 写出前处理最终正文。这两个公共函数靠方法、已注册路由及成功状态
   限定适用范围。直接使用 `Writer.Write`、SSE `Render` 和 AWS Nova JSON renderer 的渠道保留原写法，
   在各自写出前接入同一规则。流式处理逐帧执行。
3. 共用一个按 JSON 键存在性补值的实现。用现有 GJSON 读取字段及字节位置，只在缺键对象的结尾
   插入新成员。未修改的 JSON 片段直接沿用原始字节，大整数和未知字段无需重新编码。无需补键时
   返回原始载荷。合法成功帧漏补视为验收失败。已有透传行为的异常帧维持原有交付和错误处理。
   [补键实现](../../common/chat_completion_reasoning.go)
4. 补键主体放在协议归属明确的新增文件中。每个无法复用共享写出点的原生文件仅保留必要调用，
   在实现评审中说明必要性、接线点和上游同步冲突面。字段补齐以客户端最终 JSON 为准。
   [NEWAPI 原生代码最小入侵约束](../00-context/硬约束.md#7-newapi-原生代码最小入侵)

### 响应与客户端兼容性

- 用同一上游夹具比较变更前后的 HTTP 与 SSE 输出。断言已有值逐项相等，未知嵌套字段的大整数值
  精确保留。覆盖多个 choice、已有文本、已有 `null`、已有空字符串、字符串别名及缺少别名。
  已有字段为空但别名有值的场景也应保留空值。非流式测试核对正文变化时移除旧校验头，
  已有字段、错误响应和其他接口保留校验头，长度与请求 ID 继续使用既有行为。
- 流式覆盖开始、正文、推理、纯空白增量、工具参数、停止、纯用量、注释和 `[DONE]`。
  覆盖 `force_format` 与 `thinking_to_content` 的全部写出帧，以及末帧与异常帧的既有处理。
  验证流式事件顺序、结束信号、flush、错误语义及用量。补键逻辑只操作对外副本。
- 使用实际入口的固定请求对比发往上游的请求体及请求参数，在普通转换、全局请求体透传和渠道请求体
  透传三种配置下分别验证。同一输入的上游请求应保持一致。另用代表性 SDK 或 UI 执行两轮对话，
  分别覆盖按目标渠道的输入合同构造历史消息，以及原样回传首轮 assistant 消息。严格模拟上游会
  拒绝消息中的 `reasoning_content`，用于验证网关保留原有请求与错误行为，同时按渠道允许的字段
  构造消息后第二轮可以成功。灰度须用实际 SDK 或 UI 检查 `null` 和非空文本，覆盖普通转换和
  已启用的透传模式。严格渠道须验证客户已按目标输入合同组装历史，或者上游已接受响应扩展。
  如果仍有客户端原样追加 assistant 响应并因此新增 4xx，暂停扩大灰度。已影响客户时回滚
  纯补键发布。自动删字段或失败后改写重试需要独立的请求合同变更。
- 验证客户端可读取非空文本，并在 `null`、空字符串和纯用量帧时正常展示最终回答。按键是否存在
  开启思考区的消费者属于兼容性检查对象。用合成响应验证指定为范围外的接口形状保持一致。

### 严格上游的 SDK 多轮接入

面向接受文本和标准函数调用的严格渠道，可用 OpenAI Python SDK 在收到响应后保存摘要供展示，
并从响应单独构造下一轮接受的 assistant 消息。函数调用保留 ID、名称和原始参数字符串，
工具结果继续用该 ID 建立 `role: "tool"` 消息。适配其他请求字段时，以目标渠道输入合同为准。

```python
def assistant_for_history(message):
    return message.model_dump(
        mode="json",
        exclude_unset=True,
        include={
            "role": True,
            "content": True,
            "tool_calls": {
                "__all__": {
                    "id": True,
                    "type": True,
                    "function": {"name", "arguments"},
                },
            },
        },
    )
```

非流式将 `response.choices[0].message` 交给该函数，摘要从原消息的 `reasoning_content`
读取。流式从 `choices[].delta` 按 index 收集摘要，针对用于续接的 choice 汇总完整正文及工具调用，
再按相同字段构造历史。SDK 使用 `client.chat.completions.stream(...)` 时，可从
`stream.get_final_completion().choices[0].message` 取得汇总后的消息。
对要求回传推理文本、原生签名或其他状态的渠道，按该渠道的合同保留必需的续接数据。这段示例适用于
只接收正文和标准函数调用的渠道。网关仍固定输出 `reasoning_content`，并将透传请求按原字节发送。

### 性能验收

- 用同一构建环境、相同上游 fixture、连接设置、并发和帧数比较旧版与候选版。使用短正文密集流作为
  主基准，再覆盖长文本或工具帧、已有字段直接写出、需要复制别名、`force_format` 和正文模式。
  非流式包含常规小响应和大响应。
- 记录补键处理的 `ns/op`、`B/op`、`allocs/op`。在完整 HTTP/SSE 路径记录吞吐、首帧和帧间
  延迟的 p95、CPU 与内存。单列补 `null` 带来的传输字节增长，避免与处理耗时混为一项。
  处理仅保留当前帧，客户端可在流结束前持续收到帧。
- 灰度通过以满足现行性能目标、无持续性可归因回退为准。批次 1 用同机重复基线标注波动范围和可接受
  阈值，批次 2 用同一口径提交对比结果。普通正文帧通常需要补键，性能验收计入这个主路径。

后端回归运行 `go test ./common ./service ./router ./relay ./relay/helper ./relay/channel/...`，并按清单确认实际执行的
合同测试。新增后端测试使用项目约定的 `require` 和 `assert`。若单独修改 `relaykit`，在该目录运行
`GOWORK=off go test ./relayconvert/...` 与 `GOWORK=off go build ./...`。文档运行 `task docs:check`、
`task ai:check`，公开 API 文档更新时再运行 `cd web && bun run docs:validate`。

### 独立的 Gemini 转换修复

Gemini 按候选和上游顺序原样拼接各段思考文本，保留上游已有的空格和换行。非流式和流式单帧使用
同一规则，符合 Google 的流式示例逐段追加 `part.text` 的方式。单段、空思考和无思考保留原有值语义。
修复接在现有转换器分段赋值处，接取上游时核对两处摘要分支。复用该转换器的跨协议路径也会收到修复后的文本。
[Gemini 官方流式示例](https://ai.google.dev/gemini-api/docs/generate-content/thinking?hl=en)

流式转换也已按候选分别累积思考与正文。上游同一帧含两类文本时，分别写入同一 `delta` 的
`reasoning_content` 和 `content`。开启 `thinking_to_content` 时，再次收到摘要会重新打开
`<think>`，后续摘要延续同一段。下一段正文到来时直接在它所在的原帧内闭合标签，并按前缀的字符数
移动 `url_citation` 的区间。同一帧的引用、工具调用、用量和结束原因只写一次。仅有工具调用的帧
照常交付，已有思考段保持打开；若流结束时仍在思考段内，沿用终止信号，不补闭合标签。经过共享写出
且启用此选项的 OpenAI 格式流按 `choice.index` 单独维护开闭状态，候选可以在不同帧进入或结束思考。
原生代码统一接到独立文件处理。原闭合分支复制整帧，会重复发送工具调用、结束原因和用量。
