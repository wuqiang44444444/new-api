## 2. 状态与使用方法

| 标记 | 含义 | 如何处理 |
| --- | --- | --- |
| 手验 | 代码已有本地证据，尚缺目标环境验证 | 先在隔离测试分组执行，再决定灰度 |
| 环境 | 依赖目标账号、价格、存储、数据库或部署 | 先补齐前提，再执行对应手验 |
| 复验 | 文档已有真实失败或未决结果 | 先核实旧请求及配置，再验证修复结果 |

| 状态核对 | 不同文档对完成状态描述冲突 | 先找关闭依据；已完成则登记依据，不重复测试 |

建议顺序：A 配置准备 → B 价格与合同 → C 聊天 / D Batch / E—G 视频素材 → H 图片 → I 证据 → J 灰度。
按本次实际准备发布的模型选择分支，不要求一次执行所有付费组合；先做小规模代表性场景，再补必要边界。
涉及断连、重启、并发和故障恢复的演练使用隔离环境。只使用合同内正常数量及已有边界，不制造无业务意义的极端压力。

- 每个编号可对应多条“环境 × 客户模型 × 协议 × 场景”结果；所有适用子项通过后才勾选。
- 失败、未知和缺环境均保持未勾选，并记录阻塞原因；不适用项填写原因和确认人，不伪装成通过。
- 已有等价证据且版本、配置、场景仍适用时，可以引用原证据关闭，不必重复产生费用。
- 创建返回成功仅证明受理；生成效果、内容交付、客户扣费、Provider 账单分别记录。
- 创建结果不明只查询、对账和按既有流程处置，不重复 POST。Provider 成本未知时保持未知。
- 文档只保存脱敏摘要及受控证据索引，不粘贴凭据、完整签名 URL、Task 私有数据或原始 Provider 响应。

## 3. 分批手动验收

### A. 配置、版本与数据库准备

来源：[路线图](路线图.md)、[P0 盘点](../80-dev/2026-09-10-Seedance插件迁移P0本地盘点.md)、
[rc36 同步记录](../80-dev/2026-09-10-上游rc36同步实施与验证记录.md)、
[全渠道验收手册](../40-operations/05-全渠道上线验收手册.md)。

- [ ] **A01｜环境｜建立本轮验收矩阵。** 记录实际前后端版本、目标数据库版本、测试分组及拟发布的客户模型、
  精确映射、视频/素材协议、价格和合同绑定。对生产配置做脱敏只读盘点，并准备备份及恢复点；不沿用本地快照数量推断生产。
- [ ] **A02｜复验｜Seedance 渠道保存问题。** 复现路线图记录的保存故障，记录实际操作和错误；验证新建、编辑、
  停用后启用、同渠道保存及跨渠道重复启用。合法配置能保存，冲突只在管理保存/启用时拒绝；未复现时记录版本和步骤。
- [ ] **A03｜环境｜补齐明确的价格配置缺口。** 核对 P0 中 `seedance-2.0-cmcc` 无价格、
  `happyhorse-1.1-i2v` 有 tiered 模式无表达式的问题是否仍存在；按各自真实计量配置并验证保存、展示和预扣。
  前者未补价及素材/账单验收前不进入切换批次，后者单独按原生模型处理。
- [ ] **A04｜环境｜核对孤立价格条目。** 复核 P0 列出的无渠道引用价格名及当前用途；记录保留或另行清理的决定，
  不根据名字自动删除、迁移或推断 Link 身份。确认这些条目不会被误列为已可调用模型。
- [ ] **A05｜环境｜插件 1.0.2 明确激活。** 已有 active 版本的部署由管理员激活新版本，检查所有目标节点实际装载；
  新安装核对自动初始化。历史版本和冻结引用保留，节点重启后新请求使用已激活版本、旧任务仍能按原版本履约。
- [ ] **A06｜环境｜目标业务数据库升级。** 用目标部署的备份副本验证 rc36 与本地保留项、合同和托管素材相关迁移及重启，
  记录迁移前后数据与配置。已有隔离三库结果可引用；不能替代实际业务数据升级。Batch 专项另外执行 D08。
- [ ] **A07｜环境｜最低支持版本。** 补齐 MySQL 5.7.8、PostgreSQL 9.6 的兼容证据；若本轮部署不使用这些版本，
  单独记录为未覆盖的兼容门槛，不把 MySQL 8/PostgreSQL 16 成功写成最低版本通过。

### B. 多合同、计费表达式与历史账单

来源：[合同开发与验证](../30-engineering/用户模型合同开发与验证.md)、
[表达式方案 §8.3](../80-dev/2026-09-10-计费表达式前端试算与价格展示分析及修复方案.md)、
[定价回归与迁移评估](../80-dev/2026-09-09-Seedance定价回归修复与Doubao渠道迁移评估.md)、
[计费运维手册](../40-operations/01-计费与分组运维手册.md)。

- [ ] **B01｜手验｜合同与 Key 绑定闭环。** 用同一用户的两份合同及不同 Key 验证各自模型、渠道和价格；
  再检查另一用户、无绑定 Key、停用合同和受限 Key。页面选择、保存重开、模型发现及实际请求的授权结果一致。
- [ ] **B02｜手验｜Seedance 合同渠道约束。** 对合同指定渠道正常调用；再用与合同冲突的 Token 指定渠道调用。
  正常请求只到约定渠道，冲突请求在发送和扣款前拒绝，不重新选渠；Batch 按其自身合同规则同样核对实际渠道。
- [ ] **B03｜手验｜真实折扣与预算。** 对原生、Seedance、Batch 各选本轮适用样本，核对组/用户组/合同折扣、
  输出预算、钱包和 Token 限额。预扣及实际结算按冻结事实计算，折扣不重复叠乘，余额不足不发送付费请求。
- [ ] **B04｜手验｜原始表达式保存与试算。** 使用原方案两条原式及实际部署表达式，保存再打开，确认原文和语义不变；
  选择高峰、空闲、周末与边界时刻试算，核对服务器返回 quota、时间窗口和倍率，不为适应页面改写公式。
- [ ] **B05｜手验｜所有价格展示入口。** 检查公开价格卡片/列表、分组、合同、管理摘要、日志；同一表达式单价及
  USD/人民币/充值展示口径一致。切换模型、编辑及请求失败时不残留旧金额；不能展开的合法公式不伪造单价或显示假零。
- [ ] **B06｜手验｜真实消费复算。** 用新消费记录逐项核对输入、缓存、输出用量、结算时刻、实际组/合同、整数 quota
  与 Provider 账单；覆盖本轮实际使用的 OpenAI/Claude 用量口径。没有真实账单只记录本地/客户侧通过，不写成供应商对齐。
- [ ] **B07｜手验｜历史价格不被重新解释。** 修改测试模型当前表达式后查看既有日志/任务，确认原金额及冻结表达式不变；
  缺少命中事实或快照时明确未知，不按当前时间或价格补算历史。
- [ ] **B08｜复验｜历史缺证据账务。** 定价盘点中 21 条缺实际用量且保留预扣、32 条缺表达式快照的旧任务逐项确认
  现状，补充可信用量/账单或保留未知。另在目标部署只读核对原生 `TaskUsageBilling` 异常上下文；既有 settled 不直接重开。
- [ ] **B09｜手验｜媒体模式对应实际表达式。** 对纯音频、视频参考、混合媒体核对新请求冻结探针与已保存价格分支，
  特别检查 `has_video_input` 与输入模式。预扣、实际用量、补退一致；不回写旧探针，也不借其它 Provider 价格补空缺。

### D. Azure Batch

来源：[Batch 实施方案](../80-dev/2026-09-09-Azure批处理与多合同渠道定价实施方案.md)、
[Batch 实施记录 §4](../80-dev/2026-09-10-Azure批处理与多合同渠道定价实施记录.md)、
[联合修复记录](../80-dev/2026-09-10-多方案联合评审问题修复与验证记录.md)。

- [ ] **D01｜环境｜真实 Azure Batch 配置。** 核实部署/SKU、API 版本、鉴权、每行端点及输出上限支持；
  明确合同候选渠道的实际映射和线路价格，不能仅凭普通 Azure Chat 可用就开放 Batch。
- [ ] **D02｜手验｜SDK 全流程。** 通过实际客户 SDK 上传合法小型 JSONL，执行文件查询/内容、Batch 创建/查询/列表，
  等到结果可交付并下载。模型、`custom_id`、计数和状态符合公开合同；只验证已发布方法，不要求实现 Files DELETE。
- [ ] **D03｜手验｜成功、部分结果与取消。** 覆盖完成和取消，取得真实可核实的部分执行/失败结果；
  已执行行与未执行行可区分，状态和结果就绪时间一致，取消不直接整单全退，超过 24 小时目标不自动判失败退款。
- [ ] **D04｜手验｜逐行用量及收费。** 对输入、输出、缓存和失败行收费依据逐行对账；结果明细和计数一致，
  用量缺失保持待核实，可信费用按冻结价格一次结算。客户扣费、Provider 成本分别有来源。
- [ ] **D05｜手验｜客户结果文件。** 对新归集的成功文件和错误文件下载验收：公开模型来自创建时冻结的客户模型，
  失败元数据为统一错误，回答、`custom_id`、usage 保持原义，文件大小与实际交付字节一致。普通用户不获得上游身份或私有存储引用。
- [ ] **D06｜手验｜文件与作业隔离。** 用不同 user/app/合同 Key 查询输入、输出、错误文件和作业，越权均拒绝；
  合同/渠道/价格更新后，已创建作业仍按冻结身份处理，新请求才使用新配置。
- [ ] **D07｜手验｜中断及 SDK 重试行为。** 在隔离环境检查 SDK 自动重试设置、创建后断连、归集中断和恢复；
  结果不明不产生第二个 POST，不换渠道或退款；已有可信 ID 按既有恢复流程补全，不能把客户端错误当作未受理证明。
- [ ] **D08｜环境｜Batch 三库生命周期。** 分别在 SQLite、MySQL、PostgreSQL 的隔离真实库上执行表迁移、创建、
  重启重入、结果归集和结算，确认 Task、attempt、hold 及作业关联一致。rc36 schema 验证和插件锁测试不替代 Batch 验收。
- [ ] **D09｜环境｜已承诺容量。** 使用 10,000 行、合法长单行及超过 20 MiB 的结果文件，记录实际耗时、内存和存储用量；
  验证流式归集、中断恢复与完整交付，不重复扣款。按部署并发观察瓶颈，不先为假想规模增加抽象或缓存。
- [ ] **D10｜手验｜存储故障与诊断。** 隔离环境验证上传/归集存储不可用时客户收到稳定安全错误，管理员能关联到
  已净化的原因；恢复后继续既有归集流程，不能丢失资金事实或凭空形成成功结果。
