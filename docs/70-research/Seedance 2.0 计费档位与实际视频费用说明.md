# Seedance 2.0 计费档位与实际视频费用说明

> 目的：解释模型费用界面中的 `4k_video`、`4k` 等档位分别代表什么，以及为什么 4K 的每百万 Token 单价最低，但最终生成一条 4K 视频并不最便宜。
>
> 运维配置与可直接复制的表达式见 [Seedance 2.0 三渠道价格与计费表达式](../40-operations/Seedance%202.0%20三渠道价格与计费表达式.md)。

## 1. 结论

1. `4k_video` 和 `4k` 的输出分辨率都是 4K；后缀 `_video` 表示请求中含有输入视频，不表示“输出是视频”。
2. 界面显示的 `$2.4000`、`$4.0000` 是每百万输出 Token 的单价，不是生成一条视频的固定价格。
3. 4K 每百万 Token 单价虽然低于 1080p，但 4K 产生的 Token 更多，因此最终单条视频价格仍然更高。
4. 当前六档表达式与 BytePlus 官方价格一致，没有把 4K 和 `4k_video` 的价格写反。

## 2. 六个档位的真实含义

当前表达式首先判断 `_task.has_video_input`，再根据 `_task.resolution` 选择档位：

| 档位 | 命中条件 | 实际含义 | 单价 |
| --- | --- | --- | ---: |
| `4k_video` | 4K 且含输入视频 | 4K 视频生视频 | $2.4 / 百万 Token |
| `1080p_video` | 1080p 且含输入视频 | 1080p 视频生视频 | $4.7 / 百万 Token |
| `480p720p_video` | 480p/720p 且含输入视频 | 480p/720p 视频生视频 | $4.3 / 百万 Token |
| `4k` | 4K 且不含输入视频 | 4K 文生、图生或参考图生视频 | $4.0 / 百万 Token |
| `1080p` | 1080p 且不含输入视频 | 1080p 文生、图生或参考图生视频 | $7.7 / 百万 Token |
| `480p720p` | 480p/720p 且不含输入视频 | 480p/720p 文生、图生或参考图生视频 | $7.0 / 百万 Token |

`_task.has_video_input` 的代码口径很窄：只有请求中存在 URL 非空的 `video_url` 时才为 `true`。文本、首帧图、首尾帧图和普通参考图都不会命中 `_video` 档。实现见 [`billing_probe.go`](../../relay/channel/task/doubao/billing_probe.go)。

因此，更不容易误解的档位名称可以写成：

| 当前名称 | 等价解释 |
| --- | --- |
| `4k_video` | `4k_with_video_input` |
| `4k` | `4k_without_video_input` |

`tier()` 的档位名称只用于记录和展示命中的档位；参与费用计算的是第二个参数，例如 `c * 2.4`。

## 3. 界面中的“输出价格”是什么

费用界面从表达式 `c * 单价` 中提取 `c` 的系数，并把它显示在“输出”列。因此：

```text
4k_video  $2.4000
```

应读作：

```text
命中 4k_video 时，输出 Token 单价为 $2.4 / 百万 Token
```

不应读作：

```text
生成一条 4K 视频收费 $2.4
```

在表达式系统中，`c` 是上游终态 `usage.completion_tokens` 回填的计费 Token。表达式先得到 `c × 单价`，结算时再除以一百万并转换为内部额度：

```text
表达式结果 = completion_tokens × 档位单价

内部额度 = 表达式结果
         ÷ 1,000,000
         × QuotaPerUnit
         × 最终分组倍率
```

对应实现与设计说明：

- [`pkg/billingexpr/expr.md`](../../pkg/billingexpr/expr.md)：表达式系数的单位是 USD / 百万 Token。
- [`pkg/billingexpr/settle.go`](../../pkg/billingexpr/settle.go)：结算时执行 `exprOutput / 1_000_000 * QuotaPerUnit`。
- [`billing-expr.ts`](../../web/default/src/features/pricing/lib/billing-expr.ts)：前端把变量 `c` 的系数映射为“输出”价格。

## 4. 为什么 4K 单价低，最终费用却更高

Seedance 2.0 的计费 Token 不是文本分词 Token，而是根据视频时长、分辨率和帧率折算的视频几何量：

```text
预计 Token =
  (输入视频时长 + 输出视频时长)
  × 输出视频宽
  × 输出视频高
  × 输出视频帧率
  ÷ 1024
```

没有输入视频时，输入视频时长为 0。存在输入视频时，输入和输出视频时长都会进入 Token 计算。

在相同画幅、帧率和时长下，4K 的像素量远大于 1080p，所以产生的 Token 也远多于 1080p。较低的每百万 Token 单价只抵消了部分 Token 增量，并不会让 4K 的最终价格低于 1080p。

### 4.1 无视频输入的官方价格示例

BytePlus 官方给出的 16:9、24fps、输出 5 秒示例：

| 输出分辨率 | 每百万 Token 单价 | 单条视频预计价格 |
| --- | ---: | ---: |
| 480p | $7.0 | $0.35 |
| 720p | $7.0 | $0.76 |
| 1080p | $7.7 | $1.87 |
| 4K | $4.0 | $3.89 |

虽然 4K 的单位 Token 价从 `$7.7` 降到 `$4.0`，但单条 4K 视频仍约为 1080p 的 2.1 倍。

### 4.2 含视频输入的官方价格示例

BytePlus 官方给出的 16:9、输出 5 秒、输入视频 2–15 秒示例：

| 输出分辨率 | 每百万 Token 单价 | 单条视频预计价格区间 |
| --- | ---: | ---: |
| 480p | $4.3 | $0.39–$0.86 |
| 720p | $4.3 | $0.84–$1.86 |
| 1080p | $4.7 | $2.06–$4.57 |
| 4K | $2.4 | $4.20–$9.33 |

因此，`4k_video` 的 `$2.4` 虽然低于 `4k` 的 `$4.0`，但含视频输入时还会把输入视频时长计入 Token，最终费用通常更高。

BytePlus 官方定价页确认了这组单价和单条视频示例，但没有说明为什么选择这种阶梯曲线。能够确认的事实是：高分辨率和视频输入具有更大的 Token 消耗，较低的单位 Token 价只是在一定程度上平滑最终价格。

## 5. 对当前三渠道配置的判断

当前三个渠道使用同一套六档表达式时：

- `4k_video = c * 2.4`：正确；
- `4k = c * 4.0`：正确；
- 1080p 和 480p/720p 的四个系数也与 BytePlus 官方价格一致；
- 第三方中转渠道如果不支持 4K，请求不会命中 4K 分支，保留该分支不会改变现有费用。

因此无需因为界面中 4K 单价较低而调换表达式系数。核对账单时应使用：

```text
实际 completion_tokens × 当前命中档位单价 ÷ 1,000,000
```

而不能只比较界面中的单位 Token 价格。
