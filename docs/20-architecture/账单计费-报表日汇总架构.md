# 报表日汇总架构

本文描述已接入的报表读取、后台生成及发布边界。客户与上游的计算规则及正式月账单版本继续由
[客户与上游对账架构](账单计费-客户与上游对账架构.md)定义。资金和异步任务事实继续由
[异步任务与计费事实架构](账单计费-异步任务与计费事实架构.md)定义。

## 1. 职责与权威来源

| 数据 | 权威来源 | 报表用途 |
| --- | --- | --- |
| 消费、退款及计费证据 | 既有结算日志、Task、交付事件与 Batch 事实 | 账单按资金事件发生日归集。用量按既有完成时间、关联和去重规则归集 |
| 客户已确认月账单 | 现有正式版本、明细和产物 | 优先读取冻结结果，更正走现有版本流程 |
| 上游参考金额 | 现有计费快照和月度渠道系数 | 冻结本批使用的配置及版本，沿用逐笔计算和取整规则 |
| 历史日汇总和下钻 | 生产库中的报表批次、汇总和最小明细投影 | 只读展示，可重建。余额、额度、正式版本和业务写入继续走现有权威入口 |

计算复用现有账单解析、退款匹配和用量聚合器。客户账单、上游对账和用量各自使用原计算口径，
共用批次发布和资源控制。Dashboard 的 `quota_data` 仅保留现有看板用途。

## 2. 数据粒度与读取

- 以北京时间自然日为基本粒度。历史汇总按视角、作用域、日期和已有分组维度索引。客户键使用稳定的
  客户、应用及 API Key 身份，上游键按现有渠道、上游模型、计费方式与身份来源区分。展示名称与权限
  分离，已删除 Key 或渠道沿用现有展示语义。
- 个人与管理员的用量统计均从同一套日投影读取。日视图读取所选日，周视图合并北京时间周一至周日的日
  版本，月视图合并自然月内已发布的日版本。导出沿用本次读取的版本引用。管理员个人区
  使用当前登录用户的范围，管理区由现有管理权限控制。
- 用量总览、模型排行和管理员渠道排行共享所选范围和发布批次。排行按调用次数、Token 或该视角的
  金额在已发布的分组行上排序和分页。总览读取全范围聚合。总 Token 使用现有归一输入与输出，缓存读写作为
  输入子项保留；来源缺项及已知小计沿用现有质量口径。客户视图读取客户净费用，管理员上游视图
  读取渠道口径的上游参考费用。
  管理端全客户模型排行按客户模型与冻结计费方式分组并在服务端分页，单客户排行从同批客户叶行按同一维度聚合。
  Token 行展示已记录的 Token，按张行展示结算使用的有界数量，按秒行使用原有计量事实。计费方式缺证的调用和金额
  留在未知行。未保留计费方式的旧日版本在排行保持未知，按来源重建后才能拆分。渠道排行先选出请求页，
  再从同批冻结日投影合并图片张数、计费秒数和缺项状态。
- 调用次数复用现有用量聚合。客户按已结束的逻辑调用统计并保留结果分类，Batch 按行级结果计数，
  异步任务的结算或退款事件沿用原调用身份。上游按既有证据规则统计已证实发送的尝试。两个视角分别
  汇总，排行、下钻与导出使用同一视角的计数。
- 管理员上游对账增加 URL 汇总层，先按渠道和模型完成核算，再按规范化基础 URL 合并已核算金额、
  用量和待核算状态。复用现有 URL 分组身份规则，无法安全识别的 URL 按渠道分别归入未识别项。
  URL 归属和渠道集合随批次冻结，下钻仍由服务端校验渠道范围。首次回填只有当时的渠道配置时，URL
  归属按该次配置展示。已发布日期因迟到事实修正时，复用该日的已发布映射。分组用于管理员展示，
  渠道月度系数、逐笔取整、供应商身份和计费规则仍由既有渠道事实决定。
- 保存可合并的计数、计量、消费、退款、已知金额及缺失/待结算状态。均值保存分子和样本数。周期内
  按已核验的可加指标合并，再沿用原有计算器处理舍入、质量、折扣组合等非简单加和指标。过滤后的
  全范围总计与当前页行分开查询。
- 用量的任务净费用和退款活动使用独立指标，按各自日期归集。退款活动采用已入库资金事件的稳定身份。
  客户、应用、Key、渠道、模型与 Task 的既有身份检查决定能否回补任务净费用。含糊或缺证的关联
  保持待核对。视频退款状态为 pending、已记录退款起算时间且超过 24 小时、资金仍未退清时，
  用量将该状态纳入日版本，单客户账单按请求即时读取待退款计数，已确认月账单也可显示。
  两处提示独立于已发布净额和下载内容，净额只计实际已入账金额。
- 同一报表发布批次登记每个日期使用的数据版本。下钻和异步导出绑定相同批次与筛选范围，并按发起人和
  当前授权校验。明细按权限保存用于核对的字段与来源标识，避免历史源变化后出现汇总与明细不符。
  原始 `other`、Task 私有数据、请求正文、上游响应和密钥继续由原安全边界管理。深层单笔证据仍走
  既有授权入口。
- 客户账单的默认明细按发生日和已核验的调用或任务身份归组。后端在同一批次的授权和筛选范围内聚合，
  再对归组行分页；扣款、退款及净额从同批逐笔事件计算。待核对事件按稳定流水身份单列。展开和逐笔
  导出读取原事件投影。列表直接读取后端算出的有符号净额，费用明细保留扣款和退款组成。日汇总、
  归组行和逐笔事件是同一份资金事实的不同读取粒度。

## 3. 使用日志查询

控制台的使用日志直接读取最新已入库日志。个人和管理员沿用各自的日志入口。关系库通过
`page_cursor` 和 `log_ref` 读取列表和详情，范围统计通过 `range_count` 按需读取。

1. 首屏默认使用最近一小时，按页大小多读一条判断是否还有数据。普通用户查询继续应用最大时间窗。
   列表仅返回摘要，单笔详情按引用重新鉴权后读取。
2. 关系库管理员按 `created_at DESC, id DESC` 延续边界，个人按 `id DESC` 且始终限定认证用户。
   游标绑定筛选和排序，修改筛选后从首屏重查。ClickHouse 沿用页码分页，列表直接携带授权详情。
   同秒、同 Request ID 的错误与消费记录按事件类型进一步排序。
3. Request ID 等值查询保留角色范围和显式时间条件。范围统计按需执行精确计数与费用汇总。游标列表、
   详情和范围统计各有三秒查询期限，取消随请求上下文传递。
4. 原页码接口继续服务现有调用方。账单下钻单独绑定报表或正式月账单版本。

## 4. 后台生成与发布

1. 关系型日志部署启动后，现有系统任务调度和租约自动承接昨日生成、首次回填及历史修正。
   03:00 触发昨日生成，重启后自动补排最近 90 个已结束自然日内的缺失日期。已有待发布投影可复用，失败日期延后重试。
   客户原价解析版本升级后，日报任务从最近已结束日期向前检查仍保有消费或退款日志的日期，包括 90 天以前的日期。
   已按当前版本发布的日期跳过，旧版或缺失日期每轮最多新增一项重建。队列和解析版本游标同事务推进，重启后继续。
   到期的常规昨日生成和当日刷新优先于原价回补，回补沿用日报的资源门控和日期重试。
   账单和用量候选均保存原价解析版本，升级后重新构建低版本候选。
   客户用量的计费单位投影独立记录版本。主节点启动后，日报任务自动发现仍在发布的历史旧版本，按最近日期
   逐日重建用量，范围覆盖已有发布记录。新版本通过原有校验后切换指针，低版本候选重新生成。并存的迟到
   退款沿用关联范围原子发布。若来源覆盖下降，保留旧版并登记重试。
   控制台汇总、下钻和新导出统一读已发布版本。今天的阶段性结果每三小时更新。
2. 用普通已提交读分批扫描。每批绑定取消和时限，及时释放查询连接，再解析和聚合。固定本次读取边界，
   把通过验证的事实按稳定身份写入待发布版本。提交顺序和 ID 顺序可能不同，扫描上界只控制工作量。
3. 为历史批次记录各来源读取边界和覆盖情况。关系库按固定边界复核来源行数。PostgreSQL 另外复核行版本摘要、
   任务交付和计费配置的日期范围。清理覆盖状态沿用现有日志清理任务及同库账单来源保留信息。仅当已验证的汇总与待发布明细一致时发布该版本。
   来源在构建期间变化时重新安排对应范围。证据覆盖不足时保留待核对状态，数据截至描述本批已纳入的
   证据边界。
4. 以短事务更新报表发布引用，旧批次在引用有效期内保持可读。可由已投递任务事件确定的
   跨日退款，在同一次发布中切换受影响的日期引用。导出受理和版本退役锁定同一报表状态行，已受理
   的导出保留结构化版本引用。停止接受新引用后再分批清理。重试重复生成相同范围会替换待发布结果，资金事件和
   任务计数以稳定身份去重。失败或租约丢失时继续提供上一批已发布结果。
   若关联的更早日期已确认失去来源覆盖且有更完整的已发布版，在同一发布事务内保留该日版本并登记
   待核对状态，其余验证通过的范围继续发布。其他生成或校验失败仍保留整个批次的原指针。
5. 后台按已有日志和交付事实发现迟到退款及补报，并按任务稳定身份定位其完成日。对缺少可靠变更游标
   的来源做有界回看，并保留按日期主动重算入口供历史补修或配置更正使用。已保存的旧日可定向修正。Root 通过 `POST /api/billing/admin/reports/rebuild` 提交北京时间日期触发重算。
   若源已清理且报表保留的证据不足以验证更正，保留旧版和待核对状态。

待退款候选随既有报表刷新重评，等待跨过 24 小时或资金退款完成时刷新受影响的任务范围。读取资金
提交事实区分仍待退款与退款已完成、报表日志尚未补齐。

发布前只对报表自身的状态或指针使用短写事务。历史和当天扫描均使用普通读。当天允许按同一读取边界
发布带时间的阶段性结果。页面取数和手工刷新只读取已发布结果或请求后台工作。冻结正式账单与历史
报表批次分别管理。

## 5. 共库资源控制

- 账单和用量共用 `usage_report_day` 系统任务和执行槽。生成每个关系型来源使用独立单连接读池，
  同库共享一个读池。CPU 达到 70%、内存达到 80% 或采样不可用时，资源门控在批次之间等待。
  发布前保留上一次成功结果。
- 本地开发启动脚本对环回 PostgreSQL 启用连续回补。使用同一日报租约串行推进历史日期，省去日期之间的
  调度等待并跳过日报 CPU、内存门槛。逐日校验、发布事务、取消和重试继续由同一任务负责。
- 后台扫描使用批级预算，报表写入分批提交。旧代际至少保留八天，已受理导出持有引用，待引用解除后
  才能清理对应代际。
- Dashboard 的 `SaveQuotaDataCache` 在收集锁内交换待写数据，在锁外由单一执行者分批提交。
  批次回执与计数增量在同一事务写入，进程内重试可识别已经提交的批次。

## 6. 安全、兼容与接线

报表接线集中在 `model/daily_report_*`、`model/billing_report_*`、`model/usage_report_*` 和系统任务。
控制台日志仅在显式请求游标、详情或范围统计时进入专用读取路径。下钻与导出复验日期版本及角色范围。
账单通过 `report_version` 绑定所选账期的代际集合。用量通过 `report_days` 绑定日和代际，
同一范围的排行与导出沿用该集合。用量接口只接受 `period=day|week|month` 和北京时间日期，
周期边界由服务端计算。个人 `/api/usage/self/summary` 使用认证用户身份。管理员通过
`/api/usage/admin/customers`、`/customer-summary` 和 `/upstream-summary` 读取全客户、
单客户与上游范围。上游下钻校验冻结 URL 与渠道的组合；全客户模型和上游渠道排行由后端分页，
个人模型排行使用所选 API Key 范围内的用量。

日报支持 SQLite、MySQL 和 PostgreSQL 日志源。ClickHouse 的上游交互查询按渠道 ID 下钻，保留
调用方的请求上下文。日报入口明确返回来源不支持。正式月账单仍有同库拓扑和来源核验条件。真实生产的
90 天容量、迟到覆盖和关键 API 延迟是报表启用切换门槛，见[路线图](../50-planning/路线图.md)第 39 项。

## 7. 账单发布版本

- 日账单由报表任务按已入库资金事件发生日建立。候选版本分别保存客户总览、客户维度叶行、渠道计费叶行
  和逐笔证据。新日报直接保存可核验的逐笔原价与可合并小计。原价、优惠及净额的口径统一以
  [客户与上游对账架构 §7.1](账单计费-客户与上游对账架构.md#71-客户账单) 为准。
  历史复算与新写入共用原价判定。逐笔投影标识复算来源，候选与日报代际记录解析版本。
  候选复用和发布检查解析版本。更换日指针前核对同一来源范围内的入账身份、金额和旧版可核验原价，
  防止源笔数不变时已核验的原价覆盖降低。
- 日报金额格式标记只说明投影是否按该口径生成，不证明或否定单条金额。没有标记的日报忽略旧反推小计，
  只在读取边界按同一金额规则核验同日、同批、同客户已冻结的逐笔证据。旧格式转换只补原价及其质量状态；
  汇总仍使用既有日投影和合并器。补齐前分别核对扣减与退回小计，避免净额相等掩盖漏行；无法唯一归到
  某个折扣组合的原价保持未知。汇总、明细和导出不回查实时日志、当前价或当前折扣，也不改写已发布批次。
- 上游参考金额保存逐笔取整所需的原价分布，账单对账读取时按记录发生日应用当前有效的月度折扣区间，
  导出冻结提交时的区间。用量使用其发布版本中的参考费用。URL 归属
  仍按各自自然日冻结，账期内可以出现同一渠道的不同 URL。用户侧金额与上游参考金额继续分开。
- 已发布指针经租约验证后一次切换，指针同时覆盖当天客户及上游数据。控制台汇总返回所读日版本集合，
  下钻和导出将其连同原有权限及筛选范围传回。已有正式确认月账单继续使用独立正式版本。日报表保留
  逐笔账单所需字段，管理员明细仅在根权限下解密受保护的上游任务标识。
- 账单页面显示该期已发布天数以及阶段性数据的截止时间。缺少数据的日期仍占应发布天数。已知日志清理影响
  覆盖时提示部分数据，原先的更完整版本继续可用。显式绑定日报版本时仍显示已登记的覆盖缺口。
  日报 CSV 保存提交时的覆盖信息。全客户 CSV 中使用正式月账单的行不适用日报覆盖列。
  源数据的读批次不加锁。扫描后核对本次读取边界
  的行数，候选失败时不更换发布指针。迟到发现使用有界追加游标、已投递任务事实及近期回看，超出
  自动发现范围的修复走按日期重算入口。Root 可在同一日期的两个发布版本仍可读、当前代际匹配且
  资金事件和来源覆盖不变时恢复上一代际。该操作保留既有导出版本引用。关系型源的生产灰度门槛见[路线图](../50-planning/路线图.md)第 39 项。
