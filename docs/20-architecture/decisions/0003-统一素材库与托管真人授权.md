# ADR-0003: 统一素材库与托管真人授权

> 本方案从未部署到任何环境。ADR-0004 接受后，Azure Blob、扫描器、managed 素材和相关配置已在首次提交前完整移除，不存在存量数据迁移或兼容义务。

## Context

new-api 已将 DoubaoVideo 渠道划分为 `official`、`third_party_reverse_proxy` 和 `third_party_relay` 三种视频上游协议，并在模型、分组、渠道和实际 Key 之间动态路由。参考素材只有在特定上游账号内创建才能获得可用的 `asset-xxx`，而该标识不能跨账号、跨渠道使用。如果继续允许客户直接提交上游 `asset://asset-xxx`，平台无法完整证明素材归属，也无法在渠道重试时保证引用仍然有效。

素材输入同时覆盖本地文件、base64 和 HTTPS URL。外部 URL 可能失效或变更内容，不能成为平台长期素材库的事实来源。平台因此需要一份与上游账号解耦的标准素材，再按实际可用渠道创建多份上游绑定。

真人素材还会处理人脸等敏感个人信息。API Token 持有人可能是开发公司，不是素材中的真人；注册协议或 API 参数中的笼统声明不能代替真人本人的单独同意。第一版既要支持纯 API 客户，又要在把数据发送到海外上游之前获得可审计的明确授权。

## Decision

- 建设一套平台统一素材库。标准素材归属 `user_id`，在该用户的所有 API Token 间共享；`created_by_token_id` 只用于审计。
- Azure Blob Storage 是素材二进制内容的唯一持久化事实来源。本地文件、base64 和 HTTPS URL 都先规范化并固化到私有 Blob，上游只获得有限期、只读的 SAS URL。数据库只保存 container 和 blob key，不保存长期 SAS URL。
- 对外只接受平台标识 `asset://ast_xxx`。任何未登记的 `asset://asset-xxx`、上游 group ID 或其他原始上游标识都 fail closed，不向用户暴露或接受。
- 素材与上游解耦：`assets` 保存平台标准素材，`asset_bindings` 保存按渠道和凭据指纹创建的上游素材。模型或明确的素材管理目标只触发按需绑定，绑定的真实归属维度是 `channel_id + credential_fingerprint`，不为同一账号的每个模型重复上传。
- 素材协议使用独立的 `asset_upstream_profile`，不根据模型名、Base URL 或视频 profile 暗中猜测。第一版实现 `ark_assets`、`relay_assets` 和 `joycreator_assets`。`joycreator_assets` 先完整提供文档已定义的素材组/素材管理能力，但在获得视频消费合同前标记为 management-only，不进入视频素材路由集。`official` 渠道在没有正式素材消费协议之前不猜测引用字段。
- 使用素材的视频请求在渠道选择前计算所有引用的 Active 绑定渠道交集，渠道亲和、权重路由和重试都不得越过该交集。选定渠道后再将平台 URI 改写为该绑定的上游 URI。
- 开启素材 profile 的渠道第一版必须是单 Key。绑定保存凭据指纹；指纹不匹配时立即失去路由资格。存在 Active 绑定时默认禁止直接替换渠道 Key，避免制造无法删除的上游孤儿资源。
- 第一版真人素材只支持 NEWAPI 托管同意，不开放“企业已自行取得同意”声明模式。API 客户先创建一次性授权会话，真人本人打开平台 `consent_url`，单独同意并确认已满 18 周岁后，才跳转上游 H5 认证。平台在同意前不接收、不保存真人素材。
- 真人授权与 H5 认证绑定到创建时选定的单 Key 渠道。上游回调只作为触发信号，平台必须使用冻结的渠道和凭据主动查询最终 session/group 结果，不信任回调中的 group ID。
- 普通素材保存到用户删除或账户注销。真人素材保存到授权撤回、处理目的结束、用户删除或账户注销中最先发生者。删除先在本地立即禁止新引用，再通过可重试状态机清理上游绑定、素材组和 Azure Blob。

## Consequences

- 收益：客户只看到一套稳定素材 ID，同一素材可以在不暴露上游 ID 的前提下逐步绑定到多个渠道账号。
- 收益：素材归属、渠道路由、重试和删除都可以强制租户隔离，客户不能通过猜测上游 ID 跨用户引用。
- 收益：入口来源都固化到 Azure，后续上游绑定可重放，不依赖外部 URL 的存活和不变性。JoyCreator 素材也作为同一平台素材的上游副本，不建第四套用户素材库。
- 收益：真人同意、H5 认证、素材和上游 group 形成可追溯链路，授权撤回可以一次触发所有关联数据的停用与删除。
- 代价：平台新增素材、绑定、素材组、同意政策、真人授权、H5 session 和对外操作任务等持久化状态，必须管理多个无法放入同一数据库事务的外部系统。JoyCreator 还同时存在管理主键 `id`、业务标识 `assetId/groupId` 和处理结果 `vendorUrl`，适配层必须分开这些语义。
- 代价：开启素材的渠道丧失多 Key 轮询能力，渠道换 Key 也需要显式迁移或清理流程。
- 风险：上游可能修改 H5、保存期限、跨境处理地区或删除能力。这些答案必须在真人功能上线前取得书面确认，并在变更处理目的、接收方或地区时发布新同意政策。
- 后续约束：任何新素材协议都必须有协议适配器、租户归属规则和删除合同。只有明确了视频消费方、引用值和账号归属的 profile 才可进入素材感知路由；management-only profile 不得被 Distributor 选中用于视频引用。

## Alternatives Considered

- 允许客户直接传上游 `asset://asset-xxx`：未采用。平台无法验证该 ID 是否属于当前用户，也无法限制后续渠道重试。
- 为三种视频 profile 各建一套用户素材库：未采用。它会把同一文件、名称、权限和生命周期复制三次，并把上游协议差异暴露给客户。
- 素材归属 API Token：未采用。Token 是可轮换的访问凭据，不是长期业务主体；换 Token 不应导致素材失去访问。
- HTTPS URL 永久原样透传：未采用。来源可能失效、被替换或在重试时返回不同内容，与“平台素材库”的持久化语义冲突。
- 只让开发公司在 API 中声明已取得同意：第一版未采用。该模式需要企业认证、数据处理协议、授权证据抽查和违约处置，无法只靠一个布尔参数安全上线。
- 注册即视为真人同意：未采用。账户主体和人脸主体可能不同，而且人脸信息处理需要显著告知和单独同意。
- 等到 JoyCreator 有明确视频消费方后再实现其素材管理：未采用。第一版已要求交付该文档中的素材组和素材管理能力；通过 management-only 标记可以在不猜测视频协议的前提下安全上线。
