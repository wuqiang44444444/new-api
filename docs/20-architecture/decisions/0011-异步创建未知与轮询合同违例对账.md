# ADR-0011: 异步创建未知与轮询合同违例对账

> 本决策已被 [ADR-0016](0016-Seedance专用渠道与确定性素材代理.md) 取代。当前 Seedance `unknown`
> 不按期限自动释放资金，也不进入 `released_with_exposure`；当前事实见
> [Seedance 专用渠道与 Link 架构](../Seedance专用渠道与Link架构.md)。

## Context

异步上游的 POST 可能已经创建任务，但网关在读取响应或保存上游任务 ID 前崩溃。此时立即
退款并重发可能产生两个上游任务；只在捕获错误后才写 recovery snapshot，也无法覆盖“上游
成功、进程尚未来得及进入错误处理”的崩溃窗口。

Task 创建后，轮询还可能收到无效 JSON、未知状态、任务 ID 不匹配或成功结果缺字段。一次查询
响应违反协议只能证明本次响应不可采信，不能证明上游业务任务已经失败。如果直接写
`FAILURE` 并退款，会把协议观测异常错误地变成业务终态。

本决策只覆盖由本项目显式接入共享 Task 与 ADR-0008 计费门闩的数据面创建路径：已注册的 Link
视频合同，以及经分发后选中持久化媒体任务能力的图片调用。图片上游可能在响应前无法确定返回
同步结果还是异步任务，因此这类 route 的 attempt 必须先于 POST；同步成功时直接结算并关闭
attempt，异步成功时转入 Task。普通同步图片、图片编辑以及素材、真人认证等控制面资源不适用。

NEWAPI 原生 `/v1/videos`、`/v1/video/generations` 是否使用 attempt 以上游实现为准。本 ADR 不得
被用来为原生 Router 添加本地 `client_protocol`、幂等中间件、历史任务识别、fallback 或其它
兼容接线。

## Decision

### 创建尝试

- 每次准备调用上述任务型上游时，无论客户端是否提供 `Idempotency-Key`，都建立耐久的
  `create_attempt`。它与正式 Task 分离，因为此时尚未取得可信上游任务 ID，也可能最终返回
  无需 Task 的同步图片结果。
- 创建尝试至少使用以下执行状态：

```text
prepared -> sending -> upstream_succeeded -> complete
             |                |
             +-> unknown <----+
prepared/sending -> rejected
unknown -> complete | released_with_exposure
```

- `prepared` 在预扣前持久化请求 HMAC、公开任务 ID、用户/Token、客户模型、选中 Channel、
  上游协议/adapter、Provider 模型、单个凭证、冻结连接、计费合同和对账截止时间；不保存原始媒体、请求正文、
  Cookie 或原始幂等键。
- 资金预扣与 `sending`、`billing_hold=held` 在同一数据库事务提交。只有事务成功后才能向
  上游写出任何请求字节。陈旧的 `sending` 必须保守转为 `unknown`，不能自动退款或重发。
- 上游明确证明未创建时，幂等释放 hold 并进入 `rejected`。取得可信上游任务 ID 时，在同一
  事务创建 Task、把 hold 转移到 Task 的 ADR-0008 `pending` 计费状态，并把 attempt 推进为
  `complete`。
- 已选中的持久化图片 route 返回同步成功结果时，在同一资金事务结算或释放差额并把 attempt
  推进为 `complete`，不创建伪 Task。同步结果落库回放仍不属于 OpenAI 图片客户端承诺。
- 发送后超时、断连、无效或缺少 ID 的 2xx、落库前进程退出等无法证明结果的情况进入
  `unknown`。它保留 hold，禁止自动换渠道或重发 POST，由现有共享任务补偿调度器新增的
  create-attempt 扫描处理；扫描使用租约、退避和次数上限，不新增独立进程或供应商专用 worker。
- `unknown` 必须具有产品批准的客户资金占用截止时间。截止前通过上游 request ID、账单、
  管理员核对或补录任务 ID 恢复；截止后仍无法恢复时，幂等释放客户 hold，标记
  `released_with_exposure`，记录潜在供应商孤儿/平台成本，不得日后静默补扣客户。

### 客户重放语义

- 是否支持 `Idempotency-Key` 由具体客户入口明确声明，不能由共享 attempt 自动扩张。Seedance
  ModelArk V3 不提供平台自定义幂等合同，也不要求该字段；每个 POST 都是新的创建意图，结果不明时
  客户不应自动重试。
- 明确提供幂等能力的其它产品可使用同键同请求恢复已有 Task 或 attempt，同键异请求冲突，
  `unknown` 期间不再次调用上游。
- 提供幂等能力的持久化图片 route 如果已经同步成功但没有保存可回放结果，同键重放只能证明原操作已完成，
  不得再次 POST；平台返回稳定、不可重试的 `409 idempotency_result_unavailable`。如需承诺
  同步结果回放，必须另行保存经过安全审查的有界结果快照，不能假装内部 attempt 等同于响应缓存。
- 没有幂等合同或未提供 Key 时，每个 HTTP 创建请求都是新的业务尝试。内部 attempt 只保证本次请求的账务
  和恢复不丢失，不能把另一次无 Key 请求识别为原操作；客户端明确声明为 at-least-once，客户端
  在模糊错误后重试可能创建第二个上游任务。
- `create_outcome_unknown` 响应必须给出稳定错误码和平台 `request_id`。入口明确支持且原请求有 Key 时提示
  仅使用同一 Key 重放；原请求无 Key 时明确提示不要自动重试，事后新增 Key 只会创建新业务
  尝试，不能恢复原 attempt。

### 轮询合同违例

- 已有 Task 的单次查询出现无效 JSON、未知/空状态、任务 ID 不匹配、成功结果暂缺或结果地址
  不可采信时，进入内部 `reconciliation_required`，客户端继续投影合同允许的非终态/未知语义，
  计费保持 `pending`。不得仅凭该响应写 `FAILURE` 或退款。
- 对账状态使用冻结的渠道、profile、凭证和 adapter 版本有界重试，并记录脱敏响应摘要、连续
  违例次数、首次/最近发生时间和告警状态。恢复到合法响应后继续正常状态机。该扫描由现有共享
  任务补偿调度器承载，只增加扫描键和状态处理器。
- 已取得可信、完整且可确认不会通过重试改变的终态响应，但其结果确定违反公开交付上限或安全
  合同时，可以进入内部 `PROVIDER_CONTRACT_FAILURE` 平台不可交付终态，对外投影为
  `failed` 与稳定错误码 `provider_contract_failure`。它使用 ADR-0008 的冻结零目标退款：
  资金原子应用成功后为 `settled`；资金计算或持久化失败时为 `failed` 并进入既有补偿扫描。
  同时幂等记录潜在 Provider 已计费 exposure。例如图片去重结果数确定超过请求 `n`；这不等于
  声称上游业务失败。
- 上游明确返回业务失败时写 `FAILURE`。对账超过合同规定的任务最大生命周期时，可以按产品
  SLA 写 `EXPIRED` 并退款，同时记录 `upstream_outcome_unresolved` 供应商暴露；该终态表示
  平台服务期限届满，不表示已经证明上游业务失败。
- `released_with_exposure` 只属于 create attempt 的 hold 释放；它不伪造 Task，也不进入
  ADR-0008 的 `billing_state`。`upstream_outcome_unresolved` 则是 `EXPIRED` Task 的 exposure
  reason。所有 exposure 写入必须与资金结果原子提交或经唯一键幂等 outbox 保证。

### 可观测性

- 必须分别监控 `sending` 陈旧数、`create_outcome_unknown`、hold 年龄和金额、到期释放、
  `reconciliation_required`、合同违例连续次数、`provider_contract_failure`、
  `released_with_exposure` 与 `upstream_outcome_unresolved`。
- 运维配置必须按客户模型、Channel 和上游协议定义 exposure 单笔金额、单位时间金额/数量、转换率和
  最老年龄的 warning、paging 与自动停用阈值。新 profile 首期灰度时，任何
  `released_with_exposure`、`provider_contract_failure` 或
  `upstream_outcome_unresolved` 都立即 paging。
- 任何资金释放、Task 恢复、终态推进和 exposure 记录都使用持久化幂等门闩；重复调度、
  人工操作或晚到响应不得二次退款、二次建 Task 或二次结算。

## Consequences

- 收益：覆盖上游发送成功与本地错误处理之间的崩溃窗口，避免无记录的重复创建和错误退款。
- 收益：协议响应异常与业务失败分离，计费只跟随可证明的业务终态或明确的 SLA 到期政策。
- 收益：客户端资金不会因供应商结果永久不明而无限期冻结，残余成本转为可观测的平台暴露。
- 代价：正式 Task 之外增加短生命周期 create attempt，并扩展现有共享任务补偿调度器的扫描
  类型和索引。
- 代价：无 Key 请求仍不能提供 exactly-once；平台需要对到期 exposure 承担运营处置。
- 后续约束：任何新增共享 Task 创建路径必须显式评审是否在发送前进入耐久 attempt；任何
  新增轮询 adapter 必须区分“明确业务失败”“本次响应不可采信”和“可信但确定不可交付的
  终态结果”。该约束不能从路径相似性自动传播到 NEWAPI 原生协议。

## Alternatives Considered

- 只在捕获网络错误后写 unknown：未采用。进程可在错误处理前退出。
- 模糊创建失败立即退款并重试：未采用。可能形成两个计费和上游任务。
- 所有客户端强制提供幂等键：未采用。它会把平台扩展错误地变成模型官方合同必填字段。
- 单次查询合同违例立即失败退款：未采用。查询响应异常不能证明业务任务失败。
- 未知状态永久保持 pending：未采用。客户资金占用和运营风险都没有期限。
