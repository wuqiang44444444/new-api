# ADR-0012: 真人素材单图同步流式边界

## Context

[ADR-0004](./0004-中转型素材代理与上游绑定.md) 将素材库限定为 URL 控制面代理，禁止平台接收、下载或保存客户素材二进制。FunCloud 真人素材接口却只接受携带长期 Provider Bearer Key 和 `bytedToken` 的 multipart 文件上传；它没有 URL ingest、客户直传签名 URL或只允许上传的短时凭据。平台无法控制 FunCloud，而业务必须支持该渠道的真人素材。

因此“不让平台接触任何文件字节”和“接入 FunCloud 真人素材”不能同时满足。仍需保持官方 ModelArk 视频客户端、平台 `asset://ast_*`、真人授权的 user/app/end-user 隔离、渠道凭据冻结和结果未知对账，不允许把 FunCloud 私有字段或长期 Key 暴露给客户。

## Decision

本决策作为 ADR-0004 的窄范围例外，不取代其 URL 中转和控制面绑定原则：

- 只新增 `POST /v1/real-person-authorizations/{authorization_id}/asset`；请求体是单张 JPEG/PNG 原始流，要求 `Content-Length`，平台与反向代理均强制 30 MiB 上限。
- 文件通过 `io.LimitedReader -> io.Pipe -> multipart.Writer` 同步转发到 FunCloud；不完整读入内存、不落本地文件、不写对象存储或数据库、不建立通用上传会话。
- 上传必须绑定既有真人授权。读取首字节前校验 user、app、`EndUserSubjectHash`、model、channel、profile、凭据指纹、授权状态和功能 entitlement；客户不能提交 `bytedToken`、Provider Key、channel ID 或上游素材引用。
- 使用 durable upload attempt 和数据库 CAS 保证同一授权最多一个发送中的尝试。发送后结果不明进入 `create_unknown`，不得自动重传或换渠道。
- 只有真实渠道证明“成功上传必然意味着同一 `bytedToken` 已完成人验证”后，才能启用 `upload_confirmed` profile 语义。成功时在一个数据库事务中推进授权、session、平台 Asset 和 AssetBinding；证明前能力保持关闭。
- 首发一次授权只创建一张真人图片。成功后清除加密 `bytedToken`；未确认 token 复用和有效期前不支持多素材。
- 客户只获得平台 `asset://ast_*`。FunCloud `materialId`、`asset://asset-*`、H5 URL、token 和凭据只保存在私密字段且不进入公开 DTO 或普通日志。
- FunCloud 未提供删除接口时，撤回立即禁止平台引用，并把上游清理标记为 `manual_required`，不得宣称已物理删除。

## Consequences

- 收益：满足必需的 FunCloud 真人素材能力，同时保持官方视频客户端、平台素材 ID、授权状态机和渠道账号绑定不变。
- 收益：不引入 OSS、BlobStore、通用 upload session、URL 下载桥接、Base64 导入或后台文件 job，对现有 new-api 热路径只增加窄接线。
- 代价：网关和反向代理承载最长 30 MiB 的同步连接；客户端必须保持连接到 FunCloud 接收完成。
- 代价：没有源文件可供跨实例恢复；明确未发送前可重试，发送后结果未知只能人工或通过可靠上游查询对账。
- 风险：FunCloud 当前文档没有权威验证结果、单素材查询、幂等创建或删除合同，能力必须以真实渠道验收和 fail-closed 门禁控制。
- 风险：如果 FunCloud 成功上传不能证明 H5 已完成，本决策的 `upload_confirmed` 路径不可启用，必须等待新的 Provider 事实。
- 后续约束：任何通用素材上传、视频/音频上传、对象存储暂存、URL import 或多素材授权都需要新的架构评审，不能扩大本例外。

## Alternatives Considered

- 对象存储暂存：未采用。它能支持异步恢复和重试，但引入存储、加密、生命周期、跨区和敏感数据责任，超过当前单图必需范围。
- 网关本地临时文件：未采用。它把实例磁盘变成不可靠的隐式暂存系统，并增加孤儿清理和多实例迁移风险。
- 通用 upload ticket：未采用。当前只有真人单图需求，新增通用素材 source 和完整生命周期会扩大合同与冲突面。
- 客户直接调用 FunCloud：未采用。上传仍需要长期 Bearer Key；把 Provider Key 交给客户会暴露账号内其他资源和消费权限。
- 独立 media-ingress 服务：未采用。它只移动文件责任而不能消除责任，并增加部署、鉴权和故障边界。
- 等待 FunCloud 改造：未采用，因为业务要求当前接入；若未来提供 URL ingest、presigned upload 或 scoped credential，应优先替换本例外。
