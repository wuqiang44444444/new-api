# ADR-0013: Link 合同与渠道适配协议

## Context

历史文档使用方向性术语分别描述客户侧承诺和上游适配。这类表达容易导致三个问题：

- 将客户角色和 Provider 角色误解为两套并列且各自完整的系统合同；
- 将渠道适配规则误当成可以反向定义公开能力的权威来源；
- 图片、视频、任务、计费和素材等跨产品语义缺少一个统一、好理解的总称。

系统对经项目负责人明确批准、需要本地编码扩展的能力，需要一套端到端的稳定承诺，以及该承诺在具体渠道上的可验证实现。这套本地扩展不能替代或重新分类 NEWAPI 原生合同，也不应由运行时能力或候选渠道推断其身份。同时，数据库中已有 `northbound_contract_*`、`southbound_adapter_*` 等持久化字段，为术语更新立即重命名会引入不必要的迁移和兼容风险。

## Decision

1. 将 **Link 合同** 确立为“经项目负责人明确批准、通过本地代码变更实现并在代码中显式注册”的扩展合同。它覆盖该扩展的客户可见 API、公开 SKU 能力、任务与计费语义、Link 资源以及渠道实现约束。Link 合同不是全站路由总分类，不替代 NEWAPI 原生合同。
2. Link 合同由以下子概念组成：
   - **客户 API 合同**：路径、鉴权、请求、响应、错误和幂等语义；
   - **SKU 能力合同**：公开模型的字段、值域、默认值、媒体组合和能力版本；
   - **任务与计费合同**：同步或异步生命周期、查询、取消、结算、退费与对账；
   - **Link 资源合同**：平台素材的标识、所有权、授权、绑定和生命周期；
   - **渠道适配协议**：请求转换、上游鉴权、路径与模型映射、响应归一和上游任务生命周期。
3. **渠道适配协议是 Link 合同的实现子合同**，不是与 Link 合同并列的另一套公开合同。它只能证明某渠道实现了已发布的能力，不得反向扩张客户 API、SKU 能力或计费语义。
4. “客户端”和“Provider / 反代 / 中转”仅表示调用链路中的角色，不再用方向词建立并列概念。
5. 一个 Link 公开 SKU 只对应一份 Link 合同。候选渠道必须完整实现该合同；不等价时排除渠道或拆分 SKU。该等价门不得介入 NEWAPI 原生 relay 的 Ability、优先级与权重选渠。
6. Link 合同身份只由显式代码注册决定。Ability、候选渠道、模型发现、配置记录和运行时能力探测均不能创建、取消或推断 Link 合同。每个注册项必须有唯一合同 ID/版本、代码扩展接线、测试和文档。
7. NEWAPI 原生合同优先是开发治理约束，不是 Link 身份的运行时判定算法。已原生完整支持的能力不得另建 Link；如后续上游补齐等价能力，本地 Link 实现必须优先迁回并有计划退出。
8. `Link 资源` 保留为平台资源对象的专有名称，避免将“Link”单独作为合同或资源的替代词。
9. 已持久化字段和已发布程序标识符暂不重命名。文档和代码注释明确其兼容含义：`northbound_contract_id/version` 对应 Link 合同标识与版本，`southbound_adapter_version` 对应渠道适配协议版本。

## Consequences

- Link 扩展的业务、架构、开发和运维文档共享同一套概念层级，不再需要先解释方向性术语。NEWAPI 原生功能保持原有概念与实现。
- 公开能力的权威来源更清晰：Link 合同定义承诺，渠道适配协议证明实现。
- 后续设计、审计和验收必须按 Link 合同的子合同逐项检查，不能只验证请求能否转发。
- 存量字段和类型名会在一段时间内保留历史方向词，需要通过注释和术语表防止误解。
- 如未来要重命名持久化字段或公开类型，必须另立迁移决策，并同时覆盖数据库、API 兼容和回滚方案。

## Alternatives Considered

- **使用“Link 统一合同”作为总称**：“统一”与总合同语义重复，且容易让“渠道适配协议”继续作为并列层级，未采用。
- **保留两套并列的方向合同**：无法表达端到端的唯一权威边界，也会弱化 SKU 能力和计费一致性，未采用。
- **立即重命名所有数据库字段、Go 类型和 API 字段**：会扩大迁移和上游合并冲突面，而术语规范并不要求破坏兼容性，未采用。
- **将合同、资源和适配均简称为“Link”**：无法区分规则与资源对象，未采用。
