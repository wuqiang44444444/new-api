# ADR-0001: 视频上游协议适配与任务执行快照

## Context

异步视频上游既包含官方直连，也包含兼容官方合同的第三方反代和提供统一媒体任务合同的第三方中转。它们共享用户鉴权、渠道路由、模型映射、任务落库、轮询、计费和日志主链路，但在创建请求、响应结构、任务路径与状态字段上存在稳定的协议差异。

如果按供应商名称、域名、模型名或 Key 格式决定协议，渠道配置会形成隐式行为，同一协议的新供应商也需要重复修改代码。若为单个供应商引入独立适配服务、环境变量、Key 池或 Redis 任务绑定，又会与现有渠道和任务表形成重复事实来源。

异步任务还跨越创建与多次轮询。渠道地址、路径和凭证在任务执行期间可能被管理员修改；如果轮询直接读取渠道当前值，在途任务会被静默切换到另一个协议、目标或上游账号。系统必须同时满足“渠道配置是新任务的唯一可编辑配置源”和“在途任务保持创建时执行语义”这两个约束。

## Decision

- 继续复用现有 `DoubaoVideo` 渠道、异步任务和计费主链路，不新增供应商专用 Provider 类型或独立适配进程。
- 使用显式的 `video_upstream_profile` 作为唯一协议选择变量，固定支持：
  - `official`：官方 Ark 视频任务合同；
  - `third_party_reverse_proxy`：兼容官方 Ark 合同的第三方反代；
  - `third_party_relay`：需要转换为统一媒体异步任务合同的第三方中转。
- profile 只决定创建请求转换、创建响应解析、查询 URL 构造和查询响应解析。系统不得根据 Base URL、路径、模型名、模型映射、API Key、环境变量或请求头推断协议。
- 渠道记录是创建新任务时的唯一可编辑配置源：
  - `base_url` 保存上游根地址；
  - `key` 保存上游凭证；
  - `model_mapping` 保存公开模型到上游模型的映射；
  - `video_upstream_create_path` 和 `video_upstream_query_path_template` 保存第三方协议路径。
- official 使用程序内置的创建和查询路径，保存渠道时清空第三方路径字段；两种第三方 profile 必须显式配置根地址、创建路径和查询路径模板。
- 协议转换和响应归一化在 new-api 进程内完成，并使用供应商无关的类型、包名、常量和错误语义。兼容现有协议合同的新上游只需新增渠道配置；只有不兼容现有合同的上游才允许新增稳定的 profile。
- 所有新建 DoubaoVideo 任务都在 `Task.private_data` 中冻结创建时的 profile、查询根地址、查询路径模板和实际选中的单个 Key。该快照是系统写入的不可编辑执行事实，不是第二个人工配置源。
- 多 Key 渠道仍由现有渠道分配逻辑在创建阶段选出一个 Key，但轮询必须使用该选中值，不能使用渠道完整 Key 集合或任务执行期间的新 Key。
- 历史无完整快照的任务可以回退渠道当前配置，以保留升级前任务的可查询性；该回退不得用于新任务。
- 不引入供应商专用环境变量、Key 池、Redis 绑定、服务认证、素材代理或控制面。渠道的通用缓存与路由能力不受本决策影响。
- profile、地址和路径不参与定价。计费继续以客户端公开模型名、模型定价配置、分组倍率和任务计费快照为事实来源。

## Amendment — 2026-07-28

本决策继续作为 `DoubaoVideo` 南向协议与执行快照的权威决策，但不再把 `video_upstream_profile` 解释为整个视频产品的唯一协议变量：

- 北向客户端合同由 [ADR-0007](./0007-视频官方北向合同与共享任务底座.md) 的 `contract_id` 和 `client_protocol` 决定；
- `video_upstream_profile` 只决定 DoubaoVideo 渠道的南向创建与查询协议，Kling、即梦使用各自渠道 adapter；
- 新任务还冻结北向合同 ID/版本、南向 adapter 版本、proxy、客户端请求最小快照和素材 binding；这些都是原“在途任务执行事实”原则的扩展；
- 本决策中“不引入素材代理”只表示视频协议适配器不自行建设素材状态系统，不否定 ADR-0004/0005 已建立的平台素材控制面。

## Consequences

- 收益：协议合同与供应商解耦，兼容现有合同的第三方上游可以零代码接入。
- 收益：渠道地址、凭证和模型映射没有第二个人工配置位置，部署拓扑不增加供应商专用服务或状态组件。
- 收益：在途任务不会因渠道修改而切换协议、查询地址或上游账号，多 Key 创建和轮询保持同一凭证。
- 收益：协议适配逻辑可以隔离在新增文件中，现有 Router、Controller、Task relay 和轮询热路径只保留窄接线，降低后续接取上游代码的冲突面。
- 代价：第三方渠道必须显式配置和校验根地址、创建路径、查询路径模板，不能依赖供应商默认值或地址猜测。
- 代价：任务私有数据会保留一份创建时凭证；数据库、备份、日志和用户响应必须按敏感凭证边界处理。
- 风险：第三方可能在不改变地址的情况下修改协议语义；未识别状态、缺失任务 ID 或成功但无结果 URL 必须 fail closed，不能通过宽松解析掩盖合同漂移。
- 后续约束：供应商名称只能作为渠道配置或运维示例出现，不得成为通用 profile、运行时常量、包名或架构组件名称。

## Alternatives Considered

- 为每个第三方新增 Provider 类型：未采用。它会重复渠道、路由、任务和计费主链路，并扩大上游高频文件的长期修改范围。
- 部署独立兼容服务并维护专用 Key 池、Redis 绑定和控制面：未采用。协议差异不足以证明新增部署单元和第二套状态系统的必要性。
- 按 Base URL、模型名或 Key 格式推断协议：未采用。这些字段都不是稳定协议合同，会形成隐式路由和不可预测的配置耦合。
- 轮询始终读取渠道当前地址和 Key：未采用。异步任务不保证可以跨账号查询，多 Key 渠道还会产生确定的创建与查询凭证不一致。
- 支持管理员编写任意 JSON 转换脚本：未采用。它会把协议正确性、安全校验和可测试性转移到运行时配置，超出当前受控协议适配边界。
