# 异步任务与计费事实架构

本文定义共享异步执行底座中影响正确性的持久化事实、状态关系和资金边界。它服务显式接入的
Link 视频和可能返回持久化媒体任务的图片路径，不把自身扩张为所有 NEWAPI 原生协议的统一实现。

Link 客户模型 publication 由 [Link 服务合同注册与履约架构](Link服务合同注册与履约架构.md)
负责；Asset、Binding 与真人授权分别由资源和授权专题负责。

## 1. 架构边界

异步执行需要同时回答三个相互独立的问题：

1. Provider POST 是否可能已经创建任务；
2. 已取得可信任务 ID 后，任务应按哪份合同和连接继续执行；
3. 客户资金与 Provider 潜在成本应如何结算和审计。

对应的权威事实为：

| 事实 | 权威模型 | 解决的问题 |
| --- | --- | --- |
| 发送前创建事实 | `TaskCreateAttempt` | 上游可能已创建、本地尚未取得或保存 task ID |
| 客户重放索引 | `TaskCreateIdempotency` | 同一客户幂等键恢复已有 attempt/Task |
| 异步业务任务 | `Task` 与私有快照 | 按创建时合同完成轮询、终态和结果投影 |
| 资金状态 | attempt hold、`Task.private_data.async_billing`、`billing_state` | 预扣、转移、结算、退款和补偿 |
| 平台成本风险 | `ProviderCostExposure`、`ProviderExposureIncident` | 客户退款后 Provider 可能仍产生的成本 |
| 历史消费 | `Log` | 已发生消费、退款与账单投影 |

这些模型描述“已经发生了什么”。Channel、Ability、价格和运行配置只描述“下一次请求怎么执行”，
不得反向改写在途事实。

## 2. 创建尝试

### 2.1 适用范围

显式接入共享创建安全边界的 Link 视频，以及分发后选中持久化媒体任务 route 的图片调用，在向
Provider 发送 POST 前创建 `TaskCreateAttempt`。普通同步图片、素材创建、真人认证和未明确接入的
NEWAPI 原生协议不因复用 Task 模型而自动获得该语义。

### 2.2 状态机

```text
prepared -> sending -> upstream_succeeded -> complete
                \-> unknown -> complete | rejected | released_with_exposure
prepared/sending -> rejected
```

- `prepared`：冻结合同、执行、连接、计费和对账事实，但尚未允许发送请求字节；
- `sending`：资金 hold、必要的真人授权 reservation 与发送许可已在同一事务提交；
- `upstream_succeeded`：取得可验证的 Provider 创建结果，等待原子创建正式 Task；
- `unknown`：请求可能已被 Provider 接受，但结果不可证明，禁止自动重发或换渠道；
- `rejected`：有证据证明 Provider 未创建，可幂等释放 hold；
- `released_with_exposure`：对账期限届满后释放客户资金，同时记录平台潜在成本。

`prepared` 必须先提交。预扣、`billing_hold=held`、授权 reservation 与 `sending` 使用一个事务；
事务成功后才允许写出 Provider 请求。取得可信 task ID 后，Task 创建、hold 转移和 attempt 完成
再次原子提交。

### 2.3 冻结事实

attempt 至少保存：

| 字段组 | 代表事实 | 用途 |
| --- | --- | --- |
| 客户身份 | attempt/public task ID、user、token、app、client protocol | 所有权、响应和对账 |
| 客户合同 | 客户模型、publication、合同 ID/version、SKU capability version/hash | 证明客户购买的能力 |
| 执行实现 | implementation ID/version/hash、channel、Provider 模型、profile、adapter version | 不依赖当前候选恢复执行 |
| 连接 | 查询 Base URL/路径、proxy、单个 Key 或受保护连接快照 | 固定 Provider 账号和调用合同 |
| 资金 | funding source、held quota、subscription/token 跟踪字段 | 与正式 Task 计费分离 |
| 对账 | Provider request/task ID、截止时间、下一次扫描时间、次数 | 恢复未知结果或形成 exposure |

原始媒体、请求正文、Cookie、Authorization 和原始幂等键不能进入 attempt。

## 3. 客户幂等

`TaskCreateIdempotency` 是可选客户端重放索引，不是创建安全的事实源。唯一作用域为：

```text
user_id + protocol + key_hash
```

记录只保存 key 摘要、规范请求哈希、attempt 关联、可恢复 Task 摘要和到期时间：

- 同键同请求恢复已有 attempt 或 Task；
- 同键不同请求返回冲突；
- `unknown` 期间重放不再次调用 Provider；
- 没有幂等键的两个 HTTP 请求是两个业务尝试；
- 最终同步完成但平台未保存响应的图片请求进入 `completed_no_replay`，不能假装可回放结果。

内部 attempt 保证单次业务尝试不会丢失账务和对账事实，但不能识别另一次无 Key 请求是否为重试。

## 4. Task 与执行快照

取得可信 Provider task ID 后才创建正式 `Task`。Task 的公共列用于所有权、状态 CAS 和补偿扫描；
敏感执行、连接和计费事实位于不会进入客户响应的私有快照。

| 快照 | 保存内容 | 生命周期作用 |
| --- | --- | --- |
| 客户身份 | customer model、client protocol、公开 task ID | 定价、日志和响应投影 |
| 合同身份 | publication、Link 合同、SKU capability、lifecycle | 按创建时客户承诺完成任务 |
| 实现身份 | implementation ID/version/hash、Provider model、profile、adapter version | 固定南向协议和实现 |
| 连接事实 | channel、查询地址/模板、proxy、单 Key、upstream task ID | 轮询不随渠道编辑漂移 |
| 素材关联 | asset public ID、binding ID、app/subject | 审计任务创建时使用的 Link 资源 |
| 计费事实 | funding source、billing context、async billing、预扣上界 | 终态结算、退款与补偿 |
| 产品状态 | 图片或视频查询所需最小结果 | 支撑对应客户协议投影 |

Task 不保存原始媒体、明文 AssetSource URL 或完整 Provider 响应。任务轮询必须读取冻结快照调用原
渠道、凭据和 adapter；不能因 publication 改绑、渠道编辑、Key 轮换或价格变化而重新选渠。

## 5. 业务状态与 Provider 可观测性

业务终态只能由可信 Provider 事实或明确的本地生命周期规则推进。单次无效 JSON、未知状态、任务
ID 不匹配、成功结果缺失或不可采信只证明本次观测失败，不证明上游任务失败。

共享状态额外包含：

- `RECONCILIATION_REQUIRED`：当前观测不可采信，任务保持活动，计费继续 pending；
- `PROVIDER_CONTRACT_FAILURE`：已证明无法按公开合同交付，投影为失败并按冻结零目标处理。

状态更新使用条件更新或 CAS，防止并发轮询重复推进终态。资金写入失败不能回滚已经确认的 Provider
业务事实，必须由独立计费状态继续补偿。

## 6. 资金状态

正式 Task 之前的资金属于 attempt hold；只有可信 Task 创建后才转入 Task billing。

```text
attempt hold: prepared -> held -> transferred | released

task billing: pending -> settled
                    \-> failed -> settled
                    \-> debt
```

`Task.private_data.async_billing` 保存完整计费状态，普通列 `billing_state` 是补偿扫描投影。资金目标、
Task quota、私有状态和投影列必须在同一事务提交；已经 settled 的重复操作是 no-op。

计费快照必须区分：

- 客户模型与价格键；
- 预扣上界与终态目标；
- 钱包、订阅和 Token 等资金来源；
- 表达式、受控计费维度和 quota 饱和审计；
- 退款、差额补偿与 debt。

所有客户可控乘数先通过产品边界校验。quota 换算使用统一 checked 饱和函数，饱和结果必须进入
管理员审计；任何路径都不能因溢出产生负扣费或客户信用。

## 7. Provider 成本暴露与历史账单

### 7.1 `ProviderCostExposure`

客户资金释放不表示 Provider 一定没有产生成本。exposure 使用：

```text
source_kind + source_id + reason
```

作为幂等键，保存 user、channel、客户模型、publication、implementation、释放 quota、可选 Provider
金额/币种和创建时间。未知 Provider 金额保持为空，不能用客户 quota 冒充供应商货币成本。

运营处置和自动门禁由 `ProviderExposureIncident` 与聚合策略承接；普通请求错误日志不能替代耐久风险事实。

### 7.2 `Log`

`Log` 是已发生消费、退款和审计的历史事实。API Key 自助账单直接聚合日志，不新增账单快照表，也
不按当前价格重算历史。详见 [API Key 用量账单架构](API-Key用量账单架构.md)。

## 8. 并发与数据库边界

- 所有模型、迁移和补偿查询同时兼容 SQLite、MySQL >= 5.7.8 和 PostgreSQL >= 9.6；
- 共享查询优先使用 GORM；标准行锁统一使用 `lockForUpdate(tx)`；
- 发送许可、资金 hold、授权 reservation 和状态推进使用明确事务边界；
- 多实例扫描使用租约、条件更新、退避和重试上限；
- Redis 与进程缓存只能加速扫描或限流，不能替代 attempt、Task 或 billing 数据库事实；
- Task 私有 JSON 不作为跨任务关系查询来源，真人授权等可索引关系使用普通关系表。

## 9. 架构不变量

1. 没有可信 Provider task ID 时不创建伪 Task。
2. 任何适用路径在 Provider POST 前都先建立 durable attempt。
3. `sending` 与资金 hold 原子提交；结果 unknown 时不自动重发、换渠道或退款。
4. Task 按创建时合同、实现、连接和计费快照完成生命周期。
5. 客户模型用于价格、日志和响应；Provider 模型只用于上游调用。
6. 单次轮询合同违例不直接产生业务失败或退款。
7. 客户退款与 Provider 成本风险分账，exposure 必须幂等、可审计。
8. 终态、资金状态和补偿可以独立重试，但不能互相覆盖已确认事实。
9. 敏感凭据、原始媒体和完整 Provider 响应不进入公共 Task、日志或指标。
10. 新异步产品必须覆盖验证、预扣、attempt、Task、终态、结算、补偿和审计完整链路。
