# 异步任务与计费事实架构

本文定义共享异步执行底座的耐久事实、状态和资金边界。它服务显式接入的 Link 视频与可能返回持久
媒体任务的图片路径，不替代 NEWAPI 所有原生异步实现。

## 1. 权威事实

| 事实 | 权威模型 | 解决的问题 |
| --- | --- | --- |
| 发送前创建事实 | `TaskCreateAttempt` | Provider 可能已创建、本地尚未取得或保存 task ID |
| 异步业务任务 | `Task` 与私有快照 | 按创建时 Channel、adapter 和合同继续执行 |
| 资金状态 | attempt hold、Task billing、`billing_state` | 预扣、转移、结算、退款和补偿 |
| 平台成本风险 | `ProviderCostExposure` 等耐久事实 | 客户退款后 Provider 可能仍产生的成本 |
| 历史消费 | `Log` | 已发生消费、退款与账单投影 |

Channel、Ability、模型映射和价格描述下一次请求。attempt、Task、素材引用和计费快照描述已经发生的
事实，不能被当前配置反向改写。

## 2. 创建尝试

### 2.1 适用范围

显式接入共享创建安全边界的高成本视频，以及分发后选中持久化媒体任务协议的图片调用，在发送
Provider POST 前建立 `TaskCreateAttempt`。普通同步图片、素材创建、AssetGroup 和真人认证邀请不因
复用 Task 模型自动获得该状态机。

### 2.2 状态机

```text
prepared -> sending -> upstream_succeeded -> complete
                \-> unknown -> complete | rejected
prepared/sending -> rejected
```

- `prepared`：冻结客户、执行、连接、素材、计费和对账事实；
- `sending`：资金 hold 与发送许可在同一事务提交；
- `upstream_succeeded`：取得可信 Provider 创建结果，等待原子创建 Task；
- `unknown`：Provider 可能已创建，禁止自动重发、换渠道或退款；
- `rejected`：技术人员核实 Provider 明确未创建后，人工幂等释放 hold。

`prepared` 必须先提交。资金 hold、`billing_hold=held` 与 `sending` 使用同一事务；事务成功后才允许
写出 Provider 请求字节。取得可信 task ID 后，Task 创建、hold 转移和 attempt 完成再次原子提交。

### 2.3 冻结事实

attempt 至少保存：

| 字段组 | 内容 |
| --- | --- |
| 客户身份 | attempt/public ID、user、token、app、客户入口、客户模型 |
| 执行身份 | channel、Provider 模型、`upstream_protocol`、adapter 版本 |
| 连接 | 查询 Base URL/路径、proxy、受保护 Key/凭据引用 |
| 素材 | 客户请求中的 opaque `asset://` 引用快照；不附加平台所有权或 Provider 作用域结论 |
| 资金 | funding source、held quota、价格/表达式、Token/订阅跟踪 |
| 对账 | Provider request/task ID、人工核实记录与 exposure 关联 |

原始媒体、请求正文、Cookie、Authorization、完整签名 URL 和 Provider 原始响应不得进入 attempt。

## 3. 客户幂等

Seedance ModelArk V3 北向不增加平台自定义幂等合同。公开上游创建请求没有可稳定依赖的
`Idempotency-Key` 或 `ClientToken`；两个 POST 表示两个创建意图。

若其他异步产品明确提供客户幂等能力，可使用独立索引恢复同一业务 attempt，但幂等索引不是发送前
创建事实源，也不能改变 Seedance“一次 POST、结果不明不重发”的规则。

## 4. Task 与执行快照

取得可信 Provider task ID 后才创建正式 `Task`。Task 的公共列用于所有权、状态 CAS 和补偿扫描，
敏感执行、连接和计费事实保存在不会进入客户响应的私有快照。

| 快照 | 保存内容 | 作用 |
| --- | --- | --- |
| 客户身份 | customer model、client protocol、公开 task ID | 定价、日志、响应 |
| 执行事实 | channel、Provider model、protocol、adapter version | 固定南向协议 |
| 连接事实 | 查询地址/模板、proxy、受保护凭据、upstream task ID | 轮询不随渠道编辑漂移 |
| 素材关联 | asset/group public ID、Provider 作用域 | 审计创建时使用的资源 |
| 计费事实 | funding source、billing context、预扣上界、归一实际用量及字段来源 | 终态结算、退款和补偿 |
| 产品状态 | 图片或视频需要的最小结果 | 客户协议投影 |

Task 不保存原始媒体、明文源 URL 或完整 Provider 响应。轮询必须使用冻结 adapter 和连接，不能因
Channel 停用、模型映射变化、Key 轮换或价格变化而重新选渠。

旧 publication、SKU、implementation 和 binding 快照字段及其兼容解码已经删除。无法在简化事实下
继续履约的历史任务必须在部署前离线处理，不能进入新请求链。

## 5. 业务状态与 Provider 观测

业务终态只能由可信 Provider 事实或明确本地生命周期规则推进。单次无效 JSON、未知状态、task ID
不匹配、成功结果缺失或不可采信响应只说明本次观测失败，不证明上游任务失败。

共享状态可以包含：

- `RECONCILIATION_REQUIRED`：当前观测不可采信，任务保持活动，计费 pending；
- `PROVIDER_CONTRACT_FAILURE`：已有充分证据证明无法按客户合同交付。

状态更新使用条件更新或 CAS。Provider 业务事实已经确认后，资金写入失败不能回滚该事实，必须由
独立计费状态补偿。

### 5.1 合同违例可观测

冻结 adapter 的信任校验失败（例如成功终态 `completionTokens` 超出协议合理性上界）进入
`RECONCILIATION_REQUIRED` 时，`FailReason` 必须携带脱敏的违例原因
（`upstream_contract_violation: <reason>`，截断至 200 字符）并输出 WARN 日志；违例路径不落
上游原始响应体。诊断信息只用于技术人员定位，不构成对客户的响应内容。

### 5.2 任务不存在的确定语义

Provider 明确返回“任务不存在”是确定性事实，不按合同违例处理。FunCloud 查询在 HTTP 200 响应中
携带 `code=30003` 时映射为 `UpstreamTaskNotFound`；因其创建后可见性窗口未经 Provider 确认，
轮询按连续失败计数宽限（`TaskPollMaxFailures`，默认 20 次）后判 `FAILURE` 并退款。取得 Provider
对 30003 任意任务年龄确定性的确认前，不得一次即杀；确认后可收紧为立即失败。

## 6. 资金状态

```text
attempt hold: prepared -> held -> transferred | released

task billing: pending -> settled
                    \-> failed -> settled
                    \-> debt
```

正式 Task 前的资金属于 attempt hold；只有可信 Task 创建后才转入 Task billing。资金目标、Task
quota、私有计费状态和公共投影必须在同一事务提交；重复结算是幂等 no-op。

计费快照必须区分客户模型、价格键、预扣上界、终态目标、资金来源、表达式和受控计费维度。所有客户
可控乘数先做产品边界校验；quota 换算使用统一 checked 饱和函数，饱和事件进入管理员审计，任何路径
都不能因溢出产生负扣费或客户信用。

### 6.1 异步终态实际用量

Provider 查询响应中的实际用量先由冻结协议 adapter 归一，再交给冻结计费上下文结算。二者职责如下：

```text
成功终态响应
  -> 冻结 adapter 采集任意明确 usage / Token 用量字段
  -> 逐字段校验类型、非负值与上界
  -> 写入归一用量 + 字段来源
  -> 冻结计价方式决定按 Token、按秒或按次结算
```

成功终态原始响应中的任一明确 `usage` 或 Token 相关数值合法，就应形成用量事实；不由配置、逐模型
字段白名单或人工验收状态决定。多个字段按“具体输出/completion 优先、total 与 prompt 推导次之、
单独 total 最后”的顺序归一，不能相加。只有明确 completion/output/generated 字段、
`total - prompt/input` 推导或无 prompt 字段时的单独 total 能形成可计费 completion；单独
prompt/input、`total < prompt` 的不一致响应与其它数值 usage（如 `*_details` 内字段）只作为用量
证据与字段来源写入私有计费快照，不参与按 Token 结算，
也不构成明确零用量。按 Token 计费的任务用归一实际 Token 重算目标 quota；按秒
或按次计费的任务只保存 Token 证据，不改变其冻结计价单位。只有按 Token 任务的成功终态没有任何可
形成数值的合法实际用量时，才保持预扣估算。

该判断不能依赖管理员配置，也不能由共享布尔值同时控制“是否解析”和“是否结算”。原有
`IncludeVerifiedUsage` 已直接删除，没有替换为其它 Provider、模型或字段配置；冻结计价方式才是 Task
的结算事实。第一次持久化的成功终态用量参与一次幂等结算；后续相同结果是 no-op，不同结果进入合同
异常审计，不覆盖既有结算。

私有快照只保存归一数量、使用的原始字段名和必要差异证据，不保存完整 Provider 响应、媒体 URL、
凭据或私有 Task 数据。

### 6.2 用户合同计费快照

合同用户的 attempt/Task 还冻结 `ContractBillingFact`：用户、合同版本、公开模型、绑定组和八位定点折扣。
终态结算先使用创建时冻结的原生价格、组倍率和表达式求出模型费用，再应用合同折扣；合同修改、原生倍率
修改或规则删除不重解释已经创建的 Task。没有合同事实的原生/历史 Task 不读取当前合同，也不改变既有当前倍率
语义。

### 6.3 预扣上界与信任上界分离

预扣预算与协议信任上界是两个独立语义，不得互相复用：

- 预扣上界（如 `task_billing_setting.preconsume_tokens`）只决定创建时暂挂金额，是资金授信边界；
  余额不足时在发送上游前拒绝请求。
- 信任上界是冻结 adapter 判定 Provider 成功证据是否可能合理的合同边界，按冻结计费探针推导，
  不读取预扣配置。FunCloud 按 `resolution + duration_seconds` 推导：token 速率取实测上界的
  不少于 2.4 倍余量（480p 30k/s、720p 60k/s、1080p 120k/s），时长缺省按 30 秒，整体下限 100k。
  真实成功上报超过信任上界才进入 §5.1 的合同违例路径。

预扣偏低不拒绝、不失败 Provider 已经成功完成的任务；结算按真实用量双向调整。

### 6.4 差额原子补扣与欠费

成功终态按冻结规则重算目标金额后，实际费用高于预扣时先对创建时冻结的同一资金来源（钱包、订阅、
Token 额度）原子补扣差额，三个来源的资金事实在同一事务提交：

- 补扣成功：更新任务额度并记录差额消费，一次且仅一次；
- 资金来源确实不足：进入可重试 `debt`，保留冻结 `TargetQuota`，按 `next_retry_at` 由补偿扫描
  继续补扣；`debt` 不受普通结算故障的 10 次重试上限约束，普通 `failed` 仍保留原上限；
- 数据库或状态异常：进入 `failed`，按既有补偿路径处理。

业务 Task 在整个过程中保持 `SUCCESS`：欠费或结算异常只重试资金操作，不重发 Provider 请求，
不把已成功的任务改写成生成失败，也不触发退款。

### 6.5 失败终态原子退款

`FAILURE`、取消、过期与 Provider 合同失败的终态直接交还统一的原子退款入口
（`refundTaskWithReconcile`），不再进入 tiered/token 结算；原子事务同时回退钱包/订阅、Token 与
Task 计费状态，退款失败保留冻结目标供补偿扫描幂等重试，不重发 Provider 请求。Provider 未上报
用量的失败任务不得被错误标为 `settled` 并永久保留预扣。

## 7. Provider 成本暴露与日志

Task 因明确终态释放客户资金不表示 Provider 一定没有成本。成本暴露事实必须幂等保存 user、channel、
客户模型、protocol、释放 quota、原因以及可选 Provider 金额/币种。Provider 金额未知时保持为空，
不使用客户 quota 冒充供应商货币成本。create attempt 的 `unknown` 不因期限自动释放或创建 exposure；
技术人员核实后只进入明确成功恢复或 `rejected`。

`Log` 是消费、退款和审计的历史事实。API Key 自助账单聚合日志，不按当前价格重算历史。

## 8. 素材管理不是视频任务

Asset/AssetGroup 创建和删除不使用视频 `unknown`、自动对账或管理员核查状态机：

- 创建未取得可信 Provider Asset/Group ID：返回失败，删除临时源 URL，记录脱敏技术日志；
- Provider 可能留下孤儿资源：由管理员通知技术人员排查，不建立自动孤儿扫描；
- 删除未取得明确成功：返回失败并保留本地状态；
- 后续 GET 明确确认 Provider 不存在时，才更新为 deleted。

这是按业务成本和运维复杂度做出的边界，不影响高成本视频创建保留 `unknown`。

## 9. 并发与数据库

- 主模型和迁移同时支持 SQLite、MySQL >= 5.7.8、PostgreSQL >= 9.6；
- 标准行锁统一通过 `lockForUpdate(tx)`；
- 发送许可、资金 hold 和状态推进使用明确事务边界；
- 多实例补偿使用条件更新、租约和有界退避；
- Redis 与进程缓存只能加速，不能替代 attempt、Task 或 billing 主数据库事实。

## 10. 架构不变量

1. 没有可信 Provider task ID 时不创建 Task。
2. 适用路径在发送 Provider POST 前建立 durable attempt。
3. `sending` 与资金 hold 原子提交。
4. Seedance 每个创建只发送一次；`unknown` 不重发、换渠道或自动退款。
5. Task 按创建时 Channel、adapter、连接、素材和计费快照执行。
6. 单次轮询不可采信不直接产生业务失败或退款。
7. 客户退款与 Provider 成本风险分账。
8. 敏感凭据、原始媒体、完整 URL 和 Provider 原始响应不进入公共 Task 或日志。
9. 素材管理失败不建立视频级 unknown 对账系统。
10. 成功终态中的任何明确 usage/Token 数值必须由冻结 adapter 归一；不设置采集开关，客户是否按该
    用量结算只由冻结计价方式决定。
11. 预扣预算只决定创建时暂挂金额，不充当成功证据的信任上界或最终结算上界；信任上界按冻结探针
    由 adapter 推导。
12. 实际费用高于预扣时先对冻结资金来源原子补扣；只有资金来源确实不足才进入 `debt`，欠费保留
    冻结目标额度并可继续重试，不逆转业务终态。
13. 失败、取消、过期与 Provider 合同失败终态统一原子退款，不在失败路径进入 tiered/token 结算。

## Seedance 视频缺用量结算边界

已登记 Seedance 视频协议的成功任务使用冻结 Token 表达式且尚无合法用量时，计费状态为 `awaiting_usage`。
协议身份仅来自创建时冻结的 `VideoUpstreamProtocol`，不根据模型名、传输 profile 或当前渠道价格推断。
视频仍为 SUCCESS，预扣保持不变，TargetQuota 为空。资金补偿扫描只处理已知费用；现有异步轮询调度
另行补查到期的等待任务，不依赖调用方再次查询。取得可信用量后继续结算；明确零用量不视为缺失。固定参数计价
不依赖 Token，按冻结表达式和参数求值后结算，不能把预扣估算直接当最终价格。该政策不追溯改写已结算历史任务。
NEWAPI 原生和插件任务仍保持各自合同，不因模型名含 Seedance 而进入本补查路径。

表达式结算拒绝负目标费用后才允许持久化 TargetQuota。上述协议的轮询观察和计费回写在 Task 行锁内合并，
只接受第一份符合对应协议的可信用量。官方/V3 的明确零可结算，FunCloud V2 仍要求正数。取得用量时将等待状态推进到 pending；即使计算目标前进程中断，
资金补偿也能继续。已接受的用量及已建立的目标在 debt/failed 重试中保持不变，settled 不可被旧快照
重开；只有原子资金事务能变更 Task.quota。轮询不得逆转业务终态，也不回写冻结连接、客户参数和计价快照。

Task.Data 中已接受的归一用量随首次观察保留，公开 completion_tokens 使用同一 AsyncBilling 事实，
明确零用量仍返回 usage 对象。后续缺失、不同来源或不同数值保留首条 usage_discrepancy（是否报告、
Token、来源及数值证据）在私有计费数据中，不改费用或公开用量，也不向客户泄露内部审计字段。
同状态观察提交失败时不结算。北向 GET 在刷新前保存不可变公开投影：重读数据库成功时返回最新耐久
投影，重读失败时返回刷新前的耐久投影，不使用已被刷新逻辑修改的内存 Task。重读确认任务已不可见时
返回 404。不同进程读到的旧 Task 不能覆盖数据库中的资金状态。

自动补查复用 async_task_poll 调度，不创建新视频 Task。Task 的 UsageRecovery 嵌入字段持久化开始时间、
下次执行时间、次数、最近错误分类、运营待处理时间及操作审计；它们只描述补查，不成为第二套账本。
每轮最多串行处理 10 项，单次 HTTP GET 可取消且限时 30 秒；首次立即补查，随后按 60 秒起的指数间隔
退避至最多 6 小时，最多 12 次、最长 24 小时。发送 GET 前通过 Task 行锁提交下次时间和次数，
进程退出消耗一次机会，重启后按持久记录继续。旧完成回写必须匹配认领次数和下次时间，不能覆盖新认领。
旧等待任务通过同一补查入口初始化，不改历史账务。

次数或期限耗尽后保留 SUCCESS、预扣和 awaiting_usage，标记运营队列并输出告警；调度不继续空转。
Root 管理入口可查看队列；写操作要求与会话绑定的 task_contract.usage.review 安全证明。
运营可附事件编号申请一次额外 GET，或在核实供应商账单后提交明确 completion_tokens 与对账引用。
人工确认用量和 Provider 用量竞争同一首次接受事实，不可替换已接受数值；确认后进入 pending，
仍由既有资金补偿按冻结价格和资金来源结算。无法获得可信用量时不自动按零退款或按预扣结清。


### 协议适用矩阵与计量边界

| 代码协议 | 当前计费合同与等待条件 |
| --- | --- |
| modelark_v3_volcengine / modelark_v3_byteplus / modelark_v3_cmcc | 实际 Token 合同缺失 completion_tokens 时补查 |
| moxing_modelark_media_v1 | Fast/Mini/2.5 实际 Token 合同缺失可信用量时补查 |
| funcloud_modelark_v3 | 依赖用量的冻结表达式补查；纯参数表达式直接结算 |
| funcloud_seedance | 可信成功但缺失 completionTokens 时补查；非法、非正或超限计量继续按合同异常处理 |
| ark_media_v1 | 依赖实际 Token 的冻结表达式补查，不能依据反代名称判定计价单位 |
| tokensave_media_task_v1 / moxing_media_task_v1 / feicai_videos_v1 | 当前秒价按冻结参数结算，不等待 Token；若另有依赖实际用量的冻结表达式，缺用量仍不能伪装结清 |

官方 ModelArk 成功响应只以合法 completion_tokens 为客户计费依据；total/prompt 单独存在只留证据，
不代替 completion。缺失、非整数、负值或超过 int32 的 completion 不产生收费值；任务身份不匹配仍
拒绝整个观察。Ark 反代和媒体协议沿用已声明的 completion、合法 total−prompt、仅 total 的优先级；
已出现但非法的 completion/prompt 不得因被丢弃而触发仅 total 计费。FunCloud V2 缺失 Token 时不构造零，
pointConsume 继续独立保存为 Provider 成本证据，其冲突/非法值校验保持不变。

统一合并实现位于 model/task_seedance_billing_facts.go；Task 两个写入口及资金事务仅保留窄接线。
成功任务缺少冻结表达式所需用量时，资金事务也拒绝直接提交目标；不能绕过 awaiting_usage 直接退款或结清。
后台补查和运营操作复用既有表列及安全证明，不新增协议名单、运行时模型推断、并行账本或重发视频入口。
