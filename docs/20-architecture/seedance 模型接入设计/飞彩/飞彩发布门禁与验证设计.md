# 飞彩上线证据与验证设计

## 1. 责任边界

系统不为飞彩建立逐模型 publication/capability/implementation 门禁。技术人员按精确 Provider 模型和
协议版本完成真实验证，再把客户模型、Channel、模型映射、协议和价格交给管理员。

系统在保存/启用时只保证 Seedance 客户模型没有被另一已启用 Seedance Channel 使用，并校验必要
Channel 字段。管理员不填写能力 JSON，运行时不重复认证兼容性。

## 2. 逐模型证据

每个准备启用的 v2 或 v3 Provider 模型至少独立验证：

- 目标 Key 可见并有权限使用精确模型；
- duration 最小/最大/默认和精确 size；
- 图片、音频、视频角色、数量、格式和大小；
- 创建 task ID、状态、成功内容和可信失败；
- 断连、超时、坏 JSON 和未知错误的 video unknown；
- 内容 HTTPS origin、Range、有效期和跳转；
- 按秒或按次客户价格、预扣、结算、失败退款和 quota saturation；
- Provider 实际费用、失败扣费和账单口径；
- Task/attempt/计费在 SQLite、MySQL、PostgreSQL 的一致性。

一行模型的成功证据不能横向授权另一模型、另一分辨率或另一 v2/v3 协议。

“可进入审批”不等于生产已开放，仍需价格、内容、失败与账单闭环。

## 4. 配置验收

- v2/v3 使用不同客户模型名和独立 Channel；
- `model_mapping` 指向精确带后缀/无后缀 Provider 模型；
- 选择相应代码 adapter 和精确 size 表；
- Priority/Weight 置灰且不参与请求；
- Channel 保存/启用时无 Seedance 客户模型重名；
- 视频创建只发送一次，不切 v2/v3 或其它 Provider；
- 当前没有素材库协议时配置 `asset_upstream_protocol=none`。

## 5. 不变量

1. 技术人员负责兼容性和证据判断，系统不自动推导。
2. v2/v3 和十个模型分别验证、分别配置、分别启用。
3. 研究报价、模型列表和示例 size 不能替代真实黑盒。
4. 未决字段、size、媒体、账单或错误保持禁用。
5. 启用一个模型不授权其它模型。
