# TokenSave 与墨行 Seedance 渠道对接设计

## 1. 范围与状态

本文定义 TokenSave 海外 Seedance 2.0 与墨行国内 Seedance 2.0、Fast、Mini、2.5 的渠道身份、模型合同、
南向视频协议、异步执行和计费边界。素材控制面与 `asset://` 解析由
[素材库对接设计](素材库对接设计.md)负责；Seedance 共用的渠道、Task 和资金状态由
[Seedance 专用渠道与 Link 架构](../../Seedance专用渠道与Link架构.md)负责。

当前代码已实现本文描述的五个客户模型、三个视频协议、逐模型校验、南向转换和本地合同测试。
Fast 已完成一次真实视频、终态查询和账单核对，确认墨行查询接口会返回结构化 Token `usage`；代码已
删除 `IncludeVerifiedUsage`，成功终态中的明确 usage/Token 数值会直接进入归一。以上事实表示能力可
配置且 Fast 已取得一组计费证据，不表示 Fast、Mini、2.5 已生产发布；各线路仍需分别完成其余真实验收。

Provider 协议身份描述“由谁履约以及采用哪份合同”，不能只描述 JSON 外形。即使两个线路共享
`/v1/media/generations` 或近似字段，也必须使用 Provider 命名的独立协议；不得恢复按数据形状命名的
`media_task_v1`、`relay_assets_v1` 或 URL/media-arrays 通用兼容层。

| --- | --- | --- | --- |
| `doubao-seedance-2-0-260128-tokensave` | `doubao-seedance-2-0-260128` | `tokensave_media_task_v1` | `tokensave_assets_v1` |
| `doubao-seedance-2-0-260128-moxing` | `doubao-seedance-2-0-260128` | `moxing_media_task_v1` | `moxing_joycreator_assets_v1` |
| `doubao-seedance-2-0-fast-260128-moxing` | `doubao-seedance-2-0-fast-260128` | `moxing_modelark_media_v1` | `moxing_volc_assets_v1` |
| `doubao-seedance-2-0-mini-260615-moxing` | `doubao-seedance-2-0-mini-260615` | `moxing_modelark_media_v1` | `moxing_volc_assets_v1` |
| `doubao-seedance-2-5-260628-moxing` | `doubao-seedance-2-5-260628` | `moxing_modelark_media_v1` | `moxing_volc_assets_v1` |

每一行对应一个独立 `ChannelTypeSeedanceLink` Channel。Channel 的 Models 只能包含该客户模型，
`model_mapping` 只能包含表中这一条精确映射。客户模型后缀用于模型发现、Token 权限、Group、价格、
日志和客户请求；去后缀后的 Provider 模型只用于南向调用。

即使 Fast、Mini、2.5 共用墨行账号、Base URL 或 Key，也必须分别建 Channel。系统在管理保存和启用
路径校验“一个已启用客户模型只对应一个 Seedance Channel”，运行时不建立候选集合、Priority、
Weight、Affinity、随机分发、跨渠道重试或 fallback。

## 3. 管理协议身份

| 配置值 | 中文名称 | 英文名称 | 固定创建/查询路径 |
| --- | --- | --- | --- |
| `tokensave_media_task_v1` | TokenSave 媒体任务 V1 | TokenSave Media Task V1 | `/v1/media/generations`、`/v1/media/tasks/{task_id}` |
| `moxing_media_task_v1` | 墨行媒体任务 V1 | Moxing Media Task V1 | `/v1/media/generations`、`/v1/media/tasks/{task_id}` |
| `moxing_modelark_media_v1` | 墨行 ModelArk 媒体任务 V1 | Moxing ModelArk Media Task V1 | `/v1/media/generations`、`/v1/media/tasks/{task_id}` |

管理员选择代码已经注册的协议，不编写请求映射、响应脚本或状态机。内部 transport profile 可以复用
HTTP、错误和响应归一代码，但不是第二套管理员配置，也不能改变公开协议身份。协议、Provider 模型、
adapter revision、Base URL 和凭据事实在创建时冻结到 attempt/Task。

Seedance Channel 只允许一个渠道凭据，不使用 Multi-Key。`model_mapping` 只转换模型名，不根据后缀、
Base URL、价格或 Key 推断协议。

## 4. ModelArk V3 北向合同

五条线路统一接收 ModelArk V3 typed request。合同外字段、未知字段和不支持的媒体组合必须在 Provider
POST 前返回 400；不得通过 `extra`、metadata 或任意参数透传绕过校验，也不得静默删除、钳制或改义。
`output_format` 是类型化可选字段，省略与显式值保持不同语义。

| 线路 | `duration` | `resolution` | 参考媒体 | `generate_audio` | `output_format` |
| --- | --- | --- | --- | --- | --- |
| TokenSave 2.0 | `4..15` 或 `-1` | 480p/720p/1080p | 文本、首帧、尾帧、参考图片；视频和音频明确拒绝 | 按 TokenSave 合同 | 不支持 |
| 墨行 2.0 | `4..15` 或 `-1` | 480p/720p | 图片、视频、音频 | 按墨行 2.0 合同 | 不支持 |
| 墨行 Fast | `4..15` 或 `-1` | 480p/720p | 图片最多 9、视频最多 3、音频最多 3；禁止纯音频 | 支持；省略按 `true` | 不支持 |
| 墨行 Mini | `4..15` 或 `-1` | 480p/720p | 图片最多 9、视频最多 3、音频最多 3；禁止纯音频 | 支持；省略按 `true` | 不支持 |
| 墨行 2.5 | `4..30` 或 `-1` | 480p/720p | 图片最多 30、视频最多 10、音频最多 10；允许纯音频 | 支持；省略按 `true` | `mp4`、`mov` |

Fast/Mini 的 Provider 合同还要求单段参考视频或音频为 2..15 秒、参考媒体总时长不超过 15 秒；2.5
对应为 2..30 秒、总时长不超过 30 秒。当前北向媒体节点没有可靠、可验证的媒体时长字段，平台不根据
URL 猜测时长；这部分由 Provider 判定并仍需真实线路验证，不能据此放宽已在本地可验证的数量和组合边界。

TokenSave 的视频/音频拒绝属于请求规格校验，发生在 durable attempt 和资金 hold 之前；转换层保留同样
的失败关闭检查作为防御，但不是主要合同入口。

## 5. 三类南向视频履约

### 5.1 TokenSave 2.0

`tokensave_media_task_v1` 把 ModelArk V3 内容转换为 TokenSave 旧媒体任务字段，仅序列化文本、首帧、
尾帧和参考图片。视频、音频以及 `output_format` 不进入南向请求。

### 5.2 墨行国内 2.0

`moxing_media_task_v1` 使用独立转换器，把 typed content 转换为墨行 2.0 的
`reference_images`、`reference_videos` 和 `reference_audios`。它不能复用 TokenSave 对音视频的拒绝
规则；两者虽然共享 transport profile 和路径外观，公开协议和请求合同仍完全独立。

### 5.3 墨行 Fast、Mini 与 2.5

`moxing_modelark_media_v1` 直接发送 ModelArk 风格 typed payload，保留受支持的媒体节点、画幅、时长、
音频和水印；只有 2.5 支持 `seed` 和 `output_format`。四个墨行模型均不支持 `camera_fixed`，Fast 和 Mini
也不支持 `seed`；这些字段显式传入时由逐模型 validator 在 Provider POST 前拒绝。不能由同一协议名推导
三个模型拥有完全相同的参数范围。

三类 adapter 都把 Provider 创建和查询响应归一为平台 Seedance Task，不向客户暴露 Provider task ID、
Provider 模型、凭据、私有连接或原始响应。

### 5.4 墨行终态 Token usage 归一

墨行四个模型使用同一任务查询路径 `/v1/media/tasks/{task_id}`。接口文档的响应字段表把 `usage` 标成
`string`，示例又省略该字段；Fast 的真实成功响应则返回结构化对象：

```json
{
  "usage": {
    "prompt_tokens": 0,
    "completion_tokens": 40594,
    "total_tokens": 40594
  }
}
```

因此，南向归一不能把“文档表格中的 string”或“示例未出现”解释为无用量。墨行成功终态原始响应中，
只要出现任何明确的 `usage` 或 Token 相关用量字段，并且其数值可解析、非负且未溢出，就直接视为合法
Provider 用量事实并采集为证据；不再经过配置、逐模型白名单、人工验收状态或
`IncludeVerifiedUsage` 开关。对象形态直接解析，JSON 对象字符串只解码一层；无法转换成数值的普通
说明文字不能形成计费数量。Fast 已实际返回 `prompt_tokens`、`completion_tokens` 和
`total_tokens`，但这些名称不是限制其它明确 Token 用量字段的白名单。

用于 Token 计费的数量按以下顺序确定，且不得把多个字段相加：

1. 有明确的 completion/output/generated Token 字段时直接使用；
2. 缺少上述字段、但同时有 `total_tokens` 与 `prompt_tokens` 且 `total_tokens >= prompt_tokens`
   时，使用 `total_tokens - prompt_tokens`；
3. 没有 prompt 字段、只有 `total_tokens` 时，使用 `total_tokens`；
4. 以上三档都不满足时（单独 `prompt_tokens`、`total_tokens < prompt_tokens` 的不一致响应、
   `*_details` 内数值或其它明确数值 usage），全部数值只作为用量证据与字段来源写入 Task 私有
   计费快照，不形成可计费 completion，也不构成明确零用量，结算保持预扣估算；
5. 单个字段类型非法、为负数或溢出时拒绝该字段；同一响应中仍有其它合法实际用量字段时继续按上述
   顺序结算，全部不可用时才保持预扣估算。

只有 `succeeded` 终态采集用量，排队和运行中响应不解析用量。第一次成功写入的
终态实际用量成为幂等计费事实；后续重复查询不得重复结算，若返回不同用量则记录 Provider 合同异常，
不改写已结算事实。

## 6. 创建、失败与冻结事实

```text
ModelArk V3 请求
  -> 客户模型和唯一 Channel
  -> model_mapping 得到 Provider 模型
  -> typed 合同与逐模型规格校验
  -> 素材 Resolver
  -> 计费探针与预扣上界
  -> durable TaskCreateAttempt + hold + sending
  -> 唯一一次 Provider POST
  -> 可信 task ID 后原子创建 Task
```

字段越界、TokenSave 音视频输入、协议不匹配或素材不可解析都必须在 attempt 前失败。请求已经发送但无法
确认 Provider 是否创建任务时，attempt 进入 `unknown`，保留 hold 和 Provider exposure，不自动重发、
换渠道或退款。查询、删除、内容读取和结算始终使用创建时冻结的客户模型、Channel、Provider 模型、
协议、adapter revision、连接、素材和计费事实。

## 7. 计费合同

- 客户价格配置在带 `-tokensave` / `-moxing` 后缀的客户模型上，不能写到 Provider 模型名上；
- `model_mapping` 在计费探针前完成，因此探针可以按协议和 Provider 模型取得时长与音频默认值；
- TokenSave 2.0、墨行 2.0、Fast、Mini 的 `duration=-1` 按 15 秒预扣，墨行 2.5 按 30 秒预扣；
- Fast、Mini、2.5 省略 `generate_audio` 时，请求快照、预扣和结算统一按 `true`；
- TokenSave 和墨行 2.0 使用冻结请求维度按秒计费；即使墨行 2.0 返回 Token `usage`，也只保存为
  Provider 用量证据，不改变按秒客户账单；
- 墨行 Fast、Mini、2.5 按 completion tokens 计费。成功终态的用量先全部采集为证据，但只有语义可
  验证的形成（明确 completion/output/generated、`total_tokens - prompt_tokens`、无 prompt 时的
  单独 `total_tokens`）才用于差额结算；单独 prompt、不一致 total 或其它数值 usage 仅保存为
  Provider 用量证据与字段来源，保留预扣估算；
- 用量是否影响客户账单由创建时冻结的计价单位决定，不能由共享响应解析器中的
  `IncludeVerifiedUsage` 开关决定；该内部参数应删除，而不是改成按 Provider 配置 true/false；
- quota 计算使用统一 checked 饱和转换，客户费用、Provider 预期成本和 Provider 实际账单互不覆盖。

五个模型的当前价格矩阵、表达式输入和结算门槛由
[全模型与计费设计](墨行全模型与计费设计.md)负责；具体配置录入和核对步骤见
[计费与分组运维手册](../../../40-operations/01-计费与分组运维手册.md)。Provider 金额未知时保持未知，
客户退款与 Provider exposure 分账。

## 8. 发布边界

代码注册、单元测试和本地构建只证明平台合同存在。技术人员必须按客户模型逐条完成真实创建、轮询、
成功内容、失败/unknown、素材 Active 引用、平台扣费与 Provider 账单核对，再通知管理员启用对应 Channel。
一条线路通过不自动证明同协议下的其它模型通过。

系统不建立 publication、逐模型 capability、implementation 或 execution binding 自动门禁。生产资格
来自线下验收结论和管理员的明确 Channel 配置；Fast、Mini、2.5 在该结论前保持可配置但未发布。

## 10. 架构不变量

1. 客户模型、Channel、Provider 模型和代码协议是四个独立身份。
2. 五个客户模型分别使用一个 Channel 和一条精确 `model_mapping`。
3. 共用路径或 JSON 外形不产生协议等价性，不恢复通用协议 alias。
4. 不支持字段和媒体组合在 Provider POST 前明确失败。
5. 每个创建意图只发送一次 Provider POST；`unknown` 不自动退款或重发。
6. Task 后续操作只使用创建时冻结事实。
7. 计费默认值与实际发送语义一致；墨行终态合法 Token 用量必须被记录，是否参与结算由冻结计价单位
   决定，客户费用与 Provider 成本证据分离。
8. 可配置不等于已发布，单条线路证据不得扩张到其它模型。
