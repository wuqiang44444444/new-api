# 客户与上游对账架构

## 1. 目的与范围

本文描述平台管理员“客户账单”和“上游对账”两个一级 Tab，以及普通用户自助账单在后端如何以
数据库结算事实为权威完成聚合。它是只读对账投影，与预扣、结算、退款和日志写入主链路解耦。

用户自助账单按“周期 × API Key × 客户模型”聚合的逐指标数据口径由
[API Key 用量账单架构](API-Key用量账单架构.md) 详细解释；本文只补充管理员客户/上游两个 Tab、
上游月度折扣与审计、请求级计费快照，以及客户与上游口径必须分离的边界。两者共享同一前端功能模块
`web/src/features/billing-reconciliation/` 和同一组只读查询入口，但不共享金额汇总对象。

本文不设计期初/期末余额勾稽、逐笔充值冲正、跨期重算或税务发票；这些能力的边界见
[客户与上游对账单产品说明](../10-product/客户与上游对账单产品说明.md) 与[路线图](../50-planning/路线图.md)。

## 2. 当前实现状态

代码已实现：

- 用户自助账单 `GET /api/billing/statement/self`，按自然月返回 API Key → 客户模型汇总；
- 管理员客户账单：全客户月度列表与单客户渠道/API Key 两种维度汇总；
- 管理员统一上游对账：按「渠道当前基础 URL → 上游模型 × 计费方式 → 渠道贡献」聚合平台日志用量，
  并返回本地原价金额、按渠道月度系数计算的折后参考金额与完整性标记（见 7.2、7.3）；
- 上游渠道月度折扣的持久化、显式幂等月度初始化（上月复制、无来源默认 1）、expected-version 写入与
  追加式审计；旧模型级折扣经一次性幂等迁移收敛为渠道月度记录，冲突与证据不足保持待填写；
- 请求发生时在日志 `other.admin_info.statement_snapshot` 冻结版本、计费方式、Provider 模型和已结算计价因子；
- 客户与上游 CSV 导出，只导出后端返回的完整汇总；上游汇总导出记录每行的渠道折扣值和版本；
- 跨客户上游逐笔证据接口，按渠道集合、Provider 模型、计费方式和双方请求 ID 筛选。

未实现，保留为独立阶段，不在本文写成已落地事实：

- 不可变余额流水与期初/期末勾稽（`BillingBalanceLedgerEntry` 尚未创建）；
- 统一“人民币/百万 Token” PriceBook 版本快照；
- 真实 MySQL、PostgreSQL、ClickHouse 用量、月末边界与脱敏验证；
- 真实上游账单对参考金额口径的验收。

代码存在不等于生产发布。在真实三数据库、ClickHouse 合同、权限和月末验证完成前，管理员对账不得
标记为生产可用。

## 3. 架构边界与权威事实

| 数据 | 权威数据库事实 | 禁止替代来源 |
| --- | --- | --- |
| 用户、API Key、渠道、当前余额 | 主数据库 | Redis、页面状态 |
| 缺失表达式的历史任务退款分类 | 主数据库原 Task 冻结计费快照，经身份精确匹配 | 当前渠道价格、相邻日志或模型名猜测 |
| 客户请求用量、结算金额、退款、Request ID | 日志数据库的消费与退款日志 | 当前价格设置、前端重算 |
| 平台统计的上游用量 | 日志数据库按渠道、Provider 模型聚合的已持久化用量 | 进程计数器、监控指标 |
| 上游渠道月度折扣 | 主数据库 `ProviderChannelBillingDiscount` 版本；旧 `ProviderBillingDiscount` 仅作历史证据 | 前端擅自改值、配置缓存 |
| 上游折扣操作审计 | 主数据库 `ProviderBillingAudit` 追加记录 | localStorage、日志文本 |

主数据库与日志数据库可独立部署；查询服务可分别读取后服务端组合，但组合结果不得只存于内存或前端
并宣称为账单事实。任何跨请求保留的折扣与审计事实必须先写入主数据库。

缓存规则：Redis、进程缓存、React Query 只用于缩短读取，必须能从数据库完全重建；正式账单默认直查
数据库；写入成功后可失效缓存，禁止先更新缓存再异步补写；数据库与缓存不一致以数据库为准。

## 4. 路由隔离与接口合同

全部新接口在独立 `router/billing-reconciliation.go` 注册；`router/api-router.go` 只增加一行
`registerBillingReconciliationRoutes(apiRouter)`。

| 方法与路径 | 权限 | 数据库行为 |
| --- | --- | --- |
| `GET /api/billing/statement/self` | `UserAuth` | 当前用户的 API Key → 客户模型汇总 |
| `GET /api/billing/admin/customer-statements` | `AdminAuth` | 按账期生成全客户汇总，服务端搜索、质量过滤、排序和分页 |
| `GET /api/billing/statement/self/logs`、`/logs/stat` | `UserAuth` | 按认证用户与账单条件读取结算明细及全范围净额 |
| `GET /api/billing/admin/customer-logs`、`/customer-logs/stat` | `AdminAuth` | 按显式用户 ID 与账单条件读取结算明细及全范围净额 |
| `GET /api/billing/admin/customer-summary` | `AdminAuth` | 指定用户、账期和维度（`channel` / `api_key`）聚合日志数据库 |
| `GET /api/billing/admin/upstream-summary` | `AdminAuth` | 统一上游视图：按渠道当前基础 URL 归组聚合平台用量，读取本地原价投影和渠道月度折扣，返回原价及折后参考金额与完整性标记；只读，不物化折扣、不写审计 |
| `GET /api/billing/admin/upstream-details` | `AdminAuth` | 跨客户逐笔证据：按 URL 对应渠道集合、Provider 模型、计费方式和双方请求 ID 筛选；上游任务 ID 仍仅对根管理员返回 |
| `PUT /api/billing/admin/upstream-discounts` | `AdminAuth` | 版本校验保存渠道月度折扣及审计 |
| `POST /api/billing/admin/upstream-discounts/initialize` | `AdminAuth` | 显式幂等月度初始化：仅为当月无记录的渠道复制上月有效配置并写审计 |

请求约束：账期大于零且不超过产品范围，自然月边界由后端按 `Asia/Shanghai` 生成；管理员客户查询必须
显式提供合法 `user_id`，普通用户接口始终从认证上下文读取；`dimension` 只接受 `channel` 或 `api_key`，
普通用户固定 `api_key`；`billing_mode` 接受 `token`、`per_call`、`per_second` 或 `unknown`；全客户列表只在客户维度分页，顶部
总计是全部筛选结果的服务端全量聚合，不能由当前页相加。写接口经过 `AdminAuth`、CSRF 保护、参数校验和
操作审计。

响应使用统一信封：

```text
data.period / data.filters / data.result / data.generated_at / data.data_version / data.data_source
```

单客户 `data.result` 含 `summary`、`groups` 和 `data_quality`；全客户列表 `data.result` 含筛选后全量
`summary`、当页 `items`、`page`、`page_size`、`total`；上游 `data.result` 含 `url_groups`
（每组含用量、原价与折后参考金额、渠道折扣编辑区 `channel_discounts`）和 `data_quality`。
聚合行不返回 Request ID 列表，每个模型子行返回 `detail_filter`。客户账单下钻复用用量日志页面，
通过独立账单明细接口保留 `user_id + token_id/channel_id + model_name + billing_mode + 账期`；
`token_id=0` 必须显式序列化并作精确筛选，省略才表示所有密钥。客户身份不依赖可变用户名。
明细和统计使用同一结算范围及计费分类，分页总数是日志行数，净额是全部匹配行的消费减退款；
异步调整行不等于新增逻辑请求。明细页显示账单范围说明，不提供会将查询切回通用日志的筛选栏。
`data_quality.status=partial` 时必须按质量计数说明未识别或不可用的具体信息，不得把部分原价合计
展示成完整金额。模型级与汇总级质量状态使用相同规则；未识别计费分类不等于金额缺失。

现有 `GET /api/billing/self` 与 breakdown 接口作为兼容入口保留，合同不变。当前没有、也不计划增加供应商
账单导入、供应商数值维护或双方差异确认接口。

## 5. 数据模型

主数据库新增三个独立模型，不创建供应商账单、双方差异或 review 模型。

运行时唯一折扣来源 `ProviderChannelBillingDiscount` 唯一键：

```text
period_start + channel_id
```

一个渠道当月所有 Provider 模型和计费方式共用一个综合系数（`decimal(12,8)`，合法范围
`0 < 系数 <= 1`），同时保存来源月份、版本、修改人、原因和时间。月度初始化是独立、幂等的写入操作：
仅当当月无记录时复制上一个自然月同渠道的有效配置并记录来源月份；上月无有效值时初始化系数 `1`。初始化只处理未初始化项，不覆盖人工值、迁移值或已更正的继承值；
并发初始化通过渠道行锁加唯一键幂等。人工保存使用 expected version 并拒绝携带来源月份。
汇总与导出读取不物化折扣；当月无记录时投影默认系数 `1`、版本 `0`、来源 `default`。
迁移冲突用 `PendingReason` 与版本 `0` 持久化，投影为空且不可被初始化覆盖；首次人工确认升为版本 1。

旧模型级 `ProviderBillingDiscount`（键 `period_start + channel_id + provider_model + billing_mode`）
及其审计整体保留为历史证据，运行时不再读取。启动迁移 `migrateProviderModelDiscountsToChannel`
一次性、幂等、非破坏地把旧记录收敛为渠道月度记录：逐条依据当时审计证据判定来源为人工、可证明
继承自人工的复制链、系统缺省或来源不明；继承有效性按复制时点祖先的历史值核实，来源月份后续更正
不影响已发生的复制。同渠道同月有效候选系数（含有审计依据的系统默认 1）全部一致且无来源不明记录混入时收敛为一条渠道记录，
否则保持待确认；不取第一条、不平均，系统默认不标为人工确认。旧审计行不删除、不改写。

`ProviderBillingAudit` 以追加方式保存折扣每次写入的 before/after、原因和操作人（实体类型区分
模型级历史 `discount` 与渠道级 `channel_discount`）；不暴露更新或删除入口，纠错以新版本写入和
新审计行表达。迁移函数 `migrateBillingReconciliationDB` 对三个模型执行 GORM `AutoMigrate` 并
运行上述一次性折扣收敛迁移，兼容 SQLite、MySQL 与 PostgreSQL。

`BillingBalanceLedgerEntry` 尚未创建，属未实现的余额流水阶段。

## 6. 历史计费快照

快照中的 `customer_model` 保存当次客户公开模型，独立于日志原生 `model_name` 计价身份与
`provider_model`。客户账单及其专属明细在读取快照后按该身份聚合、精确筛选和展示；旧日志未保存
此事实时只保留原记录模型，不使用当前合同或映射猜测历史身份，也不回写日志。原生计价和通用日志
接口不受该只读投影影响。

请求结算时由 `service/billing_statement_snapshot.go` 在日志 `other.admin_info.statement_snapshot` 冻结
身份与分类事实，不评估或改变价格：

```text
snapshot_version = 1
billing_mode     = token | per_call | per_second | unknown
provider_model   = 上游模型，缺失时回退客户模型
model_price / model_ratio / completion_ratio / cache_ratio /
group_ratio / user_group_ratio / expr_b64 / usage_units  （仅复制当时已存在的字段）
```

快照位于 `admin_info` 下，普通用户日志响应会连同其他管理员字段一并剥离。存在冻结表达式时，账单按
其计量依赖分类，优先于旧任务快照的 per-call 标记；普通按次路径继续使用 `model_price > 0` 或显式
per-call 事实。任务零固定单价不能解释非零扣减/退款；此时没有表达式或可确认的 Token 事实，旧
per-call 标记不能证明按次。退款日志未保存表达式时，可按客户、应用/API Key、渠道、模型和 task ID
唯一匹配原 Task 冻结计费快照，只读补充分类；缺失或歧义仍为 unknown，不回写日志、不调整金额。
客户汇总、客户列表与专属明细共享该规则。显式免费按次记录保留。
人工退款的明确原预扣引用，在用户、API Key、渠道、客户模型、消费类型和全额退款一致后，只读
继承计费分类与倍率。引用唯一性核验覆盖该用户/Key 的全部历史退款，按 ID 每批 500 行扫描，
仅保留待核验引用计数；`idx_logs_user_type_token_cursor` 索引支持游标读取。不以历史行数达到
某个阈值作为放弃核验的理由。批次查询尊重调用方取消与时间预算，失败返回错误，不将部分扫描
结果作为唯一引用证明；跨期重复引用、冲突或部分退款仍不恢复。原始日志及实际金额不改写。

专属明细在角色脱敏之前，使用补证后的同一解析结果生成 `other.billing_facts` 客户安全投影；
其结构复用导出行，携带计费分类、输入语义已知性、历史组/倍率来源、合同记录状态及金额解释质量。
后续响应装配与页面读取该投影，不再从已剥离管理证据的 `other` 推断历史事实；原日志不回写，
源日志解析器不读取响应投影。退款只展示账务分类与优惠事实，不展示为新的计量消费。

折扣组合键包含发生时记录的计费组与有效倍率来源（普通组或用户专属组），独立于 API Key/渠道父级键。
同倍率不同组、同组不同来源分别成行；缺失组身份保持未记录，不查当前用户组或渠道配置。
原预扣明确关联且证据一致时，退款可以继承组身份和倍率来源；矛盾证据不拼接成可用历史价格。
计费组及倍率来源保留在逐事件明细；汇总与明细使用相同历史事实解析结果。

原生任务插件的 `u()` 单位在创建时从已选定 adapter 的已验证 schema 复制到
`BillingSnapshot.UsageUnits`，随 Task 保存并进入创建与结算日志；只引用已声明 Token 计量及 enum/
boolean 条件时归为 token；声明为 second 的单一计量或历史宿主 `_task.duration_seconds` 探针归为
per_second。缺少冻结单位、混合不同计量单位或动态字段引用保持 unknown，禁止从模型名、
字段名或当前插件配置推断历史。单位快照只服务展示，不改变表达式求值或 quota 换算。
该快照足以避免读取当前配置，但还不是统一 PriceBook；在统一单价模型落地前，
历史原价使用已记录的分组倍率；没有合同记录时合同因子为 1，有合同则叠乘已记录的合同倍率。
合同状态区分 yes（有倍率）、no（明确未适用）、unrecorded（无合同记录）与 unknown（残缺或冲突）。
没有合同记录不阻止估算，也不回写“无合同”事实；分组倍率缺失、合同残缺/冲突等仍使整层估算未知。历史日志缺少足够
快照时，能确认的 Token 和结算 quota 继续展示，原价、折扣或计费方式标记未知，不从当前配置回算，也不
把未知行计入需要该字段的折扣汇总。

## 7. 聚合口径

### 7.1 客户账单

原价反推以已舍入的整数 quota 为输入，因此只能得到估算值。页面和自助 CSV 使用“估算原价”与
“估算优惠”，不能把反推值宣称为实际折前金额。净额保持日志消费减退款，包含任务预扣和结算调整。
模型、API Key、折扣组合及总计的优惠列统一显示金额。模型优惠从已知估算原价减净额派生，
使用十进制减法和 int64 范围检查；未知保持空、零保持零。旧固化投影可从已冻结金额作同一
算术投影，不重写原文件、不重新解释历史价格。
日志开启、完整性及保留由管理员负责；账单不增加覆盖率、日志保留闸门或额外账本。

客户账单的输入 Token 表示总输入，缓存读取/写入是其子项。已保存 `input_tokens_total` 或
`usage_semantic` 时按既有用量归一规则解释；没有缓存时保留原输入。带缓存却缺少可确认语义时，
`input_tokens_unavailable_requests` 标记输入字段不可解释，模型行和 CSV 不展示部分输入合计为
完整输入；已知缓存、金额仍保留。文本结算在既有入口冻结实际计费使用的输入语义，包含原生已经支持的
Claude 转换语义；异步图片完成日志从 Task 保存的 usage 投影总输入、缓存读取和缓存写入。
历史输入只读恢复以冻结的写入证据为依据：规范化 Gemini 路径可恢复总输入；历史文本行须同时
具备已知北向路径、首段与路径一致且各段已知的完整转换链以及 upstream 计费路径。末端
OpenAI/Responses writer 的输入已包含缓存，最终 Claude writer 且 claude 标记为真时累加缓存。
通用缓存创建不重复累加；非零 TTL 创建量因旧派生分支证据不足继续未知。显式字段损坏、非法缓存量、
冲突标记或缺少 writer 证据不恢复。转换链或 upstream 单独存在不构成证明；不按模型名、当前渠道
配置或金额反推输入。直接记录的有效总输入/语义优先。正式解析版本为 4。


Batch 完成日志从经 int64 校验的持久行级事实汇总 `input_tokens_total`、`output_tokens_total` 和
`cache_tokens`，并记录 OpenAI 输入语义。原生 int32 日志列仍使用既有饱和转换；客户汇总、专属
明细和上游统计使用完整批次元数据，不把列的饱和值当作批次总量。单次资金上限、计价与资金目标不变。

客户账单和使用记录通过服务端异步导出交付。`CustomerExportJob` 冻结目标客户、筛选范围、时区、
语言、字段版本和金额换算，复用 SystemTask 调度；状态轮询只读任务表，下载只重新鉴权签发已有文件地址。
日志按有界批次和唯一 ID 游标读取，消费/退款共用账单事实解析和批量补证，不执行定价、资金扣退或 Provider 调用。
CSV 流式分片上传至既有私有对象存储，生成完成后发布全部文件；前端逐文件展示直接下载链接及到期刷新入口。
任务卡显示稳定客户 ID 和冻结范围，等待及取消状态可见；取消确认前保留执行容量。

第一版采用固定单执行槽、容量 3、每人一个活动申请、2,000 候选行/秒和固定时间/空间预算，
配合压力退让与可取消查询；不设置独立导出总开关或动态速率配置。ClickHouse 唯一游标未经验证，导出失败关闭。
同一活动申请去重与历史产物下载已经实现。账单汇总与账单明细在同库部署下复用现有事务性客户来源修订、
维护代际及当前客户名称形成内部来源校验值；生成前后校验值一致才写入产物元数据。提交时以发起人、目标
客户、导出类型、完整规范化条件、来源校验值、存储身份和有效期匹配成功任务，直接返回原记录，不占用槽位。
客户来源修订覆盖消费/退款原地修改及跨月任务证据变化；维护中、来源保留已被标为不完整、无修订跟踪、
分库部署、非结算日志筛选或缺少来源校验值的旧产物均不自动复用。数据在生成期间变化时，产物可按原有导出
语义交付，但不具备自动复用资格。当前客户任意月份的相关数据变化会保守地使其导出失去复用资格。
来源校验值不在客户响应中公开。使用记录导出和有效聚合缓存轻量通道不在本次自动复用范围。
本地回归不能替代真实 OSS、MySQL/PostgreSQL 驱动取消及核心流量下的压力验收。

客户账单导出字段版本为 11，版本随规范化条件参与自动复用判断。汇总只输出 API Key × 模型 ×
计费方式叶子行，不混入父级总计或折扣组合；金额列前置，不在客户汇总重复展示内部 quota、任务 ID
和价格快照字段。客户明细复用通用流式写入器，通过独立列投影提供中英文客户表头与枚举；使用
记录导出保留机器字段。新固化版本的汇总、明细共用上述写入入口，已有制品保持不可变。

CSV 金额按冻结换算保留八位小数，未知字段为空、退款净额为负；原始 quota 仍保存在冻结事实和
管理员使用记录 CSV 中。只导出客户安全投影，文本防公式注入。客户明细每行一个入账事件，
记录时间、请求 ID、API Key、模型、金额在前，用量、历史分组与合同倍率、最终倍率在后。
请求 ID 仅使用记录值；退款及调整不伪装为新的计量请求，不从费用反推用量。

客户明细以可读单元格保留计费分项的数量、单位、美元单价、单价基数（Token 为百万，其他为一）和
美元小计，列名明确 USD 与折扣前口径；管理员使用记录继续使用 `billing_line_items_usd` JSON。
命中阶梯及单价明细状态来自既有安全解释投影。费用解释与页面使用同一计算入口，换算由调用方
传入；没有独立证据就留空。多个分项仍只占一行，不重复累计净额。分项小计不包含未知折扣或未
记录附加费，不能代替入账金额列。

后端按请求参数选择 `token_id` 或 `channel_id` 作父级键，再按客户模型和计费方式聚合；响应同时返回
数据库全量总计与父级行，前端不二次计算正式金额。全客户首屏先按 `user_id` 聚合账期内消费与退款日志，
再批量查询主数据库用户身份；已删除客户的历史账务仍可查并标记删除状态。搜索、质量过滤、排序、全量
总计和分页全部在后端完成。用户记录物理删除但仍存在客户结算日志时，管理员仍可按稳定用户 ID
查看详情；身份显示删除标记，`current_balance=null`，不能把无法读取的当前余额显示为零。没有用户记录
且没有客户结算历史时仍返回未找到，渠道测试日志不能单独构成客户历史。

折前金额按每条消费、退款各自冻结的分组与合同倍率还原，消费正计、退款负计。模型、分组、客户和
全客户汇总保留有符号十进制中间值，到对应输出层才舍入。净额与折前净额保留符号；退款独立分组、
跨账期退款与筛选明细不得将负数截为零，保证子行与父级口径一致。优惠为折前净额减结算净额，
退款的优惠冲回同样保留符号；倍率缺失、无法拆分附加费或展示合计溢出时返回未知。
同组日志从无合同切换到合同折扣，或从合同切回无合同，须把无合同记录按有效合同倍率 `1` 参与
多折扣判断；不同倍率返回多折扣标记而非单一合同折扣。全部记录均无合同事实时不展示合同折扣。

客户查询统一使用 `customerSettlementLogs` 范围：排除原生渠道测试写入的
`type=consume + token_id=0 + token_name=模型测试 + content=模型测试` 记录，因为这些记录只有
计算费用，没有客户资金扣款。不能仅按 `token_id=0` 或日志名称排除；真实游乐场、免费调用与退款仍保留。
此规则也用于旧自助账单和使用构成接口；上游对账保留实际发生的测试调用。原始日志和余额不因此回写。

关系型日志库通过非唯一索引 `idx_logs_user_type_created_at(user_id, type, created_at)` 支持单客户
账期查询及一次性退款取证；索引只包含三个已有标量列，不复制日志正文或改变写入事务。主节点日志
初始化覆盖同库和独立日志库，已存在时不重建；ClickHouse 沿用专属迁移。关系型交互账单按日志
`id ASC` 遍历，与导出顺序一致，避免访问索引变化影响历史名称选择和折扣组合溢出归类。
退款关联的 Task 快照从主库读取，使用非唯一联合索引
`idx_tasks_task_user_app(task_id, user_id, app_id)` 支持原生 Task ID 查找与每批最多 200 个
任务 ID 的带身份精确补证；该索引替换原 `task_id` 单列索引（及早期附加式
`idx_tasks_user_app_task`），Task 总索引数不增加，由主节点启动迁移创建与退役，与日志库是否
独立无关。Task 列类型、私有快照及身份校验保持原有定义；同一作用域的重复任务仍允许写入，
补证歧义保持未知，不选取任意一条。
首次建索引具有 DDL、锁等待、磁盘及后续写入维护成本，部署前须在副本验证并安排受控迁移窗口，
不能把代码回归通过理解为在线建索引无影响。主库物理索引集合、迁移安全校验与部署约束见
[主库索引读写平衡架构](主库索引读写平衡架构.md)。

按 Token 行：`input_tokens / cache_read_tokens / cache_write_tokens / output_tokens / gross_quota / refund_quota / net_quota`。
按次行：`requests / billable_calls / refunded_calls / gross_quota / refund_quota / net_quota`。

异步任务调整行影响 Token 与费用但不重复增加逻辑请求数。净费用保留符号；跨期退款按退款日志发生时间
进入查询账期。

本地异步表达式任务的完成日志使用已接受实测与冻结条件计算 `usage_facts` 和 `matched_tier`，
不复制创建时的预算用量。预扣等于实扣时仍写零金额调整行；只有既有原子结算成功的调用负责写入，
重复补查不重复记请求或用量。创建快照保持不变。资金与日志可位于不同数据库，这不构成跨库原子保证。

### 7.2 上游平台用量

平台侧用量从日志数据库按 `period + channel_id + provider_model + billing_mode` 聚合。Provider 模型优先
读取请求发生时已持久化的上游模型快照；缺失时标记无法映射，不从当前 `model_mapping` 反推历史 Provider
模型。服务端只组合同一业务键下的平台用量、`ProviderBillingDiscount` 和数据质量。按 Token 行返回平台
记录的输入、缓存读写与输出 Token；按次行返回平台记录的请求数和计费次数。

原生渠道测试历史记录缺少缓存写入总量及 TTL 字段且不是按次计费时，返回
`data_quality.cache_write_unavailable_requests` 并将质量标为 `partial`；页面和 CSV 的缓存写入栏显示
“未记录”，已知部分仍保留在数值字段中。显式记录为 0 不属于缺失。普通日志查询为同类历史测试动态
增加公开 `cache_write_unavailable` 展示标记；这是只读响应投影，不回写日志。新测试保存已有 usage
中的总量、TTL 和语义；不从当前价格或费用反推历史缓存写入量。

上游用量采取消费行，以及能确认属于 Task 结算调整的退款行；后者可能承载完成用量，按实测正计，
不增加请求次数。识别依据为 Task ID 与明确 adjustment 事件，或旧日志同时具备实扣和预扣字段；
明确 refund/create 事件不作为退款行上的完成用量。普通客户退款不冲减 Provider 用量，也不生成上游退款次数。

在上游“双方官方原价一致”的业务前提下，汇总按客户账单原价投影复用同一还原算法为每个渠道模型行
计算有符号原价金额（消费正计、全部客户退款负计，缺失价格沿用客户账单退款补证），逐层以十进制聚合、输出层统一舍入。
原价缺少冻结价格、折扣或合同证据时保持未知并计入 `missing_historical_price_rows`；原生渠道测试行
保留用量但不进入金额，单独计入 `usage_without_amount_rows`，因此用量与金额的覆盖范围有意不同，
不能从测试用量缺少金额推断上游免费。折后参考金额 = 原价金额 × 渠道当月系数，按渠道应用后聚合；
折扣待填写或原价未知的父级金额保持不完整，可显示已配置部分的参考金额与待填写渠道数，
不把部分已知金额冒充完整总额。参考金额不代表独立采集的 Provider 成本、供应商账单或应付金额，
不进入客户结算、资金或付款依据，也不生成双方差异。

### 7.3 统一上游对账视图（URL 归组投影）

管理员统一上游视图按「渠道当前基础 URL → 上游模型 × 计费方式 → 渠道贡献」三级归组，聚合同一批
日志行和解析口径，因此 URL 组总量等于所属渠道贡献之和；渠道折扣编辑区与该层级并列，每个有用量
渠道一个槽位。归组只服务账单展示，不建立供应商身份，不参与路由、履约、计费或结算。

- 归组键是渠道当前配置基础 URL 的规范化形式：仅折叠协议/主机大小写、协议默认端口和路径末尾斜杠；
  协议、非默认端口和基础路径参与身份，不只按域名合并；编码斜杠 `%2F` 不转成路径分隔符，
  IPv6 主机保留方括号。
- URL 缺失、不可解析、含凭据、查询参数或片段时视为无法安全识别：不展示敏感部分，也不在删除这些
  部分后合并，而是按渠道单独保留归组；已删除渠道同样按渠道单独保留并标记删除状态。空 `base_url`
  继承 `GetBaseURL` 的渠道类型默认地址语义。
- 上游模型身份未知的 fallback 行不与已确认模型混并；同一上游模型按 token / per_call / per_second / unknown
  计费方式分行；模型数按模型身份（包括是否 fallback）计，不按计费方式行数计；合并行不构造指向单个渠道的伪明细入口，下钻仍通过真实渠道明细行完成。
- 汇总查询保持只读：不物化月度折扣、不写审计、不回写日志；月度初始化与人工保存通过各自的写入
  接口完成并按其动作记录审计，页面提供编辑入口不改变查询的只读职责。数据质量标记逐层聚合，
  未知不显示为零。总体质量只聚合当前 URL 筛选范围；三级行均展示请求数。页面与 CSV 注明「按渠道
  当前基础 URL 归组」及上海时区账期起止；CSV 只导出渠道明细叶行并逐行记录当次使用的渠道折扣值
  和版本，后续修改折扣不改写已生成文件，不重复导出父行合计。
响应不包含供应商 Token、次数、退款、差异率或处理状态；原价与折后参考金额是本地口径的参考展示，
不是供应商金额。平台只对账已持久化的最终用量，不假设失败重试成本为零；未交付、流中断、重试与
跨期结算造成的双方口径差异由运维线下核实；是否新增“Provider 尝试用量事实”须在真实 Provider
账单验证后单独评审。

### 跨客户上游明细导出

`POST /api/billing/admin/upstream-exports` 独立授权跨客户 `upstream_details` 任务，既有客户导出
入口继续只接受单客户类型。任务冻结渠道集合与名称、折扣及版本、筛选、币种、换算因子和字段权限；
状态、取消、下载复用原导出设施，每一步读取当前用户角色。含 Root 字段的文件在角色降级后不可下载。

汇总、明细与导出共用 `billing_upstream_reader.go`，SQL 日志以 500 行批次及固定 ID 上界读取，
使用既有退款补证；导出复用队列容量、压力退让、任务预算、CSV 分片及对象清理。未知金额保持空白，
系数保留八位精度，金额列附币种和换算因子。新请求不自动复用完成文件；重新生成沿用原冻结范围。
ClickHouse 查询保留单游标路径，未经唯一游标验证的异步导出仍明确拒绝。

## 8. 前端边界

普通用户从 `/billing` 进入自己的账单，固定 `api_key` 维度，看不到客户数量、客户搜索或上游控件；
管理员从 `/admin/billing?section=customer|upstream` 进入（旧地址 `section=upstream_url` 由路由解析后
并入统一上游视图），路由与接口均要求 `AdminAuth`。两个 Tab 共用
数据库状态提示，但请求不同接口、使用不同响应类型；客户账单与上游用量各自保留记录范围，
参考金额只读复用本地原价投影，不将二者混成供应商成本事实；禁止把客户金额与上游金额合并成同一
汇总对象。管理员访问 `/billing` 时看到的仍只是自己的账单，不自动跳转全客户列表。

既有用量日志路由仅扩展 `billingMode` 搜索参数枚举以接受 `per_second`，防止账单下钻丢失
筛选条件；分类、退款事实读取与聚合逻辑保持在账单专属文件。未来同步上游时，该路由枚举是
需要保留的最小接线点，不改变通用日志查询行为。

前端只负责格式化、展开模型行和导航；金额、Token、计费次数和数据质量均由后端返回。每次切换 Tab、
用户、账期、渠道、API Key、模型或计费方式都调用对应聚合接口。上游渠道和模型筛选作为后端聚合
条件，上游表格父行、模型行、数据质量和上游前端 CSV 均使用同一份筛选响应；全量响应只额外保留筛选选项。
客户导出独立冻结这些筛选条件，由服务端读取并生成文件，不再从浏览器响应序列化客户 CSV。
筛选查询加载或失败期间保留控件并禁用导出，不能拿未筛选渠道总计搭配筛选后子行。API Key
使用稳定 `token_id`；合并多个客户模型的上游行只下钻到渠道账期，不伪造单模型条件。

客户列表把最终费用与资金流水分开展示：结算原价、优惠、净结算金额相邻排列；累计扣减和累计退回
列于其后。累计扣减包含预扣，累计退回包含结算退差额及其他退款，不能命名为最终实付消费。
页面可见说明同时解释“结算原价 − 优惠 = 净结算金额”与“累计扣减 − 累计退回 = 净结算金额”。
计费方式未识别的历史记录数量直接使用后端质量计数，部分数据不等同于费用缺失，未知价格仍显示未知。
列表与详情分别呈现用量可用性、原价优惠估算可用性，并按非零计数列出计费方式未识别、输入不可用、
用量不可读、缓存写入不可用、估算不可用及上游模型身份缺失；用量完整不表示钱包对账完成，
不将所有情况解释为快照冲突或提示刷新。未知计费分类不展示按次计费的零值用量。
渠道名称来自当前主数据库的渠道记录；记录缺失时显示本地化编号和历史费用保留说明，不推测历史名称。
现存但空名称的渠道使用编号展示，不能据空名称判定记录已删除。

## 10. 架构不变量

1. 客户与上游是两套独立口径，金额与用量互不覆盖，前端不得合并为同一汇总对象。
2. 正式账单只读数据库结算事实，不按当前价格、用户折扣或上游折扣重算历史。
3. 客户退款不冒充 Provider 冲正，不生成上游退款次数或冲减平台记录的 Provider 用量。
4. 按 Token 与按次分行聚合，不混合用量单位；未知计费方式不猜测。
5. 上游渠道月度折扣写入使用 expected version；审计追加且不可删改。未配置时按服务端默认 `1`
   展示和计算；已知历史冲突保持待确认且不能被默认或继承覆盖。折后参考金额只是本地口径参考，不进入客户
   结算、资金或付款依据；修改渠道当月折扣只改变参考展示，不重算正式客户账单或改写历史导出。
6. 数据库缺失的历史用量、价格或折扣显示未知，不以当前配置、页面合计、Provider 金额或缓存回填。
7. 缓存可重建，从不成为账单权威，也不回填数据库。
8. 余额流水未落地前，当前余额只直读主数据库，不用日志估算期初/期末。
9. 余额换算与汇总使用定点十进制，禁止裸 `float64 -> int` 作为账单金额转换。
10. 持久化、迁移和聚合继续兼容 SQLite、MySQL >= 5.7.8 与 PostgreSQL >= 9.6；ClickHouse 日志合同另测。

## 12. 客户月账单版本固化（默认关闭）

正式版本以主库中的月份指针、版本、明细、产物清单和审计为权威，私有对象存储保存下载文件。
生成复用既有导出队列、容量、租约、压力门控和历史事实解析器；确认原子分配版本号并切换当前指针。
草稿受理时冻结代码解析版本，生成、写入明细、转待确认和确认均校验当前版本；旧规则待确认草稿
在确认时失效并释放占位。已确认版本继续按原冻结事实读取和幂等返回，不补算旧版本缺失的模型优惠。
解析升级不得修改确认版本，解释或金额修正走更正版本；所有实例升级前关闭确认。

同库批量读取可在单次导出或版本生成内复用退款引用计数，按用户/Key 的既有退款修订和维护代际
验证，完整历史只需首次遍历。复用空间有限，未缓存引用仍扫描完整历史，不因容量不足判未知；分库
不复用缺少事务修订保证的计数。来源变化、维护或修订失败使已复用的读取失败，发布前再次核验。
没有来源保留行时，Log 和 Task 修订失败均按来源创建月份持久记录 partial；导出复用检查该客户全部 partial 记录，因此跨月来源变更也不能复用旧产物。围栏持久化失败则原事务失败，不把来源写成功误当作版本可靠。
确认后读取冻结投影，来源读失败不得回落实时重算；余额仍是独立实时字段。更正创建新版本并保留旧版。
版本历史仅在月份确实不存在时返回成功空列表；月份或版本读取失败，以及月份指向的正式版本或草稿
记录缺失时，状态接口明确失败，不投影成空历史、未确认或无活动草稿。

首期仅支持 `LOG_DB == DB`。来源钩子在所有写入节点的数据库初始化完成后注册，与主节点迁移分离；
在日志或 Task 的既有 GORM 事务内维护客户月份及实际外部依赖。确认与来源写入统一先锁修订、后锁来源保留状态。
退款依赖包含原消费 ID、客户与 Key 的退款查询范围、客户与应用的 Task 身份，缺失匹配也先登记。
客户登记锁用于序列化依赖建立，不属于草稿版本向量；无关月份消费不使历史草稿失效。
普通进度轮询不更新证据修订，整体结构体 CAS 写入会比较实际依赖字段；普通消费只更新已登记的精确依赖，不新增逐请求永久依赖行。
依赖发现按 500 行游标、批级超时和执行预算读取，超过 20,000 个依赖明确失败。登记使用每批 100 行写入、
500 个作用域读取，整个登记事务沿用 5 秒批级期限；复验同样按 500 个作用域读取，避免逐依赖查询放大锁占用。

正常来源与修订同事务提交。单独修订写入失败时，来源 SQL 后的保存点允许撤销修订工作，再锁定既有
维护控制行、推进维护代际，并将该客户已有来源保留记录及来源创建月份置为 partial；这些失败保护与
来源 SQL 在同一事务提交。即使已处于 partial 或再次发生故障，故障前完成的扫描也不能覆盖新标记。
来源写入或修订写入失败的异常路径保守地使全局旧来源证明、未确认草稿及导出复用失效；已确认版本和资金不变。
若维护代际或 partial 不能持久化，则整个来源事务失败，不能声称来源仍可靠。
该机制不补造缺失消费；来源恢复必须按维护与核验协议处理。普通 `createLog` 写入失败也在日志事务退出后，
以独立事务锁定并推进维护代际、标记该客户已有来源保留记录为 partial，避免旧扫描覆盖失败状态。
保留原错误，不重放、不退款；完全数据库故障时标记也可能失败，需人工核验后恢复确认。
原始 SQL、离线导入和备份恢复必须显式进入维护协议，分库拓扑不能使用此确认能力。
离线补修必须在事务内持有当前维护代际，进入维护时持久关闭确认；退出需匹配代际和明确核验依据，
结束后仍保持确认关闭。进入/退出记录操作人和依据；失败、中断或过期进程不得解除维护。

冻结 JSON 在 MySQL 使用 LONGTEXT，在 PostgreSQL/SQLite 使用 TEXT；两份维度投影仍受聚合与执行预算限制。
管理端列表按账期索引读取当前指针，逐个提取冻结汇总，不将所有客户的完整投影同时驻留内存；
合并实时客户后统一筛选、排序和汇总，用户身份查询及排除参数数量受控。
旧试验草稿缺少精确依赖向量时不能确认，必须重新生成；正式版读取不依赖该向量。
基础产物上传后读取并验证大小和 SHA-256，成功后才解除 staged；确认服务在数据库事务外再次校验对象，
确认服务在对象读取完成后重新读取管理员权限；确认事务内继续复验清单、来源修订和状态。
下载签名前检查对象存在性，丢失时不签发无效链接。
确认说明先登记唯一 staged 清单，上传并读回验证固定对象键和摘要；下载可以从冻结确认事实幂等重建。
开关关闭不妨碍已确认请求的幂等读取；新增确认仍被拒绝。
前端只保留绑定当前查看版本的下载入口；中英文导出和版本生成共享语言归一化。
失败保留重试依据，不回退已确认版本。失效草稿清理同样先删对象再删事实，失败保留引用。

主体位于 `model/billing_statement_*`、`service/billing_statement_version_*` 与专属控制器/页面。
既有原生文件只保留迁移、路由、必要读取/清理接线以及 `createLog` 返回点的一行失败观察；
这一接线保护“资金已结算但日志写入失败”的确认边界，同步冲突限于该返回点，不重构 Provider adapter、资金算法或 Task 状态机。
本地真实数据库合同测试与对象存储连通性不代表目标部署的多实例、容量或备份恢复已验收，功能开关仍默认关闭。
[实施方案与验证记录](../99-archive/2026/09/2026-09-17-客户月账单确认与版本固化方案.md)保留部署前检查与未完成项；未完成事项见[80 目录未完成事项汇总](../50-planning/2026-09-19-80目录未完成事项汇总.md)。

## 历史语义恢复与持款投影补正边界

历史读取仅按冻结 writer 事实恢复：北向路径与转换链首段一致，已知完整链的末端决定写入语义；
Responses/普通 OpenAI 输入包含缓存，Claude writer 输入不含缓存；旧 TTL 缓存字段不足以证明
派生转换语义时保留未知。Gemini 按明确 billing-usage-gemini 标记恢复。显式字段仍优先，损坏或
冲突事实不被历史推断覆盖。历史工具费用缺少完整换算事实时保持 auxiliary_charge，不读当前价格。

客户展示分别表达用量与估算是否可用。数据完整状态不证明钱包、累计已用或资金流水已完成核对。
维护协议下的持款补正只针对已批准且执行时证据仍一致的日志投影；不触发资金或累计统计变更。
已确认账单和文件不可覆盖，补正结果通过带原因的新更正版本呈现。CLI 的排除清单不是收费依据。

### 历史尺寸倍率的计量分类

冻结表达式中的 `_task.size_multiplier` 是无量纲尺寸倍率；与明确的秒数计量共同出现时
可分类为按秒。倍率本身不能证明按次，客户自定义同名参数和未声明单位不构成证明。
该只读解释不重新发布旧字段为新计价合同能力，不改变金额或推导缺失的实际时长。


## 14. 管理端来源证据核验

`billing_statement_source_review*.go` 在同库范围内读取目标客户完整消费、退款及已结算 Task 的显式关系，
月内解释复用正式解析器及退款补证。任务最终金额与关联日志净额比较只产生待调查事项，不产生应收、补扣或退款。
日志明细和 Task 私有字段不整体返回；响应仅含客户模型、内部记录编号、时间、精确金额和证据缺口。

逐项业务决定追加既有审计：保留现有记录、待复核、减免申请、重复排除申请及账期更正申请。
后面三者只登记待处理请求，不触发资金或账单调整。最新待处理申请独立于异常列表投影，
异常消失或来源变化不能自动结案。超级管理员填写依据后可撤回或驳回申请，两者都不执行账务调整，
也不自动接受仍存在的解释缺项或金额差异。结案追加原申请上下文、前驱及零金额影响；来源收据和
决定接口版本为 3，旧收据须重新核验，已确认版本不变。
损坏或未知审计结构仅返回记录编号、人员及时间用于定位，允许查看报告，但阻止该月业务决定和
来源登记；不得忽略损坏行后恢复此前接受决定，原审计记录不得删除。
金额差异不能通过接受动作解除；来源登记要求全项审阅、
无金额阻断及备份/保留依据，提交时重新扫描，并在维护控制行与客户登记锁内核验来源和最新审阅记录。
核验指纹绑定客户、月份、解析版本、维护代际及实际证据；非相关来源变化不撤销逐项审阅。
扫描保留 30 秒期限，按当前批次字段、结构开销及持续保留的关联/待返回问题计算 64 MiB 工程预算；
已处理批次释放预算，不把完整历史累计扫描量当作内存或业务上限。依赖超过 20,000 个时立即失败。
日志按 ID 每批最多 500 条读取所需字段，跨月关系只保留核对与指纹字段；月内退款解释按当前批次建立，
其唯一性仍检查完整历史。Task 每批最多 200 条，身份计数仅按本批客户/应用/任务关系分组，不保留全客户分组集合。
管理决定历史按 ID 每批最多 100 条读取，解码前将审计文本、解码后文本及历史结构计入扫描剩余预算；
完整历史继续返回，不截断旧决定。提交时锁内重读以同一剩余额度替换历史，不重新获得完整预算，也不
重复扣除旧历史；重读同样受 30 秒期限及调用方取消约束。历史超限会使整个查询或提交失败。
超限、取消或读取失败均不返回部分报告、可登记指纹或自动接受结果；预算不是业务上的历史行数截断，也不是进程 RSS 上限。
人工外部依据仍由授权人员负责，扫描不证明不存在已删除记录。

完整性收据保存在既有来源保留记录，依赖向量复用来源修订表；字段使用 BillingStatementJSON，兼容
MySQL LONGTEXT / PostgreSQL TEXT / SQLite TEXT。审计保留来源指纹和人工依据，不创建第二资金账本。
除既有客户月和具体日志/Task/退款引用范围外，仅对已注册的任务创建月份、显式任务日志关系维护附加修订，
覆盖后补任务与跨月补写消费。登记依赖只取得锁，不增加来源修订；正式确认按维护、客户登记、证据、保留的顺序核验。

正常来源登记只推进本客户账期修订，不递增全局维护代际；进入/退出维护及来源写入、修订写入失败使用既有代际屏障。
已确认版本继续按原幂等路径读取；旧自由文本保留记录不能授权新草稿，目标环境必须重新核验。
普通管理员可查看，写入沿用 Root 权限。此次未改变原生 Relay、资金算法、Task 生命周期或离线补正入口。


### 管理决定审计与撤回

管理决定冻结请求标识、前一决定、业务原因、备注、操作者、时间、客户月份、记录类型和当时金额；
实际账单及余额变动均明确记录为零。历史决定追加保留，来源变化后仍可追溯但不能授权当前核验。
保留记录不需要人工编写技术证据，未知解释继续保留；既有退款不因“不新增退款”被撤销。

维护控制行及客户登记锁内复查最新审计，匹配来源指纹和前一决定；同一请求重试幂等，其他操作者或
修改后的请求不能复用请求标识。每次有效新决定推进客户月修订，使先前来源完整结论及未确认草稿失效。
来源收据合同为版本 2；旧收据需重审，已确认版本沿原幂等路径读取。GET 明确返回 decision_version=2，
前端遇到旧服务响应停止操作，旧 accept 请求也不能在新服务直接授权，部署需全部实例协同升级。

复用已有账单审计、来源修订和保留表，不新增迁移、并行资金账本或原生资金路径接线。
技术来源完整性登记折叠显示并与业务处理分工，隐藏交互不改变正式确认的后端要求。
