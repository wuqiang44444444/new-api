# 客户与上游对账架构

## 1. 目的与范围

本文描述平台管理员“客户账单”和“上游对账”两个一级 Tab，以及普通用户自助账单在后端如何以
数据库结算事实为权威完成聚合。它是只读对账投影，与预扣、结算、退款和日志写入主链路解耦。

用户自助账单按“周期 × API Key × 客户模型”聚合的逐指标数据口径由
[API Key 用量账单架构](API-Key用量账单架构.md) 详细解释；本文只补充管理员客户/上游两个 Tab、
上游月度折扣与审计、请求级计费快照，以及客户与上游口径必须分离的边界。两者共享同一前端功能模块
`web/src/features/billing-reconciliation/` 和同一组只读查询入口，但不共享金额汇总对象。

本文不设计期初/期末余额勾稽、逐笔充值冲正、跨期重算或税务发票；这些能力的边界见
[客户与上游对账单产品说明](../10-product/客户与上游对账单产品说明.md) 与[路线图](../50-planning/路线图.md)。

## 2. 当前实现状态

代码已实现：

- 用户自助账单 `GET /api/billing/statement/self`，按自然月返回 API Key → 客户模型汇总；
- 管理员客户账单：全客户月度列表与单客户渠道/API Key 两种维度汇总；
- 管理员上游对账：按渠道 × Provider 模型 × 计费方式聚合平台日志用量；
- 管理员上游 URL 汇总：按渠道当前基础 URL 归组的第三只读 Tab，复用上游聚合口径（见 7.3）；
- 上游月度折扣的持久化、上月复制、缺省 `1`、expected-version 写入与追加式审计；
- 请求发生时在日志 `other.admin_info.statement_snapshot` 冻结版本、计费方式、Provider 模型和已结算计价因子；
- 客户与上游 CSV 导出，只导出后端返回的完整汇总。

未实现，保留为独立阶段，不在本文写成已落地事实：

- 不可变余额流水与期初/期末勾稽（`BillingBalanceLedgerEntry` 尚未创建）；
- 统一“人民币/百万 Token” PriceBook 版本快照；
- 上游折扣的前端编辑控件；
- 真实 MySQL、PostgreSQL、ClickHouse 用量、月末边界与脱敏验证。

代码存在不等于生产发布。在真实三数据库、ClickHouse 合同、权限和月末验证完成前，管理员对账不得
标记为生产可用。

## 3. 架构边界与权威事实

| 数据 | 权威数据库事实 | 禁止替代来源 |
| --- | --- | --- |
| 用户、API Key、渠道、当前余额 | 主数据库 | Redis、页面状态 |
| 客户请求用量、结算金额、退款、Request ID | 日志数据库的消费与退款日志 | 当前价格设置、前端重算 |
| 平台统计的上游用量 | 日志数据库按渠道、Provider 模型聚合的已持久化用量 | 进程计数器、监控指标 |
| 上游月度折扣 | 主数据库 `ProviderBillingDiscount` 版本 | 前端默认值、配置缓存 |
| 上游折扣操作审计 | 主数据库 `ProviderBillingAudit` 追加记录 | localStorage、日志文本 |

主数据库与日志数据库可独立部署；查询服务可分别读取后服务端组合，但组合结果不得只存于内存或前端
并宣称为账单事实。任何跨请求保留的折扣与审计事实必须先写入主数据库。

缓存规则：Redis、进程缓存、React Query 只用于缩短读取，必须能从数据库完全重建；正式账单默认直查
数据库；写入成功后可失效缓存，禁止先更新缓存再异步补写；数据库与缓存不一致以数据库为准。

## 4. 路由隔离与接口合同

全部新接口在独立 `router/billing-reconciliation.go` 注册；`router/api-router.go` 只增加一行
`registerBillingReconciliationRoutes(apiRouter)`。

| 方法与路径 | 权限 | 数据库行为 |
| --- | --- | --- |
| `GET /api/billing/statement/self` | `UserAuth` | 当前用户的 API Key → 客户模型汇总 |
| `GET /api/billing/admin/customer-statements` | `AdminAuth` | 按账期生成全客户汇总，服务端搜索、质量过滤、排序和分页 |
| `GET /api/billing/statement/self/logs`、`/logs/stat` | `UserAuth` | 按认证用户与账单条件读取结算明细及全范围净额 |
| `GET /api/billing/admin/customer-logs`、`/customer-logs/stat` | `AdminAuth` | 按显式用户 ID 与账单条件读取结算明细及全范围净额 |
| `GET /api/billing/admin/customer-summary` | `AdminAuth` | 指定用户、账期和维度（`channel` / `api_key`）聚合日志数据库 |
| `GET /api/billing/admin/upstream-summary` | `AdminAuth` | 聚合日志数据库平台用量，读取主数据库月度折扣 |
| `GET /api/billing/admin/upstream-url-summary` | `AdminAuth` | 按渠道当前基础 URL 归组聚合同一份平台用量，只读，不读取也不物化折扣 |
| `PUT /api/billing/admin/upstream-discounts` | `AdminAuth` | 版本校验保存折扣及审计 |

请求约束：账期大于零且不超过产品范围，自然月边界由后端按 `Asia/Shanghai` 生成；管理员客户查询必须
显式提供合法 `user_id`，普通用户接口始终从认证上下文读取；`dimension` 只接受 `channel` 或 `api_key`，
普通用户固定 `api_key`；`billing_mode` 只接受 `token` 或 `per_call`；全客户列表只在客户维度分页，顶部
总计是全部筛选结果的服务端全量聚合，不能由当前页相加。写接口经过 `AdminAuth`、CSRF 保护、参数校验和
操作审计。

响应使用统一信封：

```text
data.period / data.filters / data.result / data.generated_at / data.data_version / data.data_source
```

单客户 `data.result` 含 `summary`、`groups` 和 `data_quality`；全客户列表 `data.result` 含筛选后全量
`summary`、当页 `items`、`page`、`page_size`、`total`；上游 `data.result` 含 `channels` 和 `data_quality`。
聚合行不返回 Request ID 列表，每个模型子行返回 `detail_filter`。客户账单下钻复用用量日志页面，
通过独立账单明细接口保留 `user_id + token_id/channel_id + model_name + billing_mode + 账期`；
`token_id=0` 必须显式序列化并作精确筛选，省略才表示所有密钥。客户身份不依赖可变用户名。
明细和统计使用同一结算范围及计费分类，分页总数是日志行数，净额是全部匹配行的消费减退款；
异步调整行不等于新增逻辑请求。明细页显示账单范围说明，不提供会将查询切回通用日志的筛选栏。
`data_quality.status=partial` 时必须按质量计数说明未识别或不可用的具体信息，不得把部分原价合计
展示成完整金额。模型级与汇总级质量状态使用相同规则；未识别计费分类不等于金额缺失。

现有 `GET /api/billing/self` 与 breakdown 接口作为兼容入口保留，合同不变。当前没有、也不计划增加供应商
账单导入、供应商数值维护或双方差异确认接口。

## 5. 数据模型

主数据库新增两个独立模型，不创建供应商账单、双方差异或 review 模型。

`ProviderBillingDiscount` 唯一键：

```text
period_start + channel_id + provider_model + billing_mode
```

同时保存折扣（`decimal(12,8)`）、来源月份、版本、修改人、原因和时间。新月份只复制上一个自然月；
无记录时创建值为 `1` 的当前月记录。复制或缺省发生在该账期首次生成时并立即写入数据库、追加审计，
不是每次读取动态引用上月。普通保存使用 expected version，避免并发覆盖。

`ProviderBillingAudit` 以追加方式保存折扣每次写入的 before/after、原因和操作人；不暴露更新或删除入口，
纠错以新版本写入和新审计行表达。迁移函数 `migrateBillingReconciliationDB` 对两个模型执行 GORM
`AutoMigrate`，兼容 SQLite、MySQL 与 PostgreSQL。

`BillingBalanceLedgerEntry` 尚未创建，属未实现的余额流水阶段。

## 6. 历史计费快照

快照中的 `customer_model` 保存当次客户公开模型，独立于日志原生 `model_name` 计价身份与
`provider_model`。客户账单及其专属明细在读取快照后按该身份聚合、精确筛选和展示；旧日志未保存
此事实时只保留原记录模型，不使用当前合同或映射猜测历史身份，也不回写日志。原生计价和通用日志
接口不受该只读投影影响。

请求结算时由 `service/billing_statement_snapshot.go` 在日志 `other.admin_info.statement_snapshot` 冻结
身份与分类事实，不评估或改变价格：

```text
snapshot_version = 1
billing_mode     = token | per_call | unknown
provider_model   = 上游模型，缺失时回退客户模型
model_price / model_ratio / completion_ratio / cache_ratio /
group_ratio / user_group_ratio / expr_b64 / usage_units  （仅复制当时已存在的字段）
```

快照位于 `admin_info` 下，普通用户日志响应会连同其他管理员字段一并剥离。存在冻结表达式时，账单按
其计量依赖分类，优先于旧任务快照的 per-call 标记；普通按次路径继续使用 `model_price > 0` 或显式
per-call 事实。任务零固定单价不能解释非零扣减/退款；此时没有表达式或可确认的 Token 事实，旧
per-call 标记须归为 unknown，不能制造额外的按次退款分组。显式免费按次记录保留。
原生任务插件的 `u()` 单位在创建时从已选定 adapter 的已验证 schema 复制到
`BillingSnapshot.UsageUnits`，随 Task 保存并进入创建与结算日志；只引用已声明 Token 计量及 enum/
boolean 条件时归为 token。缺少冻结单位、混合不同计量单位或动态字段引用保持 unknown，禁止从模型名、
字段名或当前插件配置推断历史。单位快照只服务展示，不改变表达式求值或 quota 换算。
该快照足以避免读取当前配置，但还不是统一 PriceBook；在统一单价模型落地前，
历史原价只有在所有相关结算行都存在冻结折扣因子时展示，任一行缺失则整层返回未知。历史日志缺少足够
快照时，能确认的 Token 和结算 quota 继续展示，原价、折扣或计费方式标记未知，不从当前配置回算，也不
把未知行计入需要该字段的折扣汇总。

## 7. 聚合口径

### 7.1 客户账单

原价反推以已舍入的整数 quota 为输入，因此只能得到估算值。页面和自助 CSV 使用“估算原价”与
“估算优惠”，不能把反推值宣称为实际折前金额。净额保持日志消费减退款，包含任务预扣和结算调整。
日志开启、完整性及保留由管理员负责；账单不增加覆盖率、日志保留闸门或额外账本。

客户账单的输入 Token 表示总输入，缓存读取/写入是其子项。已保存 `input_tokens_total` 或
`usage_semantic` 时按既有用量归一规则解释；没有缓存时保留原输入。带缓存却缺少可确认语义时，
`input_tokens_unavailable_requests` 标记输入字段不可解释，模型行和 CSV 不展示部分输入合计为
完整输入；已知缓存、金额仍保留。文本结算在既有入口冻结实际计费使用的输入语义，包含原生已经支持的
Claude 转换语义；异步图片完成日志从 Task 保存的 usage 投影总输入、缓存读取和缓存写入。

Batch 完成日志从经 int64 校验的持久行级事实汇总 `input_tokens_total`、`output_tokens_total` 和
`cache_tokens`，并记录 OpenAI 输入语义。原生 int32 日志列仍使用既有饱和转换；客户汇总、专属
明细和上游统计使用完整批次元数据，不把列的饱和值当作批次总量。单次资金上限、计价与资金目标不变。

自助下载由 `customer-statement-csv.ts` 将当前 self 接口完整响应序列化成 UTF-8 BOM CSV，包含
后端总计、API Key 和全部模型行；不受展开状态影响，不重新汇总金额。客户页面和 CSV 统一使用
`formatCustomerStatementQuota`，金额最多保留八位小数，禁用通用余额格式的非零数值下限，
并保留原始 `net_quota`，未知字段为空、负数保留。导出只选取客户可见字段，文本防公式注入；加载、
刷新、失败与空数据期间不可下载，不新增服务端导出入口。

后端按请求参数选择 `token_id` 或 `channel_id` 作父级键，再按客户模型和计费方式聚合；响应同时返回
数据库全量总计与父级行，前端不二次计算正式金额。全客户首屏先按 `user_id` 聚合账期内消费与退款日志，
再批量查询主数据库用户身份；已删除客户的历史账务仍可查并标记删除状态。搜索、质量过滤、排序、全量
总计和分页全部在后端完成。用户记录物理删除但仍存在客户结算日志时，管理员仍可按稳定用户 ID
查看详情；身份显示删除标记，`current_balance=null`，不能把无法读取的当前余额显示为零。没有用户记录
且没有客户结算历史时仍返回未找到，渠道测试日志不能单独构成客户历史。

折前金额按每条消费、退款各自冻结的分组与合同倍率还原，消费正计、退款负计。模型、分组、客户和
全客户汇总保留有符号十进制中间值，到对应输出层才舍入。净额与折前净额保留符号；退款独立分组、
跨账期退款与筛选明细不得将负数截为零，保证子行与父级口径一致。优惠为折前净额减结算净额，
退款的优惠冲回同样保留符号；倍率缺失、无法拆分附加费或展示合计溢出时返回未知。
同组日志从无合同切换到合同折扣，或从合同切回无合同，须把无合同记录按有效合同倍率 `1` 参与
多折扣判断；不同倍率返回多折扣标记而非单一合同折扣。全部记录均无合同事实时不展示合同折扣。

客户查询统一使用 `customerSettlementLogs` 范围：排除原生渠道测试写入的
`type=consume + token_id=0 + token_name=模型测试 + content=模型测试` 记录，因为这些记录只有
计算费用，没有客户资金扣款。不能仅按 `token_id=0` 或日志名称排除；真实游乐场、免费调用与退款仍保留。
此规则也用于旧自助账单和使用构成接口；上游对账保留实际发生的测试调用。原始日志和余额不因此回写。

按 Token 行：`input_tokens / cache_read_tokens / cache_write_tokens / output_tokens / gross_quota / refund_quota / net_quota`。
按次行：`requests / billable_calls / refunded_calls / gross_quota / refund_quota / net_quota`。

异步任务调整行影响 Token 与费用但不重复增加逻辑请求数。净费用保留符号；跨期退款按退款日志发生时间
进入查询账期。

本地异步表达式任务的完成日志使用已接受实测与冻结条件计算 `usage_facts` 和 `matched_tier`，
不复制创建时的预算用量。预扣等于实扣时仍写零金额调整行；只有既有原子结算成功的调用负责写入，
重复补查不重复记请求或用量。创建快照保持不变。资金与日志可位于不同数据库，这不构成跨库原子保证。

### 7.2 上游平台用量

平台侧用量从日志数据库按 `period + channel_id + provider_model + billing_mode` 聚合。Provider 模型优先
读取请求发生时已持久化的上游模型快照；缺失时标记无法映射，不从当前 `model_mapping` 反推历史 Provider
模型。服务端只组合同一业务键下的平台用量、`ProviderBillingDiscount` 和数据质量。按 Token 行返回平台
记录的输入、缓存读写与输出 Token；按次行返回平台记录的请求数和计费次数。

原生渠道测试历史记录缺少缓存写入总量及 TTL 字段且不是按次计费时，返回
`data_quality.cache_write_unavailable_requests` 并将质量标为 `partial`；页面和 CSV 的缓存写入栏显示
“未记录”，已知部分仍保留在数值字段中。显式记录为 0 不属于缺失。普通日志查询为同类历史测试动态
增加公开 `cache_write_unavailable` 展示标记；这是只读响应投影，不回写日志。新测试保存已有 usage
中的总量、TTL 和语义；不从当前价格或费用反推历史缓存写入量。

上游汇总读取消费行，以及能确认属于 Task 结算调整的退款行；后者可能承载完成用量，按实测正计，
不增加请求次数。识别依据为 Task ID 与明确 adjustment 事件，或旧日志同时具备实扣和预扣字段；
明确 refund/create 事件不作为退款行上的完成用量。普通客户退款不冲减 Provider 用量，也不生成上游退款次数。

### 7.3 上游 URL 汇总投影

管理员第三 Tab 按「渠道当前基础 URL → 上游模型 × 计费方式 → 渠道明细」三级归组，聚合与
`upstream-summary` 相同的日志行和解析口径，因此 URL 组总量等于所属渠道总量之和。归组只服务账单
展示，不建立供应商身份，不参与路由、履约、计费或结算。

- 归组键是渠道当前配置基础 URL 的规范化形式：仅折叠协议/主机大小写、协议默认端口和路径末尾斜杠；
  协议、非默认端口和基础路径参与身份，不只按域名合并；编码斜杠 `%2F` 不转成路径分隔符，
  IPv6 主机保留方括号。
- URL 缺失、不可解析、含凭据、查询参数或片段时视为无法安全识别：不展示敏感部分，也不在删除这些
  部分后合并，而是按渠道单独保留归组；已删除渠道同样按渠道单独保留并标记删除状态。空 `base_url`
  继承 `GetBaseURL` 的渠道类型默认地址语义。
- 上游模型身份未知的 fallback 行不与已确认模型混并；同一上游模型按 token / per_call / unknown
  计费方式分行；模型数按模型身份（包括是否 fallback）计，不按计费方式行数计；合并行不构造指向单个渠道的伪明细入口，下钻仍通过真实渠道明细行完成。
- 该投影完全只读：不物化月度折扣、不写审计、不回写日志。数据质量标记逐层聚合，未知不显示为零。
  总体质量只聚合当前 URL 筛选范围；三级行均展示请求数。页面与 CSV 注明「按渠道当前基础 URL 归组」；CSV 只导出渠道明细叶行，不重复导出父行合计。
响应不包含供应商 Token、次数、金额、退款、差异率或处理状态。平台只对账已持久化的最终用量，不假设
失败重试成本为零；是否新增“Provider 尝试用量事实”须在真实 Provider 账单验证后单独评审。

## 8. 前端边界

普通用户从 `/billing` 进入自己的账单，固定 `api_key` 维度，看不到客户数量、客户搜索或上游控件；
管理员从 `/admin/billing?section=customer|upstream|upstream_url` 进入，路由与接口均要求
`AdminAuth`。三个 Tab 共用
数据库状态提示，但请求不同接口、使用不同响应类型；禁止把客户金额与上游金额合并成同一汇总对象。
管理员访问 `/billing` 时看到的仍只是自己的账单，不自动跳转全客户列表。

前端只负责格式化、展开模型行和导航；金额、Token、计费次数和数据质量均由后端返回。每次切换 Tab、
用户、账期、渠道、API Key、模型或计费方式都调用对应聚合接口。上游渠道和模型筛选作为后端聚合
条件，表格父行、模型行、数据质量和前端 CSV 均使用同一份筛选响应；全量响应只额外保留筛选选项。
筛选查询加载或失败期间保留控件并禁用导出，不能拿未筛选渠道总计搭配筛选后子行。API Key
使用稳定 `token_id`；合并多个客户模型的上游行只下钻到渠道账期，不伪造单模型条件。

客户列表把最终费用与资金流水分开展示：结算原价、优惠、净结算金额相邻排列；累计扣减和累计退回
列于其后。累计扣减包含预扣，累计退回包含结算退差额及其他退款，不能命名为最终实付消费。
页面可见说明同时解释“结算原价 − 优惠 = 净结算金额”与“累计扣减 − 累计退回 = 净结算金额”。
计费方式未识别的历史记录数量直接使用后端质量计数，部分数据不等同于费用缺失，未知价格仍显示未知。
详情按非零计数列出计费方式未识别、用量不可读、缓存写入不可用、历史价格不可用及上游模型身份缺失，
不将所有情况解释为快照冲突或提示刷新。未知计费分类不展示按次计费的零值用量。
渠道名称来自当前主数据库的渠道记录；记录缺失时显示本地化编号和历史费用保留说明，不推测历史名称。
现存但空名称的渠道使用编号展示，不能据空名称判定记录已删除。

## 10. 架构不变量

1. 客户与上游是两套独立口径，金额与用量互不覆盖，前端不得合并为同一汇总对象。
2. 正式账单只读数据库结算事实，不按当前价格、用户折扣或上游折扣重算历史。
3. 客户退款不冒充 Provider 冲正，不生成上游退款次数或冲减平台记录的 Provider 用量。
4. 按 Token 与按次分行聚合，不混合用量单位；未知计费方式不猜测。
5. 上游月度折扣必须先持久化到主数据库再展示，使用 expected version；审计追加且不可删改。
6. 数据库缺失的历史用量、价格或折扣显示未知，不以当前配置、页面合计、Provider 金额或缓存回填。
7. 缓存可重建，从不成为账单权威，也不回填数据库。
8. 余额流水未落地前，当前余额只直读主数据库，不用日志估算期初/期末。
9. 余额换算与汇总使用定点十进制，禁止裸 `float64 -> int` 作为账单金额转换。
10. 持久化、迁移和聚合继续兼容 SQLite、MySQL >= 5.7.8 与 PostgreSQL >= 9.6；ClickHouse 日志合同另测。
