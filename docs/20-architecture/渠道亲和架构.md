# 渠道亲和架构

本文描述显式会话规则、默认 API Key 亲和，以及可单独启用的三级亲和和渠道故障切换。以下默认亲和章节描述三级亲和关闭时的行为。

## 范围与状态

- 显式会话规则亲和是既有已发布行为：管理员按规则把匹配的请求绑定到渠道。
- 默认 API Key 亲和已实现（`service/default_channel_affinity*.go`）并通过本地三库、竞态、
  Redis 故障注入与多实例回退演练回归，**生产未发布**：开发环境对照验证了预热后串行的缓存与
  输入费用收益，但冷启动并发无可归因收益且首 token P95 上升，延迟验收未通过。发布门槛见
  [路线图](../50-planning/路线图.md)第 39 项。

## 职责与事实源

亲和缓存是尽力使用的选渠提示，不是路由合同，也不改变任何请求的可用性语义：

- 权限、模型、协议、分组、客户合同、优先级与权重过滤仍是选渠的权威；
  客户合同路由由[合同定价架构](账单计费-用户模型合同定价架构.md)定义。
- 亲和写入或读取失败不改变已完成请求的结果；无可用绑定或缓存异常时按普通选渠继续。
- 亲和使用现有客户端协议和缓存，无需数据库迁移。

## 优先级

同一请求依次应用：显式固定渠道 → 既有会话规则 → 默认 API Key 亲和。

已匹配会话规则的请求（含规则模式 `off`、规则缓存未命中和读取异常）完全沿用该规则的既有
处理，跳过默认绑定的读取和写入；满足原规则写入条件时仍按原规则建立会话绑定。

## 默认 API Key 亲和

### 触发范围

按方法与精确路径识别三个入口：`POST /v1/chat/completions`、`POST /v1/responses`、
`POST /v1/messages`。请求须走原生分发、输入自包含且未匹配任何会话规则。引用上游状态
（`previous_response_id`、`conversation`、上游文件、向量库、工具容器）的请求，转入专用
插件或任务履约的请求，WebSocket、媒体与异步入口均不进入。Responses 中按 `call_id` 在
同一请求内配对的函数调用与文本结果可以进入。只有已缓存在内存且不超过 1 MiB 的 JSON
正文参与判定；更大正文、磁盘正文与无法判定的输入沿用原路由。

### 绑定键与选渠整合

绑定键由鉴权后的 API Key 内部 ID、客户请求模型、协议入口和有效路由范围组成；
普通分组、Auto 的有序可用范围和客户合同按现有范围事实区分。同一账号的不同 Key 各自
建立绑定，缺少有效 Key ID 时走普通选渠。键不含原始 Token、请求正文或状态引用。

命中绑定只在本次首次尝试会使用的**有效优先级层**内作为偏好择优：Auto 先确定首个有候选
的分组，合同先汇集授权候选；数据库与内存两条候选路径都接收该偏好。未命中或被停用、
移出范围的绑定按现有权重正常选渠；重试继续遵守现有可重试条件、次数和分组规则。

### 写入语义

- 只有实际成功且取得可信终态的请求可建立或刷新绑定。流式请求须有协议终态：Responses
  HTTP SSE 使用现有 `completed` 终态，仅 EOF 不写；Chat Completions 请求多个流式结果时
  须确认全部结果结束（渠道覆盖 `n` 的双向语义已回归）。
- 只更新同一首选范围及优先级层内实际成功的渠道；跨层或跨 Auto 分组的重试成功不覆盖仍有效
  的首选绑定。全局「切换成功后更新会话绑定」关闭时，换渠成功保留旧绑定，无旧绑定时此次不建。
- 首次并发不等待绑定写入；后完成的同范围、同层有效成功请求可覆盖先写入的绑定。

### 缓存与容量

- 默认绑定使用独立命名空间 `new-api:default_channel_affinity:v1`，与显式规则的本地 LRU
  隔离；本地每进程最多 10,000 条，条目有效期缺省一小时。绑定键从账号切换到 Key 后，旧
  账号键留待过期或全量清理。
- Redis 读写各限时 10 毫秒，建立 TLS 连接也受本次操作期限约束；读取超时或失败立即走普通
  选渠且当次不写绑定。后台「清空全部渠道亲和性缓存」同时覆盖显式规则与默认两个命名空间，
  按规则清理的范围不变。管理统计以 `default_user_entries` 单独披露默认键规模。
- 共享 Redis 实例的键前缀不提供实例内配额；部署须按活跃 Key、模型、范围和 TTL 评估新增
  键量与淘汰策略。

## 约束与取舍

- 渠道 ID 稳定不等于上游缓存域稳定：渠道内多 Key 轮换、第三方网关二次分发、输入前缀变化
  和缓存过期都会产生未命中；亲和收益只对本平台直接管理的渠道落点可下结论。
- 亲和与上游提示词缓存是两层机制：Anthropic 缓存域依平台而异且需要稳定前缀；OpenAI
  Responses 的 WebSocket 连接内状态断线后消失，同渠道重连无法恢复。
- 首次并发按现有权重分散，允许绑定建立前落点多渠道；冷启动并发阶段不承诺亲和收益。
- 单一大流量 Key 或用户绑定可能集中上游负载。多 Key 槽位的故障证据目前用于观察。

## 故障切换与探测恢复

- 请求策略中的故障切换开关支持关闭、仅观察和按渠道 ID 灰度。灰度路径覆盖 Claude Messages、
  Chat Completions 和 Responses HTTP。严格会话按规则显式允许故障例外，内建规则默认保持严格。
  现有渠道管理负责启停。路由临时绕开按渠道配置版本、客户模型、协议操作记录，多 Key 渠道按槽位观察。
- 同一范围在 60 秒内连续三次出现真实上游 502、503、529 或连接失败时进入冷却。HTTP 样本须同时命中
  现有重试状态码；其他可归因结果打断计数。客户端取消、局部构造错误和截断的 200 流不作为故障样本。
- 可迁移请求使用经过代码登记的文本及自包含函数工具适配范围。灰度源、备用目标和恢复探测共用一个准入条件：
  OpenAI、NewAPI 或 Anthropic 适配，单 Key，渠道与全局均未开启请求透传。切换仍受现有渠道、模型、分组和客户合同约束；
  当次补试排除失败渠，同档优先。严格会话的故障例外只补试一次，且只迁移到合规备用；优先会话补试失败或找不到
  合规备用时按剩余预算继续原有重试，并尽量避开本次已失败渠道。备用以 4xx（429 除外）拒绝迁移请求时停止。
  已开始响应不重放。只有经过登记的内容、且失败尝试落在合格的灰度渠道或已由故障切换接管时，A 才改变重试决策；其他请求沿用原有重试。带上游状态引用但查不到可信归属的
  请求沿用原有路由，并且不进入绕开、补试或试用。原生 Responses 完整终态提供可校验的续接归属，按认证身份、合同
  版本和模型隔离，绑定到渠道配置版本；归属渠道在灰度范围内时请求固定该渠道，失去资格时返回
  `upstream_continuation_unavailable`。普通会话绑定不提供上游归属证明。
- 首次绕开只在现有选渠器找到合规备用后生效。处于冷却、待确认、待试用或手工绕开的渠道退出备用候选。
  找不到合规备用时仍尝试具备选渠资格的原绑定；没有显式绑定时按原有选渠，待试用渠道上的这次请求即受控试用。
  故障切换只排除和排序候选，不因候选被筛空而让原有路由可以履约的请求失败。
- Claude CLI 的 `context_management` 迁移资格来自请求策略中的「已验证迁移对」：源渠道、目标渠道和客户模型。
  保存时绑定两端渠道的当前配置版本，之后任一端配置变化即失效。两端须为单 Key Anthropic 渠道、无参数覆盖，
  按渠道模型映射解析出的上游模型须等于迁移对登记的上游模型。两端模型 ID 不同时，`source_upstream_model` 可单独登记源 ID；目标沿用 `upstream_model`。会话规则模板只能透传请求头。请求仍限无缓存指令和
  无签名历史的流式文本，只接受 `clear_thinking_20251015` 的 `keep: "all"`，目标须有匹配的 beta 头覆盖。
  网关保留原字段，补试按选中的渠道重新计算南向头。
  [Provider 验收](../99-archive/2026/11/2026-11-14-渠道亲和故障切换与探测恢复方案.md#11-claude-cli-上下文管理修复与复验2026-11-14)
- 冷却到期后复用渠道测试执行器做同协议、同模型的恢复探测。探测不经自动启停分支。完整流终态才允许受控试用。
  Azure Foundry Claude 返回 `400 / 555420` 时，恢复探测记为 `unconfirmed`，保持待确认，既不进入受控试用也不增加失败退避。
  操作员可在冷却后允许试用；试用须有安全备用和剩余预算。中断而未确认的试用只释放名额，不加长冷却；
  结果未能写入健康状态时，决策记录显示「未记录」。Redis 用原子条件更新限制同一故障范围只有一个
  在途名额，共享读取单批限时 10ms。无 Redis 时在当前进程内协调。试用完整成功后恢复新会话候选资格。
  定时探测只针对单 Key、未开请求透传且自动检测范围为真实生成的渠道，每轮最多 4 个范围；不满足时保持待确认，
  由操作员允许受控试用。
- 仅观察模式只在请求决策记录中写入「将绕开」，不改变路由；该模式没有恢复探测，冷却到期后不再报告绕开并恢复采样。受控试用的成功、失败和待确认作为独立原因记录。
  原渠道失去资格时，未登记可迁移内容的会话沿用原有选渠，故障切换不新增错误分支。
  显式会话规则缓存保持上游的 Redis 超时与日志行为。
- 已接管的同步入口在可信完整结果后写入亲和绑定。写入时比较读取的旧值，保持并发迁移的一致性。全局关闭更新
  时保留旧绑定。渠道版本变化使旧健康记录失效。灰度关闭后恢复已有路由和绑定写入路径。
- 三级亲和可在请求策略中单独启用。会话缺失或可绕开时，在现有候选层内依次尝试 API Key、用户绑定。
  认证身份、模型、协议与授权范围组成默认缓存键，现有客户合同和任务固定渠道仍优先。原生 Gemini 请求引用
  `cachedContent` 或上传文件时不进入下层绑定，沿用原有路由。某层读取失败只放弃该层及以下的偏好，
  上层已读到的绑定仍生效；任一层读取不确定时本次不写回任何层。按层清理只涉及亲和缓存，
  续接归属与恢复状态独立保留。后台可分开清理规则缓存、清理各层缓存和删除自定义规则。现存系统默认规则受保存保护。
- 故障切换与三级亲和的开关、灰度、迁移对和写回条件都读取请求策略快照。显式会话规则查找沿用 NewAPI 原有的
  全局设置；保存请求策略的瞬间，单个请求可能读到新旧两套值，影响仅限该请求的一次选渠或写回。
