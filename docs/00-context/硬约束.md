# 硬约束

## Technology

- 后端使用 Go 1.22+、Gin、GORM v2。
- 前端实现位于 `web/`，使用 React 19、TypeScript、Rsbuild、Base UI、Tailwind CSS。
- 数据库代码必须同时兼容 SQLite、MySQL >= 5.7.8、PostgreSQL >= 9.6。
- 前端包管理和脚本优先使用 Bun。

## Security

- 绝不提交密钥、Token、Cookie、真实支付凭据或生产环境配置。
- 认证、计费、额度、限流、审计相关改动必须保留可验证的行为边界。
- 受保护的项目名称、组织/作者身份、授权、署名和元数据不得删除、替换或弱化。

## Architecture

- 代码按 Router -> Controller -> Service -> Model 的分层边界推进。
- Provider relay 请求 DTO 的可选标量字段必须使用指针类型并配合 `omitempty`，保留显式零值。
- Go 业务代码的 JSON marshal/unmarshal 必须使用 `common/json.go` 中的封装。
- 涉及表达式计费前必须先读 `pkg/billingexpr/expr.md`。

## 北向合同与南向适配

**边界：** 北向是客户端可依赖的产品合同；南向是网关对 Provider、反代和中转渠道的实现适配。渠道变化不得改变北向调用方式。

### 通用规则

- 客户端可见的路径、鉴权、字段、类型、枚举、默认值、错误、响应及任务生命周期必须来自可追溯合同。来源优先级为“NEWAPI 稳定合同 -> 模型厂商官方 API”，并记录链接、版本或验证日期；第三方或渠道私有协议只能作为南向依据。
- 一个公开模型名就是一个稳定、可计费、可验证的合同 SKU。同一 SKU 只能路由到请求、响应、错误、生命周期和计费语义等价且已验证的渠道。
- 路径、鉴权、真实模型 ID、字段名、请求结构、同步/异步信封、任务 ID、状态和查询方式等渠道差异，必须由渠道配置、模型映射、能力声明及独立 converter 消化，不得要求客户端感知渠道。
- 无法证明渠道等价时，必须移出该 SKU 的选渠集合；确需拆分 SKU 时，应分别绑定渠道、模型映射、能力和价格。不得随机进入不兼容渠道，也不得用重试、删字段或内部错误掩盖合同差异。
- 北向不得透传合同外的供应商私有参数。合法字段必须完整校验和适配；不支持时返回明确 4xx/能力不支持，或保持未发布，禁止静默忽略、钳制、降级或改义。
- 拆分 SKU 不得暴露供应商请求结构。供应商真实模型 ID 只存在于渠道配置、执行快照和审计信息中；历史私有字段或枚举只能作为有期限的迁移别名，不得写入新文档或新客户端示例。

### 产品合同

- **图片：** 默认且受保障的是统一 NEWAPI 图片合同。同一产品面统一使用 `/v1/images/generations` 及 `model`、`prompt`、`image`、`size`、`n`、`response_format`、`stream` 等标准字段；各 SKU 可声明不同能力和值域，但仍使用同一接口族、字段语义、错误信封和任务查询方式。
- **图片原生协议：** 供应商原生接口是独立、可选合同，仅在上游真实支持、网关已转发并完成渠道验证时开放；不承诺仅替换 `model` 即可跨供应商迁移，不得模拟原生协议或反向改变统一图片合同。
- **视频：** 当前只发布 Seedance、Kling 和即梦，并分别遵循 ModelArk、Kling、即梦官方完整合同。不同模型可以采用不同官方协议；同一 SKU 在直连、反代和中转渠道间必须保持合同不变。不得借 `metadata`、`extra` 或任意参数透传绕过合同。
- **下架视频：** OpenAI 视频不得重新接入、出现在模型发现或参与新任务、计费和分发。`openai_videos` 仅用于存量读取，存量退出后移除公开路由。
- **素材库：** 素材 CRUD、授权、幂等、用户隔离和生命周期由统一、供应商中立的平台合同治理。客户端只使用平台资源 ID 和 `asset://` 引用；上游账号、资源 ID、路径、鉴权、状态及实现名称只存在于南向。
- **素材引用：** 视频请求必须在对应官方合同的媒体字段中提交 `asset://`。网关须在选渠前校验所有权、状态、授权、模型、渠道账号及多素材渠道交集，并在每次南向尝试前改写为该渠道账号的上游引用，不得改变视频合同。

## 最小入侵

- 本地开发以减少未来上游同步的冲突、成本和风险为最高优先级。
- 新类型、常量、适配器、独立测试及大部分新增逻辑原则上放入新文件；现有热路径只保留必要的单行调用或极窄分支。
- 可接受新文件内少量、局部的重复，不得为抽象复用而扩写、重排或重构上游文件。
- 禁止随功能改动进行无关的重命名、移动、格式化、抽象提取或顺手重构。只有在无法安全实现、无法满足既有接口或无法通过必要验证时，才可扩大现有文件改动，并必须明确记录原因。

## 上游代码同步

- 任何从最上游仓库、上游主分支或上游发布版本接取代码的任务，都必须遵循 `docs/30-engineering/上游代码合并指南.md`。
- 除明确批准的首页、首页专属交互、纯视觉样式、主题、品牌资源及无业务语义的部署配置外，业务与运行逻辑必须完整以上游为准。上游业务文件按文件整体覆盖，并同步新增、删除、重命名和目录调整；禁止挑选代码块或暗留本地旧实现。
- 每次同步必须先列出本地保留白名单；未列入者按上游覆盖，新增例外须明确批准并写入合并记录。
- 本地业务诉求与上游冲突时，先完整采用上游实现；本地诉求必须独立评估并优先提交上游，不得在同步过程中形成隐性本地分叉。
- 每次同步必须检查数据库 Model、迁移、索引、约束、默认值、回填和数据语义，并验证三种数据库。结论不明、迁移未验证或仍有未批准差异时，不得宣布完成或发布。
