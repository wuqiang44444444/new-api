# 硬约束

## Technology

- 后端使用 Go 1.22+、Gin、GORM v2。
- 前端实现位于 `web/`，使用 React 19、TypeScript、Rsbuild、Base UI、Tailwind CSS。
- 数据库代码必须同时兼容 SQLite、MySQL >= 5.7.8、PostgreSQL >= 9.6。
- 前端包管理和脚本优先使用 Bun。

## Security

- 绝不提交密钥、Token、Cookie、真实支付凭据或生产环境配置。
- 认证、计费、额度、限流、审计相关改动必须保留可验证的行为边界。
- 受保护的项目名称、组织/作者身份、授权、署名和元数据不得删除、替换或弱化。

## Architecture

- 代码按 Router -> Controller -> Service -> Model 的分层边界推进。
- Provider relay 请求 DTO 的可选标量字段必须使用指针类型并配合 `omitempty`，保留显式零值。
- Go 业务代码的 JSON marshal/unmarshal 必须使用 `common/json.go` 中的封装。
- 涉及表达式计费前必须先读 `pkg/billingexpr/expr.md`。

## Link 合同

**边界：** Link 合同是由项目负责人明确决定新增、通过本地代码修改实现并在代码中显式注册的扩展合同。它不是全站路由的总分类，也不是对 NEWAPI 原生合同的重命名或替代。Link 合同的范围等于“已显式编码和注册的 Link 合同集合”，不通过 Ability、候选渠道、模型发现、运行时能力探测或“是否像原生”等启发式条件推断。在该显式集合内，Link 合同是客户可依赖的端到端产品合同，由客户 API、SKU 能力、任务与计费、Link 资源和渠道适配协议组成。渠道适配协议是其实现子合同，只定义网关如何调用 Provider、反代或中转渠道，不得反向扩张公开能力。术语定义见 [术语表](术语表.md)。

### 显式代码注册与原生优先

- Link 合同只能由一次明确的代码变更创建。每次新增必须同时提供唯一合同 ID、版本、显式代码注册项、路由/DTO/converter 或生命周期扩展、计费接线、回归测试和同步文档。例如，经明确代码扩展和注册的 Moxing Seedance 合同属于 Link 合同。
- 仅增加 Channel 数据、模型名、Ability、分组、优先级、权重、模型映射、参数覆盖或价格配置，不会产生 Link 合同。未在代码中显式注册的模型或渠道，一律不属于 Link 合同。
- NEWAPI 原生合同永远优先。已由 NEWAPI 原生完整支持的渠道或模型不得另建 Link 合同；这是新增代码前的治理约束，不是运行时判定 Link 身份的算法。
- 已被 NEWAPI 原生支持的渠道或模型，不得为其新增并行或包装 Router、DTO、converter、能力注册、
  公开模型别名、`client_protocol`、任务生命周期、历史读取、fallback、兼容中间件或计费体系。原生
  能力继续使用上游既有 relay、Ability、优先级、权重、模型映射与计费逻辑，Link 合同不得介入或
  收紧其入口和候选渠道。
- 如后续 NEWAPI 上游已原生提供等价能力，优先删除本地未发布 Link 实现并迁回原生合同。只有部署
  核查证明存在已发布合同或在途数据时，才可先提出独立、限期且可删除的迁移方案；不得预先为并不
  存在的历史数据建设兼容路径。

### 通用规则

- 属于 Link 扩展的客户端可见路径、鉴权、字段、类型、枚举、默认值、错误、响应及任务生命周期必须来自可追溯的 Link 合同。来源优先级为“NEWAPI 原生稳定合同 -> 模型厂商官方 API”，并记录链接、版本或验证日期；第三方或渠道私有协议只能作为渠道适配依据。
- 一个 Link 公开模型名就是一个稳定、可计费、可验证的合同 SKU。同一 Link SKU 只能路由到请求、响应、错误、生命周期和计费语义等价且已验证的渠道；该规则不得外溢到 NEWAPI 原生 SKU 的通用 relay 选渠逻辑。
- Link SKU 的版本化能力声明是字段、值域、缺省值、媒体组合、查询、取消、删除、内容下载和
  Link 资源支持语义的唯一权威。Provider 实现由不可变的 `link_implementation_id + version`
  代码注册，渠道显式绑定精确版本；profile 只描述协议适配形状。Ability 发布时和运行时都必须
  fail closed 地排除未登记、不完整或不等价候选，不能由随机选中的渠道改变公开合同。
- Ability、候选渠道和能力证明都不参与“某能力是否属于 Link 合同”的判定；Link 身份只由显式代码注册确定。在 Link 合同已注册之后，Ability 才表示“某渠道可以进入该 Link SKU 的执行选渠集合”，合同资格证明则只用于发布门禁和运行时过滤。
- Link 合同的合格候选耗尽时必须 fail closed，返回稳定的 SKU 暂不可用错误；不得静默降级、转入 NEWAPI 原生宽松候选集、随机选择未验证渠道或改变公开 SKU 语义。
- 路径、鉴权、真实模型 ID、字段名、请求结构、同步/异步信封、任务 ID、状态和查询方式等渠道差异，必须由渠道配置、模型映射、能力声明及独立 converter 消化，不得要求客户端感知渠道。
- 无法证明渠道等价时，必须移出该 SKU 的选渠集合；确需拆分 SKU 时，应分别绑定渠道、模型映射、能力和价格。不得随机进入不兼容渠道，也不得用重试、删字段或内部错误掩盖合同差异。
- 客户端不得透传合同外的供应商私有参数。合法字段必须完整校验和适配；不支持时返回明确 4xx/能力不支持，或保持未发布，禁止静默忽略、钳制、降级或改义。
- 拆分 SKU 不得暴露供应商请求结构。供应商真实模型 ID 只存在于渠道配置、执行快照和审计信息中；历史私有字段或枚举只能作为有期限的迁移别名，不得写入新文档或新客户端示例。

### 计费与 exposure 一致性

- Link 合同不得建立与 NEWAPI 并行的客户计费账本。价格、分组倍率、预扣、结算、退费、Token/用户额度、消费日志和 channel `used_quota` 必须复用 NEWAPI 原生 quota 单位与资金生命周期；Link 只能冻结必要的合同和计费快照。
- 客户退费与平台 exposure 必须分账。客户资金仍按 NEWAPI 的预扣—差额结算—退费逻辑处理；若退费时上游成本可能已发生，必须额外写入不可变、幂等的 exposure 事实，不得通过不退客户额度或篡改消费日志来隐藏平台损失。
- 为保持与 NEWAPI 原生计费统计一致，exposure 自动门禁的主额度指标使用
  `customer_quota_released`，按 channel、Link 公开 SKU、实现 ID/version、upstream profile、reason
  和滚动时间窗口聚合，并同时保留次数、速率和 unknown 转 exposure 比例。该 quota 是与客户计费
  一致的运营风险代理指标，不得表述为已确认的供应商实际成本或会计 P&L。
- `provider_amount` 和 `provider_currency` 只用于可取得时的上游账单对账；未知金额保持空值，不得用客户 quota 冒充供应商成本，也不得将不同币种未换算地直接求和。若未来需要会计级 P&L，必须另行建立有汇率时点、供应商账单来源和冲销规则的对账设计，不得污染 NEWAPI quota 账本。
- 已注册 Link 合同的执行渠道必须受 exposure 策略覆盖；策略缺失、预算耗尽或达到自动停用阈值时必须 fail closed，不得降级到未验证渠道。若要求真正的并发硬上限，必须在发送上游请求前按冻结 quota 估值原子预留 exposure budget，终态后再幂等释放或结转；事后统计与熔断不得宣称为无超调的硬上限。

### 产品合同

- **图片：** 默认且受保障的是统一 NEWAPI 图片合同。同一产品面统一使用 `/v1/images/generations` 及 `model`、`prompt`、`image`、`size`、`n`、`response_format`、`stream` 等标准字段；各 SKU 可声明不同能力和值域，但仍使用同一接口族、字段语义、错误信封和任务查询方式。
- **图片原生协议：** 供应商原生接口是独立、可选合同，仅在上游真实支持、网关已转发并完成渠道验证时开放；不承诺仅替换 `model` 即可跨供应商迁移，不得模拟原生协议或反向改变统一图片合同。
- **图片模型的 Chat 兼容合同：** 对已验证同时支持 `/v1/chat/completions` 的图片模型与渠道，必须保留该路径的独立 OpenAI 兼容合同。不得仅因模型具有图片能力或平台提供统一图片接口，就将 Chat 请求硬编码改写、重定向或强制发送到 `/v1/images/generations`。选渠道、请求转换和 Provider 路径必须以客户端实际请求路径及已验证的渠道能力为准；新增图片能力应使用独立门禁或适配文件，遵循最小入侵，不改变既有 Chat 请求体、响应、计费和重试语义。
- **视频：** NEWAPI rc23 原生 OpenAI Videos 与旧版平台视频链路以上游代码为唯一权威，不建立本地
  “恢复”“共存”或“兼容”合同。Seedance、Kling 和即梦 Link SKU 分别遵循 ModelArk、Kling、即梦
  官方完整合同；同一 Link SKU 在直连、反代和中转渠道间必须保持合同不变。
- **原生与 Link 隔离：** 显式登记的 Link SKU 只通过其发布的类型化路由、DTO、capability 和实现
  候选集提供服务。隔离发生在 Link 注册和选渠边界；不得为了识别或拒绝 Link SKU 而修改
  `/v1/videos`、`/v1/videos/:video_id/remix`、`/v1/video/generations` 等原生入口，也不得给原生
  任务冻结 Link implementation/capability 或增加本地协议推断。
- **素材库：** 素材 CRUD、授权、幂等、用户隔离和生命周期由统一、供应商中立的平台合同治理。客户端引用平台托管素材时只使用平台资源 ID 和 `asset://ast_xxx`；上游账号、资源 ID、路径、鉴权、状态及实现名称只存在于 Provider。
- **请求级媒体：** 模型官方合同明确允许且公开 SKU 声明支持时，视频请求可以在官方媒体字段中直接提交 HTTP/HTTPS URL 或 Data URL。它们只属于当前请求，不进入平台素材 CRUD、绑定、迁移或授权生命周期；网关不主动抓取、长期保存或把渠道凭据附加到这些地址，也不承诺替代 Provider 的内容安全判断。
- **平台素材引用：** 使用 `asset://ast_xxx` 时，网关须在选渠前校验所有权、状态、授权、模型、渠道账号及多素材渠道交集，并在每次 Provider 尝试前改写为该渠道账号的上游引用，不得改变视频合同。未知上游素材 ID 不得直接作为平台素材引用；平台已识别为真人或需要授权、撤回、审计能力的素材必须走托管路径。
- **真人直接媒体边界：** 没有内容分类或审核能力时，系统不能仅凭 URL/Data URL 技术判定其是否包含真人，不得把“真人直接媒体已被平台自动阻断”写成已实现保证。未开放真人能力时通过分组、条款、受控业务流程和平台托管素材状态执行；需要技术强制时，必须先增加可验证分类/审核能力或禁止全部无法证明类型的直接媒体。
- **真人授权线性化：** 真人托管素材的一次任务使用，以发送前 `sending` 事务内锁定授权并写入
  attempt—任务—素材—授权 reservation 的提交作为“已接受”时点；撤回事务必须锁定同一授权
  行。撤回先提交则不得发送上游请求，reservation 先提交则该请求属于可索引的在途任务并进入
  撤回取消/清理流程。任务内容与派生帧每次回源仍须回查授权，不得用有撤回延迟的缓存削弱
  fail-closed 保证。
- **媒体路径组合：** `asset://ast_xxx` 与请求级 URL/Data URL 是否允许在同一请求中混用，必须由公开 SKU 显式声明；未声明时拒绝，不能根据最终渠道临时决定。
- **共享 Task 创建未知：** 显式接入该安全边界的 Link 视频和持久化媒体图片调用，必须在发送
  Provider 请求前建立耐久 create attempt，并在同一事务完成资金 hold 与 `sending` 标记。发送后
  的模糊结果不得自动退款、换渠道或重发；必须有界对账，到期释放客户资金并记录平台 exposure。
  该规则不从“可能异步”或路径名称自动扩张到 NEWAPI 原生协议；素材、真人认证等控制面资源继续
  使用各自状态机。
- **轮询合同违例：** 无效 JSON、未知状态、任务 ID 不匹配或暂缺结果只能证明本次查询响应不可采信，不能直接证明业务任务失败，应进入有界对账并保持计费 pending。已取得可信终态响应但确定违反交付上限或安全合同的结果可以作为平台不可交付终态退款，并单独记录供应商成本暴露；上游明确业务失败和合同 SLA 到期分别进入对应终态。

## 最小入侵

- 本地开发以减少未来上游同步的冲突、成本和风险为最高优先级。
- 新类型、常量、适配器、独立测试及大部分新增逻辑原则上放入新文件；现有热路径只保留必要的单行调用或极窄分支。
- 可接受新文件内少量、局部的重复，不得为抽象复用而扩写、重排或重构上游文件。
- 禁止随功能改动进行无关的重命名、移动、格式化、抽象提取或顺手重构。只有在无法安全实现、无法满足既有接口或无法通过必要验证时，才可扩大现有文件改动，并必须明确记录原因。

## 上游代码同步

- 任何从最上游仓库、上游主分支或上游发布版本接取代码的任务，都必须遵循 `docs/30-engineering/上游代码合并指南.md`。
- 除明确批准的首页、首页专属交互、纯视觉样式、主题、品牌资源及无业务语义的部署配置外，业务与运行逻辑必须完整以上游为准。上游业务文件按文件整体覆盖，并同步新增、删除、重命名和目录调整；禁止挑选代码块或暗留本地旧实现。
- 面向用户的首页、首页专属交互和 Logo、favicon、Apple Touch Icon 等部署品牌资源以本地定制为准，是每次上游同步必须保留的固定白名单。上游发生前端目录迁移、资源重命名或入口文件重写时，必须把本地定制迁移到新入口，不得以任何上游默认首页或默认品牌资源覆盖。
- 本地品牌资源使用独立文件名，入口和运行时默认值必须显式指向这些文件；每次上游同步后必须检查首页、页头、登录页、页脚、错误页、浏览器 favicon 与 Apple Touch Icon，并验证服务端未配置自定义 Logo 时仍显示本地默认品牌。
- 每次同步必须先列出本地保留白名单；未列入者按上游覆盖，新增例外须明确批准并写入合并记录。
- 本地业务诉求与上游冲突时，先完整采用上游实现；本地诉求必须独立评估并优先提交上游，不得在同步过程中形成隐性本地分叉。
- 每次同步必须检查数据库 Model、迁移、索引、约束、默认值、回填和数据语义，并验证三种数据库。结论不明、迁移未验证或仍有未批准差异时，不得宣布完成或发布。
