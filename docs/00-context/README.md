# 00-context — 项目上下文

## 目标

让维护者在进入产品与架构细节前，先理解项目为何存在、服务谁、必须满足什么需求，以及哪些边界
绝对不能突破。

## 放什么

- 项目定位、目标用户、核心价值和明确非目标；
- 稳定的产品需求与事实来源；
- 跨产品、架构、工程和运维都必须遵守的硬约束；
- 当前文档使用的核心术语及其边界。

## 当前文档

1. [硬约束](硬约束.md)：任何任务首先核对的禁止事项与不变量。
2. [术语表](术语表.md)：NEWAPI 原生能力、Link 服务合同、客户模型、SKU、实现和资源等概念。
3. [项目简报](项目简报.md)：项目定位、用户、价值和范围。
4. [需求清单](需求清单.md)：产品必须提供的能力与非功能要求。

## 不放什么

- 用户操作流程和可观察验收，放入 `10-product/`；
- 系统结构、状态机、持久化和架构取舍，放入 `20-architecture/`；
- 命令、编码规范和接入步骤，放入 `30-engineering/`；
- 部署、监控、灰度和处置步骤，放入 `40-operations/`；
- 对外营销文案和 UI 方案，分别放入 `60-marketing/`、`90-ui-ux/`；
- 临时分析、计划和实施记录，放入 `50-planning/`、`80-dev/`。

## 编写要求

- 只记录当前有效的背景、需求、术语和硬边界，不写会议或实施流水；
- 约束必须短、明确、可验证，详细机制通过链接交给架构或工程文档；
- 产品承诺与“代码已存在”“真实 Provider 已验证”“生产已发布”分开表述；
- 不复制供应商协议、数据库字段清单、运维命令或页面交互细节。
